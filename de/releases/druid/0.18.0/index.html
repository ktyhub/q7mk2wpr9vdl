Druide Druide-0.18.0

Apache Druid 0.18.0 enthält über 200 neue Funktionen, Leistungsverbesserungen, Fehlerbehebungen und wichtige Dokumentationsverbesserungen von 42 Mitwirkenden. Sehen Sie sich die vollständige Liste der Änderungen und alles, was mit dem Meilenstein markiert ist an.

<a name="new-features" href="#new-features">#</a> Neue Funktionen

<a name="join" href="#join">#</a> Treten Sie dem Support bei

Join ist eine Schlüsseloperation in der Datenanalyse. Vor 0.18.0 unterstützte Druid einige Join-bezogene Funktionen, wie zum Beispiel Lookups oder Semi-Joins in SQL. Allerdings waren die Anwendungsfälle für diese Funktionen ziemlich begrenzt und bei anderen Join-Anwendungsfällen mussten Benutzer ihre Datenquellen denormalisieren, wenn sie Daten erfassen, anstatt sie zum Zeitpunkt der Abfrage zu verknüpfen, was zu einem explodierenden Datenvolumen und einer langen Erfassungszeit führen konnte. Druid 0.18.0 unterstützt zum ersten Mal in seiner Geschichte echte Joins. Druid unterstützt derzeit INNER-, LEFT- und CROSS-Joins. Für native Abfragen wurde die Datenquelle join neu eingeführt, um eine Verknüpfung zweier Datenquellen darzustellen. Derzeit ist nur der left-deep Join zulässig. Das bedeutet, dass für die linke Datenquelle nur eine table- oder eine andere join-Datenquelle zulässig ist. Für die richtige Datenquelle sind die Datenquellen lookup, inline oder query zulässig. Beachten Sie, dass die Verknüpfung von Druid-Datenquellen noch nicht unterstützt wird. Es sollte nur eine table-Datenquelle in derselben Join-Abfrage geben. Druid SQL unterstützt auch Joins. Unter dem Deckmantel werden SQL-Join-Abfragen in eine oder mehrere native Abfragen übersetzt, die Join-Datenquellen enthalten. Weitere Einzelheiten zur SQL-Übersetzung und Best Practices zum Schreiben effizienter Abfragen finden Sie unter Abfrageübersetzung. Wenn eine Join-Abfrage ausgegeben wird, bewertet der Broker zunächst alle Datenquellen mit Ausnahme der Basisdatenquelle, die die einzige table-Datenquelle in der Abfrage ist. Die Auswertung kann die Ausführung von Unterabfragen für query-Datenquellen umfassen. Sobald der Broker alle Nicht-Basisdatenquellen auswertet, ersetzt er sie durch inline-Datenquellen und sendet die neu geschriebene Abfrage an Datenknoten (weitere Einzelheiten finden Sie im Abschnitt „Abfrage-Inlining in Brokern“ weiter unten). Datenknoten verwenden den Hash-Join, um Join-Abfragen zu verarbeiten. Sie erstellen eine Hash-Tabelle für jede nicht-primäre Blattdatenquelle, sofern diese nicht bereits vorhanden ist. Beachten Sie, dass derzeit nur die Datenquelle lookup über eine vorgefertigte Hash-Tabelle verfügt. Weitere Informationen zur Ausführung von Join-Abfragen finden Sie unter Abfrageausführung. Verknüpfungen können die Leistung Ihrer Abfragen beeinträchtigen. Im Allgemeinen können alle Abfragen einschließlich Verknüpfungen langsamer sein als entsprechende Abfragen für eine denormalisierte Datenquelle. Die Funktion LOOKUP könnte eine bessere Leistung erbringen als Verknüpfungen mit Suchdatenquellen. Weitere Informationen zur Leistung von Join-Abfragen und zukünftige Pläne zur Leistungsverbesserung finden Sie unter Join-Leistung. https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> Abfrage-Inlining in Brokern

Druid ist jetzt in der Lage, eine verschachtelte Abfrage durch Inlining von Unterabfragen auszuführen. Jede Art von Unterabfrage kann über jeder anderen Art liegen, wie im folgenden Beispiel:

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

Um diese Abfrage auszuführen, wertet der Broker zunächst die Blatt-GroupBy-Unterabfrage aus. Es sendet die Unterabfrage an Datenknoten und sammelt das Ergebnis. Das gesammelte Ergebnis wird im Broker-Speicher materialisiert. Sobald der Broker alle Ergebnisse für die GroupBy-Abfrage gesammelt hat, schreibt er die TopN-Abfrage neu, indem er das Blatt „GroupBy“ durch eine Inline-Datenquelle ersetzt, die das Ergebnis der GroupBy-Abfrage enthält. Schließlich wird die neu geschriebene Abfrage an Datenknoten gesendet, um die topN-Abfrage auszuführen.

<a name="query-laning" href="#query-laning">#</a> Abfrage-Laning und Priorisierung

Wenn Sie mehrere Abfragen heterogener Arbeitslasten gleichzeitig ausführen, möchten Sie möglicherweise manchmal die Ressourcenverpflichtung für eine Abfrage basierend auf ihrer Priorität steuern. Sie möchten beispielsweise die Ressourcen begrenzen, die weniger wichtigen Abfragen zugewiesen sind, damit wichtige Abfragen rechtzeitig ausgeführt werden können, ohne durch weniger wichtige Abfragen unterbrochen zu werden. Mit Query Laning können Sie die Kapazitätsauslastung für heterogene Abfrage-Workloads steuern. Beim Laning untersucht und klassifiziert der Broker eine Anfrage, um sie einer „Lane“ zuzuordnen. Für Lanes gelten Kapazitätsgrenzen, die vom Broker durchgesetzt werden und mit denen sichergestellt werden kann, dass ausreichend Ressourcen für andere Lanes oder für interaktive Abfragen (ohne Lane) verfügbar sind, oder um den Gesamtdurchsatz für Abfragen innerhalb der Lane zu begrenzen. Die automatische Abfragepriorisierung bestimmt die Abfragepriorität basierend auf der konfigurierten Strategie. Die schwellenwertbasierte Priorisierungsstrategie wurde hinzugefügt; Es senkt automatisch die Priorität von Abfragen, die einen konfigurierbaren Satz von Schwellenwerten überschreiten, z. B. wie weit die Daten in der Vergangenheit liegen, wie groß ein Intervall ist, das eine Abfrage abdeckt, oder wie viele Segmente an einer Abfrage beteiligt sind. Weitere Einzelheiten finden Sie unter Abfragepriorisierung und Laning. https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

Neue Dimension in Abfragemetriken

Da eine native Abfrage, die Unterabfragen enthält, Teil für Teil ausgeführt werden kann, wurde ein neuer subQueryId eingeführt. Jede Unterabfrage hat unterschiedliche subQueryIds, aber dasselbe queryId. Der subQueryId ist als neue Dimension in Abfragemetriken verfügbar.

Neue Konfiguration

Eine neue druid.server.http.maxSubqueryRows-Konfiguration steuert die maximale Anzahl der im Broker-Speicher materialisierten Zeilen. Weitere Informationen finden Sie unter Abfrageausführung. https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> SQL-Gruppierungssätze

GROUPING SETS wird jetzt unterstützt, sodass Sie mehrere GROUP BY-Klauseln in einer GROUP BY-Klausel kombinieren können. Diese GROUPING SETS-Klausel wird intern mit subtotalsSpec in die groupBy-Abfrage übersetzt. Die LIMIT-Klausel wird jetzt nach subtotalsSpec und nicht mehr auf jeden Gruppierungssatz angewendet. https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> Dynamische SQL-Parameter

Druid unterstützt jetzt dynamische Parameter für SQL. Um dynamische Parameter zu verwenden, ersetzen Sie jedes Literal in der Abfrage durch ein Fragezeichen (?). Diese Fragezeichen stellen die Stellen dar, an denen die Parameter zur Ausführungszeit gebunden werden. Weitere Einzelheiten finden Sie unter Dynamische SQL-Parameter. https://github.com/apache/druid/pull/6974

<a name="important-changes" href="#important-changes">#</a> Wichtige Änderungen

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments ist standardmäßig deaktiviert

applyLimitPushDownToSegments wurde in 0.17.0 hinzugefügt, um die Grenzwertauswertung auf abfragbare Knoten zu verschieben und so die Ergebnisse während des Segmentscans für groupBy v2 einzuschränken. Dies kann zu Leistungseinbußen führen, wie in https://github.com/apache/druid/issues/9689, gemeldet, wenn viele Segmente an der Abfrageverarbeitung beteiligt sind. Dies liegt daran, dass „Limit push down to segment scan“ einen Aggregationspuffer pro Segment initialisiert, dessen Overhead nicht vernachlässigbar ist. Aktivieren Sie diese Konfiguration nur, wenn Ihre Abfrage eine relativ kleine Anzahl von Segmenten pro Verlaufs- oder Echtzeitaufgabe umfasst. https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> Brüllende Bitmaps als Standard

Druid unterstützt zwei Bitmap-Typen, nämlich Roaring und CONCISE. Da Roaring-Bitmaps ein besseres Out-of-Box-Erlebnis bieten (im Allgemeinen schnellere Abfragegeschwindigkeit), wird der Standard-Bitmap-Typ jetzt auf Roaring-Bitmaps umgestellt. Weitere Einzelheiten zu Bitmaps finden Sie unter Segmentkomprimierung. https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> Das Verhalten komplexer Metriken ändert sich zum Zeitpunkt der Aufnahme, wenn die SQL-kompatible Nullverarbeitung deaktiviert ist (Standardmodus).

Wenn die SQL-kompatible Nullbehandlung deaktiviert ist, hat sich das Verhalten der Aggregation komplexer Metriken zum Zeitpunkt der Aufnahme geändert und stimmt jetzt mit dem Verhalten zum Zeitpunkt der Abfrage überein. Die komplexen Metriken werden zu den Standardwerten 0 für Nullen aggregiert, anstatt sie während der Aufnahme zu überspringen. https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> Syntaxänderung des Array-Ausdrucks

Der Druid-Ausdruck unterstützt jetzt typisierte Konstruktoren zum Erstellen von Arrays. Arrays können mit einem expliziten Typ definiert werden. Beispielsweise erstellt <LONG>[1, 2, null] ein Array vom Typ LONG, das 1, 2 und null enthält. Beachten Sie, dass Sie ein Array auch ohne expliziten Typ erstellen können. Beispielsweise ist [1, 2, null] immer noch eine gültige Syntax zum Erstellen eines äquivalenten Arrays. In diesem Fall leitet Druid den Array-Typ aus seinen Elementen ab. Diese neue Syntax gilt auch für leere Arrays. <STRING>[], <DOUBLE>[] und <LONG>[] erstellen jeweils ein leeres Array vom Typ STRING, DOUBLE und LONG. https://github.com/apache/druid/pull/9367

<a name="pending-segments-cleanup" href="#pending-segments-cleanup">#</a> Die Bereinigung ausstehender Segmente wird standardmäßig aktiviert

Die Tabelle pendingSegments im Metadatenspeicher wird verwendet, um eindeutige neue Segment-IDs für Anhängeaufgaben wie Kafka/Kinesis-Indizierungsaufgaben oder Stapelaufgaben im Anhängemodus zu erstellen. Die automatische Bereinigung ausstehender Segmente wurde in 0.12.0 eingeführt, war jedoch vor 0.18.0 standardmäßig deaktiviert. Diese Konfiguration ist jetzt standardmäßig aktiviert. https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> Erstellen besserer Eingabeaufteilungen für die native parallele Indizierung

Die parallele Aufgabe kann jetzt bessere Aufteilungen erstellen. Jede Aufteilung kann je nach Größe mehrere Eingabedateien enthalten. Leere Dateien werden ignoriert. Die Split-Größe kann mit der neuen Split-Hint-Spezifikation gesteuert werden. Weitere Einzelheiten finden Sie unter Split-Hint-Spezifikation. https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> Transform ist jetzt ein Erweiterungspunkt

Transform ist ein Interface, der eine Transformation darstellt, die zum Zeitpunkt der Aufnahme auf jede Zeile angewendet werden soll. Diese Schnittstelle ist jetzt ein Erweiterungspunkt. Weitere Informationen zum Hinzufügen Ihres benutzerdefinierten Transform finden Sie unter [Eigene Erweiterungen schreiben] (https://druid.apache.org/docs/0.18.0/development/modules.html#writing-your-own-extensions). https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> chunkPeriod Abfragekontext wurde entfernt

chunkPeriod ist seit 0.14.0 aufgrund seiner eingeschränkten Verwendung veraltet (es war manchmal nur für groupBy v1 nützlich). Dieser Abfragekontext wurde jetzt in 0.18.0 entfernt. https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Experimentelle Unterstützung für Java 11

Druid unterstützt jetzt experimentell Java 11. Sie können dieselbe Druid-Binärdistribution mit Java 11 ausführen, die mit Java 8 kompiliert wurde. Unsere Tests auf Travis umfassen:

  • Kompilieren und Ausführen von Unit-Tests mit Java 11
  • Kompilieren mit Java 8 und Ausführen von Integrationstests mit Java 11 Die Ergebnisse der Leistungstests liegen noch nicht vor.

<a name="pac4j" href="#pac4j">#</a> Neue Pac4j-Erweiterung

Es wird dringend empfohlen, ein Upgrade auf 0.18.0 oder 0.17.1 durchzuführen, wenn Sie die LDAP-Authentifizierung mit Druid verwenden. https://github.com/apache/druid/pull/9600

<a name="known-issues" href="#known-issues">#</a> Bekannte Probleme

<a name="inline-query-multi-value" href="#inline-query-multi-value">#</a> Abfragefehler mit topN oder groupBy auf scan mit mehrwertigen Spalten

Abfrage-Inlining in Brokern wurde in 0.18.0 neu eingeführt, weist jedoch einen Fehler auf, der dazu führt, dass Abfragen mit topN oder groupBy zusätzlich zu scan fehlschlagen, wenn die Scan-Abfrage mehrwertige Dimensionen auswählt. Weitere Einzelheiten finden Sie unter https://github.com/apache/druid/issues/9697.

<a name="npe-kafka" href="#npe-kafka">#</a> NullPointerException bei Verwendung des Avro-Parsers mit dem Kafka-Indexdienst.

Der Avro-Parser funktioniert aufgrund einer falschen Nullprüfung nicht mit dem Kafka-Indexdienst. Weitere Einzelheiten finden Sie unter https://github.com/apache/druid/issues/9728.

<a name="unavailable-segment-metric" href="#unavailable-segment-metric">#</a> Irreführende segment/unavailable/count-Metrik während der Übergabe

Diese Metrik sollte auch die Anzahl der von Echtzeitaufgaben bedienten Segmente berücksichtigen, ist dies jedoch derzeit nicht. Infolgedessen scheint es, dass die Nichtverfügbarkeit ansteigt, bevor die neuen Segmente durch historische Daten geladen werden, selbst wenn tatsächlich alle Segmente kontinuierlich für eine Kombination aus Echtzeitaufgaben und historischen Daten verfügbar sind. https://github.com/apache/druid/issues/9677

<a name="sql-explain" href="#sql-explain">#</a> Geringer Unterschied zwischen dem Ergebnis der explain plan for-Abfrage und dem tatsächlichen Ausführungsplan

Das Ergebnis von explain plan for kann geringfügig von dem abweichen, was Druid tatsächlich ausführt, wenn die Abfrage Verknüpfungen oder Unterabfragen enthält. Der Unterschied besteht darin, dass jeder Teil des Abfrageplans im Ergebnis von explain plan for so dargestellt wird, als wäre es eine eigene native Abfrage. Beispielsweise könnte explain plan for für eine Verknüpfung einer Datenquelle d1 und einer GroupBy-Unterabfrage für die Datenquelle d2 einen Plan wie unten zurückgeben

     join
    /    \
scan    groupBy
 |        |
d1       d2

wohingegen der tatsächliche Abfrageplan, den Druid ausführen würde, ist

     join
    /    \
  d1    groupBy
          |
         d2

druid druid-0.18.0

Apache Druid 0.18.0 contains over 200 new features, performance enhancements, bug fixes, and major documentation improvements from 42 contributors. Check out the complete list of changes and everything tagged to the milestone.

<a name="new-features" href="#new-features">#</a> New Features

<a name="join" href="#join">#</a> Join support

Join is a key operation in data analytics. Prior to 0.18.0, Druid supported some join-related features, such as Lookups or semi-joins in SQL. However, the use cases for those features were pretty limited and, for other join use cases, users had to denormalize their datasources when they ingest data instead of joining them at query time, which could result in exploding data volume and long ingestion time.

Druid 0.18.0 supports real joins for the first time ever in its history. Druid supports INNER, LEFT, and CROSS joins for now. For native queries, the join datasource has been newly introduced to represent a join of two datasources. Currently, only the left-deep join is allowed. That means, only a table or another join datasource is allowed for the left datasource. For the right datasource, lookup, inline, or query datasources are allowed. Note that join of Druid datasources is not supported yet. There should be only one table datasource in the same join query.

Druid SQL also supports joins. Under the covers, SQL join queries are translated into one or several native queries that include join datasources. See Query translation for more details of SQL translation and best practices to write efficient queries.

When a join query is issued, the Broker first evaluates all datasources except for the base datasource which is the only table datasource in the query. The evaluation can include executing subqueries for query datasources. Once the Broker evaluates all non-base datasources, it replaces them with inline datasources and sends the rewritten query to data nodes (see the below "Query inlining in Brokers" section for more details). Data nodes use the hash join to process join queries. They build a hash table for each non-primary leaf datasource unless it already exists. Note that only lookup datasource currently has a pre-built hash table. See Query execution for more details about join query execution.

Joins can affect performance of your queries. In general, any queries including joins can be slower than equivalent queries against a denormalized datasource. The LOOKUP function could perform better than joins with lookup datasources. See Join performance for more details about join query performance and future plans for performance improvement.

https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> Query inlining in Brokers

Druid is now able to execute a nested query by inlining subqueries. Any type of subquery can be on top of any type of another, such as in the following example:

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

To execute this query, the Broker first evaluates the leaf groupBy subquery; it sends the subquery to data nodes and collects the result. The collected result is materialized in the Broker memory. Once the Broker collects all results for the groupBy query, it rewrites the topN query by replacing the leaf groupBy with an inline datasource which has the result of the groupBy query. Finally, the rewritten query is sent to data nodes to execute the topN query.

<a name="query-laning" href="#query-laning">#</a> Query laning and prioritization

When you run multiple queries of heterogenous workloads at a time, you may sometimes want to control the resource commitment for a query based on its priority. For example, you would want to limit the resources assigned to less important queries, so that important queries can be executed in time without being disrupted by less important ones.

Query laning allows you to control capacity utilization for heterogeneous query workloads. With laning, the broker examines and classifies a query for the purpose of assigning it to a 'lane'. Lanes have capacity limits, enforced by the Broker, that can be used to ensure sufficient resources are available for other lanes or for interactive queries (with no lane), or to limit overall throughput for queries within the lane.

Automatic query prioritization determines the query priority based on the configured strategy. The threshold-based prioritization strategy has been added; it automatically lowers the priority of queries that cross any of a configurable set of thresholds, such as how far in the past the data is, how large of an interval a query covers, or the number of segments taking part in a query.

See Query prioritization and laning for more details.

https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

New dimension in query metrics

Since a native query containing subqueries can be executed part-by-part, a new subQueryId has been introduced. Each subquery has different subQueryIds but same queryId. The subQueryId is available as a new dimension in query metrics.

New configuration

A new druid.server.http.maxSubqueryRows configuration controls the maximum number of rows materialized in the Broker memory.

Please see Query execution for more details.

https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> SQL grouping sets

GROUPING SETS is now supported, allowing you to combine multiple GROUP BY clauses into one GROUP BY clause. This GROUPING SETS clause is internally translated into the groupBy query with subtotalsSpec. The LIMIT clause is now applied after subtotalsSpec, rather than applied to each grouping set.

https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> SQL Dynamic parameters

Druid now supports dynamic parameters for SQL. To use dynamic parameters, replace any literal in the query with a question mark (?) character. These question marks represent the places where the parameters will be bound at execution time. See SQL dynamic parameters for more details.

https://github.com/apache/druid/pull/6974

<a name="important-changes" href="#important-changes">#</a> Important Changes

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments is disabled by default

applyLimitPushDownToSegments was added in 0.17.0 to push down limit evaluation to queryable nodes, limiting results during segment scan for groupBy v2. This can lead to performance degradation, as reported in https://github.com/apache/druid/issues/9689, if many segments are involved in query processing. This is because “limit push down to segment scan” initializes an aggregation buffer per segment, the overhead for which is not negligible. Enable this configuration only if your query involves a relatively small number of segments per historical or realtime task.

https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> Roaring bitmaps as default

Druid supports two bitmap types, i.e., Roaring and CONCISE. Since Roaring bitmaps provide a better out-of-box experience (faster query speed in general), the default bitmap type is now switched to Roaring bitmaps. See Segment compression for more details about bitmaps.

https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> Complex metrics behavior change at ingestion time when SQL-compatible null handling is disabled (default mode)

When SQL-compatible null handling is disabled, the behavior of complex metric aggregation at ingestion time has now changed to be consistent with that at query time. The complex metrics are aggregated to the default 0 values for nulls instead of skipping them during ingestion.

https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> Array expression syntax change

Druid expression now supports typed constructors for creating arrays. Arrays can be defined with an explicit type. For example, <LONG>[1, 2, null] creates an array of LONG type containing 1, 2, and null. Note that you can still create an array without an explicit type. For example, [1, 2, null] is still a valid syntax to create an equivalent array. In this case, Druid will infer the type of array from its elements. This new syntax applies to empty arrays as well. <STRING>[], <DOUBLE>[], and <LONG>[] will create an empty array of STRING, DOUBLE, and LONG type, respectively.

https://github.com/apache/druid/pull/9367

<a name="pending-segments-cleanup" href="#pending-segments-cleanup">#</a> Enabling pending segments cleanup by default

The pendingSegments table in the metadata store is used to create unique new segment IDs for appending tasks such as Kafka/Kinesis indexing tasks or batch tasks of appending mode. Automatic pending segments cleanup was introduced in 0.12.0, but has been disabled by default prior to 0.18.0. This configuration is now enabled by default.

https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> Creating better input splits for native parallel indexing

The Parallel task now can create better splits. Each split can contain multiple input files based on their size. Empty files will be ignored. The split size is controllable with the new split hint spec. See Split hint spec for more details.

https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> Transform is now an extension point

Transform is an Interface that represents a transformation to be applied to each row at ingestion time. This interface is now an Extension point. Please see Writing your own extensions for how to add your custom Transform.

https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> chunkPeriod query context is removed

chunkPeriod has been deprecated since 0.14.0 because of its limited usage (it was sometimes useful for only groupBy v1). This query context is now removed in 0.18.0.

https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Experimental support for Java 11

Druid now experimentally supports Java 11. You can run the same Druid binary distribution with Java 11 which is compiled with Java 8. Our tests on Travis include:

  • Compiling and running unit tests with Java 11
  • Compiling with Java 8 and running integration tests with Java 11

Performance testing results are not available yet.

<a name="new-extension" href="#new-extension">#</a> New Extension

<a name="pac4j" href="#pac4j">#</a> New Pac4j extension

A new extension is added in 0.18.0 to enable OpenID Connect based Authentication for Druid Processes. This can be used with any authentication server that supports same e.g. Okta. <a name="security" href="#security">#</a> Security Issues

<a name="ldap-security" href="#ldap-security">#</a> [CVE-2020-1958] Apache Druid LDAP injection vulnerability

CVE-2020-1958 has been reported recently and fixed in 0.18.0 and 0.17.1. When LDAP authentication is enabled, callers of Druid APIs can bypass the credentialsValidator.userSearch filter barrier or retrieve any LDAP attribute values of users that exist on the LDAP server, so long as that information is visible to the Druid server. Please see the description in the link for more details. It is strongly recommended to upgrade to 0.18.0 or 0.17.1 if you are using LDAP authentication with Druid.

https://github.com/apache/druid/pull/9600

<a name="kafka-client-security" href="#kafka-client-security">#</a> Updating Kafka client to 2.2.2

Kafka client library has been updated to 2.2.2, in which CVE-2019-12399 is fixed.

<a name="known-issues" href="#known-issues">#</a> Known Issues

<a name="inline-query-multi-value" href="#inline-query-multi-value">#</a> Query failure with topN or groupBy on scan with multi-valued columns

Query inlining in Brokers is newly introduced in 0.18.0 but has a bug that queries with topN or groupBy on top of scan fail if the scan query selects multi-valued dimensions. See https://github.com/apache/druid/issues/9697 for more details.

<a name="npe-kafka" href="#npe-kafka">#</a> NullPointerException when using Avro parser with Kafka indexing service.

Avro parser doesn't work with Kafka indexing service because of a wrong null check. See https://github.com/apache/druid/issues/9728 for more details.

<a name="unavailable-segment-metric" href="#unavailable-segment-metric">#</a> Misleading segment/unavailable/count metric during handoff

This metric is supposed to take the number of segments served by realtime tasks into consideration as well, but it isn't now. As a result, it appears that unavailability spikes up before the new segments are loaded by historicals, even if all segments actually are continuously available on some combination of realtime tasks and historicals.

https://github.com/apache/druid/issues/9677

<a name="sql-explain" href="#sql-explain">#</a> Slight difference between the result of explain plan for query and the actual execution plan

The result of explain plan for can be slightly different from what Druid actually executes when the query includes joins or subqueries. The difference can be found in that each part of the query plan would be represented as if it was its own native query in the result of explain plan for. For example, for a join of a datasource d1 and a groupBy subquery on datasource d2, the explain plan for could return a plan like below

     join
    /    \
scan    groupBy
 |        |
d1       d2

whereas the actual query plan Druid would execute is

     join
    /    \
  d1    groupBy
          |
         d2
