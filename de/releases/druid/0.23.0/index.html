Druide Druide-0.23.0

Apache Druid 0.23.0 enthält über 450 neue Funktionen, Fehlerbehebungen, Leistungsverbesserungen, Dokumentationsverbesserungen und zusätzliche Testabdeckung von 81 Mitwirkenden. Weitere Einzelheiten finden Sie im vollständigen Änderungssatz.

Sie können jetzt nach einer mehrwertigen Dimension als Array gruppieren. Für eine Datenquelle namens „test“:

{"timestamp": "2011-01-14T00:00:00.000Z", "tags": ["t5","t6","t7"]}  #row3
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": []}                #row4

Die folgende Abfrage:

{

  "dataSource": "test",
  "intervals": [
    "1970-01-01T00:00:00.000Z/3000-01-01T00:00:00.000Z"
  ],
  "granularity": {
    "type": "all"
  },
  "virtualColumns" : [ {
    "type" : "expression",

<a name="0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators" href="#0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators">#</a> Geben Sie eine andere Spalte als die __time-Spalte für den Zeilenvergleich in ersten/letzten Aggregatoren an

Sie können Zeitspalten in *first/*last-Aggregatoren übergeben, indem Sie die SQL-Funktionen LATEST_BY/EARLIEST_BY verwenden. Dies bietet Unterstützung für Fälle, in denen die Zeit als Teil einer anderen Spalte als „__time“ gespeichert wird. Sie können auch eine andere logische Zeitspalte angeben. (#11949) (#12145)

<a name="0.23.0-new-features-query-engine-improvements-to-querying-user-experience" href="#0.23.0-new-features-query-engine-improvements-to-querying-user-experience">#</a> Verbesserungen beim Abfragen der Benutzererfahrung

Diese Version enthält mehrere Verbesserungen für die Abfrage: – Die SQL-Abfrage-ID wurde zum Antwortheader für fehlgeschlagene SQL-Abfragen hinzugefügt, um das Auffinden der Fehlermeldungen zu erleichtern (#11756) – Eingabetypvalidierung für DataSketches HLL hinzugefügt (#12131)

  • Verbesserte JDBC-Protokollierung (#11676) – SQL-Funktionen MV_FILTER_ONLY und MV_FILTER_NONE hinzugefügt, um Zeilen mit mehrwertigen Zeichenfolgendimensionen so zu filtern, dass sie nur die angegebene Werteliste bzw. keine davon enthalten (#11650) – ARRAY_CONCAT_AGG hinzugefügt, um Array-Eingaben in einem einzigen Array zusammenzufassen (#12226) – Möglichkeit hinzugefügt, die Verwendung von Abfragekontextparametern zu autorisieren (#12396) – Verbesserte Abfrage-IDs, um die Verknüpfung von Abfragen und Unterabfragen für eine durchgängige Abfragetransparenz zu erleichtern (#11809)
  • Eine sichere Divisionsfunktion zum Schutz vor Division durch 0 hinzugefügt (#11904) – Sie können jetzt einen Abfragekontext zur intern generierten SegmentMetadata-Abfrage hinzufügen (#11429) – Unterstützung für komplexe Druidentypen zum nativen Ausdrucksverarbeitungssystem hinzugefügt, um alle Druidendaten in Ausdrücken nutzbar zu machen (#11853, #12016) – Sie können die Größe des On-Heap-Wörterbuchs auf Segmentebene über druid.query.groupBy.maxSelectorDictionarySize steuern, wenn Sie nach Ausdrücken mit Zeichenfolgen- oder Array-Werten gruppieren, für die noch keine Wörterbücher vorhanden sind.
  • Sie haben einen besseren Schutz vor Filterexplosion während der CNF-Konvertierung (#12314) (#12324) – Sie können die vollständige native Abfrage zur Erläuterung der SQL-Abfrage erhalten, indem Sie useNativeQueryExplain im Abfragekontext auf „true“ setzen (#11908).
  • Sie können festlegen, dass der Broker Echtzeitknoten oder bestimmte historische Ebenen ignoriert. (#11766) (#11732)

<a name="0.23.0-new-features-streaming-ingestion" href="#0.23.0-new-features-streaming-ingestion">#</a> Streaming-Aufnahme

<a name="0.23.0-new-features-streaming-ingestion-kafka-input-format-for-parsing-headers-and-key" href="#0.23.0-new-features-streaming-ingestion-kafka-input-format-for-parsing-headers-and-key">#</a> Kafka-Eingabeformat zum Parsen von Headern und Schlüsseln

Wir haben ein Kafka-Eingabeformat eingeführt, damit Sie zusätzlich zum Nachrichteninhalt auch Header-Daten erfassen können. Zum Beispiel:

  • das Ereignisschlüsselfeld
  • Ereignisheader – der Zeitstempel des Kafka-Ereignisses – der Kafka-Ereigniswert, der die Nutzlast speichert. (#11630)

<a name="0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements" href="#0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements">#</a> Kinesis-Einnahme – Verbesserungen

Wir haben folgende Verbesserungen bei der Kinesis-Einnahme vorgenommen – Das erneute Sharding kann die Aufnahme beeinträchtigen und verlangsamen, da viele zwischenzeitlich leere Shards erstellt werden. Diese Shards werden Aufgaben zugewiesen, was zu einem Ungleichgewicht bei der Lastzuweisung führt. Sie können skipIgnorableShards in der Kinesis-Aufnahmeoptimierungskonfiguration auf true setzen, um solche Shards zu ignorieren. (#12235) – Derzeit verwendet die Kinesis-Aufnahme DescribeStream, um die Liste der Shards abzurufen. Dieser Aufruf ist veraltet und langsamer. In dieser Version können Sie zu einem neueren API listShards wechseln, indem Sie useListShards in der Kinesis-Aufnahmeoptimierungskonfiguration auf true setzen. (#12161)

<a name="0.23.0-new-features-native-batch-ingestion" href="#0.23.0-new-features-native-batch-ingestion">#</a> Native Batch-Aufnahme

<a name="0.23.0-new-features-native-batch-ingestion-multi-dimension-range-partitioning" href="#0.23.0-new-features-native-batch-ingestion-multi-dimension-range-partitioning">#</a> Mehrdimensionale Bereichspartitionierung

Mit der mehrdimensionalen Bereichspartitionierung können Benutzer ihre Daten nach Bereichen beliebig vieler Dimensionen partitionieren. Es entwickelt die Konzepte der „Single-Dim“-Partitionierung weiter und ist heute wohl die bevorzugte sekundäre Partitionierung, sowohl hinsichtlich der Abfrageleistung als auch der Speichereffizienz. (#11848) (#11973)

<a name="0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior" href="#0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior">#</a> Verbessertes Verhalten beim Ersetzen von Daten

Wenn in früheren Versionen von Druid Daten mit dem Flag dropExisting zum Ersetzen von Daten aufgenommen wurden, behielt Druid die vorhandenen Daten für einen bestimmten Zeitraum bei, wenn keine neuen Daten zum Ersetzen vorhanden waren. Wenn Sie nun dropExisting in Ihrem ioSpec auf true setzen und Daten für einen Zeitraum erfassen, der einen Zeitabschnitt ohne Daten enthält, verwendet Druid einen Tombstone, um die vorhandenen Daten im leeren Zeitabschnitt zu überschatten. (#12137) Diese Version enthält mehrere Verbesserungen für die native Batch-Aufnahme: – Druid gibt jetzt eine neue Metrik aus, wenn eine Batch-Aufgabe mit dem Warten auf Segmentverfügbarkeit fertig ist. (#11090) – segmentAvailabilityWaitTimeMs, die Dauer in Millisekunden, die eine Aufgabe auf die Übergabe ihrer Segmente an historische Knoten gewartet hat, wurde zu IngestionStatsAndErrorsTaskReportData hinzugefügt (#11090) – Funktionalität hinzugefügt, um vorhandene Metriken während der Aufnahme beizubehalten (#12185)

  • Parallele native Batch-Aufgaben können jetzt Aufgabenberichte für den sequentiellen und einphasigen Modus (z. B. bei dynamischer Partitionierung verwendet) sowie für Unteraufgaben im einphasigen Modus bereitstellen (#11688) – Unterstützung für RowStats in druid/indexer/v1/task/{task_id}/reports API für mehrphasige parallele Indizierungsaufgabe hinzugefügt (#12280) – Die OOM-Fehler in der Dimensionsverteilungsphase der parallelen Indizierung wurden behoben (#12331) – Unterstützung für die Verarbeitung von Null-Dimensionswerten beim Erstellen von Partitionsgrenzen hinzugefügt (#11973)

<a name="0.23.0-new-features-improvements-to-ingestion-in-general" href="#0.23.0-new-features-improvements-to-ingestion-in-general">#</a> Verbesserungen bei der Aufnahme im Allgemeinen

Diese Version enthält mehrere Verbesserungen für die Aufnahme im Allgemeinen: – Der Vorlagenmodifikator wurde aus IncrementalIndex<AggregatorType> entfernt, da er nicht mehr benötigt wird – Sie können jetzt JsonPath-Funktionen in JsonPath-Ausdrücken während der Aufnahme verwenden (#11722) – Druid erstellt keine materialisierte Liste von Segmentdateien mehr und eliminiert das Schleifen über die Dateien, um OOM-Probleme zu reduzieren (#11903) – Der Hauptmethode „Merge“ in IndexMerger wurde ein intermediärer persistenter IndexSpec hinzugefügt (#11940)

  • Granularity.granularitiesFinerThan gibt jetzt ALL zurück, wenn Sie ALL übergeben (#12003) – Konfigurationsparameter zum Anhängen von Aufgaben hinzugefügt, um ihnen die Verwendung einer SHARED-Sperre zu ermöglichen (#12041) – SchemaRegistryBasedAvroBytesDecoder löst jetzt ein ParseException anstelle von RE aus, wenn das Abrufen eines Schemas fehlschlägt (#12080) – includeAllDimensions zu dimensionsSpec hinzugefügt, um alle expliziten Dimensionen zuerst in InputRow zu platzieren und anschließend alle anderen in den Eingabedaten gefundenen Dimensionen (#12276) – Möglichkeit hinzugefügt, Nullspalten in Segmenten zu speichern (#12279)

<a name="0.23.0-new-features-compaction" href="#0.23.0-new-features-compaction">#</a> Komprimierung

Diese Version enthält mehrere Verbesserungen für die Komprimierung:

  • Automatische Komprimierung unterstützt jetzt komplexe Dimensionen (#11924)
  • Automatische Komprimierung unterstützt jetzt überlappende Segmentintervalle (#12062) – Sie können jetzt die automatische Komprimierung konfigurieren, um das Verhältnis der für Komprimierungsaufgaben verfügbaren Slots aus den maximalen Slots zu berechnen, einschließlich der maximalen Worker-Knoten für die automatische Skalierung (#12263). – Sie können jetzt den Zeitraum der automatischen Komprimierung des Koordinators getrennt von anderen Indizierungsaufgaben konfigurieren (#12263).
  • Die Standardeingabesegmentgrößebytes wurde jetzt auf ~ 100 TB geändert (#12534) – Sie können die Abfragegranularität ändern, das Dimensionsschema ändern, Daten filtern und Metriken durch automatische Komprimierung hinzufügen (#11856) (#11874) (#11922) (#12125) – Sie können das Aufrollen auch für die automatische und manuelle Verdichtung steuern (#11850)

<a name="0.23.0-new-features-sql" href="#0.23.0-new-features-sql">#</a> SQL

<a name="0.23.0-new-features-sql-human-readable-and-actionable-sql-error-messages" href="#0.23.0-new-features-sql-human-readable-and-actionable-sql-error-messages">#</a> Menschenlesbare und umsetzbare SQL-Fehlermeldungen

Bis zur Version 0.22.1 gab Druid sehr kryptische und nicht hilfreiche Fehlermeldungen aus, wenn Sie eine nicht unterstützte SQL-Abfrage ausstellten. Mit dieser Änderung enthalten Fehlermeldungen genau den Teil der SQL-Abfrage, der in Druid nicht unterstützt wird. Wenn Sie beispielsweise eine Scan-Abfrage ausführen, die nach einer anderen Dimension als der Zeitspalte geordnet ist. (#11911)

<a name="0.23.0-new-features-sql-cancel-api-for-sql-queries" href="#0.23.0-new-features-sql-cancel-api-for-sql-queries">#</a> API für SQL-Abfragen abbrechen

Wir haben ein neues API zum Abbrechen von SQL-Abfragen hinzugefügt, sodass Sie jetzt SQL-Abfragen genauso abbrechen können wie native Abfragen. Sie können den API über die Webkonsole verwenden. In früheren Versionen wurde durch den Abbruch über die Konsole nur die client-Verbindung geschlossen, während die SQL-Abfrage weiterhin auf Druid ausgeführt wurde. (#11643) (#11738) (#11710)

<a name="0.23.0-new-features-sql-improved-sql-compatibility" href="#0.23.0-new-features-sql-improved-sql-compatibility">#</a> Verbesserte SQL-Kompatibilität

Wir haben Änderungen an Ausdrücken vorgenommen, die die Ausdrucksauswertung SQL-konformer machen. Dieses neue Verhalten ist standardmäßig deaktiviert. Es kann aktiviert werden, indem druid.expressions.useStrictBooleans auf true gesetzt wird. Wir empfehlen, dieses Verhalten zu aktivieren, da es in manchen Fällen auch leistungsfähiger ist. (#11184)

<a name="0.23.0-security-fixes" href="#0.23.0-security-fixes">#</a> Sicherheitskorrekturen

<a name="0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts" href="#0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts">#</a> Unterstützung für Zugriffskontrolle beim Festlegen von Abfragekontexten

Heutzutage sind den Benutzern beliebige Kontextparameter erlaubt. Dies kann 1) zu einer schlechten UX führen, wenn der Kontextparameter noch nicht ausgereift ist, oder 2) im schlimmsten Fall sogar zu Abfragefehlern oder Systemfehlern, wenn ein sensibler Parameter missbraucht wird, z. B. maxSubqueryRows. Druid hat jetzt die Möglichkeit, Kontextparameter pro Benutzerrolle einzuschränken. Das bedeutet, dass eine Abfrage fehlschlägt, wenn in der Abfrage ein Kontextparameter festgelegt ist, der für Sie nicht zulässig ist. Die Kontextparameterautorisierung kann mit Druid.auth.authorizeQueryContextParams aktiviert werden. Dies ist standardmäßig deaktiviert, um ein reibungsloseres Upgrade-Erlebnis zu ermöglichen. (#12396)

<a name="0.23.0-security-fixes-performance-improvements" href="#0.23.0-security-fixes-performance-improvements">#</a> Leistungsverbesserungen

<a name="0.23.0-security-fixes-performance-improvements-ingestion" href="#0.23.0-security-fixes-performance-improvements-ingestion">#</a> Aufnahme

– Genauere Speicherschätzungen beim Erstellen eines inkrementellen On-Heap-Index. Anstatt die maximal mögliche aggregierte Zeilengröße zu verwenden, kann Druid jetzt (basierend auf einem Task-Kontext-Flag) eine genauere Schätzung des tatsächlichen Heap-Footprints einer aggregierten Zeile verwenden. Dadurch kann der Indexer mehr Zeilen in den Speicher einpassen, bevor er eine Zwischenspeicherung durchführt. (#12073)

  • time_shift ist jetzt vektorisiert (#12254)

<a name="0.23.0-upgrading-to-0.23.0" href="#0.23.0-upgrading-to-0.23.0">#</a> Upgrade auf 0.23.0

Berücksichtigen Sie beim Upgrade von Druid 0.22.x auf 0.23.0 die folgenden Änderungen und Aktualisierungen. Wenn Sie von einer früheren Version als 0.22.1 aktualisieren, sehen Sie sich die release notes der relevanten Zwischenversionen an.

<a name="0.23.0-upgrading-to-0.23.0-autokill" href="#0.23.0-upgrading-to-0.23.0-autokill">#</a> Automatisches Löschen von Segmenten

In 0.23.0 ist das automatische Beenden von Segmenten jetzt standardmäßig aktiviert (#12187). Die neuen Standardeinstellungen sollten alle nicht verwendeten Segmente löschen, die älter als 90 Tage sind. Wenn Benutzer dieses Verhalten bei einem Upgrade nicht wünschen, sollten sie das Verhalten explizit deaktivieren. Dies ist eine riskante Änderung, da Segmente je nach Intervall sofort gelöscht werden, nachdem sie als nicht verwendet markiert wurden. Dieses Verhalten wird in der nächsten Druid-Version rückgängig gemacht oder geändert. Weitere Informationen finden Sie unter (#12693).

<a name="0.23.0-upgrading-to-0.23.0-other-changes" href="#0.23.0-upgrading-to-0.23.0-other-changes">#</a> Weitere Änderungen

– Für die Kinesis-Aufnahme ist listShards API Zugriff auf den Stream erforderlich. – Kafka clients-Bibliotheken wurden auf 3.0.0 aktualisiert (#11735) – Die dynamische Koordinatorkonfiguration „percentOfSegmentsToConsiderPerMove“ ist veraltet und wird in einer zukünftigen Version von Druid entfernt. Sie wird durch eine neue Segmentauswahlstrategie ersetzt, die in (#11257) eingeführt wurde. Diese neue Strategie ist derzeit standardmäßig deaktiviert, kann jedoch aktiviert werden, wenn Sie die dynamische Koordinatorkonfiguration useBatchedSegmentSampler auf true setzen. Wenn Sie dies als solches festlegen, wird die Verwendung des veralteten „percentOfSegmentsToConsiderPerMove“ deaktiviert. In einer zukünftigen Version wird „useBatchedSegmentSampler“ dauerhaft „true“ sein. (#11960)

<a name="0.23.0-developer-notices" href="#0.23.0-developer-notices">#</a> Entwicklerhinweise

<a name="0.23.0-developer-notices-updated-airline-dependency-to-2.x" href="#0.23.0-developer-notices-updated-airline-dependency-to-2.x">#</a> Airline-Abhängigkeit auf 2.x aktualisiert

https://github.com/airlift/airline wird nicht mehr gewartet und daher hat Druid ein Upgrade auf https://github.com/rvesse/airline (Airline 2) durchgeführt, um es aktiv nutzen zu können gepflegte Version und minimiert gleichzeitig Breaking Changes. Dies ist eine abwärtsinkompatible Änderung und benutzerdefinierte Erweiterungen, die auf dem Erweiterungspunkt CliCommandCreator basieren, müssen ebenfalls aktualisiert werden. 12270

<a name="0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks" href="#0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks">#</a> Geben Sie 404 statt 400 für unbekannte Vorgesetzte oder Aufgaben zurück

Frühere Supervisor-/Aufgabenendpunkte geben 400 zurück, wenn kein Supervisor oder keine Aufgabe gefunden wurde. Dieser Statuscode ist für das 3. System nicht freundlich und verwirrend. Und gemäß der Definition des HTTP-Statuscodes ist 404 der richtige Code für einen solchen Fall. Deshalb haben wir den Statuscode von 400 auf 404 geändert, um die Mehrdeutigkeit zu beseitigen. Alle clients dieser Endpunkte sollten die Behandlung des Antwortcodes entsprechend ändern. 11724

<a name="0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned" href="#0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned">#</a> Gibt 400 statt 500 zurück, wenn eine SQL-Abfrage nicht geplant werden kann

Jede SQL-Abfrage, die von Druid nicht geplant werden kann, gilt nicht als fehlerhafte Anfrage. Für solche Abfragen geben wir jetzt 400 zurück. Entwickler, die SQL API verwenden, sollten bei Bedarf die Behandlung des Antwortcodes ändern. 12033

<a name="0.23.0-developer-notices-responsecontext-refactoring" href="#0.23.0-developer-notices-responsecontext-refactoring">#</a> ResponseContext-Refaktorierung

0.23.0 verändert den ResponseContext und seine Tasten auf bahnbrechende Weise. Die frühere Version des Antwortkontexts schlug vor, Schlüssel in einer Aufzählung zu definieren und dann zu registrieren. Diese Version schlägt vor, Schlüssel als Objekte zu definieren und dann zu registrieren. Einzelheiten finden Sie in der Klasse ResponseContext selbst. (#11828)

<a name="0.23.0-new-features-query-engine" href="#0.23.0-new-features-query-engine">#</a> Query engine

<a name="0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays" href="#0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays">#</a> Grouping on arrays without exploding the arrays

You can now group on a multi-value dimension as an array. For a datasource named "test":

{"timestamp": "2011-01-12T00:00:00.000Z", "tags": ["t1","t2","t3"]}  #row1
{"timestamp": "2011-01-13T00:00:00.000Z", "tags": ["t3","t4","t5"]}  #row2
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": ["t5","t6","t7"]}  #row3
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": []}                #row4

The following query:

{
  "queryType": "groupBy",
  "dataSource": "test",
  "intervals": [
    "1970-01-01T00:00:00.000Z/3000-01-01T00:00:00.000Z"
  ],
  "granularity": {
    "type": "all"
  },
  "virtualColumns" : [ {
    "type" : "expression",
    "name" : "v0",
    "expression" : "mv_to_array(\"tags\")",
    "outputType" : "ARRAY<STRING>"
  } ],
  "dimensions": [
    {
      "type": "default",
      "dimension": "v0",
      "outputName": "tags"
      "outputType":"ARRAY<STRING>"
    }
  ],
  "aggregations": [
    {
      "type": "count",
      "name": "count"
    }
  ]
}

Returns the following:

[
 {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "[]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "["t1","t2","t3"]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "[t3","t4","t5"]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 2,
      "tags": "["t5","t6","t7"]"
    }
  }
]

(#12078) (#12253)

<a name="0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators" href="#0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators">#</a> Specify a column other than __time column for row comparison in first/last aggregators

You can pass time column in *first/*last aggregators by using LATEST_BY / EARLIEST_BY SQL functions. This provides support for cases where the time is stored as a part of a column different than "__time". You can also specify another logical time column. (#11949) (#12145)

We've introduced a Kafka input format so you can ingest header data in addition to the message contents. For example:

  • the event key field
  • event headers
  • the Kafka event timestamp
  • the Kafka event value that stores the payload.

(#11630)

<a name="0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements" href="#0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements">#</a> Kinesis ingestion - Improvements

We have made following improvements in kinesis ingestion

  • Re-sharding can affect and slow down ingestion as many intermediate empty shards are created. These shards get assigned to tasks causing imbalance in load assignment. You can set skipIgnorableShards to true in kinesis ingestion tuning config to ignore such shards. (#12235)
  • Currently, kinesis ingestion uses DescribeStream to fetch the list of shards. This call is deprecated and slower. In this release, you can switch to a newer API listShards by setting useListShards to true in kinesis ingestion tuning config. (#12161)

Multi-dimension range partitioning allows users to partition their data on the ranges of any number of dimensions. It develops further on the concepts behind "single-dim" partitioning and is now arguably the most preferable secondary partitioning, both for query performance and storage efficiency. (#11848) (#11973)

<a name="0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior" href="#0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior">#</a> Improved replace data behavior

In previous versions of Druid, if ingested data with dropExisting flag to replace data, Druid would retain the existing data for a time chunk if there was no new data to replace it. Now, if you set dropExisting to true in your ioSpec and ingest data for a time range that includes a time chunk with no data, Druid uses a tombstone to overshadow the existing data in the empty time chunk. (#12137)

<a name="0.23.0-security-fixes" href="#0.23.0-security-fixes">#</a> Security fixes

<a name="0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts" href="#0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts">#</a> Support for access control on setting query contexts

Today, any context params are allowed to users. This can cause 1) a bad UX if the context param is not matured yet or 2) even query failure or system fault in the worst case if a sensitive param is abused, ex) maxSubqueryRows. Druid now has an ability to limit context params per user role. That means, a query will fail if you have a context param set in the query that is not allowed to you.

The context parameter authorization can be enabled using Druid.auth.authorizeQueryContextParams. This is disabled by default to enable a smoother upgrade experience.

(#12396)

Rather than using the maximum possible aggregated row size, Druid can now use (based on a task context flag) a closer estimate of the actual heap footprint of an aggregated row. <a name="0.23.0-upgrading-to-0.23.0" href="#0.23.0-upgrading-to-0.23.0">#</a> Upgrading to 0.23.0

Consider the following changes and updates when upgrading from Druid 0.22.x to 0.23.0. If you're updating from an earlier version than 0.22.1, see the release notes of the relevant intermediate versions.

<a name="0.23.0-upgrading-to-0.23.0-autokill" href="#0.23.0-upgrading-to-0.23.0-autokill">#</a> Auto-killing of segments

In 0.23.0, Auto killing of segments is now enabled by default (#12187). The new defaults should kill all unused segments older than 90 days. If users do not want this behavior on an upgrade, they should explicitly disable the behavior. This is a risky change since depending on the interval, segments will be killed immediately after being marked unused. this behavior will be reverted or changed in the next druid release. Please see (#12693) for more details.

<a name="0.23.0-upgrading-to-0.23.0-other-changes" href="#0.23.0-upgrading-to-0.23.0-other-changes">#</a> Other changes

  • Kinesis ingestion requires listShards API access on the stream.
  • Kafka clients libraries have been upgraded to 3.0.0 (#11735)
  • The dynamic coordinator config, percentOfSegmentsToConsiderPerMove has been deprecated and will be removed in a future release of Druid. It is being replaced by a new segment picking strategy introduced in (#11257). This new strategy is currently toggled off by default, but can be toggled on if you set the dynamic coordinator config useBatchedSegmentSampler to true. Setting this as such, will disable the use of the deprecated percentOfSegmentsToConsiderPerMove. In a future release, useBatchedSegmentSampler will become permanently true. (#11960)

<a name="0.23.0-developer-notices" href="#0.23.0-developer-notices">#</a> Developer notices

<a name="0.23.0-developer-notices-updated-airline-dependency-to-2.x" href="#0.23.0-developer-notices-updated-airline-dependency-to-2.x">#</a> updated airline dependency to 2.x

https://github.com/airlift/airline is no longer maintained and so druid has upgraded to https://github.com/rvesse/airline (Airline 2) to use an actively maintained version, while minimizing breaking changes.

This is a backwards incompatible change, and custom extensions relying on the CliCommandCreator extension point will also need to be updated.

12270

<a name="0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks" href="#0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks">#</a> Return 404 instead of 400 for unknown supervisors or tasks

Earlier supervisor/task endpoint return 400 when a supervisor or a task is not found. This status code is not friendly and confusing for the 3rd system. And according to the definition of HTTP status code, 404 is right code for such case. So we have changed the status code from 400 to 404 to eliminate the ambigiuty. Any clients of these endpoints should change the response code handling accordingly.

11724

<a name="0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned" href="#0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned">#</a> Return 400 instead of 500 when SQL query cannot be planned

Any SQL query that cannot be planned by Druid is not considered a bad request. For such queries, we now return 400. Developers using SQL API should change the response code handling if needed.

12033

<a name="0.23.0-developer-notices-responsecontext-refactoring" href="#0.23.0-developer-notices-responsecontext-refactoring">#</a> ResponseContext refactoring

0.23.0 changes the the ResponseContext and it's keys in a breaking way. The prior version of the response context suggested that keys be defined in an enum, then registered. This version suggests that keys be defined as objects, then registered. See the ResponseContext class itself for the details.

(#11828)

<a name="0.23.0-developer-notices-other-changes" href="#0.23.0-developer-notices-other-changes">#</a> Other changes

  • SingleServerInventoryView has been removed. (#11770)
  • LocalInputSource does not allow ingesting same file multiple times. (#11965)
  • getType() in PostAggregator is deprecated in favour of getType(ColumnInspector) (#11818)
