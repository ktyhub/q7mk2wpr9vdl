Druide Druide-27.0.0

Apache Druid 27.0.0 enthält über 316 neue Funktionen, Fehlerbehebungen, Leistungsverbesserungen, Dokumentationsverbesserungen und zusätzliche Testabdeckung von 50 Mitwirkenden.

Weitere Einzelheiten finden Sie im vollständigen Änderungssatz, einschließlich Fehlerbehebungen.

Lesen Sie die Upgrade-Hinweise und inkompatiblen Änderungen, bevor Sie ein Upgrade auf Druid 27.0.0 durchführen.

<a name="27.0.0-highlights-query-from-deep-storage-%28experimental%29" href="#27.0.0-highlights-query-from-deep-storage-%28experimental%29">#</a> Abfrage aus dem Deep Storage (experimentell)

Druid unterstützt jetzt das Abfragen von Segmenten, die nur im Deep Storage gespeichert sind. Wenn Sie Abfragen aus dem Deep Storage durchführen, können Sie größere, für Abfragen verfügbare Daten abfragen, ohne unbedingt Ihre historischen Prozesse skalieren zu müssen, um mehr Daten aufzunehmen. Um die potenziellen Speichereinsparungen zu nutzen, stellen Sie sicher, dass Sie Ihre Laderegeln so konfigurieren, dass nicht alle Ihre Segmente in historische Prozesse geladen werden.

Beachten Sie, dass mindestens ein Segment einer Datenquelle in einen historischen Prozess geladen werden muss, damit der Broker die Abfrage planen kann. Es kann sich jedoch um ein beliebiges Segment handeln.

Die typbewusste automatische Schemaerkennung ist jetzt allgemein verfügbar. Druid kann das Schema für die von Ihnen erfassten Daten bestimmen, sodass Sie das Schema nicht manuell definieren müssen.

<a name="27.0.0-highlights-smart-segment-loading" href="#27.0.0-highlights-smart-segment-loading">#</a> Intelligentes Laden von Segmenten

Der Koordinator ist jetzt viel stabiler und benutzerfreundlicher. Im neuen smartSegmentLoading-Modus berechnet es dynamisch Werte für mehrere Konfigurationen, um die Leistung zu maximieren. Der Koordinator kann nun die Auslastung neuerer Segmente und Segmente, die überhaupt nicht verfügbar sind, gegenüber der Auslastung von Segmenten priorisieren, bei denen bereits einige Replikate im Cluster geladen sind. Es kann auch in früheren Durchläufen getroffene Entscheidungen neu bewerten und nicht mehr benötigte Vorgänge abbrechen. Darüber hinaus konkurrieren durch den Segmentausgleich gestartete Verschiebungsvorgänge nicht mit der Last nicht verfügbarer Segmente, wodurch die Reaktionszeit auf Änderungen im Cluster verkürzt und Entscheidungen zur Segmentzuweisung beschleunigt werden.

Darüber hinaus haben Führungswechsel jetzt weniger Auswirkungen und der Koordinator bleibt nicht hängen, selbst wenn eine Wiederwahl erfolgt, während ein Koordinatorlauf läuft.

Schließlich ist die cost-Balancer-Strategie jetzt wesentlich leistungsfähiger und kann mehr Segmente in einem einzigen Koordinatorlauf bewegen. Diese Verbesserungen wurden durch die Übernahme von Ideen aus der cachingCost-Strategie erzielt. Wir empfehlen die Verwendung von cost anstelle von cachingCost, da cachingCost jetzt veraltet ist.

<a name="27.0.0-highlights-smart-segment-loading-new-query-filters" href="#27.0.0-highlights-smart-segment-loading-new-query-filters">#</a> Neue Abfragefilter

Druid unterstützt jetzt die folgenden Filter:

  • Gleichheit: Verwendung anstelle des Auswahlfilters. Es stimmt nie mit Nullwerten überein.
  • Null: Passen Sie Nullwerte an. Wird anstelle des Auswahlfilters verwendet.
  • Bereich: Filtern Sie nach Bereichen von Dimensionswerten. Wird anstelle des gebundenen Filters verwendet. Es stimmt nie mit Nullwerten überein

Beachten Sie, dass der SQL-Planer von Druid diese neuen Filter standardmäßig anstelle ihrer älteren Gegenstücke verwendet, wenn druid.generic.useDefaultValueForNull=false oder wenn sqlUseBoundAndSelectors im SQL-Abfragekontext auf „false“ gesetzt ist.

Sie können diese Filter zum Filtern von Gleichheit und Bereichen in ARRAY-Spalten anstelle nur von Zeichenfolgen mit den vorherigen Selektor- und gebundenen Filtern verwenden.

Weitere Informationen finden Sie unter Abfragefilter.

<a name="27.0.0-highlights-smart-segment-loading-guardrail-for-subquery-results" href="#27.0.0-highlights-smart-segment-loading-guardrail-for-subquery-results">#</a> Leitplanke für Unterabfrageergebnisse

Benutzer können jetzt eine Leitplanke hinzufügen, um zu verhindern, dass die Ergebnisse der Unterabfrage die festgelegte Anzahl von Bytes überschreiten, indem sie druid.server.http.maxSubqueryRows in der Konfiguration des Brokers oder maxSubqueryRows im Abfragekontext festlegen. <a name="27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations" href="#27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations">#</a> Neue Broker-Konfiguration für SQL-Schema-Migrationen

Sie können jetzt besser steuern, wie Druid auf Schemaänderungen zwischen Segmenten reagiert. Dadurch kann die Abfrage stabiler werden, wenn neuere Segmente unterschiedliche Typen einführen, beispielsweise wenn eine Spalte zuvor LONG-Werte enthielt und neuere Segmente STRING enthielten.

Verwenden Sie die neue Broker-Konfiguration druid.sql.planner.metadataColumnTypeMergePolicy, um zu steuern, wie Spaltentypen für das SQL-Tabellenschema berechnet werden, wenn Unterschiede zwischen Segmenten auftreten.

Stellen Sie es auf einen der folgenden Werte ein:

  • leastRestrictive: Das Schema wird erst aktualisiert, wenn alle Segmente auf den neuen Typ neu indiziert wurden.
  • latestInterval: Das SQL-Schema wird aktualisiert, sobald der erste Job mit dem neuen Schema Segmente im neuesten Zeitintervall der Daten veröffentlicht.

leastRestrictive kann ein besseres Abfragezeitverhalten aufweisen und beseitigt einige Abfragezeitfehler, die bei Verwendung von latestInterval auftreten können.

<a name="27.0.0-highlights-smart-segment-loading" href="#27.0.0-highlights-smart-segment-loading">#</a> Smart segment loading

The Coordinator is now much more stable and user-friendly. In the new smartSegmentLoading mode, it dynamically computes values for several configs which maximize performance.

The Coordinator can now prioritize load of more recent segments and segments that are completely unavailable over load of segments that already have some replicas loaded in the cluster. It can also re-evaluate decisions taken in previous runs and cancel operations that are not needed anymore. Moreoever, move operations started by segment balancing do not compete with the load of unavailable segments thus reducing the reaction time for changes in the cluster and speeding up segment assignment decisions.

Additionally, leadership changes have less impact now, and the Coordinator doesn't get stuck even if re-election happens while a Coordinator run is in progress.

Lastly, the cost balancer strategy performs much better now and is capable of moving more segments in a single Coordinator run. These improvements were made by borrowing ideas from the cachingCost strategy. We recommend using cost instead of cachingCost since cachingCost is now deprecated.

For more information, see the following:

  • Upgrade note for config changes related to smart segment loading
  • New coordinator metrics
  • Smart segment loading documentation

  • Null: Match null values. Use in place of the selector filter.

You can use these filters for filtering equality and ranges on ARRAY columns instead of only strings with the previous selector and bound filters.

<a name="27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations" href="#27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations">#</a> New Broker configuration for SQL schema migrations

You can now better control how Druid reacts to schema changes between segments. This can make querying more resilient when newer segments introduce different types, such as if a column previously contained LONG values and newer segments contain STRING.

Use the new Broker configuration, druid.sql.planner.metadataColumnTypeMergePolicy to control how column types are computed for the SQL table schema when faced with differences between segments.

Set it to one of the following:

  • leastRestrictive: the schema only updates once all segments are reindexed to the new type.
  • latestInterval: the SQL schema gets updated as soon as the first job with the new schema publishes segments in the latest time interval of the data.

leastRestrictive can have better query time behavior and eliminates some query time errors that can occur when using latestInterval.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated">#</a> Hadoop 2 deprecated

Many of the important dependent libraries that Druid uses no longer support Hadoop 2. In order for Druid to stay current and have pathways to mitigate security vulnerabilities, the community has decided to deprecate support for Hadoop 2.x releases starting this release. Starting with Druid 28.x, Hadoop 3.x is the only supported Hadoop version.

Consider migrating to SQL-based ingestion or native ingestion if you are using Hadoop 2.x for ingestion today. If migrating to Druid ingestion is not possible, plan to upgrade your Hadoop infrastructure before upgrading to the next Druid release.

Please note that druid 27 is not compatible with Hadoop 2. You have to upgrade your Hadoop cluster to 3.x before upgrading to 27.0.0. Or you can build a hadoop 2 compatible distribution by explicitly selecting Hadoop 2 profile from druid 27 source artifact.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion">#</a> Worker input bytes for SQL-based ingestion

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes">#</a> Segment loading config changes

The following segment related configs are now deprecated and will be removed in future releases:

  • maxSegmentsInNodeLoadingQueue
  • maxSegmentsToMove
  • replicationThrottleLimit
  • useRoundRobinSegmentAssignment
  • replicantLifetime
  • maxNonPrimaryReplicantsToLoad
  • decommissioningMaxPercentOfMaxSegmentsToMove

Use smartSegmentLoading mode instead, which calculates values for these variables automatically.

Additionally, the defaults for the following Coordinator dynamic configs have changed:

  • maxsegmentsInNodeLoadingQueue : 500, previously 100
  • maxSegmentsToMove: 100, previously 5
  • replicationThrottleLimit: 500, previously 10

These new defaults can improve performance for most use cases.
