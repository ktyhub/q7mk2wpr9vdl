Druide Druide-24.0.0

Apache Druid 24.0.0 enthält über 300 neue Funktionen, Fehlerbehebungen, Leistungsverbesserungen, Dokumentationsverbesserungen und zusätzliche Testabdeckung von 67 Mitwirkenden. Weitere Einzelheiten finden Sie im vollständigen Änderungssatz.

<a name="24.0.0-new-features" href="#24.0.0-major-version">#</a> Hauptversionserhöhung

Ab dieser Version haben wir das führende 0 aus der Release-Version entfernt und alle anderen Ziffern um eine Stelle nach links verschoben. Druid hat jetzt die Hauptversion 24, einen Sprung nach oben gegenüber der vorherigen 0.23.0-Version. In Bezug auf Abwärtskompatibilität oder Breaking Changes unterscheidet sich diese Version nicht wesentlich von anderen früheren Hauptversionen wie 0.23.0 oder 0.22.0. Wir verfolgen weiterhin die gleiche Richtlinie wie in früheren Versionen: Minimierung der Anzahl von Änderungen, die beim Upgrade besondere Aufmerksamkeit erfordern, und Kennzeichnung aller Änderungen, die in den release notes vorhanden sind. Für diese Version finden Sie im Abschnitt Upgrade auf 24.0.0 eine Liste der abwärtsinkompatiblen Änderungen in dieser Version.

<a name="24.0.0-new-features" href="#24.0.0-new-features">#</a> Neue Funktionen

<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> Mehrstufige Abfrage-Task-Engine

[SQL-basierte Aufnahme] (https://druid.apache.org/docs/latest/multi-stage-query/index.html) für Apache Druid verwendet eine verteilte mehrstufige Abfragearchitektur, die eine Abfrage-Engine namens Multi-Stage Query Task Engine (MSQ Task Engine) umfasst. Die MSQ-Task-Engine erweitert die Abfragefunktionen von Druid, sodass Sie Abfragen schreiben können, die auf externe Daten verweisen, sowie die Aufnahme mit SQL INSERT und REPLACE durchführen. Im Wesentlichen können Sie eine SQL-basierte Aufnahme durchführen, anstatt die JSON-Aufnahmespezifikationen zu verwenden, die die native Aufnahme von Druid verwendet. Zusätzlich zur benutzerfreundlichen Syntax können Sie mit der SQL-Schnittstelle Transformationen durchführen, die mehrere Datenmischungen umfassen. Für die Batch-Aufnahme ab Druid 24.0.0 wird die SQL-basierte Aufnahme mit der mehrstufigen Abfrage-Task-Engine empfohlen. Auch die native Batch- und Hadoop-basierte Aufnahme wird weiterhin unterstützt. Wir empfehlen Ihnen, die [bekannten Probleme] (https://druid.apache.org/docs/latest/multi-stage-query/known-issues.html) zu lesen und die Funktion in einer Staging-Umgebung zu testen, bevor Sie sie in der Produktion einführen. Die Verwendung der mehrstufigen Abfrage-Task-Engine mit einfachen SELECT-Anweisungen (nicht INSERT ... SELECT oder REPLACE ... SELECT) ist experimentell. Wenn Sie ein Upgrade von einer früheren Version von Druid durchführen oder Docker verwenden, müssen Sie die Erweiterung druid-multi-stage-query zu druid.extensions.loadlist in Ihrer common.runtime.properties-Datei hinzufügen. Weitere Informationen finden Sie in der Dokumentation Übersicht zur SQL-basierten Aufnahme. #12524 #12386 #12523 #12589

<a name="24.0.0-new-features-nested-columns-" href="#24.0.0-new-features-nested-columns-">#</a> Verschachtelte Spalten

Druid unterstützt jetzt das direkte Speichern verschachtelter Datenstrukturen in einem neu hinzugefügten Spaltentyp COMPLEX<json>. COMPLEX<json>-Spalten speichern eine Kopie der strukturierten Daten im JSON-Format sowie spezielle interne Spalten und Indizes für verschachtelte Literalwerte – die Typen STRING, LONG und DOUBLE. Eine optimierte virtuelle Spalte ermöglicht es Druid, diese Werte mit einer Geschwindigkeit zu lesen und zu filtern, die mit den standardmäßigen Druid-Spalten LONG, DOUBLE und STRING übereinstimmt. Neu hinzugefügtes Druid SQL, native JSON-Funktionen und virtuelle Spalten ermöglichen Ihnen das Extrahieren, Transformieren und Erstellen von COMPLEX<json>-Werten zur Abfragezeit. Sie können die JSON-Funktionen auch in INSERT- und REPLACE-Anweisungen bei der SQL-basierten Erfassung oder in einem transformSpec bei der nativen Erfassung als Alternative zur Verwendung eines flattenSpec-Objekts verwenden, um verschachtelte Daten für die Erfassung zu „glätten“. Siehe SQL JSON-Funktionen, native JSON-Funktionen, Verschachtelte Spalten, [virtual für weitere Details. #12753 #12714 #12753 #12920

<a name="24.0.0-query-engine-updates" href="#24.0.0-query-engine-updates">#</a> Aktualisierungen der Abfrage-Engine

<a name="24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters" href="#24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters">#</a> Spaltenindizes und Abfrageverarbeitung von Filtern aktualisiert

Überarbeitete Spaltenindizes sind außerordentlich flexibel, sodass wir letztendlich eine breite Palette von Indextypen modellieren können. Maschinen hinzugefügt, um die Filter zu erstellen, die die aktualisierten Indizes verwenden, und gleichzeitig anderen Spaltenimplementierungen die Implementierung der integrierten Indextypen zu ermöglichen, um Adapter bereitzustellen, um die Indizierung in den von Druid bereitgestellten aktuellen Satzfiltern zu verwenden. #12388

<a name="24.0.0-query-engine-updates-time-filter-operator" href="#24.0.0-query-engine-updates-time-filter-operator">#</a> Zeitfilteroperator

Sie können jetzt den Druid-SQL-Operator TIME_IN_INTERVAL verwenden, um Abfrageergebnisse nach Zeit zu filtern. Bevorzugen Sie TIME_IN_INTERVAL gegenüber dem SQL-BETWEEN-Operator, um nach Zeit zu filtern. Weitere Informationen finden Sie unter Datums- und Uhrzeitfunktionen. #12662

<a name="24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter" href="#24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter">#</a> Nullwerte und der „in“-Filter

Wenn ein values-Array null enthält, stimmt der „in“-Filter mit Nullwerten überein. Dies unterscheidet sich vom SQL IN-Filter, der keine Nullwerte übereinstimmt. Weitere Informationen finden Sie unter Abfragefilter und SQL-Datentypen. #12863

<a name="24.0.0-query-engine-updates-virtual-columns-in-search-queries" href="#24.0.0-query-engine-updates-virtual-columns-in-search-queries">#</a> Virtuelle Spalten in Suchanfragen

Bisher konnte eine Suchabfrage nur nach Dimensionen suchen, die in der Datenquelle vorhanden waren. Suchanfragen unterstützen jetzt virtuelle Spalten als Parameter in der Abfrage. #12720

<a name="24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time" href="#24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time">#</a> Optimieren Sie einfache MIN/MAX-SQL-Abfragen auf __time

Einfache Abfragen wie select max(__time) from ds werden jetzt als timeBoundary-Abfragen ausgeführt, um die Sortierung nach Zeitdimension in einem Segment zu nutzen. Sie können ein Feature-Flag setzen, um diese Funktion zu aktivieren. #12472 #12491

<a name="24.0.0-query-engine-updates-string-aggregation-results" href="#24.0.0-query-engine-updates-string-aggregation-results">#</a> String-Aggregationsergebnisse

Der erste/letzte String-Aggregator vergleicht jetzt nur noch basierend auf Werten. Bisher wurden die Werte des ersten/letzten String-Aggregators zunächst anhand der Spalte _time und dann anhand der Werte verglichen. Wenn Sie über vorhandene Abfragen verfügen und weiterhin sowohl die Spalte _time als auch die Werte verwenden möchten, aktualisieren Sie Ihre Abfragen so, dass sie ORDER BY MAX(timeCol) verwenden. #12773

<a name="24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization" href="#24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization">#</a> Reduzierte Zuweisungen aufgrund der Jackson-Serialisierung

Neue Hilfsfunktionen in JacksonUtils eingeführt und implementiert, um die Wiederverwendung von zu ermöglichen SerializerProvider-Objekte. Darüber hinaus ist die Abwärtskompatibilität für kartenbasierte Zeilen im GroupByQueryToolChest standardmäßig deaktiviert, wodurch das Kopieren des schwergewichtigen ObjectMapper entfällt. Einführung einer Konfigurationsoption, die es Administratoren ermöglicht, die Abwärtskompatibilität explizit zu aktivieren. #12468

<a name="24.0.0-query-engine-updates-updated-ipaddress-java-library-" href="#24.0.0-query-engine-updates-updated-ipaddress-java-library-">#</a> Aktualisierte IPAddress-Java-Bibliothek

Eine neue Java-Bibliotheksabhängigkeit IPAddress hinzugefügt, um IP-Adressen zu verarbeiten. Die Bibliothek bietet IPv6-Unterstützung. Darüber hinaus wurden IPv4-Funktionen migriert, um die neue Bibliothek zu nutzen. #11634

<a name="24.0.0-improvements-to-ingestion-in-general" href="#24.0.0-improvements-to-ingestion-in-general">#</a> Verbesserungen bei der Aufnahme im Allgemeinen

Diese Version enthält die folgenden Verbesserungen für die Aufnahme im Allgemeinen.

<a name="24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management" href="#24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management">#</a> Erhöhte Robustheit für die Aufgabenverwaltung

setNumProcessorsPerTask hinzugefügt, um zu verhindern, dass verschiedene automatisch dimensionierte Thread-Pools unangemessen groß werden. Es ist nicht für jede Aufgabe ideal, ihre Pools so zu dimensionieren, als wäre es der einzige Prozess auf der gesamten Maschine. Auf großen Maschinen wird dadurch eine häufige Ursache von OutOfMemoryError behoben, da „ein nativer Thread nicht erstellt werden konnte“. #12592

<a name="24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver" href="#24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver">#</a> Avatica JDBC-Treiber

Druid akzeptiert jetzt die EIGHT_HOUR-Granularität. Sie können eingehende Daten in EIGHT_HOUR-Buckets segmentieren und Abfrageergebnisse mit einer Granularität von acht Stunden gruppieren. #12717

<a name="24.0.0-ingestion-general-updated-avro-extension" href="#24.0.0-ingestion-general-updated-avro-extension">#</a> Avro-Erweiterung aktualisiert

Die vorherige Avro-Erweiterung hat Objekte aus dem Parser durchgesickert. Wenn diese Objekte in Ihre Aufnahme gelangten, wurden die Objekte als Zeichenfolgenspalte mit dem Wert .toString() gespeichert. Diese Zeichenfolgenspalte bleibt nach dem Upgrade bestehen, gibt jedoch Map.toString() anstelle von GenericRecord.toString zurück. Wenn Sie sich auf das vorherige Verhalten verlassen haben, können Sie die Avro-Erweiterung aus einer früheren Version verwenden. #12828

<a name="24.0.0-ingestion-general-sampler-api" href="#24.0.0-ingestion-general-sampler-api">#</a> Probenehmer API

Der Sampler API verfügt über zusätzliche Grenzwerte: maxBytesInMemory und maxClientResponseBytes. Diese Optionen ergänzen die bestehenden Optionen numRows und timeoutMs. maxBytesInMemory kann verwendet werden, um die Speichernutzung auf dem Overlord während des Samplings zu steuern. maxClientResponseBytes kann von clients verwendet werden, um die maximale Größe der Antwort anzugeben, die sie lieber verarbeiten möchten. #12947

<a name="24.0.0-sql" href="#24.0.0-sql">#</a> SQL

<a name="24.0.0-sql-column-order" href="#24.0.0-sql-column-order">#</a> Spaltenreihenfolge

Die Eigenschaften DruidSchema und SegmentMetadataQuery behalten jetzt die Spaltenreihenfolge bei, anstatt die Spalten alphabetisch zu ordnen. Dies bedeutet, dass die Abfragereihenfolge besser mit der Aufnahmereihenfolge übereinstimmt. #12754

<a name="24.0.0-sql-converting-joins-to-filter" href="#24.0.0-sql-converting-joins-to-filter">#</a> JOINs in Filter konvertieren

Sie können die Leistung verbessern, indem Sie JOINs zur Laufzeit teilweise oder vollständig als Filter in die Basistabelle verschieben, indem Sie den Kontextparameter enableRewriteJoinToFilter für eine Abfrage auf true setzen. Druid verschiebt nun Join-Filter nach unten, falls die Abfrage, die den Join berechnet, auf Spalten auf der rechten Seite verweist. #12749 #12868

<a name="24.0.0-sql-add-is_active-to-sys.segments" href="#24.0.0-sql-add-is_active-to-sys.segments">#</a> is_active zu sys.segments hinzufügen

is_active als Abkürzung für (is_published = 1 AND is_overshadowed = 0) OR is_realtime = 1) hinzugefügt. Dies stellt „alle Segmente dar, die abfragbar sein sollten, unabhängig davon, ob dies jetzt tatsächlich der Fall ist oder nicht“. #11550

<a name="24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true" href="#24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true">#</a> useNativeQueryExplain ist jetzt standardmäßig auf „true“ eingestellt

Die Eigenschaft useNativeQueryExplain ist jetzt standardmäßig true. Das bedeutet, dass EXPLAIN PLAN FOR den EXPLAIN-Plan standardmäßig als JSON-Darstellung äquivalenter nativer Abfrage(n) zurückgibt. Weitere Informationen finden Sie unter Broker Generated Query Configuration Supplementation. #12936

<a name="24.0.0-inline-query-engine" href="#24.0.0-inline-query-engine">#</a> Ausführen von Abfragen mit Inline-Daten mithilfe der Druid-Abfrage-Engine

Einige Abfragen, die auf keine Tabelle verweisen, wie z. B. select 1, werden jetzt vor der Ausführung immer mit InlineDataSource in eine native Druid-Abfrage übersetzt. Wenn bei Abfragen wie SELECT (1, 2) keine Übersetzung möglich ist, tritt ein Fehler auf. In früheren Versionen wurde diese Abfrage noch ausgeführt. #12897

<a name="24.0.0-coordinator%2Foverlord" href="#24.0.0-coordinator%2Foverlord">#</a> Koordinator/Overlord

<a name="24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future" href="#24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future">#</a> Sie können den Koordinator so konfigurieren, dass er in Zukunft Segmente tötet

Sie können druid.coordinator.kill.durationToRetain jetzt auf einen negativen Zeitraum festlegen, um den Druid-Cluster so zu konfigurieren, dass Segmente gelöscht werden, deren interval_end ein Datum in der Zukunft ist. Beispielsweise würde PT-24H das Beenden von Segmenten zulassen, wenn deren Intervallenddatum zum Zeitpunkt der Generierung der Kill-Aufgabe durch das System 24 Stunden oder weniger in der Zukunft lag. Ein Clusterbetreiber kann den druid.coordinator.kill.durationToRetain auch vollständig ignorieren, indem er eine neue Konfiguration, druid.coordinator.kill.ignoreDurationToRetain=true, festlegt. Dies ignoriert das interval_end-Datum bei der Suche nach zu löschenden Segmenten und kann stattdessen jedes als nicht verwendet markierte Segment löschen. Diese neue Konfiguration ist standardmäßig deaktiviert und ein Clusterbetreiber sollte die Risiken vollständig verstehen und akzeptieren, bevor er sie aktiviert.

<a name="24.0.0-coordinator%2Foverlord-improved-overlord-stability" href="#24.0.0-coordinator%2Foverlord-improved-overlord-stability">#</a> Verbesserte Overlord-Stabilität

Reduzierte Konflikte zwischen dem Verwaltungsthread und dem Empfang von Statusaktualisierungen vom Cluster. Dies verbessert die Stabilität von Overlord und allen Aufgaben in einem Cluster, wenn die Anzahl der Aufgaben groß ist (1000+). #12099

<a name="24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging" href="#24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging">#</a> Verbesserte Coordinator-Segmentprotokollierung

Die Protokollierung der Coordinator-Laderegeln wurde aktualisiert, um die aktuellen Replikationsebenen einzubeziehen. Fehlende Segment-ID- und Tier-Informationen aus einigen Protokollmeldungen hinzugefügt. #12511

<a name="24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage" href="#24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage">#</a> Speichernutzung für Overlord-GET-Aufgaben optimiert

Der erhebliche Speicheraufwand, der durch den indirekten Aufruf der GET-Aufgaben API des Overlords durch die Webkonsole verursacht wurde, wurde behoben. Dies könnte dazu führen, dass der Server nicht mehr reagiert oder Overlord ausfällt, wenn die Registerkarte „Aufnahme“ mehrmals geöffnet wird. #12404

<a name="24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals" href="#24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals">#</a> Reduzierte Zeit zum Erstellen von Intervallen

Um die Berechnungszeit der Segmentkosten zu optimieren, indem die für die Intervallerstellung benötigte Zeit reduziert wird, speichern Sie das Segmentintervall, anstatt es jedes Mal aus Grundelementen zu erstellen, und reduzieren Sie den Speicheraufwand beim Speichern von Intervallen, indem Sie diese internieren. Die Menge der Intervalle für Segmente weist eine niedrige Kardinalität auf. #12670

<a name="24.0.0--brokers%2Foverlord" href="#24.0.0--brokers%2Foverlord">#</a> Makler/Overlord

Broker haben jetzt standardmäßig eine maximale Warteschlange von 25 MB pro Abfrage. Bisher gab es kein Standardlimit. Abhängig von Ihrem Anwendungsfall müssen Sie möglicherweise den Wert erhöhen, insbesondere wenn Sie große Ergebnismengen oder große Mengen an Zwischendaten haben. Um den maximal verfügbaren Speicher anzupassen, verwenden Sie die Eigenschaft druid.broker.http.maxQueuedBytes. Weitere Informationen finden Sie unter Konfigurationsreferenz.

<a name="24.0.0--brokers%2Foverlord-web-console" href="#24.0.0--brokers%2Foverlord-web-console">#</a> Webkonsole

Bereiten Sie sich auf ein noch besseres Erlebnis mit der Webkonsole vor! - @vogievetsky

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support">#</a> Neue Abfrageansicht (WorkbenchView) mit Registerkarten und Unterstützung für lang laufende Abfragen

Sie können die neue Abfrageansicht verwenden, um mehrstufige, aufgabenbasierte Abfragen mit den APIs /druid/v2/sql/task und /druid/indexer/v1/task/* sowie native und SQL-native Abfragen auszuführen, genau wie die alte Abfrageansicht. Ein wichtiger Punkt der SQL-MSQ-Task-basierten Abfragen ist, dass sie möglicherweise lange ausgeführt werden. Dies hat viele UX-Änderungen inspiriert/erforderlich gemacht, darunter unter anderem die folgenden:

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-tabs" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-tabs">#</a> Tabs

Sie können jetzt viele Abfragen gleichzeitig speichern und ausführen, wodurch die Benutzeroberfläche der Abfrageansicht erheblich verbessert wird. Sie können mehrere Registerkarten öffnen, sie duplizieren und als Text kopieren, um sie in eine beliebige Konsole einzufügen und dort erneut zu öffnen.

<a name="24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure" href="#24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure">#</a> Aktualisierung zum Schließen der JDBC-Anweisung

In früheren Versionen hat Druid die JDBC-Anweisung automatisch geschlossen, wenn das ResultSet geschlossen wurde. Druid hat das ResultSet auf EOF geschlossen. Druid schloss die Stellungnahme zu jeder Ausnahme ab. Dieses Verhalten ist jedoch nicht standardmäßig. In dieser Version folgt der JDBC-Treiber von Druid den JDBC-Standards stärker: Das ResultSet wird bei EOF automatisch geschlossen, schließt jedoch nicht das Statement oder PreparedStatement. Ihr Code muss diese Anweisungen schließen, möglicherweise mithilfe eines Try-with-Resources-Blocks. Das PreparedStatement kann nun mehrfach mit unterschiedlichen Parametern verwendet werden. (Früher war dies nicht der Fall, da durch das Schließen des ResultSets das PreparedStatement geschlossen wurde.) Wenn ein Aufruf einer Anweisung oder eines PreparedStatement einen Fehler auslöst, muss der client-Code die Anweisung trotzdem explizit schließen. Gemäß den JDBC-Standards werden Anweisungen bei Fehlern nicht automatisch geschlossen. Auf diese Weise können Sie Informationen über eine fehlgeschlagene Anweisung abrufen, bevor Sie diese schließen. Wenn Sie Code haben, der vom alten Verhalten abhängt, müssen Sie Ihren Code möglicherweise ändern, um die erforderliche Close-Anweisung hinzuzufügen. #12709

<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> Multi-stage query task engine

SQL-based ingestion for Apache Druid uses a distributed multi-stage query architecture, which includes a query engine called the multi-stage query task engine (MSQ task engine). The MSQ task engine extends Druid's query capabilities, so you can write queries that reference external data as well as perform ingestion with SQL INSERT and REPLACE. Essentially, you can perform SQL-based ingestion instead of using JSON ingestion specs that Druid's native ingestion uses. In addition to the easy-to-use syntax, the SQL interface lets you perform transformations that involve multiple shuffles of data.

SQL-based ingestion using the multi-stage query task engine is recommended for batch ingestion starting in Druid 24.0.0. Native batch and Hadoop-based ingestion continue to be supported as well. To read external data using the multi-stage query task engine, you must have READ permissions for the EXTERNAL resource type. Users without the correct permission encounter a 403 error when trying to run SQL queries that include EXTERN.

Druid automatically retains any segments marked as unused. Previously, Druid permanently deleted unused segments from metadata store and deep storage after their duration to retain passed. This behavior was reverted from 0.23.0. #12693

<a name="24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60" href="#24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60">#</a> Default for druid.processing.fifo

The default for druid.processing.fifo is now true. This means that tasks of equal priority are treated in a FIFO manner. For most use cases, this change can improve performance on heavily loaded clusters.

#12571

<a name="24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure" href="#24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure">#</a> Update to JDBC statement closure

In previous releases, Druid automatically closed the JDBC Statement when the ResultSet was closed. Druid closed the ResultSet on EOF. Druid closed the statement on any exception. This behavior is, however, non-standard. In this release, Druid's JDBC driver follows the JDBC standards more closely: The ResultSet closes automatically on EOF, but does not close the Statement or PreparedStatement. Your code must close these statements, perhaps by using a try-with-resources block. The PreparedStatement can now be used multiple times with different parameters. (Previously this was not true since closing the ResultSet closed the PreparedStatement.) If any call to a Statement or PreparedStatement raises an error, the client code must still explicitly close the statement. According to the JDBC standards, statements are not closed automatically on errors. This allows you to obtain information about a failed statement before closing it. If you have code that depended on the old behavior, you may have to change your code to add the required close statement.
