Druide Druide-0.7.0

Aktualisierung auf Druid 0.7.0 – Dinge, die Sie beachten sollten

  • Neue Aufnahmespezifikation Druid 0.7.0 erfordert ein neues Aufnahmespezifikationsformat. Druid 0.6.172 unterstützt sowohl das alte als auch das neue Aufnahmeformat und verfügt über Skripte zum Konvertieren vom alten in das neue Format. Dieses Skript kann mit „tools ConvertSpec“ ausgeführt werden, wobei dasselbe Main verwendet wird, das auch für die Ausführung von Druid-Knoten verwendet wird. Sie können Ihren Druid-Cluster auf 0.6.172 aktualisieren, Ihre Aufnahmespezifikationen auf das neue Format aktualisieren und dann auf Druid 0.7.0 aktualisieren. Wenn Sie Ihren Cluster direkt auf Druid 0.7.0 aktualisieren, stellen Sie sicher, dass Ihre Echtzeit-Aufnahmepipeline die neue Spezifikation versteht.
  • MySQL ist nicht mehr der Standard-Metadatenspeicher Druid bettet jetzt standardmäßig Apache Derby ein, was hauptsächlich aus Gründen der Testbarkeit ausgewählt wurde. Wir empfehlen jedoch nicht, Derby in der Produktion zu verwenden. Für andere Zwecke als Tests verwenden Sie bitte den Metadatenspeicher MySQL oder PostgreSQL. Konfigurationsparameter für die Metadatenspeicherung wurden von druid.db in druid.metadata.storage umbenannt und ein zusätzlicher druid.metadata.storage.type=<mysql|postgresql> ist erforderlich, um etwas anderes als Derby zu verwenden. Das Tool convertProps kann Sie bei der Konvertierung aller 0.6.x-Eigenschaften in 0.7-Eigenschaften unterstützen.
  • Druid unterscheidet jetzt zwischen Groß- und Kleinschreibung Bei Druid-Spaltennamen muss jetzt die Groß-/Kleinschreibung beachtet werden. Bisher haben wir versucht, bei Abfragen die Groß-/Kleinschreibung zu ignorieren und bei Daten die Groß-/Kleinschreibung beizubehalten. Wir haben uns jedoch zu dieser Änderung entschieden, da es zahlreiche Fehler im Zusammenhang mit verschiedenen Problemen mit der Groß-/Kleinschreibung gab. Wenn Sie ein Upgrade von der Version 0.6.x durchführen:
    1. Bitte stellen Sie sicher, dass die Groß-/Kleinschreibung der Spalten in Ihren Abfragen mit der Groß-/Kleinschreibung Ihrer Spaltennamen in Ihren Daten übereinstimmt, und aktualisieren Sie Ihre Abfragen entsprechend.
    2. Es ist sehr wichtig zu beachten, dass 0.6 alle Spaltennamen zum Zeitpunkt der Aufnahme und Abfrage intern in Kleinbuchstaben schreibt. In 0.7 ist dies nicht mehr der Fall. Wir empfehlen jedoch der Einfachheit halber weiterhin dringend, in 0.7 Spaltennamen in Kleinbuchstaben zu verwenden.
    3. Wenn Sie derzeit Daten mit Spaltennamen in gemischter Groß- und Kleinschreibung als Teil Ihres Daten- oder Aufnahmeschemas aufnehmen: – Schreiben Sie für TSV- oder CSV-Daten einfach die Spaltennamen in Ihrem Schema in Kleinbuchstaben, wenn Sie auf 0.7.0 aktualisieren. – Für JSON-Daten mit Feldern mit gemischter Groß-/Kleinschreibung und wenn Sie die Namen der Spalten nicht angegeben haben, können Sie jsonLowerCase parseSpec verwenden, um die Daten zum Zeitpunkt der Aufnahme in Kleinbuchstaben zu schreiben und die Abwärtskompatibilität aufrechtzuerhalten. Für alle anderen Analysespezifikationen müssen Sie das in Kleinbuchstaben schreiben Metrik-/Aggregatornamen, wenn Sie zuvor gemischte Groß- und Kleinschreibung verwendet haben.
  • Batch-Segmentankündigung ist jetzt die Standardeinstellung Druid verwendet jetzt standardmäßig die Batch-Segmentankündigung für alle Knoten. Wenn Sie Batch-Segmentankündigung bereits verwenden, sollten Sie bereit sein. Wenn Sie noch nicht auf die Verwendung der Batch-Segment-Ankündigung umgestellt haben, lesen Sie bitte [diese Anleitung im Forum] (https://groups.google.com/forum/#!searchin/druid-development/eric$200.5$20batch$20segment/druid-development/vKV8pTAd0Gg/VgC8ee6XWZ0J), um zu erfahren, wie Sie Ihren aktuellen 0.6.x-Cluster zunächst auf die Verwendung der Batch-Segment-Ankündigung aktualisieren.
  • Kafka 0.7.x wurde zugunsten von Kafka 0.8.x entfernt Wenn Sie Kafka 0.7 verwenden, müssen Sie die kafka-seven-Erweiterung manuell erstellen. Es ist im Build auskommentiert, da Kafka 0.7 in Maven Central nicht verfügbar ist. Die Kafka-Erweiterung 0.8 (kafka-eight) ist nicht betroffen.
  • Änderungen am Koordinator-Endpunkt Zahlreiche Koordinatorendpunkte haben sich geändert. Welche das sind, entnehmen Sie bitte der Koordinatordokumentation. Insbesondere:
  1. /info auf dem Koordinator wurde entfernt.
  2. /health auf historischen Knoten wurde entfernt
  • Separater Behälter für com.metamx.metrics.SysMonitor erforderlich Wenn Sie derzeit com.metamx.metrics.SysMonitor als Teil Ihrer druid.monitoring.monitors-Konfiguration haben und es behalten möchten, müssen Sie das [SIGAR-Bibliotheks-JAR] (https://repository.jboss.org/nexus/content/repositories/thirdparty-uploads/org/hyperic/sigar/1.6.5.132/sigar-1.6.5.132.jar) zu Ihrem Klassenpfad hinzufügen. Alternativ können Sie com.metamx.metrics.SysMonitor einfach entfernen, wenn Sie sich nicht auf die sys/.*-Metriken verlassen. Wir mussten die direkte Abhängigkeit von SIGAR entfernen, um Druid-Artefakte nach Maven Central zu verschieben, da SIGAR dort derzeit nicht verfügbar ist.
  • Aktualisierungsverfahren Wenn Sie eine ältere Version von Druid als 0.6.172 verwenden, aktualisieren Sie bitte zuerst auf 0.6.172. Anweisungen finden Sie in den 0.6.172 release notes. Um ein reibungsloses Upgrade ohne Ausfallzeiten zu gewährleisten, müssen Knoten in der folgenden Reihenfolge aktualisiert werden:
    1. historische Knoten
    2. Indexierungsdienst/Echtzeitknoten
    3. Router-Knoten (falls vorhanden),
    4. Brokerknoten
    5. Koordinatorknoten

Neue Funktionen

  • Unterstützung für lange metrische Spalten Bisher speicherte Druid alle Metriken als Gleitkommawerte mit einfacher Genauigkeit, was bei Abfragen mit longSum-Aggregatoren zu Rundungsfehlern und unerwarteten Ergebnissen führen konnte, insbesondere bei GroupBy-Abfragen.
  • Ansteckbarer Metadatenspeicher MySQL, PostgreSQL und Derby (zum Testen) werden jetzt sofort unterstützt. Derby unterstützt nur einen einzelnen Master oder sollte nicht für die Hochverfügbarkeitsproduktion verwendet werden. Verwenden Sie dazu das Failover MySQL oder PostgreSQL.
  • Vereinfachte Datenaufnahme API Druids Datenaufnahme API komplett wiederholen.
  • Komprimierung für metrische Spalten von LZF auf LZ4 umstellen Erste Leistungstests zeigen, dass es zwischen 15 und 25 % schneller sein kann und bei typischen Datensätzen zu etwa 3 bis 5 % kleineren Segmenten führt.
  • Konfigurierbare invertierte Bitmap-Indizes Druid unterstützt jetzt zusätzlich zu den standardmäßigen Concise Bitmaps auch Roaring Bitmaps. Erste Leistungstests zeigen, dass Roaring bei bestimmten Abfragetypen bis zu 20 % schneller sein kann, auf Kosten der durchschnittlich 20 % größeren Segmente.
  • Integrationstests Wir haben eine Reihe von Integrationstests hinzugefügt, die Docker verwenden, um einen Druid-Cluster zu starten und eine Reihe von Indizierungs- und Abfragetests auszuführen.
  • Neue Druiden-Koordinator-Konsole Wir haben eine neue Druid-Konsole eingeführt, die hoffentlich einen besseren Überblick über den Status Ihres Clusters bieten und etwas skalierbarer sein soll, wenn Sie Hunderttausende Segmente haben. Wir planen, diese Konsole zu erweitern, um mehr Informationen über den aktuellen Status eines Druid-Clusters bereitzustellen.
  • Kontext des Abfrageergebnisses Ergebniskontexte können Fehler bei Abfragen in den Abfrageheadern melden. Wir verwenden diese Funktion derzeit für interne Wiederholungsversuche, hoffen jedoch, sie erweitern zu können, um mehr Informationen an clients zu melden.

Verbesserungen

  • Schnellere Abfragegeschwindigkeiten Viele Geschwindigkeitsverbesserungen dank schnellerem Komprimierungsformat, kleinen Optimierungen in der Spaltenstruktur und Optimierungen von Abfragen mit mehreren Aggregationen sowie zahlreichen Verbesserungen der GroupBy-Abfrageleistung. Insgesamt können einige Abfragen mit dem neuen Indexformat bis zu doppelt so schnell sein.
  • Druidenartefakte in Maven Central Druidenartefakte sind jetzt [in Maven Central verfügbar] (http://search.maven.org/#search%7Cga%7C1%7Cio.druid), um Ihre eigenen Builds und Bereitstellungen zu vereinfachen.
  • Gemeinsame Konfigurationsdatei Druid verfügt jetzt über eine common.runtime.properties, in der Sie alle globalen Eigenschaften sowie alle Ihre externen Abhängigkeiten deklarieren können. Dies vermeidet eine wiederholte Konfiguration über mehrere Knoten hinweg und macht die Einrichtung eines Druid-Clusters hoffentlich etwas weniger mühsam.
  • Standard-Hostnamen, Port- und Dienstnamen Standardmäßige Hostnamen, Ports und Dienstnamen für alle Knoten bedeuten, dass im Vorfeld viel weniger Konfiguration erforderlich ist, wenn Sie mit den Standardeinstellungen zufrieden sind. Dies bedeutet auch, dass Sie alle Knotentypen auf einem einzigen Computer ausführen können, ohne sich mit Portkonflikten herumschlagen zu müssen.
  • Druidenspaltennamen unterscheiden jetzt zwischen Groß- und Kleinschreibung Tod für Gehäusewanzen. Beachten Sie die Gefahren einer Aktualisierung auf 0.7.0, wenn Sie Spalten mit gemischter Groß-/Kleinschreibung haben und 0.6.x verwenden. Weitere Einzelheiten finden Sie oben.
  • Abfragewiederholungen Druid wiederholt Abfragen jetzt automatisch für bestimmte Fehlerklassen.
  • Hintergrund-Caching Bei bestimmten Arten von Abfragen, insbesondere solchen, die unterschiedliche (Hyperloglog-)Zählungen beinhalten, kann dies die Leistung um über 20 % steigern. Das Hintergrund-Caching ist standardmäßig deaktiviert.
  • Reduzierte Koordinator-Speichernutzung Reduzierte Speichernutzung des Koordinators (um bis zu 50 %). Dies behebt ein Problem, bei dem ein Koordinator aufgrund häufiger GCs manchmal die Führung verlor.
  • Metriken können jetzt an SSL-Endpunkte ausgegeben werden
  • Zusätzliche Unterstützung für AWS-Anmeldeinformationen, Danke @gnetercutt
  • Zusätzliche Persistenz- und Drosselungsmetriken für die Echtzeitaufnahme Dies soll dabei helfen, zu diagnostizieren, wann die Echtzeitaufnahme gedrosselt wird und wie lange das Fortbestehen dauert. Diese Kennzahlen geben einen guten Hinweis darauf, wann es an der Zeit ist, die Echtzeitaufnahme auszuweiten.
  • Broker-Initialisierungsendpunkt Broker stellen jetzt einen Statusendpunkt unter /druid/broker/v1/loadstatus bereit, um anzuzeigen, ob sie zur Abfrage bereit sind, was fortlaufende Upgrades/Neustarts einfacher macht.

Fehlerbehebungen

  • Unterstützen Sie mehrere Shards derselben Datenquelle auf demselben Echtzeitknoten. Danke @zhaown – HDFS-Aufgabenprotokolle sollten jetzt wie erwartet funktionieren. Danke @flowbehappy. – Möglicher Deadlock-Zustand im Broker behoben.
  • Verschiedene Korrekturen für die GZIP-Komprimierung bei der Rückgabe von Ergebnissen.
  • druid.host sollte jetzt auch IPv6-Adressen unterstützen.

Dokumentation

  • Neue Tutorials.
  • Neue Aufnahmedokumentation.
  • Neue Konfigurationsdokumentation.
  • Verbesserungen an der Regeldokumentation. Danke @mrijke

Bekannte Probleme

– Das Zusammenführen von Segmenten mit unterschiedlichen Arten von Bitmap-Indizes ist derzeit nicht möglich. Wenn Sie also beide Arten von Indizes in Ihrem Cluster haben, müssen Sie druid.coordinator.merge.on auf „false“ setzen. „false“ ist der Standardwert der Konfiguration. – https://github.com/druid-io/druid/issues/1045 Problem mit GoupBy-Abfragen mit komplexen Aggregationen und Post-Aggregationen, die denselben Namen verwenden – https://github.com/druid-io/druid-api/pull/38 Wenn Sie longSum in Ihrer Aufnahmespezifikation verwenden, können Gleitkommadaten Ausnahmen auslösen.

Englisches Original / English original

druid druid-0.7.0

Updating to Druid 0.7.0 – Things to be Aware

  • New ingestion spec

    Druid 0.7.0 requires a new ingestion spec format. Druid 0.6.172 supports both the old and new formats of ingestion and has scripts to convert from the old to the new format. This script can be run with 'tools convertSpec' using the same Main used to run Druid nodes. You can update your Druid cluster to 0.6.172, update your ingestion specs to the new format, and then update to Druid 0.7.0. If you update your cluster to Druid 0.7.0 directly, make sure your real-time ingestion pipeline understands the new spec.

  • MySQL is no longer the default metadata storage

    Druid now defaults to embedding Apache Derby, which was chosen mainly for testability purposes. However, we do not recommend using Derby in production. For anything other than testing, please use MySQL or PostgreSQL metadata storage.

    Configuration parameters for metadata storage were renamed from druid.db to druid.metadata.storage and an additional druid.metadata.storage.type=<mysql|postgresql> is required to use anything other than Derby.

    The convertProps tool can assis you in convertng all 0.6.x properties to 0.7 properties.

  • Druid is now case-sensitive

    Druid column names are now case-sensitive. We previously tried to be case-insensitive for queries and case-preserving for data, but we decided to make this change as there were numerous bugs related to various casing problems.

    If you are upgrading from version 0.6.x:

    1. Please make sure the column casing in your queries matches the casing of your column names in your data and update your queries accordingly.
    2. One very important thing to note is that 0.6 internally lower-cased all column names at ingestion time and query time. In 0.7, this is no longer the case, however, we still strongly recommend that you use lowercase column names in 0.7 for simplicity.
    3. If you are currently ingesting data with mixed case column names as part of your data or ingestion schema:
      • for TSV or CSV data, simply lower-case your column names in your schema when you update to 0.7.0.
      • for JSON data with mixed case fields and if you were not specifying the names of the columns, you can use the jsonLowerCase parseSpec to lower-case the data for you at ingestion time and maintain backwards compatibility.

    For all other parse specs, you will need to lower-case the

    metric/aggregator names if you were using mixed case before.

  • Batch segment announcement is now the default

    Druid now uses batch segment announcement by default for all nodes. If you are already using batch segment announcement, you should be all set.

    If you have not yet updated to using batch segments announcement, please read this guide in the forum on how to update your current 0.6.x cluster to use batch announcement first.

  • Kafka 0.7.x removed in favor of Kafka 0.8.x

    If you are using Kafka 0.7, you will have to build the kafka-seven extension manually. It is commented out in the build, because Kafka 0.7 is not available in Maven Central. The Kafka 0.8 (kafka-eight) extension is unaffected.

  • Coordinator endpoint changes

    Numerous coordinator endpoints have changed. Please refer to the coordinator documentation for what they are.

    In particular:

    1. /info on the coordinator has been removed.
    2. /health on historical nodes has been removed

  • Separate jar required for com.metamx.metrics.SysMonitor

    If you currenly have com.metamx.metrics.SysMonitor as part of your druid.monitoring.monitors configuration and would like to keep it, you will have to add the SIGAR library jar to your classpath.

    Alternatively, you can simply remove com.metamx.metrics.SysMonitor if you do not rely on the sys/.* metrics.

    We had to remove the direct dependency on SIGAR in order to move Druid artifacts to Maven Central, since SIGAR is currently not available there.

  • Update Procedure

    If you are running a version of Druid older than 0.6.172, please upgrade to 0.6.172 first. See the 0.6.172 release notes for instructions.

    In order to ensure a smooth rolling upgrade without downtime, nodes must be updated in the following order:

    1. historical nodes
    2. indexing service/real-time nodes
    3. router nodes (if you have any),
    4. broker nodes
    5. coordinator nodes

New Features

  • Long metric column support

    Until now Druid stored all metrics as single precision floating point values, which could introduce rounding errors and unexpected results with queries using longSum aggregators, especially for groupBy queries.

  • Pluggable metadata storage

    MySQL, PostgreSQL, and Derby (for testing) are now supported out of the box. Derby only supports single master or should not be used for high availability production, use MySQL or PostgreSQL failover for that.

  • Simplified data ingestion API

    completely redo Druid’s data ingestion API.

  • Switch compression for metric colums from LZF to LZ4

    Initial performance tests show it may be between 15% and 25% faster, and results in segments about 3-5% smaller on typical data sets.

  • Configurable inverted bitmap indexes

    Druid now supports Roaring Bitmaps in addition to the default Concise Bitmaps. Initial performance tests show Roaring may be up to 20% faster for certain types of queries, at the expense of segments being 20% larger on average.

  • Integration tests

    We have added a set of integration tests that use Docker to spin up a Druid cluster to run a series of indexing and query tests.

  • New Druid Coordinator console

    We introduced a new Druid console that should hopefully provide a better overview of the status of your cluster and be a bit more scalable if you have hundreds of thousands of segments. We plan to expand this console to provide more information about the current state of a Druid cluster.

  • Query Result Context

    Result contexts can report errors during queries in the query headers. We are currently using this feature for internal retries, but hope to expand it to report more information back to clients.

Improvements

  • Faster query speeds

    Lots of speed improvements thanks to faster compression format, small optimizations in column structure, and optimizations of queries with multiple aggregations, as well as numerous groupBy query performance improvements. Overall, some queries can be up to twice as fast using the new index format.

  • Druid artifacts in Maven Central

    Druid artifacts are now available in Maven Central to make your own builds and deployments easier.

  • Common Configuration File

    Druid now has a common.runtime.properties where you can declare all global properties as well as all of your external dependencies. This avoids repeated configuration across multiple nodes and will hopefully make setting up a Druid cluster a little less painful.

  • Default host names, port and service names

    Default host names, ports, and service names for all nodes means a lot less configuration is required upfront if you are happy with the defaults. It also means you can run all node types on a single machine without fiddling with port conflicts.

  • Druid column names are now case sensitive

    Death to casing bugs. Be aware of the dangers of updating to 0.7.0 if you have mixed case columns and are using 0.6.x. See above for more details.

  • Query Retries

    Druid will now automatically retry queries for certain classes of failures.

  • Background caching

    For certain types of queries, especially those that involve distinct (hyperloglog) counts, this can improve performance up over 20%. Background caching is disabled by default.

  • Reduced coordinator memory usage

    Reduced coordinator memory usage (by up to 50%). This fixes a problem where a coordinator would sometimes lose leadership due to frequent GCs.

  • Metrics can now be emitted to SSL endpoints

  • Additional AWS credentials support, Thanks @gnethercutt

  • Additional persist and throttle metrics for real-time ingestion

    This should help diagnose when real-time ingestion is being throttled and how long persists are taking. These metrics provide a good indication of when it is time to scale up real-time ingestion.

  • Broker initialization endpoint

    Brokers now provides a status endpoint at /druid/broker/v1/loadstatus to indicate whether they are ready to be queried, making rolling upgrades / restarts easier.

Bug Fixes

  • Support multiple shards of the same datasource on the same realtime node. Thanks @zhaown
  • HDFS task logs should now work as expected. Thanks @flowbehappy.
  • Possible deadlock condition fixed in the Broker.
  • Various fixes for GZIP compression in returning results.
  • druid.host should now support IPv6 addresses as well.

Documentation

  • New tutorials.
  • New ingestion documentation.
  • New configuration documentation.
  • Improvements to rule documentation. Thanks @mrijke

Known issues

  • Merging segments with different types of bitmap indices is currently not possible, so if you have both types of indices in your cluster, you must set druid.coordinator.merge.on to false. ‘false’ is the default value of the config.
  • https://github.com/druid-io/druid/issues/1045 Issue with GoupBy queries with complex aggregations and post-aggregations using the same name
  • https://github.com/druid-io/druid-api/pull/38 If you are using longSum in your ingestion spec, having floating point data may throw exceptions.
