## Torch.compile
### Spezialisierung einer Tensorform mit angewendetem `mark_dynamic` weist jetzt korrekte Fehler auf (#152661)
Vor 2.8 war es möglich, dass eine Schutzvorrichtung auf einer symbolischen Form falsch war
entfällt, wenn die symbolische Formauswertung zuvor mit Schutzvorrichtungen getestet wurde
unterdrückt (dies geschieht häufig im Compiler selbst). Dies wurde behoben
in 2.8 und wird normalerweise stillschweigend „das Richtige tun“ und das Richtige hinzufügen
bewachen. Wenn jedoch der neue Wächter dazu führt, dass ein mit `mark_dynamic` gekennzeichneter Tensor entsteht
spezialisiert, kann dies zu einem Fehler führen. Eine Problemumgehung ist die Verwendung
`maybe_mark_dynamic` statt `mark_dynamic`.
Weitere Informationen finden Sie in der Diskussion in Ausgabe Nr. 157921
Kontext.
Version 2.7.0
```python
import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Version 2.8.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

NVTX3-Code wurde von cmake/public/cuda.cmake nach cmake/Dependencies.cmake verschoben (#151583)

Dies ist eine BC-bahnbrechende Änderung für die Build-Systemschnittstelle. Downstream-Projekte, die zuvor NVTX3 über cmake/public/cuda.cmake erhalten haben (d. h. Aufruf von find_package(TORCH REQUIRED)) muss nun explizit die NVTX3-Unterstützung in der Bibliothek selbst konfigurieren (d. h. USE_SYSTEM_NVTX=1 verwenden). Die Änderung besteht darin, das fehlerhafte Verhalten zu beheben, bei dem Downstream-Projekte NVTX3 aufgrund der Nichtübereinstimmung von PROJECT_SOURCE_DIR ohnehin nicht finden konnten. Version 2.7.0: – Ein Downstream-Projekt, das -DUSE_SYSTEM_NVTX verwendet, könnte NVTX3 und torch::nvtx3 über die cmake/public/cuda.cmake-Logik von PyTorch finden. – Bei einem Downstream-Projekt, das -DUSE_SYSTEM_NVTX NICHT verwendet, würden Buildfehler mit CUDA 12.8 oder höher auftreten. Version 2.8.0: – Ein Downstream-Projekt, das -DUSE_SYSTEM_NVTX verwendet, kann NVTX3 oder torch::nvtx3 nicht über cmake/public/cuda.cmake von PyTorch finden. Das Downstream-Projekt muss nun NVTX3 und Torch::nvtx3 explizit finden, indem es dieselbe Logik in PyTorchs cmake/Dependences.cmake implementiert. – Ein Downstream-Projekt, das -DUSE_SYSTEM_NVTX NICHT verwendet, wird ohne NVTX mit der Erstellung fortfahren, es sei denn, ein anderer Teil des Erstellungsprozesses aktiviert NVTX erneut.

Abwertungen

MPS-Unterstützung für MacOS Ventura wird in 2.9 entfernt

PyTorch 2.8 ist die letzte Version, die GPU-Beschleunigung unter MacOS Ventura unterstützt. Im nächsten Für die Verwendung des MPS ist die neueste Version (2.9), MacOS Sonoma (veröffentlicht im September 2023) oder höher erforderlich Backend.

torch.ao.quantization ist veraltet und wird in 2.10 entfernt (#153892)

Zum Migrieren:

  • Quantisierung im Eager-Modus (torch.ao.quantization.quantize, torch.ao.quantization.quantize_dynamic)
    • Nur Gewichtung und dynamische Quantisierung: Verwenden Sie den Eager-Modus torchao quantize_.
    • Statische Quantisierung: Verwenden Sie die torchao PT2E-Quantisierung.
  • Quantisierung im FX-Graph-Modus (torch.ao.quantization.quantize_fx.prepare_fx, torch.ao.quantization.quantize_fx.convert_fx): Verwenden Sie die PT2E-Quantisierung torchao (torchao.quantization.quantize_pt2e.prepare_pt2e, torchao.quantization.quantize_pt2e.convert_pt2e). Beachten Sie, dass die PT2E-Quantisierung auf torchao (https://github.com/pytorch/ao/tree/main/torchao/quantization/pt2e) migriert wurde. Weitere Einzelheiten finden Sie unter https://github.com/pytorch/ao/issues/2259 und https://docs.pytorch.org/ao/main/quick_start.html#pytorch-2-export-quantization.

Die Option dynamo=False (aktueller Standard) für torch.onnx.export ist veraltet (#152478, #155580)

Der Standardwert ist dynamo=True, beginnend mit PyTorch 2.9. Wir empfehlen Ihnen, die Option dynamo=True in torch.onnx.export zu migrieren. Dieses Flag macht torch.export.export zum Standardexportpfad und ersetzt TorchScript. Um das alte Verhalten beizubehalten, legen Sie dynamo=False explizit fest. Wir empfehlen Ihnen, auch mit der Option fallback=True zu experimentieren, die dafür sorgt, dass der Exporter bei Fehlern auf den Pfad dynamo=False zurückgreift.

Tracked Regressions

Windows wheel builds with CUDA 12.9.1 stack overflow during build (#156181)

Due to a bug introduced in CUDA 12.9.1, we are unable to complete full Windows wheel builds with this version, as compilation of torch.segment_reduce() crashes the build. Thus, we provide a wheel without torch.segment_reduce() included in order to sidestep the issue. If you need support for torch.segment_reduce(), please utilize a different version.

Backwards Incompatible Changes

CUDA Support

Removed support for Maxwell and Pascal architectures with CUDA 12.8 and 12.9 builds (#157517, #158478, #158744)

Due to binary size limitations, support for sm50 - sm60 architectures with CUDA 12.8 and 12.9 has been dropped for the 2.8.0 release. If you need support for these architectures, please utilize CUDA 12.6 instead.

An error is now properly thrown for the out variant of tensordot when called with a requires_grad=True tensor (#150270)

Please avoid passing an out tensor with requires_grad=True as gradients cannot be computed for this tensor.

torch.compile

Specialization of a tensor shape with mark_dynamic applied now correctly errors (#152661)

Prior to 2.8, it was possible for a guard on a symbolic shape to be incorrectly omitted if the symbolic shape evaluation was previously tested with guards suppressed (this often happens within the compiler itself). This has been fixed in 2.8 and usually will just silently "do the right thing" and add the correct guard. However, if the new guard causes a tensor marked with mark_dynamic to become specialized, this can result in an error. One workaround is to use maybe_mark_dynamic instead of mark_dynamic.

See the discussion in issue #157921 for more context.

Version 2.7.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Version 2.8.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

NVTX3 code has been moved from cmake/public/cuda.cmake to cmake/Dependencies.cmake (#151583)

This is a BC-breaking change for the build system interface. Downstream projects that previously got NVTX3 through cmake/public/cuda.cmake (i.e.. calling find_package(TORCH REQUIRED)) will now need to explicitly configure NVTX3 support in the library itself (i.e. use USE_SYSTEM_NVTX=1). The change is to fix the broken behavior where downstream projects couldn't find NVTX3 anyway due to the PROJECT_SOURCE_DIR mismatch.

Version 2.7.0:

  • A downstream project using -DUSE_SYSTEM_NVTX would be able to find NVTX3 and torch::nvtx3 via PyTorch's cmake/public/cuda.cmake logic.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX would encounter build errors with CUDA 12.8 or above.

Version 2.8.0:

  • A downstream project using -DUSE_SYSTEM_NVTX will not be able to find NVTX3 or torch::nvtx3 via PyTorch's cmake/public/cuda.cmake. The downstream project now needs to explicitly find NVTX3 and torch::nvtx3 by implementing the same logic in PyTorch's cmake/Dependences.cmake.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX will proceed building without NVTX unless another part of the build process re-enables NVTX.
