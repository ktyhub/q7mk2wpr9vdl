Highlights

Wir freuen uns, die Veröffentlichung von PyTorch® 2.5 bekannt zu geben! Diese Version verfügt über ein neues CuDNN-Backend für SDPA, das standardmäßig Beschleunigungen für Benutzer von SDPA auf H100s oder neueren GPUs ermöglicht. Darüber hinaus bietet die regionale Kompilierung von Torch.compile eine Möglichkeit, die Kaltstartzeit für Torch.compile zu verkürzen, indem es Benutzern ermöglicht, ein wiederholtes nn.Module (z. B. eine Transformatorschicht in LLM) ohne Neukompilierungen zu kompilieren. Schließlich bietet das TorchInductor CPP-Backend eine solide Leistungssteigerung mit zahlreichen Verbesserungen wie FP16-Unterstützung, CPP-Wrapper, AOT-Inductor-Modus und Max-Autotune-Modus. Diese Veröffentlichung besteht aus 4095 Commits von 504 Mitwirkenden seit PyTorch 2.4. Wir möchten unserer engagierten Community aufrichtig für Ihre Beiträge danken. Wie immer empfehlen wir Ihnen, diese auszuprobieren und etwaige Probleme zu melden, während wir 2.5 verbessern. Weitere Informationen zum Einstieg in die PyTorch 2-Serie finden Sie auf unserer Seite Erste Schritte. BETA-FUNKTIONEN

[Beta] CuDNN-Backend für SDPA

Das cuDNN-Backend „Fused Flash Attention“ wurde für torch.nn.functional.scaled_dot_product_attention gelandet. Auf NVIDIA H100-GPUs kann dies eine Geschwindigkeitssteigerung von bis zu 75 % gegenüber FlashAttentionV2 ermöglichen. Diese Beschleunigung ist standardmäßig für alle Benutzer von SDPA auf H100 oder neueren GPUs aktiviert.

[Beta] torch.compile regionale Kompilierung ohne Neukompilierungen

Regionale Kompilierung ohne Neukompilierungen über torch._dynamo.config.inline_inbuilt_nn_modules, das in 2.5+ standardmäßig auf True gesetzt ist. Mit dieser Option können Benutzer ein wiederholtes nn.Module (z. B. eine Transformatorschicht in LLM) ohne Neukompilierungen kompilieren. Im Vergleich zur Kompilierung des vollständigen Modells kann diese Option zu geringeren Kompilierungslatenzen mit einer Leistungseinbuße von 1–5 % im Vergleich zur vollständigen Modellkompilierung führen. Weitere Informationen finden Sie im Tutorial.

[Beta] TorchInductor CPU-Backend-Optimierung

Diese Funktion erweitert die CPU-Backend-Optimierung von Inductor, einschließlich der Generierung von CPP-Backend-Code und FX-Fusionen mit benutzerdefinierten CPU-Kerneln. Das Inductor-CPU-Backend unterstützt die Vektorisierung gängiger Datentypen und aller Inductor-IR-Operationen sowie die statischen und symbolischen Formen. Es ist sowohl mit Linux- als auch mit Windows-Betriebssystemen kompatibel und unterstützt den standardmäßigen Python-Wrapper, den CPP-Wrapper und den AOT-Inductor-Modus. Darüber hinaus erweitert es den Max-Autotune-Modus der GEMM-Vorlage (Prototyp in 2.5) und bietet so weitere Leistungssteigerungen. Das Backend unterstützt verschiedene FX-Fusionen und reduziert sich auf benutzerdefinierte Kernel wie oneDNN für Linear/Conv-Operationen und SDPA. Das Inductor-CPU-Backend erzielt in drei Benchmark-Suiten – TorchBench, Hugging Face und Timms – durchweg Leistungssteigerungen und übertrifft den Eager-Modus in 97.5 % der 193 getesteten Modelle.

PROTOTYP-FUNKTIONEN

[Prototyp] FlexAttention

Wir haben einen flexiblen API eingeführt, der die Implementierung verschiedener Aufmerksamkeitsmechanismen wie Sliding Window, Causal Mask und PrefixLM mit nur wenigen Zeilen idiomatischem PyTorch-Code ermöglicht. Dieser API nutzt Torch.compile, um einen fusionierten FlashAttention-Kernel zu generieren, der die zusätzliche Speicherzuweisung überflüssig macht und eine Leistung erreicht, die mit handgeschriebenen Implementierungen vergleichbar ist. Darüber hinaus generieren wir den Rückwärtsdurchlauf automatisch mithilfe der Autograd-Maschinerie von PyTorch. Darüber hinaus kann unser API die Sparsity in der Aufmerksamkeitsmaske nutzen, was zu erheblichen Verbesserungen gegenüber Standard-Aufmerksamkeitsimplementierungen führt. Weitere Informationen und Beispiele finden Sie im offiziellen Blogbeitrag und im Attention Gym.

[Prototyp] Kompiliertes Autograd

Compiled Autograd ist eine Erweiterung des PT2-Stacks, die die Erfassung des gesamten Rückwärtsdurchlaufs ermöglicht. Im Gegensatz zum Rückwärtsdiagramm, das vom AOT-Dispatcher verfolgt wird, wird die Ablaufverfolgung von Compiled Autograd bis zur Rückwärtsausführungszeit verschoben, was sie unempfindlich gegenüber Unterbrechungen des Vorwärtsdurchlaufdiagramms macht und die Aufzeichnung von Rückwärts-Hooks im Diagramm ermöglicht. Weitere Informationen finden Sie im Tutorial.

[Prototyp] Flugschreiber

Flight Recorder ist ein neues Debugging-Tool, das beim Debuggen festsitzender Jobs hilft. Das Tool erfasst kontinuierlich Informationen über Kollektive, während sie laufen. Bei der Erkennung eines feststeckenden Jobs können die Informationen verwendet werden, um schnell fehlerhafte Ränge/Maschinen zusammen mit Code-Stack-Traces zu identifizieren. Weitere Informationen finden Sie im folgenden Tutorial.

[Prototyp] Max-Autotune-Unterstützung auf der CPU mit GEMM-Vorlage

Der Max-Autotune-Modus für das Inductor-CPU-Backend in Torch.compile profiliert mehrere Implementierungen von Vorgängen zur Kompilierungszeit und wählt die leistungsstärkste aus. Dies ist insbesondere für GEMM-bezogene Vorgänge von Vorteil, da eine auf C++-Vorlagen basierende GEMM-Implementierung als Alternative zum ATen-basierten Ansatz mit oneDNN- und MKL-Bibliotheken verwendet wird. Wir unterstützen FP32, BF16, FP16 und INT8 mit Epilog-Fusionen für x86-CPUs. Wir haben bei den Dynamo-Benchmark-Suites eine Geo-Geschwindigkeitssteigerung von bis zu 7 % und eine Steigerung der Next-Token-Latenz für die LLM-Inferenz um bis zu 20 % festgestellt. Weitere Informationen finden Sie im Tutorial.

[Prototyp] TorchInductor-CPU unter Windows

Das Inductor-CPU-Backend in Torch.compile funktioniert jetzt unter Windows. Wir unterstützen derzeit MSVC (cl), clang (clang-cl) und Intel Compiler (icx-cl) für Windows Inductor. Weitere Einzelheiten finden Sie im Tutorial.

[Prototyp] FP16-Unterstützung auf dem CPU-Pfad sowohl für den Eager-Modus als auch für das TorchInductor-CPP-Backend

Float16 ist ein häufig verwendeter reduzierter Gleitkommatyp zur Leistungsverbesserung bei der Inferenz/Training neuronaler Netze. Seit dieser Version wird float16 sowohl für Eager als auch für TorchInductor auf dem CPU-Pfad unterstützt.

[Prototyp] Autoload-Geräteerweiterung

PyTorch unterstützt jetzt das automatische Laden für Out-of-Tree-Geräteerweiterungen und optimiert so die Integration, da keine manuellen Importe mehr erforderlich sind. Diese über den Torch.backends-Einstiegspunkt aktivierte Funktion vereinfacht die Nutzung, indem sie ein nahtloses Laden der Erweiterung gewährleistet und es Benutzern gleichzeitig ermöglicht, sie bei Bedarf über eine Umgebungsvariable zu deaktivieren. Weitere Informationen finden Sie im Tutorial.

[Prototyp] Verbesserte Intel-GPU-Unterstützung

Eine Erweiterung der Unterstützung für Intel-GPUs ist jetzt sowohl für die Intel® Data Center GPU Max-Serie als auch für Intel® Client-GPUs (Intel® Core™ Ultra-Prozessoren mit integrierter Intel® Arc™-Grafik und Intel® Arc™-Grafik für dGPU-Teile) verfügbar, was die Beschleunigung Ihrer maschinellen Lernworkflows auf Intel-GPUs in der PyTorch 2.5-Version erleichtern soll. In dieser Version haben wir auch die anfängliche Unterstützung von PyTorch unter Windows für Intel® Client-GPUs aktiviert. – Erweiterte PyTorch-Hardware-Backend-Unterstützungsmatrix, um sowohl Intel Data Center- als auch Client-GPUs einzubeziehen.   – Die Implementierung von SYCL*-Kerneln zur Verbesserung der Abdeckung und Ausführung von Aten-Operatoren auf Intel-GPUs, um die Leistung im PyTorch-Eager-Modus zu steigern. – Verbessertes Intel GPU-Backend von Torch.compile zur Verbesserung der Inferenz- und Trainingsleistung für eine Vielzahl von Deep-Learning-Workloads.
Diese Funktionen sind über die PyTorch-Vorschau und die nächtlichen binären PIP-Räder verfügbar. Weitere Informationen zur Intel-GPU-Unterstützung finden Sie in der Dokumentation.

– [c10d] Option für ProcessGroup und Expose Backend-Optionen entfernen, um die korrekte Codestruktur wiederzugeben (#132931) – Wir haben Dispatchable-Kollektive in 2.0 veröffentlicht und werden die Backend-Option für die Backend-Initialisierung verwenden und die PG-Optionen werden nicht mehr benötigt. – In 2.4 und früher können Benutzer Folgendes tun:

# Users can pass in a basic option when creating an instance of ProcessGroup
base_pg_options = ProcessGroup.Options(backend=str(backend))
base_pg_options._timeout = timeout

pg: ProcessGroup = ProcessGroup(

pg_options = ProcessGroupNCCL.Options()
backend = ProcessGroupNCCL(
  store, rank, group_size, pg_options
)

– Aber ab 2.5 müssen Benutzer keine Option mehr übergeben, um eine Instanz von ProcessGroup zu erstellen, und Benutzer können weiterhin das Standard-Backend für die Seite festlegen, da Benutzer immer noch versuchen, das Standard-Backend im Code zu erhalten:

# No basic option is passed in when creating a instance of ProcessGroup
pg: ProcessGroup = ProcessGroup(store, rank, group_size)
pg._set_default_backend(Backend.backend_type_map[backend])
# Users then need to create a backend option to create the comm backend (e.g., ProcessGroupNCCL)
pg_options = ProcessGroupNCCL.Options()
backend = ProcessGroupNCCL(
  store, rank, group_size, pg_options
)

ONNX

Optionen für torch.onnx.export (mit Ausnahme der ersten drei Argumente) sind jetzt nur noch Schlüsselwörter (#131501)

Optionen können nur über Schlüsselwörter bereitgestellt werden, um zukünftige Ergänzungen und Weiterentwicklungen des torch.onnx.export API zu ermöglichen. Beispiel:
Version 2.4

torch.onnx.export(model, input, f, True, False)

Version 2.5:

torch.onnx.export(model, input, f, export_params=True, verbose=False)

Das veraltete interne API torch.onnx._export wurde entfernt (133824)

torch.onnx._export ist ein interner API, der nicht für den öffentlichen Gebrauch bestimmt ist. Verwenden Sie stattdessen das öffentliche torch.onnx.export. Beispiel:
Version 2.4

torch.onnx._export(...)

Version 2.5:

torch.onnx.export(...)

Die Option op_level_debug von torch.onnx.ExportOptions wurde entfernt (#134961)

Diese Option, die dazu gedacht war, Unstimmigkeiten zwischen den Bedienern zu erkennen, erwies sich als unzuverlässig und wurde entfernt. Verwenden Sie stattdessen die Option torch.onnx.export(..., report=True, verify=True), um exportierte Modelle zu validieren.

Die ONNXProgramSerializer-Klasse wurde entfernt (#135261)

Das ONNX-Modell in torch.onnx.ONNXProgram wird jetzt von ONNX IR verwaltet und serialisiert.
Die Formate textproto, onnxtext und json werden standardmäßig unterstützt, wenn ONNXProgram.save() mit einer entsprechenden Dateierweiterung aufgerufen wird.

Die SymbolicContext-Klasse wurde entfernt (#132184)

Die veraltete Klasse torch.onnx.SymbolicContext wurde entfernt. (Nicht-Dynamo) benutzerdefinierte symbolische Funktionen können ctx: torch.onnx.SymbolicContext nicht mehr als erstes Argument annehmen.

Unterstützung für caffe2 wurde entfernt (#129021)

– Caffe2-Handling aus onnx_unpack_quantized_weights entfernen (#129021)

  • Entfernen Sie is_caffe2_aten_fallback in torch.onnx.symbolic_helper

Einige Fehlerklassen wurden entfernt

CheckerError und InvalidExportOptionsError werden entfernt. Benutzer können jederzeit RuntimeError abfangen, um Fehler beim Torch.onnx-Export zu beheben.

ONNX

Die Bereitstellung von Modellschlüsselwortargumenten für torch.onnx.export ist veraltet (#131501)

Die Möglichkeit, Modellschlüsselwortargumente als endgültiges Wörterbuch bereitzustellen, ist veraltet. Benutzer sollten stattdessen den Parameter kwargs verwenden. Veraltet:

torch.onnx.export(model, (arg1, arg2, {“kwarg1”: …}))

Zukunft:

torch.onnx.export(model, (arg1, arg2), kwargs={“kwarg1”: …})

torch.onnx.OperatorExportTypes ist veraltet (#131501)

Die Möglichkeit, operator_export_type in torch.onnx.export() bereitzustellen, ist veraltet. Exportierte ONNX-Diagramme verwenden immer die ONNX-Opset-Domäne. Die Optionen ONNX_FALLTHROUGH, ONNX_ATEN und ONNX_ATEN_FALLBACK werden nicht mehr unterstützt. Die Klasse OperatorExportTypes wird in einer zukünftigen Version entfernt.

Die Option training in torch.onnx.export ist veraltet

Stellen Sie stattdessen zuerst den Modelltrainingsmodus ein, bevor Sie exportieren. Veraltet:

torch.onnx.export(model, inputs, path, training=torch.onnx.TrainingMode.EVAL)

Zukunft:

model = model.eval()  
torch.onnx.export(model, inputs, path)

ONNX

Die Option dynamo=True und die neue Exportlogik (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

Wir führen die Option dynamo=True in torch.onnx.export() ein. Dies wird als Ersatz für torch.onnx.dynamo_export ab PyTorch 2.5 empfohlen. Version 2.5:

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) nutzt torch.export und ONNX IR, um erfasste ExportedPrograms effizient und robust in ONNX zu konvertieren. Dieser neue Prozess reduziert den Speicherverbrauch im Vergleich zu dynamo_export in 2.4 um die Hälfte, während gleichzeitig umfangreiche Tensorform- und Stack-Trace-Informationen im ONNX-Diagramm erhalten bleiben. Sie können die Option report=True nutzen, um einen Konvertierungsbericht im Markdown-Format zu erhalten und etwaige Konvertierungsprobleme zu diagnostizieren. Legen Sie verify=True fest, um das ONNX-Modell numerisch mit ONNX Runtime zu überprüfen. Wenn Sie external_data=True verwenden, um Modellgewichte als externe Daten in der .onnx-Datei zu speichern, werden Gewichtungen, die größer als 1 MB sind, jetzt an 64-KB-Adressen ausgerichtet. Dadurch können Laufzeiten Gewichtungen dem Speicher zuordnen, um die Speichereffizienz während der Inferenz zu verbessern.

[HINWEIS]
Die Option dynamo=True unterstützt derzeit nur ONNX Opset 18. Zukünftige Versionen werden die Unterstützung auf neuere Opsets erweitern. [HINWEIS]
Die Option dynamo=True erfordert die neuesten Versionen der Pakete onnxscript und onnx.

BETA FEATURES

[Beta] CuDNN backend for SDPA

The cuDNN "Fused Flash Attention" backend was landed for torch.nn.functional.scaled_dot_product_attention. On NVIDIA H100 GPUs this can provide up to 75% speed-up over FlashAttentionV2. This speedup is enabled by default for all users of SDPA on H100 or newer GPUs.

[Beta] torch.compile regional compilation without recompilations

Regional compilation without recompilations, via torch._dynamo.config.inline_inbuilt_nn_modules which default to True in 2.5+. This option allows users to compile a repeated nn.Module (e.g. a transformer layer in LLM) without recompilations. Compared to compiling the full model, this option can result in smaller compilation latencies with 1%-5% performance degradation compared to full model compilation.

See the tutorial for more information.

[Beta] TorchInductor CPU backend optimization

This feature advances Inductor’s CPU backend optimization, including CPP backend code generation and FX fusions with customized CPU kernels. The Inductor CPU backend supports vectorization of common data types and all Inductor IR operations, along with the static and symbolic shapes. It is compatible with both Linux and Windows OS and supports the default Python wrapper, the CPP wrapper, and AOT-Inductor mode.

Additionally, it extends the max-autotune mode of the GEMM template (prototyped in 2.5), offering further performance gains. The backend supports various FX fusions, lowering to customized kernels such as oneDNN for Linear/Conv operations and SDPA. The Inductor CPU backend consistently achieves performance speedups across three benchmark suites—TorchBench, Hugging Face, and timms—outperforming eager mode in 97.5% of the 193 models tested.

PROTOTYPE FEATURES

[Prototype] FlexAttention

We've introduced a flexible API that enables implementing various attention mechanisms such as Sliding Window, Causal Mask, and PrefixLM with just a few lines of idiomatic PyTorch code. This API leverages torch.compile to generate a fused FlashAttention kernel, which eliminates extra memory allocation and achieves performance comparable to handwritten implementations. Additionally, we automatically generate the backwards pass using PyTorch's autograd machinery. Furthermore, our API can take advantage of sparsity in the attention mask, resulting in significant improvements over standard attention implementations.

For more information and examples, please refer to the official blog post and Attention Gym.

[Prototype] Compiled Autograd

Compiled Autograd is an extension to the PT2 stack allowing the capture of the entire backward pass. Unlike the backward graph traced by AOT dispatcher, Compiled Autograd tracing is deferred until backward execution time, which makes it impervious to forward pass graph breaks, and allows it to record backward hooks into the graph.

Please refer to the tutorial for more information.

[Prototype] Flight Recorder

Flight recorder is a new debugging tool that helps debug stuck jobs. The tool works by continuously capturing information about collectives as they run. Upon detecting a stuck job, the information can be used to quickly identify misbehaving ranks/machines along with code stack traces.

For more information please refer to the following tutorial.

[Prototype] Max-autotune Support on CPU with GEMM Template

Max-autotune mode for the Inductor CPU backend in torch.compile profiles multiple implementations of operations at compile time and selects the best-performing one. This is particularly beneficial for GEMM-related operations, using a C++ template-based GEMM implementation as an alternative to the ATen-based approach with oneDNN and MKL libraries. We support FP32, BF16, FP16, and INT8 with epilogue fusions for x86 CPUs. We’ve seen up to 7% geomean speedup on the dynamo benchmark suites and up to 20% boost in next-token latency for LLM inference.

For more information please refer to the tutorial.

[Prototype] TorchInductor CPU on Windows

Inductor CPU backend in torch.compile now works on Windows. We support MSVC (cl), clang (clang-cl) and Intel compiler (icx-cl) for Windows inductor currently.

See the tutorial for more details.

[Prototype] FP16 support on CPU path for both eager mode and TorchInductor CPP backend

Float16 is a commonly used reduced floating point type for performance improvement in neural network inference/training. Since this release, float16 for both eager and TorchInductor is supported on the CPU path.

[Prototype] Autoload Device Extension

PyTorch now supports autoloading for out-of-tree device extensions, streamlining integration by eliminating the need for manual imports. This feature, enabled through the torch.backends entrypoint, simplifies usage by ensuring seamless extension loading, while allowing users to disable it via an environment variable if needed.

See the tutorial for more information.

[Prototype] Enhanced Intel GPU support

Intel GPUs support enhancement is now available for both Intel® Data Center GPU Max Series and Intel® Client GPUs (Intel® Core™ Ultra processors with built-in Intel® Arc™ graphics and Intel® Arc™ Graphics for dGPU parts), which is to make it easier to accelerate your Machine Learning workflows on Intel GPUs in PyTorch 2.5 release. We also enabled the initial support of PyTorch on Windows for Intel® Client GPUs in this release.

  • Expanded PyTorch hardware backend support matrix to include both Intel Data Center and Client GPUs.  
  • The implementation of SYCL* kernels to enhance coverage and execution of Aten operators on Intel GPUs to boost performance in PyTorch eager mode.
  • Enhanced Intel GPU backend of torch.compile to improve inference and training performance for a wide range of deep learning workloads.

These features are available through PyTorch preview and nightly binary PIP wheels. For more information regarding Intel GPU support, please refer to documentation.

The dynamo=True option and new export logic (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

We introduce the dynamo=True option in torch.onnx.export(). This is recommended as a replacement for torch.onnx.dynamo_export starting in PyTorch 2.5.

Version 2.5:

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) leverages torch.export and ONNX IR to convert captured ExportedPrograms to ONNX efficiently and robustly. This new process reduces memory consumption by half compared to dynamo_export in 2.4, while preserving rich tensor shape and stack trace information in the ONNX graph. You can leverage the report=True option to obtain a conversion report in markdown format to diagnose any conversion issues. Set verify=True to verify the ONNX model numerically with ONNX Runtime.

When using external_data=True to save model weights as external data to the .onnx file, weights larger than 1 MB are now aligned at 64 KB addresses. This allows runtimes to memory-map weights for better memory efficiency during inference.

[NOTE]
The dynamo=True option currently supports only ONNX opset 18. Future releases will expand support to newer opsets.

[NOTE]
The dynamo=True option requires the latest versions of onnxscript and onnx packages.
