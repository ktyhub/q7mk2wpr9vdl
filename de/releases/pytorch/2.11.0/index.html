## Python Frontend
### `torch.hub.list()`, `torch.hub.load()` und `torch.hub.help()` setzen den Parameter `trust_repo` jetzt standardmäßig auf `"check"` statt auf `None`. Die Option `trust_repo=None` wurde entfernt. (#174101)
Bisher führte die Übergabe von `trust_repo=None` (oder das Verlassen auf die Standardeinstellung) dazu, dass Code aus untrusted-Repositorys stillschweigend heruntergeladen und ausgeführt wurde, nur mit einer Warnung. Das Standardverhalten von `"check"` fordert den Benutzer nun zu einer expliziten Bestätigung auf, bevor Code aus Repositorys ausgeführt wird, die nicht in der trusted-Liste enthalten sind.
Benutzer, die explizit `trust_repo=None` übergeben haben, müssen ihren Code aktualisieren. Benutzer, die bereits `trust_repo=True`, `trust_repo=False` oder `trust_repo="check"` bestanden haben, sind nicht betroffen.
Version 2.10:
```python
# Default trust_repo=None — downloads with a warning
torch.hub.load("user/repo", "model")
# Explicit None — same behavior
torch.hub.load("user/repo", "model", trust_repo=None)

Version 2.11:

# Default trust_repo="check" — prompts for confirmation if repo is not trusted
torch.hub.load("user/repo", "model")
# To skip the prompt, explicitly trust the repo
torch.hub.load("user/repo", "model", trust_repo=True)

Torch.nn

Schiebefensterunterstützung zu varlen_attn über window_size hinzugefügt, sodass optionale Argumente nur Schlüsselwörter sind (#172238)

Die Signatur von torch.nn.attention.varlen_attn hat sich geändert: Vor den optionalen Argumenten wurde ein * (Nur-Schlüsselwort-Trennzeichen) eingefügt. Bisher konnten optionale Argumente wie is_causal, return_aux und scale positionell übergeben werden; Sie müssen nun als Schlüsselwortargumente übergeben werden. Außerdem wurde ein neues Schlüsselwortargument window_size hinzugefügt.

# Before (2.10)
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, True, None, 1.0)

# After (2.11) — pass as keyword argument
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, window_size=(-1, 0), return_aux=None, scale=1.0)

is_causal-Flag von varlen_attn entfernen (#172245)

Der Parameter is_causal wurde aus torch.nn.attention.varlen_attn entfernt. Die kausale Aufmerksamkeit wird jetzt durch den Parameter window_size ausgedrückt: Verwenden Sie window_size=(-1, 0) für die kausale Maskierung oder window_size=(W, 0) für die kausale Aufmerksamkeit mit einem Schiebefenster der Größe W. Der Standardwert window_size=(-1, -1) entspricht voller (nicht-kausaler) Aufmerksamkeit.

# Before (2.10)
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, is_causal=True)

# After (2.11) — use window_size instead
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, window_size=(-1, 0))

Verteilt

DebugInfoWriter würdigt jetzt $XDG_CACHE_HOME für sein Cache-Verzeichnis im C++-Code, konsistent mit der Python-Seite. Bisher wurde immer ~/.cache/torch verwendet. (#168232)

Dadurch werden Probleme vermieden, bei denen $HOME nicht festgelegt oder nicht beschreibbar ist. Benutzer, die sich darauf verlassen haben, dass ~/.cache/torch unabhängig von $XDG_CACHE_HOME verwendet wird, sehen möglicherweise, dass Debug-Informationen an einen anderen Speicherort geschrieben wurden. Version 2.10:

# C++ DebugInfoWriter always wrote to ~/.cache/torch

Version 2.11:

# C++ DebugInfoWriter now respects $XDG_CACHE_HOME/torch (same as Python code)
# Falls back to ~/.cache/torch if $XDG_CACHE_HOME is not set

DeviceMesh speichert jetzt direkt eine Prozessgruppenregistrierung (_pg_registry), sodass torch.compile die Verfolgung über get_group() durchführen kann. (#172272)

Dadurch kann Code beschädigt werden, der init_process_group überspringt, einen gespeicherten DTensor lädt (ein DeviceMesh ohne PGs erstellt) und später PGs separat erstellt – während der torch.compile-Laufzeit schlägt die PG-Suche fehl. Benutzer sollten sicherstellen, dass Prozessgruppen initialisiert werden, bevor sie das DeviceMesh erstellen. Version 2.10:

# PGs resolved via global _resolve_process_group at runtime
mesh = DeviceMesh(...)  # PGs could be created later

Version 2.11:

# PGs now stored on DeviceMesh._pg_registry; must exist at mesh creation
dist.init_process_group(...)  # Must be called before creating mesh
mesh = DeviceMesh(...)

Verteilt (DTensor)

DTensor.to_local() rückwärts konvertiert jetzt standardmäßig Partial-Platzierungen in Replicate, wenn grad_placements nicht bereitgestellt wird. (#173454)

Bisher blieb beim Aufruf von to_local() auf einem Partial-DTensor die Platzierung von Partial im Rückwärtsgradienten erhalten, was in Kombination mit from_local() zu falschen Farbverläufen führen konnte. Jetzt ordnet der Rückwärtsdurchlauf automatisch Partial-Vorwärtsplatzierungen Replicate-Gradientenplatzierungen zu, was dem Verhalten von from_local() entspricht. Benutzer, die sich auf das vorherige Verhalten verlassen haben (wobei to_local() rückwärts beibehaltene Partial-Verläufe waren), sehen möglicherweise andere Verlaufswerte. Um die Richtigkeit sicherzustellen, übergeben Sie grad_placements explizit an to_local(). Version 2.10:

# Partial placement preserved in backward — could produce incorrect gradients
local_tensor = partial_dtensor.to_local()

Version 2.11:

# Partial → Replicate in backward by default (correct behavior)
local_tensor = partial_dtensor.to_local()
# Or explicitly specify grad_placements for full control:
local_tensor = partial_dtensor.to_local(grad_placements=[Replicate()])

_PhiloxState.seed und _PhiloxState.offset geben jetzt torch.Tensor anstelle von int zurück (#173876)

Die DTensor RNG-interne _PhiloxState-Klasse hat ihre Eigenschaften seed und offset geändert, um Tensoren anstelle von Python-Ints zurückzugeben, und die Setter erwarten jetzt Tensoren. Dadurch ist der RNG-Status mit der PT2-Ablaufverfolgung kompatibel (die vorherigen .item()-Aufrufe waren nicht Fake-Tensor-freundlich). Code, der _PhiloxState.seed oder _PhiloxState.offset direkt liest und sie als Ints behandelt, wird fehlerhaft sein. Rufen Sie .item() auf, um den int-Wert zu erhalten. Wickeln Sie den Wert beim Festlegen in einen Tensor ein. Version 2.10:

from torch.distributed.tensor._random import _PhiloxState

philox = _PhiloxState(state)
seed: int = philox.seed          # returned int
philox.offset = 42               # accepted int

Version 2.11:

from torch.distributed.tensor._random import _PhiloxState

philox = _PhiloxState(state)
seed: int = philox.seed.item()   # now returns Tensor; call .item() for int
philox.offset = torch.tensor([42], dtype=torch.int64)  # must pass Tensor

ROCm

caffe2-Unterstützung wurde vollständig aus der Hipify-Vorverarbeitung von ROCm PyTorch entfernt. Dies wird als „hipify v2“-Verhalten bezeichnet. (#174087, #174300, #174388, #174499, #175098)

Hipify v1-Hintergrund

Als caffe2 und PyTorch getrennte Projekte waren, waren die ROCm-Unterstützungsstrategien unterschiedlich. Für caffe2 würden alle Dateien und Klassen nach dem Muster CUDA in HIP, Cuda in Hip, Cuda in Hip usw. umbenannt. PyTorch hat Klassen nicht umbenannt, sondern neue Dateien nach demselben Umbenennungsmuster erstellt (z. B. aten/src/ATen/cuda/CUDABlas.h in aten/src/ATen/hip/HIPBlas.h). Infolgedessen verfügte caffe2 über ein eigenes Geräte-Backend mit dem Namen „HIP“ (umbenannt von „CUDA“), während ROCm PyTorch sich als „cuda“-Gerät (torch.empty(1, device="cuda")) ausgibt. Sobald caffe2- und PyTorch-Projekte zusammengeführt wurden, führte dies zu einer Diskrepanz zwischen caffe2, das die Verwendung eines „HIP“-Geräts erwartete, und PyTorch, das ein „cuda“-Gerät erwartete. Um diese Diskrepanz zu mildern, wurden „Masquerading“-Klassen unter aten/src/ATen/hip/impl erstellt.

  • HIPAllocatorMasqueradingAsCUDA.h
  • HIPCachingAllocatorMasqueradingAsCUDA.h
  • HIPGuardImplMasqueradingAsCUDA.h
  • HIPStreamMasqueradingAsCUDA.h Diese Klassen wurden häufig transparent während der Hipify-Vorverarbeitung von Quelldateien durch ROCm PyTorch verwendet. Alle Dateien unter c10/ und caffe2/ wurden mit dem caffe2-Umbenennungsverhalten hipifiziert, während alle anderen „PyTorch“-Dateien die andere Strategie verwendeten. Die Masquerading-Klassen würden ihr CUDA-Gegenstück während der Hipify-Vorverarbeitung ersetzen. Beispielsweise würde der CUDAStream von c10/cuda/CUDAStream.h durch den HIPStreamMasqueradingAsCUDA von aten/src/ATen/hip/impl/HIPStreamMasqueradingAsCUDA.h ersetzt. Diese Masquerading-Klassen rufen den zugrunde liegenden caffe2-Code auf und erstellen „HIP“-Geräte, und das Gerät wird von den Masquerading-Klassen auf „cuda“ zurückgesetzt.

hipify v2 neues Verhalten

Hipify v2 (#174087, #174300, #174388, #174499, #175098) nimmt die folgenden Änderungen vor:

  • „Masquerading“-Klassen sind veraltet. Aus Gründen der Abwärtskompatibilität wurden bestehende Klassen so umgestaltet, dass sie dünne Hüllen bilden.
  • Benennen Sie „CUDA“-Klassen nicht in „HIP“ um. Benennen Sie nur CUDA Runtime APIs um. Dateien werden immer noch fehl am Platz umbenannt. – Entfernt caffe2-Workarounds für HIP-Geräte im Vergleich zu CUDA-Geräten. Es wurde große Sorgfalt darauf verwendet, diese Änderung abwärtskompatibel zu gestalten. Obwohl PyTorch heute mithilfe des Hipify v2-Verhaltens sauber erstellt, könnten nachgelagerte PyTorch-Erweiterungsprojekte, die explizit Masquerading-Header enthalten oder als Masquerading APIs bezeichnet werden, betroffen sein, was zu fehlgeschlagenen Builds führt. Bevor beispielsweise die Abwärtskompatibilität realisiert wurde, konnte das xformers-Projekt nicht mit den Hipify v2-Änderungen erstellt werden. Eine PR zeigt die Änderungen, die ursprünglich notwendig waren, um die Build-Fehler zu umgehen,, aber solche Änderungen sind nicht mehr notwendig, nachdem das BC-Breaking-Verhalten von hipify v2 verbessert wurde.

Torch.export

torch.export.export_for_training wurde entfernt (#171714)

export_for_training war zuvor als separates API zum Exportieren von Modellen unter Beibehaltung der Trainingssemantik verfügbar. Diese Funktion wurde entfernt. Benutzer sollten stattdessen torch.export.export verwenden, das das gleiche Diagramm wie das vorherige export_for_training zurückgibt.

ONNX

Entfernen Sie die Option fallback von torch.onnx.export (#173189)

Der Parameter fallback wurde aus torch.onnx.export() entfernt. Zuvor greift der Exporter bei fallback=True automatisch auf den alten, auf TorchScript basierenden Exporter zurück, wenn der Dynamo-Exporter ausfällt. Dieser Fallback wurde entfernt, da er zu kompliziert war, unterschiedliche Eingaben erforderte, unterschiedliche Modelle produzierte und Fehler vor dem neuen Exporter verbarg. Migration: Entfernen Sie fallback=True (oder fallback=False) aus Ihren torch.onnx.export()-Aufrufen. Wenn Sie ein Fallback-Verhalten benötigen, implementieren Sie es explizit in Ihrem eigenen Code, indem Sie Ausnahmen abfangen und den Legacy-Exporter separat aufrufen.

# Before
torch.onnx.export(model, args, "model.onnx", dynamo=True, fallback=True)

# After
torch.onnx.export(model, args, "model.onnx", dynamo=True)

Überlastungs-Matching-Logik aus dem ONNX-Dispatcher entfernen (#165083)

Der Parameter custom_translation_table in torch.onnx.export() akzeptiert keine Liste von Funktionen für jeden Brennerbetrieb mehr. Bisher konnten Benutzer eine Liste überladener ONNX-Funktionen übergeben (z. B. eine für Float-Tensoren, eine andere für Bool-Tensoren), und der Dispatcher wählte automatisch die richtige Überladung basierend auf den Eingabetypen aus. Diese komplexe Typvergleichslogik wurde entfernt, da Torchlib keine Überladungen mehr für dieselbe Opset-Version verwendet. Der Typ von custom_translation_table wurde von dict[Callable, Callable | Sequence[Callable]] in dict[Callable, Callable] geändert. Die Übergabe eines Sequence als Wert löst nun einen TypeError aus. Migration: Stellen Sie eine einzelne Funktion pro Operator anstelle einer Liste von Überladungen bereit. Wenn Sie typabhängiges Verhalten benötigen, behandeln Sie es innerhalb der einzelnen Funktion.

# Before
custom_translation_table = {
    torch.ops.aten.logical_and.default: [custom_impl_float, custom_impl_bool],
}

# After
custom_translation_table = {
    torch.ops.aten.logical_and.default: custom_impl,
}

Starting with PyTorch 2.11, the CUDA 12.8 and 12.9 pre-built binaries no longer include support for Volta GPUs (compute capability 7.0, e.g. V100). This change was necessary to enable updating to CuDNN 9.15.1, which is incompatible with Volta.

The signature of torch.nn.attention.varlen_attn has changed: a * (keyword-only separator) has been inserted before the optional arguments. Previously, optional arguments like is_causal, return_aux, and scale could be passed positionally; they must now be passed as keyword arguments. A new window_size keyword argument has also been added.

# Before (2.10)

output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, is_causal=True)

output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, window_size=(-1, 0))

DTensor.to_local() backward now converts Partial placements to Replicate by default when grad_placements is not provided. (#173454)

Previously, calling to_local() on a Partial DTensor would preserve the Partial placement in the backward gradient, which could produce incorrect gradients when combined with from_local(). Now, the backward pass automatically maps Partial forward placements to Replicate gradient placements, matching the behavior of from_local().

Users who relied on the previous behavior (where to_local() backward preserved Partial gradients) may see different gradient values. To ensure correctness, explicitly pass grad_placements to to_local().

Version 2.10:

# Partial placement preserved in backward — could produce incorrect gradients
local_tensor = partial_dtensor.to_local()

Version 2.11:

# Partial → Replicate in backward by default (correct behavior)

# Or explicitly specify grad_placements for full control:
local_tensor = partial_dtensor.to_local(grad_placements=[Replicate()])

_PhiloxState.seed and _PhiloxState.offset now return torch.Tensor instead of int (#173876)

The DTensor RNG internal _PhiloxState class changed its seed and offset properties to return tensors instead of Python ints, and the setters now expect tensors. This makes the RNG state compatible with PT2 tracing (the previous .item() calls were not fake-tensor friendly).

Code that directly reads _PhiloxState.seed or _PhiloxState.offset and treats them as ints will break. Call .item() to get the int value. When setting, wrap the value in a tensor.

Version 2.10:

from torch.distributed.tensor._random import _PhiloxState

philox = _PhiloxState(state)
seed: int = philox.seed          # returned int
philox.offset = 42               # accepted int

Version 2.11:

philox = _PhiloxState(state)
seed: int = philox.seed.item()   # now returns Tensor; call .item() for int
philox.offset = torch.tensor([42], dtype=torch.int64)  # must pass Tensor

ROCm

caffe2 support is fully removed from ROCm PyTorch's hipify preprocessing. This is known as "hipify v2" behavior. (#174087, #174300, #174388, #174499, #175098)

hipify v1 background

When caffe2 and PyTorch were separate projects, the ROCm support strategies were different. For caffe2, all files and classes would be renamed following the pattern of CUDA to HIP, Cuda to Hip, cuda to hip, and so on. PyTorch did not rename classes, but would create new files following the same renaming pattern (e.g., aten/src/ATen/cuda/CUDABlas.h to aten/src/ATen/hip/HIPBlas.h). As a consequence, caffe2 had a distinct device backend named "HIP" (renamed from "CUDA") while ROCm PyTorch masquerades as the "cuda" device (torch.empty(1, device="cuda")). Once caffe2 and PyTorch projects were merged, this caused a mismatch between caffe2 expecting to use a "HIP" device while PyTorch expecting a "cuda" device. To alleviate this mismatch, "Masquerading" classes were created under aten/src/ATen/hip/impl.

  • HIPAllocatorMasqueradingAsCUDA.h
  • HIPCachingAllocatorMasqueradingAsCUDA.h
  • HIPGuardImplMasqueradingAsCUDA.h
  • HIPStreamMasqueradingAsCUDA.h These classes were often transparently utilized during ROCm PyTorch's hipify preprocessing of source files. All files under c10/ and caffe2/ were hipified using the caffe2 renaming behavior, while all other "PyTorch" files used the other strategy. The Masquerading classes would replace their CUDA counterpart during hipify preprocessing. For example, c10/cuda/CUDAStream.h's CUDAStream would be replaced by aten/src/ATen/hip/impl/HIPStreamMasqueradingAsCUDA.h's HIPStreamMasqueradingAsCUDA. These Masquerading classes call the underlying caffe2 code and create "HIP" devices, and the device would be reset to "cuda" by the Masquerading classes.

hipify v2 new behavior

Hipify v2 (#174087, #174300, #174388, #174499, #175098) makes the following changes:

  • "Masquerading" classes are deprecated. Reworked to be thin shells around existing classes, for backward compatibility.
  • Do not rename "CUDA" classes to "HIP". Only rename CUDA Runtime APIs. Files are still renamed out of place.
  • Removes caffe2 work-arounds for HIP device versus CUDA device. Great care has been taken to make this change backwards compatible. Though PyTorch today builds cleanly using hipify v2 behavior, downstream PyTorch extension projects that explicitly included Masquerading headers or called Masquerading APIs could be affected, resulting in failed builds. As an example, before backwards compatibility was realized, the xformers project had failed to build using the hipify v2 changes. A PR demonstrates the changes that were initially necessary to work around the build failures, but such changes are no longer necessary after hipify v2 BC-breaking behavior was improved.

ONNX

Remove the fallback option from torch.onnx.export (#173189)

The fallback parameter has been removed from torch.onnx.export(). Previously, when fallback=True, the exporter would automatically fall back to the legacy TorchScript-based exporter if the dynamo exporter failed. This fallback was removed because it was overly complicated, required different inputs, produced different models, and hid errors from the new exporter.

Migration: Remove fallback=True (or fallback=False) from your torch.onnx.export() calls. If you need fallback behavior, implement it explicitly in your own code by catching exceptions and calling the legacy exporter separately.

# Before
torch.onnx.export(model, args, "model.onnx", dynamo=True, fallback=True)

# After
torch.onnx.export(model, args, "model.onnx", dynamo=True)

Remove overload matching logic from the ONNX dispatcher (#165083)

The custom_translation_table parameter in torch.onnx.export() no longer accepts a list of functions for each torch op. Previously, users could pass a list of overloaded ONNX functions (e.g., one for float tensors, another for bool tensors), and the dispatcher would automatically select the correct overload based on input types. This complex type-matching logic has been removed because torchlib no longer uses overloads for the same opset version.

The type of custom_translation_table changed from dict[Callable, Callable | Sequence[Callable]] to dict[Callable, Callable]. Passing a Sequence as a value now raises a TypeError.

Migration: Provide a single function per operator instead of a list of overloads. If you need type-dependent behavior, handle it inside the single function.

# Before
custom_translation_table = {
    torch.ops.aten.logical_and.default: [custom_impl_float, custom_impl_bool],
}

# After
custom_translation_table = {
    torch.ops.aten.logical_and.default: custom_impl,
}
