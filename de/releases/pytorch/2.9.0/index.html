Mit dieser Version stehen auch 3.14 und 3.14t als Vorschau zur Verfügung. ## Undefiniertes Verhalten, wenn eine Ausgabe eines benutzerdefinierten Operators den Speicher mit einer Eingabe teilt Dies ist eine Erinnerung daran, dass Ausgaben von benutzerdefinierten PyTorch-Operatoren (die mit den `torch.library`- oder `TORCH_LIBRARY`-APIs registriert werden) keine Tensoren zurückgeben dürfen, die den Speicher mit Eingabetensoren teilen. Die Verletzung dieser Bedingung führt zu undefiniertem Verhalten: Manchmal ist das Ergebnis korrekt, manchmal ist es Müll. Nach [#163227](https://github.com/pytorch/pytorch/pull/163227) können benutzerdefinierte Operatoren, die gegen diese Bedingung verstoßen haben und zuvor unter `torch.compile` korrekte Ergebnisse zurückgegeben haben, nun unter `torch.compile` stillschweigend falsche Ergebnisse zurückgeben. Da sich dadurch das Verhalten undefinierten Verhaltens ändert, betrachten wir dies nicht als Fehler, dokumentieren es jedoch in diesem Abschnitt dennoch als „potenziell unerwartete Verhaltensänderung“. Dies ist eine der von [`torch.library.opcheck`](https://docs.pytorch.org/docs/stable/library.html#testing-custom-ops) überprüften Bedingungen und wird im [The Custom Operators Manual](https://docs.google.com/document/d/1_W62p8WJOQQUzPsJYa7s701JXt0qf2OfLub2sbkHOaU/edit?tab=t.0#bookmark=id.4c0um7xkba6e) erwähnt. ### Weitere Details Ausgaben von benutzerdefinierten PyTorch-Operatoren dürfen keine Tensoren zurückgeben, die den Speicher mit Eingabetensoren teilen Beispielsweise sind die beiden folgenden benutzerdefinierten Operatoren keine gültigen benutzerdefinierten Operatoren: ```py @torch.library.custom_op("mylib::foo", mutates_args=()) def foo(x: torch.Tensor) -> torch.Tensor: # the result of `foo` must not directly be an input to foo. return x

@torch.library.custom_op("mylib::bar", mutates_args=()) def bar(x: torch.Tensor) -> torch.Tensor: # the result of bar must not be a view of an input of bar return x.view(-1)

Die einfachste Problemumgehung besteht darin, den Ausgängen ein zusätzliches `.clone()` hinzuzufügen:
```py
@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

Ein üblicher Weg, in diese Situation zu geraten, besteht darin, dass ein Benutzer einen benutzerdefinierten Operator erstellen möchte, der manchmal die Eingabe direkt ändert und manchmal einen neuen Tensor zurückgibt, wie im folgenden Beispiel.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

Diese Dynamik wird nicht unterstützt und führt zu undefiniertem Verhalten. Die Problemumgehung besteht darin, den benutzerdefinierten Operator in zwei benutzerdefinierte Operatoren aufzuteilen, einen, der die Eingabe immer direkt ändert, und einen anderen, der immer einen neuen Tensor zurückgibt.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

Upgrade auf DLPack 1.0 (#145000)

Dieses Upgrade führt die gleichen BC-bahnbrechenden Änderungen durch wie die DLPack-Version. Objekte in torch.utils.dlpack wurden aktualisiert, um diese Änderungen widerzuspiegeln, z. B. DLDeviceType. Einzelheiten zu den genauen Änderungen und zur Aktualisierung Ihres Codes finden Sie in der PR.

Entsprechende Fehler in torch.cat auslösen (#158249)

torch.cat löst nun ggf. ValueError, IndexError oder TypeError anstelle des generischen RuntimeError aus. Wenn Ihr Code diese Fehler abfängt, können Sie ihn aktualisieren, um den neuen Fehlertyp abzufangen.

Standardmäßig dynamo=True für ONNX-Exporter (#159646, #162726)

Bisher verwendete torch.onnx.export(...) den alten TorchScript-Exporter, wenn keine Argumente angegeben wurden. Der ONNX-Exporter verwendet jetzt standardmäßig die neuere torch.export.export-Pipeline (dynamo=True). Diese Änderung verbessert die Diagrammtreue und macht Exporte zukunftssicher, kann jedoch zu Fehlern bei der Diagrammerfassung führen, die zuvor maskiert oder anders behandelt wurden. Zuvor im Brenner 2.8.0:

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Jetzt in Fackel 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Empfehlung: Probieren Sie zunächst die neue Standardeinstellung aus; Greifen Sie nur dann zurück, wenn Sie auf Blockierungsprobleme stoßen, und melden Sie diese vorab. Langfristige Lösung: Beheben Sie die Grundursache, anstatt sich auf einen Fallback- oder TorchScript-Exporter zu verlassen.

Runtime-Assertions standardmäßig beim Export zugunsten einer Shape-Guards-Funktion ausschalten (#160111, #161178, #161794)

Um Laufzeitzusicherungen zu aktivieren, verwenden Sie export(..., prefer_deferred_runtime_asserts_over_guards=True). Tötet außerdem das Flag allow_complex_guards_as_runtime_asserts und verschmilzt es mit der vorherigen Option. Darüber hinaus generiert exported_program.module() einen Aufruf an ein _guards_fn-Submodul, das zusätzliche Prüfungen der Eingaben durchführt. Benutzer, die dieses Verhalten nicht wünschen, können diesen Aufruf entweder im Diagramm entfernen oder exported_program.module(check_guards=False) ausführen, um die Generierung zu vermeiden.

Standard-Opset in ONNX auf 20 setzen (#158802)

Opset 20 ermöglicht neuere Operatordefinitionen. Wenn Ihr Tool oder Ihre Downstream-Laufzeit nur Opset 18 unterstützt, heften Sie es explizit an. Für die neuesten ONNX-Operatoren können Sie mit Opset 23 experimentieren. Zuvor im Brenner 2.8.0:

# opset_version=18
torch.onnx.export(...)

Jetzt im Brenner 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

Löschen Sie draft_export im Exporter API (#161454, #162225)

Entfernen Sie die implizite Entwurfsverfolgung aus dem Standard-Exportpfad, um ein klareres Verhalten und schnellere Fehler zu erzielen. Der teure Diagnosepfad torch.export.draft_export wird nicht mehr automatisch aufgerufen (was bei großen Modellen Stunden dauern kann). Sie können sich weiterhin für eine umfassende Diagnose entscheiden: Zuvor im Brenner 2.8.0:

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

Jetzt im Brenner 2.9.0:

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both
# fail:

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Entfernen Sie torch.onnx.dynamo_export und das Brennerkompilierungs-Backend onnxrt (#158130, #158258)

torch.onnx.dynamo_export wird entfernt. Bitte verwenden Sie stattdessen torch.onnx.export. Das experimentelle ONNX Runtime-Kompilierungs-Backend (torch.compile(backend="onnxrt")) wird nicht mehr unterstützt.

torch.onnx.enable_fake_mode entfernen (#161222)

Der dynamo=True-Modus verwendet standardmäßig FakeTensors, was speichereffizient ist.

Einige öffentlich zugängliche ONNX-Dienstprogramm APIs für den TorchScript-basierten Exporter sind jetzt privat (#161323)

Veraltete Mitglieder in torch.onnx.verification werden entfernt. Bisher private torch.onnx.symbolic_opsets*-Funktionen sind nicht mehr zugänglich. Erwägen Sie, eine Kopie des Quellcodes zu erstellen, wenn Sie aus Gründen der Kompatibilität mit dem TorchScript-basierten Exporter auf private Funktionen zugreifen müssen.

torch.onnx.symbolic_caffe2 entfernen (#157102)

Die Unterstützung für caffe2 im ONNX-Exporter wurde beendet und entfernt.

/d2implyavx512upperregs-Flag entfernen, das den Build verlangsamt (#159431)

Wieder eingeführte AVX512-Optimierungen für Windows VS2022-Builds können Probleme mit bestimmten Versionen von VS2022 verursachen, siehe #145702

Fügen Sie ScalarType zur Shim-Konvertierung und stable::Tensor.scalar_type hinzu (#160557)

Zuvor konnten Benutzererweiterungen verschleierte D-Typen, die als int32_ts angezeigt wurden, nur abstrakt weitergeben. Jetzt können Benutzer torch::headeronly::ScalarType sicher in ihren Erweiterungen für wichtige Skalartypen verwenden. Dieser PR ermöglicht ABI-Stabilität durch das Hinzufügen einer Übersetzungsschicht durch den Shim, sodass Benutzererweiterungen keine Angst haben müssen, selbst wenn sich die ScalarType-Enum-Werte in der Zukunft ändern. Diese Änderung fügt ScalarType-Unterstützung für Benutzererweiterungen hinzu und ist nur knapp BC-brechend für unbeliebte D-Typen: quint*s, qint*s, Bits*, dummy_uint*s, dummy_int*s, Float8_e8m0fnu und Float4_e2m1fn_x2 in dem Anwendungsfall, in dem eine Erweiterung einen Tensor-D-Typ der oben genannten abruft und ihn an aoti_torch_call_dispatcher übergibt.

Abwertungen

pin_memory_device-Parameter in torch.utils.data.DataLoader veraltet (#158323)

Wir verschieben die Aktivierung von pin_memory zurück in BaseDataLoaderIter. Dies ist für StatefulDataloader erforderlich, das direkt BaseDataLoaderIter und nicht die Klasseninitialisierung Dataloader nutzt

torch.export.export_for_training API zugunsten des Äquivalents torch.export.export API verwerfen (#158203)

torch.export.export_for_training existiert, weil wir interne Exportverwendungen nicht in die endgültige IR migrieren konnten. Nachdem wir die Migration nun abgeschlossen haben, haben wir diesen API als veraltet markiert und gelöscht.

Backwards Incompatible Changes

Min supported Python version is now 3.10 (#162310)

The minimum version of Python required for PyTorch 2.9.0 is 3.10. We also have 3.14 and 3.14t available as preview with this release.

Undefined behavior when an output of a custom operator shares storage with an input

This is a reminder that outputs of PyTorch custom operators (that are registered using the torch.library or TORCH_LIBRARY APIs) are not allowed to return Tensors that share storage with input tensors. The violation of this condition leads to undefined behavior: sometimes the result will be correct, sometimes it will be garbage.

After #163227, custom operators that violated this condition that previously returned correct results under torch.compile may now return silently incorrect results under torch.compile. Because this is changing the behavior of undefined behavior, we do not consider this to be a bug, but we are still documenting it in this section as a "potentially unexpected behavior change".

This is one of the conditions checked for by torch.library.opcheck and is mentioned in The Custom Operators Manual

More details

Outputs of PyTorch custom operators are not allowed to return Tensors that share storage with input tensors

For example, the following two custom operators are not valid custom operators:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    # the result of `foo` must not directly be an input to foo.
    return x

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    # the result of bar must not be a view of an input of bar
    return x.view(-1)

The easiest workaround is to add an extra .clone() to the outputs:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

A common way to get into this situation is for a user to want to create a custom operator that sometimes mutates the input in-place and sometimes returns a new Tensor, like in the following example.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

This dynamism is not supported and leads to undefined behavior. The workaround is to split the custom operator into two custom operators, one that always mutates the input in-place, and another that always returns a new Tensor.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

torch.cat now raises ValueError, IndexError or TypeError where appropriate instead of the generic RuntimeError. If you code was catching these errors, you can update to catch the new error type.

Default to dynamo=True for ONNX exporter (#159646, #162726)

Previously torch.onnx.export(...) used the legacy TorchScript exporter if no arguments were provied. The ONNX exporter now uses the newer torch.export.export pipeline by default (dynamo=True). This change improves graph fidelity and future-proofs exports, but may surface graph capture errors that were previously masked or handled differently.

Previously in torch 2.8.0:

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Recommendation: first try the new default; only fall back if you hit blocking issues and report them upstream. Long term solution: fix the root cause instead of relying on fallback or TorchScript exporter.

Switch off runtime asserts by default in Export in favor of a shape guards function (#160111, #161178, #161794)

To enable runtime asserts, use export(..., prefer_deferred_runtime_asserts_over_guards=True). Also kills the allow_complex_guards_as_runtime_asserts flag, merging it into the former option.

Additionally, exported_program.module() will generate a call to a _guards_fn submodule that will run additional checks on inputs. Users who do not want this behavior can either remove this call in the graph, or do exported_program.module(check_guards=False) to avoid the generation.

Previously in torch 2.8.0:

# opset_version=18
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#

#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

# torch.export.export strict=False/True both

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Add ScalarType to shim conversion and stable::Tensor.scalar_type (#160557)

Before, user extensions could only in abstract pass around obfuscated dtypes appearing as int32_ts. Now, users can confidently use torch::headeronly::ScalarType in their extensions for major scalar types. This PR enables ABI stability by adding a translation layer through the shim, so that even if the ScalarType enum values change in the future, user extensions need not fear.

This change adds ScalarType support for user extensions and is only narrowly BC breaking for unpopular dtypes: quint*s, qint*s, Bits*, dummy_uint*s, dummy_int*s, Float8_e8m0fnu, and Float4_e2m1fn_x2 in the use case where an extension retrieves a Tensor dtype of the above and passes it into aoti_torch_call_dispatcher.
