Nachfolgend finden Sie die vollständigen release notes für diese Version. # Abwärtsinkompatible Änderungen ## Frontend erstellen – Verstärkte SVE-Kompilierungsprüfungen in `FindARM.cmake`, die möglicherweise zuvor akzeptierte, aber falsche SVE-Konfigurationen zurückweisen ([#176646](https://github.com/pytorch/pytorch/pull/176646)) Quellbuilds, die SVE ermöglichen, validieren die Compilerkonfiguration jetzt strenger. Wenn ein Build zuvor mit einem unvollständigen oder nicht übereinstimmenden SVE-Setup bestanden wurde, schlägt er jetzt möglicherweise während der CMake-Konfiguration statt später in der Kompilierung fehl. Aktualisieren Sie die Compiler-/Toolchain-Flags, damit sie die Ziel-SVE-Unterstützung genau beschreiben, oder deaktivieren Sie SVE für diesen Build. – Die zum Erstellen von PyTorch aus dem Quellcode erforderliche CUDA-Mindestversion wurde auf CUDA 12.6 ([#178925](https://github.com/pytorch/pytorch/pull/178925)) aktualisiert. Das Erstellen von PyTorch aus dem Quellcode mit CUDA-Versionen, die älter als 12.6 sind, wird nicht mehr unterstützt. Benutzer, die benutzerdefinierte Binärdateien erstellen, sollten CUDA 12.6 oder neuer installieren und sicherstellen, dass `CUDA_HOME` auf diese Installation verweist. Version 2.11: ```bash CUDA_HOME=/usr/local/cuda-12.4 python setup.py develop ``` Version 2.12: ```bash CUDA_HOME=/usr/local/cuda-12.6 python setup.py develop ``` – Ein C++20-Minimum in CMake-Build-Dateien erzwungen ([#178662](https://github.com/pytorch/pytorch/pull/178662)) Quell-Builds erfordern jetzt einen Compiler und eine Build-Konfiguration, die C++20 unterstützt. Wenn Sie benutzerdefinierte Build-Skripte oder Downstream-Erweiterungen verwalten, die PyTorch aus dem Quellcode erstellen, aktualisieren Sie den Compiler und entfernen Sie die Annahmen, dass PyTorch als C++17 erstellt werden kann. ## Verteilt – `torch.distributed.nn.functional`-Operationen erhöhen jetzt `RuntimeError` unter `torch.compile` ([#177342](https://github.com/pytorch/pytorch/pull/177342)) Alle Operationen in `torch.distributed.nn.functional` (z. B. `broadcast`, `all_reduce`, `all_gather`, `reduce_scatter`, `all_to_all_single`) lösen jetzt `RuntimeError` aus, wenn sie innerhalb von `torch.compile` aufgerufen werden. Benutzer sollten auf die Funktionskollektive API in `torch.distributed._functional_collectives` migrieren. Version 2.11: ```python @torch.compile def my_func(x): return torch.distributed.nn.functional.all_reduce(x, op=ReduceOp.SUM) ``` Version 2.12: ```python @torch.compile def my_func(x): return torch.distributed._functional_collectives.all_reduce(x, reduceOp="sum", group=group) ``` ## TorchElastic – `torchrun` verwendet jetzt standardmäßig einen vom Betriebssystem zugewiesenen freien Port für Einzelknotentraining anstelle von Port 29500 ([#175699](https://github.com/pytorch/pytorch/pull/175699)) Wenn `torchrun --nproc-per-node=N script.py` ohne Angabe von `--master-port` oder `--standalone` ausgeführt wird, verwendet das Standardverhalten jetzt automatisch einen vom Betriebssystem zugewiesenen freien Port über das `c10d`-Rendezvous-Backend. Dadurch werden Fehler „Adresse bereits verwendet“ vermieden, wenn mehrere Trainingsjobs gleichzeitig ausgeführt werden. Multi-Node-Training, explizites `--master-port`, `PET_MASTER_PORT` env var und `--standalone` bleiben unverändert. Version 2.11: ```bash # Used static rendezvous on port 29500 by default torchrun --nproc-per-node=4 train.py ``` Version 2.12: ```bash # Uses OS-assigned free port by default torchrun --nproc-per-node=4 train.py

To explicitly use a fixed port:

torchrun --nproc-per-node=4 --master-port=29500 train.py

## MPS
– Alle MPS-Tensoren werden jetzt im einheitlichen Speicher zugewiesen ([#175818](https://github.com/pytorch/pytorch/pull/175818))
Zuvor konnten MPS-Tensoren entweder nur im Gerätespeicher oder im einheitlichen Speicher zugewiesen werden. Jetzt nutzen alle MPS-Tensoren bedingungslos den einheitlichen Speicher. Dies vereinfacht die Speicherverwaltung und ermöglicht den CPU-Zugriff auf MPS-Tensordaten ohne explizite Kopien. Code, der auf der reinen Gerätespeicherplatzierung basiert, weist möglicherweise unterschiedliche Leistungsmerkmale auf.
## Induktor
– Die in 2.11 eingeführte `max_autotune`-Layouteinschränkungsverzögerung ist jetzt optional ([#175330](https://github.com/pytorch/pytorch/pull/175330))
In 2.11 hat Inductor das Einfrieren des Layouts für `max_autotune`-Vorlagen verschoben, um mehr Fusionsmöglichkeiten freizugeben. Dies verursachte einen regionalen Induktorfehlermodus, sodass die Standardeinstellung in 2.12 auf sofortiges Einfrieren des Layouts zurückgesetzt wird. Benutzer, die sich bei Fusionsmöglichkeiten auf das verzögerte Verhalten verlassen haben, sollten sich explizit über `torch._inductor.config.max_autotune_defer_layout_freezing` oder `TORCHINDUCTOR_MAX_AUTOTUNE_DEFER_LAYOUT_FREEZING=1` anmelden.
Version 2.11:
```python
# Deferred layout freezing was the default
torch.compile(model, mode="max-autotune")

Version 2.12:

import torch._inductor.config as cfg
cfg.max_autotune_defer_layout_freezing = True
# or set TORCHINDUCTOR_MAX_AUTOTUNE_DEFER_LAYOUT_FREEZING=1
torch.compile(model, mode="max-autotune")

Abwertungen

Release-Engineering

– CUDA 12.8-Builds zugunsten von CUDA 13.0 verwerfen (#179072) CUDA 12.8-Binärdateien wurden aus der PyTorch-Binär-Build-Matrix entfernt. CUDA 13.0 ist jetzt der stabile Standard und CUDA 12.6 bleibt für Benutzer mit älteren Treibern verfügbar. Benutzer, die die Index-URL cu128 explizit anpinnen, müssen zu cu130 (empfohlen) oder cu126 wechseln. Version 2.11:

pip install torch --index-url https://download.pytorch.org/whl/cu128

Version 2.12:

# Use CUDA 13.0 (default on PyPI):
pip install torch
# Or explicitly:
pip install torch --index-url https://download.pytorch.org/whl/cu130
# Older driver fallback:
pip install torch --index-url https://download.pytorch.org/whl/cu126

– Kompatibilität mit CMake < 3.10 wird in einer zukünftigen Version entfernt (#166259) Quellbuilds für CMake-Versionen, die älter als 3.10 sind, geben jetzt eine veraltete Warnung aus. Für eine zukünftige Version ist CMake 3.10 oder neuer erforderlich. Bitte aktualisieren Sie CMake vorher.

Lineare Algebra

  • Mehrere CUDA-Linearalgebra-Operatoren verwenden das MAGMA-Backend nicht mehr und senden jetzt bedingungslos an cuSolver oder cuBLAS: – torch.linalg.eigh sendet jetzt an cuSolver (#174619) – torch.linalg.lu_solve sendet jetzt an cuSolver/cuBLAS (#174248) – torch.linalg.cholesky_inverse sendet jetzt an cuSolver (#174681) – torch.linalg.cholesky_solve sendet jetzt an cuSolver (#174769) Der Benutzercode, der diese APIs aufruft, muss nicht geändert werden. Die praktischen Auswirkungen betreffen Benutzer, die auf MAGMA-spezifisches numerisches Verhalten, Leistungsmerkmale oder Debugging angewiesen sind. Diese Aufrufe verwenden jetzt die cuSolver/cuBLAS-Implementierungen auf CUDA.

FullyShardedDataParallel2 (FSDP2)

– Das Kompilieren über FSDP2-Hooks ohne Diagrammunterbrechungen wird nicht mehr unterstützt (#174863, #174906). Wenn Sie kompiliertes Autograd mit FSDP2 verwenden, aktualisieren Sie Ihren Code, um Diagrammunterbrechungen um FSDP2-Hooks zu ermöglichen, oder deaktivieren Sie kompiliertes Autograd für den FSDP2-Trainingsschritt. Version 2.11:

with torch._dynamo.config.patch(compiled_autograd=True):
    compiled_model = torch.compile(fsdp_model, fullgraph=True)
    loss = compiled_model(input).sum()
    loss.backward()

Version 2.12:

# Either run FSDP2 backward without fullgraph.
compiled_model = torch.compile(fsdp_model, fullgraph=False)
loss = compiled_model(input).sum()
loss.backward()

# Or apply compile before applying FSDP.
compiled_model_pre_fsdp = torch.compile(model, fullgraph=True)
compiled_model = fully_shard(compiled_model_pre_fsdp, ...)
loss = compiled_model(input).sum()
loss.backward()

Dynamo

– torch.compile(fullgraph=True) warnt jetzt, wenn bei einem Aufruf kein kompilierter Code ausgeführt wird; führt zu einem Fehler in 2.13 (#181940) Bisher wurde fullgraph=True erst validiert, nachdem Dynamo die Funktion tatsächlich kompiliert und ausgeführt hat. Wenn Dynamo zum Zeitpunkt des Anrufs umgangen wurde (z. B. unter einem benutzerdefinierten TorchDispatchMode), hatte die Anmerkung stillschweigend keine Auswirkung. 2.12 gibt eine Warnung aus; 2.13 wird erhöht. Für Grafikumbruchfehler ohne die stärkeren Garantien von fullgraph verwenden Sie torch._dynamo.error_on_graph_break. Version 2.12:

from torch.utils._python_dispatch import TorchDispatchMode

class LoggingMode(TorchDispatchMode):
    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        return func(*args, **(kwargs or {}))

@torch.compile(fullgraph=True)
def model(x):
    return x.sin() + 1

# A user-defined TorchDispatchMode is active, so Dynamo skips the frame
# and no compiled code runs — emits a warning in 2.12, will raise in 2.13.
with LoggingMode(): # Remove this to fix warning
    model(torch.randn(3, 4))

– Die Dynamo-Konfiguration inline_inbuilt_nn_modules ist veraltet (#177489, #178205) Das Inlining integrierter nn.Module-Instanzen ist jetzt die Standardeinstellung. Durch das Setzen des Flags wird eine veraltete Warnung ausgegeben, die in einer zukünftigen Version entfernt wird. Version 2.11:

import torch._dynamo.config as cfg
cfg.inline_inbuilt_nn_modules = True  # was a tunable knob

Version 2.12:

# No action needed — inlining is on by default.
# Remove any explicit references to torch._dynamo.config.inline_inbuilt_nn_modules.

– Dem torch.compile-Konfigurationsmodul wurde ein veraltetes Framework hinzugefügt, damit einzelne Optionen als veraltet markiert werden können (#169837)

  • Benutzerdefinierte Stream-Unterstützung zu torch.compile hinzugefügt.   • Eine Triton-Vorlage für die Tiefenansicht conv1d hinzugefügt (#175280) – AVX10.2 fp32↔fp8-Intrinsics in at::vec::convert für das Inductor C++ x86-Backend hinzugefügt (#172309)

Backwards Incompatible Changes

Build Frontend

  • Strengthened SVE compile checks in FindARM.cmake, which may reject previously accepted but incorrect SVE configurations (#176646)

    Source builds that enable SVE now validate the compiler configuration more strictly. If a build previously passed with an incomplete or mismatched SVE setup, it may now fail during CMake configuration instead of later in compilation. Update the compiler/toolchain flags so they accurately describe the target SVE support, or disable SVE for that build.

  • Updated the minimum CUDA version required to build PyTorch from source to CUDA 12.6 (#178925)

    Building PyTorch from source with CUDA versions older than 12.6 is no longer supported. Users building custom binaries should install CUDA 12.6 or newer and make sure CUDA_HOME points to that installation.

    Version 2.11:

    CUDA_HOME=/usr/local/cuda-12.4 python setup.py develop

    Version 2.12:

    CUDA_HOME=/usr/local/cuda-12.6 python setup.py develop

  • Enforced a C++20 minimum in CMake build files (#178662)

    Source builds now require a compiler and build configuration that support C++20. If you maintain custom build scripts or downstream extensions that build PyTorch from source, update the compiler and remove assumptions that PyTorch can be built as C++17.

Distributed

  • torch.distributed.nn.functional ops now raise RuntimeError under torch.compile (#177342)

    All ops in torch.distributed.nn.functional (e.g., broadcast, all_reduce, all_gather, reduce_scatter, all_to_all_single) now raise RuntimeError when called inside torch.compile. Users should migrate to the functional collectives API in torch.distributed._functional_collectives.

    Version 2.11:

    @torch.compile
def my_func(x):
    return torch.distributed.nn.functional.all_reduce(x, op=ReduceOp.SUM)

    Version 2.12:

    @torch.compile
def my_func(x):
    return torch.distributed._functional_collectives.all_reduce(x, reduceOp="sum", group=group)

TorchElastic

  • torchrun now defaults to an OS-assigned free port for single-node training instead of port 29500 (#175699)

    When running torchrun --nproc-per-node=N script.py without specifying --master-port or --standalone, the default behavior now automatically uses an OS-assigned free port via the c10d rendezvous backend. This eliminates "Address already in use" errors when running multiple training jobs concurrently. Multi-node training, explicit --master-port, PET_MASTER_PORT env var, and --standalone are unchanged.

    Version 2.11:

    # Used static rendezvous on port 29500 by default
torchrun --nproc-per-node=4 train.py

    Version 2.12:

    # Uses OS-assigned free port by default
torchrun --nproc-per-node=4 train.py

# To explicitly use a fixed port:
torchrun --nproc-per-node=4 --master-port=29500 train.py

MPS

  • All MPS tensors are now allocated in unified memory (#175818)

    Previously, MPS tensors could be allocated in either device-only or unified memory. Now all MPS tensors use unified memory unconditionally. This simplifies memory management and enables CPU access to MPS tensor data without explicit copies. Code that relied on device-only memory placement may observe different performance characteristics.

Inductor

  • The max_autotune layout-constraint deferral introduced in 2.11 is now opt-in (#175330)

    In 2.11, Inductor deferred layout freezing for max_autotune templates to expose more fusion opportunities. This caused a regional-inductor failure mode, so the default in 2.12 reverts to immediate layout freezing. Users who relied on the deferred behavior for fusion opportunities should opt in explicitly via torch._inductor.config.max_autotune_defer_layout_freezing or TORCHINDUCTOR_MAX_AUTOTUNE_DEFER_LAYOUT_FREEZING=1.

    Version 2.11:

    # Deferred layout freezing was the default
torch.compile(model, mode="max-autotune")

    Version 2.12:

    import torch._inductor.config as cfg
cfg.max_autotune_defer_layout_freezing = True
# or set TORCHINDUCTOR_MAX_AUTOTUNE_DEFER_LAYOUT_FREEZING=1
torch.compile(model, mode="max-autotune")

    CUDA 12.8 binaries have been removed from the PyTorch binary build matrix. CUDA 13.0 is now the stable default and CUDA 12.6 remains available for users on older drivers. Users explicitly pinning the cu128 index URL will need to switch to cu130 (recommended) or cu126.

    pip install torch --index-url https://download.pytorch.org/whl/cu128

    Version 2.12:

    # Use CUDA 13.0 (default on PyPI):
pip install torch
# Or explicitly:
pip install torch --index-url https://download.pytorch.org/whl/cu130
# Older driver fallback:
pip install torch --index-url https://download.pytorch.org/whl/cu126

Linear Algebra

  • Several CUDA linear algebra operators no longer use the MAGMA backend and now dispatch to cuSolver or cuBLAS unconditionally:

    • torch.linalg.eigh now dispatches to cuSolver (#174619)
    • torch.linalg.lu_solve now dispatches to cuSolver/cuBLAS (#174248)
    • torch.linalg.cholesky_inverse now dispatches to cuSolver (#174681)
    • torch.linalg.cholesky_solve now dispatches to cuSolver (#174769)

    User code calling these APIs does not need to change. The practical impact is for users who depended on MAGMA-specific numerical behavior, performance characteristics, or debugging. Those calls now use the cuSolver/cuBLAS implementations on CUDA.

    Version 2.11:

    with torch._dynamo.config.patch(compiled_autograd=True):
    compiled_model = torch.compile(fsdp_model, fullgraph=True)
    loss = compiled_model(input).sum()
    loss.backward()

    Version 2.12:

    # Either run FSDP2 backward without fullgraph.
compiled_model = torch.compile(fsdp_model, fullgraph=False)
loss = compiled_model(input).sum()
loss.backward()

# Or apply compile before applying FSDP.
compiled_model_pre_fsdp = torch.compile(model, fullgraph=True)
compiled_model = fully_shard(compiled_model_pre_fsdp, ...)
loss = compiled_model(input).sum()
loss.backward()

Dynamo

  • torch.compile(fullgraph=True) now warns when a call runs no compiled code; will error in 2.13 (#181940)

    Previously fullgraph=True was only validated once Dynamo actually compiled and ran the function. If Dynamo was bypassed at call time (e.g. under a user-defined TorchDispatchMode), the annotation silently had no effect. 2.12 emits a warning; 2.13 will raise. For graph-break errors without fullgraph's stronger guarantees, use torch._dynamo.error_on_graph_break.

    Version 2.12:

    from torch.utils._python_dispatch import TorchDispatchMode

class LoggingMode(TorchDispatchMode):
    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        return func(*args, **(kwargs or {}))

@torch.compile(fullgraph=True)
def model(x):
    return x.sin() + 1

# A user-defined TorchDispatchMode is active, so Dynamo skips the frame
# and no compiled code runs — emits a warning in 2.12, will raise in 2.13.
with LoggingMode(): # Remove this to fix warning
    model(torch.randn(3, 4))
