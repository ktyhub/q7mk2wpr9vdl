Wesentliche Änderungen

Asset-Partitionierung

Das Hauptmerkmal des Airflow 3.2.0 ist die Asset-Partitionierung – eine wichtige Weiterentwicklung der Datenerkennung Terminplanung. Anstatt Dags basierend auf einem gesamten Asset auszulösen, können Sie jetzt eine nachgelagerte Planung durchführen Verarbeitung basierend auf bestimmten Datenpartitionen. Nur der relevante Datenausschnitt löst nachgelagert aus Arbeit, wodurch die Pipeline-Orchestrierung wesentlich effizienter und präziser wird.

Dies ist wichtig, wenn Sie mit partitionierten Data Lakes arbeiten – datumspartitionierte S3-Pfade, Hive-Tabelle Partitionen, BigQuery-Tabellenpartitionen oder andere partitionierte Datenspeicher. Bisher kein Update auf ein Asset löste alle nachgelagerten Dags aus, unabhängig davon, welche Partition sich geändert hat. Jetzt nur noch das Richtige Die Arbeit wird zum richtigen Zeitpunkt ausgelöst.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/authoring-and-scheduling/assets.

Multi-Team-Bereitstellungen

Airflow 3.2 bietet Multi-Team-Unterstützung und ermöglicht es Unternehmen, mehrere isolierte Teams innerhalb einer einzigen Airflow-Bereitstellung zu betreiben. Jedes Team kann seine eigenen Dags, Verbindungen, Variablen, Pools und Executors haben – was eine echte Ressourcen- und Berechtigungsisolierung ermöglicht, ohne dass separate Airflow-Instanzen pro Team erforderlich sind.

Dies ist besonders wertvoll für Plattformteams, die mehrere Data-Engineering- oder Data-Science-Teams über eine gemeinsame Infrastruktur bedienen und gleichzeitig starke Grenzen zwischen den Ressourcen und dem Zugriff der Teams wahren.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/core-concepts/multi-team.

.. Warnung::

Multi-Team-Bereitstellungen sind in 3.2.0 experimentell und können sich in zukünftigen Versionen basierend auf ändern Benutzer-Feedback.

Synchrone Rückrufunterstützung für Deadline Alerts

Deadline Alerts unterstützen jetzt zusätzlich zu den bestehenden synchrone Rückrufe über „SyncCallback“. asynchrones „AsyncCallback“. Synchrone Rückrufe werden vom Executor ausgeführt (und nicht der Trigger) und kann optional über den Parameter „executor“ einen bestimmten Executor ansprechen.

Ein Dag kann auch mehrere Fristwarnungen definieren, indem er eine Liste an den Parameter „deadline“ übergibt. und jede Warnung kann einen der beiden Rückruftypen verwenden.

.. Warnung::

Fristwarnungen sind in 3.2.0 experimentell und können sich in zukünftigen Versionen basierend auf ändern Benutzer-Feedback. Synchrone Terminrückrufe („SyncCallback“) sind derzeit nicht möglich Unterstützt Verbindungen, die in der Airflow-Metadatendatenbank gespeichert sind.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/howto/deadline-alerts.

Verbesserungen und Leistung der Benutzeroberfläche

  • Grid-View-Virtualisierung: Die Grid-Ansicht nutzt jetzt Virtualisierung – nur sichtbare Zeilen werden im DOM gerendert. Dies verbessert die Leistung beim Anzeigen von Dags mit einer großen Anzahl von Aufgabenausführungen erheblich und reduziert die Renderzeit und den Speicherverbrauch für komplexe Dags. (#60241)

  • XCom-Verwaltung in der Benutzeroberfläche: Sie können XCom-Werte jetzt direkt über die Airflow-Benutzeroberfläche hinzufügen, bearbeiten und löschen. Dies erleichtert das Debuggen und Verwalten des XCom-Status während der Entwicklung und im täglichen Betrieb erheblich, ohne dass CLI-Befehle erforderlich sind. (#58921)

  • HITL-Detailverlauf: Die Human-in-the-Loop-Genehmigungsschnittstelle umfasst jetzt eine vollständige Verlaufsansicht, sodass Bediener und Prüfer den vollständigen Prüfpfad von Genehmigungen und Ablehnungen für jede Aufgabe einsehen können. (#56760, #55952)

  • Gantt-Diagramm-Verbesserungen:

    • Alle Aufgabenversuche werden angezeigt: Das Gantt-Diagramm zeigt jetzt jeden Versuch an, nicht nur den letzten

  • Aufgabenanzeigenamen im Gantt: task_display_name wird zur besseren Lesbarkeit angezeigt (#61438)

    • ISO-Daten im Gantt: Browserübergreifendes einheitliches Datumsformat (#61250)
    • Absturz bei Null-Datum/Uhrzeit behoben: Das Gantt-Diagramm stürzt bei Aufgaben mit Null-Datum/Uhrzeit-Feldern nicht mehr ab

Neues Flag „--only-idle“ für den Scheduler CLI

Das Flag „airflow scheduler`` command has a new ``--only-idle“, das nur zählt, wird ausgeführt, wenn das Der Planer ist inaktiv. Dies hilft Benutzern, den Scheduler einmal auszuführen und alle ausgelösten Dags und zu verarbeiten Aufgaben in der Warteschlange. Es erfordert und ergänzt das Flag „--num-runs“, sodass ein kleiner Wert festgelegt werden kann anstatt zu erraten, wie viele Iterationen der Scheduler benötigt.

Ersetzen Sie TI-Zusammenfassungsanforderungen pro Lauf durch einen einzelnen NDJSON-Stream

Die Raster-, Diagramm-, Gantt- und Aufgabendetailansichten rufen jetzt Aufgabeninstanzen ab Zusammenfassungen über eine einzige Streaming-HTTP-Anfrage („GET /ui/grid/ti_summaries/{dag_id}?run_ids=...“) anstelle einer Anfrage pro Lauf. Der Server gibt pro Lauf eine JSON-Zeile aus, sobald die Aufgabe dieses Laufs ausgeführt wird Instanzen sind bereit, sodass die Spalten nacheinander und nicht alle auf einmal angezeigt werden.

Was hat sich geändert:

  • „GET /ui/grid/ti_summaries/{dag_id}?run_ids=...“ ist jetzt der einzige Endpunkt für TI-Zusammenfassungen wird jeweils ein „application/x-ndjson“-Stream zurückgegeben Zeile ist ein serialisiertes „GridTISummaries“-Objekt für einen Lauf. – Der alte Single-Run-Endpunkt „GET /ui/grid/ti_summaries/{dag_id}/{run_id}“. wurde entfernt. – Die serialisierte Dag-Struktur wird einmal geladen und von allen Läufen gemeinsam genutzt teilen sich das gleiche „dag_version_id“, um eine redundante Deserialisierung zu vermeiden.
  • Alle UI-Ansichten (Raster, Diagramm, Gantt, Aufgabeninstanz, zugeordnete Aufgabeninstanz, Gruppe Task-Instanz) verwenden den Stream-Endpunkt und übergeben ein oder mehrere „run_ids“.

Strukturierte JSON-Protokollierung für alle API-Serverausgaben

Der neue Abschnitt „json_logs`` option under the ``[logging]“ sorgt für Luftstrom Erzeugen Sie stattdessen die gesamte Ausgabe als durch Zeilenumbrüche getrennte JSON (strukturierte Protokolle). Für Menschen lesbare formatierte Protokolle. Dies umfasst den API-Server (Gunicorn/Uvicorn), einschließlich Zugriffsprotokollen, Warnungen und nicht behandelten Ausnahmen.

Dies unterstützen noch nicht alle Komponenten – insbesondere „airflow celery worker“. Jede Nicht-JSON-Ausgabe, wenn „json_logs“ aktiviert ist, wird als Fehler behandelt. (#63365)

Entfernen Sie die alte OTel Trace-Metaklasse und gemeinsam genutzte Tracer-Wrapper

Die in „airflow.traces“ befindlichen Schnittstellen und Funktionen waren Interner Code, der eine Standardmethode zur Verwaltung von Spannen bereitstellte interner Airflow-Code. Sie waren nicht als benutzerorientierter Code gedacht und wurden nie dokumentiert. Sie werden nicht mehr benötigt, also wir Entfernen Sie sie in 3.2. (#63452)

Ausnahmeimporte auf Aufgabenebene in die Aufgabe SDK verschieben

Airflow bezieht jetzt aufgabenbezogene Ausnahmen („AirflowSkipException``, ``TaskDeferred“ usw.) von „airflow.sdk.exceptions``. ``airflow.exceptions“ macht immer noch dieselben Ausnahmen verfügbar, aber sie sind es Proxys, die „DeprecatedImportWarning“ ausgeben, damit Dag-Autoren migrieren können, bevor der Shim entfernt wird.

Was hat sich geändert:

– Laufzeitcode löst jetzt konsistent die SDK-Versionen von Ausnahmen auf Aufgabenebene aus. – Die Task SDK definiert diese Klassen neu, sodass Worker zur Laufzeit nicht mehr von „airflow-core“ abhängig sind.

  • „airflow.providers.common.compat.sdk“ zentralisiert Kompatibilitätsimporte für Anbieter.

Verhaltensänderungen:

  • Sensoren und andere Helfer, die Benutzereingaben validieren, lösen jetzt „ValueError“ aus (statt Die Argumente „AirflowException``) when ``poke_interval``/ ``timeout“ sind ungültig. – Beim Importieren veralteter Ausnahmenamen aus „airflow.exceptions“ wird eine Warnung protokolliert, die Benutzer darauf verweist den SDK-Importpfad.

Ausnahmen, die jetzt von „airflow.sdk.exceptions“ bereitgestellt werden:

  • „AirflowException`` and ``AirflowNotFoundException“.
  • „AirflowRescheduleException`` and ``AirflowSensorTimeout“.
  • „AirflowSkipException``, ``AirflowFailException``, ``AirflowTaskTimeout``, ``AirflowTaskTerminated“.
  • „TaskDeferred``, ``TaskDeferralTimeout``, ``TaskDeferralError“.
  • DagRunTriggerException and DownstreamTasksSkipped
  • AirflowDagCycleException and AirflowInactiveAssetInInletOrOutletException
  • „ParamValidationError``, ``DuplicateTaskIdFound``, ``TaskAlreadyInTaskGroup``, ``TaskNotFound``, ``XComNotFound“.
  • AirflowOptionalProviderFeatureException

Abwärtskompatibilität:

  • Vorhandene Dags/Operatoren, die weiterhin von „airflow.exceptions“ importieren, funktionieren jedoch weiterhin Sie protokollieren Warnungen.
  • Anbieter können sich darauf verlassen, dass „airflow.providers.common.compat.sdk“ einen funktionierenden Importpfad beibehält über alle unterstützten Airflow-Versionen hinweg.

Migration:

  • Aktualisieren Sie benutzerdefinierte Operatoren, Sensoren und Erweiterungen, um Ausnahmeklassen daraus zu importieren „airflow.sdk.exceptions“ (oder vom kompatiblen Anbieter des Anbieters). – Passen Sie den benutzerdefinierten Validierungscode an, um „ValueError“ für ungültige Sensorargumente zu erwarten, falls dies der Fall ist zuvor gefangen AirflowException.

Unterstützt numerische Multiplikatorwerte für den Parameter retry_exponential_backoff

Der „retry_exponential_backoff`` parameter now accepts numeric values to specify custom exponential backoff multipliers for task retries. Previously, this parameter only accepted boolean values (``True`` or ``False``), with ``True`` using a hardcoded multiplier of ``2.0“.

Neues Verhalten:

– Numerische Werte (z. B. „2.0``, ``3.5“) geben direkt den exponentiellen Backoff-Multiplikator an

  • „retry_exponential_backoff=2.0“ verdoppelt die Verzögerung zwischen jedem Wiederholungsversuch
  • retry_exponential_backoff=0 or False disables exponential backoff (uses fixed retry_delay)

Abwärtskompatibilität:

Vorhandene Dags, die boolesche Werte verwenden, funktionieren weiterhin:

  • „retry_exponential_backoff=True`` → converted to ``2.0“ (behält das ursprüngliche Verhalten bei)
  • „retry_exponential_backoff=False`` → converted to ``0.0“ (kein exponentielles Backoff)

API Änderungen:

Das REST-API-Schema für „retry_exponential_backoff`` has changed from ``type: boolean`` to ``type: number“. API clients müssen numerische Werte verwenden (boolesche Werte werden abgelehnt).

Migration:

Während boolesche Werte in Python Dags aus Gründen der Abwärtskompatibilität automatisch konvertiert werden, empfehlen wir aus Gründen der Übersichtlichkeit die Aktualisierung auf explizite numerische Werte:

  • Ändern Sie „retry_exponential_backoff=True`` → ``retry_exponential_backoff=2.0“.
  • Ändern Sie „retry_exponential_backoff=False`` → ``retry_exponential_backoff=0“.

Serialisierungs-/Deserialisierungslogik (Serde) in Task SDK verschieben

Airflow bezieht die Serde-Logik jetzt von „airflow.sdk.serde“ statt „airflow.serialization.serde``. Serializer modules have moved from ``airflow.serialization.serializers.*“. zu „airflow.sdk.serde.serializers.*``. The old import paths still work but emit ``DeprecatedImportWarning“. Migration zu steuern. Die Abwärtskompatibilitätsebene wird in Airflow 4 entfernt.

Was hat sich geändert:

– Serialisierungs-/Deserialisierungscode aus dem Paket „airflow-core`` to ``task-sdk“ verschoben – Serialisierungsmodule wurden von „airflow.serialization.serializers.*`` to ``airflow.sdk.serde.serializers.*“ verschoben – Dem Namespace „airflow.sdk.serde.serializers.*“ sollten neue Serialisierer hinzugefügt werden

Änderungen der Codeschnittstelle:

  • Importieren Sie Serialisierer aus „airflow.sdk.serde.serializers.*`` instead of ``airflow.serialization.serializers.*“.
  • Serialisierungsfunktionen aus „airflow.sdk.serde`` instead of ``airflow.serialization.serde“ importieren

Abwärtskompatibilität:

– Vorhandene Serialisierer, die aus „airflow.serialization.serializers.*“ importieren, funktionieren weiterhin mit veralteten Warnungen – Alle vorhandenen Serialisierer (builtin, datetime, pandas, numpy usw.) sind am neuen Standort verfügbar

Migration:

  • Für vorhandene benutzerdefinierte Serialisierer: Importe aktualisieren, um „airflow.sdk.serde.serializers.*“ zu verwenden
  • Für neue Serialisierer: Fügen Sie sie zu „airflow.sdk.serde.serializers.*`` namespace (e.g., create ``task-sdk/src/airflow/sdk/serde/serializers/your_serializer.py“ hinzu.

Methoden aus PriorityWeightStrategy entfernt

Auf der (experimentellen) Klasse „PriorityWeightStrategy``, functions ``serialize()“. und „deserialize()“ wurden nirgendwo verwendet und wurden entfernt. Sie Im Benutzercode sollte man sich nicht darauf verlassen. (#59780)

Methoden aus TaskInstance entfernt

In der Klasse „TaskInstance``, functions ``run()``, ``render_templates()“, „get_template_context()“ und mit ihnen verwandte private Mitglieder entfernt. Die Klasse gilt seit 3.0 als intern und sollte dies auch nicht sein Wird im Benutzercode verwendet. (#59780, #59835)

Ändern Sie die von „DagBag“ zurückgegebenen Informationen

Neues Verhalten:

  • „DagBag`` now uses ``Path.relative_to“ für konsistentes plattformübergreifendes Verhalten.
  • „FileLoadStat`` now has two additional nullable fields: ``bundle_path`` and ``bundle_name“.

Abwärtskompatibilität:

„FileLoadStat`` will no longer produce paths beginning with ``/“ mit der Bedeutung „relativ zum dags-Ordner“. Dies ist eine bahnbrechende Änderung für jeden benutzerdefinierten Code, der auf der Grundlage dieses Verhaltens zeichenfolgenbasierte Pfadmanipulationen durchführt. Benutzern wird empfohlen, diesen Code zu aktualisieren, um „pathlib.Path“ zu verwenden. (#59785)

Entfernen Sie „--conn-id`` option from ``airflow connections list“.

Der redundante Befehl „--conn-id`` option has been removed from the ``airflow connections list“ CLI. Verwenden Sie stattdessen „airflow connections get“. (#59855)

„render_template_as_native_obj“-Überschreibung auf Bedienerebene hinzufügen

Operatoren können jetzt die Einstellung „render_template_as_native_obj“ auf Dag-Ebene überschreiben. Ermöglicht eine differenzierte Kontrolle darüber, ob Vorlagen als natives Python gerendert werden Typen oder Zeichenfolgen pro Aufgabe. Stellen Sie „render_template_as_native_obj=True“ ein oder „False`` on any operator to override the Dag setting, or leave as ``None“ (Standard) vom Dag erben.

Gunicorn-Unterstützung für den API-Server mit Zero-Downtime-Worker recycling hinzufügen

Der API-Server unterstützt jetzt Gunicorn als alternativen Server mit fortlaufenden Worker-Neustarts um eine Speicheranhäufung in lang laufenden Prozessen zu verhindern.

Hauptvorteile:

  • Rollierende Arbeiter werden neu gestartet: Neue Arbeiter erscheinen und bestehen die Gesundheitsprüfungen vor alten Arbeitern werden getötet, sodass während der Worker-Recycling keine Ausfallzeit entsteht.

  • Speicherfreigabe: Gunicorn verwendet Preload + Fork, sodass Arbeiter den Speicher über teilen Copy-on-Write. Dies reduziert die Gesamtspeichernutzung im Vergleich zu uvicorn erheblich Multiprozessmodus, bei dem jeder Worker alles unabhängig lädt.

  • Korrekte FIFO-Signalverarbeitung: Gunicorns SIGTTOU tötet den ältesten Arbeiter (FIFO), nicht das neueste (LIFO), was für fortlaufende Neustarts korrekt ist.

Konfiguration:

.. code-block:: ini

[api]
# Verwenden Sie Gunicorn anstelle von Uvicorn
server_type = gunicorn

# Aktivieren Sie rollierende Worker-Neustarts alle 12 Stunden
worker_refresh_interval = 43200

# Starten Sie die Worker einzeln neu
worker_refresh_batch_size = 1

Oder über Umgebungsvariablen:

.. Codeblock:: Bash

export AIRFLOW__API__SERVER_TYPE=gunicorn
export AIRFLOW__API__WORKER_REFRESH_INTERVAL=43200

Anforderungen:

Installieren Sie das Gunicorn-Extra: „pip install 'apache-airflow-core[gunicorn]'“.

Hinweis zu Uvicorn (Standard):

Der standardmäßige Uvicorn-Modus unterstützt keine rollierenden Worker-Neustarts, weil:

  1. Mit Workers=1 gibt es keinen Masterprozess, an den Signale gesendet werden können
  2. SIGTTOU von uvicorn tötet den neuesten Arbeiter (LIFO) und vereitelt so rollierende Neustartzwecke
  3. Jeder Uvicorn-Worker lädt alles unabhängig und ohne Speicherfreigabe

Wenn Sie Worker recycling oder eine speichereffiziente Multi-Worker-Bereitstellung benötigen, verwenden Sie gunicorn. (#60921)

Verbesserte Leistung der Bereinigung gerenderter Aufgabeninstanzfelder für Dags mit vielen zugeordneten Aufgaben (~42x schneller)

Die Konfiguration „max_num_rendered_ti_fields_per_task`` is renamed to ``num_dag_runs_to_retain_rendered_fields“. (Alter Name funktioniert immer noch mit Verfallswarnung).

Die Aufbewahrung basiert jetzt auf den N letzten Tagesläufen und nicht auf den N letzten Aufgabenausführungen. Dies kann dazu führen, dass weniger Datensätze für bedingte/spärliche Aufgaben aufbewahrt werden. (#60951)

AuthManager-Backfill-Berechtigungen werden jetzt von „requires_access_dag`` on the ``DagAccessEntity.Run“ verwaltet

Die Schnittstelle „is_authorized_backfill`` of the ``BaseAuthManager“ wurde entfernt. Core wird diese Methode und ihre nicht mehr aufrufen Die Implementierung des Anbieter-Gegenstücks wird als veraltet markiert. Berechtigungen für Backfill-Vorgänge werden jetzt anhand der vorhandenen Berechtigung „DagAccessEntity.Run“ überprüft „requires_access_dag“-Dekorateur. Mit anderen Worten: Wenn ein Benutzer die Berechtigung zum Ausführen eines Dag hat, kann er darauf Backfill-Vorgänge durchführen.

Bitte aktualisieren Sie Ihre Sicherheitsrichtlinien, um sicherzustellen, dass Benutzer, die Backfill-Vorgänge durchführen müssen, über die entsprechenden „DagAccessEntity.Run“-Berechtigungen verfügen. (Benutzer Wenn Sie über die Backfill-Berechtigungen verfügen, ohne über die DagRun-Berechtigungen zu verfügen, können Sie ohne Aktualisierung keine Backfill-Vorgänge mehr ausführen.)

airflow 3.2.0

Highlights

  • Partition-aware asset scheduling — Airflow can now trigger downstream Dags from specific asset partitions instead of any update to the entire asset. For date-partitioned S3 paths, Hive tables, or BigQuery tables, this avoids unnecessary downstream runs and processes only the changed slice. This is the strongest reason to upgrade for data-aware pipelines.

  • Experimental isolation and callback features — Multi-Team Deployments provide isolated Dags, connections, variables, pools, and executors within one Airflow instance. Deadline Alerts add executor-run SyncCallback, optional executor targeting, and support for multiple alerts per Dag. Both features are experimental and may change; notably, SyncCallback cannot currently use Connections stored in the Airflow metadata database.

  • UI scaling, with one endpoint removal — Grid virtualization (#60241) reduces DOM and memory overhead, while all task views now use the streaming GET /ui/grid/ti_summaries/{dag_id}?run_ids=... endpoint instead of one request per run. Breaking: GET /ui/grid/ti_summaries/{dag_id}/{run_id} has been removed; custom consumers must handle the application/x-ndjson response, with one GridTISummaries object per line. UI XCom editing, HITL approval history, and improved Gantt views also ease operations.

  • Task SDK migration — Task-facing exceptions now come from airflow.sdk.exceptions, and serde has moved to airflow.sdk.serde and airflow.sdk.serde.serializers.*. Existing airflow.exceptions and airflow.serialization.serde imports still work with DeprecatedImportWarning, but serde compatibility paths will be removed in Airflow 4. Update custom operators, sensors, extensions, and serializers now; also adjust validation code because invalid sensor arguments now raise ValueError rather than AirflowException.

  • Other compatibility breaks and upgrade verdict — The REST API now expects numeric retry_exponential_backoff and rejects booleans, although Python Dags retain automatic boolean conversion; prefer 2.0 and 0. TaskInstance.run(), render_templates(), get_template_context(), and PriorityWeightStrategy.serialize()/deserialize() are removed. DagBag/FileLoadStat paths no longer use slash-prefixed relative paths—use pathlib.Path—and airflow connections list --conn-id is replaced by airflow connections get. This is a substantial release worth upgrading for partition-aware scheduling, large Dags, or multi-team experimentation; unaffected users can defer, but should plan the SDK and API migrations before Airflow 4.

Significant Changes

Asset Partitioning

The headline feature of Airflow 3.2.0 is asset partitioning — a major evolution of data-aware scheduling. Instead of triggering Dags based on an entire asset, you can now schedule downstream processing based on specific partitions of data. Only the relevant slice of data triggers downstream work, making pipeline orchestration far more efficient and precise.

This matters when working with partitioned data lakes — date-partitioned S3 paths, Hive table partitions, BigQuery table partitions, or any other partitioned data store. Previously, any update to an asset triggered all downstream Dags regardless of which partition changed. Now only the right work gets triggered at the right time.

For detailed usage instructions, see :doc:/authoring-and-scheduling/assets.

Multi-Team Deployments

Airflow 3.2 introduces multi-team support, allowing organizations to run multiple isolated teams within a single Airflow deployment. Each team can have its own Dags, connections, variables, pools, and executors— enabling true resource and permission isolation without requiring separate Airflow instances per team.

This is particularly valuable for platform teams that serve multiple data engineering or data science teams from shared infrastructure, while maintaining strong boundaries between teams' resources and access.

For detailed usage instructions, see :doc:/core-concepts/multi-team.

.. warning::

Multi-Team Deployments are experimental in 3.2.0 and may change in future versions based on user feedback.

Synchronous callback support for Deadline Alerts

Deadline Alerts now support synchronous callbacks via SyncCallback in addition to the existing asynchronous AsyncCallback. Synchronous callbacks are executed by the executor (rather than the triggerer), and can optionally target a specific executor via the executor parameter.

A Dag can also define multiple Deadline Alerts by passing a list to the deadline parameter, and each alert can use either callback type.

.. warning::

Deadline Alerts are experimental in 3.2.0 and may change in future versions based on user feedback. Synchronous deadline callbacks (SyncCallback) do not currently support Connections stored in the Airflow metadata database.

For detailed usage instructions, see :doc:/howto/deadline-alerts.

UI Enhancements & Performance

  • Grid View Virtualization: The Grid view now uses virtualization -- only visible rows are rendered to the DOM. This dramatically improves performance when viewing Dags with large numbers of task runs, reducing render time and memory usage for complex Dags. (#60241)

  • XCom Management in the UI: You can now add, edit, and delete XCom values directly from the Airflow UI. This makes it much easier to debug and manage XCom state during development and day-to-day operations without needing CLI commands. (#58921)

  • HITL Detail History: The Human-in-the-Loop approval interface now includes a full history view, letting operators and reviewers see the complete audit trail of approvals and rejections for any task. (#56760, #55952)

  • Gantt Chart Improvements:

    • All task tries displayed: Gantt chart now shows every attempt, not just the latest
    • Task display names in Gantt: task_display_name shown for better readability (#61438)
    • ISO dates in Gantt: Cross-browser consistent date format (#61250)
    • Fixed null datetime crash: Gantt chart no longer crashes on tasks with null datetime fields

New --only-idle flag for the scheduler CLI

The airflow scheduler command has a new --only-idle flag that only counts runs when the scheduler is idle. This helps users run the scheduler once and process all triggered Dags and queued tasks. It requires and complements the --num-runs flag so one can set a small value instead of guessing how many iterations the scheduler needs.

Replace per-run TI summary requests with a single NDJSON stream

The grid, graph, gantt, and task-detail views now fetch task-instance summaries through a single streaming HTTP request (GET /ui/grid/ti_summaries/{dag_id}?run_ids=...) instead of one request per run. The server emits one JSON line per run as soon as that run's task instances are ready, so columns appear progressively rather than all at once.

What changed:

  • GET /ui/grid/ti_summaries/{dag_id}?run_ids=... is now the sole endpoint for TI summaries, returning an application/x-ndjson stream where each line is a serialized GridTISummaries object for one run.
  • The old single-run endpoint GET /ui/grid/ti_summaries/{dag_id}/{run_id} has been removed.
  • The serialized Dag structure is loaded once and shared across all runs that share the same dag_version_id, avoiding redundant deserialization.
  • All UI views (grid, graph, gantt, task instance, mapped task instance, group task instance) use the stream endpoint, passing one or more run_ids.

Structured JSON logging for all API server output

The new json_logs option under the [logging] section makes Airflow produce all its output as newline-delimited JSON (structured logs) instead of human-readable formatted logs. This covers the API server (gunicorn/uvicorn), including access logs, warnings, and unhandled exceptions.

Not all components support this yet — notably airflow celery worker but any non-JSON output when json_logs is enabled will be treated as a bug. (#63365)

Remove legacy OTel Trace metaclass and shared tracer wrappers

The interfaces and functions located in airflow.traces were internal code that provided a standard way to manage spans in internal Airflow code. They were not intended as user-facing code and were never documented. They are no longer needed so we remove them in 3.2. (#63452)

Move task-level exception imports into the Task SDK

Airflow now sources task-facing exceptions (AirflowSkipException, TaskDeferred, etc.) from airflow.sdk.exceptions. airflow.exceptions still exposes the same exceptions, but they are proxies that emit DeprecatedImportWarning so Dag authors can migrate before the shim is removed.

What changed:

  • Runtime code now consistently raises the SDK versions of task-level exceptions.
  • The Task SDK redefines these classes so workers no longer depend on airflow-core at runtime.
  • airflow.providers.common.compat.sdk centralizes compatibility imports for providers.

Behaviour changes:

  • Sensors and other helpers that validate user input now raise ValueError (instead of AirflowException) when poke_interval/ timeout arguments are invalid.
  • Importing deprecated exception names from airflow.exceptions logs a warning directing users to the SDK import path.

Exceptions now provided by airflow.sdk.exceptions:

  • AirflowException and AirflowNotFoundException
  • AirflowRescheduleException and AirflowSensorTimeout
  • AirflowSkipException, AirflowFailException, AirflowTaskTimeout, AirflowTaskTerminated
  • TaskDeferred, TaskDeferralTimeout, TaskDeferralError
  • DagRunTriggerException and DownstreamTasksSkipped
  • AirflowDagCycleException and AirflowInactiveAssetInInletOrOutletException
  • ParamValidationError, DuplicateTaskIdFound, TaskAlreadyInTaskGroup, TaskNotFound, XComNotFound
  • AirflowOptionalProviderFeatureException

Backward compatibility:

  • Existing Dags/operators that still import from airflow.exceptions continue to work, though they log warnings.
  • Providers can rely on airflow.providers.common.compat.sdk to keep one import path that works across supported Airflow versions.

Migration:

  • Update custom operators, sensors, and extensions to import exception classes from airflow.sdk.exceptions (or from the provider compat shim).
  • Adjust custom validation code to expect ValueError for invalid sensor arguments if it previously caught AirflowException.

Support numeric multiplier values for retry_exponential_backoff parameter

The retry_exponential_backoff parameter now accepts numeric values to specify custom exponential backoff multipliers for task retries. Previously, this parameter only accepted boolean values (True or False), with True using a hardcoded multiplier of 2.0.

New behavior:

  • Numeric values (e.g., 2.0, 3.5) directly specify the exponential backoff multiplier
  • retry_exponential_backoff=2.0 doubles the delay between each retry attempt
  • retry_exponential_backoff=0 or False disables exponential backoff (uses fixed retry_delay)

Backwards compatibility:

Existing Dags using boolean values continue to work:

  • retry_exponential_backoff=True → converted to 2.0 (maintains original behavior)
  • retry_exponential_backoff=False → converted to 0.0 (no exponential backoff)

API changes:

The REST API schema for retry_exponential_backoff has changed from type: boolean to type: number. API clients must use numeric values (boolean values will be rejected).

Migration:

While boolean values in Python Dags are automatically converted for backwards compatibility, we recommend updating to explicit numeric values for clarity:

  • Change retry_exponential_backoff=True → retry_exponential_backoff=2.0
  • Change retry_exponential_backoff=False → retry_exponential_backoff=0

Move serialization/deserialization (serde) logic into Task SDK

Airflow now sources serde logic from airflow.sdk.serde instead of airflow.serialization.serde. Serializer modules have moved from airflow.serialization.serializers.* to airflow.sdk.serde.serializers.*. The old import paths still work but emit DeprecatedImportWarning to guide migration. The backward compatibility layer will be removed in Airflow 4.

What changed:

  • Serialization/deserialization code moved from airflow-core to task-sdk package
  • Serializer modules moved from airflow.serialization.serializers.* to airflow.sdk.serde.serializers.*
  • New serializers should be added to airflow.sdk.serde.serializers.* namespace

Code interface changes:

  • Import serializers from airflow.sdk.serde.serializers.* instead of airflow.serialization.serializers.*
  • Import serialization functions from airflow.sdk.serde instead of airflow.serialization.serde

Backward compatibility:

  • Existing serializers importing from airflow.serialization.serializers.* continue to work with deprecation warnings
  • All existing serializers (builtin, datetime, pandas, numpy, etc.) are available at the new location

Migration:

  • For existing custom serializers: Update imports to use airflow.sdk.serde.serializers.*
  • For new serializers: Add them to airflow.sdk.serde.serializers.* namespace (e.g., create task-sdk/src/airflow/sdk/serde/serializers/your_serializer.py)

On (experimental) class PriorityWeightStrategy, functions serialize() and deserialize() were never used anywhere, and have been removed. They should not be relied on in user code. (#59780)

Methods removed from TaskInstance

On class TaskInstance, functions run(), render_templates(), get_template_context(), and private members related to them have been removed. The class has been considered internal since 3.0, and should not be relied on in user code. (#59780, #59835)

  • FileLoadStat now has two additional nullable fields: bundle_path and bundle_name.

Backward compatibility:

Operators can now override the Dag-level render_template_as_native_obj setting, enabling fine-grained control over whether templates are rendered as native Python types or strings on a per-task basis. Set render_template_as_native_obj=True or False on any operator to override the Dag setting, or leave as None (default) to inherit from the Dag.

Add gunicorn support for API server with zero-downtime worker recycling

The API server now supports gunicorn as an alternative server with rolling worker restarts to prevent memory accumulation in long-running processes.

Key Benefits:

  • Rolling worker restarts: New workers spawn and pass health checks before old workers are killed, ensuring zero downtime during worker recycling.

  • Memory sharing: Gunicorn uses preload + fork, so workers share memory via copy-on-write. This significantly reduces total memory usage compared to uvicorn's multiprocess mode where each worker loads everything independently.

  • Correct FIFO signal handling: Gunicorn's SIGTTOU kills the oldest worker (FIFO), not the newest (LIFO), which is correct for rolling restarts.

Configuration:

.. code-block:: ini

[api]
# Use gunicorn instead of uvicorn
server_type = gunicorn

# Enable rolling worker restarts every 12 hours
worker_refresh_interval = 43200

# Restart workers one at a time
worker_refresh_batch_size = 1

Or via environment variables:

.. code-block:: bash

export AIRFLOW__API__SERVER_TYPE=gunicorn
export AIRFLOW__API__WORKER_REFRESH_INTERVAL=43200

Requirements:

Install the gunicorn extra: pip install 'apache-airflow-core[gunicorn]'

Note on uvicorn (default):

The default uvicorn mode does not support rolling worker restarts because:

  1. With workers=1, there is no master process to send signals to
  2. uvicorn's SIGTTOU kills the newest worker (LIFO), defeating rolling restart purposes
  3. Each uvicorn worker loads everything independently with no memory sharing

If you need worker recycling or memory-efficient multi-worker deployment, use gunicorn. (#60921)

Improved performance of rendered task instance fields cleanup for Dags with many mapped tasks (~42x faster)

The config max_num_rendered_ti_fields_per_task is renamed to num_dag_runs_to_retain_rendered_fields (old name still works with deprecation warning).

Retention is now based on the N most recent dag runs rather than N most recent task executions, which may result in fewer records retained for conditional/sparse tasks. (#60951)

AuthManager Backfill permissions are now handled by the requires_access_dag on the DagAccessEntity.Run

is_authorized_backfill of the BaseAuthManager interface has been removed. Core will no longer call this method and their provider counterpart implementation will be marked as deprecated. Permissions for backfill operations are now checked against the DagAccessEntity.Run permission using the existing requires_access_dag decorator. In other words, if a user has permission to run a Dag, they can perform backfill operations on it.

Please update your security policies to ensure that users who need to perform backfill operations have the appropriate DagAccessEntity.Run permissions. (Users having the Backfill permissions without having the DagRun ones will no longer be able to perform backfill operations without any update)
