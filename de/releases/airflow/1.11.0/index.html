Luftstrom-Helmdiagramm/1.11.0

Wesentliche Änderungen

Unterstützung der Namensanpassung für Helmdiagrammressourcen. Einige Ressourcen werden möglicherweise während des Upgrades umbenannt (#31066)

Dies ist ein neuer Opt-in-Schalter „useStandardNaming``, for backwards compatibility, to leverage the standard naming convention, which allows full use of ``fullnameOverride`` and ``nameOverride“ in allen Ressourcen. Die folgenden Ressourcen werden beim Upgrade auf 1.11.0 oder eine höhere Version standardmäßig in „useStandardNaming=false“ umbenannt.

  • ConfigMap {release}-airflow-config to {release}-config
  • Geheimnis „{release}-airflow-metadata`` to ``{release}-metadata“.
  • Geheimnis „{release}-airflow-result-backend`` to ``{release}-result-backend“.
  • Eingang „{release}-airflow-ingress`` to ``{release}-ingress“. Bei bestehenden Installationen werden alle Ihre Ressourcen mit einem neuen Namen neu erstellt und Helm löscht die vorherigen Ressourcen. Dadurch werden vorhandene PVCs für Protokolle, die von StatefulSet/Deployments verwendet werden, nicht gelöscht, sondern mit brandneuen PVCs neu erstellt. Wenn Sie den Protokollverlauf beibehalten möchten, müssen Sie die Daten dieser Volumes anschließend manuell auf die neuen Volumes kopieren Bereitstellung. Je nachdem, welches Speicher-Backend/welche Speicherklasse Sie verwenden, kann dieses Verfahren variieren. Wenn es Ihnen nichts ausmacht, anzufangen Bei neuen Protokollen/redis-Volumes können Sie einfach die alten PVCs löschen, die Namen sein werden, zum Beispiel:
kubectl delete pvc -n airflow logs-gta-triggerer-0
kubectl delete pvc -n airflow logs-gta-worker-0
kubectl delete pvc -n airflow redis-db-gta-redis-0

Wenn Sie „useStandardNaming`` or ``fullnameOverride“ nach dem Upgrade nicht ändern, können Sie wie gewohnt fortfahren und es werden keine unerwarteten Verhaltensweisen angezeigt.

airflow helm-chart/1.11.0

Highlights

  • Standardized resource naming (breaking behavior on upgrade) — #31066 adds an opt-in useStandardNaming switch to fully honor fullnameOverride/nameOverride, but the default (false) upgrade path itself renames core objects: {release}-airflow-config → {release}-config, -airflow-metadata → -metadata, -airflow-result-backend → -result-backend, and -airflow-ingress → -ingress. Helm deletes the old objects and recreates them under new names. Crucially, StatefulSet/Deployment log PVCs are not migrated — they're orphaned and replaced with fresh ones (e.g. logs-gta-triggerer-0, redis-db-gta-redis-0). To keep log history you must manually copy data into the new volumes; otherwise just delete the stale PVCs. If you leave useStandardNaming and fullnameOverride unchanged after upgrading, behavior is stable.

  • Bundled image/subchart bumps — Three defaults move in one release: Airflow 2.6.2 → 2.7.1 (#34186), git-sync 3.6.3 → 3.6.9 (#33748), and the bitnami/postgresql subchart 12.1.9 → 12.10.0 (#33747). Validate DAGs against 2.7.1 before rollout, and expect the PostgreSQL subchart jump to pull a different DB image — pin/verify it if your cluster standardizes on a specific PostgreSQL version.

  • KEDA autoscaling gets broader coverage — Triggerer gains KEDA scaling (#32302), workers can drive scaling from a custom query (#32308), and a new option allows a direct DB connection when PgBouncer is enabled (#32608). If you front PostgreSQL with PgBouncer, the direct-DB option lets KEDA query without going through the pooler — useful for accurate scaling metrics.

  • Expanded pod-level control surface — New knobs for hardened/production clusters: disable SA token mounts via automountServiceAccountToken (#32808), set runtimeClassName (#31868) and custom priority classes (#31615), set scheduler name in pod templates (#33843), inject container lifecycle hooks (#32349, #34677), and add startupProbe to scheduler/webserver (#33107). The lifecycle hooks and startup probe are especially relevant for slow-starting or sidecar-based deployments.

  • Upgrade-path correctness fixes — The DB migration job now runs airflow db migrate (#34178), aligning it with the newer migration flow. Also, KubeExecutor pod templates now honor workers.terminationGracePeriodSeconds (#33514), CeleryExecutor namespace is derived from the Airflow version (#32753), and the DAG processor liveness probe includes --local/--job-type args (#32426). These are quiet but important fixes for clean upgrades and graceful pod shutdown.

  • Kubernetes 1.23 support removed — #32899 drops K8s 1.23. Confirm your cluster is on 1.24+ before adopting this chart.

Significant Changes

Support naming customization on helm chart resources, some resources may be renamed during upgrade (#31066)

This is a new opt-in switch useStandardNaming, for backwards compatibility, to leverage the standard naming convention, which allows full use of fullnameOverride and nameOverride in all resources.

The following resources will be renamed using default of useStandardNaming=false when upgrading to 1.11.0 or a higher version.

  • ConfigMap {release}-airflow-config to {release}-config
  • Secret {release}-airflow-metadata to {release}-metadata
  • Secret {release}-airflow-result-backend to {release}-result-backend
  • Ingress {release}-airflow-ingress to {release}-ingress

For existing installations, all your resources will be recreated with a new name and Helm will delete the previous resources.

This won't delete existing PVCs for logs used by StatefulSet/Deployments, but it will recreate them with brand new PVCs. If you do want to preserve logs history you'll need to manually copy the data of these volumes into the new volumes after deployment. Depending on what storage backend/class you're using this procedure may vary. If you don't mind starting with fresh logs/redis volumes, you can just delete the old PVCs that will be names, for example:

kubectl delete pvc -n airflow logs-gta-triggerer-0
kubectl delete pvc -n airflow logs-gta-worker-0
kubectl delete pvc -n airflow redis-db-gta-redis-0

If you do not change useStandardNaming or fullnameOverride after upgrade, you can proceed as usual and no unexpected behaviours will be presented.
