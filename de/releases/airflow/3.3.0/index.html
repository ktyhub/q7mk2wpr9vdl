Luftstrom 3.3.0

Wesentliche Änderungen

Asset-Partitionierung (#64571, #65447, #66030, #66848, #67184, #67475, #67716, #68978)

Aufbauend auf der in 3.2.0 eingeführten Asset-Partitionierung erweitert Airflow 3.3.0 die Art und Weise, wie a Ein einzelnes Upstream-Asset-Ereignis verteilt sich auf partitionierte Downstream-Dag-Läufe. Neue Partitions-Mapper – RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + „SegmentWindow“ (kategoriales Rollup) – mit Zeitfenstern (Tag/Woche/Monat/Quartal/Jahr) zusammenstellen und a wait_policy (WaitForAll or MinimumCount(n)), um zu steuern, wann Partitionsläufe ausgelöst werden. Windows kann zeitlich vorwärts oder rückwärts aufgefächert werden, und die gesamte Auffächerung pro Upstream-Ereignis ist durch das Neue begrenzt „[scheduler] partition_mapper_max_downstream_keys“-Konfiguration (konfigurierbar pro Mapper). Luftstrom 3.3.0 fügt auch den Zeitplan „PartitionedAtRuntime“ hinzu, der es einem Dag ermöglicht, zu erklären, dass seine(n) Partitionsschlüssel(s) werden zu Beginn des Laufs zugewiesen und nicht von einem Upstream-Ereignis zugeordnet.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/authoring-and-scheduling/assets.

Aufgaben- und Asset-Statusspeicher (#65759, #66073, #66160, #66463, #66586, #66859, #67041, #67292, #67319)

Airflow 3.3.0 führt einen erstklassigen Zustandsspeicher für Aufgaben und Vermögenswerte ein (AIP-103). Aufgaben können bestehen bleiben beliebiger Schlüsselwertstatus, der über Wiederholungsversuche hinweg überlebt und über einen neuen „task_state_store“-Accessor ausgeführt wird, und Assets können ihren eigenen Status über „asset_state_store“ übertragen – beide sind über die Task SDK verfügbar. Zustand bleibt erhalten standardmäßig in der Metadatendatenbank oder in einem benutzerdefinierten Worker-seitigen Backend („[workers] state_store_backend``), unterstützt die Aufbewahrung pro Schlüssel mit regelmäßiger Speicherbereinigung und einer optionalen „clear_on_success“ und ist vollständig über den Core API und die Ausführung API verwaltbar.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/core-concepts/task-and-asset-state-store.

Pluggable Retry Policies (#65474)

Das Verhalten bei Aufgabenwiederholungen ist jetzt anpassbar (AIP-105). Zusätzlich zu einer festen „retries“-Anzahl ist dies möglich Fügen Sie eine benutzerdefinierte Wiederholungsrichtlinie hinzu, die entscheidet, ob und wann eine Aufgabe wiederholt wird, und ermöglicht so Strategien wie z B. einen erneuten Versuch nur bei bestimmten Ausnahmen oder einen Rückzug basierend auf benutzerdefinierter Logik.

Ausführliche Gebrauchsanweisungen finden Sie unter :ref:concepts:retry-policies.

Sprachaufgabe SDK (Java und Go) (#65958, #67161, #67635, #67699)

Airflow 3.3.0 fügt eine Koordinatorschicht (AIP-108) hinzu, die das Schreiben einzelner Aufgabenimplementierungen ermöglicht in Nicht-Python-Sprachen, während der Dag und seine Planung in Python bleiben. Eine Aufgabe wird im Dag deklariert mit „@task.stub(queue=...)“; Der Worker leitet es an einen konfigurierten Koordinator weiter („JavaCoordinator`` for JVM languages, ``ExecutableCoordinator“ für eigenständige native Binärdateien (z. B. Go), das die Aufgabe in einer Sprachlaufzeit ausführt und Variablen, Verbindungen und XComs zurückvermittelt durch die Ausführung API.

.. Warnung::

Die Koordinatorschicht und die Java/Go-SDKs sind in 3.3.0 experimentell und können sich in Zukunft ändern Versionen basierend auf Benutzer-Feedback.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/authoring-and-scheduling/language-sdks/index.

Dag-Bundle-Version zum Löschen, erneuten Ausführen und Auffüllen (#63884)

Die neue Einstellung „rerun_with_latest_version“ steuert, ob ein Dag-Lauf gelöscht, erneut ausgeführt oder aufgefüllt wird Verwendet die neueste Bundle-Version oder die Originalversion aus der ersten Ausführung. Der Standardwert wurde behoben nach Vorrang: ein expliziter Anforderungsparameter/CLI-Flag, dann die Dag-Ebene „rerun_with_latest_version“, dann [core] rerun_with_latest_version, and finally False for clear/rerun and True für Hinterfüllungen (Erhaltung des historischen Verhaltens). Airflow 2.x wurde immer mit dem neuesten Code erneut ausgeführt. 3.x Einführung der Bundle-Versionierung, die standardmäßig auf die Originalversion zurückgreift, und diese Einstellung gibt Benutzern die Kontrolle.

Ausführliche Informationen finden Sie unter :doc:/administration-and-deployment/dag-bundles.

Beispiel-Dags des Anbieters als dedizierte Bundles (#66161)

Beispieldags, die von Anbieterdistributionen geliefert werden, werden jetzt über „ProvidersManager“ und erkannt als eigene Dag-Bundles registriert – eines pro Anbieter, benannt „apache-airflow-providers-<distribution>-example-dags`` (or ``<distribution>-example-dags“ für Drittanbieter). Die Option „[core] load_examples“ bestimmt weiterhin, ob sie registriert sind. REST API clients, die „bundle_name`` by ``"dags-folder"“ nach vom Anbieter bereitgestellten Beispieldags gefiltert haben muss auf die neuen Paketnamen pro Anbieter aktualisiert werden; Dag-Kennungen bleiben unverändert.

Auflösung der Remote-Protokollierung von „airflow.logging_config“ entkoppelt (#67056)

Die Auflösung des Remote-Task-Log-Handlers gehört jetzt dem gemeinsam genutzten „airflow_shared.logging.factory“. Modul und wendet eine einzelne, klar definierte Priorität an:

  1. ein benutzerdefiniertes „[logging] logging_config_class`` exporting ``REMOTE_TASK_LOG“ / „DEFAULT_REMOTE_CONN_ID“ (vorhandene benutzerdefinierte Konfigurationen funktionieren weiterhin);
  2. „ProvidersManager`` scheme dispatch — the scheme of ``[logging] remote_base_log_folder“ wählt a Anbieter „RemoteLogIO`` class, instantiated via a no-argument ``from_config()“ Klassenmethode;
  3. ein vorübergehender Legacy-Fallback mit der Lesung „airflow_local_settings.py“ (muss in Airflow 4.0 entfernt werden).

„airflow.logging_config.load_logging_config`` is deprecated (it now emits ``DeprecationWarning“ und Delegierte an neue private Helfer) und „configure_logging“ löst die Fernbedienung nicht mehr eifrig auf Handler – Die Auflösung ist bei der ersten Verwendung träge. Anbieter, die einen „remote-logging:“-Block registriert haben, dies aber tun „from_config“ nicht implementieren, werden mit einer Warnung übersprungen und fallen auf den Legacy-Pfad.

Migration: Ersetzen Sie direkte Aufrufe von „airflow.logging_config.load_logging_config()“ durch die neuen Helfer und lassen Sie die Remote-Log-Handler-Klassen des Anbieters ein „from_config“ ohne Argumente implementieren Klassenmethode, die „airflow.providers.common.compat.sdk.conf“ lautet.

OpenTelemetry Timer-Metriken verwenden jetzt Histogramm (#64207)

OpenTelemetry-Timer und Timing-Metriken werden jetzt als Histogramme statt als Messgeräte aufgezeichnet, wodurch die Daten erhalten bleiben Anzahl, Summe und Bucket-Verteilung über die Aufzeichnungen hinweg.

Dag-Verarbeitungsmetrik „vor Sekunden“ ist jetzt getaggt (#62487)

„dag_processing.last_run.seconds_ago.{dag_file}“ ist jetzt eine alte Metrik. Das Neue „dag_processing.last_run.seconds_ago`` is emitted with ``file_path``, ``bundle_name“ und „file_name`` tags (``file_path`` + ``bundle_name“ identifiziert die Dag-Datei eindeutig. Die Legacy-Metrik wird weiterhin standardmäßig ausgegeben und kann über „[metrics] legacy_names_on“ deaktiviert werden.

Neue Fristenseite unter Durchsuchen (#67586)

Im Menü „Durchsuchen“ ist eine neue Seite „Fristen“ verfügbar, auf die alle Rollen zugreifen können, die bereits über eine solche Funktion verfügen „can_read`` and ``menu_access“ auf Dag Runs.

airflow 3.3.0

Highlights

  • Asset partitioning gains rollups, fan-out, and partial-window waits — RollupMapper, FanOutMapper, and FixedKeyMapper with SegmentWindow let one upstream event aggregate into or expand across partitioned downstream runs. Time windows compose with WaitForAll or MinimumCount(n), while PartitionedAtRuntime supports keys assigned only when a run starts. Bound scheduler expansion with [scheduler] partition_mapper_max_downstream_keys or per-mapper max_fan_out (#64571, #66030, #66848, #67184, #67475).

  • Task runtime gains durable state and programmable retries — task_state_store and asset_state_store provide Task SDK key-value state that survives retries and runs, with metadata-database or custom worker-side storage, retention, garbage collection, and optional clear_on_success. Separately, pluggable retry policies let tasks decide whether and when to retry based on exceptions or custom backoff logic instead of relying only on a fixed retry count (#65759, #66463, #66586, #65474).

  • Python DAGs can delegate execution to Java and Go—experimentally — Declare work with @task.stub(queue=...), then route it through JavaCoordinator or ExecutableCoordinator; Variables, Connections, and XComs are proxied through the Execution API. This keeps orchestration in Python while widening task implementation choices, but the Coordinator and SDK APIs may change in future releases (#65958, #67161).

  • Rerun bundle selection becomes explicitly controllable — rerun_with_latest_version resolves from the request or CLI flag, then the Dag setting, then [core], with defaults of False for clear/rerun and True for backfills. Set it explicitly where reproducibility matters, especially because TriggerDagRunOperator reruns also follow this setting (#63884, #67273).

  • Metrics consumers need query and dashboard updates — OpenTelemetry timers now emit Histograms rather than Gauges, changing how rates, averages, and alerts must be calculated (#64207). The per-Dag dag_processing.last_run.seconds_ago.{dag_file} metric becomes legacy; migrate to dag_processing.last_run.seconds_ago with file_path, bundle_name, and file_name tags. The legacy name remains enabled by default and can be disabled with [metrics] legacy_names_on (#62487).

  • Upgrade integrations for renamed bundles, asset ACLs, and logging hooks — Provider example Dags move from the dags-folder bundle to per-provider bundles such as apache-airflow-providers-<distribution>-example-dags, so REST clients filtering by bundle_name must change while Dag IDs remain stable (#66161). Asset.allow_producer_teams is replaced by access_control (#66954), and remote-log providers should implement a no-argument from_config(); direct airflow.logging_config.load_logging_config() callers must migrate, while the legacy airflow_local_settings.py fallback is scheduled for removal in Airflow 4.0 (#67056).

Significant Changes

Asset Partitioning (#64571, #65447, #66030, #66848, #67184, #67475, #67716, #68978)

Building on the asset partitioning introduced in 3.2.0, Airflow 3.3.0 substantially expands how a single upstream asset event fans out to partitioned downstream Dag runs. New partition mappers — RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + SegmentWindow (categorical rollup) — compose with time windows (day/week/month/quarter/year) and a wait_policy (WaitForAll or MinimumCount(n)) to control when partitioned runs fire. Windows can fan out forward or backward in time, and total fan-out per upstream event is bounded by the new [scheduler] partition_mapper_max_downstream_keys config (configurable per mapper). Airflow 3.3.0 also adds the PartitionedAtRuntime timetable, which lets a Dag declare that its partition key(s) are assigned when the run starts rather than mapped from an upstream event.

For detailed usage instructions, see :doc:/authoring-and-scheduling/assets.

Task and Asset State Store (#65759, #66073, #66160, #66463, #66586, #66859, #67041, #67292, #67319)

Airflow 3.3.0 introduces a first-class state store for tasks and assets (AIP-103). Tasks can persist arbitrary key-value state that survives across retries and runs via a new task_state_store accessor, and assets can carry their own state via asset_state_store — both available from the Task SDK. State is kept in the metadata database by default, or in a custom worker-side backend ([workers] state_store_backend), supports per-key retention with periodic garbage collection and an optional clear_on_success, and is fully manageable through the Core API and Execution API.

For detailed usage instructions, see :doc:/core-concepts/task-and-asset-state-store.

Pluggable Retry Policies (#65474)

Task retry behaviour is now pluggable (AIP-105). In addition to a fixed retries count, you can attach a custom retry policy that decides whether and when a task is retried, enabling strategies such as retrying only on specific exceptions or backing off based on custom logic.

For detailed usage instructions, see :ref:concepts:retry-policies.

Language Task SDK (Java and Go) (#65958, #67161, #67635, #67699)

Airflow 3.3.0 adds a Coordinator layer (AIP-108) that lets individual task implementations be written in non-Python languages while the Dag and its scheduling stay in Python. A task is declared in the Dag with @task.stub(queue=...); the worker routes it to a configured coordinator (JavaCoordinator for JVM languages, ExecutableCoordinator for self-contained native binaries such as Go) that runs the task in a language runtime and proxies Variables, Connections, and XComs back through the Execution API.

.. warning::

The Coordinator layer and the Java/Go SDKs are experimental in 3.3.0 and may change in future versions based on user feedback.

For detailed usage instructions, see :doc:/authoring-and-scheduling/language-sdks/index.

Dag bundle version on clear, rerun, and backfill (#63884)

The new rerun_with_latest_version setting controls whether a cleared, rerun, or backfilled Dag run uses the latest bundle version or the original version from the initial run. The default is resolved by precedence: an explicit request parameter/CLI flag, then the Dag-level rerun_with_latest_version, then [core] rerun_with_latest_version, and finally False for clear/rerun and True for backfills (preserving historical behaviour). Airflow 2.x always reran with the latest code; 3.x introduced bundle versioning defaulting to the original version, and this setting gives users control.

See :doc:/administration-and-deployment/dag-bundles for full details.

Provider example Dags as dedicated bundles (#66161)

Example Dags shipped by provider distributions are now discovered via ProvidersManager and registered as their own Dag bundles — one per provider, named apache-airflow-providers-<distribution>-example-dags (or <distribution>-example-dags for third-party providers). The [core] load_examples option still gates whether they are registered. REST API clients that filtered bundle_name by "dags-folder" for provider-shipped example Dags must update to the new per-provider bundle names; Dag identifiers are unchanged.

Remote logging resolution decoupled from airflow.logging_config (#67056)

Remote task log handler resolution is now owned by the shared airflow_shared.logging.factory module and applies a single, well-defined precedence:

  1. a user-defined [logging] logging_config_class exporting REMOTE_TASK_LOG / DEFAULT_REMOTE_CONN_ID (existing custom configs keep working);
  2. ProvidersManager scheme dispatch — the scheme of [logging] remote_base_log_folder selects a provider RemoteLogIO class, instantiated via a no-argument from_config() classmethod;
  3. a transitional legacy fallback reading airflow_local_settings.py (to be removed in Airflow 4.0).

airflow.logging_config.load_logging_config is deprecated (it now emits DeprecationWarning and delegates to new private helpers), and configure_logging no longer eagerly resolves the remote handler — resolution is lazy on first use. Providers that registered a remote-logging: block but do not implement from_config are skipped with a warning and fall through to the legacy path.

Migration: replace direct calls to airflow.logging_config.load_logging_config() with the new helpers, and have provider remote-log handler classes implement a no-argument from_config classmethod that reads airflow.providers.common.compat.sdk.conf.

OpenTelemetry timer metrics now use Histogram (#64207)

OpenTelemetry timer and timing metrics are now recorded as Histograms instead of Gauges, preserving count, sum, and bucket distribution across recordings.

Dag-processing "seconds ago" metric is now tagged (#62487)

dag_processing.last_run.seconds_ago.{dag_file} is now a legacy metric. The new dag_processing.last_run.seconds_ago is emitted with file_path, bundle_name and file_name tags (file_path + bundle_name uniquely identify the Dag file). The legacy metric is still emitted by default and can be disabled via [metrics] legacy_names_on.

New Deadlines page under Browse (#67586)

A new Deadlines page is available under the Browse menu, accessible to any role that already has can_read and menu_access on Dag Runs.
