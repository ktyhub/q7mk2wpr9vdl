Wesentliche Änderungen

Backfill-Endpunkte geben nicht mehr offen, welche Backfill-IDs in allen Dags vorhanden sind

Die vier Routen, die einen Backfill in ihrem Pfad benennen – „GET /backfills/{backfill_id}“. und die Routen „pause``, ``unpause`` and ``cancel“ – lösten den von ihnen autorisierten Dag auf gegen aus dem auf der Anfrage bereitgestellten „dag_id“, wenn die ID des Pfads mit keiner Zeile übereinstimmt. Eine unbekannte ID und ein Backfill auf einem Dag, den der Anrufer nicht sehen kann, haben daher anders geantwortet, Dadurch werden Backfill-IDs über Dags hinweg aufgezählt.

Der im Pfad genannte Backfill ist jetzt das einzige, für das diese Routen eine Autorisierung zulassen.

Verhaltensänderungen:

– Das Anfordern eines Backfills für einen Dag, den der Anrufer nicht lesen kann, gibt jetzt „404“ zurück (Backfill not found) – die gleiche Antwort, die eine unbekannte ID erhält – anstelle der „403`` returned before. A caller who can read the Dag still gets ``403“ für einen Schreibvorgang das dürfen sie nicht machen. – Ein „backfill_id`` in the path is never authorized against a ``dag_id“ im Anfragetext oder Abfragezeichenfolge. „GET /backfills``, ``POST /backfills`` and ``POST /backfills/dry_run“. Nennen Sie keinen Backfill in ihrem Pfad und autorisieren Sie die Anfrage weiterhin.

  • Alle vier Routen antworten jetzt auf eine unbekannte ID mit derselben Angabe, „Backfill not found“. Die zuvor beantworteten Routen „pause``, ``unpause`` and ``cancel“. „Could not find backfill with id {backfill_id}``. Clients matching on ``detail“. muss aktualisiert werden. (#71113)

Eine explizite Anmeldeinformation hat jetzt Vorrang vor dem Sitzungscookie

„get_user()“ ist so geschrieben, dass ein explizites Bearer-Token bevorzugt wird, dann OAuth2, dann das Sitzungscookie, aber dieser Vorrang war nicht erreichbar, wenn ein Cookie vorhanden war. „JWTRefreshMiddleware“ läuft Zunächst wird ein Benutzer allein aus dem Cookie „_token“ aufgelöst und darauf gestempelt „request.state``, and ``get_user()“ hat den zwischengespeicherten Benutzer zurückgegeben, bevor er sich einen der beiden angesehen hat explizite Berechtigung. Die effektive Reihenfolge auf jeder Core-API-Route war Cookie over Bearer.

Eine Anfrage, die sowohl ein Sitzungscookie als auch eine explizite Anmeldeinformation enthält, wird daher ausgeführt. und wurde im Audit-Protokoll als Prinzipal des Cookies und nicht als Identität des Cookies aufgezeichnet client vorgestellt. Der zwischengespeicherte Benutzer wird jetzt nur dann berücksichtigt, wenn die Anfrage „Nein“ enthält explizite Berechtigung.

Verhaltensänderungen:

Eine Anfrage, die beide einen „_token`` cookie and an ``Authorization: Bearer“-Header trägt

wird jetzt als Prinzipal des Inhaber-Tokens aufgelöst, wo es zuvor als aufgelöst wurde
Kekse. Gleiches gilt für ein Cookie in Kombination mit einem OAuth2-Token.

Ein ungültiger oder abgelaufener expliziter Berechtigungsnachweis wird jetzt sogar mit „401``/``403“ abgelehnt

wenn ein gültiges „`_token`“-Cookie damit einhergeht. Zuvor übernahm der Cookie stillschweigend
und die Anfrage war als Cookie-Prinzipal erfolgreich; Der Ausfall wird nun laut.

Anfragen mit einem einzelnen Berechtigungsnachweis sind nicht betroffen. Nur-Cookie-Browsersitzungen bleiben erhalten

Das Token-Aktualisierungsverhalten von „`JWTRefreshMiddleware`“ bleibt unverändert.

Clients, die sich auf den Cookie-Gewinn verlassen haben – zum Beispiel ein browserbasiertes Tool, das a gesendet hat

Inhabertoken des Dienstkontos, während ein Benutzersitzungscookie vorhanden war, und erwartete das
Die anzuwendende Identität des Benutzers fungiert nun als Prinzipal des Inhaber-Tokens. Entfernen Sie die

airflow 3.3.2

Highlights

  • Backfill authorization closes an ID-enumeration leak (#71113) — The four backfill routes (GET plus pause/unpause/cancel) now authorize only against the backfill named in the path, never against a dag_id from the body or query string. Hidden Dags and unknown IDs both return the same 404 "Backfill not found" (previously a distinguishable 403), so enumerating backfill IDs across Dags no longer works. Clients matching on the old detail string Could not find backfill with id {backfill_id} must be updated; GET/POST /backfills and dry_run are unchanged.
  • Explicit credentials now outrank the session cookie (#72225) — get_user()'s documented bearer → OAuth2 → cookie precedence was unreachable because JWTRefreshMiddleware cached the cookie principal first, so mixed requests ran and were audited as the cookie user. Now a request carrying both _token and a Bearer/OAuth2 token resolves as the explicit principal, and an invalid or expired explicit credential is rejected with 401/403 instead of silently falling back to the cookie. Cookie-only browser sessions keep token refresh unchanged. If a tool relied on the cookie winning, drop the header or the cookie to choose an identity explicitly.
  • Broader auth hardening across the API surface — Partitioned dag-run listings no longer disclose Dag existence (#72660), /assets/events is scoped to Dags the caller can read (#71785), testing an existing connection requires read access (#71428), deleting queued asset events requires Dag edit permission (#71828), and logout revokes every presented credential, not just the session cookie (#72933). Plugin authors should note the new docs stating that plugin FastAPI apps are not authenticated by Airflow (#72932) with an authorization example added (#72942), plus clarified timing for the is_authorized_hitl_task hook (#72807).
  • Migration and metadata fixes to validate on upgrade — The bytea→JSONB XCom migration no longer corrupts values that already parse as JSON (#72886), db migrate under PyMySQL handles schema migrations that drop unique constraints (#72613), and db clean now actually purges the callback table (#72899). Variable handling saw several corrections: non-string JSON values (#71526, #72878), write conflicts checked against the wrong team (#72125), Variable.set rewriting team_name (#71904), and export/import silently corrupting values (#71791). With large XCom histories or custom Variables, verify data after migrating.
  • Cleaner API error semantics and Task SDK stability — Endpoints now return meaningful 4xx instead of 500s: task starts against a missing Dag run (#72900), unknown task instances in state-store routes (#71860), and invalid clearTaskInstances bodies (422, #71559); the unreachable 404 on create Variable was removed (#72190). Execution API routes stay compatible with older Task SDK clients (#71438), partition_key is gated behind the 2026-06-30 Execution API version (#72827), and Task SDK IPC short reads no longer crash subprocesses or hang the supervisor (#71609).
  • Performance wins and new SDK surface — DB/memory pressure drops via N+1 fixes in bulk Variable/Pool updates (#72160) and previous-task-instance lookups (#72944), LIMIT 1 bounds on single-row lookups (#72842, #72702), and a bounded scheduler deserialized-Dag cache (#71821). New capabilities include async asset store accessors for async tasks and watchers (#72851), deadline references exposed through the SDK public interface (#71208, #72244, #72738), and create_async_metadata_engine docs (#72804).

Significant Changes

Backfill endpoints no longer disclose which backfill ids exist across Dags

The four routes that name a backfill in their path -- GET /backfills/{backfill_id} and the pause, unpause and cancel routes -- resolved the Dag they authorize against from the dag_id supplied on the request whenever the path's id matched no row. An unknown id and a backfill on a Dag the caller cannot see therefore answered differently, which enumerates backfill ids across Dags.

The backfill named in the path is now the only thing those routes authorize against.

Behaviour changes:

  • Requesting a backfill on a Dag the caller cannot read now returns 404 (Backfill not found) -- the same response an unknown id gets -- instead of the 403 returned before. A caller who can read the Dag still gets 403 for a write they are not allowed to make.
  • A backfill_id in the path is never authorized against a dag_id in the request body or query string. GET /backfills, POST /backfills and POST /backfills/dry_run name no backfill in their path and keep authorizing off the request.
  • All four routes now answer an unknown id with the same detail, Backfill not found. The pause, unpause and cancel routes previously answered Could not find backfill with id {backfill_id}. Clients matching on detail must be updated. (#71113)

An explicit credential now takes precedence over the session cookie

get_user() is written to prefer an explicit bearer token, then OAuth2, then the session cookie, but that precedence was unreachable whenever a cookie was present. JWTRefreshMiddleware runs first, resolves a user from the _token cookie alone and stamps it on request.state, and get_user() returned that cached user before looking at either explicit credential. The effective order on every core-API route was cookie over bearer.

A request carrying both a session cookie and an explicit credential therefore executed, and was recorded in the audit log, as the cookie's principal rather than the identity the client presented. The cached user is now honoured only when the request carries no explicit credential.

Behaviour changes:

A request carrying both a _token cookie and an Authorization: Bearer header

is now resolved as the bearer token's principal, where it was previously resolved as the
cookie's. The same applies to a cookie combined with an OAuth2 token.

An invalid or expired explicit credential is now rejected with 401/403 even

when a valid ``_token`` cookie accompanies it. Previously the cookie silently took over
and the request succeeded as the cookie's principal; the failure is now loud.

Requests carrying a single credential are unaffected. Cookie-only browser sessions keep

the token-refresh behaviour of ``JWTRefreshMiddleware`` unchanged.

Clients that relied on the cookie winning -- for example a browser-based tool that sent a

service account's bearer token while a user session cookie was present, and expected the
user's identity to apply -- will now act as the bearer token's principal. Remove the
header, or the cookie, to select the intended identity explicitly. (#72225)
