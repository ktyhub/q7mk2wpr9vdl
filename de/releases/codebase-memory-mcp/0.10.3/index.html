codebase-memory-mcp v0.10.3

codebase-memory-mcp v0.10.3

Eine Veröffentlichung, die nur Fixes enthält, und das meiste davon kam als fertige Arbeit von der Community an: Hier sind sechs beigesteuerte Pull-Requests enthalten, zusammen mit Reparaturen für zwei Regressionen, die wir selbst in v0.10.2 versendet haben.

Zwei Dinge, die Sie wissen sollten, bevor Sie ein Upgrade durchführen. Wenn Sie mehr als ein MCP client für dasselbe Projekt ausführen, schließt diese Version einen Fehler, der einen fehlerfreien Index stillschweigend zerstören könnte – beginnen Sie mit dem ersten Abschnitt. Und wenn die Installation oder Aktualisierung bei Ihnen fehlgeschlagen ist, werden hier drei verschiedene Ursachen behoben: eine Berechtigungsregel, die normale Home-Verzeichnisse ablehnte, eine Fehlermeldung, die den völlig falschen Grund meldete, und Codex, der Ihr Cache-Verzeichnis verlor. Einige davon scheiterten stillschweigend oder gaben dem Falschen die Schuld, weshalb sie mehrere Veröffentlichungen überlebten.

Gleichzeitige Instanzen isolieren ihre Datenbanken nicht mehr gegenseitig

Der schlimmste Fehler in dieser Version, behoben von @LynxBay. Wenn zwei cbm-Instanzen am selben Projekt teilnahmen – zwei Editoren, ein Editor plus ein CLI-Aufruf, ein Daemon und eine Streusitzung –, konnte der Verlierer des Lock Race zu dem Schluss kommen, dass die Datenbank beschädigt war, und sie unter Quarantäne stellen: umbenannt, von Grund auf neu erstellt, Stunden der Indizierung waren weg. Die Datenbank war fehlerfrei; Die Integritätsprüfung konnte einfach nicht zwischen „beschädigt“ und „beschäftigt“ unterscheiden (#1206).

Die gleiche Prüfung wies auch den gegenteiligen blinden Fleck auf: Eine Datenbank mit wirklich zerrissenen Seiten wurde bestanden, solange die Buchhaltung auf oberster Ebene korrekt aussah, sodass echte Schäden erst dann bemerkt wurden, wenn sich die Abfragen schlecht verhielten (#1037).

Integrity fällt nun ein dreiseitiges Urteil. Nur bestätigte Korruptionsquarantänen; ein Lock Race sagt „Projekt ist beschäftigt; nach Indizierung erneut versuchen“ und lässt die Daten in Ruhe; und ein tiefer quick_check fängt Schäden auf Seitenebene ein, die der flachen Sonde entgangen sind. Beide Richtungen führen Regressionstests durch.

Graphdeterminismus, zweimal

Zwei Beiträge von @Studnicky schließen zwei seit langem bestehende Ursachen für Run-to-Run-Drift – das Verhalten „gleiches Repo, leicht unterschiedliche Kantenanzahl“, das bei unseren bekannten Problemen seit dem 0.9.1 RC beobachtet wurde:

  • Wenn dieselbe logische Kante zweimal mit unterschiedlichen Attributen erzeugt wird (z. B. ein LSP-aufgelöster Aufruf und eine Textübereinstimmung), war der Überlebende derjenige, der zuletzt eintraf – eine Funktion der Thread-Planung. Bei der Zusammenführung handelt es sich nun um eine Gesamtreihenfolge: höheres Vertrauen gewinnt, Gleichstände lösen sich deterministisch auf und das Ergebnis ist konstruktionsbedingt unabhängig von der Ankunftsreihenfolge.
  • KONFIGURIERT, dass die Kandidatensammlung nichts sortiert hat, bevor die Obergrenze angewendet wurde. Welche Kandidaten überlebten, hing also von der Zusammenführungsreihenfolge der Arbeiter ab. Kandidaten werden jetzt zuerst nach einem reinen Inhaltsschlüssel sortiert – insbesondere nicht nach der Knoten-ID, die stabil aussieht, aber selbst in der Zusammenführungsreihenfolge ausgegeben wird.

Windows: Daemon-Dateien mit leerer ACL erstellt

@Kiborgik hat ein subtiles Problem diagnostiziert und behoben (#1351): Das private Verzeichnis des Daemons kombinierte eine geschützte DACL mit einem nicht vererbbaren ACE, was unter Windows bedeutet, dass Kinder nichts erben – jede darin erstellte Datei wurde mit einer leeren ACL geboren und war selbst für ihren Besitzer nicht lesbar. Verzeichnisse verfügen jetzt über ein ordnungsgemäß vererbbares ACE nur für Besitzer, sodass die strenge Sicherheitslage beibehalten wird und die Dateien tatsächlich funktionieren. Ein begleitender Fix desselben Mitwirkenden schloss eine Falle, bei der eine Maschine mit dem Namen ihres Benutzers einem leeren Prinzipal Berechtigungen erteilte; Beim Testen auf einem nicht in die Domäne eingebundenen Computer ist die Spiegelbildfalle aufgetreten, sodass unser Build-Tool das Konto jetzt anhand der SID identifiziert und die Namensauflösung ganz einstellt.

Reparaturen für zwei v0.10.2-Regressionen

Beide meldeten sich innerhalb weniger Stunden – vielen Dank für das schnelle Signal.

  • update --ui funktioniert nicht mehr (#1544, @ehendrix23). v0.10.2 entfernte die veraltete Benutzeroberfläche/Standardauswahl und die Flags, die sie steuerten, sodass ein Befehl, der in Skripten und im Muskelspeicher gespeichert war, zu einem schwerwiegenden Fehler wurde. Beide Flags werden wieder akzeptiert – sie bewirken nichts, sagen Sie es einmal, und wirklich unbekannte Flags schlagen immer noch fehl.
  • Die generierte Pi-Erweiterung hat Pi komplett kaputt gemacht (#1550, @musichen). Pi lädt eine Erweiterung, indem es ihren Standardexport aufruft; Unsere hat stattdessen eine benannte Funktion exportiert, und eine Pi-Erweiterung, die nicht geladen werden kann, nimmt jeden pi-Befehl mit sich, einschließlich pi doctor. Die Erweiterung exportiert jetzt standardmäßig ihre Factory. Unabhängig davon auch von @musichen und @henri-edh behoben, deren schärfere Beschreibung von Pis Loader der Kommentar jetzt in unserer Quelle ist.

Strukturierte Ausgabe verhindert, dass Beweise verloren gehen

trace_path(include_evidence: true) versprach Per-Hop-Spalten strategy und confidence und lieferte sie – nur im Baumformat. Mit format: "json" verschwanden beide Felder stillschweigend, was genau die Aufrufer traf, die sie am wahrscheinlichsten haben wollten: diejenigen, die strukturierte Ausgaben programmgesteuert konsumieren (#1542, @asemraza). Der JSON-Pfad trägt jetzt beide Felder mit derselben Semantik, wobei Nullen dort stehen, wo das Baumformat - ausgibt.

Unterprozess-Spawns überleben eine ausgelastete Maschine

Bei der Suche nach einem CI-Flake wurde eine echte Robustheitslücke aufgedeckt: Wenn der Kernel das Spawnen eines Prozesses mit „Erneut versuchen“ ablehnt – eine vorübergehend volle Prozesstabelle auf einer geladenen Maschine – behandelte cbm dies als dauerhaften Fehler. Ein Git-Probe- oder LSP-Server würde den Start aus einem für den Benutzer unsichtbaren Grund verweigern. Vorübergehende Spawn-Fehler werden jetzt kurz wiederholt. Echte Fehler (fehlende Binärdateien, Berechtigungen) schlagen bei unveränderter Semantik immer noch sofort fehl.

Installation und Aktivierung: Auf die Weigerung konnte niemand reagieren

Follow-up zu #1537 (@listepo), und es stellte sich heraus, dass es sich um zwei übereinander gestapelte Fehler handelte.

Der Daemon verweigerte die Ausführung, wenn irgendein Vorfahre seines Cache-Verzeichnisses gruppenbeschreibbar war – die gleiche Regel, die wir auf der Seite des Installationsprogramms in v0.10.2 entfernt haben, in der Geschwisterüberprüfung, die diese Entscheidung abdeckt, die jedoch nie geändert wurde. Ein gruppenbeschreibbarer ~ oder ~/.cache ist normal (WSL2 wird mit 0775 ausgeliefert, ebenso mehrere Distributionsgerüste und jede Maschine mit einer gemeinsam genutzten Primärgruppe), sodass der Daemon für diese Benutzer dauerhaft unbrauchbar war, ohne dass etwas geschlossen werden musste und nichts durch einen Neustart behoben werden konnte. Von der Welt beschreibbare Vorfahren werden immer noch abgelehnt – jeder lokale Benutzer könnte eine Pfadkomponente austauschen – und das private Verzeichnis selbst ist immer noch auf den Besitzer beschränkt, was die Zulassung des Vorfahren sicher macht. Darunter erfand die Fehlermeldung ihre eigenen Beweise: Der Ablehnungspfad setzte keinen Fehlercode, sodass die Berichterstattung darauf zurückfiel, alles auszudrucken, was errno gerade enthielt, und dem Reporter ENOENT zur Genehmigungsentscheidung übergab. Sie machten sich auf die Suche nach einer fehlenden Akte, die die ganze Zeit dort gewesen war. Die Nachricht nennt nun das Verzeichnis und die Regel, die es abgelehnt hat.

Auch in diesem Bereich: Der Aktivierungswächter meldete jede Ablehnung als „aktive CBM-Sitzungen konnten nicht gestoppt werden“, auch Fehler, bei denen überhaupt nichts läuft. Das sind jetzt separate Meldungen, die zweite sagt deutlich, dass nichts geschlossen werden muss, und keines der beiden Lösungen geht davon aus, dass sich eine codebase-memory-mcp-Binärdatei noch auf PATH befindet – ein Hinweis, der genau in dem Moment, in dem er gedruckt wurde, direkt nach uninstall, unbrauchbar war.

Auch behoben

  • Codex sah keine CBM-Tools, als CBM_CACHE_DIR eingestellt war (#1562, @anton-matosov). Codex übergibt nur explizit aufgelistete Variablen an einen MCP-Unterprozess, sodass der von ihm erstellte Server den Standard-Cache liest, während der Daemon den konfigurierten verwendet. Sie waren anderer Meinung und die Verbindung wurde während der Initialisierung geschlossen. Die generierte Konfiguration leitet nun die Variable weiter.
  • Die installierte Skilldatei konnte in strengen YAML-Readern nicht geladen werden (#1554, @xezzon). Sein description enthielt Triggers on: ohne Anführungszeichen, und ein Doppelpunkt in einem nicht in Anführungszeichen gesetzten YAML-Skalar bedeutet „verschachtelte Zuordnung“ – daher lehnten Parser das gesamte Dokument ab und der Skill wurde stillschweigend nie geladen.
  • search_code gab ein negatives limit als Ergebnisanzahl zurück (#1511, behoben durch @lukiod), was einem Agenten als Antwort und nicht als abgelehntes Argument vorgelesen wird.
  • ~~OpenCode-Installationen gingen in die falsche Datei (@iandol).~~ Korrektur: Dies wurde hier fälschlicherweise aufgeführt. Der Fix wurde einige Stunden nachdem das v0.10.3-Tag entfernt wurde, zusammengeführt, daher ist er in dieser Version nicht – er wird in v0.10.4 ausgeliefert. Wenn Ihre OpenCode-Konfiguration eine .jsonc-Datei ist, hat ein Upgrade auf v0.10.3 nicht geholfen, und wir entschuldigen uns für die verschwendete Zeit. – Release-Archive werden vor der Extraktion validiert (#1510, @cyphercodes): ein exakter Membersatz, wobei symbolisch verknüpfte Member komplett abgelehnt werden.

Upgrade

  • Binärinstallationen: unten herunterladen oder install.sh / install.ps1 erneut ausführen – das erneute Ausführen des Installationsprogramms ist das Update.
  • npm / PyPI: Aktualisieren Sie wie gewohnt über Ihren Paketmanager.
  • Keine Index-, Cache- oder Konfigurationsmigration.

codebase-memory-mcp v0.10.3

A fixes-only release, and most of it arrived as finished work from the community: six contributed pull requests are in here, alongside repairs for two regressions we shipped ourselves in v0.10.2.

Two things worth knowing before you upgrade. If you run more than one MCP client against the same project, this release closes a bug that could silently destroy a healthy index — start with the first section. And if installing or updating has been failing for you, three separate causes are fixed here: a permission rule that refused ordinary home directories, an error message that reported the wrong reason entirely, and Codex losing your cache directory. Several of those failed silently or blamed the wrong thing, which is why they survived multiple releases.

Concurrent instances no longer quarantine each other's databases

The worst bug in this release, fixed by @LynxBay. When two cbm instances raced on the same project — two editors, an editor plus a CLI call, a daemon and a stray session — the loser of the lock race could conclude the database was corrupt and quarantine it: renamed away, rebuilt from scratch, hours of indexing gone. The database was healthy; the integrity check just couldn't tell "damaged" from "busy" (#1206).

The same check had the opposite blind spot too: a database with genuinely torn pages passed as long as its top-level bookkeeping looked right, so real damage went unnoticed until queries misbehaved (#1037).

Integrity now returns a three-way verdict. Only confirmed corruption quarantines; a lock race says "project is busy; retry after indexing" and leaves the data alone; and a deep quick_check catches page-level damage the shallow probe missed. Both directions carry regression tests.

Graph determinism, twice

Two contributions from @Studnicky close two long-standing sources of run-to-run drift — the "same repo, slightly different edge counts" behavior tracked in our known issues since the 0.9.1 RC:

  • When the same logical edge is produced twice with different attributes (an LSP-resolved call and a textual match, say), the survivor was whichever arrived last — a function of thread scheduling. The merge is now a total order: higher confidence wins, ties break deterministically, and the outcome is independent of arrival order by construction.
  • CONFIGURES candidate collection sorted nothing before applying its cap, so which candidates survived depended on worker merge order. Candidates are now ordered by a pure content key first — notably not by node id, which looks stable but is itself handed out in merge order.

Windows: daemon files created with an empty ACL

@Kiborgik diagnosed and fixed a subtle one (#1351): the daemon's private directory combined a protected DACL with a non-inheritable ACE, which on Windows means children inherit nothing — every file created inside was born with an empty ACL and unreadable even by its owner. Directories now carry a properly inheritable owner-only ACE, so the strict security posture is kept and the files actually work. A companion fix from the same contributor closed a trap where a machine named like its user granted permissions to an empty principal; testing that on a non-domain-joined machine surfaced the mirror-image trap, so our build tooling now identifies the account by SID and stops resolving names altogether.

Repairs for two v0.10.2 regressions

Both reported within hours — thank you for the fast signal.

  • update --ui stopped working (#1544, @ehendrix23). v0.10.2 removed the obsolete ui/standard chooser and the flags that drove it, so a command living in scripts and muscle memory became a hard error. Both flags are accepted again — they do nothing, say so once, and genuinely unknown flags still fail.
  • The generated Pi extension broke Pi entirely (#1550, @musichen). Pi loads an extension by calling its default export; ours exported a named function instead, and a Pi extension that fails to load takes every pi command down with it, pi doctor included. The extension now default-exports its factory. Fixed independently by @musichen and @henri-edh as well, whose sharper description of Pi's loader is the comment now in our source.

Structured output stops dropping evidence

trace_path(include_evidence: true) promised per-hop strategy and confidence columns, and delivered them — in tree format only. With format: "json" both fields silently vanished, which hit exactly the callers most likely to want them: the ones consuming structured output programmatically (#1542, @asemraza). The JSON path now carries both fields with the same semantics, nulls standing where the tree format prints -.

Subprocess spawns survive a busy machine

Chasing a CI flake uncovered a real robustness gap: when the kernel refuses a process spawn with "try again" — a momentarily full process table on a loaded machine — cbm treated it as a permanent failure. A git probe or LSP server would refuse to start for a reason invisible to the user. Transient spawn failures now retry briefly; real errors (missing binaries, permissions) still fail immediately with unchanged semantics.

Install and activation: the refusal nobody could act on

Follow-up to #1537 (@listepo), and it turned out to be two defects stacked on each other.

The daemon refused to run when any ancestor of its cache directory was group-writable — the same rule we removed on the installer side in v0.10.2, in the sibling check that decision covers but that never got changed. A group-writable ~ or ~/.cache is ordinary (WSL2 ships 0775, so do several distro skeletons and any machine with a shared primary group), so for those users the daemon was permanently unusable, with nothing to close and nothing a reboot would fix. World-writable ancestors are still refused — any local user could swap a path component — and the private directory itself is still forced to owner-only, which is what makes admitting the ancestor safe.

Underneath that, the error message was inventing its own evidence: the refusal path set no error code, so the reporting fell back to printing whatever errno happened to hold, and handed the reporter ENOENT for a permission decision. They went looking for a missing file that was there the whole time. The message now names the directory and the rule that refused it.

Also in this area: the activation guard reported every refusal as "active CBM sessions could not be stopped", including failures where nothing is running at all. Those are now separate messages, the second says plainly that nothing needs closing, and neither remedy assumes a codebase-memory-mcp binary is still on PATH — advice that was unusable at exactly the moment it printed, right after uninstall.

Also fixed

  • Codex saw no cbm tools when CBM_CACHE_DIR was set (#1562, @anton-matosov). Codex passes only explicitly-listed variables into an MCP subprocess, so the server it spawned read the default cache while the daemon used the configured one; they disagreed and the connection closed during initialization. The generated config now forwards the variable.
  • The installed skill file failed to load in strict YAML readers (#1554, @xezzon). Its description contained Triggers on: unquoted, and a colon-space in an unquoted YAML scalar means "nested mapping" — so parsers rejected the whole document and the skill silently never loaded.
  • search_code echoed a negative limit back as the result count (#1511, fix by @lukiod), which reads to an agent as an answer rather than a rejected argument.
  • ~~OpenCode installs went into the wrong file (@iandol).~~ Correction: this was listed here in error. The fix merged a few hours after the v0.10.3 tag was cut, so it is not in this release — it ships in v0.10.4. If your OpenCode config is a .jsonc file, upgrading to v0.10.3 will not have helped, and we are sorry for the wasted time.
  • Release archives are validated before extraction (#1510, @cyphercodes): an exact member set, with symlinked members refused outright.

Upgrade

  • Binary installs: download below, or re-run install.sh / install.ps1 — re-running the installer is the update.
  • npm / PyPI: update through your package manager as usual.
  • No index, cache, or config migration.
