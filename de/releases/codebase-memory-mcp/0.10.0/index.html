⚠️ Verhaltensänderungen

  • Neue Kantenklasse: CALL_REFERENCE – und CALLS bedeutet jetzt genau eins. Das Diagramm unterscheidet jetzt das Aufrufen eines Callables von der Übergabe als Wert (app.register(pluginFn, opts)). CALLS ist ausschließlich für Aufrufe reserviert; CALL_REFERENCE wird nur ausgegeben, wenn deterministische Parser-/LSP-/Registrierungsnachweise den genauen aufrufbaren Wert belegen (vorkommensgenaue Spannen, lexikalischer Bindungsstatus, aufgelöste Symbolidentität); Mehrdeutige, verschattete oder dynamische Rebound-Vorkommen bleiben USAGE. Abfragen, bei denen davon ausgegangen wurde, dass es sich bei jeder aufrufbaren Beziehung um eine CALLS-Kante handelt, sollten die neue Bezeichnung berücksichtigen – und eine Präzision erhalten, die sie vorher nicht hatten: Eine CALL_REFERENCE-Kante ist ein Beweis, keine Vermutung.

  • Ein Archiv pro Plattform – die Benutzeroberfläche ist immer enthalten. Die Aufteilung zwischen ui-* und Nicht-UI-Variante ist weg: Jede Plattform liefert jetzt ein einzelnes Archiv mit eingebetteter Diagramm-Benutzeroberfläche aus, und die npm/PyPI-Pakete enthalten es standardmäßig (die CBM_VARIANT=ui-Opt-in-Option vom RC ist veraltet). Weniger Artefakte, keine Downloads falscher Varianten, eine zu überprüfende Komposition.

Was hat sich geändert?

Koordinationsdaemon und Parallelität

Dies ist die größte Backend-Änderung seit Beginn des Projekts: Das Ausführungsmodell von cbm wurde von unabhängigen Prozessen pro Sitzung zu einem koordinierten Backend pro Benutzer verschoben. Gleichzeitige Sitzungen werden über den Daemon (daemon start|stop|status, permanent oder sitzungsverwaltet) mit authentifiziertem IPC, Build-Fingerprint-/Versions-/Cache-Root-Konflikterkennung, physischer Job-Zulassungskontrolle für parallele Indizierung und der vom Daemon bereitgestellten Diagramm-Benutzeroberfläche koordiniert. Da es sich bei einem Daemon pro Benutzer um eine Sicherheitsgrenze handelt, wurde sein IPC entsprechend gehärtet. Unter Windows werden Pipe-clients durch die Prozessidentität und nicht durch Identitätswechsel validiert. Private Namespace-Objekte werden mit der SID des Token-Benutzers als Besitzer versehen und DACLs werden streng validiert. Unter POSIX wird die Socket-Identität anhand von Inode-gepinnten Datensätzen überprüft. Alles bleibt streng lokal.

RC-Erfahrungsberichte verschärften dann die Situation: Ein client, ​​dessen Binärbild der Daemon ablehnt, erhält jetzt eine Antwort anstelle eines unbestimmten „Ausstehend“ (#1383); eine übergroße MCP-Antwort führt zu einem strukturierten Fehler anstelle eines Prozessabbruchs (#1375); Hooks erzeugen Konflikte beim Surface-Daemon-Build an den Aufrufer, anstatt nichts auszugeben (#1388); und der Zulassungspfad, der einen nicht übereinstimmenden Build akzeptiert, benennt jetzt seine Kohorte in der Diagnose. Unter macOS werden Unterprozesse über posix_spawn statt über fork+exec erzeugt.

Vorbereitung für Worktree-native Multi-Agent-Workflows. Der Daemon ist auch die Grundlage dafür, wie Multi-Agent-Setups heute tatsächlich funktionieren: ein Agent pro Git-Worktree. Derzeit muss jeder Arbeitsbaum indiziert werden, als wäre er ein separates Repository. Mit der zentralisierten Daemon-Schicht wird in künftigen Versionen genau dies überarbeitet: Arbeitsbäume werden zu Kindern des Diagramms des Haupt-Repositorys, teilen alles unverändert mit und indizieren nur das, was sich unterscheidet – was das Agent-pro-Arbeitsbaum-Muster in Bezug auf Zeit und Speicherplatz erheblich günstiger macht.

Diagrammsemantik und Neuindizierung

Die CALL_REFERENCE-Arbeit (siehe Verhaltensänderungen) durchläuft den gesamten Stapel: Extraktion, LSP-Auflösung, sequentielle und parallele Veröffentlichung, Persistenz, MCP/UI-Zählungen und Dokumentation, mit vorkommensgenauem Abgleich, sodass ein LSP-Ergebnis niemals eine andere gleichnamige Verwendung fördern kann, und Fail-Closed-Behandlung für lexikalische Schattenbildung und Mehrdeutigkeit. Parallel dazu wurde die warme Neuindizierung in eine Delta-Merge-Pipeline verschoben – unveränderte Daten werden nach vorne kopiert und nur das geänderte Slice wird gepatcht und atomar eingelagert, wodurch der vorherige Wiederherstellungs- und Reparaturpfad ersetzt wird. Die Warm-Re-Index-Leistung in sehr großem Maßstab ist noch in Arbeit (siehe bekannte Probleme), aber die strukturelle Überarbeitung, die diese Version mit sich bringt, ist die Grundlage, auf der die verbleibenden Erfolge landen.

Werkzeugausgabe und MCP-Oberfläche

TOON komprimiert die Ausgabe über die gesamte Abfrageoberfläche (ca. 10-mal kleiner) und dann das Baumformat oben (präfixgruppierte Zeilen, genau einmalige Paginierungscursor, echte Änderungsauswirkungen in detect_changes, SCC-Zykluserkennung) für eine kombinierte Reduzierung des Ausgabetokens um ca. 99 % im Vergleich zu v0.9.0 bei großen Ergebnissen. MCP-Antworten hören auf, ihre gesamte Nutzlast in structuredContent zu duplizieren (#1375). Der optionale include_evidence legt die Herkunft der Kantenauflösung offen. detect_changes beschränkt die Seed-Erkennung auf geänderte Zeilenbereiche. ADR-Tools haben einen Community-Korrektheitstest erhalten: Lesevorgänge bleiben während der Neuindizierung nicht blockierend, irreführende Abschnittsschreibvorgänge werden zurückgewiesen und Abdeckungsbereichsbezeichnungen bleiben erhalten. index_repository löst ein repo_path aus einem bekannten Projektnamen auf; Ein ungültiger Projektname kann den Daemon nicht mehr mit .corrupt.<hex>-Dateien belasten (#1425); CLI-Aktivierungsverweigerungen werden auf die aufgezeichnete Sicherheitsprüfung zurückgeführt (#1416); und --help leitet seine Werkzeugliste aus der MCP-Registrierung ab, sodass es nicht driften kann.

Windows- und Speichersicherheit

Die #581-Kette: Leiten Sie gewöhnliche Windows-Zuweisungen über mimalloc (--wrap + static-CRT-Override), geben Sie Thread-Heaps von einem TLS-Detach-Callback frei, löschen Sie eine SQLite-Seiten-Cache-Platte, die auf arm64 fehlerhaft war, und prüfen Sie den Allocator-Besitz pro Größenklasse laut beim Start, damit „die Optimierung nur Dekoration ist“ nie wieder stillschweigend passieren kann. Neu seit dem RC: Die gleiche Audit-Philosophie, die bei den ausgelieferten Linux-Binärdateien erkannt wurde, hatte malloc nie tatsächlich über mimalloc weitergeleitet – die Überschreibung ist jetzt wirklich aktiv (#1360); Speicherdiagnosebericht, Betriebssystem-Wahrheits-RSS auf jeder Plattform; Diagrammdatenbanken unter Nicht-ASCII-Cache-Pfaden werden zuverlässig unter Windows geöffnet (jeder Wartungspfad-SQLite-Öffner durchläuft jetzt die gleiche Wide-Path-Normalisierung wie der primäre Öffnungspfad – zuvor schlug der zweite Index z. B. in einen Cache mit kyrillischem Namen fehl); stdio läuft im Binärmodus unter MCP unter Windows; erzeugte untergeordnete Prozesse blinken nicht mehr in Konsolenfenstern (#1427, plus ein Community-Fix ​​für den allgemeinen Fall); und die Codebasis lässt sich sauber unter MinGW GCC kompilieren.

Windows liefert jetzt eine einzige Binärdatei aus – und Updates werden von install.ps1 ausgeführt

Windows lieferte zuvor zwei ausführbare Dateien aus: einen kleinen permanenten Launcher und die dahinter stehende Produktbinärdatei. Es wird jetzt eine Binärdatei ausgeliefert, genau wie Linux und macOS.

Der Launcher existierte, damit das Produkt sich selbst aktualisieren konnte: Unter Windows kann eine laufende ausführbare Datei ihr eigenes Image nicht ersetzen, daher musste eine zweite residente Binärdatei den Austausch durchführen. Dieser kleine Helfer löst Antiviren-Heuristiken zuverlässig aus, und wir konnten ihn nicht behalten, ohne etwas zu versenden, das markiert wurde – daher wurde der Aktualisierungsschritt aus dem laufenden Prozess in install.ps1 verschoben, das ausgeführt wird, während codebase-memory-mcp nicht ausgeführt wird.

Was sich für Sie ändert: Unter Windows wird codebase-memory-mcp update nicht mehr direkt aktualisiert. Stattdessen wird der genaue auszuführende Befehl ausgegeben:

powershell -ExecutionPolicy Bypass -File "<install-dir>\install.ps1"

install.ps1 ist idempotent, daher ist das erneute Ausführen das Update: Es stoppt den Daemon, zieht die laufende Binärdatei zurück, installiert die neue und bereinigt. Die Installation über npm oder pip ist davon nicht betroffen – aktualisieren Sie wie zuvor mit Ihrem Paketmanager.

Sprachen und Extraktionsgenauigkeit

Semantische Auflösung auf Perl-LSP-Ebene; Unterstützung der InterSystems ObjectScript-Sprache; Mojo-Verkabelung. Neu seit dem RC: Schnelle paketübergreifende IMPORTS, die durch Package.swift-Manifeste gelöst werden; Nix-Dateien, deren Stammausdruck eine Funktion ist, löschen nicht mehr jede Definition, und Nix-Attributpfade werden mit Blattnamen und bereichsbezogenen QNs modelliert, wobei Bindungen auf Modulebene als Variablen geprägt sind; Durch einen Kommentar getrennte Dekoratoren bleiben angehängt; Gleichnamige GoogleTest-Makros in einer Datei erhalten eindeutige Namen, anstatt in einem einzelnen Knoten zusammengefasst zu werden und Aufrufkanten zu löschen (#1266); JS/TS-Template-Literal-URLs werden auf {}-Platzhalter reduziert, sodass das Routen-Rendezvous funktioniert. Die Verarbeitung von Haskell-Arrays ist aliassicher. Aus dem RC-Batch übertragen: natives fetch() als HTTP_CALLS, CommonJS require()-Schattenkorrekturen, Alias-Import-Auflösung, C/C++ #include-zu-Header-Kanten und #ifdef-Split-Wiederherstellung, PHP-Trait-Rekursion-OOM-Korrekturen, Laravel- und JAX-RS-Routenkomposition, Env-Access-CONFIGURES-Schutz, Dateiknoten-QN-Kollisionskorrekturen, UTF-8-sichere Dokumentzeichenfolgenkürzung und begrenzte GLR-Stack-Merge-Rekursion.

Abfrage-Engine (Cypher)

coalesce() und Skalarfunktionen mit mehreren Argumenten in WHERE; Pfadsemantik mit Var-Länge, korrigiert mit einer beworbenen Tiefenklemme; DISTINCT wird vor RETURN-Grenzwerten angewendet; Ganzwertrückgaben für zusammengesetzte und maskierte Eigenschaften; eine Deadline für die Ausführung; tools/list Standard-Paginierung. Neu seit dem RC: Die vollständige Multi-Key-ORDER BY-Liste wird analysiert und angewendet, wobei LIMIT intakt bleibt (#1334); OPTIONAL MATCH kann keine „Keine Übereinstimmung“-Zeile mehr erstellen, nachdem das Zeilenbudget aufgebraucht ist; und Aggregationsspalten werden nach tatsächlichen Aggregatfunktionen klassifiziert.

Store, Artefakte und Lebenszyklus

Atomic-Cache-Veröffentlichung im SQLite-Writer; Snapshot-Exporte wurden konsistent und fehlerhafte Importe abgelehnt; Ziel-WAL/SHM-Sidecars wurden vor der Installation einer neuen DB entfernt; SQLITE_CORRUPT tauchte bei Reihenscans auf; WAL begrenzt über journal_size_limit; Der Watcher indiziert Dirty Repos einmal pro Status neu. Die relative repo_path-Kanonisierung beschädigt und löscht Projekt-DBs nicht mehr automatisch. Neu seit dem RC: Die Neuindizierungsveröffentlichung erfolgt atomar durchgängig – unter privaten Pfaden bereitgestellt, überprüft und bei Fehlern unter Quarantäne gestellt; WAL-Versiegelung vor dem Artefaktaustausch; und Label-Zulassungslisten leiten durch den kanonischen typähnlichen Satz.

Agenten, clients und Installer

Die Abdeckung der Agentenintegration umfasst 43 automatische/bedingte client-Oberflächen, die jeweils nur geändert werden, wenn ihre dokumentierte Plattform, Markierung oder ihr vorhandener Konfigurationspfad vorhanden ist. Neu seit dem RC – größtenteils direkt aus RC-Erfahrungsberichten: Der Installer entfernt niemals vorhandene Hooks, wenn eine Skriptumschreibung abgelehnt wird, und --dry-run sagt genau dieses Ergebnis voraus (#1387); generierte Codex-Agent-Rollen-TOMLs deklarieren ihren Transport; pi- und OpenCode-Erweiterungen werden aus der Tool-Registrierung generiert, sodass neue Tools automatisch darin angezeigt werden. Indizierungsstämme können über CLI deklariert werden, die Erkennung bereinigt das Cache-Verzeichnis und die Komprimierung ist bei großen Eingaben größensicher; Windows-Installation/Deinstallation/Doctor schlägt bei Sitzungen, die sie selbst sicher beenden können, nicht mehr fehl (#1416). Aus dem RC-Batch übernommen: der sicherheitsgehärtete Windows-Installationstransaktionspfad, die Ablehnung unbekannter Flags mit Vorschlägen für die nächstgelegene Flag, ehrliche --dry-run-Kennzeichnung, wachsende Discovery-Walk-Stacks, FreeBSD-Speichererkennung und der strikte CBM_MEM_BUDGET_MB-Resolver.

CI- und Testinfrastruktur

Jeder Veranstaltungsort – lokales CI, PR CI, der Probelauf vor der Veröffentlichung und die Release-Pipeline – führt die gleichen kanonischen Beinskripte aus, mit einem Veranstaltungsortparitätsvertrag, der jede Abweichung in einen roten Build umwandelt; parallele Ausführung pro Suite mit einem Zero-Loss-Gate (~2.5× schnellere Suiten); erweiterte ThreadSanitizer-Abdeckung plus natives ARM64 Windows UBSan; Freigabe-Artefakt-Bescheinigung; Release-Gating-Einweichbeine. Neu seit dem RC: VirusTDas vollständige Scannen der genauen Archivartefakte ist ein standardmäßiger Abschlussschritt jedes Probelaufs (wobei die Flagging-Engine benannt und nicht nur gezählt wird); Lokale CI-Läufe werden pro Lauf-ID isoliert. und die Release-Pipeline selbst wurde öffentlich debuggt – skip_tests überspringt Smoke and Soak nicht mehr stillschweigend und Skript-Exec-Bits werden durch Vertrag fixiert.

Bekannte Probleme

  • Geringes Speicherwachstum nur für Windows bei anhaltender Abfragelast (~4.5 KB/Abfrage; weder macOS noch Linux zeigen es an). Dies ist nicht die Ratsche Nr. 581 – Eigentumsprüfungen werden bestanden und der 53-fache Fehlermodus ist verschwunden – aber es wird durch eine Folgeuntersuchung nachverfolgt.
  • Warm-Neuindizierung in sehr großem Maßstab ist immer noch langsamer als v0.9.0-era, verbessert sich aber. Die in dieser Version ausgelieferte Delta-Merge-Pipeline ersetzt den Rebuild-and-Repair-Pfad und hat die Warm-Neuindizierungszeiten in unseren A/B-Läufen bereits erheblich verkürzt; Das Schließen der verbleibenden Lücke zu den v0.9.0-era-Cache-Trefferzahlen ist derzeit in Arbeit. Die Kaltindizierung ist bei allen Basislinien oder schneller als diese.
  • Multithreaded-Edge-Count-Jitter: Knotenanzahlen sind über alle Läufe hinweg bytestabil; Kantensummen können bei Sprachen mit hoher Auflösung von Lauf zu Lauf geringfügig variieren (im schlimmsten Fall TypeScript). Wird als offene Determinismus-Untersuchung verfolgt. – Unter macOS erscheint möglicherweise eine Startzeile mem.allocator.not_owned in Protokollen – unter macOS ist dies die entworfene Konfiguration (der Allocator bedient die gebundenen SQLite-/Tree-Sitter-Populationen; gewöhnliches Malloc verbleibt beim System-Allocator) und ist harmlos. Unter Windows und jetzt auch Linux ist es der Stolperdraht für die Klasse #581: Wenn Sie es dort sehen, legen Sie es bitte ab.

Antivirus-False-Positives – die ganze Geschichte und eine Richtlinienänderung

Diese Version wird mit 0 Erkennungen für jedes Artefakt ausgeliefert – jedes Binärarchiv, beide Installationsskripts und die Hinweisdateien, die jeweils von über 60 Engines gescannt werden. Die folgende Verifizierungstabelle wird aus diesen Scans generiert und jeder darin enthaltene VirusTotal-Link ist dauerhaft: Sie können die genauen Bytes jederzeit selbst erneut überprüfen.

Wir schulden Ihnen die längere Geschichte, weil sie die Funktionsweise unseres Release-Gates verändert hat – und weil sie einer der Hauptgründe dafür ist, dass die Strecke vom RC bis zum Finale Wochen statt Tage gedauert hat.

Was ist passiert. Während des RC und der Endphase lösten einige Builds zeitweise eine Heuristik des maschinellen Lernens aus – die Engine von Microsoft meldete Trojan:Script/Wacatac.B!ml – während alle anderen Engines als sauber gemeldet wurden. Das Suffix !ml kennzeichnet die Punktzahl eines statistischen Modells, nicht eine Signaturübereinstimmung. Das Script-Token ist ein generischer Bucket in diesem Benennungsschema und sagt nichts über den Skriptinhalt aus. Wir haben es zunächst als potenziellen Kompromiss betrachtet: vollständige Zerlegung einer Release-Matrix, die aus einem Commit erstellt wurde, Reverse Engineering der gekennzeichneten Artefakte, Entropieanalyse anhand gepackter Nutzlastprofile. Nichts. Die Urteile verteilten sich auf alle Achsen gleichzeitig – die statische/dynamische Linkachse wurde zwischen den Architekturen invertiert, zwei macOS-Binärdateien mit identischer Segmentstruktur wurden sauber/markiert aufgeteilt und Geschwisterartefakte eines Builds landeten in verschiedenen Varianten-Buckets. Der entscheidende Beweis: Eine identische Datei – derselbe SHA-256 – wurde innerhalb von etwa einer Stunde von 0/62 sauber auf markiert, ohne dass sich auf unserer Seite etwas änderte. Und das Experiment, das wir in die andere Richtung durchgeführt haben, hat es bestätigt: Wir haben jedes eingebettete Shell-Skript aus der Binärdatei entfernt und das UI-Bundle und die Integrationsvorlagen in separate verifizierte Dateien verschoben – die Erkennungszahl ist nicht gesunken, sie wurde einfach zwischen den Artefakten verschoben, sodass wir zur einfacheren Einzelbinärzusammensetzung zurückgekehrt sind. Ein Teil des Urteils liegt im Status des Scanners selbst, nicht in unseren Bytes. Keine Codeänderung kann eine Nichterkennung garantieren, da der Klassifikator nicht nur den Code beurteilt.

Warum sich die Richtlinie geändert hat. In den RC-Notizen stand, dass unser Gate permanent und ohne Toleranz keine Erkennungen durchführte – und wir meinten es so, als wir es schrieben. Aber ein Null-Gate gegen ein Urteil, das sich auf identische Bytes bezieht, bedeutet, dass unser Veröffentlichungszeitpunkt eine Funktion des Cloud-Modellstatus von Defender ist, nicht von unserem Code: Jeder Vorfall kostete Tage für die Überprüfung von Bytes anhand eines Live-Defender-Endpunkts, die Einreichung eines Falsch-Positiv-Berichts bei Microsoft und das Warten auf eine Klassifizierungsrevision – wobei die Entwicklung dahinter praktisch fest blockiert war. Dies ist keine nachhaltige Art des Versands, und es wäre die unehrliche Option gewesen, so zu tun, als ob die absolute Regel immer noch in Kraft wäre. Deshalb haben wir sie durch eine Richtlinie ersetzt, die wir tatsächlich einhalten können, dokumentiert und gepinnt durch einen Vertragstest in SECURITY.md:

– Eine Version kann mit höchstens einer Erkennung ausgeliefert werden, und zwar nur, wenn die Engine von Microsoft stammt und die Bezeichnung auf !ml endet – die genaue, nachgewiesene falsch-positive Klasse, die oben beschrieben wurde.

  • Alles andere blockiert immer noch, schwer: zwei oder mehr Engines, jedes signaturbasierte Label, jeder andere Anbieter, jedes „verdächtige“ Urteil.
  • Eine tolerierte Erkennung wird veröffentlicht, niemals ausgeblendet – sie erscheint in der Verifizierungstabelle unten mit ihrem VirusTotal-Link und einer TOLERATED-Markierung, sodass Sie immer genau sehen können, was versendet wurde.

Diese Version benötigte diese Toleranz nicht – sie scannt völlig sauber – aber Sie sollten die Regel kennen, nach der zukünftige Versionen ausgeliefert werden.

Dies ist endemisch, nicht spezifisch für uns. Dieselbe !ml-Familie trifft wiederholt auf große, nicht signierte, native Open-Source-Binärdateien: llama.cpp (nichts beim Reverse Engineering gefunden), GitHubs eigene gh CLI, Microsofts eigene Go-Toolchain, Anthropics Claude Code, OpenAI-Codex, rust-lang, yt-dlp, Godot, PyInstaller, Tauri. Ein Microsoft-Ingenieur im Go-Team um es deutlich auszudrücken: * „Wir können nicht einfach etwas reparieren und alle Go-False-Positives lösen.“* Wir formen die Binärdatei absichtlich nicht um, um dem Klassifikator auszuweichen – das ist es, was Malware tut, und derselbe Ingenieur meldet, dass * „die Prüfung erhöht, anstatt sie zu vermeiden.“* Wir möchten lieber scannbar sein und ein False-Positive-Ergebnis erklären, als unlesbar zu sein und gut abzuschneiden. Was wir sowieso behoben haben. Die Untersuchung ergab echte Mängel, die aus eigener Kraft korrigiert und nun von Release-Gates bestätigt wurden: Jede Linux-Binärdatei, die wir jemals ausgeliefert hatten, forderte einen ausführbaren Stapel (eine fehlende .note.GNU-stack-Annotation); eine reine Test-Fork-Probe wurde in Produktions-Builds kompiliert; der Daemon erzeugte curl gegen GitHub und gibt API frei, um nach Updates zu suchen – entfernt, cbm stellt jetzt von sich aus keine Netzwerkanfrage mehr; Nicht verwendete Extraktions- und SQLite-Maschinen für ladbare Erweiterungen wurden kompiliert. Temp-Datei- und Symlink-Scan-Härtung; und Build-Zeitstempel für reproduzierbare Bytes entfernt.

Die dauerhafte Lösung ist die Code-Signierung, und sie ist im Gange – Identitätsvalidierung und Plattformregistrierung sind bürokratisch und nicht technisch, sodass sie nach ihrem eigenen Zeitplan endet. Unter Windows hilft das Signieren. Beachten Sie, dass es kein Code-Signatur-Schema gibt, das AV-Engines für Linux ELF-Binärdateien berücksichtigen, sodass die obige Transparenz dauerhaft und nicht vorübergehend ist. Wenn Sie etwas finden, das unserer Einschätzung widerspricht, möchten wir es wissen: Eröffnen Sie ein Problem mit der Bezeichnung av-analysis – ein konkreter Befund ändert unsere Position. What's changed

Coordination daemon & concurrency

This is the largest backend change since the project began: cbm's execution model moved from independent per-session processes to a coordinated per-user backend. Concurrent sessions coordinate through the daemon (daemon start|stop|status, permanent or session-managed) with authenticated IPC, build-fingerprint/version/cache-root conflict detection, physical-job admission control for parallel indexing, and the graph UI served from the daemon. Because a per-user daemon is a security boundary, its IPC was hardened accordingly — on Windows, pipe clients are validated by process identity rather than impersonation, private-namespace objects are owner-stamped with the token user's SID, and DACLs are strictly validated; on POSIX, socket identity is checked against inode-pinned records. Everything remains strictly local.

RC field reports then hardened the seams: a client whose binary image the daemon rejects now gets an answer instead of an indefinite "pending" (#1383); an oversized MCP reply produces a structured error instead of process death (#1375); hooks surface daemon build conflicts to their caller instead of emitting nothing (#1388); and the admission path that accepts a mismatched build now names its cohort in diagnostics. On macOS, subprocesses spawn via posix_spawn instead of fork+exec.

Preparation for worktree-native multi-agent workflows. The daemon is also the groundwork for how multi-agent setups actually run today: one agent per git worktree. Right now each worktree has to be indexed as if it were a separate repository. With the centralized daemon layer in place, upcoming releases will rework exactly this: worktrees become children of the main repository's graph, sharing everything unchanged and indexing only what differs — making the agent-per-worktree pattern dramatically cheaper in time and disk.

Graph semantics & reindexing

The CALL_REFERENCE work (see behavior changes) runs through the whole stack: extraction, LSP resolution, sequential and parallel publication, persistence, MCP/UI counts, and documentation, with occurrence-exact matching so an LSP result can never promote a different same-named usage, and fail-closed handling for lexical shadowing and ambiguity. Alongside it, warm re-indexing moved to a delta-merge pipeline — unchanged data is copied forward and only the changed slice is patched and atomically swapped in, replacing the previous rebuild-and-repair path. Warm re-index performance at very large scale is still work in progress (see known issues), but the structural rework this release ships is the foundation the remaining wins land on.

Tool output & MCP surface

TOON compact output across the query surface (~10× smaller) and then the tree format on top (prefix-grouped rows, exactly-once pagination cursors, real change-impact in detect_changes, SCC cycle detection) for a combined ~99% output-token reduction vs v0.9.0 on large results. MCP responses stop duplicating their entire payload in structuredContent (#1375). Optional include_evidence exposes edge resolution provenance. detect_changes scopes seed detection to changed line ranges. ADR tools got a community correctness pass: reads stay nonblocking during reindex, misleading section writes are rejected, and coverage scope labels are preserved. index_repository resolves a repo_path from a known project name; an invalid project name can no longer send the daemon littering .corrupt.<hex> files (#1425); CLI activation refusals are attributed to the recorded safety check (#1416); and --help derives its tool list from the MCP registry, so it can't drift.

Windows & memory safety

The #581 chain: route ordinary Windows allocations through mimalloc (--wrap + static-CRT override), release thread heaps from a TLS detach callback, drop an SQLite page-cache slab that faulted on arm64, and audit allocator ownership per size class out loud at startup so "the tuning is decoration" can never happen silently again. New since the RC: the same audit philosophy caught that shipped Linux binaries had never actually routed malloc through mimalloc — the override is now genuinely active (#1360); memory diagnostics report OS-truth RSS on every platform; graph databases under non-ASCII cache paths open reliably on Windows (every maintenance-path SQLite open now routes through the same wide-path normalization as the primary open — previously the second index into e.g. a Cyrillic-named cache failed); stdio runs in binary mode under MCP on Windows; spawned child processes no longer flash console windows (#1427, plus a community fix for the general case); and the codebase compiles cleanly under MinGW GCC.

Windows now ships a single binary — and updates run from install.ps1

Windows previously shipped two executables: a small permanent launcher plus the product binary behind it. It now ships one binary, exactly like Linux and macOS.

The launcher existed so the product could update itself in place: on Windows a running executable cannot replace its own image, so a second resident binary had to perform the swap. That small helper reliably trips antivirus heuristics, and we could not keep it without shipping something that gets flagged — so the update step moved out of the running process and into install.ps1, which runs while codebase-memory-mcp is not running.

What changes for you: on Windows, codebase-memory-mcp update no longer updates in place. It prints the exact command to run instead:

powershell -ExecutionPolicy Bypass -File "<install-dir>\install.ps1"

install.ps1 is idempotent, so re-running it is the update: it stops the daemon, retires the running binary, installs the new one, and cleans up. Installing through npm or pip is unaffected — update with your package manager as before.

Languages & extraction accuracy

Perl LSP-tier semantic resolution; InterSystems ObjectScript language support; Mojo wiring. New since the RC: Swift cross-package IMPORTS resolved through Package.swift manifests; Nix files whose root expression is a function no longer drop every definition, and Nix attrpaths are modeled with leaf names and scoped QNs, with module-level bindings minted as Variables; decorators separated by a comment stay attached; same-named GoogleTest macros in one file get unique names instead of collapsing into a single node and dropping call edges (#1266); JS/TS template-literal URLs flatten to {} placeholders so route rendezvous works; Haskell array handling is alias-safe. Carried from the RC batch: native fetch() as HTTP_CALLS, CommonJS require() shadow fixes, aliased-import resolution, C/C++ #include-to-header edges and #ifdef-split recovery, PHP trait-recursion OOM fixes, Laravel and JAX-RS route composition, env-access CONFIGURES guards, File-node QN collision fixes, UTF-8-safe docstring truncation, and bounded GLR stack-merge recursion.

Query engine (Cypher)

coalesce() and multi-arg scalar functions in WHERE; var-length path semantics fixed with an advertised depth clamp; DISTINCT applied before RETURN limits; whole-value returns for composite and escaped properties; a wall-clock execution deadline; tools/list default pagination. New since the RC: the full multi-key ORDER BY list is parsed and applied with LIMIT kept intact (#1334); OPTIONAL MATCH can no longer fabricate a "no match" row after the row budget fills; and aggregation columns are classified by actual aggregate functions.

Store, artifacts & lifecycle

Atomic cache publish in the SQLite writer; snapshot exports made consistent and corrupt imports refused; destination WAL/SHM sidecars removed before installing a fresh DB; SQLITE_CORRUPT surfaced from row scans; WAL bounded via journal_size_limit; watcher reindexes dirty repos once per distinct state; relative repo_path canonicalization no longer corrupts and auto-deletes project DBs. New since the RC: reindex publication is atomic end to end — staged under private paths, verified, and quarantined on failure; WAL sealing before artifact swap; and label allowlists route through the canonical type-like set.

Agents, clients & installer

Agent integration coverage spans 43 automatic/conditional client surfaces, each changed only when its documented platform, marker, or existing config path is present. New since the RC — mostly straight from RC field reports: the installer never removes existing hooks when a script rewrite is refused, and --dry-run predicts exactly that outcome (#1387); generated Codex agent role TOMLs declare their transport; pi and OpenCode extensions are generated from the tool registry, so new tools appear in them automatically; indexing roots can be declared from the CLI, discovery prunes the cache directory, and compression is size-safe on huge inputs; Windows install/uninstall/doctor no longer fail on sessions they themselves can stop safely (#1416). Carried from the RC batch: the security-hardened Windows install transaction path, unknown-flag rejection with nearest-flag suggestions, honest --dry-run labeling, growing discovery walk stacks, FreeBSD memory detection, and the CBM_MEM_BUDGET_MB strict resolver.

CI & test infrastructure

Every venue — local CI, PR CI, the pre-release dry run, and the release pipeline — runs the same canonical leg scripts, with a venue-parity contract that turns any drift into a red build; parallel per-suite execution with a zero-loss gate (~2.5× faster suites); widened ThreadSanitizer coverage plus native ARM64 Windows UBSan; release-artifact attestation; release-gating soak legs. New since the RC: VirusTotal scanning of the exact archive artifacts is a standard final step of every dry run (with the flagging engine named, not just counted); local-CI runs are isolated per run id; and the release pipeline itself was debugged in public — skip_tests no longer silently skips smoke and soak, and script exec bits are pinned by contract.

Known issues

  • Small Windows-only memory growth under sustained query load (~4.5 KB/query; neither macOS nor Linux shows it). This is not the #581 ratchet — ownership audits pass and the 53× failure mode is gone — but it is tracked with a follow-up investigation.
  • Warm re-index at very large scale is still slower than v0.9.0-era, but improving. The delta-merge pipeline shipped in this release replaces the rebuild-and-repair path and already cut warm re-index times substantially in our A/B runs; closing the remaining gap to the v0.9.0-era cache-hit numbers is active work in progress. Cold indexing is at or faster than all baselines.
  • Multi-threaded edge-count jitter: node counts are byte-stable across runs; edge totals can vary marginally run-to-run on resolution-heavy languages (worst case TypeScript). Tracked as an open determinism investigation.
  • On macOS a startup line mem.allocator.not_owned may appear in logs — on macOS this is the designed configuration (the allocator serves the bound sqlite/tree-sitter populations; ordinary malloc stays with the system allocator) and is harmless. On Windows and now Linux it is the tripwire for the #581 class: if you see it there, please file it.

Antivirus false positives — the full story, and a policy change

This release ships with 0 detections on every artifact — every binary archive, both install scripts, and the notices files, each scanned by 60+ engines. The verification table below is generated from those scans, and every VirusTotal link in it is durable: you can re-check the exact bytes yourself at any time.

We owe you the longer story, because it changed how our release gate works — and because it is one of the main reasons the stretch from RC to final took weeks rather than days.

What happened. During the RC and final stretch, some builds intermittently tripped one machine-learning heuristic — Microsoft's engine reporting Trojan:Script/Wacatac.B!ml — while every other engine reported clean. The !ml suffix marks a statistical model's score, not a signature match; the Script token is a generic bucket in that naming scheme and says nothing about script content. We treated it as a potential compromise first: full dissection of a release matrix built from one commit, reverse-engineering of the flagged artifacts, entropy analysis against packed-payload profiles. Nothing. The verdicts split across every axis at once — the static/dynamic link axis inverted between architectures, two macOS binaries with identical segment structure split clean/flagged, and sibling artifacts of one build landed in different variant buckets.

The decisive evidence: one identical file — same SHA-256 — went from 0/62 clean to flagged within about an hour, with no change on our side. And the experiment we ran in the other direction confirmed it: we removed every embedded shell script from the binary and moved the UI bundle and integration templates into separate verified files — the detection count did not drop, it simply moved between artifacts, so we reverted to the simpler single-binary composition. Part of the verdict lives in the scanner's own state, not in our bytes. No code change can guarantee non-detection, because the classifier is not judging only the code.

Why the policy changed. The RC notes said our gate was zero detections, permanently, with no tolerance — and we meant it when we wrote it. But a zero gate against a verdict that flips on identical bytes means our release timing is a function of Defender's cloud-model state, not of our code: each incident cost days of verifying bytes against a live Defender endpoint, filing a false-positive report with Microsoft, and waiting for a classifier revision — with development effectively hard-blocked behind it. That is not a sustainable way to ship, and pretending the absolute rule still held would have been the dishonest option. So we replaced it with a policy we can actually keep, documented and pinned by a contract test in SECURITY.md:

  • A release may ship with at most one detection, and only when the engine is Microsoft and the label ends in !ml — the exact, evidenced false-positive class described above.
  • Everything else still blocks, hard: two or more engines, any signature-based label, any other vendor, any "suspicious" verdict.
  • A tolerated detection is published, never hidden — it appears in the verification table below with its VirusTotal link and a TOLERATED marker, so you can always see exactly what shipped.

This release did not need the tolerance — it scans fully clean — but you should know the rule under which future releases ship.

This is endemic, not specific to us. The same !ml family repeatedly hits large, unsigned, native open-source binaries: llama.cpp (nothing found on reverse engineering), GitHub's own gh CLI, Microsoft's own Go toolchain, Anthropic's Claude Code, OpenAI's Codex, rust-lang, yt-dlp, Godot, PyInstaller, Tauri. A Microsoft engineer on the Go team put it plainly: "we can't exactly go fix something and solve all Go false positives." We deliberately do not reshape the binary to dodge the classifier — that is what malware does, and the same engineer reports it "increases scrutiny rather than avoiding it." We would rather be scannable and explain a false positive than be unreadable and score well.

What we fixed anyway. The investigation turned up real defects, corrected on their own merits and now asserted by release gates: every Linux binary we had ever shipped requested an executable stack (a missing .note.GNU-stack annotation); a test-only fork probe was compiled into production builds; the daemon spawned curl against the GitHub releases API to check for updates — removed, cbm now makes no network request of its own accord; unused extraction and SQLite loadable-extension machinery compiled out; temp-file and symlink-scan hardening; and build timestamps removed for reproducible bytes.

The durable fix is code signing, and it is underway — identity validation and platform enrollment are bureaucratic, not technical, so it lands on its own schedule. Signing will help on Windows; note that no code-signing scheme exists that AV engines honour for Linux ELF binaries, so the transparency above is permanent, not transitional. If you find anything that contradicts our assessment, we want to know: open an issue with the av-analysis label — a concrete finding changes our position. Until signing lands, the gate above, published hashes, build provenance attestation, and source you can always build yourself are the trust anchors for this project.
