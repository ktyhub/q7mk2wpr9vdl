oh-mein-openagent v5.1.64

Desktop-Speichersynchronisierung beginnt jetzt, sobald die Engine startet, ohne auf eine Sitzung warten zu müssen. Eine von omo host ensure gestartete Engine lädt Erweiterungen nur, wenn eine Sitzung geöffnet wird, während der Desktop keine öffnet, bis die Engine den Speichersynchronisierungs-Bootstrap-Handshake gesendet hat, sodass die beiden aufeinander warteten. Der kompilierte omo und der npm-Launcher starten nun diesen einen Anspruch, bevor die Engine geladen wird, wann immer der Start einer RPC-Engine einen memory-sync-Kanal deklariert; Die erste Sitzung verwendet es wieder. Ein Anspruch, der fehlschlägt, meldet die Speichersynchronisierung immer noch als nicht verfügbar und greift nie auf CLI-Anmeldeinformationen zurück. (#12702) (#12704)

Intern (nur Tests): Die macOS trust-Erfassung liest /etc/ssl/cert.pem über den bereits injizierbaren Bundle-Reader, und ein Test beweist nun, dass eine fehlerhafte Standarddatei den strukturierten openssl-default-file-malformed-Drop-Eintrag (Datei, Ursache, Blockindex, Eingrenzung) liefert. (#12633)

Intern (nur Tests): Die OpenSSL-Standarddateiimportfunktion testet jetzt, dass jedes High-Byte in einer BEGIN-Zeile, nicht nur ein BOM, die gesamte Datei löscht. (#12632)

Intern (Release-Tooling): Das omo-native trust-Mutationskabel zählt einen Mutanten nur dann als getötet, wenn ein benannter Test durch eine Behauptung fehlschlägt; Ein Mutant, der nur einen Laufzeitfehler auslöst oder beim Laden abstürzt, wird jetzt als crashed gemeldet und schlägt den Lauf fehl. (#12631)

Behoben

– Bei der Speichersynchronisierung geht eine Bearbeitung nicht mehr verloren, wenn zwei Geräte gleichzeitig dieselbe Zeile einer Speicherdatei ändern. Geräte dieser Version behalten beide Änderungen als ganze Zeilen bei und jedes Gerät konvergiert. Zuvor wurden die Änderungen Zeichen für Zeichen in Text zusammengeführt, der keinem von beiden entsprach (#12279).

  • Zwischen Geräten dieser Version stört eine Bearbeitung eine Zeile, die niemand bearbeitet hat, nicht. Die Ausnahme ist ein sehr umfangreiches Umschreiben: Wenn ein Gerät mehr als etwa 2.000 Zeilen einer Notiz in einem Speichervorgang hinzufügt und entfernt, wird dieser Speichervorgang wie vor diesem Fix Zeichen für Zeichen zusammengeführt, sodass eine gleichzeitige Bearbeitung derselben Zeile weiterhin verbunden werden kann. – Wenn der Textkörper der Notiz oder der neue Text nicht mit einer neuen Zeile endet, wird die Bearbeitung wie zuvor weiterhin Zeichen für Zeichen zusammengeführt, sodass zwei gleichzeitige Bearbeitungen an dieser letzten Zeile weiterhin zusammengefügt werden können.
  • Bei einem Gerät, auf dem noch eine ältere Version läuft, kann die alte Zeichenzusammenführung immer noch auf folgende Weise schiefgehen:
    • Benachbarte Zeilen können verschmelzen. Das ältere Gerät schreibt die Zeile direkt nach einer Zeile, die diese Version bearbeitet hat, neu. Abhängig von den internen IDs der beiden Geräte können die beiden Änderungen in einer Zeile zusammengeführt werden, gefolgt von einer Leerzeile. Gemessen: Von head, one, two, tail schreibt diese Version ONE und das ältere Gerät schreibt TWO, und das Ergebnis kann head, TWOONE, eine Leerzeile, tail sein. Zwei ältere Geräte sind head, ONE, TWO, tail.
    • Übriger Text wird verschoben. Das ältere Gerät bearbeitet eine Zeile, die diese Version löscht. Der übrig gebliebene Text wird in eine benachbarte Zeile eingefügt.
    • Sein eigenes Diff berührt andere Zeilen. Die Zeichenzusammenführung des älteren Geräts kreuzt in eine Zeile, die der Benutzer nicht bearbeitet hat. Dies passiert auch zwischen zwei älteren Geräten.
  • Zwei ältere Geräte behalten ihre alte Charakterzusammenführung bei, bis sie aktualisiert werden. (#12597)
  • Speichersynchronisierung: Die Push-Phase eines großen Speichersatzes benötigt keinen Speicher mehr im Verhältnis zum gesamten Satz. Bei jedem Push-Schritt wird eine Journaldatei mit den Daten jedes ausstehenden Elements mehrmals pro Stapel erneut gelesen und geschrieben. Ein Gerät, das einige tausend Speicherdateien schob, erreichte daher einen Spitzenwert von 2 GiB oder mehr (#12286). Das Journal speichert jetzt einen kleinen Index ausstehender Elemente mit ihren Daten in separaten Dateien, und ein Push liest nur den Stapel, den es sendet. Wenn Sie den Satz vor dem Push erfassen, bleibt der Text jeder erfassten Datei erhalten, bis die Erfassung endet. Ein von einem älteren Build geschriebenes Journal wird beim ersten Lesen konvertiert, einschließlich eines Journals, bei dem ein älterer Build Elemente neben dem neuen Index hinzugefügt hat. (#12597)
  • Speichersynchronisierung: Ein Gerät, das einen großen Speichersatz empfängt, wird nicht mehr mit jeder empfangenen Datei langsamer. Beim Renderschritt wurde jeder Renderdatensatz des Zyklus für jede Datei erneut gelesen, sodass der erste Abruf einiger tausend Speicherdateien mehrere zehn Minuten dauerte (#12285). Jede Datei kostet jetzt gleich viel und das Absturz-Wiederaufnahme-Verhalten bleibt unverändert. (#12597)
  • Memory Git übernimmt nicht mehr core.hooksPath, core.fsmonitor, include.path oder includeIf.*.path von einem geerbten GIT_CONFIG_COUNT-Paar oder GIT_CONFIG_PARAMETERS-Eintrag, sodass ein exportiertes Paar wie core.hooksPath=/dev/null die Hooks und den Mirror-Push des Speicher-Repositorys nicht mehr stillschweigend überspringen kann. Jedes zweite eingefügte Paar (url.*.insteadOf, http.extraHeader, Anmeldeinformationen, safe.directory, ...) gilt weiterhin, neu nummeriert; Eine injizierte Liste, die Git selbst nicht analysieren kann, wird vollständig gelöscht. Memory Git erbt außerdem nicht mehr die Repository-Umleitung (GIT_DIR, GIT_WORK_TREE, GIT_COMMON_DIR, GIT_OBJECT_DIRECTORY, GIT_NAMESPACE, GIT_CONFIG, ...), sodass es nicht mehr auf ein anderes Repository verweisen kann; GIT_INDEX_FILE, GIT_CONFIG_GLOBAL und GIT_CONFIG_NOSYSTEM bleiben erhalten. (#12360, behebt #12354) (#12597) – Die Speichersynchronisierung stoppt nicht mehr jeden Push von einem Gerät, wenn die Änderung einer Speicherdatei größer ist als das Batch-Limit von 8 MiB: Diese Datei wird zurückgehalten und im Synchronisierungsstatus mit dem Namen versehen, was zu tun ist, alle anderen Speicher werden weiterhin synchronisiert und die Datei synchronisiert sich von selbst, sobald sie passt. Eine Änderung, die ein anderes Gerät an einer zurückgehaltenen Datei vornimmt, wird beibehalten und landet in der Kopie dieses Geräts, sobald die Datei passt, und eine Änderung, die ein älterer Build bereits für eine solche Datei in die Warteschlange gestellt hatte, wird auf die gleiche Weise wiederhergestellt, anstatt hängen zu bleiben. In der TUI-Fußzeile wird sync held angezeigt und der Hinweis besagt, dass die Datei zurückgehalten wird und ein abgelehnter Eintrag, der die Synchronisierung anhält, niemals hinter einer zurückgehaltenen Datei verborgen wird. (#12284) (#12597) – Durch das Öffnen eines Speicher-Repositorys werden bis zu sechs Git-Prozesse weniger gestartet: Die lokalen Konfigurationsstandardwerte werden mit einem git config --list anstelle eines git config --get pro Schlüssel gelesen, und die Reparatur am Zeilenende wird übersprungen, während das Repository nichts verfolgt. Jede Sitzung, die Speicher öffnet, zahlt dies, und auf einer ausgelasteten Maschine kostet jeder Git-Prozess Hunderte von Millisekunden. Die eigenen Tests von Memory-Core laufen jetzt unter dem kanonischen Testbudget von 20 Sekunden statt unter den Grenzwerten von 5–15 Sekunden pro Datei, was dazu führte, dass sie nur auf ausgelasteten Hosts fehlschlugen. (#12104, behebt #12103) (#12597) – thread_send meldet eine Nachricht nicht mehr als queued, wenn sie nie abgeholt wird. Wenn die Sitzung des Zielthreads keinen laufenden Drain aufweist, antwortet der Sender jetzt mit queued_offline: Die Nachricht wird beibehalten und die Sitzung übernimmt sie bei der nächsten Ausführung, sodass ein Aufrufer weiß, dass keine Runde gestartet wurde, und handeln kann, anstatt zu warten. Der Drain meldet auch eine Nachricht, die er hinter dem nicht gesendeten Entwurf des Benutzers bereithält, sodass ein Live-Drain niemals mit einem fehlenden verwechselt wird. (#12488, behebt #12486)
  • Überprüfen Sie, ob die rekursive Entfernung (synchron und asynchron) den Pfad tatsächlich entfernt hat, versuchen Sie es erneut mit begrenzten stillen Resten und schließen Sie sich den Sweep-Test-Entfernern an, bevor Sie deren übergeordnete Geräte löschen. (#11834)

Hinzugefügt

– Windows-Versionen enthalten jetzt omo-git-job-helper.exe, einen kleinen nativen Helfer, der jeden Speicher-Git-Befehl in seinem eigenen Kill-on-Close-Jobobjekt ausführt, sodass ein späterer Autor nachweisen kann, dass der Git eines getöteten Autors verschwunden ist, bevor er eine gestrandete Sperre zurückerhält. Bisher wird der Helfer noch nicht verwendet: Memory-Core behält das heutige Windows-Verhalten bei, bis es durch eine Folgemaßnahme verkabelt wird, und keine Veröffentlichung beansprucht das neue Protokoll, bis die Belastungsreihe bei der Erstellung während der Übertragung auf Windows CI übergegangen ist. (#12105, Teil von #10391) (#12597)

oh-my-openagent v5.1.64

Desktop memory sync now starts as soon as the engine boots, without waiting for a session. An engine started by omo host ensure loads extensions only when a session opens, while the desktop opens none until the engine has sent the memory-sync bootstrap handshake, so the two waited on each other. The compiled omo and the npm launcher now start that one claim before the engine loads whenever an RPC engine's launch declares a memory-sync channel; the first session reuses it. A claim that fails still reports memory sync as unavailable and never falls back to CLI credentials. (#12702) (#12704)

Internal (tests only): macOS trust acquisition reads /etc/ssl/cert.pem through the already-injectable bundle reader, and a test now proves that a malformed default file yields the structured openssl-default-file-malformed drop entry (file, cause, block index, narrowing). (#12633)

Internal (tests only): the OpenSSL default-file importer tests now pin that any high byte on a BEGIN line, not only a BOM, drops the whole file. (#12632)

Internal (release tooling): the omo-native trust mutation harness counts a mutant as killed only when a named test fails by an assertion; a mutant that only throws a runtime error or crashes on load is now reported as crashed and fails the run. (#12631)

Fixed

  • Memory sync no longer loses an edit when two devices change the same line of a memory file at the same time. Devices on this version keep both edits as whole lines, and every device converges. Before, the edits were merged character by character into text that matched neither (#12279).
    • Between devices on this version, an edit does not disturb a line nobody edited. The exception is a very large rewrite: when one device adds and removes more than about 2,000 lines of a note in one save, that save is merged character by character, as before this fix, so a concurrent edit to the same line can still splice.
    • When the note's body or the new text does not end with a newline, the edit is still merged character by character, as before, so two concurrent edits to that last line can still splice.
    • With a device that still runs an older version, its old character merge can still go wrong in these ways:
      • Adjacent lines can fuse. The older device rewrites the line right after a line this version edited. Depending on the two devices' internal ids, the two edits can fuse into one line followed by an empty line. Measured: from head, one, two, tail, this version writes ONE and the older device writes TWO, and the result can be head, TWOONE, an empty line, tail. Two older devices give head, ONE, TWO, tail.
      • Leftover text moves. The older device edits a line this version deletes. Its leftover text joins a neighbouring line.
      • Its own diff touches other lines. The older device's character merge crosses into a line its user did not edit. This also happens between two older devices.
    • Two older devices keep their old character merge until they update. (#12597)
  • Memory sync: the push phase of a large memory set no longer needs memory in proportion to the whole set. Every push step used to re-read and re-write one journal file holding every pending item's data, several times per batch. A device pushing a few thousand memory files therefore peaked at 2 GiB or more (#12286). The journal now keeps a small index of pending items with their data in separate files, and a push reads only the batch it is sending. Capturing the set before the push still holds each captured file's text until the capture ends. A journal written by an older build is converted the first time it is read, including one where an older build added items next to the new index. (#12597)
  • Memory sync: a device receiving a large memory set no longer slows down with every file it lands. The render step used to re-read every render record of the cycle for each file, so the first pull of a few thousand memory files took tens of minutes (#12285). Each file now costs the same, and the crash-resume behavior is unchanged. (#12597)
  • Memory git no longer takes core.hooksPath, core.fsmonitor, include.path or includeIf.*.path from an inherited GIT_CONFIG_COUNT pair or GIT_CONFIG_PARAMETERS entry, so an exported pair such as core.hooksPath=/dev/null can no longer silently skip the memory repository's hooks and mirror push. Every other injected pair (url.*.insteadOf, http.extraHeader, credentials, safe.directory, ...) still applies, renumbered; an injected list git itself cannot parse is dropped whole. Memory git also no longer inherits repository redirection (GIT_DIR, GIT_WORK_TREE, GIT_COMMON_DIR, GIT_OBJECT_DIRECTORY, GIT_NAMESPACE, GIT_CONFIG, ...), so it can no longer be pointed at another repository; GIT_INDEX_FILE, GIT_CONFIG_GLOBAL and GIT_CONFIG_NOSYSTEM are kept. (#12360, fixes #12354) (#12597)
  • Memory sync no longer stops every push from a device when one memory file's change is larger than the 8 MiB batch limit: that file is held back and named in the sync status with what to do, every other memory keeps syncing, and the file syncs on its own once it fits. A change another device makes to a held file is kept and lands in this device's copy once the file fits, and a change an older build had already queued for such a file is recovered the same way instead of staying stuck. The TUI footer shows sync held and the notice says the file is being held back, and a refused entry that pauses sync is never hidden behind a held file. (#12284) (#12597)
  • Opening a memory repository starts up to six fewer git processes: the local config defaults are read with one git config --list instead of one git config --get per key, and the line-ending repair is skipped while the repository tracks nothing. Every session that opens memory pays this, and on a loaded machine each git process costs hundreds of milliseconds. memory-core's own tests now run under the canonical 20 s test budget instead of per-file 5-15 s limits, which made them fail only on busy hosts. (#12104, fixes #12103) (#12597)
  • thread_send no longer reports a message as queued when nothing will ever pick it up. When the target thread's session has no running drain, the send now answers queued_offline: the message is kept and the session takes it the next time it runs, so a caller knows no turn started and can act instead of waiting. The drain also reports a message it is holding behind the user's unsent draft, so a live drain is never mistaken for a missing one. (#12488, fixes #12486)
  • Verify recursive removal (sync and async) actually removed its path, retry bounded silent leftovers, and join sweep-test removers before deleting their fixture parents. (#11834)

Added

  • Windows releases now carry omo-git-job-helper.exe, a small native helper that runs each memory git command inside its own kill-on-close job object, so a later writer can prove that a killed writer's git is gone before it reclaims a stranded lock. Nothing uses the helper yet: memory-core keeps today's Windows behavior until a follow-up wires it in, and no release claims the new protocol until its in-flight-creation stress row has passed on Windows CI. (#12105, part of #10391) (#12597)
