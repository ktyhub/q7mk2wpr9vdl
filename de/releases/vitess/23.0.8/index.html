#vitess v23.0.8

Veröffentlichung von Vitess v23.0.8

Zusammenfassung

Nicht unterstützte sql_mode-Werte werden abgelehnt

VTGate

VTGate hat bereits SET sql_mode = ...-Anweisungen abgelehnt, die einen Modus aktivieren, den der Vitess-Parser nicht unterstützt (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). Die Prüfung verglich Modusnamen im Text und konnte umgangen werden. VTGate implementiert jetzt die sql_mode-Zuweisungssemantik von MySQL 8.x und validiert jede Zuweisung anhand dieser:

  • Das Setzen eines nicht unterstützten Modus wird auch dann abgelehnt, wenn der zugrunde liegende MySQL bereits in diesem Modus läuft, d. h. wenn der SET den Wert nicht ändern würde. Solche Anweisungen waren zuvor erfolgreich, auch wenn VTGate in diesen Modi keine Abfragen analysiert. Der Kombinationsmodus ANSI wird ebenfalls abgelehnt, da er ANSI_QUOTES, PIPES_AS_CONCAT und REAL_AS_FLOAT ermöglicht.
  • IGNORE_SPACE und HIGH_NOT_PRECEDENCE werden nun ebenfalls abgelehnt. Dies sind die beiden verbleibenden Modi, die die Interpretation von SQL-Text ändern. Der Vitess-Parser berücksichtigt sie nicht, daher würde VTGate Abfragen anders analysieren, als es der sql_mode der Sitzung verspricht. – Unbekannte Modusnamen und ungültige numerische Werte schlagen mit den eigenen Fehlern von MySQL fehl: ER_WRONG_VALUE_FOR_VAR (1231) und ER_UNSUPPORTED_SQL_MODE (3899) für die in MySQL 8.0 entfernten Modusbits. – Numerische Werte werden anhand der sql_mode-Bitmaske von MySQL dekodiert. Beispielsweise meldet SET sql_mode = 1048576, dass NO_BACKSLASH_ESCAPES nicht unterstützt wird. Gültige numerische Werte werden akzeptiert. – Konstante Werte werden zum Planungszeitpunkt ohne Shard-Roundtrip validiert. Dies umfasst konstante Ausdrücke wie CONCAT über Literalen und gilt auch, wenn --enable-system-settings deaktiviert ist. Nichtkonstante Ausdrücke werden zur Ausführungszeit validiert, sobald ihr Wert bekannt ist.

VTTablet

VTTablet wendet dieselbe Validierung an seinen eigenen Einstiegspunkten an und gibt dieselben Fehler zurück: Verbindungseinstellungen, für den Einstellungspool und für reservierte Verbindungen sowie SET sql_mode-Anweisungen für den Sitzungsbereich. Dies umfasst clients, die die VTGate-Validierung umgehen, wie z. B. VTGates, die noch nicht aktualisiert wurden, und clients, die direkt mit dem Abfragedienst kommunizieren. SET_VAR-Optimiererhinweise werden unverändert an MySQL weitergeleitet. Jede MySQL-Verbindung, die Vitess erstellt, entfernt jetzt die Modi, die die Interpretation von SQL-Text aus der Sitzung ändern. sql_mode erbt es vom globalen Wert des Servers. Alle anderen Modi, wie z. B. die strikten Modi und die Zero-Date-Modi, bleiben erhalten. Dies gilt für jede Komponente: Abfragebereitstellung, Schemaverfolgung, Heartbeats, Replikationsverwaltung, Online-DDL, VReplication und VDiff sowie Verbindungen zu externen MySQL-Servern. Der globale sql_mode wird nicht verändert.

Auswirkungen

– Clients, die SET sql_mode in einem nicht unterstützten Modus ausführen, einschließlich ANSI, IGNORE_SPACE und HIGH_NOT_PRECEDENCE, erhalten jetzt eine Fehlermeldung. Dies geschieht auch, wenn der SET mit dem aktuellen sql_mode des Backends übereinstimmt. Clients, die Modusnamen MySQL festlegen, würden ihrerseits ebenfalls einen Fehler ablehnen. – Bei einem fortlaufenden Upgrade werden VTTablets normalerweise vor VTGates aktualisiert. Eine Sitzung, die ein jetzt abgelehntes sql_mode über ein VTGate festlegt, das noch nicht aktualisiert wurde, beginnt, Fehler von aktualisierten VTTablets zu empfangen. – Ein Backend, dessen globales sql_mode einen dieser Modi enthält, behält ihn, aber Vitess-Sitzungen erben ihn nicht mehr. Weitere Informationen finden Sie unter #20883.

Tabellen-ACL: Aufrufer mit jeder Rolle für jede Tabelle können Anweisungen ausführen, deren Tabellen nicht ermittelt werden können

v23.0.7 begann, unter strenger Tabellen-ACL (--queryserver-config-strict-table-acl) Anweisungen abzulehnen, deren Tabellen vttablet nicht ermitteln kann (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA und ein CREATE TABLE, das der Parser von vttablet nicht vollständig analysieren kann) für jeden Aufrufer außerhalb der ausgenommenen ACL (--queryserver-config-acl-exempt-acl); siehe GHSA-w6mx-2f8x-pqf4. Ein Aufrufer, der ein Leser, ein Autor und ein Administrator in einer Tabellengruppe ist, die jede Tabelle abdeckt ("table_names_or_prefixes": ["%"]), hat jede Rolle in jeder Tabelle inne, die eine solche Anweisung berühren könnte, sodass jetzt DO, REPAIR, OPTIMIZE und ein teilweise geparstes CREATE TABLE dafür ausgeführt werden. CALL und LOAD DATA bleiben selbst dann verweigert, da eine SQL SECURITY DEFINER-Prozedur mit den Privilegien ihres Definierers ausgeführt wird und LOAD DATA INFILE Dateien auf dem Server liest, was keine der Tabellen-ACLs gewährt; Geben Sie sie als Anrufer in der ausgenommenen ACL aus. Diese Prüfungen werden unter der Bezeichnung undetermined-table-set TableName, in TableACLDenied oder in TableACLAllowed für einen Anrufer mit jeder Rolle in jeder Tabelle gezählt. Beim Probelauf (--queryserver-config-enable-table-acl-dry-run) erhöhen sich nur die Anweisungen, die die Prüfung verweigern würde, um TableACLPseudoDenied. Weitere Informationen finden Sie unter #21349.

Verbindungszeichensätze eingeschränkt

--db-charset und die anderen Orte, an denen ein MySQL-Verbindungszeichensatz konfiguriert ist, akzeptieren sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le oder utf32 nicht mehr, unabhängig davon, ob sie als Zeichensatz oder als eine seiner Sortierungen angegeben werden. Ein mit einem von ihnen konfiguriertes Tablet startet nicht, VTGate lehnt einen SET von character_set_client, character_set_connection, character_set_results oder collation_connection für einen von ihnen ab, oder für einen Namen, der kein Zeichensatz oder eine Kollation ist, den es mit „OK“ und „Ignorieren“ beantwortet hat, und VTTablet lehnt eine Einstellung oder SET-Anweisung ab, die die Verbindung einer Sitzung zu einem von ihnen umschalten würde. Ein client kann beim Handshake immer noch nach einem davon fragen: VTGate liest seine Anweisungen Byte für Byte, wie es die Verbindung des Tablets zu MySQL tut, sodass sie nicht aus einem Literal ausbrechen können. Vitess analysiert und maskiert SQL-Text Byte für Byte, und in diesen Zeichensätzen kann das zweite Byte eines Zeichens ein Backslash oder ein umgekehrtes Anführungszeichen sein, sodass der darin enthaltene Text auf seinem Weg durch Vitess falsch geparst oder beschädigt wurde. Verwenden Sie stattdessen utf8mb4 als Verbindungszeichensatz. Tabellen und Spalten können weiterhin mit jedem dieser Zeichensätze deklariert werden; MySQL konvertiert zwischen ihnen und dem Verbindungszeichensatz. Dies behebt GHSA-c28j-qmfx-4gxp. Weitere Informationen finden Sie unter #21392 und #21465.

Zeichensatz- und Kollatierungsnamen werden bei der Neugenerierung in Anführungszeichen gesetzt

Der Name eines Zeichensatzes, einer Sortierung, einer Engine, eines Tabellenbereichs oder eines Volltext-Parsers wird jetzt beim Parsen dekodiert und als einzelnes Token zurückgeschrieben, wenn Vitess die Anweisung neu generiert: bare, wenn es sich um einen bekannten Zeichensatz, eine Sortierung, eine Engine, einen bekannten Indextyp oder einen Parser-Namen handelt, andernfalls in umgekehrten Anführungszeichen. Für den Benutzer sichtbare Konsequenzen:

  • Ein Name in Anführungszeichen wird normalisiert. COLLATE 'utf8_bin' wird als COLLATE utf8_bin neu generiert – die Schreibweise in Anführungszeichen und ohne Anführungszeichen bedeuten denselben Namen und die dekodierte Form wird gespeichert. Wer die gedruckte Form dieser Anweisungen Byte für Byte vergleicht, erkennt die neue Schreibweise.
  • Nur bekannte Namen bleiben leer. Ein Zeichensatz- oder Sortiernamen einer beliebigen MySQL- oder MariaDB-Version, eine bekannte Speicher-Engine wie InnoDB oder memory, die Indextypen BTREE, HASH und RTREE, die Parser ngram und mecab sowie die Tablespaces innodb_system und innodb_file_per_table werden zurückgeschrieben als sie wurden buchstabiert. Jeder andere Name wird in Anführungszeichen gesetzt: TABLESPACE ts wird neu generiert als „TABLESPACE ts``, and so does an engine Vitess does not know or a keyword used as a name.WITH PARSERaccepts only a plain identifier, so a known name that is a keyword is quoted there: ``WITH PARSERmemory`` keeps its quoting whereENGINE Memorydoes not.binaryis still bare where the grammar has aBINARYalternative, except directly before theBINARYattribute:CHARACTER SET 'binary‘ BINARYregenerates as ``CHARACTER SETbinary` BINARY``.
  • COLLATE binary in einem Ausdruck wird in Anführungszeichen gesetzt. expr COLLATE binary wird neu generiert als „expr COLLATE binary``, because MySQL's expressionCOLLATEonly acceptsbinaryquoted. Column, table and databaseCOLLATE BinaryandCHARACTER SET Binär“ bleibt leer.
  • Ein leerer Zeichensatz, eine leere Sortierung, eine leere Engine oder ein leerer Partitionstabellenbereichsname wird abgelehnt. CHARACTER SET '' und COLLATE '' für eine Spalte, eine Tabelle, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE und einen Ausdruck, ENGINE '' für eine Tabelle oder eine Partition und eine Partition TABLESPACE '' analysiert nicht mehr. Ein leerer Name an diesen Positionen ist nicht vom Fehlen der Klausel zu unterscheiden, daher wäre er zuvor weggelassen oder verstümmelt worden und eine von MySQL abgelehnte Aussage hätte zu einer gültigen, anderen Aussage werden können. Nicht-DDL-Anweisungen erhalten den Fehler direkt; DDL greift auf eine teilweise Analyse zurück, sodass der eigene Text des client weitergeleitet und von MySQL abgelehnt wird. SET NAMES ... COLLATE '' und SET CHARACTER SET ... COLLATE '', die früher zum Parsen und Verwerfen der Sortierung dienten, sind jetzt ebenfalls Parse-Fehler; MySQL lehnt beides ab. CREATE/ALTER DATABASE ... CHARACTER SET '' und COLLATE '' bleiben unverändert: Sie werden weiterhin analysiert und als '' zurückgeschrieben.
  • ENCRYPTION erfordert einen Wert in Anführungszeichen. CREATE/ALTER DATABASE ... ENCRYPTION N wird nicht mehr vollständig analysiert und entspricht MySQL, das nur 'Y' oder 'N' als Zeichenfolge in Anführungszeichen akzeptiert. Eine solche Anweisung greift nun auf eine teilweise Analyse zurück, anstatt in eine Schreibweise regeneriert zu werden, die MySQL ablehnen würde. Dies behebt GHSA-j8pc-mcwq-qrg6. Weitere Informationen finden Sie unter #21435.

VTAdmin VExplain-Modi, die die Anweisung ausführen, erfordern die Aktion execute

VTAdmins VExplain API wurde mit der Aktion get autorisiert, aber VEXPLAIN QUERIES, ALL und TRACE führen die Anweisung aus, die sie erklären, sodass ein Akteur, der nur zum Lesen berechtigt ist, Daten dadurch ändern könnte (GHSA-c2r8-grjp-w8c2). Diese Modi erfordern jetzt die neue Aktion execute für die Ressource VExplain; PLAN und KEYS, die nur die Anweisung planen, benötigen weiterhin nur get. Für diese Modi akzeptiert VTAdmin auch nur einen SELECT ohne INTO, Sequenz-Nächstwerte oder beratende Sperrfunktionen und führt sie in einer schreibgeschützten Transaktion aus, die immer zurückgesetzt wird. Die VExplain-Seite in der Web-Benutzeroberfläche ist jetzt standardmäßig PLAN. Migration: Gewähren Sie die Aktion execute auf VExplain den Akteuren, die VEXPLAIN QUERIES, ALL oder TRACE ausführen sollen. Regeln, die alle Aktionen (*) und --no-rbac gewähren, enthalten dies bereits. Auswirkung: Ein Akteur mit nur get auf VExplain erhält einen unauthorized-Fehler von VEXPLAIN QUERIES, ALL und TRACE. Weitere Informationen finden Sie unter #21396.

vitess v23.0.8

Release of Vitess v23.0.8

Summary

Unsupported sql_mode values are rejected

VTGate

VTGate already rejected SET sql_mode = ... statements that enable a mode the Vitess parser does not support (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). The check compared mode names textually and could be bypassed. VTGate now implements MySQL 8.x's sql_mode assignment semantics and validates every assignment against them:

  • Setting an unsupported mode is rejected even when the underlying MySQL already runs with that mode, that is, when the SET would not change the value. Such statements previously succeeded, even though VTGate does not parse queries under these modes. The combination mode ANSI is rejected as well, because it enables ANSI_QUOTES, PIPES_AS_CONCAT, and REAL_AS_FLOAT.
  • IGNORE_SPACE and HIGH_NOT_PRECEDENCE are now also rejected. They are the two remaining modes that change how SQL text is interpreted. The Vitess parser does not honor them, so VTGate would parse queries differently than the session's sql_mode promises.
  • Unknown mode names and invalid numeric values fail with MySQL's own errors: ER_WRONG_VALUE_FOR_VAR (1231), and ER_UNSUPPORTED_SQL_MODE (3899) for the bits of modes removed in MySQL 8.0.
  • Numeric values decode against MySQL's sql_mode bitmask. For example, SET sql_mode = 1048576 reports that NO_BACKSLASH_ESCAPES is unsupported. Valid numeric values are accepted.
  • Constant values are validated at planning time, with no shard round trip. This includes constant expressions such as CONCAT over literals, and it also applies when --enable-system-settings is disabled. Non-constant expressions are validated at execution time, once their value is known.

VTTablet

VTTablet applies the same validation at its own entry points and returns the same errors: connection settings, on the settings pool and on reserved connections, and session-scope SET sql_mode statements. This covers clients that bypass VTGate's validation, such as VTGates that are not upgraded yet and clients that talk to the query service directly. SET_VAR optimizer hints are forwarded to MySQL unchanged.

Every MySQL connection Vitess creates now strips the modes that change how SQL text is interpreted from the session sql_mode it inherits from the server's global value. All other modes, such as the strict modes and the zero-date modes, are kept. This applies to every component: query serving, schema tracking, heartbeats, replication management, Online DDL, VReplication and VDiff, and connections to external MySQL servers. The global sql_mode is not changed.

Impact

  • Clients that run SET sql_mode with an unsupported mode, including ANSI, IGNORE_SPACE and HIGH_NOT_PRECEDENCE, now receive an error. This also happens when the SET matches the backend's current sql_mode. Clients that set mode names MySQL would itself reject receive an error as well.
  • During a rolling upgrade, VTTablets are typically upgraded before VTGates. A session that sets a now-rejected sql_mode through a VTGate that is not upgraded yet starts receiving errors from upgraded VTTablets.
  • A backend whose global sql_mode includes one of these modes keeps it, but Vitess sessions no longer inherit it.

See #20883 for details.

Table ACL: callers with every role on every table may run statements whose tables cannot be determined

v23.0.7 began denying, under strict table ACL (--queryserver-config-strict-table-acl), statements whose tables vttablet cannot determine (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA, and a CREATE TABLE that vttablet's parser cannot fully parse) for every caller outside the exempt ACL (--queryserver-config-acl-exempt-acl); see GHSA-w6mx-2f8x-pqf4. A caller that is a reader, a writer and an admin in a table group covering every table ("table_names_or_prefixes": ["%"]) holds every role on any table such a statement could touch, so DO, REPAIR, OPTIMIZE and a partially parsed CREATE TABLE now run for it. CALL and LOAD DATA remain denied even then, since a SQL SECURITY DEFINER procedure runs with its definer's privileges and LOAD DATA INFILE reads files on the server, neither of which table ACL grants; issue them as a caller in the exempt ACL.

These checks are counted under the undetermined-table-set TableName label, in TableACLDenied, or in TableACLAllowed for a caller with every role on every table. With dry-run (--queryserver-config-enable-table-acl-dry-run), only the statements the check would deny increment TableACLPseudoDenied.

See #21349 for details.

Connection character sets restricted

--db-charset, and the other places a MySQL connection character set is configured, no longer accept sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le or utf32, whether given as a character set or as one of its collations. A tablet configured with one of them fails to start, VTGate refuses a SET of character_set_client, character_set_connection, character_set_results or collation_connection to one of them, or to a name that is not a character set or collation, which it used to answer with OK and ignore, and VTTablet refuses a setting or SET statement that would switch a session's connection to one of them. A client may still ask for one of them at the handshake: VTGate reads its statements byte by byte, as the tablet's connection to MySQL does, so they cannot break out of a literal.

Vitess parses and escapes SQL text byte by byte, and in these character sets the second byte of a character can be a backslash or a back quote, so text in them was misparsed or corrupted on its way through Vitess. Use utf8mb4 as the connection character set instead. Tables and columns can still be declared with any of these character sets; MySQL converts between them and the connection character set.

This fixes GHSA-c28j-qmfx-4gxp.

See #21392 and #21465 for details.

Charset and collation names are quoted when regenerated

A charset, collation, engine, tablespace or full-text parser name is now decoded when parsed, and written back as a single token when Vitess regenerates the statement: bare when it is a known charset, collation, engine, index type or parser name, back-quoted otherwise.

User-visible consequences:

  • A quoted name is normalized. COLLATE 'utf8_bin' regenerates as COLLATE utf8_bin — the quoted and unquoted spellings mean the same name, and the decoded form is what is stored. Anything comparing the printed form of these statements byte for byte sees the new spelling.
  • Only known names stay bare. A charset or collation name of any MySQL or MariaDB version, a known storage engine such as InnoDB or memory, the BTREE, HASH and RTREE index types, the ngram and mecab parsers, and the innodb_system and innodb_file_per_table tablespaces are written back as they were spelled. Any other name is back-quoted: TABLESPACE ts regenerates as TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE memory does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: CHARACTER SET 'binary' BINARY regenerates as CHARACTER SET `binary` BINARY.
  • COLLATE binary in an expression is quoted. expr COLLATE binary regenerates as expr COLLATE `binary` , because MySQL's expression COLLATE only accepts binary quoted. Column, table and database COLLATE binary and CHARACTER SET binary stay bare.
  • An empty charset, collation, engine or partition tablespace name is rejected. CHARACTER SET '' and COLLATE '' on a column, a table, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE and an expression, ENGINE '' on a table or a partition, and a partition's TABLESPACE '' no longer parse. An empty name in these positions is indistinguishable from the clause being absent, so it would previously have been dropped or mangled and a statement MySQL rejects could have become a valid, different one. Non-DDL statements get the error directly; DDL falls back to a partial parse, so the client's own text is forwarded and MySQL rejects it. SET NAMES ... COLLATE '' and SET CHARACTER SET ... COLLATE '', which used to parse and discard the collation, are now parse errors too; MySQL rejects both. CREATE/ALTER DATABASE ... CHARACTER SET '' and COLLATE '' are unchanged: they still parse and are written back as ''.
  • ENCRYPTION requires a quoted value. CREATE/ALTER DATABASE ... ENCRYPTION N no longer fully parses, matching MySQL, which only accepts 'Y' or 'N' as a quoted string. Such a statement now falls back to a partial parse rather than being regenerated into a spelling MySQL would refuse.

This fixes GHSA-j8pc-mcwq-qrg6.

See #21435 for details.

VTAdmin VExplain modes that run the statement require the execute action

VTAdmin's VExplain API was authorized with the get action, but VEXPLAIN QUERIES, ALL and TRACE run the statement they explain, so an actor allowed only to read could change data through it (GHSA-c2r8-grjp-w8c2). Those modes now require the new execute action on the VExplain resource; PLAN and KEYS, which only plan the statement, still require only get. For those modes VTAdmin also accepts only a SELECT without INTO, sequence next-values or advisory lock functions, and runs them in a read-only transaction that is always rolled back. The VExplain page in the web UI now defaults to PLAN.

Migration: grant the execute action on VExplain to the actors that should run VEXPLAIN QUERIES, ALL or TRACE. Rules that grant all actions (*) and --no-rbac already include it.

Impact: an actor with only get on VExplain gets an unauthorized error from VEXPLAIN QUERIES, ALL and TRACE.

See #21396 for details.

Security fixes

  • Fixes GHSA-73pp-99vw-h5g8: SQL injection through VStream LastPK values. See #21377.
  • Fixes GHSA-92cc-q2h6-m2vr: SQL injection through convert_tz() arguments in a VStream filter. See #21377.
  • Fixes GHSA-8w3p-4xg5-rm9w: SQL injection through table names in Online DDL statements. See #21381.
  • Fixes GHSA-x56j-8c72-5xgg: SQL injection through the caller ID in query annotations (--queryserver-config-annotate-queries). See #21369.
  • Fixes GHSA-m282-7w35-g77m: SQL injection through a global SET variable name. See #21390.
  • Fixes GHSA-9248-hccp-qf8f: SQL injection through DATE, TIME and TIMESTAMP literals. See #21389.
  • Fixes GHSA-9rx3-8pwm-c228: SQL injection through a session variable value carried in a SET_VAR hint. See #21388.
  • Fixes GHSA-pfg5-ppc7-ff45: SQL hidden from parsing and table ACL checks in a trailing comment. See #21387.
  • Fixes GHSA-xf67-9r78-xv82: SQL injection through malformed numeric bind variables. See #21386.
  • Fixes GHSA-3fr2-mqr5-r5x5: VTAdmin API routes that change cluster state accepted cross-site GET requests. See #21397.
  • Fixes GHSA-78h7-x6qm-xpr8: VTAdmin's ReloadSchemaShard did not check RBAC. See #21394.
