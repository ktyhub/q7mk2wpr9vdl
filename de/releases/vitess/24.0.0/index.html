<a id="major-changes"/>Wichtige Änderungen</a>

<a id="new-support"/>Neuer Support</a>

<a id="window-function-pushdown"/>Fensterfunktions-Pushdown für Shard-Keyspaces</a>

Diese Version führt eine Optimierung ein, die es ermöglicht, Fensterfunktionen auf einzelne Shards zu verschieben, wenn diese durch eine Spalte partitioniert sind, die einem eindeutigen Vindex entspricht. Bisher erforderten alle Fensterfunktionsabfragen ein Single-Shard-Routing, was ihre Anwendbarkeit auf Shard-Tabellen einschränkte. Mit dieser Änderung können Abfragen, bei denen die PARTITION BY-Klausel mit einem eindeutigen Vindex übereinstimmt, nun nach unten verschoben und auf jedem Shard ausgeführt werden. Beispiele und weitere Details finden Sie in der Dokumentation.

<a id="view-routing-rules"/>Routing-Regeln anzeigen</a>

Vitess unterstützt jetzt Routing-Regeln für Ansichten und kann genauso wie Tabellen mit vtctldclient ApplyRoutingRules angewendet werden. Wenn eine Ansichts-Routing-Regel aktiv ist, schreibt VTGate Abfragen, die auf die Quellansicht verweisen, um, um stattdessen die Definition der Zielansicht zu verwenden. Zum Beispiel anhand dieser Routing-Regel:

{
  "rules": [
    {
      "from_table": "source_ks.my_view",
      "to_tables": ["target_ks.my_view"]
    }
  ]
}

Und diese Ansichtsdefinition:

CREATE VIEW target_ks.my_view AS SELECT id, name FROM user;

Eine Abfrage wie SELECT * FROM source_ks.my_view würde intern wie folgt umgeschrieben werden:

SELECT * FROM (SELECT id, name FROM target_ks.user) AS my_view;

Ansichtsroutingregeln erfordern, dass der Schema-Tracker Ansichten überwacht. Dies bedeutet, dass VTGate mit dem Flag --enable-views und VTTablet mit dem Flag --queryserver-enable-views gestartet werden muss. Die Zielansicht muss im angegebenen Schlüsselraum vorhanden sein, damit die Routing-Regel ordnungsgemäß funktioniert. Weitere Einzelheiten finden Sie in der Dokumentation zu Schema-Routing-Regeln.

<a id="tablet-targeting"/>Tablet-Targeting über USE-Anweisung</a>

VTGate unterstützt jetzt das Weiterleiten von Abfragen an ein bestimmtes Tablet per Alias mithilfe einer erweiterten USE-Anweisungssyntax:

USE keyspace:shard@tablet_type|tablet_alias;

So zielen Sie beispielsweise auf ein bestimmtes Replikat-Tablet ab:

USE commerce:-80@replica|zone1-0000000100;

Nach der Festlegung werden alle nachfolgenden Abfragen in der Sitzung an das angegebene Tablet weitergeleitet, bis sie mit einer Standardanweisung USE keyspace oder USE keyspace@tablet_type gelöscht werden. Dies ist nützlich für das Debuggen, die Überwachung pro Tablet, das Aufwärmen des Caches und andere betriebliche Aufgaben, bei denen die Ausrichtung auf ein bestimmtes Tablet erforderlich ist. Hinweis: Bei der Verwendung von Tablet-Targeting muss ein Shard angegeben werden. Wie beim Shard-Targeting wird hierdurch das Vindex-basierte Routing umgangen. Gehen Sie daher mit Vorsicht vor.

<a id="vtgate-binlog-dump"/>Binlog-Streaming-Unterstützung</a>

VTGate unterstützt jetzt GTID-basiertes Binlog-Streaming über zwei Protokolle:

  • MySQL-Protokoll: Clients können eine Verbindung mit dem standardmäßigen Replikationsprotokollbefehl MySQL COM_BINLOG_DUMP_GTID herstellen – es sind keine speziellen VStream-fähigen Adapter oder direkter MySQL-Zugriff erforderlich.
  • gRPC: Der neue BinlogDumpGTID-Streaming-RPC in vtgateservice bietet nativen gRPC-Zugriff für benutzerdefinierte clients ohne die MySQL-Protokollabhängigkeit. Hinweis: Es wird nur GTID-basiertes Streaming unterstützt. Datei-/positionsbasiertes Streaming ist weder über COM_BINLOG_DUMP noch über COM_BINLOG_DUMP_GTID verfügbar und gibt einen Fehler zurück. Diese Funktion ist standardmäßig deaktiviert. Aktivieren Sie es mit --enable-binlog-dump. Neue Flaggen:
  • --enable-binlog-dump: Aktiviert die Binlog-Dump-Unterstützung. Ohne dieses Flag geben Binlog-Dump-Anfragen einen Fehler zurück.
  • --binlog-dump-authorized-users: Durch Kommas getrennte Liste der Benutzer, die berechtigt sind, Binlog-Dump-Vorgänge auszuführen, oder %, um alle Benutzer zuzulassen. Anforderungen: Beim Initiieren einer Binlog-Dump-Verbindung muss clients Folgendes angeben: – Ein leerer Dateiname
  • Eine Dateiposition (filepos) von 4
  • Eine GTID-Position Geben Sie für gRPC clients den Schlüsselraum, den Shard und optional den Tablet-Typ oder Tablet-Alias direkt im BinlogDumpGTIDRequest an. Einschränkungen: – Jeder Stream läuft auf einem einzigen Tablet – keine Datenaggregation über Shards hinweg.
  • Kein automatisches Failover – wenn das Ziel-Tablet nicht verfügbar ist, schlägt der Stream fehl und der client muss sich erneut mit einem anderen Tablet verbinden.
  • Nicht kompatibel mit MoveTables- oder Reshard-Vorgängen. Verwenden Sie für diese Anwendungsfälle den VStream API.

<a id="structured-logging"/>Strukturierte Protokollierung</a>

Vitess verwendet jetzt standardmäßig die strukturierte JSON-Protokollierung. Die Protokollausgabe wird als JSON an stderr ausgegeben. Um die Mindestprotokollstufe zu konfigurieren, übergeben Sie --log-level (eines von debug, info, warn, error; Standard info). Übergeben Sie --log-format=text, um ein für Menschen lesbares Format mit automatischer Farberkennung zu erhalten. Um zum vorherigen glog-Backend zurückzukehren, übergeben Sie --log-structured=false. glog ist ab Version 24 veraltet und wird in Version 25 entfernt.

<a id="breaking-changes"/>Breaking Changes</a>

<a id="vttablet-external-decompressor-manifest"/>Externer Dekompressor wird standardmäßig nicht mehr aus dem Backup-MANIFEST gelesen</a>

Der in der MANIFEST-Datei eines Backups gespeicherte externe Dekomprimierungsbefehl wird standardmäßig nicht mehr zum Zeitpunkt der Wiederherstellung verwendet. Wenn zuvor kein --external-decompressor-Flag bereitgestellt wurde, greift VTTablet auf den im MANIFEST angegebenen Befehl zurück. Dies stellte ein Sicherheitsrisiko dar: Ein Angreifer mit Schreibzugriff auf den Backup-Speicher könnte den MANIFEST so modifizieren, dass er beliebige Befehle auf dem Tablet ausführt. Ab v24 wird der MANIFEST-basierte Dekomprimierer ignoriert, es sei denn, Sie aktivieren die neue --external-decompressor-use-manifest-Flagge ausdrücklich. Wenn Sie sich auf dieses Verhalten verlassen, fügen Sie das Flag zu Ihrer VTTablet-Konfiguration hinzu, beachten Sie jedoch die Auswirkungen auf die Sicherheit. Weitere Informationen finden Sie unter #19460.

<a id="minor-changes"/>Kleinere Änderungen</a>

<a id="minor-changes-vreplication"/>VReplication</a>

<a id="vreplication-shards-flag-start-stop"/>--shards-Flag für den Start und Stopp von MoveTables/Reshard</a>

Die Befehle start und stop für MoveTables- und Reshard-Workflows unterstützen jetzt das Flag --shards, sodass Benutzer Workflows auf einer bestimmten Teilmenge von Shards statt auf allen Shards gleichzeitig starten oder stoppen können. Beispielverwendung:

# Start workflow on specific shards only
vtctldclient MoveTables --target-keyspace customer --workflow commerce2customer start --shards="-80,80-"

# Stop workflow on specific shards only
vtctldclient Reshard --target-keyspace customer --workflow cust2cust stop --shards="80-"

<a id="vreplication-tablet-error-retry"/>Automatischer Tablet-Wiederholungsversuch für Tablet-spezifische Fehler</a>

VReplication-Workflows wiederholen den Vorgang jetzt automatisch mit anderen Tablets, wenn Tablet-spezifische Fehler auftreten. Bisher verwendeten Arbeitsabläufe ohne Zellpräferenz standardmäßig die lokale Zelle und konnten auf unbestimmte Zeit beim erneuten Versuch desselben fehlerhaften Tablets stecken bleiben. Wenn bei einem Tablet Fehler wie das Löschen des Binärprotokolls (MySQL-Fehler 1236 oder 1789) oder nicht übereinstimmende GTID-Sets auftreten, fügt VReplication dieses Tablet einer Ignorierliste hinzu und versucht es mit anderen Tablets in allen Zellen. Sobald alle passenden Tablets ausprobiert wurden, wird die Ignorierliste gelöscht und der Workflow beginnt von vorne. Dies ist besonders nützlich bei Bereitstellungen mit mehreren Zellen, bei denen einem Tablet in der lokalen Zelle möglicherweise die erforderlichen Binärprotokolle fehlen, Tablets in anderen Zellen jedoch weiterhin über diese verfügen.

<a id="minor-changes-vtgate"/>VTGate</a>

<a id="vtgate-removed-grpc-send-session-in-streaming"/>Flag --grpc-send-session-in-streaming entfernt</a>

Das VTGate-Flag --grpc-send-session-in-streaming wurde entfernt. Dieses Flag wurde in Version 22 über #17907 veraltet und standardmäßig auf true gesetzt. Die Sitzung wird jetzt immer als letztes Paket in der Streaming-Antwort für StreamExecute- und StreamExecuteMulti-RPCs gesendet. Dieses Verhalten ist zur Unterstützung von Transaktionen beim Streaming erforderlich und kann nicht deaktiviert werden. Auswirkung: Entfernen Sie jegliche Verwendung des --grpc-send-session-in-streaming-Flags aus VTGate-Startskripts oder -Konfiguration.

<a id="vtgate-new-default-legacy-replication-lag-algorithm"/>Neuer Standard für das --legacy-replication-lag-algorithm-Flag</a>

Das VTGate-Flag --legacy-replication-lag-algorithm ist jetzt standardmäßig auf false eingestellt, wodurch der alte Ansatz zur Behandlung von Replikationsverzögerungen standardmäßig deaktiviert wird. Stattdessen wird ein einfacherer Algorithmus verwendet, der ausschließlich auf geringer Verzögerung, hoher Verzögerung und minimaler Anzahl an Tablets basiert und sich in vielen Produktionsumgebungen als stabiler erwiesen hat. Eine ausführliche Erläuterung der beiden Ansätze wird in diesem Codekommentar erläutert. In Version 25 wird dieses Flag veraltet sein und in der folgenden Version entfernt. In der Zwischenzeit kann das Legacy-Verhalten durch die Einstellung --legacy-replication-lag-algorithm=true verwendet werden. Diese Einstellung wird in https://github.com/vitessio/vitess/issues/18914. verfolgt

<a id="vtgate-session-balancer-mode"/>Neuer „Sitzungs“-Modus für das --vtgate-balancer-mode-Flag</a>

Das VTGate-Flag --vtgate-balancer-mode unterstützt jetzt zusätzlich zu den bestehenden Modi „Cell“, „Prefer-Cell“ und „Random“ einen neuen „Session“-Modus. Der Sitzungsmodus leitet jede Sitzung für die Dauer der Sitzung konsistent an dasselbe Tablet weiter. Um den Sitzungsmodus zu aktivieren, setzen Sie beim Starten von VTGate das Flag:

--vtgate-balancer-mode=session

<a id="minor-changes-query-serving"/>Abfragebereitstellung</a>

<a id="query-serving-json-extract-dynamic-args"/>JSON_EXTRACT unterstützt jetzt dynamische Pfadargumente</a>

Die Funktion JSON_EXTRACT unterstützt jetzt dynamische Pfadargumente wie Bindevariablen oder Ergebnisse anderer Funktionsaufrufe. Bisher funktionierte JSON_EXTRACT nur mit statischen String-Literalen für Pfadargumente. Die NULL-Behandlung entspricht jetzt dem Verhalten von MySQL. Die Funktion gibt NULL zurück, wenn entweder das Dokument- oder das Pfadargument NULL ist. Statische Pfadargumente werden weiterhin optimiert, auch wenn sie mit dynamischen Argumenten gemischt werden, sodass bei vorhandenen Abfragen keine Leistungseinbußen auftreten.

<a id="minor-changes-vttablet"/>VTTablet</a>

<a id="vttablet-init-tablet-type-lookup"/>Neue experimentelle Flagge --init-tablet-type-lookup</a>

Mit dem neuen experimentellen Flag --init-tablet-type-lookup für VTTablet können Tablets beim Neustart automatisch ihren vorherigen Tablet-Typ wiederherstellen, indem sie den vorhandenen Topologiedatensatz nachschlagen, anstatt immer den statischen --init-tablet-type-Wert zu verwenden. Wenn diese Option aktiviert ist, verwendet das Tablet beim Neustart seinen Alias, um den Tablet-Typ im vorhandenen Topologiedatensatz zu suchen. Dadurch können Tablets ihre geänderten Rollen (z. B. RDONLY/DRAINED) über Neustarts hinweg beibehalten, ohne dass eine manuelle Neukonfiguration erforderlich ist. Wenn die Option deaktiviert ist oder kein Topologiedatensatz vorhanden ist, wird stattdessen der Standardwert --init-tablet-type verwendet. Hinweis: Vom Betreiber verwaltete Vitess-Bereitstellungen behalten im Allgemeinen keine übereinstimmenden Tablet-Datensätze im Topo bei Pod-Ersetzungen bei, sodass diese Funktion in diesen Umgebungen nur eine begrenzte Wirkung hat.

<a id="vttablet-querythrottler-metrics"/>QueryThrottler-Beobachtbarkeitsmetriken</a>

VTTablet stellt jetzt neue Metriken zur Verfügung, um das Verhalten von QueryThrottler zu verfolgen. Vier neue Metriken wurden hinzugefügt: – QueryThrottlerRequests: Gesamtzahl der vom Abfragedrossel ausgewerteten Anfragen – QueryThrottlerThrottled: Anzahl der Anfragen, die gedrosselt wurden – QueryThrottlerTotalLatencyNs: Gesamtzeit, die jede Anfrage für die Abfragedrosselung benötigt, einschließlich Auswertung, Metrikprüfungen und anderem Overhead (in Nanosekunden) – QueryThrottlerEvaluateLatencyNs: Zeit, die benötigt wird, um die Drosselungsentscheidung zu treffen (in Nanosekunden) Alle Metriken umfassen Bezeichnungen für Strategy, Workload und Priority. Die Metrik QueryThrottlerThrottled verfügt über zusätzliche Bezeichnungen für MetricName, MetricValue und DryRun, um zu identifizieren, welche Metrik die Drosselung ausgelöst hat und ob sie im Probelaufmodus aufgetreten ist. Mithilfe dieser Metriken können Sie Drosselungsmuster überwachen, ermitteln, welche Arbeitslasten gedrosselt werden, den Leistungsaufwand messen und das Verhalten im Probelaufmodus vor Konfigurationsänderungen validieren.

<a id="vttablet-querythrottler-config-watch"/>Ereignisgesteuerte Konfigurationsaktualisierungen von QueryThrottler</a>

Die QueryThrottler-Konfiguration wird jetzt an den SrvKeyspace-Datensatz im Topologieserver weitergegeben und dort gespeichert und mit Standard-Topologietools verwaltet. Bisher wurden bei Tablets alle 60 Sekunden Konfigurationsänderungen abgefragt. Tablets verwenden jetzt ereignisgesteuerte Überwachungen (WatchSrvKeyspace), um Updates sofort zu erhalten, wenn sich die Konfiguration der Abfragedrosselung ändert. Alle Tablets in einem Schlüsselraum sehen Konfigurationsänderungen ungefähr zur gleichen Zeit, und Topologieserveränderungen sind versioniert und überprüfbar. Diese Änderung ersetzt den vorherigen dateibasierten Konfigurationslader durch eine protobuf-definierte Konfigurationsstruktur, die in der Topologie gespeichert ist. Die neue Konfiguration umfasst Felder zum Aktivieren/Deaktivieren der Drosselung, zur Auswahl der Drosselungsstrategie und zum Konfigurieren strategiespezifischer Regeln.

<a id="vttablet-conn-pool-waiter-cap"/>Tablet Connection Pool Waiter Cap</a>

Mit VTTablet können Benutzer jetzt ein Limit für die Anzahl der Anfragen festlegen, die auf eine Verbindung aus dem Verbindungspool warten, z die Abfrage-, Stream- und Transaktionsverbindungspools. Die Grenzwerte werden mit den folgenden Flags festgelegt:

  • --queryserver-config-query-pool-waiter-cap
  • --queryserver-config-stream-pool-waiter-cap
  • --queryserver-config-txpool-waiter-cap Alle oben genannten haben den Standardwert 0, d. h. keine Begrenzung, wodurch das Verhalten der vorherigen Version beibehalten wird.

<a id="minor-changes-tracing"/>Ablaufverfolgung</a>

<a id="tracing-opentelemetry"/>OpenTelemetry Tracing-Unterstützung</a>

Vitess unterstützt jetzt OpenTelemetry als Tracing-Backend. Um es zu verwenden, legen Sie --tracer opentelemetry für eine beliebige Vitess-Binärdatei fest. Traces werden über OTLP/gRPC exportiert, konfigurierbar mit den folgenden Flags: – --otel-endpoint: OpenTelemetry Collector-Endpunkt. Wenn leer, wird die Umgebungsvariable OTEL_EXPORTER_OTLP_ENDPOINT verwendet; Wenn dies ebenfalls nicht eingestellt ist, verwendet das OTel SDK standardmäßig localhost:4317.

  • --otel-insecure (Standard false): unsichere Verbindung zum Kollektor verwenden.
  • --tracing-sampling-rate (Standard 0.1): Abtastrate für Ablaufverfolgungen (gemeinsam für alle Ablaufverfolgungs-Backends). Jedes OTLP-kompatible Backend (Jaeger v1.35+, Grafana Tempo, Datadog Agent usw.) kann diese Traces empfangen.

<a id="tracing-opentracing-deprecation"/>Veraltung von OpenTracing-basierten Tracing-Backends</a>

Die folgenden Tracing-Backends sind ab Version 24 veraltet und werden in Version 25 entfernt:

  • opentracing-jaeger – Verwendet die Bibliothek Jaeger client-go, die archiviert wurde. Das Jaeger-Projekt empfiehlt die Migration auf OpenTelemetry. Benutzer sollten mit einem OTLP-kompatiblen Jaeger-Endpunkt (v1.35+) auf --tracer opentelemetry migrieren.
  • opentracing-datadog – Verwendet die OpenTracing-Brücke in dd-trace-go. Benutzer sollten mit dem OTLP-Aufnahmeendpunkt des Datadog Agent auf --tracer opentelemetry migrieren. Die Optionen --tracer opentracing-jaeger und --tracer opentracing-datadog funktionieren in Version 24 weiterhin, protokollieren jedoch beim Start eine veraltete Warnung. Die folgenden Jaeger-spezifischen Flags sind ebenfalls veraltet und werden in Version 25 entfernt:
  • --jaeger-agent-host
  • --tracing-sampling-type Migration: Ersetzen Sie --tracer opentracing-jaeger durch --tracer opentelemetry und --jaeger-agent-host host:port durch --otel-endpoint host:4317. Stellen Sie sicher, dass Ihre Jaeger-Bereitstellung OTLP akzeptiert (Jaeger v1.35+ lauscht standardmäßig auf Port 4317).

<a id="minor-changes-vtorc"/>VTOrc</a>

<a id="vtorc-cell-flag"/>Neue --cell-Flagge</a>

VTOrc unterstützt jetzt ein --cell-Flag, das angibt, in welcher Vitess-Zelle der VTOrc-Prozess ausgeführt wird. Das Flag ist in v24 optional, wird aber in v25+ erforderlich sein, ähnlich dem --cell-Flag von VTGate. Wenn VTOrc bereitgestellt wird, überprüft es beim Start, ob die Zelle im Topologiedienst vorhanden ist. Ohne das Flag protokolliert VTOrc eine Warnung bezüglich der v25+-Flag-Anforderung. Dies ermöglicht eine zukünftige zellenübergreifende Problemvalidierung, bei der VTOrc eine andere Zelle auffordern kann, erkannte Probleme zu validieren, bevor Wiederherstellungsmaßnahmen ergriffen werden. Das Flag ist derzeit validiert, wird aber noch nicht in der VTOrc-Wiederherstellungslogik verwendet. Hinweis: Wenn Sie VTOrc in einer Bereitstellung mit mehreren Zellen ausführen, beginnen Sie jetzt mit der Verwendung des Flags --cell, um sich auf die v25-Anforderung vorzubereiten.

<a id="vtorc-ordered-recovery-semi-sync"/>Angeordnete Wiederherstellungsausführung und halbsynchroner Rollout</a>

VTOrc führt Wiederherstellungen jetzt pro Shard mit einer definierten Reihenfolge aus, anstatt isoliert pro Tablet. Probleme mit Reihenfolgeabhängigkeiten (z. B. halbsynchrone Konfiguration) werden zuerst seriell ausgeführt, während unabhängige Probleme gleichzeitig ausgeführt werden. Dadurch wird sichergestellt, dass abhängige Wiederherstellungen innerhalb eines Shards in der richtigen Reihenfolge erfolgen. Die wichtigste benutzerseitige Verbesserung betrifft halbsynchrone Rollouts: VTOrc stellt jetzt sicher, dass Replikate halbsynchronisiert sind, bevor die primäre Version aktualisiert wird. Bisher konnte die Aktivierung der Halbsynchronisierung auf der Primärdatenbank dazu führen, dass Schreibvorgänge blockiert werden, während die Primärdatenbank auf Halbsynchronisierungsbestätigungen wartet, für deren Senden kein Replikat bereit war. Weitere Informationen finden Sie unter #19427.

<a id="vtorc-deprecated-metric-removed"/>Veraltete VTOrc-Metrik entfernt</a>

Die Metrik DiscoverInstanceTimings wurde in Version 24 aus VTOrc entfernt. Diese Metrik wurde in Version 23 veraltet. Migration: Verwenden Sie stattdessen DiscoveryInstanceTimings, das die gleichen Zeitinformationen für Instanzerkennungsaktionen (Backend, Instanz, Andere) bereitstellt. Auswirkung: Überwachungs-Dashboards oder Warnsysteme, die DiscoverInstanceTimings verwenden, müssen aktualisiert werden, um DiscoveryInstanceTimings zu verwenden.

<a id="vtorc-snapshot-topology-deprecation"/>Veraltung der Snapshot-Topologie-Funktion</a>

Die Snapshot-Topologie-Funktion von VTOrc, die durch Setzen von --snapshot-topology-interval auf einen Wert ungleich Null aktiviert wird, ist ab Version 24 veraltet und die Logik soll in Version 25 entfernt werden. Der Mangel an Möglichkeiten zum Lesen der von dieser Funktion erstellten Snapshots in Verbindung mit der In-Memory-Natur des VTOrc-Backends bedeutet, dass diese Logik nur begrenzt nützlich ist. Diese Abwertung wird in https://github.com/vitessio/vitess/issues/18691. ausführlich erläutert und nachverfolgt Migration: Entfernen Sie das VTOrc-Flag --snapshot-topology-interval vor v25. Auswirkung: VTOrc kann in seiner Backend-Datenbank keine Snapshots der Topologie mehr erstellen.

<a id="vtorc-replication-analysis-api-removed"/>Veralteter /api/replication-analysis-Endpunkt entfernt</a>

Der Endpunkt /api/replication-analysis wurde in Version 24 aus VTOrc entfernt. Verwenden Sie stattdessen /api/detection-analysis, das die gleiche Funktionalität bietet. Migration: Aktualisieren Sie alle Skripte, Überwachungssysteme oder Automatisierungen, die /api/replication-analysis aufrufen, um stattdessen /api/detection-analysis zu verwenden. Der Ersatzendpunkt akzeptiert dieselben Abfrageparameter (keyspace, shard) und gibt dasselbe Antwortformat JSON zurück. Auswirkung: HTTP-Anfragen an /api/replication-analysis geben den Fehler „404 Not Found“ zurück.

<a id="minor-changes-metrics"/>Metriken</a>

<a id="metrics-extended-go-runtime"/>Erweiterte Go-Laufzeitmetriken über Prometheus</a>

Vitess stellt jetzt über Prometheus den gesamten Satz an Go-Laufzeitmetriken zur Verfügung. Der Standardsatz Prometheus GoCollector stellt nur drei runtime/metrics (/gc/gogc:percent, /gc/gomemlimit:bytes, /sched/gomaxprocs:threads) sowie den Legacy-Satz go_memstats_* bereit. Ab v24 stellen alle Vitess-Komponenten etwa 150 zusätzliche Metriken aus dem runtime/metrics-Paket von Go zur Verfügung. Zu den neuen Messwerten gehören:

  • Heap-Zuordnungshistogramme
  • GC-Zykluszählungen und Pausenhistogramme
  • Aufschlüsselung der Speicherklassen
  • Aufschlüsselung des Goroutine-Status
  • Planer-Latenz-Histogramme
  • Aufschlüsselung der CPU-Zeit nach Klasse (Benutzer, GC, Aufräumen, Leerlauf) Außerdem wurde ein neues go_info_ext-Messgerät mit den Etiketten compiler, GOARCH und GOOS hinzugefügt, das über die Standardmetrik go_info hinaus erweiterte Informationen zur Bauumgebung bietet. Betroffene Komponenten: vtgate, vttablet, vtctld, vtorc, vtbackup, mysqlctld Keine Konfiguration erforderlich – die Metriken werden automatisch auf dem /metrics-Endpunkt für alle Komponenten angezeigt, die das Prometheus-Backend verwenden.

<a id="minor-changes-backup-restore"/>Sichern und Wiederherstellen</a>

<a id="mysql-clone-support"/>MySQL CLONE-Unterstützung für Replikatbereitstellung</a>

VTTablet und VTBackup unterstützen jetzt die Verwendung des nativen [CLONE-Plugins] (https://dev.mysql.com/doc/refman/en/clone-plugin.html) von MySQL, um neue Replikate bereitzustellen, indem Daten direkt von einem Spender-Tablet über das Netzwerk kopiert werden. Das Kopieren von Daten auf physischer Ebene ist deutlich schneller als das logische Sichern und Wiederherstellen, insbesondere bei großen Datensätzen. Erfordert MySQL 8.0.17+ und Nur-InnoDB-Tabellen. Neue Flaggen: | Flagge | Beschreibung | |------|-------------| | --mysql-clone-enabled | Aktivieren Sie das MySQL CLONE-Plugin und erstellen Sie den Klonbenutzer während der MySQL-Initialisierung. Erforderlich für alle Tablets, die an CLONE-Vorgängen teilnehmen. | | --clone-from-primary | Klonen Sie Daten vom primären Tablet des Shards, anstatt sie aus einem Backup wiederherzustellen. Gegenseitig ausschließend mit --clone-from-tablet. | | --clone-from-tablet | Klonen Sie Daten von einem bestimmten Tablet nach Alias ​​(z. B. zone1-123), anstatt sie aus einem Backup wiederherzustellen. Gegenseitig ausschließend mit --clone-from-primary. | | --restore-with-clone | Verwenden Sie MySQL CLONE für die Wiederherstellungsphase, anstatt die Wiederherstellung aus der Sicherung durchzuführen. Erfordert entweder --clone-from-primary oder --clone-from-tablet. | | --clone-restart-wait-timeout | Zeitüberschreitung beim Warten auf den Neustart von MySQL nach Abschluss von CLONE REMOTE. Standard: 5 Minuten. | Benutzerkonfiguration klonen: | Flagge | Beschreibung | |------|-------------| | --db-clone-user | MySQL Benutzername für CLONE-Vorgänge (Spenderauthentifizierung). | | --db-clone-password | Passwort für den CLONE-Benutzer. | | --db-clone-use-ssl | Verwenden Sie SSL, wenn Sie für CLONE-Vorgänge eine Verbindung zum Spender herstellen. | Beispielverwendung: Vom primären Shard klonen:

vttablet \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-primary \
  ...

Von einem bestimmten Tablet klonen:

vtbackup \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-tablet=zone1-0000000100 \
  ...

Hinweis: Für alle Tablets, die an CLONE-Vorgängen teilnehmen (sowohl Spender als auch Empfänger), muss --mysql-clone-enabled während der MySQL-Initialisierung festgelegt sein, um sicherzustellen, dass das CLONE-Plugin geladen wird und der Klonbenutzer vorhanden ist.

<a id="restore-hook-backup-engine-env"/>Restore-Hook-Verbesserungen</a>

Erweiterte Hook-Abdeckung: Der Hook vttablet_restore_done wird jetzt ausgelöst, wenn Wiederherstellungen über vtctldclient RestoreFromBackup ausgelöst werden. Bisher wurde dieser Hook nur beim Starten oder Klonen des Tablets ausgeführt. Neue Umgebungsvariable: Der Hook setzt jetzt TM_RESTORE_DATA_BACKUP_ENGINE, um anzugeben, welche Backup-Engine verwendet wurde. Der Wert stammt aus dem Feld BackupMethod des Backup-Manifests. TM_RESTORE_DATA_BACKUP_ENGINE wird nur gesetzt, wenn eine Wiederherstellung aus einer tatsächlichen Sicherung liest – nicht für klonbasierte Wiederherstellungen oder wenn keine Sicherung verwendet wird. Hook-Skripte können damit motorspezifische Aktionen ausführen, je nachdem, ob bei der Wiederherstellung builtin, xtrabackup oder eine andere Engine verwendet wurde.

<a id="major-changes"/>Major Changes</a>

<a id="new-support"/>New Support</a>

<a id="window-function-pushdown"/>Window function pushdown for sharded keyspaces</a>

This release introduces an optimization that allows window functions to be pushed down to individual shards when they are partitioned by a column that matches a unique vindex.

Previously, all window function queries required single-shard routing, which limited their applicability on sharded tables. With this change, queries where the PARTITION BY clause aligns with a unique vindex can now be pushed down and executed on each shard.

For examples and more details, see the documentation.

<a id="view-routing-rules"/>View Routing Rules</a>

Vitess now supports routing rules for views, and can be applied the same as tables with vtctldclient ApplyRoutingRules. When a view routing rule is active, VTGate rewrites queries that reference the source view to use the target view's definition instead. For example, given this routing rule:

{
  "rules": [
    {
      "from_table": "source_ks.my_view",
      "to_tables": ["target_ks.my_view"]
    }
  ]
}

And this view definition:

CREATE VIEW target_ks.my_view AS SELECT id, name FROM user;

A query like SELECT * FROM source_ks.my_view would be internally rewritten to:

SELECT * FROM (SELECT id, name FROM target_ks.user) AS my_view;

View routing rules require the schema tracker to monitor views, which means VTGate must be started with the --enable-views flag and VTTablet with the --queryserver-enable-views flag. The target view must exist in the specified keyspace for the routing rule to function correctly. For more details, see the Schema Routing Rules documentation.

<a id="tablet-targeting"/>Tablet targeting via USE statement</a>

VTGate now supports routing queries to a specific tablet by alias using an extended USE statement syntax:

USE keyspace:shard@tablet_type|tablet_alias;

For example, to target a specific replica tablet:

USE commerce:-80@replica|zone1-0000000100;

Once set, all subsequent queries in the session route to the specified tablet until cleared with a standard USE keyspace or USE keyspace@tablet_type statement. This is useful for debugging, per-tablet monitoring, cache warming, and other operational tasks where targeting a specific tablet is required.

Note: A shard must be specified when using tablet targeting. Like shard targeting, this bypasses vindex-based routing, so use with care.

<a id="vtgate-binlog-dump"/>Binlog Streaming Support</a>

VTGate now supports GTID-based binlog streaming through two protocols:

  • MySQL protocol: Clients can connect using the standard MySQL COM_BINLOG_DUMP_GTID replication protocol command—no special VStream-aware adapters or direct MySQL access required.
  • gRPC: The new BinlogDumpGTID streaming RPC in vtgateservice provides native gRPC access for custom clients without the MySQL protocol dependency.

Note: Only GTID-based streaming is supported. File/position-based streaming is not available through either COM_BINLOG_DUMP or COM_BINLOG_DUMP_GTID and returns an error.

This feature is disabled by default. Enable it with --enable-binlog-dump.

New flags:

  • --enable-binlog-dump: Enables binlog dump support. Without this flag, binlog dump requests return an error.
  • --binlog-dump-authorized-users: Comma-separated list of users authorized to execute binlog dump operations, or % to allow all users.

Requirements:

When initiating a binlog dump connection, clients must specify:

  • An empty filename
  • A file position (filepos) of 4
  • A GTID position

For gRPC clients, specify the keyspace, shard, and optionally the tablet type or tablet alias directly in the BinlogDumpGTIDRequest.

Limitations:

  • Each stream operates on a single tablet—no data aggregation across shards.
  • No automatic failover—if the targeted tablet becomes unavailable, the stream fails and the client must reconnect to a different tablet.
  • Not compatible with MoveTables or Reshard operations. Use the VStream API for those use cases.

<a id="structured-logging"/>Structured logging</a>

Vitess now uses structured JSON logging by default. Log output is emitted as JSON to stderr. To configure the minimum log level, pass --log-level (one of debug, info, warn, error; default info). For a human-readable format with automatic color detection, pass --log-format=text. To revert to the previous glog backend, pass --log-structured=false.

glog is deprecated as of v24 and will be removed in v25.

<a id="breaking-changes"/>Breaking Changes</a>

<a id="vttablet-external-decompressor-manifest"/>External Decompressor No Longer Read from Backup MANIFEST by Default</a>

The external decompressor command stored in a backup's MANIFEST file is no longer used at restore time by default. Previously, when no --external-decompressor flag was provided, VTTablet would fall back to the command specified in the MANIFEST. This posed a security risk: an attacker with write access to backup storage could modify the MANIFEST to execute arbitrary commands on the tablet.

Starting in v24, the MANIFEST-based decompressor is ignored unless you explicitly opt in with the new --external-decompressor-use-manifest flag. If you rely on this behavior, add the flag to your VTTablet configuration, but be aware of the security implications.

See #19460 for details.

<a id="minor-changes"/>Minor Changes</a>

<a id="minor-changes-vreplication"/>VReplication</a>

<a id="vreplication-shards-flag-start-stop"/>--shards flag for MoveTables/Reshard start and stop</a>

The start and stop commands for MoveTables and Reshard workflows now support the --shards flag, allowing users to start or stop workflows on a specific subset of shards rather than all shards at once.

Example usage:

# Start workflow on specific shards only
vtctldclient MoveTables --target-keyspace customer --workflow commerce2customer start --shards="-80,80-"

# Stop workflow on specific shards only
vtctldclient Reshard --target-keyspace customer --workflow cust2cust stop --shards="80-"

<a id="vreplication-tablet-error-retry"/>Automatic tablet retry for tablet-specific errors</a>

VReplication workflows now automatically retry with different tablets when encountering tablet-specific errors. Previously, workflows without a cell preference would default to the local cell and could get stuck retrying the same failing tablet indefinitely.

When a tablet encounters errors like binary log purging (MySQL error 1236 or 1789) or GTID set mismatches, VReplication adds that tablet to an ignore list and tries other tablets across all cells. Once all matching tablets have been tried, the ignore list is cleared and the workflow retries from scratch.

This is particularly useful in multi-cell deployments where a tablet in the local cell may lack the required binary logs, but tablets in other cells still have them.

<a id="minor-changes-vtgate"/>VTGate</a>

<a id="vtgate-removed-grpc-send-session-in-streaming"/>Removed --grpc-send-session-in-streaming flag</a>

The VTGate flag --grpc-send-session-in-streaming has been removed. This flag was deprecated in v22 via #17907 and defaulted to true.

The session is now always sent as the last packet in the streaming response for StreamExecute and StreamExecuteMulti RPCs. This behavior is required to support transactions in streaming and cannot be disabled.

Impact: Remove any usage of the --grpc-send-session-in-streaming flag from VTGate startup scripts or configuration.

<a id="vtgate-new-default-legacy-replication-lag-algorithm"/>New default for --legacy-replication-lag-algorithm flag</a>

The VTGate flag --legacy-replication-lag-algorithm now defaults to false, disabling the legacy approach to handling replication lag by default.

Instead, a simpler algorithm purely based on low lag, high lag and minimum number of tablets is used, which has proven to be more stable in many production environments. A detailed explanation of the two approaches is explained in this code comment.

In v25 this flag will become deprecated and in the following release it will be removed. In the meantime, the legacy behaviour can be used by setting --legacy-replication-lag-algorithm=true. This deprecation is tracked in https://github.com/vitessio/vitess/issues/18914.

<a id="vtgate-session-balancer-mode"/>New "session" mode for --vtgate-balancer-mode flag</a>

The VTGate flag --vtgate-balancer-mode now supports a new "session" mode in addition to the existing "cell", "prefer-cell", and "random" modes. Session mode routes each session consistently to the same tablet for the session's duration.

To enable session mode, set the flag when starting VTGate:

--vtgate-balancer-mode=session

<a id="minor-changes-query-serving"/>Query Serving</a>

<a id="query-serving-json-extract-dynamic-args"/>JSON_EXTRACT now supports dynamic path arguments</a>

The JSON_EXTRACT function now supports dynamic path arguments like bind variables or results from other function calls. Previously, JSON_EXTRACT only worked with static string literals for path arguments.

NULL handling now matches MySQL behavior. The function returns NULL when either the document or path argument is NULL.

Static path arguments are still optimized, even when mixed with dynamic arguments, so existing queries won't see any performance regression.

<a id="minor-changes-vttablet"/>VTTablet</a>

<a id="vttablet-init-tablet-type-lookup"/>New Experimental flag --init-tablet-type-lookup</a>

The new experimental flag --init-tablet-type-lookup for VTTablet allows tablets to automatically restore their previous tablet type on restart by looking up the existing topology record, rather than always using the static --init-tablet-type value.

When enabled, the tablet uses its alias to look up the tablet type from the existing topology record on restart. This allows tablets to maintain their changed roles (e.g., RDONLY/DRAINED) across restarts without manual reconfiguration. If disabled or if no topology record exists, the standard --init-tablet-type value will be used instead.

Note: Vitess Operator–managed deployments generally do not keep matching tablet records in the topo across pod replacements, so this feature will have a more limited effect in those environments.

<a id="vttablet-querythrottler-metrics"/>QueryThrottler Observability Metrics</a>

VTTablet now exposes new metrics to track QueryThrottler behavior.

Four new metrics have been added:

  • QueryThrottlerRequests: Total number of requests evaluated by the query throttler
  • QueryThrottlerThrottled: Number of requests that were throttled
  • QueryThrottlerTotalLatencyNs: Total time each request takes in query throttling, including evaluation, metric checks, and other overhead (in nanoseconds)
  • QueryThrottlerEvaluateLatencyNs: Time taken to make the throttling decision (in nanoseconds)

All metrics include labels for Strategy, Workload, and Priority. The QueryThrottlerThrottled metric has additional labels for MetricName, MetricValue, and DryRun to identify which metric triggered the throttling and whether it occurred in dry-run mode.

These metrics help monitor throttling patterns, identify which workloads are throttled, measure performance overhead, and validate behavior in dry-run mode before configuration changes.

<a id="vttablet-querythrottler-config-watch"/>QueryThrottler Event-Driven Configuration Updates</a>

QueryThrottler configuration is now propagated to and stored in the SrvKeyspace record within the topology server and managed using standard topology tools. Previously, tablets polled for configuration changes every 60 seconds. Tablets now use event-driven watches (WatchSrvKeyspace) to receive updates immediately when the query throttling configuration changes. All tablets in a keyspace see configuration changes at roughly the same time, and topology server changes are versioned and auditable.

This change replaces the previous file-based configuration loader with a protobuf-defined configuration structure stored in the topology. The new configuration includes fields for enabling/disabling throttling, selecting the throttling strategy, and configuring strategy-specific rules.

<a id="vttablet-conn-pool-waiter-cap"/>Tablet Connection Pool Waiter Cap</a>

VTTablet now allows users to set a limit on the number of requests waiting to get a connection from the connection pool, for the query, stream, and transaction connection pools. The limits are set with the following flags:

  • --queryserver-config-query-pool-waiter-cap
  • --queryserver-config-stream-pool-waiter-cap
  • --queryserver-config-txpool-waiter-cap

All of the above have a default value of 0, meaning no limit, thus preserving the behavior of the previous version.

<a id="minor-changes-tracing"/>Tracing</a>

<a id="tracing-opentelemetry"/>OpenTelemetry tracing support</a>

Vitess now supports OpenTelemetry as a tracing backend. To use it, set --tracer opentelemetry on any Vitess binary. Traces are exported via OTLP/gRPC, configurable with the following flags:

  • --otel-endpoint: OpenTelemetry collector endpoint. If empty, the OTEL_EXPORTER_OTLP_ENDPOINT env var is used; if that is also unset, the OTel SDK defaults to localhost:4317.
  • --otel-insecure (default false): use insecure connection to the collector.
  • --tracing-sampling-rate (default 0.1): sampling rate for traces (shared across all tracing backends).

Any OTLP-compatible backend (Jaeger v1.35+, Grafana Tempo, Datadog Agent, etc.) can receive these traces.

<a id="tracing-opentracing-deprecation"/>Deprecation of OpenTracing-based tracing backends</a>

The following tracing backends are deprecated as of v24 and will be removed in v25:

  • opentracing-jaeger — Uses the Jaeger client-go library, which has been archived. The Jaeger project recommends migrating to OpenTelemetry. Users should migrate to --tracer opentelemetry with an OTLP-compatible Jaeger endpoint (v1.35+).
  • opentracing-datadog — Uses the OpenTracing bridge in dd-trace-go. Users should migrate to --tracer opentelemetry with the Datadog Agent's OTLP ingestion endpoint.

The --tracer opentracing-jaeger and --tracer opentracing-datadog options continue to work in v24 but will log a deprecation warning at startup. The following Jaeger-specific flags are also deprecated and will be removed in v25:

  • --jaeger-agent-host
  • --tracing-sampling-type

Migration: Replace --tracer opentracing-jaeger with --tracer opentelemetry and --jaeger-agent-host host:port with --otel-endpoint host:4317. Ensure your Jaeger deployment accepts OTLP (Jaeger v1.35+ listens on port 4317 by default).

<a id="minor-changes-vtorc"/>VTOrc</a>

<a id="vtorc-cell-flag"/>New --cell Flag</a>

VTOrc now supports a --cell flag that specifies which Vitess cell the VTOrc process is running in. The flag is optional in v24 but will be required in v25+, similar to VTGate's --cell flag.

When provided, VTOrc validates that the cell exists in the topology service on startup. Without the flag, VTOrc logs a warning about the v25+ flag requirement.

This enables future cross-cell problem validation, where VTOrc will be able to ask another cell to validate detected problems before taking recovery actions. The flag is currently validated but not yet used in VTOrc recovery logic.

Note: If you're running VTOrc in a multi-cell deployment, start using the --cell flag now to prepare for the v25 requirement.

<a id="vtorc-ordered-recovery-semi-sync"/>Ordered Recovery Execution and Semi-Sync Rollout</a>

VTOrc now executes recoveries per-shard with a defined ordering, rather than per-tablet in isolation. Problems that have ordering dependencies (e.g., semi-sync configuration) are executed serially first, while independent problems are executed concurrently. This ensures that dependent recoveries happen in the correct sequence within a shard.

The main user-facing improvement is for semi-sync rollouts: VTOrc now ensures replicas have semi-sync enabled before updating the primary. Previously, enabling semi-sync on the primary before enough replicas were ready could stall writes while the primary waited for semi-sync acknowledgements that no replica was prepared to send.

See #19427 for details.

<a id="vtorc-deprecated-metric-removed"/>Deprecated VTOrc Metric Removed</a>

The DiscoverInstanceTimings metric has been removed from VTOrc in v24. This metric was deprecated in v23.

Migration: Use DiscoveryInstanceTimings instead, which provides the same timing information for instance discovery actions (Backend, Instance, Other).

Impact: Monitoring dashboards or alerting systems using DiscoverInstanceTimings must be updated to use DiscoveryInstanceTimings.

<a id="vtorc-snapshot-topology-deprecation"/>Deprecation of Snapshot Topology feature</a>

VTOrc's Snapshot Topology feature, which is enabled by setting --snapshot-topology-interval to a non-zero-value is deprecated as of v24 and the logic is planned for removal in v25.

The lack of facilities to read the snapshots created by this feature coupled with the in-memory nature of VTOrc's backend means this logic has limited usefulness. This deprecation is explained and tracked in detail in https://github.com/vitessio/vitess/issues/18691.

Migration: remove the VTOrc flag --snapshot-topology-interval before v25.

Impact: VTOrc can no longer create snapshots of the topology in it's backend database.

<a id="vtorc-replication-analysis-api-removed"/>Deprecated /api/replication-analysis Endpoint Removed</a>

The /api/replication-analysis endpoint has been removed from VTOrc in v24. Use /api/detection-analysis instead, which provides the same functionality.

Migration: Update any scripts, monitoring systems, or automation that calls /api/replication-analysis to use /api/detection-analysis instead. The replacement endpoint accepts the same query parameters (keyspace, shard) and returns the same JSON response format.

Impact: HTTP requests to /api/replication-analysis will return a 404 Not Found error.

<a id="minor-changes-metrics"/>Metrics</a>

<a id="metrics-extended-go-runtime"/>Extended Go Runtime Metrics via Prometheus</a>

Vitess now exposes the full set of Go runtime metrics via Prometheus. The default Prometheus GoCollector only exposes three runtime/metrics (/gc/gogc:percent, /gc/gomemlimit:bytes, /sched/gomaxprocs:threads) plus the legacy go_memstats_* set. Starting in v24, all Vitess components expose approximately 150 additional metrics from Go's runtime/metrics package.

New metrics include:

  • Heap allocation histograms
  • GC cycle counts and pause histograms
  • Memory class breakdowns
  • Goroutine state breakdowns
  • Scheduler latency histograms
  • CPU time breakdowns by class (user, GC, scavenge, idle)

A new go_info_ext gauge is also added with compiler, GOARCH, and GOOS labels, providing extended build environment information beyond the standard go_info metric.

Affected components: vtgate, vttablet, vtctld, vtorc, vtbackup, mysqlctld

No configuration required — the metrics appear automatically on the /metrics endpoint for all components using the Prometheus backend.

<a id="minor-changes-backup-restore"/>Backup and Restore</a>

<a id="mysql-clone-support"/>MySQL CLONE Support for Replica Provisioning</a>

VTTablet and VTBackup now support using MySQL's native CLONE plugin to provision new replicas by copying data directly from a donor tablet over the network. Physical-level data copying is significantly faster than logical backup and restore, especially for large datasets. Requires MySQL 8.0.17+ and InnoDB-only tables.

New Flags:

| Flag | Description | |------|-------------| | --mysql-clone-enabled | Enable the MySQL CLONE plugin and create the clone user during MySQL initialization. Required for all tablets that will participate in CLONE operations. | | --clone-from-primary | Clone data from the shard's primary tablet instead of restoring from backup. Mutually exclusive with --clone-from-tablet. | | --clone-from-tablet | Clone data from a specific tablet by alias (e.g., zone1-123) instead of restoring from backup. Mutually exclusive with --clone-from-primary. | | --restore-with-clone | Use MySQL CLONE for the restore phase instead of restoring from backup. Requires either --clone-from-primary or --clone-from-tablet. | | --clone-restart-wait-timeout | Timeout for waiting for MySQL to restart after CLONE REMOTE completes. Default: 5 minutes. |

Clone User Configuration:

| Flag | Description | |------|-------------| | --db-clone-user | MySQL username for CLONE operations (donor authentication). | | --db-clone-password | Password for the CLONE user. | | --db-clone-use-ssl | Use SSL when connecting to the donor for CLONE operations. |

Example Usage:

Clone from the shard's primary:

vttablet \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-primary \
  ...

Clone from a specific tablet:

vtbackup \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-tablet=zone1-0000000100 \
  ...

Note: All tablets participating in CLONE operations (both donors and recipients) must have --mysql-clone-enabled set during MySQL initialization to ensure the CLONE plugin is loaded and the clone user exists.

<a id="restore-hook-backup-engine-env"/>Restore Hook Improvements</a>

Extended Hook Coverage: The vttablet_restore_done hook now fires when restores are triggered via vtctldclient RestoreFromBackup. Previously, this hook only ran during tablet startup or clone operations.

New Environment Variable: The hook now sets TM_RESTORE_DATA_BACKUP_ENGINE to indicate which backup engine was used. The value comes from the backup manifest's BackupMethod field.

TM_RESTORE_DATA_BACKUP_ENGINE is only set when a restore reads from an actual backup—not for clone-based restores or when no backup is used. Hook scripts can use this to perform engine-specific actions based on whether the restore used builtin, xtrabackup, or another engine.
