verifizieren 1.18.0

Dify 1.18.0 bietet Agenten, die Workflows weiterleiten, portable App-Pakete, tiefere Einblicke in verschachtelte Workflow-Ausführungen und die optionale Agent Knowledge Base-Erfahrung. OpenAPI und das neue Difyctl erweitern die Art und Weise, wie Sie Apps über die Befehlszeile erstellen und verwalten.

[!IMPORTANT] Lesen Sie vor der Bereitstellung die Upgrade-Anleitung unten. Aktualisieren Sie die API-, Worker-, Agent-Backend- und Agent-Laufzeit-Images gemeinsam. Lokale Agent-Sandboxen erfordern ein nicht leeres Authentifizierungstoken und Agent-Backend verwendet ein neues Ausführungsprotokoll. Quellinstallationen erfordern Python 3.13. Installieren Sie das neue Difyctl client und melden Sie sich erneut an. Behalten Sie Ihre bestehende PASSWORD_PEPPER-Konfiguration bei.

Release-Highlights

Agenten, die den nächsten Schritt wählen

Lassen Sie einen Agenten entscheiden, welcher Workflow-Zweig verwendet werden soll. Aktivieren Sie Ausgaberouten, geben Sie jeder Route eine Auswahlbedingung und verknüpfen Sie sie mit dem nächsten Schritt – z. B. der direkten Lösung einer Anfrage oder der Übergabe an einen Spezialisten. Die schreibgeschützte switch-Ausgabe macht die ausgewählte Route verfügbar. (#42599)

Konfiguration der Ausgaberouten mit zwei Zweigen im Workflow-Editor.

Plain Agent v2-Knoten streamen auch Text, während er generiert wird. Strukturierte Ergebnisse, weitergeleitete Ergebnisse und Knoten, die die Standardwert-Fehlerbehandlung verwenden, bleiben gepuffert. (#43986)

Tragbare Apps in einem Paket

Verschieben Sie eine App mit ihren unterstützten Ressourcen in einem einzigen .ifpkg-Paket. Workflow- und Chatflow-Pakete enthalten Inline-Agenten, Skills und ihre Dateien; Importe erstellen diese Ressourcen im Zielarbeitsbereich neu und ordnen Referenzen neu zu. Datei- und URL-Importe unterstützen sowohl Pakete als auch YAML, und der explizite YAML-Export bleibt weiterhin verfügbar. (#42066, #42579, #42626, #42863)

Studios .ifpkg-Importvorschau.

Sehen Sie sich die verschachtelten Workflow-Ausführungen an

Öffnen Sie einen Workflow-Tool-Aufruf aus dem Ausführungsverlauf und überprüfen Sie die einzelnen Schritte des untergeordneten Workflows. Verschachtelte Tools werden jetzt als untergeordnete Diagramme mit koordinierten Pausen-, Fortsetzungs-, Stopp- und Dateiausgaben ausgeführt. Zugriffsprüfungen schützen die Details der Quell-App. (#40277, #42819, #42820, #42821, #42822)

Drilldown zu einem erfolgreichen Workflow-Tool-Aufruf verfolgen.

Verschachtelte Nutzungs- und Schrittsummen können immer noch Näherungswerte sein, insbesondere nach einer Pause oder einem Stopp. Konsolen-Drilldown und externer Trace-Export haben unterschiedliche Bereiche; Die vollständigen Funktionsdetails finden Sie weiter unten.

Agent-Wissensdatenbank · Beta

Erstellen Sie einen Wissensbereich für Ihre Agenten, fügen Sie Dateien hinzu oder verbinden Sie Quellen und prüfen Sie die Dokumentenverarbeitung, Metadaten, Abrufspuren und Qualitätsbewertungen an einem Ort. Die neuen Knowledge Retrieval-Knoten- und Agent-Integrationen teilen sich zugriffskontrollierte KnowledgeFS-Bereiche. Classic Knowledge bleibt verfügbar. Dies ist eine Opt-in-Integration mit einem separaten Dienst und einer separaten Datenbank. siehe unten die Bereitstellungsanforderungen. (#44165)

Wird bald auf cloud.dify.ai verfügbar sein

Entwickler-Spotlight

Erstellen und verwalten Sie Apps mit OpenAPI und difyctl. Der CLI erkennt Befehle aus dem Betriebskatalog des Servers mit durchsuchbarer Hilfe und Unterstützung für die Workflow- und Chatflow-Erstellung, DSL-Import/Export, Einstellungen, Umgebungsvariablen, Veröffentlichung und Versionswiederherstellung. Entwurfs-Hashes schützen gleichzeitige Bearbeitungen. (#42487, #42608, #43067)

Upgrade-Anleitung

Kompatibilität und Rollout

  1. Zuerst sichern. Behalten Sie die Datenbank, die Vektorspeicherdaten, die hochgeladenen Dateien, den Agent-Snapshot/Arbeitsbereichsspeicher sowie alle Bereitstellungsgeheimnisse und Umgebungsdateien bei. Verwenden Sie ein Wartungsfenster für ein Single-Stack-Upgrade.
  2. Aktualisieren Sie die Agent-Komponenten gemeinsam. /runs akzeptiert jetzt Kompositions-V2-Anfragen und lehnt V1-Anfragen ab. Vorhandene Sitzungs-Snapshots werden beim Lesen konvertiert und als v2 gespeichert; Alte Laufzeiten können neu gespeicherte v2-Snapshots nicht lesen. Direct Agent-Backend-Integrationen müssen ihr Anforderungsformat aktualisieren. Das alte agentenspezifische AskHuman-Tool und der verzögerte Wiederaufnahmepfad werden entfernt: Historische Agentenformulare nehmen die Ausführung nicht mehr wieder auf, während gemeinsam genutzte Workflow-Human-Input-Knoten weiterhin unterstützt werden. (#43833)
  3. Legen Sie alte Workflow-Konsumenten außer Betrieb, bevor Sie Datenverkehr neuer Versionen zulassen. Lassen Sie In-Flight-Läufe beenden und ersetzen Sie dann alte Worker/Fortsetzungskonsumenten, damit sie die gemeinsame Warteschlange nicht ohne die neuen Abbruchwächter verarbeiten können. Ältere angehaltene Aufgaben-IDs können aus gültigen gespeicherten Aufruf-Snapshots innerhalb des vorhandenen Zugriffsbereichs wiederhergestellt werden; Fehlende oder ungültige Snapshots erfordern eine separate Wiederherstellung. Für verschachtelte Nutzungssummen gilt die oben genannte Einschränkung. (#40277)
  4. Konfigurieren Sie das lokale Sandbox-Token vor dem Neustart. Stellen Sie ein Geheimnis mit hoher Entropie über die gemeinsame Compose-Interpolationsquelle bereit. Das 1.17.1-Laufzeitimage unterstützt das neue Flag --require-auth-token nicht. Stellen Sie die passenden 1.18.0-Agent-Backend- und lokalen Sandbox-Images bereit. (#44152)
  5. Passwort-Hashing-Konfiguration beibehalten. Vorhandene Installationen ohne Pepper sollten PASSWORD_PEPPER leer lassen. Das Festlegen eines neuen Peppers während des Upgrades ist keine transparente Migration und erfordert einen expliziten Plan zum Zurücksetzen des Passworts. Lassen Sie alle konfigurierten Peppers über alle Instanzen hinweg unverändert und stellen Sie sie mit der Datenbank wieder her.
  6. Überprüfen Sie die Proxy-Grenze. Das gebündelte Nginx ersetzt X-Forwarded-For durch seine aufgelöste client-Adresse und Compose ermöglicht die Verarbeitung weitergeleiteter Header. Halten Sie den direkten API-Zugriff auf trusted-Anrufer beschränkt. Wenn ein Load Balancer oder Cloudflare vor Nginx sitzt, konfigurieren Sie dort die trusted-Real-IP-Verarbeitung; andernfalls teilen sich Besucher möglicherweise den Rate-Limit-Bucket des Proxys. Siehe client IP- und trusted-Proxys.
  7. KnowledgeFS absichtlich aktivieren. Standardmäßige Compose-Installationen lassen es deaktiviert; Für die Entwicklung der lokalen Community Edition ist die explizite Zustimmung zur Community-Entwicklung erforderlich. Konfigurieren Sie die separate Datenbank und Migrationen, den öffentlichen Verifizierer von Capability v2, die Dify-Signaturschlüssel, das Modellprofil (Einbettung, Begründung und Neubewertung) und Workspace-Cutover-Gates, bevor Sie den Datenverkehr aktivieren. Der optionale Dienst muss /ready bestehen, nicht nur /health. Standard-Dify-API-Bilder enthalten nicht die separate KnowledgeFS-Engine, die vom optionalen Engine-Worker-Profil verwendet wird. Das veröffentlichte Standard-KnowledgeFS-Image API ist derzeit nur amd64. Befolgen Sie den [KnowledgeFS-Bereitstellungs- und Wiederherstellungsleitfaden] (https://github.com/langgenius/dify/blob/laipz8200/release-1.18.0/docker/README.md#knowledgefs-integration-service).

Docker Verfassen

Sobald die 1.18.0-Release-Images und das Tag veröffentlicht sind, stoppen Sie den alten Stack ordnungsgemäß, wechseln Sie zum Release, führen Sie die oben genannten Konfigurationsänderungen zusammen und ziehen/starten Sie den neuen Stack:

cd dify/docker
docker compose stop -t -1
git fetch --tags
git checkout 1.18.0
# Merge required configuration changes into existing env files here.
docker compose pull
docker compose up -d

Lassen Sie Datenbankmigrationen für den API-Start aktiviert (MIGRATION_ENABLED=true) oder führen Sie sie durch Ihren verwalteten Migrationsprozess aus, bevor Sie neue Worker starten. Das gebündelte Weaviate-Update von 1.17.1 ist ein Patch-Update innerhalb von 1.39. Wenn Sie von einer Version kommen, auf der noch Weaviate 1.27 ausgeführt wird, schließen Sie zuerst das [1.17.1 gestaffelte Weaviate-Upgrade] (https://github.com/langgenius/dify/releases/tag/1.17.1) ab.

Quellbereitstellungen

Verwenden Sie Python 3.13 für API, Node.js 24.22.1 oder höher in der 24.x-Reihe und pnpm 12.10.1. Aktualisieren Sie die gesperrten Abhängigkeiten und wenden Sie die Datenbankmigrationen vom Repository-Stammverzeichnis an:

uv sync --project api --frozen
uv run --directory api flask db upgrade
pnpm install --frozen-lockfile

Erstellen Sie die Webanwendung neu und starten Sie API, Worker-, Scheduler- und Agent-Dienste aus derselben Version neu. Wenn Sie das Agent-Backend separat von der Quelle bereitstellen, aktualisieren Sie auch seine gesperrten server-Abhängigkeiten.

difyctl

Installieren Sie den passenden 1.18.0 client. Seine v2-Implementierung verwendet den v1-Anmeldestatus nicht wieder:

difyctl login --server https://your-dify.example.com
difyctl help

Aktualisieren Sie Skripts auf die aktuelle, vom Server erkannte Befehlsoberfläche. Die alte modusunabhängige /openapi/v1/apps/{app_id}:run-Route wird durch modusspezifische Vorgänge ersetzt; Verwenden Sie den Katalog anstelle von hartcodierten v1-Routen. Aktualisieren Sie die Fähigkeiten installierter Agenten mit difyctl install skills <dir>. (#42487, #42608, #43819)

<Details> <summary><strong>Neue Funktionen · umfassende Funktionen und Verfügbarkeit</strong></summary>

Agent-Wissensdatenbank und KnowledgeFS

  • Fügen Sie das Beta-Knowledge-Space-Erlebnis mit lokaler Upload-Vorschau, Connected-Source-Management, Dokumentverfügbarkeit und Metadaten, Abrufverlauf/Recherche und Qualitätsbewertung hinzu. Einstellungen steuern den Zugriff auf App, Agent und Dienst API. Classic Knowledge wird daneben weiterhin unterstützt. (#44165)
  • Knowledge Retrieval v2 und Agent-Wissensbindungen verwenden bereichsbezogene Funktionen. Veröffentlichte Explore-Läufe verwenden veröffentlichte Bindungen wieder, ohne dass normale Betrachter den Zugriff neu konfigurieren müssen. (#44165) – Klassische Datensatz-Upgrades verfügen über dauerhafte Prüfpunkte, Verfügbarkeits-/Metadatenabgleich, Wiederholungsschutz und Wiederherstellung durch Beat. Führen Sie den dedizierten Upgrade-Worker mit dem dokumentierten Prefork-Pool und den Aufgabenlimits aus. Wenden Sie b9d3f7a5c102 an, bevor Sie API/workers/Beat neu starten. Wenn Sie sich für den Dienst anmelden, werden nicht automatisch alle Classic-Datensätze migriert. (#44165)

Portable App-Pakete

– App-Exporte werden jetzt standardmäßig nach .ifpkg exportiert, wodurch die Anwendungskonfiguration und die unterstützten Ressourcen in einem tragbaren Paket zusammengefasst werden. Der explizite YAML-Export bleibt verfügbar und Importe akzeptieren beide Formate aus Dateien oder URLs. (#42066, #42189, #42425, #42552)

  • Workflow- und Chatflow-Pakete umfassen Inline-Agenten, ihre Fähigkeiten und Dateien aus dem gebundenen Konfigurations-Snapshot jedes Knotens. Durch Importe werden diese Agenten im Zielarbeitsbereich neu erstellt und ihre Ressourcen neu zugeordnet. App-Symbole, Site-Einstellungen und Knoten-Plugin-Abhängigkeiten sind im Exportfluss enthalten. Beim Import werden fehlende Ressourcen gemeldet. (#42579, #42626, #42816, #42863, #42913) – Agent-Exporte können auf eine veröffentlichte Version abzielen. Die Menüs der Agent-Version bieten jetzt die Option „Wiederherstellen“ an, und ausstehende Entwurfsspeicherungen werden vor der Wiederherstellung abgeschlossen, sodass die wiederhergestellte Konfiguration durch die automatische Speicherung nicht überschrieben werden kann. Beim Duplizieren und Exportieren von Fertigkeiten werden die zuletzt gespeicherten Entwurfsinhalte verwendet. (#42485, #42567, #42424, #42502)

Verschachtelte Workflow-Tools und Trace-Drilldown

– So genannte Workflow-Tools werden als untergeordnete Diagramme unter der Workflow-Engine ausgeführt, mit koordinierten Pausen-, Fortsetzungs-, Stopp- und Dateiausgaben. Quelldiagramme werden vor der Ausführung erfasst, sodass die erneute Veröffentlichung eines Tools keine Änderungen an einer laufenden Ausführung, einschließlich Aufrufen innerhalb von Schleifen und Iterationen, zur Folge hat. (#40277, #42820)

  • Workflow-, Chatflow- und Verlaufsansichten können einen bestimmten Tool-Aufruf öffnen und durch seine internen Ausführungsspuren navigieren. Der Zugriff auf jede Quellanwendung ist erforderlich, bevor ihre Details zurückgegeben werden. Menschliche Eingabeformulare werden anhand der Ausführungsidentität verfolgt, einschließlich wiederholter Aufrufe desselben Knotens. (#42819, #42821, #42822) – Verschachtelte Agentenprotokolle und Nutzungsdatensätze behalten ihre Quell-Workflow-Identität und ihre Beziehung zum äußeren Lauf. Verschachtelte Nutzungs- und Schrittsummen können immer noch Näherungswerte sein, insbesondere nach Pausen oder Stopps. (#42824, #42820)

Agent-Ausgaberouten und Streaming

– Agent v2-Knoten können im Rahmen der Erledigung ihrer Aufgabe einen Workflow-Zweig auswählen. Aktivieren Sie Ausgaberouten, definieren Sie mindestens zwei Zweige und ihre Auswahlbedingungen und verwenden Sie die schreibgeschützte switch-Ausgabe, um die ausgewählte Route zu überprüfen. Wenn das Routing deaktiviert ist, bleibt der normale Erfolgsausgang verfügbar. Geroutete Knoten unterstützen das Stoppen bei Fehler oder die Übernahme einer Fehlerverzweigung. Die Standardwertbehandlung auf Knotenebene ist bei aktivierten Routen nicht verfügbar. (#42599) – Plain Agent v2-Knoten streamen Text, während er generiert wird. Strukturierte oder weitergeleitete Ergebnisse bleiben gepuffert, und Knoten, die die Fehlerbehandlung mit Standardwerten verwenden, bleiben gepuffert, sodass der konfigurierte Fallback weiterhin ein fehlgeschlagenes Ergebnis ersetzen kann. (#43986)

Erstellen und verwalten Sie Apps mit OpenAPI und difyctl

  • /openapi/v1 veröffentlicht einen Serverbetriebskatalog. difyctl erkennt Befehle und ihre Eingabefelder aus diesem Katalog, stellt durchsuchbare Hilfe bereit und folgt den vom Server bereitgestellten nächsten Schritten. Die Workflow- und Chatflow-Erstellung umfasst jetzt App-Erstellung, DSL-Import/Export, Einstellungen, Umgebungsvariablen, Veröffentlichung und Versionswiederherstellung. Entwurfs-Hashes schützen Importe davor, gleichzeitige Bearbeitungen zu überschreiben. (#42487, #42608, #43067) – Der CLI beinhaltet einen difyctl-Skill für Agenten, die Dify-Apps erstellen. Installieren Sie es mit difyctl install skills <dir>. Die Geräteanmeldung unterstützt --no-wait und --resume und Ordner-Uploads senden einen mehrteiligen Teil pro Datei. (#43819, #44356) – Workspace-Besitzer können Ressourcenzugriffstoken erstellen, die an ausgewählte Apps oder Wissensdatenbanken gebunden sind. Token funktionieren mit den unterstützten Dienst-API-Routen und App-Vorgängen in difyctl; Sie gewähren keine Arbeitsbereichsverwaltung. Der Einstellungseintrag kann über NEXT_PUBLIC_ENABLE_ACCESS_TOKEN aktiviert werden, der Standardwert ist false. (#42293, #44422)

Agentenaufforderungen aus der Sandbox bearbeiten

  • dify-agent config prompt pull [--to PATH] und push [PATH|-] lesen oder ersetzen die Rohsystemeingabeaufforderung und behalten dabei UTF-8, Leerzeichen und Erwähnungsmarkierungen bei. Leerer Text löscht es. Nur der beschreibbare Build-Entwurf des aktuellen Kontos kann geändert werden; Spätere Anfragen verwenden die gespeicherte Eingabeaufforderung. (#44561)

Agent-Ausführungsverfolgung

– Agent-Apps und Workflow Agent v2-Knoten können ihre Agent-, Modell- und Tool-Ausführungsbäume über die vorhandenen Ablaufverfolgungsanbieter exportieren. Die Überwachung fügt eine gemeinsame Ablaufverfolgungskonfiguration, einen Übermittlungsstatus, Wiederholungskontrollen und Links zu der Ablaufverfolgung hinzu, die zur ausgewählten Ausführung gehört. Von einem Workflow referenzierte Agenten erben die Verfolgungsrichtlinie des Anrufers. (#44144, #44186) – Die Anwendungsverfolgung ist sowohl auf dem API als auch auf dem Agent-Backend aktiviert. Unabhängig von der Systemverfolgung ist auch ein separater, einsatzweiter OTLP-Trajektorienexporter verfügbar. (#42651, #44144) – Die internen Knoten der aufgerufenen Workflow-Tools sind von externen Exporten ausgeschlossen, da diese Exporte keine Betrachteridentität für Quell-App-Zugriffsprüfungen haben. Agenten innerhalb dieser sogenannten Tools sind vorerst ebenfalls vom neuen Export des Ausführungsbaums ausgeschlossen; Der autorisierte Konsolen-Drilldown bleibt verfügbar. (#42823, #44144)

OpenShell Sandbox Backend und E2B-Nutzungssammlung

– Die Ausführung des Agenten kann ein selbstgehostetes NVIDIA OpenShell-Gateway mit DIFY_AGENT_RUNTIME_BACKEND=openshell verwenden. Jede Bindung verfügt über eine eigene Sandbox mit authentifiziertem Shell-Zugriff, Home-Snapshots auf einem vom Betreiber verwalteten freigegebenen Volume und einer optionalen Egress-Zulassungsliste. Erforderlich ist das OpenShell-Gateway 0.0.106 oder neuer und ein kompatibles Laufzeitimage. (#41076) – OpenShell-Lease-Release schließt die Verbindung, lässt die Sandbox jedoch weiterlaufen. Es gibt keinen automatischen Leerlaufstopp oder Sandbox-TTL; Betreiber müssen diese Ressourcen verwalten. Multi-Tenant-Bereitstellungen erfordern separate OpenShell-Arbeitsbereiche und Snapshot-Volumes pro Mandant. Weitere Informationen finden Sie im OpenShell-Bereitstellungshandbuch. – Die optionale E2B-Nutzungserfassung erfasst die Ausführungsdauer und Ressourcengrößen des Anbieters über Celery Beat und die ops_trace-Warteschlange. Die Sammlung beginnt ab einer konfigurierten Aktivierungszeit und füllt frühere Ausführungen nicht auf. Sowohl die API- als auch die Agent-Backend-Messungsflags sind standardmäßig deaktiviert. (#42554)

Cloud-Zugriffskontrollen, Vorlagen und Archivverwaltung – Mit wiederverwendbaren Netzwerkzugriffsgruppen können unterstützte Cloud-Bereitstellungen IP-Regeln über Apps hinweg gemeinsam nutzen, mit Berechtigungsprüfungen, Status der gültigen Richtlinien und trusted client-IP-Vorschauen. Die Durchsetzung hängt vom Cloud-Richtliniendienst und Gateway ab; Dies ist keine eigenständige Community Edition-Firewall. (#41025, #44464) – Cloud-Benutzer können veröffentlichte Agent-Vorlagen in der Vorschau anzeigen und ausprobieren, bevor sie sie importieren. Der Agent „Aus Vorlage erstellen“ ist in den Community- und Enterprise-Editionen ausgeblendet, da seine Vorlagendatenquelle nur in der Cloud verfügbar ist. (#42837, #44035) – In Cloud Workflow Log Archives können Arbeitsbereichsbesitzer einen ausgewählten Monat dauerhaft löschen, mit Bestätigung, Fortschritt und Wiederholung. Die Aktion entfernt archivierte Objekte und vorbereitete ZIP-Downloads; Live-Workflow-Laufdatensätze liegen außerhalb seines Geltungsbereichs. Fehlgeschlagene Löschaufträge werden jetzt in die Wiederholungsrichtlinie aufgenommen, anstatt den Erfolg zu melden. (#44052, #44061, #44203)

Legacy paused task IDs can be recovered from valid saved invocation snapshots within the existing access scope; missing or invalid snapshots require separate recovery. Nested usage totals retain the limitation noted above. (#40277)
  4. Configure the Local sandbox token before restart. Supply a high-entropy secret through the shared Compose interpolation source. The 1.17.1 runtime image does not support the new --require-auth-token flag; deploy the matching 1.18.0 Agent Backend and Local sandbox images. (#44152)
  5. Preserve password hashing configuration. Existing installations without a pepper should leave PASSWORD_PEPPER empty. Setting a new pepper during the upgrade is not a transparent migration and requires an explicit password-reset plan. Keep any configured pepper unchanged across all instances and restore it with the database.
  6. Review the proxy boundary. Bundled Nginx replaces X-Forwarded-For with its resolved client address, and Compose enables forwarded-header handling. Keep direct API access restricted to trusted callers. If a load balancer or Cloudflare sits before Nginx, configure trusted real-IP handling there; otherwise visitors may share the proxy’s rate-limit bucket. See client IP and trusted proxies.
  7. Enable KnowledgeFS deliberately. Default Compose installations keep it off; local Community Edition development requires the explicit Community development opt-in. Configure its separate database and migrations, Capability v2 public verifier, Dify signing keys, model profile (embedding, reasoning, and rerank), and Workspace cutover gates before enabling traffic. The optional service must pass /ready, not only /health. Standard Dify API images do not contain the separate KnowledgeFS engine used by the optional engine-worker profile; the published default KnowledgeFS API image is currently amd64 only. Follow the KnowledgeFS deployment and recovery guide.

  • Called Workflow Tools run as child graphs under the workflow engine, with coordinated pause, resume, stop, and file outputs. Source graphs are captured before execution, so republishing a tool does not change an in-flight run, including calls inside loops and iterations. (#40277, #42820)
  • Workflow, Chatflow, and history views can open a particular tool invocation and navigate its internal execution traces. (#42819, #42821, #42822)

  • Agent v2 nodes can select a workflow branch as part of completing their task. Enable Output Routes, define at least two branches and their selection conditions, and use the read-only switch output to inspect the chosen route. With routing disabled, the normal success outlet remains available. Routed nodes support stopping on error or taking a failure branch; node-level default-value handling is unavailable with routes enabled. (#42599)
  • Plain Agent v2 nodes stream text as it is generated. Structured or routed results remain buffered, and nodes using default-value error handling stay buffered so the configured fallback can still replace a failed result. (#43986)

Build and Manage Apps with OpenAPI and difyctl

  • /openapi/v1 publishes a server operation catalog. difyctl discovers commands and their input fields from that catalog, provides searchable help, and follows server-provided next steps. Workflow and Chatflow authoring now covers app creation, DSL import/export, settings, environment variables, publishing, and version restoration. Draft hashes protect imports from overwriting concurrent edits. (#42487, #42608, #43067)
  • The CLI includes a difyctl skill for agents building Dify apps. Install it with difyctl install skills <dir>. Device login supports --no-wait and --resume, and folder uploads send one multipart part per file. (#43819, #44356)
  • Workspace owners can create resource access tokens bound to selected apps or knowledge bases. Tokens work with the supported Service API routes and app operations in difyctl; they do not grant workspace administration. The Settings entry is opt-in through NEXT_PUBLIC_ENABLE_ACCESS_TOKEN, which defaults to false. (#42293, #44422)

Edit Agent Prompts from the Sandbox

  • dify-agent config prompt pull [--to PATH] and push [PATH|-] read or replace the raw system prompt, preserving UTF-8, whitespace, and mention markers. Empty text clears it. Only the current account’s writable build draft can be changed; later requests use the saved prompt. (#44561)

Agent Execution Tracing

  • Agent apps and Workflow Agent v2 nodes can export their Agent, model, and tool execution trees through the existing tracing providers. Monitoring adds shared tracing configuration, delivery status, retry controls, and links to the trace belonging to the selected execution. Agents referenced by a Workflow inherit the caller’s tracing policy. (#44144, #44186)
  • Application tracing is opt-in on both the API and Agent Backend. A separate deployment-wide OTLP trajectory exporter is also available, independently of system tracing. (#42651, #44144)
  • Called Workflow Tools’ internal nodes are excluded from external exports because those exports have no viewer identity for source-app access checks. Agents inside those called tools are also excluded from the new execution-tree export for now; authorized Console drilldown remains available. (#42823, #44144)

OpenShell Sandbox Backend and E2B Usage Collection

  • Agent execution can use a self-hosted NVIDIA OpenShell gateway with DIFY_AGENT_RUNTIME_BACKEND=openshell. Each Binding has its own sandbox, with authenticated shell access, Home Snapshots on an operator-managed shared volume, and an optional egress allowlist. OpenShell gateway 0.0.106 or newer and a compatible runtime image are required. (#41076)
  • OpenShell lease release closes the connection but leaves the sandbox running. There is no automatic idle-stop or sandbox TTL; operators must manage those resources. Multi-tenant deployments require separate OpenShell workspaces and snapshot volumes per tenant. See the OpenShell deployment guide.
  • Optional E2B usage collection records provider execution duration and resource sizes through Celery Beat and the ops_trace queue. Collection starts from a configured activation time and does not backfill earlier executions. Both the API and Agent Backend metering flags default to off. (#42554)

Cloud Access Controls, Templates, and Archive Management

  • Reusable network access groups let supported Cloud deployments share IP rules across apps, with permission checks, effective-policy status, and trusted client-IP previews. Enforcement depends on the Cloud policy service and Gateway; this is not a standalone Community Edition firewall. (#41025, #44464)
  • Cloud users can preview and try published Agent templates before importing them. Agent “Create from Template” is hidden in Community and Enterprise editions because its template data source is Cloud-only. (#42837, #44035)
  • In Cloud Workflow Log Archives, workspace owners can permanently delete a selected month, with confirmation, progress, and retry. The action removes archived objects and prepared ZIP downloads; live workflow-run records are outside its scope. Failed deletion jobs now enter the retry policy instead of reporting success. (#44052, #44061, #44203)
