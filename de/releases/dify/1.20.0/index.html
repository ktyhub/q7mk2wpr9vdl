dify 1.20.0

Minor Veröffentlicht18. Nov. 2026 Quellelanggenius/dify Englisches Original

Diese Seite ist maschinell übersetzt. Maßgeblich ist der englische Originaltext.

verifizieren 1.20.0

Dify 1.20.0 sorgt dafür, dass Ihre Traces fließen und Ihre Wissensdatenbanken sicherer werden. Exportieren Sie Traces in einen beliebigen OpenTelemetry-Collector, sorgen Sie dafür, dass Langfuse nach der Stilllegung des alten Aufnahmeendpunkts weiterläuft, und scannen Sie hochgeladene Wissensdateien auf Malware, bevor sie indiziert werden. Chatflows können die Aktivität des Agenten-Tools anzeigen, während sie stattfindet, und persönliche Zugriffstoken ermöglichen es Skripten und Agenten, Dify OpenAPI in Ihrem Namen aufzurufen. Der gebündelte Plugin-Daemon wird auf 0.6.15-local aktualisiert. Neue Funktionen · Konfigurations- und Integrationsänderungen · Datenbankmigrationen · Upgrade-Anleitung

Neue Funktionen

Neues HITL: Integrieren Sie Genehmigungen in die Messaging-Tools Ihres Teams

Integrieren Sie die menschliche Überprüfung per E-Mail und den Messaging-Tools, die Ihr Team bereits verwendet, in Ihre Arbeitsabläufe. Das neue HITL führt gemeinsame Kanäle, zentralisierte Kontakte, Benachrichtigungsvorlagen und verifizierte Genehmigungsformulare ein – sodass Ihr Team Empfänger einmal konfigurieren und sie über Human-Input-Knoten hinweg wiederverwenden kann. Das neue HITL ist jetzt standardmäßig aktiviert (NEXT_PUBLIC_ENABLE_HITL_IM=true). (#44864, #45945)

  • Erreichen Sie Genehmiger dort, wo sie arbeiten. Konfigurieren Sie E-Mail und eine IM-Plattform – Slack, Feishu/Lark, Microsoft Teams, DingTalk oder WeCom –, um Workflow-Überprüfungsanfragen über die vorhandenen Kanäle Ihres Teams zu übermitteln.
  • Verwalten Sie Empfänger in den Kontakten. Synchronisieren Sie IM-Verzeichnisse und wählen Sie Genehmiger aus einer freigegebenen Kontaktliste aus. Workflows können auch den Initiator ansprechen oder einmalige und dynamische E-Mail-Empfänger verwenden.
  • In Karten oder Formularen genehmigen. Empfänger können Anfragen direkt in unterstützten IM-Karten überprüfen oder eigenständige Formulare öffnen, mit Dify-Anmeldung oder E-Mail-Verifizierung, um ihre Identität zu überprüfen.
  • Passen Sie Benachrichtigungen mit Workflow-Kontext an. Verwenden Sie Vorlagen und Workflow-Variablen, um wichtigen Kontext in Benachrichtigungsthemen und -texte einzubinden.
  • Zustellung testen und verfolgen. Senden Sie Testbenachrichtigungen, um Ihre Einrichtung zu überprüfen und Zustellungsaufzeichnungen zu überprüfen, um Anfragen zu beheben, die nicht wie erwartet eingegangen sind.
  • Neues HITL in bestehende Workflows übernehmen. Verwenden Sie die Opt-in-Migration, um ältere Human Input-Knoten zu aktualisieren, wenn Ihr Workflow bereit ist. Die Bereitstellungsanforderungen sind unter Konfigurations- und Integrationsänderungen aufgeführt.

Exportieren Sie Traces in einen beliebigen OpenTelemetry-Kollektor

Integrieren Sie Dify-Ausführungsspuren in Ihren vorhandenen Observability-Stack. Der neue OpenTelemetry-Anbieter exportiert App- und Agent-Traces in jeden kompatiblen Collector, sodass Sie Workflow-Schritte, Modellaufrufe und Tool-Aktivitäten gemeinsam auf Ihrer bevorzugten Plattform verfolgen können. Verwenden Sie diese Traces, um die Ausführung von Anforderungen zu überprüfen und Fehler zu diagnostizieren, ohne dass eine herstellerspezifische Dify-Integration erforderlich ist. (#45659) Langfuse-Tracing unterstützt jetzt Langfuse v4 und den aktuellen Langfuse Cloud-Aufnahmedienst. Vorhandene Langfuse-Konfigurationen funktionieren weiterhin. (#45606)

[!IMPORTANT] Langfuse Cloud hat seinen alten Aufnahmeendpunkt am 16. November 2026 eingestellt und das selbstgehostete Langfuse v4 lehnt an ihn gesendete Ereignisse ab. Führen Sie ein Upgrade auf 1.20.0 durch, um weiterhin Traces für diese Bereitstellungen bereitzustellen.

Wissens-Uploads auf Malware scannen

Schützen Sie Ihre Wissensdatenbanken, indem Sie hochgeladene Dateien auf Malware scannen, bevor sie extrahiert oder indiziert werden. Wenn diese Option aktiviert ist (FILE_SCAN_ENABLED=true), können Arbeitsbereichsbesitzer und Administratoren Scanner einmal unter Integrationen → Dateisicherheitsscan konfigurieren und dann definieren, wie jede Wissensdatenbank sie verwendet. Zu den unterstützten Scannern gehören Cloudmersive, Scanii, OPSWAT MetaDefender Cloud und ein benutzerdefinierter Endpunkt. (#46090, #46492)

  • Wählen Sie Schutz pro Wissensdatenbank. Wählen Sie einen Scanner aus und konfigurieren Sie das Fallback-Verhalten, wenn das Scannen nicht verfügbar ist oder eine Datei nicht gescannt werden kann.
  • Schützen Sie Wissens-Uploads in Dify. Das Scannen deckt klassische Wissensdatenbanken, lokale RAG-Pipeline-Dateiquellen und Agent-Wissensdatenbank-Uploads ab.
  • Sehen Sie, warum Dateien blockiert wurden. Scanfehler werden zur Überprüfung in der Dokumentenliste angezeigt.

Watch Agent-Tools funktionieren in Chatflow

Wenn ein Chatflow Aufgaben an einen Agent v2-Knoten delegiert (erfordert NEXT_PUBLIC_ENABLE_AGENT_V2_IN_CHATFLOW=true), können Benutzer jetzt in Echtzeit sehen, welche Tools er aufruft. Die Tool-Aktivität wird neben der Antwort sowohl in Vorschauen als auch in veröffentlichten Chats angezeigt, sodass Sie den Fortschritt des Agenten einfacher verfolgen können. Erweitern Sie eine beliebige Werkzeugkarte, um zu überprüfen, was angefordert und zurückgegeben wurde. (#46220)

Automatisieren Sie OpenAPI-Aufrufe mit persönlichen Zugriffstokens

Gewähren Sie Skripten, CI-Jobs und persönlichen Agenten in Ihrem Namen Zugriff auf Dify OpenAPI, ohne Ihre Konsolensitzung zu teilen. Erstellen Sie auf Ihrer Konto-Seite ein persönliches Zugriffstoken und richten Sie es auf bestimmte Arbeitsbereiche und Ressourcen ein. Sie können ein optionales Ablaufdatum festlegen, den Umfang aktualisieren, wenn sich Ihre Automatisierung weiterentwickelt, oder es widerrufen, wenn es nicht mehr benötigt wird. (#45540, #46606)

Wählen Sie GitHub Wissensquellen aus einem Baum

Durchsuchen Sie den GitHub-Inhalt, den Sie einer Wissensdatenbank hinzufügen möchten, und wählen Sie ihn aus einem erweiterbaren Baum aus Repositorys, Verzeichnissen, Problemen und Pull-Anfragen aus. Erkunden Sie die Quellstruktur und wählen Sie die genauen Seiten aus, die importiert werden sollen, unabhängig davon, ob Sie eine neue Wissensdatenbank erstellen oder eine Quelle zu einer vorhandenen hinzufügen. (#45990)

Suchen und navigieren Sie auf kleineren Bildschirmen

Suchen Sie inhaltsübergreifend und grenzen Sie die Ergebnisse mithilfe auswählbarer Bereiche in Goto Anything ein. Auf kleineren Bildschirmen werden Suche und Navigation in Schubladen geöffnet, um Platz für die aktuelle Seite zu schaffen. (#45675, #45650) Direkte Links können jetzt die Erstellungsabläufe für leere Apps oder Vorlagen in Studio öffnen. (#45717)

Flexiblere Wissensbeschreibungen und Metadaten

  • Längere Wissensdatenbankbeschreibungen. Erhöhte Beschreibungslängenbeschränkungen ermöglichen es Ihnen, mehr Kontext für jede Wissensdatenbank bereitzustellen. (#45075)
  • Externe Wissensmetadaten. Der externe Wissensabruf gibt jetzt neben dem Inhalt auch Dokumentmetadaten zurück. (#22496)

Verbesserungen

Geringerer Datenbank- und Start-Overhead. Knotenausführungsaktualisierungen vermeiden das Neuladen gespeicherter Zeilen, Anmeldeinformationsrichtlinien werden einmal pro Anbieterkonfiguration ausgewertet, Modellstandards verwenden kurzlebige Sitzungen und Einbettungsaufrufe halten eine Datenbanksitzung nicht länger offen. Auch Abhängigkeiten von Webfunktionen werden langsamer geladen. (#46410, #46441, #45806, #45788, #46145) Klarere Dokumentfehler und stabilere Layouts. Knowledge-Dokumente melden jetzt spezifische Fehlergründe und Verarbeitungsphasen. Dialoge passen sich an schmale Ansichtsfenster an und sorgen für konsistente Lebenszyklen über Konten, Wissen, Apps, Fertigkeiten und Arbeitsabläufe hinweg. Authentifizierungsseiten werden schneller geladen, passen auf kleinere Bildschirme und der Tastaturfokus bleibt zugänglich. Segmentierte Steuerelemente sorgen für eine reibungslose Animation, wobei kompakte Layouts erhalten bleiben und Präferenzen für reduzierte Bewegungen berücksichtigt werden. (#45128, #46487, #45686, #45668, #45634, #45600, #45640, #45974)

Fehlerbehebungen

  • Sicherere Dateivorschauen und signierte Links. Sandbox-Inline-SVG-Vorschauen und Überprüfung der Originalsignatur vor der Erneuerung abgelaufener Dateilinks. (#46505)
  • Stärkerer Zugriffsschutz. Redigieren Sie Knotenwiederholungsdetails aus öffentlichen Streams, verhindern Sie die Wiederverwendung von OAuth-Callbacks, erzwingen Sie Mitgliedsrollenberechtigungen und beschränken Sie die Vektorlöschung auf den Zieldatensatz. (#46517, #46001, #46053, #45586)
  • Sicherheitsabhängigkeitsaktualisierungen. Aktualisieren Sie github.com/klauspost/compress in dify-agent-runtime, um CVE-2026-116591 zu beheben, und aktualisieren Sie Node.js in Laufzeitimages auf die Sicherheitsversion 24.22.3. (#46544, #46206, #46064)
  • Zuverlässige Blockierungsworkflows. Geben Sie Datenbankverbindungen vor der Ausführung frei und geben Sie Vorbereitungsfehler sofort zurück, um eine Erschöpfung des Verbindungspools und hängende Anforderungen zu verhindern, die bis zum Timeout warten. (#46254)
  • Stabilere Worker. Lösen Sie die Auslastungsschleife Redis BRPOP und verhindern Sie überlappende Plugin-Upgrade-Prüfungen, indem Sie die Parallelität auf 20 Prüfungen für alle Worker begrenzen. (#45940, #46500)
  • Chatflow-Streams abschließen. Streams nach direkten Antworten ordnungsgemäß schließen und das Budget für die erneute Verbindung zurücksetzen, wenn ein Stream fortgesetzt wird. (#45552, #46110)
  • Korrekte Agent-Ausführung. Behalten Sie parallele Aufrufe desselben Plugin-Tools bei, übergeben Sie deklarierte App-Eingaben an Agent-Ausführungen und liefern Sie hochgeladene Bilder an Vision-Modelle. (#45207, #45425, #45745)
  • Präzise Wissensabfrage. Stellen Sie Weaviate-Keyword-/Hybrid-Ergebnisse wieder her, indem Sie BM25-Scores zurückgeben, und halten Sie die Einbettungsvektoren ausgerichtet, wenn ein Batch-Element gelöscht wird. (#45642, #45569)
  • Zuverlässige benutzerdefinierte API-Tools. Lösen Sie OpenAPI-Servervariablen auf, kodieren Sie Pfadparameter in Prozent und unterstützen Sie nullfähige Unionen für OpenAPI 3.1. (#46504, #45965, #45895)

Der OpenTelemetry-Anbieter unterstützt OTLP/HTTP mit Protobuf; gRPC wird nicht unterstützt. Die Aktivität des Live Agent-Tools erfordert eine Streaming-Ausgabe, ist für gepufferte Ausgabepfade nicht verfügbar und wird nicht aus dem Chat-Verlauf wiedergegeben. Das Scannen von Dateien ist auf Bereitstellungsebene standardmäßig deaktiviert und muss auch pro Wissensdatenbank aktiviert werden. Richtlinien für die Nichtverfügbarkeit des Scanners und nicht scannbare Dateien blockieren standardmäßig die Datei. Durch die Deaktivierung von NEXT_PUBLIC_ENABLE_HITL_IM werden gespeicherte Daten nicht zurückgesetzt oder bereits laufende serverseitige Arbeiten angehalten.

Reverse-Proxy- und Worker-Konfiguration

  • Neue API-Route: Leiten Sie im WEBHOOK-Modus /callbacks/human-input/v2/im/ an den API-Dienst (api:5001 in Docker Compose) weiter und behalten Sie dabei den Anforderungspfad, den Rohtext und die Anbietersignatur-Header bei. Die gebündelte Nginx-Vorlage enthält diese Regel bereits; Fügen Sie sein Äquivalent zu benutzerdefinierten Nginx-, Ingress- oder anderen Reverse-Proxy-Konfigurationen hinzu. Konfigurieren Sie den IM-Anbieter mit der generierten Rückruf-URL des Kanals. (#44864)
  • Neue Celery-Warteschlangen: Enthalten sind human_input_delivery für die asynchrone IM-Rückrufverarbeitung und Kartenaktualisierungen nach der Übermittlung sowie human_input_contact_sync für die Synchronisierung des IM-Kontaktverzeichnisses. Die Standard-Workerliste Docker enthält beide. Benutzerdefinierte CELERY_QUEUES-, CELERY_WORKER_QUEUES- oder Celery --queues-Listen müssen neben vorhandenen Abonnements einen aktiven Verbraucher für jede Warteschlange bereitstellen. (#44864)

Docker Umgebungsdateien

docker/envs/core-services/shared.env ist nicht mehr geladen. Verschieben Sie allgemeine API-, Worker- und Beat-Einstellungen nach api-worker.env, bevor Sie Container neu erstellen. Behalten Sie alle dienstspezifischen Einstellungen in der von diesem Dienst verwendeten Überschreibungsdatei bei. (#46497) Öffentliche URLs werden von Web, API und Workern über das neue envs/core-services/urls.defaults und das optionale urls.env gemeinsam genutzt:

  • CONSOLE_API_URL
  • CONSOLE_WEB_URL
  • SERVICE_API_URL
  • APP_API_URL
  • APP_WEB_URL Legen Sie über den Browser zugängliche Basis-URLs ohne die Suffixe /console/api, /api oder /v1 fest. Explizite Werte in urls.env überschreiben dienstspezifische URL-Einstellungen; root docker/.env überschreibt beide. Webs interner SERVER_CONSOLE_API_URL verbleibt in web.env. Dadurch wird auch ein Problem behoben, bei dem generierte Symbollinks bei Neuinstallationen auf 127.0.0.1:5001 verwiesen. (#46497)

Ältere Human-Input-Knoten werden nicht automatisch migriert und bleiben optiniert.

Upgrade-Anleitung

[!IMPORTANT] Verschieben Sie Einstellungen aus dem stillgelegten shared.env, bevor Sie Container neu erstellen. Überprüfen Sie öffentliche URLs, benutzerdefiniertes HITL-Callback-Routing und Worker-Abonnements. OpenShell-Bereitstellungen erfordern ein kompatibles Gateway-Upgrade und stellen keine Home-Snapshots mehr wieder her. Der gebündelte Plugin-Daemon wurde auf 0.6.15-local aktualisiert.

Bereiten Sie die Bereitstellung vor

  1. Daten und Konfiguration sichern. Sichern Sie Ihre Datenbank, Vector-Store-Daten, hochgeladene Dateien, den Plugin-Daemon-Speicher, den Agent-Workspace-Speicher, Bereitstellungsgeheimnisse und Umgebungsdateien. Planen Sie ein Wartungsfenster für ein Single-Stack-Upgrade.
  2. Aktualisieren Sie die Dify-Komponenten gemeinsam. Verwenden Sie passende 1.20.0 API-, Worker-, Web-, Agent-Backend- und lokale Sandbox-Images zusammen mit dem Plugin-Daemon 0.6.15-local. Behalten Sie SECRET_KEY, alle konfigurierten PASSWORD_PEPPER und das lokale Sandbox-Authentifizierungstoken unverändert bei. Persönliche Zugriffstoken hängen von SECRET_KEY ab; Stellen Sie sicher, dass für alle API-Replikate derselbe Wert verwendet wird. Wenn Sie ein Upgrade von einer Version vor 1.19.0 durchführen, befolgen Sie auch die Upgrade-Anleitung 1.19.0.
  3. shared.env migrieren. Wenn envs/core-services/api-worker.env nicht vorhanden ist, benennen Sie envs/core-services/shared.env in diesen Pfad um. Wenn beide vorhanden sind, führen Sie nur fehlende Einstellungen zusammen und behalten Sie vorhandene api-worker.env-Werte bei, einschließlich absichtlich leerer Zuweisungen. Behalten Sie dienstspezifische Einstellungen in der entsprechenden Dienstüberschreibungsdatei bei. Bereitstellungen ohne shared.env erfordern keine Migration.
  4. Öffentliche URLs konsolidieren. Erstellen Sie envs/core-services/urls.env aus urls.defaults nur, wenn es noch nicht vorhanden ist. Verschieben Sie die beabsichtigten öffentlichen URL-Werte dorthin und entfernen Sie dann doppelte Zuweisungen aus einzelnen Servicedateien. Vorhandene Root-.env-Werte behalten Vorrang. Behalten Sie das interne Web-API-Routing in web.env bei.
  5. Übernehmen Sie Umgebungs-, Routen- und Warteschlangenänderungen. Befolgen Sie die Konfigurations- und Integrationsänderungen, einschließlich der neuen HITL-Einstellungen, der IM-Rückrufroute und beider Celery-Warteschlangen.
  6. Lassen Sie die Initialisierung des Plugin-Speichers laufen. init_permissions bereitet nun auch ./volumes/plugin_daemon für die UID 1001 des Daemons vor und der Daemon wartet, bis der Vorgang abgeschlossen ist. Erstellen Sie die Bereitstellung mit docker compose up -d neu, damit der Init-Dienst ausgeführt wird. (#45615)

OpenShell-Bereitstellungen

Aktualisieren Sie das OpenShell-Gateway und SDK gemeinsam auf 0.1.3 oder höher innerhalb der unterstützten 0.1.x-Reihe und aktualisieren Sie Dify API und Agent Backend gemeinsam. Das Gateway muss die native Dienstfreigabe und Bearer-Passthrough unterstützen und dabei das von DIFY_AGENT_OPENSHELL_SHELLCTL_AUTH_TOKEN abgeleitete Autorisierungstoken pro Sandbox beibehalten. Halten Sie dieses Hauptgeheimnis für alle Agent-Backend-Replikate identisch. (#45862) Erstellen Sie das OpenShell-Laufzeitimage aus dem Release-Checkout und legen Sie DIFY_AGENT_OPENSHELL_SANDBOX_IMAGE auf die genaue Image-Referenz fest, die für die Rechenknoten des Gateways verfügbar ist. Das Bild muss sowohl shellctl als auch iproute2 enthalten; Einem älteren zwischengespeicherten Laufzeitabbild fehlen möglicherweise die erforderlichen Netzwerktools. Generieren Sie beim Upgrade vom vorherigen, gemeinsam genutzten, bereitstellungsweiten shellctl-Token ein neues Master-Geheimnis mit hoher Entropie und aktualisieren Sie alle Agent-Backend-Replikate gemeinsam. Lassen Sie aktive Arbeit ablaufen, stoppen Sie dann vorhandene Sandboxes und starten Sie sie neu, damit shellctl mit den abgeleiteten Anmeldeinformationen neu startet. Durch den erneuten Erwerb einer bereits fehlerfreien Sandbox werden deren Anmeldeinformationen nicht aktualisiert. Home-Snapshots für gemeinsam genutzte Volumes und DIFY_AGENT_OPENSHELL_SHARED_MOUNT_PATH werden entfernt. Vorhandene laufende Sandboxes behalten ihren Zustand über Stopp-/Neustartzyklen hinweg bei, während neu erstellte Bindungen vom Standard-Home des Images aus starten. DIFY_AGENT_OPENSHELL_DRIVER_CONFIG ist jetzt optional. Lesen Sie vor dem Upgrade den OpenShell-Bereitstellungsleitfaden, einschließlich der Anforderungen an das Laufzeit-Image. Andere Sandbox-Backends sind davon nicht betroffen.

Docker Verfassen

Sobald das 1.20.0-Tag und die Bilder veröffentlicht sind, stoppen Sie die Bereitstellung ordnungsgemäß, wechseln Sie zur Version, migrieren Sie lokale Konfigurationsdateien und rufen Sie dann die aktualisierten Dienste ab und starten Sie sie:

cd dify/docker
docker compose stop -t -1
git fetch --tags
git checkout 1.20.0
# Migrate shared.env, public URLs, and any custom proxy/worker configuration.

Englisches Original / English original

dify 1.20.0

Dify 1.20.0 keeps your traces flowing and your knowledge bases safer. Export traces to any OpenTelemetry collector, keep Langfuse working after its legacy ingestion endpoint retirement, and scan uploaded knowledge files for malware before they are indexed. Chatflows can show Agent tool activity as it happens, and personal access tokens let scripts and agents call the Dify OpenAPI on your behalf. The bundled plugin daemon is upgraded to 0.6.15-local.

New Features · Configuration and Integration Changes · Database Migrations · Upgrade Guide

New Features

New HITL: bring approvals into your team's messaging tools

Integrate human review into your workflows via email and the messaging tools your team already uses. New HITL introduces shared channels, centralized contacts, notification templates, and verified approval forms—allowing your team to configure recipients once and reuse them across Human Input nodes, and is now enabled by default (NEXT_PUBLIC_ENABLE_HITL_IM=true). (#44864, #45945)

  • Reach approvers where they work. Configure email and an IM platform—Slack, Feishu/Lark, Microsoft Teams, DingTalk, or WeCom—to deliver workflow review requests through your team's existing channels.
  • Manage recipients in Contacts. Sync IM directories and select approvers from a shared contact list. Workflows can also address the initiator or use one-time and dynamic email recipients.
  • Approve in cards or forms. Recipients can review requests directly in supported IM cards or open standalone forms, with Dify login or email verification to verify their identity.
  • Customize notifications with workflow context. Use templates and workflow variables to include essential context in notification subjects and bodies.
  • Test and track delivery. Send test notifications to verify your setup and inspect delivery records to troubleshoot requests that did not arrive as expected.
  • Adopt New HITL in existing workflows. Use opt-in migration to upgrade legacy Human Input nodes when your workflow is ready.

Deployment requirements are listed under Configuration and Integration Changes.

Export traces to any OpenTelemetry collector

Bring Dify execution traces into your existing observability stack. The new OpenTelemetry provider exports app and Agent traces to any compatible collector, allowing you to track workflow steps, model calls, and tool activity together in your preferred platform. Use these traces to inspect request execution and diagnose failures without requiring a vendor-specific Dify integration. (#45659)

Langfuse tracing now supports Langfuse v4 and the current Langfuse Cloud ingestion service. Existing Langfuse configurations continue to work. (#45606)

[!IMPORTANT] Langfuse Cloud retired its legacy ingestion endpoint on November 16, 2026, and self-hosted Langfuse v4 rejects events sent to it. Upgrade to 1.20.0 to keep delivering traces to those deployments.

Scan knowledge uploads for malware

Protect your knowledge bases by scanning uploaded files for malware before they are extracted or indexed. When enabled (FILE_SCAN_ENABLED=true), workspace owners and admins can configure scanners once under Integrations → File Security Scan, then define how each knowledge base uses them. Supported scanners include Cloudmersive, Scanii, OPSWAT MetaDefender Cloud, and a Custom Endpoint. (#46090, #46492)

  • Choose protection per knowledge base. Select a scanner and configure fallback behavior when scanning is unavailable or a file cannot be scanned.
  • Protect knowledge uploads across Dify. Scanning covers classic knowledge bases, RAG Pipeline local-file sources, and Agent Knowledge Base uploads.
  • See why files were blocked. Scan failures appear in the document list for review.

Watch Agent tools work in Chatflow

When a Chatflow delegates tasks to an Agent v2 node (requires NEXT_PUBLIC_ENABLE_AGENT_V2_IN_CHATFLOW=true), users can now see which tools it invokes in real time. Tool activity appears alongside the response in both previews and published chats, making it easier to follow the Agent's progress. Expand any tool card to inspect what it requested and returned. (#46220)

Automate OpenAPI calls with personal access tokens

Grant scripts, CI jobs, and personal agents access to the Dify OpenAPI on your behalf without sharing your Console session. Create a personal access token from your Account page and scope it to specific workspaces and resources. You can set an optional expiration date, update its scope as your automation evolves, or revoke it when it is no longer needed. (#45540, #46606)

Choose GitHub knowledge sources from a tree

Browse and select the GitHub content you want to add to a knowledge base from an expandable tree of repositories, directories, issues, and pull requests. Explore the source structure and pick the exact pages to import, whether you are creating a new knowledge base or adding a source to an existing one. (#45990)

Search and navigate on smaller screens

Search across content and narrow results using selectable scopes in Goto Anything. On smaller screens, search and navigation open in drawers to preserve space for the current page. (#45675, #45650)

Direct links can now open Studio's blank-app or template creation flows. (#45717)

More flexible knowledge descriptions and metadata

  • Longer knowledge base descriptions. Increased description length limits allow you to provide more context for each knowledge base. (#45075)
  • External knowledge metadata. External knowledge retrieval now returns document metadata alongside content. (#22496)

Improvements

Lower database and startup overhead. Node execution updates avoid reloading stored rows, credential policies are evaluated once per provider configuration, model defaults use short-lived sessions, and embedding calls no longer hold open a database session. Web feature dependencies also load more lazily. (#46410, #46441, #45806, #45788, #46145)

Clearer document failures and steadier layouts. Knowledge documents now report specific failure reasons and processing stages. Dialogs adapt to narrow viewports and maintain consistent lifecycles across accounts, knowledge, apps, Skills, and workflows. Authentication pages load faster, fit smaller screens, and keep keyboard focus accessible. Segmented controls animate smoothly while preserving compact layouts and respecting reduced-motion preferences. (#45128, #46487, #45686, #45668, #45634, #45600, #45640, #45974)

Bug Fixes

  • Safer file previews and signed links. Sandbox inline SVG previews and verify the original signature before renewing expired file links. (#46505)
  • Stronger access protection. Redact node-retry details from public streams, prevent OAuth callback reuse, enforce member-role permissions, and scope vector deletion to the target dataset. (#46517, #46001, #46053, #45586)
  • Security dependency updates. Upgrade github.com/klauspost/compress in dify-agent-runtime to address CVE-2026-116591, and update Node.js in runtime images to security release 24.22.3. (#46544, #46206, #46064)
  • Reliable blocking workflows. Release database connections before execution and return preparation failures immediately, preventing connection-pool exhaustion and hanging requests that wait until timeout. (#46254)
  • More stable workers. Resolve the Redis BRPOP busy loop and prevent overlapping plugin upgrade checks, capping concurrency at 20 checks across workers. (#45940, #46500)
  • Complete Chatflow streams. Properly close streams after direct replies and reset the reconnect budget when a stream resumes. (#45552, #46110)
  • Correct Agent execution. Preserve parallel calls to the same plugin tool, pass declared app inputs to Agent runs, and deliver uploaded images to vision models. (#45207, #45425, #45745)
  • Accurate knowledge retrieval. Restore Weaviate keyword/hybrid results by returning BM25 scores, and keep embedding vectors aligned when a batch item is dropped. (#45642, #45569)
  • Reliable custom API tools. Resolve OpenAPI server variables, percent-encode path parameters, and support OpenAPI 3.1 nullable unions. (#46504, #45965, #45895)

(#46616) |

For Docker Compose, configure shared backend overrides in envs/core-services/api-worker.env and Web overrides in envs/core-services/web.env. Root docker/.env takes precedence. Apply changes with docker compose up -d; a plain restart does not reload environment files.

The OpenTelemetry provider supports OTLP/HTTP with protobuf; gRPC is not supported. Live Agent tool activity requires streaming output, is unavailable for buffered-output paths, and is not replayed from chat history.

File scanning is disabled by default at the deployment level and must also be enabled per knowledge base. Policies for scanner unavailability and unscannable files both default to blocking the file.

Disabling NEXT_PUBLIC_ENABLE_HITL_IM does not roll back saved data or halt server-side work already in progress.

Reverse proxy and worker configuration

  • New API route: In WEBHOOK mode, forward /callbacks/human-input/v2/im/ to the API service (api:5001 in Docker Compose), preserving the request path, raw body, and provider signature headers. The bundled nginx template already includes this rule; add its equivalent to custom nginx, Ingress, or other reverse proxy configurations. Configure the IM provider with the channel's generated Callback URL. (#44864)
  • New Celery queues: Include human_input_delivery for asynchronous IM callback processing and post-submission card updates, and human_input_contact_sync for IM contact directory synchronization. The default Docker worker list includes both. Custom CELERY_QUEUES, CELERY_WORKER_QUEUES, or Celery --queues lists must provide an active consumer for each queue alongside existing subscriptions. (#44864)

Docker environment files

docker/envs/core-services/shared.env is no longer loaded. Move common API, worker, and Beat settings to api-worker.env before recreating containers. Preserve any service-specific settings in the override file used by that service. (#46497)

Public URLs are shared by Web, API, and workers through the new envs/core-services/urls.defaults and optional urls.env:

  • CONSOLE_API_URL
  • CONSOLE_WEB_URL
  • SERVICE_API_URL
  • APP_API_URL
  • APP_WEB_URL

Set browser-accessible base URLs without /console/api, /api, or /v1 suffixes. Explicit values in urls.env override service-specific URL settings; root docker/.env overrides both. Web's internal SERVER_CONSOLE_API_URL remains in web.env. This also resolves an issue where generated icon links pointed to 127.0.0.1:5001 on fresh installations. (#46497)

Database Migrations

Upgrading from 1.19.0 adds six migration revisions, moving the migration head from 53c10126d551 to f8b6e2c4a901. Apply the complete Alembic chain through the normal migration runner.

| Revision | Change | | --- | --- | | 6b7e2a9c4d10 | Add nullable started_by_sys_user_id to human_input_im_sync_runs and require exactly one initiating identity per row. | | b2e4c6d8a013 | Add personal access tokens and their resource/workspace scope tables. | | 8c2f5d7a1e30 | Add file scanner, scan policy, and scan-result tables. | | 91f4b2d7c8e0 | Add Evaluation configuration, run, and run-item tables. | | c7e4a1b2d9f0 | Add the Evaluation framework column with a default value. | | f8b6e2c4a901 | Merge the Evaluation and main migration branches. |

The Evaluation migrations apply to the Community Edition as well, even though CE does not expose the Evaluation feature. Include these revisions when applying the migration chain; none of the six revisions require a separate manual backfill command. (#45945, #45540, #46090, #46141)

New HITL introduces the necessary database schema and automatically backfills Contact identities for existing accounts with no extra commands required. These migrations are already included in 1.19.0—existing 1.19.0 deployments need no action, while older versions should run the full migration chain. Legacy Human Input nodes are not automatically migrated and remain opt-in.

Upgrade Guide

[!IMPORTANT] Move settings out of the retired shared.env before recreating containers. Review public URLs, custom HITL callback routing, and worker subscriptions. OpenShell deployments require a compatible gateway upgrade and no longer restore Home Snapshots. The bundled plugin daemon is updated to 0.6.15-local.

Prepare the deployment

  1. Back up data and configuration. Back up your database, vector-store data, uploaded files, plugin daemon storage, Agent workspace storage, deployment secrets, and environment files. Schedule a maintenance window for a single-stack upgrade.
  2. Upgrade the Dify components together. Use matching 1.20.0 API, worker, Web, Agent Backend, and Local sandbox images, alongside plugin daemon 0.6.15-local. Keep SECRET_KEY, any configured PASSWORD_PEPPER, and the Local sandbox authentication token unchanged. Personal access tokens depend on SECRET_KEY; ensure the same value is used across all API replicas. If upgrading from a version earlier than 1.19.0, also follow the 1.19.0 upgrade guide.
  3. Migrate shared.env. If envs/core-services/api-worker.env does not exist, rename envs/core-services/shared.env to that path. If both exist, merge only missing settings and preserve existing api-worker.env values, including intentional empty assignments. Retain service-specific settings in the appropriate service override file. Deployments without shared.env require no migration.
  4. Consolidate public URLs. Create envs/core-services/urls.env from urls.defaults only if it does not already exist. Move the intended public URL values there, then remove duplicate assignments from individual service files. Existing root .env values retain precedence. Keep internal Web API routing in web.env.
  5. Apply environment, route, and queue changes. Follow Configuration and Integration Changes, including the New HITL settings, IM callback route, and both Celery queues.
  6. Let plugin storage initialization run. init_permissions now also prepares ./volumes/plugin_daemon for the daemon's UID 1001, and the daemon waits for it to complete. Recreate the deployment with docker compose up -d so the init service runs. (#45615)

OpenShell deployments

Upgrade the OpenShell gateway and SDK together to 0.1.3 or later within the supported 0.1.x line, and upgrade the Dify API and Agent Backend together. The gateway must support native service exposure and bearer passthrough, preserving the per-sandbox authorization token derived from DIFY_AGENT_OPENSHELL_SHELLCTL_AUTH_TOKEN. Keep that master secret identical across Agent Backend replicas. (#45862)

Build the OpenShell runtime image from the release checkout and set DIFY_AGENT_OPENSHELL_SANDBOX_IMAGE to the exact image reference available to the gateway's compute nodes. The image must include both shellctl and iproute2; an older cached runtime image may lack the required networking tools.

When upgrading from the previous shared deployment-wide shellctl token, generate a fresh high-entropy master secret and update all Agent Backend replicas together. Drain active work, then stop and restart existing sandboxes so shellctl restarts with the derived credential. Reacquiring an already healthy sandbox does not refresh its credential.

Shared-volume Home Snapshots and DIFY_AGENT_OPENSHELL_SHARED_MOUNT_PATH are removed. Existing running sandboxes retain their state across stop/restart cycles, whereas newly created Bindings start from the image's default Home. DIFY_AGENT_OPENSHELL_DRIVER_CONFIG is now optional. Review the OpenShell deployment guide, including its runtime-image requirements, before upgrading. Other sandbox backends are unaffected.

Docker Compose

Once the 1.20.0 tag and images are published, stop the deployment gracefully, switch to the release, migrate local configuration files, and then pull and start the updated services:

cd dify/docker
docker compose stop -t -1
git fetch --tags
git checkout 1.20.0
# Migrate shared.env, public URLs, and any custom proxy/worker configuration.
docker compose pull
docker compose up -d

Keep API startup migrations enabled (MIGRATION_ENABLED=true), or apply the full migration chain through your managed migration process before starting new workers. Use docker compose up -d after changing environment files; a plain restart does not reload them.

Source deployments

Use Python 3.13, Node.js 24.22.3 or later in the 24.x line, and pnpm 12.18.0. After stopping the services and switching to the release, run the following commands from the repository root:

uv sync --project api --frozen
uv run --directory api flask db upgrade
pnpm install --frozen-lockfile

Rebuild Web and restart the API, workers, scheduler, and Agent services from the same release. Update the standalone Agent Backend's locked dependencies if deploying it separately. Preserve existing worker subscriptions and add the two HITL queues where needed.
