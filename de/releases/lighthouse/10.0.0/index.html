Bemerkenswerte Änderungen

Änderungen der Leistungsbewertung

In der Veröffentlichung 8.0 haben wir [die abnehmende Rolle von TTI beschrieben] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/v8-perf-faq.md#whats-the-story-with-tti), und heute haben wir die Nachfolge. Time to Interactive (TTI) trägt nicht mehr zur Leistungsbewertung bei und wird nicht im Bericht angezeigt. Im Lighthouse-Ergebnis JSON ist es jedoch weiterhin zugänglich. Ohne TTI hat sich die Gewichtung des Cumulative Layout Shift (CLS) von 15 % auf 25 % erhöht. Eine vollständige Aufschlüsselung wie die Leistungsbewertung in 10.0 berechnet wird finden Sie in den Dokumenten oder mit dem Bewertungsrechner spielen.

Typen für das Node-Paket

Lighthouse enthält jetzt Typdeklarationen! Unser [Beispielrezept für TypeScript] (https://github.com/GoogleChrome/lighthouse/tree/main/docs/recipes/type-checking) zeigt, wie man mit Lighthouse die richtige Typensicherheit erreicht.

Klassifizierung von Drittanbieter-Entitäten

Seit Lighthouse 5.3 wird der von der Community betriebene Datensatz third-party-web verwendet, um über das third-party-summary-Audit zusammenzufassen, wie jeder auf einer Seite gefundene Drittanbieter zur gesamten JavaScript-Blockierungszeit beiträgt. Mit Lighthouse 10.0 fügen wir dem JSON-Ergebnis (entities) eine neue Eigenschaft hinzu, um diesen Datensatz weiter zu nutzen. Jeder auf einer Seite gefundene Ursprung wird jetzt innerhalb von entities als Erstanbieter oder Drittanbieter klassifiziert. In 10.0 wird diese Klassifizierung verwendet, um das vorhandene Kontrollkästchen für Drittanbieterfilter zu aktivieren. In einer zukünftigen Version von Lighthouse wird dies verwendet, um die Tabellenelemente jedes Audits basierend auf der Entität, von der es stammt, zu gruppieren und die Auswirkungen der Elemente dieser bestimmten Entität zu aggregieren.

🆕 Neue Audits

Zurück/Vorwärts-Cache

Der Back/Forward-Cache (kurz bfcache) ist eine Browseroptimierung, die Seiten aus vollständig serialisierten Snapshots bereitstellt, wenn im Sitzungsverlauf vor oder zurück navigiert wird. Es gibt über 100 verschiedene Gründe, warum eine Seite möglicherweise nicht für diese Optimierung geeignet ist. Um Entwicklern zu helfen, versucht Lighthouse nun, eine Bfcache-Antwort auszulösen und listet alles auf, was den Browser daran gehindert hat, den Bfcache zu verwenden. #14465 Weitere Informationen zu bfcache finden Sie im web.dev-Artikel. Hinweis: Dieses Audit wird zunächst nicht für PageSpeed ​​Insights verfügbar sein.

Verhindern des Einfügens in Eingaben

Das Audit password-inputs-can-be-pasted-into ist jetzt paste-preventing-inputs. Die Logik dieser Prüfung funktioniert genauso wie zuvor, aber anstatt nur [type=password]-Eingaben zu berücksichtigen, schlägt sie jetzt fehl, wenn irgendein nicht schreibgeschütztes Eingabeelement den Benutzer am Einfügen hindert. #14313

Lighthouse-Dokumentation ist jetzt auf Developer.chrome.com

Unsere Dokumentation wird nicht mehr auf web.dev gehostet. Die aktuellsten Prüfdokumente finden Sie unter developer.chrome.com/docs/lighthouse/.

💥 Bahnbrechende Veränderungen

Unter der Haube nutzt Lighthouse jetzt standardmäßig die neue Infrastruktur zur Unterstützung des Benutzerflusses, auch für herkömmliche Navigationsläufe. Sie können dies deaktivieren, indem Sie im CLI --legacy-navigation verwenden. in DevTools: Aktivieren Sie „Legacy Navigation“ im Einstellungsmenü. Wenn Sie einen Anwendungsfall haben, der diese Notluke erfordert, reichen Sie bitte ein Problem ein. Wir planen, diesen alten Pfad in 11.0 zu entfernen.

Für Benutzer des Lighthouse-Ergebnisses JSON (LHR).

Seiten-URLs zum Lighthouse-Ergebnis

Bisher gab es zwei URL-Felder zur Beschreibung eines Lighthouse-Laufs:

  • requestedUrl: die von den Benutzern angegebene URL, zu der Lighthouse Chrome anweist, zu navigieren – finalUrl: die URL nach allen vom Server initiierten HTTP- und JS-initiierten Weiterleitungen Diese Taxonomie kann komplexere Szenarien wie JS-initiierte Weiterleitungen, die Verwendung des Verlaufs API oder Soft-Navigationen nicht berücksichtigen. Sie waren auch für die Zeitspannen- und Snapshot-Modi schlecht definiert. Um dies zu berücksichtigen, verfügt Lighthouse 10.0 jetzt über diese URL-Felder: – (geändert) requestedUrl: Die URL, zu der Lighthouse vor der Weiterleitung zunächst navigiert hat. Dies ist dasselbe wie zuvor für den Navigationsmodus, aber jetzt ist es undefined in Zeitspanne/Schnappschuss.
  • (neu) mainDocumentUrl: Die URL des zuletzt während einer Navigation angeforderten Dokuments. Soft-Navigationen oder Verlaufsereignisse nach dem Laden der Seite werden nicht berücksichtigt. Es ist nur im Navigationsmodus verfügbar und ist im Zeitspannen- und Snapshot-Modus nicht definiert.
  • (neu) finalDisplayedUrl: Die URL, die am Ende eines Lighthouse-Laufs in der Browser-Combobox angezeigt wird. Es berücksichtigt Soft-Navigationen und historische API-Ereignisse. Verfügbar in den Modi Navigation, Zeitspanne und Schnappschuss. – (veraltet) finalUrl: Gleicher Wert wie mainDocumentUrl.

Änderungen prüfen

  • password-inputs-can-be-pasted-into -> paste-preventing-inputs
  • preload-lcp-image -> prioritize-lcp-image – third-party-summary verwendet nicht mehr einen link-Wert für item.entity, sondern einen rohen text-Wert
  • full-page-screenshot ist kein Audit mehr, sondern wird unter lhr.fullPageScreenshot gespeichert. Um die Erfassung des ganzseitigen Screenshots im CLI zu unterdrücken, müssen Sie von --skip-audits full-page-screenshot auf --disable-full-page-screenshot migrieren.

Für Node-Benutzer

  • Knoten 14 wird nicht mehr unterstützt, das Minimum ist jetzt Knoten 16 – Falls Sie Pfade innerhalb des Lighthouse-Knotenpakets importieren: Die Ordner lighthouse-core/ und lighthouse-cli/ heißen jetzt einfach core/ und cli/
  • Konvertiert von CommonJS- in ES-Module. Sie können Lighthouse weiterhin in CommonJS verwenden, indem Sie einen dynamischen Import verwenden: await import('lighthouse'). Für den Zugriff nur auf die Funktion lighthouse in CommonJS können Sie auch require('lighthouse/core/index.cjs') verwenden
  • Die CSV-Ausgabe für Lighthouse ist jetzt viel nützlicher. Konsultieren Sie die PR für ein Beispiel des neuen Formats
  • LHError ist jetzt LighthouseError. Wenn Sie versuchen, einen von Lighthouse ausgelösten Fehler abzufangen, müssen Sie diesen unbedingt berücksichtigen!

Knoten API ändert sich

Die Funktion lighthouse verfügt jetzt über eine [bessere Integration mit Puppeteer] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/puppeteer.md). Verwenden Sie lighthouse(url, flags, config, page), um Lighthouse auszuführen, und übergeben Sie ein vorhandenes Puppeteer.Page-Handle als page. Der Benutzerfluss api wurde zum Knoteneinstiegspunkt der obersten Ebene verschoben und kann mit import {startFlow} from 'lighthouse' importiert werden. Mit den neuen Funktionen flow.startNavigation() und flow.endNavigation() können Sie eine vom Benutzer ausgelöste Navigation ohne Rückruffunktion definieren. [Ein Beispiel] finden Sie in den Benutzerablaufdokumenten (https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md#triggering-a-navigation-via-user-interactions). Um Einstellungen für einen einzelnen Benutzerflussschritt zu ändern, definieren Sie die Einstellungsüberschreibungen für die Flag-Optionen der obersten Ebene flow.snapshot({skipAduits: ['uses-http2']}) statt für die Eigenschaft settingsOverride. Um einem Flow-Schritt einen benutzerdefinierten Namen zu geben, verwenden Sie flow.snapshot({name: 'Custom name'}). Bisher erfolgte dies über stepName.

Für die Lighthouse-Anpassung (benutzerdefinierte Konfiguration, Gatherer, Audits)

– Um in Lighthouse 10.0 zu funktionieren, müssen benutzerdefinierte Gatherer die neue Gatherer-Schnittstelle implementieren (ein Beispiel). Andernfalls funktionieren sie nur im Legacy-Navigationsmodus und älteren Versionen von Lighthouse

  • Lighthouse kann passes nicht mehr verwenden, um die Seite im Navigationsmodus mehrmals zu laden. Wenn Sie die Seite mehrmals laden müssen, empfehlen wir die Verwendung eines Benutzerflusses. Anweisungen zum Konvertieren in das neue Konfigurationsformat finden Sie in unseren Konfigurationsdokumenten (https://github.com/GoogleChrome/lighthouse/blob/main/docs/configuration.md#legacy-configs). – Das ScriptElements-Artefakt heißt jetzt Scripts, mit einer etwas anderen Form
  • Audit.makeOpportunityDetails und Audit.makeTableDetails akzeptieren jetzt ein Optionsobjekt als dritten Parameter. Dies ist letztendlich eine bahnbrechende Änderung für nur Audit.makeOpportunityDetails.

Notable Changes

Performance Score Changes

In the 8.0 release, we described TTI's waning role, and today we have the followup. Time to Interactive (TTI) no longer contributes to the performance score and is not displayed in the report. However, it is still accessible in the Lighthouse result JSON.

Without TTI, the weighting of Cumulative Layout Shift (CLS) has increased from 15% to 25%. See the docs for a complete breakdown of how the Performance score is calculated in 10.0, or play with the scoring calculator.

Types for the Node package

Lighthouse now includes type declarations! Our example TypeScript recipe demonstrates how to achieve proper type safety with Lighthouse.

Third-party Entity classification

Since Lighthouse 5.3, the community-driven third-party-web dataset has been used to summarize how every third-party found on a page contributes to the total JavaScript blocking time, via the third-party-summary audit. With Lighthouse 10.0, we are adding a new property to the JSON result (entities) to make further use of this dataset. Every origin encountered on a page is now classified as first-party or third-party within entities. In 10.0, this classification is used to power the existing third-party filter checkbox.

In a future version of Lighthouse, this will be used to group the table items of every audit based on the entity it originated from, and aggregate the impact of items from that specific entity.

🆕 New Audits

Back/forward cache

The Back/forward cache (bfcache for short) is a browser optimization that serves pages from fully serialized snapshots when navigating back or forwards in session history. There are over 100 different reasons why a page may not be eligible for this optimization, so to assist developers Lighthouse now attempts to trigger a bfcache response and will list anything that prevented the browser from using the bfcache. #14465

For more on bfcache, see the web.dev article.

Note: This audit initially will not be available for PageSpeed Insights.

Preventing pasting to inputs

The audit password-inputs-can-be-pasted-into is now paste-preventing-inputs. This audit's logic works just as before, but rather than just considering [type=password] inputs, it now fails if any non-readonly input element prevents the user from pasting. #14313

Lighthouse documentation is now on developer.chrome.com

Our documentation is no longer hosted on web.dev. For the most up to date audit docs, please go to developer.chrome.com/docs/lighthouse/

💥 Breaking changes

Under the hood, Lighthouse now uses the new user-flow supporting infrastructure by default, even for traditional navigation runs. You can opt out of this by: in the CLI, use --legacy-navigation; in DevTools: check “Legacy Navigation” in the settings menu. If you have a use case that necessitates this escape hatch, please file an issue. We plan to remove this legacy path in 11.0.

For Lighthouse result JSON (LHR) users

Page URLs on the Lighthouse Result

Until now, there were two URL fields to describe a Lighthouse run:

  • requestedUrl: the url given by the users, which Lighthouse instructs Chrome to navigate to
  • finalUrl: the url after any server-initiated HTTP and JS-initiated redirects

This taxonomy cannot account for more complex scenarios, such as JS-initiated redirects, usage of the History API or soft-navigations. They were also ill-defined for timespan and snapshot modes. To account for that, Lighthouse 10.0 now has these URL fields:

  • (changed) requestedUrl: The URL that Lighthouse initially navigated to before redirects. This is the same as it was before for navigation mode, but now it will be undefined in timespan/snapshot.
  • (new) mainDocumentUrl: The URL of the last document requested during a navigation. It does not account for soft navigations or history API events made after the page loads. It is only available in navigation mode, and will be undefined in timespan and snapshot modes.
  • (new) finalDisplayedUrl: The URL displayed in the browser combobox at the end of a Lighthouse run. It accounts for soft navigations and history API events. Available in navigation, timespan, and snapshot modes.
  • (deprecated) finalUrl: Same value as mainDocumentUrl.

Audit changes

  • password-inputs-can-be-pasted-into -> paste-preventing-inputs
  • preload-lcp-image -> prioritize-lcp-image
  • third-party-summary no longer uses a link value for item.entity, instead uses a raw text value
  • full-page-screenshot is no longer an audit, instead it is stored at lhr.fullPageScreenshot. To suppress collection of the full-page screenshot in the CLI, you must migrate from --skip-audits full-page-screenshot to --disable-full-page-screenshot.

For Node users

  • Node 14 is no longer supported, the minimum is now Node 16
  • In case you import paths within the lighthouse node package: lighthouse-core/ and lighthouse-cli/ folders are now simply core/ and cli/
  • Converted from CommonJS to ES modules. You can still use lighthouse in CommonJS by using an dynamic import: await import('lighthouse'). For access to just the lighthouse function in CommonJS, you can also use require('lighthouse/core/index.cjs')
  • The CSV output for Lighthouse is much more useful now. Consult the PR for an example of the new format
  • LHError is now LighthouseError. If you are attempting to catch an error thrown by Lighthouse, be sure to account for this!

Node API changes

The lighthouse function now has better integration with Puppeteer. Use lighthouse(url, flags, config, page) to run Lighthouse, passing an existing Puppeteer.Page handle as page.

The user flow api has moved to the top level node entrypoint and can be imported with import {startFlow} from 'lighthouse'.

New flow.startNavigation() and flow.endNavigation() functions let you define a user triggered navigation without any callback function. See the user flow docs for an example.

To change settings for a single user flow step, define the settings overrides on the toplevel flags options flow.snapshot({skipAduits: ['uses-http2']}) instead of on the settingsOverride property.

To give a flow step a custom name, use flow.snapshot({name: 'Custom name'}). Previously this was done via stepName.

For Lighthouse customization (custom config, gatherers, audits)

  • To work in Lighthouse 10.0, custom gatherers will need to implement the new Gatherer interface (an example). Otherwise, they will only work in legacy navigation mode and older versions of Lighthouse
  • Lighthouse cannot use passes to load the page multiple times in navigation mode anymore. If you need to load the page multiple times, we recommend using a user flow. See our config docs for instructions on how to convert to the new config format
  • The ScriptElements artifact is now Scripts, with a slightly different shape
  • Audit.makeOpportunityDetails and Audit.makeTableDetails now accept an options object as the third parameter. This ends up being a breaking change for just Audit.makeOpportunityDetails.
