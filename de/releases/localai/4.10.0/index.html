LocalAI 4.10.0 ist da!

28 Tage und 280 Pull-Anfragen. Die Arbeit fiel an drei Fronten: Betrieb einer Flotte, Bereitstellung von Modellen aus privaten Quellen und Reparatur der Backends, auf die Sie angewiesen sind. Ein Flottenbetriebs-Dashboard ersetzt die flache Knotenliste durch Cluster-weite Aktionen zu Zustand, Kapazität, laufenden Modellen und Massenlebenszyklus. Mit einer Anmeldeinformationsdatei kann ein credentials.yaml OCI-Register, Galerien und direkte Downloads authentifizieren, ohne Token über Umgebungsvariablen zu verteilen. Und local-ai benchmark misst die End-to-End-Latenz und den Durchsatz des CLI.

Das ds4-Backend hatte vier Korrekturen, die es zusammengenommen auf CUDA zuverlässig machen: Die Kernel werden jetzt für die Zielarchitektur erstellt, aufgegebene Inferenzen werden abgebrochen, Generationsgrenzen werden durchgesetzt und vorab ausgefüllte Argumente werden vom Inhalt getrennt. Der verteilte Modus erhielt sieben Stabilisierungskorrekturen für Staging, Lebendigkeit, virtuelle Modelle und die Datenbank der Steuerungsebene. Vier CVEs wurden gepatcht, enable_thinking=false wird jetzt in jedem Text-Backend berücksichtigt und Apple M5 gibt beim Start keine SIGSEGVs mehr aus.

Highlights:

  • 📊 Flottenbetriebs-Dashboard – eine Echtzeit-Clusterübersicht, die die flache Knotenliste ersetzt. Aggregierte Integritätsbänder, Kapazitätsanzeigen für VRAM/RAM/CPU/Festplatte, eine Registerkarte für laufende Modelle, die die Replikatplatzierung zwischen den Workern zeigt, Massenentnahme/-fortsetzung/-entfernung mit begrenzter Parallelität und ein ausziehbarer Knoteninspektor. Mitarbeiter melden jetzt CPU-Telemetriedaten bei der Registrierung und beim Heartbeat.
  • 🔑 Anmeldeinformationsdatei für private Quellen – ein credentials.yaml authentifiziert OCI-Register, Galerien, HTTP-Downloads und github:-URIs. Unterstützt Basisauthentifizierung, Bearer-Tokens und benutzerdefinierte Header, wobei Geheimnisse zum Zeitpunkt der Nutzung gelesen werden, sodass rotierte K8s-Geheimnis-Mounts ohne Neustart wirksam werden, und vollständige Maskierung in Protokollen und Fehlermeldungen.
  • 📏 local-ai benchmark CLI-Befehl – misst die End-to-End-Latenz und den Durchsatz anhand konfigurierter Textmodelle. Meldet minimale/mittlere/maximale Latenz und Abschluss-Tokens/Sek. über Aufwärm- und Messläufe hinweg, mit Tabellen- und JSON-Ausgabe, Umleitungsblockierung und API-Schlüssel-Schwärzung.
  • 🔧 vllm-cpp LoRA-Fusion zur Ladezeit – lora_adapters und lora_scales werden jetzt von der vllm-cpp-Video-Engine verbraucht, wodurch LoRA-Deltas bei Motorlast in DiT-Gewichte fusioniert werden. Funktioniert sowohl für LTX2.5 als auch für MiniMax-H3 über einen generischen Pfad.
  • 🌍 Umgebungsvariablen pro Modell – eine env:-Zuordnung in der Modellkonfiguration fügt Variablen in die Backend-Prozessumgebung ein, sodass CUDA_VISIBLE_DEVICES oder VLLM_CACHE_DIR pro Modell angeheftet werden können, ohne das Backend in ein Skript einzubinden.
  • 💬 template.system_messages_after_first – Agent-Frameworks, die während des Gesprächs Systemanweisungen anhängen, stürzen Qwen3.x-Modelle nicht mehr ab. Verspätete Systemrunden können in die führende Systemnachricht eingefügt oder als Benutzerrunden weitergeleitet werden.
  • 🧠 context_size in /v1/models/capabilities - clients können jetzt das effektive Kontextfenster jedes Modells lesen, um Token zu budgetieren und Eingabeaufforderungen zu kürzen, ohne die Modellkonfiguration außerhalb des Bandes zu prüfen.
  • 🛡️ Vier CVEs gepatcht – IP-Adresse 10.3.1 (CVE-2026-69192), Container 1.7.32 und 1.7.33 (CVE-2026-46680, CVE-2026-53488) und React-Router (GHSA-qwww-vcr4-c8h2).
  • 🍎 Apple M5 SIGSEGV behoben – go-m1cpu stieg auf v0.2.2, wodurch ein Segmentierungsfehler auf der Apple M5-Hardware beim Start behoben wurde. Plus eine Fokusmodus-Umschaltung in den Chat-Einstellungen, Wiederholung der Gesichtsregistrierung für die 1:N-Registrierung, ein ROCm-Build von stablediffusion-ggml, direkte Bearbeitung verteilter Planungsregeln, Wiederaufnahme des OCI-Layer-Downloads und 140 neue Galerieeinträge.

🚀 Neue Funktionen und wichtige Verbesserungen

📊 Dashboard für den Flottenbetrieb

Die Seite „Knoten“ war eine flache Liste von Karten pro Knoten. Es zeigte Ihnen, was registriert wurde, aber nicht, was der Cluster tat, und jede Lebenszyklusaktion betraf jeweils einen Knoten.

Bei der Neufassung handelt es sich um ein Flottenbetriebs-Dashboard mit zwei Registerkarten und einem gemeinsamen Zusammenfassungs-Poller.

ClusterOverview steht ganz oben. Ein Gesundheitsband segmentiert Knoten in gesunde, erschöpfende und aufmerksamkeitsbezogene Knoten. Kapazitätsanzeigen zeigen VRAM, RAM, CPU und Festplatte und geben jeweils an, wie viele Worker diese Kennzahl nicht melden, sodass die Zahl ehrlich ist und nicht über die Berichtsknoten gemittelt wird. Eine Aufmerksamkeitswarteschlange filtert nach ausstehender Genehmigung, offline/fehlerhaft, niedrigem VRAM, niedrigem RAM und niedrigem Festplattenspeicher und zeigt Knoten an, bei denen Maßnahmen erforderlich sind, ohne dass die Gesamtsumme doppelt gezählt wird. NodeFleetTable ist sortierbar, gruppierbar (nach Beschriftung oder Typ) und mit 50 Zeilen pro Seite paginiert, wobei die Kontrollkästchenauswahl über Filter und Seiten hinweg bestehen bleibt. Bulk Drain, Resume und Remove laufen mit begrenzter Parallelität (Limit 8), sodass eine Flotte mit Tausenden von Registrierungen nutzbar ist. Spalten: Statuspille, Adresse, Kapazität (VRAM + RAM), CPU, Arbeitslast und Heartbeat. Auf ausstehenden Knoten wird eine Schaltfläche „Genehmigen“ angezeigt.

Registerkarte „Laufende Modelle“. Eine flottenweite Ansicht der geladenen Replikate auf fehlerfreien Arbeitern, gruppiert nach Modell: Modellname, Replikatanzahl, Knotenanzahl, laufende Anfragen, Backend-Typen und zuletzt verwendet. Pro-Modell-Stop fährt alle Platzierungen über POST /backend/shutdown {model} herunter, das jetzt den Remote-Unloader auslöst, selbst wenn ein lokaler Prozess vorhanden ist, und Knoten dedupliziert, bevor Stoppnachrichten gesendet werden.

Inspektoren. Ein ausziehbarer NodeInspector zeigt Zustand, Beschriftungen, Ressourcenleisten, CPU, Anzahl geladener Modelle, Backends (Lazy-Loaded) und In-Flight mit Genehmigungs-/Entleerungs-/Fortsetzungsaktionen an. Ein ModelInspector zeigt die nach Knoten gruppierte Replikatplatzierung mit clickable-Knotennamen, die einen Drilldown in einen NodeInspector ermöglichen.

Arbeiter melden jetzt cpu_logical_cores, cpu_usage_percent und cpu_load_1 bei der Registrierung und im Heartbeat. Das Dashboard zeigt die CPU-Kapazität und -Auslastung an, wobei die inaktiven Kerne als cpu_logical_cores * (1 - cpu_usage_percent / 100) abgeleitet sind.

Lebenszyklusübergänge sind jetzt atomar. MarkDraining dreht den Status um und löscht Modelldatensätze in einer Transaktion und nicht als separate Vorgänge, die mit SetNodeModel verzahnt sein könnten. ResumeNode ist bedingt: Es wird nur in den fehlerfreien Zustand abgelassen, um das Überschreiben ausstehender Genehmigungen oder gleichzeitiger Zustandsänderungen zu verhindern. HTTP-Endpunkte geben die korrekten Werte 404 (nicht gefunden) und 409 (Statuskonflikt) anstelle einer generischen 500 zurück.

🔗 PRs: #12046

🔑 Anmeldeinformationsdatei für private Quellen

Backends, Modelle und Galerieindizes können hinter privaten OCI-Registrierungen, internen HTTP-Servern oder privaten GitHub-Repos liegen. Zuvor verfügte jeder Downloadpfad über einen eigenen Ad-hoc-Authentifizierungsmechanismus und die Token waren über Umgebungsvariablen verteilt.

Eine credentials.yaml-Datei, geladen von --credentials-file / LOCALAI_CREDENTIALS_FILE, authentifiziert sie alle. Es handelt sich um eine Regelliste der obersten Ebene. Jede Regel hat ein match-URL-Präfix und genau einen Authentifizierungstyp: Basic (username + password / password_env / password_file), Bearer (bearer / bearer_env / bearer_file) oder benutzerdefinierter Header (header.name + header.value / header.value_env / header.value_file). Genau eine der einfachen Formen _env oder _file pro Geheimnis; Unbekannte Schlüssel sind Fehler, daher schlägt ein falsch geschriebener pasword_env lautstark fehl.

OCI-Register (Backend-Images, oci://- und ollama://-Modelle, Digest-Suche, Range Resume, Cosign-Überprüfung) konsultieren zuerst den Store und dann authn.DefaultKeychain (docker-Konfiguration). HTTP-Downloads, Galerien und github:-URIs werden über einen http.RoundTripper authentifiziert, der die Anmeldeinformationen auf einem Klon der Anfrage ablegt. net/http baut jeden Umleitungs-Hop aus den ursprünglichen Headern neu auf, sodass eine Umleitung zu einem anderen Host niemals die Anmeldeinformationen enthält. Ein vom Anrufer bereitgestellter Berechtigungsnachweis (z. B. HF_TOKEN) hat Vorrang: Der Transport lässt einen vorhandenen Authorization-Header in Ruhe. Geheimnisse werden zum Zeitpunkt der Nutzung und nicht zum Zeitpunkt des Ladens gelesen, sodass eine gedrehte K8s-Geheimnis-Einbindung ohne Neustart wirksam wird. Credential und Store implementieren String, GoString und LogValue, sodass kein fmt-Verb oder slog-Aufruf, auch wenn er in nicht exportierten Feldern verschachtelt ist, geheimes Material drucken kann. Anmeldeinformationen gehen nur an https oder an http, wenn die Regel allow_insecure festlegt. Übereinstimmungszeichenfolgen mit user:token@, ? (wobei signierte URLs Token enthalten) oder # werden beim Laden abgelehnt. YAML-Dekodierungsfehler werden korrigiert: In Anführungszeichen gesetzte Skalarwerte (häufig Geheimnisse) werden entfernt, sodass nur Zeilennummern und Parser-Wortlaute erhalten bleiben.

🔗 PRs: #12028

📏 local-ai benchmark CLI Befehl

Ein Benchmark-Befehl für konfigurierte Textmodelle, der antwortet: „Wie schnell ist dieses Modell auf dieser Hardware“, ohne das Terminal zu verlassen.

local-ai benchmark MODEL [MODEL ...] sendet Nicht-Streaming-POST /v1/chat/completions-Anfragen bei temperature:0 mit konfigurierbaren --runs (Standard 3), --warmup (Standard 1), --max-tokens (Standard 128) und --timeout (Standard 5 m). Es meldet die minimale, mittlere und maximale Latenz sowie End-to-End-Abschlusstokens/Sek. pro Modell.

Die Durchsatzmetrik beträgt sum(completion_tokens) / sum(latencies) für die gemessenen Läufe. Es ist nil/N/A, wenn in einem Beispiel completion_tokens in der Antwortverwendung weggelassen wird oder wenn die Gesamtlatenz Null ist. Der Befehl misst nicht die reine Dekodierungsgeschwindigkeit oder die Zeit bis zum ersten Token; Es handelt sich um einen durchgängigen client-Benchmark, der HTTP-Transport, Warteschlangen, Eingabeaufforderungsverarbeitung, Generierung und Analyse abdeckt.

Der HTTP client lehnt Umleitungen standardmäßig ab, sodass ein falsch konfigurierter Endpunkt hinter einer Umleitung nicht stillschweigend erfolgreich ist. Der Schlüssel API wird aus Fehlermeldungen entfernt und Rohtransportfehler werden als HTTP request failed maskiert, um ein Echo der Anmeldeinformationen zu vermeiden. Der vollständige Bericht wird in einem bytes.Buffer gepuffert und erst über io.Copy geschrieben, nachdem alle Modelle erfolgreich waren, sodass bei einem Fehler keine Teilausgabe zurückbleibt. Die Signalverarbeitung bricht die aktive Anfrage auf SIGINT/SIGTERM ab.

Die Ausgabe ist standardmäßig eine Tabelle oder --json für strukturierte Daten mit Latenz pro Stichprobe und nullbaren Token-Zählungen. Der Schlüssel API ist im JSON nicht enthalten. Um Backends zu vergleichen, konfigurieren Sie separate Modellaliase pro Backend und übergeben Sie diese Aliasnamen.

🔗 PRs: #12020

🔧 vllm-cpp LoRA-Fusion zur Ladezeit

Die Konfigurationsfelder lora_adapters und lora_scales sind standardmäßige LocalAI-Felder, die LoRA-Adapter-Gewichtungsdateien und Stärkemultiplikatoren pro Adapter auflisten. Das vllm-cpp-Video-Backend nutzt sie nun zum ersten Mal und fusioniert LoRA-Deltas bei Motorlast in DiT-Gewichte (Diffusion Transformer).

buildLoraExtras konvertiert die Konfigurationsfelder in indizierte Schlüssel-Wert-Paare lora_path / lora_strength. Der erste Adapter hat kein Suffix; Nachfolgende erhalten _2, _3 usw. Wenn der Singular lora_adapter gesetzt ist, wird er als erster Adapter vor der Pluralliste vorangestellt. Relative Adapterpfade werden mit dem Modellpfad verbunden; absolute Pfade gehen durch. Wenn keine Skala angegeben ist, ist die Stärke standardmäßig auf 1.0 eingestellt.

Die Paare werden über die ABI v18-Extras-Naht verpackt und an vllmVideoEngineLoad übergeben. vllm.cpps ResolveDitLoraSpecs verschmilzt die LoRA-Deltas unter Last mit den DiT-Gewichten. Ein generischer Pfad bedient sowohl LTX2.5 als auch MiniMax-H3, da die Engine die DiT-Familie automatisch vom Prüfpunkt aus erkennt.

Adapter werden immer geladen; In diesem Pfad gibt es keine Aktivierung pro Anfrage. Durch die Laufzeit-Eingabeaufforderung aktiviertes LoRA (Punica-Stil <lora:name:strength>) liegt außerhalb des Geltungsbereichs und wird separat verfolgt.

🔗 PRs: #12082

🌍 Umgebungsvariablen pro Modell

Eine env:-Zuordnung in der Modellkonfiguration fügt Variablen in die Backend-Prozessumgebung ein. Der primäre Anwendungsfall besteht darin, CUDA_VISIBLE_DEVICES pro Modell anzuheften, um die GPU-Platzierung zu steuern, er gilt jedoch für jedes Backend, das Umgebungsvariablen liest.

name: vllm-model
backend: vllm
env:
  CUDA_VISIBLE_DEVICES: "0,1"
  VLLM_CACHE_DIR: "/tmp/vllm_cache"

Die Karte wird über die gemeinsame Prozess-Spawning-Schicht in pkg/model/process.go bereitgestellt, sodass jedes gRPC-Backend sie ohne Verkabelung pro Backend erbt. Modellvariablen werden zuletzt nach der Basisumgebung angehängt, sodass sie gleichnamige geerbte Systemvariablen überschreiben. Die Benutzeroberfläche rendert eine bearbeitbare Schlüssel-/Wertzuordnung.

Modellvariablen werden nur wirksam, wenn ein Modell seinen eigenen Backend-Prozess erzeugt, nicht wenn es einen vom Arbeiter überwachten Prozess wiederverwendet. Es gibt keine Zulassungs- oder Sperrliste: Modellkonfigurationen sind eine Operator-Grenze, die mit der allgemeinen Haltung von LocalAI übereinstimmt.

🔗 PRs: #10721

💬 template.system_messages_after_first

Agenten-Frameworks fügen während des Gesprächs rechtmäßig Systemanweisungen hinzu: eine Eingabeaufforderung für Werkzeugparameter vor einem Anruf, eine Eingabeaufforderung für Anpassungen nach einem Ergebnis. Die Qwen3.x-Familie von Tokenizer-Vorlagen löst nach der ersten Runde Jinja Exception: System message must be at the beginning für jede Systemrollennachricht aus und gibt HTTP 500 zurück. Der einfache Chat sieht fehlerfrei aus; Jede Agentenaufgabe schlägt fehl.

template.system_messages_after_first steuert, was mit Systemrollenmeldungen geschieht, die nach dem zusammenhängenden führenden Systemblock erscheinen:

  • "merge" faltet verspätete Systemnachrichten mit einem \n\n-Trennzeichen in die erste Systemnachricht ein und löscht sie an ihrer ursprünglichen Position.
  • "user" schreibt jede vorhandene verspätete Systemmeldung in die Rolle user um und behält deren Position und Inhalt bei.
  • unset (Standard) bleibt unverändert bestehen; Die Tokenizer-Vorlage entscheidet.

Die Normalisierung wird in ChatEndpoint nach stripEmptySystemMessages und vor der Injektion der Tokenizer-Vorlage system_prompt ausgeführt, sodass die Jinja-Vorlage nie eine fehl am Platz befindliche Systemmeldung sieht. Es berührt nur Anfragen, deren Modellkonfiguration aktiviert ist, sodass das Standardverhalten unverändert bleibt.

"user" ist der empfohlene Modus für Agenten-Workloads: Die Anweisung bleibt dort, wo sie vom Framework platziert wurde, und das Modell folgt ihr.

🔗 PRs: #11906

🧠 context_size in /v1/models/capabilities

Der Capabilities-Endpunkt füllt nun entry.ContextSize mit backend.EffectiveContextSize(cfg), wenn das Ergebnis positiv ist. Clients können das effektive Kontextfenster jedes Modells lesen, um Tokens zu budgetieren, Eingabeaufforderungen und Verlauf zu kürzen und das Senden von mehr Kontext zu vermeiden, als das Modell akzeptiert, ohne die Modellkonfiguration außerhalb des Bandes prüfen zu müssen.

🕵️ Wiederholung der Gesichtsregistrierung

Die Gesichtserkennungs-1:N-Registrierung erhält einen Wiedergabepfad. FaceRegisterRequest akzeptiert jetzt einen Embedding (vorberechneter Vektor) und einen RegisteredAt (ursprünglicher Zeitstempel), sodass ein client, ​​der zuvor eine Einbettung über /v1/face/embed extrahiert hat, den gespeicherten Vektor, Namen, Beschriftungen und Zeitstempel direkt wiedergeben kann, wobei die Bilddecodierung und der FaceEmbed-Inferenzaufruf vollständig übersprungen werden.

Der Store leitet über uuid.NewSHA1 eine deterministische ID aus den eingebetteten Bytes und dem Store-Namespace ab, sodass die Wiedergabe desselben Vektors nach einem Neustart oder auf einem anderen Replikat dieselbe ID zurückgibt, ohne dass Duplikate erstellt werden. Der Server behält die Registrierung selbst nicht bei; clients müssen die Datensätze aufbewahren und wiedergeben, um die Registrierung nach einem Neustart wiederherzustellen.

LocalAI 4.10.0 is out!

Twenty-eight days and 280 pull requests. The work landed on three fronts: operating a fleet, feeding it models from private sources, and fixing the backends you depend on. A fleet operations dashboard replaces the flat node list with cluster-wide health, capacity, running models, and bulk lifecycle actions. A credentials file lets one credentials.yaml authenticate OCI registries, galleries and direct downloads without scattering tokens across environment variables. And local-ai benchmark measures end-to-end latency and throughput from the CLI.

The ds4 backend had four fixes that together make it reliable on CUDA: the kernels now build for the target architecture, abandoned inference is cancelled, generation boundaries are enforced, and prefilled reasoning is separated from content. Distributed mode gained seven stabilisation fixes across staging, liveness, virtual models and the control-plane database. Four CVEs were patched, enable_thinking=false is now honoured across every text backend, and Apple M5 no longer SIGSEGVs at startup.

Highlights:

  • 📊 Fleet operations dashboard - a real-time cluster overview replacing the flat node list. Aggregate health bands, capacity gauges for VRAM/RAM/CPU/disk, a running-models tab showing replica placement across workers, bulk drain/resume/remove with bounded concurrency, and a slide-out node inspector. Workers now report CPU telemetry at registration and heartbeat.
  • 🔑 Credentials file for private sources - one credentials.yaml authenticates OCI registries, galleries, HTTP downloads and github: URIs. Supports basic auth, bearer tokens and custom headers, with secrets read at use time so rotated K8s secret mounts take effect without restart, and full masking in logs and error messages.
  • 📏 local-ai benchmark CLI command - measures end-to-end latency and throughput against configured text models. Reports min/mean/max latency and completion tokens/sec across warmup and measured runs, with table and JSON output, redirect blocking, and API-key redaction.
  • 🔧 vllm-cpp LoRA fusion at load time - lora_adapters and lora_scales are now consumed by the vllm-cpp video engine, fusing LoRA deltas into DiT weights at engine load. Works for both LTX2.5 and MiniMax-H3 through one generic path.
  • 🌍 Environment variables per model - an env: map in model config injects variables into the backend process environment, so CUDA_VISIBLE_DEVICES or VLLM_CACHE_DIR can be pinned per model without wrapping the backend in a script.
  • 💬 template.system_messages_after_first - agent frameworks that append system instructions mid-conversation no longer crash Qwen3.x models. Late system turns can be merged into the leading system message or forwarded as user turns.
  • 🧠 context_size in /v1/models/capabilities - clients can now read each model's effective context window to budget tokens and truncate prompts without probing the model config out-of-band.
  • 🛡️ Four CVEs patched - ip-address 10.3.1 (CVE-2026-69192), containerd 1.7.32 and 1.7.33 (CVE-2026-46680, CVE-2026-53488), and react-router (GHSA-qwww-vcr4-c8h2).
  • 🍎 Apple M5 SIGSEGV fixed - go-m1cpu bumped to v0.2.2, fixing a segmentation fault on Apple M5 hardware at startup.

Plus a focus mode toggle in chat settings, face enrollment replay for the 1:N registry, a ROCm build of stablediffusion-ggml, in-place editing of distributed scheduling rules, OCI layer download resumption, and 140 new gallery entries.

📊 Fleet operations dashboard

The Nodes page was a flat list of per-node cards. It showed you what was registered but not what the cluster was doing, and every lifecycle action was one node at a time.

The rewrite is a fleet operations dashboard with two tabs and a shared summary poller.

ClusterOverview sits at the top. A health band segments nodes into healthy, draining and attention counts. Capacity gauges show VRAM, RAM, CPU and disk, each reporting how many workers do not report that metric so the number is honest rather than averaged over reporting nodes. An attention queue filters for pending approval, offline/unhealthy, low VRAM, low RAM and low disk, surfacing nodes that need action without double-counting the headline total.

NodeFleetTable is sortable, groupable (by label or type) and paginated at 50 rows per page, with checkbox selection that persists across filters and pages. Bulk Drain, Resume and Remove run with bounded concurrency (limit 8) so a fleet with thousands of registrations is usable. Columns: status pill, address, capacity (VRAM + RAM), CPU, workload and heartbeat. An Approve button appears on pending nodes.

Running models tab. A fleet-wide view of loaded replicas on healthy workers, grouped by model: model name, replica count, node count, in-flight requests, backend types and last used. Per-model Stop shuts down all placements through POST /backend/shutdown {model}, which now fires the remote unloader even when a local process exists, and deduplicates nodes before sending stop messages.

Inspectors. A slide-out NodeInspector shows health, labels, resource bars, CPU, loaded model count, backends (lazy-loaded) and in-flight, with Approve/Drain/Resume actions. A ModelInspector shows replica placement grouped by node, with clickable node names that drill into a NodeInspector.

Lifecycle transitions are now atomic. MarkDraining flips status and deletes model records in one transaction rather than as separate operations that could interleave with SetNodeModel. 🔑 Credentials file for private sources

Backends, models and gallery indexes can live behind private OCI registries, internal HTTP servers or private GitHub repos. Before this, each download path had its own ad-hoc auth mechanism, and tokens were scattered across environment variables.

One credentials.yaml file, loaded by --credentials-file / LOCALAI_CREDENTIALS_FILE, authenticates them all. It is a top-level YAML list of rules. Each rule has a match URL prefix and exactly one auth type: basic (username + password / password_env / password_file), bearer (bearer / bearer_env / bearer_file), or custom header (header.name + header.value / header.value_env / header.value_file). Exactly one of the plain, _env or _file form per secret; unknown keys are errors so a misspelled pasword_env fails loudly.

OCI registries (backend images, oci:// and ollama:// models, digest lookup, Range resume, cosign verify) consult the store first, then authn.DefaultKeychain (docker config). HTTP downloads, galleries and github: URIs authenticate through an http.RoundTripper that puts the credential on a clone of the request. net/http rebuilds each redirect hop from the original headers, so a redirect to another host never carries the credential. A caller-supplied credential (e.g. HF_TOKEN) takes precedence: the transport leaves an existing Authorization header alone.

Secrets are read at use time, not load time, so a rotated K8s secret mount takes effect without restart. Credential and Store implement String, GoString and LogValue, so no fmt verb or slog call, including when nested in unexported fields, can print secret material. Credentials go only to https, or to http when the rule sets allow_insecure. Match strings containing user:token@, ? (where signed URLs carry tokens) or # are rejected at load. YAML decode errors are redacted: quoted scalar values (often secrets) are stripped, keeping only line numbers and parser wording.

🔗 PRs: #12028

📏 local-ai benchmark CLI command

A benchmark command for configured text models, answering "how fast is this model on this hardware" without leaving the terminal.

local-ai benchmark MODEL [MODEL ...] sends non-streaming POST /v1/chat/completions requests at temperature:0 with configurable --runs (default 3), --warmup (default 1), --max-tokens (default 128) and --timeout (default 5m). It reports min, mean and max latency and end-to-end completion tokens/sec per model.

The throughput metric is sum(completion_tokens) / sum(latencies) across measured runs. It is nil/N/A if any sample omits completion_tokens from the response usage, or if total latency is zero. The command does not measure decode-only speed or time to first token; it is an end-to-end client benchmark covering HTTP transport, queueing, prompt processing, generation and parse.

The HTTP client refuses redirects by default, so a misconfigured endpoint behind a redirect does not silently succeed. The API key is redacted from error messages, and raw transport errors are masked as HTTP request failed to avoid credential echo. The full report is buffered in a bytes.Buffer and only written via io.Copy after all models succeed, so a failure leaves no partial output. Signal handling cancels the active request on SIGINT/SIGTERM.

Output is a table by default or --json for structured data with per-sample latency and nullable token counts. The API key is not included in the JSON. To compare backends, configure separate model aliases per backend and pass those alias names.

🔗 PRs: #12020

🔧 vllm-cpp LoRA fusion at load time

The lora_adapters and lora_scales config fields are standard LocalAI fields that list LoRA adapter weight files and per-adapter strength multipliers. The vllm-cpp video backend now consumes them for the first time, fusing LoRA deltas into DiT (diffusion Transformer) weights at engine load.

buildLoraExtras converts the config fields into indexed lora_path / lora_strength key-value pairs. The first adapter is unsuffixed; subsequent ones get _2, _3, etc. If the singular lora_adapter is set, it is prepended as the first adapter before the plural list. Relative adapter paths are joined to the model path; absolute paths pass through. Strength defaults to 1.0 when no scale is provided.

The pairs are packed via the ABI v18 extras seam and handed to vllmVideoEngineLoad. vllm.cpp's ResolveDitLoraSpecs fuses the LoRA deltas into the DiT weights at load. One generic path serves both LTX2.5 and MiniMax-H3, since the engine auto-detects the DiT family from the checkpoint.

Adapters are always loaded; there is no per-request activation in this path. Runtime prompt-activated LoRA (punica-style <lora:name:strength>) is out of scope and tracked separately.

🔗 PRs: #12082

🌍 Environment variables per model

An env: map on the model config injects variables into the backend process environment. The primary use case is pinning CUDA_VISIBLE_DEVICES per model to control GPU placement, but it applies to any backend that reads environment variables.

name: vllm-model
backend: vllm
env:
  CUDA_VISIBLE_DEVICES: "0,1"
  VLLM_CACHE_DIR: "/tmp/vllm_cache"

The map is delivered through the common process-spawning layer in pkg/model/process.go, so every gRPC backend inherits it with no per-backend wiring. Model vars are appended last, after the base env, so they override same-named inherited system vars. The UI renders an editable key/value map.

Model vars take effect only when a model spawns its own backend process, not when it reuses a worker-supervised one. There is no allowlist or blocklist: model configs are an operator trust boundary, consistent with LocalAI's general posture.

🔗 PRs: #10721

💬 template.system_messages_after_first

Agent frameworks legitimately append system instructions mid-conversation: a tool-parameter prompt before a call, an adjustment prompt after a result. The Qwen3.x family of tokenizer templates raises Jinja Exception: System message must be at the beginning for any system-role message after the first turn, returning HTTP 500. Plain chat looks healthy; every agent task fails.

template.system_messages_after_first controls what happens to system-role messages that appear after the contiguous leading system block:

  • "merge" folds late system messages into the first system message with a \n\n separator, dropping them from their original position.
  • "user" rewrites each late system message in place to role user, keeping its position and content.
  • unset (default) passes through unchanged; the tokenizer template decides.

The normalization runs in ChatEndpoint after stripEmptySystemMessages and before tokenizer-template system_prompt injection, so the Jinja template never sees an out-of-place system message. It only touches requests whose model config opts in, so default behavior is unchanged.

"user" is the recommended mode for agent workloads: the instruction stays where the framework placed it, and the model follows it.
