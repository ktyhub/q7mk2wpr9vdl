🎉 LocalAI 4.8.0-Veröffentlichung! 🚀

<h1 align="center"> <br> <img height="300" src="https://raw.githubusercontent.com/mudler/LocalAI/refs/heads/master/core/http/static/logo.png"> <br> <br> </h1>

LocalAI 4.8.0 ist da!

Zweiundzwanzig Tage, 386 Pull-Anfragen und drei neue Modalitäten. In dieser Version wird vllm.cpp eingeführt, eine vom LocalAI-Team verwaltete C++20-Engine, die als vLLM-Portierung begann und jetzt über einen eigenen Funktionsumfang verfügt und als vllm-cpp-Backend in Alpha-Entwicklungs-Builds ausgeliefert wird. Drumherum: 3D-Generierung als neue Modalität, eine mehrfamilienfähige audio.cpp-Engine, Galerieeinträge, die den Build installieren, den Ihre Hardware tatsächlich ausführen kann, und eine umfassende Zuverlässigkeitsweitergabe im verteilten Modus, die durch Produktionsvorfälle gesteuert wird.

Highlights:

  • 🚀 vllm.cpp (Alpha) – eine vom LocalAI-Team verwaltete C++20-Engine, die als vLLM-Port begann und vLLM als Referenzimplementierung beibehält: V1-Serving-Architektur (ausgelagerter KV-Cache, kontinuierliches Batching, Präfix-Caching, Scheduler, Sampler) ohne Python, PyTorch oder ggml als Inferenz. Gemessen bei 1,045x vLLM auf Qwen3.6-27B NVFP4 bei Parallelität 1, mit Token-für-Token-identischer Ausgabe. Lädt Safetensoren und GGUF, erzwingt eine strukturierte Ausgabe in der Engine und läuft auf CPU, CUDA, Metal und Vulkan. Der Apple Silicon Build verfügt über den MLX GEMM-Anbieter, gemessen mit 1,5x bis 2,2x auf einem M4. Versand als Alpha-Entwicklungs-Builds: Probieren Sie es aus, verlassen Sie sich nicht darauf.
  • 🧊 3D-Generierung – eine neue End-to-End-Modalität: Generate3D RPC, FLAG_3D-Fähigkeit, POST /v1/3d/generations, das trellis2cpp-Bild-zu-3D-Backend und eine UI-Seite mit einem nativen GLB-Viewer und Druck-Remeshing.
  • 🔊 audio.cpp – ein Backend-Prozess, der sechs Audio-Endpunkte über viele Modellfamilien hinweg bedient, ausgewählt aus den GGUF-eigenen Metadaten: Sprache, Transkription, VAD, Diarisierung, Quellentrennung und Tonerzeugung.
  • 🎛️ Ein Modell, viele Builds – ein Galerieeintrag kann variants: deklarieren und LocalAI installiert den größten Build, den Ihr Host tatsächlich ausführen kann. Kein Suchen mehr in der Galerie nach der richtigen Quantisierung.
  • ⚡ Eine viel schlankere Web-Benutzeroberfläche – gzip auf der Leitung, unveränderliches Caching für gehashte Assets und paginierte Trace-Endpunkte: Das React-Bundle ist 3,48-mal kleiner und die Trace-Abfrage ist von 21 MB auf 7 KB gesunken.
  • 📊 Eine Aktivitätsseite – die gestapelte Betriebsleiste wird auf eine Zeile reduziert, und auf einer neuen Administrator-Aktivitätsseite wird aufgezeichnet, was installiert, fehlgeschlagen oder abgebrochen wurde, anstatt sie sofort zu löschen, sobald sie abgeschlossen ist.
  • 📦 Hugging Face-Artefaktmaterialisierung – unveränderliche Snapshot-Auflösung, authentifizierte Downloads mit echtem Fortschritt und bereitgestellte Artefakte, an die sich Remote-Mitarbeiter binden können.
  • 🎚️ VRAM-Budgets – begrenzen, wie viel von einer Karte LocalAI pro Knoten verwenden darf, als Prozentsatz (80%) oder als absoluter Betrag (12GB).
  • 🗣️ Zwei neue TTS-Engines – magpie-tts-cpp (NVIDIA Magpie Multilingual, 5 Stimmen, 9+ Sprachen) und moss-tts-cpp (48-kHz-Stereo mit Referenz-Audio-Stimmenklonung).
  • 🌳 Sub-2-Bit-Modelle – ein neues bonsai-Backend bedient die 1-Bit- und ternären Bonsai-Quantisierungen von Qwen3 und Qwen3.6-27B.
  • 🖧 Härtung im verteilten Modus – der Reaper löscht keine Zeilen mehr für aktive und ausgelastete Backends, Phantomreplikate werden bereinigt und in_flight-Zähler verlieren kein Leck mehr.

Plus ein Valkey-Vektorspeicher, systemd-Socket-Aktivierung, persistenter Trace-Verlauf, zwei Sicherheitsfixes, eine Überarbeitung der Dokumentation, die direkt auf das Onboarding abzielt, und ein neues localai.io.

🚀 Neue Funktionen und wichtige Verbesserungen

🚀 Einführung von vllm.cpp (Alpha)

<p align="center"> <img src="https://raw.githubusercontent.com/mudler/vllm.cpp/master/benchmarks/media/concurrency_race.gif" alt="vllm.cpp und vLLM werden nebeneinander auf Qwen3.6-27B" width="900"> generiert <br><em>vllm.cpp gegen vLLM auf Qwen3.6-27B, identische Ausgabe bei jeder Parallelität.</em> </p>

vllm.cpp ist Apache-2.0, wird vom LocalAI-Team verwaltet und begann als C++20-Portierung von vLLM. Wir möchten, dass es sich um eine Community-First-Engine und nicht um eine reine LocalAI-Engine handelt, sodass es sich in einem eigenen Repository mit eigenen Dokumenten, Benchmark-Datensätzen und Issue-Tracker befindet und überall im Bild ohne LocalAI verwendet werden kann. Es implementiert die V1-Serving-Architektur von vLLM (ausgelagerter KV-Cache, kontinuierliches Batching, Präfix-Caching, Scheduler, Sampler) auf einer tragbaren Tensor-Laufzeitumgebung mit kein Python, kein PyTorch und kein ggml zur Inferenzzeit und verwendet vLLM selbst als Referenzimplementierung: Die Richtigkeit wird durch den Vergleich der Ausgabe damit überprüft, und die Benchmark-Scoreboard wird dagegen gehalten.

Seitdem ist ein Funktionsumfang gewachsen, über den vLLM nicht verfügt, wofür der Port gedacht war. Es lädt GGUF- und Hugging Face-Safetensoren, läuft auf CPU, Apple Metal und Vulkan zusammen mit NVIDIA CUDA, bietet spekulative Dekodierung und KV-Offload und erzwingt eine strukturierte Ausgabe in der Engine (JSON-Schema, Regex, Auswahl, GBNF). Die Benchmark-Seite misst nun mit llama.cpp, MLX-LM und DwarfStar sowie vLLM, da dies die Engines sind, mit denen es auf dieser Hardware tatsächlich konkurriert.

Das Projekt wird voraussichtlich umbenannt, über den neuen Namen muss noch entschieden werden. Es weicht so weit von vLLM ab, dass die Bezeichnung „Port“ es unterbietet und die Bezeichnung „vllm.cpp“ letztendlich in die Irre führt.

Die Upstream-Seite achtet sorgfältig auf ihr eigenes Rauschband: Auf dem 27B-Gitter ruft sie c2 bis c32 unentschieden statt siegt auf, da die Run-to-Run-Spanne 0.5 % beträgt und diese Margen zwischen 0.7 % und 1.7 % liegen. Das c1-Ergebnis ist das, hinter dem es steht.

Die Zeile DeepSeek-V4-Flash zeigt, wie weit sich das Projekt von einem vLLM-Port entfernt hat. Es führt DeepSeek-V4-Flash mit etwa 2 Bit (IQ2_XXS gemischt, etwa 80 GB) auf einem einzelnen DGX Spark aus und dekodiert mit 18.69 tok/s im Vergleich zu DwarfStars 16.33. Bei mehr als 300 Milliarden Gesamtparametern beträgt sogar ein 4-Bit-Checkpoint 156 GB oder mehr, sodass ein 2-Bit-GGUF in den einheitlichen 119-GiB-Pool des Spark passt, und das Lesen von GGUF macht dies möglich. Diese Zahl bewegte sich zweimal in einer Woche, und die zweite Bewegung kam von einem Hebel. Der dichte Q8_0-Projektionsturm wurde aus der GGUF-mmap über einheitlichen Speicher gelesen, den der GB10 pro GEMV etwa 20 % langsamer liest als der Gerätespeicher. Das einmalige Staging dieses ~6-GiB-Tower-Geräts, das sich unter Last befindet, mit denselben Bytes und denselben Kerneln, erforderte die Dekodierung von 16.23 zu 18.69, generierte dieselben Token und verbrauchte keinen Spitzenspeicher mehr. Die gleiche Änderung führte dazu, dass Laguna-XS-2.1 von 87 % des vLLM auf das 1,03-fache vor ihm lag.

Die spekulative Dekodierung verläuft ähnlich: MTP auf Qwen3.6-27B NVFP4 generiert die gleichen Token wie das MTP von vLLM und läuft bei Parallelität 1 etwa 4 % schneller.

Es wird hier als vllm-cpp-Backend ausgeliefert, das den stabilen C ABI (v5) der Engine über Purego öffnet. Gleichzeitige Anforderungen werden kontinuierlich im gemeinsamen Scheduler der Engine gebündelt und nicht serialisiert, sodass das Backend auf base.Base und nicht auf SingleThread ausgeführt wird.

Der Tool-Aufruf erfolgt konstruktionsbedingt bei llama.cpp-Parität, da Chat denselben Autoparser-Pfad wiederverwendet. Mit use_tokenizer_template rendert die Engine die eigene Chat-Vorlage des Modells (GGUF tokenizer.chat_template oder tokenizer_config.json, vollständiges Minja) und erledigt den Rest selbst:

  • tool_choice: auto wird auf eine verzögerte Dekodierungsbeschränkung für Struktur-Tags reduziert; required und benannte Auswahlmöglichkeiten erzwingen die native Syntax der Familie, sofern dies ausdrückbar ist.
  • Streaming-Parser pro Dialekt decken 30 Tool-Dialekte und 7 Argumentationsparser ab, wobei die Argumentation <think> vor dem Tool-Parsing aufgeteilt wird.
  • ChatDelta, ToolCallDelta und Reasoning-Stream genau wie das Lama-CPP-Backend.

tool_parser: und reasoning_parser: sind Modelloptionen, die bei Nichteinstellung automatisch erkannt werden.

Der Einstieg ist eine normale Backend-Installation:

name: qwen3-vllm
backend: vllm-cpp
context_size: 8192
parameters:
  model: Qwen3-4B      # a safetensors directory or a .gguf file
options:
- max_num_seqs:16      # also: block_size:<n>, num_blocks:<n>

Die Build-Matrix umfasst CPU amd64/arm64, CUDA 12/13 (einschließlich Blackwell 120a;121a), L4T arm64 für GB10, Vulkan und Darwin Metal, mit einem Galerie-Meta plus 12 Bildeinträgen. Die Importeure von llama-cpp GGUF und vllm Safetensors haben Präferenzaustausche erhalten, sodass das Backend zum Zeitpunkt des Imports ausgewählt werden kann.

Apple Silicon erhält den MLX GEMM-Anbieter. Das optionale MLX-Backend des Darwin Builders vllm.cpp, das standardmäßig an der Stelle bleibt, an der es seine ~124 MB verdienen muss. Gemessen an einem M4 (Qwen3-1.7B-bf16, p=512 g=128, Arme auf einem Binärsystem umgeschaltet, sodass es keine Build-Unterschiede gibt):

| Charge | MLX-Token/s | native Token/s | Beschleunigung | MLX TTFT | natives TTFT | |--:|--:|--:|--:|--:|--:| | 1 | 5.79 | 3.08 | 1,88x | 3.32 s | 7.68 s | | 4 | 15.75 | 10.24 | 1,54x | 9.63 s | 18.77 s | | 16 | 38.65 | 17.69 | 2,19x | 18.33 s | 54.48 s |

Lesen Sie diese als Richtwerte und nicht als verbindlich: zwei Wiederholungen mit einer Spanne von 9.4 %, sodass die Multiplikatoren etwa +/-10 % betragen. Die Lücke ist weitaus größer als der Lärm, und die Zeit bis zum ersten Token halbiert sich im gesamten Bereich ungefähr.

Dies sind Alpha-Entwicklungs-Builds, kein veröffentlichtes Backend. vllm.cpp ist früh. Es wird in 4.8 ausgeliefert, damit es Leute ausprobieren können, die es ausprobieren möchten, und nicht, weil es für alles bereit ist, worauf Sie angewiesen sind, und llama-cpp bleibt die Standardeinstellung für den tatsächlichen Gebrauch. Erwarten Sie Ecken und Kanten. Der CPU-Pfad wird durchgängig gegen Qwen3.5-2B-UD-Q8_K_XL.gguf mit der gesamten Ginkgo-Suite verifiziert: Blockieren und Streamen von Byteparität, gieriger Determinismus, Stoppwörter, GBNF-beschränkte Generierung, gleichzeitige Streams, echtes Template-Rendering, Reasoning-Split, ein required-Tool-Aufruf, der schemagültige Argumente zurückgibt, und ein auto-Lauf, bei dem die Engine das Tool selbst aktiviert und geparste Deltas streamt. Die GPU-Images werden erstellt und versendet, aber ihr Laufzeitverhalten hat dieses Gate noch nicht durchlaufen. Es wird kein Durchsatzvergleich mit Upstream-vLLM beansprucht. Bitte melden Sie, was kaputt ist.

🧊 3D-Generierung, End-to-End

<p align="center"> <img src="https://raw.githubusercontent.com/mudler/LocalAI/master/website/static/media/3d-generation.gif" alt="Ein generiertes 3D-Lama, das sich im GLB-Viewer dreht" width="760"> <br><em>trellis2-4b, 2.502.928 Eckpunkte, im Browser drehen.</em> </p>

LocalAI erhält eine neue Modalität. Image-to-3D ist durch den gesamten Stapel verdrahtet und nicht an einen vorhandenen Endpunkt geschraubt: ein Generate3D-RPC in backend.proto, eine FLAG_3D-Funktion, damit der Loader weiß, welche Backends sie bedienen können, und POST /v1/3d/generations.

Die erste Engine dahinter ist trellis2cpp, ein natives Image-to-3D-Backend über TRELLIS.2. Die React-Benutzeroberfläche erhält eine 3D-Generierungsseite mit einem nativen GLB-Viewer, einem von IndexedDB unterstützten Verlauf, damit Ihre Generationen ein Neuladen überstehen, und einer vorschaubaren Druck-Neuvernetzung für die Ausgabe, die Sie tatsächlich drucken möchten.

🔗 PRs: #10979

🔊 audio.cpp: ein Backend, sechs Audio-Endpunkte

<p align="center"> <img src="https://raw.githubusercontent.com/mudler/LocalAI/master/website/static/media/v4-8-0-ui-model-variants.png" alt="Der Modelldetailbereich mit allen Varianten" width="900"> <br><em>Ein Eintrag, vier Builds. Bestehende Installationen sind davon nicht betroffen: Jedes veröffentlichte LocalAI liest gallery/index.yaml live und ignoriert Schlüssel, die es nicht versteht, sodass ein älterer client variants: löscht und den Eintrag genau wie zuvor installiert. 🎚️ VRAM-Zuweisungsbudgets pro Knoten

Betreiber können jetzt begrenzen, wie viel VRAM LocalAI für die Modellzuweisung auf einem Knoten verwendet, als Prozentsatz (80%) oder als absoluten Betrag (12GB). Prozentsätze über 100 % werden abgelehnt; Absolute Werte über physikalischen Werten werden geklemmt.

LOCALAI_VRAM_BUDGET=12GB

Es gilt sowohl für local-ai als auch für local-ai worker (auch --vram-budget) und kann live auf der eigenständigen Einstellungsseite und pro Knoten in der verteilten Knoten-Benutzeroberfläche bearbeitet werden.

Die beiden Wege sind bewusst asymmetrisch:

  • Standalone, eine feste Obergrenze pro Prozess. xsysinfo hält es als prozessglobalen Standardwert, sodass Hardwarestandards, automatische Kontextanpassung, GGUF-Warnungen und der Watchdog ihn alle erben.

Standardmäßig nicht festgelegt bedeutet, dass alle erkannten VRAMs vorhanden sind, sodass vorhandene Bereitstellungen unverändert bleiben.

Highlights

  • vllm.cpp ships as an alpha backend (vllm-cpp) — A C++20 serving engine (Apache-2.0, maintained in its own repo) implementing vLLM's V1 architecture — paged KV cache, continuous batching, prefix caching, scheduler — with no Python, PyTorch, or ggml at inference. Safe to benchmark, not safe to depend on; the project is also slated for a rename.
  • A new 3D modality and a unified audio backend — 3D generation is wired end to end: POST /v1/3d/generations, the Generate3D RPC, FLAG_3D, and the trellis2cpp image-to-3D backend. audio.cpp collapses six audio endpoints (speech, transcription, VAD, diarization, source separation, sound generation) into one process, with the model family read from the GGUF's own audiocpp.model_spec.family key — so there are no per-model backend flags to manage. New API surface without new configuration burden; just verify your hardware is supported (CPU/CUDA/Vulkan/Metal).
  • Security: inline GRPO reward code is now gated off — POST /api/fine-tuning/jobs refuses inline reward code unless the operator sets LOCALAI_TRL_ALLOW_INLINE_REWARD=true; the previous builtin allowlist was escapable to arbitrary code execution on an endpoint that is unauthenticated by default. If you rely on custom reward functions this breaks until you opt in — set the variable deliberately and put auth in front of that endpoint. Also picks up hono 4.12.25 for CVE-2026-54290.
  • Gallery variants and HF artifact materialization — A gallery entry can declare variants:, and install-time selection picks the largest build the host can actually run (compatibility, VRAM, cgroup-aware RAM), overridable via variant on POST /models/apply, local-ai models install --variant, the MCP install_model tool, or the UI; older clients ignore the key and install as before. Hugging Face downloads now resolve immutable snapshots with authenticated, progress-reporting pulls and stage artifacts remote workers can bind to, with Python backends reusing the Go download path. The practical change: installs become hardware-aware, so the same model may resolve to different binaries on different hosts.
  • VRAM budgets and distributed reliability — LOCALAI_VRAM_BUDGET=80% or 12GB (also --vram-budget) is a hard per-process cap standalone and a scheduler placement ceiling in distributed mode, with admin overrides at PUT/DELETE /api/nodes/:id/vram-budget and an MCP set_node_vram_budget tool; unset means all detected VRAM. Distributed mode also stops reaping busy backends — workers are queried over a new models.running subject and the port-probe fallback requires three consecutive misses before declaring a worker gone — plus cleanup of in_flight leaks and phantom replicas. These are direct fixes for production incidents, so note the new deadline/probe semantics if you tune the reaper.
  • Lighter HTTP stack, but the trace API changed shape — gzip middleware (new --disable-http-compression and --http-compression-min-length flags, streaming paths excluded) and immutable caching of hashed assets cut the React bundle from ~2.8 MB to ~808 KB and the backend-trace poll from ~21 MB to ~7 KB. /api/traces and /api/backend-traces now accept limit/offset/full and return summaries by default, with GET /api/traces/{id} for the full record — clients that assumed a full payload must pass full or call the new endpoint.

🚀 New Features & Major Enhancements

🚀 Introducing vllm.cpp (alpha)

<p align="center"> <img src="https://raw.githubusercontent.com/mudler/vllm.cpp/master/benchmarks/media/concurrency_race.gif" alt="vllm.cpp and vLLM generating side by side on Qwen3.6-27B" width="900"> <br><em>vllm.cpp against vLLM on Qwen3.6-27B, identical output at every concurrency.</em> </p>

vllm.cpp is Apache-2.0, maintained by the LocalAI team, and began as a C++20 port of vLLM. We want it community-first rather than a LocalAI-only engine, so it lives in its own repository with its own docs, benchmark record and issue tracker, and it is usable without LocalAI anywhere in the picture. It implements vLLM's V1 serving architecture (paged KV cache, continuous batching, prefix caching, scheduler, sampler) on a portable tensor runtime with no Python, no PyTorch and no ggml at inference time, and uses vLLM itself as its reference implementation: correctness is checked by comparing output against it, and the benchmark scoreboard is kept against it.

It has since grown a featureset vLLM does not have, which is what the port was for. It loads GGUF as well as Hugging Face safetensors, runs on CPU, Apple Metal and Vulkan alongside NVIDIA CUDA, ships speculative decoding and KV offload, and enforces structured output in-engine (JSON schema, regex, choice, GBNF). Its benchmark page now measures against llama.cpp, MLX-LM and DwarfStar as well as vLLM, because those are the engines it actually competes with on that hardware.

The project is expected to be renamed, with the new name still to be decided. It is drifting far enough from vLLM that calling it a port undersells it and calling it vllm.cpp will eventually mislead.

The DeepSeek-V4-Flash row is the one that shows how far the project has moved from being a vLLM port. It runs DeepSeek-V4-Flash at roughly 2-bit (IQ2_XXS mixed, about 80 GB) on a single DGX Spark, decoding at 18.69 tok/s against DwarfStar's 16.33. At 300B+ total parameters even a 4-bit checkpoint is 156 GB or more, so a 2-bit GGUF is what fits inside the Spark's 119 GiB unified pool, and reading GGUF is what makes that possible.

That figure moved twice in a week, and the second move came from one lever. The dense Q8_0 projection tower was being read from the GGUF mmap over unified memory, which the GB10 reads about 20% slower per-GEMV than device memory. Staging that ~6 GiB tower device-resident once at load, same bytes and same kernels, took decode from 16.23 to 18.69, generating the same tokens and using no more peak memory. The same change took Laguna-XS-2.1 from 87% of vLLM to 1.03x ahead of it.

Speculative decoding is in similar shape: MTP on Qwen3.6-27B NVFP4 generates the same tokens as vLLM's MTP and runs about 4% faster at concurrency 1.

It ships here as the vllm-cpp backend, which dlopens the engine's stable C ABI (v5) through purego. Concurrent requests batch continuously inside the engine's shared scheduler rather than serializing, so the backend runs on base.Base rather than SingleThread.

Tool calling is at llama.cpp parity, by construction, because chat reuses the same autoparser path. With use_tokenizer_template the engine renders the model's own chat template (GGUF tokenizer.chat_template or tokenizer_config.json, full minja) and handles the rest itself:

  • tool_choice: auto lowers to a lazy structural-tag decode constraint; required and named choices force the family's native syntax where expressible.
  • Streaming per-dialect parsers cover 30 tool dialects and 7 reasoning parsers, with <think> reasoning split before tool parsing.
  • ChatDelta, ToolCallDelta and reasoning stream exactly as the llama-cpp backend does.

tool_parser: and reasoning_parser: are model options, auto-detected when unset.

A gallery entry can now declare variants:, a list of references to other gallery entries that are alternative builds of the same weights:

- name: nanbeige4.1-3b-q4      # still a normal, complete, installable entry
  url: github:mudler/LocalAI/gallery/nanbeige4.1.yaml@master
  overrides: {parameters: {model: nanbeige4.1-3b-q4_k_m.gguf}}
  files: [...]
  variants:
    - model: nanbeige4.1-3b-q8

Selection at install time, in order:

  1. Drop variants whose backend cannot run here. MLX disappears on Linux, CUDA on a Mac. Derived from the backend name, so authors never write hardware conditions.
  2. Drop what does not fit: VRAM on GPU hosts, cgroup-aware system RAM on CPU hosts, so a container sees its own limit.
  3. Take the largest that remains, on the basis that a bigger footprint is a better build of the same weights.

The entry's own build competes in that ranking and is never filtered out, so selection always ends with something installable.

Sizes come from the existing pkg/vram estimator (remote GGUF header, HTTP HEAD, the declared size:, then the HF repo listing). Nothing is downloaded to decide, and a probe failure never fails an install.

Auto-selection is the default and every surface can override it: variant on POST /models/apply and POST /api/models/install/:id, local-ai models install <name> --variant <variant>, the variant parameter on the install_model MCP tool, and a split-button menu in the models table. An explicit selection is honored even when it does not fit, with a warning, since that is a deliberate operator override.

Existing installations are unaffected: every released LocalAI reads gallery/index.yaml live and ignores keys it does not understand, so an older client drops variants: and installs the entry exactly as before. A spec re-parses the real index through a legacy-shaped struct to keep that true.

Known gaps worth stating: in distributed mode InstallModel resolves against the frontend rather than the worker that will serve the model, so a cluster with a small frontend and large workers selects conservatively. Probing within a single entry is still serial and uncapped.

Three HTTP-layer problems, all measured on a live deployment, fixed together because they all shape what goes on the wire.

🎚️ Per-node VRAM allocation budgets

Operators can now cap how much VRAM LocalAI uses for model allocation on a node, as a percentage (80%) or an absolute amount (12GB). Everywhere LocalAI reads VRAM to make an allocation decision it now uses min(detected, budget), a hard ceiling that never raises usable VRAM above physical. Percentages above 100% are rejected; absolute values above physical are clamped.

LOCALAI_VRAM_BUDGET=80%
LOCALAI_VRAM_BUDGET=12GB

It applies to both local-ai and local-ai worker (also --vram-budget), and is editable live from the standalone Settings page and per node in the distributed node UI.

The two paths are deliberately asymmetric:

  • Standalone, a hard per-process cap. xsysinfo holds it as a process-global default, so hardware defaults, context auto-fit, GGUF warnings and the watchdog all inherit it.
  • Distributed, a placement ceiling. The worker reports raw VRAM plus its budget string; the registry resolves it and caps stored available_vram on registration and heartbeat, so the SQL scheduler needs no query change. The worker still sees its full card for its own context-fit.

Admin overrides via PUT/DELETE /api/nodes/:id/vram-budget survive worker restarts, and are exposed as the set_node_vram_budget MCP tool.

Default unset means all detected VRAM, so existing deployments are unchanged.

🖧 Distributed mode reliability

Investigating a model that showed as loaded on the home page but appeared on no node in the cluster turned up four separate bugs, all fixed here.

The reaper was deleting rows for backends that were alive and working. probeLoadedModels reaped a node_models row after one failed 1 second health check, and a busy backend cannot answer one: a single-threaded Python backend blocks for minutes inside a request.

  • A new models.running subject asks the worker directly, since it holds the process handle and is not blocked by the backend. The reconciler diffs its process keys against the registry before any port probe.
  • A worker that does not answer is skipped, not assumed empty, so a NATS blip cannot delete a node's rows.
  • The port probe now separates DeadlineExceeded (busy) from Unavailable (gone), and only the latter counts, after three consecutive misses.

Every routed model also left an in-process stub in the frontend's ModelLoader, and removal paths deleted only the database row, so the stub outlived the replica and the model was reported as loaded forever. The replica-removed hook became a list, and a new local-stub invalidator drops the stub once no healthy replica remains cluster-wide.

Alongside those: in_flight counters could leak high and pin a replica's VRAM against eviction; model-load deadlines now scale with checkpoint size and with progress rather than wall-clock; staging verification counts as progress rather than a stall; backend discovery no longer hides worker-installed or GPU-only backends behind the controller's filesystem and capability; the scheduler will not place a model on a node that cannot store it; and open responses are visible and cancellable across replicas.

Worker-side, a backend process whose directory a reinstall replaced is never reused, the gRPC port allocator is bounded and stops leaking dead backends' ports, deleted backends are reaped, and the worker has a real health endpoint with a mode-aware HEALTHCHECK.

🛡️ Inline fine-tuning reward code is now opt-in

POST /api/fine-tuning/jobs accepts reward_functions[].code, an inline Python body that was executed against a hand-rolled builtin allowlist. That allowlist was not a security boundary: standard CPython introspection reaches the real os module and yields arbitrary code execution on the host. Execution happened synchronously during a smoke test at job start, and the fine-tuning endpoint is unauthenticated by default.

Rather than trying to harden the allowlist, inline reward code is now refused unless the operator explicitly opts in with LOCALAI_TRL_ALLOW_INLINE_REWARD=true on the backend. Builtin reward functions are unaffected and keep working with no configuration. The documentation no longer describes the allowlist as a sandbox and states plainly that inline code is arbitrary execution.

Two further hardening fixes landed in the same cycle:

  • Tar hardlinks that escape the extraction root are rejected (#11266). ExtractArchive pre-scanned members and rejected symlinks, but tar hardlink entries carry a regular file mode and passed that check, and Header.Linkname was never validated, so an archive could create a link to a path outside the destination directory. Linkname now gets the same path check as member names; hardlinks resolving inside the root still extract, so ordinary archives are unaffected.
  • Cyclic $ref in a JSON-schema grammar is rejected (#11041) rather than recursing into a stack-overflow crash.

This release also picks up hono 4.12.25 for CVE-2026-54290.

🔗 PRs: #11068, #11266, #11041, #11023

🔍 Traces gain request identity

The API Traces panel recorded who issued each request but never showed it, and never captured the caller's network identity. The table now has a sortable User column, and the expanded row carries User, Client IP and User Agent, from echo's RealIP() (honouring X-Forwarded-For / X-Real-IP behind a trusted proxy). Fields render only when present, so older buffered traces and unauthenticated local requests degrade cleanly. The time column now shows the date too.

🌐 A new localai.io

The site splits in two: the project site at the root, and the documentation moved under /docs/. The Hugo docs site had always been localai.io, which left nowhere to explain what LocalAI is or to show what the team builds.

Every previously published URL keeps working. GitHub Pages has no server-side rewrites, so a generator walks the built docs output and leaves a meta refresh, a canonical link and a noindex at each old root path: 214 redirect stubs, covering bare .html files as well as directory indexes, and never overwriting a path the root site owns.

The new site adds an /engines/ page driven entirely by a YAML data file (so adding an engine is one edit, not hand-written HTML in two places), a /blog/, a real POSIX install.sh and a Kubernetes manifest wired to the actual /readyz and /healthz endpoints. An ecosystem band lists the companies whose engineers have contributed, the projects that integrate LocalAI, and where LocalAI has been written about, each backed by a different and stated standard of evidence, with ADOPTERS.md as the self-service mechanism for anyone who wants to be listed.
