DeepTutor v1.5.7 Release Notes

Veröffentlichungsdatum: 2026.07.31 Eine Fortsetzung von v1.5.6, die dem Tutor Zugriff auf Tools bietet, die DeepTutor nie geliefert hat: einen kuratierten Speicher gehosteter MCP-Dienste, die jede Person für sich selbst installiert, und 101 Befehlszeilen-Apps aus dem CLI-Anything-Katalog, die der Chat-Agent direkt aufrufen kann. Beide verfügen über die Autorisierung und Isolation, die eine gemeinsame Bereitstellung tatsächlich benötigt – die Installation ist eine privilegierte Aktion, die Ausführung nicht, und nichts, was eine Person autorisiert, bleibt irgendwo, wo die Code-Sandbox lesen kann. Drop-in – keine Migrationen.

Was ist neu?

Ein MCP-Store, den Sie selbst installieren

Learning Space → MCP Services ist ein Speicher mit 45 kuratierten gehosteten Servern, die Sie selbst in einem click hinzufügen, sowie allen Remote-Servern, die Sie per URL konfigurieren. Jeder Katalogendpunkt wurde überprüft, indem ihm ein echter MCP initialize gesendet wurde, und es wurde kein Logo-CDN kontaktiert – der Rendering-Shop würde andernfalls Ihre Liste der installierten Dienste bei jedem Mal an einen Dritten senden. Server, die 401 antworten (Notion, Linear, Sentry, Asana, Montag, Canva, Prisma), melden sich über OAuth 2.1 mit PKCE und dynamischer client-Registrierung an; Eine erneute Verbindung im Hintergrund blockiert niemals auf einem Einwilligungsbildschirm, sondern meldet lediglich needs_auth, sodass die Benutzeroberfläche eine Schaltfläche „Verbinden“ anbieten kann. Statische Schlüssel werden per Referenz gespeichert und zum Zeitpunkt der Verbindung im Speicher aufgelöst, sodass ein Token niemals in einer Konfigurationsdatei landet, die angezeigt, von einem API zurückgegeben oder in ein Protokoll kopiert wird. stdio-Einträge werden für den Self-Service abgelehnt: Ein Befehl wird vom Host als App-Benutzer ausgeführt. MCP wird nicht mehr unter „Einstellungen“ konfiguriert – /settings/mcp leitet zum Store weiter – und die Werkzeugauswahl fasst jetzt Hunderte von Werkzeugen in einer Reihe pro Dienst zusammen.

CLI Apps, die der Tutor ausführen kann

Learning Space → CLI Apps katalogisiert 101 Tools, die aus den beiden CLI-Anything-Registrierungen erstellt wurden, und der Chat-Agent ruft ein installiertes Tool direkt auf, wobei das eigene Nutzungshandbuch dieser App nur dann geladen wird, wenn es benötigt wird. Die Installation ist nur für den Administrator möglich, da pip install das paketeigene setup.py im Anwendungscontainer ausführt – selbst bei größter Sorgfalt ist dies kein Selbstbedienungsvorgang. Der install_cmd der Registrierung wird nie ausgeführt: Er wird in einen Plan geparst, dessen argv DeepTutor erstellt (die Registrierungen enthalten bereits curl … | bash), npm-Installationsskripte werden erzwungen, und ein Update, das nicht erstellt werden kann, setzt die Arbeitsumgebung zurück. 66 Erstanbieter-Harness-Einträge sind an einen überprüften CLI-Anything-Commit angeheftet; Alles, was auf einen anderen Upstream verweist, wird als „Drittanbieter“ gekennzeichnet, daher ist die Installation eine bewusste Entscheidung. Apps landen in data/cli-apps, jeweils einer Umgebung, die schreibgeschützt im Sandbox-Runner bereitgestellt wird. Diese Aufteilung ist der Punkt: Ein Escape-Befehl kann den Einstiegspunkt einer App nicht überschreiben und dazu führen, dass in jedem späteren Zug für jedes Konto der Ersatz ausgeführt wird.

Anmeldeinformationen, die die Sandbox nicht erreichen kann

Alles, was eine Person autorisiert, wurde nach data/system verschoben – dem einen Zweig des Datenbaums, der niemals im Runner gebunden ist. Codex-OAuth-Tokens leben jetzt in data/system/user-secrets/<owner>/private/openai-codex/, benutzerspezifische MCP-Konfigurationen in data/system/user-mcp/<owner>.json und MCP-Tokens und API-Schlüssel daneben. Vorhandene Codex-Anmeldungen verschieben sich bei der ersten Verwendung selbst, und bei der Verschiebung wird verhindert, dass sie über ein symbolisch verknüpftes Verzeichnis ausgeführt werden, anstatt das Risiko einzugehen, den Speicher eines anderen Kontos zu verschieben. Dies schließt eher ein echtes als ein theoretisches Risiko aus: Die Pro-Benutzer-Bereitstellung, die der Läufer erhält, ist ein ganzer Benutzer-Root, sodass ein unter data/users/<uid>/ gespeicherter Berechtigungsnachweis von der Sandbox-Shell jedes anderen Kontos aus lesbar – und beschreibbar – war.

Angeschlossene Werkzeuge, pro Person geregelt

Grants erhalten eine cli_apps-Whitelist mit der gleichen standardmäßigen Verweigerungshaltung, die MCP-Tools bereits hatten: Eine installierte App ist Code eines Drittanbieters, der in der Sandbox ausgeführt wird, und eine Bereitstellung, die einen solchen Code installiert, ist nicht die gleiche Entscheidung, wenn jedes Konto sie ausführen darf. Dahinter hält eine Registrierungsansicht pro Runde die Provider-Tools eines Benutzers vollständig aus der prozessglobalen Registrierung heraus – zwei Mandanten, deren Server einen Tool-Namen teilen, können sich nicht mehr gegenseitig blockieren – und lehnt ein nicht autorisiertes Tool bei execute ab, nicht nur im Manifest, weil ein Textprotokoll-Fallback einen Namen synthetisieren kann, der nie angeboten wurde.

Ein Komponist, der Ihnen sagt, wie voll das Fenster ist

Ein Chip im Composer meldet, was dieser Zug tatsächlich in das Kontextfenster des Modells eingefügt hat und was es füllt, gemessen anhand der bereits zusammengestellten Eingabeaufforderungsblöcke, Toolschemata und Nachrichtenlisten und nicht erneut abgeleitet – so kann die Anzeige nicht von dem abweichen, was gesendet wurde. Bei langen Gesprächen wird außerdem im linken Randbereich des Transkripts ein Häkchen angezeigt, eines pro von Ihnen gestellter Frage, um durch den Verlauf zurückspringen zu können.

DeepTutor auf einem Telefon

Die Arbeitsbereichs- und Dienstprogramm-Layouts werden jetzt auf kleinen Bildschirmen zu einer einspaltigen Shell mit einer verschiebbaren Seitenleiste zusammengefasst, anstatt ein Desktop-Layout mit drei Fenstern am Rand des Ansichtsfensters darzustellen.

Verschiedene Korrekturen

– Der Composer behält den Fokus, nachdem Sie ihn gesendet haben, und erhält ihn zurück, wenn Sie die Tabs wegwechseln und zurückkehren (#720). – Freigegebene Containerbilder tragen Herkunfts- und SBOM-Bescheinigungen (#722). – git wird im Anwendungs-Image und die Node-Runtime im Runner-Image installiert, was sowohl für das App-Installationsprogramm als auch für die Konsolenskripts von npm-gepackten Apps erforderlich ist.

Upgrade-Hinweise

Drop-in von v1.5.6: pip install -U deeptutor; Docker-Benutzer ziehen ghcr.io/hkuds/deeptutor:latest. Keine Schema- oder Konfigurationsänderungen, und ein vorhandener Codex-Login wird übernommen – seine Anmeldeinformationen werden beim ersten Auflösen automatisch neu lokalisiert.

  • docker-compose-Bereitstellungen sollten neu starten, nicht nur neu starten: Der Runner-Dienst erhält einen schreibgeschützten ./data/cli-apps-Mount, und ohne die Installation werden CLI-Apps katalogisiert, können aber nicht ausgeführt werden. – MCP-Server, die unter „Einstellungen“ konfiguriert wurden, bleiben dort, wo sie sind – der bereitstellungsweite mcp.json bleibt unverändert und weiterhin im Besitz des Administrators. Der neue Shop ist ein paralleler Shop pro Konto. /settings/mcp leitet jetzt dorthin weiter.
  • Die Installation einer CLI-App ist nur für Administratoren möglich und die Zuweisung ist ein zweiter Schritt. Ein Nicht-Administratorkonto sieht keine installierte App, bis ein Zuschuss sie benennt, genauso wie MCP-Tools und -Fähigkeiten bereits funktionieren. DeepTutor v1.5.7

Highlights

  • Per-account MCP store — 45 curated hosted servers installable in one click, each catalog endpoint validated with a real MCP initialize; 401 servers (Notion, Linear, Sentry, Asana, monday, Canva, Prisma) do OAuth 2.1 + PKCE with dynamic client registration, and background reconnect reports needs_auth rather than blocking on consent. Static keys are held by reference and resolved in memory at connect time, so tokens never land in config files, API responses, or logs; stdio entries are refused because a command is host execution. /settings/mcp now redirects here, and tool pickers collapse hundreds of tools to one row per service. Editorial note: this is a parallel per-user store — deployment-wide mcp.json stays admin-owned — and the store deliberately contacts no logo CDN, which would otherwise leak your installed-service list on every paint.

  • 101 agent-callable CLI apps — catalogued from two CLI-Anything registries, with an app's usage guide loaded on demand. Install is admin-only by design: pip install executes setup.py inside the application container. The registry's install_cmd is parsed into a plan whose argv DeepTutor constructs (the registries contain curl … | bash), npm install scripts are disabled, and a failed update rolls back the environment. 66 first-party harness entries are pinned to one reviewed commit; anything else is labelled third-party. Each app gets its own environment in data/cli-apps mounted read-only into the runner, so an escaped command can't overwrite an entry point and poison every later turn for every account. Watch out: install and assign are two separate steps — non-admins see no app until a grant names it.

  • Credentials removed from sandbox reach — everything authorizing a person moved to data/system, the one data branch never bind-mounted into the runner: Codex OAuth tokens to data/system/user-secrets/<owner>/private/openai-codex/, per-user MCP configs to data/system/user-mcp/<owner>.json, with MCP tokens/API keys alongside. This closes a concrete cross-tenant hole, not a theoretical one: the runner receives a whole user root, so credentials under data/users/<uid>/ were readable and writable from other accounts' sandboxes. Existing Codex logins self-relocate on first use, and the move refuses a symlinked directory rather than risk moving another account's store.

  • Per-person tool governance — grants gain a cli_apps whitelist with the same deny-by-default posture MCP tools already had: installing an app is not the same decision as letting every account run it. Behind it, a per-turn registry view keeps one user's provider tools out of the process-global registry, so two tenants whose servers expose the same tool name can no longer clobber each other, and unauthorized tools are rejected at execute (not just in the manifest) because a text-protocol fallback can synthesize a name that was never offered.

  • Context awareness and history navigation — a composer chip reports what this turn actually put in the context window and what is filling it, measured from the already-assembled prompt blocks, tool schemas, and message list, so the readout can't drift from what was sent. Long threads gain a tick rail in the transcript gutter (one tick per question) for jumping through history; the composer also retains focus after send and regains it on tab return (#720).

  • Packaging and platform — release images now carry provenance and SBOM attestations (#722); git is added to the app image and the Node runtime to the runner image for the installer and npm console scripts; small screens get a single-column shell with a slide-over sidebar. Operational watch-out: docker-compose users must re-up, not just restart, to pick up the new read-only ./data/cli-apps mount — without it apps are catalogued but cannot execute.

No breaking changes — drop-in from v1.5.6 with no schema or config changes; existing Codex logins relocate themselves on first use.

DeepTutor v1.5.7 Release Notes

Release Date: 2026.07.31

A follow-up to v1.5.6 that opens the tutor up to tools DeepTutor never shipped: a curated store of hosted MCP services each person installs for themselves, and 101 command-line apps from the CLI-Anything catalog the chat agent can call directly. Both arrive with the authorisation and isolation a shared deployment actually needs — installing is a privileged action, running is not, and nothing that authorises a person stays anywhere the code sandbox can read. Drop-in — no migrations.

What's New

An MCP store you install from yourself

Learning Space → MCP Services is a store of 45 curated hosted servers you add for yourself in one click, plus any remote server you configure by URL. Every catalog endpoint was verified by sending it a real MCP initialize, and no logo CDN is contacted — rendering the store would otherwise ship your installed-service list to a third party on every paint. Servers that answer 401 (Notion, Linear, Sentry, Asana, monday, Canva, Prisma) sign in over OAuth 2.1 with PKCE and dynamic client registration; a background reconnect never blocks on a consent screen, it just reports needs_auth so the UI can offer a Connect button. Static keys are stored by reference and resolved in memory at connect time, so a token never lands in a config file that gets displayed, returned by an API, or copied into a log. stdio entries are refused for self-service: a command is host execution as the app user.

MCP is no longer configured under Settings — /settings/mcp redirects to the store — and the tool pickers now fold hundreds of tools into one row per service.

CLI apps the tutor can run

Learning Space → CLI Apps catalogs 101 tools snapshotted from the two CLI-Anything registries, and the chat agent calls an installed one directly, with that app's own usage guide loaded only when it is needed. Installing is administrator-only, because pip install runs the package's own setup.py in the application container — no amount of care makes that self-service. The registry's install_cmd is never executed: it is parsed into a plan whose argv DeepTutor builds (the registries already contain curl … | bash), npm install scripts are forced off, and an update that fails to build rolls the working environment back. 66 first-party harness entries are pinned to one reviewed CLI-Anything commit; anything pointing at a different upstream is labelled third-party so installing it is an informed choice.

Apps land in data/cli-apps, one environment each, mounted read-only into the sandbox runner. That split is the point: an escaped command cannot overwrite an app's entry point and have every later turn, for every account, run the replacement.

Credentials the sandbox cannot reach

Everything that authorises a person moved to data/system — the one branch of the data tree that is never bind-mounted into the runner. Codex OAuth tokens now live in data/system/user-secrets/<owner>/private/openai-codex/, per-user MCP configs in data/system/user-mcp/<owner>.json, and MCP tokens and API keys beside them. Existing Codex logins relocate themselves on first use, and the move refuses to run through a symlinked directory rather than risk relocating another account's store.

This closes a real exposure rather than a theoretical one: the per-user mount the runner receives is a whole user root, so a credential kept under data/users/<uid>/ was readable — and writable — from every other account's sandboxed shell.

Plugged-in tools, governed per person

Grants gain a cli_apps whitelist with the same deny-by-default posture MCP tools already had: an installed app is third-party code running in the sandbox, and a deployment installing one is not the same decision as every account being allowed to run it. Behind that, a per-turn registry view keeps one user's provider tools out of the process-global registry entirely — two tenants whose servers share a tool name can no longer clobber each other — and refuses an unauthorised tool at execute, not just in the manifest, because a text-protocol fallback can synthesise a name that was never offered.

A composer that tells you how full the window is

A chip in the composer reports what this turn actually put in the model's context window and what is filling it, measured from the already-assembled prompt blocks, tool schemas, and message list rather than re-derived — so the readout cannot drift from what was sent. Long conversations also get a rail of ticks in the transcript's left gutter, one per question you asked, for jumping back through the history.

DeepTutor on a phone

The workspace and utility layouts now collapse to a single-column shell with a slide-over sidebar on small screens instead of rendering a desktop three-pane layout off the edge of the viewport.

Assorted fixes

  • The composer keeps focus after you send, and gets it back when you switch tabs away and return (#720).
  • Released container images carry provenance and SBOM attestations (#722).
  • git is installed in the application image and the Node runtime in the runner image, both required by the app installer and by npm-packaged apps' console scripts.

Upgrade Notes

Drop-in from v1.5.6: pip install -U deeptutor; Docker users pull ghcr.io/hkuds/deeptutor:latest. No schema or config changes, and an existing Codex login carries over — its credentials relocate themselves the first time they are resolved.

  • docker-compose deployments should re-up, not just restart: the runner service gains a read-only ./data/cli-apps mount, and without it installed CLI apps are catalogued but cannot execute.
  • MCP servers configured under Settings stay where they are — the deployment-wide mcp.json is unchanged and still admin-owned. The new store is a parallel, per-account one; /settings/mcp now redirects to it.
  • Installing a CLI app is administrator-only, and assigning it is a second step. A non-admin account sees no installed app until a grant names it, the same way MCP tools and skills already work.
