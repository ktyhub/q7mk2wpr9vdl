Codegraph v1.1.3

[1.1.3] – 29.06.2026

Korrekturen

  • CodeGraph indiziert jetzt verschachtelte Repositorys, die Git-Datensätze enthalten, als Gitlinks, sodass ein Arbeitsbereich, der durch das Stapeln mehrerer Repos ineinander erstellt wird, vollständig von einem einzigen codegraph init an der Spitze aus indiziert. Wenn ein Repo ein anderes Git-Repo enthält, das mit git add in das Repo eingefügt wurde – Git verfolgt es also als 160000-„Commit“-Zeiger und nicht als Ordner mit Dateien – oder ein Submodul, das kein aktives, initialisiertes Submodul in Ihrem Checkout ist, wurde die Quelle dieses verschachtelten Repos früher vollständig übersprungen: Die Indizierung der obersten Ebene endete an der Grenze des verschachtelten Repos und zog nur die eigenen Dateien des äußeren Repos ein, also ein gestapeltes Repo Das Projekt war fast leer (in einem Bericht wurden etwa 10 Dateien im Stammverzeichnis indiziert). CodeGraph steigt nun in jedes dieser verschachtelten Repositorys ab, das über einen echten Arbeitsbaum auf der Festplatte verfügt, und indiziert es rekursiv als eigenes eingebettetes Repository, sodass jede Ebene eines gestapelten Arbeitsbereichs abgedeckt wird. Aktive Submodule (bereits verarbeitet) und einfache, nicht verfolgte verschachtelte Klone bleiben unverändert; ein verschachteltes Repo unter einem Abhängigkeitsverzeichnis wie vendor/ oder node_modules/ bleibt ausgeschlossen; und ein Submodul, für das nichts auf der Festplatte ausgecheckt ist, wird korrekterweise in Ruhe gelassen und nicht als leer gemeldet. Danke @ofergr und @kun-yx für die Berichte. (#1031, #1033) – CodeGraph zeigt nicht mehr die irreführende Warnung „anderer Git-Arbeitsbaum“ an, wenn Sie in einem Submodul (oder einem anderen verschachtelten Repo) eines Arbeitsbereichs arbeiten, den Sie im Stammverzeichnis indiziert haben. Da die Indizierung eines Arbeitsbereichs nun seine Submodule und eingebetteten Klone einbezieht, wird eine von innen ausgeführte Abfrage korrekt bis zum einzelnen Index des Arbeitsbereichs aufgelöst – es wurde jedoch immer noch gewarnt, dass die Ergebnisse von „einem anderen Arbeitsbaum“ stammten, und es wurde empfohlen, codegraph init -i auszuführen, was das Submodul wieder in seinen eigenen separaten Index aufgeteilt und die einheitliche Ansicht rückgängig gemacht hätte. CodeGraph erkennt jetzt, dass der Code des verschachtelten Repos bereits Teil des Arbeitsbereichsindex ist und bleibt still. Die Warnung erscheint immer noch für einen echten Git-Arbeitsbaum – ein zweites Auschecken des gleichen Repositorys in einem anderen Zweig, der tatsächlich seine eigenen nicht festgeschriebenen Symbole hat –, da er für diesen Fall existiert. (#1031, #1033) – Unter Windows wird der Hintergrundserver von CodeGraph jetzt sauber heruntergefahren, anstatt gelegentlich mit einem Absturzfehler abzubrechen. Wenn das indizierte Projekt ein verschachteltes Repository (ein Submodul oder einen eingebetteten Klon) enthielt, konnte das Stoppen des Servers dazu führen, dass der File Watcher heruntergefahren und mit einem Windows-Absturzcode beendet wurde, statt dass es sich um einen sauberen Exit handelte. Durch das Herunterfahren wird dieser Abbau nun zuerst abgeschlossen, sodass der Server sauber und zeitnah stoppt. (Nur Windows; andere Plattformen waren nicht betroffen.) (#1033)
  • C++-Klassen, die von einer Vorlagenbasis erben – class Widget : public Base<int>, eine CRTP-Basis wie class App : public CRTPBase<App> oder eine Struktur, die eine Vorlage erbt – sind jetzt im Diagramm mit dieser Basisklasse verknüpft. Zuvor führten die Vorlagenargumente (<int>) dazu, dass die Vererbung nicht erkannt wurde, sodass diese Klassen so aussahen, als würden sie von nichts erben, und die Auswirkungs-/Aufruferanalyse endete an der Grenze; Die Verbindung wird nun wie jede andere Basisklasse verfolgt. Danke @ryancu7 für den Bericht. (#1043) – Auf dem Stapel erstellte C++-Objekte – Calculator calc(0) oder Widget w{1, 2} – zeichnen jetzt auf, dass die einschließende Funktion diese Klasse instanziiert, genau wie es bereits bei der Heap-Konstruktion (new Calculator(0)) der Fall war. Bisher wurde nur das new-Formular verfolgt, sodass eine Funktion, die Objekte mit der normalen Stack-Syntax erstellte, so aussah, als würde sie diese nicht erstellen, und die Abhängigkeit fehlte bei Impact/Callern. Danke @Dshuishui für den Bericht. (#1035)
  • Das Diagramm speichert keine doppelten Kopien derselben Beziehung mehr. Die gleiche Abhängigkeit zwischen denselben zwei Symbolen an derselben Stelle könnte mehr als einmal aufgezeichnet werden, was die Kantenanzahl erhöht und dazu führt, dass Aufrufer/Auswirkungsergebnisse eine Beziehung zweimal auflisten. Jede Beziehung wird nun genau einmal gespeichert und bestehende Projekte werden automatisch dedupliziert, wenn CodeGraph sie das nächste Mal öffnet. Danke @inth3shadows für den ausführlichen Bericht. (#1034)
  • codegraph node kann jetzt eine Datei über die Befehlszeile lesen. Dateilesemodus – übergeben Sie -f/--file, um die Quelle einer Datei mit Zeilennummern und den davon abhängigen Dateien zu erhalten, die gleiche Ausgabe wie das MCP-Tool codegraph_node – wurde mit „fehlendes erforderliches Argument ‚Name‘“ abgelehnt, da der Befehl immer einen Symbolnamen erforderte, obwohl der Dateimodus keinen hat, sodass die Funktion vom CLI aus nicht erreichbar ist. Der Symbolname ist jetzt optional: codegraph node -f src/auth.ts (oder codegraph node src/auth.ts) liest die Datei, codegraph node parseToken sucht nach einem Symbol und führt es ohne keines von beiden aus, gibt einen kurzen Verwendungshinweis anstelle eines kryptischen Fehlers aus. Danke @jcrabapple für den Bericht. (#1044)
  • codegraph query druckt neben jedem Ergebnis keine bedeutungslosen Relevanzprozentsätze wie „12042 %“ mehr aus. Bei der Zahl handelte es sich um einen reinen Volltextsuchwert – der nur zum Ordnen der Ergebnisse nützlich war, nicht als tatsächliche Zahl von 0–100 %. Daher ergab die Multiplikation mit 100 wilde Werte, die die Ausgabe fehlerhaft aussehen ließen. Die Ergebnisse werden bereits mit der besten Übereinstimmung zuerst aufgelistet, sodass der CLI sie jetzt nur in dieser Reihenfolge ohne Bewertung anzeigt und mit dem übereinstimmt, was das Suchtool den KI-Agenten meldet. Wenn Sie ein Skript für codegraph query --json erstellen, ist das rohe score weiterhin für die Sortierung oder Schwellenwertermittlung enthalten. Danke @jcrabapple für den Bericht. (#1045) – codegraph explore meldet nicht mehr eine alarmierende, überhöhte Ergebnisanzahl bei umfassenden Abfragen in natürlicher Sprache. Die Zusammenfassung „N Symbole in M ​​Dateien gefunden“ zählte jedes Symbol, das die Suche beim Ranking berücksichtigte, sodass eine umfassende Abfrage (z. B. „Veröffentlichungsstatus für API“) bei einem großen Projekt Hunderte von Symbolen in einem großen Teil der Codebasis ankündigen konnte – so, als ob man sich durch alle durchwühlen müsste – obwohl nur die relevantesten Handvoll tatsächlich mit ihrer Quelle angezeigt werden. In der Zusammenfassung werden jetzt nur die Dateien gezählt, deren Quelle die Suche zurückgibt, sodass die Zahl mit der angezeigten Zahl übereinstimmt. Rangfolge und Ergebnisse bleiben unverändert: Die richtigen Symbole stehen weiterhin an erster Stelle und alle weiteren relevanten Dateien werden weiterhin namentlich unter „Oben nicht angezeigt“ aufgeführt, sodass nichts verborgen bleibt. Danke @jcrabapple für den Bericht. (#1046)
  • Android-Ressourcendateien blähen den Index nicht mehr auf. Ein res/-Baum – Layouts, Zeichenelemente, Wertetaschen (Strings, Farben, Stile), Menüs, Navigationsdiagramme – enthält keine Codesymbole, aber in einer Android-App kann es sich um die überwältigende Mehrheit der Dateien handeln (ein Projekt: 26.000+ XML-Dateien, ~97 % von allem, trägt keine Symbole bei), was die Datenbank aufblähte, die Indizierung verlangsamte und die Dateianzahl und codegraph explore/Suchergebnisse mit Einträgen auffüllte, die nichts zu finden haben. CodeGraph überspringt jetzt standardmäßig Android-Ressourcenverzeichnisse – res/layout/, res/values/, res/drawable/, res/menu/ und den Rest, einschließlich ihrer Gebietsschema-/Dichte-/Versionsvarianten wie res/values-es/ oder res/drawable-hdpi/. Ihr eigentlicher Code bleibt unberührt, ebenso wie die einzige Art von XML, die Symbole enthält – MyBatis-Mapper-Dateien, die unter src/main/resources/ und nicht unter res/ gespeichert sind. res/raw/ wird absichtlich beibehalten (es kann reale Vermögenswerte enthalten), und Sie können jedes ausgeschlossene Verzeichnis mit einer .gitignore-Negation wie !res/values/ wieder einschließen. Danke @jcrabapple für den Bericht. (#1047)

codegraph v1.1.3

[1.1.3] - 2026-06-29

Fixes

  • CodeGraph now indexes nested repositories that git records as gitlinks, so a workspace built by stacking several repos inside one another indexes completely from a single codegraph init at the top. When a repo contains another git repo that was git added into it — so git tracks it as a 160000 "commit" pointer rather than a folder of files — or a submodule that isn't an active, initialized submodule in your checkout, that nested repo's source used to be skipped entirely: indexing the top level stopped at the nested repo's boundary and pulled in only the outer repo's own files, so a stacked-repo project came up nearly empty (one report saw ~10 files indexed at the root). CodeGraph now descends into each such nested repo that has a real working tree on disk and indexes it as its own embedded repository, recursively, so every layer of a stacked workspace is covered. Active submodules (already handled) and plain untracked nested clones are unchanged; a nested repo under a dependency directory such as vendor/ or node_modules/ stays excluded; and a submodule with nothing checked out on disk is correctly left alone rather than reported as empty. Thanks @ofergr and @kun-yx for the reports. (#1031, #1033)
  • CodeGraph no longer shows a misleading "different git working tree" warning when you work inside a submodule (or other nested repo) of a workspace you indexed at its root. Because indexing a workspace now pulls in its submodules and embedded clones, a query run from inside one correctly resolves up to the workspace's single index — but it was still warning that the results came from "a different working tree" and suggesting you run codegraph init -i, which would have split the submodule back out into its own separate index and undone the unified view. CodeGraph now recognizes that the nested repo's code is already part of the workspace index and stays quiet. The warning still appears for a genuine git worktree — a second checkout of the same repository on another branch, which really does have its own uncommitted symbols — since that's the case it exists for. (#1031, #1033)
  • On Windows, CodeGraph's background server now shuts down cleanly instead of occasionally aborting with a crash error. When the indexed project contained a nested repository (a submodule or embedded clone), stopping the server could race the file watcher's teardown and exit with a Windows crash code rather than a clean exit. Shutdown now lets that teardown finish first, so the server stops cleanly and promptly. (Windows only; other platforms were unaffected.) (#1033)
  • C++ classes that inherit from a templated base — class Widget : public Base<int>, a CRTP base like class App : public CRTPBase<App>, or a struct inheriting a template — are now linked to that base class in the graph. Previously the template arguments (<int>) made the inheritance go unrecognized, so these classes looked like they inherited from nothing and impact/callers analysis stopped at the boundary; the connection is now followed like any other base class. Thanks @ryancu7 for the report. (#1043)
  • C++ objects constructed on the stack — Calculator calc(0) or Widget w{1, 2} — now record that the enclosing function instantiates that class, the same as heap construction (new Calculator(0)) already did. Previously only the new form was tracked, so a function that built objects with the ordinary stack syntax looked like it didn't construct them and the dependency was missing from impact/callers. Thanks @Dshuishui for the report. (#1035)
  • The graph no longer stores duplicate copies of the same relationship. The same dependency between the same two symbols at the same spot could be recorded more than once, which inflated edge counts and let callers/impact results list a relationship twice. Each relationship is now stored exactly once, and existing projects are de-duplicated automatically the next time CodeGraph opens them. Thanks @inth3shadows for the detailed report. (#1034)
  • codegraph node can now read a file from the command line. File-read mode — pass -f/--file to get a file's source with line numbers plus the files that depend on it, the same output as the codegraph_node MCP tool — was rejected with "missing required argument 'name'", because the command always demanded a symbol name even though file mode has none, leaving the feature unreachable from the CLI. The symbol name is now optional: codegraph node -f src/auth.ts (or codegraph node src/auth.ts) reads the file, codegraph node parseToken looks up a symbol, and running it with neither prints a short usage hint instead of a cryptic error. Thanks @jcrabapple for the report. (#1044)
  • codegraph query no longer prints meaningless relevance percentages like "12042%" next to each result. The number was a raw full-text search score — useful only for ordering the results, not as a real 0–100% figure — so multiplying it by 100 produced wild values that made the output look broken. Results are already listed best-match first, so the CLI now just shows them in that order with no score, matching what the search tool reports to AI agents. If you script against codegraph query --json, the raw score is still included for sorting or thresholding. Thanks @jcrabapple for the report. (#1045)
  • codegraph explore no longer reports an alarming, inflated result count on broad natural-language queries. The "Found N symbols across M files" summary used to count every symbol the search swept in while ranking, so a broad query (for example "publish status to the API") on a large project could announce hundreds of symbols across a big fraction of the codebase — reading as if you had to wade through all of them — even though only the most relevant handful are actually shown with their source. The summary now counts just the files explore returns source for, so the number matches what you see. Ranking and results are unchanged: the right symbols still come first, and any further relevant files are still listed by name under "Not shown above" so nothing is hidden. Thanks @jcrabapple for the report. (#1046)
  • Android resource files no longer bloat the index. A res/ tree — layouts, drawables, value bags (strings, colors, styles), menus, navigation graphs — contains no code symbols, but on an Android app it can be the overwhelming majority of files (one project: 26,000+ XML files, ~97% of everything, contributing zero symbols), which inflated the database, slowed indexing, and padded file counts and codegraph explore/search results with entries that have nothing to find. CodeGraph now skips Android resource directories by default — res/layout/, res/values/, res/drawable/, res/menu/, and the rest, including their locale/density/version variants like res/values-es/ or res/drawable-hdpi/. Your actual code is untouched, and so is the one kind of XML that does carry symbols — MyBatis mapper files, which live under src/main/resources/, not res/. res/raw/ is deliberately kept (it can hold real assets), and you can re-include any excluded directory with a .gitignore negation such as !res/values/. Thanks @jcrabapple for the report. (#1047)
