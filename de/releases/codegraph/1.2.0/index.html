Codegraph v1.2.0

[1.2.0] – 02.07.2026

Neue Funktionen

  • Methodenaufrufe, die über eine lokale Variable erfolgen, werden jetzt in vielen weiteren Sprachen in die Methode aufgelöst. Wenn Code const logger = new Logger(); logger.log(); (oder das Äquivalent) ausführt, leitet CodeGraph den Typ der lokalen Variablen aus ihrer Deklaration oder ihrem Initialisierer ab und verknüpft den Aufruf mit der richtigen Methode – sodass diese Aufrufe jetzt in Aufrufer-, Impact-/Blast-Radius- und codegraph_explore-Flow-Traces angezeigt werden, anstatt verworfen zu werden. Bisher wurde dies nur von C++ erledigt; Es deckt jetzt auch TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala und PHP ab. (#1108) – Ruby-Methodenaufrufe auf einem Empfänger (logger.log) zeichnen jetzt eine Kante zur Methode auf. Zuvor behielt der Ruby-Indexer nur den Empfänger und verwarf den Methodennamen, sodass eine über eine Variable oder ein Objekt aufgerufene Methode keine aufgezeichneten Aufrufer hatte und in den Impact-/Blast-Radius- und Flow-Traces fehlte; In Kombination mit der oben genannten lokalen Variablentypinferenz verknüpft logger = Logger.new; logger.log jetzt mit Logger#log. Auch Aufrufe einer Klassenmethode (Foo.bar) und der Objektkonstruktion (Foo.new) werden weiterhin aufgezeichnet. (#1110) – Die gleiche Auflösung lokaler Methodenaufrufe gilt jetzt auch für Lua, Luau, R und Pascal/Delphi. Eine über eine lokale Methode aufgerufene Methode – Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log() oder Pascal var lg: TLogger; ... lg.Log – verknüpft jetzt mit der richtigen Methode, anstatt gelöscht zu werden. (#1112)

Korrekturen

– Die Indizierung eines großen Projekts wird nicht mehr mit der Meldung „Hauptthread reagiert nicht – der verkeilte Prozess wird beendet“ abgebrochen. Der Sicherheitswächter, der einen wirklich hängengebliebenen Index stoppt, verwechselte langsame, aber normale Arbeit mit einem Stillstand: Bei einem großen Repo kann das Verknüpfen von Referenzen und dateiübergreifenden Beziehungen durchaus eine Weile laufen, und diese Arbeit gibt jetzt regelmäßig nach, sodass der Wächter echten Fortschritt von einem echten Stillstand unterscheiden kann. Projekte, die zuvor codegraph init / codegraph index nicht abschließen konnten (und auf CODEGRAPH_NO_WATCHDOG=1 zurückgreifen mussten), werden jetzt normal abgeschlossen, während ein wirklich hängender Prozess immer noch abgefangen wird. Vielen Dank an @zmcrazy, @YoungLiao und @GeeLab-Mob für die Berichte. (#1091) – Unter Windows blinkt ein Konsolenfenster nicht mehr kurz, wenn CodeGraph als Hintergrund-MCP-Server ausgeführt wird. Wenn der npm-Launcher die gebündelte Laufzeit startete – was jedes Mal passiert, wenn ein Editor den Server startet oder sich nach dem Leerlauf des Daemons wieder verbindet – und während seines Selbstheilungsschritts, der ein fehlendes Plattform-Bundle extrahiert, öffnete Windows für einen Moment ein schwarzes Konsolenfenster (Conhost). Beide starten jetzt im Verborgenen und entsprechen dem Verhalten des Daemons. Der Browser-Öffnungsschritt von codegraph login wurde auf die gleiche Weise gehärtet. Danke @luoyerr für den Bericht und die Ursachenanalyse. (#1092) – C++-Forward-Deklarationen verdrängen nicht mehr die eigentliche Klassendefinition. Eine class Foo;-Vorwärtsdeklaration – üblich in großen C++- und Unreal Engine-Codebasen, wo eine häufig verwendete Klasse über Dutzende von Headern vorwärtsdeklariert wird – wurde jedes Mal, wenn sie auftauchte, als eigener Klassenknoten indiziert. Die Erkundung dieser Klasse ergab also überwiegend Forward-Declaration-Sites und konnte sogar eine davon als Repräsentant für Blast-Radius auswählen, wodurch die tatsächliche Definition und ihre Mitglieder und Aufrufer vergraben wurden. Körperlose Vorwärtsdeklarationen werden jetzt für C und C++ übersprungen, genau wie dies bereits bei vorwärts deklarierten Strukturen und Aufzählungen der Fall war, sodass nur die tatsächliche Definition indiziert wird. Sprachen, in denen eine Klasse ohne Körper eine vollständige Definition ist – wie Kotlins class Empty und Scala – sind davon nicht betroffen. Danke @luoyxy für den Bericht und die Ursachenanalyse. (#1093) – C++-Methoden, die eine Referenz zurückgeben, und benutzerdefinierte Konvertierungsoperatoren werden jetzt unter ihren korrekten Namen indiziert. Ein Inline-Getter wie const FGameplayTagContainer& GetActiveTags() const – überall in Unreal Engine-Headern – wurde als & GetActiveTags() const statt als GetActiveTags indiziert, und ein Konvertierungsoperator wie operator EALSMovementState() const behielt seinen nachgestellten () const bei, anstatt operator EALSMovementState zu lesen. In beiden Fällen bedeutete der verstümmelte Name, dass Sie das Symbol nicht namentlich finden konnten und seine Aufrufer nicht verknüpft waren. Beide lesen sich jetzt sauber und entsprechen der Funktionsweise der Zeiger- und Wertrückgabemethoden. (#1096) – C++-Funktionen, die mit einem Inline-Spezifizierer-Makro vor dem Rückgabetyp geschrieben wurden, werden jetzt korrekt indiziert. In der Unreal Engine werden Inline-Helfer üblicherweise als FORCEINLINE FString GetEnumerationToString(...) geschrieben. Das Makro FORCEINLINE veranlasste den Parser, den Rückgabetyp als Teil des Funktionsnamens zu lesen (FString GetEnumerationToString anstelle von GetEnumerationToString) und verlor den tatsächlichen Rückgabetyp, sodass die Funktion nicht anhand des Namens gefunden werden konnte und ihre Aufrufer nicht verknüpft waren. CodeGraph erkennt jetzt die standardmäßigen Unreal-Inline-Makros (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), sodass sowohl der Name als auch der Rückgabetyp erfasst werden. (#1100) – Die gleiche Wiederherstellung von Funktionsnamen deckt jetzt Inline-Makros aus gängigen C++-Bibliotheken von Drittanbietern ab, nicht nur aus Unreal Engine – einschließlich pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE) und generisches ALWAYS_INLINE / FORCE_INLINE. Damit dekorierte Funktionen werden nun unter ihrem echten Namen indiziert. Bei einem großen Unreal-Projekt, das diese Bibliotheken anbietet, wurde dadurch der größte Teil der verbleibenden Verstümmelung von Funktionsnamen beseitigt. (#1101) – C++-Funktionsnamen werden jetzt auch dann wiederhergestellt, wenn sie mit einem Makro versehen sind, das CodeGraph nicht genau kennt. Bei einer zuvor mit SOME_LIBRARY_MACRO ReturnType doWork(...) geschriebenen Funktion wurde das Makro oder der Rückgabetyp immer dann in den Namen übernommen, wenn das Makro nicht von CodeGraph erkannt wurde. Jetzt wird der echte Name (doWork) unabhängig vom Makro wiederhergestellt, sodass er auffindbar ist und seine Aufrufer verlinken – keine Konfiguration pro Bibliothek erforderlich. Die Liste der erkannten Makros wurde ebenfalls erweitert (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson), sodass diese zusätzlich den Rückgabetyp erfassen. Dies bereinigt immer nur einen bereits verstümmelten Namen und ist auf C und C++ beschränkt, sodass normale Namen – und Sprachen wie Kotlin und Scala, in denen Bezeichner legitimerweise Leerzeichen enthalten können – nicht betroffen sind. (#1102) – Der Satz von C++-Bibliotheken, deren Makros für eine vollständige Wiederherstellung vom Rückgabetyp erkannt werden, wurde weit über die Unreal Engine hinaus erweitert – umfasst jetzt Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite und die gängigen Windows-Aufrufkonventionen (daher indiziert HRESULT WINAPI CreateThing(...) als CreateThing-Rückgabe). HRESULT). Bei Funktionen aus Bibliotheken, die nicht in der Liste enthalten sind, wird der Name weiterhin automatisch wiederhergestellt. Durch die Auflistung wird zusätzlich der Rückgabetyp wiederhergestellt. (#1103)

  • Die Ergebnisse der Graphendurchquerung und des Explosionsradius lassen in einigen Randfällen keine Beziehungen mehr fallen oder verwechseln sie. Wenn ein Symbol über mehr als einen Pfad erreicht werden kann, könnte eine Abfrage zum Aufprall-/Explosionsradius eine direkte Abhängigkeit zwischen zwei Symbolen auslassen, die bereits auf andere Weise verknüpft waren. Unabhängig davon könnte die von der Bibliothek API verwendete Graphendurchquerung auf niedrigerer Ebene nur eine von mehreren Beziehungen zwischen demselben Symbolpaar beibehalten (z. B. ein Symbol, das ein anderes Symbol sowohl anruft als auch referenziert), einen über zwei verschiedene Anrufstellen erreichten Anrufer zweimal zählen oder etwas mehr Ergebnisse als die angeforderte Größenbeschränkung für ein Symbol mit sehr hoher Verbindung zurückgeben. Diese bestanden seit langem und wurden größtenteils durch spätere Deduplizierung maskiert, sodass die täglichen Abfrageergebnisse weitgehend unbeeinflusst blieben, aber der Durchlauf gibt jetzt den vollständigen, korrekt begrenzten Satz zurück. Vielen Dank an @inth3shadows für die präzisen, individuell nachverfolgten Berichte. (#1086, #1087, #1088, #1089, #1090) – Methodenaufrufe für gleichnamige Klassen in verschiedenen Dateien werden jetzt in die richtige Definition aufgelöst. Wenn zwei Dateien beispielsweise jeweils eine Logger-Klasse mit ihrer eigenen log()-Methode deklarierten, könnte ein Aufruf mit der Definition verknüpft werden, die zufällig zuerst indiziert wurde – ein Aufruf in einer Datei zeigte also fälschlicherweise auf die Klasse in einer anderen, was die Aufrufer dieser Methode und den Explosionsradius verwechselte. Dies betraf Aufrufe, die als obj.log(), Logger.log() und Logger::log() in vielen Sprachen geschrieben wurden, darunter C++, Python, TypeScript, Java, C# und Rust. Wenn ein Methodenname nicht eindeutig ist, bevorzugt CodeGraph jetzt die Definition in der aufrufenden Datei selbst – im allgemeinen Fall das richtige Ziel –, während Java/Kotlin-Aufrufe, die ein import bereits an eine andere Datei anheftet, davon nicht betroffen sind. Vielen Dank an @inth3shadows für die minimale Reproduktion und Ursachenanalyse. (#1079)

codegraph v1.2.0

[1.2.0] - 2026-07-02

New Features

  • Method calls made through a local variable now resolve to the method in many more languages. When code does const logger = new Logger(); logger.log(); (or the equivalent), CodeGraph infers the local variable's type from its declaration or initializer and links the call to the right method — so these calls now show up in callers, impact/blast-radius, and codegraph_explore flow traces instead of being dropped. Previously only C++ handled this; it now also covers TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala, and PHP. (#1108)
  • Ruby method calls made on a receiver (logger.log) now record an edge to the method. Previously the Ruby indexer kept only the receiver and discarded the method name, so a method called through a variable or object had no recorded callers and was missing from impact/blast-radius and flow traces; combined with the local-variable type inference above, logger = Logger.new; logger.log now links to Logger#log. Calls to a class method (Foo.bar) and object construction (Foo.new) are still recorded too. (#1110)
  • The same local-variable method-call resolution now extends to Lua, Luau, R, and Pascal/Delphi. A method invoked through a local — Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log(), or Pascal var lg: TLogger; ... lg.Log — now links to the right method instead of being dropped. (#1112)

Fixes

  • Indexing a large project no longer gets killed partway through with a "Main thread unresponsive — killing the wedged process" message. The safety watchdog that stops a genuinely stuck index was mistaking slow-but-normal work for a hang: on a big repo, linking up references and cross-file relationships can legitimately run for a while, and that work now regularly yields so the watchdog can tell real progress from a true stall. Projects that previously failed to finish codegraph init / codegraph index (and had to fall back to CODEGRAPH_NO_WATCHDOG=1) now complete normally, while a genuinely hung process is still caught. Thanks @zmcrazy, @YoungLiao, and @GeeLab-Mob for the reports. (#1091)
  • On Windows, a console window no longer briefly flashes when CodeGraph runs as a background MCP server. When the npm launcher started the bundled runtime — which happens every time an editor starts the server or reconnects after the daemon idles out — and during its self-heal step that extracts a missing platform bundle, Windows would pop up a black console (conhost) window for a moment. Both now launch hidden, matching how the daemon already behaved; the browser-open step of codegraph login was hardened the same way. Thanks @luoyerr for the report and root-cause analysis. (#1092)
  • C++ forward declarations no longer crowd out the real class definition. A class Foo; forward declaration — common in large C++ and Unreal Engine codebases, where a heavily used class is forward-declared across dozens of headers — was indexed as its own class node every time it appeared. So exploring that class returned mostly forward-declaration sites, and could even pick one of them as the representative for blast-radius, burying the actual definition and its members and callers. Bodiless forward declarations are now skipped for C and C++, exactly as forward-declared structs and enums already were, so only the real definition is indexed. Languages where a class with no body is a complete definition — such as Kotlin's class Empty and Scala — are unaffected. Thanks @luoyxy for the report and root-cause analysis. (#1093)
  • C++ methods that return a reference, and user-defined conversion operators, are now indexed under their correct names. An inline getter like const FGameplayTagContainer& GetActiveTags() const — everywhere in Unreal Engine headers — was indexed as & GetActiveTags() const instead of GetActiveTags, and a conversion operator like operator EALSMovementState() const kept its trailing () const instead of reading operator EALSMovementState. In both cases the garbled name meant you couldn't find the symbol by name and its callers weren't linked. Both now read cleanly, matching how pointer-returning and value-returning methods already worked. (#1096)
  • C++ functions written with an inline-specifier macro before the return type are now indexed correctly. In Unreal Engine, inline helpers are commonly written FORCEINLINE FString GetEnumerationToString(...); the FORCEINLINE macro made the parser read the return type as part of the function's name (FString GetEnumerationToString instead of GetEnumerationToString) and lose the real return type, so the function couldn't be found by name and its callers weren't linked. CodeGraph now recognizes the standard Unreal inline macros (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), so both the name and the return type are captured. (#1100)
  • The same function-name recovery now covers inline macros from common third-party C++ libraries, not just Unreal Engine — including pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE), and generic ALWAYS_INLINE / FORCE_INLINE. Functions decorated with these are now indexed under their real names. On a large Unreal project vendoring these libraries this cleaned up the large majority of remaining function-name garbling. (#1101)
  • C++ function names are now recovered even when decorated with a macro CodeGraph doesn't specifically know about. A function written SOME_LIBRARY_MACRO ReturnType doWork(...) previously had the macro or return type absorbed into its name whenever the macro wasn't one CodeGraph recognized; now the real name (doWork) is recovered regardless of the macro, so it's findable and its callers link — no per-library configuration needed. The recognized-macro list was also broadened (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson) so those additionally capture the return type. This only ever cleans up an already-garbled name and is limited to C and C++, so ordinary names — and languages like Kotlin and Scala where identifiers can legitimately contain spaces — are unaffected. (#1102)
  • The set of C++ libraries whose macros are recognized for full return-type recovery was expanded well beyond Unreal Engine — now spanning Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite, and the common Windows calling conventions (so HRESULT WINAPI CreateThing(...) indexes as CreateThing returning HRESULT). Functions from libraries not on the list still get their name recovered automatically; being listed additionally recovers the return type. (#1103)
  • Graph traversal and blast-radius results no longer drop or miscount relationships in a handful of edge cases. When a symbol could be reached by more than one path, an impact/blast-radius query could leave out a direct dependency between two symbols that were already linked another way; separately, the lower-level graph traversal used by the library API could keep only one of several relationships between the same pair of symbols (for example a symbol that both calls and references another), count a caller reached through two different call sites twice, or return slightly more results than the requested size limit on a very highly-connected symbol. These were long-standing and mostly masked by later de-duplication, so day-to-day query results were largely unaffected, but the traversal now returns the complete, correctly-bounded set. Thanks @inth3shadows for the precise, individually-traced reports. (#1086, #1087, #1088, #1089, #1090)
  • Method calls to same-named classes in different files now resolve to the right definition. If two files each declared, say, a Logger class with its own log() method, a call could be linked to whichever definition happened to be indexed first — so a call in one file wrongly pointed at the class in another, mixing up that method's callers and blast radius. This affected calls written as obj.log(), Logger.log(), and Logger::log() across many languages, including C++, Python, TypeScript, Java, C#, and Rust. When a method name is ambiguous, CodeGraph now prefers the definition in the calling file itself — the correct target in the common case — while Java/Kotlin calls that an import already pins to another file are unaffected. Thanks @inth3shadows for the minimal repro and root-cause analysis. (#1079)
