Rancher v2.15.1

v2.15.1 veröffentlichen

[!IMPORTANT] – Wenn Sie den Active Directory Federation Service (AD FS) verwenden, kann ein Upgrade auf Rancher v2.10.1 oder höher zu Problemen bei der Authentifizierung führen, die einen manuellen Eingriff erfordern. Diese Probleme sind darauf zurückzuführen, dass die AD FS-Relying Party Trust nicht in der Lage ist, ein Signaturüberprüfungszertifikat aus den Metadaten abzurufen. Weitere Informationen finden Sie unter #48655. Diese Probleme können mit einer von zwei Methoden behoben werden:

  • Aktualisierung der Informationen der vertrauenden Seite Trust aus den Verbundmetadaten (Relying Party Trust → Aktualisierung aus den Metadaten der Föderation…​).

  • Direktes Hinzufügen des Zertifikats (Relying Party Trust → Eigenschaften → Registerkarte „Signatur“ → Hinzufügen → Zertifikat auswählen).

Rancher v2.15.1 ist die neueste Patch-Version von Rancher. Dies ist eine Community-Version, die Wartungsupdates und Fehlerbehebungen einführt.

Weitere Informationen zu neuen Funktionen in der allgemeinen Nebenversion finden Sie in den v2.15.0 release notes.

Sicherheitskorrekturen für Schwachstellen

Diese Version behebt die folgenden Sicherheitsprobleme:

Rancher

– Es wurde eine Sicherheitslücke im SAML-Authentifizierungs-Handler von Rancher behoben, bei der der Assertion-Replay-Schutz in Hochverfügbarkeitsbereitstellungen (Multi-Replica) unwirksam war. Da jedes Replikat verbrauchte Assertion-IDs in einem separaten In-Memory-Cache verfolgt, könnte eine erfasste SAML-Assertion gegen andere Replikate abgespielt werden, um zusätzliche authentifizierte Sitzungen als Opfer zu erstellen. Der Fix verfolgt verbrauchte Assertion-IDs über alle Replikate hinweg. Alle SAML-Anbieter waren betroffen. Weitere Informationen finden Sie unter CVE-2026-75034. – Behebt eine Sicherheitslücke im projektbezogenen Rancher-Projekt secretsController, bei dem Projektgeheimnisse nur auf der Grundlage der field.cattle.io/projectId-Annotation an Namespaces weitergegeben werden, ohne zu überprüfen, ob das referenzierte Projekt zum selben Cluster gehört. Ein authentifizierter Benutzer mit Berechtigungen zur Namespace-Erstellung auf einem Downstream-Cluster könnte diese Anmerkung fälschen, um Projektgeheimnisse aus einem nicht autorisierten Projekt in einem anderen Cluster preiszugeben. Der Controller überprüft nun, ob die Annotation auf ein Projekt innerhalb desselben Clusters verweist, bevor Geheimnisse weitergegeben werden. Weitere Informationen finden Sie unter CVE-2026-75033. – Es wurde eine Sicherheitslücke im Rancher Imperative Ext Token API (ext.cattle.io/v1-Tokens) behoben, bei der jeder authentifizierte Benutzer die Tokens anderer Benutzer auflisten und beobachten kann, indem er einen gestalteten Label-Selektor bereitstellt und Token-Metadaten und den gespeicherten Inhaber-Token-Hash offenlegt. Der Store erzwingt nun bedingungsloses Scoping pro Benutzer, sodass Aufrufer nur ihre eigenen Token sehen und Leseantworten nicht mehr den gespeicherten Token-Hash zurückgeben. Weitere Informationen finden Sie unter CVE-2026-75035. – Es wurde eine Sicherheitslücke im GlobalRole-Controller von Rancher behoben, bei der ein Benutzer mit delegierten create- oder update-Berechtigungen für GlobalRole-Ressourcen die authz.management.cattle.io/cr-name-Annotation so festlegen konnte, dass sie auf ein beliebiges vorhandenes ClusterRole (z. B. das integrierte cluster-admin) abzielt. Der Controller überschreibt dann die Regeln ohne Besitzprüfung, entzieht allen gebundenen Prinzipalen die Berechtigungen und führt zu einer dauerhaften, Cluster-weiten RBAC-Sperre auf dem lokalen Verwaltungscluster. Weitere Informationen finden Sie unter CVE-2026-71404. – Es wurde eine Sicherheitslücke im SUSE Rancher Norman /v3/users API behoben, bei der der Aktualisierungspfad keine Unveränderlichkeit der Felder username, principalIds und displayName auf einer User-Ressource erzwang. Ein Anrufer mit update-Berechtigungen für users könnte die externe Prinzipalidentität eines Benutzers neu binden und so die Kontoübernahme bei der nächsten externen Anmeldung ermöglichen oder eine Denial-of-Service-Bedingung erzeugen, die dazu führt, dass auf vorhandene Rollenbindungen nicht mehr zugegriffen werden kann. Die Store- und Admission-Webhook-Ebenen API wurden aktualisiert, um nach der Erstellung vorgenommene Änderungen an diesen Identitätsfeldern abzulehnen. Weitere Informationen finden Sie unter CVE-2026-71403.

Flotte

– Es wurde eine Sicherheitslücke in der Helm-Vorlagenvorverarbeitung von Fleet behoben, durch die vom Fleet-Controller ausgewertete Vorlagen Netzwerkressourcen erreichen konnten. Ein Benutzer, der untrusted-Bundle-Inhalte bereitstellen kann, kann Cluster-Metadaten und Informationen zu Hosts offenlegen, die vom Controller aus erreichbar sind. Die Flotte lehnt jetzt Bundles ab, deren Helm-Vorlagenwerte Netzwerkzugriff erfordern, und meldet einen Fehler für den entsprechenden GitRepo. Weitere Informationen finden Sie unter CVE-2026-75036. – Es wurde eine Sicherheitslücke in Fleet behoben, bei der von einem Agenten während der vom Agenten initiierten Clusterregistrierung bereitgestellte Cluster-Labels auf das resultierende Cluster-Objekt angewendet wurden, einschließlich reservierter management.cattle.io/-Labels, die für das Bundle-Targeting verwendet werden. In Bereitstellungen, in denen mehrere trust-Domänen einen Fleet-Workspace-Namespace gemeinsam nutzen, ermöglichte dies einem registrierenden Cluster, die Bundle- oder GitRepo-Ziele eines anderen Mandanten abzugleichen und die Manifeste und aufgelösten Werte dieses Mandanten zu empfangen. Die Flotte verwirft jetzt reservierte Etiketten, die bei der vom Agenten initiierten Registrierung bereitgestellt werden. Eigenständige Rancher-Bereitstellungen sind in ihrer Standardkonfiguration nicht betroffen, da Rancher eine vom Manager initiierte Registrierung verwendet. Weitere Informationen finden Sie unter CVE-2026-93538. – Es wurde eine Sicherheitslücke in Fleet behoben, bei der von einem Bundle über namespaceLabels und namespaceAnnotations angeforderte Namespace-Bezeichnungen und Anmerkungen ohne die Autorisierung des Dienstkontos angewendet wurden, an das das Bundle angeheftet war. In mandantenfähigen Bereitstellungen ermöglichte dies einem Bundle, Namespace-Metadaten zu ändern, die seine eigene Identität nicht ändern durfte. Das Namespace-Update wird jetzt als Dienstkonto der Bereitstellung ausgeführt und vom Downstream-RBAC Kubernetes gesteuert. Weitere Informationen finden Sie unter CVE-2026-93540.

K3s- und RKE2-Bereitstellung

Bekannte Probleme

– Es besteht ein bekanntes Problem im Zusammenhang mit CAPI-Infrastrukturanbietern innerhalb des V2-Bereitstellungsframeworks von Rancher. Beim Erstellen oder Bearbeiten von v2prov-Clustern mit nativen Infrastrukturanbietern (z. B. Änderungen seit v2.15.0

Sehen Sie sich die vollständige Liste der Änderungen an.

Installations-/Upgrade-Hinweise

Wenn Sie Rancher zum ersten Mal installieren, muss Ihre Umgebung die Installationsanforderungen erfüllen.

[!IMPORTANT] – Rancher erfordert jetzt, dass auf dem Cluster, auf dem es ausgeführt wird, die Kubernetes API Aggregation Layer aktiviert ist. Dies liegt daran, dass Rancher Kubernetes um zusätzliche APIs erweitert, indem es seinen eigenen Erweiterungsserver API registriert. Bitte beachten Sie, dass bei allen Versionen von Kubernetes, die in diesen Rancher-Versionen der K8s-Distributionen (RKE2/K3s) unterstützt werden, die Aggregationsschicht standardmäßig konfiguriert und aktiviert ist.

– Weitere Informationen finden Sie in der Dokumentation zum Erweiterungs-API-Server und #50400.

  • Der Rancher Kubernetes-Motor (RKE/RKE1) hat am 31. Juli 2025 das Ende seiner Lebensdauer erreicht. Die Rancher-Versionen 2.12.0 und höher unterstützen die Bereitstellung oder Verwaltung nachgelagerter RKE1-Cluster nicht mehr. Wir empfehlen, RKE1-Cluster auf RKE2 umzustellen, um weiterhin Support und Sicherheitsupdates zu gewährleisten. Erfahren Sie mehr über den Übergang hier.

– Rancher verfügt jetzt über eine Validierungsprüfung vor dem Upgrade für RKE1-Ressourcen, die fehlschlägt und die RKE1-Ressourcen auflistet, falls vorhanden. Weitere Informationen finden Sie unter #50286.

– Es ist wichtig, dass Sie den verfügbaren Speicherplatz auf Ihren Knoten überprüfen und entsprechend planen, bevor Sie auf Rancher v2.12.0 und höher aktualisieren, um mögliche Probleme mit der Festplattenbelastung und der Pod-Räumung zu vermeiden.

– Weitere Informationen finden Sie in der [Dokumentation „UI Server Side Pagination – Disk Space“] (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/advanced-user-guides/ui-server-side-pagination#disk-space).

– Rancher verfügt jetzt über eine Aktivierungsoption namens AUDIT_LOG_ENABLED für API-Überwachungsprotokolle für eine Rancher-Installation.

– In den Rancher-Versionen 2.11.x und früher konnte nur AUDIT_LEVEL festgelegt werden und die Standardprotokollebene (0) würde das Überwachungsprotokoll deaktivieren. In den Rancher-Versionen 2.12.x und höher enthält die Standardprotokollebene (0) jetzt nur die Metadaten der Protokollanforderung und -antwort und kann bei der Konfiguration von AUDIT_LOG_ENABLED festgelegt werden. Wenn Sie über Helm installieren oder aktualisieren, können Sie die API-Überwachungsprotokolle aktivieren und die Protokollebene angeben, indem Sie die folgende Einstellung auf Ihren Helm-Befehl anwenden: --set auditLog.enabled=true --set auditLog.level=0. Weitere Informationen finden Sie in der Dokumentation [Aktivieren des API-Überwachungsprotokolls zur Aufzeichnung von Systemereignissen] (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/advanced-user-guides/enable-api-audit-log) und #48941.

Änderungen bei Bildartefakten

Bildartefakt-Digests werden in Rancher v2.12.0, v2.11.4 und v2.10.8 umbenannt. Bis zu dieser Änderung wurden aus Kompatibilitätsgründen separate Image-Digest-Dateien für jedes Betriebssystem und jede Architektur verwaltet. Mit dieser Änderung soll für jedes Betriebssystem nur noch eine Datei bereitgestellt werden:

  • Die Dateien rancher-images-digests-linux-amd64.txt und rancher-images-digests-linux-arm64.txt sollen in rancher-images-digests-linux.txt umbenannt werden.

  • Die Dateien rancher-images-digests-windows-ltsc2019.txt und rancher-images-digests-windows-ltsc2022.txt sollen in rancher-images-digests-windows.txt umbenannt werden.

Upgrade-Anforderungen

  • Backups erstellen: Erstellen Sie ein Backup, bevor Sie Rancher aktualisieren. Um Rancher nach einem Upgrade zurückzusetzen, müssen Sie Rancher zunächst sichern und auf die vorherige Rancher-Version wiederherstellen. Da Rancher in demselben Zustand wiederhergestellt wird, in dem es sich bei der Erstellung des Backups befand, sind alle nach dem Upgrade vorgenommenen Änderungen nach der Wiederherstellung nicht enthalten.

  • Anforderungen an die Helmversion:

    • Um Rancher 2.12.x und höher zu verwalten, müssen Sie Ihren Helm client auf die Version 3.18 oder höher aktualisieren.

    – Diese Änderung ist erforderlich, um die Hinzufügung der Kubernetes 1.33-Unterstützung in dieser Version widerzuspiegeln.

    – Derzeit schreibt die offizielle [Helm Version Support Policy] (https://helm.sh/docs/topics/version_skew/) vor, dass nur Helm 3.18 den richtigen Kubernetes-Versionsbereich für Rancher 2.12 unterstützt.

  • CNI-Anforderungen: – Deaktivieren Sie für Kubernetes v1.19 und höher firewalld, da es mit verschiedenen CNI-Plugins nicht kompatibel ist. Siehe #28840.

    – Wenn Sie eine Linux-Distribution aktualisieren oder installieren, die nf_tables als Backend-Paketfilter verwendet, wie z. B. SLES 15, RHEL 8, Ubuntu 20.10, Debian 10 oder höher, aktualisieren Sie auf RKE v1.19.2 oder höher, um Flannel v0.13.0 zu erhalten. Flannel v0.13.0 unterstützt nf_tables. Siehe Flanell #1317.

  • Anforderungen für Umgebungen mit Luftspalt:

    – Wenn Sie einen Proxy vor einer Rancher-Instanz mit Luftspalt verwenden, müssen Sie zusätzliche Parameter an NO_PROXY übergeben. Siehe die Dokumentation und Problem #2725.

    – Wenn Sie Rancher mit Docker in einer Air-Gap-Umgebung installieren, müssen Sie eine benutzerdefinierte registries.yaml-Datei für den docker run-Befehl bereitstellen, wie in der K3s-Dokumentation gezeigt. Wenn die Registry über Zertifikate verfügt, müssen Sie diese ebenfalls bereitstellen. Siehe #28969.

Rancher-Helm-Diagrammversionen

In Rancher v2.6.0 und höher werden in der Apps & Marketplace-Benutzeroberfläche viele Rancher-Helm-Diagramme mit einer Hauptversion benannt, die mit 100 beginnt. Dadurch wird vermieden, dass gleichzeitige Upstream-Änderungen und Rancher-Änderungen widersprüchliche Versionsinkremente verursachen. Dies entspricht auch der semantischen Versionierung (SemVer), die eine Voraussetzung für Helm ist. Sie können die Upstream-Versionsnummer eines Diagramms in den Build-Metadaten sehen, zum Beispiel: 100.0.0+up2.1.0. Siehe #32294.

Frühere Verhaltensänderungen der Rancher

Frühere Verhaltensänderungen von Ranchern – Rancher General

  • Rancher v2.15.0:

    – Rancher v2.15 entfernt die Unterstützung für Kubernetes v1.33. Siehe #55306.

Frühere Verhaltensänderungen von Ranchern – Rancher-App (Globale Benutzeroberfläche)

  • Rancher v2.15.0:

    – Die Option zum Deaktivieren des Feature-Flags ui-sql-cache / Vai / Server-Side Pagination (SSP) in der Rancher-Benutzeroberfläche wurde in Vorbereitung auf Rancher v2.16 entfernt, wo die Funktion immer aktiviert sein wird. Siehe #16822.

    • Entfernung: Die Unterstützung für Ember-basierte UI-Plugins für Cluster- und Knotentreiber (veraltet seit Rancher v2.11.0) wurde in Rancher v2.15.0 entfernt. Migrieren Sie Ihre Plugins zum UI Extensions Framework. Einzelheiten finden Sie unter #14005.

Frühere Verhaltensänderungen von Ranchern – Bereitstellung von K3s und RKE2

  • Rancher v2.15.0:

    – Standardmäßig ermöglichen die [globalen Berechtigungen] Standard User und Create Clusters (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/new-user-guides/authentication-permissions-and-global-configuration/manage-role-based-access-control-rbac/global-permissions) jetzt das Erstellen und anschließende Aktualisieren von CAPI-Infrastrukturobjekten im fleet-default-Namespace. Beachten Sie, dass manuell erstellte Infrastrukturanbieter-Identitätsobjekte wie AWSClusterStaticIdentity oder VSphereClusterIdentity, die auf den fleet-default-Namespace abzielen, über CAPI-Infrastrukturobjekte wie AWSCluster oder VsphereCluster verwendet werden können. Siehe #53777.

    – Bei Verwendung nativer CAPI-Infrastrukturanbieter mit v2prov generiert Rancher jetzt die Bootstrap-Cloud-Konfiguration im [Jinja-Format] (https://docs.cloud-init.io/en/latest/explanation/format/jinja.html). Benutzerdaten für reguläre Knotentreiber mit v2prov sind davon nicht betroffen. Siehe #53777.

Frühere Verhaltensänderungen der Rancher – Kontinuierliche Lieferung (Flotte)

  • Rancher v2.15.0:

  • Veraltung: Fleet wird die Unterstützung für GitRepoRestriction in einer zukünftigen Version entfernen, sodass die Verwendung der Richtlinienressource zum Konfigurieren von Umgebungen mit mehreren Mandanten die einzige Option ist. Siehe #55652.

    – Veraltung: Die Flottenunterstützung für nicht authentifizierte Webhook-Aufrufe wird in einer zukünftigen Version entfernt, sodass die Einrichtung eines Webhook-Geheimnisses die einzige Option ist. Siehe #55633.

Seit langem bekannte Probleme

Seit langem bekannte Probleme – Rancher General

  • Rancher v2.15.0:

– Es besteht ein bekanntes Problem mit den Rancher-Clustern v2.15.0 und Kubernetes v1.36, bei denen Rancher-Backups aufgrund eines Problems mit dem Backup-Diagramm nicht unter den Cluster-Tools aufgeführt sind. Siehe #1055.

Seit langem bekannte Probleme – Cluster-Bereitstellung

– Nicht alle Cluster-Tools können auf einem gehärteten Cluster installiert werden.

  • Rancher v2.8.1:

    – Wenn Sie nach einer fehlgeschlagenen etcd-Snapshot-Wiederherstellung versuchen, einen neuen etcd-/Controlplane-Knoten in einem von CAPR verwalteten Cluster zu registrieren, kann der Knoten in einem dauerhaft angehaltenen Zustand stecken bleiben und die Fehlermeldung [ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again anzeigen. Um dieses Problem zu umgehen, können Sie die Pause des Clusters aufheben, indem Sie kubectl edit clusters.cluster clustername -n fleet-default ausführen und spec.unpaused auf false setzen. Siehe #43735.

Seit langem bekannte Probleme – RKE2-Bereitstellung

  • Rancher v2.7.7:

    – Aufgrund der Backoff-Logik in verschiedenen Komponenten kann es länger dauern, bis nachgelagert bereitgestellte K3s und RKE2-Cluster nach einer Migration wieder den Status Aktiv erreichen. Wenn Sie feststellen, dass ein Downstream-Cluster unmittelbar nach einer Migration immer noch aktualisiert wird oder sich in einem Fehlerzustand befindet, lassen Sie ihn bitte versuchen, sich selbst aufzulösen. Dies kann bis zu einer Stunde dauern. Siehe #34518 und #42834.

  • Rancher v2.7.6:

    – Die Bereitstellung von RKE2/K3s-Clustern mit hinzugefügten (nicht integrierten) benutzerdefinierten Knotentreibern führt dazu, dass die Bereitstellung fehlschlägt. Um dieses Problem zu umgehen, reparieren Sie die hinzugefügten Knotentreiber nach der Aktivierung. Siehe #37074.

Seit langem bekannte Probleme – K3s-Bereitstellung

  • Rancher v2.7.6:

    – Die Bereitstellung von RKE2/K3s-Clustern mit hinzugefügten (nicht integrierten) benutzerdefinierten Knotentreibern führt dazu, dass die Bereitstellung fehlschlägt. Um dieses Problem zu umgehen, reparieren die hinzugefügten Knotentreiber nach der Aktivierung. Siehe #37074.

  • Rancher v2.7.2:

    – Cluster bleiben im Status Updating, auch wenn sie Knoten im Status Error enthalten. Siehe #39164.

Seit langem bekannte Probleme – Rancher App (Globale Benutzeroberfläche)

  • Rancher v2.10.0:

    – Nach dem Löschen eines Namespace oder Projekts in der Rancher-Benutzeroberfläche bleibt der Namespace oder das Projekt sichtbar. Um dieses Problem zu umgehen, aktualisieren Sie die Seite. Siehe #12220.

  • Rancher v2.9.2:

    – Obwohl Knotenpools im Systemmodus mindestens einen Knoten haben müssen, lässt die Rancher-Benutzeroberfläche eine Mindestknotenanzahl von Null zu. Die Eingabe einer Mindestknotenanzahl von Null über die Benutzeroberfläche kann dazu führen, dass die Clustererstellung aufgrund eines Fehlers aufgrund eines ungültigen Parameters fehlschlägt. Um zu verhindern, dass dieser Fehler auftritt, geben Sie eine Mindestknotenanzahl ein, die mindestens der Knotenanzahl entspricht. Siehe #11922.

  • Rancher v2.7.7:

    – Beim Erstellen eines Clusters in der Rancher-Benutzeroberfläche ist die Verwendung eines Unterstrichs _ im Feld Cluster Name nicht zulässig. Siehe #9416.

  • Rancher v2.6.4:

    – Der Abschnitt „Deployment securityContext“ fehlt, wenn eine neue Arbeitslast erstellt wird. Dadurch wird verhindert, dass Pods gestartet werden, wenn die Unterstützung für Pod-Sicherheitsrichtlinien aktiviert ist. Siehe #4815.

Seit langem bekannte Probleme – EKS

  • Rancher v2.7.0:

    – EKS-Cluster auf Kubernetes v1.21 oder niedriger auf Rancher v2.7 können nicht aktualisiert werden. Siehe #39392.

Seit langem bekannte Probleme – Authentifizierung

  • Rancher v2.9.0:

    – Es gibt einige bekannte Probleme mit der Unterstützung des OpenID Connect-Anbieters:

    – Wenn der generische OIDC-Authentifizierungsanbieter aktiviert ist und Sie versuchen, Authentifizierungsanbieter-Benutzer zu einem Cluster oder Projekt hinzuzufügen, werden Benutzer nicht in der Dropdown-Suchleiste angezeigt. Dies ist ein erwartetes Verhalten, da der OIDC-Authentifizierungsanbieter allein nicht durchsuchbar ist. Siehe #46104.

    – Wenn der generische OIDC-Authentifizierungsanbieter aktiviert ist, können Authentifizierungsanbieter-Benutzer, die mit ihrem Benutzernamen zu einem Cluster/Projekt hinzugefügt werden, bei der Anmeldung nicht auf Ressourcen zugreifen. Ein Benutzer hat bei der Anmeldung nur dann Zugriff auf Ressourcen, wenn der Benutzer mit seiner Benutzer-ID hinzugefügt wird. Siehe #46105.

    – Wenn der generische OIDC-Authentifizierungsanbieter aktiviert ist und ein Authentifizierungsanbieter-Benutzer in einer verschachtelten Gruppe bei Rancher angemeldet ist, wird dem Benutzer beim Versuch, ein Projekt zu erstellen, die folgende Fehlermeldung angezeigt: projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg". Das Projekt wird jedoch noch erstellt. Siehe #46106.

Seit langem bekannte Probleme – Rancher Webhook

  • Rancher v2.7.2:

    • In allen Downstream-Clustern ist ein Webhook installiert. Bei dieser Funktionalität können bei Benutzern mehrere Probleme auftreten:

      – Wenn Sie ein Rollback von einer Rancher-Version v2.7.2 oder höher auf eine Rancher-Version vor v2.7.2 durchführen, bleiben die Webhooks in Downstream-Clustern. Da der Webhook so konzipiert ist, dass er 1:1 mit bestimmten Rancher-Versionen kompatibel ist, kann dies zu unerwartetem Verhalten im Downstream führen. Das Rancher-Team hat ein Skript entwickelt, das nach Abschluss des Rollbacks verwendet werden sollte (d. h. nachdem eine Rancher-Version vor v2.7.2 ausgeführt wird). Dadurch wird der Webhook aus den betroffenen Downstream-Clustern entfernt. Siehe #40816.

Seit langem bekannte Probleme – Virtualisierungsmanagement (Harvester)

  • Rancher v2.13.1:

    – Beim Upgrade auf Rancher v2.13.1 oder höher während der Verwendung von Harvester v1.6.1 können Benutzer auf ein Problem mit ihren Load Balancern in Downstream-Clustern stoßen, die den Harvester Cloud Provider verwenden, und müssen die folgende [Problemumgehung] (https://docs.harvesterhci.io/latest/troubleshooting/rancher#guest-cluster-loadbalancer-ip-is-not-reachable) durchführen, um Calico anzuweisen, keine der von kube-vip verwalteten IPs/Schnittstellen zu verwenden. Siehe #9767.

  • Rancher v2.7.2:

    – Wenn Sie Rancher v2.7.2 mit Harvester v1.1.1-Clustern verwenden, können Sie den Harvester-Cloud-Anbieter beim Bereitstellen oder Aktualisieren von Gastclustern nicht auswählen. Die Harvester release notes enthalten Anweisungen zur Behebung dieses Problems. Siehe #3750.

Seit langem bekannte Probleme – Sicherung/Wiederherstellung

– Bei der Migration zu einem Cluster mit der Rancher Backup-Funktion kann die Server-URL nicht in einen anderen Speicherort geändert werden. Es muss weiterhin dieselbe URL verwendet werden.

  • Rancher v2.13.0:

Release v2.15.1

[!IMPORTANT]

  • If you are using Active Directory Federation Service (AD FS), upgrading to Rancher v2.10.1 or later may cause issues with authentication, requiring manual intervention. These issues are due to the AD FS Relying Party Trust not being able to pick up a signature verification certificate from the metadata. For more information, see #48655. These issues can be corrected by either of two methods:

    • Updating the Relying Party Trust information from federation metadata (Relying Party Trust → Update from Federation Metadata…​).

    • Directly adding the certificate (Relying Party Trust → Properties → Signature tab → Add → Select the certificate).

Rancher v2.15.1 is the latest patch release of Rancher. This is a Community version release that introduces maintenance updates and bug fixes.

For more information on new features in the general minor release, see the v2.15.0 release notes.

Security Fixes for Vulnerabilities

This release addresses the following security issues:

Rancher

  • Fixed a security vulnerability in Rancher's SAML authentication handler where the assertion replay protection was ineffective in high-availability (multi-replica) deployments. Because each replica tracked consumed assertion IDs in a separate in-memory cache, a captured SAML assertion could be replayed against other replicas to create additional authenticated sessions as the victim. The fix tracks consumed assertion IDs across all replicas. All SAML providers were affected. For more information, refer to CVE-2026-75034.
  • Fixes a security vulnerability in the Rancher project-scoped secretsController where Project Secrets propagate to namespaces based only on the field.cattle.io/projectId annotation without validating that the referenced project belongs to the same cluster. An authenticated user with namespace creation permissions on one downstream cluster could spoof this annotation to leak Project Secrets from an unauthorized project in a different cluster. The controller now validates that the annotation references a project within the same cluster before propagating secrets. For more information, see CVE-2026-75033.
  • Fixed a security vulnerability in the Rancher imperative ext Token API (ext.cattle.io/v1 tokens) where any authenticated user can list and watch other users' tokens by supplying a crafted label selector, disclosing token metadata and the stored bearer token hash. The store now enforces per-user scoping unconditionally so callers see only their own tokens, and read responses no longer return the stored token hash. For more information, see CVE-2026-75035.
  • Fixed a security vulnerability in Rancher's GlobalRole controller where a user with delegated create or update permissions for GlobalRole resources could set the authz.management.cattle.io/cr-name annotation to target an arbitrary existing ClusterRole (such as the built-in cluster-admin). The controller then overwrites the rules without an ownership check, stripping permissions from all bound principals and causing a persistent, cluster-wide RBAC lockout on the local management cluster. For more information, refer to CVE-2026-71404.
  • Fixed a security vulnerability in the SUSE Rancher Norman /v3/users API where the update path did not enforce immutability of the username, principalIds, and displayName fields on a User resource. A caller holding update permissions on users could rebind a user's external principal identity, enabling account takeover during the next external login or creating a denial-of-service condition that left existing role bindings inaccessible. The API store and admission-webhook layers were updated to reject post-creation changes to these identity fields. For more information, see CVE-2026-71403.

Fleet

  • Fixed a security vulnerability in Fleet's Helm template preprocessing where templates evaluated by the Fleet controller could reach network resources. A user who can supply untrusted bundle content can expose cluster metadata and information about hosts reachable from the controller. Fleet now rejects bundles whose Helm template values require network access, reporting an error for the corresponding GitRepo. For more information, refer to CVE-2026-75036.
  • Fixed a security vulnerability in Fleet where cluster labels supplied by an agent during agent-initiated cluster registration were applied to the resulting Cluster object, including reserved management.cattle.io/ labels used for bundle targeting. In deployments where multiple trust domains share a Fleet workspace namespace, this allowed a registering cluster to match another tenant's Bundle or GitRepo targets and receive that tenant's manifests and resolved values Secrets. Fleet now discards reserved labels supplied at agent-initiated registration. Standalone Rancher deployments are not affected in their default configuration, as Rancher uses manager-initiated registration. For more information, refer to CVE-2026-93538.
  • Fixed a security vulnerability in Fleet where namespace labels and annotations requested by a bundle through namespaceLabels and namespaceAnnotations were applied without the authorization of the service account the bundle was pinned to. In multi-tenant deployments this allowed a bundle to modify namespace metadata that its own identity was not permitted to change. The namespace update now runs as the deployment's service account and is governed by downstream Kubernetes RBAC. For more information, refer to CVE-2026-93540.

Install/Upgrade Notes

If you’re installing Rancher for the first time, your environment must fulfill the installation requirements.

[!IMPORTANT]

  • Rancher now requires the cluster it runs on to have the Kubernetes API Aggregation Layer enabled. This is because Rancher extends Kubernetes with additional APIs by registering its own extension API server. Please note that all versions of Kubernetes supported in this Rancher versions K8s distributions (RKE2/K3s) will have the aggregation layer configured and enabled by default.

    • Refer to the Extension API Server documentation and #50400 for more information.

  • Rancher Kubernetes Engine (RKE/RKE1) has reached end of life as of July 31, 2025. Rancher versions 2.12.0 and later no longer support provisioning or managing downstream RKE1 clusters. We recommend replatforming RKE1 clusters to RKE2 to ensure continued support and security updates. Learn more about the transition here.

    • Rancher now has a pre-upgrade validation check for RKE1 resources which fails and lists the RKE1 resources if present. Refer to #50286 for more information.

  • It is crucial that you review the available disk space on your nodes and plan accordingly before upgrading to Rancher v2.12.0 and later to avoid potential disk pressure and pod eviction issues.

    • For additional information, refer to the UI Server Side Pagination - Disk Space documentation.

  • Rancher now has an enablement option called AUDIT_LOG_ENABLED for API Audit Logs for a Rancher installation.

    • In Rancher versions 2.11.x and earlier, only the AUDIT_LEVEL could be set and the default log level (0) would disable the audit log. In Rancher versions 2.12.x and later, the default log level (0) now only contains the log request and response metadata, and can be set when configuring AUDIT_LOG_ENABLED. If installing or upgrading via Helm you can enable the API Audit Logs and specify the log level by applying the following setting to your Helm command: --set auditLog.enabled=true --set auditLog.level=0. See the Enabling the API Audit Log to Record System Events documentation and #48941.

Changes in Image Artifacts

Image artifact digests are renamed in Rancher v2.12.0, v2.11.4 and v2.10.8. Up until this change, separate image digests files for each operating system and architecture have been maintained for compatibility reasons. With this change, only one file for each operating system is to be provided:

  • The rancher-images-digests-linux-amd64.txt and rancher-images-digests-linux-arm64.txt files are to be renamed to rancher-images-digests-linux.txt.

  • The rancher-images-digests-windows-ltsc2019.txt and rancher-images-digests-windows-ltsc2022.txt files are to be renamed to rancher-images-digests-windows.txt.

Upgrade Requirements

  • Creating backups: Create a backup before you upgrade Rancher. To roll back Rancher after an upgrade, you must first back up and restore Rancher to the previous Rancher version. Because Rancher will be restored to the same state as when the backup was created, any changes post-upgrade will not be included after the restore.

  • Helm version requirements:

    • To manage Rancher 2.12.x and later, you must upgrade your Helm client to version 3.18 or newer.

    • This change is required to reflect the addition of Kubernetes 1.33 support with this release.

    • Currently, the official Helm Version Support Policy dictates that only Helm 3.18 supports the proper Kubernetes version range for Rancher 2.12.

  • CNI requirements:

    • For Kubernetes v1.19 and later, disable firewalld as it’s incompatible with various CNI plugins. See #28840.

    • When upgrading or installing a Linux distribution that uses nf_tables as the backend packet filter, such as SLES 15, RHEL 8, Ubuntu 20.10, Debian 10, or later, upgrade to RKE v1.19.2 or later to get Flannel v0.13.0. Flannel v0.13.0 supports nf_tables. See Flannel #1317.

  • Requirements for air-gapped environments:

    • When using a proxy in front of an air-gapped Rancher instance, you must pass additional parameters to NO_PROXY. See the documentation and issue #2725.

    • When installing Rancher with Docker in an air-gapped environment, you must supply a custom registries.yaml file to the docker run command, as shown in the K3s documentation. If the registry has certificates, then you’ll also need to supply those. See #28969.

      • When the generic OIDC auth provider is enabled, auth provider users that are added to a cluster/project by their username are not able to access resources upon logging in. A user will only have access to resources upon login if the user is added by their userID. See #46105.

Long-standing Known Issues - Rancher Webhook

  • Rancher v2.7.2:

    • A webhook is installed in all downstream clusters. There are several issues that users may encounter with this functionality:

      • If you rollback from a version of Rancher v2.7.2 or later, to a Rancher version earlier than v2.7.2, the webhooks will remain in downstream clusters. Since the webhook is designed to be 1:1 compatible with specific versions of Rancher, this can cause unexpected behaviors to occur downstream. The Rancher team has developed a script which should be used after rollback is complete (meaning after a Rancher version earlier than v2.7.2 is running).
