Rancher v2.15.2

v2.15.2 veröffentlichen

[!IMPORTANT] – Wenn Sie den Active Directory Federation Service (AD FS) verwenden, kann ein Upgrade auf Rancher v2.10.1 oder höher zu Problemen bei der Authentifizierung führen, die einen manuellen Eingriff erfordern. Diese Probleme sind darauf zurückzuführen, dass die AD FS-Relying Party Trust nicht in der Lage ist, ein Signaturüberprüfungszertifikat aus den Metadaten abzurufen. Weitere Informationen finden Sie unter #48655. Diese Probleme können mit einer von zwei Methoden behoben werden:

  • Aktualisierung der Informationen der vertrauenden Partei Trust aus den Verbundmetadaten (Relying Party Trust → Aktualisierung aus den Metadaten der Föderation…​).

  • Direktes Hinzufügen des Zertifikats (Relying Party Trust → Eigenschaften → Registerkarte „Signatur“ → Hinzufügen → Zertifikat auswählen).

Rancher v2.15.2 ist die neueste Patch-Version von Rancher. Dies ist eine Community-Version, die Wartungsupdates und Fehlerbehebungen einführt.

Weitere Informationen zu neuen Funktionen in der allgemeinen Nebenversion finden Sie in den v2.15.0 release notes.

Sicherheitskorrekturen für Schwachstellen

Diese Version behebt die folgenden Sicherheitsprobleme:

Rancher

– Es wurde eine Sicherheitslücke in Rancher behoben, bei der beim Abmelden die Browser-Sitzungscookies gelöscht wurden, das entsprechende öffentliche API-Sitzungstoken auf dem Server jedoch nicht gelöscht wurde. Ein zuvor erfasstes Sitzungstoken blieb daher bis zu seinem natürlichen Ablauf gültig und überwand die Abmeldung als Widerrufskontrolle. Betroffen waren nur Bereitstellungen, die öffentliche API-Sitzungstokens verwenden, beispielsweise bei der OIDC-basierten Authentifizierung. Weitere Informationen finden Sie unter CVE-2026-88805. – Es wurde eine Sicherheitslücke in Rancher behoben, bei der ein kleiner Satz öffentlicher UI-Einstellungen, die von nicht authentifizierten, schreibgeschützten API-Routen bereitgestellt werden, von einem nicht authentifizierten Remote-Benutzer geändert werden konnte. Da eine dieser Einstellungen als Roh-HTML auf der Anmeldeseite gerendert wird, könnten von Angreifern kontrollierte Inhalte im Browser von Benutzern, die auf die Anmeldeseite zugreifen, gespeichert und ausgeführt werden, wodurch möglicherweise das Bootstrap-Passwort des lokalen Administrators oder eine aktive Administratorsitzung offengelegt wird. Die nicht authentifizierten Einstellungsrouten sind jetzt ausschließlich schreibgeschützt. Weitere Informationen finden Sie unter CVE-2026-88804.

Flotte

– Es wurde eine Sicherheitslücke in Fleet behoben, bei der Helm-valuesFiles-Einträge in fleet.yaml nicht auf das Bundle-Verzeichnis beschränkt waren. Ein Benutzer, der untrusted-Bundle-Inhalte bereitstellen kann, könnte dazu führen, dass Fleet Dateien außerhalb des Repository-Checkouts liest und deren Inhalte über das generierte Bundle offenlegt, einschließlich Anmeldeinformationsmaterial, zu dessen Lesen der Benutzer keine Berechtigung hatte. Fleet lehnt jetzt Wertedateipfade ab, die das Bundle-Verzeichnis verlassen. Weitere Informationen finden Sie unter CVE-2026-93537. – Es wurde ein Problem behoben, bei dem der Flottenagent die im downstreamResources eines Bundles aufgeführten Secrets und ConfigMaps kopierte und den Ziel-Namespace der Bereitstellung erstellte, indem er die eigenen Anmeldeinformationen des Agenten anstelle des an die Bereitstellung angehefteten ServiceAccounts verwendete. Diese Schreibvorgänge werden jetzt durch den Downstream-RBAC des Mandanten gesteuert. Bereitstellungen, die kein ServiceAccount anheften, gelten unverändert als Agent-Vorgang. Rancher v2.15.x ist in einer Standardinstallation betroffen, da dort die Ressourcenkopie immer aktiviert ist. Nach dem Upgrade wird eine Bereitstellung, die ein ServiceAccount ohne Berechtigung zum Erstellen des Ziel-Namespace oder zum Schreiben der kopierten Secrets und ConfigMaps darin anheftet, nicht mehr bereitgestellt. Es meldet „nicht bereit“ und versucht es erneut, bis die Erlaubnis erteilt wird. Gewähren Sie dem ServiceAccount die fehlenden Berechtigungen oder erstellen Sie den Ziel-Namespace vorab. Weitere Informationen finden Sie unter CVE-2026-88808. – Es wurde eine Sicherheitslücke im Git-Webhook-Empfänger von Fleet behoben, bei der ein nicht authentifizierter Aufrufer mit Netzwerkzugriff auf den Webhook-Dienst das Abfrageintervall von GitRepo-Ressourcen in jedem Namespace ändern konnte, wenn kein Webhook-Geheimnis konfiguriert war, was die Einführung legitimer Git-Änderungen verzögerte. Fleet wendet jetzt nur durch Webhook ausgelöste Änderungen an GitRepo-Spezifikationen für Anfragen an, die anhand eines konfigurierten Webhook-Geheimnisses überprüft wurden. Weitere Informationen finden Sie unter CVE-2026-93539.

Rancher General

Wichtige Fehlerbehebungen

– Es wurde ein bekanntes Problem mit Kubernetes v1.36-Clustern behoben, bei dem Rancher Backups aufgrund eines Problems mit dem Backup-Diagramm nicht unter den Cluster-Tools aufgeführt ist. Siehe #1055.

Authentifizierung

Wichtige Fehlerbehebungen

– Der ext.Kubeconfig-Speicher wurde aktualisiert, um ihn an das Standardverhalten von Kubernetes API-Ressourcen anzupassen. Siehe #56341.

Rollenbasierte Zugriffskontrolle (RBAC)

Wichtige Fehlerbehebungen

– Die Abgleichsschleife für globale Rollen, die das Feld inheritedFleetWorkspacePermissions enthalten, wurde behoben. Der Fix verhindert, dass Rancher-Protokolle mit Erstellungs-/Löschvorgängen als Spam versendet werden. Siehe #57050.

  • Rancher erweitert, um seine verwalteten Ressourcen für Grenzbereiche und Ressourcenkontingente besser vor Eingriffen durch reguläre Benutzer zu schützen.

    – Der Webhook lehnt jetzt Versuche von außerhalb von Rancher ab, diese verwalteten Ressourcen zu bearbeiten, eine nicht verwaltete Ressource zu „verwaltet“ hochzustufen oder eine verwaltete Ressource zu „nicht verwaltet“ herabzustufen, während Rancher selbst weiterhin vollen Zugriff erhält. Siehe #56773.

Cluster-Bereitstellung

Wichtige Fehlerbehebungen

– Es wurde ein Problem behoben, bei dem die GKE-Bereitstellungsbenutzeroberfläche Kubernetes-Versionen anbot, die von keinem GKE-Release-Kanal unterstützt werden. Rancher zeigt jetzt nur gültige GKE-Versionen für die Bereitstellung auf Release-Channel-Basis an und verhindert so, dass Benutzer Versionen auswählen, die nicht für die Bereitstellung neuer Cluster verwendet werden können. Siehe #18928 und #56879.

Bekannte Probleme

– Es gibt ein bekanntes Problem beim Löschen bereitgestellter Cluster, bei dem solche Cluster hängen bleiben, wenn sie über S3-Snapshots verfügen. Eine Problemumgehung besteht darin, alle verbleibenden s3 etcdsnapshots.rke.cattle.io-Objekte zu löschen, die zum Cluster gehören und im lokalen Cluster vorhanden sind. Weitere Informationen finden Sie unter #57506 und im Problemkommentar.

Installations-/Upgrade-Hinweise

Wenn Sie Rancher zum ersten Mal installieren, muss Ihre Umgebung die Installationsanforderungen erfüllen.

[!IMPORTANT] – Rancher erfordert nun, dass auf dem Cluster, auf dem es ausgeführt wird, die Kubernetes API Aggregation Layer aktiviert ist. Dies liegt daran, dass Rancher Kubernetes um zusätzliche APIs erweitert, indem es seinen eigenen Erweiterungsserver API registriert. Bitte beachten Sie, dass bei allen Versionen von Kubernetes, die in diesen Rancher-Versionen der K8s-Distributionen (RKE2/K3s) unterstützt werden, die Aggregationsschicht standardmäßig konfiguriert und aktiviert ist.

– Weitere Informationen finden Sie in der Dokumentation zum Erweiterungs-API-Server und #50400.

  • Der Rancher Kubernetes-Motor (RKE/RKE1) hat am 31. Juli 2025 das Ende seiner Lebensdauer erreicht. Die Rancher-Versionen 2.12.0 und höher unterstützen die Bereitstellung oder Verwaltung nachgelagerter RKE1-Cluster nicht mehr. Wir empfehlen, RKE1-Cluster auf RKE2 umzustellen, um weiterhin Support und Sicherheitsupdates zu gewährleisten. Erfahren Sie mehr über den Übergang hier.

– Rancher verfügt jetzt über eine Validierungsprüfung vor dem Upgrade für RKE1-Ressourcen, die fehlschlägt und die RKE1-Ressourcen auflistet, falls vorhanden. Weitere Informationen finden Sie unter #50286.

– Es ist wichtig, dass Sie den verfügbaren Speicherplatz auf Ihren Knoten überprüfen und entsprechend planen, bevor Sie auf Rancher v2.12.0 und höher aktualisieren, um mögliche Probleme mit der Festplattenbelastung und der Pod-Räumung zu vermeiden.

– Weitere Informationen finden Sie in der [Dokumentation „UI Server Side Pagination – Disk Space“] (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/advanced-user-guides/ui-server-side-pagination#disk-space).

– Rancher verfügt jetzt über eine Aktivierungsoption namens AUDIT_LOG_ENABLED für API-Überwachungsprotokolle für eine Rancher-Installation.

– In den Rancher-Versionen 2.11.x und früher konnte nur AUDIT_LEVEL festgelegt werden und die Standardprotokollebene (0) würde das Überwachungsprotokoll deaktivieren. In den Rancher-Versionen 2.12.x und höher enthält die Standardprotokollebene (0) jetzt nur die Metadaten der Protokollanforderung und -antwort und kann bei der Konfiguration von AUDIT_LOG_ENABLED festgelegt werden. Wenn Sie über Helm installieren oder aktualisieren, können Sie die API-Überwachungsprotokolle aktivieren und die Protokollebene angeben, indem Sie die folgende Einstellung auf Ihren Helm-Befehl anwenden: --set auditLog.enabled=true --set auditLog.level=0. Weitere Informationen finden Sie in der Dokumentation [Aktivieren des API-Überwachungsprotokolls zur Aufzeichnung von Systemereignissen] (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/advanced-user-guides/enable-api-audit-log) und #48941.

Änderungen bei Bildartefakten

Bildartefakt-Digests werden in Rancher v2.12.0, v2.11.4 und v2.10.8 umbenannt. Bis zu dieser Änderung wurden aus Kompatibilitätsgründen separate Image-Digest-Dateien für jedes Betriebssystem und jede Architektur verwaltet. Mit dieser Änderung soll für jedes Betriebssystem nur noch eine Datei bereitgestellt werden:

  • Die Dateien rancher-images-digests-linux-amd64.txt und rancher-images-digests-linux-arm64.txt sollen in rancher-images-digests-linux.txt umbenannt werden.

  • Die Dateien rancher-images-digests-windows-ltsc2019.txt und rancher-images-digests-windows-ltsc2022.txt sollen in rancher-images-digests-windows.txt umbenannt werden.

Upgrade-Anforderungen

  • Backups erstellen: Erstellen Sie ein Backup, bevor Sie Rancher aktualisieren. Um Rancher nach einem Upgrade zurückzusetzen, müssen Sie Rancher zunächst sichern und auf die vorherige Rancher-Version wiederherstellen. Da Rancher in demselben Zustand wiederhergestellt wird, in dem es sich bei der Erstellung des Backups befand, sind alle nach dem Upgrade vorgenommenen Änderungen nach der Wiederherstellung nicht enthalten.

  • Anforderungen an die Helmversion:

    • Um Rancher 2.12.x und höher zu verwalten, müssen Sie Ihren Helm client auf die Version 3.18 oder höher aktualisieren.

    – Diese Änderung ist erforderlich, um die Hinzufügung der Kubernetes 1.33-Unterstützung in dieser Version widerzuspiegeln.

    • Derzeit schreibt die offizielle [Helm Version Support Policy] (https://helm.sh/docs/topics/version_skew/) vor, dass nur Helm 3.18 den richtigen Kubernetes-Versionsbereich für Rancher 2.12 unterstützt.

  • CNI-Anforderungen:

    – Deaktivieren Sie für Kubernetes v1.19 und höher firewalld, da es mit verschiedenen CNI-Plugins nicht kompatibel ist. Siehe #28840.

    – Wenn Sie eine Linux-Distribution aktualisieren oder installieren, die nf_tables als Backend-Paketfilter verwendet, wie z. B. SLES 15, RHEL 8, Ubuntu 20.10, Debian 10 oder höher, aktualisieren Sie auf RKE v1.19.2 oder höher, um Flannel v0.13.0 zu erhalten. Flannel v0.13.0 unterstützt nf_tables. Siehe Flanell #1317.

  • Anforderungen für Umgebungen mit Luftspalt:

    – Wenn Sie einen Proxy vor einer Rancher-Instanz mit Luftspalt verwenden, müssen Sie zusätzliche Parameter an NO_PROXY übergeben. Siehe die Dokumentation und Ausgabe #2725.

    – Wenn Sie Rancher mit Docker in einer Air-Gap-Umgebung installieren, müssen Sie eine benutzerdefinierte registries.yaml-Datei für den docker run-Befehl bereitstellen, wie in der K3s-Dokumentation gezeigt. Wenn die Registry über Zertifikate verfügt, müssen Sie diese ebenfalls bereitstellen. Siehe #28969.

Rancher-Helm-Diagrammversionen

In Rancher v2.6.0 und höher werden in der Apps & Marketplace-Benutzeroberfläche viele Rancher-Helm-Diagramme mit einer Hauptversion benannt, die mit 100 beginnt. Dadurch wird vermieden, dass gleichzeitige Upstream-Änderungen und Rancher-Änderungen widersprüchliche Versionsinkremente verursachen. Dies entspricht auch der semantischen Versionierung (SemVer), die eine Voraussetzung für Helm ist. Sie können die Upstream-Versionsnummer eines Diagramms in den Build-Metadaten sehen, zum Beispiel: 100.0.0+up2.1.0. Siehe #32294.

Seit langem bekannte Probleme – RKE2-Bereitstellung

  • Rancher v2.7.7:

Seit langem bekannte Probleme – K3s-Bereitstellung

  • Rancher v2.7.6:

    – Die Bereitstellung von RKE2/K3s-Clustern mit hinzugefügten (nicht integrierten) benutzerdefinierten Knotentreibern führt dazu, dass die Bereitstellung fehlschlägt. Um dieses Problem zu umgehen, reparieren Sie die hinzugefügten Knotentreiber nach der Aktivierung. Siehe #37074.

Seit langem bekannte Probleme – Rancher App (Globale Benutzeroberfläche)

    – Nach dem Löschen eines Namespace oder Projekts in der Rancher-Benutzeroberfläche bleibt der Namespace oder das Projekt sichtbar. Um dieses Problem zu umgehen, aktualisieren Sie die Seite. Siehe #12220.

  • Rancher v2.9.2:

Die Eingabe einer Mindestknotenanzahl von Null über die Benutzeroberfläche kann dazu führen, dass die Clustererstellung aufgrund eines Fehlers aufgrund eines ungültigen Parameters fehlschlägt. Um zu verhindern, dass dieser Fehler auftritt, geben Sie eine Mindestknotenanzahl ein, die mindestens der Knotenanzahl entspricht. Siehe #11922.

  • Rancher v2.7.7:

    – Beim Erstellen eines Clusters in der Rancher-Benutzeroberfläche ist die Verwendung eines Unterstrichs _ im Feld Cluster Name nicht zulässig. Siehe #9416.

  • Rancher v2.6.4:

    – Der Abschnitt „Deployment securityContext“ fehlt, wenn eine neue Arbeitslast erstellt wird. Dadurch wird verhindert, dass Pods gestartet werden, wenn die Unterstützung für Pod-Sicherheitsrichtlinien aktiviert ist. Siehe #4815.

Seit langem bekannte Probleme – EKS

  • Rancher v2.7.0:

    – EKS-Cluster auf Kubernetes v1.21 oder niedriger auf Rancher v2.7 können nicht aktualisiert werden. Siehe #39392.

Seit langem bekannte Probleme – Authentifizierung

  • Rancher v2.9.0:

    – Es gibt einige bekannte Probleme mit der Unterstützung des OpenID Connect-Anbieters: – Wenn der generische OIDC-Authentifizierungsanbieter aktiviert ist und Sie versuchen, Authentifizierungsanbieter-Benutzer zu einem Cluster oder Projekt hinzuzufügen, werden Benutzer nicht in der Dropdown-Suchleiste angezeigt. Dies ist ein erwartetes Verhalten, da der OIDC-Authentifizierungsanbieter allein nicht durchsuchbar ist. Siehe #46104.

    – Wenn der generische OIDC-Authentifizierungsanbieter aktiviert ist, können Authentifizierungsanbieter-Benutzer, die mit ihrem Benutzernamen zu einem Cluster/Projekt hinzugefügt werden, bei der Anmeldung nicht auf Ressourcen zugreifen. Ein Benutzer hat bei der Anmeldung nur dann Zugriff auf Ressourcen, wenn der Benutzer mit seiner Benutzer-ID hinzugefügt wird. Siehe #46105.

    – Wenn der generische OIDC-Authentifizierungsanbieter aktiviert ist und ein Authentifizierungsanbieter-Benutzer in einer verschachtelten Gruppe bei Rancher angemeldet ist, wird dem Benutzer beim Versuch, ein Projekt zu erstellen, die folgende Fehlermeldung angezeigt: projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg". Das Projekt wird jedoch noch erstellt. Siehe #46106.

Seit langem bekannte Probleme – Rancher Webhook

  • Rancher v2.7.2:

    • In allen Downstream-Clustern ist ein Webhook installiert. Bei dieser Funktionalität können bei Benutzern mehrere Probleme auftreten:

      – Wenn Sie von einer Rancher-Version v2.7.2 oder höher auf eine Rancher-Version vor v2.7.2 zurücksetzen, bleiben die Webhooks in Downstream-Clustern. Da der Webhook so konzipiert ist, dass er 1:1 mit bestimmten Rancher-Versionen kompatibel ist, kann dies zu unerwartetem Verhalten im Downstream führen. Das Rancher-Team hat ein Skript entwickelt, das nach Abschluss des Rollbacks verwendet werden sollte (d. h. nachdem eine Rancher-Version vor v2.7.2 ausgeführt wird). Dadurch wird der Webhook aus den betroffenen Downstream-Clustern entfernt. Siehe #40816.

Seit langem bekannte Probleme – Virtualisierungsmanagement (Harvester)

  • Rancher v2.13.1:

    – Beim Upgrade auf Rancher v2.13.1 oder höher während der Verwendung von Harvester v1.6.1 können Benutzer auf ein Problem mit ihren Load Balancern in Downstream-Clustern stoßen, die den Harvester Cloud Provider verwenden, und müssen die folgende [Problemumgehung] (https://docs.harvesterhci.io/latest/troubleshooting/rancher#guest-cluster-loadbalancer-ip-is-not-reachable) durchführen, um Calico anzuweisen, keine der von kube-vip verwalteten IPs/Schnittstellen zu verwenden. Siehe #9767.

  • Rancher v2.7.2:

    – Wenn Sie Rancher v2.7.2 mit Harvester v1.1.1-Clustern verwenden, können Sie den Harvester-Cloud-Anbieter beim Bereitstellen oder Aktualisieren von Gastclustern nicht auswählen. Die Harvester release notes enthalten Anweisungen zur Behebung dieses Problems. Siehe #3750.

Seit langem bekannte Probleme – Sicherung/Wiederherstellung

– Bei der Migration zu einem Cluster mit der Rancher Backup-Funktion kann die Server-URL nicht in einen anderen Speicherort geändert werden. Es muss weiterhin dieselbe URL verwendet werden.

Release v2.15.2

[!IMPORTANT]

  • If you are using Active Directory Federation Service (AD FS), upgrading to Rancher v2.10.1 or later may cause issues with authentication, requiring manual intervention. These issues are due to the AD FS Relying Party Trust not being able to pick up a signature verification certificate from the metadata. For more information, see #48655. These issues can be corrected by either of two methods:

    • Updating the Relying Party Trust information from federation metadata (Relying Party Trust → Update from Federation Metadata…​).

    • Directly adding the certificate (Relying Party Trust → Properties → Signature tab → Add → Select the certificate).

Rancher v2.15.2 is the latest patch release of Rancher. This is a Community version release that introduces maintenance updates and bug fixes.

For more information on new features in the general minor release, see the v2.15.0 release notes.

Security Fixes for Vulnerabilities

This release addresses the following security issues:

Rancher

  • Fixed a security vulnerability in Rancher where logging out cleared the browser session cookies but did not delete the corresponding public API session token on the server. A previously captured session token therefore remained valid until its natural expiry, defeating logout as a revocation control. Only deployments using public API session tokens in, for example, OIDC-based authentication, were affected. For more information, refer to CVE-2026-88805.
  • Fixed a security vulnerability in Rancher where a small set of public UI settings served by unauthenticated, read-only API routes could be modified by a remote unauthenticated user. Because one of those settings is rendered as raw HTML on the login page, attacker-controlled content could be stored and executed in the browser of users accessing the login page, potentially exposing the local administrator bootstrap password or an active administrator session. The unauthenticated settings routes are now strictly read-only. For more information, see CVE-2026-88804.

Fleet

  • Fixed a security vulnerability in Fleet where Helm valuesFiles entries in fleet.yaml were not confined to the bundle directory. A user able to supply untrusted bundle content could cause Fleet to read files outside the repository checkout and expose their contents through the generated Bundle, including credential material the user had no permission to read. Fleet now rejects values file paths that escape the bundle directory. For more information, refer to CVE-2026-93537.
  • Fixed an issue where the Fleet agent copied the Secrets and ConfigMaps listed in a Bundle's downstreamResources, and created the deployment's target namespace, using the agent's own credentials instead of the ServiceAccount pinned to the deployment. Those writes are now gated by the tenant's downstream RBAC. Deployments that do not pin a ServiceAccount are unchanged as an agent operation. Rancher v2.15.x is affected in a default installation, because the resource copy is always enabled there. After upgrading, a deployment that pins a ServiceAccount without permission to create the target namespace, or to write the copied Secrets and ConfigMaps in it, will no longer deploy. It reports “not ready” and retries until the permission is granted. Grant the ServiceAccount the missing permissions, or pre-create the target namespace. For more information, refer to CVE-2026-88808.
  • Fixed a security vulnerability in Fleet's Git webhook receiver where when a webhook secret was not configured, an unauthenticated caller with network access to the webhook service could change the polling interval of GitRepo resources in any namespace, delaying the rollout of legitimate Git changes. Fleet now only applies webhook-triggered changes to GitRepo specifications for requests verified against a configured webhook secret. For more information, refer to CVE-2026-93539.

Rancher General

Major Bug Fixes

  • Fixed a known issue with Kubernetes v1.36 clusters where Rancher Backups is not listed under the Cluster Tools due to a Backups chart issue. See #1055.

Authentication

Major Bug Fixes

  • The ext.Kubeconfig store has been updated to align with standard Kubernetes API resource behavior. See #56341.

Role-Based Access Control (RBAC)

Major Bug Fixes

  • Fixed the reconciler loop for Global Roles that contain the inheritedFleetWorkspacePermissions field. The fix prevents Rancher logs from being spammed with create/delete operations. See #57050.

  • Extended Rancher to better protect its managed resources for limit ranges and resource quotas from interference by regular users.

    • The webhook now rejects attempts from outside of Rancher to edit these managed resources, to promote an unmanaged resource to managed, or to demote a managed resource to unmanaged, while still allowing Rancher itself full access. See #56773.

Cluster Provisioning

Major Bug Fixes

  • Fixed an issue where the GKE provisioning UI offered Kubernetes versions that are not supported by any GKE release channel. Rancher now shows only valid GKE versions for release-channel-based provisioning, preventing users from selecting versions that cannot be used to provision new clusters. See #18928 and #56879.

Known Issues

  • There is a known issue with provisioned clusters deletion where such clusters get stuck if they have s3 snapshots. A workaround is to delete all left over s3 etcdsnapshots.rke.cattle.io objects belonging to the cluster that are present within the local cluster. See #57506 and the issue comment for more information.

Install/Upgrade Notes

If you’re installing Rancher for the first time, your environment must fulfill the installation requirements.

[!IMPORTANT]

  • Rancher now requires the cluster it runs on to have the Kubernetes API Aggregation Layer enabled. This is because Rancher extends Kubernetes with additional APIs by registering its own extension API server. Please note that all versions of Kubernetes supported in this Rancher versions K8s distributions (RKE2/K3s) will have the aggregation layer configured and enabled by default.

    • Refer to the Extension API Server documentation and #50400 for more information.

  • Rancher Kubernetes Engine (RKE/RKE1) has reached end of life as of July 31, 2025. Rancher versions 2.12.0 and later no longer support provisioning or managing downstream RKE1 clusters. We recommend replatforming RKE1 clusters to RKE2 to ensure continued support and security updates. Learn more about the transition here.

    • Rancher now has a pre-upgrade validation check for RKE1 resources which fails and lists the RKE1 resources if present. Refer to #50286 for more information.

  • It is crucial that you review the available disk space on your nodes and plan accordingly before upgrading to Rancher v2.12.0 and later to avoid potential disk pressure and pod eviction issues.

    • For additional information, refer to the UI Server Side Pagination - Disk Space documentation.

  • Rancher now has an enablement option called AUDIT_LOG_ENABLED for API Audit Logs for a Rancher installation.

    • In Rancher versions 2.11.x and earlier, only the AUDIT_LEVEL could be set and the default log level (0) would disable the audit log. In Rancher versions 2.12.x and later, the default log level (0) now only contains the log request and response metadata, and can be set when configuring AUDIT_LOG_ENABLED. If installing or upgrading via Helm you can enable the API Audit Logs and specify the log level by applying the following setting to your Helm command: --set auditLog.enabled=true --set auditLog.level=0. See the Enabling the API Audit Log to Record System Events documentation and #48941.

Changes in Image Artifacts

Image artifact digests are renamed in Rancher v2.12.0, v2.11.4 and v2.10.8. Up until this change, separate image digests files for each operating system and architecture have been maintained for compatibility reasons. With this change, only one file for each operating system is to be provided:

  • The rancher-images-digests-linux-amd64.txt and rancher-images-digests-linux-arm64.txt files are to be renamed to rancher-images-digests-linux.txt.

  • The rancher-images-digests-windows-ltsc2019.txt and rancher-images-digests-windows-ltsc2022.txt files are to be renamed to rancher-images-digests-windows.txt.

Upgrade Requirements

  • Creating backups: Create a backup before you upgrade Rancher. To roll back Rancher after an upgrade, you must first back up and restore Rancher to the previous Rancher version. Because Rancher will be restored to the same state as when the backup was created, any changes post-upgrade will not be included after the restore.

  • Helm version requirements:

    • To manage Rancher 2.12.x and later, you must upgrade your Helm client to version 3.18 or newer.

    • This change is required to reflect the addition of Kubernetes 1.33 support with this release.

    • Currently, the official Helm Version Support Policy dictates that only Helm 3.18 supports the proper Kubernetes version range for Rancher 2.12.

  • CNI requirements:

    • For Kubernetes v1.19 and later, disable firewalld as it’s incompatible with various CNI plugins. See #28840.

    • When upgrading or installing a Linux distribution that uses nf_tables as the backend packet filter, such as SLES 15, RHEL 8, Ubuntu 20.10, Debian 10, or later, upgrade to RKE v1.19.2 or later to get Flannel v0.13.0. Flannel v0.13.0 supports nf_tables. See Flannel #1317.

  • Requirements for air-gapped environments:

    • When using a proxy in front of an air-gapped Rancher instance, you must pass additional parameters to NO_PROXY. See the documentation and issue #2725.

    • When installing Rancher with Docker in an air-gapped environment, you must supply a custom registries.yaml file to the docker run command, as shown in the K3s documentation. If the registry has certificates, then you’ll also need to supply those. See #28969.

Rancher Helm Chart Versions

In Rancher v2.6.0 and later, in the Apps & Marketplace UI, many Rancher Helm charts are named with a major version that starts with 100. This avoids simultaneous upstream changes and Rancher changes from causing conflicting version increments. This also complies with semantic versioning (SemVer), which is a requirement for Helm. You can see the upstream version number of a chart in the build metadata, for example: 100.0.0+up2.1.0. See #32294.

Long-standing Known Issues - RKE2 Provisioning

  • Rancher v2.7.7:

    • Due to the backoff logic in various components, downstream provisioned K3s and RKE2 clusters may take longer to re-achieve Active status after a migration. If you see that a downstream cluster is still updating or in an error state immediately after a migration, please let it attempt to resolve itself. This might take up to an hour to complete. See #34518 and #42834.

  • Rancher v2.7.6:

    • Clusters remain in an Updating state even when they contain nodes in an Error state. See #39164.

Long-standing Known Issues - Rancher App (Global UI)

  • Rancher v2.10.0:

    • After deleting a Namespace or Project in the Rancher UI, the Namespace or Project remains visible. As a workaround, refresh the page. See #12220.

  • Rancher v2.9.2:

    • Although system mode node pools must have at least one node, the Rancher UI allows a minimum node count of zero. Inputting a zero minimum node count through the UI can cause cluster creation to fail due to an invalid parameter error. To prevent this error from occurring, enter a minimum node count at least equal to the node count. See #11922.

Long-standing Known Issues - Authentication

  • Rancher v2.9.0:

    • There are some known issues with the OpenID Connect provider support:

      • When the generic OIDC auth provider is enabled, and you attempt to add auth provider users to a cluster or project, users are not populated in the dropdown search bar. This is expected behavior as the OIDC auth provider alone is not searchable. See #46104.

      • When the generic OIDC auth provider is enabled, auth provider users that are added to a cluster/project by their username are not able to access resources upon logging in. A user will only have access to resources upon login if the user is added by their userID. See #46105.

      • When the generic OIDC auth provider is enabled and an auth provider user in a nested group is logged into Rancher, the user will see the following error when they attempt to create a Project: projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg". However, the project is still created. See #46106.

Long-standing Known Issues - Rancher Webhook

  • Rancher v2.7.2:

    • A webhook is installed in all downstream clusters. There are several issues that users may encounter with this functionality:

      • If you rollback from a version of Rancher v2.7.2 or later, to a Rancher version earlier than v2.7.2, the webhooks will remain in downstream clusters. Since the webhook is designed to be 1:1 compatible with specific versions of Rancher, this can cause unexpected behaviors to occur downstream. The Rancher team has developed a script which should be used after rollback is complete (meaning after a Rancher version earlier than v2.7.2 is running). This removes the webhook from affected downstream clusters. See #40816.

See #9767.

  • Rancher v2.7.2:
