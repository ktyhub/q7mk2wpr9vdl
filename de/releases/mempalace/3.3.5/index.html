mempalace v3.3.5

3.3.5 ist eine Korrekturversion. Keine neuen benutzerorientierten Funktionen – die Energie des Zyklus wurde in Datenintegrität, Wiederherstellung und prozessübergreifende Korrektheit geflossen. Wenn Ihr Palast nach einer großen Mine jemals Internal error: Error finding id erreicht hat, ein Knowledge-Graph-Triple stillschweigend im Nichts verschwunden ist oder Sie unter Windows/einem Multi-Tenant-Host laufen, ist diese Version genau das Richtige für Sie. Die Überschrift behebt:

  • mempalace repair --mode from-sqlite stellt Paläste wieder her, die auf apply_logs hängengeblieben sind. Wenn der HNSW-Segmentschreiber von ChromaDB verkeilt (die im Upstream und in #1308 gemeldete Korruptionsklasse), rufen --mode legacy und die Inline-Reparatur beide Collection.count() als ihren ersten Lesevorgang auf – was genau der Aufruf ist, der ausgelöst wird. Der alte Fehlermodus war ein Reparaturdruck Cannot recover — palace may need to be re-mined from source files, obwohl die SQLite-Tabellen vollständig intakt waren. Der neue Modus liest (id, document, metadata) direkt aus chroma.sqlite3 über den Metadaten-Segment-Join, öffnet niemals einen Chromadb-client für den beschädigten Palast und fügt alles unter Ihrer konfigurierten Einbettungsfunktion erneut in einen neuen Palast ein. End-to-End-Verifizierung in einem korrupten Palast mit 52.300 Reihen in der realen Welt. (#1308)
  • Zwei Silent-Loss-Klassen im Wissensgraphen sind jetzt Schreibzeitfehler. Tripel mit valid_to < valid_from wurden früher dauerhaft gespeichert, waren aber nicht erreichbar (der zeitliche Filter stimmte mit keinem as_of überein); add_triple() lehnt jetzt invertierte Intervalle beim Schreiben ab. Und an SQLite weitergeleitete Datumszeichenfolgen werden im Voraus über sanitize_iso_temporal() (alias sanitize_iso_date()) validiert, das YYYY-MM-DD und kanonische UTC-Datumszeiten (YYYY-MM-DDTHH:MM:SSZ / +00:00) akzeptiert und alles andere ablehnt – Eingaben in natürlicher Sprache wie "yesterday" erzeugen nicht mehr stillschweigend leere Ergebnismengen. Verhaltensänderung: Teildatumseingaben, die in 3.3.4 ("2026", "2026-05") funktionierten, sind jetzt fehlerhaft; Übergeben Sie stattdessen ein vollständiges Datum oder eine kanonische UTC-Datumszeit. (#1214, #1164, #1167, #1374, #1417)
  • EntityRegistry.save() ist jetzt absturzsicher. Die Personen-/Projektkarte besteht aus monatelangen Mining-Daten, und der alte Code führte einen nicht-atomaren Path.write_text() aus – ein Stromausfall, OOM oder kill -9 zwischen Truncate und Full Flush würde ihn stillschweigend löschen (der load() der Registrierung verschluckt JSONDecodeError). Jetzt speichern schreibt in eine gleichgeordnete temporäre Datei, fsyncs und os.replace()s an Ort und Stelle. Die vorherige Registrierung bleibt bei jedem Absturz intakt, bevor die Umbenennung wiederhergestellt wird. (#1215)
  • MCP tool_search läuft durch das Post-Bulk-Mine-HNSW-Flush-Fenster. Nach einer CLI-Mine können die HNSW-Segmentmetadaten von ChromaDB für ca. 30–60 Sekunden nicht geleert werden; Die flächendeckende MCP-Suche ergab für das gesamte Fenster Internal error: Error finding id. tool_search erkennt nun diesen spezifischen Übergang, löscht sowohl den MCP-lokalen als auch den gemeinsam genutzten Backend-Cache für den Palast, schläft 2 Sekunden lang und versucht es einmal erneut. Erfolgreiche Wiederholungsversuche werden mit index_recovered: true gekennzeichnet, damit Anrufer beobachten können, wann es ausgelöst wurde. Teilweise Korrektur für den breiteren #1315-Cluster – tool_check_duplicate und andere Index-berührende Tools benötigen immer noch denselben Wrapper. (#1396)
  • Prozessübergreifende Korrektheit auf Windows- und Multi-Tenant-Hosts. ChromaBackend.close_palace() gibt jetzt ordnungsgemäß die rust-seitige SQLite-Dateisperre von ChromaDB frei – das erneute Öffnen desselben Palastpfads, nachdem shutil.rmtree nicht mehr mit SQLITE_READONLY_DBMOVED fehlschlägt. Und der _kg des MCP-Servers ist kein Singleton auf Modulebene mehr: Multi-Tenant-Hosts, die MEMPALACE_PALACE_PATH zwischen Tool-Aufrufen rotieren, treffen jetzt über einen Lazy-Pfad-Cache auf die richtige SQLite-Datei. (#1067, #1105, #1136, #1160)
  • Windows stdio ist auf der ganzen Linie UTF-8. mempalace search > out.txt und weitergeleitete fact_checker-Aufrufe mojibaken nicht länger kyrillischen/CJK-Schubladentext an der Prozessgrenze. mcp_server, hooks_cli und cli/fact_checker werden alle identisch neu konfiguriert. (#1282)
  • miner.detect_room-Routing-Korrektur für Monorepos. Die Teilzeichenfolgenprüfung war bidirektional, sodass jedes Token, das eine Teilzeichenfolge eines Raumnamens war oder umgekehrt, übereinstimmte – views/billing-page/src/Foo.test.tsx wurde an einen interviews-Raum weitergeleitet, da "views" in "interviews" zuerst übereinstimmte. Verwendet jetzt den durch Trennzeichen begrenzten Token-Abgleich (-, _, ., /). (#1004, schließt #1002)
  • mempalace compress stürzt bei Palästen über ~32.000 Schubladen nicht mehr ab. Der Schubladenabruf ist jetzt paginiert und spiegelt den Fix #851 in miner.py wider. (#1073, #1107) Intern: Testzuverlässigkeit wurde ebenfalls bestanden – tests/test_palace_locks.py und tests/test_chroma_collection_lock.py wechselten von fork zu spawn für das Spawnen von Unterprozessen (Python 3.13 + Multithreaded Parent = Deadlock unter fork, und macOS verbietet Fork-without-Exec über CoreFoundation), und mehrere Testdateien umschließen jetzt sqlite3.connect(...) in contextlib.closing(), sodass Verbindungen freigegeben werden auch der Fehlerpfad. (#1430, #1431) Die Versprechen haben sich nicht geändert. Jedes Wort ist genau gespeichert. Alles bleibt auf Ihrer Maschine. Keine Telemetrie. Keine Fallbacks auf Cloud-APIs, von denen wir Ihnen nichts erzählt haben. Jede Veröffentlichung schärft das, was bereits vorhanden ist.

mempalace v3.3.5

3.3.5 is a fixes release. No new user-facing features — the cycle's energy went into data integrity, recovery, and cross-process correctness. If your palace ever hit Internal error: Error finding id after a big mine, or you had a knowledge-graph triple silently disappear into the void, or you're running on Windows / a multi-tenant host — this release is for you.

The headline fixes:

  • mempalace repair --mode from-sqlite recovers palaces stuck on apply_logs. When ChromaDB's HNSW segment writer wedges (the corruption class reported upstream and in #1308), --mode legacy and the inline repair both call Collection.count() as their first read — which is exactly the call that raises. The old failure mode was a repair printing Cannot recover — palace may need to be re-mined from source files even though the SQLite tables were fully intact. The new mode reads (id, document, metadata) directly from chroma.sqlite3 via the metadata segment join, never opens a chromadb client against the corrupt palace, and re-upserts everything into a fresh palace under your configured embedding function. Verified end-to-end on a 52,300-row real-world corrupt palace. (#1308)

  • Two silent-loss classes in the knowledge graph are now write-time errors. Triples with valid_to < valid_from used to be durably stored but unreachable (the temporal filter matched no as_of); add_triple() now rejects inverted intervals at write time. And date strings forwarded to SQLite are validated up front via sanitize_iso_temporal() (alias sanitize_iso_date()), which accepts YYYY-MM-DD and canonical UTC datetimes (YYYY-MM-DDTHH:MM:SSZ / +00:00) and rejects everything else — natural-language inputs like "yesterday" no longer silently produce empty result sets. Behavior change: partial-date inputs that worked in 3.3.4 ("2026", "2026-05") now error; pass a full date or canonical UTC datetime instead. (#1214, #1164, #1167, #1374, #1417)

  • EntityRegistry.save() is now crash-safe. The people/projects map is months of mining data, and the old code did a non-atomic Path.write_text() — a power loss, OOM, or kill -9 between truncate and full-flush would silently wipe it (the registry's load() swallows JSONDecodeError). Save now writes to a sibling temp file, fsyncs, and os.replace()s into place. The previous registry stays intact on any crash before the rename returns. (#1215)

  • MCP tool_search rides through the post-bulk-mine HNSW flush window. After a CLI mine, ChromaDB's HNSW segment metadata can be unflushed for ~30-60s; wing-scoped MCP search was hitting Internal error: Error finding id for that entire window. tool_search now detects this specific transient, drops both the MCP-local and shared-backend caches for the palace, sleeps 2s, and retries once. Successful retries are tagged with index_recovered: true so callers can observe when it fired. Partial fix for the broader #1315 cluster — tool_check_duplicate and other index-touching tools still need the same wrapper. (#1396)

  • Cross-process correctness on Windows and multi-tenant hosts. ChromaBackend.close_palace() now properly releases ChromaDB's rust-side SQLite file lock — reopening the same palace path after shutil.rmtree no longer fails with SQLITE_READONLY_DBMOVED. And the MCP server's _kg is no longer a module-level singleton: multi-tenant hosts rotating MEMPALACE_PALACE_PATH between tool calls now hit the right SQLite file via a lazy per-path cache. (#1067, #1105, #1136, #1160)

  • Windows stdio is UTF-8 across the board. mempalace search > out.txt and piped fact_checker invocations no longer mojibake Cyrillic / CJK drawer text at the process boundary. mcp_server, hooks_cli, and cli/fact_checker all reconfigure identically. (#1282)

  • miner.detect_room routing fix for monorepos. The substring check was bidirectional, so any token that was a substring of a room name or vice versa matched — views/billing-page/src/Foo.test.tsx routed to an interviews room because "views" in "interviews" matched first. Now uses separator-bounded token matching (-, _, ., /). (#1004, closes #1002)

  • mempalace compress no longer crashes on palaces above ~32k drawers. Drawer fetch is now paginated, mirroring the #851 fix in miner.py. (#1073, #1107)

Internal: test reliability got a pass too — tests/test_palace_locks.py and tests/test_chroma_collection_lock.py switched from fork to spawn for subprocess spawning (Python 3.13 + multi-threaded parent = deadlock under fork, and macOS forbids fork-without-exec via CoreFoundation), and several test files now wrap sqlite3.connect(...) in contextlib.closing() so connections release on the failure path too. (#1430, #1431)

The promises haven't moved. Every word stored exactly. Everything stays on your machine. No telemetry. No fallbacks to cloud APIs we didn't tell you about. Each release sharpens what's already there.
