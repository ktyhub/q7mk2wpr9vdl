#cognee v1.6.10

v1.6.10 Mejoras en confiabilidad y observabilidad

Fecha de lanzamiento: 2026-11-18 Cambios: v1.6.9 → v1.6.10 Solicitudes de extracción: #6744

Resumen

Esta versión se centra en hacer que Cognee sea más confiable y más fácil de depurar: los grupos de conexiones de Postgres se ajustan para reducir las conexiones fuera de control y las largas esperas, la captura de llamadas de LLM ahora registra seguimientos anidados e información de las personas que llaman para una mejor observabilidad, y la ruta de fragmentación de documentos está reforzada para evitar la reutilización incorrecta de fragmentos. La fragmentación de CI/prueba también se amplió para reducir la descamación.

Destacados

  • Grupos de conexiones por conjunto de datos de Postgres más seguros: menor desbordamiento predeterminado y tiempos de espera limitados para evitar grandes picos de conexión y paradas prolongadas.
  • Captura de llamadas de LLM mejorada: registra las llamadas de LLM de seguimiento (anidadas) e incluye metadatos de las personas que llaman para una depuración y un análisis de uso más claros.
  • Robustez de la fragmentación: validación más estricta y estampado centralizado de fragmentos para que los fragmentos almacenados se identifiquen de manera confiable y se reutilicen cuando sea posible.
  • CI se dividió en más fragmentos para reducir la descamación y acelerar la retroalimentación de las pruebas durante el desarrollo.
  • Documentación actualizada para un nombre de modelo Anthropic retirado (ahora recomienda claude-sonnet-5-5).

Cambios importantes

  • Comportamiento del grupo de Postgres por conjunto de datos: los valores predeterminados para los grupos de conexiones de Postgres por conjunto de datos se han ajustado (desbordamiento máximo más pequeño y comportamiento de espera del grupo explícito). Si su implementación depende de picos muy grandes y de corta duración de escrituras simultáneas en motores por conjunto de datos, es posible que vea errores más inmediatos de "grupo agotado". Acción requerida: revise y, si es necesario, aumente su VECTOR_POOL_ARGS o la configuración del grupo específico del conjunto de datos y/o aumente el pool_timeout para adaptarse a su carga de trabajo.

Nuevas características

  • Seguimientos de captura de llamadas de LLM: la función de captura de llamadas de LLM (que escribe un registro JSONL por cada llamada de LLM que realiza Cognee) ahora también captura llamadas de seguimiento/anidadas de LLM y registra quién las llamó (un campo de "persona que llama"). Qué hace: obtiene un registro más claro y rastreable tanto de la solicitud de LLM original como de cualquier llamada interna posterior. Por qué es importante: depuración más sencilla, análisis de costos y observabilidad de flujos complejos de LLM de varios pasos.

Mejoras

  • Valores predeterminados del grupo de Postgres por conjunto de datos ajustados: el límite predeterminado para los grupos de Postgres por conjunto de datos (utilizados por el backend de pgvector y otros motores de base de datos por conjunto de datos) se ha reducido para que cada conjunto de datos utilice menos conexiones excesivas. Los comentarios de configuración ahora también indican un valor de pool_timeout (cuánto tiempo espera una operación para tener una conexión libre antes de fallar). Qué hace: reduce la posibilidad de abrir demasiadas conexiones de base de datos y de paradas prolongadas e inesperadas. Por qué es importante: implementaciones más predecibles y menor presión sobre los recursos de la base de datos en configuraciones multiinquilino.
  • Comprobaciones de fragmentación más estrictas: la lógica de fragmentación de documentos (que divide los documentos en 'fragmentos' más pequeños para su indexación y recuperación) ahora realiza una validación más estricta de los fragmentos. Qué hace: detecta antes fragmentos no válidos o que no coinciden y evita aceptar silenciosamente fragmentos que podrían dañar el comportamiento de actualización. Por qué es importante: menos reconstrucciones misteriosas o inconsistencia de datos al actualizar documentos.
  • Estampado de fragmentos centralizado: los objetos de fragmentos ahora se estampan centralmente con el identificador de fragmentos (el marcador que muestra qué regla de fragmentación produjo el fragmento). Qué hace: garantiza que los fragmentos almacenados lleven de manera confiable la identificación de origen en lugar de depender del estampado distribuido. Por qué es importante: mejora la precisión cuando el sistema decide si los fragmentos existentes se pueden reutilizar durante las actualizaciones incrementales.
  • Documentos: Nombre del modelo antrópico actualizado: las referencias al nombre del modelo retirado 'claude-3-5-sonnet-20241022' fueron reemplazadas por 'claude-sonnet-5-5' en la documentación. Qué hace: evita la confusión al hacer referencia a modelos eliminados. Por qué es importante: mantiene las instrucciones de configuración precisas y reduce el tiempo perdido al configurar los proveedores de Anthropic.

Rendimiento

  • Menor sobrecarga de conexión para motores Postgres por conjunto de datos: al reducir el límite de desbordamiento del grupo y aclarar los tiempos de espera del grupo, las implementaciones típicas abrirán menos conexiones de base de datos simultáneas. Impacto práctico: uso reducido de recursos de base de datos y menor contención en hosts que sirven muchos conjuntos de datos; Los picos extremos fallarán más rápido en lugar de bloquearse durante períodos prolongados.

Corrección de errores

  • Correcciones a las pruebas unitarias y la estabilidad de CI: se arreglaron varias pruebas unitarias fallidas y se reorganizó el conjunto de pruebas para mejorar la confiabilidad (consulte los cambios de CI a continuación).
  • Corrección de errores relacionados con la fragmentación: las comprobaciones de fragmentación más estrictas y el estampado centralizado resuelven casos en los que las fragmentaciones sin identificadores adecuados podrían causar fallas de actualización o estados inconsistentes.
  • Correcciones del comportamiento de espera y grupo de Postgres: se solucionaron problemas por los cuales los grupos por conjunto de datos podían crecer demasiado o bloquear a las personas que llamaban durante largos períodos sin fallar rápidamente.

Cambios técnicos

  • Aumento de la fragmentación de CI/prueba: las pruebas de integración se reparticionaron (Recuperación -> 5 fragmentos, Documentos y tareas -> 6 fragmentos, Infraestructura -> 4 fragmentos) y las pruebas unitarias se dividieron en 4 fragmentos en CI entre sistemas operativos. Qué hace: reduce la inestabilidad de las pruebas y nivela el tiempo de ejecución por fragmento. Por qué es importante: comentarios de CI más rápidos y confiables para los desarrolladores.
  • Componentes internos de observabilidad nuevos/actualizados: se agregaron nuevos archivos de módulo para capturar y escribir registros de llamadas de LLM más completos (incluidos los seguimientos) y se agregaron pruebas asociadas para cubrir esta funcionalidad.
  • Interno: versión de MCP modificada y múltiples archivos de prueba ajustados/agregados para reflejar el nuevo comportamiento y bloquear las regresiones.

cognee v1.6.10

v1.6.10  Reliability & Observability Improvements

Release Date: 2026-11-18 Changes: v1.6.9 → v1.6.10

Pull Requests: #6744

Summary

This release focuses on making Cognee more reliable and easier to debug: Postgres connection pools are tightened to reduce runaway connections and long waits, LLM call capture now records nested follow-ups and caller information for better observability, and the document chunking path is hardened to avoid incorrect chunk reuse. CI/test sharding was also expanded to reduce flakiness.

Highlights

  • Safer Postgres per-dataset connection pools: lower default overflow and bounded wait times to avoid huge connection spikes and long stalls.
  • Improved LLM call capture: records follow-up (nested) LLM calls and includes caller metadata for clearer debugging and usage analysis.
  • Chunking robustness: stricter validation and centralized stamping of chunks so stored chunks are reliably identified and reused when possible.
  • CI split into more shards to lower flakiness and speed up test feedback during development.
  • Documentation updated for a retired Anthropic model name (now recommends claude-sonnet-5-5).

Breaking Changes

  • Postgres per-dataset pool behavior: Defaults for per-dataset Postgres connection pools have been tightened (smaller max overflow and explicit pool wait behavior). If your deployment relies on very large, short-lived spikes of concurrent writes to per-dataset engines, you may see more immediate 'pool exhausted' errors. Action required: review and, if needed, increase your VECTOR_POOL_ARGS or dataset-specific pool settings and/or raise pool_timeout to suit your workload.

New Features

  • LLM call capture follow-ups: The LLM call capture feature (which writes one JSONL record per LLM call Cognee makes) now also captures follow-up / nested LLM calls and records who called them (a "caller" field). What it does: you get a clearer, traceable record of both the original LLM request and any internal subsequent calls. Why it matters: easier debugging, cost analysis and observability of complex multi-step LLM flows.

Improvements

  • Per-dataset Postgres pool defaults tightened: The default ceiling for per-dataset Postgres pools (used by the pgvector backend and other per-dataset DB engines) has been reduced so each dataset uses fewer excess connections. The configuration comments now also call out a pool_timeout value (how long an operation waits for a free connection before failing). What it does: reduces the chance of opening too many DB connections and of long, unexpected stalls. Why it matters: more predictable deployments and lower database resource pressure in multi-tenant setups.
  • Stricter chunking checks: The document chunking logic (which splits documents into smaller 'chunks' for indexing and retrieval) now performs tighter validation of chunks. What it does: catches invalid or mismatched chunks earlier and avoids silently accepting chunks that could corrupt update behavior. Why it matters: fewer mysterious rebuilds or data inconsistency when updating documents.
  • Centralized chunk stamping: Chunk objects are now stamped centrally with the chunker identifier (the marker that shows which chunking rule produced the chunk). What it does: ensures stored chunks reliably carry the origin id instead of relying on distributed stamping. Why it matters: improves correctness when the system decides whether existing chunks can be reused during incremental updates.
  • Docs: Anthropic model name updated: references to the retired model name 'claude-3-5-sonnet-20241022' were replaced with 'claude-sonnet-5-5' in documentation. What it does: prevents confusion from referencing removed models. Why it matters: keeps setup instructions accurate and reduces wasted time when configuring Anthropic providers.

Performance

  • Lower connection overhead for per-dataset Postgres engines: By reducing the pool overflow ceiling and clarifying pool timeouts, typical deployments will open fewer concurrent DB connections. Practical impact: reduced DB resource usage and lower contention on hosts that serve many datasets; extreme spikes will fail faster instead of blocking for long periods.

Bug Fixes

  • Fixes to unit tests and CI stability: Several failing unit tests were fixed and the test suite was reorganized to improve reliability (see CI changes below).
  • Chunking-related bug fixes: Tightened chunker checks and centralized stamping resolve cases where chunks without proper identifiers could cause update failures or inconsistent state.
  • Postgres pool and wait behavior fixes: Addressed issues where per-dataset pools could grow too large or block callers for long periods without failing fast.

Technical Changes

  • CI/test sharding increased: Integration tests were repartitioned (Retrieval -> 5 shards, Documents & Tasks -> 6 shards, Infrastructure -> 4 shards) and unit tests split into 4 shards in cross-OS CI. What it does: reduces test flakiness and evens out execution time per shard. Why it matters: faster, more reliable CI feedback for developers.
  • New/updated observability internals: new module files added to capture and write richer LLM call records (including follow-ups) and associated tests added to cover this functionality.
  • Internal: MCP version bumped and multiple test files adjusted/added to reflect the new behavior and to lock down regressions.
