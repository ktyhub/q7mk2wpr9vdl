#graphql-java v26.0

Esta es la versión 26.0 de graphql-java. Los aspectos más destacados se resumen a continuación; La lista completa de RP fusionados se encuentra al final.

⚠️ Cambios importantes

Los límites de complejidad de las consultas ahora se aplican de forma predeterminada

La nueva validación QueryComplexityLimits verifica maxDepth (predeterminado 100) y maxFieldsCount (predeterminado 100,000) como parte de la validación estándar. Las consultas que excedan estos límites ahora fallarán con nuevos errores de validación MaxQueryDepthExceeded / MaxQueryFieldsExceeded.

  • Establezca límites personalizados a través de GraphQLContext usando QueryComplexityLimits.KEY.
  • Desactivar completamente con QueryComplexityLimits.NONE.

Introducido en el n.° 4256.

Se cambió el filtrado de reglas de validación API

En el n.º 4228, el predicado del filtro de reglas cambió de Predicate<Class<?>> a Predicate<OperationValidationRule> en Validator.validateDocument(...) y ParseAndValidate.parseAndValidate(...). Las personas que llaman que se filtraron por clase (por ejemplo, rule -> rule != NoUnusedFragments.class) deben migrar a la enumeración (rule -> rule != OperationValidationRule.NO_UNUSED_FRAGMENTS). Se eliminaron las clases @Internal, AbstractRule y RulesVisitor.

Manejo de directivas integradas consolidadas (#4229)

  • Se eliminó DirectiveInfo. Reemplazar usos:
    • DirectiveInfo.isGraphqlSpecifiedDirective(...) → Directives.isBuiltInDirective(...)
    • DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVES → Directives.BUILT_IN_DIRECTIVES
    • DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVE_MAP → Directives.BUILT_IN_DIRECTIVES_MAP
  • El orden de las directivas ahora es consistente: las 7 directivas integradas aparecen primero, seguidas de las directivas definidas por el usuario.
  • GraphQLSchema.Builder.clearDirectives() se eliminó inicialmente y luego se volvió a agregar en el n.° 4276 con nueva semántica: borra todo additionalDirectives, pero las directivas integradas siempre se vuelven a agregar automáticamente en el momento de la compilación.

Validación de habitabilidad OneOf (#4248)

El nuevo validador rechaza los tipos de entrada OneOf que no se pueden completar con un valor finito (por ejemplo, input A @oneOf { a: A }). Los esquemas que previamente se validaron ahora podrán ser rechazados.

Validación de campos no nulos para esquemas creados con código (#4194)

Los esquemas creados con código ahora realizan la misma validación de campos obsoletos en no nulos que los creados por SDL. Los esquemas que se basan en la brecha ahora pueden no superar la validación.

GraphQLSchema.getCodeRegistry() ya no es @Nullable (#4247)

El tipo de valor devuelto se anotó incorrectamente como anulable. Las personas que llaman ahora pueden descartar cheques nulos redundantes; Las herramientas de nulidad posteriores reflejarán el cambio.

Las anotaciones de nulidad JSpecify se implementaron ampliamente

Las oleadas 2 y 3 (#4184, #4274) además de muchos RP individuales anotaron cientos de clases en graphql.analysis, graphql.execution, graphql.language, graphql.schema y otras con @NullMarked/@NullUnmarked/@Nullable. Kotlin y otras personas que llaman con reconocimiento de nulos ahora verán contratos de nulidad más estrictos; Es posible que sea necesario ajustar el código que dependía de firmas previamente permisivas.

✨ Nuevas funciones

  • GraphQLSchema.FastBuilder (#4197): un generador de esquemas más restrictivo pero ~5 veces más rápido que reduce el tiempo y la memoria para esquemas grandes.
  • Límites de complejidad de consultas (#4256): barreras de seguridad de recuento de campo/profundidad integradas en la validación (consulte los cambios importantes más arriba para el lado de cumplimiento).
  • QueryAppliedDirective sobre operaciones y documentos (#4297): las directivas aplicadas a nivel de operación/documento ahora se exponen como QueryAppliedDirective.
  • Nuevo gancho de instrumentación para resultados posteriores al manejo de excepciones (#4206, #4207): observe DataFetcherResult después de que DataFetcherExceptionHandler haya asignado excepciones a errores. ChainedInstrumentation delega correctamente el nuevo gancho.
  • Genérico DataFetcherResult.newBuilder(T data) (#4254): elimina la necesidad de testigos de tipo explícitos en el patrón común DataFetcherResult.<T>newResult().data(x)....
  • Se agregó nuevamente GraphQLSchema.Builder.clearDirectives() (#4276): útil con GraphQLSchema.transform para reescribir directivas no integradas; Los elementos integrados siempre se vuelven a agregar.
  • toString() sobre titulares de directivas AST (#4195).

⚡ Rendimiento

  • La ejecución incremental de @defer comienza antes (#4174): comienza a procesar cargas diferidas tan pronto como se detecta la primera llamada incremental en lugar de esperar a que se complete el resultado inicial.
  • Consolidación de validación (#4228): todas las reglas de validación de operaciones se ejecutan en una sola pasada OperationValidator, lo que reduce significativamente los gastos generales de validación.
  • Asignaciones reducidas en la ruta activa de ejecución (#4252):
    • Async$Many.materialisedList(): reemplazó la copia ArrayList con un contenedor Arrays.asList() de copia cero.
    • ResultPath.toStringValue — cálculo diferido; el formato de cadena solo se crea en el primer toString() (normalmente solo durante el informe de errores).
    • Nueva sobrecarga de GraphQLCodeRegistry.getDataFetcher(String, String, GraphQLFieldDefinition) que evita asignaciones de FieldCoordinates por recuperación (~54 KB/reducción de operación).
  • FastBuilder para la construcción de esquemas (#4197): consulte Nuevas funciones.
  • Se corrigió ShallowTypeRefCollector para resolver también referencias de tipo dentro de argumentos directivos aplicados y definiciones de valores de enumeración (#4288): corrección de corrección que permite usar FastBuilder en más esquemas.

🐛 Otros cambios dignos de mención

Ejecución/obtención de datos

  • Despacho de DataLoader con múltiples fragmentos @defer (#4270): soluciona un caso en el que los DataLoaders no se enviaban correctamente cuando había múltiples fragmentos diferidos en juego.
  • Condición de carrera CompletionStageSubscriber (#4296): la señal de finalización podría perderse si un CompletionStage en vuelo se resuelve al mismo tiempo. Fix está respaldado por nuevas pruebas de estrés de jcstress.
  • PropertyDataFetcher en clases no públicas (#4287): las propiedades de clases no públicas que implementan interfaces públicas (por ejemplo, TreeMap.Entry) ahora se recuperan correctamente en Java 16+ al buscar interfaces públicas.
  • ExecutableNormalizedField respeta GraphqlFieldVisibility (#4204): los API del conjunto de selección ahora usan la visibilidad configurada del esquema en lugar de ir directamente al tipo.
  • ScheduledDataLoaderRegistry corrección de "despachar todo" (#4164).
  • Delegación ChainedInstrumentation onExceptionHandled (#4207).

Visibilidad de esquema/campo

  • Correcciones para casos complejos de transformadores de visibilidad de campo y transformación de esquemas cuando las eliminaciones se suceden en cascada (#4203, #4205, #4208, #4209, #4212, #4213, #4275).
  • Regresión de tipo nulo de campos superpuestos fijada (#4291).
  • GraphQLTypeCollectingVisitor ahora atraviesa de forma recursiva referencias fuertes indirectas (#4213).
  • SchemaTraverser::depthFirst corrección de sobrecarga de firma (#4165).

Construcción / embalaje / seguridad

  • Las clases modificadas por código de bytes ya no se incluyen en los archivos JAR publicados (#4343): la anotación @Generated inyectada para los informes de cobertura se estaba filtrando en los artefactos publicados. Los JAR ahora contienen resultados impecables del compilador.
  • Detección Unicode de origen troyano/gusano de cristal (#4344): el gancho de confirmación previa y el flujo de trabajo de CI ahora rechazan caracteres BiDi/ancho cero/control peligrosos en el código fuente.
  • Compatibilidad con Windows (#4239): se eliminaron los dos puntos de los nombres de archivos performance-results/, se dividió el large-schema-5.graphqls de gran tamaño y se agregaron comprobaciones previas a la confirmación + CI.

Herramientas / DX

  • Se mejoraron los límites del tipo getDataLoader (#4180).
  • Compilación y prueba en Java 25 (#4173, #4330).
  • Muchas actualizaciones de dependencias (Reactor, Jackson, Kotlin, Groovy, Gradle, ByteBuddy, propenso a errores, etc.) en toda la versión.

graphql-java v26.0

This is the 26.0 release of graphql-java. Highlights are summarized below; the full list of merged PRs is at the end.

⚠️ Breaking Changes

Query complexity limits are now enforced by default

New QueryComplexityLimits validation checks maxDepth (default 100) and maxFieldsCount (default 100,000) as part of standard validation. Queries exceeding these limits will now fail with new MaxQueryDepthExceeded / MaxQueryFieldsExceeded validation errors.

  • Set custom limits via GraphQLContext using QueryComplexityLimits.KEY.
  • Disable entirely with QueryComplexityLimits.NONE.

Introduced in #4256.

Validation rule filtering API changed

In #4228 the rule-filter predicate changed from Predicate<Class<?>> to Predicate<OperationValidationRule> in Validator.validateDocument(...) and ParseAndValidate.parseAndValidate(...). Callers that filtered by class (e.g. rule -> rule != NoUnusedFragments.class) must migrate to the enum (rule -> rule != OperationValidationRule.NO_UNUSED_FRAGMENTS). The @Internal classes AbstractRule and RulesVisitor were removed.

Built-in directive handling consolidated (#4229)

  • DirectiveInfo was removed. Replace usages:
    • DirectiveInfo.isGraphqlSpecifiedDirective(...) → Directives.isBuiltInDirective(...)
    • DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVES → Directives.BUILT_IN_DIRECTIVES
    • DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVE_MAP → Directives.BUILT_IN_DIRECTIVES_MAP
  • Directive ordering is now consistent: all 7 built-in directives appear first, followed by user-defined directives.
  • GraphQLSchema.Builder.clearDirectives() was initially removed then re-added in #4276 with new semantics — it clears all additionalDirectives, but built-in directives are always re-added automatically at build time.

OneOf inhabitability validation (#4248)

New validator rejects OneOf input types that cannot be populated with a finite value (e.g. input A @oneOf { a: A }). Schemas that previously validated may now be rejected.

Non-null field validation for code-built schemas (#4194)

Code-built schemas now perform the same deprecated-on-non-null field validation as SDL-built ones. Schemas relying on the gap may now fail validation.

GraphQLSchema.getCodeRegistry() is no longer @Nullable (#4247)

The return type was incorrectly annotated nullable. Callers may now drop redundant null checks; downstream nullness tooling will reflect the change.

JSpecify nullability annotations rolled out broadly

Waves 2 and 3 (#4184, #4274) plus many individual PRs annotated hundreds of classes across graphql.analysis, graphql.execution, graphql.language, graphql.schema and others with @NullMarked/@NullUnmarked/@Nullable. Kotlin and other null-aware callers will now see stricter nullability contracts; code that relied on previously-permissive signatures may need adjustment.

✨ New Features

  • GraphQLSchema.FastBuilder (#4197) — a more restrictive but ~5× faster schema builder that reduces both time and memory for large schemas.
  • Query complexity limits (#4256) — depth/field-count guardrails baked into validation (see breaking changes above for the enforcement side).
  • QueryAppliedDirective on operations and documents (#4297) — directives applied at the operation/document level are now exposed as QueryAppliedDirectives.
  • New instrumentation hook for post-exception-handling results (#4206, #4207) — observe the DataFetcherResult after DataFetcherExceptionHandler has mapped exceptions to errors. ChainedInstrumentation delegates the new hook correctly.
  • Generic DataFetcherResult.newBuilder(T data) (#4254) — removes the need for explicit type witnesses on the common DataFetcherResult.<T>newResult().data(x)... pattern.
  • Re-added GraphQLSchema.Builder.clearDirectives() (#4276) — useful with GraphQLSchema.transform to rewrite non-built-in directives; built-ins are always re-added.
  • toString() on AST directives holders (#4195).

⚡ Performance

  • Incremental @defer execution starts earlier (#4174) — begins processing deferred payloads as soon as the first incremental call is detected instead of waiting for the initial result to complete.
  • Validation consolidation (#4228) — all operation validation rules run in a single OperationValidator pass, significantly cutting validation overhead.
  • Reduced allocations on the execution hot path (#4252):
    • Async$Many.materialisedList() — replaced ArrayList copy with a zero-copy Arrays.asList() wrapper.
    • ResultPath.toStringValue — lazy computation; the string form is only built on first toString() (typically only during error reporting).
    • New GraphQLCodeRegistry.getDataFetcher(String, String, GraphQLFieldDefinition) overload avoiding per-fetch FieldCoordinates allocations (~54 KB/op reduction).
  • FastBuilder for schema construction (#4197) — see New Features.
  • Fixed ShallowTypeRefCollector to also resolve type refs inside applied directive arguments and enum value definitions (#4288) — correctness fix enabling FastBuilder to be used on more schemas.

🐛 Other Noteworthy Changes

Execution / data fetching

  • DataLoader dispatch with multiple @defer fragments (#4270) — fixes a case where DataLoaders were not dispatched correctly when multiple deferred fragments were in play.
  • CompletionStageSubscriber race condition (#4296) — completion signal could be lost if an in-flight CompletionStage resolved concurrently. Fix is backed by new jcstress stress tests.
  • PropertyDataFetcher on non-public classes (#4287) — properties on non-public classes that implement public interfaces (e.g. TreeMap.Entry) now fetch correctly on Java 16+ by searching public interfaces.
  • ExecutableNormalizedField respects GraphqlFieldVisibility (#4204) — selection-set APIs now use the schema's configured visibility instead of going straight to the type.
  • ScheduledDataLoaderRegistry "dispatch all" fix (#4164).
  • ChainedInstrumentation onExceptionHandled delegation (#4207).

Schema / field visibility

  • Fixes for complex field-visibility transformer cases and schema transformation when deletions cascade (#4203, #4205, #4208, #4209, #4212, #4213, #4275).
  • Overlapping-fields null-type regression fixed (#4291).
  • GraphQLTypeCollectingVisitor now recursively traverses indirect strong references (#4213).
  • SchemaTraverser::depthFirst overload signature fix (#4165).

Build / packaging / security

  • Bytecode-modified classes no longer ship in published JARs (#4343) — the @Generated annotation injected for coverage reporting was leaking into published artifacts. JARs now contain pristine compiler output.
  • Trojan Source / glassworm Unicode detection (#4344) — pre-commit hook and CI workflow now reject dangerous BiDi/zero-width/control characters in source.
  • Windows compatibility (#4239) — removed colons from performance-results/ filenames, split the oversized large-schema-5.graphqls, added pre-commit + CI checks.

Tooling / DX

  • getDataLoader type bounds improved (#4180).
  • Build and test on Java 25 (#4173, #4330).
  • Many dependency updates (Reactor, Jackson, Kotlin, Groovy, Gradle, ByteBuddy, errorprone, etc.) across the release.
