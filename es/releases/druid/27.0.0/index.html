<a name="27.0.0-highlights-query-from-deep-storage-%28experimental%29" href="#27.0.0-highlights-query-from-deep-storage-%28experimental%29">#</a> Consulta desde almacenamiento profundo (experimental)

Druid ahora admite la consulta de segmentos que se almacenan solo en almacenamiento profundo. Cuando realiza consultas desde el almacenamiento profundo, puede consultar datos más grandes disponibles para consultas sin tener que escalar necesariamente sus procesos históricos para acomodar más datos. Para aprovechar los posibles ahorros de almacenamiento, asegúrese de configurar sus reglas de carga para no cargar todos sus segmentos en procesos históricos.

Tenga en cuenta que al menos un segmento de una fuente de datos debe cargarse en un proceso histórico para que el corredor pueda planificar la consulta. Sin embargo, puede ser cualquier segmento.

<a name="27.0.0-highlights-smart-segment-loading" href="#27.0.0-highlights-smart-segment-loading">#</a> Carga de segmentos inteligente

El Coordinador ahora es mucho más estable y fácil de usar. En el nuevo modo smartSegmentLoading, calcula dinámicamente valores para varias configuraciones que maximizan el rendimiento. El Coordinador ahora puede priorizar la carga de segmentos más recientes y segmentos que no están disponibles en absoluto sobre la carga de segmentos que ya tienen algunas réplicas cargadas en el clúster. También puede reevaluar decisiones tomadas en ejecuciones anteriores y cancelar operaciones que ya no sean necesarias. Además, las operaciones de movimiento iniciadas mediante el equilibrio de segmentos no compiten con la carga de segmentos no disponibles, lo que reduce el tiempo de reacción ante cambios en el clúster y acelera las decisiones de asignación de segmentos.

Además, los cambios de liderazgo tienen menos impacto ahora y el Coordinador no se queda estancado incluso si la reelección ocurre mientras hay una candidatura de Coordinador en progreso.

Por último, la estrategia del equilibrador cost funciona mucho mejor ahora y es capaz de mover más segmentos en una sola ejecución del Coordinador. Estas mejoras se realizaron tomando prestadas ideas de la estrategia cachingCost. Recomendamos utilizar cost en lugar de cachingCost ya que cachingCost ahora está en desuso.

Para obtener más información, consulte lo siguiente:

  • Nota de actualización para cambios de configuración relacionados con la carga de segmentos inteligentes
  • Nuevas métricas del coordinador
  • Documentación de carga de segmentos inteligentes

<a name="27.0.0-highlights-smart-segment-loading-new-query-filters" href="#27.0.0-highlights-smart-segment-loading-new-query-filters">#</a> Nuevos filtros de consulta

Druid ahora admite los siguientes filtros:

  • Igualdad: Utilizar en lugar del filtro selector. Nunca coincide con valores nulos.
  • Nulo: coincide con valores nulos. Úselo en lugar del filtro selector.
  • Rango: filtrar por rangos de valores de dimensiones. Úselo en lugar del filtro encuadernado. Nunca coincide con valores nulos

Tenga en cuenta que el planificador SQL de Druid utiliza estos nuevos filtros en lugar de sus homólogos anteriores de forma predeterminada siempre que druid.generic.useDefaultValueForNull=false o si sqlUseBoundAndSelectors se establece en falso en el contexto de consulta SQL.

Puede utilizar estos filtros para filtrar igualdad y rangos en columnas ARRAY en lugar de solo cadenas con el selector anterior y los filtros vinculados.

Para obtener más información, consulte Filtros de consulta.

<a name="27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations" href="#27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations">#</a> Nueva configuración de Broker para migraciones de esquemas SQL

Ahora puede controlar mejor cómo reacciona Druid a los cambios de esquema entre segmentos. Esto puede hacer que las consultas sean más resistentes cuando los segmentos más nuevos introducen tipos diferentes, como si una columna anteriormente contenía valores LONG y los segmentos más nuevos contienen STRING.

Utilice la nueva configuración de Broker, druid.sql.planner.metadataColumnTypeMergePolicy, para controlar cómo se calculan los tipos de columnas para el esquema de tabla SQL cuando se enfrentan diferencias entre segmentos.

Configúrelo en uno de los siguientes:

  • leastRestrictive: el esquema solo se actualiza una vez que todos los segmentos se reindexan al nuevo tipo.
  • latestInterval: el esquema SQL se actualiza tan pronto como el primer trabajo con el nuevo esquema publica segmentos en el último intervalo de tiempo de los datos.

leastRestrictive puede tener un mejor comportamiento en el tiempo de consulta y elimina algunos errores de tiempo de consulta que pueden ocurrir al usar latestInterval.

<a name="27.0.0-highlights-smart-segment-loading" href="#27.0.0-highlights-smart-segment-loading">#</a> Smart segment loading

The Coordinator is now much more stable and user-friendly. In the new smartSegmentLoading mode, it dynamically computes values for several configs which maximize performance.

The Coordinator can now prioritize load of more recent segments and segments that are completely unavailable over load of segments that already have some replicas loaded in the cluster. It can also re-evaluate decisions taken in previous runs and cancel operations that are not needed anymore. Moreoever, move operations started by segment balancing do not compete with the load of unavailable segments thus reducing the reaction time for changes in the cluster and speeding up segment assignment decisions.

Additionally, leadership changes have less impact now, and the Coordinator doesn't get stuck even if re-election happens while a Coordinator run is in progress.

Lastly, the cost balancer strategy performs much better now and is capable of moving more segments in a single Coordinator run. These improvements were made by borrowing ideas from the cachingCost strategy. We recommend using cost instead of cachingCost since cachingCost is now deprecated.

For more information, see the following:

  • Upgrade note for config changes related to smart segment loading
  • New coordinator metrics
  • Smart segment loading documentation

You can now better control how Druid reacts to schema changes between segments. This can make querying more resilient when newer segments introduce different types, such as if a column previously contained LONG values and newer segments contain STRING.

Use the new Broker configuration, druid.sql.planner.metadataColumnTypeMergePolicy to control how column types are computed for the SQL table schema when faced with differences between segments.

Set it to one of the following:

  • leastRestrictive: the schema only updates once all segments are reindexed to the new type.
  • latestInterval: the SQL schema gets updated as soon as the first job with the new schema publishes segments in the latest time interval of the data.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated">#</a> Hadoop 2 deprecated

Many of the important dependent libraries that Druid uses no longer support Hadoop 2. In order for Druid to stay current and have pathways to mitigate security vulnerabilities, the community has decided to deprecate support for Hadoop 2.x releases starting this release. Starting with Druid 28.x, Hadoop 3.x is the only supported Hadoop version.

Consider migrating to SQL-based ingestion or native ingestion if you are using Hadoop 2.x for ingestion today. If migrating to Druid ingestion is not possible, plan to upgrade your Hadoop infrastructure before upgrading to the next Druid release.

Please note that druid 27 is not compatible with Hadoop 2. You have to upgrade your Hadoop cluster to 3.x before upgrading to 27.0.0. Or you can build a hadoop 2 compatible distribution by explicitly selecting Hadoop 2 profile from druid 27 source artifact.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion">#</a> Worker input bytes for SQL-based ingestion

The maximum input bytes for each worker for SQL-based ingestion is now 512 MiB (previously 10 GiB).

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60cachingcost%60-segment-balancing-strategy-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60cachingcost%60-segment-balancing-strategy-deprecated">#</a> cachingCost segment balancing strategy deprecated

The cachingCost strategy has been deprecated and will be removed in future releases. Use an alternate segment balancing strategy instead, such as cost.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes">#</a> Segment loading config changes

The following segment related configs are now deprecated and will be removed in future releases:

  • maxSegmentsInNodeLoadingQueue
  • maxSegmentsToMove
  • replicationThrottleLimit
  • useRoundRobinSegmentAssignment
  • replicantLifetime
  • maxNonPrimaryReplicantsToLoad
  • decommissioningMaxPercentOfMaxSegmentsToMove

Use smartSegmentLoading mode instead, which calculates values for these variables automatically.

Additionally, the defaults for the following Coordinator dynamic configs have changed:

  • maxsegmentsInNodeLoadingQueue : 500, previously 100
  • maxSegmentsToMove: 100, previously 5
  • replicationThrottleLimit: 500, previously 10

These new defaults can improve performance for most use cases.

The following Coordinator dynamic configs have been removed:

  • emitBalancingStats: Stats for errors encountered while balancing will always be emitted. Other debugging stats will not be emitted but can be logged by setting the appropriate debugDimensions.
