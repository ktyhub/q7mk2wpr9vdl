druida druida-28.0.0

Apache Druid 28.0.0 contiene más de 420 funciones nuevas, correcciones de errores, mejoras de rendimiento, mejoras de documentación y cobertura de pruebas adicionales de 57 contribuyentes.

Consulte el conjunto completo de cambios para obtener detalles adicionales, incluidas correcciones de errores.

Revise las notas de actualización y los cambios incompatibles antes de actualizar a Druid 28.0.0.

<a name="28.0.0-important-changes-and-deprecations" href="#28.0.0-important-changes-and-deprecations">#</a> Funciones, cambios y obsolescencias importantes

En Druid 28.0.0, hemos realizado mejoras sustanciales en las consultas para que el sistema sea más compatible con ANSI SQL. Esto incluye cambios en el manejo de valores NULL y booleanos, así como en la lógica booleana. Al mismo tiempo, la biblioteca Apache Calcite se actualizó a la última versión. Si bien hemos documentado cambios conocidos en el comportamiento de las consultas, lea atentamente la sección notas de actualización. Pruebe su aplicación antes de implementarla en escenarios de producción amplios mientras monitorea de cerca el estado de la consulta.

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility" href="#28.0.0-important-changes-and-deprecations-sql-compatibility">#</a> Compatibilidad SQL

Druid continúa haciendo que la ejecución de consultas SQL sea más consistente con el comportamiento de SQL estándar. Sin embargo, hay indicadores de funciones disponibles para restaurar el comportamiento anterior si es necesario.

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-three-valued-logic" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-three-valued-logic">#</a> Lógica de tres valores

Los filtros nativos de Druid ahora observan SQL lógica de tres valores (true, false o unknown) en lugar de la lógica clásica de dos estados de Druid de forma predeterminada, cuando se aplican las siguientes configuraciones predeterminadas:

  • druid.generic.useThreeValueLogicForNativeFilters = true
  • druid.expressions.useStrictBooleans = true
  • druid.generic.useDefaultValueForNull = false

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-strict-booleans" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-strict-booleans">#</a> Booleanos estrictos

druid.expressions.useStrictBooleans ahora está habilitado de forma predeterminada. Druid ahora maneja valores booleanos estrictamente usando 1 (verdadero) o 0 (falso). Anteriormente, verdadero y falso podían representarse como true y false, así como 1 y 0, respectivamente. Además, Druid ahora devuelve un valor nulo para comparaciones booleanas como True && NULL.

Si no configura explícitamente esta propiedad en runtime.properties, los clústeres ahora usan tipos LONG para cualquier valor booleano ingerido y en la salida de funciones booleanas para transformaciones y operaciones en tiempo de consulta. Para obtener más información, consulte compatibilidad SQL en las notas de actualización.

#14734

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-null-handling" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-null-handling">#</a> manejo de NULL

druid.generic.useDefaultValueForNull ahora está deshabilitado de forma predeterminada. Druid ahora diferencia entre registros vacíos y registros nulos. Anteriormente, Druid podía tratar los registros vacíos como vacíos o nulos. Para obtener más información, consulte compatibilidad SQL en las notas de actualización.

<a name="28.0.0-important-changes-and-deprecations-sql-planner-improvements" href="#28.0.0-important-changes-and-deprecations-sql-planner-improvements">#</a> mejoras en el planificador SQL

Druid utiliza Apache Calcite para la planificación y optimización de SQL. A partir de Druid 28.0.0, la versión Calcite se actualizó de 1.21 a 1.35. Esta actualización trae muchas correcciones de errores en la planificación SQL de Calcite.

<a name="28.0.0-important-changes-and-deprecations-sql-planner-improvements-dynamic-parameters" href="#28.0.0-important-changes-and-deprecations-sql-planner-improvements-dynamic-parameters">#</a> Parámetros dinámicos

Como parte de la actualización de Calcite, el comportamiento de la inferencia de tipos para parámetros dinámicos ha cambiado. Para evitar problemas de interferencia de tipos, CAST explícitamente todos los parámetros dinámicos como un tipo de datos específico en consultas SQL. Por ejemplo, utilice:

SELECT (1 * CAST (? as DOUBLE))/2 as tmp

No utilice:

SELECT (1 * ?)/2 as tmp

<a name="28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage" href="#28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage">#</a> Consulta asíncrona y consulta desde almacenamiento profundo

Consulta desde almacenamiento profundo ya no es una función experimental. Cuando realiza consultas desde el almacenamiento profundo, hay más datos disponibles para consultas sin tener que escalar sus servicios históricos para acomodar más datos. Para beneficiarse del ahorro de espacio que ofrece la consulta desde el almacenamiento profundo, configure sus reglas de carga para descargar datos de sus servicios históricos.

<a name="28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-support-for-multiple-result-formats" href="#28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-support-for-multiple-result-formats">#</a> Compatibilidad con múltiples formatos de resultados

La consulta desde el almacenamiento profundo ahora admite múltiples formatos de resultados. Anteriormente, el terminal /druid/v2/sql/statements/ solo admitía resultados en el formato object. Ahora, los resultados se pueden escribir en cualquier formato especificado en el parámetro resultFormat. Para obtener más información sobre los parámetros de resultados admitidos por Druid SQL API, consulte Respuestas.

<a name="28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-broadened-access-for-queries-from-deep-storage" href="#28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-broadened-access-for-queries-from-deep-storage">#</a> Acceso ampliado para consultas desde almacenamiento profundo

Los usuarios con el permiso STATE pueden acceder a los resultados de la consulta.

<a name="28.0.0-important-changes-and-deprecations-ingest-from-multiple-kafka-topics-to-a-single-datasource" href="#28.0.0-important-changes-and-deprecations-ingest-from-multiple-kafka-topics-to-a-single-datasource">#</a> Ingesta de varios temas de Kafka en una única fuente de datos

Ahora puede ingerir datos en streaming desde varios temas de Kafka a una fuente de datos utilizando un único supervisor. Configure los temas para la especificación del supervisor utilizando un patrón de expresiones regulares como valor para topicPattern en la configuración de IO. Si agrega nuevos temas a Kafka que coinciden con la expresión regular, Druid automáticamente comienza a ingerir esos nuevos temas.

Si habilita la ingesta de múltiples temas para una fuente de datos, la degradación hará que el supervisor falle. Para obtener más información, consulte [Detener a los supervisores que ingieren varios temas de Kafka antes de degradarlos] (#detener a los supervisores que ingieren de múltiples temas-kafka antes de degradar).

<a name="28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening" href="#28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening">#</a> SQL UNNEST y aplanamiento de ingesta

La función UNNEST ya no es experimental.

Druid ahora admite UNNEST en la ingesta por lotes basada en SQL y consultas desde almacenamiento profundo, para que pueda aplanar matrices fácilmente. Para obtener más información, consulte UNNEST y Unnest matrices dentro de una columna.

Ya no es necesario incluir el parámetro de contexto enableUnnest: true para usar UNNEST.

<a name="28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening-recommended-syntax-for-sql-unnest" href="#28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening-recommended-syntax-for-sql-unnest">#</a> Sintaxis recomendada para SQL UNNEST

La sintaxis recomendada para SQL UNNEST ha cambiado. Recomendamos utilizar CROSS JOIN en lugar de comas para la mayoría de las consultas para evitar problemas con la precedencia. Por ejemplo, utilice:

SELECT column_alias_name1 FROM datasource CROSS JOIN UNNEST(source_expression1) AS table_alias_name1(column_alias_name1) CROSS JOIN UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

No utilice:

SELECT column_alias_name FROM datasource, UNNEST(source_expression1) AS table_alias_name1(column_alias_name1), UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

<a name="28.0.0-important-changes-and-deprecations-window-functions-%28experimental%29" href="#28.0.0-important-changes-and-deprecations-window-functions-%28experimental%29">#</a> Funciones de ventana (experimental)

Puede utilizar funciones de ventana en Apache Druid para producir valores basados ​​en la relación de una fila dentro de una ventana de filas con las otras filas dentro de la misma ventana. Una ventana es un grupo de filas relacionadas dentro de un conjunto de resultados. Por ejemplo, filas con el mismo valor para una dimensión específica.

Habilite las funciones de ventana en su consulta con el parámetro de contexto enableWindowing: true.

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29">#</a> Agregar y reemplazar simultáneamente (experimental)

Druid 28.0.0 agrega soporte experimental para agregar y reemplazar simultáneamente. Esta característica le permite reemplazar de forma segura los datos existentes en un intervalo de una fuente de datos mientras se agregan datos nuevos a ese intervalo. Una de las aplicaciones más comunes de esto es agregar nuevos datos a un intervalo mientras la compactación de ese intervalo ya está en progreso. Para obtener más información, consulte Agregar y reemplazar simultáneamente.

El bloqueo de segmentos quedará obsoleto y se eliminará en favor de la adición y sustitución simultáneas, cuyo diseño es mucho más sencillo. Con la adición y sustitución simultáneas, Druid no bloquea los trabajos de compactación debido a la ingesta activa en tiempo real.

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-task-locks-for-append-and-replace-batch-ingestion-jobs" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-task-locks-for-append-and-replace-batch-ingestion-jobs">#</a> Bloqueos de tareas para agregar y reemplazar trabajos de ingesta por lotes

Agregar trabajos de ingesta por lotes ahora puede compartir bloqueos. Esto le permite ejecutar varios trabajos de ingesta por lotes de anexos al mismo tiempo interno. Reemplazar trabajos de ingesta por lotes aún requiere un bloqueo exclusivo. Esto significa que puede ejecutar varios trabajos de ingesta por lotes de adición y un trabajo de ingesta por lotes de reemplazo durante un intervalo determinado.

#14407

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-streaming-ingestion-with-concurrent-replace" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-streaming-ingestion-with-concurrent-replace">#</a> Ingestión de streaming con reemplazo concurrente

Los trabajos de streaming que se leen desde Kafka y Kinesis con bloqueos APPEND ahora se pueden ingerir simultáneamente con la compactación que se ejecuta con bloqueos REPLACE. La granularidad del segmento del trabajo de transmisión debe ser igual o más fina que la del trabajo de reemplazo simultáneo.

El tipo de columna json ahora equivale a usar auto en las especificaciones de dimensiones de ingesta por lotes basadas en JSON. Actualice sus especificaciones de ingesta a json para aprovechar las características y funcionalidades de auto, incluidas las siguientes:

<a name="28.0.0-functional-area-and-related-changes-ingestion-sql-based-ingestion-ability-to-ingest-array-types" href="#28.0.0-functional-area-and-related-changes-ingestion-sql-based-ingestion-ability-to-ingest-array-types">#</a> Capacidad para ingerir tipos ARRAY

La ingesta basada en SQL ahora admite el almacenamiento de valores escritos en ARRAY en columnas escritas en ARRAY, así como el almacenamiento de matrices escritas tanto VARCHAR como numéricas. Anteriormente, el motor de tareas MSQ almacenaba valores escritos en ARRAY como dimensiones de valores múltiples en lugar de columnas escritas en ARRAY.

El motor de tareas MSQ ahora incluye el parámetro de contexto de consulta arrayIngestMode, que controla cómo Los tipos ARRAY se almacenan en segmentos de Druida. Establezca el parámetro de contexto de consulta arrayIngestMode en array para ingerir tipos ARRAY.

En Druid 28.0.0, el modo predeterminado para arrayIngestMode es mvd para compatibilidad con versiones anteriores, que solo admite matrices escritas en VARCHAR y las almacena como dimensiones de valores múltiples. Este valor predeterminado está sujeto a cambios en versiones futuras.

Para obtener información sobre cómo migrar al nuevo comportamiento, consulte las [Opciones de ingesta para columnas tipo ARRAY en las notas de actualización] (#opciones-ingestión-para-columnas-tipo-array). Para obtener información sobre el comportamiento de inserción, filtrado y agrupación de columnas con tipo ARRAY, consulte Columnas de matriz.

<a name="28.0.0-functional-area-and-related-changes-ingestion-sql-based-ingestion-numeric-array-type-support" href="#28.0.0-functional-area-and-related-changes-ingestion-sql-based-ingestion-numeric-array-type-support">#</a> Compatibilidad con tipos de matrices numéricas

Los marcos basados en filas y, por extensión, el motor de tareas MSQ ahora admiten tipos de matrices numéricas. Esto significa que todas las consultas que consumen o producen matrices funcionan con el motor de tareas MSQ. Las matrices numéricas también se pueden ingerir mediante la ingestión basada en SQL con MSQ. Por ejemplo, consultas como SELECT [1, 2] son válidas ahora porque consumen una matriz numérica en lugar de fallar con una excepción de tipo de columna no admitida.

Las nuevas funciones de consulta nativas y SQL le permiten evaluar si dos expresiones son distintas o no. Las expresiones son distintas si tienen valores diferentes o si uno de ellos es NULL. Las expresiones no son distintas si sus valores son iguales o si ambos son NULL.

Ahora puede configurar la barandilla maxSubqueryBytes en una de las siguientes opciones:

  • disabled: Configuración predeterminada. Druid no aplica la barrera de seguridad en torno al número de bytes que puede generar una subconsulta.

  • auto: Druid calcula la cantidad de memoria a utilizar para la materialización de resultados como una porción de la memoria fija del heap.
    En el contexto de la consulta, Druid usa la siguiente fórmula para determinar el límite superior en la cantidad de bytes que una subconsulta puede generar:

    ((total JVM space - memory occupied by lookups) * 0.5) / maximum queries that the system can handle concurrently

  • ENTERO: El número de bytes que se utilizarán para materializar los resultados de la subconsulta. Establezca un valor específico si comprende los patrones de consulta y desea optimizar el uso de la memoria.
    Por ejemplo, establezca el parámetro maxSubqueryBytes en 300000000 (300 * 1000 * 1000) para un límite de 300 MB. Establezca el parámetro maxSubqueryBytes en 314572800 (300 * 1024 * 1024) para un límite de 300 MiB.

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-recommended-syntax-for-sql-unnest" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-recommended-syntax-for-sql-unnest">#</a> Sintaxis recomendada para SQL UNNEST

La sintaxis recomendada para SQL UNNEST ha cambiado. Recomendamos utilizar CROSS JOIN en lugar de comas para la mayoría de las consultas para evitar problemas con la precedencia. Por ejemplo, utilice:

SELECT column_alias_name1 FROM datasource CROSS JOIN UNNEST(source_expression1) AS table_alias_name1(column_alias_name1) CROSS JOIN UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

No utilice:

SELECT column_alias_name FROM datasource, UNNEST(source_expression1) AS table_alias_name1(column_alias_name1), UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-dynamic-parameters" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-dynamic-parameters">#</a> Parámetros dinámicos

La versión de Apache Calcite se actualizó de 1.21 a 1.35. Como parte de la actualización de Calcite, el comportamiento de la inferencia de tipos para parámetros dinámicos ha cambiado. Para evitar problemas de interferencia de tipos, CAST explícitamente todos los parámetros dinámicos como un tipo de datos específico en consultas SQL. Por ejemplo, utilice:

SELECT (1 * CAST (? as DOUBLE))/2 as tmp

No utilice:

SELECT (1 * ?)/2 as tmp

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-nested-column-format" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-nested-column-format">#</a> Formato de columna anidada

Las columnas de tipo json creadas con Druid 28.0.0 no son compatibles con versiones anteriores de Druid anteriores a 26.0.0. Si está actualizando desde una versión anterior a Druid 26.0.0 y utiliza columnas json, actualice a Druid 26.0.0 antes de actualizar a Druid 28.0.0. Además, para degradar a una versión anterior a Druid 26.0.0, cualquier segmento nuevo creado en Druid 28.0.0 se debe volver a ingerir utilizando Druid 26.0.0 o 27.0.0 antes de realizar una degradación adicional.

Al actualizar desde una versión anterior, puede continuar escribiendo columnas anidadas en un formato compatible con versiones anteriores (versión 4).

En un trabajo de ingesta por lotes clásico, incluya formatVersion en la lista dimensions de la propiedad dimensionsSpec. Por ejemplo:

      "dimensionsSpec": {
        "dimensions": [
          "product",
          "department",
          {
            "type": "json",
            "name": "shipTo",
            "formatVersion": 4
          }
        ]
      },

Para configurar la versión de columna anidada predeterminada, configure la versión de formato deseada en las propiedades comunes del tiempo de ejecución. Por ejemplo:

druid.indexing.formats.nestedColumnFormatVersion=4

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-sql-compatibility" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-sql-compatibility">#</a> Compatibilidad SQL

A partir de Druid 28.0.0, la forma predeterminada en que Druid trata los valores nulos y booleanos ha cambiado.

Para valores nulos, Druid ahora diferencia entre una cadena vacía y un registro sin datos, así como entre un registro numérico vacío y 0.
Puede volver al comportamiento anterior configurando druid.generic.useDefaultValueForNull en true.

Esta propiedad afecta tanto al almacenamiento como a las consultas, y debe configurarse en todos los tipos de servicios de Druid para que estén disponibles tanto en el momento de la ingesta como en el momento de la consulta. Al revertir esta configuración al valor anterior se restaura el comportamiento anterior sin reingestión.

Para valores booleanos, Druid ahora usa estrictamente 1 (verdadero) o 0 (falso). Anteriormente, verdadero y falso podían representarse como true y false, así como 1 y 0, respectivamente. Además, Druid ahora devuelve un valor nulo para comparaciones booleanas como True && NULL.

Puede volver al comportamiento anterior configurando druid.expressions.useStrictBooleans en false. Esta propiedad afecta tanto al almacenamiento como a las consultas, y debe configurarse en todos los tipos de servicios de Druid para que estén disponibles tanto en el momento de la ingesta como en el momento de la consulta. Al revertir esta configuración al valor anterior se restaura el comportamiento anterior sin reingestión.

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-ingestion-options-for-array-typed-columns" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-ingestion-options-for-array-typed-columns">#</a> Opciones de ingesta para columnas con tipo ARRAY

A partir de Druid 28.0.0, el motor de tareas MSQ puede detectar e ingerir matrices como columnas escritas en ARRAY cuando configura el parámetro de contexto de consulta arrayIngestMode en array. El parámetro de contexto arrayIngestMode controla cómo se almacenan los valores de tipo ARRAY en los segmentos de Druid.

Cuando configura arrayIngestMode en array (recomendado para el cumplimiento de SQL), el motor de tareas MSQ almacena todos los valores escritos en ARRAY en columnas escritas en ARRAY y admite el almacenamiento de matrices escritas tanto VARCHAR como numéricas.

Para compatibilidad con versiones anteriores, arrayIngestMode por defecto es mvd. Cuando "arrayIngestMode":"mvd", Druid solo admite matrices escritas en VARCHAR y las almacena como [columnas de cadena de valores múltiples] (https://druid.apache.org/docs/latest/querying/multi-value-dimensions).

Cuando configura arrayIngestMode en none, Druid genera una excepción al intentar almacenar cualquier tipo de matrices.

Para obtener más información sobre cómo ingerir columnas escritas ARRAY con ingestión basada en SQL, consulte tipos de datos SQL y columnas de matriz.

<a name="28.0.0-important-changes-and-deprecations" href="#28.0.0-important-changes-and-deprecations">#</a> Important features, changes, and deprecations

In Druid 28.0.0, we have made substantial improvements to querying to make the system more ANSI SQL compatible. This includes changes in handling NULL and boolean values as well as boolean logic. At the same time, the Apache Calcite library has been upgraded to the latest version. While we have documented known query behavior changes, please read the upgrade notes section carefully. Test your application before rolling out to broad production scenarios while closely monitoring the query status.

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility" href="#28.0.0-important-changes-and-deprecations-sql-compatibility">#</a> SQL compatibility

Druid continues to make SQL query execution more consistent with how standard SQL behaves. However, there are feature flags available to restore the old behavior if needed.

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-three-valued-logic" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-three-valued-logic">#</a> Three-valued logic

Druid native filters now observe SQL three-valued logic (true, false, or unknown) instead of Druid's classic two-state logic by default, when the following default settings apply:

  • druid.generic.useThreeValueLogicForNativeFilters = true
  • druid.expressions.useStrictBooleans = true
  • druid.generic.useDefaultValueForNull = false

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-strict-booleans" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-strict-booleans">#</a> Strict booleans

druid.expressions.useStrictBooleans is now enabled by default. Druid now handles booleans strictly using 1 (true) or 0 (false). Previously, true and false could be represented either as true and false as well as 1 and 0, respectively. In addition, Druid now returns a null value for Boolean comparisons like True && NULL.

If you don't explicitly configure this property in runtime.properties, clusters now use LONG types for any ingested boolean values and in the output of boolean functions for transformations and query time operations. For more information, see SQL compatibility in the upgrade notes.

Druid uses Apache Calcite for SQL planning and optimization. Starting in Druid 28.0.0, the Calcite version has been upgraded from 1.21 to 1.35. This upgrade brings in many bug fixes in SQL planning from Calcite.

<a name="28.0.0-important-changes-and-deprecations-sql-planner-improvements-dynamic-parameters" href="#28.0.0-important-changes-and-deprecations-sql-planner-improvements-dynamic-parameters">#</a> Dynamic parameters

As part of the Calcite upgrade, the behavior of type inference for dynamic parameters has changed. To avoid any type interference issues, explicitly CAST all dynamic parameters as a specific data type in SQL queries. For example, use:

SELECT (1 * CAST (? as DOUBLE))/2 as tmp

Do not use:

SELECT (1 * ?)/2 as tmp

<a name="28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage" href="#28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage">#</a> Async query and query from deep storage

Query from deep storage is no longer an experimental feature. When you query from deep storage, more data is available for queries without having to scale your Historical services to accommodate more data. To benefit from the space saving that query from deep storage offers, configure your load rules to unload data from your Historical services.

<a name="28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-support-for-multiple-result-formats" href="#28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-support-for-multiple-result-formats">#</a> Support for multiple result formats

Query from deep storage now supports multiple result formats. Previously, the /druid/v2/sql/statements/ endpoint only supported results in the object format. Now, results can be written in any format specified in the resultFormat parameter. For more information on result parameters supported by the Druid SQL API, see Responses.

<a name="28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening-recommended-syntax-for-sql-unnest" href="#28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening-recommended-syntax-for-sql-unnest">#</a> Recommended syntax for SQL UNNEST

The recommended syntax for SQL UNNEST has changed. We recommend using CROSS JOIN instead of commas for most queries to prevent issues with precedence. For example, use:

SELECT column_alias_name1 FROM datasource CROSS JOIN UNNEST(source_expression1) AS table_alias_name1(column_alias_name1) CROSS JOIN UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

Do not use:

SELECT column_alias_name FROM datasource, UNNEST(source_expression1) AS table_alias_name1(column_alias_name1), UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

<a name="28.0.0-important-changes-and-deprecations-window-functions-%28experimental%29" href="#28.0.0-important-changes-and-deprecations-window-functions-%28experimental%29">#</a> Window functions (experimental)

You can use window functions in Apache Druid to produce values based upon the relationship of one row within a window of rows to the other rows within the same window. A window is a group of related rows within a result set. For example, rows with the same value for a specific dimension.

Enable window functions in your query with the enableWindowing: true context parameter.

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29">#</a> Concurrent append and replace (experimental)

Druid 28.0.0 adds experimental support for concurrent append and replace. This feature allows you to safely replace the existing data in an interval of a datasource while new data is being appended to that interval. One of the most common applications of this is appending new data to an interval while compaction of that interval is already in progress. For more information, see Concurrent append and replace.

Segment locking will be deprecated and removed in favor of concurrent append and replace that is much simpler in design. With concurrent append and replace, Druid doesn't lock compaction jobs out because of active realtime ingestion.

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-task-locks-for-append-and-replace-batch-ingestion-jobs" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-task-locks-for-append-and-replace-batch-ingestion-jobs">#</a> Task locks for append and replace batch ingestion jobs

Append batch ingestion jobs can now share locks. This allows you to run multiple append batch ingestion jobs against the same time internal. Replace batch ingestion jobs still require an exclusive lock. This means you can run multiple append batch ingestion jobs and one replace batch ingestion job for a given interval.

#14407

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-streaming-ingestion-with-concurrent-replace" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-streaming-ingestion-with-concurrent-replace">#</a> Streaming ingestion with concurrent replace

Streaming jobs reading from Kafka and Kinesis with APPEND locks can now ingest concurrently with compaction running with REPLACE locks. The segment granularity of the streaming job must be equal to or finer than that of the concurrent replace job.

<a name="28.0.0-functional-area-and-related-changes-querying-functions-for-evaluating-distinctness" href="#28.0.0-functional-area-and-related-changes-querying-functions-for-evaluating-distinctness">#</a> Functions for evaluating distinctness

New SQL and native query functions allow you to evaluate whether two expressions are distinct or not distinct. Expressions are distinct if they have different values or if one of them is NULL. Expressions are not distinct if their values are the same or if both of them are NULL.

Because the functions treat NULLs as known values when used as a comparison operator, they always return true or false even if one or both expressions are NULL.

The following table shows the difference in behavior between the equals sign (=) and IS [NOT] DISTINCT FROM:

| A | B | A=B | A IS NOT DISTINCT FROM B| |---|---|-----|-------------------------| | 0 | 0 | true | true | | 0 | 1 | false | false | | 0 | null | unknown | false | | null | null | unknown | true |

<a name="28.0.0-functional-area-and-related-changes-querying-improved-subquery-guardrail" href="#28.0.0-functional-area-and-related-changes-querying-improved-subquery-guardrail">#</a> Improved subquery guardrail

You can now set the maxSubqueryBytes guardrail to one of the following:

  • disabled: Default setting. Druid doesn't apply the guardrail around the number of bytes a subquery can generate.

  • auto: Druid calculates the amount of memory to use for the materialization of results as a portion of the fixed memory of the heap.
    In the query context, Druid uses the following formula to determine the upper limit on the number of bytes a subquery can generate:

    ((total JVM space - memory occupied by lookups) * 0.5) / maximum queries that the system can handle concurrently

  • INTEGER: The number of bytes to use for materializing subquery results. Set a specific value if you understand the query patterns and want to optimize memory usage.
    For example, set the maxSubqueryBytes parameter to 300000000 (300 * 1000 * 1000) for a 300 MB limit. Set the maxSubqueryBytes parameter to 314572800 (300 * 1024 * 1024) for a 300 MiB limit.

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-recommended-syntax-for-sql-unnest" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-recommended-syntax-for-sql-unnest">#</a> Recommended syntax for SQL UNNEST

The recommended syntax for SQL UNNEST has changed. We recommend using CROSS JOIN instead of commas for most queries to prevent issues with precedence. For example, use:

SELECT column_alias_name1 FROM datasource CROSS JOIN UNNEST(source_expression1) AS table_alias_name1(column_alias_name1) CROSS JOIN UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

Do not use:

SELECT column_alias_name FROM datasource, UNNEST(source_expression1) AS table_alias_name1(column_alias_name1), UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-dynamic-parameters" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-dynamic-parameters">#</a> Dynamic parameters

The Apache Calcite version has been upgraded from 1.21 to 1.35. As part of the Calcite upgrade, the behavior of type inference for dynamic parameters has changed. To avoid any type interference issues, explicitly CAST all dynamic parameters as a specific data type in SQL queries. For example, use:

SELECT (1 * CAST (? as DOUBLE))/2 as tmp

Do not use:

SELECT (1 * ?)/2 as tmp

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-nested-column-format" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-nested-column-format">#</a> Nested column format

json type columns created with Druid 28.0.0 are not backwards compatible with Druid versions older than 26.0.0. If you are upgrading from a version prior to Druid 26.0.0 and you use json columns, upgrade to Druid 26.0.0 before you upgrade to Druid 28.0.0. Additionally, to downgrade to a version older than Druid 26.0.0, any new segments created in Druid 28.0.0 should be re-ingested using Druid 26.0.0 or 27.0.0 prior to further downgrading.

When upgrading from a previous version, you can continue to write nested columns in a backwards compatible format (version 4).

In a classic batch ingestion job, include formatVersion in the dimensions list of the dimensionsSpec property. For example:

      "dimensionsSpec": {
        "dimensions": [
          "product",
          "department",
          {
            "type": "json",
            "name": "shipTo",
            "formatVersion": 4
          }
        ]
      },

To set the default nested column version, set the desired format version in the common runtime properties. For example:

druid.indexing.formats.nestedColumnFormatVersion=4

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-sql-compatibility" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-sql-compatibility">#</a> SQL compatibility

Starting with Druid 28.0.0, the default way Druid treats nulls and booleans has changed.

For nulls, Druid now differentiates between an empty string and a record with no data as well as between an empty numerical record and 0.
You can revert to the previous behavior by setting druid.generic.useDefaultValueForNull to true.

This property affects both storage and querying, and must be set on all Druid service types to be available at both ingestion time and query time. Reverting this setting to the old value restores the previous behavior without reingestion.

For booleans, Druid now strictly uses 1 (true) or 0 (false). Previously, true and false could be represented either as true and false as well as 1 and 0, respectively. In addition, Druid now returns a null value for boolean comparisons like True && NULL.

You can revert to the previous behavior by setting druid.expressions.useStrictBooleans to false. This property affects both storage and querying, and must be set on all Druid service types to be available at both ingestion time and query time. Reverting this setting to the old value restores the previous behavior without reingestion.

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-ingestion-options-for-array-typed-columns" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-ingestion-options-for-array-typed-columns">#</a> Ingestion options for ARRAY typed columns

Starting with Druid 28.0.0, the MSQ task engine can detect and ingest arrays as ARRAY typed columns when you set the query context parameter arrayIngestMode to array. The arrayIngestMode context parameter controls how ARRAY type values are stored in Druid segments.

When you set arrayIngestMode to array (recommended for SQL compliance), the MSQ task engine stores all ARRAY typed values in ARRAY typed columns and supports storing both VARCHAR and numeric typed arrays.

For backwards compatibility, arrayIngestMode defaults to mvd. When "arrayIngestMode":"mvd", Druid only supports VARCHAR typed arrays and stores them as multi-value string columns.

When you set arrayIngestMode to none, Druid throws an exception when trying to store any type of arrays.

For more information on how to ingest ARRAY typed columns with SQL-based ingestion, see SQL data types and Array columns.
