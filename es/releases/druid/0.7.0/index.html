druida druida-0.7.0

Actualización a Druid 0.7.0 – Cosas a tener en cuenta

  • Nueva especificación de ingesta Druid 0.7.0 requiere un nuevo formato de especificación de ingesta. Druid 0.6.172 admite formatos de ingesta tanto antiguos como nuevos y tiene scripts para convertir del formato antiguo al nuevo. Este script se puede ejecutar con 'tools convertSpec' usando el mismo Main usado para ejecutar los nodos Druid. Puede actualizar su clúster Druid a 0.6.172, actualizar sus especificaciones de ingesta al nuevo formato y luego actualizar a Druid 0.7.0. Si actualiza su clúster a Druid 0.7.0 directamente, asegúrese de que su canal de ingesta en tiempo real comprenda la nueva especificación.
  • MySQL ya no es el almacenamiento de metadatos predeterminado Druid ahora incorpora de forma predeterminada Apache Derby, que se eligió principalmente con fines de capacidad de prueba. Sin embargo, no recomendamos utilizar Derby en producción. Para cualquier otra cosa que no sea realizar pruebas, utilice el almacenamiento de metadatos MySQL o PostgreSQL. Los parámetros de configuración para el almacenamiento de metadatos cambiaron de nombre de druid.db a druid.metadata.storage y se requiere un druid.metadata.storage.type=<mysql|postgresql> adicional para usar cualquier cosa que no sea Derby. La herramienta convertProps puede ayudarle a convertir todas las propiedades 0.6.x en propiedades 0.7.
  • Druida ahora distingue entre mayúsculas y minúsculas Los nombres de las columnas de druida ahora distinguen entre mayúsculas y minúsculas. Anteriormente intentamos no distinguir entre mayúsculas y minúsculas para las consultas y preservarlas para los datos, pero decidimos hacer este cambio ya que había numerosos errores relacionados con varios problemas de mayúsculas y minúsculas. Si está actualizando desde la versión 0.6.x:
    1. Asegúrese de que las mayúsculas y minúsculas de las columnas en sus consultas coincidan con las mayúsculas y minúsculas de los nombres de las columnas en sus datos y actualice sus consultas en consecuencia.
    2. Una cosa muy importante a tener en cuenta es que 0.6 pone internamente en minúsculas todos los nombres de las columnas en el momento de la ingesta y en el momento de la consulta. En 0.7, este ya no es el caso; sin embargo, recomendamos encarecidamente que utilice nombres de columna en minúsculas en 0.7 para simplificar.
    3. Si actualmente está ingiriendo datos con nombres de columnas en mayúsculas y minúsculas mixtas como parte de su esquema de ingestión o datos:
      • para datos TSV o CSV, simplemente escriba en minúsculas los nombres de las columnas en su esquema cuando actualice a 0.7.0.
      • para datos JSON con campos de mayúsculas y minúsculas y si no estaba especificando los nombres de las columnas, puede usar jsonLowerCase parseSpec para poner en minúsculas los datos en el momento de la ingesta y mantener la compatibilidad con versiones anteriores. Para todas las demás especificaciones de análisis, deberá escribir en minúsculas nombres de métricas/agregadores si antes usaba mayúsculas y minúsculas mixtas.
  • El anuncio del segmento de lotes ahora es el predeterminado Druid ahora usa anuncios de segmentos por lotes de forma predeterminada para todos los nodos. Si ya está utilizando anuncio de segmento de lote, debería estar todo listo. Si aún no ha actualizado para usar el anuncio de segmentos por lotes, lea esta guía en el foro sobre cómo actualizar su clúster 0.6.x actual para usar el anuncio por lotes primero.
  • Kafka 0.7.x eliminado a favor de Kafka 0.8.x Si está utilizando Kafka 0.7, deberá crear la extensión kafka-seven manualmente. Está comentado en la compilación porque Kafka 0.7 no está disponible en Maven Central. La extensión Kafka 0.8 (kafka-eight) no se ve afectada.
  • Cambios en el punto final del coordinador Numerosos puntos finales del coordinador han cambiado. Consulte la [documentación del coordinador] (http://druid.io/docs/0.7.0-rc3/Coordinator.html#http-endpoints) para conocer cuáles son. En particular:
  1. Se eliminó /info en el coordinador.
  2. Se eliminó /health en nodos históricos.
  • Se requiere un frasco separado para com.metamx.metrics.SysMonitor Si actualmente tiene com.metamx.metrics.SysMonitor como parte de su configuración de druid.monitoring.monitors y desea conservarlo, deberá agregar el tarro de biblioteca SIGAR a su classpath. Alternativamente, puede simplemente eliminar com.metamx.metrics.SysMonitor si no confía en las métricas de sys/.*. Tuvimos que eliminar la dependencia directa de SIGAR para poder mover los artefactos druidas a Maven Central, ya que SIGAR actualmente no está disponible allí.
  • Procedimiento de actualización Si está ejecutando una versión de Druid anterior a 0.6.172, actualice primero a 0.6.172. Consulte 0.6.172 release notes para obtener instrucciones. Para garantizar una actualización fluida y sin tiempo de inactividad, los nodos deben actualizarse en el siguiente orden:
    1. nodos históricos
    2. servicio de indexación/nodos en tiempo real
    3. nodos de enrutador (si tiene alguno),
    4. nodos de intermediario Cinco, nodos coordinadores

Nuevas características

  • Soporte de columna métrica larga Hasta ahora, Druid almacenaba todas las métricas como valores de punto flotante de precisión simple, lo que podía introducir errores de redondeo y resultados inesperados con consultas que utilizaban agregadores longSum, especialmente para consultas groupBy.
  • Almacenamiento de metadatos conectable MySQL, PostgreSQL y Derby (para pruebas) ahora son compatibles de fábrica. Derby solo admite un solo maestro o no debe usarse para producción de alta disponibilidad; use la conmutación por error MySQL o PostgreSQL para eso.
  • Ingestión de datos simplificada API Rehacer completamente la ingesta de datos de Druid API.
  • Cambiar la compresión para columnas métricas de LZF a LZ4 Las pruebas de rendimiento iniciales muestran que puede ser entre un 15% y un 25% más rápido y da como resultado segmentos entre un 3 y un 5% más pequeños en conjuntos de datos típicos.
  • Índices de mapa de bits invertidos configurables Druid ahora admite mapas de bits rugientes además de los mapas de bits concisos predeterminados. Las pruebas de rendimiento iniciales muestran que Roaring puede ser hasta un 20% más rápido para ciertos tipos de consultas, a expensas de que los segmentos sean un 20% más grandes en promedio.
  • Pruebas de integración Hemos agregado un conjunto de pruebas de integración que utilizan Docker para activar un clúster Druid para ejecutar una serie de pruebas de indexación y consulta.
  • Nueva consola del Coordinador de Druidas Presentamos una nueva consola Druid que, con suerte, debería proporcionar una mejor descripción general del estado de su clúster y ser un poco más escalable si tiene cientos de miles de segmentos. Planeamos expandir esta consola para brindar más información sobre el estado actual de un clúster de Druida.
  • Contexto del resultado de la consulta Los contextos de resultados pueden informar errores durante las consultas en los encabezados de consulta. Actualmente utilizamos esta función para reintentos internos, pero esperamos ampliarla para informar más información a clients.

Mejoras

  • Velocidades de consulta más rápidas Muchas mejoras de velocidad gracias a un formato de compresión más rápido, pequeñas optimizaciones en la estructura de columnas y optimizaciones de consultas con múltiples agregaciones, así como numerosas mejoras en el rendimiento de las consultas groupBy. En general, algunas consultas pueden ser hasta dos veces más rápidas con el nuevo formato de índice.
  • Artefactos druidas en Maven Central Los artefactos druidas ahora están disponibles en Maven Central para facilitar sus propias compilaciones e implementaciones.
  • Archivo de configuración común Druid ahora tiene common.runtime.properties donde puede declarar todas las propiedades globales, así como todas sus dependencias externas. Esto evita la configuración repetida en múltiples nodos y, con suerte, hará que la configuración de un clúster Druid sea un poco menos dolorosa.
  • Nombres de host, puertos y servicios predeterminados Los nombres de host, puertos y nombres de servicios predeterminados para todos los nodos significan que se requiere mucha menos configuración inicial si está satisfecho con los valores predeterminados. También significa que puede ejecutar todos los tipos de nodos en una sola máquina sin tener que lidiar con conflictos de puertos.
  • Los nombres de las columnas de druida ahora distinguen entre mayúsculas y minúsculas Muerte a los errores de carcasa. Tenga en cuenta los peligros de actualizar a 0.7.0 si tiene columnas de casos mixtos y está utilizando 0.6.x. Consulte arriba para obtener más detalles.
  • Reintentos de consulta Druid ahora reintentará automáticamente las consultas para ciertas clases de fallas.
  • Almacenamiento en caché en segundo plano Para ciertos tipos de consultas, especialmente aquellas que involucran recuentos distintos (hyperloglog), esto puede mejorar el rendimiento hasta en un 20 %. El almacenamiento en caché en segundo plano está deshabilitado de forma predeterminada.
  • Uso reducido de memoria del coordinador Reducción del uso de memoria del coordinador (hasta en un 50%). Esto soluciona un problema por el cual un coordinador a veces perdía liderazgo debido a las frecuentes reuniones generales.
  • Las métricas ahora se pueden emitir a puntos finales SSL
  • Soporte adicional para credenciales de AWS, gracias @gnethercutt
  • Métricas adicionales de persistencia y aceleración para la ingesta en tiempo real Esto debería ayudar a diagnosticar cuándo se está frenando la ingestión en tiempo real y cuánto tiempo dura la persistencia. Estas métricas proporcionan una buena indicación de cuándo es el momento de ampliar la ingesta en tiempo real.
  • Punto final de inicialización del agente Los corredores ahora proporcionan un punto final de estado en /druid/broker/v1/loadstatus para indicar si están listos para ser consultados, lo que facilita las actualizaciones/reinicios continuos.

Corrección de errores

  • Admite múltiples fragmentos de la misma fuente de datos en el mismo nodo en tiempo real. Gracias @zhaown
  • Los registros de tareas de HDFS ahora deberían funcionar como se esperaba. Gracias @flowbehappy.
  • Posible condición de interbloqueo solucionada en el Broker.
  • Varias correcciones para la compresión GZIP al devolver resultados.
  • druid.host ahora también debería admitir direcciones IPv6.

Documentación

  • Nuevos tutoriales.
  • Nueva documentación de ingestión.
  • Nueva documentación de configuración.
  • Mejoras en la documentación de reglas. Gracias @mrijke

Problemas conocidos

  • Actualmente no es posible fusionar segmentos con diferentes tipos de índices de mapa de bits, por lo que si tiene ambos tipos de índices en su clúster, debe configurar druid.coordinator.merge.on en falso. 'falso' es el valor predeterminado de la configuración.
  • https://github.com/druid-io/druid/issues/1045 Problema con consultas GoupBy con agregaciones complejas y post-agregaciones que usan el mismo nombre
  • https://github.com/druid-io/druid-api/pull/38 Si utiliza longSum en su especificación de ingesta, tener datos de punto flotante puede generar excepciones.

druid druid-0.7.0

Updating to Druid 0.7.0 – Things to be Aware

  • New ingestion spec

    Druid 0.7.0 requires a new ingestion spec format. Druid 0.6.172 supports both the old and new formats of ingestion and has scripts to convert from the old to the new format. This script can be run with 'tools convertSpec' using the same Main used to run Druid nodes. You can update your Druid cluster to 0.6.172, update your ingestion specs to the new format, and then update to Druid 0.7.0. If you update your cluster to Druid 0.7.0 directly, make sure your real-time ingestion pipeline understands the new spec.

  • MySQL is no longer the default metadata storage

    Druid now defaults to embedding Apache Derby, which was chosen mainly for testability purposes. However, we do not recommend using Derby in production. For anything other than testing, please use MySQL or PostgreSQL metadata storage.

    Configuration parameters for metadata storage were renamed from druid.db to druid.metadata.storage and an additional druid.metadata.storage.type=<mysql|postgresql> is required to use anything other than Derby.

    The convertProps tool can assis you in convertng all 0.6.x properties to 0.7 properties.

  • Druid is now case-sensitive

    Druid column names are now case-sensitive. We previously tried to be case-insensitive for queries and case-preserving for data, but we decided to make this change as there were numerous bugs related to various casing problems.

    If you are upgrading from version 0.6.x:

    1. Please make sure the column casing in your queries matches the casing of your column names in your data and update your queries accordingly.
    2. One very important thing to note is that 0.6 internally lower-cased all column names at ingestion time and query time. In 0.7, this is no longer the case, however, we still strongly recommend that you use lowercase column names in 0.7 for simplicity.
    3. If you are currently ingesting data with mixed case column names as part of your data or ingestion schema:
      • for TSV or CSV data, simply lower-case your column names in your schema when you update to 0.7.0.
      • for JSON data with mixed case fields and if you were not specifying the names of the columns, you can use the jsonLowerCase parseSpec to lower-case the data for you at ingestion time and maintain backwards compatibility.

    For all other parse specs, you will need to lower-case the

    metric/aggregator names if you were using mixed case before.

  • Batch segment announcement is now the default

    Druid now uses batch segment announcement by default for all nodes. If you are already using batch segment announcement, you should be all set.

    If you have not yet updated to using batch segments announcement, please read this guide in the forum on how to update your current 0.6.x cluster to use batch announcement first.

  • Kafka 0.7.x removed in favor of Kafka 0.8.x

    If you are using Kafka 0.7, you will have to build the kafka-seven extension manually. It is commented out in the build, because Kafka 0.7 is not available in Maven Central. The Kafka 0.8 (kafka-eight) extension is unaffected.

  • Coordinator endpoint changes

    Numerous coordinator endpoints have changed. Please refer to the coordinator documentation for what they are.

    In particular:

    1. /info on the coordinator has been removed.
    2. /health on historical nodes has been removed

  • Separate jar required for com.metamx.metrics.SysMonitor

    If you currenly have com.metamx.metrics.SysMonitor as part of your druid.monitoring.monitors configuration and would like to keep it, you will have to add the SIGAR library jar to your classpath.

    Alternatively, you can simply remove com.metamx.metrics.SysMonitor if you do not rely on the sys/.* metrics.

    We had to remove the direct dependency on SIGAR in order to move Druid artifacts to Maven Central, since SIGAR is currently not available there.

  • Update Procedure

    If you are running a version of Druid older than 0.6.172, please upgrade to 0.6.172 first. See the 0.6.172 release notes for instructions.

    In order to ensure a smooth rolling upgrade without downtime, nodes must be updated in the following order:

    1. historical nodes
    2. indexing service/real-time nodes
    3. router nodes (if you have any),
    4. broker nodes
    5. coordinator nodes

New Features

  • Long metric column support

    Until now Druid stored all metrics as single precision floating point values, which could introduce rounding errors and unexpected results with queries using longSum aggregators, especially for groupBy queries.

  • Pluggable metadata storage

    MySQL, PostgreSQL, and Derby (for testing) are now supported out of the box. Derby only supports single master or should not be used for high availability production, use MySQL or PostgreSQL failover for that.

  • Simplified data ingestion API

    completely redo Druid’s data ingestion API.

  • Switch compression for metric colums from LZF to LZ4

    Initial performance tests show it may be between 15% and 25% faster, and results in segments about 3-5% smaller on typical data sets.

  • Configurable inverted bitmap indexes

    Druid now supports Roaring Bitmaps in addition to the default Concise Bitmaps. Initial performance tests show Roaring may be up to 20% faster for certain types of queries, at the expense of segments being 20% larger on average.

  • Integration tests

    We have added a set of integration tests that use Docker to spin up a Druid cluster to run a series of indexing and query tests.

  • New Druid Coordinator console

    We introduced a new Druid console that should hopefully provide a better overview of the status of your cluster and be a bit more scalable if you have hundreds of thousands of segments. We plan to expand this console to provide more information about the current state of a Druid cluster.

  • Query Result Context

    Result contexts can report errors during queries in the query headers. We are currently using this feature for internal retries, but hope to expand it to report more information back to clients.

Improvements

  • Faster query speeds

    Lots of speed improvements thanks to faster compression format, small optimizations in column structure, and optimizations of queries with multiple aggregations, as well as numerous groupBy query performance improvements. Overall, some queries can be up to twice as fast using the new index format.

  • Druid artifacts in Maven Central

    Druid artifacts are now available in Maven Central to make your own builds and deployments easier.

  • Common Configuration File

    Druid now has a common.runtime.properties where you can declare all global properties as well as all of your external dependencies. This avoids repeated configuration across multiple nodes and will hopefully make setting up a Druid cluster a little less painful.

  • Default host names, port and service names

    Default host names, ports, and service names for all nodes means a lot less configuration is required upfront if you are happy with the defaults. It also means you can run all node types on a single machine without fiddling with port conflicts.

  • Druid column names are now case sensitive

    Death to casing bugs. Be aware of the dangers of updating to 0.7.0 if you have mixed case columns and are using 0.6.x. See above for more details.

  • Query Retries

    Druid will now automatically retry queries for certain classes of failures.

  • Background caching

    For certain types of queries, especially those that involve distinct (hyperloglog) counts, this can improve performance up over 20%. Background caching is disabled by default.

  • Reduced coordinator memory usage

    Reduced coordinator memory usage (by up to 50%). This fixes a problem where a coordinator would sometimes lose leadership due to frequent GCs.

  • Metrics can now be emitted to SSL endpoints

  • Additional AWS credentials support, Thanks @gnethercutt

  • Additional persist and throttle metrics for real-time ingestion

    This should help diagnose when real-time ingestion is being throttled and how long persists are taking. These metrics provide a good indication of when it is time to scale up real-time ingestion.

  • Broker initialization endpoint

    Brokers now provides a status endpoint at /druid/broker/v1/loadstatus to indicate whether they are ready to be queried, making rolling upgrades / restarts easier.

Bug Fixes

  • Support multiple shards of the same datasource on the same realtime node. Thanks @zhaown
  • HDFS task logs should now work as expected. Thanks @flowbehappy.
  • Possible deadlock condition fixed in the Broker.
  • Various fixes for GZIP compression in returning results.
  • druid.host should now support IPv6 addresses as well.

Documentation

  • New tutorials.
  • New ingestion documentation.
  • New configuration documentation.
  • Improvements to rule documentation. Thanks @mrijke

Known issues

  • Merging segments with different types of bitmap indices is currently not possible, so if you have both types of indices in your cluster, you must set druid.coordinator.merge.on to false. ‘false’ is the default value of the config.
  • https://github.com/druid-io/druid/issues/1045 Issue with GoupBy queries with complex aggregations and post-aggregations using the same name
  • https://github.com/druid-io/druid-api/pull/38 If you are using longSum in your ingestion spec, having floating point data may throw exceptions.
