druida druida-24.0.0

Apache Druid 24.0.0 contiene más de 300 funciones nuevas, correcciones de errores, mejoras de rendimiento, mejoras de documentación y cobertura de pruebas adicionales de 67 contribuyentes. Consulte el conjunto completo de cambios para obtener detalles adicionales.

<a name="24.0.0-new-features" href="#24.0.0-major-version">#</a> Mejora de la versión principal

A partir de esta versión, eliminamos el 0 principal de la versión de lanzamiento y promocionamos todos los demás dígitos un lugar a la izquierda. Druid se encuentra ahora en la versión principal 24, un salto con respecto a la versión anterior 0.23.0. En términos de compatibilidad con versiones anteriores o cambios importantes, esta versión no es significativamente diferente de otras versiones importantes anteriores, como 0.23.0 o 0.22.0. Continuamos con la misma política que hemos utilizado en versiones anteriores: minimizar la cantidad de cambios que requieren atención especial al actualizar y resaltar los que existen en los release note. Para esta versión, consulte la [sección Actualización a 24.0.0] (#24.0.0-upgrading-to-24.0) para obtener una lista de cambios incompatibles con versiones anteriores en esta versión.

<a name="24.0.0-new-features" href="#24.0.0-new-features">#</a> Nuevas funciones

<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> Motor de tareas de consulta de varias etapas

Ingestión basada en SQL para Apache Druid utiliza una arquitectura de consulta distribuida de varias etapas, que incluye un motor de consulta llamado motor de tareas de consulta de varias etapas (motor de tareas MSQ). El motor de tareas MSQ amplía las capacidades de consulta de Druid, por lo que puede escribir consultas que hagan referencia a datos externos, así como realizar la ingesta con SQL INSERT y REPLACE. Básicamente, puede realizar una ingesta basada en SQL en lugar de utilizar las especificaciones de ingesta JSON que utiliza la ingesta nativa de Druid. Además de la sintaxis fácil de usar, la interfaz SQL le permite realizar transformaciones que implican múltiples combinaciones de datos. Se recomienda la ingesta basada en SQL utilizando el motor de tareas de consulta de varias etapas para la ingesta por lotes a partir de Druid 24.0.0. También se sigue admitiendo la ingestión nativa por lotes y basada en Hadoop. Le recomendamos revisar los problemas conocidos y probar la función en un entorno de prueba antes de implementarla en producción. El uso del motor de tareas de consulta de varias etapas con declaraciones SELECT simples (no INSERT ... SELECT o REPLACE ... SELECT) es experimental. Si está actualizando desde una versión anterior de Druid o está utilizando Docker, deberá agregar la extensión druid-multi-stage-query a druid.extensions.loadlist en su archivo common.runtime.properties. Para obtener más información, consulte la documentación descripción general para la ingesta basada en SQL. #12524 #12386 #12523 #12589

<a name="24.0.0-new-features-nested-columns-" href="#24.0.0-new-features-nested-columns-">#</a> Columnas anidadas

Druid ahora admite el almacenamiento directo de estructuras de datos anidadas en un tipo de columna COMPLEX<json> recién agregado. Las columnas COMPLEX<json> almacenan una copia de los datos estructurados en formato JSON, así como columnas e índices internos especializados para valores literales anidados: tipos STRING, LONG y DOUBLE. Una columna virtual optimizada permite a Druid leer y filtrar estos valores a velocidades consistentes con las columnas estándar Druid LONG, DOUBLE y STRING. Druid SQL recientemente agregado, funciones nativas JSON y una columna virtual le permiten extraer, transformar y crear valores COMPLEX<json> en el momento de la consulta. También puede utilizar las funciones JSON en declaraciones INSERT y REPLACE en la ingesta basada en SQL, o en un transformSpec en la ingesta nativa como alternativa al uso de un objeto flattenSpec para "aplanar" datos anidados para la ingesta. Consulte funciones SQL JSON, funciones nativas JSON, columnas anidadas, virtuales columnas y el resumen de funciones para obtener más detalles. #12753 #12714 #12753 #12920

<a name="24.0.0-query-engine-updates" href="#24.0.0-query-engine-updates">#</a> Actualizaciones del motor de consultas

<a name="24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters" href="#24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters">#</a> Índices de columnas actualizados y procesamiento de consultas de filtros

Se rediseñaron los índices de columnas para que sean extraordinariamente flexibles, lo que eventualmente nos permitirá modelar una amplia gama de tipos de índices. Se agregó maquinaria para crear los filtros que usan los índices actualizados, al tiempo que se permite que otras implementaciones de columnas implementen los tipos de índice integrados para proporcionar adaptadores para utilizar la indexación en los filtros del conjunto actual que proporciona Druid. #12388

<a name="24.0.0-query-engine-updates-time-filter-operator" href="#24.0.0-query-engine-updates-time-filter-operator">#</a> Operador de filtro de tiempo

Ahora puede utilizar el operador Druid SQL TIME_IN_INTERVAL para filtrar los resultados de la consulta según el tiempo. Prefiera TIME_IN_INTERVAL sobre el operador SQL BETWEEN para filtrar a tiempo. Para obtener más información, consulte [Funciones de fecha y hora] (docs/querying/sql-scalar.md#date-and-time-functions). #12662

<a name="24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter" href="#24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter">#</a> Valores nulos y el filtro "in"

Si una matriz values contiene null, el filtro "en" coincide con valores nulos. Esto difiere del filtro SQL IN, que no coincide con valores nulos. Para obtener más información, consulte Filtros de consulta y tipos de datos SQL. #12863

<a name="24.0.0-query-engine-updates-virtual-columns-in-search-queries" href="#24.0.0-query-engine-updates-virtual-columns-in-search-queries">#</a> Columnas virtuales en consultas de búsqueda

Anteriormente, una consulta de búsqueda solo podía buscar dimensiones que existían en la fuente de datos. Las consultas de búsqueda ahora admiten columnas virtuales como parámetro en la consulta. #12720

<a name="24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time" href="#24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time">#</a> Optimice consultas SQL MIN/MAX simples en __time

Las consultas simples como select max(__time) from ds ahora se ejecutan como consultas timeBoundary para aprovechar la clasificación por dimensión temporal en un segmento. Puede configurar un indicador de función para habilitar esta función. #12472 #12491

<a name="24.0.0-query-engine-updates-string-aggregation-results" href="#24.0.0-query-engine-updates-string-aggregation-results">#</a> Resultados de agregación de cadenas

El primer/último agregador de cadenas ahora solo compara según los valores. Anteriormente, los valores del primer/último agregador de cadenas se comparaban primero en función de la columna _time y luego en los valores. Si tiene consultas existentes y desea continuar usando la columna y los valores _time, actualice sus consultas para usar ORDER BY MAX(timeCol). #12773

<a name="24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization" href="#24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization">#</a> Asignaciones reducidas debido a la serialización de Jackson

Se introdujeron e implementaron nuevas funciones auxiliares en JacksonUtils para permitir la reutilización de Objetos SerializerProvider. Además, se deshabilitó la compatibilidad con versiones anteriores para filas basadas en mapas en el GroupByQueryToolChest de forma predeterminada, lo que elimina la necesidad de copiar el pesado ObjectMapper. Se introdujo una opción de configuración para permitir a los administradores habilitar explícitamente la compatibilidad con versiones anteriores. #12468

<a name="24.0.0-query-engine-updates-updated-ipaddress-java-library-" href="#24.0.0-query-engine-updates-updated-ipaddress-java-library-">#</a> Biblioteca Java IPAddress actualizada

Se agregó una nueva dependencia de la biblioteca Java IPAddress para manejar direcciones IP. La biblioteca incluye soporte para IPv6. Además, se migraron funciones de IPv4 para utilizar la nueva biblioteca. #11634

<a name="24.0.0-query-engine-updates-query-performance-improvements" href="#24.0.0-query-engine-updates-query-performance-improvements">#</a> Mejoras en el rendimiento de consultas

Operaciones y funciones SQL optimizadas de la siguiente manera:

  • Agregadores numéricos más recientes vectorizados (#12439)
  • isEmpty() y equals() optimizados en RangeSets (#12477)
  • Reutilización optimizada de objetos Yielder (#12475)
  • Las operaciones en columnas numéricas con índices ahora son más rápidas (#12830)
  • GroupBy optimizado reduciendo las asignaciones. Asignaciones reducidas al reutilizar la entrada y los titulares de llaves (#12474)
  • Se agregó una versión vectorizada del último agregador de cadenas (#12493)
  • Se agregó acceso directo UTF-8 para filtros IN (#12517)
  • Se habilitaron columnas virtuales para almacenar en caché sus resultados en caso de que Druid las llame varias veces en la misma fila subyacente (#12577)
  • Druid ahora reescribe una unión como filtro cuando es posible en uniones IN (#12225)
  • Se agregó tamaño automático para diccionarios GroupBy (#12763)
  • Druid ahora distribuye las conexiones JDBC de manera más uniforme entre los brokers (#12817)

<a name="24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management" href="#24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management">#</a> Mayor solidez para la gestión de tareas

Se agregó setNumProcessorsPerTask para evitar que varios grupos de subprocesos de tamaño automático se vuelvan excesivamente grandes. No es ideal que cada tarea dimensione sus grupos como si fuera el único proceso en toda la máquina. En máquinas grandes, esto resuelve una causa común de OutOfMemoryError debido a que "no se puede crear un hilo nativo". #12592

<a name="24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver" href="#24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver">#</a> Controlador Avatica JDBC

Druid ahora acepta la granularidad EIGHT_HOUR. Puede segmentar los datos entrantes en depósitos EIGHT_HOUR, así como agrupar los resultados de las consultas con una granularidad de ocho horas. #12717

<a name="24.0.0-ingestion-general" href="#24.0.0-ingestion-general">#</a> Ingestión general

<a name="24.0.0-ingestion-general-updated-avro-extension" href="#24.0.0-ingestion-general-updated-avro-extension">#</a> Extensión Avro actualizada

La extensión Avro anterior filtró objetos del analizador. Si estos objetos se filtraron en su ingesta, los objetos se almacenaron como una columna de cadena con el valor .toString(). Esta columna de cadena permanecerá después de la actualización, pero devolverá Map.toString() en lugar de GenericRecord.toString. Si confió en el comportamiento anterior, puede usar la extensión Avro de una versión anterior. #12828

<a name="24.0.0-ingestion-general-sampler-api" href="#24.0.0-ingestion-general-sampler-api">#</a> Muestra API

El muestreador API tiene límites adicionales: maxBytesInMemory y maxClientResponseBytes. Estas opciones aumentan las opciones existentes numRows y timeoutMs. maxBytesInMemory se puede utilizar para controlar el uso de la memoria en Overlord durante el muestreo. clients puede utilizar maxClientResponseBytes para especificar el tamaño máximo de respuesta que preferirían manejar. #12947

<a name="24.0.0-sql" href="#24.0.0-sql">#</a> SQL

<a name="24.0.0-sql-column-order" href="#24.0.0-sql-column-order">#</a> Orden de columnas

Las propiedades DruidSchema y SegmentMetadataQuery ahora conservan el orden de las columnas en lugar de ordenarlas alfabéticamente. Esto significa que el orden de las consultas coincide mejor con el orden de ingesta. #12754

<a name="24.0.0-sql-converting-joins-to-filter" href="#24.0.0-sql-converting-joins-to-filter">#</a> Conversión de JOIN para filtrar

Puede mejorar el rendimiento enviando JOIN parcial o totalmente a la tabla base como filtro en tiempo de ejecución configurando el parámetro de contexto enableRewriteJoinToFilter en true para una consulta. Druid ahora presiona hacia abajo los filtros de combinación en caso de que la combinación informática de consulta haga referencia a alguna columna del lado derecho. #12749 #12868

<a name="24.0.0-sql-add-is_active-to-sys.segments" href="#24.0.0-sql-add-is_active-to-sys.segments">#</a> Agregar is_active a sys.segments

Se agregó is_active como abreviatura de (is_published = 1 AND is_overshadowed = 0) OR is_realtime = 1). Esto representa "todos los segmentos que deberían ser consultables, ya sea que realmente lo sean o no en este momento". #11550

<a name="24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true" href="#24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true">#</a> useNativeQueryExplain ahora tiene el valor predeterminado verdadero

La propiedad useNativeQueryExplain ahora tiene como valor predeterminado true. Esto significa que EXPLAIN PLAN FOR devuelve el plan de explicación como una representación JSON de consultas nativas equivalentes de forma predeterminada. Para obtener más información, consulte Suplemento de configuración de consultas generadas por el agente. #12936

<a name="24.0.0-inline-query-engine" href="#24.0.0-inline-query-engine">#</a> Ejecución de consultas con datos en línea utilizando el motor de consultas druid

Algunas consultas que no hacen referencia a ninguna tabla, como select 1, ahora siempre se traducen a una consulta nativa de Druid con InlineDataSource antes de su ejecución. Si la traducción no es posible, para consultas como SELECT (1, 2), se produce un error. En versiones anteriores, esta consulta aún se ejecutaba. #12897

<a name="24.0.0-coordinator%2Foverlord" href="#24.0.0-coordinator%2Foverlord">#</a> Coordinador/Señor supremo

<a name="24.0.0-coordinator%2Foverlord-puedes-configurar-el-coordinador-para-matar-segmentos-en-el-futuro" href="#24.0.0-coordinator%2Foverlord-puedes-configurar-el-coordinador-para-matar-segmentos-en-el-futuro">#</a> Puedes configurar el Coordinador para matar segmentos en el futuro

Ahora puede establecer druid.coordinator.kill.durationToRetain en un período negativo para configurar el clúster Druid para eliminar segmentos cuyo interval_end sea una fecha en el futuro. Por ejemplo, PT-24H permitiría eliminar segmentos si su fecha de finalización del intervalo fuera de 24 horas o menos en el futuro en el momento en que el sistema genera la tarea de eliminación. Un operador de clúster también puede ignorar por completo el druid.coordinator.kill.durationToRetain estableciendo una nueva configuración, druid.coordinator.kill.ignoreDurationToRetain=true. Esto ignora la fecha interval_end cuando se buscan segmentos para eliminar y, en su lugar, puede eliminar cualquier segmento marcado como no utilizado. Esta nueva configuración está desactivada de forma predeterminada y un operador de clúster debe comprender y aceptar completamente los riesgos antes de habilitarla.

<a name="24.0.0-coordinator%2Foverlord-improved-overlord-stability" href="#24.0.0-coordinator%2Foverlord-improved-overlord-stability">#</a> Estabilidad de Overlord mejorada

Reducción de la contención entre el hilo de administración y la recepción de actualizaciones de estado del clúster. Esto mejora la estabilidad de Overlord y de todas las tareas en un grupo cuando hay un gran número de tareas (más de 1000). #12099

<a name="24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging" href="#24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging">#</a> Registro de segmentos de Coordinador mejorado

Se actualizó el registro de reglas de carga del Coordinador para incluir los niveles de replicación actuales. Se agregó ID de segmento faltante e información de nivel de algunos de los mensajes de registro. #12511

<a name="24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage" href="#24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage">#</a> Uso optimizado de memoria de las tareas GET de Overlord

Se solucionó la importante sobrecarga de memoria causada por la consola web que llamaba indirectamente a las tareas GET del Overlord API. Esto podría causar falta de respuesta o falla de Overlord cuando la pestaña de ingesta se abrió varias veces. #12404

<a name="24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals" href="#24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals">#</a> Tiempo reducido para crear intervalos

Para optimizar el tiempo de cálculo del costo del segmento reduciendo el tiempo necesario para la creación de intervalos, almacene el intervalo del segmento en lugar de crearlo cada vez a partir de primitivos y reduzca la sobrecarga de memoria de los intervalos de almacenamiento internándolos. El conjunto de intervalos para segmentos tiene una cardinalidad baja. #12670

<a name="24.0.0--brokers%2Foverlord" href="#24.0.0--brokers%2Foverlord">#</a> Corredores/Overlord

Los corredores ahora tienen un valor predeterminado de 25 MB como máximo en cola por consulta. Anteriormente, no había ningún límite predeterminado. Dependiendo de su caso de uso, es posible que necesite aumentar el valor, especialmente si tiene grandes conjuntos de resultados o grandes cantidades de datos intermedios. Para ajustar la memoria máxima disponible, utilice la propiedad druid.broker.http.maxQueuedBytes. Para obtener más información, consulte Referencia de configuración.

<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> Multi-stage query task engine

SQL-based ingestion for Apache Druid uses a distributed multi-stage query architecture, which includes a query engine called the multi-stage query task engine (MSQ task engine). The MSQ task engine extends Druid's query capabilities, so you can write queries that reference external data as well as perform ingestion with SQL INSERT and REPLACE. Essentially, you can perform SQL-based ingestion instead of using JSON ingestion specs that Druid's native ingestion uses. In addition to the easy-to-use syntax, the SQL interface lets you perform transformations that involve multiple shuffles of data.

SQL-based ingestion using the multi-stage query task engine is recommended for batch ingestion starting in Druid 24.0.0. Native batch and Hadoop-based ingestion continue to be supported as well. We recommend you review the known issues and test the feature in a staging environment before rolling out in production. Using the multi-stage query task engine with plain SELECT statements (not INSERT ... SELECT or REPLACE ... SELECT) is experimental.

If you're upgrading from an earlier version of Druid or you're using Docker, you'll need to add the druid-multi-stage-query extension to druid.extensions.loadlist in your common.runtime.properties file.

For more information, refer to the Overview documentation for SQL-based ingestion.

<a name="24.0.0-new-features-nested-columns-" href="#24.0.0-new-features-nested-columns-">#</a> Nested columns

Druid now supports directly storing nested data structures in a newly added COMPLEX<json> column type. COMPLEX<json> columns store a copy of the structured data in JSON format as well as specialized internal columns and indexes for nested literal values—STRING, LONG, and DOUBLE types. An optimized virtual column allows Druid to read and filter these values at speeds consistent with standard Druid LONG, DOUBLE, and STRING columns.

Newly added Druid SQL, native JSON functions, and virtual column allow you to extract, transform, and create COMPLEX<json> values in at query time. You can also use the JSON functions in INSERT and REPLACE statements in SQL-based ingestion, or in a transformSpec in native ingestion as an alternative to using a flattenSpec object to "flatten" nested data for ingestion.

See SQL JSON functions, native JSON functions, Nested columns, virtual columns, and the feature summary for more detail.

You can now set druid.coordinator.kill.durationToRetain to a negative period to configure the Druid cluster to kill segments whose interval_end is a date in the future. For example, PT-24H would allow segments to be killed if their interval_end date was 24 hours or less into the future at the time that the kill task is generated by the system. A cluster operator can also disregard the druid.coordinator.kill.durationToRetain entirely by setting a new configuration, druid.coordinator.kill.ignoreDurationToRetain=true. This ignores interval_end date when looking for segments to kill, and can instead kill any segment marked unused. This new configuration is turned off by default, and a cluster operator should fully understand and accept the risks before enabling it.

To read external data using the multi-stage query task engine, you must have READ permissions for the EXTERNAL resource type. Users without the correct permission encounter a 403 error when trying to run SQL queries that include EXTERN.

The way you assign the permission depends on your authorizer. For example, with [basic security]((/docs/development/extensions-core/druid-basic-security.md) in Druid, add the EXTERNAL READ permission by sending a POST request to the roles API.

The example adds permissions for users with the admin role using a basic authorizer named MyBasicMetadataAuthorizer. The following permissions are granted:

  • DATASOURCE READ
  • DATASOURCE WRITE
  • CONFIG READ
  • CONFIG WRITE
  • STATE READ
  • STATE WRITE
  • EXTERNAL READ

<a name="24.0.0-upgrading-to-24.0-behavior-for-unused-segments" href="#24.0.0-upgrading-to-24.0-behavior-for-unused-segments">#</a> Behavior for unused segments

Druid automatically retains any segments marked as unused. Previously, Druid permanently deleted unused segments from metadata store and deep storage after their duration to retain passed. This behavior was reverted from 0.23.0. #12693

<a name="24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60" href="#24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60">#</a> Default for druid.processing.fifo

The default for druid.processing.fifo is now true. This means that tasks of equal priority are treated in a FIFO manner. For most use cases, this change can improve performance on heavily loaded clusters.

#12571

<a name="24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure" href="#24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure">#</a> Update to JDBC statement closure

In previous releases, Druid automatically closed the JDBC Statement when the ResultSet was closed. Druid closed the ResultSet on EOF. Druid closed the statement on any exception. This behavior is, however, non-standard. In this release, Druid's JDBC driver follows the JDBC standards more closely: The ResultSet closes automatically on EOF, but does not close the Statement or PreparedStatement. Your code must close these statements, perhaps by using a try-with-resources block. The PreparedStatement can now be used multiple times with different parameters. (Previously this was not true since closing the ResultSet closed the PreparedStatement.) If any call to a Statement or PreparedStatement raises an error, the client code must still explicitly close the statement. According to the JDBC standards, statements are not closed automatically on errors. This allows you to obtain information about a failed statement before closing it. If you have code that depended on the old behavior, you may have to change your code to add the required close statement.
