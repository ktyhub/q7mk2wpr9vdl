{"timestamp": "2011-01-14T00:00:00.000Z", "tags": []}                #row4

La siguiente consulta:

{
  "queryType": "groupBy",
  "dataSource": "test",
  "intervals": [
    "1970-01-01T00:00:00.000Z/3000-01-01T00:00:00.000Z"
  ],
  "granularity": {
    "type": "all"
  },
  "virtualColumns" : [ {
    "type" : "expression",
    "name" : "v0",
    "expression" : "mv_to_array(\"tags\")",
    "outputType" : "ARRAY<STRING>"
  } ],
  "dimensions": [
    {
      "type": "default",

      "outputName": "tags"
      "outputType":"ARRAY<STRING>"
    }
  ],

    {
      "type": "count",

    }
  ]
}

Esta versión incluye varias mejoras para realizar consultas:

  • Se agregaron funciones SQL MV_FILTER_ONLY y MV_FILTER_NONE para filtrar filas de dimensiones de cadena de valores múltiples para incluir solo la lista de valores proporcionada o ninguno de ellos respectivamente (#11650)
  • Se agregó ARRAY_CONCAT_AGG para agregar entradas de matriz en una sola matriz (#12226)
  • Se agregó la capacidad de autorizar el uso de parámetros de contexto de consulta (#12396)

<a name="0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements" href="#0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements">#</a> Ingestión de Kinesis: mejoras

Hemos realizado las siguientes mejoras en la ingestión de kinesis.

  • La nueva fragmentación puede afectar y ralentizar la ingestión ya que se crean muchos fragmentos vacíos intermedios. Estos fragmentos se asignan a tareas que provocan un desequilibrio en la asignación de carga. Puede configurar skipIgnorableShards en true en la configuración de ajuste de ingesta de Kinesis para ignorar dichos fragmentos. (#12235)
  • Actualmente, la ingestión de Kinesis utiliza DescribeStream para recuperar la lista de fragmentos. Esta llamada está en desuso y es más lenta. En esta versión, puede cambiar a un API listShards más nuevo configurando useListShards en true en la configuración de ajuste de ingesta de Kinesis. (#12161)

Ahora, si configura dropExisting en true en su ioSpec e ingiere datos para un rango de tiempo que incluye un fragmento de tiempo sin datos, Druid usa una lápida para eclipsar los datos existentes en el fragmento de tiempo vacío. (#12137) Esta versión incluye varias mejoras para la ingesta de lotes nativos:

  • Se agregó funcionalidad para preservar las métricas existentes durante la ingesta (#12185)
  • La tarea por lotes nativa paralela ahora puede proporcionar informes de tareas para el modo secuencial y monofásico (por ejemplo, usado con partición dinámica), así como subtareas del modo monofásico (#11688).
  • Se agregó soporte para RowStats en druid/indexer/v1/task/{task_id}/reports API para tareas de indexación paralela de múltiples fases (#12280)
  • Se corrigieron las fallas de OOM en la fase de distribución de dimensiones de la indexación paralela (#12331)

Hasta la versión 0.22.1, si emitías una consulta SQL no compatible, Druid arrojaba mensajes de error muy crípticos e inútiles. Con este cambio, los mensajes de error incluyen exactamente la parte de la consulta SQL que no es compatible con Druid. <a name="0.23.0-security-fixes" href="#0.23.0-security-fixes">#</a> Correcciones de seguridad

<a name="0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts" href="#0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts">#</a> Soporte para control de acceso en la configuración de contextos de consulta

Hoy en día, los usuarios pueden acceder a cualquier parámetro de contexto. Esto puede causar 1) una mala experiencia de usuario si el parámetro de contexto aún no está maduro o 2) incluso una falla en la consulta o una falla del sistema en el peor de los casos si se abusa de un parámetro sensible, por ejemplo, maxSubqueryRows. Druid ahora tiene la capacidad de limitar los parámetros de contexto por función de usuario. Eso significa que una consulta fallará si tiene un parámetro de contexto establecido en la consulta que no está permitido. La autorización del parámetro de contexto se puede habilitar usando Druid.auth.authorizeQueryContextParams. Esto está deshabilitado de forma predeterminada para permitir una experiencia de actualización más fluida. (#12396)

<a name="0.23.0-upgrading-to-0.23.0" href="#0.23.0-upgrading-to-0.23.0">#</a> Actualización a 0.23.0

Considere los siguientes cambios y actualizaciones al actualizar de Druid 0.22.x a 0.23.0. Si está actualizando desde una versión anterior a 0.22.1, consulte los release note de las versiones intermedias relevantes.

<a name="0.23.0-upgrading-to-0.23.0-autokill" href="#0.23.0-upgrading-to-0.23.0-autokill">#</a> Eliminación automática de segmentos

En 0.23.0, la eliminación automática de segmentos ahora está habilitada de forma predeterminada (#12187). Los nuevos valores predeterminados deberían eliminar todos los segmentos no utilizados que tengan más de 90 días. Si los usuarios no desean este comportamiento en una actualización, deben desactivarlo explícitamente. Este es un cambio arriesgado ya que, según el intervalo, los segmentos se eliminarán inmediatamente después de marcarse como no utilizados. Este comportamiento se revertirá o cambiará en la próxima versión de druida. Consulte (#12693) para obtener más detalles.

<a name="0.23.0-upgrading-to-0.23.0-other-changes" href="#0.23.0-upgrading-to-0.23.0-other-changes">#</a> Otros cambios

  • La ingestión de Kinesis requiere acceso listShards API a la transmisión.
  • Las bibliotecas Kafka clients se han actualizado a 3.0.0 (#11735)
  • La configuración del coordinador dinámico, percentOfSegmentsToConsiderPerMove, ha quedado obsoleta y se eliminará en una versión futura de Druid. Está siendo reemplazada por una nueva estrategia de selección de segmentos introducida en (#11257). Esta nueva estrategia actualmente está desactivada de forma predeterminada, pero se puede activar si establece la configuración del coordinador dinámico useBatchedSegmentSampler en verdadero. Configurar esto como tal deshabilitará el uso del obsoleto percentOfSegmentsToConsiderPerMove. En una versión futura, useBatchedSegmentSampler será permanentemente verdadero. (#11960)

El supervisor anterior/punto final de tarea devuelve 400 cuando no se encuentra un supervisor o una tarea. Este código de estado no es amigable y confuso para el tercer sistema. <a name="0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays" href="#0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays">#</a> Grouping on arrays without exploding the arrays

You can now group on a multi-value dimension as an array. For a datasource named "test":

{"timestamp": "2011-01-12T00:00:00.000Z", "tags": ["t1","t2","t3"]}  #row1
{"timestamp": "2011-01-13T00:00:00.000Z", "tags": ["t3","t4","t5"]}  #row2
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": ["t5","t6","t7"]}  #row3
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": []}                #row4

The following query:

{
  "queryType": "groupBy",
  "dataSource": "test",
  "intervals": [
    "1970-01-01T00:00:00.000Z/3000-01-01T00:00:00.000Z"
  ],
  "granularity": {
    "type": "all"
  },
  "virtualColumns" : [ {
    "type" : "expression",
    "name" : "v0",
    "expression" : "mv_to_array(\"tags\")",
    "outputType" : "ARRAY<STRING>"
  } ],
  "dimensions": [
    {
      "type": "default",
      "dimension": "v0",
      "outputName": "tags"
      "outputType":"ARRAY<STRING>"
    }
  ],
  "aggregations": [
    {
      "type": "count",
      "name": "count"
    }
  ]
}

Returns the following:

[
 {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "[]"
    }
  },

    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "["t1","t2","t3"]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "[t3","t4","t5"]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",

]

We have made following improvements in kinesis ingestion

  • Re-sharding can affect and slow down ingestion as many intermediate empty shards are created. These shards get assigned to tasks causing imbalance in load assignment. You can set skipIgnorableShards to true in kinesis ingestion tuning config to ignore such shards. (#12235)

<a name="0.23.0-security-fixes" href="#0.23.0-security-fixes">#</a> Security fixes

<a name="0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts" href="#0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts">#</a> Support for access control on setting query contexts

Today, any context params are allowed to users. This can cause 1) a bad UX if the context param is not matured yet or 2) even query failure or system fault in the worst case if a sensitive param is abused, ex) maxSubqueryRows. Druid now has an ability to limit context params per user role. That means, a query will fail if you have a context param set in the query that is not allowed to you.

The context parameter authorization can be enabled using Druid.auth.authorizeQueryContextParams. This is disabled by default to enable a smoother upgrade experience.

(#12396)

<a name="0.23.0-upgrading-to-0.23.0" href="#0.23.0-upgrading-to-0.23.0">#</a> Upgrading to 0.23.0

Consider the following changes and updates when upgrading from Druid 0.22.x to 0.23.0. If you're updating from an earlier version than 0.22.1, see the release notes of the relevant intermediate versions.

<a name="0.23.0-upgrading-to-0.23.0-autokill" href="#0.23.0-upgrading-to-0.23.0-autokill">#</a> Auto-killing of segments

In 0.23.0, Auto killing of segments is now enabled by default (#12187). The new defaults should kill all unused segments older than 90 days. If users do not want this behavior on an upgrade, they should explicitly disable the behavior. This is a risky change since depending on the interval, segments will be killed immediately after being marked unused. this behavior will be reverted or changed in the next druid release. Please see (#12693) for more details.

<a name="0.23.0-upgrading-to-0.23.0-other-changes" href="#0.23.0-upgrading-to-0.23.0-other-changes">#</a> Other changes

  • Kinesis ingestion requires listShards API access on the stream.
  • Kafka clients libraries have been upgraded to 3.0.0 (#11735)
  • The dynamic coordinator config, percentOfSegmentsToConsiderPerMove has been deprecated and will be removed in a future release of Druid. It is being replaced by a new segment picking strategy introduced in (#11257). This new strategy is currently toggled off by default, but can be toggled on if you set the dynamic coordinator config useBatchedSegmentSampler to true. Setting this as such, will disable the use of the deprecated percentOfSegmentsToConsiderPerMove. In a future release, useBatchedSegmentSampler will become permanently true. (#11960)

<a name="0.23.0-developer-notices" href="#0.23.0-developer-notices">#</a> Developer notices

<a name="0.23.0-developer-notices-updated-airline-dependency-to-2.x" href="#0.23.0-developer-notices-updated-airline-dependency-to-2.x">#</a> updated airline dependency to 2.x

https://github.com/airlift/airline is no longer maintained and so druid has upgraded to https://github.com/rvesse/airline (Airline 2) to use an actively maintained version, while minimizing breaking changes.

This is a backwards incompatible change, and custom extensions relying on the CliCommandCreator extension point will also need to be updated.

12270

<a name="0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks" href="#0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks">#</a> Return 404 instead of 400 for unknown supervisors or tasks

Earlier supervisor/task endpoint return 400 when a supervisor or a task is not found. This status code is not friendly and confusing for the 3rd system. And according to the definition of HTTP status code, 404 is right code for such case. So we have changed the status code from 400 to 404 to eliminate the ambigiuty. Any clients of these endpoints should change the response code handling accordingly.

11724

<a name="0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned" href="#0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned">#</a> Return 400 instead of 500 when SQL query cannot be planned

Any SQL query that cannot be planned by Druid is not considered a bad request. For such queries, we now return 400. Developers using SQL API should change the response code handling if needed.

12033

<a name="0.23.0-developer-notices-responsecontext-refactoring" href="#0.23.0-developer-notices-responsecontext-refactoring">#</a> ResponseContext refactoring

0.23.0 changes the the ResponseContext and it's keys in a breaking way. The prior version of the response context suggested that keys be defined in an enum, then registered. This version suggests that keys be defined as objects, then registered. See the ResponseContext class itself for the details.

(#11828)

<a name="0.23.0-developer-notices-other-changes" href="#0.23.0-developer-notices-other-changes">#</a> Other changes

  • SingleServerInventoryView has been removed. (#11770)
  • LocalInputSource does not allow ingesting same file multiple times. (#11965)
  • getType() in PostAggregator is deprecated in favour of getType(ColumnInspector) (#11818)
