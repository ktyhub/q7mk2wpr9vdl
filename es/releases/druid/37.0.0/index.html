druida druida-37.0.0

Apache Druid 37.0.0 contiene más de 255 funciones nuevas, correcciones de errores, mejoras de rendimiento, mejoras de documentación y cobertura de pruebas adicionales de 29 contribuyentes.

Consulte el conjunto completo de cambios para obtener detalles adicionales, incluidas correcciones de errores.

Revise las notas de actualización y los cambios incompatibles antes de actualizar a Druid 37.0.0. Si está actualizando varias versiones, consulte la página [Notas de actualización] (upgrade-notes.md), que enumera las notas de actualización para las versiones más recientes de Druid.

Funciones importantes, cambios y obsolescencias

Esta sección contiene información importante sobre funciones nuevas y existentes.

Ingestión basada en Hadoop

Se eliminó la compatibilidad con la ingesta basada en Hadoop. La característica quedó obsoleta en Druid 34.

Utilice uno de los otros métodos de ingesta admitidos por Druid, como la ingesta basada en SQL o la ingesta sin MiddleManager utilizando Kubernetes.

#19109

Lista de bloqueo de consultas

Ahora puede utilizar el Broker API (/druid/coordinator/v1/config/broker) para crear una lista de bloqueo de consultas para bloquear consultas dinámicamente por fuente de datos, tipo de consulta o contexto de consulta. La lista de bloqueo entra en vigor sin que Druid reinicie. Las reglas de bloqueo utilizan la lógica AND, lo que significa que todos los criterios deben coincidir.

El siguiente ejemplo bloquea todas las consultas groupBy en la fuente de datos wikipedia con un parámetro de contexto de consulta de priority igual a 0:

POST /druid/coordinator/v1/config/broker
  {
    "queryBlocklist": [
      {
        "ruleName": "block-wikipedia-groupbys",
        "dataSources": ["wikipedia"],
        "queryTypes": ["groupBy"],
        "contextMatches": {"priority": "0"}
      }
    ]
  }

#19011

Compactación menor para compactación basada en Overlord (experimental)

Ahora puede configurar la compactación menor para compactar solo los segmentos recientemente ingeridos mientras actualiza los segmentos compactados existentes. Cuando Druid actualiza segmentos, actualiza los metadatos en lugar de utilizar recursos para compactarlos nuevamente. Puede utilizar el motor de compactación nativo o el motor de tareas MSQ.

Utilice la política de compactación mostFragmentedFirst y establezca un porcentaje de umbral basado en filas o en bytes para una compactación menor.

#19059 #19205 #19016

Reindexación en cascada (experimental)

Al utilizar la reindexación en cascada, ahora puede definir reglas basadas en la edad para aplicar automáticamente diferentes configuraciones de compactación según la antigüedad de sus datos. Mientras que la compactación automática estándar aplica una única configuración plana en toda una fuente de datos, la reindexación en cascada le permite adaptar la configuración de compactación a las características de sus datos.

Por ejemplo, puede mantener los datos recientes en segmentos por hora y, al mismo tiempo, pasar automáticamente a segmentos diarios después de 90 días para reducir el recuento de segmentos. También puede aplicar capas de eliminación de filas basadas en la edad (como eliminar el tráfico de bots de datos más antiguos), cambiar la configuración de compresión o pasar a un resumen con una granularidad de consulta más gruesa a medida que los datos envejecen. Las reglas se definen en línea en la especificación del supervisor.

Debe utilizar supervisores de compactación con el motor de tareas MSQ para utilizar la reindexación en cascada.

#18939 #19213 #19106 #19078

Ingestión de múltiples supervisores

La ingesta de múltiples supervisores ahora está disponible de forma generalizada. Puede ejecutar varios supervisores de flujo que ingieran en la misma fuente de datos.

#18983

Autorizador de solo lectura

Se agregó un autorizador ReadOnly a Druid. Este es el primer autorizador global de Druid. El autorizador impone una restricción global a todas las operaciones que no sean LECTURA, negándolas independientemente de los permisos de los usuarios individuales. Puede utilizar esta capacidad para garantizar que todos los usuarios de un autorizador específico estén limitados al acceso de LECTURA.

Existe una limitación conocida por la que algunos puntos finales actualmente requieren acceso de ESCRITURA a pesar de ser de solo LECTURA, como GET /druid/indexer/v1/supervisor. Estas operaciones fracasarán.

#19243

Formato de entrada de ahorro

Como parte de la extensión del colaborador de Thrift, Druid ahora admite datos codificados en Thrift para la ingesta de streaming de Kafka y Kinesis mediante InputFormat. Anteriormente, Druid admitía esto a través de analizadores, que se eliminaron en Druid 37.

#19111

Para utilizar esta función, debe agregar druid-thrift-extensions a su lista de carga de extensiones.

Caché incremental

La caché de metadatos de segmento incremental (useIncrementalCache) ahora está disponible de forma general y su valor predeterminado es ifSynced. Druid bloquea las lecturas del caché hasta que se sincroniza con el almacén de metadatos al menos una vez después de convertirse en líder.

#19252

Gestión de tareas basada en Kubernetes

Esta extensión ya está disponible de forma generalizada.

#19128

Contexto de consulta predeterminado dinámico

Ahora puede agregar parámetros de contexto de consulta predeterminados como una configuración dinámica al Broker. Esto le permite anular los valores predeterminados estáticos establecidos en sus propiedades de tiempo de ejecución sin reiniciar su implementación o tener que actualizar varias consultas individualmente. Druid aplica parámetros de contexto de consulta según la siguiente prioridad:

  1. El contexto de consulta incluido con la consulta.
  2. El contexto de consulta establecido como una configuración dinámica en el Broker
  3. Los parámetros del contexto de consulta establecidos en las propiedades del tiempo de ejecución.
  4. Los valores predeterminados que vienen con Druid

Tenga en cuenta que, al igual que otras configuraciones dinámicas de Broker, esta es la opción de mejor esfuerzo. Es posible que la configuración no se aplique en ciertos casos, como cuando un Broker se ha iniciado recientemente y aún no ha recibido la configuración, o si el El corredor no puede comunicarse con el Coordinador. Si un parámetro de contexto de consulta es fundamental para todas sus consultas, configúrelo en las propiedades del tiempo de ejecución.

#19144

Mesa sys.queries (experimental)

La nueva tabla de consultas del sistema proporciona información sobre las consultas actualmente en ejecución y completadas recientemente que utilizan el motor Dart. Esta tabla está desactivada de forma predeterminada. Para habilitar la tabla, configure lo siguiente:

druid.sql.planner.enableSysQueriesTable = true

Como parte de este cambio, el /druid/v2/sql/queries API ahora admite un parámetro includeComplete que muestra consultas completadas recientemente.

#18923

Autocompactación con supervisores de compactación

Se ha mejorado la compactación automática mediante supervisores de compactación, ahora está disponible de forma generalizada y es el valor predeterminado recomendado. Las tareas de compactación automática ahora tienen el prefijo auto en lugar de coordinator-issued.

Como parte de la mejora, los estados de compactación ahora se almacenan en una ubicación central, una nueva mesa indexingStates. Los segmentos individuales solo necesitan almacenar una referencia única (indexing_state_fingerprint) hasta su estado de compactación total.

Dado que muchos segmentos en una única fuente de datos comparten el mismo estado de compactación subyacente, esto reduce en gran medida los requisitos de almacenamiento de metadatos para la compactación automática.

Para compatibilidad con versiones anteriores, Druid continúa conservando el estado de compactación detallado en cada segmento. Esta funcionalidad se eliminará en una versión futura. Puede dejar de almacenar el estado de compactación detallado configurando storeCompactionStatePerSegment en false en la configuración de compactación del clúster. Si lo desactiva y necesita bajar la versión, Druid necesita volver a compactar cualquier segmento que se haya compactado desde que cambió la configuración.

Este cambio tiene impactos de actualización para el almacenamiento de metadatos y el almacenamiento en caché de metadatos. Para obtener más información, consulte la nota de actualización Almacenamiento de metadatos para autocompactación con supervisores de compactación.

#19113 #18844 #19252

Selección de nivel de corredor para servidores en tiempo real

Se agregaron druid.broker.realtime.select.tier y druid.broker.realtime.balancer.type en los Brokers para anular opcionalmente la selección de niveles del Broker y las estrategias de equilibrio para servidores en tiempo real. Si estas propiedades no están configuradas (el valor predeterminado), los servidores en tiempo real continúan usando las configuraciones druid.broker.select y druid.broker.balancer existentes que se aplican tanto a los servidores históricos como a los de tiempo real.

#19062

Enrutamiento manual del agente en la consola web

Ahora puede configurar qué Broker utiliza el enrutador para las consultas emitidas desde la consola web. Es posible que desee hacer esto si hay corredores que no tienen visibilidad en ciertos niveles de datos y sabe que está consultando datos disponibles solo en un nivel determinado.

Para especificar un corredor, agregue la siguiente configuración a web-console/console-config.js:

consoleBrokerService: 'druid/BROKER_NAME'

#19069

Extensión del cónsul

La extensión de colaborador druid-consul-extensions permite que los clústeres de Druid utilicen Consul para el descubrimiento de servicios y Elección de coordinador/líder supremo en lugar de ZooKeeper. La extensión admite ACL, TLS/mTLS y métricas.

Antes de cambiar a Consul, debe configurar druid.serverview.type=http y druid.indexer.runner.type=httpRemote en todo el grupo.

Ingestión de streaming

Se ha cambiado el comportamiento de taskCountMin y taskCountStart para el escalado automático. Druid ahora calcula el número inicial de tareas a iniciar verificando las configuraciones en el siguiente orden: taskCountStart (opcional), luego taskCount (en ioConfig), luego taskCountMin.

Aislamiento de consultas mejorado

Se agregó el parámetro serverPriorityToReplicas a las especificaciones del supervisor de transmisión (Kafka, Kinesis y Rabbit). Esto permite a los operadores distribuir réplicas de tareas entre diferentes prioridades de servidor para tareas de indexación en tiempo real. De manera similar a la organización por niveles históricos, esto permite el aislamiento de consultas para escenarios de cargas de trabajo mixtas en los Peons, lo que permite que algunas réplicas de tareas manejen consultas de prioridades específicas.

Consultando

grupoPor configuración de consulta

Se agregó una nueva propiedad de configuración de consulta groupBy druid.query.groupBy.maxSpillFileCount para limitar la cantidad máxima de archivos de derrame creados por consulta. #19141

Manejo mejorado de agregados anidados

Druida ahora puede fusionar dos agregados con una proyección entre ellos. Por ejemplo, la siguiente consulta:

SELECT
  hr,
  UPPER(t1.x) x,
  SUM(t1.cnt) cnt,
  MIN(t1.mn) mn,
  MAX(t1.mx) mx
FROM (
  SELECT
    floor(__time to hour) hr,
    dim2 x,
    COUNT(*) cnt,
    MIN(m1 * 5) mn,
    MAX(m1 + m2) mx
  FROM druid.foo
  WHERE dim2 IN ('abc', 'def', 'a', 'b', '')
  GROUP BY 1, 2
) t1
WHERE t1.x IN ('abc', 'foo', 'bar', 'a', '')
GROUP BY 1, 2

se puede simplificar a lo siguiente:

SELECT
  FLOOR(__time TO hour) hr,
  UPPER(dim2) x,
  COUNT(*) cnt,
  MIN(m1 * 5) mn,
  MAX(m1 + m2) mx
FROM druid.foo
WHERE dim2 IN ('abc', 'a', '')
GROUP BY 1, 2

Gestión de clústeres

Nuevas estrategias de selección de niveles de broker

Los operadores ahora pueden configurar dos nuevas implementaciones de Broker TierSelectorStrategy:

  • strict: solo selecciona servidores cuyas prioridades coincidan con la lista configurada. Configuración de ejemplo: druid.broker.select.tier=strict y druid.broker.select.tier.strict.priorities=[1].
  • pooled: agrupa servidores según las prioridades configuradas y selecciona entre ellas, lo que permite que las consultas utilicen múltiples niveles de prioridad para mejorar la disponibilidad. Configuración de ejemplo: druid.broker.select.tier=pooled y druid.broker.select.tier.pooled.priorities=[2,1].

También puede utilizar druid.broker.realtime.select.tier para configurar estas estrategias para servidores en tiempo real.

Gestión de datos

Configuración de tiempo de espera por segmento

Ahora puedes establecer un tiempo de espera para los segmentos en una fuente de datos específica usando una configuración dinámica:

POST /druid/coordinator/v1/config/broker
  {
    "perSegmentTimeoutConfig": {
      "my_large_datasource": { "perSegmentTimeoutMs": 5000, "monitorOnly": false },
      "my_new_datasource": { "perSegmentTimeoutMs": 3000, "monitorOnly": true }
    }
  }

Esto resulta útil cuando diferentes fuentes de datos tienen diferentes características de rendimiento; por ejemplo, permiten tiempos de espera más prolongados para conjuntos de datos más grandes.

#19221

Limpiador de almacenamiento duradero

El limpiador de almacenamiento duradero ahora admite retención configurable basada en tiempo para los resultados de consultas MSQ. Anteriormente, los resultados de las consultas se conservaban para todas las tareas conocidas, lo que no era fiable para las tareas completadas. Con este cambio, los resultados de la consulta se conservan durante un período de tiempo configurable según el tiempo de creación de la tarea.

La nueva propiedad de configuración druid.msq.intermediate.storage.cleaner.durationToRetain controla el período de retención de los resultados de la consulta. El período de retención predeterminado es de 6 horas.

Extensiones

Kubernetes

Se agregó un nuevo paso WebClientOptions para Vert.x HTTP client en kubernetes-overlord-extensions. Los operadores ahora pueden configurar cualquier propiedad en el objeto Vert.x WebClientOptions subyacente utilizando las propiedades de tiempo de ejecución de Druid. Algunas de las opciones que puede configurar incluyen el tamaño del grupo de conexiones, tiempos de espera de mantenimiento y tiempos de espera de inactividad. Esto es particularmente útil para entornos con balanceadores de carga intermedios que cierran conexiones inactivas. La mayoría de las implementaciones de Druid no necesitarán esta configuración.

Filtros

Ahora puede configurar filtros residuales para columnas sin partición cuando utiliza la fuente de entrada Iceberg. Configure residualFilterMode en la fuente de entrada Iceberg en uno de los siguientes:

ALTER TABLE druid_segments ADD COLUMN indexing_state_fingerprint VARCHAR(255);

druid druid-37.0.0

Apache Druid 37.0.0 contains over 255 new features, bug fixes, performance enhancements, documentation improvements, and additional test coverage from 29 contributors.

See the complete set of changes for additional details, including bug fixes.

Review the upgrade notes and incompatible changes before you upgrade to Druid 37.0.0. If you are upgrading across multiple versions, see the Upgrade notes page, which lists upgrade notes for the most recent Druid versions.

Important features, changes, and deprecations

This section contains important information about new and existing features.

Hadoop-based ingestion

Support for Hadoop-based ingestion has been removed. The feature was deprecated in Druid 34.

Use one of Druid's other supported ingestion methods, such as SQL-based ingestion or MiddleManager-less ingestion using Kubernetes.

#19109

Query blocklist

You can now use the Broker API (/druid/coordinator/v1/config/broker) to create a query blocklist to dynamically block queries by datasource, query type, or query context. The blocklist takes effect without a restarting Druid. Block rules use AND logic, which means all criteria must match.

The following example blocks all groupBy queries on the wikipedia datasource with a query context parameter of priority equal to 0:

POST /druid/coordinator/v1/config/broker
  {
    "queryBlocklist": [
      {
        "ruleName": "block-wikipedia-groupbys",
        "dataSources": ["wikipedia"],
        "queryTypes": ["groupBy"],
        "contextMatches": {"priority": "0"}
      }
    ]
  }

#19011

Minor compaction for Overlord-based compaction (experimental)

You can now configure minor compaction to compact only newly ingested segments while upgrading existing compacted segments. When Druid upgrades segments, it updates the metadata instead of using resources to compact it again. You can use the native compaction engine or the MSQ task engine.

Use the mostFragmentedFirst compaction policy and set either a percentage of rows-based or byte-based threshold for minor compaction.

#19059 #19205 #19016

Cascading reindexing (experimental)

Using cascading reindexing, you can now define age-based rules to automatically apply different compaction configurations based on the age of your data. While standard auto-compaction applies a single flat configuration across an entire datasource, cascading reindexing lets you tailor your compaction settings to the characteristics of your data.

For example, you can keep recent data in hourly segments while automatically rolling up to daily segments after 90 days to reduce segment count. You can also layer on age-based row deletion (such as dropping bot traffic from older data), change compression settings, or shift to rollup with coarser query granularity as data ages. Rules are defined inline in the supervisor spec.

You must use compaction supervisors with the MSQ task engine to use cascading reindexing.

#18939 #19213 #19106 #19078

Multi-supervisor ingestion

Multi-supervisor ingestion is now generally available. You can run multiple stream supervisors that ingest into the same datasource.

#18983

Read-only authorizer

Added a ReadOnly authorizer to Druid. This is the first global authorizer for Druid. The authorizer enforces a global restriction on all non-READ operations, denying them regardless of individual user permissions. You can use this capability to ensure all users of a specific authorizer are limited to READ access.

There is a known limitation where some endpoints currently require WRITE access despite being READ-only, such as GET /druid/indexer/v1/supervisor. These operations will fail.

#19243

Thrift input format

As part of the Thrift contributor extension, Druid now supports Thrift-encoded data for Kafka and Kinesis streaming ingestion using InputFormat. Previously, Druid supported this through parsers, which have been removed in Druid 37.

#19111

To use this feature, you must add druid-thrift-extensions to your extension load list.

Incremental cache

Incremental segment metadata cache (useIncrementalCache) is now generally available and defaults to ifSynced. Druid blocks reads from the cache until it has synced with the metadata store at least once after becoming leader.

#19252

Kubernetes-based task management

This extension is now generally available.

#19128

Dynamic default query context

You can now add default query context parameters as a dynamic configuration to the Broker. This allows you to override static defaults set in your runtime properties without restarting your deployment or having to update multiple queries individually. Druid applies query context parameters based on the following priority:

  1. The query context included with the query
  2. The query context set as a dynamic configuration on the Broker
  3. The query context parameters set in the runtime properties
  4. The defaults that ship with Druid

Note that like other Broker dynamic configuration, this is best-effort. Settings may not be applied in certain cases, such as when a Broker has recently started and hasn't received the configuration yet, or if the Broker can't contact the Coordinator. If a query context parameter is critical for all your queries, set it in the runtime properties.

#19144

sys.queries table (experimental)

The new system queries table provides information about currently running and recently completed queries that use the Dart engine. This table is off by default. To enable the table, set the following:

druid.sql.planner.enableSysQueriesTable = true

As part of this change, the /druid/v2/sql/queries API now supports an includeComplete parameter that shows recently completed queries.

#18923

Auto-compaction with compaction supervisors

Auto-compaction using compaction supervisors has been improved, now generally available, and the recommended default. Automatic compaction tasks are now prefixed with auto instead of coordinator-issued.

As part of the improvement compaction states are now stored in a central location, a new indexingStates table. Individual segments only need to store a unique reference (indexing_state_fingerprint) to their full compaction state.

Since many segments in a single datasource share the same underlying compaction state, this greatly reduces metadata storage requirements for automatic compaction.

For backwards compatibility, Druid continues to persist the detailed compaction state in each segment. This functionality will be removed in a future release.

You can stop storing detailed compaction state by setting storeCompactionStatePerSegment to false in the cluster compaction config. If you turn it off and need to downgrade, Druid needs to re-compact any segments that have been compacted since you changed the config.

This change has upgrade impacts for metadata storage and metadata caching. For more information, see the Metadata storage for auto-compaction with compaction supervisors upgrade note.

#19113 #18844 #19252

Broker tier selection for realtime servers

Added druid.broker.realtime.select.tier and druid.broker.realtime.balancer.type on the Brokers to optionally override the Broker’s tier selection and balancer strategies for realtime servers. If these properties are not set (the default), realtime servers continue to use the existing druid.broker.select and druid.broker.balancer configurations that apply to both historical and realtime servers.

#19062

Manual Broker routing in the web console

You can now configure which Broker the Router uses for queries issued from the web console. You may want to do this if there are Brokers that don't have visibility into certain data tiers, and you know you're querying data available only on a certain tier.

To specify a Broker, add the following config to web-console/console-config.js:

consoleBrokerService: 'druid/BROKER_NAME'

#19069

Consul extension

The contributor extension druid-consul-extensions lets Druid clusters use Consul for service discovery and Coordinator/Overlord leader election instead of ZooKeeper. The extension supports ACLs, TLS/mTLS, and metrics.

Before you switch to Consul, you need to set druid.serverview.type=http and druid.indexer.runner.type=httpRemote cluster wide.

Improved handling of nested aggregates

Druid can now merge two aggregates with a projection between them. For example, the following query:

SELECT
  hr,
  UPPER(t1.x) x,
  SUM(t1.cnt) cnt,
  MIN(t1.mn) mn,
  MAX(t1.mx) mx
FROM (
  SELECT
    floor(__time to hour) hr,
    dim2 x,
    COUNT(*) cnt,
    MIN(m1 * 5) mn,
    MAX(m1 + m2) mx
  FROM druid.foo
  WHERE dim2 IN ('abc', 'def', 'a', 'b', '')
  GROUP BY 1, 2
) t1
WHERE t1.x IN ('abc', 'foo', 'bar', 'a', '')
GROUP BY 1, 2

can be simplified to the following:

SELECT
  FLOOR(__time TO hour) hr,
  UPPER(dim2) x,
  COUNT(*) cnt,
  MIN(m1 * 5) mn,
  MAX(m1 + m2) mx
FROM druid.foo
WHERE dim2 IN ('abc', 'a', '')
GROUP BY 1, 2

The Iceberg input source now supports GCS warehouses. To use this feature, you must load the druid-google-extensions extension in addition to the Iceberg extension. #19137

Filters

You can now configure residual filters for non-partition columns when using the Iceberg input source. Set residualFilterMode in the Iceberg input source to one of the following:

  • ignore: (default) Ingest the residual rows with a warning log unless filtered by transformSpec.
  • fail: Fail the ingestion job when residual filters are detected. Use this to ensure that filters only target partition columns.

#18953

HDFS storage

Added support for lz4 compression. As part of this change, the following metrics are now available:

  • hdfs/pull/size
  • hdfs/pull/duration
  • hdfs/push/size
  • hdfs/push/duration

#18982

Upgrade notes and incompatible changes

Upgrade notes

Hadoop-based ingestion

Support for Hadoop-based ingestion has been removed. The feature was deprecated in Druid 34.

Use one of Druid's other supported ingestion methods, such as SQL-based ingestion or MiddleManager-less ingestion using Kubernetes.

#19109

AWS SDK v2

Druid now uses AWS SDK version 2.40.0 since v1 of the SDK is at end of life.

#18891

Segment metadata cache on by default

Starting in Druid 37, the segment metadata cache is on by default. This feature allows the Broker to cache segment metadata polled from the Coordinator, rather than having to fetch metadata for every query against the sys.segments table. This improves performance but increases memory usage on Brokers.

The druid.sql.planner.metadataSegmentCacheEnable config controls this feature.

#19075

Parser changes

Streaming ingestion parser

Support for the deprecated parser has been removed for streaming ingest tasks such as Kafka and Kinesis. Operators must now specify inputSource/inputFormat on the ioConfig of the supervisor spec, and the dataSchema must not specify a parser. Do this before upgrading to Druid 37 or newer.

#19173 #19166

Removed ParseSpec and deprecated parsers

The Parser for native batch tasks and streaming ingestion indexing services has been removed. Where possible, use the input format instead. Note that JavascriptParseSpec and JSONLowercaseParseSpec have no InputFormat equivalents.

Druid supports custom text data formats and can use the Regex input format to parse them. However, be aware doing this to parse data is less efficient than writing a native Java InputFormat extension, or using an external stream processor. We welcome contributions of new input formats.

#19239

Rolling upgrades from Druid versions prior to version 0.23

You can't perform a rolling upgrade from versions earlier than Druid 0.23.

#18961

Metadata storage for auto-compaction with compaction supervisors

Automatic compaction with supervisors requires incremental segment metadata caching on the Overlord and a new metadata store table; no action is required if you are using the default settings for the following configs:

  • druid.manager.segments.useIncrementalCache
  • druid.metadata.storage.connector.createTables

If druid.manager.segments.useIncrementalCache is set to never, update it to ifSynced or always. For more information about the config, see Segment metadata cache.

If you set the druid.metadata.storage.connector.createTables config to false, you need to manually alter the segments table and create the compactionStates table. The Postgres DDL is provided below as a guide:

-- create the indexing states lookup table and associated indices
CREATE TABLE druid_indexingStates (
    created_date VARCHAR(255) NOT NULL,
    datasource VARCHAR(255) NOT NULL,
    fingerprint VARCHAR(255) NOT NULL,
    payload BYTEA NOT NULL,
    used BOOLEAN NOT NULL,
    pending BOOLEAN NOT NULL,
    used_status_last_updated VARCHAR(255) NOT NULL,
    PRIMARY KEY (fingerprint),
  );

  CREATE INDEX idx_druid_compactionStates_used ON druid_compactionStates(used, used_status_last_updated);

-- modify druid_segments table to have a column for storing compaction state fingerprints
ALTER TABLE druid_segments ADD COLUMN indexing_state_fingerprint VARCHAR(255);

You may have to adapt the syntax to fit your table naming prefix and metadata store backend.

#18844

Segment locking

Segment locking and NumberedOverwriteShardSpec are deprecated and will be removed in a future release. Use time chunk locking instead. You can make sure only time chunk locking is used by setting druid.indexer.tasklock.forceTimeChunkLock to true, which is the default.

#19050

Incompatible changes

Removed defaultProcessingRate config

This config allowed scaling actions to begin prior to the first metrics becoming available.

#19028

Front-coding format

Druid now defaults to v1 of the front-coded format instead of version 0 if enabled. Version 1 was introduced in Druid 26. Downgrading to or upgrading from a version of Druid prior to 26 may require reindexing if you have front-coding enabled with version 0.
