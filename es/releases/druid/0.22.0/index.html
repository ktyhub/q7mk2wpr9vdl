druida druida-0.22.0

Apache Druid 0.22.0 contiene más de 400 funciones nuevas, correcciones de errores, mejoras de rendimiento, mejoras de documentación y cobertura de pruebas adicionales de 73 contribuyentes. Consulte el conjunto completo de cambios para obtener detalles adicionales.

<a name="22-new-features" href="#22-new-features">#</a> Nuevas funciones

<a name="22-query" href="#22-query">#</a> Motor de consultas

<a name="22-multi-distinct" href="#22-multi-distinct">#</a> Compatibilidad con múltiples agregadores distintos en la misma consulta

Druid ahora puede admitir múltiples recuentos 'exactos' de DISTINCT utilizando el agregador de agrupación que normalmente se utiliza con conjuntos de agrupación. Tenga en cuenta que esto solo se aplica a recuentos exactos, cuando druid.sql.planner.useApproximateCountDistinct es falso y se puede habilitar configurando druid.sql.planner.useGroupingSetForExactDistinct en true. https://github.com/apache/druid/pull/11014

<a name="22-array-agg" href="#22-array-agg">#</a> Funciones de agregación SQL ARRAY_AGG y STRING_AGG

Se ha agregado la función de agregación ARRAY_AGG para permitir acumular valores o valores distintos de una columna en un único resultado de matriz. Esta versión también agrega STRING_AGG, que es similar a ARRAY_AGG, excepto que une los valores de la matriz en una sola cadena con un 'delimitador' proporcionado e ignora los valores nulos. Ambas funciones aceptan un parámetro de tamaño máximo para controlar el tamaño máximo del resultado y fallarán si se excede este valor. Consulte la documentación SQL para obtener detalles adicionales. https://github.com/apache/druid/pull/11157 https://github.com/apache/druid/pull/11241

<a name="22-bitwise" href="#22-bitwise">#</a> Expresiones y agregadores de funciones matemáticas bit a bit

Varias funciones SQL nuevas para realizar matemáticas 'bit a bit' (junto con las expresiones nativas correspondientes), incluidas BITWISE_AND, BITWISE_OR, BITWISE_XOR, etc. Además, se agregaron las funciones de agregación BIT_AND, BIT_OR y BIT_XOR para acumular valores en una columna con la función bit a bit correspondiente. Para obtener detalles completos, consulte la documentación SQL. https://github.com/apache/druid/pull/10605 https://github.com/apache/druid/pull/10823 https://github.com/apache/druid/pull/11280

<a name="22-human-format" href="#22-human-format">#</a> Funciones de formato de números legibles por humanos

Se han agregado tres nuevas funciones de formato de número de expresión nativa y SQL en Druid 0.22.0, HUMAN_READABLE_BINARY_BYTE_FORMAT, HUMAN_READABLE_DECIMAL_BYTE_FORMAT y HUMAN_READABLE_DECIMAL_FORMAT, que permiten transformar los resultados a un formato de consumo más amigable para los resultados de las consultas. Para obtener más información, consulte la documentación SQL. https://github.com/apache/druid/issues/10584 https://github.com/apache/druid/pull/10635

<a name="22-expr-agg" href="#22-expr-agg">#</a> Agregador de expresiones

Druid 0.22.0 agrega una nueva función de agregación de expresiones de consulta JSON 'nativa', que le permite usar expresiones nativas de Druid para realizar operaciones de "plegar" (alternativamente conocidas como "reducir") para acumular algún valor en cualquier número de columnas de entrada. Esto agrega una flexibilidad significativa a lo que se puede hacer en un agregador Druid, similar en muchos aspectos a lo que era posible con el agregador Javascript, pero de una manera mucho más segura y protegida. Las expresiones que ahora pueden realizar un "pliegue" en las columnas de entrada también realmente completan las capacidades de las expresiones nativas, además de las funciones de "mapa" (columnas virtuales de expresión), "filtro" (filtros de expresión) y post-transformación (post-agregadores de expresión) que antes eran posibles. Dado que utiliza expresiones, el rendimiento aún no es óptimo y aún no está documentado directamente, pero es la tecnología subyacente detrás de SQL ARRAY_AGG, STRING_AGG y las funciones de agregador bit a bit que también se agregan en esta versión. https://github.com/apache/druid/pull/11104

<a name="22-sql-routing" href="#22-sql-routing">#</a> Mejoras en el enrutamiento de consultas SQL

Druid 0.22 agrega algunas funciones nuevas para brindar a los escritores de extensiones un control mejorado sobre cómo se enrutan las consultas entre los enrutadores y corredores de Druid. El primero agrega una nueva estrategia de selección de broker manual al enrutador Druid, que permite que una consulta especifique manualmente a qué brokers Druid se debe enviar una consulta en función de un parámetro de contexto de consulta brokerService a cualquier grupo de brokers definido en druid.router.tierToBrokerMap (esto corresponde al 'nombre de servicio' del conjunto de brokers, druid.service). La segunda característica nueva permite al enrutador Druid analizar y examinar consultas SQL para que las estrategias de selección de intermediarios también puedan funcionar para consultas SQL. Esto se puede habilitar configurando druid.router.sql.enable en verdadero. Esto no afecta a las consultas JDBC, que utilizan un mecanismo diferente para facilitar conexiones "fijas" a un único intermediario. https://github.com/apache/druid/pull/11566 https://github.com/apache/druid/pull/11495

<a name="22-query-error-log" href="#22-query-error-log">#</a> Registro de errores de consulta mejorado

<a name="22-batch" href="#22-batch">#</a> Ingestión de lotes nativos

<a name="22-shuffle-deep-storage" href="#22-shuffle-deep-storage">#</a> Compatibilidad con el uso de almacenamiento profundo para datos aleatorios intermedios

Las tareas de ingesta de dos fases de 'acumulación perfecta' nativa de Druid ahora admiten el uso de almacenamiento profundo como ubicación aleatoria, como una alternativa a los discos locales en administradores intermedios o indexadores. Para utilizar esta función, configure druid.processing.intermediaryData.storage.type en deepstore, que utiliza el tipo de almacenamiento profundo configurado. Nota: Con el tipo "almacenamiento profundo", los datos se almacenan en el directorio shuffle-data en la ruta de almacenamiento profundo configurada; la limpieza automática para este directorio aún no es compatible. Se pueden configurar reglas del ciclo de vida del almacenamiento en la nube para la limpieza automática de datos en la ubicación del prefijo shuffle-data. https://github.com/apache/druid/pull/11507

<a name="22-batch-memory" href="#22-batch-memory">#</a> Uso de memoria de la tarea de ingesta por lotes nativa mejorada

La ingesta por lotes nativa de Druid ha recibido una nueva opción de configuración, druid.indexer.task.batchProcessingMode, que introduce dos nuevos modos operativos que deberían permitir que la ingesta por lotes funcione con una huella de uso de memoria dinámica más pequeña y predecible. El modo CLOSED_SEGMENTS_SINKS es el más agresivo y debería tener el menor consumo de memoria, y funciona eliminando en la memoria el seguimiento y el mmap de los segmentos intermedios producidos durante la creación del segmento, pero no está muy bien probado en este momento, por lo que se considera experimental. CLOSED_SEGMENTS, que es la nueva opción predeterminada, elimina mmap de segmentos intermedios, pero aún rastrea todo el conjunto de segmentos en el montón, aunque está relativamente bien probado en este punto y se considera estable. OPEN_SEGMENTS utilizará la ruta de ingesta anterior, que se comparte con la ingesta de streaming y realiza un mmap en segmentos intermedios y crea una línea de tiempo para que estos segmentos puedan consultarse mediante consultas en tiempo real. Esto no es necesario en absoluto para el lote, pero se puede seleccionar el modo OPEN_SEGMENTS si ocurre algún problema con los 2 modos más nuevos. https://github.com/apache/druid/pull/11123 https://github.com/apache/druid/pull/11294 https://github.com/apache/druid/pull/11536

<a name="22-batch-wait-for-handoff" href="#22-batch-wait-for-handoff">#</a> Permitir que las tareas por lotes esperen hasta la transferencia del segmento antes de completarse

Las tareas de ingesta por lotes nativas de Druid ahora se pueden configurar opcionalmente para que no finalicen hasta que los servidores históricos hayan cargado completamente los segmentos ingeridos. Esto puede resultar útil en escenarios en los que vale la pena utilizar el estado de la tarea como medida para saber si la ingesta se ha completado y los segmentos están disponibles para consultar a cambio de mantener ocupado un espacio de tarea adicional. Esto se puede habilitar agregando awaitSegmentAvailabilityTimeoutMillis a tuningConfig en la especificación de ingesta, que especifica la cantidad máxima de tiempo que una tarea esperará a que se carguen los segmentos antes de finalizar. Si no todos los segmentos están disponibles cuando expire este tiempo de espera, el trabajo aún se realizará correctamente. Sin embargo, en el informe de ingesta, segmentAvailabilityConfirmed será falso. Esto indica que la transferencia no se realizó correctamente y es posible que no todos estos segmentos recién indexados estén disponibles para su consulta. Por otro lado, si todos los segmentos quedan disponibles para su consulta en los servicios históricos antes de que expire el tiempo de espera, el valor de esa clave en el informe será verdadero. Este valor tuningConfig no se admite para tareas de compactación en este momento. Si un usuario intenta especificar un valor para awaitSegmentAvailabilityTimeoutMillis para Compactación, la tarea fallará y le indicará que no es compatible. https://github.com/apache/druid/pull/10676

<a name="22-compact" href="#22-compact">#</a> Gestión del ciclo de vida de los datos

<a name="22-compact-granularity" href="#22-compact-granularity">#</a> Admite la gestión de segmentos y granularidad de consultas para la autocompactación

La compactación manual y automática de Druid ahora se puede configurar para cambiar la granularidad del segmento, y la compactación manual también puede cambiar la granularidad de la consulta. Además, la compactación preservará la granularidad del segmento de forma predeterminada. Esto permite a los operadores realizar opciones más fácilmente, como cambiar datos antiguos a segmentos más grandes y consultar granularidades a cambio de un menor tamaño de datos. Consulte documentos de compactación para obtener más detalles. https://github.com/apache/druid/pull/10843 https://github.com/apache/druid/pull/10856 https://github.com/apache/druid/pull/10900 https://github.com/apache/druid/pull/10912 https://github.com/apache/druid/pull/11009

<a name="22-compact-skip-lock" href="#22-compact-skip-lock">#</a> Permitir que la compactación omita temporalmente los intervalos bloqueados

La autocompactación de Druid ahora omitirá temporalmente de forma predeterminada los intervalos bloqueados en lugar de esperar a que el bloqueo se libere, lo que debería mejorar la velocidad a la que se pueden compactar las fuentes de datos. Esto está controlado por druid.coordinator.compaction.skipLockedIntervals y se puede establecer en falso si este comportamiento no es deseado por algún motivo. https://github.com/apache/druid/pull/11190

<a name="22-config-cleanup" href="#22-config-cleanup">#</a> Soporte para limpieza automática adicional de metadatos

Puede configurar la limpieza automática para eliminar registros del almacén de metadatos después de eliminar algunas entidades de Druid:

  • registros de segmentos
  • registros de auditoría
  • registros del supervisor
  • registros de reglas
  • registros de configuración de compactación
  • registros de fuentes de datos creados por supervisores Esta característica ayuda a mantener el rendimiento cuando tiene una alta tasa de abandono de fuentes de datos, lo que significa que con frecuencia crea y elimina muchas fuentes de datos de corta duración u otras entidades relacionadas. Puede limitar el período de tiempo para conservar los registros de metadatos no utilizados para evitar que se llene su almacén de metadatos. Consulte [documentación de limpieza automática] (https://druid.apache.org/docs/0.22.0/operations/clean-metadata-store.html) para obtener más información. https://github.com/apache/druid/pull/11078 https://github.com/apache/druid/pull/11084 https://github.com/apache/druid/pull/11164 https://github.com/apache/druid/pull/11200 https://github.com/apache/druid/pull/11227 https://github.com/apache/druid/pull/11232 https://github.com/apache/druid/pull/11245

<a name="22-data-cleanup" href="#22-data-cleanup">#</a> Eliminación de datos

Se ha agregado una nueva configuración, dropExisting al ioConfig de las tareas de ingesta y compactación por lotes nativas de Druid, que si se establece en verdadero (y appendToExist es falso), la tarea de ingesta marcará transaccionalmente todos los segmentos existentes en el intervalo como no utilizados, reemplazándolos con el nuevo conjunto de segmentos. Esto puede resultar útil en casos de uso de compactación en los que el ensombrecimiento normal no reemplaza completamente un conjunto de segmentos en un intervalo, como cuando se cambia la granularidad del segmento a un tamaño más pequeño y algunos de los depósitos de granularidad más pequeños no tendrían datos, dejando los segmentos originales solo parcialmente ensombrecidos. Tenga en cuenta que esta funcionalidad aún es experimental y puede provocar que los datos no estén disponibles temporalmente dentro del interval compactado. Cambiar esta configuración no hace que los intervalos se vuelvan a compactar. De manera similar, markAsUnused se agregó como una opción a la tarea de matar druida, que marcará cualquier segmento en el intervalo proporcionado como "no utilizado" antes de eliminar todos los segmentos no utilizados. Esto es útil para permitir que la secuencia marcar no utilizado -> eliminar se produzca con una única llamada API para la persona que llama, además de permitir que la acción de desmarcar se produzca bajo un bloqueo de intervalo de tarea. https://github.com/apache/druid/pull/11070 https://github.com/apache/druid/pull/11025 https://github.com/apache/druid/pull/11501

<a name="22-coordinador" href="#22-coordinador">#</a> Coordinador

<a name="22-coord-timeout" href="#22-coord-timeout">#</a> Control sobre el comportamiento del tiempo de espera de carga del segmento del coordinador con administración de segmentos basada en Apache Zookeeper

Una nueva opción de configuración dinámica del coordinador Druid permite controlar el comportamiento cada vez que se agota el tiempo de espera de una acción de carga de segmento cuando se utiliza la gestión de segmentos basada en Zookeeper. replicateAfterLoadTimeout cuando se establece en verdadero, el coordinador intentará replicar el segmento que no se pudo cargar en un servidor histórico diferente. Esto ayuda a mejorar la disponibilidad del segmento si hay algunos servidores históricos lentos en el clúster. Sin embargo, el historial lento aún puede cargar el segmento más tarde y es posible que el coordinador deba emitir solicitudes de eliminación si el segmento está sobrerreplicado. https://github.com/apache/druid/pull/10213

<a name="22-coord-balance" href="#22-coord-balance">#</a> Equilibrio de segmentos del coordinador más rápido

Otra nueva opción de configuración dinámica del coordinador, useBatchedSegmentSampler, cuando se establece en verdadero puede proporcionar potencialmente un gran aumento de rendimiento en la velocidad a la que el coordinador puede procesar la fase de equilibrio de segmentos. Esto debería ser particularmente notable en tamaños de clústeres muy grandes con muchos segmentos, pero está deshabilitado de forma predeterminada para pecar de cauteloso. https://github.com/apache/druid/pull/11257

<a name="22-coord-replication" href="#22-coord-replication">#</a> Estado de carga mejorado API para calcular opcionalmente la replicación insuficiente según el tamaño del clúster

El estado de carga del coordinador Druid API ahora admite un nuevo parámetro de consulta de URL opcional, computeUsingClusterView, que cuando se especifica hará que el coordinador calcule una replicación insuficiente para los segmentos según la cantidad de servidores disponibles dentro del clúster en los que se puede replicar el segmento, en lugar del recuento de replicación configurado en la regla de carga. Por ejemplo, si las reglas de carga especifican 2 réplicas, pero solo hay 1 servidor que puede contener segmentos, este API no se informará como subrreplicado porque los segmentos están tan replicados como sea posible para el tamaño de clúster determinado. https://github.com/apache/druid/pull/11056

<a name="22-coord-rep-limit" href="#22-coord-rep-limit">#</a> Límites opcionales en el número de replicantes no primarios cargados por ciclo de coordinación

Una nueva configuración dinámica del coordinador, maxNonPrimaryReplicantsToLoad, con el valor predeterminado de Integer.MAX_VALUE, permite a los operadores definir un límite superior estricto en la cantidad de replicantes no primarios que se cargarán en un único ciclo de ejecución del coordinador. El valor predeterminado imitará el comportamiento que existe hoy. Uso de ejemplo: si establece esta configuración en 1000, el coordinador cargará un máximo de 1000 replicantes no primarios en cada ejecución del ciclo de ejecución. Es decir, si ingiere 2000 segmentos con un factor de replicación de 2, el coordinador cargaría 2000 replicantes primarios y 1000 replicantes no primarios en la primera ejecución. Luego, en la siguiente ejecución, se cargarán los últimos 1000 replicantes no primarios. https://github.com/apache/druid/pull/11135

<a name="22-up-dropped-zk-3.4" href="#22-up-dropped-zk-3.4">#</a> Se eliminó el soporte para Apache ZooKeeper 3.4

Siguiendo a 0.21, que oficialmente desaprobó el soporte para Zookeeper 3.4, [que ha estado al final de su vida útil por un tiempo] (https://mail-archives.apache.org/mod_mbox/zookeeper-user/202004.mbox/%3C41A7EC67-D8F4-4C3A-B2DB-C2741C2EECA3%40apache.org%3E), el soporte para ZooKeeper 3.4 ahora se eliminó en 0.22.0. Asegúrese de actualizar su clúster Zookeeper antes de actualizar su clúster Druid a 0.22.0. https://github.com/apache/druid/issues/10780 https://github.com/apache/druid/pull/11073

<a name="22-up-batch-lineage" href="#22-up-batch-lineage">#</a> Corrección de asignación de segmentos de ingesta de lotes nativos

Druid 0.22.0 incluye una importante corrección de errores en la indexación por lotes nativa donde las fallas transitorias de las subtareas de indexación pueden resultar en particiones no contiguas en los segmentos de resultados, que nunca serán consultables debido a la lógica que verifica el conjunto "completo". Este problema se resolvió en la última versión de Druid, pero requirió un cambio en el protocolo que utilizan las tareas por lotes para asignar segmentos, y este cambio puede causar problemas durante las degradaciones si decide retroceder de Druid 0.22.0 a una versión anterior. Para evitar errores en la tarea durante una degradación continua, configure

druid.indexer.task.default.context={ "useLineageBasedSegmentAllocation" : false }

en las propiedades de tiempo de ejecución de Overlord y espere a que se completen todas las tareas que tienen useLineageBasedSegmentAllocation configurado en verdadero antes de iniciar la degradación. Después de que se hayan completado todas estas tareas, la degradación no debería tener más problemas y la configuración se puede eliminar de la configuración de Overlord (recomendado, ya que querrás habilitar esta configuración si estás ejecutando Druid 0.22.0 o una versión más reciente). https://github.com/apache/druid/pull/11189

<a name="22-up-sql-buckets" href="#22-up-sql-buckets">#</a> Las series temporales de SQL ya no omiten depósitos vacíos con toda la granularidad

Antes de Druid 0.22, un grupo SQL por consulta que utiliza una única clave de agrupación universal (por ejemplo, solo agregadores) como SELECT COUNT(*), SUM(x) FROM y WHERE z = 'someval' produciría un conjunto de resultados vacío en lugar del [0, null] que se podría esperar de esta consulta que no coincide con resultados. Esto se debía a que, en el fondo, esto se planificaría en una consulta de serie temporal con granularidad 'TODA' y skipEmptyBuckets establecido en verdadero en el contexto de la consulta. Esta última opción provocó que los resultados de dicha consulta no arrojaran resultados, ya que no hay depósitos con valores para agregar y, por lo tanto, se omiten, generando un conjunto de resultados vacío en lugar de un conjunto de resultados "nulo". Este comportamiento se ha cambiado para que se comporte en línea con otras implementaciones de SQL, pero el comportamiento anterior se puede obtener estableciendo explícitamente skipEmptyBuckets en el contexto de consulta. https://github.com/apache/druid/pull/11188

<a name="22-up-reingest" href="#22-up-reingest">#</a> Cambios incompatibles con la reingestión de druidas

Las tareas por lotes que utilizan una fuente de entrada 'Druida' para reingerir datos de segmento ya no aceptarán las secciones de 'dimensiones' y 'métricas' de su especificación de tarea, y ahora usarán internamente un nuevo filtro de columnas para especificar qué columnas del segmento original deben conservarse. Además, timestampSpec ya no se ignora, lo que permite modificar o reemplazar la columna __time por una columna diferente. Estos cambios además corrigen un error por el cual las columnas transformadas se ignoraban y no estaban disponibles en los nuevos segmentos. https://github.com/apache/druid/pull/10267

<a name="22-up-ie11" href="#22-up-ie11">#</a> La consola web de Druid ya no es compatible con IE11 y otros navegadores antiguos

Es posible que algunas cosas aún funcionen, pero ya no es compatible oficialmente, por lo que se pueden utilizar las funciones más nuevas del Javascript para desarrollar la consola web. https://github.com/apache/druid/pull/11357

<a name="22-up-ie11" href="#22-up-ie11">#</a> Se modificó el tamaño máximo predeterminado de la cola de carga de segmentos

La configuración dinámica del coordinador druida maxSegmentsInNodeLoadingQueue se ha cambiado de ilimitada (0) a 100. Esto debería hacer que el coordinador se comporte de una manera mucho más relajada durante períodos de volatilidad del clúster, como una actualización continua, pero limita el número total de segmentos que se cargarán en cualquier ciclo de coordinador determinado a 100 por servidor, lo que puede reducir la velocidad a la que se inicia y carga desde el almacenamiento profundo un clúster completamente detenido. https://github.com/apache/druid/pull/11540

druid druid-0.22.0

Apache Druid 0.22.0 contains over 400 new features, bug fixes, performance enhancements, documentation improvements, and additional test coverage from 73 contributors. See the complete set of changes for additional details.

<a name="22-new-features" href="#22-new-features">#</a> New features

<a name="22-query" href="#22-query">#</a> Query engine

<a name="22-multi-distinct" href="#22-multi-distinct">#</a> Support for multiple distinct aggregators in same query

Druid now can support multiple DISTINCT 'exact' counts using the grouping aggregator typically used with grouping sets. Note that this only applies to exact counts - when druid.sql.planner.useApproximateCountDistinct is false, and can be enabled by setting druid.sql.planner.useGroupingSetForExactDistinct to true.

https://github.com/apache/druid/pull/11014

<a name="22-array-agg" href="#22-array-agg">#</a> SQL ARRAY_AGG and STRING_AGG aggregator functions

The ARRAY_AGG aggregation function has been added, to allow accumulating values or distinct values of a column into a single array result. This release also adds STRING_AGG, which is similar to ARRAY_AGG, except it joins the array values into a single string with a supplied 'delimiter' and it ignores null values. Both of these functions accept a maximum size parameter to control maximum result size, and will fail if this value is exceeded. See SQL documentation for additional details.

https://github.com/apache/druid/pull/11157 https://github.com/apache/druid/pull/11241

<a name="22-bitwise" href="#22-bitwise">#</a> Bitwise math function expressions and aggregators

Several new SQL functions functions for performing 'bitwise' math (along with corresponding native expressions), including BITWISE_AND, BITWISE_OR, BITWISE_XOR and so on. Additionally, aggregation functions BIT_AND, BIT_OR, and BIT_XOR have been added to accumulate values in a column with the corresponding bitwise function. For complete details see SQL documentation.

https://github.com/apache/druid/pull/10605 https://github.com/apache/druid/pull/10823 https://github.com/apache/druid/pull/11280

<a name="22-human-format" href="#22-human-format">#</a> Human readable number format functions

Three new SQL and native expression number format functions have been added in Druid 0.22.0, HUMAN_READABLE_BINARY_BYTE_FORMAT, HUMAN_READABLE_DECIMAL_BYTE_FORMAT, and HUMAN_READABLE_DECIMAL_FORMAT, which allow transforming results into a more friendly consumption format for query results. For more information see SQL documentation.

https://github.com/apache/druid/issues/10584 https://github.com/apache/druid/pull/10635

<a name="22-expr-agg" href="#22-expr-agg">#</a> Expression aggregator

Druid 0.22.0 adds a new 'native' JSON query expression aggregator function, that lets you use Druid native expressions to perform "fold" (alternatively known as "reduce") operations to accumulate some value on any number of input columns. This adds significant flexibility to what can be done in a Druid aggregator, similar in a lot of ways to what was possible with the Javascript aggregator, but in a much safer, sandboxed manner.

Expressions now being able to perform a "fold" on input columns also really rounds out the abilities of native expressions in addition to the previously possible "map" (expression virtual columns), "filter" (expression filters) and post-transform (expression post-aggregators) functions.

Since this uses expressions, performance is not yet optimal, and it is not directly documented yet, but it is the underlying technology behind the SQL ARRAY_AGG, STRING_AGG, and bitwise aggregator functions also added in this release.

https://github.com/apache/druid/pull/11104

<a name="22-sql-routing" href="#22-sql-routing">#</a> SQL query routing improvements

Druid 0.22 adds some new facilities to provide extension writers with enhanced control over how queries are routed between Druid routers and brokers. The first adds a new manual broker selection strategy to the Druid router, which allows a query to manually specify which Druid brokers a query should be sent to based on a query context parameter brokerService to any broker pool defined in druid.router.tierToBrokerMap (this corresponds to the 'service name' of the broker set, druid.service).

The second new feature allows the Druid router to parse and examine SQL queries so that broker selection strategies can also function for SQL queries. This can be enabled by setting druid.router.sql.enable to true. This does not affect JDBC queries, which use a different mechanism to facilitate "sticky" connections to a single broker.

https://github.com/apache/druid/pull/11566 https://github.com/apache/druid/pull/11495

<a name="22-proto-jdbc" href="#22-proto-jdbc">#</a> Avatica protobuf JDBC Support

Druid now supports using Avatica Protobuf JDBC connections, such as for use with the Avatica Golang Driver, and has a separate endpoint from the JSON JDBC uri.

String url = "jdbc:avatica:remote:url=http://localhost:8082/druid/v2/sql/avatica-protobuf/;serialization=protobuf";

https://github.com/apache/druid/pull/10543

<a name="22-query-error-log" href="#22-query-error-log">#</a> Improved query error logging

Query exceptions have been changed from WARN level to ERROR level to include additional information in the logs to help troubleshoot query failures. Additionally, a new query context flag, enableQueryDebugging has been added that will include stack traces in these query error logs, to provide even more information without the need to enable logs at the DEBUG level.

https://github.com/apache/druid/pull/11519

<a name="22-streaming-task-autoscaling" href="#22-streaming-task-autoscaling">#</a> Task autoscaling for Kafka and Kinesis streaming ingestion

Druid 0.22.0 now offers experimental support for dynamic Kafka and Kinesis task scaling. The included strategies are driven by periodic measurement of stream lag (which is based on message count for Kafka, and difference of age between the message iterator and the oldest message for Kinesis), and will adjust the number of tasks based on the amount of 'lag' and several configuration parameters. https://github.com/apache/druid/pull/10524 https://github.com/apache/druid/pull/10985

<a name="22-shuffle-deep-storage" href="#22-shuffle-deep-storage">#</a> Support for using deep storage for intermediary shuffle data

Druid native 'perfect rollup' 2-phase ingestion tasks now support using deep storage as a shuffle location, as an alternative to local disks on middle-managers or indexers. To use this feature, set druid.processing.intermediaryData.storage.type to deepstore, which uses the configured deep storage type.

Note - With "deepstore" type, data is stored in shuffle-data directory under the configured deep storage path, auto clean up for this directory is not supported yet. One can setup cloud storage lifecycle rules for auto clean up of data at shuffle-data prefix location.

https://github.com/apache/druid/pull/11507

<a name="22-batch-memory" href="#22-batch-memory">#</a> Improved native batch ingestion task memory usage

Druid native batch ingestion has received a new configuration option, druid.indexer.task.batchProcessingMode which introduces two new operating modes that should allow batch ingestion to operate with a smaller and more predictable heap memory usage footprint. The CLOSED_SEGMENTS_SINKS mode is the most aggressive, and should have the smallest memory footprint, and works by eliminating in memory tracking and mmap of intermediary segments produced during segment creation, but isn't super well tested at this point so considered experimental. CLOSED_SEGMENTS, which is the new default option, eliminates mmap of intermediary segments, but still tracks the entire set of segments in heap, though it is relatively well tested at this point and considered stable. OPEN_SEGMENTS will use the previous ingestion path, which is shared with streaming ingestion and performs a mmap on intermediary segments and builds a timeline so that these segments can be queryable by realtime queries. This is not needed at all for batch, but OPEN_SEGMENTS mode can be selected if any problems occur with the 2 newer modes.

https://github.com/apache/druid/pull/11123 https://github.com/apache/druid/pull/11294 https://github.com/apache/druid/pull/11536

<a name="22-batch-wait-for-handoff" href="#22-batch-wait-for-handoff">#</a> Allow batch tasks to wait until segment handoff before completion

Druid native batch ingestion tasks can now be optionally configured to not terminate until after the ingested segments are completely loaded by Historical servers. This can be useful for scenarios when the trade-off of keeping an extra task slot occupied is worth using the task state as a measure of if ingestion is complete and segments are available to query.

This can be enabled by adding awaitSegmentAvailabilityTimeoutMillis to the tuningConfig in the ingestion spec, which specifies the maximum amount of time that a task will wait for segments to be loaded before terminating. If not all segments become available by the time this timeout expires, the job will still succeed. However, in the ingestion report, segmentAvailabilityConfirmed will be false. This indicates that handoff was not successful and these newly indexed segments may not all be available for query. On the other hand, if all segments become available for query on the Historical services before the timeout expires, the value for that key in the report will be true.

This tuningConfig value is not supported for compaction tasks at this time. If a user tries to specify a value for awaitSegmentAvailabilityTimeoutMillis for Compaction, the task will fail telling the user it is not supported.

https://github.com/apache/druid/pull/10676

<a name="22-compact-granularity" href="#22-compact-granularity">#</a> Support managing segment and query granularity for auto-compaction

Druid manual and automatic compaction can now be configured to change segment granularity, and manual compaction can also change query granularity. Additionally, compaction will preserve segment granularity by default. This allows operators to more easily perform options like changing older data to larger segment and query granularities in exchange for decreased data size. See compaction docs for details.

<a name="22-compact-skip-lock" href="#22-compact-skip-lock">#</a> Allow compaction to temporarily skip locked intervals

Druid auto-compaction will now by default temporarily skip locked intervals instead of waiting for the lock to become free, which should improve the rate at which datasources can be compacted. <a name="22-config-cleanup" href="#22-config-cleanup">#</a> Support for additional automatic metadata cleanup

You can configure automated cleanup to remove records from the metadata store after you delete delete some entities from Druid:

  • segments records
  • audit records
  • supervisor records
  • rule records
  • compaction configuration records
  • datasource records created by supervisors

This feature helps maintain performance when you have a high datasource churn rate, meaning you frequently create and delete many short-lived datasources or other related entities. <a name="22-data-cleanup" href="#22-data-cleanup">#</a> Dropping data

A new setting, dropExisting has been added to the ioConfig of Druid native batch ingestion tasks and compaction, which if set to true (and appendToExist is false), then the ingestion task will transactionally mark all existing segments in the interval as unused, replacing them with the new set of segments. This can be useful in compaction use cases where normal overshadowing does not completely replace a set of segments in an interval, such as when changing segment granularity to a smaller size and some of the smaller granularity buckets would have no data, leaving the original segments only partially overshadowed.

Note that this functionality is still experimental, and can result in temporary data unavailability for data within the compacted interval. Changing this config does not cause intervals to be compacted again.

Similarly, markAsUnused has been added as an option to the Druid kill task, which will mark any segments in the supplied interval as 'unused' prior to deleting all of the unused segments. This is useful for allowing the mark unused -> delete sequence to happen with a single API call for the caller, as well as allowing the unmark action to occur under a task interval lock.

<a name="22-coordinator" href="#22-coordinator">#</a> Coordinator

<a name="22-coord-timeout" href="#22-coord-timeout">#</a> Control over coordinator segment load timeout timeout behavior with Apache Zookeeper based segment management

A new Druid coordinator dynamic configuration option allows controlling the behavior whenever a segment load action times out when using Zookeeper based segment management. replicateAfterLoadTimeout when set to true, the coordinator will attempt to replicate the segment that failed to load to a different historical server. This helps improve the segment availability if there are a few slow historical servers in the cluster. However, the slow historical may still load the segment later and the coordinator may need to issue drop requests if the segment is over-replicated.

<a name="22-coord-balance" href="#22-coord-balance">#</a> Faster coordinator segment balancing

Another new coordinator dynamic configuration option, useBatchedSegmentSampler, when set to true can potentially provide a large performance increase in the speed which the coordinator can process the segment balancing phase. This should be particularly notable at very large cluster sizes with many segments, but is disabled by default to err on the side of caution.

https://github.com/apache/druid/pull/11257

<a name="22-coord-replication" href="#22-coord-replication">#</a> Improved loadstatus API to optionally compute under-replication based on cluster size

The Druid coordinator load status API now supports a new optional URL query parameter, computeUsingClusterView, which when specified will cause the coordinator compute under-replication for segments based on the number of servers available within cluster that the segment can be replicated to, instead of the configured replication count configured in load rule. For example, if the load rules specify 2 replicas, but there is only 1 server which can hold segments, this API would not report as under-replicated because the segments are as replicated as is possible for the given cluster size.

https://github.com/apache/druid/pull/11056

<a name="22-coord-rep-limit" href="#22-coord-rep-limit">#</a> Optional limits on the number of non-primary replicants loaded per coordination cycle

A new coordinator dynamic configuration, maxNonPrimaryReplicantsToLoad, with default value of Integer.MAX_VALUE, lets operators to define a hard upper limit on the number of non-primary replicants that will be loaded in a single coordinator execution cycle. The default value will mimic the behavior that exists today.

Example usage: If you set this configuration to 1000, the coordinator will load a maximum of 1000 non-primary replicants in each run cycle execution. Meaning if you ingested 2000 segments with a replication factor of 2, the coordinator would load 2000 primary replicants and 1000 non-primary replicants on the first execution. Then the next execution, the last 1000 non-primary replicants will be loaded.

<a name="22-up-batch-lineage" href="#22-up-batch-lineage">#</a> Native batch ingestion segment allocation fix

Druid 0.22.0 includes an important bug-fix in native batch indexing where transient failures of indexing sub-tasks can result in non-contiguous partitions in the result segments, which will never become queryable due to logic which checks for the 'complete' set. This issue has been resolved in the latest version of Druid, but required a change in the protocol which batch tasks use to allocate segments, and this change can cause issues during rolling downgrades if you decide to roll back from Druid 0.22.0 to an earlier version.

To avoid task failure during a rolling-downgrade, set

druid.indexer.task.default.context={ "useLineageBasedSegmentAllocation" : false }

in the overlord runtime properties, and wait for all tasks which have useLineageBasedSegmentAllocation set to true to complete before initiating the downgrade. After these tasks have all completed the downgrade shouldn't have any further issue and the setting can be removed from the overlord configuration (recommended, as you will want this setting enabled if you are running Druid 0.22.0 or newer).

https://github.com/apache/druid/pull/11189

<a name="22-up-sql-buckets" href="#22-up-sql-buckets">#</a> SQL timeseries no longer skip empty buckets with all granularity

Prior to Druid 0.22, an SQL group by query which is using a single universal grouping key (e.g. only aggregators) such as SELECT COUNT(*), SUM(x) FROM y WHERE z = 'someval' would produce an empty result set instead of [0, null] that might be expected from this query matching no results. This was because underneath this would plan into a timeseries query with 'ALL' granularity, and skipEmptyBuckets set to true in the query context. This latter option caused the results of such a query to return no results, as there are no buckets with values to aggregate and so they are skipped, making an empty result set instead of a 'nil' result set. This behavior has been changed to behave in line with other SQL implementations, but the previous behavior can be obtained by explicitly setting skipEmptyBuckets on the query context.

https://github.com/apache/druid/pull/11188

<a name="22-up-reingest" href="#22-up-reingest">#</a> Druid reingestion incompatible changes

Batch tasks using a 'Druid' input source to reingest segment data will no longer accept the 'dimensions' and 'metrics' sections of their task spec, and now will internally use a new columns filter to specify which columns from the original segment should be retained. Additionally, timestampSpec is no longer ignored, allowing the __time column to be modified or replaced with a different column. These changes additionally fix a bug where transformed columns would be ignored and unavailable on the new segments.

https://github.com/apache/druid/pull/10267

<a name="22-up-ie11" href="#22-up-ie11">#</a> Druid web-console no longer supports IE11 and other older browsers

Some things might still work, but it is no longer officially supported so that newer Javascript features can be used to develop the web-console. https://github.com/apache/druid/pull/11357

<a name="22-up-ie11" href="#22-up-ie11">#</a> Changed default maximum segment loading queue size

Druid coordinator maxSegmentsInNodeLoadingQueue dynamic configuration has been changed from unlimited (0) to instead to 100. This should make the coordinator behave in a much more relaxed manner during periods of cluster volatility, such as a rolling upgrade, but caps the total number of segments that will be loaded in any given coordinator cycle to 100 per server, which can slow down the speed at which a completely stopped cluster is started and loaded from deep storage.
