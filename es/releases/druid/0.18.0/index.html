druida druida-0.18.0

Apache Druid 0.18.0 contiene más de 200 funciones nuevas, mejoras de rendimiento, correcciones de errores y mejoras importantes en la documentación de 42 contribuyentes. Consulte la lista completa de cambios y todo lo etiquetado en el hito.

<a name="new-features" href="#new-features">#</a> Nuevas funciones

<a name="join" href="#join">#</a> Únase al soporte

Unirse es una operación clave en el análisis de datos. Antes de 0.18.0, Druid admitía algunas funciones relacionadas con uniones, como búsquedas o semiuniones en SQL. Sin embargo, los casos de uso de esas funciones eran bastante limitados y, para otros casos de uso de unión, los usuarios tenían que desnormalizar sus fuentes de datos cuando ingieren datos en lugar de unirse a ellos en el momento de la consulta, lo que podría resultar en un volumen de datos explosivo y un tiempo de ingestión prolongado. Druid 0.18.0 admite uniones reales por primera vez en su historia. Druid admite uniones INNER, LEFT y CROSS por ahora. Para consultas nativas, la fuente de datos join se introdujo recientemente para representar una unión de dos fuentes de datos. Actualmente, sólo se permite la unión izquierda-profunda. Eso significa que solo se permite una fuente de datos table u otra join para la fuente de datos izquierda. Para la fuente de datos correcta, se permiten fuentes de datos lookup, inline o query. Tenga en cuenta que aún no se admite la unión de fuentes de datos de Druid. Solo debe haber una fuente de datos table en la misma consulta de unión. Druid SQL también admite uniones. En secreto, las consultas de unión SQL se traducen en una o varias consultas nativas que incluyen fuentes de datos de unión. Consulte Traducción de consultas para obtener más detalles sobre la traducción de SQL y las mejores prácticas para escribir consultas eficientes. Cuando se emite una consulta de unión, el Broker primero evalúa todas las fuentes de datos excepto la fuente de datos base, que es la única fuente de datos table en la consulta. La evaluación puede incluir la ejecución de subconsultas para fuentes de datos query. Una vez que el Broker evalúa todas las fuentes de datos no base, las reemplaza con fuentes de datos inline y envía la consulta reescrita a los nodos de datos (consulte la sección "Inclusión de consultas en Brokers" a continuación para obtener más detalles). Los nodos de datos utilizan la unión hash para procesar consultas de unión. Crean una tabla hash para cada fuente de datos hoja no primaria, a menos que ya exista. Tenga en cuenta que actualmente solo la fuente de datos lookup tiene una tabla hash prediseñadas. Consulte Ejecución de consultas para obtener más detalles sobre la ejecución de consultas de unión. Las uniones pueden afectar el rendimiento de sus consultas. En general, cualquier consulta que incluya uniones puede ser más lenta que las consultas equivalentes realizadas en una fuente de datos desnormalizada. La función LOOKUP podría funcionar mejor que las uniones con fuentes de datos de búsqueda. Consulte Rendimiento de unión para obtener más detalles sobre el rendimiento de consultas de unión y planes futuros para mejorar el rendimiento. https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> Consulta incorporada en Brokers

Druid ahora puede ejecutar una consulta anidada integrando subconsultas. Cualquier tipo de subconsulta puede estar encima de cualquier tipo de otra, como en el siguiente ejemplo:

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

Para ejecutar esta consulta, el Broker primero evalúa la subconsulta hoja groupBy; envía la subconsulta a los nodos de datos y recopila el resultado. El resultado recogido se materializa en la memoria del Broker. Una vez que el Broker recopila todos los resultados de la consulta groupBy, reescribe la consulta topN reemplazando la hoja groupBy con una fuente de datos en línea que tiene el resultado de la consulta groupBy. Finalmente, la consulta reescrita se envía a los nodos de datos para ejecutar la consulta topN.

<a name="query-laning" href="#query-laning">#</a> Línea de consultas y priorización

Cuando ejecuta varias consultas de cargas de trabajo heterogéneas a la vez, es posible que en ocasiones desee controlar el compromiso de recursos para una consulta en función de su prioridad. Por ejemplo, querrá limitar los recursos asignados a consultas menos importantes, de modo que las consultas importantes puedan ejecutarse a tiempo sin que las menos importantes las interrumpan. La ruta de consultas le permite controlar la utilización de la capacidad para cargas de trabajo de consultas heterogéneas. Con laning, el corredor examina y clasifica una consulta con el fin de asignarla a una "carril". Los carriles tienen límites de capacidad, aplicados por el Broker, que se pueden utilizar para garantizar que haya suficientes recursos disponibles para otros carriles o para consultas interactivas (sin carril), o para limitar el rendimiento general de las consultas dentro del carril. La priorización automática de consultas determina la prioridad de la consulta según la estrategia configurada. Se ha agregado la estrategia de priorización basada en umbrales; reduce automáticamente la prioridad de las consultas que cruzan cualquiera de un conjunto configurable de umbrales, como qué tan atrás están los datos, qué tan grande es el intervalo que cubre una consulta o la cantidad de segmentos que participan en una consulta. Consulte Priorización de consultas y carriles para obtener más detalles. https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

Nueva dimensión en métricas de consulta

Dado que una consulta nativa que contiene subconsultas se puede ejecutar parte por parte, se ha introducido un nuevo subQueryId. Cada subconsulta tiene subQueryId diferentes pero el mismo queryId. El subQueryId está disponible como una nueva dimensión en métricas de consulta.

Nueva configuración

Una nueva configuración druid.server.http.maxSubqueryRows controla el número máximo de filas materializadas en la memoria del Broker. Consulte Ejecución de consulta para obtener más detalles. https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> conjuntos de agrupación SQL

Ahora se admite GROUPING SETS, lo que le permite combinar varias cláusulas GROUP BY en una cláusula GROUP BY. Esta cláusula GROUPING SETS se traduce internamente a la consulta groupBy con subtotalsSpec. La cláusula LIMIT ahora se aplica después de subtotalsSpec, en lugar de aplicarse a cada conjunto de agrupación. https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> Parámetros dinámicos de SQL

Druid ahora admite parámetros dinámicos para SQL. Para utilizar parámetros dinámicos, reemplace cualquier literal de la consulta con un carácter de signo de interrogación (?). Estos signos de interrogación representan los lugares donde se vincularán los parámetros en el momento de la ejecución. Consulte parámetros dinámicos de SQL para obtener más detalles. https://github.com/apache/druid/pull/6974

<a name="important-changes" href="#important-changes">#</a> Cambios importantes

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments está deshabilitado de forma predeterminada

applyLimitPushDownToSegments se agregó en 0.17.0 para reducir la evaluación de límites a los nodos consultables, lo que limita los resultados durante la exploración de segmentos para groupBy v2. Esto puede provocar una degradación del rendimiento, como se informa en https://github.com/apache/druid/issues/9689, si hay muchos segmentos involucrados en el procesamiento de consultas. Esto se debe a que "limitar el empuje hacia abajo para escanear segmentos" inicializa un búfer de agregación por segmento, cuya sobrecarga no es despreciable. Habilite esta configuración solo si su consulta involucra una cantidad relativamente pequeña de segmentos por tarea histórica o en tiempo real. https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> Mapas de bits rugientes por defecto

Druid admite dos tipos de mapas de bits, es decir, Roaring y CONCISE. Dado que los mapas de bits Roaring brindan una mejor experiencia inmediata (velocidad de consulta más rápida en general), el tipo de mapa de bits predeterminado ahora se cambia a mapas de bits Roaring. Consulte Compresión de segmentos para obtener más detalles sobre los mapas de bits. https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> Cambio de comportamiento de métricas complejas en el momento de la ingesta cuando el manejo de nulos compatible con SQL está deshabilitado (modo predeterminado)

Cuando el manejo de nulos compatible con SQL está deshabilitado, el comportamiento de la agregación de métricas complejas en el momento de la ingesta ahora ha cambiado para ser coherente con el del momento de la consulta. Las métricas complejas se agregan a los valores 0 predeterminados para valores nulos en lugar de omitirlos durante la ingesta. https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> Cambio de sintaxis de expresión de matriz

La expresión druida ahora admite constructores escritos para crear matrices. Las matrices se pueden definir con un tipo explícito. Por ejemplo, <LONG>[1, 2, null] crea una matriz de tipo LONG que contiene 1, 2 y null. Tenga en cuenta que aún puede crear una matriz sin un tipo explícito. Por ejemplo, [1, 2, null] sigue siendo una sintaxis válida para crear una matriz equivalente. En este caso, Druid inferirá el tipo de matriz a partir de sus elementos. Esta nueva sintaxis también se aplica a matrices vacías. <STRING>[], <DOUBLE>[] y <LONG>[] crearán una matriz vacía de tipo STRING, DOUBLE y LONG, respectivamente. https://github.com/apache/druid/pull/9367

<a name="pending-segments-cleanup" href="#pending-segments-cleanup">#</a> Habilitación de la limpieza de segmentos pendientes de forma predeterminada

La tabla pendingSegments en el almacén de metadatos se utiliza para crear nuevos ID de segmento únicos para agregar tareas como tareas de indexación de Kafka/Kinesis o tareas por lotes del modo de agregar. La limpieza automática de segmentos pendientes se introdujo en 0.12.0, pero se deshabilitó de forma predeterminada antes de 0.18.0. Esta configuración ahora está habilitada de forma predeterminada. https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> Creación de mejores divisiones de entrada para la indexación paralela nativa

La tarea paralela ahora puede crear mejores divisiones. Cada división puede contener varios archivos de entrada según su tamaño. Los archivos vacíos serán ignorados. El tamaño de división se puede controlar con la nueva especificación de sugerencia de división. Consulte Especificación de sugerencia dividida para obtener más detalles. https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> La transformación ahora es un punto de extensión

Transform es un Interface que representa una transformación que se aplicará a cada fila en el momento de la ingesta. Esta interfaz es ahora un punto de extensión. Consulte Escribir sus propias extensiones para saber cómo agregar su Transform personalizado. https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> chunkPeriod se elimina el contexto de consulta

chunkPeriod ha quedado obsoleto desde 0.14.0 debido a su uso limitado (a veces era útil solo para groupBy v1). Este contexto de consulta ahora se elimina en 0.18.0. https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Soporte experimental para Java 11

Druid ahora admite experimentalmente Java 11. Puede ejecutar la misma distribución binaria de Druid con Java 11 que está compilada con Java 8. Nuestras pruebas en Travis incluyen:

  • Compilación y ejecución de pruebas unitarias con Java 11.
  • Compilando con Java 8 y ejecutando pruebas de integración con Java 11 Los resultados de las pruebas de rendimiento aún no están disponibles.

<a name="sql-explain" href="#sql-explain">#</a> Ligera diferencia entre el resultado de la consulta explain plan for y el plan de ejecución real

El resultado de explain plan for puede ser ligeramente diferente de lo que Druid realmente ejecuta cuando la consulta incluye uniones o subconsultas. La diferencia se puede encontrar en que cada parte del plan de consulta se representaría como si fuera su propia consulta nativa en el resultado de explain plan for. Por ejemplo, para una unión de una fuente de datos d1 y una subconsulta groupBy en la fuente de datos d2, el explain plan for podría devolver un plan como el siguiente

     join
    /    \
scan    groupBy
 |        |
d1       d2

mientras que el plan de consulta real que ejecutaría Druid es

     join
    /    \
  d1    groupBy
          |
         d2

druid druid-0.18.0

Apache Druid 0.18.0 contains over 200 new features, performance enhancements, bug fixes, and major documentation improvements from 42 contributors. Check out the complete list of changes and everything tagged to the milestone.

<a name="new-features" href="#new-features">#</a> New Features

<a name="join" href="#join">#</a> Join support

Join is a key operation in data analytics. Prior to 0.18.0, Druid supported some join-related features, such as Lookups or semi-joins in SQL. However, the use cases for those features were pretty limited and, for other join use cases, users had to denormalize their datasources when they ingest data instead of joining them at query time, which could result in exploding data volume and long ingestion time.

Druid 0.18.0 supports real joins for the first time ever in its history. Druid supports INNER, LEFT, and CROSS joins for now. For native queries, the join datasource has been newly introduced to represent a join of two datasources. Currently, only the left-deep join is allowed. That means, only a table or another join datasource is allowed for the left datasource. For the right datasource, lookup, inline, or query datasources are allowed. Note that join of Druid datasources is not supported yet. There should be only one table datasource in the same join query.

Druid SQL also supports joins. Under the covers, SQL join queries are translated into one or several native queries that include join datasources. See Query translation for more details of SQL translation and best practices to write efficient queries.

When a join query is issued, the Broker first evaluates all datasources except for the base datasource which is the only table datasource in the query. The evaluation can include executing subqueries for query datasources. Once the Broker evaluates all non-base datasources, it replaces them with inline datasources and sends the rewritten query to data nodes (see the below "Query inlining in Brokers" section for more details). Data nodes use the hash join to process join queries. They build a hash table for each non-primary leaf datasource unless it already exists. Note that only lookup datasource currently has a pre-built hash table. See Query execution for more details about join query execution.

Joins can affect performance of your queries. In general, any queries including joins can be slower than equivalent queries against a denormalized datasource. The LOOKUP function could perform better than joins with lookup datasources. See Join performance for more details about join query performance and future plans for performance improvement.

https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> Query inlining in Brokers

Druid is now able to execute a nested query by inlining subqueries. Any type of subquery can be on top of any type of another, such as in the following example:

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

To execute this query, the Broker first evaluates the leaf groupBy subquery; it sends the subquery to data nodes and collects the result. The collected result is materialized in the Broker memory. Once the Broker collects all results for the groupBy query, it rewrites the topN query by replacing the leaf groupBy with an inline datasource which has the result of the groupBy query. Finally, the rewritten query is sent to data nodes to execute the topN query.

<a name="query-laning" href="#query-laning">#</a> Query laning and prioritization

When you run multiple queries of heterogenous workloads at a time, you may sometimes want to control the resource commitment for a query based on its priority. For example, you would want to limit the resources assigned to less important queries, so that important queries can be executed in time without being disrupted by less important ones.

Query laning allows you to control capacity utilization for heterogeneous query workloads. With laning, the broker examines and classifies a query for the purpose of assigning it to a 'lane'. Lanes have capacity limits, enforced by the Broker, that can be used to ensure sufficient resources are available for other lanes or for interactive queries (with no lane), or to limit overall throughput for queries within the lane.

Automatic query prioritization determines the query priority based on the configured strategy. The threshold-based prioritization strategy has been added; it automatically lowers the priority of queries that cross any of a configurable set of thresholds, such as how far in the past the data is, how large of an interval a query covers, or the number of segments taking part in a query.

See Query prioritization and laning for more details.

https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

New dimension in query metrics

Since a native query containing subqueries can be executed part-by-part, a new subQueryId has been introduced. Each subquery has different subQueryIds but same queryId. The subQueryId is available as a new dimension in query metrics.

New configuration

A new druid.server.http.maxSubqueryRows configuration controls the maximum number of rows materialized in the Broker memory.

Please see Query execution for more details.

https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> SQL grouping sets

GROUPING SETS is now supported, allowing you to combine multiple GROUP BY clauses into one GROUP BY clause. This GROUPING SETS clause is internally translated into the groupBy query with subtotalsSpec. The LIMIT clause is now applied after subtotalsSpec, rather than applied to each grouping set.

https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> SQL Dynamic parameters

Druid now supports dynamic parameters for SQL. To use dynamic parameters, replace any literal in the query with a question mark (?) character. These question marks represent the places where the parameters will be bound at execution time. See SQL dynamic parameters for more details.

https://github.com/apache/druid/pull/6974

<a name="important-changes" href="#important-changes">#</a> Important Changes

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments is disabled by default

applyLimitPushDownToSegments was added in 0.17.0 to push down limit evaluation to queryable nodes, limiting results during segment scan for groupBy v2. This can lead to performance degradation, as reported in https://github.com/apache/druid/issues/9689, if many segments are involved in query processing. This is because “limit push down to segment scan” initializes an aggregation buffer per segment, the overhead for which is not negligible. Enable this configuration only if your query involves a relatively small number of segments per historical or realtime task.

https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> Roaring bitmaps as default

Druid supports two bitmap types, i.e., Roaring and CONCISE. Since Roaring bitmaps provide a better out-of-box experience (faster query speed in general), the default bitmap type is now switched to Roaring bitmaps. See Segment compression for more details about bitmaps.

https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> Complex metrics behavior change at ingestion time when SQL-compatible null handling is disabled (default mode)

When SQL-compatible null handling is disabled, the behavior of complex metric aggregation at ingestion time has now changed to be consistent with that at query time. The complex metrics are aggregated to the default 0 values for nulls instead of skipping them during ingestion.

https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> Array expression syntax change

Druid expression now supports typed constructors for creating arrays. Arrays can be defined with an explicit type. For example, <LONG>[1, 2, null] creates an array of LONG type containing 1, 2, and null. Note that you can still create an array without an explicit type. For example, [1, 2, null] is still a valid syntax to create an equivalent array. In this case, Druid will infer the type of array from its elements. This new syntax applies to empty arrays as well. <STRING>[], <DOUBLE>[], and <LONG>[] will create an empty array of STRING, DOUBLE, and LONG type, respectively.

https://github.com/apache/druid/pull/9367

<a name="pending-segments-cleanup" href="#pending-segments-cleanup">#</a> Enabling pending segments cleanup by default

The pendingSegments table in the metadata store is used to create unique new segment IDs for appending tasks such as Kafka/Kinesis indexing tasks or batch tasks of appending mode. Automatic pending segments cleanup was introduced in 0.12.0, but has been disabled by default prior to 0.18.0. This configuration is now enabled by default.

https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> Creating better input splits for native parallel indexing

The Parallel task now can create better splits. Each split can contain multiple input files based on their size. Empty files will be ignored. The split size is controllable with the new split hint spec. See Split hint spec for more details.

https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> Transform is now an extension point

Transform is an Interface that represents a transformation to be applied to each row at ingestion time. This interface is now an Extension point. Please see Writing your own extensions for how to add your custom Transform.

https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> chunkPeriod query context is removed

chunkPeriod has been deprecated since 0.14.0 because of its limited usage (it was sometimes useful for only groupBy v1). This query context is now removed in 0.18.0.

https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Experimental support for Java 11

Druid now experimentally supports Java 11. You can run the same Druid binary distribution with Java 11 which is compiled with Java 8. Our tests on Travis include:

  • Compiling and running unit tests with Java 11
  • Compiling with Java 8 and running integration tests with Java 11

Performance testing results are not available yet.

<a name="security" href="#security">#</a> Security Issues

<a name="ldap-security" href="#ldap-security">#</a> [CVE-2020-1958] Apache Druid LDAP injection vulnerability

CVE-2020-1958 has been reported recently and fixed in 0.18.0 and 0.17.1. When LDAP authentication is enabled, callers of Druid APIs can bypass the credentialsValidator.userSearch filter barrier or retrieve any LDAP attribute values of users that exist on the LDAP server, so long as that information is visible to the Druid server. Please see the description in the link for more details. It is strongly recommended to upgrade to 0.18.0 or 0.17.1 if you are using LDAP authentication with Druid.

https://github.com/apache/druid/pull/9600

<a name="known-issues" href="#known-issues">#</a> Known Issues

<a name="inline-query-multi-value" href="#inline-query-multi-value">#</a> Query failure with topN or groupBy on scan with multi-valued columns

Query inlining in Brokers is newly introduced in 0.18.0 but has a bug that queries with topN or groupBy on top of scan fail if the scan query selects multi-valued dimensions. See https://github.com/apache/druid/issues/9697 for more details.

<a name="npe-kafka" href="#npe-kafka">#</a> NullPointerException when using Avro parser with Kafka indexing service.

Avro parser doesn't work with Kafka indexing service because of a wrong null check. See https://github.com/apache/druid/issues/9728 for more details.

<a name="unavailable-segment-metric" href="#unavailable-segment-metric">#</a> Misleading segment/unavailable/count metric during handoff

This metric is supposed to take the number of segments served by realtime tasks into consideration as well, but it isn't now. As a result, it appears that unavailability spikes up before the new segments are loaded by historicals, even if all segments actually are continuously available on some combination of realtime tasks and historicals.

https://github.com/apache/druid/issues/9677

<a name="sql-explain" href="#sql-explain">#</a> Slight difference between the result of explain plan for query and the actual execution plan

The result of explain plan for can be slightly different from what Druid actually executes when the query includes joins or subqueries. The difference can be found in that each part of the query plan would be represented as if it was its own native query in the result of explain plan for. For example, for a join of a datasource d1 and a groupBy subquery on datasource d2, the explain plan for could return a plan like below

     join
    /    \
scan    groupBy
 |        |
d1       d2

whereas the actual query plan Druid would execute is

     join
    /    \
  d1    groupBy
          |
         d2
