dify 1.19.0

Dify 1.19.0 ofrece seguimiento de flujo de trabajo anidado a sus herramientas de observabilidad. Siga un flujo de trabajo en las herramientas de flujo de trabajo que llama, inspeccione los pasos dentro de cada invocación y mantenga el contexto LLM junto al árbol de ejecución.

Esta versión también hace que las herramientas de flujo de trabajo sean portátiles con paquetes de aplicaciones, agrega automatización de Skill Hub y facilita la carga y la vista previa de los archivos del agente. El demonio del complemento incluido se actualizó a 0.6.14-local.

Aspectos destacados del lanzamiento

Seguimiento de flujo de trabajo anidado

Vea lo que sucede dentro de una herramienta de flujo de trabajo, hasta sus convocatorias de LLM.

Sobre la base del desglose de la consola introducido en 1.18.0, los nuevos seguimientos externos ahora incluyen los pasos de ejecución persistentes llamados herramientas de flujo de trabajo. Los pasos secundarios aparecen debajo del intervalo de herramientas que los invocó, preservando la jerarquía entre llamadas anidadas y repetidas. (#44673)

Del flujo de trabajo externo a una llamada LLM anidada: el árbol de ejecución y los mensajes formateados, juntos en Langfuse. Captura de pantalla de #44673.

  • Sigue la jerarquía. Expande las llamadas Herramientas de flujo de trabajo para ver sus pasos de ejecución internos en el intervalo de herramientas de invocación.
  • Comprenda cada invocación. Las llamadas repetidas y los fallos conservan su lugar en el seguimiento.
  • Mantenga el contexto LLM. Inspeccione las indicaciones y respuestas formateadas, el uso de tokens y los enlaces de proyectos, seguimiento y observación.

[!NOTA] La configuración de su proveedor guardada continúa funcionando. La jerarquía más rica se aplica a las nuevas ejecuciones; Las huellas históricas no se rellenan. Las ejecuciones de flujos de trabajo anidados de forma independiente siguen siendo seguimientos separados vinculados por identificadores principales. Para implementaciones continuas, siga la transición de la cola de seguimiento a continuación.

Incorpora herramientas de flujo de trabajo con tus aplicaciones

Exporte una aplicación y lleve consigo los flujos de trabajo detrás de sus herramientas de flujo de trabajo. Los paquetes .ifpkg incluyen esos flujos de trabajo en sus versiones vinculadas, incluidas las dependencias transitivas. La importación reutiliza herramientas que ya están en el espacio de trabajo de destino y recrea, publica y registra las que faltan, reasignando sus referencias. (#44592)

Todas las exportaciones de aplicaciones de Dify ahora usan formato de paquete v2, incluidas las aplicaciones sin herramientas de flujo de trabajo. Se siguen admitiendo las importaciones v1 existentes y la exportación explícita de YAML. Consulte la guía de actualización antes de importar nuevos paquetes a instalaciones anteriores. (#45353)

Subir juntos. Vista previa en su lugar.

Seleccione o suelte varios archivos de configuración del Agente y cárguelos en paralelo. Las cargas exitosas se vinculan en un lote atómico, los guardados simultáneos de Composer conservan los archivos más recientes y las cargas rápidas mantienen la posición del cursor mientras se insertan múltiples referencias. (#44947)

Lea archivos PDF en línea, inspeccione archivos de origen con resaltado de sintaxis y vea cuándo se ha truncado el texto. Las vistas previas cubren archivos configurados, miembros de habilidades y archivos del directorio de trabajo, con una acción de descarga cuando no se puede cargar un PDF. (#45032, #45045)

Destacado del desarrollador

Administre las habilidades del espacio de trabajo a través de OpenAPI y difyctl. Busque e inspeccione habilidades, exporte un borrador o una versión publicada, importe archivos locales y publique una nueva versión desde la línea de comandos. (#44941)

<detalles> <summary><strong>Los seis comandos de habilidad</strong></summary>

| Comando | Capacidad | | --- | --- | | difyctl get skill | Lista de habilidades, con filtros de palabras clave y etiquetas. | | difyctl describe skill | Lea los detalles, el borrador del hash y la última versión publicada. | | difyctl get skill version | Lista de versiones publicadas. | | difyctl export skill | Exporte el borrador o una versión publicada seleccionada como ZIP. | | difyctl import skill --files <dir> | Cree una habilidad o reemplace el borrador de una habilidad existente a partir de archivos locales. | | difyctl publish skill | Publicar el borrador como una nueva versión. |

</detalles>

Estas operaciones requieren que se habilite una persona que llama a la cuenta, los permisos del espacio de trabajo correspondientes y las habilidades. La importación no se publica. La importación sobre una habilidad existente se clasifica como destructiva; el catálogo de operaciones y CLI ayudan a distinguir las operaciones de lectura, escritura y destructivas. (#44941, #45314, #44587)

<a id="guía-de-actualización"></a>

Guía de actualización

[!IMPORTANTE] Lea la guía de actualización antes de implementar. Docker Compose ahora requiere v2.35.0 o posterior. Conserve los archivos del entorno existentes, actualice los componentes de Dify juntos y utilice la nueva cola de seguimiento durante las implementaciones continuas. Los nuevos paquetes de aplicaciones utilizan el formato v2 y requieren un importador de destino compatible. El demonio del complemento incluido se traslada a 0.6.14-local.

Compatibilidad e implementación

  1. Primero haga una copia de seguridad. Conserve la base de datos, los datos del almacén de vectores, los archivos cargados, el almacenamiento de instantáneas/espacio de trabajo del agente, los secretos de implementación y los archivos de entorno. Utilice una ventana de mantenimiento para una actualización de una sola pila.
  2. Actualice los componentes juntos. Utilice imágenes coincidentes de 1.19.0 API, trabajador, web, backend del agente y sandbox local, con el demonio de complemento 0.6.14-local. Mantenga sin cambios el token de autenticación de la zona de pruebas local existente y cualquier PASSWORD_PEPPER configurado. Si actualiza desde una versión anterior a 1.18.0, siga también la guía de actualización de 1.18.0.
  3. Utilice Docker Compose 2.35.0 o posterior. Esta es la versión mínima admitida para que las anulaciones raíz de .env tengan prioridad cuando Compose resuelve los valores predeterminados del servicio. Verifique su versión instalada con docker compose version. (#45359)
  4. Mantenga los valores predeterminados rastreados separados de las anulaciones locales. Los archivos docker/envs/**/*.defaults incluidos se cargan automáticamente. Personalice un servicio a través de su archivo local .env correspondiente, utilizando la ruta de anulación documentada en el archivo predeterminado; root docker/.env contiene entradas de implementación y anulaciones explícitas. Conserve los archivos .env existentes y edítelos en su lugar. Revise las asignaciones vacías accidentalmente y los valores fijados en copias de plantillas más antiguas antes de actualizar. (#45359, #45376)
  5. Los archivos shared.env existentes siguen siendo compatibles. Las personalizaciones comunes de API, Workers y Beat ahora pertenecen a docker/envs/core-services/api-worker.env. Compose todavía lee primero el docker/envs/core-services/shared.env heredado y luego el api-worker.env, por lo que api-worker.env gana cuando ambos establecen valores en conflicto. Root docker/.env tiene prioridad sobre ambos. Una copia sin cambios de api-worker.defaults conserva las personalizaciones existentes de shared.env. Consulte la guía de configuración Docker. (#45376)
  6. Colas de seguimiento separadas durante una actualización continua. Las nuevas tareas tienen como valor predeterminado OPS_TRACE_QUEUE=ops_trace_v2; API, los trabajadores y Beat deben estar de acuerdo. Las listas personalizadas CELERY_QUEUES, CELERY_WORKER_QUEUES o --queues deben incluir la nueva cola. Mantenga a los trabajadores de rastreo antiguos en ops_trace hasta que los productores antiguos y todos sus trabajos en cola, activos, reservados, programados y de reintento hayan finalizado. No purgue la cola anterior ni solicite al nuevo controlador retirado que exporte mensajes heredados. Consulte la guía de implementación de seguimiento. (#44673)
  7. Actualice los destinos de los paquetes antes de importar nuevos paquetes de aplicaciones. Los nuevos paquetes de aplicaciones siempre usan el formato v2. Los importadores más antiguos, incluidas las compilaciones con la estricta regla v2 anterior, pueden rechazarlas. Las importaciones de la versión 1 siguen siendo compatibles con 1.19.0. La exportación explícita de YAML permanece disponible, pero no incluye dependencias de la herramienta de flujo de trabajo. (#44592, #45353)

Docker Redactar

Una vez que se publiquen la etiqueta de lanzamiento y las imágenes de 1.19.0, detenga correctamente una implementación de pila única, cambie a la configuración de lanzamiento, retención y revisión, luego extraiga e inicie las nuevas imágenes:

cd dify/docker
docker compose stop -t -1
git fetch --tags
git checkout 1.19.0
# Merge required configuration changes into existing env files here.
docker compose pull
docker compose up -d

Mantenga habilitadas las migraciones de inicio API (MIGRATION_ENABLED=true) o aplique la cadena de migración completa a través de su proceso de migración administrada antes de iniciar nuevos trabajadores. Para implementaciones continuas, siga la secuencia de cola de seguimiento separada en lugar de mezclar consumidores antiguos y nuevos.

Configure las credenciales del complemento compartido, PLUGIN_DAEMON_KEY y PLUGIN_DIFY_INNER_API_KEY, en la raíz docker/.env para que el demonio y sus clients reciban valores coincidentes. Los puertos, las rutas de volumen, los perfiles y la programación de comprobaciones de estado también siguen siendo entradas de configuración raíz. Consulte la guía de configuración Docker. (#45359)

Implementaciones de origen

Utilice Python 3.13, Node.js 24.22.1 o posterior en la línea 24.x y pnpm 12.16.1. pnpm ya no proporciona Node.js para el espacio de trabajo, por lo tanto, instale el tiempo de ejecución Node.js requerido por separado. (#44976, #45094)

Desde la raíz del repositorio:

uv sync --project api --frozen
uv run --directory api flask db upgrade
pnpm install --frozen-lockfile

Reconstruya la aplicación web y reinicie los servicios API, trabajador, programador y agente desde la misma versión. Actualice las dependencias bloqueadas server del agente backend independiente cuando lo implemente por separado.

difyctl

Instale el 1.19.0 client correspondiente y utilice difyctl help para descubrir el catálogo de servidores actual. Actualice las habilidades del agente instalado con difyctl install skills <dir>. La automatización del flujo de trabajo y del chat debe utilizar la operación stop.run revisada; Las aplicaciones basadas en mensajes utilizan stop.task.

Los cambios operativos a planificar incluyen:

  • Índices de limpieza de almacenamiento (d7e9a1c3f502). Agregue índices de referencia en message_files.upload_file_id, workflow_node_execution_offload.file_id y workflow_draft_variable_files.upload_file_id. PostgreSQL los crea simultáneamente, pero la construcción del índice aún escanea datos y consume E/S. Las actualizaciones en línea reutilizan índices coincidentes en buen estado y rechazan definiciones conflictivas o no válidas. Investigar una compilación no válida interrumpida antes de volver a intentarlo; no elimine índices saludables como recuperación de rutina. (#44982)
  • Seguimiento de la unicidad de la configuración (53c10126d551). Mantenga una configuración por aplicación/proveedor y agregue un índice único.   • El historial de seguimiento no se reconstruye. Los datos del libro mayor de seguimiento del agente existente siguen siendo legibles, pero los seguimientos exportados anteriormente no adquieren los nuevos intervalos anidados. (#44673)

Cambios detallados

<detalles> <summary><strong>Nuevas capacidades · rastreo, paquetes y habilidades</strong></summary>

Seguimiento e integraciones de proveedores

  • Consolidar la entrega a través de la interfaz de proveedor compartida para Langfuse, LangSmith, Opik, Weave, Arize, Phoenix, Aliyun, MLflow, Databricks y Tencent. Las exportaciones reintentables reenvían la misma unidad de seguimiento con identificadores deterministas. (#44673)
  • Incluir marcos de ejecución persistentes denominados herramientas de flujo de trabajo en exportaciones externas, bajo sus intervalos de herramientas de invocación. Las ejecuciones de flujos de trabajo anidados de forma independiente siguen siendo seguimientos separados vinculados por identificadores principales. (#44673)
  • Mantenga las credenciales de seguimiento como de solo escritura. Los secretos en blanco u omitidos preservan los valores almacenados; Para cambiar un host, punto final o URL de destino es necesario volver a introducir sus secretos. (#44673)

Paquetes de aplicaciones portátiles

  • Empaquetar los flujos de trabajo detrás de las llamadas herramientas de flujo de trabajo, incluidas las dependencias transitivas, con un máximo predeterminado de 20 flujos de trabajo de herramientas incluidos. Las herramientas de destino que faltan se recrean y publican; Se reutilizan las herramientas existentes. La creación de herramientas faltantes requiere permiso de administración de herramientas y una cuota de aplicaciones suficiente. Los paquetes que necesitan confirmación de la versión DSL se rechazan en este flujo y las aplicaciones creadas antes de un error de importación se limpian. (#44592)
  • Emitir siempre el formato v2 para los paquetes de aplicaciones, incluidos los paquetes anidados y los paquetes sin herramientas de flujo de trabajo. Esto no cambia el formato del paquete separado lista-Agente. (#45353)
  • Los ID de herramientas de flujo de trabajo y API ya no se convierten en dependencias falsas del complemento langgenius/<uuid> durante la exportación. (#44592)

Habilidades y OpenAPI

  • Exporte borradores o versiones de Skill publicadas, importe carpetas y publique a través de operaciones de espacio de trabajo autenticadas por cuenta. Una importación con un ID de habilidad reemplaza el borrador de esa habilidad; el nombre SKILL.md importado debe coincidir. Las comprobaciones opcionales draft_hash rechazan los reemplazos obsoletos, pero utilizan marcas de tiempo de segunda resolución y no detectan ediciones realizadas en el mismo segundo. (#44941)
  • La importación de habilidades elimina la basura del sistema operativo, rechaza rutas duplicadas o no seguras, impone límites de tamaño/archivo, reutiliza activos binarios idénticos y elimina activos escritos por una importación fallida. Se conservan los guiones literales dentro del texto inicial de la habilidad. (#44941, #43602)
  • El catálogo de operaciones publica el efecto de cada operación y la ayuda CLI lo muestra. La detención del flujo de trabajo/flujo de chat utiliza la propiedad y el estado de ejecución almacenados; las ejecuciones desconocidas devuelven 404, y las ejecuciones finalizadas o no detenibles devuelven 409. La detención de la aplicación de mensajes mantiene su semántica de ID de tarea. (#44587, #45314)
  • Agregue el paquete experimental @dify/openapi-content-mapper para llamadas API escritas y ayudas de consulta inferidas de fuentes OpenAPI, con tipos de esquema/entrada/salida reutilizables y subrutas de tipos compatibles con contratos opcionales. Esta es la base del desarrollo; Estos cambios no migran las llamadas de producción de Console o Marketplace fuera de sus clients existentes. (#44627, #44915)

Flujos de trabajo y ejecución

  • Restaure el respaldo de salida estructurada para modelos sin soporte nativo y conserve los valores booleanos JSON en lugar de convertirlos en cadenas. (#44962)
  • Respete los valores predeterminados de lista de archivos y archivos configurados en Studio, aplicaciones publicadas y ejecución de API. La limpieza explícita se distingue de la omisión, restablecer las conversaciones restaura los valores predeterminados y guardar los valores predeterminados del archivo ya no envía objetos Blob al navegador que causan errores 415. (#44780, #45042)
  • Conserve el cero numérico en las entradas y vistas previas requeridas de Studio, y conserve tanto el cero como el falso en las declaraciones iniciales. Las cargas útiles de referencias de archivos que no son objetos recurren a la referencia original en lugar de fallar inesperadamente. (#45005, #44833, #45088)
  • Admita solicitudes de flujo de trabajo y flujo de chat de transmisión solo una vez según los límites de simultaneidad de la aplicación, por lo que un límite de uno acepta la única solicitud activa. Los eventos de Terminal Chatflow ahora detienen el mecanismo de vigilancia de ejecución y liberan su contexto retenido. (#45038, #45029)
  • Preservar la identidad de la persona que llama para el acceso programado a los archivos del Agente, usar el reloj UTC para el sys.timestamp del nodo de inicio y ordenar vistas previas de la programación semanal por fecha. Los números de formulario/consulta de webhook conservan la precisión de números enteros y rechazan valores no finitos. (#44796, #44847, #44718, #44706)
  • Actualizar los nodos de flujo de trabajo disponibles cuando cambia la disponibilidad, conservar las variables generadas al aplicar un mensaje generado, escapar del resaltado de búsqueda de variables y preservar el enfoque del editor de mensajes cuando se actualizan los metadatos variables. (#44769, #45274, #44625, #44791)
  • Solicite confirmación de limpieza del lienzo solo cuando borre un borrador guardado previamente que no esté vacío y envuelva mensajes de error de flujo de trabajo largos. (#45028, #45106)

Agentes, herramientas y habilidades

  • Conserve las credenciales OAuth actualizadas y serialice las actualizaciones simultáneas en todas las herramientas y fuentes de datos, protegiendo los tokens rotativos y la reautorización simultánea. dify 1.19.0

Dify 1.19.0 brings nested workflow tracing to your observability tools. Follow a workflow into the Workflow Tools it calls, inspect the steps inside each invocation, and keep the LLM context alongside the execution tree.

This release also makes Workflow Tools portable with App packages, adds Skill Hub automation, and makes Agent files easier to upload and preview. The bundled plugin daemon is upgraded to 0.6.14-local.

Release highlights · Upgrade guide · Detailed changes

<a id="release-highlights"></a>

Release highlights

Nested workflow tracing

See what happens inside a Workflow Tool, all the way down to its LLM calls.

Building on the Console drilldown introduced in 1.18.0, new external traces now include the persisted execution steps inside called Workflow Tools. Child steps appear beneath the Tool span that invoked them, preserving the hierarchy across nested and repeated calls. (#44673)

From the outer workflow to a nested LLM call: the execution tree and formatted messages, together in Langfuse. Screenshot from #44673.

  • Follow the hierarchy. Expand called Workflow Tools to see their internal execution steps under the invoking Tool span.
  • Understand each invocation. Repeated calls and failures retain their place in the trace.
  • Keep the LLM context. Inspect formatted prompts and responses, token usage, and project, trace, and observation links.

[!NOTE] Your saved provider settings continue to work. The richer hierarchy applies to new executions; historical traces are not backfilled. Independently nested workflow runs remain separate traces linked by parent identifiers. For rolling deployments, follow the tracing queue transition below.

Take Workflow Tools with your apps

Export an app and bring the workflows behind its Workflow Tools with it. .ifpkg packages include those workflows at their bound versions, including transitive dependencies. Import reuses tools already in the destination workspace and recreates, publishes, and registers missing ones, remapping their references. (#44592)

All Dify app exports now use package format v2, including apps without Workflow Tools. Existing v1 imports and explicit YAML export remain supported. See the upgrade guide before importing new packages into older installations. (#45353)

Upload together. Preview in place.

Select or drop multiple Agent configuration files and upload them in parallel. Successful uploads are bound in one atomic batch, concurrent Composer saves preserve the latest files, and Prompt uploads keep the cursor position while inserting multiple references. (#44947)

Read PDFs inline, inspect source files with syntax highlighting, and see when text has been truncated. Previews cover configured files, Skill members, and working-directory files, with a download action when a PDF cannot be loaded. (#45032, #45045)

<a id="upgrade-guide"></a>

Upgrade guide

[!IMPORTANT] Read the upgrade guide before deploying. Docker Compose now requires v2.35.0 or later. Preserve existing environment files, upgrade the Dify components together, and use the new tracing queue during rolling deployments. New App packages use format v2 and require a compatible destination importer. The bundled plugin daemon moves to 0.6.14-local.

Compatibility and rollout

  1. Back up first. Retain the database, vector-store data, uploaded files, Agent snapshot/workspace storage, deployment secrets, and environment files. Use a maintenance window for a single-stack upgrade.
  2. Upgrade the components together. Use matching 1.19.0 API, worker, web, Agent Backend, and Local sandbox images, with plugin daemon 0.6.14-local. Keep the existing Local sandbox authentication token and any configured PASSWORD_PEPPER unchanged. If upgrading from before 1.18.0, also follow the 1.18.0 upgrade guide.
  3. Use Docker Compose 2.35.0 or later. This is the minimum supported version for root .env overrides to take precedence when Compose resolves service defaults. Check your installed version with docker compose version. (#45359)
  4. Keep tracked defaults separate from local overrides. Bundled docker/envs/**/*.defaults files load automatically. Customize a service through its matching local .env file, using the override path documented in the defaults file; root docker/.env holds deployment inputs and explicit overrides. Preserve existing .env files and edit them in place. Review accidentally empty assignments and values pinned by older template copies before upgrading. (#45359, #45376)
  5. Existing shared.env files remain supported. Common API, worker, and Beat customizations now belong in docker/envs/core-services/api-worker.env. Compose still reads legacy docker/envs/core-services/shared.env first, then api-worker.env, so api-worker.env wins when both set conflicting values. Root docker/.env takes precedence over both. An unchanged copy of api-worker.defaults preserves existing shared.env customizations. See the Docker configuration guide. (#45376)
  6. Separate tracing queues during a rolling upgrade. New tasks default to OPS_TRACE_QUEUE=ops_trace_v2; API, workers, and Beat must agree. Custom CELERY_QUEUES, CELERY_WORKER_QUEUES, or --queues lists must include the new queue. Keep old tracing workers on ops_trace until old producers and all their queued, active, reserved, scheduled, and retry work have finished. Do not purge the old queue or ask the new retired handler to export legacy messages. See the tracing rollout guide. (#44673)
  7. Upgrade package destinations before importing new App packages. New app packages always use format v2. Older importers, including builds with the earlier strict v2 rule, may reject them. Version 1 imports remain supported on 1.19.0. Explicit YAML export remains available, but does not carry bundled Workflow Tool dependencies. (#44592, #45353)
