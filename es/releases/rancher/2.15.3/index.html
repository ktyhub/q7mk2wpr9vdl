ranchero v2.15.3

Lanzamiento v2.15.3

[!IMPORTANTE]

  • Si está utilizando el Servicio de federación de Active Directory (AD FS), la actualización a Rancher v2.10.1 o posterior puede causar problemas con la autenticación, lo que requiere intervención manual. Estos problemas se deben a que la parte dependiente de AD FS Trust no puede obtener un certificado de verificación de firma de los metadatos. Para obtener más información, consulte #48655. Estos problemas se pueden corregir mediante cualquiera de dos métodos:

  • Actualización de la información de la parte de confianza Trust a partir de los metadatos de la federación (Parte de confianza Trust → Actualización de los metadatos de la federación…​).

  • Agregar directamente el certificado (Parte de confianza Trust → Propiedades → pestaña Firma → Agregar → Seleccionar el certificado).

Rancher v2.15.3 es el último parche de Rancher. Esta es una versión comunitaria que presenta actualizaciones de mantenimiento y correcciones de errores.

Para obtener más información sobre las nuevas funciones de la versión menor general, consulte v2.15.0 release notes.

Correcciones de seguridad para vulnerabilidades

Esta versión aborda los siguientes problemas de seguridad:

Ranchero

  • Se corrigió una vulnerabilidad de seguridad en el punto final del metaproxy de Rancher donde la lista de destino permitida se evaluaba en una ubicación que no podía evitar que se reenviara una solicitud. Un usuario autenticado podría hacer que el servidor Rancher envíe solicitudes a servicios internos que la lista de permitidos debe bloquear y recibir las respuestas. La lista de permitidos ahora se aplica en el controlador de solicitudes, que rechaza los destinos no permitidos antes de que se realice cualquier conexión. Para obtener más información, consulte CVE-2026-88809.
  • Se corrigió una vulnerabilidad de seguridad en la validación RBAC de Rancher donde no se verificaba el campo inheritedNamespacedRules de un GlobalRole para escalada de privilegios. Un usuario con permisos delegados para administrar roles globales y enlaces de roles globales podría otorgar permisos en clústeres posteriores que excedieran los suyos. Los webhooks de admisión GlobalRole y GlobalRoleBinding ahora validan este campo de la misma manera que los demás campos con permiso. Para obtener más información, consulte CVE-2026-88810.
  • Se corrigió una vulnerabilidad de seguridad en el metaproxy de Rancher Manager donde las credenciales de Rancher de la persona que llama no se eliminaban consistentemente de las solicitudes enviadas a hosts de proveedores de nube de terceros. La credencial de sesión de un usuario que inició sesión se podría enviar a un proveedor de nube durante el uso normal de las vistas de aprovisionamiento, y se podría enviar un token Rancher de API client cuando se omitieran los encabezados de selección de credenciales del proxy. El proxy ahora elimina las credenciales de la persona que llama en cada ruta de solicitud. Para obtener más información, consulte CVE-2026-88811.
  • Se corrigió una vulnerabilidad de seguridad en Rancher donde la verificación de autorización que protege el shell del clúster local no se aplicaba a todas las rutas API que podían alcanzarlo. Cualquier usuario autenticado, incluido uno sin permisos en el clúster local, podría obtener un pod de shell sin privilegios en el clúster de administración, rompiendo el aislamiento esperado del plano de administración. La verificación de autorización ahora se aplica de manera consistente para todos los formularios de solicitud. Para obtener más información, consulte CVE-2026-104623.

Flota

  • Se corrigió una vulnerabilidad de escalada de privilegios en el controlador de administración de agentes de Fleet, donde un objeto de clúster de Fleet creado por un usuario normal podía hacer referencia a credenciales administrativas para el clúster de administración de Rancher (local). Esto permitió que un usuario autenticado que tuviera solo el rol global predeterminado user, sin permisos en el clúster local, obtuviera administrador de clúster en el clúster de administración de Rancher y, por lo tanto, en todos los clústeres administrados. Fleet ahora solo acepta un secreto de kubeconfig de otro espacio de nombres cuando el secreto está etiquetado para su uso en el espacio de nombres de referencia y solo implementa agentes en el clúster de administración para sus propios clústeres de sistemas. Para obtener más información, consulte CVE-2026-94290.
  • Se corrigió una vulnerabilidad de seguridad en Fleet donde la identidad del clúster reclamada durante el registro del clúster no estaba vinculada al token de registro utilizado para la solicitud. Un poseedor de un token de registro de espacio de trabajo válido que conociera el identificador client de otro clúster podría obtener credenciales para el espacio de nombres de administración de flotas de ese clúster e interrumpir a su agente legítimo. Fleet ahora registra el token de registro con el que está registrado un clúster y rechaza las solicitudes de registro que afirman la misma identidad de clúster con un token diferente. Para obtener más información, consulte CVE-2026-104615.

Para obtener detalles adicionales, consulte la página de avisos de seguridad y CVE en la [documentación] de Rancher (https://ranchermanager.docs.rancher.com/v2.15/reference-guides/rancher-security/security-advisories-and-cves) o en el [repositorio] GitHub de Rancher (https://github.com/rancher/rancher/security/advisories).

General ganadero

Correcciones de errores importantes

  • Se solucionó un problema por el cual la configuración de Rancher configurada usando variables de entorno retenía valores obsoletos y el atributo source: env después de que se eliminaba la variable de entorno. Cuando se elimina una variable de entorno, Rancher ahora borra la fuente y el valor del entorno almacenado al inicio. Luego, la configuración vuelve a su valor predeterminado. Consulte Consulte #58075.

Aprovisionamiento de clústeres

Correcciones de errores importantes

  • Se solucionó un problema por el cual los clústeres importados podían dejar de estar disponibles después de actualizar Rancher si el agente del clúster se volvía a implementar antes de que se migrara su token de registro, dejando al agente con un token vacío. Consulte #58028.

  • Se solucionó un problema por el cual los clústeres aprovisionados con instantáneas de S3 etcd podían permanecer bloqueados durante la eliminación. Consulte #57506.

Notas de instalación/actualización

Si está instalando Rancher por primera vez, su entorno debe cumplir con los [requisitos de instalación] (https://ranchermanager.docs.rancher.com/v2.15/getting-started/installation-and-upgrade/installation-requirements).

[!IMPORTANTE]

  • Rancher ahora requiere que el clúster en el que se ejecuta tenga habilitada la Capa de agregación Kubernetes API. Esto se debe a que Rancher amplía Kubernetes con API adicionales registrando su propia extensión de servidor API. Tenga en cuenta que todas las versiones de Kubernetes compatibles con las distribuciones K8 de esta versión Rancher (RKE2/K3) tendrán la capa de agregación configurada y habilitada de forma predeterminada.

  • Consulte la documentación del servidor de extensión API y #50400 para obtener más información.

  • El motor Rancher Kubernetes (RKE/RKE1) llegó al final de su vida útil a partir del 31 de julio de 2025. Las versiones Rancher 2.12.0 y posteriores ya no admiten el aprovisionamiento ni la gestión de clústeres RKE1 posteriores. Recomendamos cambiar la plataforma de los clústeres RKE1 a RKE2 para garantizar soporte continuo y actualizaciones de seguridad. Obtenga más información sobre la transición aquí.

  • Rancher ahora tiene una verificación de validación previa a la actualización para los recursos RKE1 que falla y enumera los recursos RKE1 si están presentes. Consulte #50286 para obtener más información.

  • Es fundamental que revise el espacio en disco disponible en sus nodos y planifique en consecuencia antes de actualizar a Rancher v2.12.0 y posteriormente para evitar posibles problemas de presión del disco y desalojo de pods.

  • Para obtener información adicional, consulte la [Paginación del lado del servidor de la interfaz de usuario: documentación sobre el espacio en disco] (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/advanced-user-guides/ui-server-side-pagination#disk-space).

  • Rancher ahora tiene una opción de habilitación llamada AUDIT_LOG_ENABLED para los registros de auditoría API para una instalación de Rancher.

  • En las versiones Rancher 2.11.x y anteriores, solo se podía configurar AUDIT_LEVEL y el nivel de registro predeterminado (0) deshabilitaría el registro de auditoría. En las versiones Rancher 2.12.x y posteriores, el nivel de registro predeterminado (0) ahora solo contiene los metadatos de solicitud y respuesta de registro, y se puede configurar al configurar AUDIT_LOG_ENABLED. Si instala o actualiza a través de Helm, puede habilitar los registros de auditoría API y especificar el nivel de registro aplicando la siguiente configuración a su comando Helm: --set auditLog.enabled=true --set auditLog.level=0. Consulte la documentación Cómo habilitar el registro de auditoría API para registrar eventos del sistema y #48941.

Cambios en los artefactos de imagen

Los resúmenes de artefactos de imágenes cambiaron de nombre a Rancher v2.12.0, v2.11.4 y v2.10.8. Hasta este cambio, se mantenían archivos de resúmenes de imágenes separados para cada sistema operativo y arquitectura por razones de compatibilidad. Con este cambio, solo se proporcionará un archivo para cada sistema operativo:

  • Los archivos rancher-images-digests-linux-amd64.txt y rancher-images-digests-linux-arm64.txt pasarán a llamarse rancher-images-digests-linux.txt.

  • Los archivos rancher-images-digests-windows-ltsc2019.txt y rancher-images-digests-windows-ltsc2022.txt pasarán a llamarse rancher-images-digests-windows.txt.

Requisitos de actualización

  • Creando copias de seguridad: Crea una copia de seguridad antes de actualizar Rancher. Para revertir Rancher después de una actualización, primero debe realizar una copia de seguridad y restaurar Rancher a la versión anterior de Rancher. Debido a que Rancher se restaurará al mismo estado que cuando se creó la copia de seguridad, los cambios posteriores a la actualización no se incluirán después de la restauración.

  • Requisitos de la versión del timón:

    • Para administrar Rancher 2.12.x y versiones posteriores, debe actualizar su Helm client a la versión 3.18 o posterior.

    • Este cambio es necesario para reflejar la incorporación de compatibilidad con Kubernetes 1.33 con esta versión.

    • Actualmente, la [Política de soporte de versión de Helm] oficial (https://helm.sh/docs/topics/version_skew/) dicta que solo Helm 3.18 admite el rango de versión Kubernetes adecuado para Rancher 2.12.

  • Requisitos CNI:

    • Para Kubernetes v1.19 y posteriores, desactive firewalld ya que es incompatible con varios complementos CNI. Consulte #28840.

    • Al actualizar o instalar una distribución de Linux que utiliza nf_tables como filtro de paquetes backend, como SLES 15, RHEL 8, Ubuntu 20.10, Debian 10 o posterior, actualice a RKE v1.19.2 o posterior para obtener franela v0.13.0. La franela v0.13.0 admite nf_tables. Ver Franela #1317.

  • Requisitos para entornos con espacios separados de aire:

    • Cuando utilice un proxy frente a una instancia Rancher aislada, debe pasar parámetros adicionales a NO_PROXY. Consulte la documentación y emita #2725.

  • Al instalar Rancher con Docker en un entorno con espacio de aire, debe proporcionar un archivo registries.yaml personalizado al comando docker run, como se muestra en la [documentación de K3s] (https://docs.k3s.io/installation/private-registry). Si el registro tiene certificados, también deberá proporcionarlos. Consulte #28969.

rancher v2.15.3

Release v2.15.3

[!IMPORTANT]

  • If you are using Active Directory Federation Service (AD FS), upgrading to Rancher v2.10.1 or later may cause issues with authentication, requiring manual intervention. These issues are due to the AD FS Relying Party Trust not being able to pick up a signature verification certificate from the metadata. For more information, see #48655. These issues can be corrected by either of two methods:

    • Updating the Relying Party Trust information from federation metadata (Relying Party Trust → Update from Federation Metadata…​).

    • Directly adding the certificate (Relying Party Trust → Properties → Signature tab → Add → Select the certificate).

Rancher v2.15.3 is the latest patch release of Rancher. This is a Community version release that introduces maintenance updates and bug fixes.

For more information on new features in the general minor release, see the v2.15.0 release notes.

Security Fixes for Vulnerabilities

This release addresses the following security issues:

Rancher

  • Fixed a security vulnerability in the Rancher meta proxy endpoint where the destination allowlist was evaluated in a location that could not prevent a request from being forwarded. An authenticated user could cause the Rancher server to send requests to internal services that the allowlist is intended to block and receive the responses. The allowlist is now enforced in the request handler, which rejects disallowed destinations before any connection is made. For more information, see CVE-2026-88809.
  • Fixed a security vulnerability in Rancher's RBAC validation where the inheritedNamespacedRules field of a GlobalRole was not checked for privilege escalation. A user with delegated permissions to manage global roles and global role bindings could grant permissions in downstream clusters that exceeded their own. The GlobalRole and GlobalRoleBinding admission webhooks now validate this field in the same way as the other permission-carrying fields. For more information, refer to CVE-2026-88810.
  • Fixed a security vulnerability in the Rancher Manager meta proxy where the caller's own Rancher credentials were not consistently removed from requests forwarded to third-party cloud provider hosts. A signed-in user's session credential could be sent to a cloud provider during ordinary use of provisioning views, and an API client's Rancher token could be sent when it omitted the proxy's credential selection headers. The proxy now strips the caller's credentials on every request path. For more information, refer to CVE-2026-88811.
  • Fixed a security vulnerability in Rancher where the authorization check that protects the local cluster shell was not applied to every API route that could reach it. Any authenticated user, including one with no permissions on the local cluster, could obtain an unprivileged shell pod on the management cluster, breaking the expected isolation of the management plane. The authorization check is now enforced consistently for all request forms. For more information, see CVE-2026-104623.

Fleet

  • Fixed a privilege escalation vulnerability in Fleet's agent management controller, where a Fleet cluster object created by an ordinary user could reference administrative credentials for the Rancher management (local) cluster. This allowed an authenticated user holding only the default user global role, with no permissions on the local cluster, to gain cluster-admin on the Rancher management cluster and thereby on all managed clusters. Fleet now only accepts a kubeconfig secret from another namespace when the secret is labeled for use by the referencing namespace, and only deploys agents onto the management cluster for its own system clusters. For more information, refer to CVE-2026-94290.
  • Fixed a security vulnerability in Fleet where the cluster identity claimed during cluster registration was not bound to the registration token used for the request. A holder of a valid workspace registration token who knew another cluster's client identifier could obtain credentials for that cluster's Fleet management namespace and disrupt its legitimate agent. Fleet now records the registration token a cluster is registered with and rejects registration requests that claim the same cluster identity with a different token. For more information, refer to CVE-2026-104615.

For additional details, see the Security Advisories and CVEs page in Rancher's documentation or in Rancher's GitHub repository.

Rancher general

Major bug fixes

  • Fixed an issue where Rancher settings configured using environment variables retained stale values and the source: env attribute after the environment variable was removed. When an environment variable is removed, Rancher now clears the stored environment source and value on startup. The setting then reverts to its default value. See See #58075.

Cluster provisioning

Major bug fixes

  • Fixed an issue where imported clusters could become unavailable after upgrading Rancher if the cluster agent was redeployed before its registration token was migrated, leaving the agent with an empty token. See #58028.

  • Fixed an issue where provisioned clusters with S3 etcd snapshots could remain stuck during deletion. See #57506.

Install/Upgrade Notes

If you’re installing Rancher for the first time, your environment must fulfill the installation requirements.

[!IMPORTANT]

  • Rancher now requires the cluster it runs on to have the Kubernetes API Aggregation Layer enabled. This is because Rancher extends Kubernetes with additional APIs by registering its own extension API server. Please note that all versions of Kubernetes supported in this Rancher versions K8s distributions (RKE2/K3s) will have the aggregation layer configured and enabled by default.

    • Refer to the Extension API Server documentation and #50400 for more information.

  • Rancher Kubernetes Engine (RKE/RKE1) has reached end of life as of July 31, 2025. Rancher versions 2.12.0 and later no longer support provisioning or managing downstream RKE1 clusters. We recommend replatforming RKE1 clusters to RKE2 to ensure continued support and security updates. Learn more about the transition here.

    • Rancher now has a pre-upgrade validation check for RKE1 resources which fails and lists the RKE1 resources if present. Refer to #50286 for more information.

  • It is crucial that you review the available disk space on your nodes and plan accordingly before upgrading to Rancher v2.12.0 and later to avoid potential disk pressure and pod eviction issues.

    • For additional information, refer to the UI Server Side Pagination - Disk Space documentation.

  • Rancher now has an enablement option called AUDIT_LOG_ENABLED for API Audit Logs for a Rancher installation.

    • In Rancher versions 2.11.x and earlier, only the AUDIT_LEVEL could be set and the default log level (0) would disable the audit log. In Rancher versions 2.12.x and later, the default log level (0) now only contains the log request and response metadata, and can be set when configuring AUDIT_LOG_ENABLED. If installing or upgrading via Helm you can enable the API Audit Logs and specify the log level by applying the following setting to your Helm command: --set auditLog.enabled=true --set auditLog.level=0. See the Enabling the API Audit Log to Record System Events documentation and #48941.

Changes in Image Artifacts

Image artifact digests are renamed in Rancher v2.12.0, v2.11.4 and v2.10.8. Up until this change, separate image digests files for each operating system and architecture have been maintained for compatibility reasons. With this change, only one file for each operating system is to be provided:

  • The rancher-images-digests-linux-amd64.txt and rancher-images-digests-linux-arm64.txt files are to be renamed to rancher-images-digests-linux.txt.

  • The rancher-images-digests-windows-ltsc2019.txt and rancher-images-digests-windows-ltsc2022.txt files are to be renamed to rancher-images-digests-windows.txt.

Upgrade Requirements

  • Creating backups: Create a backup before you upgrade Rancher. To roll back Rancher after an upgrade, you must first back up and restore Rancher to the previous Rancher version. Because Rancher will be restored to the same state as when the backup was created, any changes post-upgrade will not be included after the restore.

  • Helm version requirements:

    • To manage Rancher 2.12.x and later, you must upgrade your Helm client to version 3.18 or newer.

    • This change is required to reflect the addition of Kubernetes 1.33 support with this release.

    • Currently, the official Helm Version Support Policy dictates that only Helm 3.18 supports the proper Kubernetes version range for Rancher 2.12.

  • CNI requirements:

    • For Kubernetes v1.19 and later, disable firewalld as it’s incompatible with various CNI plugins. See #28840.

    • When upgrading or installing a Linux distribution that uses nf_tables as the backend packet filter, such as SLES 15, RHEL 8, Ubuntu 20.10, Debian 10, or later, upgrade to RKE v1.19.2 or later to get Flannel v0.13.0. Flannel v0.13.0 supports nf_tables. See Flannel #1317.

  • Requirements for air-gapped environments:

    • When using a proxy in front of an air-gapped Rancher instance, you must pass additional parameters to NO_PROXY. See the documentation and issue #2725.

    • When installing Rancher with Docker in an air-gapped environment, you must supply a custom registries.yaml file to the docker run command, as shown in the K3s documentation. If the registry has certificates, then you’ll also need to supply those. See #28969.

Long-standing Known Issues - Cluster Provisioning

  • Rancher v2.15.1:

    • Creating or editing v2prov clusters with native CAPI infrastructure providers from the UI can under some failure conditions leave unused infrastructure resources in the management cluster that must be cleaned up manually. See #55705.

  • Rancher v2.15.0:

    • Imported clusters cannot reconnect to Rancher if their registration token is rotated while they are disconnected and the grace period ends before they reconnect. The cluster agent logs 400 Bad Request with the response body cluster not found. As a workaround, re-run the registration command from the cluster Registration tab on the downstream cluster. To prevent the issue, increase the crt-default-grace-period-minutes setting to cover the expected downtime, or disable the crt-token-ttl-rotation feature flag. See #57078.

  • Not all cluster tools can be installed on a hardened cluster.

  • Rancher v2.8.1:

    • When you attempt to register a new etcd/controlplane node in a CAPR-managed cluster after a failed etcd snapshot restoration, the node can become stuck in a perpetual paused state, displaying the error message [ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again. As a workaround, you can unpause the cluster by running kubectl edit clusters.cluster clustername -n fleet-default and set spec.unpaused to false. See #43735.

Long-standing Known Issues - RKE2 Provisioning

  • Rancher v2.7.7:

    • Due to the backoff logic in various components, downstream provisioned K3s and RKE2 clusters may take longer to re-achieve Active status after a migration. If you see that a downstream cluster is still updating or in an error state immediately after a migration, please let it attempt to resolve itself. This might take up to an hour to complete. Long-standing Known Issues - Rancher Webhook

  • Rancher v2.7.2:
