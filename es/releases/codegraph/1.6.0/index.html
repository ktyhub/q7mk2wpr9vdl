códice v1.6.0

[1.6.0] - 2026-08-26

Destacados

  • GitHub Copilot ahora es compatible: codegraph install lo configura en VS Code, Copilot CLI y los IDE de JetBrains, junto a los agentes que ya conocía.
  • Configuración con un solo comando: codegraph install --yes --init conecta a sus agentes e indexa su proyecto sin indicaciones, ideal para un contenedor nuevo o CI.
  • Mejores respuestas para su agente: codegraph_explore ya no repite el código que ya le mostró, siempre recupera los archivos y símbolos que solicitó por nombre y gasta su espacio en el código que realmente responde a la pregunta en lugar de archivos similares, generados y correcciones de tipo.
  • Su gráfico permanece correcto mientras continúa codificando: un índice de larga duración ya no se deriva de uno nuevo, y las ediciones en codegraph.json (como exclude) se aplican inmediatamente sin necesidad de reiniciar.
  • No más bloqueos o bloqueos silenciosos: los archivos C/C++ profundamente anidados, los proyectos Swift Vapor y los grandes lotes de sincronización que solían interrumpir o detener la indexación ahora finalizan limpiamente.
  • Se solucionó una pérdida de espacio en disco: una sesión cerrada a la fuerza podría dejar atrás el registro de escritura anticipada de la base de datos para crecer sin límites (se informó de decenas de gigabytes); el registro sobrante ahora se vuelve a doblar en el índice y se recorta automáticamente la próxima vez que se abre el proyecto. El índice en sí no tiene límite de tamaño.
  • Funciona desde un espacio de trabajo o raíz monorepo: el servidor MCP encuentra su proyecto indexado cuando se inicia desde una carpeta situada encima de él y lo indica claramente cuando no puede encontrar uno.
  • Gráficos de código más precisos para proyectos TypeScript, Rust, Erlang, C/C++ y Python; consulte la lista completa a continuación.
  • También nuevo: configuración del Codex por proyecto (codegraph install --location=local), una configuración deprioritize para evitar que las carpetas auxiliares superen en rango a su código real, el comando codegraph context y estadísticas de uso que ahora permanecen completamente en los propios servidores de CodeGraph. Después de la actualización, ejecute codegraph index una vez en cada proyecto para que su gráfico existente recoja estas correcciones: codegraph status le recuerda cuando es necesario.

Nuevas características

  • GitHub Copilot ahora es un agente compatible: codegraph install puede configurar Copilot Chat en VS Code (copilot-vscode), GitHub Copilot CLI (copilot-cli) y el complemento Copilot en JetBrains IDE (copilot-jetbrains). Las superficies Copilot instaladas se detectan automáticamente como cualquier otro agente, las entradas del servidor MCP existentes en sus archivos de configuración se conservan y codegraph uninstall invierte la configuración limpiamente. Reinicie VS Code o su IDE de JetBrains después de la instalación para que Copilot recoja el servidor.
  • codegraph install --init conecta a sus agentes y crea el índice del proyecto actual en un solo comando, y codegraph init --yes se ejecuta sin ningún mensaje, por lo que un nuevo contenedor o trabajo de CI puede iniciar CodeGraph con una sola línea no interactiva (codegraph install --yes --init). El instalador nunca indexa nada a menos que usted lo solicite con la bandera, y se aplica el rechazo de seguridad habitual para un directorio de inicio o raíz del sistema de archivos. (#1578)
  • Codex CLI ahora se puede configurar por proyecto en lugar de solo para todo el usuario: codegraph install --location=local escribe ./.codex/config.toml y el bloque CodeGraph en el AGENTS.md de su proyecto, por lo que CodeGraph se conecta solo a ese repositorio en lugar de a cada sesión de Codex en la máquina. codegraph uninstall --location=local lo invierte y la instalación global no se modifica en ningún caso. Codex solo aplica la configuración de un proyecto una vez que haya marcado el proyecto como trusted, por lo que el instalador lo dice después de una instalación local. Gracias @maxmilian. (#1531)
  • Una nueva configuración de deprioritize en codegraph.json evita que las rutas que nombre superen el código de su producto en la búsqueda y las respuestas de codegraph_explore, sin eliminar nada del índice. Toma patrones de estilo gitignore como exclude, pero es solo de clasificación: árboles de secuencias de comandos auxiliares, resultados generados o directorios complementarios opcionales cuyos nombres de símbolos genéricos (usage, run, status) de otro modo desplazarían el código que realmente responde a una consulta permanecería completamente indexado y se podría encontrar, y una consulta que realmente apunta a dicho árbol todavía lo devuelve. Gracias @maxmilian. (#982)
  • codegraph_explore ya no vuelve a enviar la fuente que ya devolvió anteriormente en la misma conversación. Un archivo que ya le ha mostrado regresa como un breve puntero (la ruta, los símbolos y el rango de línea exacto, con la confirmación de que el archivo no ha cambiado desde entonces) y el espacio que se libera se gasta en código que aún no ha visto, por lo que una llamada de seguimiento cubre nuevos terrenos en lugar de repetir la última. Si un archivo se editó en el medio, su fuente siempre se muestra nuevamente en su totalidad. Configure CODEGRAPH_EXPLORE_DEDUP=0 para desactivar esto.
  • Cuando un agente se conecta a través de MCP, CodeGraph ahora indica de antemano que indexa más de 30 idiomas (TypeScript/JavaScript, Python, Go, Rust, Java, C#, C/C++, PHP, Ruby, Swift, Kotlin y más), por lo que los agentes ya no asumen que un idioma no es compatible y se saltan el gráfico. (#671)
  • La telemetría de uso anónimo ahora se almacena completamente en la infraestructura propia de CodeGraph: ningún proveedor de análisis externo recibe nada de ella y el punto final que la recibe no realiza ninguna solicitud saliente. Los eventos individuales se eliminan después de 90 días, dejando solo totales diarios anónimos. No ha cambiado nada sobre lo que se recopila, su dirección IP nunca se lee ni se almacena, y cada interruptor de apagado funciona exactamente como antes (codegraph telemetry off, CODEGRAPH_TELEMETRY=0, DO_NOT_TRACK=1). TELEMETRY.md sigue siendo la lista completa campo por campo.

Correcciones

Mejores respuestas de codegraph_explore

  • Nombrar un archivo por su ruta en una consulta codegraph_explore ahora funciona de manera confiable: la ruta se resuelve en función del índice y se garantiza que ese archivo ocupará un lugar en la parte superior de la respuesta. Anteriormente, la ruta se dividía en fragmentos (segmentos de ruta entre corchetes como [id] de SvelteKit empeoraban esto) y piezas como page o runs coincidían con todos los archivos hermanos, por lo que el archivo que realmente nombró podría quedar excluido de la respuesta por completo. Una ruta que no coincide con ningún archivo indexado ahora se indica en lugar de ignorarse silenciosamente.
  • Nombrar un archivo kebab-case sin su extensión en una consulta codegraph_explore (background-image-table en lugar de background-image-table.tsx, como se escriben las rutas de importación y la prosa) ahora también devuelve ese archivo exacto. Anteriormente, el nombre estaba dividido en guiones, y en una interfaz con formato de kebab, esas piezas (background, image, table) se encuentran entre las palabras más comunes en el código base, por lo que archivos hermanos similares llenaban la respuesta, mientras que el archivo nombrado nunca aparecía. Las palabras con guiones que no nombran un archivo indexado, como "llamada cruzada" o "sin bloqueo", se dejan en paz.
  • Las preguntas codegraph_explore redactadas de forma sencilla ahora encuentran el código camelCase: una consulta como "desplazamiento automático hacia abajo" puede llegar a una función denominada scrollFeedToBottom, porque las palabras de consulta se comparan con las palabras dentro de los identificadores, no solo con los nombres completos.
  • Las variables y constantes ahora cuentan cuando codegraph_explore elige sus símbolos iniciales, por lo que el estado contenido en variables simples (variables de estilo $state en Svelte, por ejemplo) ya no se pasa por alto.
  • codegraph_explore ahora concentra su respuesta en el código que realmente responde a su pregunta en lugar de distribuirla en archivos que simplemente comparten una palabra con ella, por lo que llega más respuesta en una sola llamada. Gracias @LeDuyViet por las medidas detalladas y la reproducción. (#1500)
  • Los archivos que están débilmente relacionados con su pregunta ahora regresan como un nombre, símbolo y número de línea en lugar de gastar la respuesta en su fuente; nombre uno de ellos en un seguimiento codegraph_explore para recuperarlo completo. (#1500)
  • Una capa CRUD o protobuf generada ya no desplaza el código escrito a mano que se encuentra a su lado: los archivos generados ahora se reconocen por el banner de estilo // Code generated by … DO NOT EDIT. escrito en la parte superior del archivo, no solo por un nombre de archivo que parece generado. Vuelva a indexar después de actualizar para detectar la nueva detección. (#1500)
  • Los archivos de prueba y especificaciones en el directorio de nivel superior test/ o spec/ de un repositorio ahora se reconocen como tales, por lo que ya no ocupan espacio en el código que usted preguntó. (#1500)
  • Los archivos de declaración de tipo generados que se anuncian con un banner "Generado por... ejecutando..." (el worker-configuration.d.ts de Cloudflare Wrangler es el más común) ahora se reconocen como generados. Anteriormente, un archivo como ese podía tomar la mayor parte de una respuesta codegraph_explore con nada más que unas pocas palabras comunes, eliminando por completo el código escrito a mano sobre el que preguntaste. Vuelva a indexar después de actualizar para detectar la nueva detección.
  • Un archivo de declaración de tipo escrito a mano (un .d.ts ambiental de ajustes globales, tipificaciones proporcionadas y aumento de módulos) ya no se hace cargo de una respuesta codegraph_explore sobre cómo funciona algo. Archivos como estos declaran nombres comunes (Body, Message, ImageMetadata) y nada más, por lo que una pregunta redactada de forma sencilla podría coincidir con una lo suficientemente fuerte como para ocupar el primer lugar y excluir al controlador real de la respuesta. Ahora tienen una clasificación más baja en preguntas sobre comportamiento y todavía aparecen listados por nombre, por lo que una llamada de seguimiento los recupera. Preguntar sobre un tipo por nombre aún devuelve su declaración primero, y un módulo de tipos compartidos que el resto de su código importa no se ve afectado.
  • Cuando nombras un símbolo en una consulta codegraph_explore, su definición ahora vuelve. Dos casos lo perdieron anteriormente. Si los símbolos que nombró no se llaman entre sí (las funciones hermanas dentro de la misma fábrica o módulo son el ejemplo cotidiano), CodeGraph dejó de tratarlos como símbolos que había solicitado y respondió con lo que se encontraba en la parte superior de su archivo; en un archivo de 1400 líneas, eso significaba que una interfaz QueuedMessage del mismo tronco en la línea 70 regresaba, mientras que la función queueMessage en la línea 1087 no. Y cuando era necesario recortar una respuesta para que encajara, se recortaba desde la parte inferior del archivo hacia abajo, por lo que lo primero que se cortaba siempre era un símbolo cerca del final de un archivo largo. El recorte ahora protege las definiciones que nombró dondequiera que se encuentren en el archivo.
  • Un archivo creado en torno a una función muy larga ya no toma la respuesta completa de codegraph_explore, o desaparece de ella. Anteriormente, un archivo de este tipo se mostraba completo por muy grande que fuera, lo que consumía el espacio para cada archivo que necesitaba, y cuando la función era más grande que la respuesta completa, el archivo se eliminaba sin una palabra. Estos archivos ahora regresan como una ventana delimitada en líneas completas (la firma y la parte superior del cuerpo, más el sitio de la llamada cuando la ruta de la llamada lo atraviesa) y el resto está a un seguimiento de codegraph_explore.
  • codegraph_explore ya no permite que el primer archivo de una respuesta pase el espacio reservado para los archivos que se encuentran debajo, por lo que el resto de la respuesta aún llega. Anteriormente, un archivo grande cerca de la parte superior podía consumir silenciosamente todo lo que quedaba, y los archivos clasificados debajo de él (cada uno de los cuales ya se consideraba lo suficientemente relevante como para incluirlo) se eliminaban sin fuente alguna; en una pregunta, solo uno de seis logró responder. Cada archivo ahora conserva lo que se le dio, y una pregunta que realmente se refiere a un archivo todavía se concentra en ese archivo.
  • Cuando una respuesta codegraph_explore supera su límite de tamaño, ahora elimina las notas finales en lugar de la fuente de un archivo completo. Anteriormente, el último archivo se cortaba a pesar de que bastaba con recortar las notas, por lo que un archivo que ya había sido leído, clasificado y renderizado se desechaba en el último momento. En una variedad de proyectos reales, esto devuelve un archivo más y hasta un 20 % más de fuente por llamada.
  • Cada archivo que codegraph_explore decide incluir ahora llega. Un archivo que se muestra completo aún podría ocupar espacio reservado para los archivos debajo de él (la solución anterior cubría los archivos mostrados como extractos pero no los archivos mostrados completos) y la contabilidad del propio tamaño de la respuesta no contaba el encabezado de cada archivo, por lo que la respuesta superó su límite y se descartó un archivo completamente preparado al final. Un archivo que ya no encaja completo ahora se muestra como extractos en lugar de desaparecer, y uno que sobrepasa un poco se recorta para ajustarse en lugar de eliminarse.
  • La lista de archivos que una respuesta no pudo cubrir (las sugerencias de "explorar estos nombres en busca de su fuente") ya no se descarta cuando la respuesta está completa. Ahora está presupuestado y recortado para adaptarse, por lo que una respuesta completa aún le indica lo que omitió y qué nombres preguntar a continuación, en lugar de terminar sin ningún indicador.
  • Cuando una respuesta de codegraph_explore muestra un archivo como extractos, un extracto grande que ya no encajaba se eliminó por completo en lugar de acortarse. Si el primer extracto del archivo resultaba ser trivial (un bloque de importación, un ayudante de una línea al lado del código sobre el que preguntaste), el extracto que contenía la respuesta real era el que se desechaba y el archivo regresaba con una cuarta parte del espacio que se le había asignado. En proyectos reales, eso significaba que el archivo mejor clasificado entregaba una fracción de su participación, mientras que un archivo mucho menos relevante se quedaba con el resto. Los extractos ahora se acortan para que quepan, método completo por método completo, y solo se eliminan cuando lo que queda es demasiado pequeño para contener algo legible.
  • La sección de radio de explosión de codegraph_explore marcaba "no se encontraron pruebas de cobertura" cada vez que ninguna prueba llamaba a un símbolo directamente, calificando falsamente a los ayudantes que realizan pruebas a través de sus interlocutores como no probados (alrededor del 40% de los símbolos marcados en una muestra medida). La verificación ahora sigue las cadenas de llamadas de hasta 3 saltos e informa la cobertura indirecta como "probada a través de las personas que llaman"; cuando no se encuentra nada, indica exactamente lo que se comprobó en lugar de una advertencia incondicional. Gracias @inth3shadows por medir la tasa de falsos positivos. (#1475)
  • Cuando un archivo cambiaba en el disco después de su última sincronización de índice, codegraph_node y codegraph_explore podían devolver un código de símbolo diferente bajo el nombre solicitado (bytes del archivo actual cortados en posiciones de línea obsoletas) mientras lo presentaban textualmente, como fuente digna de trust. Esto afecta más a los proyectos consultados a través de projectPath (por ejemplo, subproyectos de un monorepo), que no tienen un observador de archivos en vivo para marcar las ediciones pendientes. Ambas herramientas ahora verifican cada archivo con el índice antes de mostrar el código dividido: un archivo desactualizado se muestra completo con su fuente actual completa o su código se retiene con un aviso claro de "cambiado en el disco"; nunca se muestra como un segmento incorrecto. Una nueva reindexación restaura la salida normal automáticamente. Gracias @inth3shadows por el informe exhaustivo y los pases de verificación. (#1474)

Encontrar su proyecto, actualizaciones en vivo y el CLI

  • El servidor MCP ahora encuentra su proyecto cuando se inicia desde una carpeta del espacio de trabajo encima de él: si el directorio de inicio no tiene un índice propio, pero exactamente un proyecto indexado se encuentra debajo (un contenedor de repositorio, un espacio de trabajo de agente, una raíz de monorepo), ese proyecto se convierte en el predeterminado de la sesión (observación de archivos en vivo y el demonio compartido incluido) en lugar de que cada llamada de herramienta falle hasta que se proporcione un projectPath o --path. Gracias @nakisen. (#1606)
  • Cuando no se puede resolver ningún proyecto, el servidor MCP ahora lo dice en lugar de iniciarse silenciosamente: una línea de registro de inicio nombra el directorio que buscó y las llamadas a herramientas enumeran los subproyectos indexados que puede ver cerca para que pueda pasar uno como projectPath. Anteriormente, el servidor parecía saludable desde el exterior, mientras que todas las herramientas no tenían ningún proyecto desde el cual responder. Gracias @nakisen. (#1607)
  • La edición de exclude o include (o .gitignore) de codegraph.json mientras el servidor MCP se está ejecutando ahora tiene efecto inmediatamente. Anteriormente, el observador de archivos en ejecución mantenía el alcance que tenía cuando se inició, por lo que codegraph sync eliminó un archivo recién excluido y luego el observador lo volvió a agregar silenciosamente segundos después, lo que parecía que exclude no funcionaba en absoluto, hasta que se reiniciaba el servidor. Un cambio de alcance ahora actualiza el observador y activa una conciliación completa, y un archivo modificado que el observador entrega para sincronizar se vuelve a verificar primero con el alcance actual, por lo que el CLI y el servidor en vivo ya no pueden estar en desacuerdo sobre lo que pertenece al índice. Gracias @K1nG11. (#1590)
  • codegraph status ahora ve archivos nuevos dentro de directorios nuevos. Git informa un directorio sin seguimiento como una única entrada colapsada, por lo que los archivos fuente creados allí (un frontend/ recién estructurado, por ejemplo) faltaban en el informe de cambios pendientes, lo que podría afirmar que todo estaba actualizado mientras que esos archivos aún no habían sido indexados. Gracias @maxmilian. (#1213)
  • El comando codegraph context <task> documentado en la ayuda de CLI ahora realmente existe: crea un paquete de contexto listo para inyectar para una tarea (símbolos relevantes, sus relaciones y código) en Markdown o JSON, restaurando el contrato en el que se basan las integraciones externas como Memorix (--path, --format json, --max-nodes, --no-code). (#1611)
  • En Windows, el enlace de solicitud de Claude Code escrito por codegraph install fallaba con "comando no encontrado" cuando los enlaces se ejecutaban a través de Git Bash, que necesita la extensión .cmd para encontrar el iniciador. El instalador ahora escribe el comando correcto para la plataforma y al volver a ejecutar codegraph install (o codegraph upgrade) se repara una instalación existente en su lugar. (#1466)
  • Buscar un símbolo por nombre ya no lee el gráfico completo. Cada búsqueda hizo una pasada completa por todos los símbolos indexados para cada palabra que escribiste, y una pregunta que nombraba varios símbolos hizo dos pasadas más por nombre, incluso para una palabra que no coincide con nada, que es el caso común. Por lo tanto, el costo creció con el tamaño del proyecto y se pagó nuevamente en cada mensaje cuando se habilita el enlace rápido. Estas búsquedas ahora pasan por el índice de nombres. Los resultados son idénticos; sólo cambia el tiempo para conseguirlos, y ya no crece con el proyecto. Gracias @maxmilian.

Confiabilidad de indexación y uso del disco

  • La indexación ya no bloquea todo el proceso (un error de segmentación sin mensaje ni índice parcial) en un archivo C/C++ (o cualquier otro) con un anidamiento extremadamente profundo, como los accesorios de prueba de estrés del analizador en los conjuntos de pruebas clang y gcc o un corpus fuzzer. Dicho archivo ahora se entrega al analizador alternativo y se registra con una advertencia de análisis mientras el resto del repositorio se indexa normalmente. Gracias @ apollo600 por el diagnóstico exacto. (#1581)
  • La indexación ya no se bloquea en un proyecto de Swift Vapor que contiene una llamada con una larga lista de argumentos. Una única llamada de estilo .get(...) con muchos argumentos etiquetados y ningún controlador use: (la forma que producen los creadores de solicitudes generadas) podría detener codegraph index, codegraph sync y el servidor MCP indefinidamente. La detección de rutas ahora maneja dichos archivos en milisegundos, y cada forma de ruta previamente reconocida todavía se analiza exactamente como antes. Gracias @maxmilian. (#1544) (Rápido)
  • La sincronización de un lote grande de archivos modificados ya no falla con el mensaje "Se excedió el tamaño máximo de la pila de llamadas" a la mitad. El fallo abortó la resolución de referencia después de que los símbolos de los archivos ya estaban almacenados, dejando el gráfico con muchas menos conexiones que las que tendría un índice nuevo, y afectó exactamente a los escenarios que vuelven a analizar muchos archivos a la vez, incluida la reparación automática anterior. Gracias @netbrah por identificar el error. (#1558)
  • Un índice de larga duración ya no se aleja de lo que produciría un nuevo codegraph index. Cuando un archivo ganaba o perdía un símbolo, las referencias a ese nombre en los archivos que la sincronización nunca tocó seguían apuntando a la definición que era correcta antes del cambio y, debido a que nada distinguía dos definiciones con el mismo nombre, el ganador podía depender del orden en que se escribieron los archivos, que difiere entre un índice completo y una sincronización. En el repositorio de este proyecto, la reproducción de 80 confirmaciones a través de sync dejó un 5.7% de conexiones incorrectas; ahora es 1.3%, y la mitad de las respuestas incorrectas que aún se afirman cae en un 99.7%. Dado que los bordes de llamada son lo que siguen las preguntas de flujo y lo que codegraph_explore clasifica los archivos, estas respuestas silenciosamente degradadas como un índice envejecido, sin nada que lo indique. La velocidad de sincronización no cambia y una edición que solo cambia el cuerpo de una función no supone ningún trabajo adicional. Configure CODEGRAPH_NO_REBIND=1 para optar por no participar.
  • Se corrigió una regresión v1.5.0 donde un archivo perfectamente válido podía registrarse permanentemente con 0 símbolos, sin reportar ningún error. Cuando se interrumpía el primer intento de análisis de un archivo (una falla del trabajador de análisis o un tiempo de espera, muy probablemente en máquinas lentas o muy cargadas), el reintento automático almacenaba un resultado vacío para cualquier idioma en la ruta de extracción nativa, por lo que las funciones y clases del archivo desaparecían silenciosamente de la búsqueda, las personas que llamaban y el impacto hasta que se editaba el archivo. Los reintentos ahora almacenan los símbolos reales del archivo, y un archivo ya grabado como libre de símbolos se detecta y repara automáticamente en la siguiente sincronización o reindexación después de la actualización. Gracias @Baiae por el informe. (#1541)
  • Un proceso CodeGraph que es eliminado a la fuerza (por el proceso de vigilancia atascado, una falla o el sistema operativo) ya no deja atrás el registro de escritura anticipada de la base de datos para crecer sin límites. Anteriormente, cada sesión cancelada acumulaba más datos en el mismo archivo de registro y nunca nada los reducía, lo que en máquinas donde las sesiones se cancelaban regularmente podía consumir silenciosamente decenas de gigabytes de disco. El tamaño restante del registro ahora está limitado (64 MB de forma predeterminada; CODEGRAPH_WAL_HEAL_MB lo cambia), y cualquier sobrante de gran tamaño se vuelve a doblar en el índice y se recorta automáticamente la próxima vez que se abre el proyecto. Esto limita solo el registro: el índice en sí no tiene límite de tamaño y aún se permite que el registro de un repositorio grande crezca en proporción a su índice mientras se construye. Gracias @tiendungdev por el excepcional informe de Windows que precisó esto. (#1431)
  • El mecanismo de vigilancia del servidor en segundo plano ya no mata un servidor en buen estado que simplemente está esperando en un disco lento: como ya lo hace la indexación, ahora verifica si los archivos de la base de datos aún están progresando antes de concluir que el proceso está bloqueado. Menos muertes espurias también significan menos registros de escritura anticipada sobrantes. (#1431)
  • codegraph status ahora muestra el tamaño del registro de escritura anticipada junto al tamaño de la base de datos y advierte cuando las sesiones canceladas la han dejado sobredimensionada, y cada línea en el registro del servidor en segundo plano ahora lleva una marca de tiempo para que las eliminaciones y reinicios se puedan ubicar en el tiempo. (#1431)
  • Un demonio en segundo plano dejado por una eliminación por falta de memoria o una eliminación forzada ya no puede bloquear todas las sesiones futuras cuando el sistema operativo reutiliza su ID de proceso: la administración del demonio ahora verifica que un proceso registrado sea realmente un demonio CodeGraph antes de trust enviarlo o señalarlo, y codegraph unlock borra los artefactos del demonio obsoleto, así como el bloqueo de indexación. Gracias @ hcg1023 por el informe y @ danusha2345 por la solución. (#1553)
  • Cuando la indexación tiene que recurrir al análisis de un archivo sin líneas de comentarios (una recuperación de último recurso después de repetidas fallas del analizador), el archivo ahora se marca con una advertencia visible en lugar de informarse como indexado limpiamente. El resultado recuperado puede ser incompleto, y los informes exitosos hicieron que un índice nuevo discrepara silenciosamente con un nuevo análisis posterior del mismo archivo sin cambios. Gracias @jeremypetz por la contabilidad precisa del símbolo de inicio versus sincronización que expuso esto. (#1565)
  • Los encabezados C/C++ de solo datos cerca del límite de tamaño de archivo ya no retienen un trabajador analizador durante varios minutos antes de que se agote el tiempo de espera; el presupuesto de análisis de archivos grandes predeterminado ahora está limitado, mientras que aún se respeta un tiempo de espera mayor configurado explícitamente. (#1555)
  • Reabrir un índice después de una falla durante la carga masiva ahora restaura cada índice de base de datos eliminado, y una sincronización de recuperación exitosa marca el índice como completo en lugar de dejarlo permanentemente marcado como interrumpido. (#1556)
  • Los archivos omitidos porque son demasiado grandes o fallan repetidamente al analizarse ahora se registran con el motivo, por lo que los archivos rechazados sin cambios ya no se cubren ni se reintentan en cada verificación de estado y sincronización, y un análisis exitoso posterior de dicho archivo reemplaza el registro con sus símbolos reales. Gracias @netbrah por el excepcional análisis de fallas detrás de este lote y @danusha2345 por las correcciones. (#1557)
  • El análisis de punteros de funciones de C/C++ ahora limita sus cachés de patrones compilados, por lo que los repositorios muy grandes ya no pueden agotar el espacio de código de expresión regular del motor JavaScript durante la indexación. (#1559)
  • El análisis de renderizado JSX ahora se ejecuta solo en archivos de la familia JavaScript, por lo que las cadenas con apariencia JSX en C/C++ (o cualquier otro lenguaje) ya no crean bordes de llamada imposibles, tanto en proyectos de C puro como en monorepos de lenguaje mixto. (#1560)

Precisión del lenguaje y el marco

  • Las llamadas a los métodos de una constante literal de objeto exportada (export const api = { call() { … } } utilizada como espacio de nombres de módulo, una forma común de organizar una superficie TypeScript API) ahora se resuelven en el método, tanto en el archivo de definición como mediante importaciones. Anteriormente, una llamada de este tipo no estaba vinculada a nada (o a la constante misma), por lo que codegraph callers y el análisis de impacto informaron que no había llamadas para métodos que se llamaban desde todas partes. Vuelva a indexar después de actualizar para recoger los bordes. Gracias @IAliceBobI por el informe preciso y la causa raíz. (#1573)
  • Ahora se seleccionan los alias de importación definidos en una configuración compartida TypeScript. Los monorepos estilo Nx mantienen cada alias @scope/... en un tsconfig.base.json que la raíz tsconfig.json solo hereda a través de extends, por lo que CodeGraph no encontró ningún alias y cada importación entre paquetes volvió a coincidir solo con el nombre, lo que silenciosamente adjunta resultados a símbolos no relacionados que comparten un nombre, exactamente donde un monorepo necesita que codegraph_impact y codegraph_callers sean correctos. Ahora se siguen cadenas de varias configuraciones profundas, una configuración heredada de un paquete en node_modules y una baseUrl declarada en una configuración heredada, y una tsconfig.base.json se lee directamente cuando la raíz tsconfig.json es solo un shell de referencias de proyecto o no está allí en absoluto. Vuelva a indexar después de la actualización. Gracias @maxmilian. (#1534)
  • Los métodos implementados en un bloque impl genérico o con parámetros de por vida (impl<T> Source for BufSource<T>, impl<'a> Iterator for Parents<'a>) ahora se registran bajo el tipo de implementación en lugar del rasgo. Anteriormente, un método de este tipo no se podía encontrar por su tipo ("quién llama a BufSource::read" no tenía respuesta) y colisionaba con la propia declaración del rasgo, que incluso podía inventar un borde de gráfico de llamada a partir de un cuerpo impl que no contiene ninguna llamada. Las implicaciones en una referencia (impl Trait for &Foo) y en un tipo calificado por módulo (impl Trait for m::Foo) también se atribuyen a su tipo. Vuelva a indexar después de la actualización. Gracias @Dshuishui. (#1588) (Rust)
  • Una llamada a un método en un campo de estructura (self.inner.run() con inner: Inner) ahora se resuelve en el método del tipo declarado del campo. Anteriormente, la llamada se reducía al nombre del método simple y coincidía con el método con el mismo nombre más cercano, que a menudo era el método de llamada en sí, registrando recursividad que no está en la fuente (unos cientos de estos auto-bordes solo en ripgrep), o un método de un tipo no relacionado. Se revisan las referencias y los campos Box/Rc/Arc, al igual que las llamadas a métodos propios de Rust; un campo cuyo tipo es externo (un tipo estándar o de terceros), un parámetro genérico o un contenedor como Option/Vec se deja sin resolver en lugar de adivinarse. Vuelva a indexar después de la actualización. Gracias @Dshuishui. (#1585) (Rust)
  • Las funciones de Erlang que comparten un nombre pero difieren en aridad ahora son símbolos separados con la propia identidad module:fun/arity del lenguaje, por lo que el f/1 cotidiano que delega a f/2 se muestra como un borde de llamada real en lugar de un bucle automático, cada aridad mantiene su propio -spec y su intervalo de fuente, -export([f/1]) marca exactamente esa aridad como pública, y solicita a codegraph_explore un símbolo en el camino. Erlang lo deletrea – cowboy_req:header/3 – devuelve esa definición. Vuelva a indexar los proyectos de Erlang después de la actualización. Gracias @Dshuishui. (#1610) (Erlang)
  • El envío de comportamiento de Erlang ya no contabiliza erróneamente la aridad de un sitio de llamada cuando un argumento es un literal binario como <<1,2,3>>: las comas internas se contaban como separadores de argumentos, lo que eliminaba silenciosamente (o podía vincular erróneamente) el borde de envío con la devolución de llamada del comportamiento. (#1358) (Erlang)
  • Un encabezado C++ .h cuya única construcción C++ es un tipo derivado simple (struct Derived : Base sin macro de exportación, palabra clave class ni sección de acceso) ahora se reconoce como C++ (anteriormente solo se reconocía el formato de macro de exportación). Dicho encabezado se leía como C, por lo que la estructura derivada desapareció del índice y en su lugar apareció una función fantasma con el nombre del tipo base. La verificación ahora también cubre todo el archivo en lugar de sus primeros kilobytes, por lo que un preámbulo largo compatible con C ya no oculta la señal. Vuelva a indexar después de actualizar para seleccionar los encabezados afectados. Gracias @Jaysenpeng. (#1592)
  • Las uniones C, C++, Objective-C y Rust ahora están indexadas como nodos union de primera clase. Una declaración union anteriormente no producía ningún símbolo, por lo que nunca apareció en la búsqueda o codegraph_explore, y todo lo adjunto a ella desapareció con ella; en Rust, cada impl SomeTrait for MyUnion perdió su ventaja, los métodos de esa impl se dejaron apuntando a un tipo que el gráfico no contenía y al preguntar qué tipos implementan un rasgo se omitieron silenciosamente los de unión. Una tabla de despacho con forma de unión en C ahora resuelve sus punteros de función como una tabla con forma de estructura. Un typedef union { … } Name; en C mantiene el nombre de typedef y ya no se confunde con un alias de tipo simple. Gracias @ctype-lab. Vuelva a indexar después de la actualización para incorporar uniones en proyectos existentes. (#1515)
  • Las clases Python utilizadas como valores (return SomeSerializer de un método de fábrica, alias handler = SomeClass, listas y dictados de registro y clases pasadas como argumentos) ahora producen bordes de referencia en el gráfico. Anteriormente, estos modismos eran invisibles, por lo que en los proyectos Django y Django REST Framework, al preguntar por las personas que llaman a un serializador o el impacto de editarlo, se omitían las vistas que realmente lo usan. Vuelva a indexar después de actualizar para seleccionar los nuevos bordes. (#1478)
  • Las importaciones de SAP HANA .xsjs/.xsjslib ahora se resuelven entre archivos: un import { x } from './helpers' sin extensión en un archivo .xsjs encuentra helpers.xsjslib, por lo que se crea el borde de llamada entre archivos y codegraph_callers/codegraph_impact lo ve. Anteriormente, la ruta de importación no se resolvía y la llamada volvía a coincidir con el mismo nombre, lo que podía vincular el borde a un archivo no relacionado que exportaba el mismo símbolo. Complementa el soporte de extracción .xsjs / .xsjslib. Gracias @maxmilian. (#556)

codegraph v1.6.0

[1.6.0] - 2026-08-26

Highlights

  • GitHub Copilot is now supported — codegraph install sets it up in VS Code, the Copilot CLI, and JetBrains IDEs, next to the agents it already knew.
  • Set up in one command — codegraph install --yes --init wires up your agents and indexes your project with no prompts, ideal for a fresh container or CI.
  • Better answers for your agent — codegraph_explore no longer repeats code it already showed you, always brings back the files and symbols you asked for by name, and spends its space on the code that actually answers the question rather than look-alikes, generated files, and type shims.
  • Your graph stays right as you keep coding — a long-running index no longer drifts from a fresh one, and edits to codegraph.json (such as exclude) apply immediately without a restart.
  • No more silent crashes or hangs — deeply nested C/C++ files, Swift Vapor projects, and large sync batches that used to kill or stall indexing now finish cleanly.
  • A disk-space leak is fixed — a force-killed session could leave the database's write-ahead log behind to grow without bound (tens of gigabytes was reported); the leftover log is now folded back into the index and trimmed automatically the next time the project opens. The index itself has no size limit.
  • Works from a workspace or monorepo root — the MCP server finds your indexed project when launched from a folder above it, and says so clearly when it can't find one.
  • More accurate code graphs for TypeScript, Rust, Erlang, C/C++, and Python projects — see the full list below.
  • Also new: per-project Codex setup (codegraph install --location=local), a deprioritize setting to keep helper folders from outranking your real code, the codegraph context command, and usage stats that now stay entirely on CodeGraph's own servers.

After upgrading, run codegraph index once in each project so your existing graph picks up these fixes — codegraph status reminds you when it's needed.

New Features

  • GitHub Copilot is now a supported agent: codegraph install can configure Copilot Chat in VS Code (copilot-vscode), the GitHub Copilot CLI (copilot-cli), and the Copilot plugin in JetBrains IDEs (copilot-jetbrains). Installed Copilot surfaces are auto-detected like every other agent, existing MCP server entries in their config files are preserved, and codegraph uninstall reverses the setup cleanly. Restart VS Code or your JetBrains IDE after installing so Copilot picks up the server.

  • codegraph install --init wires up your agents and builds the current project's index in one command, and codegraph init --yes runs without any prompts — so a fresh container or CI job can bootstrap CodeGraph with a single non-interactive line (codegraph install --yes --init). The installer still never indexes anything unless you ask for it with the flag, and the usual safety refusal for a home directory or filesystem root applies. (#1578)

  • Codex CLI can now be set up per project instead of only user-wide: codegraph install --location=local writes ./.codex/config.toml and the CodeGraph block in your project's AGENTS.md, so CodeGraph is wired into that repo only rather than every Codex session on the machine. codegraph uninstall --location=local reverses it, and the global install is untouched either way. Codex only applies a project's config once you've marked the project trusted, so the installer says so after a local install. Thanks @maxmilian. (#1531)

  • A new deprioritize setting in codegraph.json keeps the paths you name from outranking your product code in search and codegraph_explore answers, without removing anything from the index. It takes gitignore-style patterns just like exclude, but is ranking-only: helper-script trees, generated output, or optional add-on directories whose generic symbol names (usage, run, status) would otherwise crowd out the code that actually answers a query stay fully indexed and findable — and a query that genuinely targets such a tree still returns it. Thanks @maxmilian. (#982)

  • codegraph_explore no longer re-sends source it already returned earlier in the same conversation. A file it has already shown you comes back as a short pointer — the path, the symbols and the exact line range, with confirmation that the file hasn't changed since — and the space that frees is spent on code you haven't seen yet, so a follow-up call covers new ground instead of repeating the last one. If a file was edited in between, its source is always shown again in full. Set CODEGRAPH_EXPLORE_DEDUP=0 to turn this off.

  • When an agent connects over MCP, CodeGraph now states up front that it indexes 30+ languages — TypeScript/JavaScript, Python, Go, Rust, Java, C#, C/C++, PHP, Ruby, Swift, Kotlin, and more — so agents no longer assume a language isn't supported and skip the graph. (#671)

  • Anonymous usage telemetry is now stored entirely on CodeGraph's own first-party infrastructure — no third-party analytics vendor receives any of it, and the endpoint that receives it makes no outbound requests at all. Individual events are deleted after 90 days, leaving only anonymous daily totals. Nothing about what is collected changed, your IP address is still never read or stored, and every off-switch works exactly as before (codegraph telemetry off, CODEGRAPH_TELEMETRY=0, DO_NOT_TRACK=1). TELEMETRY.md remains the complete field-by-field list.

Fixes

Better answers from codegraph_explore

  • Naming a file by its path in a codegraph_explore query now works reliably: the path is resolved against the index and that file is guaranteed a place at the top of the answer. Previously the path was broken into fragments — bracketed route segments like SvelteKit's [id] made this worst — and pieces like page or runs matched every sibling file, so the file you actually named could be crowded out of the answer entirely. A path that doesn't match any indexed file is now called out instead of silently ignored.

  • Naming a kebab-case file without its extension in a codegraph_explore query — background-image-table rather than background-image-table.tsx, the way import paths and prose spell it — now returns that exact file too. Previously the name was split at the hyphens, and in a kebab-cased frontend those pieces (background, image, table) are among the most common words in the codebase, so look-alike sibling files filled the answer while the named file never appeared. Hyphenated words that don't name an indexed file, like "cross-call" or "non-blocking", are left alone.

  • Plainly-worded codegraph_explore questions now find camelCase code: a query like "auto-scroll to bottom" can reach a function named scrollFeedToBottom, because query words are matched against the words inside identifiers, not just whole names.

  • Variables and constants now count when codegraph_explore picks its starting symbols, so state held in plain variables — $state-style variables in Svelte, for example — no longer gets overlooked.

  • codegraph_explore now concentrates its answer on the code that actually answers your question instead of spreading it across files that merely share a word with it, so more of the answer arrives in a single call. Thanks @LeDuyViet for the detailed measurements and reproduction. (#1500)

  • Files only weakly related to your question now come back as a name, symbol and line number instead of spending the answer on their source — name one of them in a follow-up codegraph_explore to get it back in full. (#1500)

  • A generated CRUD or protobuf layer no longer crowds out the hand-written code sitting beside it: generated files are now recognized by the // Code generated by … DO NOT EDIT. style banner written at the top of the file, not just by a filename that looks generated. Re-index after upgrading to pick up the new detection. (#1500)

  • Test and spec files in a repository's top-level test/ or spec/ directory are now recognized as such, so they no longer take room from the code you asked about. (#1500)

  • Generated type-declaration files that announce themselves with a "Generated by … by running …" banner — Cloudflare Wrangler's worker-configuration.d.ts is the common one — are now recognized as generated. Previously a file like that could take most of a codegraph_explore answer on nothing more than a few common words, pushing the hand-written code you asked about out of the response entirely. Re-index after upgrading to pick up the new detection.

  • A hand-written type-declaration file — an ambient .d.ts of global shims, vendored typings, module augmentation — no longer takes over a codegraph_explore answer about how something works. Files like these declare common names (Body, Message, ImageMetadata) and nothing else, so a plainly-worded question could match one strongly enough that it ranked first and crowded the actual handler out of the answer. They are now ranked lower for questions about behaviour, and are still listed by name so one follow-up call fetches them. Asking about a type by name still returns its declaration first, and a shared types module the rest of your code imports is unaffected.

  • When you name a symbol in a codegraph_explore query, its definition now actually comes back. Two cases previously lost it. If the symbols you named don't call one another — sibling functions inside the same factory or module are the everyday example — CodeGraph stopped treating them as symbols you had asked for, and answered with whatever sat at the top of their file instead; on one 1,400-line file that meant a same-stem QueuedMessage interface on line 70 came back while the queueMessage function on line 1087 did not. And when an answer had to be trimmed to fit, it was trimmed from the bottom of the file down, so a symbol near the end of a long file was always the first thing cut. Trimming now protects the definitions you named wherever they sit in the file.

  • A file built around one very long function no longer takes the whole codegraph_explore answer for itself — or disappears from it. Previously such a file was shown in full however big it was, which used up the room every file after it needed, and when the function was larger than the entire response the file was dropped without a word. These files now come back as a bounded window on whole lines — the signature and the top of the body, plus the call site when the call path runs through it — with the rest one follow-up codegraph_explore away.

  • codegraph_explore no longer lets the first file in an answer spend the room set aside for the files below it, so the rest of the answer still arrives. Previously a large file near the top could quietly use up everything left, and the files ranked under it — each already judged relevant enough to include — were dropped with no source at all; on one question only one of six made it into the answer. Every file now keeps what it was given, and a question that really is about one file still concentrates on that file.

  • When a codegraph_explore answer runs right up against its size limit, it now drops the trailing notes rather than a whole file's source. Previously the last file was cut even though trimming the notes alone would have fit, so a file that had already been read, ranked and rendered was thrown away at the last moment. Across a range of real projects this returns one more file and up to 20% more source per call.

  • Every file codegraph_explore decides to include now actually arrives. A file shown in full could still spend room set aside for files below it — the fix above covered files shown as excerpts but not files shown whole — and the answer's own size bookkeeping under-counted each file's heading, so the answer ran past its limit and a fully prepared file was discarded at the end. A file that no longer fits whole is now shown as excerpts instead of vanishing, and one that overshoots by a little is trimmed to fit rather than dropped.

  • The list of files an answer could not cover — the "explore these names for their source" pointers — is no longer thrown away when the answer is full. It is now budgeted for and trimmed to fit, so a full answer still tells you what it left out and which names to ask for next, instead of ending with no pointers at all.

  • When a codegraph_explore answer shows a file as excerpts, a large excerpt that no longer fit was dropped entirely instead of being shortened. If the file's first excerpt happened to be a trivial one — an import block, a one-line helper next to the code you asked about — the excerpt carrying the actual answer was the one thrown away, and the file came back with a quarter of the room it had been given. On real projects that meant the top-ranked file delivered a fraction of its share while a far less relevant file took the rest. Excerpts are now shortened to fit, whole method by whole method, and only dropped when what is left is too small to hold anything readable.

  • The blast-radius section of codegraph_explore flagged "no covering tests found" whenever no test called a symbol directly — falsely branding helpers that tests exercise through their callers as untested (about 40% of flagged symbols in a measured sample). The check now follows caller chains up to 3 hops and reports indirect coverage as "tested via callers"; when nothing is found it states exactly what was checked instead of an unconditional warning. Thanks @inth3shadows for measuring the false-positive rate. (#1475)

  • When a file changed on disk after its last index sync, codegraph_node and codegraph_explore could return a different symbol's code under the requested name — current file bytes cut at outdated line positions — while presenting it as verbatim, trustworthy source. This hit hardest on projects queried through projectPath (for example, sub-projects of a monorepo), which have no live file watcher to flag pending edits. Both tools now verify each file against the index before showing sliced code: an out-of-date file is either shown whole with its full current source, or its code is withheld with a clear "changed on disk" notice — never served as a wrong slice. A fresh re-index restores normal output automatically. Thanks @inth3shadows for the thorough report and verification passes. (#1474)

Finding your project, live updates, and the CLI

  • The MCP server now finds your project when it's launched from a workspace folder above it: if the launch directory has no index of its own but exactly one indexed project sits below it (a repo container, an agent workspace, a monorepo root), that project becomes the session's default — live file watching and the shared daemon included — instead of every tool call failing until a projectPath or --path is supplied. Thanks @nakisen. (#1606)

  • When no project can be resolved at all, the MCP server now says so instead of starting silently: a startup log line names the directory it searched, and tool calls list the indexed sub-projects it can see nearby so you can pass one as projectPath. Previously the server looked healthy from the outside while every tool quietly had no project to answer from. Thanks @nakisen. (#1607)

  • Editing codegraph.json's exclude or include (or a .gitignore) while the MCP server is running now takes effect immediately. Previously the running file watcher kept the scope it had when it started, so a newly excluded file was removed by codegraph sync and then quietly re-added by the watcher seconds later — which looked like exclude not working at all — until the server was restarted. A scope change now refreshes the watcher and triggers a full reconcile, and a changed file the watcher hands to sync is re-checked against the current scope first, so the CLI and the live server can no longer disagree about what belongs in the index. Thanks @K1nG11. (#1590)

  • codegraph status now sees new files inside brand-new directories. Git reports an entirely-untracked directory as a single collapsed entry, so source files created there — a freshly scaffolded frontend/, for example — were missing from the pending-changes report, which could claim everything was up to date while those files had not yet been indexed. Thanks @maxmilian. (#1213)

  • The codegraph context <task> command documented in the CLI help now actually exists — it builds a ready-to-inject context pack for a task (relevant symbols, their relationships, and code) in markdown or JSON, restoring the contract external integrations like Memorix rely on (--path, --format json, --max-nodes, --no-code). (#1611)

  • On Windows, the Claude Code prompt hook written by codegraph install failed with "command not found" when hooks run through Git Bash, which needs the .cmd extension to find the launcher. The installer now writes the platform-correct command, and re-running codegraph install (or codegraph upgrade) repairs an existing install in place. (#1466)

  • Looking a symbol up by name no longer reads the whole graph. Every search made one full pass over all indexed symbols for each word you typed, and a question that named several symbols made two more passes per name — including for a word that matches nothing, which is the common case. The cost therefore grew with the size of the project, and it was paid again on every message when the prompt hook is enabled. These lookups now go through the name index instead. Results are identical; only the time to get them changes, and it no longer grows with the project. Thanks @maxmilian.

Indexing reliability and disk usage

  • Indexing no longer crashes the whole process — a segmentation fault with no message and no partial index — on a C/C++ (or any other) file with extremely deep nesting, such as the parser stress-test fixtures in the clang and gcc test suites or a fuzzer corpus. Such a file is now handed to the fallback parser and recorded with a parse warning while the rest of the repository indexes normally. Thanks @apollo600 for the exact diagnosis. (#1581)

  • Indexing no longer hangs on a Swift Vapor project containing a call with a long argument list. A single .get(...)-style call with many labeled arguments and no use: handler — the shape generated request builders produce — could stall codegraph index, codegraph sync, and the MCP server indefinitely. Route detection now handles such files in milliseconds, and every previously-recognized route shape still parses exactly as before. Thanks @maxmilian. (#1544) (Swift)

  • Syncing a large batch of changed files no longer crashes with "Maximum call stack size exceeded" partway through. The crash aborted reference resolution after the files' symbols were already stored, leaving the graph with far fewer connections than a fresh index would have — and it hit exactly the scenarios that re-parse many files at once, including the automatic repair above. Thanks @netbrah for pinpointing the failure. (#1558)

  • A long-lived index no longer drifts away from what a fresh codegraph index would produce. When a file gained or lost a symbol, references to that name in files the sync never touched kept pointing at the definition that was correct before the change, and — because nothing distinguished two same-named definitions — the winner could come down to the order files happened to be written, which differs between a full index and a sync. On this project's own repository, replaying 80 commits through sync left 5.7% of connections wrong; it is now 1.3%, and the wrong-answers-still-being-asserted half drops by 99.7%. Since call edges are what flow questions follow and what codegraph_explore ranks files by, this quietly degraded answers as an index aged, with nothing to indicate it. Syncing is unchanged in speed, and an edit that only changes a function's body does no extra work at all. Set CODEGRAPH_NO_REBIND=1 to opt out.

  • Fixed a v1.5.0 regression where a perfectly valid file could be permanently recorded as having 0 symbols, with no error reported. When a file's first parse attempt was interrupted — a parsing worker crash or timeout, most likely on slow or heavily loaded machines — the automatic retry stored an empty result for any language on the native extraction path, so the file's functions and classes silently vanished from search, callers, and impact until the file was next edited. Retries now store the file's real symbols, and a file already recorded as symbol-free is detected and repaired automatically by the next sync or re-index after upgrading. Thanks @Baiae for the report. (#1541)

  • A CodeGraph process that gets force-killed — by the stuck-process watchdog, a crash, or the OS — no longer leaves the database's write-ahead log behind to grow without bound. Previously each killed session stacked more data onto the same log file and nothing ever shrank it, which on machines where sessions were killed regularly could quietly eat tens of gigabytes of disk. The log's resting size is now bounded (64 MB by default; CODEGRAPH_WAL_HEAL_MB changes it), and any oversized leftover is folded back into the index and trimmed automatically the next time the project is opened. This bounds only the log — the index itself has no size limit, and a large repository's log is still allowed to grow in proportion to its index while it is being built. Thanks @tiendungdev for the exceptional Windows report that pinned this down. (#1431)

  • The background server's watchdog no longer kills a healthy server that is just waiting on a slow disk: like indexing already does, it now checks whether the database files are still making progress before concluding the process is stuck. Fewer spurious kills also means fewer leftover write-ahead logs. (#1431)

  • codegraph status now shows the write-ahead log's size next to the database size and warns when killed sessions have left it oversized, and every line in the background server's log now carries a timestamp so kills and restarts can be placed in time. (#1431)

  • A background daemon left behind by an out-of-memory kill or force-kill can no longer block every future session when the operating system reuses its process ID: daemon management now verifies a recorded process is really a CodeGraph daemon before trusting or signaling it, and codegraph unlock clears stale daemon artifacts as well as the indexing lock. Thanks @hcg1023 for the report and @danusha2345 for the fix. (#1553)

  • When indexing has to fall back to parsing a file with its comment lines stripped — a last-resort recovery after repeated parser crashes — the file is now flagged with a visible warning instead of being reported as cleanly indexed. The recovered result can be incomplete, and reporting success made a fresh index quietly disagree with a later re-parse of the same unchanged file. Thanks @jeremypetz for the precise init-versus-sync symbol accounting that exposed this. (#1565)

  • Data-only C/C++ headers near the file-size limit no longer hold a parser worker for several minutes before timing out; the default large-file parse budget is now bounded, while an explicitly configured larger timeout is still honored. (#1555)

  • Reopening an index after a crash during bulk loading now restores every dropped database index, and a successful recovery sync marks the index complete instead of leaving it permanently flagged as interrupted. (#1556)

  • Files skipped because they are too large or repeatedly fail to parse are now recorded with the reason, so unchanged rejected files are no longer rediscovered and retried on every status check and sync — and a later successful parse of such a file replaces the record with its real symbols. Thanks @netbrah for the exceptional failure analysis behind this batch, and @danusha2345 for the fixes. (#1557)

  • C/C++ function-pointer analysis now bounds its compiled-pattern caches, so very large repositories can no longer exhaust the JavaScript engine's regular-expression code space during indexing. (#1559)

  • JSX rendering analysis now runs only on JavaScript-family files, so JSX-looking strings in C/C++ (or any other language) no longer create impossible call edges — in pure-C projects and in mixed-language monorepos alike. (#1560)

Language and framework accuracy

  • Calls to the methods of an exported object-literal constant — export const api = { call() { … } } used as a module's namespace, a common way to organize a TypeScript API surface — now resolve to the method, both in the defining file and through imports. Previously such a call linked to nothing (or to the constant itself), so codegraph callers and impact analysis reported zero callers for methods that are called from everywhere. Re-index after upgrading to pick up the edges. Thanks @IAliceBobI for the precise report and root-cause. (#1573)

  • Import aliases defined in a shared TypeScript config are now picked up. Nx-style monorepos keep every @scope/... alias in a tsconfig.base.json that the root tsconfig.json only inherits through extends, so CodeGraph found no aliases at all and every cross-package import fell back to matching on name alone — which quietly attaches results to unrelated symbols that happen to share a name, exactly where a monorepo needs codegraph_impact and codegraph_callers to be right. Chains several configs deep, a config inherited from a package in node_modules, and a baseUrl declared in an inherited config are all followed now, and a tsconfig.base.json is read directly when the root tsconfig.json is only a project-references shell or isn't there at all. Re-index after upgrading. Thanks @maxmilian. (#1534)

  • Methods implemented in a generic or lifetime-parameterized impl block (impl<T> Source for BufSource<T>, impl<'a> Iterator for Parents<'a>) are now recorded under the implementing type instead of the trait. Previously such a method could not be found by its type — "who calls BufSource::read" had no answer — and it collided with the trait's own declaration, which could even invent a call-graph edge out of an impl body that contains no call at all. Impls on a reference (impl Trait for &Foo) and on a module-qualified type (impl Trait for m::Foo) are attributed to their type too. Re-index after upgrading. Thanks @Dshuishui. (#1588) (Rust)

  • A method call on a struct field — self.inner.run() with inner: Inner — now resolves to the method on the field's declared type. Previously the call was reduced to the bare method name and matched whichever same-named method was nearest, which was often the calling method itself, recording recursion that isn't in the source (a few hundred such self-edges in ripgrep alone), or a method of an unrelated type. References and Box/Rc/Arc fields are looked through, as Rust's own method calls are; a field whose type is external (a std or third-party type), a generic parameter, or a container like Option/Vec is left unresolved rather than guessed. Re-index after upgrading. Thanks @Dshuishui. (#1585) (Rust)

  • Erlang functions that share a name but differ in arity are now separate symbols with the language's own module:fun/arity identity, so the everyday f/1 delegating to f/2 shows as a real call edge instead of a self-loop, each arity keeps its own -spec and source span, -export([f/1]) marks exactly that arity as public, and asking codegraph_explore for a symbol the way Erlang spells it — cowboy_req:header/3 — returns that definition. Re-index Erlang projects after upgrading. Thanks @Dshuishui. (#1610) (Erlang)

  • Erlang behaviour dispatch no longer miscounts a call site's arity when an argument is a binary literal like <<1,2,3>> — the commas inside were counted as argument separators, which silently dropped (or could mislink) the dispatch edge to the behaviour callback. (#1358) (Erlang)

  • A C++ .h header whose only C++ construct is a plain derived type — struct Derived : Base with no export macro, class keyword, or access section — is now recognized as C++ (previously only the export-macro form was). Such a header was read as C, so the derived struct vanished from the index and a phantom function named after the base type appeared in its place. The check now also covers the whole file rather than its first few kilobytes, so a long C-compatible preamble no longer hides the signal. Re-index after upgrading to pick up affected headers. Thanks @Jaysenpeng. (#1592)

  • C, C++, Objective-C and Rust unions are now indexed as first-class union nodes. A union declaration previously produced no symbol at all, so it never appeared in search or codegraph_explore, and anything attached to it disappeared with it — in Rust, every impl SomeTrait for MyUnion lost its edge, the methods from that impl were left pointing at a type the graph did not contain, and asking which types implement a trait quietly skipped the union ones. A union-shaped dispatch table in C now resolves its function pointers like a struct-shaped one. A typedef union { … } Name; in C keeps the typedef's name and is no longer mistaken for a plain type alias. Thanks @ctype-lab. Re-index after upgrading to pick up unions in existing projects. (#1515)

  • Python classes used as values — return SomeSerializer from a factory method, handler = SomeClass aliases, registry dicts and lists, and classes passed as arguments — now produce reference edges in the graph. Previously these idioms were invisible, so on Django and Django REST Framework projects, asking for a serializer's callers or the impact of editing it missed the views that actually use it. Re-index after upgrading to pick up the new edges. (#1478)

  • SAP HANA .xsjs / .xsjslib imports now resolve across files: an extensionless import { x } from './helpers' in a .xsjs file finds helpers.xsjslib, so the cross-file call edge is created and codegraph_callers / codegraph_impact see it. Previously the import path resolved to nothing and the call fell back to same-name matching, which could bind the edge to an unrelated file that happened to export the same symbol. Complements the .xsjs / .xsjslib extraction support. Thanks @maxmilian. (#556)
