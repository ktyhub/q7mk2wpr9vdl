códice v1.5.0

[1.5.0] - 2026-07-21

⚡ Lanzamiento del motor Rust: con sincronización casi instantánea

Esta versión reconstruye el motor de análisis de CodeGraph como un kernel nativo Rust, revisa el proceso de resolución a su alrededor y hace que el gráfico en vivo sea efectivamente instantáneo: ahora se guarda el gráfico en menos de un segundo, incluso en un repositorio de 27,000 archivos. Es la mayor mejora de rendimiento en la historia del proyecto y cada gráfico se verifica byte por byte como idéntico al motor anterior.

  • Análisis nativo de Rust para 20 idiomas: TypeScript, JavaScript (+TSX/JSX), Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua y Luau ahora analizan en un kernel Rust compilado (Metal y CUDA sigue el camino de C++). Las plataformas sin un binario prediseñado y los archivos individuales con errores de sintaxis recurren automáticamente al motor anterior: el mismo gráfico en ambos sentidos, probado en repositorios desde pequeñas bibliotecas hasta el kernel de Linux.
  • Se adapta a su máquina: CodeGraph dimensiona sus trabajadores de análisis, grupo de resolución y cachés a partir de lo que el sistema realmente tiene: recuentos de núcleos reales (contenedores/cgroup-aware, no del host), memoria disponible honesta en macOS y Linux, y costo de resolución medido por proyecto. Una estación de trabajo grande obtiene todo el proceso paralelo; un VPS de 2 núcleos obtiene una canalización ajustada para finalizar de manera confiable en lugar de quedarse sin memoria: el kernel de Linux (archivos de 70k) se indexa hasta su finalización en una máquina de 2 núcleos y 6 GB en menos de 12 minutos, en comparación con 26 al comienzo de este ciclo.
  • La resolución es dramáticamente más rápida en todos los ámbitos: resolución paralela adaptable, búsqueda de método candidato más inteligente y recorrido de supertipo/conformidad memorizado. El repositorio del compilador Swift (archivos de 27k, Swift + C++) pasó de más de 3 minutos a aproximadamente 100 segundos dentro de este ciclo de lanzamiento; Los proyectos de la familia Rust, Lua y Java ven mejoras de dos dígitos.
  • La sincronización ahora es casi instantánea: un guardado llega al gráfico en menos de un segundo, incluso a escala del compilador. El observador siempre activo se activa después de una ventana silenciosa de 300 ms para guardados individuales (las ráfagas de ediciones aún se fusionan) y entrega las rutas exactas cambiadas para sincronizar en lugar de volver a escanear todo el árbol: trabajo de guardado en gráfico nuevo medido de ~0,3 s en un proyecto Java de 4400 archivos y ~0,4 s en el repositorio del compilador Swift de 27 000 archivos, byte idéntico a un completo reconciliación. Detalles completos en las entradas a continuación.

Nuevas características

  • La indexación de proyectos TypeScript, TSX, JavaScript, JSX, Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua y Luau es más rápida: el análisis y la extracción de símbolos ahora se ejecutan en un motor nativo cuando hay un binario prediseñado disponible para su plataforma (los paquetes de lanzamiento incluyen uno), lo que produce exactamente el mismo gráfico. verificado byte por byte con el motor anterior en repositorios reales, desde bibliotecas pequeñas hasta vscode-, dubbo-, django-, git-, protobuf-, tokio-, rust-analyzer-, jellyfin-, rails-, symfony-, swift-nio-, kotlinx.coroutines-, ggplot2-, Kong-, Scala-3-compiler- y Bases de código de escala Flutter (miembros generados por Lombok, tablas de punteros de función C y encabezados con macros pesadas estilo Unreal-Engine incluidos; las fuentes CUDA y Metal siguen el camino de C++). La aceleración es mayor en máquinas con recursos limitados, como los corredores de CI. No se necesita configuración: las plataformas sin el binario nativo y los archivos individuales con errores de sintaxis usan automáticamente el motor anterior y CODEGRAPH_KERNEL=0 desactiva la ruta nativa por completo.
  • La resolución de referencia ahora se ejecuta en paralelo en proyectos grandes. Cuando un proyecto tiene suficientes referencias pendientes para que valga la pena (aproximadamente 150k+, típico de las grandes bases de código Java/Kotlin/Spring), la resolución se distribuye entre los subprocesos de trabajo mientras los resultados se aplican en el orden exacto que habría utilizado la ruta de un solo subproceso: el gráfico resulta byte por byte idéntico, aproximadamente el doble de rápido de un extremo a otro en un proyecto Java de 4000 archivos en nuestras pruebas. Los proyectos pequeños mantienen la ruta de un solo subproceso automáticamente (la distribución cuesta más de lo que ahorra allí). Configure CODEGRAPH_NO_PARALLEL_RESOLVE=1 para desactivarlo o CODEGRAPH_PARALLEL_RESOLVE_MIN=<count> para sintonizarlo cuando se active.
  • La indexación de proyectos grandes obtuvo otra aceleración considerable: alrededor de un cuarto menos de tiempo en el mismo proyecto Java de 4.000 archivos, con el gráfico aún byte por byte idéntico. Dos cambios: la base de datos ya no intercala costosas tareas de limpieza de puntos de control en medio de la resolución en un índice nuevo (en su lugar, se dobla una vez al final), y mientras se escriben los resultados de un lote, los subprocesos de trabajo ya están resolviendo el siguiente lote en lugar de permanecer inactivos.
  • El análisis de envío dinámico que se ejecuta al final de la indexación (devolución de llamada, evento y cableado de marco) ahora ejecuta sus pases en paralelo en proyectos grandes, reduciendo esa etapa aproximadamente a la mitad allí, y un pase que falla ahora reintenta de manera segura en lugar de fallar en todo el índice, lo que también hace que las bases de código muy grandes que anteriormente murieron en esta etapa tengan más probabilidades de indexarse ​​hasta su finalización. Los gráficos siguen siendo idénticos byte por byte.
  • En proyectos grandes, la indexación escribe sus datos de relaciones notablemente más rápido: los índices de bases de datos secundarias se reservan durante la mayor parte de la resolución de referencia y se reconstruyen una vez al final, en lugar de mantenerse fila por fila. Los gráficos siguen siendo idénticos byte por byte y los proyectos pequeños no se ven afectados.
  • Fiabilidad de base de código muy grande: en proyectos de varios millones de símbolos, una pasada de análisis que falla en un subproceso de trabajo ahora se omite con un mensaje claro en lugar de volver a intentarlo de una manera que podría eliminar todo el índice, y la reconstrucción del índice al final de la indexación ya no corre el riesgo de hacer tropezar al organismo de control de actividad en gráficos enormes. Validado de un extremo a otro en el kernel de Linux (70k archivos, 2M de símbolos, 6,4M de relaciones): ahora indexa hasta completarse incluso en una máquina de 2 núcleos.
  • La indexación es significativamente más rápida: un codegraph init nuevo en un proyecto mediano TypeScript requiere aproximadamente un tercio menos de tiempo de reloj de pared, con el mismo gráfico producido byte por byte. Las ganancias provienen de escribir por lotes en bases de datos, almacenar archivos en un hilo de escritura dedicado, memorizar búsquedas repetidas de resolución de importación, omitir el mantenimiento del índice de búsqueda por fila durante la compilación masiva (reconstruida una vez al final) y, solo en bases de datos completamente nuevas, diferir la durabilidad del disco hasta que se complete el índice, ya que un primer índice interrumpido simplemente se vuelve a ejecutar. Configure CODEGRAPH_NO_FAST_INIT=1 para mantener la durabilidad total frente a fallas durante la compilación inicial, o CODEGRAPH_NO_STORE_WORKER=1 para almacenar en el hilo principal.

  • Cada lanzamiento ahora es verificable criptográficamente: los paquetes npm se publican con la procedencia npm (la insignia "Procedencia" en npmjs.com, lo que demuestra que cada versión fue creada por el flujo de trabajo de lanzamiento de este repositorio a partir de una confirmación específica), y los paquetes de lanzamiento GitHub llevan certificaciones de compilación firmadas que puede consultar con gh attestation verify <file> -R colbymchenry/codegraph.
  • La indexación dentro de contenedores con CPU o memoria limitada (Docker, ejecutores de CI) ahora dimensiona sus grupos de trabajadores a partir de la asignación real del contenedor en lugar de la de la máquina host, y las bases de código gigantes ya no aumentan los archivos de bases de datos temporales durante la indexación (anteriormente, decenas de GB de disco transitorio en proyectos de escala de kernel de Linux). En conjunto, estos previenen fallas por falta de memoria y falta de disco en máquinas restringidas; configure CODEGRAPH_RESOLVE_WORKERS para anular explícitamente el recuento de trabajadores de resolución.
  • La indexación de proyectos muy grandes en máquinas multinúcleo se volvió más rápida: los trabajadores de resolución paralela ahora actualizan periódicamente sus conexiones de base de datos de sólo lectura, lo que permite que el mantenimiento de la base de datos avance en lugar de acumular silenciosamente un trabajo pendiente detrás de lectores de larga duración, un trabajo pendiente que estaba gravando las escrituras del propio indexador. Los gráficos siguen siendo idénticos byte por byte; la ganancia es mayor a escala del kernel de Linux en máquinas de muchos núcleos.
  • La indexación en macOS ahora utiliza el espacio de memoria real de la máquina al dimensionar sus trabajadores de resolución paralela. macOS mantiene deliberadamente la RAM llena de caché recuperable, por lo que la lectura anterior de memoria libre resultó pequeña (~1 GB en una máquina que de otro modo estaría inactiva) y silenciosamente redujo a la mitad el grupo de trabajadores: el índice nuevo de un proyecto Java mediano funcionó entre un 15 y un 20 % más lento de lo que permitía el hardware. Los gráficos siguen siendo idénticos byte por byte; La misma solución también permite que un caché de análisis basado en memoria funcione completamente en macOS para bases de código C grandes.
  • La nueva indexación obtuvo una considerable aceleración en todos los ámbitos: durante la compilación inicial, los índices de búsqueda secundarios de la base de datos se apartan y se reconstruyen una vez después del análisis en lugar de mantenerse fila por fila (el mismo truco probado que ya se usó en la fase de vinculación posterior, ahora aplicado a todo el carril de análisis) y el bucle de resolución de referencia también deja de mantener índices de búsqueda que nunca lee, reconstruyéndolos al final cuando casi no queda nada en la tabla. La fase de análisis de un proyecto Java mediano se ejecuta aproximadamente un 58 % más rápido y su índice actualizado completo aproximadamente un 19 % más rápido de un extremo a otro; un índice a escala de kernel de Linux que tomó ~15 minutos en una máquina de 8 núcleos ahora se completa en aproximadamente 11, y solo la fase de resolución se reduce en un tercio. Los gráficos siguen siendo idénticos byte por byte y las sincronizaciones incrementales no se ven afectadas.
  • Guardar un archivo ahora actualiza el gráfico casi de inmediato: el observador de archivos se activa después de una ventana silenciosa de 300 ms para uno o dos archivos modificados (las ráfagas aún se fusionan bajo el rebote completo, y CODEGRAPH_WATCH_DEBOUNCE_MS sigue siendo el límite superior), y las sincronizaciones activadas por el observador concilian exactamente las rutas modificadas en lugar de recorrer todo el repositorio con estadísticas. Las eliminaciones de directorios y las tormentas de eventos aún ejecutan el escaneo completo, por lo que nunca se pasa por alto nada que los eventos no puedan describir. Medido: el trabajo de sincronización de guardar en un gráfico nuevo se reduce a ~0,3 s en un proyecto de 4400 archivos y ~0,4 s en uno de 27 000 archivos, con gráficos resultantes byte por byte idénticos a una conciliación completa.
  • La indexación de Swift y otras bases de código con muchos protocolos/interfaces se volvió dramáticamente más rápida: la caminata de conformidad que verifica si un método vive en los supertipos de un receptor (protocolos, clases base, extensiones) ahora recuerda sus respuestas durante la duración de cada lote de resolución en lugar de volver a consultar el gráfico para cada sitio de llamada; en el repositorio del compilador Swift (archivos de 27k), esa caminata se ejecutó casi un millón de veces por índice. Un nuevo índice de ese repositorio cae de aproximadamente 185 segundos a menos de 100, con el gráfico byte por byte idéntico. La búsqueda de candidatos a métodos también obtuvo un índice de propietario por nombre, por lo que los nombres con mucha sobrecarga (init en Swift, execute en Java) ya no pagan una exploración completa de candidatos por tipo de receptor.
  • Resolver llamadas a métodos a través de variables locales (recv.method(), recv:method() de Lua, recv$method() de R) se volvió mucho más económico en repositorios donde se llama al mismo receptor una y otra vez: el escaneo de declaración que escribe el receptor ahora recuerda lo que ya ha escaneado por alcance en lugar de volver a leer las mismas líneas fuente para cada sitio de llamada, y los patrones de expresiones regulares con los que escanea se compilan una vez por receptor en lugar de por llamada. El nuevo índice de Kong cae otro 8% además de la solución de resolución requerida (23% acumulativo), con gráficos byte por byte idénticos en todas partes, incluidos los proyectos Java, donde este mismo escaneo escribe con éxito decenas de miles de receptores.
  • La indexación de proyectos Lua y Luau se aceleró considerablemente: al resolver cada require(...) ya no se vuelve a escanear la lista completa de archivos del proyecto cuatro veces: un índice de nombre de archivo por proyecto responde instantáneamente a la misma búsqueda, reduciendo la resolución por requisito de aproximadamente un milisegundo a microsegundos. Un nuevo índice de Kong (1.870 archivos Lua) se ejecuta aproximadamente un 16% más rápido de un extremo a otro, con el gráfico byte por byte idéntico. La misma limpieza también cierra un borde de obsolescencia latente donde las búsquedas de cuadernos COBOL podrían seguir entregando una lista de archivos en caché después de que los archivos cambiaran.
  • La resolución de referencias paralelas ahora se activa de forma adaptativa en lugar de mediante un límite fijo de tamaño de proyecto: el indexador mide la tasa de resolución real por referencia en el primer lote y acelera el grupo de trabajadores a mitad de ejecución cuando el trabajo restante lo justifica. Los idiomas cuyas referencias son costosas de resolver son los que más se benefician, especialmente Rust: un nuevo índice de Tokio se ejecuta aproximadamente un 23% más rápido, con el gráfico byte por byte idéntico. Los proyectos pequeños y las máquinas de bajo núcleo (ejecutores de CI de 2 núcleos) mantienen la ruta de un solo subproceso exactamente como antes.
  • El análisis de envío dinámico al final de la indexación ahora omite pasos que probablemente no puedan producir nada para el proyecto en cuestión: React vuelve a renderizar el puente cuando ninguna clase tiene un método render, el emparejamiento multiplataforma React Native y Expo cuando los idiomas requeridos no están presentes, y el enlace del mapeador MyBatis cuando no hay un XML del mapeador. Anteriormente, cada uno de estos escaneaba el gráfico completo antes de quedar vacío, en un proyecto Java de 4.000 archivos que representaba aproximadamente 0.9 segundos de análisis desperdiciado por índice nuevo. El pase puente de implementación de interfaz también se volvió más económico en el trabajo real: ya no recupera la lista de métodos de una interfaz central una vez por implementador, y las clases que no extienden ni implementan nada se omiten antes de cualquier búsqueda por clase. Los gráficos siguen siendo idénticos byte por byte.
  • La indexación de grandes bases de código C y C++ invierte mucho menos tiempo en el análisis de envío de punteros de función (el paso que conecta las tablas de controlador como una tabla de comandos o una estructura de operaciones con sus sitios de llamada): cada archivo fuente ahora se lee y prepara una vez en lugar de cuatro veces, los archivos que no pueden contribuir con ningún cableado de envío se omiten directamente en los pasos de enlace posteriores, y en plataformas con el motor nativo el escaneo por archivo ahora también se ejecuta de forma nativa. En un árbol a escala de kernel de Linux, el pase se ejecuta aproximadamente un tercio más rápido de un extremo a otro, con gráficos idénticos byte por byte; Las plataformas sin un binario nativo mantienen los mismos resultados en la ruta anterior.

Correcciones

  • Los archivos TypeScript, TSX y JavaScript ahora se analizan con gramáticas actualizadas: la sintaxis moderna, como las declaraciones using y los atributos de importación, ya no generan errores de análisis que podrían eliminar los símbolos circundantes. (Las gramáticas incluidas anteriormente datan de 2023).
  • Los archivos Rust también se analizan con una gramática actualizada ahora (la compilación incluida anteriormente data de 2023), lo que además mejora la atribución de llamadas a métodos: las llamadas a través de campos de estructura se resuelven con el contexto del receptor en lugar de recurrir a coincidencias ambiguas de nombres simples, eliminando una clase de bordes de llamadas incorrectos en nombres comunes como len y start.
  • Los archivos Ruby también se analizan con una gramática actualizada ahora (la compilación incluida anteriormente data de principios de 2024), lo que corrige un error de análisis de las llamadas al método del operador de navegación segura (recv&.!= x) que habían registrado el nombre incorrecto de la persona que llama.
  • Los archivos PHP ahora también se analizan con una gramática actualizada (la compilación incluida anteriormente data de 2023): los archivos que utilizan funciones PHP modernas (constantes de enumeración, enlaces de propiedades PHP 8.4, encadenamiento new X()->method() sin paréntesis) ya no presentan errores de análisis o errores de análisis que eliminan o confunden sus símbolos, por lo que las bases de código como Symfony y Laravel indexan con mucha mayor precisión.
  • Los archivos Swift también se analizan con una gramática actualizada ahora (la compilación incluida anteriormente data de 2023): las pruebas rápidas #expect, las macros de estilo #Preview, el modificador de acceso package y el throws escrito ya no producen errores de análisis que eliminan los símbolos circundantes; los proyectos Swift del lado del servidor como Vapor experimentan la mayor recuperación.
  • La gramática de Dart ahora está incluida con CodeGraph en lugar de resolverse desde un paquete de terceros cuya compilación de Dart flotaba en una referencia ascendente no fijada: una actualización de dependencia de rutina ya no puede cambiar silenciosamente la forma en que se analizan los archivos de Dart.
  • Al buscar o explorar por nombres de campos ahora se encuentra el código que los define. Una consulta hecha de claves de objetos o nombres de campos API (profileInfo isTrialEligible quotaInfo billingMethod) solía devolver resultados no relacionados mientras que los archivos de definición nunca aparecían, porque cada uno de los tres pasos de recuperación eliminaba términos camelCase de varias palabras: un error interno de comparación de casos, un paso de coincidencia que solo consideraba clases (nunca funciones o métodos) y siembra de exploración que requería coincidencias exactas de nombres de símbolos. Los tres están arreglados: codegraph_explore con una bolsa de nombres de campos ahora muestra los controladores y servicios que ensamblan esos campos. (#1196)
  • includeIgnored de codegraph.json funciona nuevamente para el diseño de "carpeta de repositorios": cuando una regla .gitignore cubre un directorio principal (/repos/) que contiene varios repositorios git integrados, optar por los repositorios individuales ("includeIgnored": ["repos/a/"] - la ortografía exacta que sugiere la propia sugerencia de codegraph init) anteriormente no coincidía con nada e indexaba cero archivos, devolviéndole la misma sugerencia. Ambas grafías ahora funcionan: nombrar el directorio principal para optar por todo lo que hay debajo de él, o nombrar repositorios individuales para optar por solo esos, y la sugerencia ya no vuelve a sugerir repositorios que ya están configurados. (#1295)
  • Las llamadas a métodos en literales (", ".join(...) en Python, "x".split(...) en JavaScript y similares) ya no producen bordes de llamada a funciones de proyecto no relacionadas que comparten el nombre de la función incorporada: una base de código con una función llamada join, get o update podría mostrar personas que llaman fantasmas de cada uso de cadena incorporada. Además, una función anidada dentro de otra función ahora solo coincide como destino de llamada desde dentro de su contenedor, ya que no se puede acceder a ella desde ningún otro lugar. Los resultados de las pruebas de radio de explosión y afectados se vuelven más limpios especialmente en las bases de código Python y JavaScript. (#1230)
  • Las llamadas al método Go a través de un campo de estructura (target.conn.Exec(...)) ya no se vinculan a métodos locales no relacionados con el mismo nombre cuando el tipo de campo es externo: las llamadas conn *sql.DB se atribuían a una interfaz local que declaraba Exec, fabricando dependencias internas. Las llamadas de campo encadenadas ahora se resuelven infiriendo el tipo declarado del campo a partir de la definición de la estructura: los tipos en el proyecto (incluidos los no exportados como tree *node de chi) obtienen bordes de llamada correctos y validados que nunca antes existieron, y los tipos externos (biblioteca estándar, módulos de terceros) se dejan desvinculados en lugar de adivinarse. (#1276)
  • Las llamadas al método TypeScript/JavaScript a través de un singleton importado (import { store } from './store'; store.notify()) ahora se resuelven en el método de clase en lugar de la constante exportada, por lo que codegraph callers ve llamadores del método entre archivos; anteriormente solo se atribuían llamadas al mismo archivo y un método usado en todas partes podía parecer no utilizado. La misma inferencia de tipos basada en declaraciones se aplica en todos los lenguajes que la comparten (Python, Java, Kotlin, Go y más), y una inferencia fallida mantiene la ventaja anterior en lugar de adivinar. (#1292)
  • codegraph node <symbol> -f <file> ahora imprime el cuerpo fuente del símbolo. Fijar un nombre ambiguo a un archivo específico (el objetivo de -f cuando muchos archivos definen la misma función) devolvió solo la ubicación y el rastro de la persona que llama sin código. (#1284)
  • La eliminación de un directorio completo ahora se realiza mediante el modo de visualización: los archivos que contiene se eliminan del índice en la siguiente sincronización automática en lugar de permanecer como registros obsoletos hasta que una edición no relacionada active uno. Los sistemas operativos a menudo informan la eliminación de un directorio como un evento único en el directorio mismo (sin eventos por archivo para su contenido), que el observador descartó previamente. (#1285)
  • codegraph sync ahora obtiene la misma corrección de disco lento que aceleró la indexación completa en 1.4.0: los puntos de control de la base de datos se difieren durante toda la ejecución incremental en lugar de activarse cada pocos megabytes de escritura. En unidades mecánicas y otros sistemas de almacenamiento de alta latencia, una pequeña sincronización en un índice grande ya no se detiene durante minutos con una CPU cercana a cero: el costo de una sincronización aumenta con lo que cambia, no con el tamaño del índice existente. El mismo interruptor CODEGRAPH_NO_WAL_DEFER=1 lo apaga. (#1248)
  • Las funciones C declaradas con una macro de atributo específica del proyecto delante de un tipo de retorno definido por tipo (SEC_ATTR UINT32 MyFunc(VOID), común en el código incrustado y del kernel) ahora están indexadas con sus nombres reales. Anteriormente, el analizador tropezó con la macro desconocida y almacenó la lista de parámetros como el nombre de la función, dejando entradas como "(VOID)" en el gráfico y haciendo que la función real fuera imposible de encontrar. (#1211)
  • El código C y C++ con muchas macros indexa de forma mucho más completa. Quince modismos omnipresentes que anteriormente hacían que el analizador se recuperara de errores (eliminar símbolos, confundir nombres, crear entradas fantasmas o perder las relaciones entre los reales) ahora se analizan limpiamente: la protección de compatibilidad #ifdef __cplusplus / extern "C" { en encabezados C, macros de iterador en posición de declaración (list_for_each_entry(pos, head, member) { … } y toda la familia Linux-kernel/git/jemalloc, incluidas llamadas que cruzan líneas, como hlist_for_each_entry_rcu(…) con un argumento lockdep_is_held), las anotaciones de declaración dispersa/de Linux (static int __init foo(void), void __user *buf, container_of(p, struct T, m)), anotaciones parametrizadas (__free(kfree), __printf(4, 0), __counted_by(count)), macros de declaración por CPU y cola de trabajo (static DEFINE_PER_CPU(struct T, name);, formularios inicializados incluidos), argumentos de tipo simple para asignador y macros de lista (kzalloc_obj(struct T), list_entry(p, struct T, member)), va_arg con un tipo calificado o de puntero, definiciones de macros variables con nombre GNU (#define dbg(fmt, args...)), marcadores de compilador de estilo static notrace, declaraciones C23 auto, anotaciones de parámetros finales (int argc UNUSED, estilo propio de git), macros de administración de espacio de nombres solas en una línea (FMT_BEGIN_NAMESPACE, Q_OBJECT de Qt) y macros de atributos de función delante de los tipos de retorno de C++. En el kernel de Linux, esto reduce a casi la mitad los archivos perdidos al analizar errores en los directorios principales y recupera miles de relaciones de llamadas y referencias que la recuperación de errores eliminó silenciosamente, con git y redis viendo cortes más pequeños del mismo tipo; Los gráficos permanecen byte por byte idénticos entre los motores nativo y alternativo. Una solución relacionada evita que el manejo de la macro corrompa las líneas #define que mencionan los mismos nombres de macro, lo que eliminó una clase de errores de análisis fantasma en encabezados de estilo fmt.
  • Los métodos de C++ definidos fuera de línea dentro de un espacio de nombres (namespace sim { Output MyClass::Apply(...) { ... } }) ahora llevan el espacio de nombres en su nombre completo, que coincide con su clase. Los sitios de llamadas totalmente calificados de otros archivos (sim::MyClass::Apply(...)) se resuelven nuevamente en la definición, por lo que codegraph callers y el impacto del archivo ya no aparecen vacíos para este patrón. (#1291)
  • Los métodos de C++ definidos fuera de línea en una clase de plantilla (template <typename T> T Box<T>::get() { ... }) ya no mantienen la lista de parámetros de plantilla en su nombre completo. Ahora se indexan como Box::get, idéntico a una definición en línea del mismo método, por lo que se vinculan a su clase y se resuelven desde los sitios de llamadas nuevamente, y las listas patológicas de parámetros de plantillas de múltiples líneas ya no pueden hacer que el nombre calificado supere los límites de nombres del sistema de archivos. (#1286)

Un registro ahora tiene que verse como tal: su primer argumento debe ser una ruta con el prefijo / (todos los enrutadores) o un patrón Go 1.22 "METHOD /path" en Handle/HandleFunc, que ahora también extrae el método en lugar de enumerar la ruta como ANY. (#1259)
  • La salida de progreso en Windows ya no mezcla carriles ASCII | con el marco Unicode │ ◆ ● a su alrededor. En terminales que procesan Unicode (Windows Terminal, VS Code, ConEmu/Cmder, JetBrains, Alacritty), todo el bloque codegraph init / index / sync ahora se dibuja con caracteres de dibujo de cuadros coincidentes; Las consolas heredadas no reconocidas mantienen la salida segura totalmente ASCII que evita caracteres confusos. CODEGRAPH_ASCII=1 / CODEGRAPH_UNICODE=1 aún se anula en cualquier dirección. (#398)
  • La salida CLI ahora respeta la convención NO_COLOR y los nuevos indicadores --color / --no-color, y se vuelve simple automáticamente cuando se canaliza: comandos como codegraph status, query, callers y files ya no incorporan códigos de color ANSI cuando la salida estándar no es una terminal y un codegraph init / index canalizado / sync imprime líneas simples por fase en lugar de caracteres de control de animación de progreso. FORCE_COLOR o --color fuerzan el color nuevamente para las tuberías que lo renderizan. (#1281)
  • Las personas que llaman y el análisis de impacto ya no subestiman silenciosamente una función que llama a la misma persona que llama muchas veces. Cuando una persona que llama contenía varios sitios de llamadas para la misma persona que llama y un límite de lote de resolución interna los dividió, la limpieza después del primer lote eliminó las filas pendientes de los sitios posteriores antes de que se intentaran: sus bordes nunca se crearon, de manera determinista, y qué bordes desaparecieron cambiaron con cambios no relacionados en el recuento total de referencias del proyecto. La limpieza posterior al pase ahora apunta a la fila exacta de la base de datos de la que proviene cada referencia procesada. Encontrado al validar la corrección de llamada del operador en nlohmann/json, donde las 11 llamadas de write_cbor a to_char_type indexadas como 10. (#1269)
  • Las llamadas explícitas a operadores de C++ (a.operator+(b), p->operator+(b), a.operator[](3) y otras formas simbólicas) ahora producen una ventaja calls en el método del operador, por lo que un operador invocado solo a través de la sintaxis explícita ya no parece no llamado en los llamadores y en el análisis de impacto. tree-sitter analiza estos sitios de llamadas con el nombre del operador atrapado en un nodo de error (nunca como un acceso de miembro normal), por lo que el destino de la llamada se leyó silenciosamente solo como la variable del receptor; el nombre del operador ahora se recupera del nodo de error y se resuelve mediante inferencia del tipo de receptor como cualquier otra llamada de miembro: un operador con el mismo nombre en una clase no relacionada nunca puede capturar el borde. Los usos de Infix (a + b, a[i]) necesitan inferencia de tipos reales y se rastrean por separado. (#1247)
  • codegraph init y codegraph index ya no parecen colgados después de que "Resolver referencias" alcanza el 100%. El enlace de envío dinámico que se ejecuta después de la resolución (devoluciones de llamada, rerenderizaciones de React, punteros de función C y el resto) no tenía visualización de progreso, por lo que en los repositorios donde lleva un tiempo (especialmente bases de código C grandes) la barra simplemente permaneció congelada al 100% hasta que terminó. Ese trabajo ahora se muestra como su propia fase de progreso de "Enlace de envío dinámico", y el paso más pesado (enlace de puntero de función C) informa adicionalmente el progreso dentro del paso, por lo que una base de código C grande hace avanzar la barra suavemente en lugar de estacionarla en un número durante la mayor parte de la fase.
  • La indexación ya no imprime advertencias repetidas de "SQLite es una característica experimental" que confundían la visualización del progreso. La advertencia proviene del SQLite integrado de Node y se activa una vez por trabajador de análisis; ahora está suprimido en todas las rutas de lanzamiento.

codegraph v1.5.0

[1.5.0] - 2026-07-21

⚡ The Rust engine release — with near-instant sync

This release rebuilds CodeGraph's parsing engine as a native Rust kernel, overhauls the resolution pipeline around it, and makes the live graph effectively instant: a save now reaches the graph in well under a second, even on a 27,000-file repository. It is the largest performance upgrade in the project's history — and every graph is verified byte-for-byte identical to the previous engine.

  • Native Rust parsing for 20 languages — TypeScript, JavaScript (+TSX/JSX), Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua, and Luau now parse in a compiled Rust kernel (Metal and CUDA ride the C++ path). Platforms without a prebuilt binary, and individual files with syntax errors, fall back to the previous engine automatically — same graph either way, proven on repositories from small libraries to the Linux kernel.
  • Adaptive to your machine — CodeGraph sizes its parse workers, resolver pool, and caches from what the system actually has: real core counts (container/cgroup-aware, not the host's), honest available memory on macOS and Linux, and measured per-project resolution cost. A big workstation gets the full parallel pipeline; a 2-core VPS gets a pipeline tuned to finish reliably instead of running out of memory — the Linux kernel (70k files) indexes to completion on a 2-core, 6GB machine in under 12 minutes — down from 26 at the start of this cycle.
  • Resolution is dramatically faster across the board — adaptive parallel resolution, smarter method-candidate lookup, and memoized supertype/conformance walking. The Swift compiler repository (27k files, Swift + C++) went from over 3 minutes to about 100 seconds within this release cycle; Rust, Lua, and Java-family projects all see double-digit improvements.
  • Sync is now near-instant — a save reaches the graph in well under a second, even at compiler scale. The always-on watcher fires after a 300ms quiet window for lone saves (bursts of edits still coalesce), and hands the exact changed paths to sync instead of re-scanning the whole tree — measured save-to-fresh-graph work of ~0.3s on a 4,400-file Java project and ~0.4s on the 27,000-file Swift compiler repository, byte-identical to a full reconciliation.

Full details in the entries below.

New Features

  • Indexing TypeScript, TSX, JavaScript, JSX, Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua, and Luau projects is faster: parsing and symbol extraction now run in a native engine when a prebuilt binary is available for your platform (release bundles include one), producing exactly the same graph — verified byte-for-byte against the previous engine on real repositories, from small libraries up to vscode-, dubbo-, django-, git-, protobuf-, tokio-, rust-analyzer-, jellyfin-, rails-, symfony-, swift-nio-, kotlinx.coroutines-, ggplot2-, Kong-, Scala-3-compiler-, and Flutter-scale codebases (Lombok-generated members, C function-pointer tables, and Unreal-Engine-style macro-heavy headers included; CUDA and Metal sources ride the C++ path). The speedup is largest on resource-constrained machines like CI runners. No setup needed: platforms without the native binary, and individual files with syntax errors, automatically use the previous engine, and CODEGRAPH_KERNEL=0 turns the native path off entirely.
  • Reference resolution now runs in parallel on large projects. When a project has enough pending references to make it worthwhile (roughly 150k+, typical for big Java/Kotlin/Spring codebases), resolution fans out across worker threads while results are applied in the exact order the single-threaded path would have used — the graph comes out byte-for-byte identical, about twice as fast end-to-end on a 4,000-file Java project in our testing. Small projects keep the single-threaded path automatically (the fan-out costs more than it saves there). Set CODEGRAPH_NO_PARALLEL_RESOLVE=1 to disable, or CODEGRAPH_PARALLEL_RESOLVE_MIN=<count> to tune when it engages.
  • Indexing large projects got another sizeable speedup — about a quarter less wall-clock on the same 4,000-file Java project, with the graph still byte-for-byte identical. Two changes: the database no longer interleaves expensive checkpoint housekeeping into the middle of resolution on a fresh index (it's folded once at the end instead), and while one batch's results are being written out, the worker threads are already resolving the next batch instead of sitting idle.
  • The dynamic-dispatch analysis that runs at the end of indexing (callback, event, and framework wiring) now runs its passes in parallel on large projects, cutting that stage roughly in half there — and a pass that crashes now retries safely instead of failing the whole index, which also makes very large codebases that previously died in this stage more likely to index to completion. Graphs remain byte-for-byte identical.
  • On large projects, indexing writes its relationship data noticeably faster: secondary database indexes are set aside during the bulk of reference resolution and rebuilt once at the end, instead of being maintained row by row. Graphs remain byte-for-byte identical, and small projects are unaffected.
  • Very-large-codebase reliability: on multi-million-symbol projects, an analysis pass that fails on a worker thread is now skipped with a clear message instead of being retried in a way that could take down the whole index, and the end-of-indexing index rebuild no longer risks tripping the liveness watchdog on huge graphs. Validated end-to-end on the Linux kernel (70k files, 2M symbols, 6.4M relationships) — it now indexes to completion even on a 2-core machine.
  • Indexing is significantly faster — a fresh codegraph init on a medium TypeScript project takes about a third less wall-clock time, with the same graph produced byte-for-byte. The gains come from batching database writes, storing files on a dedicated writer thread, memoizing repeated import-resolution lookups, skipping per-row search-index maintenance during the bulk build (rebuilt once at the end), and — on completely fresh databases only — deferring disk durability until the index completes, since an interrupted first index is simply re-run. Set CODEGRAPH_NO_FAST_INIT=1 to keep full crash-durability during the initial build, or CODEGRAPH_NO_STORE_WORKER=1 to store on the main thread.
  • codegraph install and codegraph upgrade now offer CodeGraph Pro beta access after finishing — answer yes, type your email, and you join the same waitlist as the getcodegraph.com homepage form. Strictly opt-in and asked at most once per machine total: nothing is sent unless you say yes and enter an email, either answer is remembered so no later install or upgrade ever re-asks, and non-interactive runs (--yes, scripts, CI) never see the question.
  • Every release is now cryptographically verifiable: npm packages publish with npm provenance (the "Provenance" badge on npmjs.com, proving each version was built by this repository's release workflow from a specific commit), and the GitHub Release bundles carry signed build attestations you can check with gh attestation verify <file> -R colbymchenry/codegraph.
  • Indexing inside CPU- or memory-limited containers (Docker, CI runners) now sizes its worker pools from the container's actual allowance instead of the host machine's, and giant codebases no longer balloon temporary database files during indexing (previously tens of GB of transient disk on Linux-kernel-scale projects). Together these prevent out-of-memory and out-of-disk failures on constrained machines; set CODEGRAPH_RESOLVE_WORKERS to override the resolution worker count explicitly.
  • Indexing very large projects on multi-core machines got faster again: the parallel-resolution workers now periodically refresh their read-only database connections, which lets database housekeeping advance instead of silently building up a backlog behind long-lived readers — a backlog that was taxing the indexer's own writes. Graphs remain byte-for-byte identical; the win is largest at Linux-kernel scale on many-core machines.
  • Indexing on macOS now uses the machine's real memory headroom when sizing its parallel-resolution workers. macOS deliberately keeps RAM filled with reclaimable cache, so the previous free-memory reading came back tiny (~1GB on an otherwise idle machine) and silently halved the worker pool — a medium Java project's fresh index ran about 15–20% slower than the hardware allowed. Graphs remain byte-for-byte identical; the same fix also lets a memory-driven analysis cache engage fully on macOS for large C codebases.
  • Fresh indexing got a sizeable across-the-board speedup: during the initial build, the database's secondary lookup indexes are set aside and rebuilt once after parsing instead of being maintained row by row — the same proven trick the later linking phase already used, now applied to the whole parse lane — and the reference-resolution loop likewise stops maintaining lookup indexes it never reads, rebuilding them at the end when almost nothing is left in the table. A medium Java project's parse phase runs about 58% faster and its full fresh index about 19% faster end-to-end; a Linux-kernel-scale index that took ~15 minutes on an 8-core machine now completes in about 11, with the resolution phase alone dropping by a third. Graphs remain byte-for-byte identical, and incremental syncs are unaffected.
  • Saving a file now updates the graph almost immediately: the file watcher fires after a 300ms quiet window for one or two changed files (bursts still coalesce under the full debounce, and CODEGRAPH_WATCH_DEBOUNCE_MS remains the upper bound), and watcher-triggered syncs reconcile exactly the changed paths instead of stat-walking the entire repository. Directory deletions and event storms still run the full scan-diff, so nothing the events can't describe is ever missed. Measured: save-to-fresh-graph sync work drops to ~0.3s on a 4,400-file project and ~0.4s on a 27,000-file one, with resulting graphs byte-for-byte identical to a full reconciliation.
  • Indexing Swift and other protocol/interface-heavy codebases got dramatically faster: the conformance walk that checks whether a method lives on a receiver's supertypes (protocols, base classes, extensions) now remembers its answers for the duration of each resolution batch instead of re-querying the graph for every call site — on the Swift compiler repository (27k files) that walk ran nearly a million times per index. A fresh index of that repo drops from about 185 seconds to under 100, with the graph byte-for-byte identical. Method-candidate lookup also gained a per-name owner index, so overload-heavy names (init in Swift, execute in Java) no longer pay a full candidate scan per receiver type.
  • Resolving method calls through local variables (recv.method(), Lua's recv:method(), R's recv$method()) got much cheaper on repos where the same receiver is called over and over: the declaration scan that types the receiver now remembers what it has already scanned per scope instead of re-reading the same source lines for every call site, and the regex patterns it scans with are compiled once per receiver instead of per call. Kong's fresh index drops another 8% on top of the require-resolution fix (23% cumulative), with graphs byte-for-byte identical everywhere — including Java projects, where this same scan successfully types tens of thousands of receivers.
  • Indexing Lua and Luau projects got a sizeable speedup: resolving each require(...) no longer rescans the project's entire file list four times — a per-project filename index answers the same lookup instantly, cutting per-require resolution from about a millisecond to microseconds. A fresh index of Kong (1,870 Lua files) runs about 16% faster end-to-end, with the graph byte-for-byte identical. The same housekeeping also closes a latent staleness edge where COBOL copybook lookups could keep serving a cached file list after files changed.
  • Parallel reference resolution now engages adaptively instead of by a fixed project-size cutoff: the indexer measures the actual per-reference resolution rate on the first batch and spins up the worker pool mid-run whenever the remaining work justifies it. Languages whose references are expensive to resolve benefit most — Rust especially: a fresh index of tokio runs about 23% faster, with the graph byte-for-byte identical. Small projects and low-core machines (2-core CI runners) keep the single-threaded path exactly as before.
  • The dynamic-dispatch analysis at the end of indexing now skips passes that provably can't produce anything for the project at hand: React re-render bridging when no class has a render method, React Native and Expo cross-platform pairing when the required languages aren't present, and MyBatis mapper linking when there's no mapper XML. Previously each of these scanned the whole graph before coming up empty — on a 4,000-file Java project that was about 0.9 seconds of wasted analysis per fresh index. The interface-implementation bridging pass also got cheaper on real work: it no longer re-fetches a hub interface's method list once per implementer, and classes that extend or implement nothing are skipped before any per-class lookups. Graphs remain byte-for-byte identical.
  • Indexing large C and C++ codebases spends much less time in the function-pointer dispatch analysis (the pass that connects handler tables like a command table or an ops struct to their call sites): each source file is now read and prepared once instead of four times, files that can't contribute any dispatch wiring are skipped outright in the later linking steps, and on platforms with the native engine the per-file scanning itself now runs natively too. On a Linux-kernel-scale tree the pass runs about a third faster end-to-end, with graphs byte-for-byte identical; platforms without a native binary keep the same results on the previous path.

Fixes

  • TypeScript, TSX, and JavaScript files now parse with up-to-date grammars — modern syntax such as using declarations and import attributes no longer trips parse errors that could drop surrounding symbols. (The previously bundled grammars dated from 2023.)
  • Rust files also parse with an up-to-date grammar now (the previously bundled build dated from 2023), which additionally sharpens method-call attribution: calls through struct fields resolve with receiver context instead of falling back to ambiguous bare-name matching, removing a class of wrong call edges on common names like len and start.
  • Ruby files also parse with an up-to-date grammar now (the previously bundled build dated from early 2024), which fixes a misparse of safe-navigation operator-method calls (recv&.!= x) that had recorded the wrong callee name.
  • PHP files also parse with an up-to-date grammar now (the previously bundled build dated from 2023): files using modern PHP features — enum constants, PHP 8.4 property hooks, parenthesis-free new X()->method() chaining — no longer hit parse errors or misparses that dropped or garbled their symbols, so codebases like Symfony and Laravel index substantially more accurately.
  • Swift files also parse with an up-to-date grammar now (the previously bundled build dated from 2023): swift-testing #expect, #Preview-style macros, the package access modifier, and typed throws no longer produce parse errors that dropped surrounding symbols — server-side Swift projects like Vapor see the biggest recovery.
  • Dart's grammar is now bundled with CodeGraph itself instead of being resolved from a third-party package whose Dart build floated on an unpinned upstream reference — a routine dependency update can no longer silently change how Dart files parse.
  • Searching or exploring by field names now finds the code that defines them. A query made of object keys or API field names (profileInfo isTrialEligible quotaInfo billingMethod) used to return unrelated results while the defining files never appeared, because three retrieval steps each dropped multi-word camelCase terms: an internal case-comparison bug, a match step that only considered classes (never functions or methods), and exploration seeding that required exact symbol-name matches. All three are fixed — codegraph_explore with a bag of field names now surfaces the controllers and services that assemble those fields. (#1196)
  • codegraph.json's includeIgnored works again for the "folder of repos" layout: when one .gitignore rule covers a parent directory (/repos/) holding several embedded git repositories, opting in the individual repos ("includeIgnored": ["repos/a/"] — the exact spelling codegraph init's own hint suggests) previously matched nothing and indexed zero files, looping the same suggestion back at you. Both spellings now work — name the parent directory to opt in everything under it, or name individual repos to opt in just those — and the hint no longer re-suggests repos that are already configured. (#1295)
  • Method calls on literals (", ".join(...) in Python, "x".split(...) in JavaScript, and the like) no longer produce call edges to unrelated project functions that happen to share the builtin's name — a codebase with a function called join, get, or update could show phantom callers from every string-builtin use. Additionally, a function nested inside another function is now only matched as a call target from inside its container, since it isn't reachable from anywhere else. Blast-radius and affected-test results get cleaner on Python and JavaScript codebases especially. (#1230)
  • Go method calls through a struct field (target.conn.Exec(...)) no longer bind to unrelated same-named local methods when the field's type is external — conn *sql.DB calls were being attributed to a local interface that happened to declare Exec, fabricating internal dependencies. Chained field calls now resolve by inferring the field's declared type from the struct definition: in-project types (including unexported ones like chi's tree *node) gain correct, validated call edges that never existed before, and external types (standard library, third-party modules) are left unlinked instead of guessed. (#1276)
  • TypeScript/JavaScript method calls through an imported singleton (import { store } from './store'; store.notify()) now resolve to the class method instead of the exported constant, so codegraph callers sees cross-file callers of the method — previously only same-file calls were attributed and a method used everywhere could look unused. The same declaration-based type inference applies across the languages that share it (Python, Java, Kotlin, Go, and more), and a failed inference keeps the old edge rather than guessing. (#1292)
  • codegraph node <symbol> -f <file> now prints the symbol's source body. Pinning an ambiguous name to a specific file (the whole point of -f when many files define the same function) returned only the location and caller trail with no code. (#1284)
  • Deleting a whole directory is now picked up by watch mode: the files inside it are removed from the index on the next auto-sync instead of lingering as stale records until an unrelated edit happened to trigger one. Operating systems often report a directory deletion as a single event on the directory itself (with no per-file events for its contents), which the watcher previously discarded. (#1285)
  • codegraph sync now gets the same slow-disk fix that made full indexing fast in 1.4.0: database checkpointing is deferred for the whole incremental run instead of firing every few megabytes of writes. On mechanical drives and other high-latency storage, a small sync on a large index no longer stalls for minutes at near-zero CPU — the cost of a sync scales with what changed, not with the size of the existing index. The same CODEGRAPH_NO_WAL_DEFER=1 switch turns it off. (#1248)
  • C functions declared with a project-specific attribute macro in front of a typedef'd return type (SEC_ATTR UINT32 MyFunc(VOID) — common in embedded and kernel code) are now indexed under their real names. Previously the parser tripped over the unknown macro and stored the parameter list as the function name, leaving entries like "(VOID)" in the graph and making the real function unfindable. (#1211)
  • Macro-heavy C and C++ code indexes much more completely. Fifteen ubiquitous idioms that previously tripped the parser into error recovery — dropping symbols, garbling names, minting phantom entries, or losing the relationships between real ones — now parse cleanly: the #ifdef __cplusplus / extern "C" { compatibility guard in C headers, iterator macros in statement position (list_for_each_entry(pos, head, member) { … } and the whole Linux-kernel/git/jemalloc family — including calls that wrap across lines, like hlist_for_each_entry_rcu(…) with a lockdep_is_held argument), the Linux/sparse declaration annotations (static int __init foo(void), void __user *buf, container_of(p, struct T, m)), parameterized annotations (__free(kfree), __printf(4, 0), __counted_by(count)), per-CPU and work-queue declaration macros (static DEFINE_PER_CPU(struct T, name);, initialized forms included), bare type arguments to allocator and list macros (kzalloc_obj(struct T), list_entry(p, struct T, member)), va_arg with a qualified or pointer type, GNU named-variadic macro definitions (#define dbg(fmt, args...)), static notrace-style compiler markers, C23 auto declarations, trailing parameter annotations (int argc UNUSED, git's house style), namespace-management macros alone on a line (FMT_BEGIN_NAMESPACE, Qt's Q_OBJECT), and function attribute macros in front of C++ return types. On the Linux kernel this cuts files lost to parse errors on the core directories by nearly half and recovers thousands of call and reference relationships that error recovery silently dropped, with git and redis seeing smaller cuts of the same kind; graphs stay byte-for-byte identical between the native and fallback engines. A related fix stops the macro handling itself from corrupting #define lines that mention the same macro names, which removed a class of phantom parse errors in fmt-style headers.
  • C++ methods defined out-of-line inside a namespace (namespace sim { Output MyClass::Apply(...) { ... } }) now carry the namespace in their qualified name, matching their class. Fully-qualified call sites from other files (sim::MyClass::Apply(...)) resolve to the definition again, so codegraph callers and file impact no longer come up empty for this pattern. (#1291)
  • C++ methods defined out-of-line on a template class (template <typename T> T Box<T>::get() { ... }) no longer keep the template parameter list in their qualified name. They now index as Box::get — identical to an inline definition of the same method — so they link to their class and resolve from call sites again, and pathological multi-line template parameter lists can no longer blow the qualified name past filesystem name limits. (#1286)
  • Go route detection no longer misidentifies ordinary method calls that share HTTP verb names — cache.Put("key", value), store.Get("config", out), bus.Handle("user.created", handler) and the like were being indexed as HTTP routes, polluting route listings in cache-heavy codebases. A registration now has to look like one: its first argument must be a /-prefixed path (all routers) or a Go 1.22 "METHOD /path" pattern on Handle/HandleFunc, which now also extracts the method instead of listing the route as ANY. (#1259)
  • Progress output on Windows no longer mixes ASCII | rails with the Unicode │ ◆ ● frame around them. In terminals that render Unicode (Windows Terminal, VS Code, ConEmu/Cmder, JetBrains, Alacritty), the whole codegraph init / index / sync block now draws with matching box-drawing characters; unrecognized legacy consoles keep the safe all-ASCII output that avoids garbled characters. CODEGRAPH_ASCII=1 / CODEGRAPH_UNICODE=1 still override in either direction. (#398)
  • CLI output now honors the NO_COLOR convention and new --color / --no-color flags, and goes plain automatically when piped: commands like codegraph status, query, callers, and files no longer embed ANSI color codes when stdout isn't a terminal, and a piped codegraph init / index / sync prints simple per-phase lines instead of progress-animation control characters. FORCE_COLOR or --color forces color back on for pipes that render it. (#1281)
  • Callers and impact analysis no longer silently under-count a function that calls the same callee many times. When one caller contained several call sites to the same callee and an internal resolution batch boundary happened to split them, cleanup after the first batch removed the later sites' pending rows before they were ever attempted — their edges were never created, deterministically, and which edges went missing shifted with unrelated changes to the project's total reference count. Post-pass cleanup now targets the exact database row each processed reference came from. Found while validating the operator-call fix on nlohmann/json, where write_cbor's 11 calls to to_char_type indexed as 10. (#1269)
  • C++ explicit operator calls — a.operator+(b), p->operator+(b), a.operator[](3), and the other symbolic forms — now produce a calls edge to the operator method, so an operator invoked only through the explicit syntax no longer looks uncalled in callers and impact analysis. tree-sitter parses these call sites with the operator name stranded in an error node (never as a normal member access), so the call's target was silently read as just the receiver variable; the operator name is now recovered from the error node and resolved through receiver-type inference like any other member call — a same-named operator on an unrelated class can never capture the edge. Infix uses (a + b, a[i]) need real type inference and are tracked separately. (#1247)
  • codegraph init and codegraph index no longer look hung after "Resolving refs" reaches 100%. The dynamic-dispatch linking that runs after resolution (callbacks, React re-renders, C function pointers, and the rest) had no progress display, so on repos where it takes a while — large C codebases especially — the bar just sat frozen at 100% until it finished. That work now shows as its own "Linking dynamic dispatch" progress phase, and the heaviest pass — C function-pointer linking — additionally reports progress within the pass, so a large C codebase advances the bar smoothly instead of parking it on one number for the bulk of the phase.
  • Indexing no longer prints repeated "SQLite is an experimental feature" warnings that garbled the progress display. The warning comes from Node's built-in SQLite and fired once per parsing worker; it's now suppressed on every launch path.
