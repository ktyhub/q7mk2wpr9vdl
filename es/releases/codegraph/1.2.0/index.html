códice v1.2.0

[1.2.0] - 2026-07-02

Nuevas características

  • Las llamadas a métodos realizadas a través de una variable local ahora se resuelven en el método en muchos más idiomas. Cuando el código hace const logger = new Logger(); logger.log(); (o su equivalente), CodeGraph infiere el tipo de variable local a partir de su declaración o inicializador y vincula la llamada al método correcto, por lo que estas llamadas ahora aparecen en las llamadas, el radio de impacto/explosión y los seguimientos de flujo codegraph_explore en lugar de descartarse. Anteriormente sólo C++ manejaba esto; ahora también cubre TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala y PHP. (#1108)
  • Las llamadas al método Ruby realizadas en un receptor (logger.log) ahora registran una ventaja en el método. Anteriormente, el indexador de Ruby mantenía solo el receptor y descartaba el nombre del método, por lo que un método llamado a través de una variable u objeto no tenía personas que llamaban registradas y faltaba en el radio de impacto/explosión y en los rastros de flujo; Combinado con la inferencia de tipo de variable local anterior, logger = Logger.new; logger.log ahora se vincula a Logger#log. Las llamadas a un método de clase (Foo.bar) y a la construcción de un objeto (Foo.new) también se siguen registrando. (#1110)
  • La misma resolución de llamada a método de variable local ahora se extiende a Lua, Luau, R y Pascal/Delphi. Un método invocado a través de un local (Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log() o Pascal var lg: TLogger; ... lg.Log) ahora se vincula al método correcto en lugar de descartarse. (#1112)

Correcciones

  • La indexación de un proyecto grande ya no se cancela a la mitad con el mensaje "El hilo principal no responde: se cancela el proceso bloqueado". El organismo de control de seguridad que detiene un índice realmente atascado estaba confundiendo un trabajo lento pero normal con un bloqueo: en un repositorio grande, vincular referencias y relaciones entre archivos puede ejecutarse legítimamente durante un tiempo, y ese trabajo ahora produce rendimientos regulares para que el organismo de control pueda distinguir el progreso real de un verdadero bloqueo. Los proyectos que anteriormente no pudieron finalizar codegraph init / codegraph index (y tuvieron que recurrir a CODEGRAPH_NO_WATCHDOG=1) ahora se completan normalmente, mientras que un proceso genuinamente colgado todavía está atrapado. Gracias @zmcrazy, @YoungLiao y @GeeLab-Mob por los informes. (#1091)
  • En Windows, una ventana de consola ya no parpadea brevemente cuando CodeGraph se ejecuta como servidor MCP en segundo plano. Cuando el lanzador npm iniciaba el tiempo de ejecución del paquete (lo que ocurre cada vez que un editor inicia el servidor o se vuelve a conectar después de que el demonio se apaga) y durante su paso de autocuración que extrae un paquete de plataforma faltante, Windows aparecía una ventana de consola negra (conhost) por un momento. Ambos ahora se inician ocultos, coincidiendo con el comportamiento del demonio; el paso de apertura del navegador de codegraph login se reforzó de la misma manera. Gracias @luoyerr por el informe y el análisis de la causa raíz. (#1092)
  • Las declaraciones directas de C++ ya no desplazan la definición de clase real. Una declaración directa class Foo;, común en grandes bases de código de C++ y Unreal Engine, donde una clase muy utilizada se declara anticipadamente en docenas de encabezados, se indexaba como su propio nodo de clase cada vez que aparecía. Entonces, explorar esa clase arrojó principalmente sitios de declaración directa, e incluso podría elegir uno de ellos como representante del radio de explosión, enterrando la definición real y sus miembros y llamadores. Las declaraciones directas sin cuerpo ahora se omiten para C y C++, exactamente como ya lo eran las estructuras y enumeraciones declaradas hacia adelante, por lo que solo se indexa la definición real. Los lenguajes donde una clase sin cuerpo es una definición completa, como class Empty y Scala de Kotlin, no se ven afectados. Gracias @luoyxy por el informe y el análisis de la causa raíz. (#1093)
  • Los métodos de C++ que devuelven una referencia y los operadores de conversión definidos por el usuario ahora están indexados con sus nombres correctos. Un captador en línea como const FGameplayTagContainer& GetActiveTags() const (en todas partes de los encabezados de Unreal Engine) se indexó como & GetActiveTags() const en lugar de GetActiveTags, y un operador de conversión como operator EALSMovementState() const mantuvo su () const final en lugar de leer operator EALSMovementState. En ambos casos, el nombre confuso significaba que no se podía encontrar el símbolo por nombre y quienes lo llamaban no estaban vinculados. Ambos ahora se leen claramente, coincidiendo con la forma en que ya funcionaban los métodos de devolución de puntero y de devolución de valor. (#1096)
  • Las funciones de C++ escritas con una macro de especificador en línea antes del tipo de retorno ahora están indexadas correctamente. En Unreal Engine, los ayudantes en línea se escriben comúnmente FORCEINLINE FString GetEnumerationToString(...); la macro FORCEINLINE hizo que el analizador leyera el tipo de retorno como parte del nombre de la función (FString GetEnumerationToString en lugar de GetEnumerationToString) y perdiera el tipo de retorno real, por lo que la función no se pudo encontrar por nombre y sus llamadores no estaban vinculados. CodeGraph ahora reconoce las macros en línea estándar de Unreal (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), por lo que se capturan tanto el nombre como el tipo de retorno. (#1100)
  • La misma recuperación de nombre de función ahora cubre macros en línea de bibliotecas C++ comunes de terceros, no solo Unreal Engine, incluidos pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE) y ALWAYS_INLINE/FORCE_INLINE genéricos. Las funciones decoradas con estos ahora están indexadas con sus nombres reales. En un gran proyecto de Unreal que vende estas bibliotecas, esto limpió la gran mayoría de los nombres de funciones confusos restantes. (#1101)
  • Los nombres de funciones de C++ ahora se recuperan incluso cuando están decorados con una macro que CodeGraph no conoce específicamente. Una función escrita SOME_LIBRARY_MACRO ReturnType doWork(...) anteriormente tenía la macro o el tipo de retorno absorbido en su nombre siempre que la macro no era reconocida por CodeGraph; ahora el nombre real (doWork) se recupera independientemente de la macro, por lo que se puede encontrar y las personas que lo llaman se vinculan; no se necesita configuración por biblioteca. La lista de macros reconocidas también se amplió (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson) para que capturen adicionalmente el tipo de devolución. Esto solo limpia un nombre ya confuso y está limitado a C y C++, por lo que los nombres comunes (y lenguajes como Kotlin y Scala donde los identificadores pueden contener espacios legítimamente) no se ven afectados. (#1102)
  • El conjunto de bibliotecas de C++ cuyas macros se reconocen para una recuperación completa del tipo de retorno se amplió mucho más allá de Unreal Engine; ahora abarca Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite y las convenciones de llamada comunes de Windows (por lo que HRESULT WINAPI CreateThing(...) indexa como CreateThing que regresa). HRESULT). Las funciones de las bibliotecas que no están en la lista aún recuperan su nombre automáticamente; al aparecer en la lista se recupera adicionalmente el tipo de devolución. (#1103)
  • Los resultados del recorrido del gráfico y del radio de explosión ya no disminuyen ni cuentan mal las relaciones en un puñado de casos extremos. Cuando se puede llegar a un símbolo por más de una ruta, una consulta de radio de impacto/explosión podría omitir una dependencia directa entre dos símbolos que ya estaban vinculados de otra manera; Por separado, el recorrido del gráfico de nivel inferior utilizado por la biblioteca API podría mantener solo una de varias relaciones entre el mismo par de símbolos (por ejemplo, un símbolo que llama y hace referencia a otro), contar dos veces a una persona que llama a través de dos sitios de llamadas diferentes o devolver un poco más de resultados que el límite de tamaño solicitado en un símbolo muy conectado. Estos eran de larga data y en su mayoría estaban enmascarados por la deduplicación posterior, por lo que los resultados de las consultas diarias no se vieron afectados en gran medida, pero el recorrido ahora devuelve el conjunto completo y correctamente delimitado. Gracias @inth3shadows por los informes precisos y rastreados individualmente. (#1086, #1087, #1088, #1089, #1090)
  • Las llamadas a métodos a clases con el mismo nombre en archivos diferentes ahora se resuelven con la definición correcta. Si cada uno de dos archivos declarara, digamos, una clase Logger con su propio método log(), se podría vincular una llamada a cualquier definición que estuviera indexada primero, por lo que una llamada en un archivo apuntaba erróneamente a la clase en otro, mezclando las llamadas de ese método y el radio de explosión. Esto afectó a las llamadas escritas como obj.log(), Logger.log() y Logger::log() en muchos lenguajes, incluidos C++, Python, TypeScript, Java, C# y Rust. Cuando el nombre de un método es ambiguo, CodeGraph ahora prefiere la definición en el archivo de llamada (el destino correcto en el caso común), mientras que las llamadas de Java/Kotlin que un import ya está anclado a otro archivo no se ven afectadas. Gracias @inth3shadows por la reproducción mínima y el análisis de causa raíz. (#1079)

codegraph v1.2.0

[1.2.0] - 2026-07-02

New Features

  • Method calls made through a local variable now resolve to the method in many more languages. When code does const logger = new Logger(); logger.log(); (or the equivalent), CodeGraph infers the local variable's type from its declaration or initializer and links the call to the right method — so these calls now show up in callers, impact/blast-radius, and codegraph_explore flow traces instead of being dropped. Previously only C++ handled this; it now also covers TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala, and PHP. (#1108)
  • Ruby method calls made on a receiver (logger.log) now record an edge to the method. Previously the Ruby indexer kept only the receiver and discarded the method name, so a method called through a variable or object had no recorded callers and was missing from impact/blast-radius and flow traces; combined with the local-variable type inference above, logger = Logger.new; logger.log now links to Logger#log. Calls to a class method (Foo.bar) and object construction (Foo.new) are still recorded too. (#1110)
  • The same local-variable method-call resolution now extends to Lua, Luau, R, and Pascal/Delphi. A method invoked through a local — Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log(), or Pascal var lg: TLogger; ... lg.Log — now links to the right method instead of being dropped. (#1112)

Fixes

  • Indexing a large project no longer gets killed partway through with a "Main thread unresponsive — killing the wedged process" message. The safety watchdog that stops a genuinely stuck index was mistaking slow-but-normal work for a hang: on a big repo, linking up references and cross-file relationships can legitimately run for a while, and that work now regularly yields so the watchdog can tell real progress from a true stall. Projects that previously failed to finish codegraph init / codegraph index (and had to fall back to CODEGRAPH_NO_WATCHDOG=1) now complete normally, while a genuinely hung process is still caught. Thanks @zmcrazy, @YoungLiao, and @GeeLab-Mob for the reports. (#1091)
  • On Windows, a console window no longer briefly flashes when CodeGraph runs as a background MCP server. When the npm launcher started the bundled runtime — which happens every time an editor starts the server or reconnects after the daemon idles out — and during its self-heal step that extracts a missing platform bundle, Windows would pop up a black console (conhost) window for a moment. Both now launch hidden, matching how the daemon already behaved; the browser-open step of codegraph login was hardened the same way. Thanks @luoyerr for the report and root-cause analysis. (#1092)
  • C++ forward declarations no longer crowd out the real class definition. A class Foo; forward declaration — common in large C++ and Unreal Engine codebases, where a heavily used class is forward-declared across dozens of headers — was indexed as its own class node every time it appeared. So exploring that class returned mostly forward-declaration sites, and could even pick one of them as the representative for blast-radius, burying the actual definition and its members and callers. Bodiless forward declarations are now skipped for C and C++, exactly as forward-declared structs and enums already were, so only the real definition is indexed. Languages where a class with no body is a complete definition — such as Kotlin's class Empty and Scala — are unaffected. Thanks @luoyxy for the report and root-cause analysis. (#1093)
  • C++ methods that return a reference, and user-defined conversion operators, are now indexed under their correct names. An inline getter like const FGameplayTagContainer& GetActiveTags() const — everywhere in Unreal Engine headers — was indexed as & GetActiveTags() const instead of GetActiveTags, and a conversion operator like operator EALSMovementState() const kept its trailing () const instead of reading operator EALSMovementState. In both cases the garbled name meant you couldn't find the symbol by name and its callers weren't linked. Both now read cleanly, matching how pointer-returning and value-returning methods already worked. (#1096)
  • C++ functions written with an inline-specifier macro before the return type are now indexed correctly. In Unreal Engine, inline helpers are commonly written FORCEINLINE FString GetEnumerationToString(...); the FORCEINLINE macro made the parser read the return type as part of the function's name (FString GetEnumerationToString instead of GetEnumerationToString) and lose the real return type, so the function couldn't be found by name and its callers weren't linked. CodeGraph now recognizes the standard Unreal inline macros (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), so both the name and the return type are captured. (#1100)
  • The same function-name recovery now covers inline macros from common third-party C++ libraries, not just Unreal Engine — including pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE), and generic ALWAYS_INLINE / FORCE_INLINE. Functions decorated with these are now indexed under their real names. On a large Unreal project vendoring these libraries this cleaned up the large majority of remaining function-name garbling. (#1101)
  • C++ function names are now recovered even when decorated with a macro CodeGraph doesn't specifically know about. A function written SOME_LIBRARY_MACRO ReturnType doWork(...) previously had the macro or return type absorbed into its name whenever the macro wasn't one CodeGraph recognized; now the real name (doWork) is recovered regardless of the macro, so it's findable and its callers link — no per-library configuration needed. The recognized-macro list was also broadened (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson) so those additionally capture the return type. This only ever cleans up an already-garbled name and is limited to C and C++, so ordinary names — and languages like Kotlin and Scala where identifiers can legitimately contain spaces — are unaffected. (#1102)
  • The set of C++ libraries whose macros are recognized for full return-type recovery was expanded well beyond Unreal Engine — now spanning Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite, and the common Windows calling conventions (so HRESULT WINAPI CreateThing(...) indexes as CreateThing returning HRESULT). Functions from libraries not on the list still get their name recovered automatically; being listed additionally recovers the return type. (#1103)
  • Graph traversal and blast-radius results no longer drop or miscount relationships in a handful of edge cases. When a symbol could be reached by more than one path, an impact/blast-radius query could leave out a direct dependency between two symbols that were already linked another way; separately, the lower-level graph traversal used by the library API could keep only one of several relationships between the same pair of symbols (for example a symbol that both calls and references another), count a caller reached through two different call sites twice, or return slightly more results than the requested size limit on a very highly-connected symbol. These were long-standing and mostly masked by later de-duplication, so day-to-day query results were largely unaffected, but the traversal now returns the complete, correctly-bounded set. Thanks @inth3shadows for the precise, individually-traced reports. (#1086, #1087, #1088, #1089, #1090)
  • Method calls to same-named classes in different files now resolve to the right definition. If two files each declared, say, a Logger class with its own log() method, a call could be linked to whichever definition happened to be indexed first — so a call in one file wrongly pointed at the class in another, mixing up that method's callers and blast radius. This affected calls written as obj.log(), Logger.log(), and Logger::log() across many languages, including C++, Python, TypeScript, Java, C#, and Rust. When a method name is ambiguous, CodeGraph now prefers the definition in the calling file itself — the correct target in the common case — while Java/Kotlin calls that an import already pins to another file are unaffected. Thanks @inth3shadows for the minimal repro and root-cause analysis. (#1079)
