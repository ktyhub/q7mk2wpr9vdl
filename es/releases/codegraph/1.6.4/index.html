codegraph v1.6.4

códice v1.6.4

[1.6.4] - 2026-11-20

Destacados

  • Las preguntas pequeñas cuestan menos. Pregúntele a su agente qué es una función o constante, o quién la llama, y codegraph_explore ahora responde con la definición y cada línea que la utiliza, en lugar de una respuesta larga sobre archivos relacionados.
  • Respuestas más rápidas en Claude Code. El enlace de solicitud ahora pregunta al servidor CodeGraph que ya se está ejecutando para su proyecto en lugar de cargar el índice nuevamente en cada solicitud, lo que es más importante en proyectos grandes, y codegraph impact vuelve a ser tan rápido como lo era en 1.6.2.
  • Más seguro en una computadora compartida. Cada sesión de agente ahora verifica que el servidor en segundo plano al que se conecta se ejecute como usted antes de enviarle algo.
  • Más de su código en el gráfico. Las rutas Elysia (Bun), PHP incluye las creadas desde la raíz del servidor web o la propia carpeta del archivo, los constructores primarios Dart 3.13 y la nueva sintaxis Kotlin ahora se leen, y las rutas ASP.NET Core reciben el nombre de la forma en que ASP.NET las sirve.
  • Enlaces más precisos. Docenas de correcciones ayudan a que las llamadas lleguen al código que quieren decir, sobre todo en JavaScript y TypeScript, Python, Rust, C#, PHP y Java, y codegraph affected ya no selecciona pruebas en el otro lado de una llamada HTTP, una cola o un evento a menos que pase --cross-tier.
  • Menos comandos atascados. Un git add o una confirmación ya no falla con "index.lock: El archivo existe" mientras CodeGraph se sincroniza, un archivo cuyo análisis nunca termina ya no impide que codegraph init o la sincronización finalice, y un servidor cuya carpeta de proyecto se eliminó ahora se apaga.
  • Actualización: vuelva a indexar sus proyectos con codegraph index después de esta versión. Muchas de estas correcciones se escriben durante la indexación, y codegraph status y su agente le informan cuándo se creó un índice con una versión anterior.

Seguridad

  • En una computadora compartida con otros usuarios, cada sesión de agente ahora verifica que el servidor en segundo plano CodeGraph al que se conecta se ejecute como usted antes de enviarle algo, y sirve la sesión en sí cuando el servidor no puede probarlo, por lo que otro usuario ya no puede reemplazar a su servidor para leer las consultas de su agente o darle respuestas inventadas. Gracias @aidenpan0x por señalarlo.

Nuevas características

  • El enlace de solicitud de Claude Code ahora obtiene su contexto del servidor CodeGraph que ya se está ejecutando para su proyecto en lugar de cargar el índice nuevamente en cada solicitud, por lo que las solicitudes estructurales se responden antes, sobre todo en proyectos grandes; sin ningún servidor en ejecución, uno que esté ocupado o uno que no pueda probar que se ejecuta como usted, el gancho lo resuelve por sí solo como antes. Gracias @aidenpan0x por el informe, las medidas y la solicitud de extracción. (#3284)
  • Los backends de Elysia (Bun) ahora tienen sus rutas HTTP en el gráfico, nombradas por la ruta completa que toma una solicitud, con los prefijos de new Elysia({ prefix }), .group() y .use() en otro archivo incluidos y vinculados a sus controladores, por lo que codegraph_explore puede seguir una solicitud desde su ruta hasta su código. Gracias @ChampPABA por el informe. (#3255)
  • PHP incluye creado desde la raíz del servidor web, como require $_SERVER['DOCUMENT_ROOT'] . '/inc/header.php', ahora se vincula a su archivo: CodeGraph determina qué carpeta sirve el servidor desde donde las rutas de acceso nombran los archivos, no vincula nada cuando no lo resuelven en lugar de adivinar, y toma "webRoot": "public" en codegraph.json (o "." para la raíz del proyecto) cuando prefiere nombrarlo usted mismo. Gracias @craftya por el informe. (#3298)
  • Kotlin ahora se lee con una versión más nueva de su gramática, por lo que el código que solía leerse mal, como una clase anotada cuyos métodos aparecían como funciones de nivel superior, una clase que delega by a otro objeto, o una sintaxis más nueva como guardias when y campos de respaldo explícitos, ahora tiene sus clases, funciones y llamadas en el gráfico al que pertenecen. (#3410)
  • codegraph_explore ahora responde a una pregunta sobre un símbolo, como "¿quién llama a toValidURL?" o "¿qué es MAX_RETRIES?", con la fuente de ese símbolo y cada línea que lo usa, cada una con la función en la que se encuentra y el texto de la línea, en lugar de llenar toda su respuesta con archivos que solo comparten palabras con el nombre, por lo que estas pequeñas preguntas cuestan menos y no dejan nada que buscar después. Gracias @GeorgeTaveras1231 por las medidas. (#3407)

Correcciones

Configuración, el servidor en segundo plano y el CLI

  • codegraph affected ya no selecciona pruebas en el otro lado de una llamada HTTP, una cola o un evento, como las especificaciones de una aplicación Angular para un cambio en el controlador Spring al que llama, ya que esas pruebas se burlan de ese límite; pase --cross-tier para incluirlos. Gracias @jotder por el informe. (#3320)
  • CodeGraph ya no toma el bloqueo de índice de git mientras revisa su repositorio en busca de cambios, por lo que un git add en un enlace previo a la confirmación, una confirmación o un checkout que se ejecuta mientras CodeGraph se sincroniza ya no falla con "index.lock: El archivo existe". Gracias @iamclaudia-ai por el informe. (#3295)
  • codegraph impact y codegraph_impact vuelven a ser tan rápidos como lo eran en 1.6.2, con los mismos resultados: 1.6.3 leyó los dependientes de cada símbolo de una manera que ralentizó cada paso del recorrido. Gracias @inth3shadows por el informe y la solución, y @ Marcos-199-GitHub por el n.° 3285. (#3248)
  • Cuando se detiene la sincronización de actualización del servidor CodeGraph en un proyecto grande porque las llamadas a la herramienta que está sirviendo evitan que su registro de escritura anticipada se reduzca, ahora espera antes de volver a intentarlo, un poco más cada vez, en lugar de comenzar de nuevo cada segundo mientras sigues trabajando. Gracias @kiliman por el informe. (#3273)
  • Un servidor CodeGraph MCP iniciado en una carpeta sin índice ya no inicia su proceso de vigilancia de bloqueo independiente hasta que la sesión llama por primera vez a una herramienta o abre un proyecto, por lo que las sesiones que solo enumeran las herramientas, ya que muchos hosts las abren, usan menos memoria. Gracias @AiurArtanis por el informe y @johnhldiver-beep por el n.° 3257. (#3250)
  • Un servidor CodeGraph cuya carpeta de proyecto se elimina, como un árbol de trabajo git eliminado, ahora sale en aproximadamente medio minuto, cerrando su observador de archivos y saliendo de las listas de servidores codegraph daemon, en lugar de ejecutarse hasta que finalice su última sesión y se agote el tiempo de espera. En Windows, también deja de evitar que se eliminen los archivos de índice de esa carpeta. Gracias @deniskern por el informe y @johnhldiver-beep por el n.° 3259. (#3245)
  • La ejecución de codegraph upgrade desde su carpeta de inicio ya no trata la configuración de todo el usuario de sus agentes como un proyecto: el servidor CodeGraph del Cursor sigue el espacio de trabajo que abre en lugar de estar anclado a su carpeta de inicio, y no se escribe ninguna sección de CodeGraph en ~/AGENTS.md, ~/GEMINI.md o ~/QWEN.md. Gracias @shoma-endo por el informe y @b84330808 y @LuisAlbertoMK. (#3234)
  • En OpenCode, las instrucciones de CodeGraph, tanto las que envía su servidor como la sección que codegraph install escribe en el AGENTS.md de OpenCode, ahora nombran sus herramientas de la forma en que OpenCode las enumera (codegraph_codegraph_explore), para que el agente ya no llame a un nombre de herramienta que no existe. Gracias @expiren por el informe. (#1267)
  • codegraph init en un proyecto cuya última ejecución de índice se eliminó o falló parcialmente ahora dice que el índice está incompleto y que se debe ejecutar codegraph index, en lugar de "Ya inicializado", que se lee como una configuración funcional. Gracias @maxmilian por el reporte y @LuisAlbertoMK. (#3228)
  • codegraph callers, callees y impact ahora advierten cuando un archivo en la respuesta cambió en el disco después de su última indexación, como ya lo hicieron codegraph node y explore, por lo que un número de línea desplazado ya no se lee como actual. Con --json, la advertencia va a stderr y la respuesta enumera esos archivos en changedOnDisk. Gracias @arifpambudi242 por el informe y @mohitdixit02. (#3260)
  • codegraph status ahora informa ediciones, archivos nuevos y eliminaciones en fuentes ignoradas por git que codegraph.json include incorpora al índice, en lugar de actualizar el índice hasta que una sincronización los detecte. Gracias @mixxer por el informe y la solicitud de extracción. (#3086)
  • En Linux y macOS, cuando el sistema cierra CodeGraph con una señal, como cuando se queda sin memoria durante codegraph init o codegraph index, el comando ahora dice qué señal y sale como lo haría un shell (137 para SIGKILL), en lugar de salir 1 sin mensaje. Gracias @inth3shadows por el informe y @johnhldiver-beep. (#3277)
  • La solicitud de una prueba Spring o Laravel ahora está vinculada solo a una ruta de su propia aplicación, no a la ruta de un servidor JavaScript o TypeScript que coincide con la ruta, por lo que codegraph affected ya no selecciona pruebas Java o PHP para un cambio en su código web. Gracias @jotder por el informe. (#3320)

Indexación y sincronización

  • codegraph sync y el observador de archivos ahora siguen una edición que agrega, elimina o redirecciona un miembro de un objeto exportado, como export const api = { getUser, saveUser }, por lo que una llamada como api.saveUser() en un archivo editado no toca los enlaces al nuevo miembro o al objeto, como lo hace un índice nuevo. Gracias @inth3shadows por el informe. (#3015)
  • Un archivo cuyo análisis nunca finaliza, como un archivo .tsx con un atributo JSX medio escrito, ya no impide que codegraph init salga ni deja a codegraph sync y al observador de archivos girando con la CPU completa: su análisis ahora se detiene en el límite de tiempo de análisis del archivo y el archivo aparece como un análisis cuyo tiempo de espera se agotó. Gracias @inth3shadows por el informe. (#3274)
  • Después de actualizar, codegraph status y la primera respuesta de CodeGraph en cada sesión del agente ahora marcan un proyecto indexado por 1.6.3 o anterior como desactualizado, ya que esta versión lee el código que faltan esos índices, como los constructores primarios de Dart, las rutas de Elysia, PHP incluye construido a partir de __DIR__ y los métodos de un objeto export default; ejecute codegraph index en cada proyecto para reconstruirlo. (#3411)

JavaScript y TypeScript

  • Los controladores de eventos JavaScript y TypeScript registrados con on() ahora están vinculados solo desde el código que se emite en el mismo emisor y al controlador definido donde están registrados, por lo que dos módulos que mantienen cada uno su propio emisor y usan el mismo nombre de evento ya no se cruzan. Gracias @inth3shadows por el informe. (#2973)
  • En JavaScript, los métodos escritos de la manera clásica, Ctor.prototype.m = function () {…} y un Ctor.m = function () {…} estático, ahora están indexados como métodos de su constructor, y las funciones de un objeto module.exports = {…} como exportaciones de ese módulo, por lo que this.m() dentro de ellos llega al m del constructor o del propio objeto en lugar de una función no relacionada con el mismo nombre en otro lugar. Gracias @inth3shadows por el informe. (#2966)
  • En JavaScript y TypeScript, las funciones de un objeto que un módulo exporta de forma predeterminada, como una tienda Vuex dividida en actions.js, getters.js y mutations.js (export default { fetchUser() {…} }), ahora están indexadas como default::fetchUser, por lo que codegraph_explore, node, query, callers y el impacto los encuentran y una llamada a través del la importación predeterminada del módulo, this.fetchUser() o Vuex dispatch('fetchUser') se vincula a ellos; un Vuex commit ahora siempre se vincula a una mutación y un dispatch a una acción. Gracias @ daniel-luan-tran por el informe. (#3393)
  • En JavaScript y TypeScript, this.findAll() en una clase que incluye un asistente importado del mismo nombre ahora se vincula al método propio de la clase en lugar del asistente importado. Gracias @inth3shadows por el informe. (#2954)
  • En JavaScript y TypeScript, una llamada escrita en this, como this.cast() o this.validate(), ya no enlaza con un const, un enlace require o una declaración de función que solo comparte su nombre, en el mismo archivo u otro, porque lo que alcanza la llamada es una propiedad del objeto.
  • En TypeScript, una llamada a un parámetro o local llamado como una importación, como stream.write() dentro de stream(c, async (stream) => …), ahora pasa por ese parámetro o local, y un método llamado a una función importada ya no se vincula a la función misma; El mismo error a través de require ya se solucionó en 1.6.3. Gracias @inth3shadows por el informe. (#2953)
  • En JavaScript y TypeScript, una llamada a un nombre que una función alrededor de la persona que llama declara para sí misma, como un ayudante que llama una función de flecha interna, ahora se vincula a esa declaración local en lugar de la importación del archivo del mismo nombre. Gracias @inth3shadows por el informe. (#2949)
  • En JavaScript y TypeScript, una llamada a un ayudante declarado dentro de un bloque describe(…), o cualquier otra devolución de llamada, ahora se vincula al ayudante que ese bloque declara en lugar de uno con el mismo nombre de otro bloque que se encuentra más cerca. Gracias @inth3shadows por el informe. (#2944)
  • En JavaScript y TypeScript, una llamada dentro de un pliego, como <input {...register('email')} /> con register tomado de useForm(), ya no se vincula a una función de proyecto no relacionada que comparte el nombre. Gracias @inth3shadows por el informe. (#2962)
  • En JavaScript y TypeScript, un espacio de nombres de módulo que otro módulo pasa por su nombre, como import { z } from 'zod' o import * as z from './external'; export { z } de zod, o export * as ns from './schemas', ahora lleva a z.string() a lo que ese módulo exporta, como lo hace import * as z, en lugar de a un método con el mismo nombre en otros lugares. Gracias @inth3shadows por el informe. (#2951)
  • En JavaScript y TypeScript, una importación a través de un barril de varias líneas export * ahora se vincula al módulo que exporta el nombre en sí, la línea que aparezca primero, en lugar de un método con el mismo nombre de un objeto que exporta otro módulo. Gracias @inth3shadows por el informe. (#3233)
  • En JavaScript y TypeScript, un método llamado en una variable que completa una llamada de biblioteca, como const root = createRoot(el) de react-dom, net.createServer() o canvas.getContext('2d'), ya no se vincula al único método de proyecto que comparte su nombre. Gracias @inth3shadows por el informe. (#2947)
  • En TypeScript, un método llamado en una variable que completa la fábrica estática de una clase, como const writer = DatabaseConnection.initialize(path), ahora se vincula al método de la clase que la fábrica dice que devuelve, en lugar de una clase adivinada a partir del nombre de la variable. Gracias @inth3shadows por el informe. (#2946)
  • En TypeScript, una llamada a través de una propiedad de tipo función de una interfaz, como matcher.snapshot(), ya no se vincula al método de una clase no relacionada con el mismo nombre; una clase que implementa la interfaz, o la construye, todavía está vinculada. Gracias @inth3shadows por el informe. (#3035)
  • En JavaScript y TypeScript, una llamada a dos o más campos profundos de this, como this.cache.list.push(1) o this.extractor.functionTypes.includes(type), ya no se vincula a un método de proyecto no relacionado llamado como el propio push, includes, has o set de JavaScript, ni a una propiedad que simplemente comparte el nombre. Gracias @inth3shadows por el informe. (#2948)
  • En JavaScript y TypeScript, una entrada workspaces que apunta fuera del proyecto, como "../shared" en package.json o pnpm-workspace.yaml, ya no hace que el paquete de esa carpeta cuente como parte del proyecto, por lo que una llamada a través de una importación del mismo ya no está vinculada a una función suya no relacionada con el mismo nombre. Gracias @bompus por el informe y @johnhldiver-beep. (#3093)
  • En JavaScript y TypeScript, una llamada a una variable local declarada después de otra en la misma declaración, como let n = 0, ob = make(), o junto a un valor predeterminado en una desestructuración, como const { ob = make() } = o, se vincula nuevamente cuando una variable del mismo nombre fuera de la función contiene un tipo de biblioteca, como lo hacía antes de 1.6.3. Gracias @inth3shadows por el informe y @mohitdixit02. (#3293)
  • En JavaScript, una llamada a un miembro que un módulo requerido de su proyecto no tiene, como utils.missing() después de const utils = require('./utils'), ya no se vincula a un método de clase no relacionada con ese nombre. Gracias @inth3shadows por el informe y @johnhldiver-beep. (#3272)
  • Una llamada fetch o HTTP-client al API de otra empresa, como fetch('https://api.github.com/users/…'), ya no enlaza con la ruta de su propio servidor con la misma ruta; una llamada a localhost, a un host que su código complete o mediante un enlace URL base de client. Gracias @inth3shadows por el informe y @johnhldiver-beep. (#2974)
  • En JavaScript y TypeScript, una llamada o new de un global, como parseInt(…), new Response(…) o new URL(…), en un módulo que no importa ese nombre ya no se vincula a una exportación con el mismo nombre de otro archivo en su proyecto. Gracias @inth3shadows por el informe. (#3238)
  • En JavaScript, un require() de una carpeta por una ruta relativa, como require('..') de las pruebas de un paquete, ahora carga el archivo con el nombre package.json de la carpeta como main, como lo hace Node, por lo que llama a través del enlace a la función que exporta el archivo. Antes, no se seguía una carpeta sin index.js y la llamada se vinculaba a la variable que contenía el resultado require(); en Fastify, el Fastify() de cada prueba está vinculado a su propio archivo de prueba. Gracias @inth3shadows por el informe. (#2964)
  • En JavaScript, una variable que contiene lo que devuelve la función de un módulo requerido, como const app = require('./app')(), ya no cuenta como el módulo en sí, por lo que una llamada como app.listen() ya no se vincula a la función de fábrica del módulo y se vincula al método de la clase que la fábrica devuelve cuando se conoce. Gracias @inth3shadows por el informe. (#2964)
  • En JavaScript y TypeScript, un nombre importado de un paquete que su package.json no incluye pero que su proyecto ha instalado, como import { useForm } from 'react-hook-form' elevado a la raíz de un monorepo node_modules, ya no se vincula a una función no relacionada con el mismo nombre en otra parte de su proyecto (#3271). Vuelva a indexar los proyectos JavaScript y TypeScript después de la actualización.

Python

  • En Python, import time ya no vincula el archivo de importación a una función de proyecto que se llama time, por lo que dicha función deja de enumerar cada archivo que importa el módulo de biblioteca estándar entre sus llamadores y en su impacto. Lo mismo ocurre con json, copy, random, logging y cualquier otro módulo, y con una variable alternativa como brotli = None junto a un import brotli protegido. Gracias @inth3shadows por el informe. (#3239)
  • En Python, una llamada a una función o método declarado con typing.overload, como command y prompt de click, ahora se vincula al def que se ejecuta en lugar del primer código auxiliar de @overload, por lo que la implementación muestra a sus llamadores y una ruta de llamada continúa a través de él. Un código auxiliar sin implementación debajo, como en un Protocol, sigue siendo el objetivo, y el overload de otra biblioteca cuyos cuerpos se ejecutan se deja solo. Gracias @inth3shadows por el informe y @nilotpal-n7. (#2963)
  • En Python, una llamada como self.create_app() en un atributo que contiene un invocable ya no se vincula a una función o variable con el mismo nombre en otro archivo, ni, cuando la clase establece ese atributo, al método de otra clase con ese nombre, por lo que la carga de la aplicación de flask deja de mostrar una aplicación de ejemplo como su destinatario. Un método que la clase tiene, hereda o una subclase anula aún vincula, al igual que una función que la clase almacena con ese nombre. Gracias @inth3shadows por el informe y @nilotpal-n7. (#2958)
  • En Python, un incorporado escrito sin formato, como raise TimeoutError(…), class Bad(ValueError) o sorted(rows), ya no se vincula a una clase de proyecto o función con ese nombre en un archivo que el código no importa, por lo que el propio TimeoutError de un proyecto deja de recopilar cada archivo que genera el incorporado. Un nombre que el archivo define o importa todavía vincula. Gracias @inth3shadows por el informe. (#3232)
  • En Python, una llamada de un nombre al código que lo rodea se vincula a sí mismo, como un flat = lambda … local, un parámetro, un bucle o variable de comprensión, un parámetro lambda, o un parámetro local o de una función adjunta, ya no se vincula a una función o variable a nivel de módulo de ese nombre, ya sea que esté en el mismo archivo o en uno que el código nunca importa. Gracias @inth3shadows por los informes y @johnhldiver-beep. (#3037, #3230, #3231)
  • En Python, un local construido a partir de una clase a través de su módulo, como client = httpx.AsyncClient(), o vinculado por with o async with … as client, ahora tiene esa clase, por lo que client.get() se vincula a AsyncClient.get en lugar del método de una clase nombrada como la variable, como Client.get. Un with cuya clase entrega algo más de __enter__, y una clase de un módulo fuera de su proyecto, aún no le dan ningún tipo al local. Gracias @inth3shadows por el informe y @nilotpal-n7. (#2957)
  • En Python, un método llamado en un enlace local desde una llamada, como made = make(q) o s = store.stage(), ahora va por el tipo que la función o método llamado declara que devuelve: un Path, un str u otra clase externa a su proyecto no vincula nada, donde cualquier método de proyecto que compartiera el nombre podría hacerlo, y una de sus propias clases vincula su propio método incluso cuando otras clases tienen uno con ese nombre. Gracias @inth3shadows por los informes y @johnhldiver-beep. (#3038, #3240)
  • En Python, un from x import name escrito dentro de una función ahora se aplica solo a esa función, por lo que las llamadas de name en el resto del archivo llegan al propio def name del archivo en lugar de a la función importada, como espera un contenedor que importa el original que envuelve. Gracias @inth3shadows por el informe. (#3229)

Java, Kotlin, C# y ASP.NET

  • En Java, cuando dos paquetes declaran una clase con el mismo nombre, una llamada estática, una llamada a un nuevo objeto o una llamada a través de una variable ahora llega a la que el archivo que llama puede ver, incluso a través de una importación con comodines, y una llamada escrita con el paquete, como com.x.b.Util.log(…), llega a la clase de ese paquete. Gracias @inth3shadows por los informes y @johnhldiver-beep. (#2976, #3290, #3291)
  • En Kotlin, una extensión declarada en un alias de importación de un tipo de biblioteca, como fun DeclAlias.pad() después de import androidx.compose.ui.Modifier as DeclAlias, ahora vincula desde llamadas de ese tipo, independientemente del nombre con el que lo importe el archivo de llamada. Gracias @mixxer por el informe y la solicitud de extracción. (#3084)
  • En C#, un método llamado según lo que devuelve un método de la misma clase, como GetMailer().Send(), ahora se vincula al método del tipo que se declara que ese método devolverá. Gracias @Gobakabana por el informe. (#2906)
  • En ASP.NET Core, las rutas de atributos ahora se denominan de la forma en que ASP.NET las sirve: [controller] y [action] están completos, cada controlador usa su propio [Route] (o el de su controlador base), las rutas de ~/ son independientes y las acciones marcadas como [HttpHead], [HttpOptions] o [AcceptVerbs], con su propio [Route] o en una lista de atributos están ya no se pierde. Gracias @Gobakabana por el informe. (#2905)
  • En C#, un método de extensión ahora coincide con el tipo que toma su parámetro this, por lo que "hi".Shout() y mailer.Shout() alcanzan cada uno su propia extensión, y una llamada del método propio de una cadena ya no llega a una extensión de proyecto con el mismo nombre. Gracias @Gobakabana por el informe. (#2906)
  • En C#, un método llamado a través de ?. o !., como _mailer?.Send(), ahora se vincula al método del tipo de receptor. Gracias @Gobakabana por el informe. (#2906)

codegraph v1.6.4

[1.6.4] - 2026-11-20

Highlights

  • Small questions cost less. Ask your agent what a function or constant is, or who calls it, and codegraph_explore now answers with the definition and every line that uses it, instead of a long answer about related files.
  • Faster answers in Claude Code. The prompt hook now asks the CodeGraph server already running for your project instead of loading the index again on every prompt, which matters most in large projects, and codegraph impact is as fast as it was in 1.6.2 again.
  • Safer on a shared computer. Each agent session now checks that the background server it connects to runs as you before sending it anything.
  • More of your code in the graph. Elysia (Bun) routes, PHP includes built from the web server's root or the file's own folder, Dart 3.13 primary constructors and newer Kotlin syntax are now read, and ASP.NET Core routes are named the way ASP.NET serves them.
  • More accurate links. Dozens of fixes help calls reach the code they mean, most of all in JavaScript and TypeScript, Python, Rust, C#, PHP and Java, and codegraph affected no longer picks tests on the far side of an HTTP call, a queue or an event unless you pass --cross-tier.
  • Fewer stuck commands. A git add or commit no longer fails with "index.lock: File exists" while CodeGraph syncs, a file whose parse never ends no longer keeps codegraph init or sync from finishing, and a server whose project folder was deleted now shuts down.
  • Upgrading: re-index your projects with codegraph index after this release. Many of these fixes are written while indexing, and codegraph status and your agent both tell you when an index was built by an older version.

Security

  • On a computer shared with other users, each agent session now checks that the CodeGraph background server it connects to runs as you before sending it anything, and serves the session itself when the server can't prove it, so another user can no longer stand in for your server to read your agent's queries or feed it made-up answers. Thanks @aidenpan0x for pointing it out.

New Features

  • The Claude Code prompt hook now gets its context from the CodeGraph server already running for your project instead of loading the index again on every prompt, so structural prompts are answered sooner, most of all in large projects; with no server running, one that is busy, or one that can't prove it runs as you, the hook works it out itself as before. Thanks @aidenpan0x for the report, the measurements and the pull request. (#3284)
  • Elysia (Bun) backends now have their HTTP routes in the graph, named by the full path a request takes, with the prefixes of new Elysia({ prefix }), .group() and a .use() in another file included, and linked to their handlers, so codegraph_explore can follow a request from its route into your code. Thanks @ChampPABA for the report. (#3255)
  • PHP includes built from the web server's root, like require $_SERVER['DOCUMENT_ROOT'] . '/inc/header.php', now link to their file: CodeGraph works out which folder the server serves from where your includes' paths name files, links nothing when they don't settle it rather than guess, and takes "webRoot": "public" in codegraph.json (or "." for the project root) when you'd rather name it yourself. Thanks @artisanya for the report. (#3298)
  • Kotlin is now read with a newer version of its grammar, so code it used to misread, such as an annotated class whose methods showed up as top-level functions, a class that delegates by another object, or newer syntax like when guards and explicit backing fields, now has its classes, functions and calls in the graph where they belong. (#3410)
  • codegraph_explore now answers a question about one symbol, like "who calls toValidURL?" or "what is MAX_RETRIES?", with that symbol's source and every line that uses it, each with the function it sits in and the line's text, instead of filling its whole answer with files that only share words with the name, so these small questions cost less and leave nothing to search for afterwards. Thanks @GeorgeTaveras1231 for the measurements. (#3407)

  • CodeGraph no longer takes git's index lock while it checks your repository for changes, so a git add in a pre-commit hook, a commit or a checkout that runs while CodeGraph syncs no longer fails with "index.lock: File exists". Thanks @iamclaudia-ai for the report. (#3295)
  • codegraph impact and codegraph_impact are as fast as they were in 1.6.2 again, with the same results: 1.6.3 read each symbol's dependents in a way that slowed down every step of the walk. Thanks @inth3shadows for the report and the fix, and @Marcos-199-GitHub for #3285. (#3248)

  • A CodeGraph MCP server started in a folder with no index no longer starts its separate hang-watchdog process until the session first calls a tool or opens a project, so sessions that only list the tools, as many hosts open them, use less memory. Thanks @clayly for the report. (#3410)

PHP and Laravel

  • In PHP, a method called on a freshly built object, like (new SettingClient())->getSet(1), now links to the class the file's namespace and use imports name, or to a method it inherits, so these calls show up in callers and impact. Thanks @holysor for the report. (#3244)
  • In Laravel, a route written like [UserController::class, 'show'] now links to the controller the routes file imports, through a plain or aliased use, a group use, an imported namespace or a fully qualified name, instead of a same-named controller elsewhere or nothing. Thanks @inth3shadows for the reports and @johnhldiver-beep. (#2975, #3292)
  • In PHP, a method called in a different letter case than its declaration, like PriceConverter::CalcBasePrice(1) or $c->GetRate() for calcBasePrice and getRate, now links to that method, as PHP reads method names without regard to case, so those calls show up in callers and impact. Thanks @artisanya for the report and @johnhldiver-beep. (#3297)
  • In PHP code written for PHP 7 and older, a string offset in braces, like $code{0}, no longer makes the function or class around it disappear from the index with its calls credited to the file; it now reads like $code[0]. Thanks @artisanya for the report. (#3299)
  • In PHP, a require or include of a file inside a function or method now counts as that function depending on the file, so callers and impact follow code in the included file back to the function and its callers. Thanks @artisanya for the report. (#3296)
  • In PHP, an include built from the file's own directory, like require_once __DIR__ . '/inc/a.php' or dirname(__FILE__) . '/inc/b.php', now links to that file the way a plain require_once 'lib.php' does, and a path starting with ./ or ../ links only to the file named exactly, as PHP loads it, never one with .php added. Thanks @artisanya for the report and @inth3shadows. (#3298)

Rust

  • In Rust, a call through a module that a glob use brings in, like gzip::write() in a test module with use super::*, or that a use inside the function names, now links to that module's function again. Thanks @Egrn for the report and @mohitdixit02. (#3253)
  • In Rust, codegraph_explore's blast radius now recognizes unit tests in a #[cfg(test)] module or a tests.rs file, instead of reporting "no tests found" for the functions they test. Thanks @moogiemode for the report and @maxmilian. (#3265)
  • In Rust, a function or method passed as a value through its path, like g.map(Graph::counts) or .map(Self::helper), now counts in its callers and impact the way a function passed by name already did, linked only when the path names it for certain: never another type's method of the same name, and never a method of a trait implementation, since which one Rust uses there depends on the type of the argument. Thanks @Egrn for the report and @inth3shadows. (#3254)
  • In Rust, a call on a value whose type comes from outside your project, like an outside crate's builder chain or stdout.flush(), no longer links to one of your methods that only shares its name, such as your own impl Write's write and flush or an associated function like Graph::build(n), and Rules::default() on a #[derive(Default)] type no longer links to another type's default. Thanks @Egrn for the report. (#3252)
  • In Rust, a call written in the arguments of format!, println!, write!, assert_eq!, vec!, matches! or serde_json's json! now links to the function or method it calls, as the same call outside the macro does, and a variant in a matches! pattern now counts as a use of its enum. Thanks @Egrn for the report. (#3251)

Go, Swift, Dart, C and C++

  • A C++ .h header that only declares functions and extern variables, with no class, namespace or template in it, is now read as C++ when it uses a template type like CComPtr<IDiaDataSource>, a reference parameter like bstr_t& path or const qstring &name, or a default argument like int depth = 0, instead of as C, which dropped its symbols and warned "parse produced no symbols (tree has errors)". Thanks @sonyps5201314 for the report. (#3397)
  • In Swift, a type no longer picks up the inheritance of a type nested inside it, which linked a name used in the type to an unrelated type's nested type and put it in the wrong impact results. Thanks @bob-codedaptive for the report and @remote-controlled-man. (#3213)
  • In Go, a method called on new(T) or make(T) now links to that type's method, not a same-named method of another type that happened to be found first. Thanks @inth3shadows for the report. (#3237)
  • In Swift, an if or while whose condition is try await f() no longer breaks the method around it: the next member landed inside that method, and calls were recorded under names made of source text. Swift files are now read with a newer Swift grammar, which also parses more Swift 6 code without errors. Thanks @bob-codedaptive for the report. (#3212)
  • In Dart, a class declared with a Dart 3.13 primary constructor, like class Point(final int x, final int y) {…} or class const Foo({required final int a}), is now indexed under its own name with its members, where it had been named const or dropped with the rest of its file; Dart files are now read with a newer Dart grammar, which also parses dot shorthands and other recent Dart syntax without errors. Thanks @cutehackers for the report. (#3270)
