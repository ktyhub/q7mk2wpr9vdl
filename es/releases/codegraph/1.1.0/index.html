códice v1.1.0

[1.1.0] - 2026-06-23

Nuevas características

  • Claude Code: un gancho de carga frontal opcional hace que su agente busque CodeGraph automáticamente. Cuando hace una pregunta estructural: "cómo funciona X", "qué llama a Y", "rastrear el flujo de A a B", CodeGraph inyecta la fuente relevante y las rutas de llamada en el mensaje desde el principio, de modo que el agente responde desde el gráfico en lugar de buscar para reconstruirlo. Se le pregunta durante codegraph install (predeterminado sí; solo Claude Code, ya que es el agente con enlaces de aviso), codegraph uninstall lo elimina y codegraph upgrade lo activa para las configuraciones de Claude existentes. Es estrictamente aditivo y degradable (las indicaciones no estructurales y los proyectos no indexados se dejan en paz) y puede desactivarlo en cualquier momento sin desinstalarlo configurando CODEGRAPH_NO_PROMPT_HOOK=1.
  • Las acciones, mutaciones y captadores de la tienda Vue ahora están indexados como símbolos que puedes encontrar y leer. Ya sea que su tienda sea Vuex (objetos mutations / actions en un módulo) o Pinia, tanto el formulario de opciones (defineStore({ actions: { … } })) como el formulario de configuración (defineStore('id', () => { … }), donde las acciones son funciones locales), cada acción, mutación y captador es ahora un nodo real. Entonces codegraph search encuentra login o getSessionList, y codegraph_explore/codegraph_node muestran su cuerpo y lo que llama, en lugar de "no encontrado" porque la función solo existía como una propiedad literal de objeto.
  • codegraph_explore ahora conecta un componente de Vue a la acción de tienda Pinia que llama. Cuando el código hace const store = useUserStore() y luego store.fetchUser(), esa llamada ahora se vincula a la acción fetchUser en el módulo de tienda, entonces "¿qué sucede cuando esta vista carga sus datos?" traza desde el componente hasta el cuerpo de la acción en lugar de detenerse en la línea store.fetchUser(). Funciona para ambos estilos de tienda Pinia (opciones y configuración) y se mantiene preciso (un método integrado como store.$patch() o un método no relacionado con el mismo nombre no está mal vinculado).
  • codegraph_explore ahora sigue el envío de cadenas Vuex. Una llamada dispatch('user/login') o commit('SET_TOKEN') (incluidas las claves 'module/action' con espacio de nombres) ahora se vincula a la acción o mutación que nombra, resuelta en el módulo de tienda correcto incluso cuando varios módulos comparten un nombre de acción (y sin ser engañado por un ayudante api/ del mismo nombre). Entonces "¿qué se ejecuta cuando esto se envía?" rastrea desde la llamada hasta el controlador de la tienda y luego hasta las mutaciones que comete. La forma canónica del módulo export default { namespaced, actions, mutations } de Vuex ahora también está indexada, por lo que esos controladores son símbolos que se pueden encontrar.
  • codegraph_explore ahora conecta flujos de recuperación de datos de React creados en RTK Query (createApi de Redux Toolkit). Un punto final definido dentro de createApi({ endpoints }) y el gancho useGetXQuery/useUpdateYMutation que genera eran invisibles para el análisis, entonces "¿qué busca este componente?" o "¿de dónde obtiene el useGetThingQuery sus datos?" estaba sin salida, porque el gancho, el punto final y el componente no tenían nada que los vinculara. CodeGraph ahora indexa cada punto final y cada gancho generado como símbolos reales y conecta la ruta component → useGetXQuery → getX → queryFn, por lo que el flujo se resuelve en una llamada de exploración en lugar de leer el segmento API manualmente. Se reconocen tanto el estilo de flecha (endpoints: build => ({ … })) como el de método (endpoints(builder) { return { … } }), junto con la variante useLazyGetXQuery; Los ganchos escritos a mano con un nombre similar se dejan intactos.
  • codegraph_explore ahora sigue el envío de la tarea Apio en Python. Una llamada send_email.delay(...) o send_email.apply_async(...) ahora se vincula a la función @shared_task / @app.task que ejecuta, generalmente definida en un módulo diferente (tasks.py) desde donde se activa (una vista o servicio), entonces "¿qué sucede realmente cuando se envía esto?" rastrea desde el sitio de la llamada directamente al cuerpo de la tarea en lugar de detenerse en la línea .delay(). Se reconocen ambos dialectos decoradores (@shared_task simple y la forma argumentada @app.task(bind=True, …)), incluido el estilo de llamada tasks.invalidate_cache.apply_async() calificado por módulo. Se mantiene preciso: un .delay() en algo que no es una tarea de Celery nunca se desvincula erróneamente, por lo que un proyecto que no utiliza Celery no se ve afectado.
  • codegraph_explore ahora sigue a Eventos de aplicación de primavera en Java. Una llamada publishEvent(new OrderShippedEvent(...)) ahora se vincula a cada @EventListener que maneja ese evento (generalmente en una clase diferente), entonces "¿qué reacciona cuando se publica esto?" rastrea el editor directamente en cada método de oyente en lugar de terminar en publishEvent(...). El enlace es por tipo de evento y se reconocen todos los estilos de oyente comunes: un @EventListener escrito en su parámetro, la forma @EventListener(SomeEvent.class), @TransactionalEventListener y el antiguo implements ApplicationListener<SomeEvent>. Un evento se distribuye entre todos sus oyentes, y una aplicación Spring simple sin bus de eventos no se ve afectada.
  • codegraph_explore ahora sigue el envío de solicitudes y notificaciones de MediatR en C#/.NET. Una llamada a _mediator.Send(command) o _mediator.Publish(notification) ahora se vincula al método Handle del IRequestHandler<>/INotificationHandler<> correspondiente, generalmente en un archivo diferente en un diseño de arquitectura limpia, entonces "¿qué maneja este comando?" rastrea desde el controlador directamente al controlador en lugar de detenerse en la llamada del mediador. El tipo enviado se reconoce ya sea que esté construido en línea (Send(new GetFooQuery())), integrado en un local primero (var cmd = new …; Send(cmd)) o pasado como parámetro, y coincide por tipo, por lo que un MessagingCenter.Send(...) o un DTO del mismo nombre que no sea una solicitud nunca se vincula erróneamente y un proyecto sin MediatR no se ve afectado.
  • codegraph_explore ahora sigue el envío de trabajos en segundo plano de Sidekiq en Ruby. Una llamada DestroyUserWorker.perform_async(id) (o .perform_in / .perform_at) ahora se vincula al método perform de ese trabajador, generalmente en app/workers/, lejos del controlador o modelo que lo pone en cola, entonces "¿qué se ejecuta aquí en segundo plano?" trazas desde la cola directamente al cuerpo del trabajo. Tanto el include Sidekiq::Job moderno como el Sidekiq::Worker más antiguo son reconocidos, los trabajadores con espacio de nombres se resuelven en la clase correcta incluso cuando varios comparten un nombre (por ejemplo, Comments::NotifyWorker vs Articles::NotifyWorker), y el perform_later de Rails ActiveJob, un mecanismo diferente, se deja intencionalmente solo.
  • codegraph_explore ahora sigue eventos de Laravel en PHP. Una llamada event(new OrderShipped($order)) ahora se vincula a cada oyente que la maneja (el método handle() de cada oyente, generalmente una clase app/Listeners/ separada), entonces "¿qué reacciona a este evento?" rastros del despacho directamente a los cuerpos de los oyentes. Los oyentes se encuentran en ambas formas en que Laravel los registra: mediante un handle(OrderShipped $event) escrito (descubrimiento automático, que incluye una unión handle(A|B $event) que escucha dos eventos) y mediante el mapa protected $listen en su EventServiceProvider (que también detecta un oyente cuyo handle() no tiene sugerencia de tipo). Un evento se despliega para todos sus oyentes y los trabajos en cola (enviados a través de ::dispatch() en lugar de event()) se omiten correctamente.
  • CodeGraph ahora comprende los métodos generados por Lombok en Java. @Getter, @Setter, @Data, @Value y @Builder generan captadores, definidores, builder(), equals/hashCode/toString y el campo @Slf4j log en tiempo de compilación, por lo que esos métodos nunca aparecen en el código fuente, y user.getName(), User.builder() o La llamada log.info(...) solía resolverse en nada, interrumpiendo silenciosamente el análisis de la cadena de llamadas (el agente concluiría que el método no existía y lo reconstruiría a mano). Esos miembros ahora están indexados a partir de las anotaciones y los campos, por lo que aparecen en codegraph search y codegraph_explore/codegraph_node, y las personas que llaman los rastrean como cualquier método escrito a mano. Están marcados como generados por Lombok, por lo que se leen como generados, no escritos a mano; un método que usted mismo escribe nunca se anula, los campos estáticos no tienen acceso y una clase sin Lombok no se ve afectada. Gracias @git87663849. (#912)
  • codegraph_explore ahora sigue despacho de puntero de función C y C++. C aplica polimorfismo con punteros de función: una estructura lleva un campo de puntero de función, funciones concretas se registran en ella a través de una tabla (static struct cmd commands[] = {{"add", cmd_add}, …}), un inicializador designado (.handler = on_open) o una asignación, y el código se distribuye indirectamente (p->fn(argv)). Nada de eso fue visible para el análisis: la llamada indirecta se resolvió en nada, por lo que el ejecutor de comandos de git parecía no haber llamado a nada y las implementaciones de una vtable no tenían llamadores. CodeGraph ahora vincula el sitio de envío a los controladores registrados, codificados por el campo de estructura, entonces "¿qué se ejecuta cuando esto se envía?" rastrea desde p->fn(...) en cada función registrada para ese campo. Esto cubre el modismo de la tabla de comandos (git, redis) y el modismo ops-struct/vtable (codificadores de contenido de curl, controladores de protocolo), incluido el caso en el que se reasigna una ranura de enlace genérica desde un registro (h->func = found->fn). Se mantiene preciso: los distintos campos de puntero de función no se entrecruzan, un campo de datos simple nunca se trata como un envío y un proyecto sin envío de puntero de función no se ve afectado. (#932)
  • codegraph_explore ahora sigue enlaces de ruta GoFrame en Go. Los cables del enrutador estándar de GoFrame enrutan de manera reflectante: la ruta y el método se encuentran en una etiqueta de estructura g.Meta en un tipo de solicitud (g.Meta `path:"/user/sign-in" método:"post"`), the controller method that serves it is matched by that request type, and the two are joined at runtime by group.Bind(...) — so there was no path string and no edge from a route to its handler, and "where is /user/sign-in handled?" or "where are the routes bound to controllers?" could only be answered by reading. CodeGraph now indexes each g.Meta route as a real route node and links it to the controller method whose signature takes that request type, so a route resolves to its handler structurally in one codegraph_explore call. The link is by request type, not method name — so it's correct even when the two differ (a DeptSearchReq served by a List method); it tells apart the many identical request types a large app defines one-per-module (cash.ListReq vs order.ListReq) por paquete, incluidos los módulos complementarios clonados; y una ruta cuyo controlador no está presente se deja desvinculada en lugar de adivinarse. (#747)
  • El servidor MCP ahora funciona en configuraciones monorepos y multiproyecto. Antes, si iniciaba CodeGraph en algún lugar sin .codegraph/ propio (generalmente una raíz monorepo donde solo indexaba servicios individuales), el servidor no exponía ninguna herramienta, por lo que su agente no podía consultar CodeGraph ni siquiera para los subproyectos que estaban indexados. Ahora las herramientas están siempre disponibles: apunte una consulta a cualquier proyecto indexado con el argumento projectPath (su ruta o cualquier lugar dentro de ella) y respuestas CodeGraph desde el índice de ese proyecto, para tantos proyectos como desee en una sesión. También significa que un proyecto que indexas después de que el servidor inició se retoma sin reiniciar, mientras que antes las herramientas permanecían ocultas porque el servidor solo buscaba un índice una vez en el inicio. Un proyecto que realmente no tiene índice todavía le dice claramente a su agente que use sus herramientas integradas allí (y que puede ejecutar codegraph init para habilitarlo), por lo que el uso de un solo proyecto no cambia. Gracias @MaiLunJiye. (#964)
  • El gancho de carga frontal de Claude ahora encuentra sus subproyectos indexados en un monorepo. El gancho opcional UserPromptSubmit que inyecta contexto CodeGraph para preguntas estructurales anteriormente solo buscaba un índice en o encima de su directorio de trabajo, por lo que si abría la raíz de monorepo pero indexaba paquetes individuales (packages/api, services/auth), no encontraba nada y permanecía en silencio exactamente donde era más útil. Ahora también analiza en subproyectos: un único subproyecto indexado obtiene su contexto de carga frontal automática y, con varios ganchos, carga frontalmente el que nombra su pregunta (y enumera el resto para que el agente pueda apuntar a ellos mediante projectPath). Los repositorios de un solo proyecto no se ven afectados y el análisis se limita y se omite por completo fuera de una raíz del espacio de trabajo reconocible. (#964)
  • codegraph_explore ahora muestra el código correcto en grandes proyectos multicapa. Cuando hace una pregunta de flujo de backend en un repositorio que combina un servidor API con una interfaz grande que refleja las mismas palabras de dominio (por ejemplo, una interfaz de usuario de administrador app/ ubicada sobre un servidor api/), el archivo del lado del servidor que realmente coincide con varios de los términos de su consulta ya no es eliminado de los resultados por la capa de interfaz más grande e interconectada. Un archivo corroborado por dos o más términos de consulta distintos ahora se mantiene en la respuesta incluso cuando una capa más densa y no relacionada lo desplazaría, por lo que "cómo lee X los elementos/maneja la solicitud" devuelve el servicio o controlador que hace el trabajo en lugar de un muro de vistas frontales. Los proyectos de una sola capa no se ven afectados; configure CODEGRAPH_RANK_NO_MULTITERM=1 para volver a la clasificación anterior.
  • El análisis de impacto y radio de explosión para TypeScript, JavaScript, Go, Python, Rust, Ruby, C, Java, C#, PHP, Scala, Kotlin, Swift, Dart y Pascal/Delphi ahora comprende a los lectores de una constante. Cuando cambia una constante de alcance de archivo, nivel de paquete, nivel de módulo o nivel de clase (un objeto de configuración, una tabla de búsqueda, una constante compartida), los otros símbolos en ese archivo que lo leen ahora se muestran como afectados, donde antes eran invisibles (el impacto solo seguía llamadas, importaciones y herencia, por lo que los consumidores de una constante parecían "nada depende de esto"). Esto hace que codegraph impact y el rastro de impacto en codegraph_explore/codegraph_node capten la clase de cambio "cambiar esta tabla, romper sus lectores". Está activado de forma predeterminada y no agrega nodos a su gráfico; Los archivos agrupados/minimizados y los nombres sombreados ambiguamente se omiten para mantener los resultados precisos. Configure CODEGRAPH_VALUE_REFS=0 para apagarlo.
  • Las constantes y globales de ámbito de archivo C (escalares static const, tablas de búsqueda de puntero/matriz y globales mutables compartidos) ahora se reconocen como símbolos por derecho propio. Anteriormente no fueron extraídos en absoluto, por lo que nunca aparecieron en la búsqueda ni llevaron a ningún dependiente; ahora aparecen en codegraph search y participan en el análisis de impacto (ver arriba), por lo que al cambiar una tabla de búsqueda en C aparecen las funciones del mismo archivo que la leen.
  • Las constantes Java static final, las constantes C# const / static readonly, los valores Scala object y los niveles superiores de Kotlin / object / companion object val ahora se clasifican como constantes en lugar de campos genéricos, por lo que participan en el análisis de impacto del lector de constantes anterior: cambie una tabla public static final, una const string, Scala object Config { val Timeout = … } o Kotlin companion object { const val … } y los métodos que lo leen ahora aparecen como afectados. (Las propiedades de instancia Java final / C# readonly / Scala & Kotlin class por objeto no cambian). Las constantes de Kotlin anteriormente no se indexaban como sus propios símbolos, por lo que ahora también aparecen en codegraph search.
  • Las constantes let y static let de nivel superior de Swift (incluidas aquellas con espacios de nombres en un enum/struct, el patrón Swift común) ahora están indexadas como constantes y participan en el análisis de impacto del lector constante anterior: cambie un static let defaultRetryLimit o un enum Constants { static let … } y el mismo código de archivo que lo lee se muestra como afectado. Las propiedades calculadas y los let por instancia no se tratan como constantes.
  • Las constantes de nivel superior const/final y de clase static const/static final de Dart ahora están indexadas como constantes y participan en el análisis de impacto del lector de constantes anterior. Los campos de instancia, var y locales no se tratan como constantes. (El código Dart generado con los sufijos estándar .g.dart/.freezed.dart/.pb.dart ya se omitió).
  • Ahora puedes enseñarle a CodeGraph sobre extensiones de archivos personalizadas. Coloque un codegraph.json en la raíz de su repositorio con un mapa extensions ({ "extensions": { ".dota_lua": "lua", ".tpl": "php" } }) y los archivos con esas extensiones se indexarán en el idioma que nombre, en lugar de omitirse silenciosamente porque la extensión no era una de las predeterminadas integradas. Se acepta y se confirma junto con su código para que todo el equipo lo comparta, sus asignaciones se superponen a las funciones integradas y ganan en conflictos (incluso puede volver a señalar una función integrada, por ejemplo, .h → cpp), y se advierte sobre un lenguaje tipográfico o una configuración mal formada y se omite en lugar de interrumpir la indexación. Los proyectos sin codegraph.json se comportan exactamente como antes. (#906)

Correcciones

  • codegraph index y codegraph init ya no se arrastran durante la fase "Resolución de referencias" en proyectos grandes, especialmente aquellos que combinan un gran front-end y back-end, donde la fase podría extenderse a muchos minutos. Un paquete o módulo importado a través de cientos o miles de archivos (react, un paquete de interfaz de usuario compartido, Python logging / typing) se trataba como si cada una de esas declaraciones de importación pudiera ser su definición, por lo que el solucionador comparó cada importación con todas las demás: trabajo que crece con el cuadrado de cuán ampliamente se importa un paquete, razón por la cual explotó solo en repositorios grandes y con muchas importaciones. Las importaciones ahora se resuelven directamente en las definiciones a las que realmente apuntan, por lo que esas comparaciones redundantes desaparecieron (la resolución de referencia es dramáticamente más rápida en repositorios grandes) y el gráfico ya no acumula los enlaces sin sentido de importación a importación que creaba el antiguo respaldo. (#915)
  • Los resultados de la herramienta MCP ya no aparecen como encabezados de gran tamaño en clients de renderizado de Markdown (como la extensión Claude Code VSCode). Los resultados utilizaron encabezados Markdown (##/###) para cosas como el resumen de estado, cada resultado de búsqueda y cada sección de archivo en una exploración, por lo que una consulta normal llenó la transcripción con líneas de fuente grande; peor con codegraph_search y codegraph_explore, donde el ruido creció con la cantidad de resultados. Los encabezados de sección ahora son etiquetas en negrita, que se muestran en tamaño de texto normal manteniendo la misma estructura. La salida del terminal/CLI no cambia. (#778)
  • Un servidor MCP apuntado a un repositorio muy grande (decenas de miles de archivos) ya no se bloquea en la primera llamada a la herramienta después de un nuevo inicio. Al iniciar, CodeGraph concilia su índice con los archivos actuales en el disco, y en un repositorio enorme que la conciliación podría ejecutarse durante minutos mientras bloquea la primera solicitud, el tiempo suficiente para que el servidor en segundo plano a veces se reiniciara a mitad del escaneo, por lo que la primera consulta nunca regresó. La conciliación ahora se produce a medida que se ejecuta (manteniendo el servidor receptivo en lugar de fijarlo), y la primera llamada a la herramienta espera solo brevemente antes de responder y dejar que el resto termine en segundo plano, por lo que obtiene una primera respuesta rápida y el índice aún se pone al día. Configure CODEGRAPH_CATCHUP_GATE_TIMEOUT_MS para ajustar cuánto tiempo espera la primera llamada (predeterminado 3000 ms) o =0 para esperar siempre la conciliación completa. (#905)
  • codegraph install ahora conecta a sus agentes y se detiene ahí: ya no indexa el directorio actual. La creación del gráfico de un proyecto es siempre el codegraph init (o codegraph index) explícito, por lo que usted decide qué se indexa y cuándo, y los pasos son los mismos ya sea que haya instalado globalmente o solo para un proyecto. Esto aclara la confusión en la que una instalación local del proyecto se indexaba silenciosamente pero una global no, y en la que los documentos y la herramienta no estaban de acuerdo sobre si aún era necesario ejecutar init. (#826)
  • Componentes de React declarados con forwardRef, memo o componentes con estilo/emoción (const Button = forwardRef(...), const Card = memo(...), const Box = styled.button\…`) are now recognized as components, so finding where they're used works. Before, they were indexed as plain constants, so codegraph callersand impact analysis reported "no callers found" even when the component was rendered across dozens of files — a dangerous false "safe to change" right before refactoring a shared component. Now every<Button/>` enlaces de uso al componente, por lo que los llamadores y el radio de explosión están completos. Este es el estilo de declaración estándar shadcn/ui, por lo que para los sistemas de diseño típicos de React todo La capa de interfaz de usuario ya no es invisible para el análisis de impacto. Gracias @Arlandaren por el informe y @maxmilian por la causa raíz (#841).
  • Las rutas React Router y Next.js definidas en los archivos .tsx / .jsx ahora están indexadas. Las rutas escritas como archivos de página JSX (<Route path="/users" element={<UsersPage/>}/>, createBrowserRouter([...]) y Next.js app//pages/) se omitían por completo (solo se recogieron las rutas que estaban en formato .ts/.js), entonces "¿qué se representa en esta ruta?" y faltaba el enlace ruta → página-componente para la mayoría de las aplicaciones React. Ahora esas rutas aparecen en codegraph search/codegraph_explore y se conectan al componente que representan, al igual que la ruta backend → enlaces del controlador en otros marcos.
  • codegraph sync (y la sincronización automática del observador de archivos detrás del uso siempre activo/MCP) ya no elimina las llamadas de una función cuando se edita el archivo en el que se encuentra la función. Volver a indexar un archivo después de una edición, incluso un cambio de cadena de documentos solamente, cortaba los bordes de calls/references provenientes de otros archivos sin cambios (por ejemplo, llamadas de from pkg import mod; mod.fn() o cualquier archivo cruzado). referencia), por lo que codegraph callers/impact informaría abruptamente "no hay llamadas" para una función que se utiliza en todo el código base, hasta la próxima reindexación completa. La sincronización ahora conserva esos bordes cruzados entrantes a lo largo de la reindexación, volviendo a hacer coincidirlos con el símbolo incluso cuando la edición cambió su número de línea. Es más visible en los grandes árboles de paquetes Python, pero se aplica a todos los idiomas. Gracias @JosefAschauer. (#899)
  • codegraph index ahora reconstruye el gráfico completo desde cero, por lo que produce el mismo resultado que un codegraph init nuevo en lugar de informar "0 nodos, 0 aristas" y parecer que borró su índice. Anteriormente, al volver a ejecutar index en un proyecto sin cambios se omitían todos los archivos (su contenido no había cambiado) y mostraba un resumen que parecía vacío; ahora se borra y se vuelve a indexar para lograr una reconstrucción completa y honesta en todo momento. Utilice codegraph sync para actualizaciones incrementales rápidas entre reconstrucciones completas. Gracias @ Arc-univers. (#874)
  • El observador de archivos que sincroniza automáticamente el gráfico ahora falla claramente cuando la visualización en vivo ya no se puede trust, en lugar de verse saludable mientras el índice se vuelve obsoleto silenciosamente. Si el sistema operativo se queda sin recursos de vigilancia de archivos, u otro proceso mantiene el bloqueo de escritura por mucho más tiempo que un guardado normal, CodeGraph ahora desactiva la sincronización automática una vez, con un único mensaje claro que le indica que ejecute codegraph sync (o confíe en los enlaces de sincronización de Git) para actualizar, en lugar de volver a intentarlo para siempre o repetir el mismo error en un bucle. Y aunque la sincronización automática está deshabilitada, las respuestas de la herramienta CodeGraph (y codegraph status) ahora lo dicen claramente, por lo que su agente de IA sabe leer archivos directamente en lugar de usar un índice congelado. Esto es especialmente importante para sesiones MCP/daemon de larga duración, que de otro modo podrían seguir generando resultados obsoletos aunque parezcan funcionar. Gracias @thismilktea. (#876)
  • En Linux, alcanzar el límite de vigilancia de inotify del kernel en un proyecto grande ya no deja silenciosamente a la mitad del árbol sin vigilancia. CodeGraph ahora te lo dice una vez, nombrando la configuración exacta a generar (fs.inotify.max_user_watches, por ejemplo, sudo sysctl fs.inotify.max_user_watches=1048576), y sigue observando en vivo los directorios que podría registrar mientras codegraph sync (o los ganchos de git sync) cubre el resto. (#876)
  • Un servidor MCP de larga ejecución ahora detecta cuando un árbol de trabajo git obtiene su propio índice. Antes, si el servidor (o demonio compartido) veía por primera vez un árbol de trabajo antes de ejecutar codegraph init en él, por lo que la búsqueda llegaba al índice de pago principal, fijaba esa decisión durante toda su vida: incluso después de que el árbol de trabajo tenía su propio .codegraph/, cada consulta seguía llegando al índice de pago principal y cada resultado llevaba una advertencia falsa de "este índice pertenece a un árbol de trabajo de git diferente", hasta que reiniciaba el servidor. El CLI lo hizo bien, pero el servidor MCP no, y volver a indexar no ayudó. El servidor ahora vuelve a verificar a qué índice pertenece una ruta en cada llamada, por lo que el propio índice del árbol de trabajo se selecciona (y la advertencia obsoleta desaparece) sin reiniciar. (#926)
  • Un servidor MCP de larga duración ahora se recupera cuando su índice se elimina y se reconstruye en la misma ruta. Si .codegraph/ se eliminó y se volvió a crear mientras el servidor lo mantenía abierto (lo más fácil es recrear un árbol de trabajo de git en la misma ruta, o rm implementando .codegraph/ y ejecutando codegraph init nuevamente), el servidor siguió leyendo el archivo de base de datos antiguo y eliminado y mostró una instantánea congelada: los símbolos renombrados o eliminados aún se mostraban activos, faltaban otros nuevos y codegraph sync no podía actualizarlo; solo se solucionó reiniciando el servidor. eso. El servidor ahora detecta que el archivo de la base de datos se intercambió y vuelve a abrir el archivo activo en su lugar, por lo que los resultados permanecen correctos sin necesidad de reiniciar. (En Linux y macOS; Windows no permite eliminar un archivo abierto, por lo que no se ve afectado). (#925)
  • El servidor MCP ahora abre y sincroniza automáticamente un proyecto que se encuentra dentro de una carpeta que un repositorio git adjunto ignora. Antes, si el directorio que indexaba estaba dentro de un repositorio más grande que lo ignoraba, el demonio MCP compartido no podía abrir el proyecto (su registro repetía Failed to open project … path should be a path.relative() d string, but got "./"), por lo que el observador de archivos nunca se iniciaba y el índice se quedaba obsoleto silenciosamente hasta que ejecutaba codegraph sync a mano (configurar CODEGRAPH_NO_DAEMON=1 era la única solución). El demonio ahora abre el proyecto y comienza a observar como se esperaba. Más visible con Codex en Windows, pero la causa no era específica de la plataforma. (#936)
  • Un árbol de trabajo git de un submódulo ya no se indexa como una copia duplicada del código de ese submódulo. CodeGraph ya omite los árboles de trabajo ordinarios (una segunda vista de trabajo de un repositorio que indexa), pero un árbol de trabajo creado a partir de un submódulo (común en monorepos que verifican los submódulos en árboles de trabajo para el trabajo de funciones paralelas) se confundió con un repositorio incrustado genuino y se barrió, duplicando cada símbolo que compartía con el pago del submódulo real (un informe tenía ~28% de su índice como duplicados, inflando tanto los resultados de la consulta como la base de datos). Estos árboles de trabajo de submódulos ahora se reconocen y se omiten, mientras que el pago del propio submódulo permanece indexado como código distinto. Gracias @charlesxu2026-ship-it. (#945)
  • Una clase o estructura de C++ anotada con una macro de exportación/visibilidad (class MYLIB_EXPORT Foo : public Bar { … }, el patrón común de exportación/visibilidad de DLL en los encabezados) ya no está mal indexada como una función que abarca todo el cuerpo de la clase. Sin saber que la macro es una macro, el analizador la leyó como un tipo y toda la declaración como una función, por lo que la clase surgió como un function fantasma que apareció como un llamador falso en codegraph callers, codegraph impact y análisis de radio explosivo, y recuentos de símbolos sesgados. CodeGraph ahora reconoce este error de análisis y descarta el nodo falso. Gracias @spwlyzx. (#946)
  • codegraph status ya no informa cambios fantasmas pendientes para los archivos que CodeGraph mantiene deliberadamente fuera del índice: un archivo rastreado dentro de un directorio de dependencia comprometido (un vendor/ o node_modules/ registrado) o un archivo rastreado en un directorio .gitignored. Un índice completo los excluye correctamente, y codegraph sync nunca los indexa, pero el rápido detector de cambios detrás de codegraph status marcó cada edición de dicho archivo como "modificado" (y uno nuevo como "agregado"), por lo que el recuento de cambios pendientes nunca se borra, sin importar cuántas veces haya sincronizado. La detección de cambios ahora aplica las mismas reglas de ignorar que el índice completo, por lo que status concuerda con sync, y las herramientas creadas sobre la detección de cambios API de CodeGraph obtienen la misma lista corregida. (#766)
  • Los archivos a los que se accede a través de un directorio con enlace simbólico que apunta fuera de su proyecto ahora se indexan en lugar de omitirse silenciosamente. Cuando una carpeta en su repositorio es un enlace simbólico a una ubicación fuera de la raíz del repositorio (el diseño estándar para juegos personalizados de Dota 2 y proyectos similares vinculados a SDK, donde game/ y content/ se vinculan al árbol del motor), CodeGraph siguió el enlace simbólico para descubrir esos archivos, pero luego bloqueó cada uno de ellos mientras leía, registraba Path traversal blocked in batch reader y no indexaba nada debajo de ellos. El lector ahora está de acuerdo con el escaneo del directorio e indexa esos archivos. La protección contra fugas de ruta ../ no ha cambiado, y la protección que impide que su agente reciba contenido de archivos desde fuera del repositorio tampoco ha cambiado: solo la ruta de lectura del indexador sigue estos enlaces simbólicos en el repositorio. (#935)

codegraph v1.1.0

[1.1.0] - 2026-06-23

New Features

  • Claude Code: an optional front-load hook makes your agent reach for CodeGraph automatically. When you ask a structural question — "how does X work", "what calls Y", "trace the flow from A to B" — CodeGraph injects the relevant source and call paths into the prompt up front, so the agent answers from the graph instead of grepping around to rebuild it. You're asked during codegraph install (default yes; Claude Code only, since it's the agent with prompt hooks), it's removed by codegraph uninstall, and codegraph upgrade turns it on for existing Claude setups. It's strictly additive and degradable — non-structural prompts and un-indexed projects are left alone — and you can switch it off any time without uninstalling by setting CODEGRAPH_NO_PROMPT_HOOK=1.

  • Vue store actions, mutations, and getters are now indexed as symbols you can find and read. Whether your store is Vuex (mutations / actions objects in a module) or Pinia — both the options form (defineStore({ actions: { … } })) and the setup form (defineStore('id', () => { … }), where actions are local functions) — each action, mutation, and getter is now a real node. So codegraph search finds login or getSessionList, and codegraph_explore / codegraph_node show its body and what it calls, instead of "not found" because the function only existed as an object-literal property.

  • codegraph_explore now connects a Vue component to the Pinia store action it calls. When code does const store = useUserStore() and then store.fetchUser(), that call now links through to the fetchUser action in the store module — so "what happens when this view loads its data?" traces from the component into the action's body instead of stopping at the store.fetchUser() line. Works for both Pinia store styles (options and setup), and stays precise (a built-in like store.$patch() or an unrelated same-named method isn't mislinked).

  • codegraph_explore now follows Vuex string dispatch. A dispatch('user/login') or commit('SET_TOKEN') call — namespaced 'module/action' keys included — now links to the action or mutation it names, resolved to the correct store module even when several modules share an action name (and without being fooled by a same-named api/ helper). So "what runs when this dispatches?" traces from the call into the store handler and on to the mutations it commits. Vuex's canonical export default { namespaced, actions, mutations } module shape is now indexed too, so those handlers are findable symbols.

  • codegraph_explore now connects React data-fetching flows built on RTK Query (Redux Toolkit's createApi). An endpoint defined inside createApi({ endpoints }) and the useGetXQuery / useUpdateYMutation hook it generates were both invisible to analysis — so "what does this component fetch?" or "where does useGetThingQuery get its data?" dead-ended, because the hook, the endpoint, and the component had nothing linking them. CodeGraph now indexes each endpoint and each generated hook as real symbols and wires the path component → useGetXQuery → getX → queryFn, so the flow resolves in one explore call instead of reading the API slice by hand. Both the arrow (endpoints: build => ({ … })) and method (endpoints(builder) { return { … } }) styles are recognized, along with the useLazyGetXQuery variant; hand-written hooks of a similar name are left untouched.

  • codegraph_explore now follows Celery task dispatch in Python. A send_email.delay(...) or send_email.apply_async(...) call now links to the @shared_task / @app.task function it runs — typically defined in a different module (tasks.py) from where it's triggered (a view or service) — so "what actually happens when this is dispatched?" traces from the call site straight into the task body instead of stopping at the .delay() line. Both decorator dialects are recognized (bare @shared_task and the arg'd @app.task(bind=True, …) form), including the module-qualified tasks.invalidate_cache.apply_async() call style. It stays precise: a .delay() on something that isn't a Celery task is never mislinked, so a project that doesn't use Celery is unaffected.

  • codegraph_explore now follows Spring application events in Java. A publishEvent(new OrderShippedEvent(...)) call now links to every @EventListener that handles that event — usually in a different class — so "what reacts when this is published?" traces from the publisher straight into each listener method instead of dead-ending at publishEvent(...). The link is by event type, and all the common listener styles are recognized: a @EventListener typed on its parameter, the @EventListener(SomeEvent.class) form, @TransactionalEventListener, and the older implements ApplicationListener<SomeEvent>. One event fans out to all its listeners, and a plain Spring app with no event bus is unaffected.

  • codegraph_explore now follows MediatR request and notification dispatch in C#/.NET. A _mediator.Send(command) or _mediator.Publish(notification) call now links to the Handle method of the matching IRequestHandler<> / INotificationHandler<> — usually in a different file in a Clean Architecture layout — so "what handles this command?" traces from the controller straight into the handler instead of stopping at the mediator call. The sent type is recognized whether it's constructed inline (Send(new GetFooQuery())), built into a local first (var cmd = new …; Send(cmd)), or passed in as a parameter, and it's matched by type — so a MessagingCenter.Send(...) or a same-named DTO that isn't a request is never mislinked, and a project without MediatR is unaffected.

  • codegraph_explore now follows Sidekiq background-job dispatch in Ruby. A DestroyUserWorker.perform_async(id) (or .perform_in / .perform_at) call now links to that worker's perform method — usually in app/workers/ away from the controller or model that enqueues it — so "what runs in the background here?" traces from the enqueue straight into the job body. Both the modern include Sidekiq::Job and the older Sidekiq::Worker are recognized, namespaced workers resolve to the right class even when several share a name (e.g. Comments::NotifyWorker vs Articles::NotifyWorker), and Rails ActiveJob's perform_later — a different mechanism — is intentionally left alone.

  • codegraph_explore now follows Laravel events in PHP. An event(new OrderShipped($order)) call now links to every listener that handles it — each listener's handle() method, usually a separate app/Listeners/ class — so "what reacts to this event?" traces from the dispatch straight into the listener bodies. Listeners are found both ways Laravel registers them: by a typed handle(OrderShipped $event) (auto-discovery, including a handle(A|B $event) union that listens for two events) and by the protected $listen map in your EventServiceProvider (which also catches a listener whose handle() has no type-hint). One event fans out to all its listeners, and queued jobs — dispatched via ::dispatch() rather than event() — are correctly left out.

  • CodeGraph now understands Lombok-generated methods in Java. @Getter, @Setter, @Data, @Value, and @Builder generate getters, setters, builder(), equals/hashCode/toString, and the @Slf4j log field at compile time, so those methods never appear in the source — and a user.getName(), User.builder(), or log.info(...) call used to resolve to nothing, silently breaking call-chain analysis (the agent would conclude the method didn't exist and reconstruct it by hand). Those members are now indexed from the annotations and fields, so they appear in codegraph search and codegraph_explore/codegraph_node, and callers trace through them like any hand-written method. They're marked as Lombok-generated so they read as generated, not hand-written; a method you write yourself is never overridden, static fields get no accessor, and a class without Lombok is unaffected. Thanks @git87663849. (#912)

  • codegraph_explore now follows C and C++ function-pointer dispatch. C does polymorphism with function pointers: a struct carries a function-pointer field, concrete functions are registered into it through a table (static struct cmd commands[] = {{"add", cmd_add}, …}), a designated initializer (.handler = on_open), or an assignment, and the code dispatches indirectly (p->fn(argv)). None of that was visible to analysis — the indirect call resolved to nothing, so git's command runner looked like it called nothing and a vtable's implementations had no callers. CodeGraph now links the dispatch site to the registered handlers, keyed by the struct field, so "what runs when this dispatches?" traces from p->fn(...) into every function registered for that field. This covers the command-table idiom (git, redis) and the ops-struct/vtable idiom (curl's content-encoders, protocol handlers), including the case where a generic hook slot is reassigned from a registry (h->func = found->fn). It stays precise — distinct function-pointer fields don't cross-link, a plain data field is never treated as a dispatch, and a project without function-pointer dispatch is unaffected. (#932)

  • codegraph_explore now follows GoFrame route bindings in Go. GoFrame's standard router wires routes reflectively: the path and method live in a g.Meta struct tag on a request type (g.Meta `path:"/user/sign-in" method:"post"`), the controller method that serves it is matched by that request type, and the two are joined at runtime by group.Bind(...) — so there was no path string and no edge from a route to its handler, and "where is /user/sign-in handled?" or "where are the routes bound to controllers?" could only be answered by reading. CodeGraph now indexes each g.Meta route as a real route node and links it to the controller method whose signature takes that request type, so a route resolves to its handler structurally in one codegraph_explore call. The link is by request type, not method name — so it's correct even when the two differ (a DeptSearchReq served by a List method); it tells apart the many identical request types a large app defines one-per-module (cash.ListReq vs order.ListReq) by package, including cloned addon modules; and a route whose handler isn't present is left unlinked rather than guessed. (#747)

  • The MCP server now works in monorepos and multi-project setups. Before, if you started CodeGraph somewhere with no .codegraph/ of its own — most often a monorepo root where you only indexed individual services — the server exposed no tools at all, so your agent couldn't query CodeGraph even for the sub-projects that were indexed. Now the tools are always available: point a query at any indexed project with the projectPath argument (its path, or anywhere inside it) and CodeGraph answers from that project's index — for as many projects as you like in one session. It also means a project you index after the server started is picked up without restarting, where before the tools stayed hidden because the server only checked for an index once at launch. A project that genuinely has no index still cleanly tells your agent to use its built-in tools there (and that you can run codegraph init to enable it), so single-project use is unchanged. Thanks @MaiLunJiye. (#964)

  • The Claude front-load hook now finds your indexed sub-projects in a monorepo. The optional UserPromptSubmit hook that injects CodeGraph context for structural questions previously only looked for an index at or above your working directory — so if you opened the monorepo root but indexed individual packages (packages/api, services/auth), it found nothing and stayed silent exactly where it was most useful. It now also looks into sub-projects: a single indexed sub-project gets its context front-loaded automatically, and with several the hook front-loads the one your question names (and lists the rest so the agent can target them by projectPath). Single-project repos are unaffected, and the scan is bounded and skipped entirely outside a recognizable workspace root. (#964)

  • codegraph_explore now surfaces the right code in large multi-layer projects. When you ask a backend-flow question in a repo that pairs an API server with a big frontend that mirrors the same domain words — say an app/ admin UI sitting over an api/ server — the server-side file that genuinely matches several of your query's terms is no longer pushed out of the results by the larger, more interconnected frontend layer. A file corroborated by two or more distinct query terms is now kept in the answer even when a denser unrelated layer would otherwise crowd it out, so "how does X read items / handle the request" returns the service or handler that does the work instead of a wall of frontend views. Single-layer projects are unaffected; set CODEGRAPH_RANK_NO_MULTITERM=1 to revert to the previous ranking.

  • Impact and blast-radius analysis for TypeScript, JavaScript, Go, Python, Rust, Ruby, C, Java, C#, PHP, Scala, Kotlin, Swift, Dart, and Pascal/Delphi now understands the readers of a constant. When you change a file-scope, package-level, module-level, or class-level constant — a config object, a lookup table, a shared constant — the other symbols in that file that read it now show up as affected, where before they were invisible (impact only followed calls, imports, and inheritance, so a constant's consumers looked like "nothing depends on this"). This makes codegraph impact, and the impact trail in codegraph_explore/codegraph_node, catch the "change this table, break its readers" class of change. It's on by default and adds no nodes to your graph; bundled/minified files and ambiguously-shadowed names are skipped to keep results precise. Set CODEGRAPH_VALUE_REFS=0 to turn it off.

  • C file-scope constants and globals — static const scalars, pointer/array lookup tables, and shared mutable globals — are now recognized as symbols in their own right. They previously weren't extracted at all, so they never appeared in search or carried any dependents; now they show up in codegraph search and participate in impact analysis (see above), so changing a C lookup table surfaces the same-file functions that read it.

  • Java static final constants, C# const / static readonly constants, Scala object vals, and Kotlin top-level / object / companion object vals are now classified as constants rather than generic fields, so they participate in the constant-reader impact analysis above — change a public static final table, a const string, a Scala object Config { val Timeout = … }, or a Kotlin companion object { const val … } and the methods that read it now show up as affected. (Per-object Java final / C# readonly / Scala & Kotlin class instance properties are unchanged.) Kotlin constants were previously not indexed as their own symbols at all, so they now also appear in codegraph search.

  • Swift top-level lets and static let constants (including those namespaced in an enum/struct, the common Swift pattern) are now indexed as constants and participate in the constant-reader impact analysis above — change a static let defaultRetryLimit or an enum Constants { static let … } and the same-file code that reads it shows up as affected. Computed properties and per-instance lets are not treated as constants.

  • Dart top-level const/final and class static const/static final constants are now indexed as constants and participate in the constant-reader impact analysis above. Instance fields, vars, and locals are not treated as constants. (Generated Dart code with the standard .g.dart/.freezed.dart/.pb.dart suffixes is already skipped.)

  • You can now teach CodeGraph about custom file extensions. Drop a codegraph.json at your repo root with an extensions map — { "extensions": { ".dota_lua": "lua", ".tpl": "php" } } — and files with those extensions get indexed under the language you name, instead of being silently skipped because the extension wasn't one of the built-in defaults. It's opt-in and committed alongside your code so the whole team shares it, your mappings layer on top of the built-ins and win on conflict (you can even re-point a built-in, e.g. .h → cpp), and a typo'd language or a malformed config is warned about and skipped rather than breaking indexing. Projects without a codegraph.json behave exactly as before. (#906)

Fixes

  • codegraph index and codegraph init no longer crawl during the "Resolving refs" phase on large projects — most painfully ones that mix a big front-end and back-end, where the phase could stretch to many minutes. A package or module imported across hundreds or thousands of files (react, a shared UI package, Python logging / typing) was being treated as if every one of those import statements might be its definition, so the resolver compared each import against all the others — work that grows with the square of how widely a package is imported, which is why it blew up only on big, import-heavy repos. Imports now resolve straight to the definitions they actually point at, so those redundant comparisons are gone (reference resolution is dramatically faster on large repos), and the graph no longer accumulates the meaningless import-to-import links the old fallback created. (#915)
  • MCP tool results no longer show up as oversized headings in Markdown-rendering clients (such as the Claude Code VSCode extension). Results used Markdown headings (##/###) for things like the status summary, each search hit, and every file section in an exploration, so a normal query filled the transcript with large-font lines — worst with codegraph_search and codegraph_explore, where the noise grew with the number of results. Section headers are now bold labels, which render at normal text size while keeping the same structure. Terminal/CLI output is unchanged. (#778)
  • An MCP server pointed at a very large repository (tens of thousands of files) no longer hangs on the first tool call after a fresh start. On startup CodeGraph reconciles its index against the current files on disk, and on a huge repo that reconcile could run for minutes while blocking the very first request — long enough that the background server was sometimes force-restarted mid-scan, so the first query never came back at all. The reconcile now yields as it runs (keeping the server responsive instead of pinning it), and the first tool call waits only briefly for it before answering and letting the rest finish in the background — so you get a fast first response and the index still catches up. Set CODEGRAPH_CATCHUP_GATE_TIMEOUT_MS to tune how long that first call waits (default 3000ms), or =0 to always wait for the full reconcile. (#905)
  • codegraph install now wires up your agents and stops there — it no longer indexes the current directory. Building a project's graph is always the explicit codegraph init (or codegraph index), so you decide what gets indexed and when, and the steps are the same whether you installed globally or just for one project. This clears up the confusion where a project-local install silently indexed but a global one didn't, and where the docs and the tool disagreed about whether you still had to run init. (#826)
  • React components declared with forwardRef, memo, or styled-components / emotion (const Button = forwardRef(...), const Card = memo(...), const Box = styled.button\…`) are now recognized as components, so finding where they're used works. Before, they were indexed as plain constants, so codegraph callersand impact analysis reported "no callers found" even when the component was rendered across dozens of files — a dangerous false "safe to change" right before refactoring a shared component. Now every<Button/>` usage links back to the component, so callers and blast radius are complete. This is the standard shadcn/ui declaration style, so for typical React design systems the whole UI layer is no longer invisible to impact analysis. Thanks @Arlandaren for the report and @maxmilian for the root-cause. (#841)
  • React Router and Next.js routes defined in .tsx / .jsx files are now indexed. Routes written as JSX — <Route path="/users" element={<UsersPage/>}/>, createBrowserRouter([...]), and Next.js app//pages/ page files — were being skipped entirely (only routes that happened to live in plain .ts/.js were picked up), so "what renders at this path?" and the route → page-component link were missing for most React apps. Now those routes show up in codegraph search/codegraph_explore and connect to the component they render, just like the backend route → handler links on other frameworks.
  • codegraph sync (and the file-watcher auto-sync behind always-on / MCP use) no longer drops a function's callers when you edit the file that function lives in. Re-indexing a file after an edit — even a docstring-only change — was severing the calls / references edges coming from other, unchanged files (e.g. from pkg import mod; mod.fn() callers, or any cross-file reference), so codegraph callers / impact would abruptly report "no callers" for a function that's used throughout the codebase, until the next full re-index. Sync now preserves those incoming cross-file edges across the re-index, re-matching them to the symbol even when the edit shifted its line number. Most visible in large Python package trees, but it applies to every language. Thanks @JosefAschauer. (#899)
  • codegraph index now rebuilds the full graph from scratch, so it produces the same result as a fresh codegraph init instead of reporting "0 nodes, 0 edges" and looking like it wiped your index. Previously, re-running index on an unchanged project skipped every file (their contents hadn't changed) and showed an empty-looking summary; it now clears and re-indexes for an honest, complete rebuild every time. Use codegraph sync for fast incremental updates between full rebuilds. Thanks @Arc-univer. (#874)
  • The file watcher that auto-syncs the graph now fails cleanly when live watching can no longer be trusted, instead of looking healthy while the index quietly goes stale. If the operating system runs out of file-watch resources, or another process holds the write lock far longer than a normal save, CodeGraph now disables auto-sync once — with a single clear message telling you to run codegraph sync (or rely on the git sync hooks) to refresh — rather than retrying forever or repeating the same error on a loop. And while auto-sync is disabled, CodeGraph's tool responses (and codegraph status) now say so plainly, so your AI agent knows to read files directly instead of trusting a frozen index. This mostly matters for long-running MCP/daemon sessions, which could otherwise keep serving stale results while appearing to work. Thanks @thismilktea. (#876)
  • On Linux, hitting the kernel's inotify watch limit on a large project no longer silently leaves half the tree unwatched. CodeGraph now tells you once — naming the exact setting to raise (fs.inotify.max_user_watches, e.g. sudo sysctl fs.inotify.max_user_watches=1048576) — and keeps live-watching the directories it could register while codegraph sync (or the git sync hooks) covers the rest. (#876)
  • A long-running MCP server now notices when a git worktree gains its own index. Before, if the server (or shared daemon) first saw a worktree before you ran codegraph init in it — so the lookup walked up to the main checkout's index — it pinned that decision for its whole life: even after the worktree had its own .codegraph/, every query kept hitting the main checkout's index and every result carried a false "this index belongs to a different git working tree" warning, until you restarted the server. The CLI got it right but the MCP server didn't, and re-indexing didn't help. The server now re-checks which index a path belongs to on each call, so the worktree's own index is picked up — and the stale warning drops — without a restart. (#926)
  • A long-running MCP server now recovers when your index is deleted and rebuilt at the same path. If .codegraph/ was removed and recreated while the server held it open — most easily by recreating a git worktree at the same path, or rm-ing .codegraph/ and running codegraph init again — the server kept reading the old, deleted database file and served a frozen snapshot: renamed or removed symbols still showed as live, new ones were missing, and codegraph sync couldn't refresh it — only restarting the server fixed it. The server now detects that the database file was swapped out from under it and reopens the live one in place, so results stay correct without a restart. (On Linux and macOS; Windows doesn't allow deleting an open file, so it isn't affected.) (#925)
  • The MCP server now opens and auto-syncs a project that lives inside a folder an enclosing git repository ignores. Before, if the directory you indexed sat within a larger repo that gitignored it, the shared MCP daemon failed to open the project — its log repeated Failed to open project … path should be a path.relative() d string, but got "./" — so the file watcher never started and the index silently went stale until you ran codegraph sync by hand (setting CODEGRAPH_NO_DAEMON=1 was the only workaround). The daemon now opens the project and starts watching as expected. Most visible with Codex on Windows, but the cause wasn't platform-specific. (#936)
  • A git worktree of a submodule is no longer indexed as a duplicate copy of that submodule's code. CodeGraph already skips ordinary worktrees (a second working view of a repo it indexes), but a worktree created from a submodule — common in monorepos that check submodules out into worktrees for parallel feature work — was mistaken for a genuine embedded repo and swept in, duplicating every symbol it shared with the real submodule checkout (one report had ~28% of its index as duplicates, inflating both query results and the database). These submodule worktrees are now recognized and skipped, while the submodule's own checkout stays indexed as distinct code. Thanks @charlesxu2026-ship-it. (#945)
  • A C++ class or struct annotated with an export/visibility macro — class MYLIB_EXPORT Foo : public Bar { … }, the common DLL-export / visibility pattern in headers — is no longer mis-indexed as a function spanning the whole class body. Not knowing the macro is a macro, the parser read it as a type and the whole declaration as a function, so the class surfaced as a phantom function that showed up as a false caller in codegraph callers, codegraph impact, and blast-radius analysis, and skewed symbol counts. CodeGraph now recognizes this misparse and drops the bogus node. Thanks @spwlyzx. (#946)
  • codegraph status no longer reports phantom pending changes for files CodeGraph deliberately keeps out of the index — a tracked file inside a committed dependency dir (a checked-in vendor/ or node_modules/), or a tracked file under a .gitignored directory. A full index correctly excludes these, and codegraph sync never indexes them, but the fast change-detector behind codegraph status flagged every edit to such a file as "modified" (and a new one as "added") — so the pending-changes count never cleared no matter how many times you synced. Change detection now applies the same ignore rules the full index does, so status agrees with sync, and tools built on CodeGraph's change-detection API get the same corrected list. (#766)
  • Files reached through a symlinked directory that points outside your project now index instead of being silently skipped. When a folder in your repo is a symlink to a location outside the repo root — the standard layout for Dota 2 custom games and similar SDK-linked projects, where game/ and content/ link into the engine tree — CodeGraph followed the symlink to discover those files but then blocked every one of them while reading, logging Path traversal blocked in batch reader and indexing nothing under them. The reader now agrees with the directory scan and indexes those files. The guard against ../ path escapes is unchanged, and the protection that keeps your agent from being served file contents from outside the repo is also unchanged — only the indexer's own read path follows these in-repo symlinks. (#935)
