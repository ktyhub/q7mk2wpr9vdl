carrito v2.10.0

¡Caddy 2.10 ya está aquí! Además de las correcciones de errores, esta versión incluye:

  • ClientHello cifrado (ECH): Esta nueva tecnología cifra la última parte de texto sin formato de una conexión TLS: ClientHello, que incluye el nombre de dominio al que se está conectando. El borrador de especificación para ECH está casi finalizado, por lo que ahora podemos admitir esta función de privacidad para TLS. Esta es una capacidad poderosa pero matizada; Recomendamos encarecidamente leer [la documentación de ECH] (https://caddyserver.com/docs/automatic-https#encrypted-clienthello-ech) en nuestro sitio web.
  • Intercambio de claves post-cuántico (PQC): Caddy ahora admite el grupo criptográfico estandarizado x25519mlkem768 de forma predeterminada.
  • Perfiles ACME: Los perfiles ACME son un borrador experimental que le permite elegir propiedades de sus certificados con más flexibilidad que los métodos CSR tradicionales. Por ejemplo, Let's Encrypt emitirá certificados de 6 días bajo un perfil determinado. Caddy puede llegar a utilizar ese perfil de forma predeterminada.
  • Vía encabezado: El proxy inverso ahora establece un encabezado Vía en lugar de un encabezado de servidor duplicado.
  • Proveedor de DNS global: Ahora puede especificar un módulo DNS "global" predeterminado para usar en lugar de tener que configurarlo localmente en cada parte de su configuración que requiera un proveedor de DNS (por ejemplo, desafíos de DNS de ACME y ECH). Esta es la opción global dns en Caddyfile, o en la configuración JSON, es el parámetro dns en la configuración de la aplicación tls.
  • Comodines utilizados de forma predeterminada: Anteriormente, Caddy obtenía certificados individuales para cada dominio en su configuración literalmente; ahora los comodines, si están presentes, se utilizarán para los subdominios, en lugar de obtener certificados individuales. Este cambio fue motivado por la novedosa posibilidad de privacidad de subdominios que ofrece ECH. Se puede anular con tls force_automate en Caddyfile. Se ha eliminado la opción experimental auto_https prefer_wildcard.
  • libdns 1.0 APIs: Muchos de ustedes usan módulos de proveedor de DNS para resolver los desafíos de DNS de ACME o para habilitar DNS dinámico. Implementan interfaces definidas por libdns para obtener, configurar, agregar y eliminar registros DNS. Después de 5 años de experiencia en producción, incluidas las lecciones aprendidas con ECH, se actualizaron los libdns API y se etiquetó la versión beta de 1.0. Los paquetes de proveedores de DNS deberán actualizar su código para que sean compatibles, lo que ayudará a garantizar la estabilidad y una semántica bien definida para el futuro. Varios paquetes ya se han actualizado o están en proceso de actualización (cloudflare, rfc2136 y desec, por nombrar algunos).
  • Configuración global de dns: Ahora que varios componentes de la configuración de Caddy pueden afectar los registros DNS (desafíos ACME, publicación ECH, etc.), existe una nueva opción global dns que se puede usar para especificar la configuración de su proveedor de DNS en un solo lugar. Esto evita la repetición de credenciales para servidores donde todos los dominios son administrados por un único proveedor de DNS. ¡Gracias a todos los contribuyentes que han ayudado a hacer esto posible! :tada: :partying_face: :champagne: :advertencia: Si bien tradicionalmente hemos admitido las últimas 2 versiones menores de Go para adaptarse a algunas políticas de distribución/administrador de paquetes, ahora solo admitimos la última versión menor de Go. Vale la pena poner a disposición de todos los beneficios de privacidad y seguridad agregados en las nuevas versiones de Go (como la criptografía poscuántica) lo antes posible, en lugar de frenar a toda la base de usuarios o mantener múltiples configuraciones de compilación de código.

Detalles cifrados de ClientHello (ECH)

(Esta es una breve descripción general. Recomendamos leer la documentación completa.) Normalmente, los nombres de los servidores (nombres de dominio o "SNI") se envían en texto sin formato ClientHello al establecer conexiones TLS. Con ECH, el verdadero nombre del servidor está cifrado (y empaquetado) mediante un ClientHello "externo" que tiene un SNI genérico de su elección. Dado que muchos sitios en el mismo servidor comparten el mismo SNI externo, tanto clients como el servidor tienen más privacidad relacionada con los nombres de dominio. Caddy implementa ECH totalmente automatizado, lo que significa que genera (y pronto, rota), publica y ofrece configuraciones ECH simplemente especificando un proveedor de DNS y el nombre de dominio público/externo que se utilizará. El ECH completamente automatizado requiere un módulo DNS integrado en su binario Caddy. Para que un client, ​​como un navegador, sepa que puede usar ECH y qué parámetros usar, se debe publicar la configuración de ECH del servidor. Esta configuración incluye el nombre público, los parámetros criptográficos y una clave pública para cifrar el ClientHello interno. Por convención, los navegadores leen el registro DNS estandarizado de tipo HTTPS que contiene una SvcParamKey ech. Caddy establece este registro DNS para todos los dominios que se están protegiendo, pero necesita que el módulo del proveedor de DNS esté conectado y configurado para poder hacerlo. Si ya está utilizando el desafío DNS ACME, ya debería tener un proveedor de DNS conectado. Si prefiere compilar Caddy desde la fuente con un módulo DNS, es fácil con xcaddy, por ejemplo: $ xcaddy build --with github.com/caddy-dns/cloudflare La configuración mínima necesaria para habilitar ClientHello es también la configuración recomendada, ya que maximiza los beneficios de privacidad en la mayoría de las situaciones. Sólo necesita la opción global ech y un proveedor de DNS especificado. Aquí hay un ejemplo que utiliza Cloudflare como servidor de nombres: Archivo Caddy:

{
	debug  # not required; recommended while testing
	dns cloudflare {env.CLOUDFLARE_API_KEY}
	ech ech.example.net
}

example.com {
	respond "Hello there!"
}

Esto protege todos sus sitios (example.com en este caso) detrás del nombre público de ech.example.net. (Como otro ejemplo, Cloudflare usa cloudflare-ech.com para todos los sitios a los que presta servicios. Recomendamos elegir un único dominio público y usarlo para proteger todos sus sitios). El nombre externo/público que elija debe apuntar a su servidor. Caddy obtendrá un certificado para este nombre para facilitar conexiones seguras y confiables para clients cuando sea necesario. Sin un certificado, clients puede verse obligado a conectarse de forma insegura o no poder conectarse en absoluto, en algunos casos, lo que no sólo los deja vulnerables, sino que también corre el riesgo de exponer los nombres de los sitios de su servidor. Luego, Caddy utiliza el proveedor de DNS especificado para publicar las configuraciones de ECH para los distintos nombres de su sitio. Crea (o aumenta) registros de tipo HTTPS para los dominios de sus sitios (no su nombre público ECH). Tenga en cuenta que los módulos del proveedor de DNS se mantienen de forma independiente y es posible que no se haya probado su compatibilidad con registros de tipo HTTPS. Comuníquese con los encargados del mantenimiento de su módulo si tiene problemas. Si tiene necesidades de configuración más avanzadas, puede usar la configuración JSON (más detalles próximamente; por ahora, consulte el n.° 6862 o consulte el código fuente; o use caddy adapt para convertir un Caddyfile a JSON).

Prueba y verificación de ClientHello cifrado

Primero asegúrese de que Caddy se ejecute correctamente con ECH habilitado (y un módulo DNS) en la configuración. Debería ver registros que indiquen que está generando una configuración ECH y publicándola en su(s) nombre(s) de dominio. Necesitará utilizar un client que admita ECH. Algunas versiones personalizadas de curl lo hacen, y Firefox y los navegadores modernos basados ​​en Chrome también lo hacen, pero primero debe habilitar DNS sobre HTTPS o DNS sobre TLS (ya que, obviamente, consultar DNS en texto sin formato para un nombre de dominio protegido expondrá el dominio y frustrará el propósito de ECH). Si reutiliza un nombre de dominio existente, borre su caché de DNS. Firefox tiene una manera de hacer esto para su caché en about:networking#dns. Una vez que tenga un client adecuado, use Wireshark para capturar paquetes de red mientras carga su sitio. Debería ver solo el nombre externo/público como valores SNI (Indicador de nombre de servidor) en la captura de paquetes. Si en algún momento ve el nombre verdadero del sitio, ECH no está funcionando correctamente; podría ser un problema de client o del servidor. Antes de informar un error, primero intente identificarlo como un problema del servidor. ¡Pero definitivamente informe errores del servidor! ¡Gracias! (Tenga en cuenta que ECH no se publica automáticamente para dominios con CNAME y el dominio ya debe tener un registro en la zona).

caddy v2.10.0

Highlights

  • Encrypted ClientHello (ECH) — Caddy now automatically generates, publishes, and serves ECH configurations (#6862), hiding inner SNI behind a shared outer/public name. Enable it with the global ech and dns options; your binary needs a DNS provider module, and the outer name must point to your server with a valid certificate. Publication requires an existing DNS record and does not cover CNAME’d domains. Test with an ECH-capable client using DoH or DoT—plaintext DNS still exposes the hostname.

  • Hybrid post-quantum TLS by default — Caddy now enables the standardized x25519mlkem768 key-exchange group, improving TLS resilience against future quantum attacks without requiring configuration changes. This release also drops support for older Go minor versions: custom builds and CI pipelines must use the latest Go minor.

  • Wildcard certificates are now preferred — Existing managed wildcard certificates will cover matching subdomains instead of Caddy obtaining individual certificates (#6959), reducing issuance and renewal operations. This can change which certificate clients receive; use tls force_automate to retain per-domain behavior. The experimental auto_https prefer_wildcard option has been removed.

  • Experimental ACME profile support — Initial support lets Caddy request certificate properties beyond traditional CSR constraints, including CA-specific profiles such as Let’s Encrypt’s short-lived certificates. Treat this as opt-in and experimental: profile availability depends on the CA, and Caddy does not use these profiles by default yet.

  • DNS provider plugins must be upgraded — Caddy adopts the libdns 1.0 beta APIs, breaking compatibility with providers built against older interfaces. Update and rebuild custom binaries with compatible provider releases—Cloudflare, RFC2136, and deSEC are among those updated or being updated.

  • Reverse proxy header behavior changes — reverse_proxy now sends a standards-oriented Via header instead of adding a duplicate Server header (#6275). Update downstream middleware, monitoring, or tests that rely on the previous synthesized Server value.

Caddy 2.10 is here! Aside from bug fixes, this release features:

  • Encrypted ClientHello (ECH): This new technology encrypts the last plaintext portion of a TLS connection: the ClientHello, which includes the domain name being connected to. The draft spec for ECH is almost finalized, so we can now support this privacy feature for TLS. This is a powerful but nuanced capability; we highly recommend reading the ECH documentation on our website.
  • Post-quantum (PQC) key exchange: Caddy now supports the standardized x25519mlkem768 cryptographic group by default.
  • ACME profiles: ACME profiles are an experimental draft that allow you to choose properties of your certificates with more flexibility than traditional CSR methods. For example, Let's Encrypt will issue 6-day certificates under a certain profile. Caddy may eventually use that profile by default.
  • Via header: The reverse proxy now sets a Via header instead of a duplicate Server header.
  • Global DNS provider: You can now specify a default "global" DNS module to use instead of having to configure it locally in every part of your config that requires a DNS provider (for example, ACME DNS challenges, and ECH). This is the dns global option in the Caddyfile, or in JSON config, it's the dns parameter in the tls app configuration.
  • Wildcards used by default: Previously, Caddy would obtain individual certificates for every domain in your config literally; now wildcards, if present, will be utilized for subdomains, rather than obtaining individual certificates. This change was motivated by the novel possibility for subdomain privacy afforded by ECH. It can be overridden with tls force_automate in the Caddyfile. The experimental auto_https prefer_wildcard option has been removed.
  • libdns 1.0 APIs: Many of you use DNS provider modules to solve ACME DNS challenges or to enable dynamic DNS. They implement interfaces defined by libdns to get, set, append, and delete DNS records. After 5 years of production experience, including lessons learned with ECH, libdns APIs have been updated and 1.0 beta has been tagged. DNS provider packages will need to update their code to be compatible, which will help ensure stability and well-defined semantics for the future. Several packages have already updated or are in the process of updating (cloudflare, rfc2136, and desec to name a few).
  • Global dns config: Now that several components of Caddy configuration may affect DNS records (ACME challenges, ECH publication, etc.), there is a new dns global option that can be used to specify your DNS provider config in a single place. This prevents repetition of credentials for servers where all the domains are managed by a single DNS provider.

Thank you to the many contributors who have helped to make this possible! :tada: :partying_face: :champagne:

:warning: While have traditionally supported the last 2 minor Go versions to accommodate some distribution / package manager policies, we now only support the latest minor Go version. The privacy and security benefits added in new Go versions (such as post-quantum cryptography) are worth making available to everyone as soon as possible, rather than holding back the entire user base or maintaining multiple code compilation configurations.

Encrypted ClientHello (ECH) details

(This is a brief overview. We recommend reading the full documentation.)

Typically, server names (domain names, or "SNI") are sent in the plaintext ClientHello when establishing TLS connections. With ECH, the true server name is encrypted (and wrapped) by an "outer" ClientHello which has a generic SNI of your choosing. With many sites on the same server sharing the same outer SNI, both clients and the server have more privacy related to domain names.

Caddy implements fully automated ECH, meaning that it generates (and soon, rotates), publishes, and serves ECH configurations simply by specifying a DNS provider, and the outer/public domain name to use.

Fully automated ECH requires a DNS module built into your Caddy binary. In order for a client, such as a browser, to know it can use ECH, and what parameters to use, the server's ECH configuration must be published. This config includes the public name, cryptographic parameters, and a public key for encrypting the inner ClientHello. By convention, browsers read the standardized HTTPS-type DNS record containing a ech SvcParamKey. Caddy sets this DNS record for all domains being protected, but it needs that DNS provider module plugged in and configured in order to do this. If you are already using the DNS ACME challenge, you should already have a DNS provider plugged in. If you prefer to build Caddy from source with a DNS module, it's easy with xcaddy, for example: $ xcaddy build --with github.com/caddy-dns/cloudflare

The minimum config needed to enable ClientHello is also the recommended config, as it maximizes privacy benefits in most situations. You just need the ech global option and a DNS provider specified. Here's an example using Cloudflare as the nameserver:

Caddyfile:

{
	debug  # not required; recommended while testing
	dns cloudflare {env.CLOUDFLARE_API_KEY}
	ech ech.example.net
}

example.com {
	respond "Hello there!"
}

This protects all your sites (example.com in this case) behind the public name of ech.example.net. (As another example, Cloudflare uses cloudflare-ech.com for all the sites it serves. We recommend choosing a single public domain and use it to protect all your sites.)

The outer/public name you choose should point to your server. Caddy will obtain a certificate for this name in order to facilitate safe, reliable connections for clients when needed. Without a certificate, clients may be forced to connect insecurely, or fail to connect at all, in some cases, which not only leaves them vulnerable, but also risks exposing the names of your server's sites.

Caddy then uses the specified DNS provider to publish the ECH config(s) for your various site names. It creates (or augments) HTTPS-type records for the domains of your sites (not your ECH public name). Note that DNS provider modules are independently-maintained, and may not have been tested for compatibility with HTTPS-type records. Please contact your module's maintainers if you experience issues.

If you have more advanced configuration needs, you can use the JSON configuration (more details coming soon; for now, see #6862 or look at the source code; or use caddy adapt to convert a Caddyfile to JSON).

Testing and verifying Encrypted ClientHello

First make sure Caddy runs successfully with ECH enabled (and a DNS module) in the config. You should see logs that it is generating an ECH config and publishing it to your domain name(s).

You will need to use a client that supports ECH. Some custom builds of curl do, and Firefox and modern Chrome-based browsers do as well, but you need to enable DNS-over-HTTPS or DNS-over-TLS first (since, obviously, querying DNS in plaintext for a protected domain name will expose the domain and defeat the purpose of ECH).

If reusing an existing domain name, clear your DNS cache. Firefox has a way of doing this for its cache at about:networking#dns.

Once you have a suitable client, use Wireshark to capture network packets as you load your site. You should see only the outer/public name as SNI (ServerName Indicator) values in the packet capture. If at any time you see the true site name, ECH is not working properly -- it could be a client or server issue. Before filing a bug, please try to pinpoint it as a server issue first. But definitely report server bugs! Thank you!

(Note that ECH is not automatically published for CNAME'd domains, and the domain must already have a record in the zone.)
