Cambios significativos

Bucles de tareas (#73005, #74222, #74275, #74345)

Airflow 3.4.0 presenta Task Loops (AIP-111): un grupo de tareas decorado se puede repetir varias veces. tiempos decididos en tiempo de ejecución usando el bucle .loop(). A conditional loop works like a do ... while - el cuerpo se ejecuta al menos una vez y una condición until decide cuándo detenerse, limitada por max_iterations. Cada iteración puede utilizar el resultado de la iteración anterior y las iteraciones se ejecutan una tras otro (las tareas dentro de una iteración aún pueden ejecutarse en paralelo). Se mantienen los reintentos bajo un UUID por intento para que los datos de cada iteración se conserven y se puedan borrar de forma selectiva.

Para obtener instrucciones de uso detalladas, consulte :doc:/authoring-and-scheduling/loops.

.. nota:: La degradación a cualquier versión anterior a 3.4.0 puede ser lenta, dependiendo del número de Filas de XCom que se han escrito después de la actualización. La actualización se probó en un Mesa XCom de 300 m de fila, así que no se preocupe por el tiempo de actualización (nos aseguramos que los datos de XCom no se hayan tocado ni leído durante la migración para conservarlos rápido).

Esto se debe a que esta versión contiene una migración que comienza a almacenar nuevos XCom. filas en una tabla xcom_v2, y para bajar de categoría tenemos que moverlas a la tabla anterior, y no hay manera de hacer esto sin copiar la valores xcom escritos.

La degradación se niega a continuar cuando encuentra datos que no puede asignar de forma segura. Cada migración se confirma por separado, por lo que las migraciones posteriores 3.4.0 ya se han revertido en ese punto: corrija los datos y vuelva a ejecutar el baje la versión o ejecute airflow db migrate para volver a 3.4.

En MySQL, una falla después de esas comprobaciones deja el esquema parcialmente degradado, ya que MySQL no puede revertir DDL. Hacer una copia de seguridad antes de intentar Se recomienda degradar el MySQL, por lo que se puede restaurar en ese caso.

Pausa elegantemente Dags drenando ejecuciones activas (#72407, #73225, #73055, #73763)

Airflow ahora admite un estado de programación "draining" para Dags. El drenaje impide que el programador crear nuevas ejecuciones de Dag programadas o activadas por activos y al mismo tiempo permitir Dag ya en cola y en ejecución corre para continuar. Las ejecuciones activadas explícitamente siguen permitidas.

Una vez finalizadas las ejecuciones sobresalientes de Dag, Dag pasa automáticamente a "paused". Los usuarios pueden cancele el drenaje para devolver el Dag a active.

Las ejecuciones manuales, los reabastecimientos y las materializaciones de activos en un Dag pausado pueden agotar el Dag en lugar de Reanudarlo: elija Drenar en la interfaz de usuario o configure drain_dag en la solicitud REST API. Drenaje permite que se inicien o reanuden ejecuciones inacabadas del Dag, excepto aquellas mantenidas por reabastecimientos en pausa, no crea ejecuciones programadas y pausa el Dag nuevamente una vez que finalizan todas las ejecuciones inacabadas. Los reabastecimientos en pausa permanecen pausado y debe reanudarse para que finalicen sus carreras y se complete el drenaje.

La programación de la interfaz de usuario, REST API y airflowctl expose the active, draining, and paused estados, y la lista de Dags puede pausar, drenar o reanudar la pausa de varios Dags seleccionados a la vez. existente is_paused API usage remains supported; use scheduling_state cuando el estado de drenaje debe ser seleccionados o reportados explícitamente.

Los latidos de las tareas ya no los reintenta [workers] execution_api_retries (#73244)

Los latidos tenían dos mecanismos de reintento superpuestos: la tarea SDK API client reintentaba cada solicitud, incluidos los latidos del corazón, y el supervisor contaba por separado los fallos de latidos consecutivos [workers] max_failed_heartbeats. Los reintentos de client también tuvieron el efecto secundario no deseado de bloqueando el bucle del monitor del supervisor mientras retrocedía, por lo que durante una interrupción del servidor API el El supervisor se retrasaría en el envío de registros de tareas y/o en darse cuenta de que el subproceso de tareas se había completado. salió.

Los reintentos de latido ahora se rigen únicamente por max_failed_heartbeats, cuyo valor predeterminado ha sido ajustado desde 3 to 30 para mantener aproximadamente la misma tolerancia para un servidor API inalcanzable que Los dos mecanismos combinados dieron antes.

Si ha configurado [workers] max_failed_heartbeats explícitamente, es posible que desee reconsiderar el valor que han elegido. Ahora es todo el presupuesto de reintento: con el valor predeterminado [trabajadores] min_heartbeat_interval of 5 seconds, the worker tolerates roughly 5 * max_failed_heartbeats segundos de indisponibilidad de API antes de finalizar una tarea en ejecución. Probablemente deberías conservar el valor resultante debajo de cualquier [scheduler] task_instance_heartbeat_timeout configurado (predeterminado 300 segundos).

Los números de intentos de TaskInstance ahora aumentan antes de que comience el siguiente intento (#73554)

.. nota::

Si tiene sistemas externos que analizan los registros de tareas o el estado de TI en busca de una TI lista para reintentar, Deberá estar al tanto de este cambio y actualizar su código.

Por ejemplo, si realizó una solicitud para "OBTENER /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id}esperando obtener información sobre el intento fallido, ahora necesitarás mirarGET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id}/tries/{try_number - 1}``

Airflow ahora asigna el UUID de una instancia de tarea y el número de prueba juntos de manera inmutable para que funcionen de manera consistente. identificar el mismo intento.

Anteriormente, cuando una tarea entraba en el período de recuperación de reintento, se le asignaba un nuevo UUID, pero continuaba. intente el número N y tenga el estado de UP_FOR_RETRY hasta que termine ese período (en cuyo momento ese intento se marcará como FALLADO y se incrementará el número de intento). En cambio, el intento fallido es inmediatamente marcado con el estado FAILED y un nuevo intento creado en el estado UP_FOR_RETRY.

Desaprobar las dependencias del grupo de tareas cyclic (#73746)

Un Dag cuyos grupos de tareas dependen entre sí en un ciclo, cuando cada grupo de tareas se trata como un solo unidad, ahora emite un TaskGroupCycleDeprecationWarning en el momento del análisis y muestra una advertencia Dag en la interfaz de usuario que nombra los grupos de tareas y las tareas involucradas. Estos Dags todavía analizan y ejecutan, porque su las dependencias de tareas son acyclic, pero se planea que Airflow 3.5 las rechace en el momento del análisis.

Una dependencia dentro o fuera de cualquier tarea en un TaskGroup cuenta como una dependencia de todo el grupo, por lo que una La ruta que sale de un grupo de tareas y regresa a él es un ciclo. Por ejemplo, "a >> bridge >> b", con a and b in the same TaskGroup and bridge fuera de él, hace que el grupo dependa de También se establece bridge and bridge depend on the group, even if a >> b.

  • Mover tareas entre grupos de tareas, o fuera de ellos, para que cada grupo dependa de los demás en uno dirección solamente. En el ejemplo anterior, saque bridge into the group, or move b.
  • Para detectar estos Dags en CI, ejecute sus pruebas de Dag con -W error::flujo de aire.sdk.exceptions.TaskGroupCycleDeprecationWarning. La verificación se ejecuta cuando un Dag es agregado a un DagBag, so only tests that load your Dags into a DagBag y afirma que hay no hay errores de importación que los detecten; una prueba que solo importa un archivo Dag no lo hace.

Consulte "Dependencias del grupo de tareas Cyclic" en la documentación de Dags.

Las imágenes de producción y CI de Airflow ahora se basan en Docker Hardened Images <https://dhi.io>_ para Python y Debian 13 "trixie".

Python ya no se compila desde el código fuente durante la creación de la imagen: proviene de la base reforzada imagen en su lugar, que elimina la descarga del código fuente, la verificación de su firma y la compilación mismo de la construcción. Python todavía vive en /usr/python, que ahora es un enlace simbólico al Ubicación /opt/python que utiliza la imagen base, por lo que las rutas dentro de la imagen no cambian.

El argumento de compilación BASE_IMAGE ahora por defecto es ghcr.io/apache/airflow/base/python:<version>-debian13-dev, el espejo público de Airflow del imagen ascendente dhi.io/python, por lo que crear una imagen no necesita credenciales de registro. cualquiera anulando la imagen BASE_IMAGE with a plain debian:bookworm-slim tiene que cambiar a una imagen que ya proporciona Python, o cree el tipo legacy.

El sistema operativo base pasó de Debian 12 "bookworm" a Debian 13 "trixie". Paquetes de biblioteca renombrados en time_t transition (for example libssl3 is now libssl3t64 de 64 bits de trixie) tienen que ser actualizado en RUNTIME_APT_DEPS / ADDITIONAL_RUNTIME_APT_DEPS personalizado y compatible con MySQL client ahora proviene de MariaDB 11.8.

Para la línea 3.4.x, las imágenes de producción se crearon de la manera anterior: Python compiladas a partir de fuentes en Sabor debian:bookworm-slim - are still published as the deprecated legacy, seleccionado con el nuevo argumento de compilación AIRFLOW_IMAGE_FLAVOR="legacy". Se eliminarán en Airflow 3.5.0.

El PYTHON_LTO build argument is gone. To build a FIPS-compliant image, point BASE_IMAGE en un En su lugar, variante FIPS de la imagen reforzada, por ejemplo, dhi.io/python:3.13.16-debian13-fips-dev.

Tarea SDK API client trusts el almacén de certificados del sistema en lugar de certifi (#73116)

Con [api] client_use_public_certs habilitado (el valor predeterminado), la tarea SDK client que habla con el La ejecución API ahora trust almacena el certificado del sistema operativo a través de truststore en lugar de los certifi CA bundle. CAs from [api] ssl_ca_file and [api] ssl_cert todavía están trusted además del almacén del sistema, y certifi ya no es una dependencia de la tarea SDK.

Los trabajadores deben tener las CA públicas en las que confían instaladas en el almacén del sistema (por ejemplo, la Paquete ca-certificates en imágenes basadas en Debian). En macOS y Windows, validación de certificados se delega al sistema operativo, que puede rechazar los certificados de servidor que OpenSSL aceptó, como certificados de CA privada sin el uso de clave extendida serverAuth.

Los trabajadores mayores ya no pueden reanudar las tareas aplazadas cuyo next_kwargs tenga clases personalizadas (#73577)

Cuando se reanuda una tarea diferida en un trabajador con una Tarea SDK anterior, el servidor API ya no reconstruye clases arbitrarias a partir del next_kwargs to convert them to the legacy format. Built-in value types, assets and asset aliases (including asset access control) are still converted, without constructing them. A deferred task whose next_kwargs almacenado. Ahora falla cualquier otra clase en dicho trabajador con un error al nombrar el tipo y solicitar actualizar la Tarea SDK, en lugar de fallar en una carga útil que no puede decodificar.

Qué hacer: si ejecuta trabajadores con apache-airflow-task-sdk 1.1.x or older and your deferrable operators or triggers pass instances of custom classes in next_kwargs (for example via self.defer(..., kwargs=...) or in the trigger event payload), upgrade the Task SDK on those workers to 1.2.0 or later. Newer workers receive next_kwargs unchanged and are not affected. Until all workers are upgraded, pass only built-in values, assets and asset aliases in next_kwargs de tareas que pueden reanudarse en trabajadores mayores.

Los kwargs de devolución de llamada de alerta de fecha límite se decodifican donde se ejecuta la devolución de llamada (#74830)

El programador ya no decodifica los argumentos de palabras clave de las devoluciones de llamadas de alertas de fecha límite. ellos se mantienen en su forma serializada y se decodifican donde se ejecuta la devolución de llamada: por el activador de un AsyncCallback, and by the callback runner on the worker for a SyncCallback.

Los trabajadores que ejecutan alertas de fecha límite SyncCallback necesitan una tarea SDK que incluya este cambio, por lo que actualice apache-airflow and apache-airflow-task-sdk en trabajadores juntos. un trabajador con un apache-airflow actualizado y una tarea anterior SDK fallan en dichas devoluciones de llamada con un error de ejecutarlos. Las devoluciones de llamada creadas antes de la actualización se ejecutan como antes.

Backends XCom personalizados que anulan serialize_value must implement store_value para admitir bucles de tareas (#74858)

Cada iteración de una tarea dentro de un bucle es su propia instancia de tarea, pero serialize_value recibe el mismo dag_id, run_id, task_id, map_index and key para todos ellos, por lo que un backend que construye su ubicación de almacenamiento a partir de ellos hace que XCom de cada iteración leer de nuevo como el valor de la última iteración. Los servidores deben anular store_value y load_value instead, and build the storage location with XComCoordinate.build_path, que es único por instancia de tarea o por escritura cuando la escritura no puede conocer la instancia de tarea.

Un Dag que usa un bucle falla al iniciarse cuando el backend de XCom configurado todavía almacena valores a través de serialize_value, incluso si ya escribe en una ubicación única. Esto incluye XComObjectStorageBackend from apache-airflow-providers-common-io 1.10.1 y anteriores; actualice el proveedor antes de utilizar bucles de tareas con él.

Los backends personalizados del Task State Store también deberán incluir scope.region_id en su clave de almacenamiento para admitir tareas asignadas dentro de un bucle e iteraciones de bucle regeneradas mediante limpieza.

airflow.utils.email está en desuso en favor del proveedor SMTP (#75414)

Las funciones en airflow.utils.email (send_email, send_email_smtp, send_mime_email, build_mime_message and get_email_address_list) ahora vive en airflow.providers.smtp.utils.emailer. The old names still work and raise a DeprecatedImportWarning. El flujo de aire ahora requiere "apache-airflow-providers-smtp>=3.2.0".

Mantenga [email] email_backend set to airflow.utils.email.send_email_smtp. Airflow trata ese valor como "enviar correos electrónicos de tareas con SmtpNotifier", que lee todas las configuraciones SMTP de Connection. Cambiándolo a en su lugar, la ruta del proveedor envía a través de la configuración [smtp].

Si llamas a estas funciones directamente:

  • La conexión SMTP se busca con BaseHook.get_connection. Un script que se ejecuta fuera de Airflow Los procesos necesitan la conexión en una variable de entorno o en un backend secreto, no solo en los metadatos. base de datos.
  • Las configuraciones se leen a través de la configuración de la tarea SDK, por lo que los valores cambian en tiempo de ejecución con airflow.configuration.conf.set() are not seen. airflow.cfg y las variables de entorno funcionan como antes.
  • Las pruebas que parchean airflow.utils.email.send_mime_email ya no interceptan la llamada realizada por send_email_smtp. Patch airflow.providers.smtp.utils.emailer.send_mime_email en su lugar.

  • El servidor API utiliza un segundo grupo de conexiones de base de datos

    Los trabajadores del servidor API ahora ejecutan algunos trabajos de base de datos en el motor asíncrono, así como en el de sincronización, y cada motor tiene su propio grupo de conexiones, dimensionado por el mismo [database] sql_alchemy_pool_size and [database] sql_alchemy_max_overflow settings. What uses the async pool depends on the --apps option of airflow api-server:

    • execution: latidos de la tarea y varias lecturas de la Ejecución API.
    • core: la entrada del registro de auditoría registrada para cada solicitud de escritura a través de REST API o la interfaz de usuario.
    • all (el valor predeterminado): ambos de los anteriores.

    Por lo tanto, en cada modo, un trabajador puede abrir hasta dos veces sql_alchemy_pool_size + sql_alchemy_max_overflow connections (30 with the defaults) and keep up to twice sql_alchemy_pool_size of them idle. Account for this, per [api] workers, when sizing PgBouncer or the database's max_connections. El grupo asíncrono se utiliza desde #67800, #73403, #73407 y #76416. (#76430)

airflow 3.4.0

Highlights

  • Runtime task loops — .loop() supports bounded, conditional do…while iterations with sequential data dependencies and parallel tasks inside each iteration; retry attempts remain isolated by UUID (#73005, #74222, #74275, #74345). Plan rollbacks carefully: XCom v2 requires copying data when downgrading, refuses unsafe mappings, and can leave MySQL partially downgraded because DDL is not transactional—take a backup first.

  • Experimental non-Python DAG support — AIP-85 adds pluggable importers for TypeScript, Go, Java, and schema-validated YAML DAGs, including real operators and explicit templating (#72369, #73728, #73853, #74020, #74084, #74333, #74586). These DAGs appear alongside Python DAGs, but the importer framework and language SDK APIs are experimental and may change.

  • Executor and Postgres migration work — Out-of-tree executors should implement supported_workload_types and trigger_workloads; legacy queue APIs remain as shims but emit RemovedInAirflow4Warning, while connection tests now share the heartbeat budget and take priority over tasks (#63491). Metadata databases default to psycopg3 for sync and async engines, with URL rewriting and statement preparation disabled for transaction-mode PgBouncer; install provider extras and configure explicitly to retain psycopg2 or asyncpg (#68496, #69469).

  • Asset-triggered runs become event-granular — Single-asset schedules, asset OR expressions, AssetOrTimeSchedule, and PartitionedAssetTimetable create one run per event, potentially increasing run volume; set batch_asset_events=True or [scheduler] batch_asset_events and reparse DAGs to retain batching (#68517). Multi-event conditions still batch, airflow db clean now removes pending downstream triggers so deleted events cannot fire runs, and events queued before schedule removal remain eligible to trigger (#70972).

  • Task-instance clearing resets state-store data — Clearing an individual task now deletes its task_state_store entries, so resumed workflows restart instead of reconnecting to checkpoints or external jobs; pass keep_task_state=True or enable the UI setting to preserve them (#72100). Retries and whole-Dag-run clearing retain task state, making this distinction important for cleanup automation.

  • Tighter authorization and team-name migration — Non-DAG audit rows now require AUDIT_LOGS_ALL; FAB custom roles need explicit All Audit Logs.can_read, while unsupported views are denied with a warning instead of causing a server error (#70759). Team names are restricted to lowercase characters and single underscores, migration refuses case-only name collisions, and legacy names containing __ continue working but make airflow teams sync fail until renamed (#70886).

Significant Changes

Task Loops (#73005, #74222, #74275, #74345)

Airflow 3.4.0 introduces Task Loops (AIP-111): a decorated task group can be repeated a number of times decided at runtime using .loop(). A conditional loop works like a do ... while loop - the body runs at least once and an until condition decides when to stop, bounded by max_iterations. Each iteration can use the previous iteration's result and iterations run one after another (tasks within an iteration can still run in parallel). Retried attempts are kept under a per-attempt UUID so each iteration's data is preserved and can be cleared selectively.

For detailed usage instructions, see :doc:/authoring-and-scheduling/loops.

.. note:: Downgrading to any version earlier than 3.4.0 can be slow, depending on the number of XCom rows that have been written after upgrading. Upgrading was tested on a 300m row XCom table, so please don't worry about upgrade time (we made sure that the XCom data didn't get touched or read during migration to keep it fast).

This is because this release contains a migration that starts storing new XCom rows in an xcom_v2 table, and in order to downgrade we have to move those over to the old table, and there is no way of doing this without copying the written xcom values.

The downgrade refuses to continue when it finds data it cannot map back safely. Each migration commits separately, so the later 3.4.0 migrations have already been reversed at that point: fix the data and re-run the downgrade, or run airflow db migrate to return to 3.4.

On MySQL a failure after those checks leaves the schema partly downgraded, as MySQL cannot roll back DDL. Taking a backup before attempting the downgrade on MySQL is advised, so it can be restored in that case.

Dag Importer for non-Python Dags (#72369, #73728, #73853, #74020, #74084, #74333, #74586)

Airflow 3.4.0 can author an entire Dag - schedule, tasks, and dependencies - in a language other than Python. AIP-85 adds a pluggable Dag Importer in the Task SDK that teaches the Dag processor to recognize source formats beyond .py: each format registers an importer, the processor runs the matching language runtime, and the resulting Dags surface in Airflow like Python Dags. The formats that land on it are the TypeScript, Go, and Java language SDKs and a native YAML Dag format (a .yaml file with a $schema marker, validated against a schema and built into real operators, with explicit templating). The Dag Importer framework and the language SDKs are experimental in 3.4 and their APIs may change.

For detailed usage instructions, see :doc:/administration-and-deployment/dag-importers.

Unify executor workload queues under BaseExecutor.executor_queues (#63491)

Executor workload state is now stored on the unified BaseExecutor.executor_queues mapping keyed by WorkloadType and scheduled through trigger_workloads. The previous per-type attributes and entrypoints (queued_tasks, queued_callbacks, supports_callbacks, trigger_tasks, order_queued_tasks_by_priority) and the Airflow 3.3 connection-test surface are folded into this mapping and kept as backward-compatible shims that emit RemovedInAirflow4Warning (to be removed in Airflow 4.0). Out-of-tree executors should declare supported_workload_types and implement trigger_workloads. Connection tests are now admitted under the same per-heartbeat budget as tasks and prioritized ahead of them. See #63491 <https://github.com/apache/airflow/pull/63491>_ for the full migration guide.

psycopg3 is now the default Postgres driver (#68496)

psycopg3 (psycopg) is now the default driver for the metadata database, for both the sync and the async engine, replacing psycopg2 and asyncpg. A bare postgresql:// (or a legacy postgres:// / postgres+psycopg2://) sql_alchemy_conn is rewritten to postgresql+psycopg://, and the derived async URL uses postgresql+psycopg_async:// when psycopg3 is installed (falling back to asyncpg otherwise). Airflow also disables psycopg3's server-side statement preparation (prepare_threshold = None) so the metadata database works out of the box behind transaction-mode PgBouncer, the recommended production setup. To keep psycopg2 or asyncpg, install the apache-airflow-providers-postgres[psycopg2] / [asyncpg] extra and configure the connection explicitly; see #68496 and #69469 for details, including how to re-enable statement preparation.

Asset-triggered Dags create one run per event by default (#68517)

Single-asset schedules and asset OR expressions now create one Dag run per event instead of consuming all queued events in one run. This also applies to AssetOrTimeSchedule and PartitionedAssetTimetable.

To retain batching, set batch_asset_events=True on the timetable or enable [scheduler] batch_asset_events and reparse the affected Dags. Already serialized timetables without this option retain their previous batching behavior until reparsed.

Schedules requiring several events, including schedule=[a, b], asset AND expressions, and partitioned timetables using RollupMapper, continue to batch by default. Explicitly setting batch_asset_events=False for these schedules raises a timetable validation error.

Custom graph colors return via ui_color and ui_fgcolor (#68760)

The ui_color and ui_fgcolor attributes on operators and TaskGroups color the graph view again -- the node fill from ui_color and the operator label from ui_fgcolor, as they did in Airflow 2. They were silently ignored since Airflow 3.0.

The value can be a raw color (a hex code like #e8b7e4 or a CSS name) or a Chakra theme token -- a palette token such as blue.500 or a semantic token such as brand.solid that adapts to light and dark mode (including tokens added through custom UI theming); a token resolves through a theme-controlled CSS variable. The node border keeps reflecting the task-instance run state; the custom color is applied to the fill and label only.

validate_key now raises ValueError instead of AirflowException (#68890)

The airflow.utils.helpers.validate_key utility now raises ValueError instead of AirflowException when an invalid key is provided (for example an invalid format or a length-limit violation).

The deprecated Dataset alias has been removed from the airflow module (#70154)

Use Asset from airflow.sdk instead.

Audit log rows not tied to a Dag now require the AUDIT_LOGS_ALL view (#70759)

Rows in the audit log whose dag_id is NULL record operations that are not tied to a Dag, such as Connection, Variable and Pool changes. They were returned to any caller that could read event logs at all, because there is no per-Dag key to authorize them on and both read paths fell back to a Dag-level audit log check.

They are now gated on a dedicated AccessView.AUDIT_LOGS_ALL, in the same way AccessView.IMPORT_ERRORS_ALL gates import errors for files with no registered Dag. Rows bound to a Dag keep their existing per-Dag check.

  • GET /eventLogs no longer returns rows with a NULL dag_id to callers without the new view, and excludes them from total_entries and pagination. GET /eventLogs/{event_log_id} returns 403 for such a row. An id matching no row still returns 404.
  • With the simple auth manager the view is granted to the ADMIN role only. With the FAB auth manager it maps to a new All Audit Logs resource, which ships in the Admin role; custom roles that need to read these rows must be granted All Audit Logs.can_read explicitly.
  • An auth manager that cannot map a requested AccessView now denies that view and emits a UserWarning instead of raising KeyError. This affects auth managers older than the core they run against, which previously failed the request with a server error.

Team names must now be lower case, and cannot contain two consecutive underscores (#70886)

airflow teams create and airflow teams sync now accept only names matching (?!.*__)[a-z0-9_-]{3,50} -- lower case letters, digits, hyphens and single underscores. Upper case letters and __ were previously accepted.

A team name is embedded in the AIRFLOW_CONN__<TEAM>___<ID> environment variable namespace that holds team scoped secrets, and the backend upper-cases the name when it builds that variable. data_eng and Data_Eng therefore resolved a single namespace between them, and a name containing ___ could not be told apart from the separator.

airflow db migrate lower-cases every stored team name, moving that team's Dag bundles, Connections, Variables, Pools and Triggers with it. Two stored names that differ only in case would collapse onto one row and silently merge two teams, so migration refuses to start while any such pair exists -- rename all but one first. Names that stay invalid for another reason, such as containing __, are migrated as they are; they keep working, but airflow teams sync exits non-zero until they are renamed.

Changes to how pending asset events trigger Dag runs (#70972)

Deleting asset event records with airflow db clean now also removes any asset events that are still pending for a downstream Dag. This mainly affects Dags waiting on a multi-asset condition, where a pending event can be purged before the condition is met. Deleting an asset event now consistently means it will not trigger a run; previously such a pending trigger could still fire after the event had been purged.

Relatedly, an asset event that was queued for a Dag while it was scheduled on that asset is still used to trigger the run, and appears among the run's triggering events, even if the asset is later removed from the Dag's schedule. Previously, they were silently dropped.

Callbacks now redeem a single-use token before they run (#71192)

A worker now redeems a callback's single-use token with the API server (PATCH /execution/callbacks/{callback_id}/run) before importing and running the callback. Redeeming the token moves the callback from queued to running and swaps it for a short-lived execution-scoped token. Before this change a callback ran without the worker making any authenticated call, so the token minted for it was never checked.

Because the token is single-use, a redelivered or replayed message that reaches a callback that is already running or finished is refused rather than run again. A worker on 3.4 needs an API server that serves this endpoint; a worker talking to an older API server negotiates the API version and behaves as though the endpoint is not there.

Clearing a task now discards its task state store entries by default (#72100)

Clearing a task instance now discards its task_state_store entries, so the next attempt starts from the beginning instead of resuming from a checkpoint or reconnecting to an external job recorded by the cleared attempt. Retries are unaffected and keep task state as before. This applies to clearing individual task instances (the clear endpoint/dialog and airflowctl tasks/dags clear); clearing a whole Dag run still keeps task state (tracked in #72929 <https://github.com/apache/airflow/issues/72929>_). To preserve the old behaviour, pass keep_task_state=True (or tick "keep task state" in the clear dialog; a per-browser default is available under Settings > Clearing). Note a task-instance clear now also deletes task_state_store rows for that task instance.

[core] execute_tasks_new_python_interpreter now applies to Airflow 3 task processes (#72164)

On Airflow 3 the option had no effect on task execution (only the Edge worker read it). When set to True, the task supervisor now exec\ s a fresh interpreter right after forking the task process, which prevents the fork from inheriting a lock held by a supervisor thread (a permanent hang at the task's first TLS call). Deployments that kept the option True from Airflow 2 get this behaviour, and its per-task interpreter start-up cost, on upgrade without further action; set it to False to keep bare fork. The task process reads the global value, so a team-scoped Edge setting alone does not turn it on. Edge workers with the option True already start a fresh interpreter for the supervisor and will now start a second one for the task. The Dag processor, the triggerer and task callbacks (which the callback supervisor runs from a closure that cannot be named for an exec'd child) are not affected and keep bare fork.

Gracefully pause Dags by draining active runs (#72407, #73225, #73055, #73763)

Airflow now supports a draining scheduling state for Dags. Draining stops the scheduler from creating new scheduled or asset-triggered Dag runs while allowing already queued and running Dag runs to continue. Explicitly triggered runs remain allowed.

After outstanding Dag runs finish, the Dag automatically transitions to paused. Users can cancel draining to return the Dag to active.

Manual runs, backfills and asset materializations on a paused Dag can drain the Dag instead of unpausing it: choose Drain in the UI, or set drain_dag in the REST API request. Draining lets unfinished runs of the Dag start or resume, except those held by paused backfills, creates no scheduled runs, and pauses the Dag again once all unfinished runs finish. Paused backfills remain paused and must be resumed for their runs to finish and draining to complete.

The UI, REST API, and airflowctl expose the active, draining, and paused scheduling states, and the Dags list can pause, drain, or unpause several selected Dags at once. Existing is_paused API usage remains supported; use scheduling_state when the draining state must be selected or reported explicitly.

Reparsing a file with no registered Dag now requires the REPARSE_ALL view (#72896)

A file that failed to import before defining any Dag has no per-Dag key to authorize a reparse against, so PUT /parseDagFile/{file_token} previously returned 404 for it. Reparsing such a file is now gated on a dedicated AccessView.REPARSE_ALL -- a write action of its own, distinct from the permission to view import errors -- and the Dag import errors modal gains a reparse action for these files.

  • PUT /parseDagFile/{file_token} for a file with no registered Dag authorizes against REPARSE_ALL and returns 403 when the caller lacks it, instead of 404. A file that has a registered Dag keeps its existing per-Dag can_edit check.
  • With the simple auth manager the view is granted to the ADMIN role only. With the FAB auth manager it maps to a new All Reparses resource, which ships in the Admin role; custom roles that need to reparse such files must be granted All Reparses.can_read explicitly.

Removed the --file-io option from the airflow info command (#73054)

--file-io uploaded the report to file.io and printed a shareable link. file.io no longer accepts anonymous uploads, so the option could not succeed; it also ended in an unhandled traceback rather than reporting the failure.

Redirect the output instead::

airflow info --anonymize > airflow-info.txt

Note that --file-io applied --anonymize implicitly. Pass --anonymize explicitly when sharing a report: plain airflow info prints connection strings, including passwords, in cleartext.

Task heartbeats are no longer retried by [workers] execution_api_retries (#73244)

Heartbeats had two overlapping retry mechanisms: the Task SDK API client retried every request, including heartbeats, and the supervisor separately counted consecutive heartbeat failures against [workers] max_failed_heartbeats. The client retries also had the unwanted side-effect of blocking the supervisor's monitor loop while it backed off, so during an API server outage the supervisor would be delayed forwarding task logs and/or noticing that the task subprocess had exited.

Heartbeat retries are now governed solely by max_failed_heartbeats, whose default has been adjusted from 3 to 30 to keep roughly the same tolerance for an unreachable API server as the two mechanisms combined gave before.

If you have set [workers] max_failed_heartbeats explicitly, you may wish reconsider value you have chosen. It is now the whole retry budget: with the default [workers] min_heartbeat_interval of 5 seconds, the worker tolerates roughly 5 * max_failed_heartbeats seconds of API unavailability before terminating a running task. You should likely keep the resulting value below any configured [scheduler] task_instance_heartbeat_timeout (default 300 seconds).

Deadline alert callbacks validated at parse time; numeric intervals deprecated (#73294)

DeadlineAlert now refuses a callback that is not exactly AsyncCallback or SyncCallback, so a subclass fails when the Dag is parsed rather than when the scheduler reads it back. The scheduler decodes stored callbacks by exact class name so no class named by a Dag author is imported or instantiated there, which means a subclass could be written and then never read.

Passing a number as the interval is deprecated and now emits RemovedInAirflow4Warning. It is still accepted and taken as a count of seconds, but the supported types are timedelta and VariableInterval. A timedelta subclass such as pendulum.duration(...) is accepted and normalized to a plain timedelta, where previously it passed validation and then failed during serialization. interval=True is refused, because bool is an int subclass and would otherwise be taken as one second.

The POST /assets/{asset_id}/materialize endpoint now requires a JSON request body (#73328)

Previously a request with no body was accepted and the asset was materialized with default values. The endpoint now requires an explicit JSON body, consistent with the other mutating endpoints: a request without a body is rejected with 422, and an empty HTML form is not a valid input anymore. All body fields remain optional, so an empty object ({}) is a valid body.

TaskInstance try numbers now increase before the next try starts (#73554)

.. note::

If you have any external systems that look at task logs or TI state for an up-for-retry TI, you will need to be aware of this change and update your code.

For example, if you made a request to GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id} expecting to get info about the failed try, you will now need to look at GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id}/tries/{try_number - 1}

When a task is up_for_retry, try_number now identifies the upcoming try. To retrieve the try that failed, request /tries/{try_number - 1}. The UI shows the pending try and provides a link to the previous try's logs.

Airflow now allocates a task instance's UUID and try number together immutably so they consistently identify the same try.

Previously when a task entered the retry cooldown period, it would be given a new UUID, but keep on try number N and have the state of UP_FOR_RETRY until that period was up (at which point that try would be marked FAILED and the try number incremented). Instead, the failed try is immediately marked with state of FAILED, and a new try created in state UP_FOR_RETRY.

Deprecate cyclic TaskGroup dependencies (#73746)

A Dag whose TaskGroups depend on each other in a cycle, when each TaskGroup is treated as a single unit, now issues a TaskGroupCycleDeprecationWarning at parse time and shows a Dag warning in the UI that names the TaskGroups and tasks involved. These Dags still parse and run, because their task dependencies are acyclic, but Airflow 3.5 is planned to reject them at parse time.

A dependency into or out of any task in a TaskGroup counts as a dependency of the whole group, so a path that leaves a TaskGroup and comes back into it is a cycle. For example, a >> bridge >> b, with a and b in the same TaskGroup and bridge outside it, makes the group depend on bridge and bridge depend on the group, even if a >> b is also set.

  • Move tasks between TaskGroups, or out of them, so that each group depends on the others in one direction only. In the example above, move bridge into the group, or move b out of it.
  • To catch these Dags in CI, run your Dag tests with -W error::airflow.sdk.exceptions.TaskGroupCycleDeprecationWarning. The check runs when a Dag is added to a DagBag, so only tests that load your Dags into a DagBag and assert there are no import errors catch them; a test that only imports a Dag file does not.

See "Cyclic TaskGroup dependencies" in the Dags documentation.

Language SDK coordinators load task handlers from a Dag bundle (#73970)

Put the artifacts in a Dag bundle registered in [dag_processor] dag_bundle_config_list and set task_handler_bundle_name in the coordinator's kwargs, or leave it unset to use the task's own Dag bundle. CI and production images are now based on Docker Hardened Images and Debian 13 (#73038)

Airflow's CI and production images are now based on Docker Hardened Images <https://dhi.io>_ for Python and Debian 13 "trixie".

Python is no longer compiled from source during the image build - it comes from the hardened base image instead, which removes the source download, its signature verification and the compilation itself from the build. Python still lives in /usr/python, which is now a symlink to the /opt/python location the base image uses, so paths inside the image are unchanged.

The BASE_IMAGE build argument now defaults to ghcr.io/apache/airflow/base/python:<version>-debian13-dev, Airflow's public mirror of the upstream dhi.io/python image, so building an image needs no registry credentials. Anyone overriding BASE_IMAGE with a plain debian:bookworm-slim image has to switch to an image that already provides Python, or build the legacy flavor.

The base OS moved from Debian 12 "bookworm" to Debian 13 "trixie". Library packages renamed in trixie's 64-bit time_t transition (for example libssl3 is now libssl3t64) have to be updated in custom RUNTIME_APT_DEPS / ADDITIONAL_RUNTIME_APT_DEPS, and the MySQL-compatible client now comes from MariaDB 11.8.

For the 3.4.x line, production images built the previous way - Python compiled from sources on debian:bookworm-slim - are still published as the deprecated legacy flavor, selected with the new AIRFLOW_IMAGE_FLAVOR="legacy" build argument. They will be removed in Airflow 3.5.0.

The PYTHON_LTO build argument is gone. To build a FIPS-compliant image, point BASE_IMAGE at a FIPS variant of the hardened image instead, for example dhi.io/python:3.13.16-debian13-fips-dev.

Task SDK API client trusts the system certificate store instead of certifi (#73116)

With [api] client_use_public_certs enabled (the default), the Task SDK client that talks to the Execution API now trusts the operating system's certificate store through truststore instead of the certifi CA bundle. CAs from [api] ssl_ca_file and [api] ssl_cert are still trusted in addition to the system store, and certifi is no longer a Task SDK dependency.

Workers must have the public CAs they rely on installed in the system store (for example, the ca-certificates package on Debian-based images). On macOS and Windows, certificate validation is delegated to the operating system, which can reject server certificates that OpenSSL accepted, such as private-CA certificates without the serverAuth extended key usage.

Older workers can no longer resume deferred tasks whose next_kwargs hold custom classes (#73577)

When a deferred task resumes on a worker with an older Task SDK, the API server no longer reconstructs arbitrary classes from the stored next_kwargs to convert them to the legacy format. Built-in value types, assets and asset aliases (including asset access control) are still converted, without constructing them. A deferred task whose next_kwargs hold any other class now fails on such a worker with an error naming the type and asking to upgrade the Task SDK, instead of crashing on a payload it cannot decode.

What to do: if you run workers with apache-airflow-task-sdk 1.1.x or older and your deferrable operators or triggers pass instances of custom classes in next_kwargs (for example via self.defer(..., kwargs=...) or in the trigger event payload), upgrade the Task SDK on those workers to 1.2.0 or later. Newer workers receive next_kwargs unchanged and are not affected. Until all workers are upgraded, pass only built-in values, assets and asset aliases in next_kwargs of tasks that may resume on older workers.

Deadline Alert callback kwargs are decoded where the callback runs (#74830)

The keyword arguments of Deadline Alert callbacks are no longer decoded by the scheduler. They are kept in their serialized form and decoded where the callback runs: by the triggerer for an AsyncCallback, and by the callback runner on the worker for a SyncCallback.

Workers that run SyncCallback Deadline Alerts need a Task SDK that includes this change, so upgrade apache-airflow and apache-airflow-task-sdk on workers together. A worker with an upgraded apache-airflow and an older Task SDK fails such callbacks with an error instead of running them. Callbacks created before the upgrade run as before.

Custom XCom backends that override serialize_value must implement store_value to support task loops (#74858)

Every iteration of a task inside a loop is its own task instance, but serialize_value receives the same dag_id, run_id, task_id, map_index and key for all of them, so a backend that builds its storage location from those makes every iteration's XCom read back as the last iteration's value. Backends should override store_value and load_value instead, and build the storage location with XComCoordinate.build_path, which is unique per task instance, or per write when the write cannot know the task instance.

A Dag that uses a loop fails on startup when the configured XCom backend still stores values through serialize_value, even if it already writes to a unique location. This includes XComObjectStorageBackend from apache-airflow-providers-common-io 1.10.1 and earlier; upgrade the provider before using task loops with it.

Custom Task State Store backends will likewise need to include scope.region_id in their storage key to support mapped tasks inside a loop and loop iterations regenerated by clearing.

airflow.utils.email is deprecated in favor of the SMTP provider (#75414)

The functions in airflow.utils.email (send_email, send_email_smtp, send_mime_email, build_mime_message and get_email_address_list) now live in airflow.providers.smtp.utils.emailer. The old names still work and raise a DeprecatedImportWarning. Airflow now requires apache-airflow-providers-smtp>=3.2.0.

Keep [email] email_backend set to airflow.utils.email.send_email_smtp. Airflow treats that value as "send task emails with SmtpNotifier", which reads all SMTP settings from the Connection. Changing it to the provider path sends through the [smtp] settings instead.

If you call these functions directly:

  • The SMTP Connection is looked up with BaseHook.get_connection. A script that runs outside Airflow's processes needs the Connection in an environment variable or a secrets backend, not only in the metadata database.
  • Settings are read through the Task SDK configuration, so values changed at runtime with airflow.configuration.conf.set() are not seen. airflow.cfg and environment variables work as before.
  • Tests that patch airflow.utils.email.send_mime_email no longer intercept the call made by send_email_smtp. Patch airflow.providers.smtp.utils.emailer.send_mime_email instead.

  • The API server uses a second database connection pool

    API server workers now run some database work on the async engine as well as the sync one, and each engine has its own connection pool, sized by the same [database] sql_alchemy_pool_size and [database] sql_alchemy_max_overflow settings. What uses the async pool depends on the --apps option of airflow api-server:

    • execution: task heartbeats and several Execution API reads.
    • core: the audit log entry recorded for each write request through the REST API or the UI.
    • all (the default): both of the above.

    In every mode a worker can therefore open up to twice sql_alchemy_pool_size + sql_alchemy_max_overflow connections (30 with the defaults) and keep up to twice sql_alchemy_pool_size of them idle. Account for this, per [api] workers, when sizing PgBouncer or the database's max_connections.

    The async pool is used since #67800, #73403, #73407 and #76416. (#76430)
