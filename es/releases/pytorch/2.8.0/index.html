## antorcha.compilar
### Errores de especialización de una forma tensorial con `mark_dynamic` aplicados ahora correctamente (#152661)
Antes de 2.8, era posible que una guarda con una forma simbólica estuviera incorrectamente
omitido si la evaluación de la forma simbólica se probó previamente con guardas
suprimido (esto sucede a menudo dentro del propio compilador). Esto ha sido arreglado
en 2.8 y normalmente simplemente "hará lo correcto" en silencio y agregará la información correcta
guardia. Sin embargo, si la nueva guardia hace que un tensor marcado con `mark_dynamic` se vuelva
especializado, esto puede resultar en un error. Una solución es utilizar
`maybe_mark_dynamic` en lugar de `mark_dynamic`.
Consulte la discusión en el número 157921 para obtener más información.
contexto.
Versión 2.7.0
```python
import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Versión 2.8.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

El código NVTX3 se ha movido de cmake/public/cuda.cmake a cmake/Dependencies.cmake (#151583)

Este es un cambio radical para la interfaz del sistema de compilación. Proyectos downstream que anteriormente obtuvieron NVTX3 a través de cmake/public/cuda.cmake (es decir, llamar a find_package(TORCH REQUIRED)) ahora necesitará configurar explícitamente la compatibilidad con NVTX3 en la propia biblioteca (es decir, usar USE_SYSTEM_NVTX=1). El cambio es para corregir el comportamiento incorrecto donde los proyectos posteriores no pudieron encontrar NVTX3 de todos modos debido a la falta de coincidencia de PROJECT_SOURCE_DIR. Versión 2.7.0:

  • Un proyecto posterior que utilice -DUSE_SYSTEM_NVTX podría encontrar NVTX3 y torch::nvtx3 a través de la lógica cmake/public/cuda.cmake de PyTorch.
  • Un proyecto posterior que NO utilice -DUSE_SYSTEM_NVTX encontraría errores de compilación con CUDA 12.8 o superior. Versión 2.8.0:
  • Un proyecto posterior que utilice -DUSE_SYSTEM_NVTX no podrá encontrar NVTX3 o torch::nvtx3 a través de cmake/public/cuda.cmake de PyTorch. El proyecto posterior ahora necesita encontrar explícitamente NVTX3 y torch::nvtx3 implementando la misma lógica en cmake/Dependences.cmake de PyTorch.
  • Un proyecto posterior que NO utilice -DUSE_SYSTEM_NVTX continuará con la compilación sin NVTX a menos que otra parte del proceso de compilación vuelva a habilitar NVTX.

Deprecaciones

La compatibilidad con MPS para MacOS Ventura se eliminará en 2.9

PyTorch 2.8 es la última versión que admitirá la aceleración de GPU en MacOS Ventura. en el próximo versión (2.9), se requerirá MacOS Sonoma (lanzado en septiembre de 2023) o superior para usar MPS back-end.

torch.ao.quantization está en desuso y se eliminará en 2.10 (#153892)

Para migrar:

  • Cuantización en modo ansioso (torch.ao.quantization.quantize, torch.ao.quantization.quantize_dynamic)
    • Cuantización dinámica y de solo peso: utilice el modo ansioso torchao quantize_.
    • Cuantización estática: utilice la cuantización torchao PT2E.
  • Cuantización en modo gráfico FX (torch.ao.quantization.quantize_fx.prepare_fx, torch.ao.quantization.quantize_fx.convert_fx): utilice la cuantización torchao PT2E (torchao.quantization.quantize_pt2e.prepare_pt2e, torchao.quantization.quantize_pt2e.convert_pt2e). Tenga en cuenta que la cuantificación PT2E se ha migrado a torchao (https://github.com/pytorch/ao/tree/main/torchao/quantization/pt2e). Consulte https://github.com/pytorch/ao/issues/2259 y https://docs.pytorch.org/ao/main/quick_start.html#pytorch-2-export-quantization para obtener más detalles.

La opción dynamo=False (predeterminada actual) para torch.onnx.export está en desuso (#152478, #155580)

El valor predeterminado será dynamo=True a partir de PyTorch 2.9. Se le recomienda migrar para utilizar la opción dynamo=True en torch.onnx.export. Este indicador convierte a torch.export.export en la ruta de exportación predeterminada, reemplazando a TorchScript. Para mantener el comportamiento anterior, establezca dynamo=False explícitamente. Le recomendamos que también experimente con la opción fallback=True que hará que el exportador recurra a la ruta dynamo=False si hay errores.

Tracked Regressions

Windows wheel builds with CUDA 12.9.1 stack overflow during build (#156181)

Due to a bug introduced in CUDA 12.9.1, we are unable to complete full Windows wheel builds with this version, as compilation of torch.segment_reduce() crashes the build. Thus, we provide a wheel without torch.segment_reduce() included in order to sidestep the issue. If you need support for torch.segment_reduce(), please utilize a different version.

torch.compile

Specialization of a tensor shape with mark_dynamic applied now correctly errors (#152661)

Prior to 2.8, it was possible for a guard on a symbolic shape to be incorrectly omitted if the symbolic shape evaluation was previously tested with guards suppressed (this often happens within the compiler itself). This has been fixed in 2.8 and usually will just silently "do the right thing" and add the correct guard. However, if the new guard causes a tensor marked with mark_dynamic to become specialized, this can result in an error. One workaround is to use maybe_mark_dynamic instead of mark_dynamic.

See the discussion in issue #157921 for more context.

Version 2.7.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Version 2.8.0

import torch

x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile

    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))

NVTX3 code has been moved from cmake/public/cuda.cmake to cmake/Dependencies.cmake (#151583)

This is a BC-breaking change for the build system interface. Downstream projects that previously got NVTX3 through cmake/public/cuda.cmake (i.e.. calling find_package(TORCH REQUIRED)) will now need to explicitly configure NVTX3 support in the library itself (i.e. use USE_SYSTEM_NVTX=1). The change is to fix the broken behavior where downstream projects couldn't find NVTX3 anyway due to the PROJECT_SOURCE_DIR mismatch.

Version 2.7.0:

  • A downstream project using -DUSE_SYSTEM_NVTX would be able to find NVTX3 and torch::nvtx3 via PyTorch's cmake/public/cuda.cmake logic.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX would encounter build errors with CUDA 12.8 or above.

Version 2.8.0:

  • A downstream project using -DUSE_SYSTEM_NVTX will not be able to find NVTX3 or torch::nvtx3 via PyTorch's cmake/public/cuda.cmake. The downstream project now needs to explicitly find NVTX3 and torch::nvtx3 by implementing the same logic in PyTorch's cmake/Dependences.cmake.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX will proceed building without NVTX unless another part of the build process re-enables NVTX.
