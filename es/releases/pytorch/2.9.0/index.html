A continuación se muestran los release note completos para esta versión. # Cambios incompatibles hacia atrás ## La versión mínima admitida de Python ahora es 3.10 (#162310) La versión mínima de Python requerida para PyTorch 2.9.0 es 3.10. También tenemos 3.14 y 3.14t disponibles como vista previa con esta versión. ## Comportamiento indefinido cuando una salida de un operador personalizado comparte almacenamiento con una entrada Este es un recordatorio de que las salidas de los operadores personalizados de PyTorch (que se registran mediante `torch.library` o `TORCH_LIBRARY` API) no pueden devolver tensores que compartan almacenamiento con tensores de entrada. La violación de esta condición conduce a un comportamiento indefinido: a veces el resultado será correcto, a veces será basura. Después de [#163227](https://github.com/pytorch/pytorch/pull/163227), los operadores personalizados que violaron esta condición que anteriormente devolvía resultados correctos en `torch.compile` ahora pueden devolver resultados silenciosamente incorrectos en `torch.compile`. Debido a que esto está cambiando el comportamiento de un comportamiento indefinido, no lo consideramos un error, pero aún lo estamos documentando en esta sección como un "cambio de comportamiento potencialmente inesperado". Esta es una de las condiciones verificadas por [`torch.library.opcheck`](https://docs.pytorch.org/docs/stable/library.html#testing-custom-ops) y se menciona en [El manual de operadores personalizados](https://docs.google.com/document/d/1_W62p8WJOQQUzPsJYa7s701JXt0qf2OfLub2sbkHOaU/edit?tab=t.0#bookmark=id.4c0um7xkba6e) ### Más detalles Las salidas de los operadores personalizados de PyTorch no pueden devolver tensores que comparten almacenamiento con tensores de entrada. Por ejemplo, los dos operadores personalizados siguientes no son operadores personalizados válidos: ```py @torch.library.custom_op("mylib::foo", mutates_args=()) def foo(x: torch.Tensor) -> torch.Tensor: # the result of `foo` must not directly be an input to foo. return x

@torch.library.custom_op("mylib::bar", mutates_args=()) def bar(x: torch.Tensor) -> torch.Tensor: # the result of bar must not be a view of an input of bar return x.view(-1)

La solución más sencilla es agregar un `.clone()` adicional a las salidas:
```py
@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

Una forma común de llegar a esta situación es que un usuario quiera crear un operador personalizado que a veces mute la entrada en el lugar y a veces devuelva un nuevo tensor, como en el siguiente ejemplo.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

Este dinamismo no se sustenta y conduce a comportamientos indefinidos. La solución es dividir el operador personalizado en dos operadores personalizados, uno que siempre muta la entrada en el lugar y otro que siempre devuelve un nuevo tensor.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

Construya núcleos metálicos de MacOS-14+ y elimine toda la lógica específica anterior a MacOS-14; requiere MacOS-14+ en adelante (#159733, #159912)

PyTorch MPS solo es compatible con MacOS-14 o posterior. Si necesita utilizar MPS en MacOS Ventura, evite actualizar a Python-3.9 o superior

Actualice a DLPack 1.0 (#145000)

Esta actualización realiza los mismos cambios radicales que la versión DLPack. Los objetos en torch.utils.dlpack se han actualizado para reflejar estos cambios, como DLDeviceType. Consulte el PR para obtener detalles sobre los cambios exactos y cómo actualizar su código.

Generar errores apropiados en torch.cat (#158249)

torch.cat ahora genera ValueError, IndexError o TypeError cuando corresponda en lugar del genérico RuntimeError. Si su código detecta estos errores, puede actualizarlo para detectar el nuevo tipo de error.

Valor predeterminado dynamo=True para el exportador ONNX (#159646, #162726)

Anteriormente, torch.onnx.export(...) usaba el exportador TorchScript heredado si no se proporcionaban argumentos. El exportador ONNX ahora utiliza la canalización torch.export.export más nueva de forma predeterminada (dynamo=True). Este cambio mejora la fidelidad de los gráficos y las exportaciones preparadas para el futuro, pero puede revelar errores de captura de gráficos que anteriormente estaban enmascarados o manejados de manera diferente. Anteriormente en la antorcha 2.8.0:

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Ahora en antorcha 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Recomendación: primero pruebe el nuevo valor predeterminado; solo retroceda si encuentra problemas de bloqueo y los informa en sentido ascendente. Solución a largo plazo: solucionar la causa raíz en lugar de depender del respaldo o del exportador TorchScript.

Desactive las afirmaciones en tiempo de ejecución de forma predeterminada en Exportar en favor de una función de protección de formas (#160111, #161178, #161794)

Para habilitar las afirmaciones en tiempo de ejecución, utilice export(..., prefer_deferred_runtime_asserts_over_guards=True). También elimina la bandera allow_complex_guards_as_runtime_asserts, fusionándola con la opción anterior. Además, exported_program.module() generará una llamada a un submódulo _guards_fn que ejecutará comprobaciones adicionales en las entradas. Los usuarios que no quieran este comportamiento pueden eliminar esta llamada en el gráfico o hacer exported_program.module(check_guards=False) para evitar la generación.

Establecer el opset predeterminado en 20 en ONNX (#158802)

Opset 20 permite definiciones de operadores más nuevas. Si sus herramientas o tiempo de ejecución posterior solo admiten el opset 18, fíjelo explícitamente. Para los operadores ONNX más recientes, puede experimentar con el opset 23. Anteriormente en la antorcha 2.8.0:

# opset_version=18
torch.onnx.export(...)

Ahora en antorcha 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

Suelte draft_export en el exportador API (#161454, #162225)

Elimine el seguimiento de borradores implícito de la ruta del exportador predeterminado, logrando un comportamiento más claro y fallas más rápidas. La costosa ruta de diagnóstico torch.export.draft_export ya no se invoca automáticamente (lo que podría llevar horas en modelos grandes). Aún puedes optar por recibir diagnósticos profundos: Anteriormente en la antorcha 2.8.0:

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

Ahora en antorcha 2.9.0:

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both
# fail:

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Eliminar torch.onnx.dynamo_export y el backend de compilación de la antorcha onnxrt (#158130, #158258)

Se elimina torch.onnx.dynamo_export. Utilice torch.onnx.export en su lugar. El backend de compilación experimental de ONNX Runtime (torch.compile(backend="onnxrt")) ya no es compatible.

Eliminar torch.onnx.enable_fake_mode (#161222)

El modo dynamo=True utiliza FakeTensor de forma predeterminada, lo que ahorra memoria.

Algunas utilidades públicas de ONNX API para el exportador basado en TorchScript ahora son privadas (#161323)

Se eliminan los miembros obsoletos en torch.onnx.verification. Ya no se podrá acceder a las funciones anteriormente privadas del torch.onnx.symbolic_opsets*. Considere hacer una copia del código fuente si necesita acceder a funciones privadas para lograr compatibilidad con el exportador basado en TorchScript.

Eliminar torch.onnx.symbolic_caffe2 (#157102)

La compatibilidad con caffe2 en el exportador ONNX finalizó y se eliminó.

Eliminar el indicador /d2implyavx512upperregs que ralentiza la compilación (#159431)

Las optimizaciones AVX512 reintroducidas para las compilaciones de Windows VS2022 pueden causar problemas con versiones específicas de VS2022; consulte el n.° 145702

Agregue ScalarType a la conversión de cuña y stable::Tensor.scalar_type (#160557)

Antes, las extensiones de usuario solo podían pasar de forma abstracta tipos de caracteres ofuscados que aparecían como int32_ts. Ahora, los usuarios pueden utilizar con confianza torch::headeronly::ScalarType en sus extensiones para los principales tipos escalares. Este PR permite la estabilidad de ABI al agregar una capa de traducción a través del shim, de modo que incluso si los valores de enumeración ScalarType cambian en el futuro, las extensiones de usuario no deben temer. Este cambio agrega compatibilidad con ScalarType para extensiones de usuario y solo se rompe por poco BC para tipos de d impopulares: quint*, qint*, Bits*, dummy_uint*, dummy_int*, Float8_e8m0fnu y Float4_e2m1fn_x2 en el caso de uso en el que una extensión recupera un tipo de tensor del anterior y lo pasa a aoti_torch_call_dispatcher.

Deprecaciones

Desaprobar el parámetro pin_memory_device en torch.utils.data.DataLoader (#158323)

Movemos la habilitación de pin_memory nuevamente dentro de BaseDataLoaderIter. Esto es necesario para StatefulDataloader que aprovechó BaseDataLoaderIter directamente en lugar del inicio de clase Dataloader.

Desaprobar torch.export.export_for_training API en favor del equivalente torch.export.export API (#158203)

torch.export.export_for_training existe porque no pudimos migrar los usos internos de exportación al IR final. Ahora que hemos completado la migración, desaprobamos y eliminamos este API.

Backwards Incompatible Changes

Min supported Python version is now 3.10 (#162310)

The minimum version of Python required for PyTorch 2.9.0 is 3.10. We also have 3.14 and 3.14t available as preview with this release.

Undefined behavior when an output of a custom operator shares storage with an input

This is a reminder that outputs of PyTorch custom operators (that are registered using the torch.library or TORCH_LIBRARY APIs) are not allowed to return Tensors that share storage with input tensors. The violation of this condition leads to undefined behavior: sometimes the result will be correct, sometimes it will be garbage.

After #163227, custom operators that violated this condition that previously returned correct results under torch.compile may now return silently incorrect results under torch.compile. Because this is changing the behavior of undefined behavior, we do not consider this to be a bug, but we are still documenting it in this section as a "potentially unexpected behavior change".

This is one of the conditions checked for by torch.library.opcheck and is mentioned in The Custom Operators Manual

More details

Outputs of PyTorch custom operators are not allowed to return Tensors that share storage with input tensors

For example, the following two custom operators are not valid custom operators:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    # the result of `foo` must not directly be an input to foo.
    return x

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    # the result of bar must not be a view of an input of bar
    return x.view(-1)

The easiest workaround is to add an extra .clone() to the outputs:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

A common way to get into this situation is for a user to want to create a custom operator that sometimes mutates the input in-place and sometimes returns a new Tensor, like in the following example.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

This dynamism is not supported and leads to undefined behavior. The workaround is to split the custom operator into two custom operators, one that always mutates the input in-place, and another that always returns a new Tensor.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

torch.cat now raises ValueError, IndexError or TypeError where appropriate instead of the generic RuntimeError. If you code was catching these errors, you can update to catch the new error type.

Default to dynamo=True for ONNX exporter (#159646, #162726)

Previously torch.onnx.export(...) used the legacy TorchScript exporter if no arguments were provied. The ONNX exporter now uses the newer torch.export.export pipeline by default (dynamo=True). This change improves graph fidelity and future-proofs exports, but may surface graph capture errors that were previously masked or handled differently.

Previously in torch 2.8.0:

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Recommendation: first try the new default; only fall back if you hit blocking issues and report them upstream. Long term solution: fix the root cause instead of relying on fallback or TorchScript exporter.

Switch off runtime asserts by default in Export in favor of a shape guards function (#160111, #161178, #161794)

To enable runtime asserts, use export(..., prefer_deferred_runtime_asserts_over_guards=True). Also kills the allow_complex_guards_as_runtime_asserts flag, merging it into the former option.

Additionally, exported_program.module() will generate a call to a _guards_fn submodule that will run additional checks on inputs. Users who do not want this behavior can either remove this call in the graph, or do exported_program.module(check_guards=False) to avoid the generation.

Previously in torch 2.8.0:

# opset_version=18
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

Previously in torch 2.8.0:

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

Now in torch 2.9.0:

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Add ScalarType to shim conversion and stable::Tensor.scalar_type (#160557)

Before, user extensions could only in abstract pass around obfuscated dtypes appearing as int32_ts. Now, users can confidently use torch::headeronly::ScalarType in their extensions for major scalar types. This PR enables ABI stability by adding a translation layer through the shim, so that even if the ScalarType enum values change in the future, user extensions need not fear.

This change adds ScalarType support for user extensions and is only narrowly BC breaking for unpopular dtypes: quint*s, qint*s, Bits*, dummy_uint*s, dummy_int*s, Float8_e8m0fnu, and Float4_e2m1fn_x2 in the use case where an extension retrieves a Tensor dtype of the above and passes it into aoti_torch_call_dispatcher.
