CARACTERÍSTICAS BETA

[Beta] Backend CuDNN para SDPA

El backend cuDNN "Fused Flash Attention" se implementó para torch.nn.functional.scaled_dot_product_attention. En las GPU NVIDIA H100, esto puede proporcionar hasta un 75 % de aceleración con respecto a FlashAttentionV2. Esta aceleración está habilitada de forma predeterminada para todos los usuarios de SDPA en GPU H100 o más nuevas.

[Beta] torch.compile compilación regional sin recompilaciones

Compilación regional sin recompilaciones, a través de torch._dynamo.config.inline_inbuilt_nn_modules que por defecto es True en 2.5+. Esta opción permite a los usuarios compilar un nn.Module repetido (por ejemplo, una capa de transformador en LLM) sin recompilaciones. En comparación con la compilación del modelo completo, esta opción puede generar latencias de compilación más pequeñas con una degradación del rendimiento del 1 % al 5 % en comparación con la compilación del modelo completo. Consulte el tutorial para obtener más información.

[Beta] Optimización del backend de la CPU de TorchInductor

Esta característica avanza en la optimización del backend de la CPU de Inductor, incluida la generación de código de backend CPP y fusiones FX con núcleos de CPU personalizados. El backend de la CPU de Inductor admite la vectorización de tipos de datos comunes y todas las operaciones de IR de Inductor, junto con las formas estáticas y simbólicas. Es compatible con los sistemas operativos Linux y Windows y admite el contenedor predeterminado Python, el contenedor CPP y el modo AOT-Inductor. Además, amplía el modo de ajuste automático máximo de la plantilla GEMM (creada en 2.5), ofreciendo mayores ganancias de rendimiento. El backend admite varias fusiones de efectos, descendiendo a núcleos personalizados como oneDNN para operaciones lineales/conv y SDPA. El backend de la CPU Inductor logra consistentemente aceleraciones de rendimiento en tres conjuntos de pruebas comparativas (TorchBench, Hugging Face y timms), superando el modo ansioso en 97.5% de los 193 modelos probados.

CARACTERÍSTICAS DEL PROTOTIPO

[Prototipo] FlexAttention

Hemos introducido un API flexible que permite implementar varios mecanismos de atención, como ventana deslizante, máscara causal y PrefixLM con solo unas pocas líneas de código idiomático de PyTorch. Este API aprovecha torch.compile para generar un kernel FlashAttention fusionado, que elimina la asignación de memoria adicional y logra un rendimiento comparable al de las implementaciones escritas a mano. Además, generamos automáticamente el pase hacia atrás utilizando la maquinaria de autogrado de PyTorch. Además, nuestro API puede aprovechar la escasez en la máscara de atención, lo que resulta en mejoras significativas con respecto a las implementaciones de atención estándar. Para obtener más información y ejemplos, consulte la [publicación del blog oficial] (https://pytorch.org/blog/flexattention/) y el [Gimnasio de atención] (https://github.com/pytorch-labs/attention-gym).

[Prototipo] Autogrado compilado

Autograd compilado es una extensión de la pila PT2 que permite capturar todo el pase hacia atrás. A diferencia del gráfico hacia atrás rastreado por el despachador AOT, el seguimiento de Autograd compilado se difiere hasta el momento de ejecución hacia atrás, lo que lo hace inmune a las interrupciones del gráfico de paso hacia adelante y le permite registrar ganchos hacia atrás en el gráfico. Consulte el tutorial para obtener más información.

[Prototipo] Registrador de vuelo

Flight recorder es una nueva herramienta de depuración que ayuda a depurar trabajos atascados. La herramienta funciona capturando continuamente información sobre los colectivos mientras se ejecutan. Al detectar un trabajo atascado, la información se puede utilizar para identificar rápidamente rangos/máquinas que se comportan mal junto con seguimientos de la pila de códigos. Para obtener más información, consulte el siguiente tutorial.

[Prototipo] Compatibilidad con Max-autotune en CPU con plantilla GEMM

El modo de ajuste automático máximo para el backend de la CPU Inductor en torch.compile perfila múltiples implementaciones de operaciones en tiempo de compilación y selecciona la de mejor rendimiento. Esto es particularmente beneficioso para operaciones relacionadas con GEMM, utilizando una implementación de GEMM basada en plantillas C++ como alternativa al enfoque basado en ATen con bibliotecas oneDNN y MKL. Admitimos FP32, BF16, FP16 e INT8 con fusiones de epílogo para CPU x86. Hemos visto una aceleración geomedia de hasta un 7 % en los conjuntos de pruebas de dynamo y un aumento de hasta un 20 % en la latencia del siguiente token para la inferencia de LLM. Para obtener más información, consulte el tutorial.

[Prototipo] CPU TorchInductor en Windows

El backend de la CPU del inductor en torch.compile ahora funciona en Windows. Actualmente admitimos MSVC (cl), clang (clang-cl) y el compilador Intel (icx-cl) para el inductor de Windows. Consulte el tutorial para obtener más detalles.

[Prototipo] Compatibilidad con FP16 en la ruta de la CPU tanto para el modo ansioso como para el backend de CPP de TorchInductor

Float16 es un tipo de punto flotante reducido comúnmente utilizado para mejorar el rendimiento en la inferencia/entrenamiento de redes neuronales. Desde esta versión, float16 tanto para ansioso como para TorchInductor es compatible con la ruta de la CPU.

[Prototipo] Extensión del dispositivo de carga automática

PyTorch ahora admite la carga automática para extensiones de dispositivos fuera del árbol, lo que agiliza la integración al eliminar la necesidad de importaciones manuales. Esta característica, habilitada a través del punto de entrada torch.backends, simplifica el uso al garantizar una carga de extensión perfecta, al tiempo que permite a los usuarios desactivarla a través de una variable de entorno si es necesario. Consulte el tutorial para obtener más información.

[Prototipo] Compatibilidad mejorada con GPU Intel

La mejora de compatibilidad con las GPU Intel ahora está disponible para las GPU Intel® Data Center GPU Max Series y las GPU Intel® Client (procesadores Intel® Core™ Ultra con gráficos Intel® Arc™ integrados y gráficos Intel® Arc™ para piezas dGPU), lo que facilitará la aceleración de los flujos de trabajo de aprendizaje automático en las GPU Intel en la versión PyTorch 2.5. También habilitamos el soporte inicial de PyTorch en Windows para las GPU Intel® Client en esta versión.

  • Matriz de soporte de backend de hardware PyTorch ampliada para incluir GPU Intel Data Center y Client.  
  • La implementación de kernels SYCL* para mejorar la cobertura y ejecución de los operadores de Aten en GPU Intel para aumentar el rendimiento en el modo ansioso de PyTorch.
  • Backend de GPU Intel mejorado de torch.compile para mejorar la inferencia y el rendimiento del entrenamiento para una amplia gama de cargas de trabajo de aprendizaje profundo.
    Estas funciones están disponibles a través de la vista previa de PyTorch y las ruedas PIP binarias nocturnas. Para obtener más información sobre la compatibilidad con GPU Intel, consulte la documentación.

ONNX

Las opciones para torch.onnx.export (excepto los primeros tres argumentos) ahora son solo palabras clave (#131501)

Las opciones se pueden proporcionar mediante palabras clave únicamente para permitir la futura incorporación y evolución del torch.onnx.export API. Ejemplo:
Versión 2.4

torch.onnx.export(model, input, f, True, False)

Versión 2.5:

torch.onnx.export(model, input, f, export_params=True, verbose=False)

Se ha eliminado el API interno torch.onnx._export obsoleto (133824)

torch.onnx._export es un API interno que no está destinado al consumo público. Utilice el torch.onnx.export público en su lugar. Ejemplo:
Versión 2.4

torch.onnx._export(...)

Versión 2.5:

torch.onnx.export(...)

Se ha eliminado la opción op_level_debug de torch.onnx.ExportOptions (#134961)

Esta opción, diseñada para identificar discrepancias entre operadores, resultó poco confiable y ha sido eliminada. En su lugar, utilice la opción torch.onnx.export(..., report=True, verify=True) para validar los modelos exportados.

La clase ONNXProgramSerializer ha sido eliminada (#135261)

El modelo ONNX en torch.onnx.ONNXProgram ahora lo mantiene y serializa ONNX IR.
Los formatos textproto, onnxtext y json se admiten de forma predeterminada cuando se llama a ONNXProgram.save() con la extensión de archivo correspondiente.

La clase SymbolicContext ha sido eliminada (#132184)

Se ha eliminado la clase torch.onnx.SymbolicContext en desuso. Las funciones simbólicas personalizadas (sin dinamo) ya no pueden tomar ctx: torch.onnx.SymbolicContext como primer argumento.

Se ha eliminado el soporte para caffe2 (#129021)

  • Eliminar el manejo de Caffe2 de onnx_unpack_quantized_weights (#129021)
  • Eliminar is_caffe2_aten_fallback en torch.onnx.symbolic_helper

Se eliminan algunas clases de errores.

Se eliminan CheckerError y InvalidExportOptionsError. Los usuarios siempre pueden capturar RuntimeError para manejar los errores de exportación de torch.onnx.

El suministro de argumentos de palabras clave de modelo a torch.onnx.export está en desuso (#131501)

La capacidad de proporcionar argumentos de palabras clave modelo como diccionario final está obsoleta. Los usuarios deberían utilizar el parámetro kwargs en su lugar. En desuso:

torch.onnx.export(model, (arg1, arg2, {“kwarg1”: …}))

Futuro:

torch.onnx.export(model, (arg1, arg2), kwargs={“kwarg1”: …})

torch.onnx.OperatorExportTypes está en desuso (#131501)

La capacidad de suministrar operator_export_type en torch.onnx.export() está en desuso. Los gráficos ONNX exportados siempre utilizarán el dominio opset de ONNX. Las opciones ONNX_FALLTHROUGH, ONNX_ATEN y ONNX_ATEN_FALLBACK ya no son compatibles. La clase OperatorExportTypes se eliminará en una versión futura.

La opción training en torch.onnx.export está en desuso

Primero configure el modo de entrenamiento del modelo antes de exportar. En desuso:

torch.onnx.export(model, inputs, path, training=torch.onnx.TrainingMode.EVAL)

Futuro:

model = model.eval()  
torch.onnx.export(model, inputs, path)

ONNX

La opción dynamo=True y la nueva lógica de exportación (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

Introducimos la opción dynamo=True en torch.onnx.export(). Esto se recomienda como reemplazo de torch.onnx.dynamo_export a partir de PyTorch 2.5. Versión 2.5:

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) aprovecha torch.export y ONNX IR para convertir ExportedProgram capturados a ONNX de manera eficiente y sólida. Este nuevo proceso reduce el consumo de memoria a la mitad en comparación con dynamo_export en 2.4, al tiempo que conserva la rica información sobre la forma del tensor y el seguimiento de la pila en el gráfico ONNX. Puede aprovechar la opción report=True para obtener un informe de conversión en formato de rebajas para diagnosticar cualquier problema de conversión. Configure verify=True para verificar numéricamente el modelo ONNX con ONNX Runtime. Cuando se utiliza external_data=True para guardar pesos de modelo como datos externos en el archivo .onnx, los pesos mayores de 1 MB ahora se alinean en direcciones de 64 KB. Esto permite que los tiempos de ejecución asocien los pesos de la memoria para una mejor eficiencia de la memoria durante la inferencia.

[NOTA]
La opción dynamo=True actualmente solo admite el opset 18 de ONNX. Las versiones futuras ampliarán el soporte a los opsets más nuevos. [NOTA]
La opción dynamo=True requiere las últimas versiones de los paquetes onnxscript y onnx.

Highlights

We are excited to announce the release of PyTorch® 2.5! This release features a new CuDNN backend for SDPA, enabling speedups by default for users of SDPA on H100s or newer GPUs. As well, regional compilation of torch.compile offers a way to reduce the cold start up time for torch.compile by allowing users to compile a repeated nn.Module (e.g. a transformer layer in LLM) without recompilations. Finally, TorchInductor CPP backend offers solid performance speedup with numerous enhancements like FP16 support, CPP wrapper, AOT-Inductor mode, and max-autotune mode. This release is composed of 4095 commits from 504 contributors since PyTorch 2.4. We want to sincerely thank our dedicated community for your contributions. As always, we encourage you to try these out and report any issues as we improve 2.5. More information about how to get started with the PyTorch 2-series can be found at our Getting Started page. As well, please check out our new ecosystem projects releases with TorchRec and TorchFix.

BETA FEATURES

[Beta] CuDNN backend for SDPA

The cuDNN "Fused Flash Attention" backend was landed for torch.nn.functional.scaled_dot_product_attention. On NVIDIA H100 GPUs this can provide up to 75% speed-up over FlashAttentionV2. This speedup is enabled by default for all users of SDPA on H100 or newer GPUs.

[Beta] torch.compile regional compilation without recompilations

Regional compilation without recompilations, via torch._dynamo.config.inline_inbuilt_nn_modules which default to True in 2.5+. This option allows users to compile a repeated nn.Module (e.g. a transformer layer in LLM) without recompilations. Compared to compiling the full model, this option can result in smaller compilation latencies with 1%-5% performance degradation compared to full model compilation.

See the tutorial for more information.

[Beta] TorchInductor CPU backend optimization

This feature advances Inductor’s CPU backend optimization, including CPP backend code generation and FX fusions with customized CPU kernels. The Inductor CPU backend supports vectorization of common data types and all Inductor IR operations, along with the static and symbolic shapes. It is compatible with both Linux and Windows OS and supports the default Python wrapper, the CPP wrapper, and AOT-Inductor mode.

Additionally, it extends the max-autotune mode of the GEMM template (prototyped in 2.5), offering further performance gains. The backend supports various FX fusions, lowering to customized kernels such as oneDNN for Linear/Conv operations and SDPA. The Inductor CPU backend consistently achieves performance speedups across three benchmark suites—TorchBench, Hugging Face, and timms—outperforming eager mode in 97.5% of the 193 models tested.

PROTOTYPE FEATURES

[Prototype] FlexAttention

We've introduced a flexible API that enables implementing various attention mechanisms such as Sliding Window, Causal Mask, and PrefixLM with just a few lines of idiomatic PyTorch code. This API leverages torch.compile to generate a fused FlashAttention kernel, which eliminates extra memory allocation and achieves performance comparable to handwritten implementations. Additionally, we automatically generate the backwards pass using PyTorch's autograd machinery. Furthermore, our API can take advantage of sparsity in the attention mask, resulting in significant improvements over standard attention implementations.

For more information and examples, please refer to the official blog post and Attention Gym.

[Prototype] Compiled Autograd

Compiled Autograd is an extension to the PT2 stack allowing the capture of the entire backward pass. Unlike the backward graph traced by AOT dispatcher, Compiled Autograd tracing is deferred until backward execution time, which makes it impervious to forward pass graph breaks, and allows it to record backward hooks into the graph.

Please refer to the tutorial for more information.

[Prototype] Flight Recorder

Flight recorder is a new debugging tool that helps debug stuck jobs. The tool works by continuously capturing information about collectives as they run. Upon detecting a stuck job, the information can be used to quickly identify misbehaving ranks/machines along with code stack traces.

For more information please refer to the following tutorial.

[Prototype] Max-autotune Support on CPU with GEMM Template

Max-autotune mode for the Inductor CPU backend in torch.compile profiles multiple implementations of operations at compile time and selects the best-performing one. This is particularly beneficial for GEMM-related operations, using a C++ template-based GEMM implementation as an alternative to the ATen-based approach with oneDNN and MKL libraries. We support FP32, BF16, FP16, and INT8 with epilogue fusions for x86 CPUs. We’ve seen up to 7% geomean speedup on the dynamo benchmark suites and up to 20% boost in next-token latency for LLM inference.

For more information please refer to the tutorial.

[Prototype] TorchInductor CPU on Windows

Inductor CPU backend in torch.compile now works on Windows. We support MSVC (cl), clang (clang-cl) and Intel compiler (icx-cl) for Windows inductor currently.

See the tutorial for more details.

[Prototype] FP16 support on CPU path for both eager mode and TorchInductor CPP backend

Float16 is a commonly used reduced floating point type for performance improvement in neural network inference/training. Since this release, float16 for both eager and TorchInductor is supported on the CPU path.

[Prototype] Autoload Device Extension

PyTorch now supports autoloading for out-of-tree device extensions, streamlining integration by eliminating the need for manual imports. This feature, enabled through the torch.backends entrypoint, simplifies usage by ensuring seamless extension loading, while allowing users to disable it via an environment variable if needed.

See the tutorial for more information.

[Prototype] Enhanced Intel GPU support

Intel GPUs support enhancement is now available for both Intel® Data Center GPU Max Series and Intel® Client GPUs (Intel® Core™ Ultra processors with built-in Intel® Arc™ graphics and Intel® Arc™ Graphics for dGPU parts), which is to make it easier to accelerate your Machine Learning workflows on Intel GPUs in PyTorch 2.5 release. We also enabled the initial support of PyTorch on Windows for Intel® Client GPUs in this release.

  • Expanded PyTorch hardware backend support matrix to include both Intel Data Center and Client GPUs.  
  • The implementation of SYCL* kernels to enhance coverage and execution of Aten operators on Intel GPUs to boost performance in PyTorch eager mode.
  • Enhanced Intel GPU backend of torch.compile to improve inference and training performance for a wide range of deep learning workloads.

These features are available through PyTorch preview and nightly binary PIP wheels. For more information regarding Intel GPU support, please refer to documentation.

ONNX

The dynamo=True option and new export logic (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

We introduce the dynamo=True option in torch.onnx.export(). This is recommended as a replacement for torch.onnx.dynamo_export starting in PyTorch 2.5.

Version 2.5:

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) leverages torch.export and ONNX IR to convert captured ExportedPrograms to ONNX efficiently and robustly. This new process reduces memory consumption by half compared to dynamo_export in 2.4, while preserving rich tensor shape and stack trace information in the ONNX graph. You can leverage the report=True option to obtain a conversion report in markdown format to diagnose any conversion issues. Set verify=True to verify the ONNX model numerically with ONNX Runtime.

When using external_data=True to save model weights as external data to the .onnx file, weights larger than 1 MB are now aligned at 64 KB addresses. This allows runtimes to memory-map weights for better memory efficiency during inference.

[NOTE]
The dynamo=True option currently supports only ONNX opset 18. Future releases will expand support to newer opsets.

[NOTE]
The dynamo=True option requires the latest versions of onnxscript and onnx packages.
