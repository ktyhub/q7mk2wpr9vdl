Aspectos destacados

¡Nos complace anunciar el lanzamiento de PyTorch® 2.6 (release notes)! Esta versión presenta múltiples mejoras para PT2: torch.compile ahora se puede usar con Python 3.13; nueva perilla relacionada con el rendimiento torch.compiler.set_stance; varias mejoras de AOTInductor. Además de las mejoras de PT2, otro punto destacado es la compatibilidad con FP16 en CPU X86. NOTA: A partir de esta versión, no publicaremos en Conda; consulte [[Anuncio] Desactivación del canal oficial Anaconda de PyTorch] (https://github.com/pytorch/pytorch/issues/138506) para obtener más detalles. Para esta versión, los binarios experimentales de Linux enviados con CUDA 12.6.3 (así como los binarios de Linux Aarch64, Linux ROCm 6.2.4 y Linux XPU) se compilan con CXX11_ABI=1 y [utilizan la plataforma de compilación Manylinux 2.28] (https://dev-discuss.pytorch.org/t/pytorch-linux-wheels-switching-to-new-wheel-build-platform-manylinux-2-28-on-november-12-2024/2581). Si crea extensiones de PyTorch con extensiones C++ o CUDA personalizadas, actualice estas compilaciones para usar CXX_ABI=1 también e informe cualquier problema que esté observando. Para la próxima versión de PyTorch 2.7, planeamos cambiar todas las compilaciones de Linux a Manylinux 2.28 y CXX11_ABI=1; consulte [RFC] PyTorch next wheel build platform: manylinux-2.28 para obtener detalles y discusión. También en esta versión, como medida importante de mejora de la seguridad, hemos cambiado el valor predeterminado para el parámetro weights_only de torch.load. Este es un cambio que rompe la compatibilidad con versiones anteriores; consulte [esta publicación del foro] (https://dev-discuss.pytorch.org/t/bc-breaking-change-torch-load-is-being-flipped-to-use-weights-only-true-by-default-in-the-nightlies-after-137602/2573) para obtener más detalles. Esta versión se compone de 3892 confirmaciones de 520 contribuyentes desde PyTorch 2.5. Queremos agradecer sinceramente a nuestra dedicada comunidad por sus contribuciones. Como siempre, lo alentamos a que los pruebe e informe cualquier problema a medida que mejoramos PyTorch. Puede encontrar más información sobre cómo comenzar con la serie PyTorch 2 en nuestra página [Introducción] (https://pytorch.org/get-started/pytorch-2.0/). <tabla>

Una de las posturas, por ejemplo, es “eager_on_recompile”, que indica a PyTorch que codifique con entusiasmo cuando sea necesario volver a compilar, reutilizando el código compilado almacenado en caché cuando sea posible. Para obtener más información, consulte la [documentación set_stance](https://pytorch.org/docs/2.6/generated/torch.compiler.set_stance.html#torch.compiler.set_stance) y el tutorial [Control de compilación dinámica con torch.compiler.set_stance](https://pytorch.org/tutorials/recipes/torch_compiler_set_stance_tutorial.html). **[Beta] antorcha.library.triton_op** `torch.library.triton_op` ofrece una forma estándar de crear operadores personalizados respaldados por núcleos Triton definidos por el usuario. Cuando los usuarios convierten los núcleos Triton definidos por el usuario en operadores personalizados, `torch.library.triton_op` permite a `torch.compile` echar un vistazo a la implementación, lo que permite a `torch.compile` optimizar el núcleo Triton que contiene. Para obtener más información, consulte la [documentación de triton_op](https://pytorch.org/docs/2.6/library.html#torch.library.triton_op) y el tutorial [Uso de núcleos Triton definidos por el usuario con torch.compile](https://pytorch.org/tutorials/recipes/torch_compile_user_defined_triton_kernel_tutorial.html). **[Beta] soporte de torch.compile para Python 3.13** Anteriormente, `torch.compile` solo admitía Python hasta la versión 3.12. Los usuarios ahora pueden optimizar modelos con `torch.compile` en Python 3.13. **[Beta] Nuevo empaque API para AOTInductor** Se ha introducido un nuevo formato de paquete, “[archivo PT2](https://docs.google.com/document/d/1RQ4cmywilnFUT1VE-4oTGxwXdc8vowCSZsrRgo3wFA8/edit?usp=sharing)”. Básicamente, contiene un archivo zip de todos los archivos que AOTInductor debe utilizar y permite a los usuarios enviar todo lo necesario a otros entornos. También existe una funcionalidad para empaquetar múltiples modelos en un solo artefacto y almacenar metadatos adicionales dentro del paquete. Para obtener más detalles, consulte el [Tutorial de AOTInductor de torch.export para el tiempo de ejecución de Python] actualizado (https://pytorch.org/tutorials/recipes/torch_export_aoti_python.html). **[Beta] AOTInductor: minificador** Si un usuario encuentra un error al usar AOTInductor API, AOTInductor Minifier permite la creación de un nn.Module mínimo que reproduce el error. Para obtener más información, consulte la [documentación del minificador AOTInductor] (https://pytorch.org/docs/2.6/torch.compiler_aot_inductor_minifier.html). **[Beta] AOTInductor: generación de código en modo compatible con ABI** El código de modelo generado por AOTInductor depende de las bibliotecas cpp de Pytorch. A medida que Pytorch evoluciona rápidamente, es importante asegurarse de que los modelos compilados previamente por AOTInductor puedan continuar ejecutándose en versiones más nuevas de Pytorch, es decir, que AOTInductor sea compatible con versiones anteriores. Para garantizar la compatibilidad con versiones anteriores de la interfaz binaria de la aplicación (ABI), hemos definido cuidadosamente un conjunto de interfaces C estables en libtorch y nos aseguramos de que AOTInductor genere código que solo haga referencia al conjunto específico de API y nada más en libtorch. Mantendremos estable el conjunto de C API en todas las versiones de Pytorch y, por lo tanto, brindaremos garantías de compatibilidad con versiones anteriores para los modelos compilados por AOTInductor. **[Beta] Compatibilidad con FP16 para CPU X86 (tanto en modo ansioso como en modo Inductor)** El tipo de datos Float16 se usa comúnmente para reducir el uso de memoria y realizar cálculos más rápidos en la inferencia y el entrenamiento de IA. Las CPU como la recientemente lanzada [Intel® Xeon® 6 con P-Cores](https://www.intel.com/content/www/us/en/products/details/processors/xeon/xeon6-p-cores.html) admiten el tipo de datos Float16 con acelerador nativo [AMX](https://www.intel.com/content/www/us/en/products/docs/accelerator-engines/advanced-matrix-extensions/overview.html). La compatibilidad con Float16 en CPU X86 se introdujo en PyTorch 2.5 como una característica prototipo, y ahora se ha mejorado aún más tanto para el modo ansioso como para el modo Torch.compile + Inductor, lo que la convierte en una característica de nivel Beta con funcionalidad y rendimiento verificados con una amplia gama de cargas de trabajo. ### CARACTERÍSTICAS DEL PROTOTIPO **[Prototipo] Experiencia de usuario de PyTorch mejorada en GPU Intel** La experiencia del usuario de PyTorch en las GPU Intel se mejora aún más con pasos de instalación simplificados, distribución binaria de versiones de Windows y cobertura ampliada de modelos de GPU compatibles, incluidos los últimos gráficos discretos Intel® Arc™ Serie B. If you build PyTorch extensions with custom C++ or CUDA extensions, please update these builds to use CXX_ABI=1 as well and report any issues you are seeing. BETA FEATURES

[Beta] torch.compiler.set_stance

This feature enables the user to specify different behaviors (“stances”) that torch.compile can take between different invocations of compiled functions. One of the stances, for example, is

“eager_on_recompile”, that instructs PyTorch to code eagerly when a recompile is necessary, reusing cached compiled code when possible.

For more information please refer to the set_stance documentation and the Dynamic Compilation Control with torch.compiler.set_stance tutorial.

[Beta] torch.library.triton_op

torch.library.triton_op offers a standard way of creating custom operators that are backed by user-defined triton kernels.

When users turn user-defined triton kernels into custom operators, torch.library.triton_op allows torch.compile to peek into the implementation, enabling torch.compile to optimize the triton kernel inside it.

For more information please refer to the triton_op documentation and the Using User-Defined Triton Kernels with torch.compile tutorial.

[Beta] torch.compile support for Python 3.13

torch.compile previously only supported Python up to version 3.12. Users can now optimize models with torch.compile in Python 3.13.

[Beta] New packaging APIs for AOTInductor

A new package format, “PT2 archive”, has been introduced. This essentially contains a zipfile of all the files that need to be used by AOTInductor, and allows users to send everything needed to other environments. There is also functionality to package multiple models into one artifact, and to store additional metadata inside of the package.

For more details please see the updated torch.export AOTInductor Tutorial for Python runtime.

[Beta] AOTInductor: minifier

If a user encounters an error while using AOTInductor APIs, AOTInductor Minifier allows creation of a minimal nn.Module that reproduces the error.

For more information please see the AOTInductor Minifier documentation.

[Beta] AOTInductor: ABI-compatible mode code generation

AOTInductor-generated model code has dependency on Pytorch cpp libraries. As Pytorch evolves quickly, it’s important to make sure previously AOTInductor compiled models can continue to run on newer Pytorch versions, i.e. AOTInductor is backward compatible.

In order to guarantee application binary interface (ABI) backward compatibility, we have carefully defined a set of stable C interfaces in libtorch and make sure AOTInductor generates code that only refers to the specific set of APIs and nothing else in libtorch. We will keep the set of C APIs stable across Pytorch versions and thus provide backward compatibility guarantees for AOTInductor-compiled models.

[Beta] FP16 support for X86 CPUs (both eager and Inductor modes)

Float16 datatype is commonly used for reduced memory usage and faster computation in AI inference and training. CPUs like the recently launched Intel® Xeon® 6 with P-Cores support Float16 datatype with native accelerator AMX. Float16 support on X86 CPUs was introduced in PyTorch 2.5 as a prototype feature, and now it has been further improved for both eager mode and Torch.compile + Inductor mode, making it Beta level feature with both functionality and performance verified with a broad scope of workloads.

There is a known regression (#144152) that torch.device(0) makes CUDA init fail in subprocess since PyTorch 2.5.0. There was an attempt to fix the regressions, but it caused some complications and was reverted.

A regressions (https://github.com/pytorch/pytorch/issues/145220) was reported for PyTorch 2.6.0 with compilation of the out= variant of the torch.all operator. This should be a rare use case, a workaround can be rewriting the model code to avoid the out= variant.

Flip default torch.load to weights_only (#137602, #138225, #138866, #139221, #140304, #138936, #139541, #140738, #142153, #139433)

We are closing the loop on the deprecation that started in 2.4 and flipped torch.load to use weights_only=True by default.

When this flag is set, instead of using the usual pickle module, torch.load uses a custom unpickler constrained to call only functions and classes needed for loading state dictionaries and basic types.

While this change is disruptive for users serializing more than basic types, we expect the increased security by default is a tradeoff that is worth it. Do note that, even though this default is safer, we still recommend only loading trusted checkpoints and rely on more constrained (and even safer) formats like safetensors for un-trusted checkpoints.

For full details, please refer to this dev-discuss post.
