Los tensores anidados ya no están incluidos en la lista permitida para torch.load(..., weights_only=True) (#194380)

Los tensores anidados anidados, irregulares y con zancadas ya no están en la lista de permitidos predeterminada de weights_only. La carga de un punto de control que contiene uno con weights_only=True (el valor predeterminado) ahora falla con Unsupported global: GLOBAL torch.nested._internal.nested_tensor._rebuild_njt was not an allowed global by default (o GLOBAL torch._utils._rebuild_nested_tensor para tensores anidados con zancadas). Para cargar puntos de control que contienen tensores anidados, permítalos explícitamente con torch.serialization.safe_globals (ver más abajo) o use weights_only=False para archivos trust. Versión 2.14:

loaded = torch.load("njt.pt", weights_only=True)  # works

Versión 2.15:

from torch.nested._internal.nested_tensor import _rebuild_njt, NestedTensor
with torch.serialization.safe_globals([_rebuild_njt, NestedTensor]):
    loaded = torch.load("njt.pt", weights_only=True)

Los operadores llamados a través de torch.ops.* y torch._C._dispatch_call_boxed ahora usan la propia traducción de advertencias y excepciones de PyTorch en lugar de la de pybind11 (#193451)

Hacemos que las llamadas torch.ops.* pasen por la misma traducción de excepción y advertencia que el resto de la biblioteca. Esto significa que algunas traducciones de excepciones que solían ser manejadas por pybind ahora se manejan de forma nativa. Por lo tanto, se pierde la traducción de la excepción de pybind definida por el usuario. Es posible que se restaure en una versión futura como parte de una mejora más amplia del controlador de excepciones. Además, las advertencias TORCH_WARN de estos operadores ahora llegan al módulo warnings de Python, por lo que aparecen cuando las advertencias se convierten en errores (-W error). std::out_of_range todavía se convierte en IndexError (#195713). Versión 2.14:

# C++ op: throw std::invalid_argument("bad size");
try:
    torch.ops.my_lib.my_op(x)
except ValueError:  # pybind11 translation
    ...

Versión 2.15:

# C++ op: TORCH_CHECK_VALUE(false, "bad size");
try:
    torch.ops.my_lib.my_op(x)
except ValueError:
    ...

# TORCH_WARN from the op is now a Python warning
with warnings.catch_warnings():
    warnings.simplefilter("ignore")
    torch.ops.my_lib.my_op(x)

Autogrado

Los puntos de control de activación selectiva ahora guardan, en lugar de volver a calcular, las salidas de los operadores con un efecto ordenado a menos que la política devuelva CheckpointPolicy.MUST_RECOMPUTE (#196956)

En modo ansioso, si una política create_selective_checkpoint_contexts devuelve CheckpointPolicy.PREFER_RECOMPUTE para un operador sin alias con un efecto ordenado (por ejemplo, a través de register_effect(torch.library.EffectType.ORDERED)), esa elección ahora se anula y sus resultados se guardan, por lo que el efecto secundario ya no se reproduce al retroceder. Esto puede aumentar la memoria de activación. Para mantener el comportamiento de 2.14, devuelva CheckpointPolicy.MUST_RECOMPUTE para ese operador. Se excluyen los operadores del espacio de nombres c10d. Bajo torch.compile, CheckpointPolicy.MUST_RECOMPUTE en un operador efectivo ahora aparece en el momento de la compilación: RuntimeError: AOTAutograd does not support MUST_RECOMPUTE for effectful operations because forward effects cannot join the backward effect-token chain. Use una política de guardado en su lugar.

policy = lambda ctx, op, *args, **kwargs: CheckpointPolicy.PREFER_RECOMPUTE
checkpoint(fn, x, use_reentrant=False, context_fn=lambda: create_selective_checkpoint_contexts(policy))
# 2.14: an effectful op in fn runs twice; 2.15: once (use CheckpointPolicy.MUST_RECOMPUTE to replay)

Distribuido (c10d)

El backend de nccl ahora utiliza una implementación NCCL reescrita y limpia de forma predeterminada (#192281, #192895, #193237, #193241)

backend="nccl" (también el backend CUDA predeterminado de init_process_group()) ahora crea la nueva implementación. La implementación heredada está disponible como backend="nccl-legacy" solo para esta versión: nccl-legacy y TORCH_DIST_USE_NCCL2=0 se eliminarán en la próxima versión, así que migre a nccl o nccl-lazy. Utilice nccl (inicialización ansiosa) de forma predeterminada. Utilice nccl-lazy cuando necesite comunicadores punto a punto independientes: los colectivos se ejecutan en un comunicador creado con entusiasmo, y cada par de pares de envío/recepción obtiene su propio comunicador y transmisión creados de manera diferida, por lo que P2P simultáneo con diferentes pares puede superponerse (como en el backend heredado). Diferencias con el backend heredado:

  • Los comunicadores se crean con entusiasmo en init_process_group()/new_group(), asignando memoria GPU incluso para grupos no utilizados.
  • Cada grupo está vinculado a un dispositivo CUDA: device_id, de lo contrario LOCAL_RANK % torch.cuda.device_count() (o el módulo de clasificación global del recuento de dispositivos); torch.cuda.set_device() no se utiliza. Los tensores de otra GPU fallan con Expected tensor on cuda:X but found tensor on cuda:Y o ProcessGroupNCCL is bound to device cuda:X but an operation was issued on cuda:Y. Pase device_id si es necesario; varias GPU por proceso requieren nccl-legacy.
  • dist.get_backend_impl(...) devuelve la nueva clase de backend, por lo que isinstance(..., ProcessGroupNCCL) es False y faltan métodos heredados como comm_split_count().
  • El valor work.get_future() de un all_gather asíncrono es la lista de salidas por rango, no una lista de un elemento que contiene un tensor apilado; En su lugar, lea la lista de salida pasada a all_gather (funciona en ambos backends). Para restaurar temporalmente el comportamiento heredado en 2.15, configure TORCH_DIST_USE_NCCL2=0 en cada rango antes de crear el grupo de procesos, o use nccl-legacy: Versión 2.14:
dist.init_process_group("nccl")  # ProcessGroupNCCL

Versión 2.15:

dist.init_process_group("nccl", device_id=torch.device("cuda", local_rank))  # new implementation
dist.init_process_group("nccl-lazy", device_id=torch.device("cuda", local_rank))  # independent P2P communicators
dist.init_process_group("nccl-legacy")  # legacy implementation, removed in the next release

Puntos de control distribuidos

Los metadatos de puntos de control distribuidos ahora registran los pasos del tensor, por lo que los puntos de control guardados con PyTorch 2.15 no se pueden cargar con PyTorch 2.14 o versiones anteriores (#194251)

TensorProperties obtiene un campo strides opcional en el archivo .metadata encurtido. En versiones anteriores, dcp.load genera un CheckpointException que informa too many values to unpack (expected 5). No hay ninguna bandera para escribir el formato antiguo. Versión 2.14 (cargando un punto de control 2.15):

dcp.load(state_dict, checkpoint_id="/ckpt/step_100")
# CheckpointException: ... too many values to unpack (expected 5)

Versión 2.15:

dcp.load(state_dict, checkpoint_id="/ckpt/step_100")  # loads 2.14 and 2.15 checkpoints

FSDP2 distribuido

Con MixedPrecisionPolicy(reduce_dtype=None), fully_shard ahora acumula y reduce gradientes en el parámetro grad_dtype (su tipo d original por defecto) en lugar de en param_dtype (#194434).

Esto es una ruptura BC: mp_policy.reduce_dtype=None ya no es mp_policy.param_dtype por defecto.

  • [caso popular] parámetros fp32, MixedPrecisionPolicy(param_dtype=bf16)
    • antes: la acumulación de graduados y la reducción ocurren en bf16
    • después: la acumulación de graduación y la reducción ocurren en fp32 (2x bytes de reducción-dispersión)
  • [caso raro] parámetros bf16, MixedPrecisionPolicy(param_dtype=fp32)
    • antes: la acumulación de graduados y la reducción ocurren en fp32
    • después: la acumulación de graduados y la reducción ocurren en bf16 Cómo lidiar con BC: configure explícitamente mp_policy.reduce_dtype. En la acumulación de graduados (sin reducción-dispersión), el .grad del parámetro no fragmentado siempre mantiene el valor acumulado, visible a través de model.parameters() mientras no está fragmentado. Antes de este cambio, .grad era None cuando se configuró reduce_dtype y difería de param_dtype (FSDP mantuvo la suma en un búfer oculto de reduce_dtype). Versión 2.14:
# fp32 parameters
mp_policy = MixedPrecisionPolicy(param_dtype=torch.bfloat16)
fully_shard(model, mp_policy=mp_policy)
# gradients accumulate and reduce-scatter in bf16

Versión 2.15:

# fp32 parameters
mp_policy = MixedPrecisionPolicy(param_dtype=torch.bfloat16)
fully_shard(model, mp_policy=mp_policy)
# gradients accumulate and reduce-scatter in fp32

# to keep the 2.14 behavior, set reduce_dtype explicitly
mp_policy = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.bfloat16)
fully_shard(model, mp_policy=mp_policy)

torch.distributed.config.pipeline_per_direction_p2p pasa a llamarse pipeline_per_edge_p2p y ahora utiliza un comunicador por borde dirigido de rango a rango (#196666)

Los nombres antiguos se eliminaron sin alias: al establecer el atributo se genera AttributeError: torch.distributed.config.pipeline_per_direction_p2p does not exist y TORCH_DISTRIBUTED_PIPELINE_PER_DIRECTION_P2P se ignora silenciosamente. Versión 2.14:

dist_config.pipeline_per_direction_p2p = True

Versión 2.15:

dist_config.pipeline_per_edge_p2p = True  # or TORCH_DISTRIBUTED_PIPELINE_PER_EDGE_P2P=1

Perfilador

Los seguimientos de pila de C++ ahora están simbolizados con dladdr en lugar de addr2line de forma predeterminada (#195462)

TORCH_DISABLE_ADDR2LINE ahora está activado de forma predeterminada, ya que addr2line es lento y puede bloquearse. Los marcos de C++ en los errores TORCH_SHOW_CPP_STACKTRACES=1 y las instantáneas de memoria CUDA ahora muestran la ruta de la biblioteca y el desplazamiento, además del nombre del símbolo solo si se exportan (de lo contrario, ??). Para restaurar addr2line, configure TORCH_DISABLE_ADDR2LINE=0 o TORCH_SYMBOLIZE_MODE=addr2line.

TORCH_SHOW_CPP_STACKTRACES=1 TORCH_DISABLE_ADDR2LINE=0 python train.py

Las instantáneas de memoria CUDA registran la etiqueta mallocWithAddress del asignador en un nuevo campo internal_metadata en lugar de agregarla a user_metadata (#193432)

user_metadata en las entradas de seguimiento de torch.cuda.memory._snapshot() ahora es exactamente lo que se configuró con torch.cuda.memory._set_memory_metadata (que ahora también acepta un dictado). Las herramientas que buscaron user_metadata por mallocWithAddress deben leer internal_metadata en su lugar.

# 2.14
tagged = [e for e in trace if "mallocWithAddress" in e["user_metadata"]]
# 2.15
tagged = [e for e in trace if e.get("internal_metadata") == "mallocWithAddress"]

Eliminar la propiedad obsoleta FunctionEvent.metadata_json (#198265)

Al acceder a él ahora se genera AttributeError: 'FunctionEvent' object has no attribute 'metadata_json' y se elimina el argumento del constructor metadata_json. Utilice FunctionEvent.metadata, un diccionario que se completa cuando se configura _ExperimentalConfig(expose_kineto_event_metadata=True) (no el obsoleto event_metadata).

metadata = event.metadata_json  # 2.14: JSON string
metadata = event.metadata  # 2.15: dict[str, Any] or None

Cambie el nombre del backend experimental del perfilador de monitores CUPTI a Cuspy, sin alias para los nombres antiguos (#195881)

En _ExperimentalConfig(custom_profiler_config=...), "cupti_monitor" ahora es "cuspy" y "cupti_monitor_async_export" ahora es "cuspy_async_export"; Los nombres antiguos vuelven silenciosamente al backend predeterminado de Kineto. prof.take_pending_cupti_export() ahora es take_pending_cuspy_export() (el antiguo nombre plantea AttributeError). Prefiere el nuevo torch.profiler.CuspyConfig.

# 2.14
cfg = _ExperimentalConfig(custom_profiler_config='{"backend":"cupti_monitor"}')
# 2.15
cfg = _ExperimentalConfig(custom_profiler_config='{"backend":"cuspy"}')

Dinamo

Las operaciones de orden superior ahora rechazan la mutación de entrada y el alias en sus cuerpos a menos que la operación opte por participar (#185738)

Antes, Dynamo permitía que cualquier cuerpo de operación de orden superior mutara o creara un alias en sus entradas de forma predeterminada. Las operaciones que no implementan esa semántica podrían producir silenciosamente gráficos no válidos. La mutación y el alias ahora están desactivados de forma predeterminada. Los contenedores integrados que los admiten (wrap, checkpoint, autograd.Function, contenedores autocast/set-grad) optan por participar. Un flex_attention mask_mod puede leer vistas capturadas, pero no debe mutar entradas ni devolver alias. En fullgraph=True, la mutación o el alias no admitido genera Encountered input mutation during higher order op tracing o Encountered aliasing during higher order op tracing; de lo contrario, el gráfico de Dynamo se rompe y vuelve a una ejecución ansiosa. Vuelva a escribir el cuerpo de la operación de orden superior para evitar mutaciones o alias. Por ejemplo, reescriba un modificador de puntuación flex_attention local como una operación fuera de lugar: Versión 2.14:

def score_mod(score, b, h, q, k):
    score.add_(1)
    return score.clone()

Versión 2.15:

def score_mod(score, b, h, q, k):
    return score + 1

##Inductor

torch.compiler.nested_compile_region(options=...) ahora acepta solo una lista permitida de parches de configuración de Inductor (#195864, #195865)

Los parches pasados a través de get_invoke_subgraph_compile_options(fw_inductor_config_patches=..., bw_inductor_config_patches=...) solían aceptar cualquier clave torch._inductor.config, aunque muchos fueron ignorados silenciosamente. Ahora sólo se aceptan fallback_by_default y max_autotune; otras teclas generan ValueError: Inductor config key '<key>' is not supported in forward nested compile-region options (o backward). Aplique otras opciones a toda la función compilada. Los diccionarios de parches ahora se crean instantáneas cuando se crean las opciones, por lo que la mutación posterior no tiene ningún efecto y el valor predeterminado ya no establece implícitamente triton.autotune_at_compile_time=True. Versión 2.14:

opts = get_invoke_subgraph_compile_options(fw_inductor_config_patches={"triton.multi_kernel": 1})

Versión 2.15:

opts = get_invoke_subgraph_compile_options(fw_inductor_config_patches={"max_autotune": True})
compiled = torch.compile(fn, options={"triton.multi_kernel": 1})

torch.compiler.precompile ahora es un módulo en lugar de un invocable; capturar con torch.compiler.precompile.capture(...) y recargar con torch.compiler.precompile.load(...) (#197993, #198135, #198213)

Llamar a torch.compiler.precompile(fn, *example_inputs) ahora genera TypeError: 'module' object is not callable. capture(fn, *, artifact_path, cache_path) devuelve un administrador de contexto al que llamas una vez dentro del bloque with; escribe ambos archivos cuando el bloque sale limpiamente (o en cap.save()), y load ahora toma esas rutas. decompositions= pasa a tracer=MakeFxTracer(decompositions=...). Versión 2.14:

python_code, cache = torch.compiler.precompile(lambda m, x: m(x), model, x)
f = torch.compiler.precompile.load(python_code, cache)

Versión 2.15:

with torch.compiler.precompile.capture(lambda m, x: m(x), artifact_path="m.py", cache_path="m.cache") as cap:
    cap(model, x)
f = torch.compiler.precompile.load("m.py", "m.cache")

Componibilidad

Bajo la funcionalización, una salida regenerada de split, split_with_sizes o unbind ahora se reconstruye como un único slice o select de su base, por lo que su grad_fn es SliceBackward0/SelectBackward0 en lugar de SplitBackward0/SplitWithSizesBackward0/UnbindBackward0 (#194037).

Esto reduce en gran medida el tiempo de compilación del código que muta muchas vistas split() (por ejemplo, de 32 a 15 con 128 vistas). Los gradientes no cambian, pero el error local ahora nombra la nueva operación con índice de salida 0: RuntimeError: Output 0 of Select is a view and is being modified inplace. El código que inspecciona los nombres de grad_fn, coincide con el texto de error anterior o coincide con patrones de nodos split/unbind en gráficos funcionalizados necesita actualización. No hay ninguna opción para restaurar el comportamiento anterior. Versión 2.14:

>>> out = torch.func.functionalize(f)(x)  # f returns base.unbind(0)[1] after base.add_(1)
>>> out.grad_fn
<UnbindBackward0 object at 0x...>

Versión 2.15:

>>> out = torch.func.functionalize(f)(x)
>>> out.grad_fn
<SelectBackward0 object at 0x...>

Ingeniería de lanzamiento

Las ruedas PyPI ahora se envían con CUDA 13.2, y las ruedas CUDA 12.6 y CUDA 13.0 ya no están publicadas (#196249, #198913)

La rueda PyPI predeterminada se mueve de CUDA 13.0 a CUDA 13.2. Las ruedas 2.15 son cu132 y cu134; cu126 y cu130 ya no se fabrican. Las ruedas CUDA 13 necesitan el controlador NVIDIA 580 o posterior y una GPU de Turing (sm_75) o posterior, por lo que las GPU y hosts Maxwell, Pascal y Volta con un controlador CUDA 12.x deben permanecer en 2.14. Versión 2.15:

# PyPI wheel now uses CUDA 13.2
pip install torch

# CUDA 13.4 wheels
pip install torch --index-url https://download.pytorch.org/whl/cu134

# To stay on CUDA 12.6 or CUDA 13.0, pin PyTorch 2.14:
pip install torch==2.14.0 --index-url https://download.pytorch.org/whl/cu126  # or cu130

Las ruedas Python 3.10 ya no están publicadas (#198233, #199398)

PyTorch 2.15 eleva la versión mínima admitida de Python para binarios a 3.11: no se construyen ruedas cp310 para torch o las ruedas Triton, y CI ya no realiza pruebas en Python 3.10. En Python 3.10, pip no puede encontrar una rueda 2.15. Actualice a Python 3.11 o más reciente, o permanezca en PyTorch 2.14. Versión 2.14:

python3.10 -m pip install torch  # cp310 wheel available

Versión 2.15:

python3.11 -m pip install torch==2.15.0  # Python 3.11 through 3.15 (including 3.14t and 3.15t)

Las ruedas ROCm se mueven a ROCm 7.14 y 10.0; Las ruedas ROCm 7.2 y los núcleos gfx900/gfx906 se eliminan (#194919)

Los usuarios de gfx900 (MI25) y gfx906 (MI50/MI60, Radeon VII) pueden permanecer en 2.14 (rocm7.2) o compilar desde el código fuente con esos objetivos en PYTORCH_ROCM_ARCH.

pip install torch --index-url https://download.pytorch.org/whl/rocm7.14  # or rocm10.0

Las ruedas CUDA de Linux ya no dependen de la biblioteca cuRAND (#194850)

PyTorch solo usa el dispositivo cuRAND API, por lo que torch ya no vincula libcurand, ya no lo precarga en import torch y los requisitos CUDA de la rueda ya no incluyen cuRAND. Las extensiones o bibliotecas que llaman al host cuRAND API (por ejemplo, curandCreateGenerator) y dependen de que pip install torch incorpore la biblioteca cuRAND pueden no cargar libcurand.so y ahora deben instalarlo ellas mismas. Versión 2.15:

pip install torch
pip install "cuda-toolkit[curand]==13.2.2"  # match the toolkit version of your wheel

CUDA

torch.histc(..., out=...) en CUDA ahora genera un error cuando out no tiene el mismo tipo de entrada (#196100)

CUDA solía transmitir silenciosamente cualquier tipo de código out. Ahora iguala CPU y MPS y rechaza discrepancias, incluso las que se amplían. Calcule sin out y transmita en su lugar. Versión 2.14:

>>> torch.histc(x, bins=4, min=-2.0, max=2.0, out=int64_out)  # silently truncated

Versión 2.15:

RuntimeError: torch.histogram: input tensor and hist tensor should have the same dtype, but got input float and hist long int
>>> int64_out.copy_(torch.histc(x, bins=4, min=-2.0, max=2.0))  # workaround

En CUDA, los espacios de trabajo cuBLAS y cuBLASLt ahora se asignan para cada operación en lugar de almacenarse en caché por identificador y flujo (#194311)

Los gráficos capturados por separado en una secuencia podrían compartir el espacio de trabajo en caché y fallar al reproducirse con CUDA error: an illegal memory access was encountered. Los espacios de trabajo ahora se liberan después de cada operación, por lo que torch.cuda.memory_allocated() los excluye y el identificador de torch.cuda.current_blas_handle() no tiene ningún espacio de trabajo ATen adjunto. Configure TORCH_CUBLAS_WORKSPACE_CACHE=1 para restaurar el almacenamiento en caché (no es seguro con varios gráficos en una secuencia). TORCH_CUBLASLT_UNIFIED_WORKSPACE ahora sólo tiene efecto con el almacenamiento en caché habilitado. ROCm tiene un cambio coincidente (#196920). Versión 2.14:

>>> torch.mm(a, a, out=out)
>>> torch.cuda.memory_allocated() - before > 0  # workspace stays allocated
True

Versión 2.15:

>>> torch.cuda.memory_allocated() - before  # freed after the op

CPU (AArch64)

Float32 torch.sin y torch.cos en CPU Arm (NEON y SVE) ahora usan los kernels 3.5-ULP de SLEEF en lugar de los kernels 1.0-ULP, igualando la precisión de la implementación x86 AVX2 y ejecutándose entre 1,7 y 2,4 veces más rápido en Neoverse V1/V2 (#196315)

Los resultados de Float32 sin y cos en Arm ahora pueden diferir de versiones anteriores en los últimos bits. Las comparaciones bit por bit con las salidas doradas almacenadas, torch.equal o torch.testing.assert_close con rtol=0, atol=0 pueden fallar; Las tolerancias predeterminadas de assert_close no se ven afectadas. No hay ningún interruptor para restaurar los núcleos anteriores; Si necesita una mayor precisión, calcule en float64 y retroceda. Versión 2.14:

>>> x.cos()  # float32 on Arm: within 1 ULP

Versión 2.15:

>>> x.cos()  # float32 on Arm: within 2 ULP
>>> x.double().cos().float()  # workaround: correctly rounded

diputados

macOS 14 llegó al final de su vida útil, por lo que se eliminaron sus soluciones MPS. En macOS 14, torch.backends.mps.is_available() devuelve False y la asignación en mps genera el siguiente error. Para seguir usando MPS, permanezca en PyTorch 2.14 o actualice macOS; Las compilaciones de CPU todavía se ejecutan en macOS más antiguos. Extensiones de C++: se eliminó at::mps::MacOSVersion::MACOS_14_4.

>>> torch.ones(2, device="mps")  # 2.15 on macOS 14

##XPU

Elimina la propiedad allocator de torch.xpu.MemPool, alineándola con otros aceleradores (#192041)

torch.xpu.MemPool ya no expone el asignador con el que se construyó, por lo que pool.allocator ahora genera AttributeError. En su lugar, mantenga su propia referencia al asignador; pasar uno al constructor MemPool no cambia. Antes:

pool = torch.xpu.MemPool(allocator.allocator())
my_allocator = pool.allocator

Después:

my_allocator = allocator.allocator()
pool = torch.xpu.MemPool(my_allocator)

Interfaz compleja

Las operaciones que no están definidas para entradas complejas ahora generan TypeError en lugar de RuntimeError (#192350)

Esto cubre operaciones dependientes de la orden (sort, argsort, topk, argmax/argmin, max/min con dim, maximum/minimum, fmax/fmin, aminmax), isposinf/isneginf, view_as_real/imag en tensores reales y view_as_complex en tensores complejos, que coinciden con Python (1j < 2j es un TypeError). except RuntimeError: ya no los detecta; atrapar (RuntimeError, TypeError). Las operaciones aún no implementadas para un tipo d (por ejemplo, rad2deg, nansum, heaviside en complejo, topk/argmax en bool) ahora generan NotImplementedError, que except RuntimeError: aún detecta. Los max()/min()/amax/amin completos no cambian.

torch.sort(torch.randn(3, dtype=torch.cfloat))
# 2.14: RuntimeError:  Sort does not support complex dtypes on CPU
# 2.15: TypeError:  Sort does not support complex dtypes on CPU

Deprecaciones

Optimizador

Pasar un set simple de parámetros a un optimizador está obsoleto y ahora emite un FutureWarning; se convertirá en un error en una versión futura (#198710)

El orden de iteración establecido puede cambiar entre ejecuciones, por lo que el estado del optimizador podría no coincidir silenciosamente con los parámetros al recargar. La advertencia dice: optimizer parameters need to be organized in ordered collections, but the ordering of tensors in sets will change between runs. Please use a list instead.

opt = torch.optim.Adam(set(model.parameters()))  # 2.15: FutureWarning
opt = torch.optim.Adam(list(model.parameters()))  # recommended

Interfaz de álgebra lineal

MAGMA está obsoleto para la factorización de LU con pivote en CUDA: torch.linalg.lu_factor, torch.linalg.lu y las operaciones que lo usan internamente (torch.linalg.solve, torch.linalg.inv, torch.linalg.det, torch.linalg.slogdet) ahora siempre usan cuSOLVER (#190661)

Esto sólo afecta al código que establece torch.backends.cuda.preferred_linalg_library("magma"): la LU pivotada ahora usa cuSOLVER de todos modos; un nuevo kernel LU por lotes incorporado reemplaza al de MAGMA para lotes grandes. Cuando se prefiere MAGMA, la primera llamada advierte: linalg.lu_factor: MAGMA, as a linear algebra backend, is deprecated and will be removed in future releases. pivot=False todavía usa MAGMA cuando se prefiere. Para evitar la advertencia, utilice el backend predeterminado o cuSOLVER.

torch.backends.cuda.preferred_linalg_library("magma")
LU, pivots = torch.linalg.lu_factor(A)  # 2.14: MAGMA; 2.15: cuSOLVER + UserWarning
torch.backends.cuda.preferred_linalg_library("default")  # recommended

##Inductor

Desaprobar torch._inductor.config.triton.use_block_ptr porque Triton eliminó su puntero de bloque API (#191007)

Con un Triton que ya no proporciona punteros de bloque, use_block_ptr=True ahora no es operativo y recurre a la ruta de indexación predeterminada con un FutureWarning: config.triton.use_block_ptr=True but the installed Triton no longer provides the block-pointer frontend API único, en lugar de fallar con CompilationError: ... Block pointers have been removed in favor of the tensor descriptor API. Utilice descriptores tensoriales en su lugar. Versión 2.14:

torch._inductor.config.triton.use_block_ptr = True

Versión 2.15:

torch._inductor.config.triton.use_tensor_descriptor = True

Desaprobar las configuraciones no operativas torch._inductor.config.use_mixed_mm y torch._inductor.config.mixed_mm_choice (#193721)

Estas configuraciones se han ignorado desde que se eliminó la ruta mixed_mm sintonizada. La lectura o configuración ahora emite un FutureWarning único, como torch._inductor.config.use_mixed_mm is deprecated and does not do anything. Se eliminaron autoheuristic_collect.mixed_mm y autoheuristic_use.mixed_mm y "mixed_mm" ya no es el TORCHINDUCTOR_AUTOHEURISTIC_USE predeterminado. Elimine estas configuraciones de su código. Versión 2.14:

torch._inductor.config.use_mixed_mm = True  # silently ignored

Versión 2.15:

# FutureWarning; delete the line

Cambie el nombre de torch._inductor.config.benchmark_epilogue_fusion a benchmark_template_fusion y max_epilogue_benchmarked_choices a max_template_fusion_benchmarked_choices (#198430)

La configuración también cubre la fusión del prólogo, por lo que los nombres antiguos eran engañosos. Los nombres antiguos permanecen como alias obsoletos que emiten un FutureWarning de una sola vez. La variable de entorno ahora es TORCHINDUCTOR_BENCHMARK_TEMPLATE_FUSION; TORCHINDUCTOR_BENCHMARK_EPILOGUE_FUSION todavía se lee como alternativa. Versión 2.14:

torch._inductor.config.benchmark_epilogue_fusion = False

Versión 2.15:

torch._inductor.config.benchmark_template_fusion = False

CUDA

torch.cuda.graph_annotations.clear_kernel_annotations() está en desuso y ahora emite un FutureWarning (#195398)

El registro de anotaciones del kernel del gráfico CUDA ahora se limpia después de sí mismo: las anotaciones se vuelven a ingresar en el gráfico ejecutable cuando se crea una instancia y se eliminan cuando se destruye ese gráfico. Una limpieza global también descarta las anotaciones de los gráficos que aún están activos. Elimine la llamada y restablezca o elimine un gráfico para eliminar sus anotaciones. Versión 2.14:

annotations = get_kernel_annotations()
clear_kernel_annotations()

Versión 2.15:

annotations = get_kernel_annotations()
# No clear needed; g's annotations are dropped when g is reset or destroyed.

Backwards Incompatible Changes

Python Frontend

import torch can no longer be re-executed in the same process, including via importlib.reload(torch) (#194654)

importlib.reload(torch) and del sys.modules["torch"] + re-import now raise, as does retrying import torch after it failed. Re-running the module body was already unsafe in exactly the same way as the retry, so the new check does not distinguish the two. Normal use is unaffected: a successful import leaves torch in sys.modules so the body never re-runs, and re-entrant imports from a backend extension during autoload still short-circuit on sys.modules without reaching the check.

Version 2.14:

import importlib
import torch

importlib.reload(torch)
# RuntimeError: Only a single TORCH_LIBRARY can be used to register the namespace triton; ...
# (re-importing after a failed `import torch` failed with similarly misleading errors or could segfault)

Version 2.15:

import importlib
import torch

importlib.reload(torch)
# ImportError: `torch` can only be initialized once per process, so this module cannot
# be imported again: neither via `importlib.reload(torch)`, nor by re-importing after
# a failed `import torch`.

Nested tensors are no longer allowlisted for torch.load(..., weights_only=True) (#194380)

Nested jagged and strided nested tensors are no longer on the default weights_only allowlist. Loading a checkpoint that contains one with weights_only=True (the default) now fails with Unsupported global: GLOBAL torch.nested._internal.nested_tensor._rebuild_njt was not an allowed global by default (or GLOBAL torch._utils._rebuild_nested_tensor for strided nested tensors). To load checkpoints containing nested tensors, allow them explicitly with torch.serialization.safe_globals (see below), or use weights_only=False for trusted files.

Version 2.14:

loaded = torch.load("njt.pt", weights_only=True)  # works

Version 2.15:

from torch.nested._internal.nested_tensor import _rebuild_njt, NestedTensor
with torch.serialization.safe_globals([_rebuild_njt, NestedTensor]):
    loaded = torch.load("njt.pt", weights_only=True)

Operators called through torch.ops.* and torch._C._dispatch_call_boxed now use PyTorch's own warning and exception translation instead of pybind11's (#193451)

We make torch.ops.* calls go through the same exception and warning translation as the rest of the library. This means that some exception translation that used to be handled by pybind is now handled natively. User-defined pybind exception translation is thus lost. Restoring it may be done in a future release as part of a broader exception handler improvement.

In addition, TORCH_WARN warnings from these operators now reach Python's warnings module, so they raise when warnings are turned into errors (-W error). std::out_of_range still becomes IndexError (#195713).

Version 2.14:

# C++ op: throw std::invalid_argument("bad size");
try:
    torch.ops.my_lib.my_op(x)
except ValueError:  # pybind11 translation
    ...

Version 2.15:

# C++ op: TORCH_CHECK_VALUE(false, "bad size");
try:
    torch.ops.my_lib.my_op(x)
except ValueError:
    ...

# TORCH_WARN from the op is now a Python warning
with warnings.catch_warnings():
    warnings.simplefilter("ignore")
    torch.ops.my_lib.my_op(x)

Autograd

Selective activation checkpointing now saves, rather than recomputes, the outputs of operators with an ordered effect unless the policy returns CheckpointPolicy.MUST_RECOMPUTE (#196956)

In eager mode, if a create_selective_checkpoint_contexts policy returns CheckpointPolicy.PREFER_RECOMPUTE for a non-aliasing operator with an ordered effect (e.g. via register_effect(torch.library.EffectType.ORDERED)), that choice is now overridden and its outputs are saved, so the side effect is no longer replayed during backward. This can increase activation memory. To keep the 2.14 behavior, return CheckpointPolicy.MUST_RECOMPUTE for that operator. Operators in the c10d namespace are excluded. Under torch.compile, CheckpointPolicy.MUST_RECOMPUTE on an effectful operator now raises at compile time: RuntimeError: AOTAutograd does not support MUST_RECOMPUTE for effectful operations because forward effects cannot join the backward effect-token chain. Use a save policy instead.

policy = lambda ctx, op, *args, **kwargs: CheckpointPolicy.PREFER_RECOMPUTE
checkpoint(fn, x, use_reentrant=False, context_fn=lambda: create_selective_checkpoint_contexts(policy))
# 2.14: an effectful op in fn runs twice; 2.15: once (use CheckpointPolicy.MUST_RECOMPUTE to replay)

Distributed (c10d)

The nccl backend now uses a rewritten, cleaned-up NCCL implementation by default (#192281, #192895, #193237, #193241)

backend="nccl" (also the default CUDA backend of init_process_group()) now creates the new implementation. The legacy implementation is available as backend="nccl-legacy" for this release only: nccl-legacy and TORCH_DIST_USE_NCCL2=0 will be removed in the next release, so migrate to nccl or nccl-lazy.

Use nccl (eager initialization) by default. Use nccl-lazy when you need independent point-to-point communicators: collectives run on one eagerly created communicator, and each send/recv peer pair gets its own lazily created communicator and stream, so concurrent P2P to different peers can overlap (as in the legacy backend).

Differences from the legacy backend:

  • Communicators are created eagerly in init_process_group()/new_group(), allocating GPU memory even for unused groups.
  • Each group is bound to one CUDA device: device_id, else LOCAL_RANK % torch.cuda.device_count() (or the global rank modulo the device count); torch.cuda.set_device() is not used. Tensors on another GPU fail with Expected tensor on cuda:X but found tensor on cuda:Y or ProcessGroupNCCL is bound to device cuda:X but an operation was issued on cuda:Y. Pass device_id if needed; several GPUs per process requires nccl-legacy.
  • dist.get_backend_impl(...) returns the new backend class, so isinstance(..., ProcessGroupNCCL) is False and legacy-only methods such as comm_split_count() are missing.
  • An async all_gather's work.get_future() value is the list of per-rank outputs, not a one-element list holding a stacked tensor; read the output list passed to all_gather instead (works on both backends).

To temporarily restore the legacy behavior in 2.15, set TORCH_DIST_USE_NCCL2=0 on every rank before creating the process group, or use nccl-legacy:

Version 2.14:

dist.init_process_group("nccl")  # ProcessGroupNCCL

Version 2.15:

dist.init_process_group("nccl", device_id=torch.device("cuda", local_rank))  # new implementation
dist.init_process_group("nccl-lazy", device_id=torch.device("cuda", local_rank))  # independent P2P communicators
dist.init_process_group("nccl-legacy")  # legacy implementation, removed in the next release

Distributed Checkpointing

Distributed checkpoint metadata now records tensor strides, so checkpoints saved with PyTorch 2.15 cannot be loaded by PyTorch 2.14 or earlier (#194251)

TensorProperties gains an optional strides field in the pickled .metadata file. In older versions dcp.load raises a CheckpointException reporting too many values to unpack (expected 5). There is no flag to write the old format.

Version 2.14 (loading a 2.15 checkpoint):

dcp.load(state_dict, checkpoint_id="/ckpt/step_100")
# CheckpointException: ... too many values to unpack (expected 5)

Version 2.15:

dcp.load(state_dict, checkpoint_id="/ckpt/step_100")  # loads 2.14 and 2.15 checkpoints

Distributed FSDP2

With MixedPrecisionPolicy(reduce_dtype=None), fully_shard now accumulates and reduces gradients in the parameter's grad_dtype (its original dtype by default) instead of in param_dtype (#194434)

This is BC-breaking: mp_policy.reduce_dtype=None no longer defaults to mp_policy.param_dtype.

  • [popular case] fp32 params, MixedPrecisionPolicy(param_dtype=bf16)
    • before: grad accumulation and reduce happen in bf16
    • after: grad accumulation and reduce happen in fp32 (2x reduce-scatter bytes)
  • [rare case] bf16 params, MixedPrecisionPolicy(param_dtype=fp32)
    • before: grad accumulation and reduce happen in fp32
    • after: grad accumulation and reduce happen in bf16

How to deal with BC: explicitly set mp_policy.reduce_dtype.

In grad accumulation (no reduce-scatter), the unsharded param's .grad always holds the accumulated value, visible via model.parameters() while unsharded. Before this change, .grad was None when reduce_dtype was set and differed from param_dtype (FSDP kept the sum in a hidden reduce_dtype buffer).

Version 2.14:

# fp32 parameters
mp_policy = MixedPrecisionPolicy(param_dtype=torch.bfloat16)
fully_shard(model, mp_policy=mp_policy)
# gradients accumulate and reduce-scatter in bf16

Version 2.15:

# fp32 parameters
mp_policy = MixedPrecisionPolicy(param_dtype=torch.bfloat16)
fully_shard(model, mp_policy=mp_policy)
# gradients accumulate and reduce-scatter in fp32

# to keep the 2.14 behavior, set reduce_dtype explicitly
mp_policy = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.bfloat16)
fully_shard(model, mp_policy=mp_policy)

Distributed Pipelining

torch.distributed.config.pipeline_per_direction_p2p is renamed to pipeline_per_edge_p2p and now uses one communicator per directed rank-to-rank edge (#196666)

The old names were removed with no alias: setting the attribute raises AttributeError: torch.distributed.config.pipeline_per_direction_p2p does not exist, and TORCH_DISTRIBUTED_PIPELINE_PER_DIRECTION_P2P is silently ignored.

Version 2.14:

dist_config.pipeline_per_direction_p2p = True

Version 2.15:

dist_config.pipeline_per_edge_p2p = True  # or TORCH_DISTRIBUTED_PIPELINE_PER_EDGE_P2P=1

Profiler

C++ stack traces are now symbolized with dladdr instead of addr2line by default (#195462)

TORCH_DISABLE_ADDR2LINE now defaults to on, since addr2line is slow and can hang. C++ frames in TORCH_SHOW_CPP_STACKTRACES=1 errors and CUDA memory snapshots now show the library path and offset, plus the symbol name only if exported (otherwise ??). To restore addr2line, set TORCH_DISABLE_ADDR2LINE=0 or TORCH_SYMBOLIZE_MODE=addr2line.

TORCH_SHOW_CPP_STACKTRACES=1 TORCH_DISABLE_ADDR2LINE=0 python train.py

CUDA memory snapshots record the allocator's mallocWithAddress tag in a new internal_metadata field instead of appending it to user_metadata (#193432)

user_metadata in torch.cuda.memory._snapshot() trace entries is now exactly what was set with torch.cuda.memory._set_memory_metadata (which now also accepts a dict). Tools that searched user_metadata for mallocWithAddress must read internal_metadata instead.

# 2.14
tagged = [e for e in trace if "mallocWithAddress" in e["user_metadata"]]
# 2.15
tagged = [e for e in trace if e.get("internal_metadata") == "mallocWithAddress"]

Remove the deprecated FunctionEvent.metadata_json property (#198265)

Accessing it now raises AttributeError: 'FunctionEvent' object has no attribute 'metadata_json', and the metadata_json constructor argument is removed. Use FunctionEvent.metadata, a dict populated when _ExperimentalConfig(expose_kineto_event_metadata=True) is set (not the deprecated event_metadata).

metadata = event.metadata_json  # 2.14: JSON string
metadata = event.metadata  # 2.15: dict[str, Any] or None

Rename the experimental CUPTI monitor profiler backend to Cuspy, without aliases for the old names (#195881)

In _ExperimentalConfig(custom_profiler_config=...), "cupti_monitor" is now "cuspy" and "cupti_monitor_async_export" is now "cuspy_async_export"; old names silently fall back to the default Kineto backend. prof.take_pending_cupti_export() is now take_pending_cuspy_export() (the old name raises AttributeError). Prefer the new torch.profiler.CuspyConfig.

# 2.14
cfg = _ExperimentalConfig(custom_profiler_config='{"backend":"cupti_monitor"}')
# 2.15
cfg = _ExperimentalConfig(custom_profiler_config='{"backend":"cuspy"}')

Dynamo

Higher-order ops now reject input mutation and aliasing in their bodies unless the op opts in (#185738)

Before, Dynamo let any higher-order op body mutate or alias its inputs by default. Ops that do not implement those semantics could silently produce invalid graphs. Mutation and aliasing are now off by default. The built-in wrappers that support them (wrap, checkpoint, autograd.Function, autocast/set-grad wrappers) opt in. A flex_attention mask_mod may read captured views but must not mutate inputs or return aliases. Under fullgraph=True, unsupported mutation or aliasing raises Encountered input mutation during higher order op tracing or Encountered aliasing during higher order op tracing; otherwise, Dynamo graph breaks and falls back to eager execution. Rewrite the higher-order op body to avoid mutation or aliasing.

For example, rewrite an in-place flex_attention score modifier as an out-of-place operation:

Version 2.14:

def score_mod(score, b, h, q, k):
    score.add_(1)
    return score.clone()

Version 2.15:

def score_mod(score, b, h, q, k):
    return score + 1

Inductor

torch.compiler.nested_compile_region(options=...) now accepts only an allowlist of Inductor config patches (#195864, #195865)

Patches passed through get_invoke_subgraph_compile_options(fw_inductor_config_patches=..., bw_inductor_config_patches=...) used to accept any torch._inductor.config key, though many were silently ignored. Only fallback_by_default and max_autotune are now accepted; other keys raise ValueError: Inductor config key '<key>' is not supported in forward nested compile-region options (or backward). Apply other options to the whole compiled function. Patch dictionaries are now snapshotted when the options are created, so later mutation has no effect, and the default no longer implicitly sets triton.autotune_at_compile_time=True.

Version 2.14:

opts = get_invoke_subgraph_compile_options(fw_inductor_config_patches={"triton.multi_kernel": 1})

Version 2.15:

opts = get_invoke_subgraph_compile_options(fw_inductor_config_patches={"max_autotune": True})
compiled = torch.compile(fn, options={"triton.multi_kernel": 1})

torch.compiler.precompile is now a module instead of a callable; capture with torch.compiler.precompile.capture(...) and reload with torch.compiler.precompile.load(...) (#197993, #198135, #198213)

Calling torch.compiler.precompile(fn, *example_inputs) now raises TypeError: 'module' object is not callable. capture(fn, *, artifact_path, cache_path) returns a context manager that you call once inside the with block; it writes both files when the block exits cleanly (or on cap.save()), and load now takes those paths. decompositions= moves to tracer=MakeFxTracer(decompositions=...).

Version 2.14:

python_code, cache = torch.compiler.precompile(lambda m, x: m(x), model, x)
f = torch.compiler.precompile.load(python_code, cache)

Version 2.15:

with torch.compiler.precompile.capture(lambda m, x: m(x), artifact_path="m.py", cache_path="m.cache") as cap:
    cap(model, x)
f = torch.compiler.precompile.load("m.py", "m.cache")

Composability

Under functionalization, a regenerated output of split, split_with_sizes or unbind is now rebuilt as a single slice or select of its base, so its grad_fn is SliceBackward0/SelectBackward0 instead of SplitBackward0/SplitWithSizesBackward0/UnbindBackward0 (#194037)

This greatly reduces compile time for code that mutates many split() views (for example 32s to 15s with 128 views). Gradients are unchanged, but the in-place error now names the new op with output index 0: RuntimeError: Output 0 of Select is a view and is being modified inplace. Code that inspects grad_fn names, matches the old error text, or pattern-matches split/unbind nodes in functionalized graphs needs updating. There is no option to restore the previous behavior.

Version 2.14:

>>> out = torch.func.functionalize(f)(x)  # f returns base.unbind(0)[1] after base.add_(1)
>>> out.grad_fn
<UnbindBackward0 object at 0x...>

Version 2.15:

>>> out = torch.func.functionalize(f)(x)
>>> out.grad_fn
<SelectBackward0 object at 0x...>

Release Engineering

PyPI wheels now ship with CUDA 13.2, and CUDA 12.6 and CUDA 13.0 wheels are no longer published (#196249, #198913)

The default PyPI wheel moves from CUDA 13.0 to CUDA 13.2. The 2.15 wheels are cu132 and cu134; cu126 and cu130 are no longer built. CUDA 13 wheels need NVIDIA driver 580 or newer and a GPU of Turing (sm_75) or newer, so Maxwell, Pascal and Volta GPUs and hosts with a CUDA 12.x driver should stay on 2.14.

Version 2.15:

pip install torch

# CUDA 13.4 wheels

# To stay on CUDA 12.6 or CUDA 13.0, pin PyTorch 2.14:

PyTorch 2.15 raises the minimum supported Python version for binaries to 3.11: no cp310 wheels are built for torch or the Triton wheels, and CI no longer tests on Python 3.10. On Python 3.10, pip cannot find a 2.15 wheel. Upgrade to Python 3.11 or newer, or stay on PyTorch 2.14.

Version 2.14:

python3.10 -m pip install torch  # cp310 wheel available

Version 2.15:

python3.11 -m pip install torch==2.15.0  # Python 3.11 through 3.15 (including 3.14t and 3.15t)

ROCm wheels move to ROCm 7.14 and 10.0; ROCm 7.2 wheels and gfx900/gfx906 kernels are dropped (#194919)

gfx900 (MI25) and gfx906 (MI50/MI60, Radeon VII) users can stay on 2.14 (rocm7.2) or build from source with those targets in PYTORCH_ROCM_ARCH.

pip install torch --index-url https://download.pytorch.org/whl/rocm7.14  # or rocm10.0

Linux CUDA wheels no longer depend on the cuRAND library (#194850)

PyTorch only uses the cuRAND device API, so torch no longer links libcurand, no longer preloads it on import torch, and the wheel's CUDA requirements no longer include cuRAND. Extensions or libraries that call the cuRAND host API (for example curandCreateGenerator) and relied on pip install torch bringing in the cuRAND library can fail to load libcurand.so and must now install it themselves.

Version 2.15:

pip install torch
pip install "cuda-toolkit[curand]==13.2.2"  # match the toolkit version of your wheel

CUDA

torch.histc(..., out=...) on CUDA now raises an error when out does not have the same dtype as the input (#196100)

CUDA used to silently cast into any out dtype. It now matches CPU and MPS and rejects mismatches, even widening ones. Compute without out and cast instead.

Version 2.14:

>>> torch.histc(x, bins=4, min=-2.0, max=2.0, out=int64_out)  # silently truncated

Version 2.15:

RuntimeError: torch.histogram: input tensor and hist tensor should have the same dtype, but got input float and hist long int
>>> int64_out.copy_(torch.histc(x, bins=4, min=-2.0, max=2.0))  # workaround

On CUDA, cuBLAS and cuBLASLt workspaces are now allocated for each operation instead of being cached per handle and stream (#194311)

Graphs captured separately on one stream could share the cached workspace and fail on replay with CUDA error: an illegal memory access was encountered. Workspaces are now freed after each op, so torch.cuda.memory_allocated() excludes them and the handle from torch.cuda.current_blas_handle() has no ATen workspace attached. Set TORCH_CUBLAS_WORKSPACE_CACHE=1 to restore caching (unsafe with multiple graphs on one stream). TORCH_CUBLASLT_UNIFIED_WORKSPACE now only takes effect with caching enabled. ROCm has a matching change (#196920).

Version 2.14:

>>> torch.mm(a, a, out=out)
>>> torch.cuda.memory_allocated() - before > 0  # workspace stays allocated
True

Version 2.15:

>>> torch.cuda.memory_allocated() - before  # freed after the op
0

CPU (AArch64)

Float32 torch.sin and torch.cos on Arm CPUs (NEON and SVE) now use SLEEF's 3.5-ULP kernels instead of the 1.0-ULP kernels, matching the accuracy of the x86 AVX2 implementation and running 1.7x-2.4x faster on Neoverse V1/V2 (#196315)

Float32 sin and cos results on Arm can now differ from earlier releases in the last bits. Bit-for-bit comparisons against stored golden outputs, torch.equal, or torch.testing.assert_close with rtol=0, atol=0 may fail; default assert_close tolerances are unaffected. There is no switch to restore the previous kernels; if you need tighter accuracy, compute in float64 and cast back.

Version 2.14:

>>> x.cos()  # float32 on Arm: within 1 ULP

Version 2.15:

>>> x.cos()  # float32 on Arm: within 2 ULP
>>> x.double().cos().float()  # workaround: correctly rounded

MPS

The MPS backend now requires macOS 15 (Sequoia) or newer (#199261, #200290)

macOS 14 has reached end of life, so its MPS workarounds were removed. On macOS 14, torch.backends.mps.is_available() returns False and allocating on mps raises the error below. To keep using MPS, stay on PyTorch 2.14 or upgrade macOS; CPU builds still run on older macOS. C++ extensions: at::mps::MacOSVersion::MACOS_14_4 was removed.

>>> torch.ones(2, device="mps")  # 2.15 on macOS 14
RuntimeError: The MPS backend is supported on macOS 15.0+. Current OS version can be queried using `sw_vers`

XPU

Remove the allocator property from torch.xpu.MemPool, aligning with other accelerators (#192041)

torch.xpu.MemPool no longer exposes the allocator it was constructed with, so pool.allocator now raises AttributeError. Keep your own reference to the allocator instead; passing one to the MemPool constructor is unchanged.

Before:

pool = torch.xpu.MemPool(allocator.allocator())
my_allocator = pool.allocator

After:

my_allocator = allocator.allocator()
pool = torch.xpu.MemPool(my_allocator)

Complex Frontend

Ops that are undefined for complex inputs now raise TypeError instead of RuntimeError (#192350)

This covers order-dependent ops (sort, argsort, topk, argmax/argmin, max/min with dim, maximum/minimum, fmax/fmin, aminmax), isposinf/isneginf, view_as_real/imag on real tensors, and view_as_complex on complex tensors, matching Python (1j < 2j is a TypeError). except RuntimeError: no longer catches these; catch (RuntimeError, TypeError). Ops not yet implemented for a dtype (e.g. rad2deg, nansum, heaviside on complex, topk/argmax on bool) now raise NotImplementedError, which except RuntimeError: still catches. Full max()/min()/amax/amin are unchanged.

torch.sort(torch.randn(3, dtype=torch.cfloat))
# 2.14: RuntimeError:  Sort does not support complex dtypes on CPU
# 2.15: TypeError:  Sort does not support complex dtypes on CPU

Deprecations

Optimizer

Passing a bare set of parameters to an optimizer is deprecated and now emits a FutureWarning; it will become an error in a future release (#198710)

Set iteration order can change between runs, so optimizer state could silently mismatch parameters on reload. The warning reads: optimizer parameters need to be organized in ordered collections, but the ordering of tensors in sets will change between runs. Please use a list instead.

opt = torch.optim.Adam(set(model.parameters()))  # 2.15: FutureWarning
opt = torch.optim.Adam(list(model.parameters()))  # recommended

Linear Algebra Frontend

MAGMA is deprecated for LU factorization with pivoting on CUDA: torch.linalg.lu_factor, torch.linalg.lu, and the ops that use it internally (torch.linalg.solve, torch.linalg.inv, torch.linalg.det, torch.linalg.slogdet) now always use cuSOLVER (#190661)

This only affects code that sets torch.backends.cuda.preferred_linalg_library("magma"): pivoted LU now uses cuSOLVER anyway; a new built-in batched LU kernel replaces MAGMA's for large batches. When MAGMA is preferred, the first call warns: linalg.lu_factor: MAGMA, as a linear algebra backend, is deprecated and will be removed in future releases. pivot=False still uses MAGMA when it is preferred. To avoid the warning, use the default or cuSOLVER backend.

torch.backends.cuda.preferred_linalg_library("magma")
LU, pivots = torch.linalg.lu_factor(A)  # 2.14: MAGMA; 2.15: cuSOLVER + UserWarning

CUDA

torch.cuda.graph_annotations.clear_kernel_annotations() is deprecated and now emits a FutureWarning (#195398)

The CUDA graph kernel annotation registry now cleans up after itself: annotations are rekeyed to the executable graph when it is instantiated and dropped when that graph is destroyed.
