bóveda v2.1.2

07 de octubre de 2026

CAMBIOS ÚLTIMOS:

  • pki: la finalización de ACME con la política de directorio predeterminada sign-verbatim ahora rechaza las CSR que contienen URI SAN, correo electrónico SAN u otras SAN. Los desafíos de ACME solo verifican los nombres DNS y las direcciones IP; esos tipos de SAN nunca se validan y no deben aparecer en los certificados emitidos. Los operadores que requieran el comportamiento anterior pueden configurar default_directory_policy = "sign-verbatim-unsafe" en config/acme, aceptando que los certificados resultantes puedan contener afirmaciones de identidad no verificadas. SEGURIDAD:
  • core (empresa): evita que se omita la canonicalización del nombre de la política en las restricciones de parámetros de ACL.
  • núcleo/complemento: corrige las entradas del catálogo de complementos restauradas a partir de una instantánea de balsa, escrita a través de sys/raw o replicada, pudiendo ejecutar un binario fuera de plugin_directory.
  • core/policy: fortalece la construcción de ACL en el momento de la solicitud para ignorar referencias de políticas heredadas mal formadas que contienen segmentos de navegación de ruta (. o ..), de modo que los nombres de estilo transversal nunca se resuelvan ni apliquen.
  • núcleo: se corrigió una omisión de las políticas de ACL de denegación exacta donde los nombres de rol de AppRole, AWS, Azure, GCP, Kubernetes, SCEP o TPM, las claves de mapeo de políticas de usuario o equipo GitHub, los nombres de certificados o CRL, los nombres de políticas de ACL/RGP/EGP o los nombres de usuario de contraseña podían evadir la denegación y ser resueltos por el backend en el mismo recurso protegido. Los nombres de grupo Okta, los nombres LDAP y RADIUS en los montajes que se dejan en su configuración predeterminada que no distingue entre mayúsculas y minúsculas y los nombres Enterprise SCIM client (identity/scim/client/<name>, donde una escritura de variante de mayúsculas y minúsculas sobrescribe el client existente) no están cubiertos por esta solución y permanecen sujetos a la misma omisión; Evite combinar un permiso comodín con una denegación exacta en esas monturas y caminos. CAMBIOS:
  • núcleo/complemento: las entradas del catálogo de complementos ahora se comparan con plugin_directory cada vez que se utilizan, no solo durante el registro. Una entrada cuyo comando se resuelve fuera del directorio, incluso a través de un enlace simbólico, se rechaza con plugin command is outside of configured plugin directory, y los montajes que lo utilizan se omiten al inicio mientras se conservan sus datos. Dichos complementos deben registrarse nuevamente con su binario dentro de plugin_directory.
  • núcleo/política: Vault ahora valida los nombres de las políticas con comprobaciones basadas en segmentos. Los nombres vacíos y los nombres que contienen segmentos de ruta . o .. se rechazan para asignaciones y escrituras de nuevas políticas, mientras que los nombres que contienen / y \ siguen siendo compatibles. Durante la construcción de la ACL en el momento de la solicitud, las referencias de políticas de estilo transversal heredadas no se aplican (se tratan como no válidas y no resueltas), lo que puede reducir los permisos de token efectivos. Los operadores deben auditar y cambiar el nombre de las políticas afectadas antes de actualizar.
  • núcleo: rutas de reglas de ACL y Sentinel EGP dirigidas a un rol específico de AppRole, AWS, Azure, GCP, Kubernetes, SCEP o TPM, clave de mapeo de políticas de usuario o equipo GitHub, nombre de certificado o CRL, nombre de política de ACL/RGP/EGP o nombre de usuario de contraseña ahora se comparan con el nombre de recurso en minúsculas, ya que estos backends resuelven esos nombres sin distinguir entre mayúsculas y minúsculas. Una regla escrita con un nombre de recurso en mayúsculas y minúsculas (por ejemplo, auth/approle/role/MyRole) ya no coincide con las solicitudes de ese recurso y se debe reescribir usando el nombre en minúsculas (auth/approle/role/myrole). La forma en minúsculas también es lo que las políticas Sentinel RGP y EGP observan como request.path, por lo que las reglas de políticas que comparan ese valor con una ruta de mayúsculas y minúsculas mixtas (por ejemplo, request.path is "auth/approle/role/MyRole") también deben actualizarse. Los complementos secretos y de autenticación externa no se ven afectados por esta normalización y continúan recibiendo solicitudes con su formato original. Las reglas de denegación existentes que utilizan nombres de recursos en mayúsculas y minúsculas no se abrirán (se volverán permitidas todas) después de la actualización hasta que se vuelvan a escribir con nombres en minúsculas. MEJORAS:
  • auth/spiffe (empresa): agregue el controlador cli de inicio de sesión SPIFFE.
  • secretos/pki: agregue el campo extra_subject_names_oids a los roles para permitir especificar componentes adicionales del nombre del sujeto OID. CORRECCIÓN DE ERRORES:
  • auth/approle: Se corrigió la validación de token_bound_cidrs al usar bloques /128 para rol e ID secreto
  • ui: Se corrigió la regresión donde la solicitud de configuración de facturación de recuento de client omitía el encabezado del espacio de nombres raíz, lo que provocaba mensajes 404 en Monitoreo > Recuento de Client cuando se veía desde un espacio de nombres secundario

vault v2.1.2

October 07, 2026

BREAKING CHANGES:

  • pki: ACME finalization with the default sign-verbatim directory policy now rejects CSRs that contain URI SANs, email SANs, or Other SANs. ACME challenges only verify DNS names and IP addresses; those SAN types are never validated and must not appear in issued certificates. Operators who require the previous behaviour can set default_directory_policy = "sign-verbatim-unsafe" in config/acme, accepting that the resulting certificates may contain unverified identity claims.

SECURITY:

  • core (enterprise): Prevent policy-name canonicalization bypasses in ACL parameter restrictions.
  • core/plugin: Fix plugin catalog entries restored from a raft snapshot, written through sys/raw, or replicated being able to run a binary outside plugin_directory.
  • core/policy: Harden request-time ACL construction to ignore malformed legacy policy references containing path-navigation segments (. or ..) so traversal-style names are never resolved or applied.
  • core: Fixed a bypass of exact-deny ACL policies where case-variant AppRole, AWS, Azure, GCP, Kubernetes, SCEP, or TPM role names, GitHub team or user policy mapping keys, certificate or CRL names, ACL/RGP/EGP policy names, or userpass usernames could evade the deny and be resolved by the backend to the same protected resource. Okta group names, LDAP and RADIUS names on mounts left in their default case-insensitive configuration, and Enterprise SCIM client names (identity/scim/client/<name>, where a case-variant write overwrites the existing client) are not covered by this fix and remain subject to the same bypass; avoid combining a wildcard allow with an exact deny on those mounts and paths.

CHANGES:

  • core/plugin: Plugin catalog entries are now checked against plugin_directory whenever they are used, not only at registration. An entry whose command resolves outside the directory, including through a symlink, is refused with plugin command is outside of configured plugin directory, and mounts that use it are skipped at startup while keeping their data. Such plugins must be registered again with their binary inside plugin_directory.
  • core/policy: Vault now validates policy names with segment-aware checks. Empty names and names containing . or .. path segments are rejected for new policy writes and assignments, while names containing / and \ remain supported. During request-time ACL construction, legacy traversal-style policy references are not applied (treated as invalid and unresolved), which can reduce effective token permissions. Operators should audit and rename affected policies before upgrading.
  • core: ACL and Sentinel EGP rule paths targeting a specific AppRole, AWS, Azure, GCP, Kubernetes, SCEP, or TPM role, GitHub team or user policy mapping key, certificate or CRL name, ACL/RGP/EGP policy name, or userpass username are now matched against the lowercased resource name, since these backends resolve those names case-insensitively. A rule written with a mixed-case resource name (for example auth/approle/role/MyRole) no longer matches requests for that resource and must be rewritten using the lowercase name (auth/approle/role/myrole). The lowercased form is also what Sentinel RGP and EGP policies observe as request.path, so policy rules that compare that value against a mixed-case path (for example request.path is "auth/approle/role/MyRole") must be updated as well. External auth and secret plugins are not affected by this normalization and continue to receive requests with their original casing. Existing deny rules using mixed-case resource names will fail open (become allow-all) after upgrade until rewritten with lowercase names.

IMPROVEMENTS:

  • auth/spiffe (enterprise): Add SPIFFE login cli handler.
  • secrets/pki: Add extra_subject_names_oids field to roles to allow specifying additional OID subject name components.

BUG FIXES:

  • auth/approle: Fix token_bound_cidrs validation when using /128 blocks for role and secret ID
  • ui: Fix regression where the client count billing configuration request omitted the root-namespace header, causing 404s on Monitoring > Client Count when viewed from a child namespace
