#LightRAG v1.5.3

⚠️ Notas de actualización (implementaciones de Milvus existentes)

Debido al PR #3228, la actualización de una implementación de Milvus existente desencadena una migración automática única en el siguiente inicialize_storages(): la colección heredada se copia en la nueva colección con sufijo de modelo (actualizada con esquema y truncada en bytes) antes de que el servicio esté listo. Planifique el tiempo de inicio adicional y el rendimiento de escritura en colecciones grandes.

  • La migración se ejecuta solo una vez. Una vez que existe la colección con sufijo, cada inicio posterior la valida y la carga directamente y no vuelve a escanear ni migrar la colección heredada.
  • Los datos heredados nunca se eliminan automáticamente. Por seguridad, la antigua colección {workspace}_{namespace} se conserva, no se elimina, por lo que el almacenamiento de vectores se duplica temporalmente después de la actualización. Esto es intencional: la migración no le recupera el espacio.
    • Acción requerida: una vez que haya confirmado que la migración se realizó correctamente y que el nuevo sistema funcione correctamente con la colección con sufijo de modelo, elimine manualmente la colección anterior {workspace}_{namespace} para recuperar el almacenamiento. Hasta que lo haga, los vectores duplicados permanecerán en el disco.
  • Las colecciones heredadas cuyos datos son incompatibles (dimensión vectorial diferente o un esquema simple antiguo sin campo vectorial) no se migran; en su lugar, se crea una nueva colección con sufijos y los datos heredados no se modifican.

LightRAG v1.5.3

Highlights

  • Milvus upgrades require a one-time migration — PR #3228 isolates collections by embedding model. The next initialize_storages() copies legacy data into a model-suffixed collection with schema upgrades and byte truncation, adding startup time and migration write I/O. The old {workspace}_{namespace} collection remains untouched, duplicating vector storage until you manually drop it after verification. Incompatible dimensions or schemas are skipped rather than converted; migration resilience is improved in #3258–#3260.
  • Offline vector-database recovery — PR #3243 adds an offline VDB rebuild path for vector drift, giving operators a dedicated recovery tool for damaged or inconsistent vector state. Schedule a maintenance window because the rebuild is not an online operation.
  • MAX_ASYNC now enforces a deployment-wide limit — PR #3253 makes the cap aggregate across gunicorn workers instead of applying independently per process, so existing settings may reduce effective parallelism. Aggregated queue statistics and server mode/worker-count reporting (#3265) help validate the resulting concurrency.
  • Storage and provider fixes prevent stale data and resource leaks — Qdrant/PostgreSQL workspace drops now remove legacy rows that could resurrect cleared data (#3254), while Mongo and Anthropic clients are closed on release/error paths (#3251, #3261). Malformed multimodal JSON is retried (#3242), MinerU transport failures reach doc_status.error_msg (#3274), and sync wrappers provide clearer event-loop diagnostics (#3271).
  • Security boundaries are tighter — Workspace path traversal is rejected (#3244), and Neo4j APOC labelFilter is parameterized to prevent Cypher injection (#3257). Deployments accepting untrusted workspace names or graph labels should prioritize this upgrade.
  • Compatibility — No breaking changes are listed.

⚠️ Upgrade Notes (existing Milvus deployments)

Due to PR #3228, upgrading an existing Milvus deployment triggers a one-time automatic migration on the next initialize_storages(): the legacy collection is copied into the new model-suffixed collection (schema-upgraded and byte-truncated) before the service becomes ready. Plan for the extra startup time and write throughput on large collections.

  • The migration runs only once. After the suffixed collection exists, every subsequent startup validates and loads it directly and does not re-scan or re-migrate the legacy collection.
  • The legacy data is never deleted automatically. For safety the old {workspace}_{namespace} collection is kept, not dropped, so vector storage is temporarily duplicated after the upgrade. This is intentional — the migration does not reclaim the space for you.
    • Action required: once you have confirmed the migration succeeded and the new system works correctly against the model-suffixed collection, manually drop the old {workspace}_{namespace} collection yourself to reclaim storage. Until you do, the duplicated vectors remain on disk.
  • Legacy collections whose data is incompatible (different vector dimension, or an old simple schema with no vector field) are not migrated; a fresh suffixed collection is created instead and the legacy data is left untouched.
