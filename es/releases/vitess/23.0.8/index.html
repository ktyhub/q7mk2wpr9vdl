#vitess v23.0.8

Lanzamiento de Vitess v23.0.8

Resumen

Se rechazan los valores sql_mode no admitidos

Puerta VTG

VTGate ya rechazó declaraciones SET sql_mode = ... que habilitan un modo que el analizador Vitess no admite (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). La verificación comparó los nombres de los modos textualmente y podría omitirse. VTGate ahora implementa la semántica de asignación sql_mode de MySQL 8.x y valida cada asignación con respecto a ella:

  • La configuración de un modo no compatible se rechaza incluso cuando el MySQL subyacente ya se ejecuta con ese modo, es decir, cuando el SET no cambiaría el valor. Dichas declaraciones anteriormente tuvieron éxito, aunque VTGate no analiza consultas bajo estos modos. El modo de combinación ANSI también se rechaza porque habilita ANSI_QUOTES, PIPES_AS_CONCAT y REAL_AS_FLOAT.
  • Ahora también se rechazan IGNORE_SPACE y HIGH_NOT_PRECEDENCE. Son los dos modos restantes que cambian la forma en que se interpreta el texto SQL. El analizador Vitess no los respeta, por lo que VTGate analizaría las consultas de manera diferente a las promesas sql_mode de la sesión.
  • Los nombres de modos desconocidos y los valores numéricos no válidos fallan con los errores propios de MySQL: ER_WRONG_VALUE_FOR_VAR (1231) y ER_UNSUPPORTED_SQL_MODE (3899) para los bits de modos eliminados en MySQL 8.0.
  • Los valores numéricos se decodifican con la máscara de bits sql_mode de MySQL. Por ejemplo, SET sql_mode = 1048576 informa que NO_BACKSLASH_ESCAPES no es compatible. Se aceptan valores numéricos válidos.
  • Los valores constantes se validan en el momento de la planificación, sin ida y vuelta. Esto incluye expresiones constantes como CONCAT sobre literales y también se aplica cuando --enable-system-settings está deshabilitado. Las expresiones no constantes se validan en el momento de la ejecución, una vez que se conoce su valor.

VTTablet

VTTablet aplica la misma validación en sus propios puntos de entrada y devuelve los mismos errores: configuración de conexión, en el grupo de configuración y en conexiones reservadas, y declaraciones SET sql_mode de ámbito de sesión. Esto cubre clients que omiten la validación de VTGate, como VTGates que aún no se han actualizado y clients que se comunican directamente con el servicio de consulta. Las sugerencias del optimizador SET_VAR se envían a MySQL sin cambios. Cada conexión MySQL que crea Vitess ahora elimina los modos que cambian cómo se interpreta el texto SQL de la sesión sql_mode que hereda del valor global del servidor. Se mantienen todos los demás modos, como los modos estrictos y los modos de fecha cero. Esto se aplica a todos los componentes: servicio de consultas, seguimiento de esquemas, latidos, administración de replicación, DDL en línea, VReplication y VDiff, y conexiones a servidores MySQL externos. El sql_mode global no cambia.

Impacto

  • Los Clients que ejecutan SET sql_mode con un modo no compatible, incluidos ANSI, IGNORE_SPACE y HIGH_NOT_PRECEDENCE, ahora reciben un error. Esto también sucede cuando el SET coincide con el sql_mode actual del backend. Clients que establecen nombres de modo MySQL también rechazarían recibir un error.
  • Durante una actualización continua, las VTTablets generalmente se actualizan antes que las VTGates. Una sesión que configura un sql_mode ahora rechazado a través de un VTGate que aún no está actualizado comienza a recibir errores de VTTablets actualizados.
  • Un backend cuyo sql_mode global incluya uno de estos modos lo conserva, pero las sesiones de Vitess ya no lo heredan. Consulte #20883 para obtener más detalles.

Tabla ACL: las personas que llaman con cada función en cada tabla pueden ejecutar declaraciones cuyas tablas no se pueden determinar

v23.0.7 comenzó a negar, bajo la tabla estricta ACL (--queryserver-config-strict-table-acl), declaraciones cuyas tablas vttablet no puede determinar (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA y un CREATE TABLE que el analizador de vttablet no puede analizar completamente) para cada persona que llama fuera de la ACL exenta (--queryserver-config-acl-exempt-acl); consulte GHSA-w6mx-2f8x-pqf4. Una persona que llama, que es un lector, un escritor y un administrador en un grupo de tablas que cubre cada tabla ("table_names_or_prefixes": ["%"]), tiene todos los roles en cualquier tabla que dicha declaración pueda tocar, por lo que DO, REPAIR, OPTIMIZE y un CREATE TABLE parcialmente analizado ahora se ejecutan para él. CALL y LOAD DATA permanecen denegados incluso entonces, ya que un procedimiento SQL SECURITY DEFINER se ejecuta con los privilegios de su definidor y LOAD DATA INFILE lee archivos en el servidor, ninguna de las cuales concede ACL; Emitirlos como persona que llama en la ACL exenta. Estas comprobaciones se cuentan bajo la etiqueta undetermined-table-set TableName, en TableACLDenied o en TableACLAllowed para una persona que llama con todos los roles en cada tabla. Con el ensayo (--queryserver-config-enable-table-acl-dry-run), solo las declaraciones que la verificación denegaría incrementan TableACLPseudoDenied. Consulte #21349 para obtener más detalles.

Juegos de caracteres de conexión restringidos

--db-charset y los otros lugares donde se configura un juego de caracteres de conexión MySQL, ya no aceptan sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le o utf32, ya sea que se proporcionen como un juego de caracteres o como una de sus clasificaciones. Una tableta configurada con uno de ellos no se inicia, VTGate rechaza un SET de character_set_client, character_set_connection, character_set_results o collation_connection a uno de ellos, o a un nombre que no es un juego de caracteres o intercalación, que solía responder con OK e ignorar, y VTTablet rechaza una configuración o declaración SET que cambiaría la conexión de una sesión a uno de ellos. Un client aún puede solicitar uno de ellos en el apretón de manos: VTGate lee sus declaraciones byte a byte, como lo hace la conexión de la tableta a MySQL, por lo que no pueden salir de un literal. Vitess analiza y escapa el texto SQL byte a byte, y en estos conjuntos de caracteres el segundo byte de un carácter puede ser una barra invertida o una comilla invertida, por lo que el texto en ellos se analizó mal o se corrompió en su camino a través de Vitess. Utilice utf8mb4 como juego de caracteres de conexión. Las tablas y columnas aún se pueden declarar con cualquiera de estos conjuntos de caracteres; MySQL realiza conversiones entre ellos y el juego de caracteres de conexión. Esto corrige GHSA-c28j-qmfx-4gxp. Consulte #21392 y #21465 para obtener más detalles.

Los nombres de conjuntos de caracteres y de intercalación se citan cuando se regeneran

Un conjunto de caracteres, intercalación, motor, espacio de tabla o nombre de analizador de texto completo ahora se decodifica cuando se analiza y se vuelve a escribir como un token único cuando Vitess regenera la declaración: desnudo cuando se trata de un conjunto de caracteres, intercalación, motor, tipo de índice o nombre de analizador conocido, entre comillas en caso contrario. Consecuencias visibles para el usuario:

  • Un nombre entre comillas está normalizado. COLLATE 'utf8_bin' se regenera como COLLATE utf8_bin: la ortografía entre comillas y sin comillas significa el mismo nombre, y lo que se almacena es la forma decodificada. Cualquier cosa que compare la forma impresa de estas declaraciones byte por byte verá la nueva ortografía.
  • Solo los nombres conocidos permanecen desnudos. Un nombre de conjunto de caracteres o de intercalación de cualquier versión de MySQL o MariaDB, un motor de almacenamiento conocido como InnoDB o memory, los tipos de índice BTREE, HASH y RTREE, los analizadores ngram y mecab, y los espacios de tablas innodb_system y innodb_file_per_table se vuelven a escribir tal como estaban. deletreado. Cualquier otro nombre está entre comillas: TABLESPACE ts se regenera como TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE Memory does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: CHARACTER SET 'binary' BINARY regenerates as CHARACTER SET `binary` BINARY.
  • COLLATE binary en una expresión está entre comillas. expr COLLATE binary se regenera como expr COLLATE `binary` , because MySQL's expression COLLATE only accepts binary quoted. Column, table and database COLLATE binario and CHARACTER SET binario permanece desnudo.
  • Se rechaza un nombre de espacio de tabla de partición, motor o conjunto de caracteres vacío. CHARACTER SET '' y COLLATE '' en una columna, una tabla, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE y una expresión, ENGINE '' en una tabla o partición, y una partición TABLESPACE '' ya no se analiza. Un nombre vacío en estas posiciones es indistinguible de la cláusula ausente, por lo que anteriormente se habría eliminado o alterado y una declaración que MySQL rechaza podría haberse convertido en una válida y diferente. Las declaraciones que no son DDL obtienen el error directamente; DDL recurre a un análisis parcial, por lo que se reenvía el propio texto de client y MySQL lo rechaza. SET NAMES ... COLLATE '' y SET CHARACTER SET ... COLLATE '', que solían analizar y descartar la clasificación, ahora también son errores de análisis; MySQL rechaza ambos. CREATE/ALTER DATABASE ... CHARACTER SET '' y COLLATE '' no han cambiado: todavía analizan y se escriben de nuevo como ''.
  • ENCRYPTION requiere un valor entrecomillado. CREATE/ALTER DATABASE ... ENCRYPTION N ya no analiza completamente, coincidiendo con MySQL, que solo acepta 'Y' o 'N' como una cadena entrecomillada. Una declaración de este tipo ahora recurre a un análisis parcial en lugar de regenerarse en una ortografía que MySQL rechazaría. Esto soluciona GHSA-j8pc-mcwq-qrg6. Consulte #21435 para obtener más detalles.

Los modos VTAdmin VExplain que ejecutan la declaración requieren la acción execute

VExplain API de VTAdmin fue autorizado con la acción get, pero VEXPLAIN QUERIES, ALL y TRACE ejecutan la declaración que explican, por lo que un actor al que solo se le permite leer podría cambiar datos a través de ella (GHSA-c2r8-grjp-w8c2). Esos modos ahora requieren la nueva acción execute en el recurso VExplain; PLAN y KEYS, que solo planifican la declaración, aún requieren solo get. Para esos modos, VTAdmin también acepta solo un SELECT sin INTO, secuencia de valores siguientes o funciones de bloqueo de asesoramiento, y los ejecuta en una transacción de solo lectura que siempre se revierte. La página VExplain en la interfaz de usuario web ahora tiene como valor predeterminado PLAN. Migración: otorga la acción execute en VExplain a los actores que deben ejecutar VEXPLAIN QUERIES, ALL o TRACE. Las reglas que otorgan todas las acciones (*) y --no-rbac ya lo incluyen. Impacto: un actor con solo get en VExplain recibe un error unauthorized de VEXPLAIN QUERIES, ALL y TRACE. Consulte #21396 para obtener más detalles.

vitess v23.0.8

Release of Vitess v23.0.8

Summary

Unsupported sql_mode values are rejected

VTGate

VTGate already rejected SET sql_mode = ... statements that enable a mode the Vitess parser does not support (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). The check compared mode names textually and could be bypassed. VTGate now implements MySQL 8.x's sql_mode assignment semantics and validates every assignment against them:

  • Setting an unsupported mode is rejected even when the underlying MySQL already runs with that mode, that is, when the SET would not change the value. Such statements previously succeeded, even though VTGate does not parse queries under these modes. The combination mode ANSI is rejected as well, because it enables ANSI_QUOTES, PIPES_AS_CONCAT, and REAL_AS_FLOAT.
  • IGNORE_SPACE and HIGH_NOT_PRECEDENCE are now also rejected. They are the two remaining modes that change how SQL text is interpreted. The Vitess parser does not honor them, so VTGate would parse queries differently than the session's sql_mode promises.
  • Unknown mode names and invalid numeric values fail with MySQL's own errors: ER_WRONG_VALUE_FOR_VAR (1231), and ER_UNSUPPORTED_SQL_MODE (3899) for the bits of modes removed in MySQL 8.0.
  • Numeric values decode against MySQL's sql_mode bitmask. For example, SET sql_mode = 1048576 reports that NO_BACKSLASH_ESCAPES is unsupported. Valid numeric values are accepted.
  • Constant values are validated at planning time, with no shard round trip. This includes constant expressions such as CONCAT over literals, and it also applies when --enable-system-settings is disabled. Non-constant expressions are validated at execution time, once their value is known.

VTTablet

VTTablet applies the same validation at its own entry points and returns the same errors: connection settings, on the settings pool and on reserved connections, and session-scope SET sql_mode statements. This covers clients that bypass VTGate's validation, such as VTGates that are not upgraded yet and clients that talk to the query service directly. SET_VAR optimizer hints are forwarded to MySQL unchanged.

Every MySQL connection Vitess creates now strips the modes that change how SQL text is interpreted from the session sql_mode it inherits from the server's global value. All other modes, such as the strict modes and the zero-date modes, are kept. This applies to every component: query serving, schema tracking, heartbeats, replication management, Online DDL, VReplication and VDiff, and connections to external MySQL servers. The global sql_mode is not changed.

Impact

  • Clients that run SET sql_mode with an unsupported mode, including ANSI, IGNORE_SPACE and HIGH_NOT_PRECEDENCE, now receive an error. This also happens when the SET matches the backend's current sql_mode. Clients that set mode names MySQL would itself reject receive an error as well.
  • During a rolling upgrade, VTTablets are typically upgraded before VTGates. A session that sets a now-rejected sql_mode through a VTGate that is not upgraded yet starts receiving errors from upgraded VTTablets.
  • A backend whose global sql_mode includes one of these modes keeps it, but Vitess sessions no longer inherit it.

See #20883 for details.

Table ACL: callers with every role on every table may run statements whose tables cannot be determined

v23.0.7 began denying, under strict table ACL (--queryserver-config-strict-table-acl), statements whose tables vttablet cannot determine (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA, and a CREATE TABLE that vttablet's parser cannot fully parse) for every caller outside the exempt ACL (--queryserver-config-acl-exempt-acl); see GHSA-w6mx-2f8x-pqf4. A caller that is a reader, a writer and an admin in a table group covering every table ("table_names_or_prefixes": ["%"]) holds every role on any table such a statement could touch, so DO, REPAIR, OPTIMIZE and a partially parsed CREATE TABLE now run for it. CALL and LOAD DATA remain denied even then, since a SQL SECURITY DEFINER procedure runs with its definer's privileges and LOAD DATA INFILE reads files on the server, neither of which table ACL grants; issue them as a caller in the exempt ACL.

These checks are counted under the undetermined-table-set TableName label, in TableACLDenied, or in TableACLAllowed for a caller with every role on every table. With dry-run (--queryserver-config-enable-table-acl-dry-run), only the statements the check would deny increment TableACLPseudoDenied.

See #21349 for details.

Connection character sets restricted

--db-charset, and the other places a MySQL connection character set is configured, no longer accept sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le or utf32, whether given as a character set or as one of its collations. A tablet configured with one of them fails to start, VTGate refuses a SET of character_set_client, character_set_connection, character_set_results or collation_connection to one of them, or to a name that is not a character set or collation, which it used to answer with OK and ignore, and VTTablet refuses a setting or SET statement that would switch a session's connection to one of them. A client may still ask for one of them at the handshake: VTGate reads its statements byte by byte, as the tablet's connection to MySQL does, so they cannot break out of a literal.

Vitess parses and escapes SQL text byte by byte, and in these character sets the second byte of a character can be a backslash or a back quote, so text in them was misparsed or corrupted on its way through Vitess. Use utf8mb4 as the connection character set instead. Tables and columns can still be declared with any of these character sets; MySQL converts between them and the connection character set.

This fixes GHSA-c28j-qmfx-4gxp.

See #21392 and #21465 for details.

Charset and collation names are quoted when regenerated

A charset, collation, engine, tablespace or full-text parser name is now decoded when parsed, and written back as a single token when Vitess regenerates the statement: bare when it is a known charset, collation, engine, index type or parser name, back-quoted otherwise.

User-visible consequences:

  • A quoted name is normalized. COLLATE 'utf8_bin' regenerates as COLLATE utf8_bin — the quoted and unquoted spellings mean the same name, and the decoded form is what is stored. Anything comparing the printed form of these statements byte for byte sees the new spelling.
  • Only known names stay bare. A charset or collation name of any MySQL or MariaDB version, a known storage engine such as InnoDB or memory, the BTREE, HASH and RTREE index types, the ngram and mecab parsers, and the innodb_system and innodb_file_per_table tablespaces are written back as they were spelled. Any other name is back-quoted: TABLESPACE ts regenerates as TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE memory does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: CHARACTER SET 'binary' BINARY regenerates as CHARACTER SET `binary` BINARY.
  • COLLATE binary in an expression is quoted. expr COLLATE binary regenerates as expr COLLATE `binary` , because MySQL's expression COLLATE only accepts binary quoted. Column, table and database COLLATE binary and CHARACTER SET binary stay bare.
  • An empty charset, collation, engine or partition tablespace name is rejected. CHARACTER SET '' and COLLATE '' on a column, a table, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE and an expression, ENGINE '' on a table or a partition, and a partition's TABLESPACE '' no longer parse. An empty name in these positions is indistinguishable from the clause being absent, so it would previously have been dropped or mangled and a statement MySQL rejects could have become a valid, different one. Non-DDL statements get the error directly; DDL falls back to a partial parse, so the client's own text is forwarded and MySQL rejects it. SET NAMES ... COLLATE '' and SET CHARACTER SET ... COLLATE '', which used to parse and discard the collation, are now parse errors too; MySQL rejects both. CREATE/ALTER DATABASE ... CHARACTER SET '' and COLLATE '' are unchanged: they still parse and are written back as ''.
  • ENCRYPTION requires a quoted value. CREATE/ALTER DATABASE ... ENCRYPTION N no longer fully parses, matching MySQL, which only accepts 'Y' or 'N' as a quoted string. Such a statement now falls back to a partial parse rather than being regenerated into a spelling MySQL would refuse.

This fixes GHSA-j8pc-mcwq-qrg6.

See #21435 for details.

VTAdmin VExplain modes that run the statement require the execute action

VTAdmin's VExplain API was authorized with the get action, but VEXPLAIN QUERIES, ALL and TRACE run the statement they explain, so an actor allowed only to read could change data through it (GHSA-c2r8-grjp-w8c2). Those modes now require the new execute action on the VExplain resource; PLAN and KEYS, which only plan the statement, still require only get. For those modes VTAdmin also accepts only a SELECT without INTO, sequence next-values or advisory lock functions, and runs them in a read-only transaction that is always rolled back. The VExplain page in the web UI now defaults to PLAN.

Migration: grant the execute action on VExplain to the actors that should run VEXPLAIN QUERIES, ALL or TRACE. Rules that grant all actions (*) and --no-rbac already include it.

Impact: an actor with only get on VExplain gets an unauthorized error from VEXPLAIN QUERIES, ALL and TRACE.

See #21396 for details.

Security fixes

  • Fixes GHSA-73pp-99vw-h5g8: SQL injection through VStream LastPK values. See #21377.
  • Fixes GHSA-92cc-q2h6-m2vr: SQL injection through convert_tz() arguments in a VStream filter. See #21377.
  • Fixes GHSA-8w3p-4xg5-rm9w: SQL injection through table names in Online DDL statements. See #21381.
  • Fixes GHSA-x56j-8c72-5xgg: SQL injection through the caller ID in query annotations (--queryserver-config-annotate-queries). See #21369.
  • Fixes GHSA-m282-7w35-g77m: SQL injection through a global SET variable name. See #21390.
  • Fixes GHSA-9248-hccp-qf8f: SQL injection through DATE, TIME and TIMESTAMP literals. See #21389.
  • Fixes GHSA-9rx3-8pwm-c228: SQL injection through a session variable value carried in a SET_VAR hint. See #21388.
  • Fixes GHSA-pfg5-ppc7-ff45: SQL hidden from parsing and table ACL checks in a trailing comment. See #21387.
  • Fixes GHSA-xf67-9r78-xv82: SQL injection through malformed numeric bind variables. See #21386.
  • Fixes GHSA-3fr2-mqr5-r5x5: VTAdmin API routes that change cluster state accepted cross-site GET requests. See #21397.
  • Fixes GHSA-78h7-x6qm-xpr8: VTAdmin's ReloadSchemaShard did not check RBAC. See #21394.
