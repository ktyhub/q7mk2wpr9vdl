<a id="major-changes"/>Cambios importantes</a>

<a id="new-support"/>Nuevo soporte</a>

<a id="window-function-pushdown"/>Función de ventana pushdown para espacios de claves fragmentados</a>

Esta versión presenta una optimización que permite que las funciones de la ventana se envíen a fragmentos individuales cuando están divididos por una columna que coincide con un vindex único. Anteriormente, todas las consultas de funciones de ventana requerían enrutamiento de un solo fragmento, lo que limitaba su aplicabilidad en tablas fragmentadas. Con este cambio, las consultas en las que la cláusula PARTITION BY se alinea con un vindex único ahora se pueden presionar hacia abajo y ejecutar en cada fragmento. Para obtener ejemplos y más detalles, consulte la documentación.

<a id="view-routing-rules"/>Ver reglas de enrutamiento</a>

Vitess ahora admite reglas de enrutamiento para vistas y se puede aplicar de la misma manera que las tablas con vtctldclient ApplyRoutingRules. Cuando una regla de enrutamiento de vista está activa, VTGate reescribe las consultas que hacen referencia a la vista de origen para usar la definición de la vista de destino. Por ejemplo, dada esta regla de enrutamiento:

{
  "rules": [
    {
      "from_table": "source_ks.my_view",
      "to_tables": ["target_ks.my_view"]
    }
  ]
}

Y esta definición de vista:

CREATE VIEW target_ks.my_view AS SELECT id, name FROM user;

Una consulta como SELECT * FROM source_ks.my_view se reescribiría internamente como:

SELECT * FROM (SELECT id, name FROM target_ks.user) AS my_view;

Las reglas de enrutamiento de vistas requieren que el rastreador de esquemas supervise las vistas, lo que significa que VTGate debe iniciarse con el indicador --enable-views y VTTablet con el indicador --queryserver-enable-views. La vista de destino debe existir en el espacio de claves especificado para que la regla de enrutamiento funcione correctamente. Para obtener más detalles, consulte la documentación de reglas de enrutamiento de esquemas.

<a id="tablet-targeting"/>Orientación a tabletas mediante declaración USE</a>

VTGate ahora admite enrutamiento de consultas a una tableta específica por alias usando una sintaxis de declaración USE extendida:

USE keyspace:shard@tablet_type|tablet_alias;

Por ejemplo, para apuntar a una réplica de tableta específica:

USE commerce:-80@replica|zone1-0000000100;

Una vez configuradas, todas las consultas posteriores en la sesión se dirigen a la tableta especificada hasta que se borran con una declaración estándar USE keyspace o USE keyspace@tablet_type. Esto es útil para la depuración, el monitoreo por tableta, el calentamiento de caché y otras tareas operativas donde se requiere apuntar a una tableta específica. Nota: Se debe especificar un fragmento cuando se utiliza la segmentación por tableta. Al igual que la segmentación por fragmentos, esto evita el enrutamiento basado en vindex, así que utilícelo con cuidado.

<a id="vtgate-binlog-dump"/>Soporte de transmisión de Binlog</a>

VTGate ahora admite la transmisión de binlog basada en GTID a través de dos protocolos:

  • Protocolo MySQL: Clients se puede conectar utilizando el comando de protocolo de replicación estándar MySQL COM_BINLOG_DUMP_GTID; no se requieren adaptadores especiales compatibles con VStream ni acceso directo a MySQL.
  • gRPC: El nuevo RPC de transmisión BinlogDumpGTID en vtgateservice proporciona acceso nativo a gRPC para clients personalizados sin la dependencia del protocolo MySQL. Nota: Solo se admite la transmisión basada en GTID. La transmisión basada en archivos/posición no está disponible a través de COM_BINLOG_DUMP o COM_BINLOG_DUMP_GTID y devuelve un error. Esta característica está deshabilitada de forma predeterminada. Habilítelo con --enable-binlog-dump. Nuevas banderas:
  • --enable-binlog-dump: Habilita el soporte de volcado de binlog. Sin este indicador, las solicitudes de volcado de binlog devuelven un error.
  • --binlog-dump-authorized-users: lista separada por comas de usuarios autorizados para ejecutar operaciones de volcado de binlog, o % para permitir a todos los usuarios. Requisitos: Al iniciar una conexión de volcado de binlog, clients debe especificar:
  • Un nombre de archivo vacío
  • Una posición de archivo (filepos) de 4
  • Una posición GTID Para gRPC clients, especifique el espacio de claves, el fragmento y, opcionalmente, el tipo de tableta o el alias de tableta directamente en BinlogDumpGTIDRequest. Limitaciones:
  • Cada transmisión funciona en una sola tableta, sin agregación de datos entre fragmentos.
  • Sin conmutación por error automática: si la tableta de destino deja de estar disponible, la transmisión falla y el client debe volver a conectarse a una tableta diferente.
  • No compatible con operaciones MoveTables o Reshard. Utilice VStream API para esos casos de uso.

<a id="structured-logging"/>Registro estructurado</a>

Vitess ahora utiliza el registro estructurado JSON de forma predeterminada. La salida del registro se emite como JSON a stderr. Para configurar el nivel de registro mínimo, pase --log-level (uno de debug, info, warn, error; predeterminado info). Para obtener un formato legible por humanos con detección automática de color, pase --log-format=text. Para volver al backend glog anterior, pase --log-structured=false. glog está obsoleto a partir de la versión 24 y se eliminará en la versión 25.

<a id="breaking-changes"/>Cambios importantes</a>

<a id="vttablet-external-decompressor-manifest"/>El descompresor externo ya no lee desde el MANIFEST de copia de seguridad de forma predeterminada</a>

El comando de descompresor externo almacenado en el archivo MANIFEST de una copia de seguridad ya no se utiliza en el momento de la restauración de forma predeterminada. Anteriormente, cuando no se proporcionaba ningún indicador --external-decompressor, VTTablet recurría al comando especificado en MANIFEST. Esto planteaba un riesgo de seguridad: un atacante con acceso de escritura al almacenamiento de copia de seguridad podría modificar el MANIFEST para ejecutar comandos arbitrarios en la tableta. A partir de la versión 24, el descompresor basado en MANIFEST se ignora a menos que opte explícitamente por el nuevo indicador --external-decompressor-use-manifest. Si confía en este comportamiento, agregue la marca a su configuración de VTTablet, pero tenga en cuenta las implicaciones de seguridad. Consulte #19460 para obtener más detalles.

<a id="minor-changes"/>Cambios menores</a>

<a id="cambios-menores-vreplication"/>VReplication</a>

<a id="vreplication-shards-flag-start-stop"/>marca --shards para iniciar y detener MoveTables/Reshard</a>

Los comandos start y stop para flujos de trabajo MoveTables y Reshard ahora admiten el indicador --shards, lo que permite a los usuarios iniciar o detener flujos de trabajo en un subconjunto específico de fragmentos en lugar de todos los fragmentos a la vez. Uso de ejemplo:

# Start workflow on specific shards only
vtctldclient MoveTables --target-keyspace customer --workflow commerce2customer start --shards="-80,80-"

# Stop workflow on specific shards only
vtctldclient Reshard --target-keyspace customer --workflow cust2cust stop --shards="80-"

<a id="vreplication-tablet-error-retry"/>Reintento automático de tableta para errores específicos de la tableta</a>

Los flujos de trabajo de VReplication ahora reintentan automáticamente con diferentes tabletas cuando encuentran errores específicos de la tableta. Anteriormente, los flujos de trabajo sin una preferencia de celda utilizaban de forma predeterminada la celda local y podían quedarse atascados al volver a intentar la misma tableta defectuosa indefinidamente. Cuando una tableta encuentra errores como la purga de registros binarios (error MySQL 1236 o 1789) o discrepancias en el conjunto de GTID, VReplication agrega esa tableta a una lista de ignorados y prueba otras tabletas en todas las celdas. Una vez que se han probado todas las tabletas coincidentes, la lista de ignorados se borra y el flujo de trabajo se reintenta desde cero. Esto es particularmente útil en implementaciones de varias celdas donde una tableta en la celda local puede carecer de los registros binarios necesarios, pero las tabletas en otras celdas todavía los tienen.

<a id="cambios-menores-vtgate"/>VTGate</a>

<a id="vtgate-removed-grpc-send-session-in-streaming"/>Se eliminó la bandera --grpc-send-session-in-streaming</a>

Se ha eliminado el indicador VTGate --grpc-send-session-in-streaming. Esta bandera quedó obsoleta en v22 a través de #17907 y su valor predeterminado es true. La sesión ahora siempre se envía como el último paquete en la respuesta de transmisión para los RPC StreamExecute y StreamExecuteMulti. Este comportamiento es necesario para admitir transacciones en streaming y no se puede desactivar. Impacto: Elimina cualquier uso del indicador --grpc-send-session-in-streaming de los scripts de inicio o la configuración de VTGate.

<a id="vtgate-new-default-legacy-replication-lag-algorithm"/>Nuevo valor predeterminado para el indicador --legacy-replication-lag-algorithm</a>

El indicador VTGate --legacy-replication-lag-algorithm ahora tiene como valor predeterminado false, lo que desactiva el enfoque heredado para manejar el retraso de replicación de forma predeterminada. En su lugar, se utiliza un algoritmo más simple basado exclusivamente en un retraso bajo, un retraso alto y un número mínimo de tabletas, que ha demostrado ser más estable en muchos entornos de producción. Una explicación detallada de los dos enfoques [se explica en este comentario de código] (https://github.com/vitessio/vitess/blob/main/go/vt/discovery/replicationlag.go#L125-L149). En v25, este indicador quedará obsoleto y en la siguiente versión se eliminará. Mientras tanto, se puede utilizar el comportamiento heredado configurando --legacy-replication-lag-algorithm=true. Esta desaprobación se registra en https://github.com/vitessio/vitess/issues/18914.

<a id="vtgate-session-balancer-mode"/>Nuevo modo "sesión" para el indicador --vtgate-balancer-mode</a>

El indicador VTGate --vtgate-balancer-mode ahora admite un nuevo modo de "sesión" además de los modos "celda", "celda preferida" y "aleatorio" existentes. El modo de sesión dirige cada sesión de forma consistente a la misma tableta durante la duración de la sesión. Para habilitar el modo de sesión, configure la bandera al iniciar VTGate:

--vtgate-balancer-mode=session

<a id="minor-changes-query-serving"/>servicio de consultas</a>

<a id="query-serving-json-extract-dynamic-args"/>JSON_EXTRACT ahora admite argumentos de ruta dinámica</a>

La función JSON_EXTRACT ahora admite argumentos de ruta dinámica como variables de vinculación o resultados de otras llamadas a funciones. Anteriormente, JSON_EXTRACT solo funcionaba con cadenas literales estáticas para argumentos de ruta. El manejo de NULL ahora coincide con el comportamiento de MySQL. La función devuelve NULL cuando el argumento del documento o de la ruta es NULL. Los argumentos de ruta estática aún están optimizados, incluso cuando se mezclan con argumentos dinámicos, por lo que las consultas existentes no verán ninguna regresión en el rendimiento.

<a id="cambios-menores-vttablet"/>VTTablet</a>

<a id="vttablet-init-tablet-type-lookup"/>Nueva bandera experimental --init-tablet-type-lookup</a>

El nuevo indicador experimental --init-tablet-type-lookup para VTTablet permite que las tabletas restauren automáticamente su tipo de tableta anterior al reiniciar buscando el registro de topología existente, en lugar de usar siempre el valor estático --init-tablet-type. Cuando está habilitado, la tableta usa su alias para buscar el tipo de tableta en el registro de topología existente al reiniciar. Esto permite que las tabletas mantengan sus roles modificados (por ejemplo, RDONLY/DRAINED) durante los reinicios sin necesidad de reconfiguración manual. Si está deshabilitado o si no existe ningún registro de topología, se utilizará el valor estándar --init-tablet-type. Nota: Las implementaciones administradas por el operador de Vitess generalmente no mantienen registros de tabletas coincidentes en el cronograma entre los reemplazos de pods, por lo que esta característica tendrá un efecto más limitado en esos entornos.

<a id="vttablet-querythrottler-metrics"/>Métricas de observabilidad de QueryThrottler</a>

VTTablet ahora expone nuevas métricas para rastrear el comportamiento de QueryThrottler. Se han agregado cuatro nuevas métricas:

  • QueryThrottlerRequests: número total de solicitudes evaluadas por el regulador de consultas
  • QueryThrottlerThrottled: número de solicitudes limitadas
  • QueryThrottlerTotalLatencyNs: tiempo total que tarda cada solicitud en la limitación de consultas, incluida la evaluación, las comprobaciones de métricas y otros gastos generales (en nanosegundos)
  • QueryThrottlerEvaluateLatencyNs: tiempo necesario para tomar la decisión de aceleración (en nanosegundos) Todas las métricas incluyen etiquetas para Strategy, Workload y Priority. La métrica QueryThrottlerThrottled tiene etiquetas adicionales para MetricName, MetricValue y DryRun para identificar qué métrica desencadenó la limitación y si ocurrió en modo de ejecución en seco. Estas métricas ayudan a monitorear los patrones de limitación, identificar qué cargas de trabajo están limitadas, medir la sobrecarga de rendimiento y validar el comportamiento en modo de ejecución en seco antes de cambios de configuración.

<a id="vttablet-querythrottler-config-watch"/>Actualizaciones de configuración basadas en eventos de QueryThrottler</a>

La configuración de QueryThrottler ahora se propaga y almacena en el registro SrvKeyspace dentro del servidor de topología y se administra mediante herramientas de topología estándar. Anteriormente, las tabletas encuestaban los cambios de configuración cada 60 segundos. Las tabletas ahora usan vigilancias basadas en eventos (WatchSrvKeyspace) para recibir actualizaciones inmediatamente cuando cambia la configuración de limitación de consultas. Todas las tabletas en un espacio de claves ven los cambios de configuración aproximadamente al mismo tiempo, y los cambios del servidor de topología están versionados y son auditables. Este cambio reemplaza el cargador de configuración basado en archivos anterior con una estructura de configuración definida por protobuf almacenada en la topología. La nueva configuración incluye campos para habilitar/deshabilitar la limitación, seleccionar la estrategia de limitación y configurar reglas específicas de la estrategia.

<a id="vttablet-conn-pool-waiter-cap"/>Gorra de camarero de piscina de conexión de tableta</a>

VTTablet ahora permite a los usuarios establecer un límite en la cantidad de solicitudes en espera de obtener una conexión del grupo de conexiones, por ejemplo. los grupos de conexiones de consultas, flujos y transacciones. Los límites se establecen con las siguientes banderas:

  • --queryserver-config-query-pool-waiter-cap
  • --queryserver-config-stream-pool-waiter-cap
  • --queryserver-config-txpool-waiter-cap Todo lo anterior tiene un valor predeterminado de 0, es decir, sin límite, preservando así el comportamiento de la versión anterior.

<a id="seguimiento-de-cambios-menores"/>Seguimiento</a>

<a id="tracing-opentelemetry"/>soporte de rastreo OpenTelemetry</a>

Vitess ahora admite OpenTelemetry como motor de seguimiento. Para usarlo, configure --tracer opentelemetry en cualquier binario Vitess. Las trazas se exportan a través de OTLP/gRPC, configurable con los siguientes indicadores:

  • --otel-endpoint: punto final del colector OpenTelemetry. Si está vacío, se utiliza la var env OTEL_EXPORTER_OTLP_ENDPOINT; si tampoco está configurado, el OTel SDK por defecto es localhost:4317.
  • --otel-insecure (por defecto false): utiliza una conexión insegura al colector.
  • --tracing-sampling-rate (0.1 predeterminado): frecuencia de muestreo para seguimientos (compartida entre todos los servidores de seguimiento). Cualquier backend compatible con OTLP (Jaeger v1.35+, Grafana Tempo, Datadog Agent, etc.) puede recibir estos seguimientos.

<a id="tracing-opentracing-deprecation"/>Desuso de los backends de seguimiento basados en OpenTracing</a>

Los siguientes backends de seguimiento están obsoletos a partir de la versión 24 y se eliminarán en la versión 25:

  • opentracing-jaeger: utiliza la biblioteca Jaeger client-go, que ha sido archivada. El proyecto Jaeger recomienda migrar a OpenTelemetry. Los usuarios deben migrar a --tracer opentelemetry con un terminal Jaeger compatible con OTLP (v1.35+).
  • opentracing-datadog: utiliza el puente OpenTracing en dd-trace-go. Los usuarios deben migrar a --tracer opentelemetry con el punto final de ingesta OTLP del agente Datadog. Las opciones --tracer opentracing-jaeger y --tracer opentracing-datadog continúan funcionando en v24 pero registrarán una advertencia de obsolescencia al inicio. Las siguientes marcas específicas de Jaeger también están obsoletas y se eliminarán en la versión 25:
  • --jaeger-agent-host
  • --tracing-sampling-type Migración: Reemplace --tracer opentracing-jaeger por --tracer opentelemetry y --jaeger-agent-host host:port por --otel-endpoint host:4317. Asegúrese de que su implementación de Jaeger acepte OTLP (Jaeger v1.35+ escucha en el puerto 4317 de forma predeterminada).

<a id="cambios-menores-vtorc"/>VTOrc</a>

<a id="vtorc-cell-flag"/>Nueva bandera --cell</a>

VTOrc ahora admite un indicador --cell que especifica en qué celda Vitess se ejecuta el proceso VTOrc. El indicador es opcional en v24 pero será obligatorio en v25+, similar al indicador --cell de VTGate. Cuando se proporciona, VTOrc valida que la celda existe en el servicio de topología al inicio. Sin la bandera, VTOrc registra una advertencia sobre el requisito de la bandera v25+. Esto permite una futura validación de problemas entre celdas, donde VTOrc podrá pedirle a otra celda que valide los problemas detectados antes de tomar acciones de recuperación. El indicador está actualmente validado pero aún no se utiliza en la lógica de recuperación de VTOrc. Nota: Si está ejecutando VTOrc en una implementación de varias celdas, comience a usar el indicador --cell ahora para prepararse para el requisito v25.

<a id="vtorc-ordered-recovery-semi-sync"/>Ejecución de recuperación ordenada e implementación de semisincronización</a>

VTOrc ahora ejecuta recuperaciones por fragmento con un orden definido, en lugar de por tableta de forma aislada. Los problemas que tienen dependencias de orden (por ejemplo, configuración semisincronizada) se ejecutan en serie primero, mientras que los problemas independientes se ejecutan simultáneamente. Esto garantiza que las recuperaciones dependientes se realicen en la secuencia correcta dentro de un fragmento. La principal mejora de cara al usuario es para las implementaciones de semisincronización: VTOrc ahora garantiza que las réplicas tengan habilitada la semisincronización antes de actualizar la principal. Anteriormente, habilitar la semisincronización en el principal antes de que estuvieran listas suficientes réplicas podía detener las escrituras mientras el principal esperaba confirmaciones de semisincronización que ninguna réplica estaba preparada para enviar. Consulte #19427 para obtener más detalles.

<a id="vtorc-deprecated-metric-removed"/>Métrica VTOrc obsoleta eliminada</a>

La métrica DiscoverInstanceTimings se eliminó de VTOrc en v24. Esta métrica quedó obsoleta en v23. Migración: utilice DiscoveryInstanceTimings en su lugar, que proporciona la misma información de tiempo, por ejemplo, acciones de descubrimiento (Backend, Instancia, Otros). Impacto: Los paneles de monitoreo o los sistemas de alerta que usan DiscoverInstanceTimings deben actualizarse para usar DiscoveryInstanceTimings.

<a id="vtorc-snapshot-topology-deprecation"/>Desuso de la función Topología de instantáneas</a>

La función Topología de instantáneas de VTOrc, que se habilita configurando --snapshot-topology-interval en un valor distinto de cero, está obsoleta a partir de v24 y se planea eliminar la lógica en v25. La falta de funciones para leer las instantáneas creadas por esta función, junto con la naturaleza en memoria del backend de VTOrc, significa que esta lógica tiene una utilidad limitada. Esta desaprobación se explica y se rastrea en detalle en https://github.com/vitessio/vitess/issues/18691.. Migración: elimine el indicador VTOrc --snapshot-topology-interval anterior a v25. Impacto: VTOrc ya no puede crear instantáneas de la topología en su base de datos backend.

<a id="vtorc-replication-analysis-api-removed"/>Punto final /api/replication-analysis obsoleto eliminado</a>

El punto final /api/replication-analysis se eliminó de VTOrc en v24. Utilice /api/detection-analysis en su lugar, que proporciona la misma funcionalidad. Migración: actualice cualquier script, sistema de monitoreo o automatización que llame a /api/replication-analysis para usar /api/detection-analysis en su lugar. El punto final de reemplazo acepta los mismos parámetros de consulta (keyspace, shard) y devuelve el mismo formato de respuesta JSON. Impacto: Las solicitudes HTTP a /api/replication-analysis devolverán un error 404 No encontrado.

<a id="minor-changes-metrics"/>Métricas</a>

<a id="metrics-extended-go-runtime"/>Métricas de tiempo de ejecución de Go extendidas a través de Prometheus</a>

Vitess ahora expone el conjunto completo de métricas de tiempo de ejecución de Go a través de Prometheus. El Prometheus GoCollector predeterminado solo expone tres runtime/metrics (/gc/gogc:percent, /gc/gomemlimit:bytes, /sched/gomaxprocs:threads) más el conjunto heredado go_memstats_*. A partir de la versión 24, todos los componentes de Vitess exponen aproximadamente 150 métricas adicionales del paquete runtime/metrics de Go. Las nuevas métricas incluyen:

  • Histogramas de asignación de montón
  • Recuentos de ciclos de GC e histogramas de pausa
  • Desgloses de clases de memoria.
  • Averías del estado de rutina
  • Histogramas de latencia del programador
  • Desgloses del tiempo de CPU por clase (usuario, GC, barrido, inactivo) También se agrega un nuevo medidor go_info_ext con etiquetas compiler, GOARCH y GOOS, que brindan información ampliada sobre el entorno de construcción más allá de la métrica estándar go_info. Componentes afectados: vtgate, vttablet, vtctld, vtorc, vtbackup, mysqlctld No se requiere configuración: las métricas aparecen automáticamente en el punto final /metrics para todos los componentes que utilizan el backend Prometheus.

<a id="minor-changes-backup-restore"/>Copia de seguridad y restauración</a>

<a id="mysql-clone-support"/>MySQL CLONE Compatibilidad con el aprovisionamiento de réplicas</a>

VTTablet y VTBackup ahora admiten el uso del [complemento CLONE] nativo de MySQL (https://dev.mysql.com/doc/refman/en/clone-plugin.html) para aprovisionar nuevas réplicas copiando datos directamente desde una tableta donante a través de la red. La copia de datos a nivel físico es significativamente más rápida que la copia de seguridad y la restauración lógicas, especialmente para conjuntos de datos grandes. Requiere tablas MySQL 8.0.17+ y solo InnoDB. Nuevas banderas: | Bandera | Descripción | |------|-------------| | --mysql-clone-enabled | Habilite el complemento MySQL CLONE y cree el usuario clonado durante la inicialización de MySQL. Requerido para todas las tabletas que participarán en operaciones CLONE. | | --clone-from-primary | Clona datos de la tableta principal del fragmento en lugar de restaurarlos desde la copia de seguridad. Mutuamente excluyente con --clone-from-tablet. | | --clone-from-tablet | Clonar datos de una tableta específica por alias (por ejemplo, zone1-123) en lugar de restaurarlos desde una copia de seguridad. Mutuamente excluyente con --clone-from-primary. | | --restore-with-clone | Utilice MySQL CLONE para la fase de restauración en lugar de restaurar desde la copia de seguridad. Requiere --clone-from-primary o --clone-from-tablet. | | --clone-restart-wait-timeout | Tiempo de espera de espera para que MySQL se reinicie después de que se complete CLONE REMOTE. Predeterminado: 5 minutos. | Configuración de clonación de usuario: | Bandera | Descripción | |------|-------------| | --db-clone-user | MySQL nombre de usuario para operaciones CLONE (autenticación de donante). | | --db-clone-password | Contraseña del usuario CLONE. | | --db-clone-use-ssl | Utilice SSL cuando se conecte con el donante para operaciones CLONE. | Ejemplo de uso: Clonar desde el fragmento primario:

vttablet \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-primary \
  ...

Clonar desde una tableta específica:

vtbackup \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-tablet=zone1-0000000100 \
  ...

Nota: Todas las tabletas que participan en operaciones CLONE (tanto donantes como destinatarios) deben tener --mysql-clone-enabled configurado durante la inicialización de MySQL para garantizar que el complemento CLONE esté cargado y que el usuario clonado exista.

<a id="restore-hook-backup-engine-env"/>Mejoras en el enlace de restauración</a>

Cobertura de gancho extendida: el gancho vttablet_restore_done ahora se activa cuando las restauraciones se activan a través de vtctldclient RestoreFromBackup. Anteriormente, este enlace solo se ejecutaba durante el inicio de la tableta o durante las operaciones de clonación. Nueva variable de entorno: el enlace ahora configura TM_RESTORE_DATA_BACKUP_ENGINE para indicar qué motor de respaldo se usó. El valor proviene del campo BackupMethod del manifiesto de respaldo. TM_RESTORE_DATA_BACKUP_ENGINE solo se configura cuando una restauración lee desde una copia de seguridad real, no para restauraciones basadas en clones o cuando no se utiliza ninguna copia de seguridad. Los scripts de enlace pueden usar esto para realizar acciones específicas del motor en función de si la restauración utilizó builtin, xtrabackup u otro motor.

<a id="major-changes"/>Major Changes</a>

<a id="new-support"/>New Support</a>

<a id="window-function-pushdown"/>Window function pushdown for sharded keyspaces</a>

This release introduces an optimization that allows window functions to be pushed down to individual shards when they are partitioned by a column that matches a unique vindex.

Previously, all window function queries required single-shard routing, which limited their applicability on sharded tables. With this change, queries where the PARTITION BY clause aligns with a unique vindex can now be pushed down and executed on each shard.

For examples and more details, see the documentation.

<a id="view-routing-rules"/>View Routing Rules</a>

Vitess now supports routing rules for views, and can be applied the same as tables with vtctldclient ApplyRoutingRules. When a view routing rule is active, VTGate rewrites queries that reference the source view to use the target view's definition instead. For example, given this routing rule:

{
  "rules": [
    {
      "from_table": "source_ks.my_view",
      "to_tables": ["target_ks.my_view"]
    }
  ]
}

And this view definition:

CREATE VIEW target_ks.my_view AS SELECT id, name FROM user;

A query like SELECT * FROM source_ks.my_view would be internally rewritten to:

SELECT * FROM (SELECT id, name FROM target_ks.user) AS my_view;

View routing rules require the schema tracker to monitor views, which means VTGate must be started with the --enable-views flag and VTTablet with the --queryserver-enable-views flag. The target view must exist in the specified keyspace for the routing rule to function correctly. For more details, see the Schema Routing Rules documentation.

<a id="tablet-targeting"/>Tablet targeting via USE statement</a>

VTGate now supports routing queries to a specific tablet by alias using an extended USE statement syntax:

USE keyspace:shard@tablet_type|tablet_alias;

For example, to target a specific replica tablet:

USE commerce:-80@replica|zone1-0000000100;

Once set, all subsequent queries in the session route to the specified tablet until cleared with a standard USE keyspace or USE keyspace@tablet_type statement. This is useful for debugging, per-tablet monitoring, cache warming, and other operational tasks where targeting a specific tablet is required.

Note: A shard must be specified when using tablet targeting. Like shard targeting, this bypasses vindex-based routing, so use with care.

<a id="vtgate-binlog-dump"/>Binlog Streaming Support</a>

VTGate now supports GTID-based binlog streaming through two protocols:

  • MySQL protocol: Clients can connect using the standard MySQL COM_BINLOG_DUMP_GTID replication protocol command—no special VStream-aware adapters or direct MySQL access required.
  • gRPC: The new BinlogDumpGTID streaming RPC in vtgateservice provides native gRPC access for custom clients without the MySQL protocol dependency.

Note: Only GTID-based streaming is supported. File/position-based streaming is not available through either COM_BINLOG_DUMP or COM_BINLOG_DUMP_GTID and returns an error.

This feature is disabled by default. Enable it with --enable-binlog-dump.

New flags:

  • --enable-binlog-dump: Enables binlog dump support. Without this flag, binlog dump requests return an error.
  • --binlog-dump-authorized-users: Comma-separated list of users authorized to execute binlog dump operations, or % to allow all users.

Requirements:

When initiating a binlog dump connection, clients must specify:

  • An empty filename
  • A file position (filepos) of 4
  • A GTID position

For gRPC clients, specify the keyspace, shard, and optionally the tablet type or tablet alias directly in the BinlogDumpGTIDRequest.

Limitations:

  • Each stream operates on a single tablet—no data aggregation across shards.
  • No automatic failover—if the targeted tablet becomes unavailable, the stream fails and the client must reconnect to a different tablet.
  • Not compatible with MoveTables or Reshard operations. Use the VStream API for those use cases.

<a id="structured-logging"/>Structured logging</a>

Vitess now uses structured JSON logging by default. Log output is emitted as JSON to stderr. To configure the minimum log level, pass --log-level (one of debug, info, warn, error; default info). For a human-readable format with automatic color detection, pass --log-format=text. To revert to the previous glog backend, pass --log-structured=false.

glog is deprecated as of v24 and will be removed in v25.

<a id="breaking-changes"/>Breaking Changes</a>

<a id="vttablet-external-decompressor-manifest"/>External Decompressor No Longer Read from Backup MANIFEST by Default</a>

The external decompressor command stored in a backup's MANIFEST file is no longer used at restore time by default. Previously, when no --external-decompressor flag was provided, VTTablet would fall back to the command specified in the MANIFEST. This posed a security risk: an attacker with write access to backup storage could modify the MANIFEST to execute arbitrary commands on the tablet.

Starting in v24, the MANIFEST-based decompressor is ignored unless you explicitly opt in with the new --external-decompressor-use-manifest flag. If you rely on this behavior, add the flag to your VTTablet configuration, but be aware of the security implications.

See #19460 for details.

<a id="minor-changes"/>Minor Changes</a>

<a id="minor-changes-vreplication"/>VReplication</a>

<a id="vreplication-shards-flag-start-stop"/>--shards flag for MoveTables/Reshard start and stop</a>

The start and stop commands for MoveTables and Reshard workflows now support the --shards flag, allowing users to start or stop workflows on a specific subset of shards rather than all shards at once.

Example usage:

# Start workflow on specific shards only
vtctldclient MoveTables --target-keyspace customer --workflow commerce2customer start --shards="-80,80-"

# Stop workflow on specific shards only
vtctldclient Reshard --target-keyspace customer --workflow cust2cust stop --shards="80-"

<a id="vreplication-tablet-error-retry"/>Automatic tablet retry for tablet-specific errors</a>

VReplication workflows now automatically retry with different tablets when encountering tablet-specific errors. Previously, workflows without a cell preference would default to the local cell and could get stuck retrying the same failing tablet indefinitely.

When a tablet encounters errors like binary log purging (MySQL error 1236 or 1789) or GTID set mismatches, VReplication adds that tablet to an ignore list and tries other tablets across all cells. Once all matching tablets have been tried, the ignore list is cleared and the workflow retries from scratch.

This is particularly useful in multi-cell deployments where a tablet in the local cell may lack the required binary logs, but tablets in other cells still have them.

<a id="minor-changes-vtgate"/>VTGate</a>

<a id="vtgate-removed-grpc-send-session-in-streaming"/>Removed --grpc-send-session-in-streaming flag</a>

The VTGate flag --grpc-send-session-in-streaming has been removed. This flag was deprecated in v22 via #17907 and defaulted to true.

The session is now always sent as the last packet in the streaming response for StreamExecute and StreamExecuteMulti RPCs. This behavior is required to support transactions in streaming and cannot be disabled.

Impact: Remove any usage of the --grpc-send-session-in-streaming flag from VTGate startup scripts or configuration.

<a id="vtgate-new-default-legacy-replication-lag-algorithm"/>New default for --legacy-replication-lag-algorithm flag</a>

The VTGate flag --legacy-replication-lag-algorithm now defaults to false, disabling the legacy approach to handling replication lag by default.

Instead, a simpler algorithm purely based on low lag, high lag and minimum number of tablets is used, which has proven to be more stable in many production environments. A detailed explanation of the two approaches is explained in this code comment.

In v25 this flag will become deprecated and in the following release it will be removed. In the meantime, the legacy behaviour can be used by setting --legacy-replication-lag-algorithm=true. This deprecation is tracked in https://github.com/vitessio/vitess/issues/18914.

<a id="vtgate-session-balancer-mode"/>New "session" mode for --vtgate-balancer-mode flag</a>

The VTGate flag --vtgate-balancer-mode now supports a new "session" mode in addition to the existing "cell", "prefer-cell", and "random" modes. Session mode routes each session consistently to the same tablet for the session's duration.

To enable session mode, set the flag when starting VTGate:

--vtgate-balancer-mode=session

<a id="minor-changes-query-serving"/>Query Serving</a>

<a id="query-serving-json-extract-dynamic-args"/>JSON_EXTRACT now supports dynamic path arguments</a>

The JSON_EXTRACT function now supports dynamic path arguments like bind variables or results from other function calls. Previously, JSON_EXTRACT only worked with static string literals for path arguments.

NULL handling now matches MySQL behavior. The function returns NULL when either the document or path argument is NULL.

Static path arguments are still optimized, even when mixed with dynamic arguments, so existing queries won't see any performance regression.

<a id="minor-changes-vttablet"/>VTTablet</a>

<a id="vttablet-init-tablet-type-lookup"/>New Experimental flag --init-tablet-type-lookup</a>

The new experimental flag --init-tablet-type-lookup for VTTablet allows tablets to automatically restore their previous tablet type on restart by looking up the existing topology record, rather than always using the static --init-tablet-type value.

When enabled, the tablet uses its alias to look up the tablet type from the existing topology record on restart. This allows tablets to maintain their changed roles (e.g., RDONLY/DRAINED) across restarts without manual reconfiguration. If disabled or if no topology record exists, the standard --init-tablet-type value will be used instead.

Note: Vitess Operator–managed deployments generally do not keep matching tablet records in the topo across pod replacements, so this feature will have a more limited effect in those environments.

<a id="vttablet-querythrottler-metrics"/>QueryThrottler Observability Metrics</a>

VTTablet now exposes new metrics to track QueryThrottler behavior.

Four new metrics have been added:

  • QueryThrottlerRequests: Total number of requests evaluated by the query throttler
  • QueryThrottlerThrottled: Number of requests that were throttled
  • QueryThrottlerTotalLatencyNs: Total time each request takes in query throttling, including evaluation, metric checks, and other overhead (in nanoseconds)
  • QueryThrottlerEvaluateLatencyNs: Time taken to make the throttling decision (in nanoseconds)

All metrics include labels for Strategy, Workload, and Priority. The QueryThrottlerThrottled metric has additional labels for MetricName, MetricValue, and DryRun to identify which metric triggered the throttling and whether it occurred in dry-run mode.

These metrics help monitor throttling patterns, identify which workloads are throttled, measure performance overhead, and validate behavior in dry-run mode before configuration changes.

<a id="vttablet-querythrottler-config-watch"/>QueryThrottler Event-Driven Configuration Updates</a>

QueryThrottler configuration is now propagated to and stored in the SrvKeyspace record within the topology server and managed using standard topology tools. Previously, tablets polled for configuration changes every 60 seconds. Tablets now use event-driven watches (WatchSrvKeyspace) to receive updates immediately when the query throttling configuration changes. All tablets in a keyspace see configuration changes at roughly the same time, and topology server changes are versioned and auditable.

This change replaces the previous file-based configuration loader with a protobuf-defined configuration structure stored in the topology. The new configuration includes fields for enabling/disabling throttling, selecting the throttling strategy, and configuring strategy-specific rules.

<a id="vttablet-conn-pool-waiter-cap"/>Tablet Connection Pool Waiter Cap</a>

VTTablet now allows users to set a limit on the number of requests waiting to get a connection from the connection pool, for the query, stream, and transaction connection pools. The limits are set with the following flags:

  • --queryserver-config-query-pool-waiter-cap
  • --queryserver-config-stream-pool-waiter-cap
  • --queryserver-config-txpool-waiter-cap

All of the above have a default value of 0, meaning no limit, thus preserving the behavior of the previous version.

<a id="minor-changes-tracing"/>Tracing</a>

<a id="tracing-opentelemetry"/>OpenTelemetry tracing support</a>

Vitess now supports OpenTelemetry as a tracing backend. To use it, set --tracer opentelemetry on any Vitess binary. Traces are exported via OTLP/gRPC, configurable with the following flags:

  • --otel-endpoint: OpenTelemetry collector endpoint. If empty, the OTEL_EXPORTER_OTLP_ENDPOINT env var is used; if that is also unset, the OTel SDK defaults to localhost:4317.
  • --otel-insecure (default false): use insecure connection to the collector.
  • --tracing-sampling-rate (default 0.1): sampling rate for traces (shared across all tracing backends).

Any OTLP-compatible backend (Jaeger v1.35+, Grafana Tempo, Datadog Agent, etc.) can receive these traces.

<a id="tracing-opentracing-deprecation"/>Deprecation of OpenTracing-based tracing backends</a>

The following tracing backends are deprecated as of v24 and will be removed in v25:

  • opentracing-jaeger — Uses the Jaeger client-go library, which has been archived. The Jaeger project recommends migrating to OpenTelemetry. Users should migrate to --tracer opentelemetry with an OTLP-compatible Jaeger endpoint (v1.35+).
  • opentracing-datadog — Uses the OpenTracing bridge in dd-trace-go. Users should migrate to --tracer opentelemetry with the Datadog Agent's OTLP ingestion endpoint.

The --tracer opentracing-jaeger and --tracer opentracing-datadog options continue to work in v24 but will log a deprecation warning at startup. The following Jaeger-specific flags are also deprecated and will be removed in v25:

  • --jaeger-agent-host
  • --tracing-sampling-type

Migration: Replace --tracer opentracing-jaeger with --tracer opentelemetry and --jaeger-agent-host host:port with --otel-endpoint host:4317. Ensure your Jaeger deployment accepts OTLP (Jaeger v1.35+ listens on port 4317 by default).

<a id="minor-changes-vtorc"/>VTOrc</a>

<a id="vtorc-cell-flag"/>New --cell Flag</a>

VTOrc now supports a --cell flag that specifies which Vitess cell the VTOrc process is running in. The flag is optional in v24 but will be required in v25+, similar to VTGate's --cell flag.

When provided, VTOrc validates that the cell exists in the topology service on startup. Without the flag, VTOrc logs a warning about the v25+ flag requirement.

This enables future cross-cell problem validation, where VTOrc will be able to ask another cell to validate detected problems before taking recovery actions. The flag is currently validated but not yet used in VTOrc recovery logic.

Note: If you're running VTOrc in a multi-cell deployment, start using the --cell flag now to prepare for the v25 requirement.

<a id="vtorc-ordered-recovery-semi-sync"/>Ordered Recovery Execution and Semi-Sync Rollout</a>

VTOrc now executes recoveries per-shard with a defined ordering, rather than per-tablet in isolation. Problems that have ordering dependencies (e.g., semi-sync configuration) are executed serially first, while independent problems are executed concurrently. This ensures that dependent recoveries happen in the correct sequence within a shard.

The main user-facing improvement is for semi-sync rollouts: VTOrc now ensures replicas have semi-sync enabled before updating the primary. Previously, enabling semi-sync on the primary before enough replicas were ready could stall writes while the primary waited for semi-sync acknowledgements that no replica was prepared to send.

See #19427 for details.

<a id="vtorc-deprecated-metric-removed"/>Deprecated VTOrc Metric Removed</a>

The DiscoverInstanceTimings metric has been removed from VTOrc in v24. This metric was deprecated in v23.

Migration: Use DiscoveryInstanceTimings instead, which provides the same timing information for instance discovery actions (Backend, Instance, Other).

Impact: Monitoring dashboards or alerting systems using DiscoverInstanceTimings must be updated to use DiscoveryInstanceTimings.

<a id="vtorc-snapshot-topology-deprecation"/>Deprecation of Snapshot Topology feature</a>

VTOrc's Snapshot Topology feature, which is enabled by setting --snapshot-topology-interval to a non-zero-value is deprecated as of v24 and the logic is planned for removal in v25.

The lack of facilities to read the snapshots created by this feature coupled with the in-memory nature of VTOrc's backend means this logic has limited usefulness. This deprecation is explained and tracked in detail in https://github.com/vitessio/vitess/issues/18691.

Migration: remove the VTOrc flag --snapshot-topology-interval before v25.

Impact: VTOrc can no longer create snapshots of the topology in it's backend database.

<a id="vtorc-replication-analysis-api-removed"/>Deprecated /api/replication-analysis Endpoint Removed</a>

The /api/replication-analysis endpoint has been removed from VTOrc in v24. Use /api/detection-analysis instead, which provides the same functionality.

Migration: Update any scripts, monitoring systems, or automation that calls /api/replication-analysis to use /api/detection-analysis instead. The replacement endpoint accepts the same query parameters (keyspace, shard) and returns the same JSON response format.

Impact: HTTP requests to /api/replication-analysis will return a 404 Not Found error.

<a id="minor-changes-metrics"/>Metrics</a>

<a id="metrics-extended-go-runtime"/>Extended Go Runtime Metrics via Prometheus</a>

Vitess now exposes the full set of Go runtime metrics via Prometheus. The default Prometheus GoCollector only exposes three runtime/metrics (/gc/gogc:percent, /gc/gomemlimit:bytes, /sched/gomaxprocs:threads) plus the legacy go_memstats_* set. Starting in v24, all Vitess components expose approximately 150 additional metrics from Go's runtime/metrics package.

New metrics include:

  • Heap allocation histograms
  • GC cycle counts and pause histograms
  • Memory class breakdowns
  • Goroutine state breakdowns
  • Scheduler latency histograms
  • CPU time breakdowns by class (user, GC, scavenge, idle)

A new go_info_ext gauge is also added with compiler, GOARCH, and GOOS labels, providing extended build environment information beyond the standard go_info metric.

Affected components: vtgate, vttablet, vtctld, vtorc, vtbackup, mysqlctld

No configuration required — the metrics appear automatically on the /metrics endpoint for all components using the Prometheus backend.

<a id="minor-changes-backup-restore"/>Backup and Restore</a>

<a id="mysql-clone-support"/>MySQL CLONE Support for Replica Provisioning</a>

VTTablet and VTBackup now support using MySQL's native CLONE plugin to provision new replicas by copying data directly from a donor tablet over the network. Physical-level data copying is significantly faster than logical backup and restore, especially for large datasets. Requires MySQL 8.0.17+ and InnoDB-only tables.

New Flags:

| Flag | Description | |------|-------------| | --mysql-clone-enabled | Enable the MySQL CLONE plugin and create the clone user during MySQL initialization. Required for all tablets that will participate in CLONE operations. | | --clone-from-primary | Clone data from the shard's primary tablet instead of restoring from backup. Mutually exclusive with --clone-from-tablet. | | --clone-from-tablet | Clone data from a specific tablet by alias (e.g., zone1-123) instead of restoring from backup. Mutually exclusive with --clone-from-primary. | | --restore-with-clone | Use MySQL CLONE for the restore phase instead of restoring from backup. Requires either --clone-from-primary or --clone-from-tablet. | | --clone-restart-wait-timeout | Timeout for waiting for MySQL to restart after CLONE REMOTE completes. Default: 5 minutes. |

Clone User Configuration:

| Flag | Description | |------|-------------| | --db-clone-user | MySQL username for CLONE operations (donor authentication). | | --db-clone-password | Password for the CLONE user. | | --db-clone-use-ssl | Use SSL when connecting to the donor for CLONE operations. |

Example Usage:

Clone from the shard's primary:

vttablet \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-primary \
  ...

Clone from a specific tablet:

vtbackup \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-tablet=zone1-0000000100 \
  ...

Note: All tablets participating in CLONE operations (both donors and recipients) must have --mysql-clone-enabled set during MySQL initialization to ensure the CLONE plugin is loaded and the clone user exists.

<a id="restore-hook-backup-engine-env"/>Restore Hook Improvements</a>

Extended Hook Coverage: The vttablet_restore_done hook now fires when restores are triggered via vtctldclient RestoreFromBackup. Previously, this hook only ran during tablet startup or clone operations.

New Environment Variable: The hook now sets TM_RESTORE_DATA_BACKUP_ENGINE to indicate which backup engine was used. The value comes from the backup manifest's BackupMethod field.

TM_RESTORE_DATA_BACKUP_ENGINE is only set when a restore reads from an actual backup—not for clone-based restores or when no backup is used. Hook scripts can use this to perform engine-specific actions based on whether the restore used builtin, xtrabackup, or another engine.
