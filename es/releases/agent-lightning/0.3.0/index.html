agente-rayo v0.3.0

Agent-lightning v0.3.0 es una versión importante que presenta varias características nuevas y correcciones de errores. El lanzamiento es un esfuerzo de colaboración entre los equipos centrales de Agent-lightning y la comunidad. Gracias a todos los contribuyentes que hicieron posible este lanzamiento.

Destacados

  • Integración de Tinker: admite Tinker como backend alternativo para el aprendizaje por refuerzo (#226 #245 #264 #269 #327). Consulte código de ejemplo, blog 1 y blog 2.
  • Integración de Azure OpenAI: admite Azure OpenAI como backend para la inferencia de LLM y el ajuste supervisado (#256 #327). Código de ejemplo.
  • Se agrega Lightning Store basada en MongoDB como backend alternativo para Lightning Store (#323). Documentación.
  • Paquete de contribución: agregue un paquete de contribución para proyectos comunitarios. Search-R1 está integrado como una receta de contribución. Más por venir. (#239 #396 #410 #412 #417).
  • RESTful API: Estabiliza y documenta RESTful API para Lightning Store (#241 #275). Documentación.
  • Convenciones semánticas de OTel que están diseñadas específicamente para áreas de optimización de agentes (#340). Documentación.
  • [Vista previa] Panel de control de Agent-Lightning ya está disponible (#288 #289 #291 #296 #371 #375). Es la aplicación web oficial para inspeccionar y depurar experimentos de Agent-lightning. Ver detalles aquí.
  • [Vista previa] Ejemplo de multimodalidad con VERL y un agente LangGraph en el conjunto de datos ChartQA (#379). Código de ejemplo.
  • [Vista previa] Integre Claude Code como LitAgent y respalde la capacitación en SWE-Bench (#332 #346 #348). Código de ejemplo.
  • [Vista previa] Weave tracer como sustituto del rastreador AgentOps (#277 #411 #420 #423). Documentación.
  • [Vista previa] Agregación de niveles de trayectoria para una capacitación más eficiente con VERL. Consulte blog y documentación.

Punto de referencia de la tienda

En esta versión, el núcleo de Lightning Store se rediseñó para lograr una eficiencia y escalabilidad significativamente mayores (#315 #318 #328 #342 #344 #356 #380 #388 #418 #421). Los resultados de las pruebas comparativas a continuación demuestran el impacto: con una gran cantidad de corredores simultáneos, v0.3.0 ofrece un aumento de rendimiento de hasta 15 veces en comparación con v0.2.2.

| Rendimiento (#despliegue/seg) | v0.2.2 | v0.3.0 (en memoria) | v0.3.0 (Mongo) | | :---- | :---- | :---- | :---- | | Mínimo (lote, #corredor=32, #turnos=6) | 8.73 | 9.06 | 8.71 | | Medio (lote, #corredores=100, #turnos=10) | 12.03 | 23.26 | 32.79 | | Medio-alto (lote, #corredores=300, #turnos=6) | 10.61 | 24.42 | 40.24 | | Grande (lote, #corredores=1000, #turnos=3) | 3.36 | 14.60 | 50.05 | | Cola larga (cola, #corredores=256, #turnos=4) | 7.42 | 30.86 | 57.01 | | Trazo pesado (cola, #corredores=512, #turnos=20) | 5.93 | 13.28 | 29.41 |

Notas:

  1. Las pruebas comparativas se ejecutaron en una única máquina virtual de Azure Standard_D32as_v4 (se utilizaron pruebas de seguimiento grandes y pesadas Standard_D64ads_v5), ejecutadas a través de acciones GitHub.
  2. Se evalúan dos patrones de algoritmo: el patrón por lotes envía un grupo de implementaciones y espera a que todos terminen antes de comenzar el siguiente grupo, mientras que el patrón de cola mantiene un número determinado de implementaciones en curso y envía nuevas tan pronto como se libera capacidad. Los detalles de configuración están disponibles aquí.
  3. El número de vueltas es directamente proporcional al número de tramos que genera cada despliegue.

agent-lightning v0.3.0

Agent-lightning v0.3.0 is a major release that introduces several new features and bug fixes. The release is a collaborative effort between Agent-lightning core teams and the community. Thanks to all the contributors who made this release possible.

Highlights

  • Tinker integration: Support Tinker as an alternative backend for Reinforcement Learning (#226 #245 #264 #269 #327). See example code, blog 1 and blog 2.
  • Azure OpenAI integration: Support Azure OpenAI as a backend for LLM inference and supervised fine-tuning (#256 #327). Example code.
  • MongoDB-based Lightning Store is added as an alternative backend for Lightning Store (#323). Documentation.
  • Contrib package: Add contrib package for community projects. Search-R1 is integrated as a contrib recipe. More coming. (#239 #396 #410 #412 #417).
  • RESTful API: Stabilize and document RESTful API for Lightning Store (#241 #275). Documentation.
  • OTel Semantic Conventions that are specifically designed for Agent-optimization areas (#340). Documentation.
  • [Preview] Agent-lightning Dashboard is now available (#288 #289 #291 #296 #371 #375). It's the official web application for inspecting and debugging Agent-lightning experiments. See details here.
  • [Preview] Multi-modality example featuring VERL and a LangGraph agent on ChartQA dataset (#379). Example code.
  • [Preview] Integrate Claude Code as a LitAgent and support training on SWE-Bench (#332 #346 #348). Example code.
  • [Preview] Weave tracer as a substitute for AgentOps tracer (#277 #411 #420 #423). Documentation.
  • [Preview] Trajectory Level Aggregation for more efficient training with VERL. See blog and documentation.

Store Benchmark

In this release, the Lightning Store core was redesigned for significantly greater efficiency and scalability (#315 #318 #328 #342 #344 #356 #380 #388 #418 #421). The benchmark results below demonstrate the impact: with large numbers of concurrent runners, v0.3.0 delivers up to a 15x increase in throughput compared to v0.2.2.

| Throughput (#rollout/sec) | v0.2.2 | v0.3.0 (in-memory) | v0.3.0 (Mongo) | | :---- | :---- | :---- | :---- | | Minimal (batch, #runner=32, #turns=6) | 8.73 | 9.06 | 8.71 | | Medium (batch, #runners=100, #turns=10) | 12.03 | 23.26 | 32.79 | | Mid-high (batch, #runners=300, #turns=6) | 10.61 | 24.42 | 40.24 | | Large (batch, #runners=1000, #turns=3) | 3.36 | 14.60 | 50.05 | | Long queue (queue, #runners=256, #turns=4) | 7.42 | 30.86 | 57.01 | | Heavy trace (queue, #runners=512, #turns=20) | 5.93 | 13.28 | 29.41 |

Notes:

  1. Benchmarks were run on a single Standard_D32as_v4 Azure VM (Large and heavy trace tests used Standard_D64ads_v5), executed via GitHub Actions.
  2. Two algorithm patterns are evaluated: the batch pattern submits a group of rollouts and waits for all to finish before starting the next group, while the queue pattern maintains a set number of in-flight rollouts, submitting new ones as soon as capacity frees up. Configuration details are available here.
  3. The number of turns is directly proportional to the number of spans each rollout generates.
