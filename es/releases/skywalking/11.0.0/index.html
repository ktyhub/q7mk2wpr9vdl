Proyecto

  • Mueva la maquinaria de carga de clases DSL bajo core/dsl. core/classloader solo contenía tipos DSL (RuleClassLoader, DSLClassLoaderManager, ClassLoaderGc, UnloadProbePayload y BytecodeClassDefiner), por lo que ahora es core/dsl/classloader, y Catalog pasa a core/dsl porque una taxonomía de archivos de reglas no es un problema de carga de clases. Tres copias del envío "definir una clase generada en el cargador correcto" (MAL, LAL, MeterSystem) colapsan en un BytecodeClassDefiner.define estático, lo que también le da al JDK 17 --add-opens un hogar en lugar de cuatro. Tres de las cuatro copias de la búsqueda del directorio de volcado de clase generada se convierten en DslGeneratedFileWriter.resolveClassDumpDir; OAL mantiene el suyo, porque su indicador de depuración se puede configurar independientemente de la variable de entorno y dos pruebas se basan en eso. Ningún cambio de comportamiento.
  • Amplíe el administrador GET /inspect/entities API para inspeccionar una métrica persistente por cualquier OAP, incluso uno que este nodo no define localmente. Cuando el registro local desconoce la métrica, la persona que llama proporciona valueColumn + valueType y el backend de almacenamiento resuelve el índice/tabla/grupo físico desde su propia configuración en ejecución (sin lectura de esquema de base de datos/metadatos de tabla): ES usa el índice metrics-all combinado + discriminador metric_table, JDBC prueba las tablas de funciones del nodo mediante el discriminador table_name y BanyanDB sintetiza un archivo de solo lectura esquema de medida. Ya no se requiere alcance: el entity_id se decodifica estructuralmente (servicio/segundo nivel/relaciones) con una hoja genérica name. Las métricas definidas localmente mantienen los nombres de campo exactos, el alcance y mqeEntity como antes.
  • Agregue el administrador POST /inspect/values API: lea la serie de valores de una métrica persistente por otro OAP (uno que este nodo no define localmente) proporcionando su {valueColumn, valueType}. El motor MQE real se ejecuta sobre una superposición InspectQueryContext con ámbito de solicitud (proporcionar si está ausente: el catálogo local siempre gana) que hace que la métrica externa parezca registrada en cada ruta de lectura: ValueColumnMetadata resuelve su columna/tipo/alcance de valor, y los registros de ubicación de almacenamiento resuelven dónde reside (MetadataRegistry sintetiza un esquema de medida BanyanDB, IndexController resuelve el índice ES metrics-all, TableHelper prueba las tablas de funciones JDBC), por lo que la lectura devuelve el MQE ExpressionResult nativo sin mayúsculas especiales por DAO. Solo administrador (una lectura forzada que este OAP no puede validar); no reflejado en la superficie pública REST/GraphQL. Consulte Inspeccionar API.
  • Elimina la conversión de alarma a evento siempre activa (EventHookCallback). Una alarma activada ya no se sintetiza en la canalización de eventos como un evento Alarm/AlarmRecovery; los eventos ahora se originan únicamente a partir de fuentes de eventos reales (agentes, SkyWalking CLI, Kubernetes Event Exporter). Las alarmas permanecen disponibles a través del almacén de alarmas (getAlarm/queryAlarms) y los ganchos de alarma configurados. Esto descarta un "Evento conocido" documentado y elimina 1 o 2 registros de eventos sintéticos por cada disparo de alarma.
  • TLS para todos los servidores HTTP/REST OAP, con recarga en caliente de certificados. Agrega la estructura de configuración restSSLEnabled / restSSLKeyPath / restSSLCertChainPath a cada servidor HTTP OAP (REST principal, servidor compartido, administrador, PromQL, LogQL, TraceQL y consulta/receptor Zipkin), cada uno con sus propias variables de entorno dedicadas (SW_CORE_REST_SSL_*, SW_RECEIVER_SHARING_REST_SSL_*, SW_ADMIN_SERVER_REST_SSL_*, SW_PROMQL_REST_SSL_*, SW_LOGQL_REST_SSL_*, SW_TRACEQL_REST_SSL_*, SW_QUERY_ZIPKIN_REST_SSL_*, SW_RECEIVER_ZIPKIN_REST_SSL_*). El Armeria HTTPServer compartido recarga el par de claves desde el disco durante la rotación (a través de TlsProvider.ofScheduled), de modo que los certificados actualizados se recogen sin reiniciar el OAP, coincidiendo con el comportamiento de recarga en caliente SSL existente del gRPC. HTTP TLS es solo del lado del servidor (no mTLS).
  • Nueva consulta GraphQL queryAlarms: filtros de entidad/capa/regla para alarmas. Agrega una consulta de alarma completa API junto con el getAlarm heredado. El nuevo queryAlarms(condition: AlarmQueryCondition!): Alarms acepta un único tipo de entrada que agrupa todos los filtros que almacena el registro de alarma: entities: [Entity!] (reutiliza la forma MQE Entity: fija a servicios/instancias/puntos finales/procesos específicos o sus relaciones, comparado con la alarma id0 O id1); layer: String (filtro por capa de la entidad alarmada: coincidencia única, ya que las filas de alarma persisten en una capa); ruleNames: [String!] (filtro por el cual se disparó la regla de alarma); más keyword, tags, duration, paging. El getAlarm heredado está marcado como @deprecated pero aún se dirige al mismo DAO, sin roturas de client. Adiciones de backend: una nueva columna layer en AlarmRecord completada en el momento de la alarma a través de MetadataQueryService.getService(serviceId).getLayers(); las columnas id0/id1 existentes cambiaron de storageOnly = true a indexadas para que el filtro de entidad baje al almacenamiento. IAlarmQueryDAO.queryAlarms(condition, limit, from) es un nuevo método abstracto: los backends de almacenamiento de terceros fallan en la compilación si omiten la anulación (patrón SWIP-14). Los tres backends incluidos lo implementan: BanyanDB / Elasticsearch / JDBC. Semántica del operador: (1) Las entidades de relación son de coincidencia exacta. Pasar {scope: ServiceRelation, serviceName: A, destServiceName: B} coincide solo con la alarma donde id0=serviceId(A) AND id1=serviceId(B), no con ninguna alarma que toque A o B en cualquier lado. Las consultas más amplias de "cualquier cosa que involucre A" deben pasar la entidad individual sin relación ({scope: Service, serviceName: A}, que se expande a id0=A OR id1=A). (2) Capa única por fila de alarma. La columna persistente almacena UNA capa (la primera entrada de la lista de capas resueltas de la entidad: el origen primero para las relaciones). Un servicio en [GENERAL, K8S_SERVICE] cuyos metadatos se resuelven primero en GENERAL se archiva en GENERAL; al consultar layer: "K8S_SERVICE" se lo perderá. Nota de migración del operador: las filas de alarmas previas a la actualización existentes siguen siendo filtrables por los campos heredados getAlarm; Los nuevos filtros de entidad/capa/regla en queryAlarms se aplican solo a las alarmas escritas después de la actualización (los índices de almacenamiento existentes no realizan la transición index: false → true; los nuevos índices diarios recogen las columnas indexadas). Las adiciones de esquema no son bloqueantes: el arranque omite silenciosamente los cambios de atributos de columna en los índices existentes.
  • 🚨 Cambio importante: apm-webapp y el submódulo skywalking-booster-ui se eliminan. Esta distribución OAP ya no incluye una interfaz de usuario web incluida. El proxy inverso Armeria heredado en apm-webapp/ (el binario que impulsó la imagen skywalking/ui Docker) y el submódulo git skywalking-ui (que rastreaba apache/skywalking-booster-ui) se eliminan junto con el objetivo Maven docker.ui, la compilación de la imagen skywalking/ui Docker, el paquete de la aplicación web apm-dist/ y cada ruta de flujo de trabajo de CI que creó o impulsó la imagen de la interfaz de usuario. La interfaz de usuario oficial ahora es Horizon UI, un subproyecto de SkyWalking que se lanza independientemente del backend de OAP según su propio cronograma, con imágenes de contenedor publicadas en Docker Hub en apache/skywalking-ui (etiquetas latest / horizon-<version>; imágenes de desarrollo por confirmación en vivo en ghcr.io/apache/skywalking-horizon-ui). No existe una asignación 1:1 entre las versiones de OAP y las versiones de Horizon UI: los operadores fijan la etiqueta de imagen de UI en su implementación y actualizan las dos en cadencias separadas. La interfaz de usuario de Horizon consume la superficie GraphQL/REST pública del OAP (12800 predeterminado) y el host de administración (17128 predeterminado). Los archivos semilla del panel de control en disco en oap-server/server-starter/src/main/resources/ui-initialized-templates/ se eliminan; UITemplateInitializer / UIMenuInitializer se eliminan de CoreModuleProvider.notifyAfterCompleted() y Horizon UI incluye su propia biblioteca de panel y su propio menú de barra lateral. Las plantillas de interfaz de usuario ahora se crean y actualizan a través de la nueva superficie REST /ui-management/templates/* en el servidor de administración (ver más abajo). Todas las mutaciones y consultas de GraphQL relacionadas con la interfaz de usuario (UIConfigurationManagement: addTemplate, changeTemplate, disableTemplate, getAllTemplates, getDashboardConfiguration, getMenuItems) se retiran del esquema público de GraphQL, junto con el indicador SW_ENABLE_UPDATE_UI_TEMPLATE. El backend de OAP tampoco almacena ni ofrece el menú de la barra lateral: UIMenuManagementService, UIMenuManagementDAO, UIMenu, MenuItem y se eliminaron todas las implicaciones de almacenamiento; Horizon UI posee el menú client-side y usa listServices(layer:...) para la activación dinámica de "la capa tiene servicios". Ruta de actualización: reemplace skywalking/ui:<tag> con la imagen de la interfaz de usuario de Horizon apache/skywalking-ui:latest (o una etiqueta horizon-<version>; elija una versión según las notas de compatibilidad de OAP de la interfaz de usuario de Horizon, se admite OAP 11.0+) en su implementación, exponga el puerto 17128 del contenedor OAP y migre cualquier script que llame a las mutaciones de la interfaz de usuario GraphQL heredada a los puntos finales REST en Administración de UI API. Todos los puntos finales de estado/depuración (/status/*, /debugging/*) también pasan a ser solo de administrador: el enlace dual REST público para el estado se retira en la misma versión.

Reenvía al UITemplateManagementService existente (sin cambios de DAO de almacenamiento). Habilitado de forma predeterminada (SW_UI_MANAGEMENT=default, en un host de administración predeterminado). Reemplaza el solucionador de plantillas GraphQL UIConfigurationManagement retirado. El menú de la barra lateral NO se muestra intencionalmente; consulte la entrada de cambios importantes más arriba. Referencia del operador: Administración de UI API.
  • Todos los módulos de funciones de administración están activados de forma predeterminada. admin-server, status, inspect, ui-management, dsl-debugging y receiver-runtime-rule están habilitados de forma predeterminada. Los operadores que no desean una característica particular configuran su var env SW_* en vacío. Esto cierra una brecha de usabilidad del 10.4.0 donde las superficies de reglas de tiempo de ejecución/depuración dsl requerían una suscripción explícita a pesar de que el host de administración ya estaba activado.
  • El estado API se movió al host de administración. Las rutas de estado/depuración (/status/*, /debugging/*) ahora se registran en el host REST del servidor de administración (17128 predeterminado); ya no se reflejan en core.restPort (12800 predeterminado). Alinea el estado con todos los demás módulos de funciones de administración (inspección, depuración de dsl, regla de tiempo de ejecución, administración de interfaz de usuario). La interfaz de usuario de Horizon consume el estado del host de administración. Los URI y las cargas útiles no cambian; sólo el anfitrión se movió. Una excepción: /status/config/ttl también está vinculado al host REST público (12800), por lo que las herramientas del ecosistema que descubren límites TTL a través de REST antes de emitir /graphql no necesitan aprender el puerto de administración.
  • Nuevo módulo admin-server: host compartido para administración/escritura bajo demanda API. Se ejecuta en dos puertos: una superficie HTTP REST (17128 predeterminado) para terminales orientados al operador y un bus gRPC interno de administrador (17129 predeterminado) para RPC de clúster peer-to-peer (suspensión/reanudar/regla de tiempo de ejecución). Adelante; instalación de depuración DSL / recopilación / parada / stopByClientId). El bus interno de administración es un transporte dedicado separado del puerto gRPC del clúster/agente público (core.gRPCPort, predeterminado 11800), por lo que los RPC de administrador privilegiados permanecen fuera del radio de explosión de la red del agente; los operadores vinculan gRPCHost a una interfaz privada de igual a igual únicamente. Tanto el complemento de reglas de tiempo de ejecución como el nuevo DSL Debug API (a continuación) se montan en este host compartido. Habilitado de forma predeterminada para que se pueda acceder al módulo de función de estado desde el primer momento; el host se vincula a 0.0.0.0:17128 y no tiene autenticación incorporada y debe estar protegido mediante puerta de enlace con listas de IP permitidas, nunca expuesto a la Internet pública (consulte el aviso de seguridad del administrador API). Configure SW_ADMIN_SERVER= (vacío) para deshabilitarlo por completo. El bloque de configuración de reglas de tiempo de ejecución pierde sus claves restHost/restPort/restContextPath/restIdleTimeOut/ restAcceptQueueSize/httpMaxRequestHeaderSize (y las variables de entorno SW_RECEIVER_RUNTIME_RULE_REST_* correspondientes); Las perillas a nivel de host se mueven debajo del nuevo bloque admin-server (SW_ADMIN_SERVER_HOST / SW_ADMIN_SERVER_PORT / SW_ADMIN_SERVER_GRPC_HOST / SW_ADMIN_SERVER_GRPC_PORT / SW_ADMIN_SERVER_INTERNAL_COMM_TIMEOUT, etc.).
  • Actualización activa de reglas de tiempo de ejecución para MAL y LAL. Los operadores ahora pueden enviar cambios de reglas de métricas (MAL) y registros (LAL) sin reiniciar OAP. Una inserción a un nuevo punto final de administración mantiene la regla en el backend de almacenamiento configurado y cada nodo del clúster converge al nuevo contenido en aproximadamente 30 segundos. Flujos de trabajo comunes:
    • addOrUpdate: crea o reemplaza una regla. El cuerpo es el YAML sin formato que normalmente enviaría con los archivos de reglas estáticas de OAP. Devuelve 200 una vez que la regla se aplica localmente y persiste; los compañeros lo detectan en su siguiente escaneo periódico (≤ 30 s).
    • inactivate: pausa suave de una regla. El OAP deja de emitir métricas para esa regla, pero la medida de backend (y su historial) se conserva, por lo que un addOrUpdate posterior al mismo (catalog, name) no tiene pérdidas. La intención "apagada" es duradera durante los reinicios; Las reglas empaquetadas en el disco no resucitan automáticamente cuando un inactivate elimina la anulación del tiempo de ejecución. Esta es la forma segura de desconectar una regla.
  • delete: elimina una fila INACTIVE (las reglas activas devuelven 409 requires_inactivate_first). Para reglas de solo tiempo de ejecución sin YAML incluido en el disco, la fila se elimina; la medida de backend (si la hay) se deja en su lugar como un artefacto inerte, coincidiendo con la semántica de eliminación de reglas incluidas (eliminar un YAML de otel-rules/ en el disco tampoco elimina su medida). Para las reglas que tienen un gemelo YAML incluido, delete simple devuelve 409 requires_revert_to_bundled; permitir que el paquete se haga cargo silenciosamente del (catalog, name) es un cambio de estado significativo que requiere una decisión explícita del operador. Vuelva a emitir con ?mode=revertToBundled para volver al paquete: esa ruta ejecuta la canalización de cambio de esquema (rehidrata el DSL de tiempo de ejecución localmente, luego aplica el YAML empaquetado a través de la canalización de aplicación estándar para que el delta de tiempo de ejecución → paquete elimine métricas de solo tiempo de ejecución, registre métricas solo de paquete y reutilice métricas compartidas de paquete en forma coincidente) antes de eliminar la fila. Devuelve 400 no_bundled_twin cuando se utiliza ?mode=revertToBundled sin un YAML incluido en el disco.
    • get / bundled / list / dump: puntos finales del lado de lectura para recuperar el YAML de una sola regla (con soporte para ETag; ?source=bundled lee el YAML incluido en el disco incluso cuando hay una anulación del tiempo de ejecución), enumerando la superposición del paquete versus el tiempo de ejecución por catálogo. inspeccionar el estado de las reglas de todo el clúster como un sobre JSON ({generatedAt, loaderStats, rules}: cada fila lleva status/localState/loaderKind/bundled/bundledContentHash para que una interfaz de usuario pueda generar insignias de anulación sin un segundo viaje de ida y vuelta) y exportar todas las reglas como tar.gz para respaldo/DR. Las actualizaciones en caliente sobreviven al reinicio de OAP: en el arranque, OAP fusiona archivos de reglas empaquetados con reglas de tiempo de ejecución persistentes, por lo que el clúster nunca regresa silenciosamente a los valores predeterminados empaquetados. Todas las escrituras de administrador para un clúster de reglas de tiempo de ejecución se serializan en un único OAP "principal" (primer par determinista ordenado, sin elección de líder): los nodos no principales que reciben una escritura HTTP la reenvían de forma transparente al principal a través del bus gRPC interno del administrador, por lo que un balanceador de carga L7 frente al puerto de administración puede enrutar cualquier solicitud del operador a cualquier OAP. La convergencia del clúster en el tick de actualización periódica se puede configurar a través de receiver-runtime-rule.refreshRulesPeriod (30 predeterminado). El punto final está deshabilitado de forma predeterminada y escucha en el puerto 17128 (HTTP) cuando está habilitado. No tiene autenticación incorporada: los operadores deben protegerlo mediante puertas de enlace con listas de direcciones IP permitidas y nunca exponerlo a la Internet pública. Las rutas se montan en el nuevo host HTTP admin-server, que está activado de forma predeterminada; habilite la función de regla de tiempo de ejecución con SW_RECEIVER_RUNTIME_RULE=default.
  • Depurador en vivo para MAL / LAL / OAL: implementa SWIP-13 Depurador en vivo para MAL / LAL / OAL. Depurador en tiempo de ejecución basado en muestras que captura entradas/salidas por etapa a medida que los tres DSL procesan la ingesta en vivo. El costo de la ruta inactiva es una lectura de bool volátil por sitio de llamada de sonda que JIT elimina después del calentamiento; Las sesiones activas se distribuyen a cada par del clúster a través del bus interno de administración gRPC para que cada par capture su propia porción. El despliegue es seguro para LB: cualquier nodo puede servir cualquier verbo (POST crea sessionId en el nodo receptor, transmite la instalación a los pares, devuelve 404 rule_not_found solo cuando ningún nodo posee la regla), por lo que un balanceador de carga L7 frente al puerto de administración enruta las solicitudes del operador libremente. Se monta en el host admin-server compartido (/dsl-debugging/* para el plano de control de sesión, /runtime/oal/* para el selector de reglas OAL). Deshabilitado por defecto; habilítelo con SW_DSL_DEBUGGING=default (el servidor de administración está activado de forma predeterminada). injectionEnabled es un conmutador codegen de arranque cuyo valor predeterminado es true: una vez que el módulo está habilitado, las sondas se activan y las sesiones registran muestras; configure false solo si se desea la superficie REST pero no se acepta ninguna sobrecarga de sonda del lado codegen. Los límites por sesión imponen límites estrictos (recordCap ≤ 10000, retentionMillis ≤ 1 hora): las solicitudes fuera de rango devuelven 400 invalid_limits. Las sesiones LAL aceptan un indicador granularity=block|statement por sesión: el modo de bloque captura las etapas del analizador/extractor/sumidero; El modo de declaración registra adicionalmente una entrada line por declaración de extractor individual, con el número de línea de origen y el texto DSL palabra por palabra para que la interfaz de usuario pueda resaltar qué declaración se activó. Las capturas MAL representan el mapa SampleFamily superviviente del filtro a nivel de archivo ({"families": N, "items": [...]}), por lo que las expresiones multimétricas muestran la reducción del filtro entre familias en la carga útil capturada. Las cargas útiles de captura incluyen cuerpos de registro sin procesar y mapas analizados: trate el puerto de administración como infraestructura autenticada según el [aviso de seguridad del administrador API] (../setup/backend/admin-api/readme.md). Referencias de operadores por DSL: MAL, OAL, LAL.
  • Las discrepancias en el esquema de BanyanDB ahora son visibles en el arranque, no silenciosas. Si BanyanDB ya contiene un recurso cuya forma no coincide con lo que declara la regla actual (por ejemplo, se editó una regla en el disco mientras OAP estaba fuera de línea), OAP ahora omite ese recurso, registra un ERROR con la diferencia entre declarado y backend y continúa con el arranque; anteriormente, la discrepancia se aceptaba silenciosamente y las muestras para el recurso afectado se descartaban silenciosamente. Para remodelar una métrica que no coincide, presione el YAML deseado hasta el POST /runtime/rule/addOrUpdate.

Project

  • Move the DSL class-loading machinery under core/dsl. core/classloader held only DSL types — RuleClassLoader, DSLClassLoaderManager, ClassLoaderGc, UnloadProbePayload and BytecodeClassDefiner — so it is now core/dsl/classloader, and Catalog moves to core/dsl because a rule-file taxonomy is not a class-loading concern. Three of the four copies of the generated-class dump-directory lookup become DslGeneratedFileWriter.resolveClassDumpDir; OAL keeps its own, because its debug flag is settable independently of the environment variable and two tests rely on that. No behaviour change.
  • Extend the GET /inspect/entities admin API to inspect a metric persisted by any OAP, even one this node does not define locally. When the metric is unknown to the local registry, the caller supplies valueColumn + valueType and the storage backend resolves the physical index/table/group from its own running config (no DB schema/table-metadata read): ES uses the merged metrics-all index + metric_table discriminator, JDBC probes the node's function tables by the table_name discriminator, and BanyanDB synthesizes a read-only measure schema. Scope is no longer required — the entity_id is decoded structurally (service / 2nd-level / relations) with a generic name leaf. Locally-defined metrics keep the exact field names, scope, and mqeEntity as before.
  • Add the POST /inspect/values admin API — read the value series of a metric persisted by another OAP (one this node does not define locally) by supplying its {valueColumn, valueType}. The real MQE engine runs over a request-scoped InspectQueryContext overlay (provide-if-absent — the local catalog always wins) that makes the foreign metric look registered to every read path: ValueColumnMetadata resolves its value column / type / scope, and the storage location registries resolve where it lives (MetadataRegistry synthesizes a BanyanDB measure schema, IndexController resolves the ES metrics-all index, TableHelper probes the JDBC function tables), so the read returns the native MQE ExpressionResult with no per-DAO special-casing. Admin-only (a forced read this OAP cannot validate); not mirrored onto the public REST / GraphQL surface. See the Inspect API.
  • Remove the always-on alarm-to-event conversion (EventHookCallback). A triggered alarm is no longer synthesized into the events pipeline as an Alarm/AlarmRecovery event; events now originate only from real event sources (agents, SkyWalking CLI, Kubernetes Event Exporter). Alarms remain available through the alarm store (getAlarm/queryAlarms) and the configured alarm hooks. This drops a documented "Known Event" and removes 1-2 synthetic event records per alarm fire.
  • TLS for all OAP HTTP/REST servers, with cert hot-reload. Adds the restSSLEnabled / restSSLKeyPath / restSSLCertChainPath config structure to every OAP HTTP server — core REST, sharing-server, admin, PromQL, LogQL, TraceQL and Zipkin query/receiver — each with its own dedicated environment variables (SW_CORE_REST_SSL_*, SW_RECEIVER_SHARING_REST_SSL_*, SW_ADMIN_SERVER_REST_SSL_*, SW_PROMQL_REST_SSL_*, SW_LOGQL_REST_SSL_*, SW_TRACEQL_REST_SSL_*, SW_QUERY_ZIPKIN_REST_SSL_*, SW_RECEIVER_ZIPKIN_REST_SSL_*). The shared Armeria HTTPServer reloads the key pair from disk on rotation (via TlsProvider.ofScheduled) so refreshed certificates are picked up without restarting the OAP, matching the existing gRPC SSL hot-reload behavior. HTTP TLS is server-side only (no mTLS).
  • New queryAlarms GraphQL query — entity / layer / rule filters for alarms. Adds a comprehensive alarm query API alongside the legacy getAlarm. The new queryAlarms(condition: AlarmQueryCondition!): Alarms accepts a single input type bundling every filter the alarm record stores: entities: [Entity!] (reuses the MQE Entity shape — pin to specific services / instances / endpoints / processes or their relations, matched against alarm id0 OR id1); layer: String (filter by the alarmed entity's layer — single match, since alarm rows persist one layer); ruleNames: [String!] (filter by which alarm rule fired); plus keyword, tags, duration, paging. Legacy getAlarm is marked @deprecated but still routes to the same DAO — no client breakage. Backend additions: a new layer column on AlarmRecord populated at alarm-mint time via MetadataQueryService.getService(serviceId).getLayers(); the existing id0/id1 columns flipped from storageOnly = true to indexed so the entity filter pushes down to storage. IAlarmQueryDAO.queryAlarms(condition, limit, from) is a new abstract method — 3rd-party storage backends fail at compile if they miss the override (SWIP-14 pattern). All three bundled backends implement it: BanyanDB / Elasticsearch / JDBC. Operator semantics: (1) Relation entities are exact-match. Passing {scope: ServiceRelation, serviceName: A, destServiceName: B} matches only the alarm where id0=serviceId(A) AND id1=serviceId(B), not any alarm that touches A or B on either side. Wider "anything involving A" queries should pass the individual non-relation entity instead ({scope: Service, serviceName: A} — which expands to id0=A OR id1=A). (2) Single layer per alarm row. The persisted column stores ONE layer (the first entry of the entity's resolved layer list — source-first for relations). A service in [GENERAL, K8S_SERVICE] whose metadata resolves to GENERAL first is filed under GENERAL; querying layer: "K8S_SERVICE" will miss it. Operator migration note: existing pre-upgrade alarm rows continue to be filterable by the legacy getAlarm fields; the new entity / layer / rule filters in queryAlarms apply only to alarms written after the upgrade (existing storage indices don't transition index: false → true in place; new daily-rolled indices pick up the indexed columns). Schema additions are non-blocking — bootstrap silently skips column-attribute changes on existing indices.

  • Runtime rule hot-update for MAL and LAL. Operators can now ship metric (MAL) and log (LAL) rule changes without restarting OAP. A push to a new admin endpoint persists the rule to the configured storage backend, and every node in the cluster converges to the new content within ~30 seconds. Common workflows:
    • addOrUpdate — create or replace a rule. Body is the raw YAML you would normally ship with OAP's static rule files. Returns 200 once the rule is applied locally and persisted; peers pick it up on their next periodic scan (≤ 30 s).
    • inactivate — soft-pause a rule. The OAP stops emitting metrics for that rule but the backend measure (and its history) is preserved, so a later addOrUpdate to the same (catalog, name) is lossless. The "off" intent is durable across reboots; bundled rules on disk are not auto-resurrected when an inactivate removes the runtime override. This is the safe way to take a rule offline.
    • delete — removes an INACTIVE row (active rules return 409 requires_inactivate_first). For runtime-only rules with no bundled YAML on disk, the row is dropped; the backend measure (if any) is left in place as an inert artefact, matching bundled-rule deletion semantics (removing a YAML from otel-rules/ on disk doesn't drop its measure either). Returns 400 no_bundled_twin when ?mode=revertToBundled is used without a bundled YAML on disk.
    • get / bundled / list / dump — read-side endpoints for fetching a single rule's YAML (with ETag support; ?source=bundled reads the on-disk bundled YAML even when a runtime override is in place), listing the bundled-vs-runtime overlay per catalog, inspecting cluster-wide rule state as a JSON envelope ({generatedAt, loaderStats, rules} — each row carries status/localState/loaderKind/bundled/bundledContentHash so a UI can render override badges without a second roundtrip), and exporting all rules as a tar.gz for backup / DR. The endpoint is disabled by default and listens on port 17128 (HTTP) when enabled. Such a queue runs its drain loops on virtual threads where the runtime provides them (JDK 25+) and falls back to N platform threads otherwise; the count, and therefore concurrency, batching, back-pressure, drop semantics and per-partition ordering, are identical on both paths. Shutdown latency is the one exception: the platform scheduler drops drain tasks parked on their idle backoff, while the virtual-thread adapter sleeps inside the submitted task and cannot, so an ioBound queue should keep maxIdleMs within shutdownTimeoutMs. There is deliberately no CPU-proportional form: virtual threads are not preemptive, so CPU-bound work would hold its carrier and starve the shared carrier pool, and L1/L2/TopN stay on cpuCores/fixed. Drain loops hold the read lock for the whole cycle — the running recheck, the partition dequeue, the idle notification and the dispatch — because onIdle() touches the same worker state as consume() and an unlocked dequeue would let shutdown dispatch a newer batch ahead of one a task already holds. The compiler honours JLS-style binary numeric promotion and emits Java arithmetic in the declared primitive type — (x as Integer) + (y as Integer) compiles to int + int (not widened to long). + with any String operand falls back to string concatenation; - / * / / against non-numeric operands produces a compile-time error. The as Double and as Float casts are accepted in typeCast clauses, including in def declarations. Numeric comparisons honour declared casts on both sides (no more universal h.toLong() wrapper).
  • Fix: avgHistogramPercentile / sumHistogramPercentile meter functions reported the smallest finite bucket boundary (e.g. 10 for OTel gen_ai_server_request_duration whose le is rewritten from 0.01s → 10ms) for every rank when no samples were observed in any bucket. The percentile loop's count >= roof check matched on the first sorted bucket because both sides were 0. calculate() now short-circuits to 0 for every rank when the windowed total is 0.
  • Fix: MAL expPrefix now applies to every metric source in exp, not just the leading one. Previously the prefix was spliced after the first ., so secondary metrics inside arguments (e.g. the divisor in a.sum(['s']).safeDiv(b.sum(['s']))) silently skipped the prefix — a rule like envoy-ai-gateway's request_latency_avg (sum / count) would tag-rewrite only the dividend. The injection is now AST-aware: every bare-IDENTIFIER metric source is wrapped, while downsampling-type constants (SUM, AVG, LATEST, SUM_PER_MIN, MAX, MIN) are skipped.
  • Add @Stream(allowBootReshape = true) opt-in for additive boot-time reshape of BanyanDB streams / measures. Code-defined stream classes (e.g. AlarmRecord) can now annotate their schema as eligible for in-place additive update at OAP boot — a new @Column is appended to the live tag-family / fields via client.update instead of being silently rejected with SKIPPED_SHAPE_MISMATCH (which previously forced operators to drop the measure / stream and lose historical rows). Additive includes both new tags / fields and relocating an existing tag between families when a @Column's storageOnly flag flips (e.g. id1 moving from storage-only → searchable when it becomes indexed). The opt-in is per-stream and gated by an isPurelyAdditive shape diff: tag type changes, tag drops, kind flips (tag↔field), entity / interval / sharding-key changes, and field re-typing still skip with SKIPPED_SHAPE_MISMATCH, so identity-breaking edits remain explicit operator actions. Only the init / standalone OAP performs the reshape; non-init peers continue through the existing poll-and-wait loop so a single node drives DDL. When a check* records SKIPPED_SHAPE_MISMATCH the dependent IndexRule / IndexRuleBinding reconciliation is also skipped — preventing the previous gap where the binding silently updated to a tag list that diverged from the live tag-family layout. AlarmRecord is opted in. Default remains false for all other models — boot-time reshape stays off unless the annotation is explicitly set. Operator caveat: BanyanDB does not physically migrate existing rows when a tag's family changes; pre-existing data stays in its original on-disk location while new writes go to the declared family — expect a backfill window for queries that route through new IndexRules on relocated tags.

Also realign jackson-databind 2.16.0 → 2.18.8 so the whole jackson family is managed at a single version (it had been left behind the other jackson artifacts).
  • Bump Apache Curator 4.3.0 → 5.9.0 and Apache ZooKeeper 3.5.7 → 3.9.5 together to clear CVE-2023-44981 (the bundled ZooKeeper jar carried it; OAP is a ZooKeeper client only, so the server-side bug was never reachable, but the jar tripped Dependabot). The cluster-zookeeper and configuration-zookeeper plugins use only stable Curator APIs, so no source changes were required. Operator-facing change: the supported ZooKeeper server version is now 3.6+ (Curator 5.x uses ZooKeeper persistent watches, added in server 3.6.0); older servers (3.5.x, 3.4.x) are no longer supported.
  • Migrate the Consul cluster and configuration client from the abandoned com.orbitz.consul:consul-client 1.5.3 to the maintained fork org.kiwiproject:consul-client 0.9.0 to clear the okhttp CVE the old client carried (CVE-2021-0341; the old client pinned okhttp 3.14.9, fixed in okhttp 4.9.2+), so the BOM now pins okhttp to 4.12.0. The fork's 0.9.x line is the last one built for JDK 11 (which SkyWalking still targets); 1.0.0+ is compiled to JDK 17 bytecode, so the migration stays on 0.9.0. The cluster-consul and configuration-consul plugins use only stable Consul client APIs, so the change is a package rename (com.orbitz.consul → org.kiwiproject.consul); okhttp is pulled only by the Consul plugins (the fabric8 Kubernetes client excludes its okhttp transport), so no other module is affected.
  • Bump test-scope assertj-core 3.20.2 → 3.27.7 to clear CVE-2026-24400 (XXE in isXmlEqualTo, not used by any test).

  • Fix: continuous profiling policy validation now rejects a threshold / count of 0 to match the error messages and rover's value >= threshold trigger semantics (a 0 threshold would always trigger). CPU percent and HTTP error rate are tightened from [0-100] to (0-100].
  • Fix wrong BanyanDB resource options in record data.
  • Align the default BanyanDB stage segmentInterval values so each coarser stage is an integer multiple of the finer one (records cold 3 → 4, metricsMinute cold 5 → 6, metricsHour warm 7 → 10 and cold 15 → 20), keeping hot → warm → cold lifecycle migration on the cheap whole-segment fast path.
  • Fix: layer-extensions.yml is now excluded from the skywalking-oap jar and shipped to the distribution config/ directory, so an operator-edited config/layer-extensions.yml is no longer shadowed by the empty template bundled in the jar. Because the OAP launch script puts oap-libs/*.jar ahead of config/ on the classpath, ResourceUtils.read("layer-extensions.yml") previously always resolved the jar-bundled layers: [] and silently ignored the operator's file — custom layers declared there never registered. The file now follows the same exclude-from-jar + copy-to-config/ packaging as every other operator-editable config (application.yml, alarm-settings.yml, etc.).
  • Fix: the v2 MAL compiler now resolves custom layers referenced as Layer.NAME in an expression. A custom layer declared through a layerDefinitions: block (or layer-extensions.yml / the LayerExtension SPI) has no generated Layer.* static field, so service(['svc'], Layer.IOT_FLEET) previously failed code generation because Layer has no IOT_FLEET field. The compiler now lowers every Layer.NAME static-field reference to a runtime Layer.nameOf("NAME") registry lookup, so a custom layer can be referenced exactly like a built-in one (Layer.GENERAL). For a built-in layer this is equivalent, because Layer.nameOf("GENERAL") returns the same instance as the Layer.GENERAL field. The lowering is scoped to Layer only; the other MAL enum types (DetectPoint, DownsamplingType, etc.) are real Java enums and keep their direct static-field reference.
  • Fix Envoy ALS rendering for the LAL live-debugger and the persisted log content: an Istio metadata-exchange peer in common_properties.filter_state_objects (legacy Wasm wasm.*_peer = Any{BytesValue} wrapping a FlatBuffer, or modern *_peer = Any{Struct}) is now decoded into the readable peer metadata (pod / namespace / labels) instead of an opaque jsonformat-failed envelope or base64. The serialization is hardened so a single un-printable field can no longer blank the whole entry — the LalPayloadDebugDump printer carries a well-known-type TypeRegistry and sanitizes every value JsonFormat would reject (an unresolvable, no-slash, or corrupt-bytes Any degrades to an @unresolved placeholder; a non-finite Value double NaN/Infinity is rendered as a string), keeping the rest of the entry readable. Because the LAL output builder's bindInput runs eagerly before the debug capture, this also stops an unregistered filter_state_objects type from throwing and aborting the whole rule (dropping the mesh log). Decoding is wired through a new LalInputDebugRenderer SPI (EnvoyAlsHttpDebugRenderer / EnvoyAlsTcpDebugRenderer) so log-analyzer reaches the receiver-side decoders without depending on the Envoy receiver, and covers both HTTP and TCP access logs.
  • Surface the effective BanyanDB configuration (bydb.yml / bydb-topn.yml) in the /debugging/config/dump admin API. Because the BanyanDB config moved to a separate file in 10.2.0, a BanyanDB deployment previously showed an empty storage.banyandb block in the dump; its post-environment-resolution values are now merged into the same response under storage.banyandb.* (TopN rules under storage.banyandb.topN.*), masked by the same secret-keyword list, via a generic ConfigDumpExtension SPI on ServerStatusService that any module loading config from a secondary file can implement.
  • Fix: an MQE top_n(metric, N, order, attrX='value') query whose attribute is not a column of the target metric now returns a descriptive MQE error instead of a raw storage IOException surfaced as Internal IO exception, query metrics error.. Attribute columns (attr0..attrN) exist only on decorated metrics (service_* / endpoint_* / kubernetes_service_*, set to the layer name via OAL .decorator(...)) and the MAL meter base; metrics such as relations or database / cache / mq access carry none, so passing an attribute condition previously reached the storage engine with a tag it does not define and failed there. MQEVisitor now validates each attribute key against the metric's registered queryable columns before the storage call and raises IllegalExpressionException (naming the attribute and the metric) when it is absent.
  • Migrate all BanyanDB storage read queries from the typed query-builder API to BydbQL.
  • Fix: BanyanDB queries no longer silently truncate at the storage engine's implicit row cap. BanyanDB applies its own default limit to any query that carries none — 100 rows for measures, 20 for streams/traces — and applies it after GROUP BY, so an over-long result set is cut short rather than rejected. OAP never sent a limit on several read paths, so a metrics query returned at most 100 data points regardless of the requested range: a 4-hour minute-step read rendered only its first 100 minutes and the rest showed as empty, even though DurationUtils allows up to 500 steps. The same cap silently shortened topology relation maps, instance/process metadata lists, profiling thread snapshots and eBPF task lists. Every BydbQL query now leaves OAP with an explicit LIMIT: the entity-scoped metrics read sends the exact number of assembled duration points (matching the row set the ES/JDBC DAOs fetch by id), ad-hoc SELECT TOP sends its own N, and anything that does not paginate itself falls back to the configured resultWindowMaxSize (default 10000) instead of the engine default. ES and JDBC storage were never affected.
  • Support BanyanDB's group-scoped trace retention pipeline in bydb.yml. The trace and zipkinTrace groups gain a pipeline block (enabled, enabledEvents, mergeGraceSeconds, finalizeGraceSeconds, and an ordered plugins chain) that OAP pushes onto the BanyanDB group as a TracePipelineConfig, letting a sampler plugin drop traces inside the data node during Hot-phase compaction — after storage, so it reclaims space already written and decides per whole trace, unlike the ingest-side server-side trace sampling. Disabled by default, since it deletes stored traces. Even when enabled it is inert unless the data node runs the plugin-capable BanyanDB image with the sampler .so mounted — a node without that support ignores the config, and one that cannot load the plugin logs an error and merges unfiltered, so nothing is dropped unexpectedly. The two grace windows use -1 for "inherit the data node default" (30s merge / 5m finalize) because the node treats any non-positive grace as unset. enabledEvents accepts a comma-separated string so it can be set from the environment (SW_STORAGE_BANYANDB_TRACE_PIPELINE_ENABLED_EVENTS and its ZIPKIN_ variant) as well as a YAML block list; an empty value falls back to PIPELINE_EVENT_MERGE, so PIPELINE_EVENT_FINALIZE runs only when named explicitly. Each plugin's config is passed through verbatim as a protobuf Struct: nested lists and objects (e.g. keepTagRules) now survive the config loader and are serialized as real ListValue/Struct rather than being flattened to a string. Note a float written as a ${ENV:default} placeholder still reaches the plugin as a JSON string, because the shared placeholder resolver only preserves String/Integer/Long/Boolean; the first-party samplers accept a quoted number for exactly this reason. See Trace Tail Sampling for how a trace is judged, and BanyanDB storage for the configuration keys.
  • Fix: a blank value in bydb.yml (key: with nothing after it) aborted OAP startup with an opaque NullPointerException from java.util.Properties, which rejects null values. The BanyanDB config loader now skips blank entries and leaves the field at its default, the same outcome as omitting the line.
  • Route LAL rules within a layer by their input type, so a single layer can host rules over different proto inputs. Each compiled rule now carries its effective input type (the proto class its parsed.* getters cast to, or null for parser-based / untyped rules), and LogFilterListener skips any rule whose type doesn't match the incoming log instead of running every rule in the layer. This fixes a latent ClassCastException (caught and logged per log) that fired whenever a MESH log of one shape reached a rule compiled for another — e.g. an Envoy TCP access log or a network-profiling LogData hitting the HTTP envoy-als rule. Adds an envoy-als-tcp rule (inputType: TCPAccessLogEntry) alongside the existing HTTP envoy-als; both share the MESH layer and each now only sees its own entry type.

The shared HTTP hook helper treated only 200 and 204 as success, so any other 2xx — notably the 202 Accepted returned by asynchronous intake APIs such as PagerDuty's Events API v2 — produced send to ... failure. Response code: 202 at ERROR level on every delivered alarm. The alarm was still delivered; the log entry was wrong. The check now accepts the whole 2xx range, for all alarm hooks.
