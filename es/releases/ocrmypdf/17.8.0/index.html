#OCRmyPDF v17.8.0

  • --output-type auto (el valor predeterminado) vuelve a producir PDF/A siempre que puede, que coincide con el comportamiento "PDF/A por defecto" de OCRmyPDF 16. Primero prueba el ayuno. Conversión sin Ghostscript (validada por veraPDF cuando esté disponible) y ahora recurre a Ghostscript cuando no puede producir PDF/A, solo emite un PDF normal cuando ni siquiera Ghostscript puede convertir de forma segura (por ejemplo, un entrada con fuentes CID/CJK no incrustadas, según {issue}1561). Una consecuencia es que la ruta predeterminada puede volver a invocar Ghostscript, que es más lento y puede transcodificar imágenes; use --output-type pdf para omitir la conversión de PDF/A enteramente.
  • Se corrigió la detección de veraPDF 1.30.0 y versiones más recientes: las compilaciones recientes imprimen JVM advertencias antes de su cadena de versión, lo que provocó que OCRmyPDF informara veraPDF como no disponible y omitir la ruta rápida de PDF/A.
  • OCRmyPDF ya no daña silenciosamente una capa de texto CID no incrustado (CJK) cuando produciendo PDF/A ({issue}1561). PDF/A requiere que todas las fuentes estén incrustadas, por lo que Ghostscript sustituye y vuelve a incrustar fuentes CID no incrustadas, como el OCR capa de texto que Adobe Acrobat agrega a los documentos CJK escaneados, lo que destroza el texto y destruye la capacidad de búsqueda. OCRmyPDF ahora detecta fuentes CID no incrustadas antes de la conversión: con --output-type auto (el valor predeterminado) produce un PDF normal y conserva la capa de texto existente, y con un explícito --output-type pdfa* se detiene con un error en lugar de emitir datos corruptos salida. Utilice --output-type pdf para mantener la capa de texto, o --force-ocr para reconstruirlo con fuentes incrustadas.
  • Ahora es posible escribir el PDF de salida en la salida estándar (ocrmypdf input.pdf -). protegido contra la corrupción a nivel del sistema operativo. Anteriormente OCRmyPDF no se basó en ningún código durante el proceso: bibliotecas, complementos o complementos de terceros. llamadas perdidas print(): alguna vez escribiendo en stdout; una sola escritura accidental corrompería silenciosamente el PDF. El programa de línea de comando ahora guarda el archivo real. stdout al inicio, antes de que se carguen los complementos o se inicie cualquier proceso/hilo de trabajo. iniciado y redirige el descriptor de archivo 1 a stderr, de modo que solo los OCRmyPDF La salida final del PDF puede llegar a la salida estándar. Una consecuencia es que un complemento que Las impresiones intencionadas en stdout harán que la salida se redirija a stderr.
  • Se agregó la función pública API {func}ocrmypdf.configure_stdout_protection, que instala esta misma protección. Como {func}ocrmypdf.configure_logging, es opcional y está destinado a personas que llaman y desean un comportamiento similar al de una línea de comandos; las aplicaciones que administran su propia salida estándar no deberían llamarlo.
  • Se corrigió un UnicodeDecodeError no detectado al procesar un PDF cuyo El diccionario /DocumentInfo contiene una clave /Name codificada en Latin-1 (o otra codificación que no sea UTF-8), como /Saks#e5r. repair_docinfo_nuls ahora trata dicho bloque como mal formado, registra un mensaje y continúa en lugar de estrellando la tubería ({issue}1540). Las versiones actuales de pikepdf toleran estos claves mediante surrogate-escaping, pero las versiones anteriores surgieron al iterar el diccionario.

OCRmyPDF v17.8.0

Highlights

  • --output-type auto is PDF/A-first again — The default now mirrors OCRmyPDF 16: it attempts the fast, Ghostscript-free conversion (validated by veraPDF when available), then falls back to Ghostscript, and only emits a plain PDF if even Ghostscript can't safely convert. Adopters should expect the default path to re-invoke Ghostscript — slower and potentially image-transcoding — so pin --output-type pdf if you need deterministic, non-archival output.

  • Non-embedded CID/CJK text layers are protected, not corrupted (issue 1561) — PDF/A's embedded-font requirement used to make Ghostscript re-embed Acrobat's OCR layer on scanned CJK documents, mangling it and destroying searchability. OCRmyPDF now detects these fonts before conversion: auto produces a regular PDF and preserves the text layer, while explicit --output-type pdfa* fails with an error rather than shipping corrupt files. If you must have PDF/A for such inputs, plan to run --force-ocr to rebuild the layer with embedded fonts.

  • veraPDF 1.30.0+ detection fixed — Recent veraPDF builds print JVM warnings before their version string, which made OCRmyPDF report veraPDF as missing and skip the fast PDF/A path entirely. Upgrading removes that silent performance regression: anyone on a modern veraPDF was quietly getting the slower Ghostscript fallback.

  • stdout output hardened at the file-descriptor level (+ new API) — ocrmypdf input.pdf - now saves the real stdout before plugins or workers start and redirects fd 1 to stderr, so only the final PDF can reach stdout and a stray print() can't corrupt the stream. Watch out: plugins that intentionally write to stdout will now be redirected to stderr. Library callers wanting CLI-like behavior can opt in through the new ocrmypdf.configure_stdout_protection() (a sibling of configure_logging()); applications managing their own stdout should leave it alone.

  • Malformed /DocumentInfo names no longer crash (issue 1540) — A Latin-1-encoded /Name key such as /Saks#e5r previously raised an uncaught UnicodeDecodeError in repair_docinfo_nuls and aborted the pipeline; it's now flagged as malformed, logged, and skipped. This matters most if you're pinned to older pikepdf versions that lacked surrogate-escaping tolerance for such keys.

No breaking changes.

  • --output-type auto (the default) again produces PDF/A whenever it can, matching OCRmyPDF 16's "PDF/A by default" behavior. It first tries the fast Ghostscript-free conversion (validated by veraPDF when available) and now falls back to Ghostscript when that cannot produce PDF/A, only emitting a regular PDF when even Ghostscript cannot safely convert (for example, an input with non-embedded CID/CJK fonts, per {issue}1561). A consequence is that the default path may once again invoke Ghostscript, which is slower and may transcode images; use --output-type pdf to skip PDF/A conversion entirely.
  • Fixed detection of veraPDF 1.30.0 and newer: recent builds print JVM warnings before their version string, which caused OCRmyPDF to report veraPDF as unavailable and skip the fast PDF/A path.
  • OCRmyPDF no longer silently corrupts a non-embedded CID (CJK) text layer when producing PDF/A ({issue}1561). PDF/A requires all fonts to be embedded, so Ghostscript substitutes and re-embeds non-embedded CID fonts — such as the OCR text layer Adobe Acrobat adds to scanned CJK documents — which mangles the text and destroys searchability. OCRmyPDF now detects non-embedded CID fonts before conversion: with --output-type auto (the default) it produces a regular PDF and preserves the existing text layer, and with an explicit --output-type pdfa* it stops with an error rather than emit corrupted output. Use --output-type pdf to keep the text layer, or --force-ocr to rebuild it with embedded fonts.
  • Writing the output PDF to standard output (ocrmypdf input.pdf -) is now protected against corruption at the operating system level. Previously OCRmyPDF relied on no in-process code — third-party libraries, plugins, or stray print() calls — ever writing to stdout; a single accidental write would silently corrupt the PDF. The command line program now saves the real stdout at startup, before plugins are loaded or any worker process/thread is started, and redirects file descriptor 1 to stderr, so that only OCRmyPDF's final PDF output can reach stdout. A consequence is that a plugin which intentionally prints to stdout will have that output redirected to stderr.
  • Added the public API function {func}ocrmypdf.configure_stdout_protection, which installs this same protection. Like {func}ocrmypdf.configure_logging, it is optional and intended for callers that want command-line-like behavior; applications that manage their own standard output should not call it.
  • Fixed an uncaught UnicodeDecodeError when processing a PDF whose /DocumentInfo dictionary contains a /Name key encoded in Latin-1 (or another non-UTF-8 encoding), such as /Saks#e5r. repair_docinfo_nuls now treats such a block as malformed, logs a message, and continues instead of crashing the pipeline ({issue}1540). Current pikepdf releases tolerate these keys by surrogate-escaping them, but older versions raised while iterating the dictionary.
