mempalace v3.3.5

3.3.5 es una versión de correcciones. No hay nuevas funciones orientadas al usuario: la energía del ciclo se destinó a la integridad de los datos, la recuperación y la corrección entre procesos. Si su palacio alguna vez llegó a Internal error: Error finding id después de una gran mina, o si un gráfico de conocimiento triple desapareció silenciosamente en el vacío, o está ejecutando Windows o un host multiinquilino, esta versión es para usted. El titular corrige:

  • mempalace repair --mode from-sqlite recupera palacios atascados en apply_logs. Cuando el escritor del segmento HNSW de ChromaDB se bloquea (la clase de corrupción reportada anteriormente y en el n.° 1308), --mode legacy y la reparación en línea llaman a Collection.count() como su primera lectura, que es exactamente la llamada que surge. El antiguo modo de falla era una reparación que imprimía Cannot recover — palace may need to be re-mined from source files a pesar de que las tablas SQLite estaban completamente intactas. El nuevo modo lee (id, document, metadata) directamente desde chroma.sqlite3 a través de la unión del segmento de metadatos, nunca abre un chromadb client contra el palacio corrupto y vuelve a insertar todo en un palacio nuevo bajo su función de incrustación configurada. Verificado de extremo a extremo en un palacio corrupto del mundo real de 52.300 filas. (#1308)
  • Dos clases de pérdida silenciosa en el gráfico de conocimiento ahora son errores de tiempo de escritura. Los tripletes con valid_to < valid_from solían almacenarse de forma duradera pero eran inalcanzables (el filtro temporal no coincidía con as_of); add_triple() ahora rechaza intervalos invertidos en el momento de la escritura. Y las cadenas de fecha enviadas a SQLite se validan por adelantado a través de sanitize_iso_temporal() (alias sanitize_iso_date()), que acepta YYYY-MM-DD y fechas horarias UTC canónicas (YYYY-MM-DDTHH:MM:SSZ / +00:00) y rechaza todo lo demás: las entradas de lenguaje natural como "yesterday" ya no producen silenciosamente conjuntos de resultados vacíos. Cambio de comportamiento: las entradas de fecha parcial que funcionaron en 3.3.4 ("2026", "2026-05") ahora tienen error; en su lugar, pase una fecha completa o una fecha y hora UTC canónica. (#1214, #1164, #1167, #1374, #1417)
  • EntityRegistry.save() ahora es a prueba de fallas. El mapa de personas/proyectos lleva meses de extracción de datos, y el código anterior hacía un Path.write_text() no atómico: una pérdida de energía, OOM o kill -9 entre truncado y descarga total lo borraría silenciosamente (el load() del registro se traga JSONDecodeError). Guardar ahora escribe en un archivo temporal hermano, fsync y os.replace() en su lugar. El registro anterior permanece intacto en caso de falla antes de que regrese el cambio de nombre. (#1215)
  • MCP tool_search pasa por la ventana de descarga de HNSW posterior a la mina masiva. Después de una mina CLI, los metadatos del segmento HNSW de ChromaDB se pueden recuperar durante aproximadamente 30 a 60 segundos; La búsqueda de MCP con alcance lateral estaba presionando Internal error: Error finding id durante toda esa ventana. tool_search ahora detecta este transitorio específico, descarta tanto el caché local de MCP como el de backend compartido para el palacio, duerme 2 segundos y vuelve a intentarlo una vez. Los reintentos exitosos están etiquetados con index_recovered: true para que las personas que llaman puedan observar cuándo se disparó. Solución parcial para el clúster #1315 más amplio: tool_check_duplicate y otras herramientas de manipulación de índices aún necesitan el mismo contenedor. (#1396)
  • Corrección entre procesos en Windows y hosts multiinquilino. ChromaBackend.close_palace() ahora libera correctamente el bloqueo de archivos SQLite del lado rust de ChromaDB: reabrir la misma ruta del palacio después de shutil.rmtree ya no falla con SQLITE_READONLY_DBMOVED. Y el _kg del servidor MCP ya no es un singleton a nivel de módulo: los hosts multiinquilino que rotan MEMPALACE_PALACE_PATH entre llamadas a herramientas ahora acceden al archivo SQLite correcto a través de un caché diferido por ruta. (#1067, #1105, #1136, #1160)
  • Windows stdio es UTF-8 en todos los ámbitos. mempalace search > out.txt y las invocaciones canalizadas de fact_checker ya no mojibake texto del cajón cirílico/CJK en el límite del proceso. mcp_server, hooks_cli y cli/fact_checker se reconfiguran de manera idéntica. (#1282)
  • Corrección de enrutamiento miner.detect_room para monorepos. La verificación de subcadena era bidireccional, por lo que cualquier token que fuera una subcadena del nombre de una sala o viceversa coincidía: views/billing-page/src/Foo.test.tsx se enrutaba a una sala interviews porque "views" in "interviews" coincidía primero. Ahora utiliza coincidencia de tokens delimitada por separador (-, _, ., /). (#1004, cierra #1002)
  • mempalace compress ya no falla en palacios con más de ~32k cajones. La búsqueda de cajones ahora está paginada, reflejando la corrección #851 en miner.py. (#1073, #1107) Interno: la confiabilidad de la prueba también fue aprobada: tests/test_palace_locks.py y tests/test_chroma_collection_lock.py cambiaron de fork a spawn para la generación de subprocesos (Python 3.13 + padre multiproceso = punto muerto en fork, y macOS prohíbe la bifurcación sin ejecución a través de CoreFoundation), y varios archivos de prueba ahora envuelven sqlite3.connect(...) en contextlib.closing() para que las conexiones se liberen en el camino del fracaso también. (#1430, #1431) Las promesas no se han movido. Cada palabra almacenada exactamente. Todo permanece en tu máquina. Sin telemetría. No hay alternativas para los API en la nube de los que no le hablamos. Cada lanzamiento agudiza lo que ya existe.

mempalace v3.3.5

3.3.5 is a fixes release. No new user-facing features — the cycle's energy went into data integrity, recovery, and cross-process correctness. If your palace ever hit Internal error: Error finding id after a big mine, or you had a knowledge-graph triple silently disappear into the void, or you're running on Windows / a multi-tenant host — this release is for you.

The headline fixes:

  • mempalace repair --mode from-sqlite recovers palaces stuck on apply_logs. When ChromaDB's HNSW segment writer wedges (the corruption class reported upstream and in #1308), --mode legacy and the inline repair both call Collection.count() as their first read — which is exactly the call that raises. The old failure mode was a repair printing Cannot recover — palace may need to be re-mined from source files even though the SQLite tables were fully intact. The new mode reads (id, document, metadata) directly from chroma.sqlite3 via the metadata segment join, never opens a chromadb client against the corrupt palace, and re-upserts everything into a fresh palace under your configured embedding function. Verified end-to-end on a 52,300-row real-world corrupt palace. (#1308)

  • Two silent-loss classes in the knowledge graph are now write-time errors. Triples with valid_to < valid_from used to be durably stored but unreachable (the temporal filter matched no as_of); add_triple() now rejects inverted intervals at write time. And date strings forwarded to SQLite are validated up front via sanitize_iso_temporal() (alias sanitize_iso_date()), which accepts YYYY-MM-DD and canonical UTC datetimes (YYYY-MM-DDTHH:MM:SSZ / +00:00) and rejects everything else — natural-language inputs like "yesterday" no longer silently produce empty result sets. Behavior change: partial-date inputs that worked in 3.3.4 ("2026", "2026-05") now error; pass a full date or canonical UTC datetime instead. (#1214, #1164, #1167, #1374, #1417)

  • EntityRegistry.save() is now crash-safe. The people/projects map is months of mining data, and the old code did a non-atomic Path.write_text() — a power loss, OOM, or kill -9 between truncate and full-flush would silently wipe it (the registry's load() swallows JSONDecodeError). Save now writes to a sibling temp file, fsyncs, and os.replace()s into place. The previous registry stays intact on any crash before the rename returns. (#1215)

  • MCP tool_search rides through the post-bulk-mine HNSW flush window. After a CLI mine, ChromaDB's HNSW segment metadata can be unflushed for ~30-60s; wing-scoped MCP search was hitting Internal error: Error finding id for that entire window. tool_search now detects this specific transient, drops both the MCP-local and shared-backend caches for the palace, sleeps 2s, and retries once. Successful retries are tagged with index_recovered: true so callers can observe when it fired. Partial fix for the broader #1315 cluster — tool_check_duplicate and other index-touching tools still need the same wrapper. (#1396)

  • Cross-process correctness on Windows and multi-tenant hosts. ChromaBackend.close_palace() now properly releases ChromaDB's rust-side SQLite file lock — reopening the same palace path after shutil.rmtree no longer fails with SQLITE_READONLY_DBMOVED. And the MCP server's _kg is no longer a module-level singleton: multi-tenant hosts rotating MEMPALACE_PALACE_PATH between tool calls now hit the right SQLite file via a lazy per-path cache. (#1067, #1105, #1136, #1160)

  • Windows stdio is UTF-8 across the board. mempalace search > out.txt and piped fact_checker invocations no longer mojibake Cyrillic / CJK drawer text at the process boundary. mcp_server, hooks_cli, and cli/fact_checker all reconfigure identically. (#1282)

  • miner.detect_room routing fix for monorepos. The substring check was bidirectional, so any token that was a substring of a room name or vice versa matched — views/billing-page/src/Foo.test.tsx routed to an interviews room because "views" in "interviews" matched first. Now uses separator-bounded token matching (-, _, ., /). (#1004, closes #1002)

  • mempalace compress no longer crashes on palaces above ~32k drawers. Drawer fetch is now paginated, mirroring the #851 fix in miner.py. (#1073, #1107)

Internal: test reliability got a pass too — tests/test_palace_locks.py and tests/test_chroma_collection_lock.py switched from fork to spawn for subprocess spawning (Python 3.13 + multi-threaded parent = deadlock under fork, and macOS forbids fork-without-exec via CoreFoundation), and several test files now wrap sqlite3.connect(...) in contextlib.closing() so connections release on the failure path too. (#1430, #1431)

The promises haven't moved. Every word stored exactly. Everything stays on your machine. No telemetry. No fallbacks to cloud APIs we didn't tell you about. Each release sharpens what's already there.
