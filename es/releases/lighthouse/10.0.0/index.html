Cambios notables

Cambios en la puntuación de rendimiento

En la versión 8.0, [describimos el papel menguante de TTI] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/v8-perf-faq.md#whats-the-story-with-tti), y hoy tenemos el seguimiento. El tiempo de interacción (TTI) ya no contribuye a la puntuación de rendimiento y no se muestra en el informe. Sin embargo, todavía se puede acceder a él en el resultado de Lighthouse JSON. Sin TTI, la ponderación del cambio de diseño acumulativo (CLS) ha aumentado del 15% al ​​25%. Consulte los documentos para obtener un desglose completo de cómo se calcula la puntuación de rendimiento en 10.0 o juegue con la calculadora de puntuación.

Tipos para el paquete Node

¡Lighthouse ahora incluye declaraciones de tipo! Nuestro ejemplo de receta TypeScript demuestra cómo lograr la seguridad de tipos adecuada con Lighthouse.

Clasificación de entidades de terceros

Desde Lighthouse 5.3, el conjunto de datos impulsado por la comunidad third-party-web se ha utilizado para resumir cómo cada tercero encontrado en una página contribuye al tiempo total de bloqueo de JavaScript, a través de la auditoría third-party-summary. Con Lighthouse 10.0, agregamos una nueva propiedad al resultado de JSON (entities) para hacer un mayor uso de este conjunto de datos. Cada origen encontrado en una página ahora se clasifica como propio o de terceros dentro de entities. En 10.0, esta clasificación se utiliza para activar la casilla de verificación de filtro de terceros existente. En una versión futura de Lighthouse, esto se utilizará para agrupar los elementos de la tabla de cada auditoría según la entidad de la que se originó y agregar el impacto de los elementos de esa entidad específica.

🆕 Nuevas Auditorías

Caché atrás/adelante

La caché hacia atrás/adelante (bfcache para abreviar) es una optimización del navegador que ofrece páginas a partir de instantáneas completamente serializadas cuando se navega hacia atrás o hacia adelante en el historial de sesiones. Hay más de 100 razones diferentes por las que una página puede no ser elegible para esta optimización, por lo que, para ayudar a los desarrolladores, Lighthouse ahora intenta activar una respuesta de bfcache y enumerará todo lo que impidió que el navegador usara bfcache. #14465 Para obtener más información sobre bfcache, consulte el artículo de web.dev. Nota: Esta auditoría inicialmente no estará disponible para PageSpeed ​​Insights.

Impedir pegar en entradas

La auditoría password-inputs-can-be-pasted-into ahora es paste-preventing-inputs. La lógica de esta auditoría funciona igual que antes, pero en lugar de simplemente considerar las entradas [type=password], ahora falla si cualquier elemento de entrada que no sea de solo lectura impide que el usuario pegue. #14313

La documentación de Lighthouse ahora está en desarrollador.chrome.com

Nuestra documentación ya no está alojada en web.dev. Para obtener los documentos de auditoría más actualizados, visite developer.chrome.com/docs/lighthouse/

💥 Cambios importantes

Bajo el capó, Lighthouse ahora utiliza la nueva infraestructura de soporte de flujo de usuarios de forma predeterminada, incluso para ejecuciones de navegación tradicionales. Puede optar por no participar de esta manera: en el CLI, use --legacy-navigation; en DevTools: marque "Navegación heredada" en el menú de configuración. Si tiene un caso de uso que requiere esta trampilla de escape, presente un problema. Planeamos eliminar esta ruta heredada en 11.0.

Para usuarios de Lighthouse result JSON (LHR)

URL de página en el resultado de Lighthouse

Hasta ahora, había dos campos de URL para describir una ejecución de Lighthouse:

  • requestedUrl: la URL proporcionada por los usuarios, a la que Lighthouse le indica a Chrome que navegue.
  • finalUrl: la URL después de cualquier redireccionamiento iniciado por HTTP y JS iniciado por el servidor Esta taxonomía no puede dar cuenta de escenarios más complejos, como redireccionamientos iniciados por JS, uso del Historial API o navegaciones suaves. También estaban mal definidos para los modos de intervalo de tiempo y de instantánea. Para tener en cuenta eso, Lighthouse 10.0 ahora tiene estos campos de URL:
  • (modificado) requestedUrl: la URL a la que Lighthouse navegó inicialmente antes de las redirecciones. Esto es lo mismo que antes para el modo de navegación, pero ahora será undefined en intervalo de tiempo/instantánea.
  • (nuevo) mainDocumentUrl: La URL del último documento solicitado durante una navegación. No tiene en cuenta las navegaciones suaves ni los eventos del historial API realizados después de que se carga la página. Solo está disponible en el modo de navegación y no estará definido en los modos de intervalo de tiempo e instantánea.
  • (nuevo) finalDisplayedUrl: la URL que se muestra en el cuadro combinado del navegador al final de una ejecución de Lighthouse. Tiene en cuenta las navegaciones suaves y el historial de eventos API. Disponible en modos de navegación, intervalo de tiempo e instantánea.
  • (obsoleto) finalUrl: Mismo valor que mainDocumentUrl.

Auditoría de cambios

  • password-inputs-can-be-pasted-into -> paste-preventing-inputs
  • preload-lcp-image -> prioritize-lcp-image
  • third-party-summary ya no usa un valor link para item.entity, en su lugar usa un valor text sin formato
  • full-page-screenshot ya no es una auditoría, sino que se almacena en lhr.fullPageScreenshot. Para suprimir la recopilación de capturas de pantalla de página completa en CLI, debe migrar de --skip-audits full-page-screenshot a --disable-full-page-screenshot.

Para usuarios de Nodo

  • El nodo 14 ya no es compatible, el mínimo ahora es el nodo 16
  • En caso de que importe rutas dentro del paquete del nodo faro: las carpetas lighthouse-core/ y lighthouse-cli/ ahora son simplemente core/ y cli/.
  • Convertido de módulos CommonJS a ES. Aún puedes usar lighthouse en CommonJS usando una importación dinámica: await import('lighthouse'). Para acceder solo a la función lighthouse en CommonJS, también puede usar require('lighthouse/core/index.cjs')
  • La salida CSV de Lighthouse ahora es mucho más útil. Consulte el PR para un ejemplo del nuevo formato
  • LHError ahora es LighthouseError. Si está intentando detectar un error generado por Lighthouse, ¡asegúrese de tenerlo en cuenta!

Cambios en el nodo API

La función lighthouse ahora tiene mejor integración con Puppeteer. Utilice lighthouse(url, flags, config, page) para ejecutar Lighthouse, pasando un identificador Puppeteer.Page existente como page. El flujo de usuario api se ha movido al punto de entrada del nodo de nivel superior y se puede importar con import {startFlow} from 'lighthouse'. Las nuevas funciones flow.startNavigation() y flow.endNavigation() le permiten definir una navegación activada por el usuario sin ninguna función de devolución de llamada. Consulte los documentos de flujo de usuarios para ver un ejemplo. Para cambiar la configuración de un solo paso de flujo de usuario, defina las anulaciones de configuración en las opciones de indicadores de nivel superior flow.snapshot({skipAduits: ['uses-http2']}) en lugar de en la propiedad settingsOverride. Para darle un nombre personalizado a un paso de flujo, use flow.snapshot({name: 'Custom name'}). Anteriormente esto se hacía mediante stepName.

Para la personalización de Lighthouse (configuración personalizada, recopiladores, auditorías)

  • Para funcionar en Lighthouse 10.0, los recopiladores personalizados deberán implementar la nueva interfaz Gatherer (un ejemplo). De lo contrario, solo funcionarán en el modo de navegación heredado y versiones anteriores de Lighthouse.
  • Lighthouse ya no puede usar passes para cargar la página varias veces en el modo de navegación. Si necesita cargar la página varias veces, le recomendamos utilizar un flujo de usuario. Consulte nuestros documentos de configuración para obtener instrucciones sobre cómo convertir al nuevo formato de configuración
  • El artefacto ScriptElements ahora es Scripts, con una forma ligeramente diferente
  • Audit.makeOpportunityDetails y Audit.makeTableDetails ahora aceptan un objeto de opciones como tercer parámetro. Esto termina siendo un cambio radical por solo Audit.makeOpportunityDetails.

Notable Changes

Performance Score Changes

In the 8.0 release, we described TTI's waning role, and today we have the followup. Time to Interactive (TTI) no longer contributes to the performance score and is not displayed in the report. However, it is still accessible in the Lighthouse result JSON.

Without TTI, the weighting of Cumulative Layout Shift (CLS) has increased from 15% to 25%. See the docs for a complete breakdown of how the Performance score is calculated in 10.0, or play with the scoring calculator.

Types for the Node package

Lighthouse now includes type declarations! Our example TypeScript recipe demonstrates how to achieve proper type safety with Lighthouse.

Third-party Entity classification

Since Lighthouse 5.3, the community-driven third-party-web dataset has been used to summarize how every third-party found on a page contributes to the total JavaScript blocking time, via the third-party-summary audit. With Lighthouse 10.0, we are adding a new property to the JSON result (entities) to make further use of this dataset. Every origin encountered on a page is now classified as first-party or third-party within entities. In 10.0, this classification is used to power the existing third-party filter checkbox.

In a future version of Lighthouse, this will be used to group the table items of every audit based on the entity it originated from, and aggregate the impact of items from that specific entity.

🆕 New Audits

Back/forward cache

The Back/forward cache (bfcache for short) is a browser optimization that serves pages from fully serialized snapshots when navigating back or forwards in session history. There are over 100 different reasons why a page may not be eligible for this optimization, so to assist developers Lighthouse now attempts to trigger a bfcache response and will list anything that prevented the browser from using the bfcache. #14465

For more on bfcache, see the web.dev article.

Note: This audit initially will not be available for PageSpeed Insights.

Preventing pasting to inputs

The audit password-inputs-can-be-pasted-into is now paste-preventing-inputs. This audit's logic works just as before, but rather than just considering [type=password] inputs, it now fails if any non-readonly input element prevents the user from pasting. #14313

Lighthouse documentation is now on developer.chrome.com

Our documentation is no longer hosted on web.dev. For the most up to date audit docs, please go to developer.chrome.com/docs/lighthouse/

💥 Breaking changes

Under the hood, Lighthouse now uses the new user-flow supporting infrastructure by default, even for traditional navigation runs. You can opt out of this by: in the CLI, use --legacy-navigation; in DevTools: check “Legacy Navigation” in the settings menu. If you have a use case that necessitates this escape hatch, please file an issue. We plan to remove this legacy path in 11.0.

For Lighthouse result JSON (LHR) users

Page URLs on the Lighthouse Result

Until now, there were two URL fields to describe a Lighthouse run:

  • requestedUrl: the url given by the users, which Lighthouse instructs Chrome to navigate to
  • finalUrl: the url after any server-initiated HTTP and JS-initiated redirects

This taxonomy cannot account for more complex scenarios, such as JS-initiated redirects, usage of the History API or soft-navigations. They were also ill-defined for timespan and snapshot modes. To account for that, Lighthouse 10.0 now has these URL fields:

  • (changed) requestedUrl: The URL that Lighthouse initially navigated to before redirects. This is the same as it was before for navigation mode, but now it will be undefined in timespan/snapshot.
  • (new) mainDocumentUrl: The URL of the last document requested during a navigation. It does not account for soft navigations or history API events made after the page loads. It is only available in navigation mode, and will be undefined in timespan and snapshot modes.
  • (new) finalDisplayedUrl: The URL displayed in the browser combobox at the end of a Lighthouse run. It accounts for soft navigations and history API events. Available in navigation, timespan, and snapshot modes.
  • (deprecated) finalUrl: Same value as mainDocumentUrl.

Audit changes

  • password-inputs-can-be-pasted-into -> paste-preventing-inputs
  • preload-lcp-image -> prioritize-lcp-image
  • third-party-summary no longer uses a link value for item.entity, instead uses a raw text value
  • full-page-screenshot is no longer an audit, instead it is stored at lhr.fullPageScreenshot. To suppress collection of the full-page screenshot in the CLI, you must migrate from --skip-audits full-page-screenshot to --disable-full-page-screenshot.

For Node users

  • Node 14 is no longer supported, the minimum is now Node 16
  • In case you import paths within the lighthouse node package: lighthouse-core/ and lighthouse-cli/ folders are now simply core/ and cli/
  • Converted from CommonJS to ES modules. You can still use lighthouse in CommonJS by using an dynamic import: await import('lighthouse'). For access to just the lighthouse function in CommonJS, you can also use require('lighthouse/core/index.cjs')
  • The CSV output for Lighthouse is much more useful now. Consult the PR for an example of the new format
  • LHError is now LighthouseError. If you are attempting to catch an error thrown by Lighthouse, be sure to account for this!

Node API changes

The lighthouse function now has better integration with Puppeteer. Use lighthouse(url, flags, config, page) to run Lighthouse, passing an existing Puppeteer.Page handle as page.

The user flow api has moved to the top level node entrypoint and can be imported with import {startFlow} from 'lighthouse'.

New flow.startNavigation() and flow.endNavigation() functions let you define a user triggered navigation without any callback function. See the user flow docs for an example.

To change settings for a single user flow step, define the settings overrides on the toplevel flags options flow.snapshot({skipAduits: ['uses-http2']}) instead of on the settingsOverride property.

To give a flow step a custom name, use flow.snapshot({name: 'Custom name'}). Previously this was done via stepName.

For Lighthouse customization (custom config, gatherers, audits)

  • To work in Lighthouse 10.0, custom gatherers will need to implement the new Gatherer interface (an example). Otherwise, they will only work in legacy navigation mode and older versions of Lighthouse
  • Lighthouse cannot use passes to load the page multiple times in navigation mode anymore. If you need to load the page multiple times, we recommend using a user flow. See our config docs for instructions on how to convert to the new config format
  • The ScriptElements artifact is now Scripts, with a slightly different shape
  • Audit.makeOpportunityDetails and Audit.makeTableDetails now accept an options object as the third parameter. This ends up being a breaking change for just Audit.makeOpportunityDetails.
