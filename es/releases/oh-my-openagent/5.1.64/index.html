#oh-mi-openagent v5.1.64

La sincronización de la memoria del escritorio ahora comienza tan pronto como se inicia el motor, sin esperar una sesión. Un motor iniciado por omo host ensure carga extensiones solo cuando se abre una sesión, mientras que el escritorio no abre ninguna hasta que el motor haya enviado el protocolo de enlace de arranque de sincronización de memoria, por lo que los dos se esperaron el uno al otro. El omo compilado y el lanzador npm ahora inician ese reclamo antes de que se cargue el motor cada vez que el lanzamiento de un motor RPC declara un canal memory-sync; la primera sesión lo reutiliza. Un reclamo que falla aún informa que la sincronización de la memoria no está disponible y nunca recurre a las credenciales CLI. (#12702) (#12704)

Interno (solo pruebas): la adquisición de macOS trust lee /etc/ssl/cert.pem a través del lector de paquetes ya inyectable, y una prueba ahora demuestra que un archivo predeterminado con formato incorrecto produce la entrada de colocación estructurada openssl-default-file-malformed (archivo, causa, índice de bloque, estrechamiento). (#12633)

Interno (solo pruebas): las pruebas del importador de archivos predeterminado de OpenSSL ahora indican que cualquier byte alto en una línea BEGIN, no solo una lista de materiales, descarta todo el archivo. (#12632)

Interno (herramientas de liberación): el arnés de mutación trust omo-nativo cuenta a un mutante como muerto sólo cuando una prueba nombrada falla por una afirmación; un mutante que solo arroja un error de tiempo de ejecución o falla durante la carga ahora se informa como crashed y falla la ejecución. (#12631)

Fijo

  • La sincronización de memoria ya no pierde una edición cuando dos dispositivos cambian la misma línea de un archivo de memoria al mismo tiempo. Los dispositivos de esta versión mantienen ambas ediciones como líneas completas y todos los dispositivos convergen. Antes, las ediciones se fusionaban carácter por carácter en texto que no coincidía con ninguno de los dos (#12279).
    • Entre dispositivos en esta versión, una edición no altera una línea que nadie editó. La excepción es una reescritura muy grande: cuando un dispositivo agrega y elimina más de aproximadamente 2000 líneas de una nota en un guardado, ese guardado se fusiona carácter por carácter, como antes de esta solución, por lo que una edición simultánea en la misma línea aún puede fusionarse.
    • Cuando el cuerpo de la nota o el nuevo texto no termina con una nueva línea, la edición aún se fusiona carácter por carácter, como antes, por lo que aún se pueden unir dos ediciones simultáneas en esa última línea.
    • Con un dispositivo que todavía ejecuta una versión anterior, la combinación de caracteres anterior aún puede salir mal de estas maneras:
      • Las líneas adyacentes pueden fusionarse. El dispositivo anterior reescribe la línea justo después de una línea editada en esta versión. Dependiendo de las identificaciones internas de los dos dispositivos, las dos ediciones pueden fusionarse en una línea seguida de una línea vacía. Medido: de head, one, two, tail, esta versión escribe ONE y el dispositivo anterior escribe TWO, y el resultado puede ser head, TWOONE, una línea vacía, tail. Dos dispositivos más antiguos son head, ONE, TWO, tail.
      • El texto sobrante se mueve. El dispositivo anterior edita una línea que esta versión elimina. El texto sobrante se une a una línea vecina.
      • Su propia diferencia toca otras líneas. La combinación de caracteres del dispositivo anterior se cruza en una línea que su usuario no editó. Esto también sucede entre dos dispositivos más antiguos.
    • Dos dispositivos más antiguos mantienen la combinación de caracteres antiguos hasta que se actualizan. (#12597)
  • Sincronización de memoria: la fase de inserción de un conjunto de memoria grande ya no necesita memoria en proporción a todo el conjunto. Cada paso de inserción se utiliza para releer y reescribir un archivo de diario que contiene los datos de cada elemento pendiente, varias veces por lote. Por lo tanto, un dispositivo que almacena unos pocos miles de archivos de memoria alcanzó un máximo de 2 GiB o más (#12286). El diario ahora mantiene un pequeño índice de elementos pendientes con sus datos en archivos separados, y un envío lee solo el lote que está enviando. La captura del conjunto antes del envío aún conserva el texto de cada archivo capturado hasta que finaliza la captura. Un diario escrito por una versión anterior se convierte la primera vez que se lee, incluido uno en el que una versión anterior agregó elementos junto al nuevo índice. (#12597)
  • Sincronización de memoria: un dispositivo que recibe una gran cantidad de memoria ya no se ralentiza con cada archivo que descarga. El paso de renderizado solía volver a leer cada registro de renderizado del ciclo para cada archivo, por lo que la primera extracción de unos pocos miles de archivos de memoria tomó decenas de minutos (#12285). Cada archivo ahora cuesta lo mismo y el comportamiento de reanudación tras fallo no ha cambiado. (#12597)
  • Memory git ya no toma core.hooksPath, core.fsmonitor, include.path o includeIf.*.path de un par GIT_CONFIG_COUNT heredado o de una entrada GIT_CONFIG_PARAMETERS, por lo que un par exportado como core.hooksPath=/dev/null ya no puede omitir silenciosamente los ganchos y el mirror push del repositorio de memoria. Todos los demás pares inyectados (url.*.insteadOf, http.extraHeader, credenciales, safe.directory, ...) todavía se aplican, renumerados; una lista inyectada que git no puede analizar se elimina por completo. Memory git tampoco hereda la redirección del repositorio (GIT_DIR, GIT_WORK_TREE, GIT_COMMON_DIR, GIT_OBJECT_DIRECTORY, GIT_NAMESPACE, GIT_CONFIG, ...), por lo que ya no puede apuntar a otro repositorio; Se mantienen GIT_INDEX_FILE, GIT_CONFIG_GLOBAL y GIT_CONFIG_NOSYSTEM. (#12360, corrige #12354) (#12597)
  • La sincronización de la memoria ya no detiene cada pulsación desde un dispositivo cuando el cambio de un archivo de memoria supera el límite de lote de 8 MiB: ese archivo se retiene y se nombra en el estado de sincronización con qué hacer, todas las demás memorias se siguen sincronizando y el archivo se sincroniza por sí solo una vez que cabe. Un cambio que otro dispositivo realiza en un archivo retenido se conserva y llega a la copia de este dispositivo una vez que el archivo encaja, y un cambio que una compilación anterior ya había puesto en cola para dicho archivo se recupera de la misma manera en lugar de permanecer bloqueado. El pie de página de TUI muestra sync held y el aviso dice que el archivo se está reteniendo, y una entrada rechazada que pausa la sincronización nunca se oculta detrás de un archivo retenido. (#12284) (#12597)
  • Al abrir un repositorio de memoria se inician hasta seis procesos git menos: los valores predeterminados de configuración local se leen con un git config --list en lugar de un git config --get por clave, y la reparación del final de línea se omite mientras el repositorio no rastrea nada. Cada sesión que abre memoria paga esto, y en una máquina cargada cada proceso git cuesta cientos de milisegundos. Las propias pruebas de Memory-Core ahora se ejecutan bajo el presupuesto de prueba canónico de 20 s en lugar de los límites por archivo de 5 a 15 s, lo que las hacía fallar solo en hosts ocupados. (#12104, corrige #12103) (#12597)
  • thread_send ya no informa un mensaje como queued cuando nada lo detecta. Cuando la sesión del hilo de destino no tiene drenaje en ejecución, el envío ahora responde queued_offline: el mensaje se conserva y la sesión lo toma la próxima vez que se ejecuta, por lo que la persona que llama sabe que no se inició ningún turno y puede actuar en lugar de esperar. El drenaje también informa un mensaje que contiene detrás del borrador no enviado del usuario, por lo que un drenaje activo nunca se confunde con uno faltante. (#12488, corrige #12486)
  • Verifique que la eliminación recursiva (sincronizada y asíncrona) realmente haya eliminado su ruta, vuelva a intentar los restos silenciosos limitados y únase a los eliminadores de prueba de barrido antes de eliminar sus dispositivos principales. (#11834)

Agregado

  • Las versiones de Windows ahora incluyen omo-git-job-helper.exe, un pequeño asistente nativo que ejecuta cada comando git de memoria dentro de su propio objeto de trabajo de cierre al cerrar, de modo que un escritor posterior pueda demostrar que el git del escritor eliminado desapareció antes de que recupere un bloqueo bloqueado. Nada utiliza el asistente todavía: el núcleo de memoria mantiene el comportamiento actual de Windows hasta que un seguimiento lo conecta, y ninguna versión reclama el nuevo protocolo hasta que su fila de estrés de creación en vuelo haya pasado a Windows CI. (#12105, parte de #10391) (#12597)

oh-my-openagent v5.1.64

Desktop memory sync now starts as soon as the engine boots, without waiting for a session. An engine started by omo host ensure loads extensions only when a session opens, while the desktop opens none until the engine has sent the memory-sync bootstrap handshake, so the two waited on each other. The compiled omo and the npm launcher now start that one claim before the engine loads whenever an RPC engine's launch declares a memory-sync channel; the first session reuses it. A claim that fails still reports memory sync as unavailable and never falls back to CLI credentials. (#12702) (#12704)

Internal (tests only): macOS trust acquisition reads /etc/ssl/cert.pem through the already-injectable bundle reader, and a test now proves that a malformed default file yields the structured openssl-default-file-malformed drop entry (file, cause, block index, narrowing). (#12633)

Internal (tests only): the OpenSSL default-file importer tests now pin that any high byte on a BEGIN line, not only a BOM, drops the whole file. (#12632)

Internal (release tooling): the omo-native trust mutation harness counts a mutant as killed only when a named test fails by an assertion; a mutant that only throws a runtime error or crashes on load is now reported as crashed and fails the run. (#12631)

Fixed

  • Memory sync no longer loses an edit when two devices change the same line of a memory file at the same time. Devices on this version keep both edits as whole lines, and every device converges. Before, the edits were merged character by character into text that matched neither (#12279).
    • Between devices on this version, an edit does not disturb a line nobody edited. The exception is a very large rewrite: when one device adds and removes more than about 2,000 lines of a note in one save, that save is merged character by character, as before this fix, so a concurrent edit to the same line can still splice.
    • When the note's body or the new text does not end with a newline, the edit is still merged character by character, as before, so two concurrent edits to that last line can still splice.
    • With a device that still runs an older version, its old character merge can still go wrong in these ways:
      • Adjacent lines can fuse. The older device rewrites the line right after a line this version edited. Depending on the two devices' internal ids, the two edits can fuse into one line followed by an empty line. Measured: from head, one, two, tail, this version writes ONE and the older device writes TWO, and the result can be head, TWOONE, an empty line, tail. Two older devices give head, ONE, TWO, tail.
      • Leftover text moves. The older device edits a line this version deletes. Its leftover text joins a neighbouring line.
      • Its own diff touches other lines. The older device's character merge crosses into a line its user did not edit. This also happens between two older devices.
    • Two older devices keep their old character merge until they update. (#12597)
  • Memory sync: the push phase of a large memory set no longer needs memory in proportion to the whole set. Every push step used to re-read and re-write one journal file holding every pending item's data, several times per batch. A device pushing a few thousand memory files therefore peaked at 2 GiB or more (#12286). The journal now keeps a small index of pending items with their data in separate files, and a push reads only the batch it is sending. Capturing the set before the push still holds each captured file's text until the capture ends. A journal written by an older build is converted the first time it is read, including one where an older build added items next to the new index. (#12597)
  • Memory sync: a device receiving a large memory set no longer slows down with every file it lands. The render step used to re-read every render record of the cycle for each file, so the first pull of a few thousand memory files took tens of minutes (#12285). Each file now costs the same, and the crash-resume behavior is unchanged. (#12597)
  • Memory git no longer takes core.hooksPath, core.fsmonitor, include.path or includeIf.*.path from an inherited GIT_CONFIG_COUNT pair or GIT_CONFIG_PARAMETERS entry, so an exported pair such as core.hooksPath=/dev/null can no longer silently skip the memory repository's hooks and mirror push. Every other injected pair (url.*.insteadOf, http.extraHeader, credentials, safe.directory, ...) still applies, renumbered; an injected list git itself cannot parse is dropped whole. Memory git also no longer inherits repository redirection (GIT_DIR, GIT_WORK_TREE, GIT_COMMON_DIR, GIT_OBJECT_DIRECTORY, GIT_NAMESPACE, GIT_CONFIG, ...), so it can no longer be pointed at another repository; GIT_INDEX_FILE, GIT_CONFIG_GLOBAL and GIT_CONFIG_NOSYSTEM are kept. (#12360, fixes #12354) (#12597)
  • Memory sync no longer stops every push from a device when one memory file's change is larger than the 8 MiB batch limit: that file is held back and named in the sync status with what to do, every other memory keeps syncing, and the file syncs on its own once it fits. A change another device makes to a held file is kept and lands in this device's copy once the file fits, and a change an older build had already queued for such a file is recovered the same way instead of staying stuck. The TUI footer shows sync held and the notice says the file is being held back, and a refused entry that pauses sync is never hidden behind a held file. (#12284) (#12597)
  • Opening a memory repository starts up to six fewer git processes: the local config defaults are read with one git config --list instead of one git config --get per key, and the line-ending repair is skipped while the repository tracks nothing. Every session that opens memory pays this, and on a loaded machine each git process costs hundreds of milliseconds. memory-core's own tests now run under the canonical 20 s test budget instead of per-file 5-15 s limits, which made them fail only on busy hosts. (#12104, fixes #12103) (#12597)
  • thread_send no longer reports a message as queued when nothing will ever pick it up. When the target thread's session has no running drain, the send now answers queued_offline: the message is kept and the session takes it the next time it runs, so a caller knows no turn started and can act instead of waiting. The drain also reports a message it is holding behind the user's unsent draft, so a live drain is never mistaken for a missing one. (#12488, fixes #12486)
  • Verify recursive removal (sync and async) actually removed its path, retry bounded silent leftovers, and join sweep-test removers before deleting their fixture parents. (#11834)

Added

  • Windows releases now carry omo-git-job-helper.exe, a small native helper that runs each memory git command inside its own kill-on-close job object, so a later writer can prove that a killed writer's git is gone before it reclaims a stranded lock. Nothing uses the helper yet: memory-core keeps today's Windows behavior until a follow-up wires it in, and no release claims the new protocol until its in-flight-creation stress row has passed on Windows CI. (#12105, part of #10391) (#12597)
