formato-google-java v2.0.0

google-java-format 2.0.0 reemplaza el motor de diseño del formateador y realiza algunas mejoras en el formato lambda (#19). Esta versión también agrega un paso de limpieza opcional que realiza pequeños cambios que no son espacios en blanco, que está habilitado de forma predeterminada.

Debido a estos cambios, 2.0.0 reformatea más código existente que una versión típica. Recomendamos reformatear su código base en una sola confirmación al actualizar.

Cambios de formato

  • Una lambda que es el único argumento de una llamada ahora se mantiene en la misma línea que la llamada, en lugar de comenzar en una nueva línea con un nivel adicional de sangría (#19):

    executor.submit(() -> {
  doSomething();
});

  • Los bloques de texto ahora tienen sangría como parte del pase de formato principal, por lo que su sangría es correcta incluso con --skip-reflowing-long-strings.

  • Se corrigió la sangría de los comentarios después de assert, constantes de enumeración, inicializadores de for, recursos de try, cláusulas multicaptura y argumentos de tipo.

Limpiezas

  • Se agregó una bandera --cleanup, habilitada de forma predeterminada, para pequeños cambios que no sean espacios en blanco:

    • eliminar puntos y comas redundantes
    • eliminar paréntesis de anotaciones vacías (@Foo() → @Foo)
    • eliminar paréntesis alrededor de un único parámetro lambda sin tipo ((x) -> ... → x -> ...) (#762)

    Las limpiezas sólo se aplican a los rangos que se están formateando. Utilice --cleanup=false para cambiar únicamente los espacios en blanco (y los indicadores --skip-sorting-imports, --skip-removing-unused-imports y --skip-reordering-modifiers existentes para los demás cambios que no sean espacios en blanco).

  • Al formatear un rango con --lines o --offset y las limpiezas habilitadas, las declaraciones sin formato fuera del rango se vuelven a sangrar para que coincidan con la salida formateada, por lo que una edición que agrega o elimina un nivel de anidamiento no deja el código circundante desalineado. Se eliminan las líneas en blanco que quedan tras las limpiezas.

Configuración

  • --max-line-length=N establece el límite de columnas (predeterminado 100) (#425). (Esta bandera se introdujo en v1.37.0)

Soporte de idiomas

  • Admite clases de valor y registros de valor (JEP 401: Objetos de valor (vista previa))

Javadoc

  • Elimina los asteriscos finales antes de */ (#67).
  • Preservar la sangría relativa en bloques <pre>{@code ...} sin * inicial.
  • Unir palabras con guiones divididas en líneas.

Cuerdas largas

  • Al formatear un rango con --lines o --offset, solo se redistribuyen los literales de cadena larga en el rango solicitado (#1114).
  • Las barras invertidas de escape (por ejemplo, \\t en una ruta de Windows o una expresión regular) ya no se dividen cuando se redistribuyen literales de cadena largos (#1186, #1253, #1439).
  • Las fallas durante el reflujo de cadenas largas se informan como errores en lugar de bloquear o colgar el CLI (#1439).

Otras correcciones

  • Se corrigió el formato en el complemento Eclipse, que fallaba con NoClassDefFoundError desde 1.36.0 porque el complemento no incluía commonmark (#1428).
  • El error al combinar --dry-run con --replace ahora nombra la bandera derecha (#1094).

API cambios

  • JavaFormatterOptions.Builder.cleanup(boolean) controla el nuevo paso de limpieza y el valor predeterminado es true. Esto significa que Formatter.formatSource ahora realiza los cambios que no son espacios en blanco enumerados anteriormente de forma predeterminada. Integraciones que dan formato al código que el usuario está editando, p. formatear al guardar en un IDE, debe configurar cleanup(false); el complemento IntelliJ hace esto.
  • Formatter.getFormatReplacements ahora es estrictamente solo para espacios en blanco: ya no reordena los modificadores y nunca aplica limpiezas. Utilice Formatter.formatSource(String, Collection<Range<Integer>>) para formatear rangos de caracteres con reordenamiento de modificadores.
  • JavaFormatterOptions.Style se convirtió en récord en 1.37.0. Los métodos compatibles con enumeraciones, como Style.valueOf(String), se han restaurado para herramientas como Spotless que los llamaron (#1478).
  • Las clases del motor de diseño anterior (com.google.googlejavaformat.Doc, OpsBuilder y tipos relacionados) ya no se utilizan para formatear Java, pero todavía se incluyen para otros formateadores que se basan en ellas.

Changelog completo: https://github.com/google/google-java-format/compare/v1.37.0...v2.0.0

google-java-format v2.0.0

google-java-format 2.0.0 replaces the formatter's layout engine, and makes some improvements to lambda formatting (#19). This release also adds an optional cleanup pass that makes small non-whitespace changes, which is enabled by default.

Because of these changes, 2.0.0 reformats more existing code than a typical release. We recommend reformatting your codebase in a single commit when upgrading.

Formatting changes

  • A lambda that is the only argument of a call is now kept on the same line as the call, instead of starting on a new line with an extra level of indentation (#19):

    executor.submit(() -> {
  doSomething();
});

  • Text blocks are now indented as part of the main formatting pass, so their indentation is correct even with --skip-reflowing-long-strings.

  • Fixed indentation of comments after assert, enum constants, for initializers, try resources, multi-catch clauses, and type arguments.

Cleanups

  • Added a --cleanup flag, enabled by default, for small non-whitespace changes:

    • removing redundant semicolons
    • removing empty annotation parentheses (@Foo() → @Foo)
    • removing parentheses around a single untyped lambda parameter ((x) -> ... → x -> ...) (#762)

    Cleanups only apply to the ranges being formatted. Use --cleanup=false to only change whitespace (and the existing --skip-sorting-imports, --skip-removing-unused-imports, and --skip-reordering-modifiers flags for the other non-whitespace changes).

  • When formatting a range with --lines or --offset and cleanups enabled, unformatted statements outside the range are re-indented to match the formatted output, so an edit that adds or removes a level of nesting doesn't leave the surrounding code misaligned. Blank lines left behind by cleanups are removed.

Configuration

  • --max-line-length=N sets the column limit (default 100) (#425). (This flag was introduced in v1.37.0)

Language support

  • Support value classes and value records (JEP 401: Value Objects (Preview))

Javadoc

  • Strip trailing asterisks before */ (#67).
  • Preserve relative indentation in <pre>{@code ...} blocks without leading *.
  • Join hyphenated words broken across lines.

Long strings

  • When formatting a range with --lines or --offset, only long string literals in the requested range are reflowed (#1114).
  • Escaped backslashes (e.g. \\t in a Windows path or a regular expression) are no longer split when reflowing long string literals (#1186, #1253, #1439).
  • Failures while reflowing long strings are reported as errors instead of crashing or hanging the CLI (#1439).

Other fixes

  • Fixed formatting in the Eclipse plugin, which failed with NoClassDefFoundError since 1.36.0 because the plugin didn't bundle commonmark (#1428).
  • The error for combining --dry-run with --replace now names the right flag (#1094).

API changes

  • JavaFormatterOptions.Builder.cleanup(boolean) controls the new cleanup pass, and defaults to true. This means Formatter.formatSource now makes the non-whitespace changes listed above by default. Integrations that format code the user is editing, e.g. format-on-save in an IDE, should set cleanup(false); the IntelliJ plugin does this.
  • Formatter.getFormatReplacements is now strictly whitespace-only: it no longer reorders modifiers, and never applies cleanups. Use Formatter.formatSource(String, Collection<Range<Integer>>) to format character ranges with modifier reordering.
  • JavaFormatterOptions.Style became a record in 1.37.0. The enum-compatible methods, such as Style.valueOf(String), have been restored for tools like Spotless that called them (#1478).
  • The previous layout engine's classes (com.google.googlejavaformat.Doc, OpsBuilder, and related types) are no longer used to format Java, but are still included for other formatters that build on them.
