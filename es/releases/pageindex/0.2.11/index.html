Índice de página v0.2.11

  • PageIndex SDK, local o cloud: RAG sin vectores, basado en razonamiento, de extremo a extremo.
  • Indexación mucho más rápida: el motor PageIndex Flash obtiene el árbol a partir de las estadísticas de diseño: no interviene ningún LLM para la generación de la estructura en sí, los LLM solo escriben los resúmenes de los nodos, y la expansión del árbol ahora propone una ola de nodos simultáneamente.
client = PageIndexClient()
client.submit_document("report.pdf")
client.chat("What does the report conclude?")

Índice, chat, integración de agentes, un client. El modo local no necesita servidor, ni base de datos vectorial, ni clave PageIndex API.

Destacados

  • Motor Flash: el valor predeterminado local (mode="standard" mantiene el canal LLM clásico). Los marcadores incrustados se consumen cuando trustworthy, y la optimización del árbol está activada de forma predeterminada: optimize="merge" para el pase determinista sin LLM, "full" (predeterminado) agrega expansión de LLM, que ahora ejecuta una ola de nodos simultáneamente en lugar de un viaje de ida y vuelta a la vez.
  • Una superficie completa, local y en la nube: PageIndexLocalClient(storage_path=...) es el mismo client que la nube: herramientas de envío, árbol, contenido de página, chat y agente, todas presentes en ambos modos, por lo que el código se mueve entre ellos sin cambios.
  • Integración de agentes: el contrato de herramienta MCP en la nube, en proceso: client.agent_tools() (funciones simples), as_openai_tools(), as_anthropic_tools(), as_claude_mcp(), además de paquetes de una llamada openai_agent_config() / anthropic_runner_config() / claude_agent_config() y agent_instructions() para el aviso del sistema. Cloud clients obtiene la herramienta de servidor en vivo configurada a través del puente MCP (punto final de solo lectura de forma predeterminada); Los clients locales obtienen el subconjunto en proceso con los mismos esquemas y sobres: el agente solicita el puerto sin cambios.
  • Superficies de chat: chat(): preguntas y respuestas, en cualquier backend; Puertas de protocolo chat_completions() / responses() / messages() con segmentación doc_id, transmisión, contabilidad de uso honesto y continuidad de caché de avisos en todos los turnos.
  • Perillas de modelo y conexión: index_model / chat_model, index_backend / chat_backend (y backend por llamada) transmitidas palabra por palabra a cada carril: proveedores enrutados por LiteLLM, servidores compatibles con OpenAI sin llave, Azure/Bedrock/Vertex incluidos.
  • Dependencias: Python >= 3.10; openai-agents en la instalación base (el motor de chat); Extras [anthropic] y [claude] para esos SDK.

También en 0.2.11

  • Documentos en la nube, tu propio modelo: api_key decide dónde residen tus documentos; un modelo de chat configurado decide quién responde y los dos se combinan. PageIndexClient(api_key="pi-...", chat_model="openai/gpt-5.2") ejecuta el mismo motor de control de calidad de documentos en proceso sobre el conjunto de herramientas en vivo en la nube; chat(), chat_completions(), responses() y messages() funcionan. El contenido de la página fluye a través de su proceso hasta su proveedor en sus credenciales; doc_id apunta al nivel de aviso; enable_citations se queda con el chat administrado.
  • ranuras index= / chat=: la ortografía agrupada de los argumentos planos: una taquigrafía de cadena o un dictado (index={"model": ..., "storage_path": ...}, chat={"model": ..., "backend": ...}). "cloud" / "local" nombran un lado, un mode= opcional lo verifica y PageIndexLocalClient / PageIndexCloudClient toman las mismas ranuras. PageIndexCloudClient() lee PAGEINDEX_API_KEY; un PageIndexClient() simple permanece local sin importar lo que depare el entorno.
  • Formas de configuración escritas: IndexConfig / CloudIndexConfig / LocalIndexConfig / ChatConfig, con py.typed enviado para que su verificador de tipos las vea.
  • Validación estricta: claves desconocidas, lados mixtos, valores vacíos y conflictos de modo/contenido rechazan la construcción con el vocabulario legal del mensaje: nada se adivina en silencio.
  • La indexación falla ruidosamente: las credenciales inactivas o un modelo faltante fallan en la ejecución en lugar de almacenar un documento con resúmenes en blanco; un desbordamiento de contexto sigue siendo un error por mensaje que la ejecución absorbe; Las respuestas del modelo completamente vacío nunca almacenan un documento listo para recuperar.
  • Los sobres de chat se añaden palabra por palabra: la salida de messages() vuelve a la siguiente solicitud sin cambios; Las marcas de caché de Claude siguen el recorrido del cable; openai_agent_config() toma model_settings y name.
  • Cada error de la nube lleva su estado HTTP; Los metadatos NaN/Infinity se rechazan en la puerta; La línea flash del CLI resuelve --summary-model como las otras líneas. Compatibilidad: los valores que no configuran nada ("", cadenas de solo espacios en blanco, {}) ahora se niegan en la construcción; en una nube client, ​​api_key + chat_model (o chat_backend) selecciona el chat de su propio modelo en lugar de generar errores, y client.retrieve_model = m hace lo mismo. PageIndex v0.2.11

  • The PageIndex SDK, local or cloud — vectorless, reasoning-based RAG, end to end.
  • Much faster indexing — the PageIndex Flash engine gets the tree from layout stats: no LLM involved for the structure generation itself, LLMs only write the node summaries — and tree expansion now proposes a wave of nodes concurrently.
client = PageIndexClient()
client.submit_document("report.pdf")
client.chat("What does the report conclude?")

Index, to chat, to agent integration, one client. Local mode needs no server, no vector DB, no PageIndex API key.

Highlights

  • Flash engine: the local default (mode="standard" keeps the classic LLM pipeline). Embedded bookmarks are consumed when trustworthy, and tree optimization is on by default — optimize="merge" for the deterministic LLM-free pass, "full" (default) adds LLM expand, which now runs a wave of nodes concurrently instead of one round-trip at a time.
  • One complete surface, local and cloud: PageIndexLocalClient(storage_path=...) is the same client as cloud — submit, tree, page content, chat, and agent tools all present in both modes, so code moves between them unchanged.
  • Agent integration: the cloud MCP tool contract, in-process — client.agent_tools() (plain functions), as_openai_tools(), as_anthropic_tools(), as_claude_mcp(), plus one-call openai_agent_config() / anthropic_runner_config() / claude_agent_config() bundles and agent_instructions() for the system prompt. Cloud clients get the live server tool set over the MCP bridge (read-only endpoint by default); local clients get the in-process subset with the same schemas and envelopes — agent prompts port unchanged.
  • Chat surfaces: chat() — question in, answer out, on any backend; chat_completions() / responses() / messages() protocol doors with doc_id targeting, streaming, honest usage accounting, and prompt-cache continuity across turns.
  • Model & connection knobs: index_model / chat_model, index_backend / chat_backend (and per-call backend) passed verbatim to each lane — LiteLLM-routed providers, keyless OpenAI-compatible servers, Azure/Bedrock/Vertex included.
  • Dependencies: Python >= 3.10; openai-agents in the base install (the chat engine); [anthropic] and [claude] extras for those SDKs.

Also in 0.2.11

  • Cloud documents, your own model: api_key decides where your documents live; a configured chat model decides who answers — and the two combine. PageIndexClient(api_key="pi-...", chat_model="openai/gpt-5.2") runs the same in-process document-QA engine over the live cloud tool set; chat(), chat_completions(), responses() and messages() all work. Page content flows through your process to your provider on your credentials; doc_id targets at the prompt level; enable_citations stays with the managed chat.
  • index= / chat= slots: the grouped spelling of the flat arguments — a string shorthand or a dict (index={"model": ..., "storage_path": ...}, chat={"model": ..., "backend": ...}). "cloud" / "local" name a side, an optional mode= cross-checks it, and PageIndexLocalClient / PageIndexCloudClient take the same slots. PageIndexCloudClient() reads PAGEINDEX_API_KEY; a bare PageIndexClient() stays local no matter what the environment holds.
  • Typed config shapes: IndexConfig / CloudIndexConfig / LocalIndexConfig / ChatConfig, with py.typed shipped so your type checker sees them.
  • Strict validation: unknown keys, mixed sides, empty values and mode/content conflicts refuse at construction with the legal vocabulary in the message — nothing is silently guessed.
  • Indexing fails loud: dead credentials or a missing model fail the run instead of storing a document with blank summaries; a context overflow stays a per-prompt failure the run absorbs; all-empty model replies never store a retrieval-ready document.
  • Chat envelopes append verbatim: messages() output goes back into the next request unchanged; Claude cache marks follow the wire routing; openai_agent_config() takes model_settings and name.
  • Every cloud error carries its HTTP status; NaN/Infinity metadata is rejected at the gate; the CLI's flash lane resolves --summary-model like the other lanes.

Compatibility: values that configure nothing ("", whitespace-only strings, {}) now refuse at construction; on a cloud client, api_key + chat_model (or chat_backend) selects own-model chat instead of erroring, and client.retrieve_model = m does the same.
