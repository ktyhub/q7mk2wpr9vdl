#FastGPT v4.16.0

📦 Guía de actualización

1. Actualice la variable de entorno Agent-sandbox-proxy (opcional)

4.16.0 necesita depender del proxy para el acceso al proxy de recursos estáticos. Si la puerta de enlace admite ws y http en el mismo puerto, solo puede abrir un puerto. Si no es compatible, puede configurar el puerto de acceso http configurando PREVIEW_PORT.

# ws和http服务的端口
PORT=1006
# http服务的端口，可以覆盖 PORT
PREVIEW_PORT=1007

La dirección de acceso comienza con http:// o https://. Cuando se implementa con un solo puerto, puede apuntar al mismo nombre de dominio y puerto que AGENT_SANDBOX_PROXY_URL, pero los protocolos usan HTTP(S) y WebSocket(S) respectivamente. Se recomienda encarecidamente que el nombre de dominio configurado y el sitio principal de FastGPT utilicen orígenes diferentes. La implementación del mismo origen permitirá que estos scripts ingresen al límite de seguridad del mismo origen del sitio principal y potencialmente accedan a las credenciales o interfaces del sitio principal. Actualmente, el sistema no exige la verificación del origen para el aislamiento.

Puedes comprobar si es accesible visitando: https://{{host}}/health.

4. Limpiar la configuración del modelo del sistema histórico

Esta versión comienza a utilizar un esquema estricto al inicializar y guardar modelos del sistema. Las cadenas numéricas, los gradientes de precios en forma de cadena o los campos faltantes guardados en versiones anteriores pueden provocar que falle la verificación inicial. Después de la actualización, primero ejecute el ensayo para ver la configuración del modelo que debe procesarse; La ejecución en seco no modificará los datos ni actualizará el caché:

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

Después de confirmar que no hay datos en invalidSamples que requieran procesamiento manual, realice una limpieza formal:

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

La limpieza convierte cadenas numéricas legales en números, convierte la cadena del formato priceTiers en una matriz y elimina números opcionales ilegales. Los números requeridos ilegales o faltantes utilizan los valores predeterminados del sistema: maxContext/maxResponse/quoteMaxToken para LLM es 16000/16000/13000, defaultToken/maxToken para incrustación es 500/3000 y el precio es 0. functionCall sigue siendo opcional y el weight que falta en la incrustación se reemplaza por 0.

La ejecución formal escribe datos de manera uniforme y actualiza inmediatamente la caché del modelo del sistema; la caché en tiempo de ejecución se reconstruye incluso si no hay registros para actualizar. Es seguro volver a ejecutar la interfaz; cuando vuelva a realizar el funcionamiento en seco, wouldUpdate debería ser 0. Los registros que no puedan pasar el esquema del modelo completo actual no se escribirán y todos los detalles se devolverán en invalidSamples.

5. Migrar datos de la herramienta HTTP

Esta versión cambia los parámetros de matriz de la herramienta HTTP en modo manual al esquema estándar JSON. Los entornos que han creado herramientas HTTP manuales antes de la actualización deben realizar esta migración; No es necesario migrar las herramientas HTTP en modo OpenAPI y el script se omitirá automáticamente.

Primero ejecute un simulacro para ver los datos pendientes en la aplicación actual y las versiones históricas. el ensayo no modifica los datos:

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

Luego de confirmar el resultado, realice la migración oficial:

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

El script primero filtrará las aplicaciones por tipo de herramienta HTTP y luego migrará las versiones históricas correspondientes basadas en appId de estas aplicaciones. Sólo se procesarán los modos manuales que no existen para apiSchemaStr, no se modificarán otras aplicaciones ni los modos OpenAPI. La migración se ejecuta en lotes y se puede volver a intentar de forma segura; total.changedDocumentCount en el resultado devuelto indica la cantidad de documentos que se encontraron para procesar. Después de la ejecución formal, puede volver a realizar un ensayo para confirmar que el valor es 0.

6. Migrar datos de Agent Sandbox (más lento)

Esta versión ajusta el Agent Sandbox de App Chat de "una instancia por conversación" a "una instancia compartida por la misma aplicación y el mismo usuario". Los archivos de diferentes conversaciones todavía se guardan en el directorio sessions/<chatId> respectivamente, y las habilidades publicadas se guardan en el directorio compartido projects.

Si Agent Sandbox estaba habilitado anteriormente, la migración del espacio de trabajo heredado debe completarse en el siguiente orden. Los entornos que no hayan habilitado Agent Sandbox pueden omitir esta sección.

Primero realice un ensayo para ver el recuento pendiente de la normalización del campo de Sandbox beta6 y la limpieza del antiguo chat de depuración de habilidades. La ejecución en seco no crea recursos, no accede al almacenamiento de objetos ni modifica datos:

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

Realice la migración oficial después de ver los resultados del ensayo. La migración oficial primero realizará la normalización beta6 y solo continuará con el archivado del espacio de trabajo en la misma solicitud cuando el recuento pendiente restante llegue a cero:

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

Si failures solo contiene Sandbox source is missing or deleted y se ha confirmado que la aplicación o habilidad correspondiente ya no existe, puedes omitir explícitamente estos entornos limitados residuales:

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false,"skipError":true}'

skipError El valor predeterminado es false, manteniendo una migración estricta cuando se omite. Este modificador solo omite todo el grupo cuyo origen falta o se elimina temporalmente, y no archiva, elimina ni migra el entorno limitado dentro de él; Los detalles de omisión se devuelven a través de skippedCount y skipped. Otros errores, como el archivado, el almacenamiento de objetos, los proveedores y el control de concurrencia, aún pueden bloquear las migraciones.

La migración primero ejecutará la lógica previa completa de V4.15.0-beta6: completar el sourceType/sourceId del antiguo Sandbox, limpiar los campos heredados, eliminar los recursos huérfanos que no se pueden atribuir y limpiar los antiguos datos de tres tablas del Skill Debug Chat que faltan sourceType y los prefijos antiguos de los depósitos públicos y privados. Las habilidades con el mismo ID que la aplicación omitirán la limpieza del chat. Después de reformular los dos tipos de datos, el total es normalization.pendingCount; si la cantidad no es 0, no se ingresará en el archivo del espacio de trabajo. Después de la puesta a cero, archive directamente todos los espacios de trabajo antiguos y limpie los recursos informáticos antiguos, luego migre las habilidades y, finalmente, agréguelas en Sandbox a nivel de usuario por aplicación y usuario. Mientras haya un error en la fase de archivo, la fase de instalación no comenzará. El nuevo Sandbox se pausará una vez completada la instalación de Workspace y se iniciará según el proceso normal cuando se utilice por primera vez. Es seguro reintentar los scripts y los archivos y migraciones completados no se vuelven a ejecutar; Los archivos antiguos y los registros antiguos de MongoDB se conservan como copias de seguridad una vez completada la migración.

Verifique los resultados devueltos para normalization.pendingCount, normalizationBlocked, failedCount, failures, skippedCount y skipped. Solo cuando normalization.pendingCount y failedCount son 0 y normalizationBlocked es false, significa que se completaron todas las migraciones de Sandbox no omitidas; Los registros heredados en skipped se conservarán y no se migrarán.

🚀 Nuevo contenido

  1. El Agent Sandbox se cambia a una instancia de nivel de usuario de la aplicación. Varias conversaciones de la misma aplicación y el mismo usuario reutilizan el Sandbox y aíslan cada archivo de conversación a través de un directorio de sesión independiente.
  2. Los archivos y HTML de Sandbox admiten la vista previa directa a través de enlaces de solo lectura a corto plazo y ya no es necesario cargarlos repetidamente en el almacenamiento de objetos para obtener una vista previa.
  3. App Workflow archiva y restaura automáticamente el espacio de trabajo cuando cambia el proveedor de Sandbox o la imagen del tiempo de ejecución, y el proceso de actualización se completa de forma silenciosa durante la ejecución actual.
  4. El nodo de la herramienta de flujo de trabajo admite la generación automática de parámetros de entrada específicos por parte del Agente y conserva las configuraciones existentes, como valores fijos, referencias y entradas del usuario.
  5. Cuando ChatAgent selecciona una herramienta, permite especificar manualmente si se generan parámetros para la IA.
  6. Los datos de la base de conocimientos admiten la personalización de metadata y los metadatos de JSON se pueden importar a través de plantillas API, CSV o Excel; Este campo se conservará en los resultados de búsqueda y en las exportaciones de copias de seguridad. Tanto la importación de plantillas como la importación de copias de seguridad admiten archivos .csv y .xlsx, utilizando encabezados q, a, index y metadata; q, a y metadata tienen una columna cada uno y index puede tener varias columnas en cualquier orden. Los archivos de Excel solo admiten una única hoja de trabajo y no pueden contener celdas combinadas. Los archivos CSV o Excel que no se puedan analizar correctamente generarán una excepción de formato de archivo.
  7. Cargue archivos grandes en trozos.
  8. Cuando el administrador configura la clave de la herramienta del sistema, está cifrada (compatible con la clave configurada).
  9. Guía de estado vacía en la lista de habilidades y vínculo al seleccionar habilidades.
  10. La configuración del sistema de la aplicación de flujo de trabajo se mueve al panel de configuración independiente en la barra de herramientas en el lado izquierdo del lienzo, que se abrirá automáticamente al crear una nueva aplicación de flujo de trabajo.
  11. La declaración de apertura admite la configuración independiente de múltiples preguntas preestablecidas y se puede ordenar arrastrando y soltando.

⚙️ Optimización

  1. Reconstruir el ciclo de vida y el proceso de migración del Agent Sandbox. Crear, pausar, archivar, restaurar, eliminar y cambiar de proveedor admiten protección de concurrencia, reanudación de puntos de interrupción y reintentos idempotentes.
  2. Cuando Agent Sandbox no está disponible o no es compatible con el paquete de equipo actual, App Chat desactiva automáticamente la capacidad Sandbox y otros modelos, herramientas, bases de conocimiento y nodos de flujo de trabajo aún pueden continuar ejecutándose.
  3. Los volúmenes persistentes se pueden conservar después de detener OpenSandbox y reutilizarlos durante ejecuciones posteriores; Los umbrales de pausa y archivo admiten la configuración a través de variables de entorno.
  4. La aplicación y la habilidad tienen un estado de actualización de imagen en tiempo de ejecución unificado y la página de edición de habilidades puede sondear continuamente los resultados de la actualización.
  5. Cree automáticamente directorios principales antes de escribir archivos Sandbox para evitar errores al escribir rutas anidadas.
  6. Optimice los problemas de compatibilidad, como los datos de flujo de trabajo antiguos y los parámetros de herramientas.
  7. El agente pregunta a la interfaz de usuario.
  8. Reconstruya la página del canal de lanzamiento, muéstrela en grupos por canales nativos y canales de terceros, y muestre la cantidad configurada de cada canal.
  9. La actualización por lotes del mercado de herramientas admite la visualización de algunos elementos fallidos, el reintento o la desinstalación individualmente y mejora la visualización de las versiones instaladas y el estado de las actualizaciones.
  10. El límite superior del número de aplicaciones rápidas en la página del portal se ajusta a 3 y las configuraciones históricas que han excedido el límite superior son compatibles.
  11. El analizador de PDF utiliza un recorte de bordes dinámico en lugar de un recorte de bordes fijos para evitar recortar el contenido real.

FastGPT v4.16.0

Highlights

  • Agent Sandbox is now shared per App/user — Multiple chats in the same App now reuse one Sandbox for the same user instead of creating one per conversation. Files remain isolated under sessions/<chatId>, while published Skills share projects. Short-lived read-only preview links eliminate duplicate object-storage uploads, and provider/runtime-image changes automatically archive and restore Workspaces. Sandbox failures or unsupported plans now disable only Sandbox, leaving models, tools, knowledge bases, and Workflow nodes operational.

  • Breaking: Sandbox deployment and data migration — The E2B provider is removed: switch to opensandbox or sealosdevbox, delete AGENT_SANDBOX_E2B_API_KEY, and retire AGENT_SANDBOX_DISK_MB and other E2B variables. In both fastgpt-app and fastgpt-pro, configure AGENT_SANDBOX_PREVIEW_PROXY_URL for HTTP(S), while AGENT_SANDBOX_PROXY_URL uses WebSocket(S); OpenSandbox also requires VM_VOLUME_NAME_PREFIX. Configure proxy PREVIEW_PORT if HTTP and WebSocket cannot share a port, and preferably use a separate origin because isolation is not enforced. Use matching fastgpt-app/fastgpt-pro v4.16.0 and agent-sandbox-proxy/agent-sandbox-volumn v0.3.0 images—mixed preview-protocol versions are unsupported. Any environment that previously enabled Sandbox must run /api/admin/4160/initUserSandbox with dryRun:true, then dryRun:false, checking normalization.pendingCount, failedCount, and normalizationBlocked. Use skipError:true only after confirming failures are missing/deleted sources; skipped Legacy records remain unmigrated.

  • Breaking: strict system-model configuration validation — Legacy numeric strings, stringified priceTiers, and missing fields can now fail initialization or save validation. Run /api/admin/dataClean/cleanSystemModelConfigs with dryRun:true, review invalidSamples, then execute with dryRun:false. Cleaning converts valid numeric strings to numbers and priceTiers strings to arrays, removes invalid optional numerics, and applies defaults: LLM maxContext/maxResponse/quoteMaxToken become 16000/16000/13000, Embedding defaultToken/maxToken become 500/3000, and price becomes 0. The formal run rebuilds the model cache even when nothing changes; records that still fail the complete Schema are not written.

  • Breaking: manual HTTP tool schemas require migration — Manual-mode array parameters now use standard JSON Schema. Environments with manually created HTTP tools must run /api/admin/4160/initHttpToolSchema with dryRun:true, then dryRun:false. The retryable migration also processes matching historical app versions; a follow-up dry-run should show total.changedDocumentCount as 0. Only manual tools lacking apiSchemaStr are changed—OpenAPI-mode tools and other applications are skipped.

  • Upgrade value and who can skip — This is a substantive release, not a re-tag. Upgrade for shared Sandboxes, dataset metadata with .csv/.xlsx template and backup imports, chunked large-file uploads, AI-generated workflow/tool parameters, and fixes for S3/DOCX filenames containing spaces or special characters. Security-sensitive deployments should also upgrade because system-tool secrets are encrypted and system-model initialization no longer exposes API keys, request URLs, or internal configuration. Sandbox-free installations can skip initUserSandbox, and OpenAPI-only HTTP-tool users can skip initHttpToolSchema; after a clean model-config dry-run, users who need none of these features or fixes can defer upgrading.

1. 更新 Agent-sandbox-proxy 环境变量（可选）

4.16.0 需要依赖 proxy 进行静态资源代理访问，如果网关支持 ws 和 http 在同一个端口，则可以只开放一个端口。如果不支持，可以通过设置 PREVIEW_PORT 来设置 http 访问端口。

# ws和http服务的端口

# http服务的端口，可以覆盖 PORT
PREVIEW_PORT=1007

访问地址以 http:// 或 https:// 开头。单端口部署时，它可以与 AGENT_SANDBOX_PROXY_URL 指向同一域名和端口，但协议分别使用 HTTP(S) 和 WebSocket(S)。强烈建议配置的域名与 FastGPT 主站使用不同的 origin。同源部署会让这些脚本进入主站的同源安全边界，可能访问主站凭证或接口。系统当前不会强制检查 origin 是否隔离。

可以通过访问: https://{{host}}/health 来确认是否可访问。

4. 清洗历史系统模型配置

本版本开始在系统模型初始化及保存时使用严格 Schema。此前版本保存的数字字符串、字符串形式的价格梯度或缺失字段可能导致初始化校验失败。升级后请先执行 dry-run，查看需要处理的模型配置；dry-run 不会修改数据或刷新缓存：

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

确认 invalidSamples 中没有需要人工处理的数据后，执行正式清洗：

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

清洗会将合法数字字符串转换为 number、将字符串形式的 priceTiers 转换为数组，并删除非法的可选数字。非法或缺失的必填数字使用系统默认值：LLM 的 maxContext/maxResponse/quoteMaxToken 分别为 16000/16000/13000，Embedding 的 defaultToken/maxToken 分别为 500/3000，价格为 0。functionCall 保持可选，Embedding 缺失的 weight 补为 0。

正式执行会统一写入数据并立即刷新系统模型缓存；即使没有记录需要更新，也会重新构建运行时缓存。接口可安全重复执行；再次 dry-run 时，wouldUpdate 应为 0。无法通过当前完整模型 Schema 的记录不会写入，详情会全部返回在 invalidSamples 中。

5. 迁移 HTTP 工具数据

本版本将手动模式 HTTP 工具的数组参数改为标准 JSON Schema。升级前创建过手动 HTTP 工具的环境需要执行此迁移；OpenAPI 模式的 HTTP 工具无需迁移，脚本会自动跳过。

先执行 dry-run，查看当前应用及历史版本中的待处理数据。dry-run 不会修改数据：

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

确认结果后执行正式迁移：

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

脚本会先按 HTTP 工具类型筛选应用，再根据这些应用的 appId 迁移对应的历史版本。仅 apiSchemaStr 不存在的手动模式会被处理，其他应用及 OpenAPI 模式不会修改。迁移按批次执行且可安全重试；返回结果中 total.changedDocumentCount 表示发现的待处理文档数，正式执行后可再次 dry-run，确认该值为 0。

6. 迁移 Agent Sandbox 数据(较慢)

本版本将 App Chat 的 Agent Sandbox 从“每个对话一个实例”调整为“同一 App、同一用户共享一个实例”。不同对话的文件仍分别保存在 sessions/<chatId> 目录中，已发布 Skill 则统一保存在共享的 projects 目录中。

如果此前启用过 Agent Sandbox，必须按以下顺序完成旧 Workspace 迁移。未启用过 Agent Sandbox 的环境可以跳过本节。

先执行 dry-run，查看 beta6 Sandbox 字段归一化和旧 Skill Debug Chat 清理的待处理数。dry-run 不会创建资源、访问对象存储或修改数据：

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

查看 dry-run 结果后执行正式迁移。正式迁移会先执行 beta6 归一化，并且只在剩余待处理数归零时，才在同一请求中继续 Workspace 归档：

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

如果 failures 中仅包含 Sandbox source is missing or deleted，并且已确认对应 App 或 Skill 确实不再存在，可以显式跳过这些残留 Sandbox：

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false,"skipError":true}'

skipError 默认为 false，省略时保持严格迁移。该开关只跳过 source 已缺失或已软删除的整个分组，不会归档、删除或迁移其中的 Sandbox；跳过明细通过 skippedCount 和 skipped 返回。归档、对象存储、Provider 和并发控制等其他错误仍会阻断迁移。

迁移会先执行 V4.15.0-beta6 的完整前置逻辑：补齐旧 Sandbox 的 sourceType/sourceId、清理遗留字段、删除无法归属的孤立资源，并清理缺失 sourceType 的旧 Skill Debug Chat 三表数据及私有、公开 Bucket 旧前缀。与 App 同 ID 的 Skill 会跳过 Chat 清理。两类数据重新统计后合计为 normalization.pendingCount；数量不为 0 时不会进入 Workspace 归档。归零后直接归档全部旧 Workspace 并清理旧计算资源，再迁移 Skill，最后按 App、用户聚合到用户级 Sandbox。只要归档阶段存在失败，安装阶段就不会开始。新的 Sandbox 会在 Workspace 安装完成后暂停，首次使用时再按正常流程启动。脚本可安全重试，已完成的归档和迁移不会重复执行；迁移完成后会保留旧归档和旧 MongoDB 记录作为备份。

请检查返回结果中的 normalization.pendingCount、normalizationBlocked、failedCount、failures、skippedCount 和 skipped。只有 normalization.pendingCount 和 failedCount 均为 0，且 normalizationBlocked 为 false 时，才表示所有未跳过的 Sandbox 迁移完成；skipped 中的 Legacy 记录会保留且不会迁移。

🚀 新增内容

  1. Agent Sandbox 改为 App 用户级实例，同一 App、同一用户的多个对话复用 Sandbox，并通过独立 session 目录隔离各对话文件。
  2. Sandbox HTML 和文件支持通过短期只读链接直接预览，不再为预览重复上传到对象存储。
  3. App Workflow 在 Sandbox Provider 或运行时镜像变化时自动归档并恢复 Workspace，升级过程在当前运行中静默完成。
  4. 工作流工具节点支持将指定输入参数交由 Agent 自动生成，并保留固定值、引用和用户输入等既有配置。
  5. ChatAgent 选择工具时，支持手动指定是否为 AI 生成参数。
  6. 知识库数据支持自定义 metadata，可通过 API、CSV 或 Excel 模板导入 JSON 元数据；检索结果和备份导出会保留该字段。模板导入和备份导入均支持 .csv 和 .xlsx 文件，使用 q、a、index、metadata 表头；q、a、metadata 各一列，index 可多列且顺序任意。Excel 文件仅支持单个工作表且不能包含合并单元格，无法正确解析的 CSV 或 Excel 文件会提示文件格式异常。
  7. 大文件分块上传。
  8. 管理员配置系统工具密钥时，加密（兼容已配置的密钥）。
  9. 技能列表空状态引导，以及选择技能时联动。
  10. 工作流应用的系统配置移至画布左侧工具栏中的独立配置面板，新建工作流应用时会自动打开。
  11. 开场白支持独立配置多个预设问题，并可拖拽排序。

⚙️ 优化

  1. 重构 Agent Sandbox 生命周期和迁移流程，创建、暂停、归档、恢复、删除及 Provider 切换支持并发保护、断点续跑和幂等重试。
  2. Agent Sandbox 不可用或当前团队套餐不支持时，App Chat 自动禁用 Sandbox 能力，其他模型、工具、知识库和 Workflow 节点仍可继续运行。
  3. OpenSandbox 停止后可保留持久卷并在后续运行时复用；暂停和归档阈值支持通过环境变量配置。
  4. App 与 Skill 统一运行时镜像升级状态，Skill 编辑页可持续轮询升级结果。
  5. Sandbox 文件写入前自动创建父目录，避免写入嵌套路径失败。
  6. 优化工作流旧数据、工具参数等兼容问题。
  7. Agent Ask UI。
  8. 重构发布渠道页面，按原生渠道和第三方渠道分组展示，并显示各渠道已配置数量。
  9. 工具市场批量更新支持展示部分失败项、单独重试或卸载，并完善已安装版本和更新状态的展示。
  10. 门户页快捷应用数量上限调整为 3 个，并兼容已超出上限的历史配置。
  11. PDF 解析器动态边缘裁剪，而不是固定边缘裁剪，避免裁剪掉真实内容。

  8. 修复系统工具列表中已卸载工具的展示问题。

  14. 修复新建工作流应用时，国际化资源未预加载导致初始配置文案异常的问题。

  16. 修复应用发布后，文件变量无法上传文件的问题。
  17. 修复共享工作流工具的文件参数无法上传文件的问题。
  18. 修复 S3 对象键和文件名包含空格、%、#、?、斜杠等特殊字符时，可能导致上传、解析、预览或下载异常的问题。
  19. 修复系统默认模型未进行敏感信息过滤的问题，避免系统初始化接口响应返回模型 API Key、请求地址及内部配置。
