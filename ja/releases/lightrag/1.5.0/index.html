#ライトラグv1.5.0

主要な改善点

  • 🎉✨機能: LightRAG はマルチモーダル ドキュメント処理 をサポートし、ドキュメント内の画像、表、数式を最大限に活用してクエリに答えることができます。 RagAnything のすべてのマルチモーダル処理機能は LightRAG に統合されています。 (RagAnything は今後、コア機能のアップデートやメンテナンスを受信しなくなります)
  • ✨🎉機能: 文書処理パイプラインが完全にアップグレードされ、MinerU および Docling を使用したファイル コンテンツの解析と抽出がサポートされ、マルチモーダル コンテンツ分析およびエンティティ関係抽出とシームレスに統合されました。
  • 💡✨機能: LightRAG には ネイティブ解析 が導入され、DOCX ドキュメントから高品質のコンテンツ抽出が可能になります。 Word の自動番号付けの正確な再構築、画像、表、数式の抽出をサポートし、マルチモーダル コンテンツ分析およびエンティティ関係抽出とのシームレスな統合を提供します。 ネイティブ パーサーの拡張フォーマット サポートが近日中に提供される予定です。
  • 💡🧠機能: 選択可能な 4 つのテキスト チャンキング戦略: Fix、Recursive、Vector、および Paragraph が導入されました。 各チャンキング戦略のパラメーターは、環境変数を通じて構成できます。
  • 💡🎯機能: ファイル処理パイプラインは、ファイル拡張子またはファイルごとに基づいてファイル解析エンジンとテキスト チャンク戦略の選択をサポートします。詳しい使用方法については、FileProcessingPipeline.mdを参照してください。
  • 🚀⚡パフォーマンス: 各ファイル処理バッチが終了するまでベクトル計算を延期することにより、ベクトル ストレージ永続ロジックを最適化し、一元的な一括計算を可能にしました。 これにより、ベクター モデルの呼び出し数が大幅に削減され、サポートされているすべてのベクター DB LightRAG の更新/挿入速度が大幅に向上しました。
  • voyage-3、text-embedding-004、embed-multilingual-v3.0、jina-embeddings-v3 などの非対称モデルの タスク対応埋め込み サポートを有効にします。
  • LLM JSON 構造化出力 の導入により、エンティティ/リレーション抽出の信頼性が向上しました。有効にするには、ENTITY_EXTRACTION_USE_JSON=true を設定します。
  • ENTITY_TYPE_PROMPT_FILE を導入して、LLM 主導の エンティティ タイプ認識および抽出のための強化されたガイダンスをユーザーに提供します。
  • AWS Bedrock API で Amazon モデルと Anthropic モデルを完全にサポートします。
  • 🎯✨🎉機能: 役割固有の LLM 構成 サポートを実装し、EXTRACT、QUERY、KEYWORDS、および VLM という 4 つの異なる役割を導入し、それぞれ独立した LLM 設定を持ちます。クエリ待機時間を最適化するために、KEYWORDS ロールを小さなパラメーターの非推論高速モデルで構成することをお勧めします。精度とスループットのバランスをとるため、中パラメータの非推論モデルを使用した EXTRACT ロール。もう 1 つは、クエリの品質を向上させるための大きなパラメーターの推論モデルを備えた QUERY ロールです。詳しい使用手順については、RoleSpecificLLMConfiguration.md を参照してください。

何が壊れているのか

  • 💥警告: データの移行とシステムの再起動によりサービス停止が長引く可能性があるため、現在 OpenSearch および MongoDB グラフ ストレージを利用しているユーザーはアップグレードを慎重に計画する必要があります。
  • ⚠️**ENTITY_TYPES 環境変数は非推奨になりました**。この新しいバージョンを起動する前に、ENTITY_TYPE_PROMPT_FILE に置き換えてください。
  • 💔非推奨のフィールドを削除: lightrag/base.py から QueryParam.model_func を削除
  • 3.3.0 より前の OpenSearch バージョンの場合は、LightRAG をアップグレードする前に OpenSearch をアップグレードしてください (https://github.com/HKUDS/LightRAG/pull/2991 を参照)。
  • ⚠️delete_entity/delete_relation をドキュメント API からグラフ API に移動します

|前 |後 | | ----------------------------------- | ------------------------------- | | DELETE /documents/delete_entity | DELETE /graph/entity/delete | | DELETE /documents/delete_relation | DELETE /graph/relation/delete |

LightRAG v1.5.0

Highlights

  • Multimodal + document-pipeline overhaul — The headline change: RAG-Anything's full multimodal stack is merged into LightRAG, so images, tables, and formulas in documents are now usable for queries. Parsing is rebuilt around MinerU and Docling plus a new Native Parser for DOCX (accurate auto-numbering reconstruction, image/table/formula extraction), and file parsing engine + chunking strategy can be chosen per-extension or per-file. Migration note: RAG-Anything will get no further core updates, and its embedded fallbacks were removed (PR #2997), so anyone depending on the standalone project or those fallbacks must move to LightRAG's pipeline. This alone justifies the upgrade for anyone needing multimodal retrieval.

  • Role-specific LLM configuration and new tuning knobs — LLM settings are now split into four independent roles — EXTRACT, QUERY, KEYWORDS, VLM (see docs/RoleSpecificLLMConfiguration.md). Guidance: small non-reasoning model for KEYWORDS (latency), medium non-reasoning for EXTRACT, large reasoning for QUERY. Alongside this come four selectable chunking strategies — Fix, Recursive, Vector, Paragraph — configured via environment variables, task-aware embeddings for asymmetric models (voyage-3, text-embedding-004, embed-multilingual-v3.0, jina-embeddings-v3), JSON-structured entity extraction via ENTITY_EXTRACTION_USE_JSON=true, and ENTITY_TYPE_PROMPT_FILE. Worth upgrading if you care about query latency/quality tuning.

  • Breaking changes requiring a migration plan — This release is not drop-in. ENTITY_TYPES is deprecated in favor of ENTITY_TYPE_PROMPT_FILE (replace before launch); QueryParam.model_func was removed from lightrag/base.py; and delete endpoints moved from the document API to the graph API — DELETE /documents/delete_entity → DELETE /graph/entity/delete and DELETE /documents/delete_relation → DELETE /graph/relation/delete. OpenSearch users below 3.3.0 must upgrade OpenSearch first (PR #2991), and OpenSearch/MongoDB graph-storage users face potential extended outages from data migration and restarts. Bedrock config was renamed aws_bedrock → bedrock with BindingOptions support (PR #2966) — update your config keys.

  • Ingest performance and provider hardening — Vector persistence now defers computation to the end of each file-processing batch for centralized bulk upsert, cutting vector-model invocations and speeding up upserts across all supported vector DBs; Postgres adds a binary parameter for vector similarity queries (PR #2949). Amazon and Anthropic models on AWS Bedrock are fully supported, and there's a batch of reliability fixes (LLM client/stream cleanup, role-cache isolation, parser-routing and DOCX idempotency fixes). Compelling for large-scale ingestion and Bedrock/Gemini deployments.

  • Verdict — Upgrade if you need multimodal processing, per-role LLM tuning, or faster bulk ingest, and you can absorb the config/API migration. Skip or delay if you're on OpenSearch/MongoDB graph storage without a maintenance window, or still rely on ENTITY_TYPES, QueryParam.model_func, or the old /documents/delete_* endpoints — migrate those first. This is a substantial feature release with genuine breaking changes, not a no-op or metadata-only re-tag.

Major Improvements

  • 🎉✨Feacture: LightRAG now supports multimodal document processing and can fully leverage images, tables, and formulas within documents to answer queries. All RagAnything’s multimodal processing capabilities are merged into LightRAG; ( RagAnything will no longer receive core feature updates or maintenance going forward)
  • ✨🎉Feacture: Fully upgraded the document processing pipeline, with support for using MinerU and Docling to parse and extract file content, seamlessly integrating with multimodal content analysis and entity-relationship extraction.
  • 💡✨Feacture: LightRAG now introduces Native Parsing, enabling high-quality content extraction from DOCX documents. It supports accurate reconstruction of Word auto-numbering, as well as extraction of images, tables, and formulas, providing seamless integration with multimodal content analysis and entity-relationship extraction. Expanded format support for the Native Parser is coming soon.
  • 💡🧠Feacture: Introduced four selectable text chunking strategies: Fix, Recursive, Vector, and Paragraph. The parameters for each chunking strategy can be configured through environment variables.
  • 💡🎯Feacture: The file processing pipeline supports selecting the file parsing engine and text chunking strategy either based on file extensions or on a per-file basis. For detailed usage instructions, refer to FileProcessingPipeline.md.
  • 🚀⚡Performance: Optimized the vector storage persistence logic by deferring vector computations until the end of each file processing batch, enabling centralized bulk computation. This significantly reduced the number of vector model invocations and significantly enhance the upsert speed of all vector DB LightRAG supported.
  • Enable task-aware embedding support for asymmetric models, including voyage-3, text-embedding-004, embed-multilingual-v3.0, and jina-embeddings-v3.
  • Improved entity/relation extraction reliability by introducing LLM JSON-structured output; set ENTITY_EXTRACTION_USE_JSON=true to enable it.
  • Introduce ENTITY_TYPE_PROMPT_FILE to empower users with enhanced guidance for LLM-driven entity type recognition and extraction.
  • Fully support Amazon and Anthropic models on AWS Bedrock API.
  • 🎯✨🎉Feacture: Implemented role-specific LLM configuration support, introducing four distinct roles: EXTRACT, QUERY, KEYWORDS, and VLM, each with independent LLM settings. It is recommended to configure the KEYWORDS role with a small-parameter, non-reasoning, high-speed model to optimize query latency; the EXTRACT role with a medium-parameter, non-reasoning model to balance accuracy and throughput; and the QUERY role with a large-parameter reasoning model to enhance query quality. For detailed usage instructions, refer to RoleSpecificLLMConfiguration.md.
