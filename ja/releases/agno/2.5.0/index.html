#アグノv2.5.0 #Changelog

新機能

  • チーム実行モード: 4 つの実行モードを備えた TeamMode 列挙型が導入されました。
    • coordinate (デフォルト): リーダーがメンバーを選択し、タスクを作成し、応答を合成するスーパーバイザー パターン
    • route: リーダーが専門家にルーティングし、その応答を直接返すルーター パターン
    • broadcast: リーダーが同じタスクをすべてのメンバーに同時に委任するブロードキャスト パターン
    • tasks: リーダーが目標を共有タスク リストに分解する自律的なタスクベースの実行
  • Teams 向けヒューマンインザループ (HITL): 一時停止した実行のための RunRequirement システムが改善され、以下のサポートが向上しました。 ・ツールの確認フロー
    • スキーマ検証によるユーザー入力の収集
    • 外部ツールの実行
  • 承認システム: 人間による承認ワークフローのための新しい @approval デコレータ:
    • @approval(type="required"): 承認をブロックし、承認 API によって解決されるまで実行を一時停止します。
    • @approval(type="audit"): コンプライアンス/ロギングのためのノンブロッキング監査証跡
    • ステータス追跡付きの永続的な承認レコード (保留中、承認済み、拒否、期限切れ、キャンセル)
    • 承認リスト、検査、解決のための承認 API
  • スケジューラー: 再試行、タイムアウト、およびタイムゾーンのサポートを備えた、エージェント、チーム、およびワークフローの Cron ベースのスケジューリング。
  • LearningMachine for Teams: 永続的な学習のための LearningMachine のサポートを追加しました。
  • ツール、ナレッジ、およびメンバーの呼び出し可能なファクトリ: ツール、ナレッジ、およびチーム メンバーを、RunContext へのアクセスにより実行時に解決される呼び出し可能なファクトリとして定義できるようになりました。 cache_callables によるキャッシュと、セッション スコープの解決のためのカスタム キャッシュ キーをサポートします。
  • インフラ: AWS EFS のサポートを追加
  • 知識の分離: isolate_vector_search flag を知識クラスに追加しました。有効にすると、ドキュメントの挿入中に linked_to メタデータがタグ付けされ、検索がこのタグでフィルタリングされ、分離された検索結果を維持しながら、複数のナレッジ インスタンスが同じベクトル データベースを共有できるようになります。既存のデータとの下位互換性を確保するため、デフォルトは False です。

改善点

  • エージェント/チームのリファクタリング: 懸念事項をより明確に分離するための、エージェント クラスとチーム クラスの主要な内部リファクタリング。

バグ修正:

  • LanceDb Cloud: テーブルを再度開かないよう search() を修正しました。ベクトル/ハイブリッド/キーワード検索では、.to_pandas() の代わりに .to_list() を使用します。
  • 主キー制約: _unique_constraints の代わりに主キーを使用するように、sessions、component_configs、および component_links テーブルを修正しました。

重大な変更

  • store_history_messages のデフォルトは False になりました: 履歴メッセージはデフォルトでは保存されなくなりました。これにより、不必要なストレージのオーバーヘッドが削減され、明示的に必要な場合を除き会話履歴を保持しないことでプライバシーが向上し、ストレージ コストをより適切に制御できるようになります。保存された履歴に依存する場合は、store_history_messages=True を明示的に設定します。
  • ナレッジの一意性: ナレッジ インスタンスには、データベース、テーブル、ナレッジ名の一意の組み合わせが必要になりました。データの競合を防ぐために、個別の名前がなければ、複数のナレッジ インスタンスが同じテーブルを共有することはできません。

agno v2.5.0

Changelog

New Features

  • Team Execution Modes: Introduced TeamMode enum with four execution modes:
    • coordinate (default): Supervisor pattern where the leader picks members, crafts tasks, and synthesizes responses
    • route: Router pattern where the leader routes to a specialist and returns their response directly
    • broadcast: Broadcast pattern where the leader delegates the same task to all members simultaneously
    • tasks: Autonomous task-based execution where the leader decomposes goals into a shared task list
  • Human-in-the-Loop (HITL) for Teams: Improved RunRequirement system for paused runs with better support for:
    • Tool confirmation flows
    • User input collection with schema validation
    • External tool execution
  • Approval System: New @approval decorator for human approval workflows:
    • @approval(type="required"): Blocking approval that pauses the run until resolved via approvals API
    • @approval(type="audit"): Non-blocking audit trail for compliance/logging
    • Persistent approval records with status tracking (pending, approved, rejected, expired, cancelled)
    • Approvals API for listing, inspecting, and resolving approvals
  • Scheduler: Cron-based scheduling for agents, teams, and workflows with retry, timeout, and timezone support.
  • LearningMachine for Teams: Added support for LearningMachine for persistent learning.
  • Callable Factories for Tools, Knowledge, and Members: Tools, knowledge, and team members can now be defined as callable factories that are resolved at runtime with access to RunContext. Supports caching via cache_callables and custom cache keys for session-scoped resolution.
  • Infra: Adds support for AWS EFS
  • Knowledge Isolation: Added isolate_vector_search flag to Knowledge class. When enabled, documents are tagged with linked_to metadata during insert and searches filter by this tag, allowing multiple Knowledge instances to share the same vector database while maintaining isolated search results. Defaults to False for backwards compatibility with existing data.

Improvements

  • Agent/Team Refactor: Major internal refactor of Agent and Team classes for cleaner separation of concerns.

Bug Fixes:

  • LanceDb Cloud: Fixed search() to stop reopening the table; use .to_list() instead of .to_pandas() in vector/hybrid/keyword search.
  • Primary key constraint: Fixed sessions, component_configs and component_links table to use primary key instead of _unique_constraints.

Highlights

  • Team execution modes — TeamMode replaces the one-size-fits-all supervisor loop with four topologies: coordinate (default leader-led synthesis), route (leader hands off to a single specialist and returns its answer verbatim), broadcast (same task fanned out to every member), and tasks (leader decomposes goals into a shared task list). This is the headline of the v2.5 Agent/Team refactor (PRs #6429, #6506, #6511, #6514, #6515). route is your lever for cutting latency and token spend when you don't need synthesis; tasks is the one to watch for long-running autonomous work.

  • First-class approvals — The new @approval decorator offers type="required" (pauses the run until resolved through the approvals API) and type="audit" (non-blocking trail for compliance), with persistent records tracking pending/approved/rejected/expired/cancelled and a paginated listing/resolution API (PR #6526). If you hand-rolled HITL gating on RunRequirement, this is the migration path — but note that "required" approvals now genuinely block execution, so any unattended pipeline needs a resolver wired up or it will stall.

  • Scheduler — Cron-based scheduling is built into agents, teams, and workflows with retry, timeout, and timezone support, so you can drop external cron wrappers. Watch the AgentOS integration landmines fixed here: a scheduler property setter conflict (#6520) and a double MCP lifespan (#6522). If you already expose a scheduler property on your AgentOS app, test that path specifically before upgrading.

  • Callable factories for tools, knowledge, and members — These can now be declared as callables resolved at runtime with access to RunContext, with cache_callables and custom cache keys enabling session-scoped resolution. The practical win is per-tenant or per-session configuration without rebuilding the whole agent graph; the risk is that a poorly chosen cache key can leak one session's resolved tools or knowledge into another.

  • Knowledge isolation and uniqueness — isolate_vector_search (PR #6519) tags documents with linked_to metadata on insert and filters searches by that tag, letting multiple Knowledge instances share one vector database without cross-contamination; it deliberately defaults to False to protect existing data. Pair this with the new breaking uniqueness rule: the database/table/name combination must be unique, so two Knowledge instances on the same table now require distinct names or they conflict. Combined with AgentOS's new select-Knowledge-by-name (#6287), instance names become semantically meaningful rather than cosmetic.

  • History storage now off by default — store_history_messages defaults to False, so conversation history is no longer persisted unless you opt in. The upside is lower storage cost and better privacy; the gotcha is a silent behavioral change for anything that reads history back (audits, debugging, continuation logic). Set store_history_messages=True explicitly if your app depends on it.

Breaking Changes

  • store_history_messages now defaults to False: History messages are no longer stored by default. This reduces unnecessary storage overhead, improves privacy by not persisting conversation history unless explicitly needed, and gives better control over storage costs. If you rely on stored history, set store_history_messages=True explicitly.
  • Knowledge Uniqueness: Knowledge instances now require a unique combination of database, table, and knowledge name. Multiple Knowledge instances cannot share the same table without distinct names to prevent data conflicts.
