#アグノv3.1.4

#Changelog

新機能:

  • サンドボックス化されたハーネス エージェント: ClaudeAgent および CodexAgent は sandbox= パラメーターを受け取り、ホスト上ではなく分離されたセッションごとのコンピューター内でハーネス プロセス全体を実行します。セッション状態は、コンテナー、ホスト、または最後に実行されたレプリカを失っても存続します。保持する新しいクラスはありません: ClaudeAgent(id="coder", db=PostgresDb(...), sandbox=DockerSandbox("agno-sandbox:local", network="isolated")) がセットアップ全体であり、エージェントは最初の使用時に PostgresDb からコーディネーターを構築します。各ターンは、エージェントの Postgres (<session_table>_sandbox_bindings、初回使用時に作成) のリース行を通じてセッションを要求し、セッションの最後にコミットされたチェックポイント (ワークスペースとハーネス独自の会話ファイル) から復元された計算を開始し、ターンを実行してから、新しいチェックポイントをキャプチャして検証し、1 つのトランザクションで実行行と回復ポイントを公開します。キャンセルまたは失敗したターンでは何も公開されず、前のチェックポイントが回復ポイントのままになります。ターンは、検証できない状態で続行を拒否します。最後のチェックポイントでコミットされたネイティブ会話 ID (クロード セッション ID、コーデックス スレッド ID) を渡し、それを失った復元は、新しい会話をサイレントに開始するのではなく、モデルが実行される前に native_state_missing で失敗します。型指定されたハーネス設定は、JSON としてランタイムに送信されます。ホストのみの設定 (cwd、retries、env、ネイティブ オプション オブジェクト) は、構築時に名前によって拒否されます。 require_native_resume および strict_persistence は BaseExternalAgent の新しいオプションであり、agno[claude] / agno[codex] インストール エクストラはハーネス SDK をカバーします。 クックブック を参照してください。 (#11028、#11043、#11056、#11057)
  • Docker サンドボックス: DockerSandbox は顧客が運営するプロバイダーです。コンテナーは、読み取り専用イメージ ファイル システム、削除された機能、特権昇格なし、CPU、メモリ、およびプロセスの制限、/workspace および /runtime の制限付き tmpfs、ホストまたは Docker ソケット マウントなし、明示的に構成された環境値とハーネスのモデル API キーのみを備えた UID 1000 として実行されます。ネットワークのデフォルトは none です。 network="isolated" はコンテナ間のトラフィックをオフにしたマネージド ブリッジを提供し、subnet= はその範囲を選択します。決定論的なセッションと世代のアイデンティティは、作成の競合と失われた応答を調和させます。コマンドが自動的に再試行されることはありません。 pause / resume はカーネル フリーザを通じて提供され、DockerCheckpointTransfer はチェックポイントを出入りします。 cookbook/frameworks/sandbox/build_image.py はランタイム イメージをビルドします。 クックブックを参照してください。 (#10975、#11028)
  • Amazon Bedrock AgentCore Sandbox: AgentCoreSandbox は、Docker 転送の隣に AgentCoreCheckpointTransfer を持つ同じコントラクトを AgentCore ランタイムに実装します。各サンドボックス世代は、Firecracker microVM の 1 つの AgentCore ランタイム セッションです。 create は、名前空間、エージェント、セッション、および世代から派生したセッション ID を通じて冪等です。ポート 8080 のルート サーバーは、microVM を要求し、UID 1000 としてランタイムを開始し、その後のすべての操作を要求された構成とランダムな具体化でフェンスして、古いハンドルが後の要求で動作しないようにし、開始呼び出しとポーリング呼び出しを転送し、/workspace で UID 1000 にドロップするガードの背後でコマンドを実行します。チェックポイントは、キャプチャおよび復元中に UID 1000 プロセスを停止し、最大 2 GiB のチャンクで InvokeAgentRuntime を移動します。一時停止はサポートされておらず、AgentCore セッション ストレージは使用されません。プロバイダー パッケージは agno.sandbox.docker および agno.sandbox.agentcore に移動されました。 DockerCheckpointTransfer は agno.sandbox.docker からインポートされるようになりました。このランタイムには、Docker にも適用される 2 つの Codex 修正も追加されました。CODEX_HOME が作成され、チェックポイントで auth.json が除外されるため、一致する格納されたログインがない場合に OPENAI_API_KEY から Codex をログインします。 cookbook/frameworks/sandbox/agentcore/agentcore_setup.py は、ランタイムをビルド、プッシュ、デプロイします。 クックブックを参照してください。 (#11050)
  • ウォーム サンドボックス ターン: コーディネーターは、セッションのコンピュータを破壊するのではなく、ターン後に warm_computer_seconds (デフォルト 300) の間保持します。Docker で一時停止し、AgentCore でアイドル状態のままにします。そのウィンドウ内の次のターンではそれが再開されますが、何も復元されません。それ以外の場合は、古いコンピュータを廃棄し、チェックポイントから復元された新しい世代でコールド パスを使用します。チェックポイントはターンごとにキャプチャされるため、ウォームコンピュータはチェックポイントがすでに保持している状態へのショートカットにすぎません。完了した実行ごとの metadata.sandbox.resumed は、そのターンがどのパスを通過したかを示し、コーディネーターの retire_computer / sweep_warm は、セッションが戻らなかったコンピューターを削除します。 Docker のライブでは、8.2 の冷たさに対して、温かいクロードのターンが 4.6 をとりました。 AgentCore 3.3 と 8.2 の比較。 クックブックを参照してください。 (#11088)
  • AgentOS を介したサンドボックス: サンドボックス エージェントの POST /agents/{agent_id}/runs は、新しいエンドポイントなしでフォアグラウンド、ストリーミング、およびバックグラウンドのリクエストを永続キューに送信します。 Idempotency-Key 再試行では同じ実行が返されますが、別のセッション、入力、オプション、または添付バイトでは 409 が返されます。 Clients は /runs/{run_id}/resume (last_event_index) で再接続し、レプリカ間を含めて /runs/{run_id}/cancel でキャンセルします。別のレプリカで解決されたキャンセルは、実行がキャンセルされたものとして記録され、実行行でのユーザーの順番が維持されます。サンドボックス エージェントに調整する Postgres がない場合、AgentOS は起動時に失敗し、キュー ワーカーがアクティブになるとホスト ローカルのデフォルト チェックポイント ストアを拒否し、起動時および送信前に各サンドボックス エージェントのバインディング テーブルを検証して、以前のビルドのテーブルに対する救済策を指定します。 クックブックを参照してください。 (#11043、#11105)
  • サンドボックス エージェントの添付ファイル: サンドボックス ClaudeAgent または CodexAgent 上の run / arun は images= および files= を受け入れ、AgentOS の実行ルートはそれらをアップロードとして受け入れます。サンドボックスに送信されるのはバイトのみです。各添付ファイルは永続書き込みの前に検証およびエンコードされ、ハーネス独自のステージングによって /workspace/.agno/uploads/<run_id>/ の下でステージングされ、ターンのチェックポイントに保持されるため、後で電源を入れた新しいコンピュータでもファイルを読み取ることができます。リクエストには最大 16 個の添付ファイルと合計 512 KiB が含まれます。 URL、メディア参照、サーバー ファイル パス、オーディオおよびビデオは拒否されます。キューに入れられた実行では送信の添付ファイルが保存されるため、再試行すると同じバイトが送信されます。 クックブックを参照してください。 (#10990、#11091)
  • クロード コード用の画像と PDF インライン: ClaudeAgent は、添付された画像 (PNG、JPEG、GIF、WEBP) および PDF を、クロードの読み取りツール用にディスクに書き込むだけでなく、コンテンツ ブロックとしてメッセージ内に最大 4 MiB 送信するようになりました。これは、エージェント SDK のストリーミング入力の形式となります。クロードは画像を直接確認し、ファイルを読み戻すことはありません。これにより、ファイル全体が Base64 として返され、数百 KB の画像に対して SDK の 1 MiB メッセージ バッファとサンドボックスの 256 KiB イベント フレームがオーバーフローしていました。ファイルがインラインになるかどうかはそのバイト数に基づいて決定されるため、ラベルが間違っているファイルはファイル ツールのディスク上に残ります。他のファイルと大きなイメージは読み取りパスを保持します。 クックブックを参照してください。 (#11115)
  • セッションごとのキュー: 1 つのセッションでの永続的なバックグラウンド実行が、コンポーネントごとに送信順に一度に 1 つずつ実行されるようになりました。各チケットには店舗が割り当てた session_seq が記載されています。チケットは、セッション内の兄弟が実行中または一時停止中でなく、以前の兄弟がまだキューに入っていないときにのみ要求されるため、待機中のチケットは試行もワーカー スロットも消費しません。 max_concurrency 内では、異なるセッションが同時に実行されます。一時停止された実行はセッションを保持し、続行または再試行された実行はその場所を保持し、PENDING の実行ポーリングでは、背後でブロックされた実行とともに waiting_on が伝えられます。 QueueConfig.queue_per_session (デフォルトはオン) がそれを制御し、外部エージェントは関係なくシリアル化され、GET /config が有効な設定を報告します。 クックブックを参照してください。 (#9587)
  • インスタント永続送信:永続送信を受け入れるレプリカは、チケットのコミット後に独自のキュー ワーカーをウェイクアップするため、次のポーリングまで poll_interval まで待つのではなく、ミリ秒単位で実行が開始されます。飽和したレプリカはスロットの解放時に起動し、ピアは引き続き独自のポーリングでジョブを選択します。耐久性は変更されません。行は誰かが目覚める前にコミットされます。 (#9667)
  • ChartTools: 単一の create_chart ツールを備えた新しいツールキット。チャート ペイロード (bar、line、area、pie、bar-horizontal、bar-stacked、area-stacked) を検証し、Agno OS がレンダリングできる準備の整ったフェンスで囲まれたチャート ブロックを返し、ユーザーが実行する必要があったスキーマ プロンプトを置き換えます。検証の失敗はモデルに何を修正すべきかを指示し、ツールキットには独自の指示が同梱されるため、エージェントが必要とするのは tools=[ChartTools()] だけです。 クックブックを参照してください。 (#8295)

改善点:

  • Db-Backed および Factory コンポーネントの永続キュー: コンポーネント API を通じて作成されたコンポーネント上でのバックグラウンド実行、バージョン固定実行、および AgentFactory / TeamFactory / WorkflowFactory での送信は、受け入れ側レプリカ上の切り離されたタスクにドロップされるのではなく、永続キューに乗るようになりました。受け入れエンドポイントはチケットに解決スコープ (ソース、所有者、バージョン、ファクトリの場合は trusted クレームとファクトリ入力) をスタンプし、ワーカーはクレーム時にその解決を再生します。ワーカー上で ctx.request を読み取るファクトリは、ライブ リクエストがチケットに乗ることができないため、修正を指定するメッセージが表示されて実行に失敗します。工場出荷時の実行読み取りルートは、すべてのポーリングで 400 と回答しなくなりました。 クックブック を参照してください。 (#9796、#11045)
  • Codex 権限ポリシーの名前付け: sandbox= はプロバイダーを使用するようになったため、CodexAgent(sandbox="read-only") は Codex 独自の構成キーに一致する sandbox_mode に名前変更されました。古い文字列形式は依然として DeprecationWarning で機能します。 (#11043)
  • サンドボックス クックブック: cookbook/frameworks/sandbox/ は docker/ フォルダーと agentcore/ フォルダーに分割されており、それぞれにプロバイダー、チェックポイント、コーディネーター、リカバリ、キャンセル、添付ファイル、ウォーム ターン、および AgentOS をカバーする独自の README とテスト ログが含まれています。 build_image.py は、構築されたタグをイメージ ストアにロードし、そこにあることを確認します。 (#11050、#11081、#11105)
  • Gemini Cookbook: 現在のモデルと API に更新されました。 (#11038)

バグ修正:

  • サンドボックス チェックポイントの復元: docker cp --archive がコンテナのユーザーを名前として解決するようデーモンに要求するため、サンドボックス セッションの 2 ターンごとに getent unable to find entry "1000:1000" in passwd database が失敗しました。復元では、アーカイブ モードを使用せずにコピーし、復元されたすべてのエントリを 1000:1000 自体に固定するようになりました。 (#11094)
  • サンドボックス ストアおよびコーディネーター: 同じ実行のワーカー クレームと競合するキュー キャンセルが、ロック順序でデッドロックする可能性があります。停止パスはセッションを取得し、他のすべてのストア トランザクションと同じ順序で実行およびバインドします。 DockerSandbox を介した同期呼び出しでは、呼び出しごとに HTTP client がリークしました。キャンセルされたサンドボックス実行では、キューが予期する EXECUTING キャンセル ステージが記録されるようになりました。クリーンアップとコミットの間に終了マークが付けられた実行は、finalizing のバインディングを離れる代わりに停止パスを通過し、長いプロバイダー呼び出しによってリースが延長されます。 (#11057、#11092)
  • サンドボックス送信: user_id を使用せずに作成されたセッションに user_id を送信したり、その逆を行うと、キャンセルされたジョブが残された 500 ではなく、チケットが存在する前に 404 が応答されます。実行行が存在する前にジョブが失敗したフォアグラウンド リクエストは、チケットのエラーを 503 ではなく 500 として返し、client に再接続を要求します。 (#11105)
  • WebSocket Tails: 永続キューを使用すると、ワークフロー実行が WebSocket 経由でストリーミング中に 2 番目のメッセージを送信したチャット client が、最初の実行のイベントの取得を停止しました。テール ポンプは (ソケット、ラン) ごとにキー付けされるようになり、再サブスクライブによりそのランのポンプのみが置き換えられ、ソケットは最大 32 のランを接続できます。 (#11039)
  • API ドキュメントの順序: ファイルシステム ルートは、セットアップおよび再同期時にデータベース ルートの後に登録されるため、生成される API ドキュメントにはそれらが順番にリストされます。 (#11099)
  • テスト: WebSocket ファクトリ ワークフロー テストは、ファクトリの送信が永続キューに乗り始めた後、作成されたインライン パスを固定します。 (#11106)

agno v3.1.4

Highlights

  • Durable sandboxed harness agents — ClaudeAgent and CodexAgent now accept sandbox= providers and coordinate execution through Postgres leases, preserving workspace and native conversation state across container, host, or replica loss. Checkpoint verification and run publication happen atomically; a restore missing the committed Claude session ID or Codex thread ID fails with native_state_missing before inference rather than silently starting a new conversation. Host-only options such as cwd, retries, env, and native option objects are rejected at construction; install the agno[claude] or agno[codex] extras (#11028, #11043, #11056, #11057).

  • Sandbox providers and migration notes — DockerSandbox defaults to networking disabled and runs as UID 1000 with a read-only filesystem, dropped capabilities, resource limits, and no host or Docker-socket mounts; network="isolated" enables a restricted bridge. AgentCoreSandbox uses Firecracker microVMs and idempotent runtime sessions, with chunked checkpoints up to 2 GiB, but does not support pause. Imports must move to agno.sandbox.docker or agno.sandbox.agentcore (including DockerCheckpointTransfer), while Codex’s old sandbox="read-only" form still works with a DeprecationWarning—use sandbox_mode now that sandbox= selects a provider (#10975, #11043, #11050).

  • Warm sandbox turns reduce restart latency — Computers now remain warm for warm_computer_seconds (default 300): Docker pauses them and AgentCore leaves them idle, allowing the next turn to resume without checkpoint restoration. Checkpoints are still captured after every turn, so warm state is only a performance shortcut; use metadata.sandbox.resumed to identify the execution path and retire_computer / sweep_warm to reclaim abandoned computers. Reported latency fell from 8.2 seconds cold to 4.6 seconds on Docker and 3.3 seconds on AgentCore (#11088).

  • AgentOS gains durable sandbox lifecycle support — Existing /agents/{agent_id}/runs endpoints route sandboxed foreground, streaming, and background work through the durable queue without new endpoints. Idempotency-Key retries return the original run, while changed inputs return 409; clients can reconnect with last_event_index or cancel across replicas. Deployment now requires Postgres for sandbox coordination: AgentOS fails at startup without it, rejects the host-local checkpoint store once a queue worker is active, and validates binding tables before accepting submissions (#11043, #11105).

  • Per-session serialization becomes the default — Durable background runs execute at most one at a time per session, in submission order, via QueueConfig.queue_per_session=True; external agents are serialized even when this setting is disabled. Paused, continued, and retried runs retain their place without consuming attempts or worker slots, while different sessions remain concurrent up to max_concurrency. DB-backed, version-pinned, and factory components now use the durable queue with local-worker wake-on-submit; factories that read ctx.request during worker execution will fail because the live request cannot be serialized (#9587, #9667, #9796, #11045).

  • Checkpointed attachments and safer Claude media handling — Sandboxed run / arun calls and AgentOS uploads accept validated image/file bytes, stage them under /workspace/.agno/uploads/<run_id>/, and retain them in the turn checkpoint, with a 16-attachment and 512 KiB total limit; URLs, media references, server paths, audio, and video are refused. ClaudeAgent also sends recognized images and PDFs up to 4 MiB inline as content blocks—subject to the sandbox limit when sandboxed—avoiding base64-heavy disk reads that could overflow SDK message or sandbox event buffers; oversized, unsupported, or mislabelled files remain on disk for file tools (#10990, #11091, #11115).

Changelog

New Features:

  • Sandboxed Harness Agents: ClaudeAgent and CodexAgent take a sandbox= parameter and run the whole harness process inside an isolated, per-session computer instead of on the host, with session state that survives losing the container, the host or the replica that ran the last turn. No new classes to hold: ClaudeAgent(id="coder", db=PostgresDb(...), sandbox=DockerSandbox("agno-sandbox:local", network="isolated")) is the whole setup, and the agent builds its coordinator from its PostgresDb on first use. Each turn claims the session through a lease row in the agent's Postgres (<session_table>_sandbox_bindings, created on first use), starts compute restored from the session's last committed checkpoint (workspace plus the harness's own conversation files), runs the turn, then captures and verifies a new checkpoint and publishes the run row and recovery point in one transaction. A cancelled or failed turn publishes nothing and the previous checkpoint stays the recovery point. The turn refuses to continue on state it cannot verify: it passes the native conversation id (Claude session id, Codex thread id) committed with the last checkpoint, and a restore that lost it fails with native_state_missing before the model runs instead of silently starting a new conversation. Typed harness settings travel to the runtime as JSON; host-only settings (cwd, retries, env, native option objects) are rejected by name at construction. require_native_resume and strict_persistence are new options on BaseExternalAgent, and agno[claude] / agno[codex] install extras cover the harness SDKs. See cookbook. (#11028, #11043, #11056, #11057)
  • Docker Sandbox: DockerSandbox is the customer-operated provider. Containers run as UID 1000 with a read-only image filesystem, dropped capabilities, no privilege escalation, CPU, memory and process limits, bounded tmpfs for /workspace and /runtime, no host or Docker socket mounts, and only explicitly configured environment values plus the harness's model API key. Networking defaults to none; network="isolated" gives a managed bridge with inter-container traffic off, and subnet= picks its range. Deterministic session and generation identity reconciles creation races and lost responses; commands are never retried automatically. pause / resume are provided through the kernel freezer, and DockerCheckpointTransfer moves checkpoints in and out. cookbook/frameworks/sandbox/build_image.py builds the runtime image. See cookbook. (#10975, #11028)
  • Amazon Bedrock AgentCore Sandbox: AgentCoreSandbox implements the same contract on AgentCore Runtime, with AgentCoreCheckpointTransfer next to the Docker transfer. Each sandbox generation is one AgentCore runtime session in a Firecracker microVM; create is idempotent through a session id derived from the namespace, agent, session and generation. A root server on port 8080 claims the microVM, starts the runtime as UID 1000, fences every later operation with the claimed configuration and a random incarnation so a stale handle can never act on a later claim, forwards start and poll calls, and runs commands behind a guard that drops to UID 1000 in /workspace. Checkpoints stop UID 1000 processes during capture and restore and move through InvokeAgentRuntime in chunks, up to 2 GiB. Pause is not supported and AgentCore session storage is not used. The provider packages moved to agno.sandbox.docker and agno.sandbox.agentcore; DockerCheckpointTransfer now imports from agno.sandbox.docker. The runtime also gained two Codex fixes that apply to Docker as well: it creates CODEX_HOME, and it logs Codex in from OPENAI_API_KEY when no stored login matches, since checkpoints exclude auth.json. cookbook/frameworks/sandbox/agentcore/agentcore_setup.py builds, pushes and deploys the runtime. See cookbook. (#11050)
  • Warm Sandbox Turns: The coordinator keeps a session's computer for warm_computer_seconds (default 300) after a turn instead of destroying it: paused on Docker, left idle on AgentCore. The next turn inside that window resumes it and restores nothing; otherwise it retires the old computer and takes the cold path on a fresh generation restored from the checkpoint. The checkpoint is still captured after every turn, so a warm computer is only a shortcut to the state the checkpoint already holds. metadata.sandbox.resumed on every completed run says which path the turn took, and retire_computer / sweep_warm on the coordinator remove computers that sessions never came back for. Live on Docker a warm Claude turn took 4.6 s against 8.2 s cold; on AgentCore 3.3 s against 8.2 s. See cookbook. (#11088)
  • Sandbox Through AgentOS: POST /agents/{agent_id}/runs for a sandboxed agent submits foreground, streaming and background requests to the durable queue with no new endpoints. An Idempotency-Key retry returns the same run, while a different session, input, options or attachment bytes returns 409. Clients reconnect with /runs/{run_id}/resume (last_event_index) and cancel with /runs/{run_id}/cancel, including across replicas: a cancel settled on another replica now records the run as cancelled and keeps the user's turn on the run row. AgentOS fails at startup if a sandboxed agent has no Postgres to coordinate on, refuses the host-local default checkpoint store once a queue worker is active, and validates each sandboxed agent's bindings table at startup and before a submission, naming the remedy for a table from an earlier build. See cookbook. (#11043, #11105)
  • Attachments for Sandboxed Agents: run / arun on a sandboxed ClaudeAgent or CodexAgent accept images= and files=, and the AgentOS run route accepts them as uploads. Only bytes cross into the sandbox: each attachment is validated and encoded before any durable write, staged under /workspace/.agno/uploads/<run_id>/ by the harness's own staging, and kept in the turn's checkpoint so later turns on a new computer can still read it. A request carries at most 16 attachments and 512 KiB in total; URLs, media references, server file paths, audio and video are refused. Queued runs store the attachments with the submission, so a retry sends the same bytes. See cookbook. (#10990, #11091)
  • Images and PDFs Inline for Claude Code: ClaudeAgent now sends attached images (PNG, JPEG, GIF, WEBP) and PDFs up to 4 MiB inside the message as content blocks, the form the Agent SDK's streaming input takes, instead of only writing them to disk for Claude's Read tool. Claude sees the picture directly and never reads the file back, which used to return the whole file as base64 and overflow the SDK's 1 MiB message buffer and the sandbox's 256 KiB event frame for images of a few hundred KB. Whether a file goes inline is decided from its bytes, so a mislabelled file stays on disk for the file tools; other files and larger images keep the Read path. See cookbook. (#11115)
  • Queue Per Session: Durable background runs on one session now execute at most one at a time, in submission order, for every component. Each ticket carries a store-assigned session_seq; a ticket is claimed only while no sibling in its session is running or paused and no earlier sibling is still queued, so waiting tickets spend no attempt and no worker slot. Different sessions stay concurrent within max_concurrency. A paused run holds its session, a continued or retried run keeps its place, and a PENDING run poll carries waiting_on with the run it is blocked behind. QueueConfig.queue_per_session (default on) controls it, external agents are serialized regardless, and GET /config reports the effective setting. See cookbook. (#9587)
  • Instant Durable Submissions: The replica that accepts a durable submission wakes its own queue worker after the ticket commits, so the run starts in milliseconds instead of waiting up to poll_interval for the next poll. A saturated replica wakes on slot release, and peers still pick up jobs on their own poll. Durability is untouched: the row is committed before anyone is woken. (#9667)
  • ChartTools: New toolkit with a single create_chart tool that validates a chart payload (bar, line, area, pie, bar-horizontal, bar-stacked, area-stacked) and returns a ready fenced chart block for Agno OS to render, replacing the schema prompt users had to carry. Validation failures tell the model what to fix, and the toolkit ships its own instructions, so tools=[ChartTools()] is all an agent needs. See cookbook. (#8295)

Improvements:

  • Durable Queue for Db-Backed and Factory Components: Background runs on components created through the components API, on version-pinned runs, and on AgentFactory / TeamFactory / WorkflowFactory submissions now ride the durable queue instead of dropping to a detached task on the accepting replica. The accepting endpoint stamps a resolution scope on the ticket (source, owner, version, and for factories the trusted claims and factory input), and the worker replays that resolution at claim time. A factory that reads ctx.request on the worker fails the run with a message naming the fix, since the live request cannot ride the ticket. The run read routes for factory runs no longer answer 400 on every poll. See cookbook. (#9796, #11045)
  • Codex Permission Policy Naming: CodexAgent(sandbox="read-only") is renamed sandbox_mode, matching Codex's own config key, since sandbox= now takes a provider. The old string form still works with a DeprecationWarning. (#11043)
  • Sandbox Cookbooks: cookbook/frameworks/sandbox/ is split into docker/ and agentcore/ folders, each with its own README and test log, covering the provider, checkpoints, the coordinator, recovery, cancellation, attachments, warm turns and AgentOS. build_image.py loads the built tag into the image store and verifies it is there. (#11050, #11081, #11105)
  • Gemini Cookbooks: Updated to the current models and API. (#11038)

Bug Fixes:

  • Sandbox Checkpoint Restore: Every second turn in a sandbox session failed with getent unable to find entry "1000:1000" in passwd database, because docker cp --archive asks the daemon to resolve the container's user as a name. Restore now copies without archive mode and pins every restored entry to 1000:1000 itself. (#11094)
  • Sandbox Store and Coordinator: A queue cancel racing a worker claim of the same run could deadlock on lock order; the stop path now takes the session, run and binding in the same order as every other store transaction. Sync calls through DockerSandbox leaked an HTTP client per call. Cancelled sandbox runs now record the EXECUTING cancellation stage the queue expects. A run marked finished between cleanup and commit goes through the stop path instead of leaving the binding in finalizing, and long provider calls extend their lease. (#11057, #11092)
  • Sandbox Submissions: Submitting with a user_id to a session created without one, or the reverse, answers 404 before any ticket exists instead of a 500 with a cancelled job left behind. A foreground request whose job failed before its run row existed returns the ticket's error as a 500 instead of a 503 asking the client to reconnect. (#11105)
  • WebSocket Tails: With a durable queue, a chat client that sent a second message while a workflow run was streaming over the WebSocket stopped getting events for the first run. Tail pumps are now keyed per (socket, run), a re-subscribe replaces only that run's pump, and a socket may attach up to 32 runs. (#11039)
  • API Docs Order: The FileSystem routes are registered after the Database routes on setup and resync, so the generated API docs list them in order. (#11099)
  • Tests: The WebSocket factory workflow tests pin the inline path they were written for, after factory submissions started riding the durable queue. (#11106)
