<a id="major-changes"/>大きな変更点</a>

<a id="breaking-changes"/>重大な変更</a>

<a id="deleted-metrics-breaking"/>削除された VTGate メトリクス</a>

4 つの非推奨の VTGate メトリックは、v23.0.0 で完全に削除されました。これらのメトリクスは v22.0.0 で非推奨になりました。 |メトリクス名 |コンポーネント | | で廃止予定 |--------------------------------------|-----------|---------------| | QueriesProcessed | vtゲート | v22.0.0 | | QueriesRouted | vtゲート | v22.0.0 | | QueriesProcessedByTable | vtゲート | v22.0.0 | | QueriesRoutedByTable | vtゲート | v22.0.0 | 影響: これらのメトリクスを使用する監視ダッシュボードまたはアラート システムは、v22.0.0 で導入された代替メトリクスを使用するように更新する必要があります。

  • QueriesProcessed の代わりに QueryExecutions を使用します。
  • QueriesRouted の代わりに QueryRoutes を使用します。
  • QueriesProcessedByTable および QueriesRoutedByTable の代わりに QueryExecutionsByTable を使用します。 新しい指標の詳細については、v22.0.0 release notes を参照してください。

<a id="executefetchasdba-multistatement"/>ExecuteFetchAsDba は複数ステートメント SQL を受け入れなくなりました</a>

TabletManager の ExecuteFetchAsDba RPC メソッドは、複数のステートメントを含む SQL クエリを明示的に拒否するようになりました (PR #18183 以降)。 影響: 以前にセミコロンで区切られた複数の SQL ステートメントを ExecuteFetchAsDba に渡していたコードまたはオートメーションは、エラーを受け取るようになります。各 SQL ステートメントは個別の RPC 呼び出しで送信する必要があります。 移行: 複数ステートメントの SQL を個々の RPC 呼び出しに分割します。

// Before (no longer works):
ExecuteFetchAsDba("CREATE TABLE t1 (id INT); CREATE TABLE t2 (id INT);")

// After (required in v23+):
ExecuteFetchAsDba("CREATE TABLE t1 (id INT);")
ExecuteFetchAsDba("CREATE TABLE t2 (id INT);")

<a id="grpc-error-codes"/>gRPC TabletManager エラー コードの変更</a>

vttablet gRPC tabletmanager client は、内部 go/vt/vterrors パッケージ (PR #18565) によってラップされたエラーを返すようになりました。 影響: google-gRPC エラー コードに依存する外部オートメーションは、vterrors.Code(err) を使用してエラー コードを検査するように更新する必要があります。これにより、proto/vtrpc.proto で定義された vtrpcpb.Code が返されます。 移行:

// Before:
if status.Code(err) == codes.NotFound { ... }

// After:
if vterrors.Code(err) == vtrpcpb.Code_NOT_FOUND { ... }

<a id="gtid-api-changes"/>GTID API 署名の変更</a>

GTID パフォーマンスの最適化の一環として、PR #18196 でいくつかの GTID 関連の API シグネチャが変更されました。 変更: BinlogEvent.GTID() メソッド シグネチャ 影響: API を解析する GTID を直接使用するコードは更新が必要な場合があります。これらは内部 API であるため、ほとんどのユーザーは影響を受けません。

<a id="generateshardranges-api"/>GenerateShardRanges API 署名の変更</a>

PR #18633 で key.GenerateShardRanges() 関数シグネチャが変更され、生成されるシャード名の 16 進幅を制御する新しい hexChars int パラメータが追加されました。 影響: GenerateShardRanges() を直接呼び出すコードは、新しいパラメーターを渡すように更新する必要があります。 対応する vtctldclient コマンドは、この動作を制御するための新しい --chars フラグを取得しました。

<a id="flag-naming-convention-migration"/>フラグ命名規則の移行</a>

Vitess v23.0.0 には、すべてのバイナリにわたる CLI フラグ命名規則の主要な標準化が含まれています。 PR #18280 および関連する PR では、989 フラグ がアンダースコア表記 (flag_name) からダッシュ表記 (flag-name) に移行されました。

下位互換性

  • v23.0.0 および v24.0.0: アンダースコアとダッシュの両方の形式がサポートされています。アンダースコア形式は 非推奨ですが、機能します。
  • v25.0.0: アンダースコア形式は削除されます。ダッシュ形式のみが受け入れられます。

自動正規化

フラグの正規化は pflag レベル (PR #18642) で自動的に行われるため、v23/v24 ではコードを変更することなく両方の形式が受け入れられます。

フラグの名前変更の例

影響を受ける一般的なフラグ (989 個のフラグの完全なリストは PR #18280 で入手可能): バックアップ フラグ:

  • --azblob_backup_account_name → --azblob-backup-account-name
  • --s3_backup_storage_bucket → --s3-backup-storage-bucket
  • --xtrabackup_root_path → --xtrabackup-root-path レプリケーション フラグ:
  • --heartbeat_enable → --heartbeat-enable
  • --replication_connect_retry → --replication-connect-retry gRPC フラグ (PR #18009):
  • gRPC 関連のすべてのフラグを標準化 (30 以上のフラグ)

アクションが必要です

ユーザーは、v25.0.0 にアップグレードする前に、ダッシュベースのフラグ名を使用するように構成ファイル、スクリプト、自動化を更新する必要があります。移行には v23 および v24 との下位互換性があり、段階的な更新が可能です。

<a id="new-default-versions"/>新しいデフォルト バージョン</a>

<a id="upgrade-to-mysql-8-4"/>MySQL 8.4 にアップグレード</a>

vitess/lite:latest イメージで使用されるデフォルトのメジャー MySQL バージョンは、8.0.40 から 8.4.6 になります。 この変更は #18569 にマージされました。 VTGate は、デフォルトで 8.0.40 の代わりに MySQL バージョン 8.4.6 もアドバタイズします。それが実行中のバージョンではない場合は、mysql_server_version フラグを設定して、必要なバージョンをアドバタイズできます。

⚠️ vitess-operator を使用してこのリリースにアップグレードする:

vitess-operator を使用している場合は、MySQL のバージョンを 8.0.40 から 8.4.6 にアップグレードすることを考慮して、手動でアップグレードする必要があります。

  1. YAML ファイル内の追加の cnf に innodb_fast_shutdown=0 を追加します。
  2. このファイルを適用します。
  3. すべてのポッドが正常になるまで待ちます。
  4. 次に、新しい Docker イメージ (vitess/lite:v23.0.0) を使用するように YAML ファイルを変更します。
  5. YAML ファイル内の余分な cnf から innodb_fast_shutdown=0 を削除します。
  6. このファイルを適用します。

これは、最新の 8.0.x から 8.4.x に移行するときに 1 回だけ必要です。 8.4.x を使用すると、innodb_fast_shutdown=0 を実行しなくても、8.4.x バージョン間でアップグレードおよびダウングレードすることができます。

<a id="new-support"/>新しいサポート</a>

<a id="multi-query-execution"/>複数クエリの実行</a>

Vitess v23.0.0 では、新しい ExecuteMulti および StreamExecuteMulti API (PR #18059) を通じて、単一の RPC 呼び出しで複数のクエリを実行するためのネイティブ サポートが導入されています。 この機能により、手動によるクエリの分割や複数のラウンドトリップを必要とせずに、より効率的なバッチ クエリの実行が可能になります。 使用例:

queries := []string{
    "SELECT * FROM users WHERE id = 1",
    "SELECT * FROM orders WHERE user_id = 1",
    "SELECT * FROM payments WHERE user_id = 1",
}
results, err := vtgateConn.ExecuteMulti(ctx, queries)

設定: VTGate の --mysql-server-multi-query-protocol フラグで有効にします。

<a id="transaction-timeout-session-variable"/>トランザクション タイムアウト セッション変数</a>

新しい transaction_timeout セッション変数 (PR #18560) が追加され、トランザクション タイムアウト期間をセッションごとに制御できるようになりました。 使用方法:

-- Set transaction timeout to 30 seconds for this session
SET transaction_timeout = 30;

-- Begin a transaction that will automatically rollback if not committed within 30s
BEGIN;
-- ... perform operations ...
COMMIT;

これにより、グローバル サーバー設定と比較してより詳細なタイムアウト制御が可能になり、次の場合に役立ちます。

  • タイムアウトの延長が必要な、長時間実行されるバッチ操作
  • 対話型セッションはすぐに失敗する必要があります
  • アプリケーションのワークロードごとに異なるタイムアウト要件

<a id="query-throttler" />実験的: クエリ スロットラー</a>

Vitess v23.0.0 は、受信クエリのレートを制限するための新しい実験的なクエリ スロットラー フレームワークを導入しています (RFC issue #18412、PR #18449、PR #18657)。この新しいスロットラーの作業は現在進行中であり、将来的に重大な変更が行われる可能性があります。 この実験的な機能に関するフィードバックは、GitHub の問題または [Vitess Community Slack] (https://vitess.io/slack) の #feat-handling-overload チャネルで歓迎されます。 特徴:

  • スロットルルールのファイルベースの構成
  • 強制を行わずにスロットリングをテストするためのドライラン モード
  • 動的なルールのリロード 構成:
  • --query-throttler-config-refresh-interval - スロットラー設定をリロードする頻度 ドライラン モード: 実際にクエリをブロックせずにスロットル ルールをテストします。これは、適用前に構成を検証するのに役立ちます。

<a id="multiple-lookup-vindexes-support"/>複数のルックアップ Vindex のサポート</a>

単一のワークフロー内で複数のルックアップ vindex を作成することが、--params-file フラグ (PR #17566) によってサポートされるようになりました。 使用方法:

# Create multiple lookup vindexes from JSON configuration
vtctldclient LookupVindexCreate \
  --workflow my_lookup_workflow \
  --params-file /path/to/params.json \
  commerce

params.json の例:

{
  "vindexes": [
    {
      "name": "user_email_lookup",
      "type": "consistent_lookup_unique",
      "table_owner": "users",
      "table_owner_columns": ["email"]
    },
    {
      "name": "user_name_lookup",
      "type": "consistent_lookup",
      "table_owner": "users",
      "table_owner_columns": ["name"]
    }
  ]
}

これにより、複数の vindex を設定する際のワークフローの効率が大幅に向上し、必要な個別の操作の数が減ります。

<a id="reference-tables-in-materialize-workflows"/>マテリアライズ ワークフローの参照テーブル</a>

新しい Materialize ... update サブコマンド (PR #17804) を使用して、参照テーブルを既存のマテリアライズ ワークフローに追加できるようになりました。 使用方法:

# Add reference tables to an existing workflow
vtctldclient Materialize --workflow my_workflow update \
  --add-reference-tables ref_table1,ref_table2 \
  --target-keyspace my_keyspace

使用例: ワークフロー全体を再作成することなく、実行中のマテリアライズ ワークフローに参照テーブルを段階的に追加し、運用の柔軟性を向上させます。

<a id="online-ddl-shard-specific-completion"/>オンライン DDL シャード固有の完了</a>

新しい COMPLETE VITESS_SHARDS 構文 (PR #18331) を使用して、オンライン DDL 移行をシャードごとに完了できるようになりました。 使用方法:

-- Complete migration on specific shards only
ALTER VITESS_MIGRATION '9e8a9249_3976_11ed_9442_0a43f95f28a3'
  COMPLETE VITESS_SHARDS '-80,80-';

-- Complete migration on all remaining shards
ALTER VITESS_MIGRATION '9e8a9249_3976_11ed_9442_0a43f95f28a3'
  COMPLETE;

利点:

  • シャード間でのスキーマ変更の段階的なロールアウト
  • 完全なロールアウト前にシャードのサブセットに対する変更を検証する機能
  • 移行のタイミングと影響をより適切に制御

<a id="with-recursive-ctes"/>再帰的 CTE を使用する</a>

Vites は、WITH RECURSIVE 共通テーブル式 (PR #18590) をサポートするようになり、階層データの再帰クエリが可能になりました。 例:

-- Find all employees in a management hierarchy
WITH RECURSIVE employee_hierarchy AS (
    SELECT id, name, manager_id, 1 as level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.id, e.name, e.manager_id, eh.level + 1
    FROM employees e
    INNER JOIN employee_hierarchy eh ON e.manager_id = eh.id
)
SELECT * FROM employee_hierarchy ORDER BY level, name;

これは、階層型またはグラフ状のデータ構造を持つアプリケーションに対する SQL 互換性の大幅な強化です。

<a id="create-table-select-support"/>CREATE TABLE ... SELECT サポート</a>

SQL パーサーは CREATE TABLE ... SELECT ステートメント (PR #18443) をサポートするようになり、MySQL の互換性が向上しました。 例:

-- Create a table from a query result
CREATE TABLE recent_orders
SELECT * FROM orders
WHERE order_date > DATE_SUB(NOW(), INTERVAL 30 DAY);

<a id="modified-metrics"/>変更された指標</a>

キースペース/シャード ラベルで強化された VTOrc リカバリ メトリクス

次の VTOrc リカバリ メトリックには、既存の RecoveryType ラベル (PR #18304) に加えて、Keyspace ラベルと Shard ラベルが含まれるようになりました。 1.FailedRecoveries 2.PendingRecoveries 3.RecoveriesCount 4.SuccessfulRecoveries 影響: これらのメトリクスを使用してクエリとダッシュボードを監視するには、追加のラベル ディメンションを考慮して更新が必要になる場合があります。 利点:

  • リカバリの問題が発生しているキースペース/シャードをより詳細に観察可能
  • キースペース/シャードごとの回復パターンに関するアラート機能
  • クラスター固有の問題のトラブルシューティングの改善 PromQL クエリの例:
# Before (v22): Recovery count by type only
sum(rate(RecoveriesCount[5m])) by (RecoveryType)

# After (v23): Recovery count by type, keyspace, and shard
sum(rate(RecoveriesCount[5m])) by (RecoveryType, Keyspace, Shard)

VTGate QueryExecutionsByTable の動作の変更

QueryExecutionsByTable メトリクスは、成功したクエリ実行のみをカウントするようになりました (PR #18584)。以前は、成功/失敗に関係なく、すべてのクエリ試行がカウントされていました。 影響:

  • ワークロードに重大なクエリ障害が発生した場合、メトリクス値が減少する可能性があります
  • 成功したクエリの量をより正確に表現
  • 失敗したクエリは、エラー メトリクスを介して個別に追跡されます。

<a id="query-planning-improvements"/>クエリ プランニングの改善</a>

シングルシャードクエリのウィンドウ関数

ウィンドウ関数を単一シャード クエリ (PR #18103) にプッシュダウンできるようになり、分析ワークロードのパフォーマンスが向上しました。 v23 より前: 単一シャード クエリの場合でも、ウィンドウ関数は常に VTGate レベルで実行されていました。 v23 以降: クエリが単一のシャードをターゲットにしている場合、ウィンドウ関数がプッシュダウンされ、データ転送が削減され、パフォーマンスが向上します。 例:

-- This query now executes entirely on the target shard
SELECT
    user_id,
    order_date,
    amount,
    SUM(amount) OVER (PARTITION BY user_id ORDER BY order_date) as running_total
FROM orders
WHERE user_id = 12345;  -- Single-shard query

UNION クエリのマージの改善

UNION クエリの最適化が大幅に強化されました (PR #18289、PR #18393): 拡張された UNION マージ: Equal および IN オペコードを含む UNION クエリをより積極的にマージし、より単純な SQL を生成できるようになりました。 派生テーブルの削除: UNION クエリに対する不必要な派生テーブルのラッピングが回避され、よりクリーンで効率的な SQL が生成されます。 例:

-- Query:
SELECT * FROM t1 WHERE id = 1
UNION
SELECT * FROM t1 WHERE id = 2;

-- Before v23: Wrapped in derived table
SELECT * FROM (
    SELECT * FROM t1 WHERE id = 1
    UNION
    SELECT * FROM t1 WHERE id = 2
) AS dt;

-- After v23: Direct UNION (simpler, more efficient)
SELECT * FROM t1 WHERE id = 1
UNION
SELECT * FROM t1 WHERE id = 2;

SINGLE モードでのマルチシャード読み取り専用トランザクション

SINGLE トランザクション モードを使用する場合、読み取り専用トランザクションが複数のシャードにまたがることができるようになりました (PR #18173)。 v23 より前: SINGLE モードでは、読み取り専用のものも含め、すべてのトランザクションが単一のシャードに制限されていました。 v23 以降: 読み取り専用トランザクションは SINGLE モードで複数のシャードにアクセスできるため、一貫性の保証を犠牲にすることなく柔軟性が向上します。 影響: SINGLE トランザクション モードを使用するアプリケーションは、MULTI または TWOPC モードにアップグレードすることなく、トランザクション内でマルチシャード読み取りクエリを実行できるようになりました。

プリペアド ステートメントの遅延最適化

プリペアド ステートメントは遅延最適化 (PR #18126) をサポートするようになり、プラン生成にランタイム値が必要な場合でも準備を成功させることができます。 利点:

  • より多くの準備されたステートメントが準備時に成功します
  • パラメータ依存の最適化によるクエリのサポートの向上
  • 失敗した PREPARE ステートメントによるアプリケーション エラーの減少 動作: 準備されたステートメントを準備時に完全に最適化できない場合、最適化はバインド変数値が使用可能な実行時間まで延期されます。

INSTANT DDL のクエリ バッファリング

INSTANT DDL 操作 (PR #17945) にクエリ バッファリングが実装され、スキーマ変更時のクエリの失敗が減少しました。 特徴:

  • INSTANT DDL 実行中のクエリの自動バッファリング
  • ブロッキングトランザクションの強制終了
  • アプリケーションに対して透過的 影響: スキーマ変更中にアプリケーションで発生するクエリ エラーが減少し、DDL 操作中の可用性が向上します。

<a id="vtorc-dynamic-ers-disabled"/>EmergencyReparentShard ベースのリカバリの動的制御</a>

注: EmergencyReparentShard ベースのリカバリを無効にすると、可用性のリスクが生じます。細心の注意を払って使用してください。たとえば自動化などでこの機能に頻繁に依存している場合、これはアンチパターンの兆候である可能性があります。その場合は、問題を作成して、VTOrc でのユースケースのネイティブなサポートについて話し合ってください。 新しい vtctldclient RPC SetVtorcEmergencyReparent が導入され (PR #17985)、EmergencyReparentShard アクションを含む VTOrc リカバリをキースペースごとまたはシャードごとに無効にできるようになりました。このバージョンより前は、EmergencyReparentShard ベースのリカバリの無効化は、グローバルまたは VTOrc インスタンスごとにのみ可能でした。 VTOrc は、リカバリのたびにトポから更新されるこのキースペース/シャード レベルの設定を考慮するようになります。無効な状態は、最初にキースペースかどうかを確認し、次にシャードの状態を確認することによって判断されます。キースペースレベルのオーバーライドを削除しても、シャードごとのオーバーライドは削除されません。 EmergencyReparentShard ベースの VTOrc リカバリを無効にしてキースペース/シャードの可観測性を提供するために、EmergencyReparentShardDisabled メトリクスが追加されました。このメトリック ラベルを使用してアラートを作成し、EmergencyReparentShard ベースのリカバリが望ましくない期間無効にならないようにすることができます。 例:

# Disable ERS recoveries for a keyspace
vtctldclient SetVtorcEmergencyReparent --keyspace commerce --enabled=false

# Disable ERS recoveries for a specific shard
vtctldclient SetVtorcEmergencyReparent --keyspace commerce --shard 80- --enabled=false

# Re-enable ERS recoveries
vtctldclient SetVtorcEmergencyReparent --keyspace commerce --enabled=true

<a id="mysql-caching-sha2-password"/>管理対象 MySQL 構成のデフォルトは caching-sha2-password</a>

MySQL 8.0.26 以降のデフォルトの認証プラグインは、mysql_native_password ではなく caching_sha2_password になりました (PR #18010)。この変更は、mysql_native_password が非推奨となり、将来の MySQL バージョンで削除されるために行われました。 mysql_native_password は下位互換性のために引き続き有効です。 この変更は特にレプリケーション ユーザーに影響します。ユーザーに明示的なパスワードが設定されている場合は、v23 にアップグレードした後、次のようなステートメントを使用してこのユーザーを必ずアップグレードすることをお勧めします。

ALTER USER 'vt_repl'@'%' IDENTIFIED WITH caching_sha2_password BY 'your-existing-password';

Vitess の将来のバージョンでは、マネージド MySQL インスタンスに対して mysql_native_password 認証プラグインが無効になります。

<a id="mysql-timezone-env"/>MySQL タイムゾーン環境の伝達</a>

TZ のような環境変数が mysqlctl から mysqld プロセスに伝播されないバグを修正しました (PR #18561)。 その結果、環境からのタイムゾーン設定は以前は無視されていました。 mysqld は環境変数を正しく継承するようになりました。 ⚠️ デプロイメントへの影響: 古い動作に依存し、非 UTC タイムゾーンを明示的に設定しているデプロイメントでは、DATETIME 値の解釈方法が変更される可能性があります。互換性を維持するには、MySQL ポッドで TZ=UTC を明示的に設定します。

<a id="grpctmclient-err-changes"/>gRPC tabletmanager client エラーの変更</a>

vttablet gRPC tabletmanager client は、内部 go/vt/vterrors パッケージ (PR #18565) によってラップされたエラーを返すようになりました。 google-gRPC エラー コードに依存する外部オートメーションでは、vterrors.Code(err) を使用してエラー コードを検査する必要があります。これにより、proto/vtrpc.proto プロトバッファ で定義された vtrpcpb.Code が返されます。 移行のガイダンスについては、重大な変更 を参照してください。

<a id="docker"/>Docker</a>

Bullseye は 1 年前に EOL になりました ため、v23 以降、debian:bullseye に基づくイメージの構築や公開は行わなくなります (PR #18609)。 Debian Bookworm のビルドは継続され、最近リリースされた Debian Trixie が追加されます。 v23 では、デフォルトの Debian タグが Trixie に明示的に変更されません。

// Before:
if status.Code(err) == codes.NotFound { ... }

<a id="query-planning-improvements"/>Query Planning Improvements</a>

Window Functions in Single-Shard Queries

Window functions can now be pushed down to single-shard queries (PR #18103), improving performance for analytics workloads.

Before v23: Window functions were always executed at VTGate level, even for single-shard queries.

After v23: Window functions are pushed down when the query targets a single shard, reducing data transfer and improving performance.

Example:

-- This query now executes entirely on the target shard
SELECT
    user_id,
    order_date,
    amount,
    SUM(amount) OVER (PARTITION BY user_id ORDER BY order_date) as running_total
FROM orders
WHERE user_id = 12345;  -- Single-shard query

UNION Query Merging Improvements

UNION query optimization has been significantly enhanced (PR #18289, PR #18393):

Extended UNION Merging: UNION queries with Equal and IN opcodes can now be merged more aggressively, generating simpler SQL.

Derived Table Elimination: Unnecessary derived table wrapping is avoided for UNION queries, producing cleaner and more efficient SQL.

Example:

-- Query:
SELECT * FROM t1 WHERE id = 1
UNION
SELECT * FROM t1 WHERE id = 2;

-- Before v23: Wrapped in derived table
SELECT * FROM (
    SELECT * FROM t1 WHERE id = 1
    UNION
    SELECT * FROM t1 WHERE id = 2
) AS dt;

-- After v23: Direct UNION (simpler, more efficient)
SELECT * FROM t1 WHERE id = 1
UNION
SELECT * FROM t1 WHERE id = 2;

Multi-Shard Read-Only Transactions in SINGLE Mode

Read-only transactions can now span multiple shards when using SINGLE transaction mode (PR #18173).

Before v23: SINGLE mode restricted all transactions to single shards, even read-only ones.

After v23: Read-only transactions can access multiple shards in SINGLE mode, improving flexibility without sacrificing consistency guarantees.

Impact: Applications using SINGLE transaction mode can now perform multi-shard read queries within transactions without needing to upgrade to MULTI or TWOPC modes.

Deferred Optimization for Prepared Statements

Prepared statements now support deferred optimization (PR #18126), allowing preparation to succeed even when plan generation requires runtime values.

Benefits:

  • More prepared statements succeed at preparation time
  • Better support for queries with parameter-dependent optimization
  • Reduced application errors from failed PREPARE statements

Behavior: When a prepared statement cannot be fully optimized at preparation time, optimization is deferred to execution time when bind variable values are available.

Query Buffering for INSTANT DDL

Query buffering has been implemented for INSTANT DDL operations (PR #17945), reducing query failures during schema changes.

Features:

  • Automatic buffering of queries during INSTANT DDL execution
  • Forced termination of blocking transactions
  • Transparent to applications

Impact: Applications experience fewer query errors during schema changes, improving availability during DDL operations.

<a id="vtorc-dynamic-ers-disabled"/>Dynamic control of EmergencyReparentShard-based recoveries</a>

Note: disabling EmergencyReparentShard-based recoveries introduces availability risks; please use with extreme caution! vtctldclient SetVtorcEmergencyReparent --keyspace commerce --enabled=false

vtctldclient SetVtorcEmergencyReparent --keyspace commerce --shard 80- --enabled=false

vtctldclient SetVtorcEmergencyReparent --keyspace commerce --enabled=true

In future Vitess versions, the mysql_native_password authentication plugin will be disabled for managed MySQL instances.

<a id="mysql-timezone-env"/>MySQL timezone environment propagation</a>

Fixed a bug where environment variables like TZ were not propagated from mysqlctl to the mysqld process (PR #18561). As a result, timezone settings from the environment were previously ignored. Now mysqld correctly inherits environment variables.

⚠️ Deployment Impact: Deployments that relied on the old behavior and explicitly set a non-UTC timezone may see changes in how DATETIME values are interpreted. To preserve compatibility, set TZ=UTC explicitly in MySQL pods.

<a id="grpctmclient-err-changes"/>gRPC tabletmanager client error changes</a>

The vttablet gRPC tabletmanager client now returns errors wrapped by the internal go/vt/vterrors package (PR #18565). External automation relying on google-gRPC error codes should now use vterrors.Code(err) to inspect the code of an error, which returns vtrpcpb.Codes defined in the proto/vtrpc.proto protobuf.

See Breaking Changes for migration guidance.

<a id="docker"/>Docker</a>

Bullseye went EOL 1 year ago, so starting from v23, we will no longer build or publish images based on debian:bullseye (PR #18609).

Builds will continue for Debian Bookworm, and add the recently released Debian Trixie. v23 explicitly does not change the default Debian tag to Trixie.
