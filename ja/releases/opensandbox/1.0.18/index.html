OpenSandbox java/sandbox/v1.0.18

新機能

⚠️ 行動の変化

  • 自動再試行はデフォルトで有効になっています — 非ストリーミング Kotlin SDK clients は、SDK 再試行ポリシーを自動的に適用するようになりました。デフォルトでは、べき等メソッドは 429、502、および 503 応答を再試行しますが、POST および PATCH ステータス コードの再試行はオプトインのままです。送信前の接続が失敗しても再試行される可能性があります。以前の SDK ポリシーの動作を必要とするアプリケーションは、.retryPolicy(RetryPolicy.disabled()) を構成する必要があります。これにより、非ストリーミング通話に対する OkHttp の既存の接続回復を保持しながら、SDK によって管理される再試行が無効になります。ストリーミング コマンドおよびコード実行リクエストが自動的に再試行されることはありません。 #1413

✨ 特徴

  • 回復力のある Kotlin トランスポート — 制限付き指数バックオフ、ジッター モード、Retry-After サポート、試行ごとのタイムアウト、全体の期限、および再試行コールバックを備えた構成可能な再試行ポリシーが追加されました。パブリック例外階層は、生成されたパスと手書きの API パス全体で一貫して再試行可能性、リクエスト ID、再試行遅延、生の応答本文を公開しながら、レート制限、タイムアウト、接続失敗を区別するようになりました。 #1413
  • ローリング プール ウォームアップ — サンドボックス プールの補充では、warmupConcurrency をローリング実行中の制限として扱い、各ウォームアップが終了するとすぐに容量を再利用するため、1 回のゆっくりとした作成によって残りの補充ウェーブが停止することがなくなりました。ウォームアップの実行中も、分散プライマリ ハートビート、所有権フェンシング、クリーンアップ、バックオフが継続されます。パブリック API と構成名は変更されません。 #1427

🐛 バグ修正

  • より安全なプールのシャットダウンとライフサイクルの再起動 — 正常なシャットダウンは、エグゼキュータを強制終了する前に認められたウォームアップを排出し、中断が発生したときにリモートで作成されたサンドボックスを確実にクリーンアップして、リソース リーク ウィンドウを閉じます。また、プールの取得パスとウォームアップ パスは、キャンセルを正しく伝播し、ライフサイクル世代によって作業をフェンスし、Exception 以外の障害に対してもリソースとカウンターを解放し、リタイアされた作業が再起動されたプールに漏洩するのを防ぎます。 #1415 #1438

📦 その他

  • Kotlin/JVM サンドボックス、コード インタープリター、Redis プール、および BOM アーティファクトを、既存の com.alibaba.opensandbox 座標の下のバージョン 1.0.18 で公開しました。 #1415

OpenSandbox java/sandbox/v1.0.18

Highlights

  • Default retries alter non-streaming behavior — Kotlin SDK clients now retry 429, 502, and 503 responses automatically for idempotent methods; POST and PATCH status-code retries remain opt-in, and streaming command/code-execution requests never retry. To preserve the previous SDK behavior, configure .retryPolicy(RetryPolicy.disabled()); OkHttp’s existing non-streaming connection recovery still applies. #1413
  • Resilient transport and diagnostics — New retry policies support bounded exponential backoff, configurable jitter, Retry-After, per-attempt timeouts, overall deadlines, and callbacks. A clearer exception hierarchy distinguishes rate limits, timeouts, and connection failures while consistently exposing retryability, request IDs, retry delays, and raw response bodies across generated and handwritten API paths. #1413
  • Rolling pool warmups remove head-of-line blocking — warmupConcurrency now limits in-flight warmups rather than fixed batches, releasing capacity as each creation completes. Slow sandbox creations no longer stall the rest of a refill wave, while heartbeats, ownership fencing, cleanup, backoff, and public configuration remain unchanged. #1427
  • Shutdown and restart paths close resource leaks — Graceful shutdown drains admitted warmups before terminating executors and cleans up remotely created sandboxes after interruption. Cancellation propagation, lifecycle-generation fencing, and cleanup for non-Exception failures also prevent retired work and leaked counters from contaminating a restarted pool. #1415 #1438
  • Artifacts published under existing coordinates — Kotlin/JVM sandbox, code-interpreter, Redis pool, and BOM artifacts are available at 1.0.18 under com.alibaba.opensandbox, so adoption requires a version bump rather than group or artifact migration. #1415

What's New

⚠️ Behavior Changes

  • Automatic retries are enabled by default — Non-streaming Kotlin SDK clients now apply the SDK retry policy automatically. By default, idempotent methods retry 429, 502, and 503 responses, while POST and PATCH status-code retries remain opt-in; pre-send connection failures may still be retried. Applications that require the previous SDK-policy behavior should configure .retryPolicy(RetryPolicy.disabled()); this disables SDK-managed retries while retaining OkHttp's pre-existing connection recovery for non-streaming calls. Streaming command and code-execution requests never retry automatically. #1413

✨ Features

  • Resilient Kotlin transport — Added configurable retry policies with bounded exponential backoff, jitter modes, Retry-After support, per-attempt timeouts, overall deadlines, and retry callbacks. The public exception hierarchy now distinguishes rate limits, timeouts, and connection failures while exposing retryability, request IDs, retry delays, and raw response bodies consistently across generated and handwritten API paths. #1413
  • Rolling pool warmups — Sandbox pool replenishment now treats warmupConcurrency as a rolling in-flight limit and immediately reuses capacity when each warmup finishes, so one slow creation no longer stalls the rest of the refill wave. Distributed primary heartbeats, ownership fencing, cleanup, and backoff continue while warmups run; public APIs and configuration names remain unchanged. #1427

🐛 Bug Fixes

  • Safer pool shutdown and restart lifecycle — Graceful shutdown now drains admitted warmups before forcing executor termination and reliably cleans up remotely created sandboxes when interruption occurs, closing a resource-leak window. Pool acquire and warmup paths also propagate cancellation correctly, fence work by lifecycle generation, and release resources and counters even for non-Exception failures, preventing retired work from leaking into a restarted pool. #1415 #1438

📦 Misc

  • Published Kotlin/JVM sandbox, code-interpreter, Redis pool, and BOM artifacts at version 1.0.18 under the existing com.alibaba.opensandbox coordinates. #1415
