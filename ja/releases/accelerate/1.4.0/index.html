v1.4.0 を加速します

torchao FP8、初期 Tensor Parallel サポート、およびメモリ リークの修正

torchao FP8

このリリースでは、新しい FP8 API が導入され、新しいバックエンド torchao が導入されています。使用するには、mixed_precision="fp8" を設定しながら、AORecipeKwargs を Accelerator に渡します。これは初期サポートであり、成熟するにつれて、将来のリリースではさらに多くの機能 (accelerate config/yaml など) を組み込む予定です。ベンチマークの例を [こちら] (https://github.com/huggingface/accelerate/tree/main/benchmarks/fp8/torchao) でご覧ください。

TensorParallel

加速データローダーを使用する場合、TP に対する社内ソリューションの初期サポートがあります。 PRはこちらをご覧ください。

accelerate v1.4.0

Highlights

  • FP8 training via torchao backend — A new FP8 API and second FP8 backend land in this release (PR #3348). To adopt it, instantiate Accelerator with mixed_precision="fp8" and pass AORecipeKwargs — it's an opt-in path, not automatic. Important caveat for adopters: this is explicitly initial support, so expect rough edges; config/yaml and accelerate config integration aren't wired up yet, so you'll be configuring in code for now. Benchmarks for evaluating throughput/memory tradeoffs are published in the repo's benchmarks/fp8/torchao examples — worth measuring before committing, since FP8 numerics can affect convergence.
  • Tensor Parallel support (in-house, dataloader-aware) — First-party TP arrives via PR #3173, but scoped to working with accelerate dataloaders. This matters because TP has historically required external frameworks (Megatron, DeepSpeed); having it native means fewer moving parts for sharded inference/training on multi-GPU. Treat it as early-stage: verify sharding semantics and data-loader compatibility against your own workload rather than assuming parity with mature TP implementations.
  • FP8 + DeepSpeed now works together — PR #3361 fixes the interaction between FP8 and DeepSpeed, closing a gap that previously blocked combining the two. If you're on DeepSpeed and want FP8, this is the release that unblocks that combination — but given the FP8 and TP features are both flagged as initial support, validate carefully in a staged rollout.
  • Memory leak fixed in GradientState ↔ DataLoader references — PR #3391 replaces the strong reference from GradientState to the DataLoader with weakrefs. For long-running training jobs or repeated Accelerator lifecycles, this is the most operationally significant fix in the release: it removes a real retention path that could keep dataloaders (and their datasets) alive across runs. If you've seen memory creep in multi-run processes, this is worth upgrading for even if you don't use the new features.
  • Broader accelerator coverage and correctness fixes — The MUSA backend gains more functionality (#3359), XPU gets expanded BNB test coverage and a device-map fix (#3349, #3350, #3397), and two correctness fixes land: a triton version check (#3345) and a torch_dtype fix in memory estimation (#3383). If you're on non-CUDA hardware, note the direction: tests are being generalized away from CUDA-only assumptions (#3302, #3301), so XPU/MUSA support is actively maturing, though it remains less battle-tested than CUDA.
  • No breaking changes were introduced in this release.

torchao FP8, initial Tensor Parallel support, and memory leak fixes

torchao FP8

This release introduces a new FP8 API and brings in a new backend: torchao. To use, pass in AORecipeKwargs to the Accelerator while setting mixed_precision="fp8". This is initial support, as it matures we will incorporate more into it (such as accelerate config/yaml) in future releases. See our benchmark examples here

TensorParallel

We have intial support for an in-house solution to TP when working with accelerate dataloaders. check out the PR here
