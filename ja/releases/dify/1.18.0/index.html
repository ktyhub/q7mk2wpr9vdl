#ディファイ1.18.0

Dify 1.18.0 は、ワークフローをルーティングするエージェント、ポータブル アプリ パッケージ、ネストされたワークフロー実行に対するより深い可視性、およびオプトインのエージェント ナレッジ ベース エクスペリエンスをもたらします。 OpenAPI と新しい difyctl により、コマンド ラインからアプリを構築および管理する方法が拡張されます。

[!重要] 展開する前に、以下のアップグレード ガイドをお読みください。 API、ワーカー、エージェント バックエンド、およびエージェント ランタイム イメージを一緒にアップグレードします。ローカル エージェント サンドボックスには空ではない認証トークンが必要で、エージェント バックエンドは新しい実行プロトコルを使用します。ソースのインストールには Python 3.13 が必要です。新しい difyctl client をインストールし、再度サインインします。既存の PASSWORD_PEPPER 構成を保存します。

リリースのハイライト

次のステップを選択するエージェント

どのワークフロー ブランチを取るかをエージェントに決定させます。 出力ルートを有効にし、各ルートに選択条件を与えて、リクエストを直接解決するか専門家に渡すなど、次のステップに接続します。読み取り専用の switch 出力は、選択されたルートを公開します。 (#42599)

ワークフロー エディターに 2 つの分岐がある出力ルート構成。

Plain Agent v2 ノードは、生成されたテキストもストリーミングします。構造化された結果、ルーティングされた結果、およびデフォルト値のエラー処理を使用するノードはバッファされたままになります。 (#43986)

ポータブル アプリを 1 つのパッケージに

サポートされているリソースを含むアプリを単一の .ifpkg パッケージに移動します。ワークフロー パッケージとチャットフロー パッケージには、インライン エージェント、スキル、およびそのファイルが含まれています。インポートは、宛先ワークスペースでそれらのリソースを再作成し、参照を再マップします。ファイルと URL のインポートはパッケージと YAML の両方をサポートしており、明示的な YAML エクスポートは引き続き利用可能です。 (#42066、#42579、#42626、#42863)

Studio の .ifpkg インポート プレビュー。

ネストされたワークフロー実行の内部を確認する

実行履歴から ワークフロー ツールの呼び出し を開き、子ワークフローの個々のステップを検査します。ネストされたツールは、調整された一時停止、再開、停止、およびファイル出力を備えた子グラフとして実行されるようになりました。アクセス チェックにより、ソース アプリの詳細が保護されます。 (#40277、#42819、#42820、#42821、#42822)

成功したワークフロー ツールの呼び出しへのトレース ドリルダウン。

ネストされた使用量とステップの合計は、特に一時停止または停止した後では、おおよその値になる可能性があります。コンソールのドリルダウンと外部トレースのエクスポートにはスコープが異なります。機能の詳細については、以下をご覧ください。

エージェントナレッジベース · ベータ版

エージェント用のナレッジ スペースを作成し、ファイルを追加したりソースに接続したり、ドキュメント処理、メタデータ、取得トレース、品質評価を 1 か所で検査したりできます。新しいナレッジ検索ノードとエージェント統合は、アクセス制御された KnowledgeFS スペースを共有します。従来の知識は引き続き利用可能です。これは、別のサービスおよびデータベースとのオプトイン統合です。以下の展開要件を参照してください。 (#44165)

間もなくcloud.dify.aiで利用可能になります

開発者スポットライト

OpenAPI と difyctl を使用してアプリを構築および管理します。 CLI は、ワークフローとチャットフローの作成、DSL のインポート/エクスポート、設定、環境変数、公開、およびバージョンの復元に関する検索可能なヘルプとサポートを備えて、サーバーの操作カタログからコマンドを検出します。ドラフト ハッシュは同時編集を保護します。 (#42487、#42608、#43067)

Dify アプリを構築するエージェント用にバンドルされたスキルをインストールします。

difyctl install skills <dir>

新しい client には、新たにサインインする必要があります。以下の展開手順を参照してください。 (#43819)

アップグレードガイド

互換性と展開

  1. 最初にバックアップします。 データベース、ベクター ストア データ、アップロードされたファイル、エージェント スナップショット/ワークスペース ストレージ、およびすべての展開シークレットと環境ファイルを保持します。単一スタックのアップグレードにはメンテナンス期間を使用します。
  2. エージェント コンポーネントを一緒にアップグレードします。 /runs は構成 v2 を受け入れ、v1 リクエストを拒否するようになりました。既存のセッション スナップショットは読み取り時に変換され、v2 として保存されます。古いランタイムは、新しく保存された v2 スナップショットを読み取ることができません。ダイレクト エージェント バックエンド統合では、リクエスト形式を更新する必要があります。古いエージェント固有の AskHuman ツールと遅延再開パスは削除されました。履歴エージェント フォームは実行を再開しなくなりましたが、共有ワークフロー ヒューマン入力ノードはサポートされたままです。 (#43833)
  3. 新しいバージョンのトラフィックを許可する前に、古いワークフロー コンシューマを廃止します。 実行中の実行を終了させてから、従来のワーカーを置き換えてコンシューマを再開し、新しいキャンセル ガードなしでは共有キューを処理できないようにします。従来の一時停止されたタスク ID は、既存のアクセス スコープ内で保存された有効な呼び出しスナップショットから回復できます。スナップショットが欠落しているか無効である場合は、個別にリカバリする必要があります。ネストされた使用量の合計には、上記の制限が適用されます。 (#40277)
  4. 再起動前にローカル サンドボックス トークンを構成します。 共有 Compose 補間ソースを通じて高エントロピー シークレットを指定します。 1.17.1 ランタイム イメージは、新しい --require-auth-token フラグをサポートしません。一致する 1.18.0 エージェント バックエンド イメージとローカル サンドボックス イメージを展開します。 (#44152)
  5. パスワード ハッシュ設定を保持します。 ペッパーのない既存のインストールでは、PASSWORD_PEPPER を空のままにしておく必要があります。アップグレード中に新しい Pepper を設定することは透過的な移行ではないため、明示的なパスワード リセット計画が必要です。構成された Pepper をすべてのインスタンスにわたって変更せずに維持し、データベースとともに復元します。
  6. プロキシ境界を確認します。 バンドルされた Nginx は、X-Forwarded-For を解決された client アドレスに置き換え、Compose で転送ヘッダーの処理を有効にします。直接の API アクセスを trust の発信者に制限してください。ロードバランサーまたはCloudflareがNginxの前にある場合は、そこでtrustedリアルIP処理を構成します。そうしないと、訪問者がプロキシのレート制限バケットを共有する可能性があります。 client IP および trusted プロキシ を参照してください。
  7. KnowledgeFS を意図的に有効にします。 デフォルトの Compose インストールでは、KnowledgeFS はオフのままです。ローカルの Community Edition 開発には、明示的なコミュニティ開発のオプトインが必要です。トラフィックを有効にする前に、個別のデータベースと移行、Capability v2 パブリック検証ツール、Dify 署名キー、モデル プロファイル (埋め込み、推論、再ランク付け)、およびワークスペース カットオーバー ゲートを構成します。オプションのサービスは、/health だけでなく、/ready も渡す必要があります。標準の Dify API イメージには、オプションのエンジン ワーカー プロファイルで使用される個別の KnowledgeFS エンジンは含まれていません。公開されているデフォルトの KnowledgeFS API イメージは、現在 amd64 のみです。 KnowledgeFS 導入および回復ガイド に従ってください。

Docker 作成

1.18.0 リリース イメージとタグが公開されたら、古いスタックを正常に停止し、リリースに切り替え、上記の構成変更をマージし、新しいスタックをプル/開始します。

cd dify/docker
docker compose stop -t -1
git fetch --tags
git checkout 1.18.0
# Merge required configuration changes into existing env files here.
docker compose pull
docker compose up -d

API の起動に対してデータベース移行を有効 (MIGRATION_ENABLED=true) のままにするか、新しいワーカーを開始する前に管理された移行プロセスを通じてデータベース移行を実行します。 1.17.1 にバンドルされている Weaviate アップデートは、1.39 内のパッチ アップデートです。 Weaviate 1.27 がまだ実行されているバージョンからの場合は、最初に 1.17.1 段階的な Weaviate アップグレード を完了してください。

ソースの展開

24.x 行の API、Node.js 24.22.1 以降、および pnpm 12.10.1 には Python 3.13 を使用します。ロックされた依存関係を更新し、リポジトリ ルートからデータベース移行を適用します。

uv sync --project api --frozen
uv run --directory api flask db upgrade
pnpm install --frozen-lockfile

Web アプリケーションを再構築し、同じリリースから API、ワーカー、スケジューラ、およびエージェント サービスを再起動します。 Agent Backend をソースとは別にデプロイする場合は、ロックされた server 依存関係も更新します。

difyctl

対応する 1.18.0 client を取り付けます。その v2 実装では、v1 のログイン状態は再利用されません。

difyctl login --server https://your-dify.example.com
difyctl help

現在サーバーで検出されたコマンド サーフェスにスクリプトを更新します。古いモードに依存しない /openapi/v1/apps/{app_id}:run ルートは、モードごとの操作に置き換えられます。ハードコーディングされた v1 ルートの代わりにカタログを使用します。インストールされているエージェント スキルを difyctl install skills <dir> で更新します。 (#42487、#42608、#43819)

エージェントナレッジベースとKnowledgeFS

  • ローカル アップロード プレビュー、接続されたソース管理、ドキュメントの可用性とメタデータ、取得履歴/調査、品質評価を備えたベータ版ナレッジスペース エクスペリエンスを追加します。設定は、アプリ、エージェント、サービス API のアクセスを制御します。 Classic Knowledge も引き続きサポートされます。 (#44165)
  • Knowledge Retrieval v2 およびエージェントのナレッジ バインディングは、スコープ付きの機能を使用します。公開された Explore の実行では、通常の閲覧者がアクセスを再構成する必要がなく、公開されたバインディングが再利用されます。 (#44165)
  • クラシック データセットのアップグレードには、永続的なチェックポイント、可用性/メタデータの調整、再試行保護、Beat によるリカバリがあります。文書化されたプリフォーク プールとタスク制限を使用して専用のアップグレード ワーカーを実行します。 API/workers/Beat を再起動する前に、b9d3f7a5c102 を適用してください。サービスをオプトインしても、すべてのクラシック データセットが自動的に移行されるわけではありません。 (#44165)

ポータブル アプリ パッケージ

  • アプリのエクスポートはデフォルトで .ifpkg になり、アプリケーション構成とそのサポートされるリソースが 1 つのポータブル パッケージにまとめられます。明示的な YAML エクスポートは引き続き利用可能で、インポートではファイルまたは URL からの両方の形式を受け入れます。 (#42066、#42189、#42425、#42552)
  • ワークフローおよびチャットフロー パッケージには、インライン エージェント、そのスキル、および各ノードのバインドされた構成スナップショットからのファイルが含まれています。インポートにより、宛先ワークスペースでそれらのエージェントが再作成され、そのリソースが再マップされます。エクスポート フローには、アプリ アイコン、サイト設定、ノード プラグインの依存関係が含まれます。不足しているリソースがインポート中に報告されます。 (#42579、#42626、#42816、#42863、#42913)
  • エージェントのエクスポートは、公開されたバージョンをターゲットにすることができます。エージェント バージョンのメニューでは復元が可能になり、保留中のドラフト保存は復元前に終了するため、復元された構成は自動保存によって上書きされません。スキルの複製とエクスポートには、保存された最新のドラフト コンテンツが使用されます。 (#42485、#42567、#42424、#42502)

ネストされたワークフロー ツールとトレース ドリルダウン

  • 呼び出されたワークフロー ツールは、ワークフロー エンジンの下で子グラフとして実行され、一時停止、再開、停止、およびファイル出力が調整されます。ソース グラフは実行前にキャプチャされるため、ツールを再公開しても、ループや反復内の呼び出しを含む実行中の実行は変更されません。 (#40277、#42820)
  • ワークフロー、チャットフロー、および履歴ビューでは、特定のツール呼び出しを開いて、その内部実行トレースをナビゲートできます。詳細が返される前に、各ソース アプリケーションにアクセスする必要があります。人間の入力フォームは、同じノードの繰り返しの呼び出しなど、実行 ID によって追跡されます。 (#42819、#42821、#42822)
  • ネストされたエージェントのログと使用状況レコードは、ソース ワークフロー ID と外部実行との関係を保持します。 特に一時停止または停止後は、ネストされた使用量とステップの合計がおおよその値になる可能性があります。 (#42824、#42820)

エージェントの出力ルートとストリーミング

  • エージェント v2 ノードは、タスクを完了する一環としてワークフロー ブランチを選択できます。出力ルートを有効にし、少なくとも 2 つの分岐とその選択条件を定義し、読み取り専用の switch 出力を使用して選択されたルートを検査します。ルーティングを無効にしても、通常の成功アウトレットは利用可能なままです。ルーティングされたノードは、エラー時の停止または失敗時の分岐をサポートします。ルートが有効な場合、ノードレベルのデフォルト値の処理は使用できません。 (#42599)
  • Plain Agent v2 ノードは、生成されたテキストをストリーミングします。構造化またはルーティングされた結果はバッファされたままであり、デフォルト値のエラー処理を使用するノードもバッファされたままであるため、構成されたフォールバックで失敗した結果を置き換えることができます。 (#43986)

OpenAPI と difyctl を使用したアプリの構築と管理

  • /openapi/v1 はサーバー運用カタログを公開します。 difyctl は、そのカタログからコマンドとその入力フィールドを検出し、検索可能なヘルプを提供し、サーバーが提供する次のステップに従います。ワークフローとチャットフローのオーサリングには、アプリの作成、DSL インポート/エクスポート、設定、環境変数、公開、バージョンの復元が含まれるようになりました。ドラフト ハッシュは、インポートを同時編集の上書きから保護します。 (#42487、#42608、#43067)
  • CLI には、Dify アプリを構築するエージェント向けの difyctl スキルが含まれています。 difyctl install skills <dir>と合わせて取り付けます。デバイスのログインは --no-wait および --resume をサポートし、フォルダーのアップロードではファイルごとに 1 つのマルチパート パートが送信されます。 (#43819、#44356)
  • ワークスペース所有者は、選択したアプリまたはナレッジ ベースにバインドされたリソース アクセス トークンを作成できます。トークンは、サポートされているサービス API ルートおよび difyctl のアプリ操作で機能します。ワークスペース管理は許可されません。 [設定] エントリは NEXT_PUBLIC_ENABLE_ACCESS_TOKEN を通じてオプトインされており、デフォルトは false です。 (#42293、#44422)

サンドボックスからエージェント プロンプトを編集

  • dify-agent config prompt pull [--to PATH] および push [PATH|-] は、UTF-8、空白、およびメンション マーカーを保持しながら、生のシステム プロンプトを読み取るか置き換えます。空のテキストを入力するとクリアされます。現在のアカウントの書き込み可能なビルド ドラフトのみを変更できます。後のリクエストでは、保存されたプロンプトが使用されます。 (#44561)

エージェント実行トレース

  • エージェント アプリとワークフロー エージェント v2 ノードは、既存のトレース プロバイダーを通じてエージェント、モデル、ツール実行ツリーをエクスポートできます。モニタリングにより、共有トレース構成、配信ステータス、再試行制御、および選択した実行に属するトレースへのリンクが追加されます。ワークフローによって参照されるエージェントは、呼び出し元のトレース ポリシーを継承します。 (#44144、#44186)
  • アプリケーション トレースは、API とエージェント バックエンドの両方でオプトインされています。システム トレースとは別に、展開全体にわたる別の OTLP 軌跡エクスポーターも使用できます。 (#42651、#44144)
  • 呼び出されたワークフロー ツールの内部ノードは、外部エクスポートから除外されます。これは、これらのエクスポートにはソース アプリのアクセス チェックのためのビューア ID がないためです。呼び出されたツール内のエージェントも、今のところ新しい実行ツリーのエクスポートから除外されています。承認されたコンソールのドリルダウンは引き続き利用可能です。 (#42823、#44144)

OpenShell サンドボックス バックエンドと E2B 使用状況の収集

  • エージェントの実行では、DIFY_AGENT_RUNTIME_BACKEND=openshell を備えたセルフホスト型 NVIDIA OpenShell ゲートウェイを使用できます。各バインディングには、認証されたシェル アクセス、オペレーター管理の共有ボリューム上のホーム スナップショット、およびオプションの出力許可リストを備えた独自のサンドボックスがあります。 OpenShell ゲートウェイ 0.0.106 以降と互換性のあるランタイム イメージが必要です。 (#41076)
  • OpenShell のリースを解放すると、接続は閉じられますが、サンドボックスは実行されたままになります。自動アイドルストップやサンドボックス TTL はありません。オペレーターはそれらのリソースを管理する必要があります。マルチテナント展開には、テナントごとに個別の OpenShell ワークスペースとスナップショット ボリュームが必要です。 OpenShell 導入ガイド を参照してください。
  • オプションの E2B 使用状況収集は、Celery Beat および ops_trace キューを通じてプロバイダーの実行時間とリソース サイズを記録します。収集は構成されたアクティブ化時間から開始され、以前の実行はバックフィルされません。 API とエージェント バックエンド メータリング フラグはどちらもデフォルトでオフになっています。 (#42554)

クラウド アクセス制御、テンプレート、およびアーカイブ管理

  • 再利用可能なネットワーク アクセス グループにより、サポートされているクラウド展開で、権限チェック、有効なポリシー ステータス、および trusted client-IP プレビューを使用して、アプリ間で IP ルールを共有できます。適用はクラウド ポリシー サービスとゲートウェイに依存します。これはスタンドアロンの Community Edition ファイアウォールではありません。 (#41025、#44464)
  • クラウド ユーザーは、公開されたエージェント テンプレートをインポートする前にプレビューして試すことができます。エージェントの「テンプレートから作成」は、テンプレート データ ソースがクラウド専用であるため、Community Edition および Enterprise Edition では非表示になります。 (#42837、#44035)
  • Cloud Workflow Log Archives では、ワークスペース所有者は、確認、進行状況、再試行を行って、選択した月を完全に削除できます。このアクションにより、アーカイブされたオブジェクトと準備された ZIP ダウンロードが削除されます。ライブ ワークフロー実行レコードはその範囲外です。失敗した削除ジョブは、成功を報告するのではなく、再試行ポリシーに入るようになりました。 (#44052、#44061、#44203)

ワークフローとスケジュール

  • コラボレーション中に LLM プロンプト/モデルの変更を保持し、インポートされたグラフを正しく同期します。コード生成では、存続するパラメーター名の入力バインディングが保持され、複数行/非構造化署名とカンマを含む Python パラメーターが理解され、ユーザー コード内のリテラル {{inputs}} テキストが保持されます。 (#42124、#42817、#44075、#44046、#44337、#43438)
  • ワークフローに貼り付けるとき、およびエディターでワークフロー グラフをロード/保存するときに、サポートされていないチャットフロー メモリ設定を削除します。既存の公開バージョンまたは API 専用フローは、このエディターの修正によって書き換えられません。 (#43597、#43752)
  • コード ノードの出力が削除、追加、または名前変更された場合に、構成されたフォールバック値を保持します。空のキャンバスを保存する前に確認が必要です。実行中のツール ファイルへのアクセスを後のノードでも保持します。 (#42678、#43668、#41300)
  • タスクの所有権を保持し、インテントを停止するため、遅延書き込みや同時再開によって停止したワークフローを復活させることはできません。失敗した非同期トリガー ディスパッチはトリガー ログに失敗として記録され、再開後も経過時間は一貫したままになります。 (#40277、#43009、#44161)
  • スケジュールされたファイア アンド フォーゲット ディスパッチでは、タスク グループごとに Redis 結果バックエンド ドレイナーが作成されなくなり、アイドル状態の結果接続が蓄積されるのを防ぎます。同じ修正は、トリガーのリフレッシュとパイプラインのディスパッチにも適用されます。 (#44551)
  • ドラフトを編集しても、公開されたトリガー サブスクリプションは削除されなくなりました。これにより、新たな損傷は防止されますが、アップグレード前にすでに失われた関係は再構築されません。 (#44068)

エージェントとスキル

  • ツール呼び出しをキャンセルした後も会話を継続できます。再生されたツール呼び出し ID は安定したままになります。並行ツールの結果は自分の考えに固執したままになります。また、最初のイベント書き込みエラーは、実行を実行したままにするのではなく、実行を終了します。 Redis イベント リプレイは Redis 6 でも動作します。 (#41846、#43796、#43843、#43959、#44420)
  • E2B は、より安全な再試行動作を備えた SDK 2.55.1 を使用します。リソースの作成は、あいまいな 502 の後に再実行されませんが、安全なライフサイクル操作により一時的な障害からの回復が保持されます。一時停止とホーム スナップショットは明示的にフルメモリ モードを要求します。 (#43930)
  • E2B サンドボックスの取得では、ホーム リソースとワークスペース リソースが存在するかどうかがチェックされ、欠落が確認されたエンタープライズ ホーム スナップショットは削除が成功したものとしてカウントされます。 (#44014、#44085)
  • スキル添付ファイルは、フォーマットされた DOCX テキスト、RTF Unicode フォールバック長とバイナリ境界、および PPTX プレゼンテーション順序を保持します。 (#43718、#43789、#43893)
  • RTF 抽出では、切り詰めの前に UTF-16 サロゲート ペアを結合し、一致しないサロゲートを置き換えて、UTF-8 エンコードの失敗を回避します。 (#44565)

知識と検索

  • CSV セルの内容、Notion の言及/数式、再帰的分割の改行を保持します。 URL インポートでは、コンテンツ タイプから有用なファイル拡張子が推測され、サポートされていないパイプライン ファイル タイプは明示的なエラーを返します。影響を受けるドキュメントを再インポートして、すでに誤ってインデックス付けされているコンテンツを再生成します。 (#42159、#42171、#44179、#42364、#44012)

dify 1.18.0

Dify 1.18.0 brings Agents that route workflows, portable app packages, deeper visibility into nested workflow runs, and the opt-in Agent Knowledge Base experience. OpenAPI and the new difyctl expand how you build and manage apps from the command line.

[!IMPORTANT] Read the upgrade guide below before deploying. Upgrade the API, workers, Agent Backend, and Agent runtime images together. Local Agent sandboxes require a non-empty authentication token, and Agent Backend uses a new run protocol. Source installations require Python 3.13. Install the new difyctl client and sign in again. Preserve your existing PASSWORD_PEPPER configuration.

Release highlights

Agents that choose the next step

Let an Agent decide which workflow branch to take. Enable Output Routes, give each route a selection condition, and connect it to the next step—such as resolving a request directly or handing it to a specialist. The read-only switch output exposes the chosen route. (#42599)

Output Routes configuration with two branches in the workflow editor.

Plain Agent v2 nodes also stream text as it is generated. Structured results, routed results, and nodes using default-value error handling remain buffered. (#43986)

Portable apps in one package

Move an app with its supported resources in a single .ifpkg package. Workflow and Chatflow packages carry inline Agents, Skills, and their files; imports recreate those resources in the destination workspace and remap references. File and URL imports support both packages and YAML, and explicit YAML export remains available. (#42066, #42579, #42626, #42863)

Studio's .ifpkg import preview.

See inside nested workflow runs

Open a Workflow Tool invocation from the run history and inspect the child workflow's individual steps. Nested tools now run as child graphs with coordinated pause, resume, stop, and file outputs. Access checks protect the source app's details. (#40277, #42819, #42820, #42821, #42822)

Trace drilldown into a successful Workflow Tool invocation.

Nested usage and step totals can still be approximate, particularly after a pause or stop. Console drilldown and external trace export have different scopes; see the full feature details below.

Agent Knowledge Base · Beta

Create a knowledge space for your agents, add files or connect sources, and inspect document processing, metadata, retrieval traces, and quality evaluations in one place. The new Knowledge Retrieval node and Agent integrations share access-controlled KnowledgeFS spaces. Classic Knowledge remains available. This is an opt-in integration with a separate service and database; see the deployment requirements below. (#44165)

Will soon be available on cloud.dify.ai

Developer spotlight

Build and manage apps with OpenAPI and difyctl. The CLI discovers commands from the server's operation catalog, with searchable help and support for Workflow and Chatflow creation, DSL import/export, settings, environment variables, publishing, and version restoration. Draft hashes protect concurrent edits. (#42487, #42608, #43067)

Install the bundled skill for agents building Dify apps:

difyctl install skills <dir>

The new client requires a fresh sign-in; see the deployment instructions below. (#43819)

Upgrade guide

Compatibility and Rollout

  1. Back up first. Retain the database, vector-store data, uploaded files, Agent snapshot/workspace storage, and all deployment secrets and env files. Use a maintenance window for a single-stack upgrade.
  2. Upgrade the Agent components together. /runs now accepts composition v2 and rejects v1 requests. Existing session snapshots are converted on read and saved as v2; old runtimes cannot read newly saved v2 snapshots. Direct Agent Backend integrations must update their request format. The old Agent-specific AskHuman tool and deferred resume path are removed: historical Agent forms no longer resume execution, while shared Workflow Human Input nodes remain supported. (#43833)
  3. Retire old workflow consumers before admitting new-version traffic. Let in-flight runs finish, then replace legacy workers/resume consumers so they cannot process the shared queue without the new cancellation guards. Legacy paused task IDs can be recovered from valid saved invocation snapshots within the existing access scope; missing or invalid snapshots require separate recovery. Nested usage totals retain the limitation noted above. (#40277)
  4. Configure the Local sandbox token before restart. Supply a high-entropy secret through the shared Compose interpolation source. The 1.17.1 runtime image does not support the new --require-auth-token flag; deploy the matching 1.18.0 Agent Backend and Local sandbox images. (#44152)
  5. Preserve password hashing configuration. Existing installations without a pepper should leave PASSWORD_PEPPER empty. Setting a new pepper during the upgrade is not a transparent migration and requires an explicit password-reset plan. Keep any configured pepper unchanged across all instances and restore it with the database.
  6. Review the proxy boundary. Bundled Nginx replaces X-Forwarded-For with its resolved client address, and Compose enables forwarded-header handling. Keep direct API access restricted to trusted callers. If a load balancer or Cloudflare sits before Nginx, configure trusted real-IP handling there; otherwise visitors may share the proxy’s rate-limit bucket. See client IP and trusted proxies.
  7. Enable KnowledgeFS deliberately. Default Compose installations keep it off; local Community Edition development requires the explicit Community development opt-in. Configure its separate database and migrations, Capability v2 public verifier, Dify signing keys, model profile (embedding, reasoning, and rerank), and Workspace cutover gates before enabling traffic. The optional service must pass /ready, not only /health. Standard Dify API images do not contain the separate KnowledgeFS engine used by the optional engine-worker profile; the published default KnowledgeFS API image is currently amd64 only. Follow the KnowledgeFS deployment and recovery guide.
