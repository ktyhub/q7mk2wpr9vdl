リリース ハイライト <a id="v2100-release-highlights"></a>

シークレット管理 <a id="v2100-highlight-secrets-management"></a>

コレクターの資格情報をプレーンテキストの構成ファイルに含めないようにしてください。 Netdata では、シークレットを直接保存するのではなく、コレクター設定でシークレットを参照できるようになりました。パスワード、トークン、および API キーは、選択したソースから実行時に解決されます。

リゾルバー

Netdata は、シンプルなものからエンタープライズ グレードまで、次の 4 つのリゾルバー タイプを提供します。

|リゾルバー |構文 |最適な用途 | |:-------------------------------------|:--------------------------------------------|:--------------------------------------------------------------------------------------------| | 環境変数 | ${env:VAR_NAME} |シークレットは Netdata サービス環境にすでに挿入されています。 | ファイル | ${file:/absolute/path} |ディスク上のローカル ファイルに保存されたシークレット (ボリュームとしてマウントされた Docker シークレット、Kubernetes シークレット) | | コマンド | ${cmd:/absolute/path args} | trusted ローカル コマンドによって返されるシークレット (例: 1Password CLI、カスタム スクリプト) | シークレットストア | ${store:<kind>:<name>:<operand>} |シークレットはクラウド プロバイダーまたは Vault で一元管理されます。

サポートされている Secretstore バックエンド

シークレットを一元管理している組織の場合、Netdata は 4 つの Secretstore バックエンドと統合します。

|バックエンド |種類 |オペランドの形式 |認証モード | |:------------------------------------------------------------------------------------------------------------------------------|:----------|:-------------------------------------|:--------------------------------------------------------| | AWS シークレットマネージャー | aws-sm | secret-name[#key] |環境認証情報、ECS タスクロール、EC2 インスタンスプロファイル | | Azure Key Vault | azure-kv | vault-name/secret-name |サービス プリンシパル、マネージド ID、デフォルトの資格情報チェーン | | Google シークレット マネージャー | gcp-sm | project/secret[/version] |メタデータ サーバー、サービス アカウント ファイル | | ハシコープ保管庫 | vault | path#key |トークン、トークンファイル |

Netdata 動的構成 UI (Collectors → go.d → SecretStores) または /etc/netdata/go.d/ss/ の構成ファイルを介してシークレットストアを構成します。

例

HashiCorp Vault からパスワードを参照する MySQL コレクター:

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

リゾルバの種類は自由に組み合わせることができます。たとえば、同じ設定値の環境変数からユーザー名を読み取り、シークレットストアからパスワードを読み取ります。

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

仕組み

  • シークレットは、コレクター ジョブが開始または再起動されるたびに解決されます。
  • シークレットストアを更新すると、それを使用するコレクタ ジョブが自動的に再起動され、新しい認証情報が取得されます。
  • Secretstore の構成値自体も ${env:...}、${file:...}、${cmd:...} リゾルバーをサポートしているため、バックエンドの資格情報をプレーン テキストで保存する必要もありません。

[!ヒント] 詳細なセットアップ、バックエンド固有の認証ガイド、およびトラブルシューティングについては、Secrets Management ドキュメント を参照してください。

Nagios プラグイン コレクター <a id="v2100-highlight-nagios-plugins"></a>

新しい Nagios プラグイン コレクター を使用して、Nagios 互換プラグイン とカスタム スクリプトを Netdata 内で直接実行します。 Nagios プラグイン出力形式 に従う実行可能ファイルはすべて、パッケージ化された Nagios プラグイン、カスタム シェル スクリプト、またはコンパイルされたバイナリなど、そのまま使用できます。

得られるもの

|特集 |詳細 | |:-------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------| | 状態監視のチェック |プロセス終了コードから OK、WARNING、CRITICAL、UNKNOWN の状態を追跡します。 | 自動パフォーマンス データ チャート | Nagios パフォーマンス データ値は自動的に解析され、グラフ化されます。 | しきい値ベースのアラート | perfdata に警告/クリティカルしきい値が含まれる場合、Netdata はしきい値状態グラフ (ok/警告/クリティカル) を導出し、組み込みアラートを作成します。 | 実行メトリクス |各チェックの実行時間、CPU 時間、メモリ使用量を測定します。 | Nagios スタイルのスケジューリング |構成可能なチェック間隔、再試行間隔、最大チェック試行、および期間 | | ソフト/ハード ステート ロジック |非 OK の結果は、アラートをトリガーする前に retry_interval から max_check_attempts まで再試行し、一時的な障害による誤ったアラームを防ぎます。

組み込みアラート

コレクターには 4 つの在庫アラートが同梱されています。

|警告 |トリガー条件 | |:------------------------------------------|:--------------------------------------------| | nagios_job_execution_state_warn |チェックは警告ハード状態です | | nagios_job_execution_state_crit |チェックは重大なハード状態です | | nagios_job_perfdata_threshold_state_warn | perfdata メトリックが警告しきい値を超えています。 | nagios_job_perfdata_threshold_state_crit | perfdata メトリックがクリティカルしきい値を超えています。

すべてのストック アラートはソフト再試行状態を抑制します。アラートは、設定された max_check_attempts が連続して失敗した場合にのみ起動されます。

例

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0

# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

これにより、チェック ステート チャート、実行メトリックが生成されます。また、スクリプトはしきい値 (warn >2s / crit >5s の response_time) を含むパフォーマンス データを出力するため、しきい値ステート チャートと組み込みアラートを備えた自動応答時間チャートが生成されます。

[!ヒント] 完全なセットアップ ガイド、カスタム スクリプトのウォークスルー、および期間の設定については、Nagios Plugins コレクターのドキュメント を参照してください。

Azure Monitor コレクター <a id="v2100-highlight-azure-monitor"></a>

新しい Azure Monitor コレクター を使用して、Netdata から Azure インフラストラクチャ全体を監視します。 自動リソース検出を使用して、Azure Monitor メトリック API からプラットフォーム メトリックを収集します。サブスクリプションをポイントすると、リソースが見つかり、組み込みプロファイル (事前構成されたメトリック セット) と照合され、メトリックの収集が開始されます。

[!重要] これは アルファ版の機能です。構成形式は今後のリリースで変更される可能性があります。

Release Highlights <a id="v2100-release-highlights"></a>

Secrets Management <a id="v2100-highlight-secrets-management"></a>

Keep collector credentials out of plain-text configuration files. Netdata now lets you reference secrets in collector configurations instead of storing them directly. Passwords, tokens, and API keys are resolved at runtime from the source you choose.

Resolvers

Netdata provides four resolver types, from simple to enterprise-grade:

| Resolver | Syntax | Best For | |:-------------------------|:-----------------------------------|:----------------------------------------------------------------------------------------------| | Environment variable | ${env:VAR_NAME} | Secrets already injected into the Netdata service environment | | File | ${file:/absolute/path} | Secrets stored in local files on disk (Docker Secrets, Kubernetes Secrets mounted as volumes) | | Command | ${cmd:/absolute/path args} | Secrets returned by a trusted local command (e.g., 1Password CLI, custom scripts) | | Secretstore | ${store:<kind>:<name>:<operand>} | Secrets managed centrally in cloud providers or Vault |

Supported Secretstore Backends

For organizations managing secrets centrally, Netdata integrates with four secretstore backends:

| Backend | Kind | Operand Format | Authentication Modes | |:------------------------------------------------------------------------------------------------------------------------------------|:-----------|:---------------------------|:--------------------------------------------------------------| | AWS Secrets Manager | aws-sm | secret-name[#key] | Environment credentials, ECS task role, EC2 instance profile | | Azure Key Vault | azure-kv | vault-name/secret-name | Service principal, Managed identity, Default credential chain | | Google Secret Manager | gcp-sm | project/secret[/version] | Metadata server, Service account file | | HashiCorp Vault | vault | path#key | Token, Token file |

Configure secretstores through the Netdata Dynamic Configuration UI (Collectors → go.d → SecretStores) or via configuration files under /etc/netdata/go.d/ss/.

Example

A MySQL collector referencing its password from HashiCorp Vault:

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

You can mix resolver types freely. For example, read the username from an environment variable and the password from a secretstore in the same config value:

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

How It Works

  • Secrets are resolved each time a collector job starts or restarts.
  • Updating a secretstore automatically restarts collector jobs that use it so they pick up new credentials.
  • Secretstore configuration values themselves also support ${env:...}, ${file:...}, and ${cmd:...} resolvers, so backend credentials don't need to be stored in plain text either.

[!TIP] For detailed setup, backend-specific authentication guides, and troubleshooting, see the Secrets Management documentation.

Nagios Plugins Collector <a id="v2100-highlight-nagios-plugins"></a>

Run Nagios-compatible plugins and custom scripts directly inside Netdata with the new Nagios Plugins collector. Any executable that follows the Nagios plugin output format works out of the box: packaged Nagios plugins, custom shell scripts, or compiled binaries.

What You Get

| Feature | Details | |:--------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------| | Check State Monitoring | Tracks OK, WARNING, CRITICAL, and UNKNOWN states from the process exit code | | Automatic Performance Data Charts | Nagios performance data values are parsed and charted automatically | | Threshold-Based Alerting | When perfdata includes warning/critical thresholds, Netdata derives a threshold state chart (ok/warning/critical) and creates built-in alerts | | Execution Metrics | Measures run duration, CPU time, and memory usage of each check | | Nagios-Style Scheduling | Configurable check intervals, retry intervals, max check attempts, and time periods | | Soft/Hard State Logic | Non-OK results retry at retry_interval up to max_check_attempts before triggering alerts, preventing false alarms from transient failures |

Built-in Alerts

The collector ships with four stock alerts:

| Alert | Triggers When | |:-------------------------------------------|:-------------------------------------------------| | nagios_job_execution_state_warn | A check is in WARNING hard state | | nagios_job_execution_state_crit | A check is in CRITICAL hard state | | nagios_job_perfdata_threshold_state_warn | A perfdata metric exceeds its warning threshold | | nagios_job_perfdata_threshold_state_crit | A perfdata metric exceeds its critical threshold |

All stock alerts suppress soft retry states. Alerts fire only after the configured max_check_attempts consecutive failures.

Example

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0

# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

This produces check state charts, execution metrics, and because the script emits perfdata with thresholds (response_time with warn >2s / crit >5s), an automatic response time chart with a threshold state chart and built-in alerts.

[!TIP] For the full setup guide, custom scripts walkthrough, and time period configuration, see the Nagios Plugins collector documentation.
