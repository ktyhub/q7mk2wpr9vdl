プロジェクト

  • DSL クラスローディングマシンを core/dsl の下に移動します。 core/classloader は、DSL タイプ (RuleClassLoader、DSLClassLoaderManager、ClassLoaderGc、UnloadProbePayload、および BytecodeClassDefiner) のみを保持していました。そのため、現在は core/dsl/classloader になり、ルール ファイル分類はクラス読み込みの問題ではないため、Catalog は core/dsl に移動します。 「生成されたクラスを適切なローダーに定義する」ディスパッチの 3 つのコピー (MAL、LAL、MeterSystem) は静的 BytecodeClassDefiner.define に折りたたまれます。これにより、JDK 17 --add-opens の根拠も 4 つではなく 1 つになります。生成されたクラスのダンプ ディレクトリ ルックアップの 4 つのコピーのうち 3 つは DslGeneratedFileWriter.resolveClassDumpDir になります。 OAL は独自のデバッグ フラグを保持します。これは、そのデバッグ フラグが環境変数とは独立して設定可能であり、2 つのテストがそれに依存しているためです。行動の変化はありません。
  • GET /inspect/entities 管理者 API を拡張して、任意 OAP (このノードがローカルに定義していないものでも) によって保持されるメトリックを検査します。メトリックがローカル レジストリで不明な場合、呼び出し元は valueColumn + valueType を指定し、ストレージ バックエンドは独自の実行構成から物理インデックス/テーブル/グループを解決します (DB スキーマ/テーブル メタデータの読み取りなし)。ES はマージされた metrics-all インデックス + metric_table 識別子を使用し、JDBC は table_name 識別子によってノードの関数テーブルを調査します。 BanyanDB は読み取り専用のメジャー スキーマを合成します。スコープは不要になりました。entity_id は、汎用の name リーフを使用して構造的に (サービス / 第 2 レベル / リレーション) デコードされます。ローカルで定義されたメトリックは、以前と同様に正確なフィールド名、スコープ、および mqeEntity を保持します。
  • POST /inspect/values 管理者 API を追加します。{valueColumn, valueType} を指定することで、別 OAP (このノードがローカルに定義していないもの) によって保持されているメトリックの値シリーズを読み取ります。実際の MQE エンジンは、リクエスト スコープの InspectQueryContext オーバーレイ (存在しない場合は常にローカル カタログが優先) 上で実行され、外部メトリックがすべての読み取りパスに登録されているように見えます。ValueColumnMetadata はその値の列 / タイプ / スコープを解決し、格納場所レジストリはその値が存在する場所を解決します (MetadataRegistry は BanyanDB メジャー スキーマを合成し、IndexController は ES metrics-all を解決します)。インデックス、TableHelper は JDBC 関数テーブルをプローブします)、そのため、読み取りでは、DAO ごとの特殊ケースのないネイティブ MQE ExpressionResult が返されます。管理者専用 (この OAP は強制読み取りを検証できません)。パブリック REST / GraphQL サーフェスにはミラーリングされません。 API の検査 を参照してください。
  • 常時オンのアラームからイベントへの変換 (EventHookCallback) を削除します。トリガーされたアラームは、Alarm/AlarmRecovery イベントとしてイベント パイプラインに合成されなくなりました。イベントは実際のイベント ソース (エージェント、SkyWalking CLI、Kubernetes Event Exporter) からのみ発生するようになりました。アラームは、アラーム ストア (getAlarm/queryAlarms) および設定されたアラーム フックを通じて引き続き使用できます。これにより、文書化された「既知のイベント」が削除され、警報火災ごとに 1 ～ 2 つの合成イベント レコードが削除されます。
  • 証明書ホットリロードを備えたすべての OAP HTTP/REST サーバーの TLS。 すべての OAP HTTP サーバー (コア REST、共有サーバー、管理、PromQL、LogQL、TraceQL、および Zipkin クエリ/レシーバー) に restSSLEnabled / restSSLKeyPath / restSSLCertChainPath 構成構造を追加します。それぞれに独自の専用環境変数 (SW_CORE_REST_SSL_*、SW_RECEIVER_SHARING_REST_SSL_*、 SW_ADMIN_SERVER_REST_SSL_*、SW_PROMQL_REST_SSL_*、SW_LOGQL_REST_SSL_*、SW_TRACEQL_REST_SSL_*、SW_QUERY_ZIPKIN_REST_SSL_*、SW_RECEIVER_ZIPKIN_REST_SSL_*)。共有 Armeria HTTPServer は、ローテーション (TlsProvider.ofScheduled 経由) でディスクからキー ペアをリロードするため、OAP を再起動せずに更新された証明書が取得され、既存の gRPC SSL ホットリロード動作と一致します。 HTTP TLS はサーバー側のみです (mTLS はありません)。
  • 新しい queryAlarms GraphQL クエリ — アラームのエンティティ/レイヤー/ルール フィルター。 従来の getAlarm に加えて、包括的なアラーム クエリ API を追加します。新しい queryAlarms(condition: AlarmQueryCondition!): Alarms は、アラーム レコードが保存するすべてのフィルターをバンドルする単一の入力タイプを受け入れます。 entities: [Entity!] (MQE Entity 形状を再利用 — アラーム id0 または id1 と一致する特定のサービス/インスタンス/エンドポイント/プロセスまたはそれらの関係にピン留め); layer: String (アラームが発生したエンティティのレイヤーによるフィルター - アラーム行は 1 つのレイヤーに保持されるため、単一の一致)。 ruleNames: [String!] (アラーム ルールが起動されたフィルター);さらに、keyword、tags、duration、paging。レガシー getAlarm は @deprecated とマークされていますが、依然として同じ DAO にルーティングされます。client は破損しません。バックエンドの追加: AlarmRecord 上の新しい layer 列は、アラームミント時に MetadataQueryService.getService(serviceId).getLayers() 経由で設定されます。既存の id0/id1 列は storageOnly = true からインデックス付きに反転され、エンティティ フィルターがストレージにプッシュダウンされました。 IAlarmQueryDAO.queryAlarms(condition, limit, from) は新しい抽象メソッドです。オーバーライドを見逃すと、サードパーティのストレージ バックエンドはコンパイルに失敗します (SWIP-14 パターン)。バンドルされている 3 つのバックエンドはすべて、BanyanDB / Elasticsearch / JDBC を実装しています。 演算子のセマンティクス: (1) リレーション エンティティは完全一致です。 {scope: ServiceRelation, serviceName: A, destServiceName: B} を渡すと、id0=serviceId(A) AND id1=serviceId(B) のアラームのみに一致し、どちらかの側で A または B に接触するアラームには一致しません。より広範な「A に関係するもの」クエリでは、代わりに個々の非関係エンティティ ({scope: Service, serviceName: A} - id0=A OR id1=A に拡張) を渡す必要があります。 (2) アラーム行ごとに 1 つのレイヤー。 永続列には 1 つのレイヤー (エンティティの解決されたレイヤー リストの最初のエントリ、リレーションの場合はソースが最初) が格納されます。メタデータが最初に GENERAL に解決される [GENERAL, K8S_SERVICE] のサービスは、GENERAL の下にファイルされます。 layer: "K8S_SERVICE" をクエリすると見逃されます。 オペレータ移行に関する注意事項: 既存のアップグレード前のアラーム行は引き続き従来の getAlarm フィールドでフィルタリングできます。 queryAlarms の新しいエンティティ/レイヤー/ルール フィルターは、アップグレード後に書き込まれたアラームにのみ適用されます (既存のストレージ インデックスは所定の位置で index: false → true に移行しません。新しい日次ロール インデックスはインデックス付き列を選択します)。スキーマの追加は非ブロッキングです。ブートストラップは既存のインデックスの列属性の変更をサイレントにスキップします。
  • 🚨 重大な変更: apm-webapp および skywalking-booster-ui サブモジュールが削除されました。 この OAP ディストリビューションには、バンドルされた Web UI が同梱されなくなりました。 apm-webapp/ のレガシー Armeria リバース プロキシ (skywalking/ui Docker イメージを動かしたバイナリ) と skywalking-ui git サブモジュール (apache/skywalking-booster-ui を追跡した) は両方とも、docker.ui Maven ターゲット、skywalking/ui Docker イメージ ビルド、apm-dist/ Web アプリ パッケージ化、およびビルドまたはプッシュされたすべての CI ワークフロー パスとともに削除されます。 UIイメージ。現在、公式 UI は Horizo​​n UI となっており、独自のスケジュールで OAP バックエンドを独立してリリースする SkyWalking サブプロジェクトで、コンテナ イメージは apache/skywalking-ui の Docker ハブにリリースされています (タグ latest / horizon-<version>、コミットごとの開発イメージは ghcr.io/apache/skywalking-horizon-ui にあります)。 OAP バージョンと Horizo​​n UI バージョンの間には 1 対 1 のマッピングはありません。オペレーターは展開内で UI イメージ タグを固定し、2 つを別々の頻度でアップグレードします。 Horizo​​n UI は、OAP のパブリック GraphQL/REST サーフェス (デフォルト 12800) と管理ホスト (デフォルト 17128) を使用します。 oap-server/server-starter/src/main/resources/ui-initialized-templates/ 内のディスク上のダッシュボード シード ファイルは削除されます。 ZZPH100​​ZZ / UIMenuInitializer は CoreModuleProvider.notifyAfterCompleted() から削除され、Horizo​​n UI には独自のダッシュボード ライブラリと独自のサイドバー メニューが同梱されています。 UI テンプレートは、管理サーバー上の新しい /ui-management/templates/* REST サーフェスを通じて作成および更新されるようになりました (以下を参照)。すべての UI 関連の GraphQL ミューテーションとクエリ (UIConfigurationManagement: addTemplate、changeTemplate、disableTemplate、getAllTemplates、getDashboardConfiguration、getMenuItems) は、SW_ENABLE_UPDATE_UI_TEMPLATE フラグとともにパブリック GraphQL スキーマから廃止されました。 OAP バックエンドもサイドバー メニューの保存や提供を行わなくなりました。UIMenuManagementService、UIMenuManagementDAO、UIMenu、MenuItem、およびストレージ インプリメントはすべて削除されました。 Horizo​​n UI はメニュー client 側を所有し、動的な「レイヤーにサービスがある」ゲーティングに listServices(layer:...) を使用します。アップグレード パス: 導入環境で skywalking/ui:<tag> を Horizon UI イメージ apache/skywalking-ui:latest (または horizon-<version> タグ - Horizon UI の OAP 互換性に関する注意事項に従ってバージョンを選択し、OAP 11.0+ がサポートされています) に置き換え、OAP コンテナからポート 17128 を公開し、従来の GraphQL UI ミューテーションを呼び出したスクリプトを以下の REST エンドポイントに移行します。 UI 管理 API。すべてのステータス/デバッグ エンドポイント (/status/*、/debugging/*) も管理者専用に移行します。ステータスのパブリック REST デュアル バインドは、同じリリースで廃止されます。
  • 新しい ui-management 管理モジュール — ダッシュボード テンプレート用の REST サーフェス。 管理サーバー (ポート 17128) で 5 つの操作をホストします: GET /ui-management/templates、GET /ui-management/templates/{id}、POST /ui-management/templates、PUT /ui-management/templates、POST /ui-management/templates/{id}/disable。既存の UITemplateManagementService に転送します (ストレージ DAO の変更なし)。デフォルトで有効になります (SW_UI_MANAGEMENT=default、デフォルトでオンになっている管理ホスト上)。廃止された GraphQL UIConfigurationManagement テンプレート リゾルバーを置き換えます。サイドバー メニューは意図的に提供されていません。上記の重大な変更のエントリを参照してください。オペレーターリファレンス: UI Management API。
  • すべての管理機能モジュールはデフォルトでオンになっています。 admin-server、status、inspect、ui-management、dsl-debugging、および receiver-runtime-rule はすべてデフォルトで有効になっています。特定の機能を必要としないオペレーターは、SW_* 環境変数を空に設定します。これにより、管理ホストがすでにオンになっているにもかかわらず、ランタイム ルール / DSL デバッグ サーフェスで明示的なオプトインが必要だった 10.4.0 とのユーザビリティのギャップが解消されます。
  • ステータス API が管理ホストに移動されました。 ステータス/デバッグ ルート (/status/*、/debugging/*) が管理サーバー REST ホスト (デフォルト 17128) に登録されるようになりました。 core.restPort (デフォルトは 12800) にミラーリングされなくなりました。ステータスを他のすべての管理機能モジュール (検査、DSL デバッグ、ランタイム ルール、UI 管理) と調整します。 Horizo​​n UI は管理ホストからステータスを消費します。 URI とペイロードは変更されません。ホストだけが移動しました。 1 つの例外: /status/config/ttl はパブリック REST ホスト (12800) にもバインドされているため、/graphql を発行する前に REST 経由で TTL 境界を検出するエコシステム ツールは管理ポートを学習する必要がありません。
  • 新しい admin-server モジュール — 管理/オンデマンド書き込み API 用の共有ホスト。 2 つのポートで実行: オペレーター側エンドポイント用の HTTP REST サーフェス (デフォルト 17128) と、ピアツーピア クラスター RPC 用の 管理内部 gRPC バス (デフォルト 17129) (ランタイム ルール)一時停止/再開/転送、DSL デバッグのインストール/収集/停止/stopByClientId)。管理内部バスは、パブリック エージェント/クラスターの gRPC ポート (core.gRPCPort、デフォルト 11800) とは別の専用トランスポートであるため、特権管理 RPC はエージェント ネットワークの影響範囲外に留まります。オペレーターは gRPCHost をプライベート ピアツーピア インターフェイスにのみバインドします。ランタイム ルール プラグインと新しい DSL デバッグ API (下記) は両方ともこの共有ホストにマウントされます。 デフォルトで有効になっているため、すぐにステータス機能モジュールにアクセスできます。ホストは 0.0.0.0:17128 にバインドされ、認証が組み込まれておらず、IP 許可リストでゲートウェイで保護されている必要があり、決して公共のインターネットに公開しないでください (管理者 API セキュリティ通知 を参照)。完全に無効にするには、SW_ADMIN_SERVER= (空) を設定します。 runtime-rule config ブロックは、restHost/restPort/restContextPath/restIdleTimeOut/restAcceptQueueSize/httpMaxRequestHeaderSize キー (および一致する SW_RECEIVER_RUNTIME_RULE_REST_* 環境変数) を失います。ホストレベルのノブは、新しい admin-server ブロック (SW_ADMIN_SERVER_HOST / SW_ADMIN_SERVER_PORT / SW_ADMIN_SERVER_GRPC_HOST / SW_ADMIN_SERVER_GRPC_PORT / SW_ADMIN_SERVER_INTERNAL_COMM_TIMEOUT など) の下に移動します。
  • MAL および LAL のランタイム ルールのホット アップデート。 オペレーターは、OAP を再起動せずにメトリック (MAL) およびログ (LAL) ルールの変更を出荷できるようになりました。新しい管理エンドポイントにプッシュすると、構成されたストレージ バックエンドにルールが永続化され、クラスター内のすべてのノードが 30 秒以内に新しいコンテンツに収束します。一般的なワークフロー:
    • addOrUpdate — ルールを作成または置換します。本体は、通常 OAP の静的ルール ファイルに同梱される生の YAML です。ルールがローカルに適用されて永続化されると、200 を返します。ピアは次の定期スキャン (<= 30 秒) でそれを検出します。
    • inactivate — ソフト一時停止ルール。 OAP はそのルールのメトリクスの出力を停止しますが、バックエンド メジャー (およびその履歴) は保持されるため、同じ (catalog, name) に対する後の addOrUpdate はロスレスです。 「オフ」インテントは再起動後も持続します。 inactivate がランタイム オーバーライドを削除しても、ディスク上のバンドル ルールは自動的に復活しません。これはルールをオフラインにする安全な方法です。

Such a queue runs its drain loops on virtual threads where the runtime provides them (JDK 25+) and falls back to N platform threads otherwise; the count, and therefore concurrency, batching, back-pressure, drop semantics and per-partition ordering, are identical on both paths. Shutdown latency is the one exception: the platform scheduler drops drain tasks parked on their idle backoff, while the virtual-thread adapter sleeps inside the submitted task and cannot, so an ioBound queue should keep maxIdleMs within shutdownTimeoutMs. There is deliberately no CPU-proportional form: virtual threads are not preemptive, so CPU-bound work would hold its carrier and starve the shared carrier pool, and L1/L2/TopN stay on cpuCores/fixed. Drain loops hold the read lock for the whole cycle — the running recheck, the partition dequeue, the idle notification and the dispatch — because onIdle() touches the same worker state as consume() and an unlocked dequeue would let shutdown dispatch a newer batch ahead of one a task already holds. Concurrent shutdown callers await the winner's completion rather than returning early. A consumer is never interrupted mid-batch.

The schema fence runs on a configurable, generous budget (receiver-runtime-rule.deferredFenceTimeoutSeconds, default 180s) and gates everything durable or visible: because an un-propagated write is silently dropped at the data node, the order after a successful DDL is suspend → DDL → fence → persist → commit → resume. The rule row (the durable commit point) is written only AFTER the fence confirms, so "durable" implies "schema propagated cluster-wide" — a main crash before persist leaves no row (peers/crash-recovery stay safely on the old content; the orphaned measure is inert), and any durable row is guaranteed fence-confirmed, so convergence never resumes dispatch against an unpropagated schema. The fence + persist + resume run in the background so they never block the HTTP response — POST /addOrUpdate returns its applyId immediately at fencing (accepted, not yet durable; dispatch for that rule still paused — a clean gap, not dropped writes), and the operator polls GET /runtime/rule/status to watch fencing → rolling-out → applied (or degraded/failed); on a genuine laggard, dispatch resumes after the budget so one stuck node can't park the metric forever. A GetApplyStatus admin-internal gRPC served by the main backs the query — by applyId, or by catalog+name (+ optional contentHash, the durable identity) once the handle is gone after a page refresh. When the live status is gone (apply-id evicted, main restarted, or the main is unreachable), the query degrades to the durable rule row: a matching ACTIVE row reports applied derived from the content hash (a durable row is, by the fence-then-persist order, already propagation-confirmed). Non-main nodes route the read to the deterministic main; status is in-memory by design, with the content hash reconstructing truth after a restart.

See Trace Tail Sampling for how a trace is judged, and BanyanDB storage for the configuration keys.
  • Fix: a blank value in bydb.yml (key: with nothing after it) aborted OAP startup with an opaque NullPointerException from java.util.Properties, which rejects null values. The BanyanDB config loader now skips blank entries and leaves the field at its default, the same outcome as omitting the line.
  • Route LAL rules within a layer by their input type, so a single layer can host rules over different proto inputs. Each compiled rule now carries its effective input type (the proto class its parsed.* getters cast to, or null for parser-based / untyped rules), and LogFilterListener skips any rule whose type doesn't match the incoming log instead of running every rule in the layer. This fixes a latent ClassCastException (caught and logged per log) that fired whenever a MESH log of one shape reached a rule compiled for another — e.g. an Envoy TCP access log or a network-profiling LogData hitting the HTTP envoy-als rule. Adds an envoy-als-tcp rule (inputType: TCPAccessLogEntry) alongside the existing HTTP envoy-als; both share the MESH layer and each now only sees its own entry type.
  • Fix the PagerDuty alarm hook to default its Events API v2 endpoint to https://events.pagerduty.com/v2/enqueue.
  • Fix HttpAlarmCallback logging a successful alarm delivery as a failure. The shared HTTP hook helper treated only 200 and 204 as success, so any other 2xx — notably the 202 Accepted returned by asynchronous intake APIs such as PagerDuty's Events API v2 — produced send to ... failure. Response code: 202 at ERROR level on every delivered alarm. The alarm was still delivered; the log entry was wrong. The check now accepts the whole 2xx range, for all alarm hooks.
  • Make the PagerDuty Events API v2 endpoint configurable through a new optional events-api-url setting on each pagerduty hook, defaulting to the US service region endpoint. An account in PagerDuty's EU service region can now point the hook straight at https://events.eu.pagerduty.com/v2/enqueue rather than relying on PagerDuty forwarding the request — and the routing key and alarm payload from an EU-region account no longer transit the US region.
  • Bump the default BanyanDB compatible server API version (SW_STORAGE_BANYANDB_COMPATIBLE_SERVER_API_VERSIONS) from 0.10 to 0.11.
