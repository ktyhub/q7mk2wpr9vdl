<a name="30.0.0-upcoming-removals" href="#30.0.0-upcoming-removals">#</a> 今後の削除予定

Druid の継続的な改善の一環として、より堅牢な機能を提供し、標準 ANSI SQL との整合性を高めた新しいイテレーションを優先して、特定の機能と動作を非推奨にします。これらの新機能の多くは、いくつかのリリースの新しい展開のデフォルトになっています。

次の機能は非推奨となり、現在 Druid 32.0.0 でのサポートを削除する予定です。

  • 非 SQL 準拠の null 処理: デフォルトでは、Druid は空の文字列とデータのないレコード、および空の数値レコードと 0 を区別するようになりました。詳細については、「NULL 値」を参照してください。 SQL 準拠のロジックに関するチュートリアルについては、Null 処理チュートリアル を参照してください。
  • 非厳密なブール演算: Druid は現在、1 (true) または 0 (false) を厳密に使用します。以前は、true と false は、それぞれ true と false、または 1 と 0 として表すことができました。さらに、Druid は、True && NULL のようなブール比較に対して null 値を返すようになりました。詳細については、「ブール ロジック」を参照してください。 SQL 準拠のロジックを使用するフィルターの例については、クエリ フィルター を参照してください。
  • 2 値ロジック: デフォルトでは、Druid は取り込みとクエリの両方に 3 値ロジックを使用するようになりました。これは主に、NULL 値を持つ列に対して論理 NOT 演算を使用するフィルターに影響します。詳細については、「ブール ロジック」を参照してください。 SQL 準拠のロジックを使用するフィルターの例については、クエリ フィルター を参照してください。

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-concurrent-append-and-replace-improvements" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-concurrent-append-and-replace-improvements">#</a> 同時追加と置換の改善

ストリーミング取り込みスーパーバイザーは同時追加をサポートするようになりました。つまり、同時ロックも使用している場合、ストリーミング タスクは置換タスク (圧縮または再インデックス作成) と同時に実行できます。同時追加を有効にするには、コンテキスト パラメーター useConcurrentLocks を true に設定します。

スーパーバイザを更新して "useConcurrentLocks": true を使用すると、取り込みの遅れやタスクの失敗を引き起こすことなく、同時追加への移行がシームレスに行われます。

Druid は、複雑な列とネストされた配列のグループ化をサポートするようになりました。 これは、ネイティブ クエリと MSQ タスク エンジンの両方が、結果を返すときに複雑な列と入れ子になった配列をグループ化できることを意味します。

さらに、MSQ タスク エンジンは、取り込み中に、サポートされている複雑な列 (JSON 列など) をロールアップして並べ替えることができます。

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance">#</a> AND フィルターのパフォーマンスの向上

Druid クエリ処理は、AND フィルターの子がインデックスを計算するタイミングと、スキャン中に他のフィルターの選択性に基づいて単純に行を一致させるタイミングを適応的に決定するようになりました。 フィルター パーティショニングとして知られるこの機能は、クエリ内のフィルターの順序に応じてパフォーマンスが大幅に向上する可能性があります。

たとえば、SELECT SUM(longColumn) FROM druid.table WHERE stringColumn1 = '1000' AND stringColumn2 LIKE '%1%' のようなクエリを考えてみましょう。以前は、Druid はフィルターを処理するときに、インデックスが利用可能な場合にはインデックスを使用していました。 それは必ずしも理想的とは限りません。 stringColumn1 = '1000' が 100 行と一致する場合を想像してください。インデックスを使用する場合、フィルターのインデックスを計算するには、真となる stringColumn2 LIKE '%1%' の値をすべて検索する必要があります。 stringColumn2 に 100 を超える値がある場合、残りの 100 行の一致を単にチェックするよりも悪い結果になります。

新しいロジックにより、Druid は AND フィルターの各句を処理するときにインデックスの選択性をチェックするようになりました。 残りの行を照合するよりもインデックスを計算する方が多くの作業が必要であると判断した場合、Druid はインデックスの計算をスキップします。

クエリの WHERE 句にフィルターを記述する順序によって、クエリのパフォーマンスが向上する可能性があります。 今後もさらなる改善が予定されていますが、クエリの順序を変更することで既存の改善を試すことができます。 Druid がクエリをより効率的に処理できるように、IS NULL、=、比較 (>、>=,、<、<=) などの計算負荷の低いインデックスを AND フィルターの先頭近くに配置します。 フォールバック動作は Druid が以前に行っていたことであるため、この方法でフィルターを順序付けしなくても、以前のリリースからパフォーマンスが低下することはありません。

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-centralized-datasource-schema-%28alpha%29" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-centralized-datasource-schema-%28alpha%29">#</a> 一元化されたデータソース スキーマ (アルファ)

データソース スキーマをコーディネーター上で一元管理するように Druid を構成できるようになりました。 以前は、ブローカーはセグメント スキーマのデータ ノードとタスクをクエリする必要がありました。 データソース スキーマを一元化すると、ブローカーの起動時間と展開の効率が向上します。

この機能を有効にするには、次の構成を設定します。

  • 共通のランタイム プロパティで、druid.centralizedDatasourceSchema.enabled を true に設定します。
  • MiddleManager を使用している場合は、MiddleManager ランタイム プロパティで druid.indexer.fork.property.druid.centralizedDatasourceSchema.enabled を true に設定する必要もあります。

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-rabbitmq-extension" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-rabbitmq-extension">#</a> RabbitMQ 拡張機能

新しい RabbitMQ 拡張機能は、コミュニティへの貢献として利用できます。 RabbitMQ 拡張機能 (druid-rabbit-indexing-service) を使用すると、Rabbit インデックス作成タスクの作成と存続期間を管理できます。これらのインデックス作成タスクは、RabbitMQ から スーパー ストリーム を通じてイベントを読み取ります。

スーパー ストリームはパーティショニングを完全にサポートし、正確に 1 回の配信を可能にするため、以前の RabbitMQ Firehose の欠点がなく、Druid の最新の取り込みアルゴリズムと互換性があります。

これは従来の交換ではなく、RabbitMQ ストリーム機能を使用することに注意してください。メッセージを使用する前に、メッセージがスーパー ストリーム内にあることを確認する必要があります。詳細については、RabbitMQ ドキュメント を参照してください。

<a name="30.0.0-upcoming-removals" href="#30.0.0-upcoming-removals">#</a> Upcoming removals

As part of the continued improvements to Druid, we are deprecating certain features and behaviors in favor of newer iterations that offer more robust features and are more aligned with standard ANSI SQL. Many of these new features have been the default for new deployments for several releases.

The following features are deprecated, and we currently plan to remove support in Druid 32.0.0:

  • Non-SQL compliant null handling: By default, Druid now differentiates between an empty string and a record with no data as well as between an empty numerical record and 0. For more information, see NULL values. For a tutorial on the SQL-compliant logic, see the Null handling tutorial.
  • Non-strict Boolean handling: Druid now strictly uses 1 (true) or 0 (false). Previously, true and false could be represented either as true and false or as 1 and 0, respectively. In addition, Druid now returns a null value for Boolean comparisons like True && NULL. For more information, see Boolean logic. For examples of filters that use the SQL-compliant logic, see Query filters.
  • Two-value logic: By default, Druid now uses three-valued logic for both ingestion and querying. This primarily affects filters using logical NOT operations on columns with NULL values. For more information, see Boolean logic. For examples of filters that use the SQL-compliant logic, see Query filters.

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-concurrent-append-and-replace-improvements" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-concurrent-append-and-replace-improvements">#</a> Concurrent append and replace improvements

Streaming ingestion supervisors now support concurrent append, that is streaming tasks can run concurrently with a replace task (compaction or re-indexing) if it also happens to be using concurrent locks. Set the context parameter useConcurrentLocks to true to enable concurrent append.

Once you update the supervisor to have "useConcurrentLocks": true, the transition to concurrent append happens seamlessly without causing any ingestion lag or task failures.

#16369

Druid now performs active cleanup of stale pending segments by tracking the set of tasks using such pending segments. This allows concurrent append and replace to upgrade only a minimal set of pending segments and thus improve performance and eliminate errors. Additionally, it helps in reducing load on the metadata store.

#16144

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-grouping-on-complex-columns" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-grouping-on-complex-columns">#</a> Grouping on complex columns

Druid now supports grouping on complex columns and nested arrays. This means that both native queries and the MSQ task engine can group on complex columns and nested arrays while returning results.

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance">#</a> Improved AND filter performance

Druid query processing now adaptively determines when children of AND filters should compute indexes and when to simply match rows during the scan based on selectivity of other filters. Known as filter partitioning, it can result in dramatic performance increases, depending on the order of filters in the query.

For example, take a query like SELECT SUM(longColumn) FROM druid.table WHERE stringColumn1 = '1000' AND stringColumn2 LIKE '%1%'. Previously, Druid used indexes when processing filters if they are available. That's not always ideal; imagine if stringColumn1 = '1000' matches 100 rows. With indexes, we have to find every value of stringColumn2 LIKE '%1%' that is true to compute the indexes for the filter. If stringColumn2 has more than 100 values, it ends up being worse than simply checking for a match in those 100 remaining rows.

With the new logic, Druid now checks the selectivity of indexes as it processes each clause of the AND filter. If it determines it would take more work to compute the index than to match the remaining rows, Druid skips computing the index.

The order you write filters in a WHERE clause of a query can improve the performance of your query. More improvements are coming, but you can try out the existing improvements by reordering a query. Put indexes that are less intensive to compute such as IS NULL, =, and comparisons (>, >=, <, and <=) near the start of AND filters so that Druid more efficiently processes your queries. Not ordering your filters in this way won’t degrade performance from previous releases since the fallback behavior is what Druid did previously.

<a name="30.0.0-functional-area-and-related-changes-data-management-changes-to-coordinator-default-values" href="#30.0.0-functional-area-and-related-changes-data-management-changes-to-coordinator-default-values">#</a> Changes to Coordinator default values

Changed to the default values for the Coordinator service as follows:

  • The default value of druid.coordinator.kill.period has been changed from P1D to the runtime value of druid.coordinator.period.indexingPeriod. This default value can be overridden by explicitly specifying druid.coordinator.kill.period in the Coordinator runtime properties.
  • The default value for the dynamic configuration property killTaskSlotRatio has been updated from 1.0 to 0.1. This ensures that kill tasks take up at least one task slot and at most 10% of all available task slots by default.

#16247

<a name="30.0.0-functional-area-and-related-changes-data-management-compaction-completion-reports" href="#30.0.0-functional-area-and-related-changes-data-management-compaction-completion-reports">#</a> Compaction completion reports

Parallel compaction task completion reports now have segmentsRead and segmentsPublished fields to show how effective a compaction task is.

#15947

<a name="30.0.0-functional-area-and-related-changes-data-management-%60googletasklogs%60-upload-buffer-size" href="#30.0.0-functional-area-and-related-changes-data-management-%60googletasklogs%60-upload-buffer-size">#</a> GoogleTaskLogs upload buffer size

Changed the upload buffer size in GoogleTaskLogs to 1 MB instead of 15 MB to allow more uploads in parallel and prevent the MiddleManager service from running out of memory.

#16236

<a name="30.0.0-functional-area-and-related-changes-data-management-other-data-management-improvements" href="#30.0.0-functional-area-and-related-changes-data-management-other-data-management-improvements">#</a> Other data management improvements

  • Improved compaction task reports. They can now contain multiple sets of segment output reports instead of overwriting previous reports #15981
  • Improved segment killing in Azure to be faster #15770
  • Improved the retry behavior for deep storage connections #15938
  • Improved segment creation so that all segments created in a batch have the same created_date entry, which can help in troubleshooting ingestion issues #15977
  • Improved how Druid parses JSON by using charsetFix #16212

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring">#</a> Metrics and monitoring

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring-new-unused-segment-metric" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring-new-unused-segment-metric">#</a> New unused segment metric

You can now use the kill/eligibleUnusedSegments/count metric to find the number of unused segments of a datasource that are identified as eligible for deletion from the metadata store by the Coordinator.

#15941 #15977

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring-kafka-emitter-improvements" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring-kafka-emitter-improvements">#</a> Kafka emitter improvements

You can now set custom dimensions for events emitted by the Kafka emitter as a JSON map for the druid.emitter.kafka.extra.dimensions property. For example, druid.emitter.kafka.extra.dimensions={"region":"us-east-1","environment":"preProd"}.

#15845

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring-prometheus-emitter-improvements" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring-prometheus-emitter-improvements">#</a> Prometheus emitter improvements

The Prometheus emitter extension now emits service/heartbeat and zk-connected metrics.

#16209

Also added the following missing metrics to the default Prometheus emitter mapping: query/timeout/count, mergeBuffer/pendingRequests, ingest/events/processedWithError, ingest/notices/queueSize and segment/count.

#16329

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring-statsd-emitter-improvements" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring-statsd-emitter-improvements">#</a> StatsD emitter improvements

You can now configure queueSize,poolSize,processorWorkers, and senderWorkers parameters for the StatsD emitter. Use these parameters to increase the capacity of the StatsD client when its queue size is full.

#16283

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring-improved-%60segment%2Funavailable%2Fcount%60-metric" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring-improved-%60segment%2Funavailable%2Fcount%60-metric">#</a> Improved segment/unavailable/count metric

The segment/unavailable/count metric now accounts for segments that can be queried from deep storage (replicaCount=0).

#16020

Added a new metric segment/deepStorage/count to support the query from deep storage feature.

#16072

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring-other-metrics-and-monitoring-improvements" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring-other-metrics-and-monitoring-improvements">#</a> Other metrics and monitoring improvements

  • Added a new task/autoScaler/requiredCount metric that provides a count of required tasks based on the calculations of the lagBased autoscaler. Compare that value to task/running/count to discover the difference between the current and desired task counts #16199
  • Added jvmVersion dimension to the JvmMonitor module #16262
  • Exposed Kinesis lag metrics for use in alerts #16172
  • Fixed an issue with metric emission in the segment generation phase #16146

You can now configure the CPU cores for Peons (Kubernetes jobs) using the Overlord property druid.indexer.runner.cpuCoreInMicro.

<a name="30.0.0-functional-area-and-related-changes-extensions-delta-lake-improvements" href="#30.0.0-functional-area-and-related-changes-extensions-delta-lake-improvements">#</a> Delta Lake improvements

You can use these filters to filter out data files from a snapshot, reducing the number of files Druid has to ingest from a Delta table.

For more information, see Delta filter object.

#16288

Also added a text box for the Delta Lake filter to the web console. The text box accepts an optional JSON object that is passed down as the filter to the delta input source.

#16379

<a name="30.0.0-functional-area-and-related-changes-extensions-improve-performance-of-ldap-credentials-validator" href="#30.0.0-functional-area-and-related-changes-extensions-improve-performance-of-ldap-credentials-validator">#</a> Improve performance of LDAP credentials validator

Improved performance of LDAP credentials validator by keeping password hashes in an in-memory cache. This helps avoid re-computation of password hashes, thus speeding up the process of LDAP-based Druid authentication.

#15993

<a name="30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes" href="#30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes">#</a> Upgrade notes

<a name="30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-append-jsonpath-function" href="#30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-append-jsonpath-function">#</a> Append JsonPath function

The append function for JsonPath for ORC format now fails with an exception. Previously, it would run but not append anything.

#15772

<a name="30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-kinesis-ingestion-tuning" href="#30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-kinesis-ingestion-tuning">#</a> Kinesis ingestion tuning

The following properties have been deprecated as part of simplifying the memory tuning for Kinesis ingestion:

  • recordBufferSize, use recordBufferSizeBytes instead
  • maxRecordsPerPoll, use maxBytesPerPoll instead

#15360

<a name="30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-improved-supervisor-rolling-restarts" href="#30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-improved-supervisor-rolling-restarts">#</a> Improved Supervisor rolling restarts

The stopTaskCount config now prioritizes stopping older tasks first. As part of this change, you must also explicitly set a value for stopTaskCount. It no longer defaults to the same value as taskCount.

#15859

<a name="30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-changes-to-coordinator-default-values" href="#30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-changes-to-coordinator-default-values">#</a> Changes to Coordinator default values

Changed the following default values for the Coordinator service:

  • The default value for druid.coordinator.kill.period (if unspecified) has changed from P1D to the value of druid.coordinator.period.indexingPeriod. Operators can choose to override druid.coordinator.kill.period and that takes precedence over the default behavior.
  • The default value for the dynamic configuration property killTaskSlotRatio has been updated from 1.0 to 0.1. This ensures that kill tasks take up only one task slot by default instead of consuming all available task slots.

#16247

<a name="30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60googletasklogs%60-upload-buffer-size" href="#30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60googletasklogs%60-upload-buffer-size">#</a> GoogleTaskLogs upload buffer size

Changed the upload buffer size in GoogleTaskLogs to 1 MB instead of 15 MB to allow more uploads in parallel and prevent the MiddleManager service from running out of memory.

#16236

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes">#</a> Incompatible changes

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-changes-to-%60targetdatasource%60-in-explain-queries" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-changes-to-%60targetdatasource%60-in-explain-queries">#</a> Changes to targetDataSource in EXPLAIN queries

Druid 30.0.0 includes a breaking change that restores the behavior for targetDataSource to its 28.0.0 and earlier state, different from Druid 29.0.0 and only 29.0.0. In 29.0.0, targetDataSource returns a JSON object that includes the datasource name. In all other versions, targetDataSource returns a string containing the name of the datasource.

If you're upgrading from any version other than 29.0.0, there is no change in behavior.

If you are upgrading from 29.0.0, this is an incompatible change.

#16004

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-zookeeper-based-segment-loading" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-zookeeper-based-segment-loading">#</a> Removed ZooKeeper-based segment loading

ZooKeeper-based segment loading is being removed due to known issues. It has been deprecated for several releases. Recent improvements to the Druid Coordinator have significantly enhanced performance with HTTP-based segment loading.

#15705

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-coordinator-configs" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-coordinator-configs">#</a> Removed Coordinator configs

Removed the following Coordinator configs:

  • druid.coordinator.load.timeout: Not needed as the default value of this parameter (15 minutes) is known to work well for all clusters.
  • druid.coordinator.loadqueuepeon.type: Not needed as this value is always http.
  • druid.coordinator.curator.loadqueuepeon.numCallbackThreads: Not needed as ZooKeeper(curator)-based segment loading isn't an option anymore.

Auto-cleanup of compaction configs of inactive datasources is now enabled by default.
