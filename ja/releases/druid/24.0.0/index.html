<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> マルチステージ クエリ タスク エンジン

Apache Druid の SQL ベースの取り込み は、分散型マルチステージ クエリ アーキテクチャを使用します。これには、マルチステージ クエリ タスク エンジン (MSQ タスク エンジン) と呼ばれるクエリ エンジンが含まれます。 MSQ タスク エンジンは Druid のクエリ機能を拡張するため、外部データを参照するクエリを作成したり、SQL INSERT および REPLACE を使用して取り込みを実行したりできます。基本的に、Druid のネイティブ取り込みで使用される JSON 取り込み仕様を使用する代わりに、SQL ベースの取り込みを実行できます。使いやすい構文に加えて、SQL インターフェイスを使用すると、データの複数のシャッフルを伴う変換を実行できます。 Druid 24.0.0 以降のバッチ取り込みには、マルチステージ クエリ タスク エンジンを使用した SQL ベースの取り込みが推奨されます。ネイティブ バッチと Hadoop ベースの取り込みも引き続きサポートされます。 既知の問題 を確認し、実稼働環境に展開する前にステージング環境で機能をテストすることをお勧めします。マルチステージ クエリ タスク エンジンをプレーン SELECT ステートメント (INSERT ... SELECT や REPLACE ... SELECT ではない) で使用することは実験段階です。 以前のバージョンの Druid からアップグレードする場合、または Docker を使用している場合は、common.runtime.properties ファイル内の druid.extensions.loadlist に druid-multi-stage-query 拡張子を追加する必要があります。 詳細については、SQL ベースの取り込みに関する 概要 ドキュメントを参照してください。 #12524 #12386 #12523 #12589

<a name="24.0.0-new-features-nested-columns-" href="#24.0.0-new-features-nested-columns-">#</a> ネストされた列

Druid は、新しく追加された COMPLEX<json> 列タイプでのネストされたデータ構造の直接保存をサポートするようになりました。 COMPLEX<json> 列には、JSON 形式の構造化データのコピーと、ネストされたリテラル値 (STRING、LONG、および DOUBLE 型) の特殊な内部列とインデックスが格納されます。最適化された仮想列により、Druid は標準の Druid LONG、DOUBLE、STRING 列と一致する速度でこれらの値を読み取り、フィルター処理できます。 新しく追加された Druid SQL、ネイティブ JSON 関数、および仮想列を使用すると、クエリ時に COMPLEX<json> 値を抽出、変換、作成できます。 flattenSpec オブジェクトを使用してネストされたデータを取り込み用に「平坦化」する代わりに、SQL ベースの取り込みの INSERT および REPLACE ステートメントで JSON 関数を使用したり、ネイティブ取り込みの transformSpec で JSON 関数を使用したりすることもできます。 SQL JSON 関数、ネイティブ JSON 関数、ネストされた列、[virtual] を参照してください。 columns](docs/querying/virtual-columns.md#nested-field-virtual-column)、および詳細については 機能の概要 を参照してください。 #12753 #12714 #12753 #12920

<a name="24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters" href="#24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters">#</a> 列インデックスとフィルターのクエリ処理を更新しました。

列インデックスが非常に柔軟になるように再加工され、最終的には幅広い種類のインデックスをモデル化できるようになります。更新されたインデックスを使用するフィルターを構築するための機構を追加しました。また、他の列実装で組み込みインデックス タイプを実装して、Druid が提供する現在のセット フィルターでインデックスを使用するためのアダプターを提供できるようにしました。 #12388

Druid SQL 演算子 TIME_IN_INTERVAL を使用して、時間に基づいてクエリ結果をフィルターできるようになりました。時間どおりにフィルタリングするには、SQL BETWEEN 演算子よりも TIME_IN_INTERVAL を優先します。詳細については、「日付と時刻関数」(docs/querying/sql-scalar.md#date-and-time-functions) を参照してください。 #12662

<a name="24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter" href="#24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter">#</a> Null 値と「in」フィルター

values 配列に null が含まれている場合、「in」フィルターは NULL 値と一致します。これは、NULL 値と一致しない SQL IN フィルターとは異なります。 詳細については、クエリ フィルター および SQL データ型 を参照してください。 #12863

<a name="24.0.0-query-engine-updates-virtual-columns-in-search-queries" href="#24.0.0-query-engine-updates-virtual-columns-in-search-queries">#</a> 検索クエリの仮想列

以前は、検索クエリ はデータ ソースに存在するディメンションでのみ検索できました。検索クエリは、クエリ内のパラメーターとして 仮想列 をサポートするようになりました。 #12720

<a name="24.0.0-query-engine-updates-string-aggregation-results" href="#24.0.0-query-engine-updates-string-aggregation-results">#</a> 文字列の集計結果

最初/最後の文字列アグリゲータは、値に基づいてのみ比較するようになりました。以前は、最初/最後の文字列アグリゲーターの値は、最初に _time 列に基づいて比較され、次に値に基づいて比較されました。 既存のクエリがあり、_time 列と値の両方を引き続き使用したい場合は、ORDER BY MAX(timeCol) を使用するようにクエリを更新します。 #12773

<a name="24.0.0-ingestion-general-updated-avro-extension" href="#24.0.0-ingestion-general-updated-avro-extension">#</a> Avro 拡張機能を更新しました

以前の Avro 拡張機能では、パーサーからオブジェクトがリークしていました。これらのオブジェクトが取り込みに漏洩した場合、オブジェクトは .toString() の値を持つ文字列列として保存されます。この文字列列はアップグレード後も残りますが、GenericRecord.toString ではなく Map.toString() を返します。以前の動作に依存していた場合は、以前のリリースの Avro 拡張機能を使用できます。 #12828

<a name="24.0.0-ingestion-general-sampler-api" href="#24.0.0-ingestion-general-sampler-api">#</a> サンプラー API

サンプラー API には追加の制限 (maxBytesInMemory および maxClientResponseBytes) があります。これらのオプションは、既存のオプション numRows および timeoutMs を拡張します。 maxBytesInMemory を使用すると、サンプリング中に Overlord のメモリ使用量を制御できます。 maxClientResponseBytes は、client が処理したい応答の最大サイズを指定するために使用できます。 #12947

<a name="24.0.0-sql-add-is_active-to-sys.segments" href="#24.0.0-sql-add-is_active-to-sys.segments">#</a> is_active を sys.segments に追加します

(is_published = 1 AND is_overshadowed = 0) OR is_realtime = 1) の短縮形として is_active を追加しました。これは、「実際に現在存在しているかどうかに関係なく、クエリ可能であるべきすべてのセグメント」を表します。 #11550

<a name="24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true" href="#24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true">#</a> useNativeQueryExplain のデフォルトが true になりました

useNativeQueryExplain プロパティのデフォルトは true になりました。これは、EXPLAIN PLAN FOR が、デフォルトで、Explain Plan を同等のネイティブ クエリの JSON 表現として返すことを意味します。詳細については、「ブローカー生成クエリ構成の補足」(/docs/configuration/index.md) を参照してください。 #12936

<a name="24.0.0-inline-query-engine" href="#24.0.0-inline-query-engine">#</a> druid クエリ エンジンを使用したインライン データでのクエリの実行

select 1 など、テーブルを参照しない一部のクエリは、実行前に常に InlineDataSource を使用してネイティブ Druid クエリに変換されるようになりました。 SELECT (1, 2) などのクエリで変換できない場合は、エラーが発生します。以前のバージョンでは、このクエリは引き続き実行されます。 #12897

<a name="24.0.0-coordinator%2Foverlord" href="#24.0.0-coordinator%2Foverlord">#</a> コーディネーター/オーバーロード

<a name="24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future" href="#24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future">#</a> 将来、セグメントを強制終了するようにコーディネーターを構成できます。

druid.coordinator.kill.durationToRetain を負のピリオドに設定して、interval_end が将来の日付であるセグメントを強制終了するように Druid クラスターを構成できるようになりました。たとえば、PT-24H では、システムによって kill タスクが生成された時点で、interval_end の日付が 24 時間以内である場合に、セグメントを強制終了できます。 クラスター オペレーターは、新しい構成 druid.coordinator.kill.ignoreDurationToRetain=true を設定することで、druid.coordinator.kill.durationToRetain を完全に無視することもできます。これにより、強制終了するセグメントを探すときに interval_end の日付が無視され、代わりに未使用のマークが付けられたセグメントを強制終了できます。この新しい構成はデフォルトでオフになっているため、クラスター オペレーターは有効にする前にリスクを十分に理解し、受け入れる必要があります。

<a name="24.0.0-coordinator%2Foverlord-improved-overlord-stability" href="#24.0.0-coordinator%2Foverlord-improved-overlord-stability">#</a> Overlord の安定性の向上

管理スレッドとクラスターからのステータス更新の受信の間の競合が減少しました。これにより、タスク数が多い (1000 以上) 場合の、オーバーロードとクラスター内のすべてのタスクの安定性が向上します。 #12099

<a name="24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging" href="#24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging">#</a> コーディネーター セグメントのログの改善

現在のレプリケーション レベルを含むようにコーディネーターのロード ルールのログを更新しました。一部のログ メッセージに欠落していたセグメント ID と階層情報が追加されました。 #12511

<a name="24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage" href="#24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage">#</a> 最適化されたオーバーロード GET タスクのメモリ使用量

Web コンソールが Overlord の GET タスク API を間接的に呼び出すことによって引き起こされる重大なメモリ オーバーヘッドに対処しました。これにより、取り込みタブを複数回開いたときに応答しなくなったり、オーバーロードのエラーが発生したりする可能性がありました。 #12404

<a name="24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals" href="#24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals">#</a> 間隔の作成時間の短縮

間隔の作成にかかる時間を削減してセグメント コストの計算時間を最適化するには、セグメント間隔をプリミティブから毎回作成するのではなく格納し、間隔をインターニングすることで間隔を格納するメモリ オーバーヘッドを削減します。セグメントの間隔のセットはカーディナリティが低いです。 #12670

<a name="24.0.0-new-features" href="#24.0.0-major-version">#</a> Major version bump

Starting with this release, we have dropped the leading 0 from the release version and promoted all other digits one place to the left. Druid is now at major version 24, a jump up from the prior 0.23.0 release. In terms of backward-compatibility or breaking changes, this release is not significantly different than other previous major releases such as 0.23.0 or 0.22.0. We are continuing with the same policy as we have used in prior releases: minimizing the number of changes that require special attention when upgrading, and calling out any that do exist in the release notes. For this release, please refer to the Upgrading to 24.0.0 section for a list of backward-incompatible changes in this release.

<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> Multi-stage query task engine

SQL-based ingestion for Apache Druid uses a distributed multi-stage query architecture, which includes a query engine called the multi-stage query task engine (MSQ task engine). The MSQ task engine extends Druid's query capabilities, so you can write queries that reference external data as well as perform ingestion with SQL INSERT and REPLACE. Essentially, you can perform SQL-based ingestion instead of using JSON ingestion specs that Druid's native ingestion uses. In addition to the easy-to-use syntax, the SQL interface lets you perform transformations that involve multiple shuffles of data.

SQL-based ingestion using the multi-stage query task engine is recommended for batch ingestion starting in Druid 24.0.0. Native batch and Hadoop-based ingestion continue to be supported as well. We recommend you review the known issues and test the feature in a staging environment before rolling out in production. Using the multi-stage query task engine with plain SELECT statements (not INSERT ... SELECT or REPLACE ... SELECT) is experimental.

If you're upgrading from an earlier version of Druid or you're using Docker, you'll need to add the druid-multi-stage-query extension to druid.extensions.loadlist in your common.runtime.properties file.

For more information, refer to the Overview documentation for SQL-based ingestion.

<a name="24.0.0-new-features-nested-columns-" href="#24.0.0-new-features-nested-columns-">#</a> Nested columns

Druid now supports directly storing nested data structures in a newly added COMPLEX<json> column type. COMPLEX<json> columns store a copy of the structured data in JSON format as well as specialized internal columns and indexes for nested literal values—STRING, LONG, and DOUBLE types. An optimized virtual column allows Druid to read and filter these values at speeds consistent with standard Druid LONG, DOUBLE, and STRING columns.

Newly added Druid SQL, native JSON functions, and virtual column allow you to extract, transform, and create COMPLEX<json> values in at query time. You can also use the JSON functions in INSERT and REPLACE statements in SQL-based ingestion, or in a transformSpec in native ingestion as an alternative to using a flattenSpec object to "flatten" nested data for ingestion.

See SQL JSON functions, native JSON functions, Nested columns, virtual columns, and the feature summary for more detail.

The data loader exists as a GUI wizard to help users craft a JSON ingestion spec using point and click and quick previews. The SQL data loader is the SQL-based ingestion analog of that.

Like the native based data loader, the SQL-based data loader stores all the state in the SQL query itself. You can opt to manipulate the query directly at any stage. See (#12919) for more information about how the data loader differs from the Connect external data workflow.

<a name="24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60" href="#24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60">#</a> Default for druid.processing.fifo

The default for druid.processing.fifo is now true. This means that tasks of equal priority are treated in a FIFO manner. For most use cases, this change can improve performance on heavily loaded clusters.

#12571

<a name="24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure" href="#24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure">#</a> Update to JDBC statement closure

In previous releases, Druid automatically closed the JDBC Statement when the ResultSet was closed. Druid closed the ResultSet on EOF. Druid closed the statement on any exception. This behavior is, however, non-standard. In this release, Druid's JDBC driver follows the JDBC standards more closely: The ResultSet closes automatically on EOF, but does not close the Statement or PreparedStatement. Your code must close these statements, perhaps by using a try-with-resources block. The PreparedStatement can now be used multiple times with different parameters. (Previously this was not true since closing the ResultSet closed the PreparedStatement.) If any call to a Statement or PreparedStatement raises an error, the client code must still explicitly close the statement. According to the JDBC standards, statements are not closed automatically on errors. This allows you to obtain information about a failed statement before closing it. If you have code that depended on the old behavior, you may have to change your code to add the required close statement.
