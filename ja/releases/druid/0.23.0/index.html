<a name="0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays" href="#0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays">#</a> 配列を分解せずに配列をグループ化する

複数値のディメンションを配列としてグループ化できるようになりました。 「test」という名前のデータソースの場合:

{"timestamp": "2011-01-12T00:00:00.000Z", "tags": ["t1","t2","t3"]}  #row1
{"timestamp": "2011-01-13T00:00:00.000Z", "tags": ["t3","t4","t5"]}  #row2
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": ["t5","t6","t7"]}  #row3
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": []}                #row4

次のクエリ:

{
  "queryType": "groupBy",
  "dataSource": "test",
  "intervals": [
    "1970-01-01T00:00:00.000Z/3000-01-01T00:00:00.000Z"
  ],
  "granularity": {
    "type": "all"
  },
  "virtualColumns" : [ {
    "type" : "expression",
    "name" : "v0",
    "expression" : "mv_to_array(\"tags\")",
    "outputType" : "ARRAY<STRING>"
  } ],
  "dimensions": [
    {
      "type": "default",

      "outputName": "tags"
      "outputType":"ARRAY<STRING>"

    {
      "type": "count",
      "name": "count"
    }
  ]
}

<a name="0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators" href="#0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators">#</a> 最初/最後のアグリゲーターでの行比較には __time 列以外の列を指定します

LATEST_BY / EARLIEST_BY SQL 関数を使用して、*first/*last アグリゲーターに時刻列を渡すことができます。これにより、時間が「__time」とは異なる列の一部として保存される場合がサポートされます。別の論理時間列を指定することもできます。 (#11949) (#12145)

<a name="0.23.0-new-features-query-engine-improvements-to-querying-user-experience" href="#0.23.0-new-features-query-engine-improvements-to-querying-user-experience">#</a> ユーザー エクスペリエンスのクエリの改善

このリリースには、クエリに関するいくつかの改善が含まれています。

  • エラー メッセージを見つけやすくするために、失敗した SQL クエリの応答ヘッダーに SQL クエリ ID を追加しました (#11756)
  • DataSketches HLL の入力タイプ検証を追加しました (#12131)
  • JDBC ログの改善 (#11676)
  • 複数値文字列ディメンションの行をフィルタリングして、指定された値のリストのみを含めるか、値をまったく含めないようにするための SQL 関数 MV_FILTER_ONLY および MV_FILTER_NONE を追加しました (#11650)
  • 配列入力を単一の配列に集約するための ARRAY_CONCAT_AGG を追加しました (#12226)
  • クエリコンテキストパラメータの使用を承認する機能を追加しました (#12396)
  • クエリ ID を改善して、クエリとサブクエリを簡単にリンクしてエンドツーエンドのクエリを可視化しました (#11809)
  • 0による除算を防ぐための安全な除算機能を追加しました (#11904)
  • 内部生成された SegmentMetadata クエリにクエリ コンテキストを追加できるようになりました (#11429)
  • ネイティブ式処理システムに Druid 複合タイプのサポートを追加し、すべての Druid データを式内で使用できるようにしました (#11853、#12016)
  • 既存の辞書を持たない文字列または配列値の式をグループ化する場合、druid.query.groupBy.maxSelectorDictionarySize を介してヒープ上のセグメントレベルの辞書のサイズを制御できます。
  • CNF 変換中のフィルター爆発に対する保護が強化されました (#12314) (#12324)
  • クエリコンテキストで useNativeQueryExplain を true に設定することで、SQL クエリを説明する完全なネイティブ クエリを取得できます (#11908)
  • ブローカーにリアルタイム ノードまたは特定の履歴層を無視させることができます。 (#11766) (#11732)

<a name="0.23.0-new-features-streaming-ingestion" href="#0.23.0-new-features-streaming-ingestion">#</a> ストリーミング取り込み

<a name="0.23.0-new-features-streaming-ingestion-kafka-input-format-for-parsing-headers-and-key" href="#0.23.0-new-features-streaming-ingestion-kafka-input-format-for-parsing-headers-and-key">#</a> ヘッダーとキーを解析するための Kafka 入力形式

Kafka 入力形式を導入したので、メッセージの内容に加えてヘッダー データも取り込むことができます。たとえば:

  • イベントキーフィールド
  • イベントヘッダー
  • Kafkaイベントのタイムスタンプ
  • ペイロードを保存する Kafka イベント値。 (#11630)

<a name="0.23.0-new-features-streaming-ingestion-kinesis-ingestion---改善" href="#0.23.0-new-features-streaming-ingestion-kinesis-ingestion---改善">#</a> Kinesis の取り込み - 改善

キネシス摂取において以下の改善を行いました

  • 再シャーディングは、多くの中間の空のシャードが作成されるため、取り込みに影響を与え、速度が低下する可能性があります。これらのシャードはタスクに割り当てられるため、負荷割り当ての不均衡が生じます。 kinesis 取り込みチューニング設定で skipIgnorableShards を true に設定すると、そのようなシャードを無視できます。 (#12235)
  • 現在、kinesis の取り込みは DescribeStream を使用してシャードのリストを取得します。この呼び出しは非推奨であり、速度が遅くなります。このリリースでは、Kinesis インジェストチューニング構成で useListShards を true に設定することで、新しい API listShards に切り替えることができます。 (#12161)

<a name="0.23.0-new-features-native-batch-ingestion" href="#0.23.0-new-features-native-batch-ingestion">#</a> ネイティブ バッチ取り込み

<a name="0.23.0-new-features-native-batch-ingestion-multi-dimension-range-partitioning" href="#0.23.0-new-features-native-batch-ingestion-multi-dimension-range-partitioning">#</a> 多次元範囲パーティショニング

多次元範囲パーティショニングにより、ユーザーは任意の数の次元の範囲でデータを分割できます。これは、「単一次元」パーティショニングの背後にある概念をさらに発展させたもので、クエリのパフォーマンスとストレージ効率の両方の観点から、おそらく最も望ましい二次パーティショニングとなっています。 (#11848) (#11973)

<a name="0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior" href="#0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior">#</a> データの置換動作の改善

Druid の以前のバージョンでは、データを置き換えるために dropExisting フラグを使用してデータが取り込まれた場合、置き換える新しいデータがない場合、Druid は既存のデータをタイム チャンクの間保持していました。ここで、ioSpec で dropExisting を true に設定し、データのないタイム チャンクを含む時間範囲のデータを取り込むと、Druid はトゥームストーンを使用して、空のタイム チャンク内の既存のデータを覆い隠します。 (#12137) このリリースには、ネイティブ バッチ取り込みに関するいくつかの改善が含まれています。

  • Druid は、バッチ タスクがセグメントの可用性の待機を終了したときに新しいメトリクスを発行するようになりました。 (#11090)
  • segmentAvailabilityWaitTimeMs (セグメントが履歴ノードにハンドオフされるまでタスクが待機したミリ秒単位) を IngestionStatsAndErrorsTaskReportData に追加しました (#11090)
  • 取り込み中に既存のメトリクスを保持する機能を追加しました (#12185)
  • 並列ネイティブ バッチ タスクは、シングル フェーズ モードのサブタスクだけでなく、シーケンシャル モードおよびシングル フェーズ モード (動的パーティショニングで使用されるなど) のタスク レポートも提供できるようになりました (#11688)
  • マルチフェーズ並列インデックス付けタスク用の druid/indexer/v1/task/{task_id}/reports API に RowStats のサポートを追加しました (#12280)
  • 並列インデックス作成のディメンション分散フェーズでの OOM エラーを修正しました (#12331)
  • パーティション境界の作成時に null ディメンション値を処理するためのサポートを追加しました (#11973)

<a name="0.23.0-new-features-improvements-to-ingestion-in-general" href="#0.23.0-new-features-improvements-to-ingestion-in-general">#</a> 取り込み全般の改善

このリリースには、取り込み全般に関していくつかの改善が含まれています。

  • テンプレート修飾子は不要になったため、IncrementalIndex<AggregatorType> から削除しました。
  • 取り込み中に JsonPath 式で JsonPath 関数を使用できるようになりました (#11722)
  • Druid はセグメント ファイルの実体化リストを作成しなくなり、OOM 問題を軽減するためにファイルのループを制限しました (#11903)
  • 中間永続型 IndexSpec を IndexMerger のメインの「マージ」メソッドに追加しました (#11940)
  • ALL を渡した場合、Granularity.granularitiesFinerThan は ALL を返すようになりました (#12003)
  • SHARED ロックを使用できるようにタスクを追加するための設定パラメータを追加しました (#12041)
  • SchemaRegistryBasedAvroBytesDecoder は、スキーマの取得に失敗した場合に RE の代わりに ParseException をスローするようになりました (#12080)
  • includeAllDimensions を dimensionsSpec に追加して、すべての明示的なディメンションを最初に InputRow に配置し、その後に入力データで見つかった他のディメンションを配置しました (#12276)
  • Null 列をセグメントに格納する機能を追加しました (#12279)

<a name="0.23.0-new-features-sql" href="#0.23.0-new-features-sql">#</a> SQL

<a name="0.23.0-new-features-sql-human-readable-and-actionable-sql-error-messages" href="#0.23.0-new-features-sql-human-readable-and-actionable-sql-error-messages">#</a> 人間が判読可能で実用的な SQL エラー メッセージ

バージョン 0.22.1 までは、サポートされていない SQL クエリを発行すると、Druid は非常に不可解で役に立たないエラー メッセージをスローしていました。この変更により、エラー メッセージには、Druid でサポートされていない SQL クエリの部分が正確に含まれます。たとえば、時間列以外のディメンションで順序付けされたスキャン クエリを実行する場合です。 (#11911)

<a name="0.23.0-new-features-sql-cancel-api-for-sql-queries" href="#0.23.0-new-features-sql-cancel-api-for-sql-queries">#</a> SQL クエリの API をキャンセルします

SQL クエリをキャンセルするための新しい API が追加されたため、ネイティブ クエリをキャンセルするのと同じように SQL クエリをキャンセルできるようになりました。 API は Web コンソールから使用できます。以前のバージョンでは、コンソールからのキャンセルは、SQL クエリが Druid 上で実行され続けている間、client 接続を閉じるだけでした。 (#11643) (#11738) (#11710)

<a name="0.23.0-new-features-sql-improved-sql-compatibility" href="#0.23.0-new-features-sql-improved-sql-compatibility">#</a> SQL の互換性の向上

式の評価がより SQL に準拠するように式に変更を加えました。この新しい動作はデフォルトでは無効になっています。 druid.expressions.useStrictBooleans ～ true を設定することで有効にできます。場合によってはパフォーマンスが向上するため、この動作を有効にすることをお勧めします。 (#11184)

<a name="0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts" href="#0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts">#</a> クエリ コンテキストの設定におけるアクセス制御のサポート

現在、ユーザーはあらゆるコンテキスト パラメータを許可されています。これにより、1) コンテキスト パラメータがまだ成熟していない場合は UX が悪化する、または 2) 機密パラメータが悪用された場合、最悪の場合にはクエリの失敗やシステム障害が発生する可能性があります (例) maxSubqueryRows。 Druid には、ユーザー ロールごとにコンテキスト パラメータを制限できる機能が追加されました。つまり、許可されていないコンテキスト パラメータがクエリに設定されている場合、クエリは失敗します。 コンテキスト パラメーターの承認は、Druid.auth.authorizeQueryContextParams を使用して有効にできます。これは、よりスムーズなアップグレード エクスペリエンスを可能にするために、デフォルトでは無効になっています。 (#12396)

<a name="0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks" href="#0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks">#</a> 不明なスーパーバイザーまたはタスクの場合は 400 ではなく 404 を返します

以前のスーパーバイザ/タスク エンドポイントは、スーパーバイザまたはタスクが見つからない場合に 400 を返しました。このステータス コードは、3 番目のシステムにとっては分かりにくく、混乱を招きます。 HTTP ステータス コードの定義によれば、このような場合に適切なコードは 404 です。そこで、曖昧さを排除するためにステータス コードを 400 から 404 に変更しました。これらのエンドポイントの client は、それに応じて応答コードの処理を変更する必要があります。 11724

Druid によって計画できない SQL クエリは、不正なリクエストとはみなされません。このようなクエリに対しては、400 を返すようになりました。SQL API を使用する開発者は、必要に応じて応答コードの処理を変更する必要があります。 12033

<a name="0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays" href="#0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays">#</a> Grouping on arrays without exploding the arrays

You can now group on a multi-value dimension as an array. For a datasource named "test":

{"timestamp": "2011-01-12T00:00:00.000Z", "tags": ["t1","t2","t3"]}  #row1
{"timestamp": "2011-01-13T00:00:00.000Z", "tags": ["t3","t4","t5"]}  #row2
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": ["t5","t6","t7"]}  #row3
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": []}                #row4

The following query:

{
  "queryType": "groupBy",
  "dataSource": "test",
  "intervals": [
    "1970-01-01T00:00:00.000Z/3000-01-01T00:00:00.000Z"
  ],
  "granularity": {
    "type": "all"
  },
  "virtualColumns" : [ {
    "type" : "expression",
    "name" : "v0",
    "expression" : "mv_to_array(\"tags\")",
    "outputType" : "ARRAY<STRING>"
  } ],
  "dimensions": [
    {
      "type": "default",
      "dimension": "v0",
      "outputName": "tags"
      "outputType":"ARRAY<STRING>"
    }
  ],
  "aggregations": [
    {
      "type": "count",
      "name": "count"
    }
  ]
}

Returns the following:

[
 {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "[]"
    }
  },

    "timestamp": "1970-01-01T00:00:00.000Z",

      "count": 1,
      "tags": "["t1","t2","t3"]"
    }

]

(#12078) (#12253)

You can pass time column in *first/*last aggregators by using LATEST_BY / EARLIEST_BY SQL functions. This provides support for cases where the time is stored as a part of a column different than "__time". You can also specify another logical time column. (#11949) (#12145)

We've introduced a Kafka input format so you can ingest header data in addition to the message contents. For example:

  • the event key field
  • event headers
  • the Kafka event timestamp
  • the Kafka event value that stores the payload.

<a name="0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements" href="#0.23.0-new-features-streaming-ingestion-kinesis-ingestion---improvements">#</a> Kinesis ingestion - Improvements

We have made following improvements in kinesis ingestion

  • Re-sharding can affect and slow down ingestion as many intermediate empty shards are created. These shards get assigned to tasks causing imbalance in load assignment. You can set skipIgnorableShards to true in kinesis ingestion tuning config to ignore such shards. (#12235)
  • Currently, kinesis ingestion uses DescribeStream to fetch the list of shards. This call is deprecated and slower. In this release, you can switch to a newer API listShards by setting useListShards to true in kinesis ingestion tuning config. (#12161)

Multi-dimension range partitioning allows users to partition their data on the ranges of any number of dimensions. It develops further on the concepts behind "single-dim" partitioning and is now arguably the most preferable secondary partitioning, both for query performance and storage efficiency. In previous versions of Druid, if ingested data with dropExisting flag to replace data, Druid would retain the existing data for a time chunk if there was no new data to replace it. Now, if you set dropExisting to true in your ioSpec and ingest data for a time range that includes a time chunk with no data, Druid uses a tombstone to overshadow the existing data in the empty time chunk. (#12137)

Until version 0.22.1, if you issued an unsupported SQL query, Druid would throw very cryptic and unhelpful error messages. <a name="0.23.0-security-fixes" href="#0.23.0-security-fixes">#</a> Security fixes

<a name="0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts" href="#0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts">#</a> Support for access control on setting query contexts

Today, any context params are allowed to users. This can cause 1) a bad UX if the context param is not matured yet or 2) even query failure or system fault in the worst case if a sensitive param is abused, ex) maxSubqueryRows. Druid now has an ability to limit context params per user role. That means, a query will fail if you have a context param set in the query that is not allowed to you.

The context parameter authorization can be enabled using Druid.auth.authorizeQueryContextParams. This is disabled by default to enable a smoother upgrade experience.

<a name="0.23.0-upgrading-to-0.23.0" href="#0.23.0-upgrading-to-0.23.0">#</a> Upgrading to 0.23.0

Consider the following changes and updates when upgrading from Druid 0.22.x to 0.23.0. If you're updating from an earlier version than 0.22.1, see the release notes of the relevant intermediate versions.

<a name="0.23.0-upgrading-to-0.23.0-autokill" href="#0.23.0-upgrading-to-0.23.0-autokill">#</a> Auto-killing of segments

In 0.23.0, Auto killing of segments is now enabled by default (#12187). The new defaults should kill all unused segments older than 90 days. If users do not want this behavior on an upgrade, they should explicitly disable the behavior. This is a risky change since depending on the interval, segments will be killed immediately after being marked unused. this behavior will be reverted or changed in the next druid release. Please see (#12693) for more details.

<a name="0.23.0-upgrading-to-0.23.0-other-changes" href="#0.23.0-upgrading-to-0.23.0-other-changes">#</a> Other changes

  • Kinesis ingestion requires listShards API access on the stream.
  • Kafka clients libraries have been upgraded to 3.0.0 (#11735)
  • The dynamic coordinator config, percentOfSegmentsToConsiderPerMove has been deprecated and will be removed in a future release of Druid. It is being replaced by a new segment picking strategy introduced in (#11257). This new strategy is currently toggled off by default, but can be toggled on if you set the dynamic coordinator config useBatchedSegmentSampler to true. Setting this as such, will disable the use of the deprecated percentOfSegmentsToConsiderPerMove. In a future release, useBatchedSegmentSampler will become permanently true. (#11960)

<a name="0.23.0-developer-notices" href="#0.23.0-developer-notices">#</a> Developer notices

<a name="0.23.0-developer-notices-updated-airline-dependency-to-2.x" href="#0.23.0-developer-notices-updated-airline-dependency-to-2.x">#</a> updated airline dependency to 2.x

https://github.com/airlift/airline is no longer maintained and so druid has upgraded to https://github.com/rvesse/airline (Airline 2) to use an actively maintained version, while minimizing breaking changes.

This is a backwards incompatible change, and custom extensions relying on the CliCommandCreator extension point will also need to be updated.

12270

<a name="0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks" href="#0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks">#</a> Return 404 instead of 400 for unknown supervisors or tasks

Earlier supervisor/task endpoint return 400 when a supervisor or a task is not found. This status code is not friendly and confusing for the 3rd system. And according to the definition of HTTP status code, 404 is right code for such case. So we have changed the status code from 400 to 404 to eliminate the ambigiuty. Any clients of these endpoints should change the response code handling accordingly.

11724

<a name="0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned" href="#0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned">#</a> Return 400 instead of 500 when SQL query cannot be planned

Any SQL query that cannot be planned by Druid is not considered a bad request. For such queries, we now return 400. Developers using SQL API should change the response code handling if needed.

12033

<a name="0.23.0-developer-notices-responsecontext-refactoring" href="#0.23.0-developer-notices-responsecontext-refactoring">#</a> ResponseContext refactoring

0.23.0 changes the the ResponseContext and it's keys in a breaking way. The prior version of the response context suggested that keys be defined in an enum, then registered. This version suggests that keys be defined as objects, then registered. See the ResponseContext class itself for the details.
