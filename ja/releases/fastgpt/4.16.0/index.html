#FastGPT v4.16.0

📦 アップグレード ガイド

1. Agent-sandbox-proxy 環境変数を更新します (オプション)

4.16.0 は、静的リソース プロキシ アクセスのためにプロキシに依存する必要があります。ゲートウェイが同じポートで ws と http をサポートしている場合、開くことができるポートは 1 つだけです。サポートされていない場合は、PREVIEW_PORT を設定することで http アクセス ポートを設定できます。

# ws和http服务的端口
PORT=1006
# http服务的端口，可以覆盖 PORT
PREVIEW_PORT=1007

アクセスアドレスはhttp://またはhttps://で始まります。単一ポートを使用して展開する場合、AGENT_SANDBOX_PROXY_URL と同じドメイン名とポートを指すことができますが、プロトコルはそれぞれ HTTP(S) と WebSocket(S) を使用します。構成されたドメイン名と FastGPT メイン サイトでは異なるオリジンを使用することを強くお勧めします。同一オリジン展開では、これらのスクリプトがメイン サイトの同一オリジン セキュリティ境界に侵入し、メイン サイトの資格情報またはインターフェイスにアクセスできる可能性があります。現在、システムは分離のためのオリジンのチェックを強制していません。

https://{{host}}/health にアクセスすると、アクセス可能かどうかを確認できます。

2. fastgpt 環境変数を更新します (サンドボックスが有効な場合は更新する必要があります)。

変数は、fastgpt-app と fastgpt-pro で同時に変更されます。

# opensandbox 需配置，存储全前缀名（之前是配置在 volumn 镜像环境变量里）
VM_VOLUME_NAME_PREFIX=fastgpt-session
  1. 非推奨のサンドボックス環境変数

AGENT_SANDBOX_DISK_MB、E2B 関連の変数。

  1. 新しいオプションのサンドボックス構成変数

|変数 |デフォルト値 |説明 | | -------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------- | | AGENT_SANDBOX_CPU_COUNT | 1 |エージェント サンドボックス 単一インスタンスの CPU コア制限。 | | AGENT_SANDBOX_MEMORY_MIB | 2048 |エージェント サンドボックスの単一インスタンスのメモリ制限、単位 MiB。 | | AGENT_SANDBOX_STORAGE_SIZE_GI | 1 |エージェント サンドボックスのストレージ容量 (Gi 単位)。 Sealos Devbox のストレージ制限と、OpenSandbox Kubernetes モードでの新しい PVC の作成に使用されます。 | | AGENT_SANDBOX_SUSPEND_MINUTES | 60 |実行中のサンドボックスが非アクティブになってから自動的に一時停止するまでの時間 (分単位)。 | | AGENT_SANDBOX_ARCHIVE_INACTIVE_DAYS | 7 |一時停止されたサンドボックスは、非アクティブな期間 (日単位) が経過すると、自動的にアーカイブされます。 |

4. クリーンな履歴システム モデル構成

このバージョンでは、システム モデルの初期化および保存時に厳密なスキーマの使用が開始されます。数値文字列、文字列形式の価格勾配、または以前のバージョンで保存されたフィールドが欠落していると、初期検証が失敗する可能性があります。アップグレード後、最初にドライランを実行して、処理する必要があるモデル構成を表示してください。ドライランではデータの変更やキャッシュの更新は行われません。

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

invalidSamples に手動処理が必要なデータがないことを確認した後、正式なクリーニングを実行します。

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

クリーニングでは、正当な数値文字列が数値に変換され、priceTiers 形式の文字列が配列に変換され、不正なオプションの数値が削除されます。必須の数値が不正または欠落している場合は、システムのデフォルト値が使用されます。LLM の maxContext/maxResponse/quoteMaxToken は 16000/16000/13000、埋め込みの defaultToken/maxToken は 500/3000、価格は 0 です。 functionCall はオプションのままで、埋め込みで欠落している weight は 0 に置き換えられます。

正式な実行では、データが均一に書き込まれ、システム モデル キャッシュが即座に更新されます。更新するレコードがない場合でも、ランタイム キャッシュは再構築されます。このインターフェイスは安全に再実行できます。再度予行運転すると、wouldUpdate は 0 になるはずです。現在の完全なモデル スキーマを通過できないレコードは書き込まれず、詳細はすべて invalidSamples で返されます。

5. HTTP ツールのデータを移行する

このリリースでは、手動モード HTTP ツールの配列パラメーターが標準の JSON スキーマに変更されます。アップグレード前に手動 HTTP ツールを作成した環境では、この移行を実行する必要があります。 OpenAPI モードの HTTP ツールは移行する必要がなく、スクリプトは自動的にスキップされます。

まずドライランを実行して、現在のアプリケーションと過去のバージョンの保留中のデータを表示します。ドライランではデータは変更されません。

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

結果を確認したら、正式な移行を実行します。

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

このスクリプトは、まず HTTP ツール タイプでアプリケーションをフィルタリングし、次にこれらのアプリケーションの appId に基づいて対応する履歴バージョンを移行します。 apiSchemaStr に存在しない手動モードのみが処理され、他のアプリケーションや OpenAPI モードは変更されません。移行はバッチで実行されるため、安全に再試行できます。返された結果の total.changedDocumentCount は、処理対象として見つかったドキュメントの数を示します。正式な実行後、再度ドライランを実行して、値が 0 であることを確認できます。

6. エージェント サンドボックス データを移行する (時間がかかります)

このバージョンでは、App Chat のエージェント サンドボックスが「会話ごとに 1 つのインスタンス」から「同じアプリと同じユーザーによって共有される 1 つのインスタンス」に調整されます。さまざまな会話のファイルは引き続き sessions/<chatId> ディレクトリにそれぞれ保存され、公開されたスキルは共有 projects ディレクトリに保存されます。

エージェント サンドボックスが以前に有効になっていた場合は、従来のワークスペースの移行を次の順序で完了する必要があります。エージェント サンドボックスが有効になっていない環境では、このセクションをスキップできます。

最初にドライランを実行して、beta6 サンドボックス フィールドの正規化と古いスキル デバッグ チャットのクリーンアップの保留中の数を表示します。ドライランでは、リソースの作成、オブジェクト ストレージへのアクセス、データの変更は行われません。

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

予行演習の結果を確認した後、正式な移行を実行します。正式な移行では、最初にベータ 6 正規化が実行され、残りの保留数がゼロになった場合にのみ、同じリクエストでワークスペースのアーカイブが継続されます。

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

failures に Sandbox source is missing or deleted のみが含まれており、対応するアプリまたはスキルが存在しないことが確認されている場合は、これらの残りのサンドボックスを明示的にスキップできます。

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false,"skipError":true}'

skipError デフォルトは false で、省略しても厳密な移行が維持されます。このスイッチは、ソースが欠落しているか論理的に削除されたグループ全体をスキップするだけであり、その中のサンドボックスはアーカイブ、削除、移行されません。スキップの詳細は、skippedCount および skipped を介して返されます。アーカイブ、オブジェクト ストレージ、プロバイダー、同時実行制御などの他のエラーによっても、移行がブロックされる可能性があります。

移行では、まず V4.15.0-beta6 の完全な事前ロジックが実行されます。つまり、古いサンドボックスの sourceType/sourceId を完了し、レガシー フィールドをクリーンアップし、属性を特定できない孤立したリソースを削除し、sourceType が欠落している古いスキル デバッグ チャットの 3 つのテーブル データと、プライベート バケットとパブリック バケットの古いプレフィックスをクリーンアップします。アプリと同じ ID を持つスキルはチャットのクリーンアップをスキップします。 2 種類のデータを再度記載すると、合計は normalization.pendingCount になります。数量が 0 でない場合、ワークスペース アーカイブには入力されません。ゼロ化後、すべての古いワークスペースを直接アーカイブし、古いコンピューティング リソースをクリーンアップしてからスキルを移行し、最後にアプリとユーザーごとにユーザーレベルのサンドボックスに集約します。アーカイブ段階で障害が発生する限り、インストール段階は開始されません。新しいサンドボックスは、ワークスペースのインストールが完了すると一時停止され、初めて使用するときに通常のプロセスに従って開始されます。スクリプトは安全に再試行でき、完了したアーカイブと移行は再実行されません。古いアーカイブと古い MongoDB レコードは、移行の完了後もバックアップとして保持されます。

normalization.pendingCount、normalizationBlocked、failedCount、failures、skippedCount、skipped の返された結果を確認してください。 normalization.pendingCount と failedCount が両方とも 0 であり、normalizationBlocked が false である場合にのみ、スキップされていないすべてのサンドボックス移行が完了したことを意味します。 skipped のレガシー レコードは保持され、移行されません。

🚀 新しいコンテンツ

  1. エージェント サンドボックスはアプリのユーザーレベルのインスタンスに変更されます。同じアプリと同じユーザーの複数の会話はサンドボックスを再利用し、独立したセッション ディレクトリを通じて各会話ファイルを分離します。
  2. サンドボックス HTML とファイルは、短期間の読み取り専用リンクを介した直接プレビューをサポートしており、プレビューのためにオブジェクト ストレージに繰り返しアップロードする必要がなくなりました。
  3. アプリ ワークフローは、サンドボックス プロバイダーまたはランタイム イメージが変更されると、ワークスペースを自動的にアーカイブおよび復元し、アップグレード プロセスは現在の実行中にサイレントに完了します。
  4. ワークフロー ツール ノードは、エージェントによる指定された入力パラメータの自動生成をサポートし、固定値、参照、ユーザー入力などの既存の設定を保持します。
  5. ChatAgent がツールを選択するときに、AI のパラメーターを生成するかどうかの手動指定をサポートします。
  6. ナレッジ ベース データは metadata のカスタマイズをサポートし、JSON メタデータは API、CSV、または Excel テンプレートを通じてインポートできます。このフィールドは検索結果とバックアップ エクスポートに保持されます。テンプレート インポートとバックアップ インポートはどちらも、q、a、index、および metadata ヘッダーを使用して、.csv および .xlsx ファイルをサポートします。 q、a、および metadata にはそれぞれ 1 つの列があり、index には任意の順序で複数の列を含めることができます。 Excel ファイルは単一のワークシートのみをサポートし、結合されたセルを含めることはできません。 CSV または Excel ファイルを正しく解析できない場合は、ファイル形式の例外が表示されます。
  7. 大きなファイルを分割してアップロードします。
  8. 管理者がシステム ツール キーを設定すると、そのキーは暗号化されます (設定されたキーと互換性があります)。
  9. スキルリストの空ステータス案内とスキル選択時の連携。
  10. ワークフロー アプリケーションのシステム構成は、キャンバスの左側にあるツールバーの独立した構成パネルに移動されます。このパネルは、新しいワークフロー アプリケーションを作成するときに自動的に開きます。
  11. 冒頭のステートメントは、事前に設定された複数の質問の独立した構成をサポートしており、ドラッグ アンド ドロップで並べ替えることができます。

⚙️ 最適化

  1. エージェント サンドボックスのライフ サイクルと移行プロセスを再構築します。作成、一時停止、アーカイブ、復元、削除、およびプロバイダーの切り替えは、同時実行保護、ブレークポイントの再開、冪等な再試行をサポートします。
  2. エージェント サンドボックスが使用できない場合、または現在のチーム パッケージでサポートされていない場合、App Chat はサンドボックス機能を自動的に無効にし、他のモデル、ツール、ナレッジ ベース、およびワークフロー ノードは引き続き実行できます。
  3. OpenSandbox の停止後も永続ボリュームを保持し、その後の実行中に再利用できます。一時停止およびアーカイブのしきい値は、環境変数による構成をサポートします。
  4. アプリとスキルはランタイム イメージのアップグレード ステータスを統合しており、スキル編集ページはアップグレード結果を継続的にポーリングできます。
  5. ネストされたパスの書き込み失敗を避けるために、サンドボックス ファイルを書き込む前に親ディレクトリを自動的に作成します。
  6. 古いワークフロー データやツール パラメーターなどの互換性の問題を最適化します。
  7. エージェントの質問 UI。
  8. リリース チャネル ページを再構成し、ネイティブ チャネルとサードパーティ チャネルごとにグループに表示し、各チャネルの構成数量を表示します。
  9. ツール マーケットのバッチ更新は、失敗したアイテムの表示、個別の再試行またはアンインストールをサポートし、インストールされているバージョンと更新ステータスの表示を改善します。
  10. ポータルページのクイックアプリケーション数の上限が 3 に調整され、上限を超えた過去の構成も互換になります。
  11. PDF パーサーは、実際のコンテンツの切り抜きを避けるために、固定エッジ トリミングではなく動的エッジ トリミングを使用します。

Highlights

  • Agent Sandbox is now shared per App/user — Multiple chats in the same App now reuse one Sandbox for the same user instead of creating one per conversation. Files remain isolated under sessions/<chatId>, while published Skills share projects. Short-lived read-only preview links eliminate duplicate object-storage uploads, and provider/runtime-image changes automatically archive and restore Workspaces. Sandbox failures or unsupported plans now disable only Sandbox, leaving models, tools, knowledge bases, and Workflow nodes operational.

  • Breaking: Sandbox deployment and data migration — The E2B provider is removed: switch to opensandbox or sealosdevbox, delete AGENT_SANDBOX_E2B_API_KEY, and retire AGENT_SANDBOX_DISK_MB and other E2B variables. In both fastgpt-app and fastgpt-pro, configure AGENT_SANDBOX_PREVIEW_PROXY_URL for HTTP(S), while AGENT_SANDBOX_PROXY_URL uses WebSocket(S); OpenSandbox also requires VM_VOLUME_NAME_PREFIX. Configure proxy PREVIEW_PORT if HTTP and WebSocket cannot share a port, and preferably use a separate origin because isolation is not enforced. Use matching fastgpt-app/fastgpt-pro v4.16.0 and agent-sandbox-proxy/agent-sandbox-volumn v0.3.0 images—mixed preview-protocol versions are unsupported. Any environment that previously enabled Sandbox must run /api/admin/4160/initUserSandbox with dryRun:true, then dryRun:false, checking normalization.pendingCount, failedCount, and normalizationBlocked. Use skipError:true only after confirming failures are missing/deleted sources; skipped Legacy records remain unmigrated.

  • Breaking: strict system-model configuration validation — Legacy numeric strings, stringified priceTiers, and missing fields can now fail initialization or save validation. Run /api/admin/dataClean/cleanSystemModelConfigs with dryRun:true, review invalidSamples, then execute with dryRun:false. Cleaning converts valid numeric strings to numbers and priceTiers strings to arrays, removes invalid optional numerics, and applies defaults: LLM maxContext/maxResponse/quoteMaxToken become 16000/16000/13000, Embedding defaultToken/maxToken become 500/3000, and price becomes 0. The formal run rebuilds the model cache even when nothing changes; records that still fail the complete Schema are not written.

  • Breaking: manual HTTP tool schemas require migration — Manual-mode array parameters now use standard JSON Schema. Environments with manually created HTTP tools must run /api/admin/4160/initHttpToolSchema with dryRun:true, then dryRun:false. The retryable migration also processes matching historical app versions; a follow-up dry-run should show total.changedDocumentCount as 0. Only manual tools lacking apiSchemaStr are changed—OpenAPI-mode tools and other applications are skipped.

  • Upgrade value and who can skip — This is a substantive release, not a re-tag. Upgrade for shared Sandboxes, dataset metadata with .csv/.xlsx template and backup imports, chunked large-file uploads, AI-generated workflow/tool parameters, and fixes for S3/DOCX filenames containing spaces or special characters. Security-sensitive deployments should also upgrade because system-tool secrets are encrypted and system-model initialization no longer exposes API keys, request URLs, or internal configuration. Sandbox-free installations can skip initUserSandbox, and OpenAPI-only HTTP-tool users can skip initHttpToolSchema; after a clean model-config dry-run, users who need none of these features or fixes can defer upgrading.

1. 更新 Agent-sandbox-proxy 环境变量（可选）

4.16.0 需要依赖 proxy 进行静态资源代理访问，如果网关支持 ws 和 http 在同一个端口，则可以只开放一个端口。如果不支持，可以通过设置 PREVIEW_PORT 来设置 http 访问端口。

# ws和http服务的端口
PORT=1006
# http服务的端口，可以覆盖 PORT
PREVIEW_PORT=1007

访问地址以 http:// 或 https:// 开头。单端口部署时，它可以与 AGENT_SANDBOX_PROXY_URL 指向同一域名和端口，但协议分别使用 HTTP(S) 和 WebSocket(S)。强烈建议配置的域名与 FastGPT 主站使用不同的 origin。同源部署会让这些脚本进入主站的同源安全边界，可能访问主站凭证或接口。系统当前不会强制检查 origin 是否隔离。

可以通过访问: https://{{host}}/health 来确认是否可访问。

4. 清洗历史系统模型配置

本版本开始在系统模型初始化及保存时使用严格 Schema。此前版本保存的数字字符串、字符串形式的价格梯度或缺失字段可能导致初始化校验失败。升级后请先执行 dry-run，查看需要处理的模型配置；dry-run 不会修改数据或刷新缓存：

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

确认 invalidSamples 中没有需要人工处理的数据后，执行正式清洗：

curl -X POST 'https://你的域名/api/admin/dataClean/cleanSystemModelConfigs' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

清洗会将合法数字字符串转换为 number、将字符串形式的 priceTiers 转换为数组，并删除非法的可选数字。非法或缺失的必填数字使用系统默认值：LLM 的 maxContext/maxResponse/quoteMaxToken 分别为 16000/16000/13000，Embedding 的 defaultToken/maxToken 分别为 500/3000，价格为 0。functionCall 保持可选，Embedding 缺失的 weight 补为 0。

正式执行会统一写入数据并立即刷新系统模型缓存；即使没有记录需要更新，也会重新构建运行时缓存。接口可安全重复执行；再次 dry-run 时，wouldUpdate 应为 0。无法通过当前完整模型 Schema 的记录不会写入，详情会全部返回在 invalidSamples 中。

5. 迁移 HTTP 工具数据

本版本将手动模式 HTTP 工具的数组参数改为标准 JSON Schema。升级前创建过手动 HTTP 工具的环境需要执行此迁移；OpenAPI 模式的 HTTP 工具无需迁移，脚本会自动跳过。

先执行 dry-run，查看当前应用及历史版本中的待处理数据。dry-run 不会修改数据：

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

确认结果后执行正式迁移：

curl -X POST 'https://你的域名/api/admin/4160/initHttpToolSchema' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

脚本会先按 HTTP 工具类型筛选应用，再根据这些应用的 appId 迁移对应的历史版本。仅 apiSchemaStr 不存在的手动模式会被处理，其他应用及 OpenAPI 模式不会修改。迁移按批次执行且可安全重试；返回结果中 total.changedDocumentCount 表示发现的待处理文档数，正式执行后可再次 dry-run，确认该值为 0。

6. 迁移 Agent Sandbox 数据(较慢)

本版本将 App Chat 的 Agent Sandbox 从“每个对话一个实例”调整为“同一 App、同一用户共享一个实例”。不同对话的文件仍分别保存在 sessions/<chatId> 目录中，已发布 Skill 则统一保存在共享的 projects 目录中。

如果此前启用过 Agent Sandbox，必须按以下顺序完成旧 Workspace 迁移。未启用过 Agent Sandbox 的环境可以跳过本节。

先执行 dry-run，查看 beta6 Sandbox 字段归一化和旧 Skill Debug Chat 清理的待处理数。dry-run 不会创建资源、访问对象存储或修改数据：

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":true}'

查看 dry-run 结果后执行正式迁移。正式迁移会先执行 beta6 归一化，并且只在剩余待处理数归零时，才在同一请求中继续 Workspace 归档：

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false}'

如果 failures 中仅包含 Sandbox source is missing or deleted，并且已确认对应 App 或 Skill 确实不再存在，可以显式跳过这些残留 Sandbox：

curl -X POST 'https://你的域名/api/admin/4160/initUserSandbox' \
  -H 'Content-Type: application/json' \
  -H 'rootkey: 你的ROOT_KEY' \
  -d '{"dryRun":false,"skipError":true}'

skipError 默认为 false，省略时保持严格迁移。该开关只跳过 source 已缺失或已软删除的整个分组，不会归档、删除或迁移其中的 Sandbox；跳过明细通过 skippedCount 和 skipped 返回。归档、对象存储、Provider 和并发控制等其他错误仍会阻断迁移。

迁移会先执行 V4.15.0-beta6 的完整前置逻辑：补齐旧 Sandbox 的 sourceType/sourceId、清理遗留字段、删除无法归属的孤立资源，并清理缺失 sourceType 的旧 Skill Debug Chat 三表数据及私有、公开 Bucket 旧前缀。与 App 同 ID 的 Skill 会跳过 Chat 清理。两类数据重新统计后合计为 normalization.pendingCount；数量不为 0 时不会进入 Workspace 归档。归零后直接归档全部旧 Workspace 并清理旧计算资源，再迁移 Skill，最后按 App、用户聚合到用户级 Sandbox。只要归档阶段存在失败，安装阶段就不会开始。新的 Sandbox 会在 Workspace 安装完成后暂停，首次使用时再按正常流程启动。脚本可安全重试，已完成的归档和迁移不会重复执行；迁移完成后会保留旧归档和旧 MongoDB 记录作为备份。

请检查返回结果中的 normalization.pendingCount、normalizationBlocked、failedCount、failures、skippedCount 和 skipped。只有 normalization.pendingCount 和 failedCount 均为 0，且 normalizationBlocked 为 false 时，才表示所有未跳过的 Sandbox 迁移完成；skipped 中的 Legacy 记录会保留且不会迁移。
