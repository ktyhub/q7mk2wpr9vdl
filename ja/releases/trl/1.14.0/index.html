trl v1.14.0

特徴

trl.losses はなくなりました: DPO、KTO、GRPO は独自のログプロブをストリーミングします

[!警告] from trl.losses import FusedLinearDPOLoss (または FusedLinearKTOLoss、FusedLinearGRPOLoss、FusedLinearJSDLoss) は機能しなくなりました。 v1.13 で導入されたモジュールは削除されました。 v1.13 はライガーの chunked_loss を目的地ではなくホールディングアクションとして trl.losses にベンダーしました (#7063)。抱えていた問題: これらのクラスは各トレーナーの損失計算を再実装するため、TRL はすべての式のコピーを 2 つ保持し、ドリフトをコピーしました。そのドリフトがバグのあった場所です。 GRPO の grad_norm はデフォルトのパスとは異なり、KTO は PEFT に基づく参照モデルを無視し、KTO クラスの重みと DPO label_smoothing はサイレントに削除されました。何よりも悪いことに、単純な DDP では、融合されたパスがアンラップ モデルで損失をもたらしたため、DistributedDataParallel のレデューサーが装備されることはなく、勾配が完全に減少することもありませんでした。すべてのランクが黙って独自の状態を維持していました。 修正するには、再実装を停止する必要があります。 DPO、KTO、および GRPO が融合パスから必要とするのは、選択されたトークンのトークンごとの log-probs だけです。TRL には、まさにそのための _ChunkedLogProbFunction がすでにありました。オンライン logsumexp で語彙をストリーミングし、バックワード パスで再計算します。各トレーナーは変更せずに backbone -> _ChunkedLogProbFunction -> its own existing loss code を実行するようになりました。完全なロジットは依然として実現されないため、各損失の 1 つの実装とメモリ勝利は保持されます。 13の制限は、損失がそれらの選択肢を表現できない形で書き換えられたためにのみ存在しました。ほとんどがなくなりました。use_liger_kernel=True を備えた DPO は、混合損失タイプ、f ダイバージェンス、および事前計算された参照対数確率を受け入れるようになり、GRPO はエントロピーとオフポリシー マスキングを取得します。まだ拒否されました: use_weighting、compute_metrics、lm_head の PEFT アダプター、即時学習 PEFT、および MoE 補助損失。 シングル H100、Qwen3-0.6B、bs=4、シーケンス 512: |設定 |中央ステップ |ピーク | | --- | --- | --- | | v1.13 融合、インライン参照 | 0.2243 | 7.05 GB | | v1.14 チャンク化されたインライン参照 | 0.2457 s (+9.5%) | 7.05GB | | v1.14 チャンク、precompute_ref_log_probs=True | 0.1971 s (-12.1%) | 4.83 GB (-31%) | 3 行目がポイントです。融合されたパスが事前に計算された参照ログ確率を完全に拒否したため、その構成は以前には存在しませんでした。 use_liger_kernel=True は引き続き動作し、変圧器を介して Liger のモデル カーネルを有効にします。 DPO、GRPO、KTO では、Liger の融合損失の代わりに TRL のチャンク対数確率パスが選択されるようになりました。

融合された Triton logprob + エントロピー カーネルが TRL で出荷されるようになりました

ロス ヘッドは TRL が所有する唯一のホット パスです。トランスフォーマーはすでにモデルの内部をカーネル化しており、デコーダーの後に起こることをハブ上でカバーするものは何もありません。 1 つの H100 (bf16、V=151936、H=4096、8192 トークン) では、selective_log_softmax と entropy_from_logits のコストは 12.8 ミリ秒、[8, 1024, 151936] よりも 2.32 GiB です。融合された Triton カーネルは、同様の処理を 0.89 ミリ秒 (およそ 14 倍) で実行し、置換される bf16 パスよりも fp32 参照の近くに到達します。 GRPO はこれをステップごとに 2 ～ 4 回実行します。 現在、trl.kernels でツリー内に存在し、CUDA、ROCm、および XPU でデフォルトでオンになり、フォールバックとして PyTorch 実装が使用されます。ハブから一時的にロードされました。このカーネルは純粋な Triton であり、実行時にコンパイルされるため、ハブは何も購入しませんでしたが、カーネルが機能するかどうかに関係のないバージョン ゲート、オフラインで失敗するダウンロード、kernels がインストールされている人向けの trust_remote_code=True、すべてをラップするサイレント except Exception: pass、および 13 件中 13 件のテストが CI でスキップされました。

壊れる

6 人の実験トレーナーが削除されました

GRPOWithReplayBufferTrainer、BCOTrainer、PRMTrainer、XPOTrainer、NashMDTrainer、および GSPO トークン トレーナーは trl.experimental から削除されました。 変わったのは、trl.experimental には常に保証がないということではなく、決定が文書化されるようになったという事実です。以前は、削除は一度に 1 つのプル リクエストごとに議論され、機能に到達する前にすべてのスレッドがポリシーを再議論していました。 #7182 は判決の重みを解決し、#7254 はそれをドキュメントに記載しました: 使用状況、外部の問題、実際に機能を実行している人々からのプルリクエスト、安定したトレーナーがすでにそれをカバーしているかどうか、メンテナンスコスト、下流の消費者、所有者、年齢。テストではなく判断に意図的に入力します。しきい値や通知サイクルはなく、数値は削除プル リクエストに残り、そこで確認できます。紙のインデックス エントリは、記述されているコードよりも長く存続します。 数字がそれを証明するものです。 BCOTrainer は、2 か月で 11 回の本格的なトレーニングに対応する、独自の参照モデルの処理、DeepSpeed の準備、トークン化、評価ループを実行する 1,600 行でした。これは、TRL が scikit-learn と joblib に依存していた唯一の理由でもあり、現在では両方とも pyproject.toml から削除されています。 GRPOWithReplayBufferTrainer は GRPO から _generate_and_score_completions を手動でコピーし、8 回のトレーニングで 616 行のうち 385 行が異なるようにドリフトしました。

修正

  • プレーン DDP では、KTO の勾配がすべて低減されることはありません。 compute_loss は、ZeRO-3 と FSDP に対してのみ分散ラッパーを介してリダイレクトされるため、プレーン DDP では、ラップされていないモデルで損失が発生し、DistributedDataParallel.forward() は実行されず、その減速機は装備されることはなく、すべてのランクが独自の勾配を静かに維持しました。 @qgallouedec 著、https://github.com/huggingface/trl/pull/7247
  • 入力テーブルがスライスされたときに重複したデータをラップしてパッキングします。 _pack_wrapped はスライスされたビューからの出力のサイズを調整しましたが、生の子バッファーから読み取ったので、スライスからではなくバッファーの先頭から再読み込みし、datasets.map(batched=True) はスライスされたテーブルを渡しました。 @qgallouedec 著、https://github.com/huggingface/trl/pull/6670
  • 一部のランクのみにログを記録する報酬関数が実行をハングまたはクラッシュしました。 GRPO と RLOO は各ランクが保持するキーをループし、キーごとに 1 つのコレクティブを呼び出したので、ランクは異なるコレクティブを呼び出しました。ランク 0 の log_metric だけが NCCL でハングし、log_extra は 1EB 割り当ての gather_object 内でクラッシュしました。 @behroozazarkhalili 著、https://github.com/huggingface/trl/pull/7382
  • 特別なトークン ID は、Trainer が実際に読み取る設定に到達するようになりました。そのため、トレイン時に再調整されなくなり、ユーザーが行っていない変更 (#7093 の一部) がログに記録されます: トレーナー内の EOS (#7127)、複合モデルのテキスト設定に書き込まれた (#7315)、報酬モデルのパッド トークン (#7318)、およびビジョン データセットに適用された要求されたパッド トークン(#7316、#7352)
  • https://github.com/huggingface/trl/pull/6769 の @behroozazarkhalili による蒸留および GOLD エントリ ポイントでデフォルトで教師を量子化しない
  • データセット キャッシュがノードローカルである場合、https://github.com/huggingface/trl/pull/7241 の @qgallouedec によってノードごとにデータセットを 1 回準備します
  • https://github.com/huggingface/trl/pull/7248 の @qgallouedec によるモデル構成から MoE 補助損失係数を読み取ります
  • https://github.com/huggingface/trl/pull/7213 の @albertvillanova によって呼び出し可能なクラスとして書かれた await 非同期報酬関数
  • https://github.com/huggingface/trl/pull/7195 の @kashif による OffloadActivations の 2 つのストリーム レースを修正
  • https://github.com/huggingface/trl/pull/7193 の @kashif によるストリーム モードでのオフロードされたアクティベーション ストレージのみ重複排除します。

trl v1.14.0

Features

trl.losses is gone: DPO, KTO and GRPO stream their own log-probs

[!WARNING] from trl.losses import FusedLinearDPOLoss (or FusedLinearKTOLoss, FusedLinearGRPOLoss, FusedLinearJSDLoss) no longer works. The module introduced in v1.13 has been removed.

v1.13 vendored Liger's chunked_loss into trl.losses as a holding action, not a destination (#7063). The problem it was holding: those classes reimplement each trainer's loss math, so TRL carried two copies of every formula, and copies drift. That drift is where the bugs were. GRPO's grad_norm differed from the default path, KTO ignored the reference model under PEFT, KTO class weights and DPO label_smoothing were silently dropped. Worst of all, under plain DDP the fused path ran the loss on the unwrapped model, so DistributedDataParallel's reducer was never armed and gradients were never all-reduced: every rank silently kept its own.

The fix is to stop reimplementing. All DPO, KTO and GRPO need from the fused path is per-token log-probs of the selected tokens, and TRL already had _ChunkedLogProbFunction for exactly that: it streams the vocabulary with an online logsumexp and recomputes in the backward pass. Each trainer now runs backbone -> _ChunkedLogProbFunction -> its own existing loss code, unchanged. One implementation of each loss, and the memory win is kept, because full logits are still never materialized.

Thirteen restrictions existed only because the loss had been rewritten in a form that could not express those options. Most are gone: DPO with use_liger_kernel=True now accepts mixed loss types, f-divergences and precomputed reference log-probs, and GRPO gains entropy and off-policy masking. Still refused: use_weighting, compute_metrics, a PEFT adapter on lm_head, prompt-learning PEFT, and the MoE auxiliary loss.

Single H100, Qwen3-0.6B, bs=4, seq 512:

| config | median step | peak | | --- | --- | --- | | v1.13 fused, inline ref | 0.2243 s | 7.05 GB | | v1.14 chunked, inline ref | 0.2457 s (+9.5%) | 7.05 GB | | v1.14 chunked, precompute_ref_log_probs=True | 0.1971 s (-12.1%) | 4.83 GB (-31%) |

The third row is the point: that configuration did not exist before, because the fused path rejected precomputed reference log-probs outright.

use_liger_kernel=True still works and still enables Liger's model kernels through transformers. In DPO, GRPO and KTO it now selects TRL's chunked log-probability path instead of Liger's fused loss.

A fused Triton logprob + entropy kernel now ships in TRL

The loss head is the only hot path TRL owns: transformers already kernelizes the model internals, and nothing on the Hub covers what happens after the decoder. On one H100 (bf16, V=151936, H=4096, 8192 tokens), selective_log_softmax plus entropy_from_logits cost 12.8 ms and 2.32 GiB over [8, 1024, 151936]. A fused Triton kernel does the same in 0.89 ms, roughly 14x, and lands closer to the fp32 reference than the bf16 path it replaces. GRPO runs this two to four times per step.

It now lives in-tree at trl.kernels and is on by default on CUDA, ROCm and XPU, with the PyTorch implementation as fallback. It was briefly loaded from the Hub; that was reversed because this kernel is pure Triton and compiles at runtime, so the Hub bought nothing while costing a version gate unrelated to whether the kernel works, a download that fails offline, trust_remote_code=True for anyone with kernels installed, a silent except Exception: pass wrapped around all of it, and 13 of 13 tests skipped in CI.

Breaking

Six experimental trainers removed

GRPOWithReplayBufferTrainer, BCOTrainer, PRMTrainer, XPOTrainer, NashMDTrainer and the GSPO-token trainer are gone from trl.experimental.

What changed is not the guarantee, which was always that trl.experimental has none, but the fact that the decision is now written down. Removals used to be argued one pull request at a time, with every thread relitigating the policy before it got to the feature. #7182 settled what the judgment weighs, and #7254 put it in the docs: usage, external issues and pull requests that come from people actually running the feature, whether a stable trainer already covers it, maintenance cost, downstream consumers, owner, and age. Deliberately inputs to a judgment rather than a test: no threshold, no notice cycle, and the numbers stay in the removal pull request where you can check them. A paper index entry outlives the code it described.

The numbers are what make the case. BCOTrainer was 1,600 lines carrying its own reference-model handling, DeepSpeed preparation, tokenization and eval loop, for 11 genuine trainings in two months; it was also the only reason TRL depended on scikit-learn and joblib at all, and both are now gone from pyproject.toml. GRPOWithReplayBufferTrainer had hand-copied _generate_and_score_completions from GRPO and drifted to 385 of 616 lines different, for 8 trainings.

Fixes

  • Gradients were never all-reduced for KTO under plain DDP. compute_loss redirected through the distributed wrapper only for ZeRO-3 and FSDP, so on plain DDP the loss ran on the unwrapped model, DistributedDataParallel.forward() never ran, its reducer was never armed, and every rank silently kept its own gradients. By @qgallouedec in https://github.com/huggingface/trl/pull/7247
  • Wrapped packing duplicated data when the input table was sliced. _pack_wrapped sized the output from the sliced view but read from the raw child buffer, so it re-read from the start of the buffer instead of from the slice, and datasets.map(batched=True) passes sliced tables. By @qgallouedec in https://github.com/huggingface/trl/pull/6670
  • A reward function logging on only some ranks hung or crashed the run. GRPO and RLOO looped over the keys each rank held and called one collective per key, so ranks called different collectives: log_metric on rank 0 alone hung on NCCL, and log_extra crashed inside gather_object with a 1EB allocation. By @behroozazarkhalili in https://github.com/huggingface/trl/pull/7382
  • Special token ids now reach the config the Trainer actually reads, so it no longer realigns them at train time and logs a change the user did not make (part of #7093): eos in the trainers (#7127), written to the text config for composite models (#7315), the reward model pad token (#7318), and the requested pad token applied to vision datasets (#7316, #7352)
  • Do not quantize the teacher by default in the distillation and GOLD entry points by @behroozazarkhalili in https://github.com/huggingface/trl/pull/6769
