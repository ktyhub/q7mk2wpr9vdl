FunASR 1.4.22

出典: dedefbf643289098e5473fa0cc6ce085e2e9533e / タグ v1.4.22。

修正

Deliver #3841: generate() に渡された merge_length_s は、構築時間/デフォルトのマージ長よりも優先されます。配信 #3833: 動的沈黙スケジュールは、蓄積されたチャンク時間ではなく、現在の音声セグメントの継続時間を使用してフレームごとに評価されます。固定しきい値のオプトアウトは引き続き利用可能です。

これは、事前トレーニングされた ASR の品質、Windows/NPU の受け入れ、または完全なリポジトリ スイートの結果を保証するものではありません。

個別にリリースされた funasr-onnx==0.4.8 および funasr-torch==0.1.6 には、独自のタグ、パッケージ、検証が付いています。このルート パッケージ リリースでは、それらは再公開されません。別途再現された非 LFR フロントエンド例外は、このリリースでは修正されていません。

検証範囲

  • 新しい候補リリース/README チェック: 45 件、スキップ 0 件。関連ドキュメント/パッケージ/リリース チェック: 104 件、明示的に記録されたスキップ 2 件。失敗やエラーはありません。
  • 実際にインストールされている候補ホイール: コールごと/構築/デフォルトのマージ長と動的/固定 VAD スケジューリングをカバーする 9 CPU ユニット契約。モック化された境界はハードウェア推論ではありません。 439 個のパッケージ ファイルと 13 個のエントリポイントすべてが、承認されたソースと一致します。
  • #3841/#3833 の 32 AutoModel および 24 VAD の実際の L20Z FP32 分析統合ケースを、封印された生のレシートを再ハッシュし、正確なソースを取り付けられたホイールにバインドした後、再利用しました。以前の個別の実行では、合計 216,521 の CUDA イベントが記録されました。これは、新しい GPU の実行、BF16 の実行、または事前トレーニングされた品質の検証ではありません。
  • 正確なリリースヘッドおよびマージメイン CI が実際のログ/アーティファクトとともに受け入れられました。最終タグのワークフローと新しくダウンロードされた Python ホイール/SDIST は、バイト/メタデータ/アーカイブ/ソース チェック、厳密な Twine、オフライン インストール、実際のインポート、および CLI チェックに合格しました。
  • 10 個の変更されていないランタイム アーカイブは、新しいアセット メタデータと既存のランタイム ソース リリースに対して新たにハッシュされた完全なキャッシュ バイトを再利用します。これらは再構築または再実行されませんでした。 SHA256SUMS は 12 個のペイロードすべてをカバーします。これはランタイム ハードウェアに関する新しい主張ではありません。
  • 完全なリポジトリ スイート、運用環境のアップグレード、Nano ベンチマーク、または導入/成長に関する主張は行われません。

  • 修正(ランタイム): https://github.com/modelscope/FunASR/pull/3838 の @tanishqbaweja による ContextualParaformer および SeacoParaformer のすべてのバッチをデコードします
  • 修正(ランタイム): https://github.com/modelscope/FunASR/pull/3839 の @LauraGPT により ONNX ホットワード バッチ修正を 0.4.7 としてリリース
  • 修正(ランタイム): https://github.com/modelscope/FunASR/pull/3840 の @LauraGPT により、Torch ホットワード バッチ修正を 0.1.5 としてリリース
  • fix(auto): https://github.com/modelscope/FunASR/pull/3841 の @MohammadHijjawi97 によってgenerate()に渡されたmerge_length_sを尊重します
  • 修正(vad): https://github.com/modelscope/FunASR/pull/3833 の @lingfengyao によるフレームごとのオフライン動的沈黙スケジュールを適用します。
  • 修正(ランタイム): https://github.com/modelscope/FunASR/pull/3842 の @BillVan1945 による空白および不完全な CMVN ファイルの処理
  • 修正(ランタイム): https://github.com/modelscope/FunASR/pull/3843 の @LauraGPT により ONNX CMVN パーサー修正を 0.4.8 としてリリース

FunASR v1.4.22

Highlights

  • Per-call merge length wins (#3841) — generate(merge_length_s=...) now takes precedence over the construction-time/default value, so chunk-merging behavior can be tuned per request without rebuilding the model. Watch out: pipelines that expected the constructor value to govern generate() will now see the call-site value override it — audit both paths when upgrading.
  • Frame-accurate VAD silence schedule (#3833) — the offline dynamic silence threshold is now evaluated per frame against the current speech-segment duration instead of accumulated chunk time, which changes where endpoints/silence splits land for dynamic VAD. The fixed-threshold opt-out remains for teams that need the old behavior.
  • Hotword batching fixed for Contextual/SeacoParaformer (#3838) — these models now decode every batch, so hotwords in batches beyond the first are no longer silently dropped — a genuine accuracy fix for batched contextual ASR. Shipped downstream as funasr-onnx 0.4.7 (#3839) and funasr-torch 0.1.5 (#3840).
  • CMVN parser hardening (#3842) — blank or incomplete CMVN files are now handled instead of failing, which matters if you ship hand-edited or partially downloaded model assets. Released downstream as funasr-onnx 0.4.8 (#3843) and funasr-torch 0.1.6 (#3844).
  • Runtime fixes live in separate packages — funasr-onnx==0.4.8 and funasr-torch==0.1.6 have their own tags, packages and verification and are not republished by the root funasr==1.4.22; bump them directly to pick up the hotword and CMVN fixes. The separately reproduced no-LFR frontend exception is also still unfixed here.
  • What this release does not claim — verification reused the 32 AutoModel and 24 VAD L20Z FP32 cases and 10 prebuilt runtime archives (rehashed, not re-executed); there is no new GPU/BF16 run, pretrained-quality, Windows/NPU, or full-suite validation. Treat 1.4.22 as a correctness/maintenance release and benchmark on your own hardware before adopting.

No breaking changes.

FunASR 1.4.22

Source: dedefbf643289098e5473fa0cc6ce085e2e9533e / tag v1.4.22.

Fix

Deliver #3841: merge_length_s passed to generate() takes precedence over construction-time/default merge length. Deliver #3833: the dynamic silence schedule is evaluated per frame using the current speech-segment duration, not accumulated chunk time; the fixed-threshold opt-out remains available.

This does not claim pretrained ASR quality, Windows/NPU acceptance or a full repository-suite result.

The separately released funasr-onnx==0.4.8 and funasr-torch==0.1.6 have their own tags, packages and verification. This root-package release does not republish them. The separately reproduced no-LFR frontend exception is not fixed by this release.

Verification Scope

  • New candidate release/README checks: 45 cases, 0 skips. Related docs/package/release checks: 104 cases, 2 explicitly recorded skips; no failures or errors.
  • Actual installed candidate wheel: 9 CPU unit contracts covering per-call/construction/default merge length and dynamic/fixed VAD scheduling. Their mocked boundaries are not hardware inference. All 439 package files and 13 entrypoints match the accepted source.
  • Reused the 32 AutoModel and 24 VAD real L20Z FP32 analytic integration cases from #3841/#3833 after rehashing their sealed raw receipts and binding the exact source to the installed wheel. Their separate prior runs record 216521 CUDA events in total. This is not a new GPU execution, BF16 run or pretrained-quality validation.
  • Exact release-head and merged-main CI were accepted with actual logs/artifacts. The final-tag workflow and the newly downloaded Python wheel/sdist passed byte/metadata/archive/source checks, strict Twine, offline installation, actual import and CLI checks.
  • The 10 unchanged runtime archives reuse complete cache bytes freshly hashed against new asset metadata and the existing runtime source release. They were not rebuilt or re-executed. SHA256SUMS covers all 12 payloads. This is not a new runtime-hardware claim.
  • No full repository-suite, production-environment upgrade, Nano benchmark or adoption/growth claim is made.
