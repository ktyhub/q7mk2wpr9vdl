エアフロー 2.10.0

重大な変更

データセットは非アクティブな DAG をトリガーしなくなりました (#38891)

以前は、DAG が一時停止または削除されても、受信データセット イベントは引き続き発生していました。 これをトリガーすると、一時停止が解除されるか DAG に再度追加されるときに DAG が実行されます。 ファイル。これは変更されました。 DAG のデータセット スケジュールを満たすことができるようになりました DAG がアクティブなときに発生するイベントによって。これは重大な変更ではありますが、 以前の動作はバグとみなされます。 時間ベースのスケジューリングの動作は、タイムテーブル部分も含めて変更されません。 「DatasetOrTimeSchedule」の。

try_number はタスク実行中にインクリメントされなくなりました (#39336)

以前は、ワーカーでのタスク実行の開始時に試行番号 (try_number) が増加していました。これには多くの理由から問題がありました。 1 つは、試行回数が増加するはずのないときに、つまり再スケジュールまたは延期から再開​​するときに増加したことを意味します。そしてそれはまた、 タスクがまだ開始されていないときの試行番号が「間違っている」。これら 2 つの問題の回避策は、多くの混乱を引き起こしました。 現在は代わりに、タスク実行の試行回数はタスクがスケジュールされた時点で決定され、実行中に変更されず、減分されることもありません。 したがって、タスクの実行後、観察される試行回数はタスクの実行時と同じままになります。 「新しい試行」がある場合にのみ、試行番号が再び増加します。 この変更の結果の 1 つは、ユーザーがタスクを「手動で」実行していた場合 (例: ti.run() directly, or command line airflow tasks run を呼び出した場合)、 試行回数は増加しなくなりました。 Airflow は、タスクが常にスケジューラによってスケジュールされた後に実行されることを前提としているため、これを重大な変更とはみなしません。

FAB Auth Manager の /logout エンドポイントが CSRF で保護されるようになりました (#40145)

既存のすべての「/logout`` endpoint's method in FAB Auth Manager has been changed from ``GET`` to ``POST」 AuthViews (AuthDBView, AuthLDAPView, AuthOAuthView, AuthOIDView, AuthRemoteUserView)、および セキュリティを強化し、不正なログアウトを防止するための CSRF 保護が含まれるようになりました。

OpenTelemetry Apache Airflow (#37948) のトレース。

この新機能により、Apache Airflow が 1) スケジューラのエアフロー システム トレースを出力する機能が追加されます。 トリガ、エグゼキュータ、プロセッサ 2) デプロイされた DAG 実行の DAG 実行トレース (OpenTelemetry 形式)。以前は、OpenTelemetry でメトリクスを発行するメトリクスのみがサポートされていました。 この新機能により、ユーザーが OpenTelemetry 標準を使用してトレース データを出力し、OTLP 互換エンドポイントに送信できるように、より豊富なデータが追加されます。

タスク フロー (@skip_if, @run_if) のデコレータ。タスクをスキップするかどうかを簡単に適用できます。 (#41116)

この機能はデコレータを追加して、タスクを簡単にスキップできるようにします。

複数のエグゼキュータを同時に使用する (#40701)

以前はハイブリッド エグゼキュータとして知られていたこの新機能により、Airflow は複数のエグゼキュータを同時に使用できるようになります。 DAG、または個々のタスクも構成可能 ニーズに最も適した特定のエグゼキューターを使用します。単一の DAG には、すべて異なるエグゼキュータを使用するタスクを含めることができます。エアフローのドキュメントを参照してください。 さらに詳しく。注: この機能はまだ実験段階です。詳細については、「documentation on Executor <https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/executor/index.html#using-multiple-executors-concurrently>_」を参照してください。

スカーフ ベースのテレメトリ: Airflow はテレメトリ データを収集しますか? (#39510)

Airflow は Scarf を統合して、動作中の基本的な使用状況データを収集します。デプロイメントでは、[usage_data_collection]enabled オプションを False に設定するか、SCARF_ANALYTICS=false 環境変数を設定することで、データ収集をオプトアウトできます。 詳細については、「FAQ on this <https://airflow.apache.org/docs/apache-airflow/stable/faq.html#does-airflow-collect-any-telemetry-data>_」を参照してください。

airflow 2.10.0

Highlights

  • Dataset schedules only advance while a DAG is active (#38891) — Events received while a DAG is paused or removed no longer satisfy its schedule when it returns. Event-driven integrations must account for this breaking change; time-based scheduling, including DatasetOrTimeSchedule, remains unchanged.
  • try_number is fixed when a task is scheduled (#39336) — It no longer increments at worker startup and stays constant through reschedule/deferral cycles; only a new try increments it. Custom runners using ti.run() or airflow tasks run must stop relying on automatic increments.
  • FAB logout now requires POST and CSRF protection (#40145) — All FAB authentication views changed /logout from GET to POST. Update custom templates, automation, bookmarks, and proxy rules to submit a valid CSRF-protected POST.
  • Multiple executors can be assigned per DAG or task (#40701, #38474) — A single DAG can mix executor types through the new executor field and operator parameter. The capability remains experimental, so validate executor/task compatibility before production adoption.
  • OpenTelemetry tracing joins metrics support (#37948) — Airflow emits scheduler, triggerer, executor, processor, and DAG-run traces to OTLP-compatible endpoints. Plan exporter configuration, sampling, and cardinality controls before enabling it broadly.
  • Usage telemetry is collected by default (#39510) — Scarf gathers basic operational usage data. Compliance-sensitive deployments should explicitly set [usage_data_collection]enabled = False or SCARF_ANALYTICS=false and verify the setting across all environments.

Significant Changes

Datasets no longer trigger inactive DAGs (#38891)

Previously, when a DAG is paused or removed, incoming dataset events would still trigger it, and the DAG would run when it is unpaused or added back in a DAG file. This has been changed; a DAG's dataset schedule can now only be satisfied by events that occur when the DAG is active. While this is a breaking change, the previous behavior is considered a bug.

The behavior of time-based scheduling is unchanged, including the timetable part of DatasetOrTimeSchedule.

try_number is no longer incremented during task execution (#39336)

Previously, the try number (try_number) was incremented at the beginning of task execution on the worker. This was problematic for many reasons. For one it meant that the try number was incremented when it was not supposed to, namely when resuming from reschedule or deferral. And it also resulted in the try number being "wrong" when the task had not yet started. The workarounds for these two issues caused a lot of confusion.

Now, instead, the try number for a task run is determined at the time the task is scheduled, and does not change in flight, and it is never decremented. So after the task runs, the observed try number remains the same as it was when the task was running; only when there is a "new try" will the try number be incremented again.

One consequence of this change is, if users were "manually" running tasks (e.g. by calling ti.run() directly, or command line airflow tasks run), try number will no longer be incremented. Airflow assumes that tasks are always run after being scheduled by the scheduler, so we do not regard this as a breaking change.

/logout endpoint in FAB Auth Manager is now CSRF protected (#40145)

The /logout endpoint's method in FAB Auth Manager has been changed from GET to POST in all existing AuthViews (AuthDBView, AuthLDAPView, AuthOAuthView, AuthOIDView, AuthRemoteUserView), and now includes CSRF protection to enhance security and prevent unauthorized logouts.

OpenTelemetry Traces for Apache Airflow (#37948).

This new feature adds capability for Apache Airflow to emit 1) airflow system traces of scheduler, triggerer, executor, processor 2) DAG run traces for deployed DAG runs in OpenTelemetry format. Previously, only metrics were supported which emitted metrics in OpenTelemetry. This new feature will add richer data for users to use OpenTelemetry standard to emit and send their trace data to OTLP compatible endpoints.

Decorator for Task Flow (@skip_if, @run_if) to make it simple to apply whether or not to skip a Task. (#41116)

This feature adds a decorator to make it simple to skip a Task.

Using Multiple Executors Concurrently (#40701)

Previously known as hybrid executors, this new feature allows Airflow to use multiple executors concurrently. DAGs, or even individual tasks, can be configured to use a specific executor that suits its needs best. A single DAG can contain tasks all using different executors. Please see the Airflow documentation for more details. Note: This feature is still experimental. See documentation on Executor <https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/executor/index.html#using-multiple-executors-concurrently>_ for a more detailed description.

Scarf based telemetry: Does Airflow collect any telemetry data? (#39510)

Airflow integrates Scarf to collect basic usage data during operation. Deployments can opt-out of data collection by setting the [usage_data_collection]enabled option to False, or the SCARF_ANALYTICS=false environment variable. See FAQ on this <https://airflow.apache.org/docs/apache-airflow/stable/faq.html#does-airflow-collect-any-telemetry-data>_ for more information.
