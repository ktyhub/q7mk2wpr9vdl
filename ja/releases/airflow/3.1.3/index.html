エアフロー 3.1.3

📦 PyPI: https://pypi.org/project/apache-airflow/3.1.3/ 📚 ドキュメント: https://airflow.apache.org/docs/apache-airflow/3.1.3/ 🛠 Release Note: https://airflow.apache.org/docs/apache-airflow/3.1.3/release_notes.html 🐳 Docker 画像: 「docker プル アパッチ/エアフロー:3.1.3」 🚏 制約: https://github.com/apache/airflow/tree/constraints-3.1.3

重大な変更

API サーバーコンテキスト (プラグイン、ログハンドラー) での接続と変数アクセスを修正(#56583)

以前は、API サーバー コンテキスト (プラグイン、ミドルウェア、ログ ハンドラー) で使用されるフックは「ImportError」で失敗していました。 SUPERVISOR_COMMS, because SUPERVISOR_COMMS はタスク ランナーの子プロセスにのみ存在します。 この問題は、3 つの個別のシークレット バックエンド チェーンを使用して自動コンテキスト検出を実装することで修正されました。 コンテキスト検出:

  1. Client コンテキスト (ワーカー内のタスク ランナー): SUPERVISOR_COMMS の存在によって検出されました
  2. サーバー コンテキスト (API サーバー、スケジューラ): _AIRFLOW_PROCESS_CONTEXT=server 環境変数で明示的にマークされています
  3. フォールバック コンテキスト (スーパーバイザー、不明なコンテキスト): どちらのマーカーも存在せず、最小限のセーフ チェーンを使用します バックエンド チェーン:
  • Client: EnvironmentVariablesBackend → ExecutionAPISecretsBackend (SUPERVISOR_COMMS 経由で実行 API にルーティング)
  • サーバー: EnvironmentVariablesBackend → MetastoreBackend (データベースへの直接アクセス)
  • フォールバック: EnvironmentVariablesBackend のみ (+ AWS Secrets Manager、Vault などの構成からの外部バックエンド) フォールバック チェーンは、アクセスする必要があるスーパーバイザー プロセス (タスク ランナーの開始前、ワーカー側) にとって非常に重要です。 リモートログ設定用の外部シークレットですが、MetastoreBackend は使用しないでください (ワーカーの分離を維持するため)。 アーキテクチャの利点:
  • ワーカー (スーパーバイザー + タスク実行者) は決して「MetastoreBackend」を使用せず、厳密な分離を維持します。
  • 外部シークレット バックエンド (AWS Secrets Manager、Vault など) は 3 つのコンテキストすべてで動作します
  • 外部バックエンドで接続が見つからない場合、スーパーバイザーは実行 API client にフォールバックします
  • API サーバーとスケジューラーはデータベースに直接アクセスして最適なパフォーマンスを実現します 影響:
  • GCSHook, S3Hook のようなフックがログ ハンドラーとプラグインで正しく動作するようになりました。
  • 既存のプラグインやフックのコード変更は不要
  • ワーカーはデータベースへの直接アクセスから隔離されたままになります (ネットワークレベルの DB ブロックは完全にサポートされています)
  • 外部シークレットはどこでも機能します (ワーカー、スーパーバイザ、API サーバー)
  • 安全な最小限のチェーンによる未知のコンテキストの堅牢な処理 参照: #56120 <https://github.com/apache/airflow/issues/56120>、#56583 <https://github.com/apache/airflow/issues/56583>、#51816 <https://github.com/apache/airflow/issues/51816>__

API サーバーでユーザー コードを実行した安全でない dag レポート API エンドポイントを削除 (#56609)

「/api/v2/dagReports」エンドポイントは、ユーザー DAG ファイルを API サーバー プロセスに直接ロードしたため、削除されました。 Airflow のセキュリティ アーキテクチャに違反します。このエンドポイントは UI で使用されておらず、既知のコンシューマーもありませんでした。 DAG によるレポートの読み込みには、代わりに airflow dags report CLI コマンドを使用してください。

airflow 3.1.3

Highlights

  • Context-aware secrets backends — API server and scheduler now read secrets directly from the metastore, while workers use the Execution API or environment/external backends and remain isolated from the database. Hooks such as GCSHook and S3Hook now work in plugins, middleware, and log handlers without code changes (#56583).
  • Breaking: DAG reports API removed — /api/v2/dagReports was deleted because it executed user DAG code inside the API server, violating Airflow’s security model. Any external consumers must migrate to the airflow dags report CLI command (#56609).
  • Credential-safe template errors — Jinja rendering failures no longer expose secrets, reducing credential leakage through error messages and logs (#57962). HITL tasks also now validate parameters correctly, preventing invalid inputs from slipping through (#58144).
  • Safer upgrades with NaN XCom values — Database migrations no longer fail when XCom contains NaN, including NaN represented in string values (#57893, #57614). Test upgrades against representative XCom data if your environment relies on custom serializers or older records.
  • Scheduler and trigger-rule corrections — The scheduler now uses the correct cached max_active_runs value, and task context/error handling is fixed for trigger-rule executions (#57959, #57892, #57786). Actual task concurrency may therefore change to match your DAG configuration.
  • Faster UI and task-instance APIs — Multiple fixes reduce slow page loads and task-instance list response times, including asset pages and DAG/task views (#58064, #57856, #57794). Connection testing and logout were also repaired (#57852, #58043).

Significant Changes

Fix Connection & Variable access in API server contexts (plugins, log handlers)(#56583)

Previously, hooks used in API server contexts (plugins, middlewares, log handlers) would fail with an ImportError for SUPERVISOR_COMMS, because SUPERVISOR_COMMS only exists in task runner child processes.

This has been fixed by implementing automatic context detection with three separate secrets backend chains:

Context Detection:

  1. Client contexts (task runner in worker): Detected via SUPERVISOR_COMMS presence
  2. Server contexts (API server, scheduler): Explicitly marked with _AIRFLOW_PROCESS_CONTEXT=server environment variable
  3. Fallback contexts (supervisor, unknown contexts): Neither marker present, uses minimal safe chain

Backend Chains:

  • Client: EnvironmentVariablesBackend → ExecutionAPISecretsBackend (routes to Execution API via SUPERVISOR_COMMS)
  • Server: EnvironmentVariablesBackend → MetastoreBackend (direct database access)
  • Fallback: EnvironmentVariablesBackend only (+ external backends from config like AWS Secrets Manager, Vault)

The fallback chain is crucial for supervisor processes (worker-side, before task runner starts) which need to access external secrets for remote logging setup but should not use MetastoreBackend (to maintain worker isolation).

Architecture Benefits:

  • Workers (supervisor + task runner) never use MetastoreBackend, maintaining strict isolation
  • External secrets backends (AWS Secrets Manager, Vault, etc.) work in all three contexts
  • Supervisor falls back to Execution API client for connections not found in external backends
  • API server and scheduler have direct database access for optimal performance

Impact:

  • Hooks like GCSHook, S3Hook now work correctly in log handlers and plugins
  • No code changes required for existing plugins or hooks
  • Workers remain isolated from direct database access (network-level DB blocking fully supported)
  • External secrets work everywhere (workers, supervisor, API server)
  • Robust handling of unknown contexts with safe minimal chain

See: #56120 <https://github.com/apache/airflow/issues/56120>, #56583 <https://github.com/apache/airflow/issues/56583>, #51816 <https://github.com/apache/airflow/issues/51816>__

Remove insecure dag reports API endpoint that executed user code in API server (#56609)

The /api/v2/dagReports endpoint has been removed because it loaded user DAG files directly in the API server process, violating Airflow's security architecture. This endpoint was not used in the UI and had no known consumers. Use the airflow dags report CLI command instead for DAG loading reports.
